# MAWS charter

> **Parent:** root, the project's standing purpose (this document is the root spec; `CLAUDE.md` points here). **Level name:** P0, the first release. Children dispatch per their grain hint in §12, each carrying its section as its spec; each child's artifact (execution document, ledger, findings) opens by citing this document, its child id, and the parent pin (the git blob hash of this file at dispatch).

MAWS is a codename. This document is the chartering design for the project: what it is for, what was decided and why, what ships first, and how the pieces fit. It is the root spec: the approved design up top and, from §10 on, the decomposition into children. Research behind every claim lives in `research/`.

Status: approved by the owner on 2026-09-28 after one critique round and the protocol probe; routed to decomposition into milestone specs. Decisions marked **D-n** were made with the project owner in the brainstorming rounds; decisions marked **S-n** are technical calls made by the design and can be overridden.

## 1. Purpose

**Higher purpose.** A general, state-of-the-art desktop workstation for supervising AI coding agents, built on the Claude Code engine. It replaces the Claude Code terminal UI, Claude Desktop's Code surface, and the Codex desktop app for its owner and a few colleagues. It is general at the base; the owner's own workflows (doperpowers, ptc, workflows, teams, orchestration ideas) arrive later as plugins on top of a strong base, not as hardcoded features. (D-5)

**What it is for.** Two scenes carry equal weight from the first release. (D-6)

- Scene A, supervision: several projects, many live sessions, approvals and questions pending, workflows running with many agents. Open MAWS and know within seconds where you are needed.
- Scene B, depth: one session with the diff panel open, a file tab beside the transcript, a terminal in the session's worktree, the browser showing the dev server the agent started.

**Benchmarks.** Codex desktop sets the interaction bar; it is the app generally praised for UX. Claude Desktop matters as Anthropic's own integration of the same engine we use, so it tells us how the engine is wired, what the app must own around it, and which behaviours the engine already expects from a host. (D-14)

**What it must not be.** Not "VS Code with a chat sidebar" and not "a chat app with a file tree". Not a thin client: the wire does not carry everything, and the app owns a real state layer around the engine. Not a fork of Claude Code: the engine binary stays unmodified. Nothing in either benchmark app actively annoys the owner; the terminal power features the GUIs drop (queued messages, `!` bash mode, keybindings, slash palette) are enhancements to add, not faults to fix. (D-13)

## 4. Architecture

### 4.1 Process model

- **Renderer** (sandboxed, context-isolated): React 19 with the React Compiler, Tailwind v4, Radix primitives. Talks to the main process through a small validated command/event IPC schema. Never receives the shell, git or engine bridge directly.
- **Main process** (privileged): owns windows, layout persistence, notifications, the session index, the git service, and the IPC boundary.
- **Utility processes**: the engine host (engine adapter, process table and filesystem state service, so a renderer reload or window crash never touches a session), the PTY host (node-pty), and a heavy-work worker for transcript indexing and search.
- **Engine child processes**: one `claude` process per live session. Launch line: `-p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --include-partial-messages --forward-subagent-text --replay-user-messages --include-hook-events --setting-sources user,project,local`, plus cwd, additional directories, model, effort, permission mode (auto by default, per D-18, inherited from settings), and resume or fork flags. The binary is an absolute pinned path, never resolved through PATH. The environment is constructed, not inherited: at startup the app captures the login shell's environment once (as Claude Desktop's shell-path worker does) and passes an allowlist (PATH, HOME, locale, `CLAUDE_*`, `ANTHROPIC_*` and the tool paths the engine needs), because a Dock-launched app has none of the shell's exports. The allowlist excludes the variables a parent Claude session injects into its children (`CLAUDE_CODE_SESSION_ID`, `CLAUDE_PID`, the messaging socket and token, `CLAUDE_CODE_USER_DIALOG_TIMEOUT_MS`), which the second probe pass had to scrub to get a clean child. It adds `CLAUDE_CODE_FORK_SUBAGENT=true` so fork-type subagents work as in the terminal, and by default (D-19) the gateway variables `ANTHROPIC_BASE_URL`, the marker `ANTHROPIC_AUTH_TOKEN` and `ENABLE_TOOL_SEARCH=true` (Claude Code turns MCP tool search off behind a base URL it does not consider first-party), after a relay health check; a direct launch is the exception, chosen per session or offered when the relay is unreachable, and changing it restarts the process. A direct launch cannot rely on unsetting them: the owner's `settings.json` `env` block routes the session regardless of the process environment, so the direct launch also passes `--settings` with empty-string `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN` (verified in pass 2). `CLAUDE_CODE_SUBAGENT_MODEL` is a per-session launch choice shown in Session info, because it silently decides which model workflow and subagent workers run on. It passes the owner's `ANTHROPIC_DEFAULT_*_MODEL` overrides through when present, since they are part of the routing setup; Session info shows which overrides are in effect. The host's `initialize` sets `perTaskStopAffordance: true` (otherwise Stop kills every background agent and workflow), `supportedDialogKinds`, `workspaceTrust` attestation, and dialog expiry "never" through flag settings so unanswered dialogs and elicitations wait for the human. Version-pinned; the app records the engine version per session. (S-1)

### 4.2 Engine adapter

The adapter owns the raw NDJSON transport rather than wrapping the public SDK's `query()`. Reason: the public 0.3.259 `Query` type lacks wrappers for most 2.1.283 control requests, and two writers on the same stdin is a race. The adapter implements: initialize handshake with hook registration; request ids, cancellation and timeouts; `can_use_tool`, `hook_callback`, `elicitation`, `request_user_dialog` and AskUserQuestion round trips; outgoing control requests (interrupt, set_permission_mode, set_model, effort, get_usage, get_context_usage, get_settings, list_permission_rules, get_hooks_listing, get_memory_dialog, get_skills_dialog, get_sandbox_dialog, get_workspace_diff, export_conversation, rewind_conversation, fork_conversation, rename_session, generate_session_title, stop_task, reload_plugins, side_question); stdin frames (`user`, `bash_command`, `keep_alive`); unknown-field retention and unknown-frame journaling. (S-2)

Events are normalised into a graph keyed separately by session id, message uuid, API message id, tool-use id, task id and agent id. Child-agent traffic is attributed by `parent_tool_use_id` and never flattened into the parent conversation. Raw frames are journaled per session for replay and for compatibility diagnosis. (S-3)

Verified against the real binary by the protocol probe (`spikes/protocol-probe/`, fixtures under `fixtures/`), which corrects the spec-derived picture in these places:

- No host handshake is required; the first `user` frame starts the session and `system/init` arrives per turn, carrying the command, skill, agent and model lists the palette needs (`get_skills_dialog` returned empty, so the palette reads `init`).
- AskUserQuestion reaches the host as a `can_use_tool` request flagged `requires_user_interaction`; the answer is an allow with `updatedInput.answers` keyed by question text. There is no separate question request type to implement.
- A denied tool produces an error `tool_result` and `result.permission_denials`; no `system/permission_denied` frame appears on this path. `permission_suggestions` can be absent. `updatedPermissions` rules with session destination take effect immediately.
- Child agents deliver their assistant and user records with `parent_tool_use_id`, per message, with no token-level `stream_event` for children. Subagent panels therefore update per message, and their full transcripts are the `agent-*.jsonl` files on disk. Both children in the probe ran in the background even when only one asked to.
- `--resume` restores the session but never replays history over the wire; the transcript view is rebuilt from the JSONL by the filesystem service. `fork_conversation` answered "unsupported" in a routed session; forking is the `--fork-session` launch flag.
- `bash_command` output comes back as replayed `user` records tagged as bash input, stdout, stderr and exit code, bracketed by command-lifecycle frames; the replayed-row renderer keys on those tags, and the app-owned queue does not count that lifecycle as a released user message.
- Interrupt with `cancel_queued` cancels queued messages explicitly; the running turn ends as `error_during_execution` with terminal reason `aborted_streaming`, and the next turn resumes. `bash_command` yields replayed user frames tagged as bash input, stdout, stderr and exit code.
- All thirteen structured reads succeed. `get_usage` returned session accounting but no rate-limit windows, so the status line takes its 5h and 7d windows from ClaudeUsage, with the engine's windows as the fallback for unrouted sessions.
- The first pass ran routed through the gateway with empty settings sources. The second pass (`spikes/protocol-probe/findings-pass2.md`, fixtures under `fixtures/pass2/`) repeated the usage, models and fork reads unrouted and ran everything else under the owner's real settings. `fork_conversation` is unsupported unrouted too. `list_models` carries `supportsAutoMode` and `supportsFastMode` per model; Haiku cannot hold auto mode and silently runs in `default`. Unrouted model turns are still unverified because the owner's login had expired; the rerun is a tracked residual.
- Memory under the owner's settings: one idle session is 270 to 420 MB for the whole process tree (stdio MCP servers are about 40 percent), about 550 MB at peak during a tool call; three idle sessions each settle near 270 MB. A parked prewarmed spare is 255 MB, `claim_session` takes under 100 ms, and a cold initialize takes 0.8 to 1.1 s with the owner's settings.
- Auto mode through the gateway: the effective mode is `auto` in the initialize response and every `system/init`; `get_status` reports the server classifier lane enabled with no refusal, dialog or warning. Allow verdicts are visible after all: each `stream_event` `message_delta.safeguard_results` entry carries `evaluated/not_flagged` keyed by tool-use id, while allows produce no control frames. Only ask rules escalated (`can_use_tool` with `decision_reason_type: "rule"`); no classifier denial was provoked, so the `automode-*` denial kinds remain unobserved. A GPT-routed main takes the local classifier lane instead (Sonnet 5 requests through the gateway, counted as usage; verified by a peer probe, recorded in the Decision Log).
- Workflows: `task_started` (`local_workflow`), an `async_launched` tool result, `task_progress.workflow_progress` snapshots with phase and per-agent entries, `task_updated`, `task_notification`, and then an engine-initiated follow-up turn that produces a `result` the host never asked for. Background completions do the same. The adapter accepts unsolicited turns and never releases a queued message into one.
- Rewind: `rewind_conversation` needs `last_seen_user_message_uuid` or answers `stale_target`; success returns `prefillText` and emits no reset frame, so the host truncates its own view and pre-fills the composer. The JSONL is never truncated: the engine appends a `last-prompt` anchor with `rewound: true` and the next turn branches from the older leaf. `rewind_files` is disabled without file checkpointing.
- Hooks: host callback hooks round-trip through `hook_callback` with no deadline and `additionalContext` accepted, but emit no `hook_started`/`hook_response` frames and are absent from `get_hooks_listing`; only settings and plugin hooks do. MCP elicitation arrives as `elicitation` with `mode: "form"` and the accepted content reaches the server. No producer of `request_user_dialog` was reachable. Dialog expiry set through `--settings` is effective.
- `perTaskStopAffordance`: without it an interrupt kills a running background workflow; with it the workflow survives. Background Bash survives either way. The interrupted foreground call is tagged `user-rejected`, not `interrupted`, so the pairing of `user-rejected` with an aborted terminal reason renders as an interruption.
- Trust: unattested project rules are ignored with a stderr notice; `set_cwd` into an untrusted directory returns `needs_trust` and succeeds on retry with trust accepted; `workspaceTrust` in `initialize` records trust and loads the rules at once; trust persists in `~/.claude.json`.
- Grants: a session grant is lost on `--resume` and `apply_flag_settings` restores it with no re-prompt. A matching ask rule outranks any allow rule, so a prompt raised by an ask rule offers no "always allow" scope. A host deny is reported as `permission-rule`.
- Resume while live: against a print-mode holder there is no engine guard, and both processes write sibling branches into one JSONL; against a `claude --bg` holder the resume is refused with an attach or fork message. MAWS detects holders itself and opens them read-only.
- `bash_command` alone never reaches the model's context; the following non-querying `user` echo does, and that echo yields an empty `result` with a null terminal reason which the adapter treats as a receipt, not a turn.

Further engine semantics the design commits to:

- **Queue ownership.** MAWS owns the message queue: queued messages persist in the index and one is released into the engine when a turn ends; Steer bypasses the queue with immediate priority. The engine's own in-memory queue is not used for user drafts, so the queue survives process exit.
- **Plan approval** has three outcomes: implement (allow, which restores the pre-plan permission mode), clear context and implement (deny, set the mode, start a fresh turn seeded with the plan), keep planning (deny with feedback). A conversation reset renders as a transcript boundary row.
- **`!` bash mode** sends the `bash_command` frame and then a non-querying `user` frame carrying the command and its output so the result lands in the model's context as it does in the terminal (verified: without the echo the model never sees the output). **`#` memory** has no wire mechanism; it is an app-side append to the memory file chosen from `get_memory_dialog`.
- **Revisable log.** Retractions (`supersedes`, retracted message uuids), refusal fallbacks, `compact_boundary` and compacting status are events the renderer applies, not ignores; the transcript is not append-only.
- **Edit and resubmit** forks by default; rewind is an explicit action.

### 4.3 Filesystem state service

One watcher plus append-aware JSONL tailers over the engine's own store (respecting `CLAUDE_CONFIG_DIR`):

- `projects/<slug>/<session>.jsonl` main transcripts, titles, compaction and rewind anchors; used for resume backfill, replay and terminal-started sessions.
- `projects/<slug>/<session>/subagents/agent-*.jsonl` and `.meta.json` for child transcripts and lineage.
- `tool-results/` for spilled large results, lazily loaded.
- `tasks/`, `workflows/` snapshots and journals, `sessions/<pid>.json` for live peers, `jobs/` for detached sessions, `teams/`.
- Settings, agents, skills, plugins and commands files for the palette and the management widgets.

The service never writes into engine-owned locks, mailboxes or journals. The main JSONL is append-only even across rewind: the engine appends a `last-prompt` anchor with `rewound: true` and the next turn branches from an older leaf, so the current transcript is the parent chain from the latest leaf, not the file in order. The tailer follows that chain and re-anchors by uuid rather than byte offset, which also covers a truncating writer if one ever appears. Whole-file sidecars (`.meta.json`, `custom-title.json`, workflow snapshots) are parsed with retry because their write atomicity is unknown. Spilled results are loaded by the path the engine reports, never by a derived name, because background shell output and regular spills use different keys. The project slug is derived from the realpath of the directory, not the path as passed, so the service maps a session id to its files by discovery (`projects/*/<session>.jsonl`) or by realpath-then-slug, never from a cwd string, and reads the session's directory from the first JSONL record. Live holders are read from `sessions/<pid>.json`.

### 4.4 Session service and index

SQLite (Node's built-in `node:sqlite`, which Electron 44 exposes with FTS5; better-sqlite3 ships no prebuild for its ABI) holds only what the engine does not: project list and membership, app session records (app id ↔ engine session id, title and its provenance, worktree, pin, archive state, last-seen cursor for unread), attention items, drafts, replay fixtures. Two things the cut placed here live elsewhere (amended 2026-09-28 on C4's parent-impact): queued messages and grant snapshots live in the engine host's per-session state file under `userData`, because the engine host releases the queue at turn end and cannot reach main's database; tab and panel layout lives in main's `layout.json`. Both survive process exit, which is what the placement was for. (S-4)

Session process policy is memory-budgeted, never a fixed timer. A process stays live while it has a running turn, background tasks or workflows, session-scoped permission grants, connected MCP servers per `mcp_status`, or a held peer message. Idle processes without those are candidates for exit only under budget pressure, least recently used first. The budget counts the whole process tree under the engine pid (stdio MCP servers included) and is visible in Session info; measured under the owner's settings, an idle session is 270 to 420 MB and a tool call peaks near 550 MB. When a process with session grants must exit, the app snapshots the grants it issued (it sees every `updatedPermissions` it sent) and re-applies them on resume through `apply_flag_settings` (verified: the restored grant is not re-prompted). Exit never silently discards background work: the user is asked. Until the budget policy ships (C12), engine processes never exit on their own: only archive, quit, or an explicit stop ends one. (S-5)

### 4.5 Git and worktree service

Read-only status, branch, diff and log through the `git` binary, with a repository watcher for the toolbar and pinned summary. Worktrees are ordinary trusted `git worktree add` under `<repo>/.claude/worktrees/`, the same convention the engine's own `EnterWorktree` uses, so both coexist. Cleanup distinguishes archive, remove a clean checkout, discard uncommitted changes and delete a branch. (S-6)

### 4.6 Permission broker

A request router with one pending table for tool permissions, questions, plan approvals, dialogs and elicitations. Each item carries request id, session, agent, tool, input preview, engine suggestions and the scope options the engine accepts. Items move through pending, delivered, and confirmed or retired. "Delivered" is not an alarm state: a long command keeps an item delivered for minutes with nothing wrong. There is no acknowledgement frame for a `control_response`: delivery truth is a successful write to a live process; the only failure signals are a stdin write error and process exit; confirmation is the earliest frame carrying the item's tool-use id (tool result, tool progress, hook frame, denial record). If the process exits with delivered or pending items, the broker raises one Needs-you entry at exit time from its own table ("session interrupted, N approvals lost"); on resume the engine retires the dangling tool calls itself and will not ask again, so nothing is re-pended. Abort from the engine removes an item. A prompt raised by an ask rule (`decision_reason_type: "rule"`) offers no "always allow" scope, because an ask rule outranks any allow rule. An interrupt reports the aborted call as `user-rejected`; the broker pairs that with the turn's aborted terminal reason and records an interruption, not a refusal. Items are the source of the Needs-you section. (S-7)

### 4.7 Libraries

Streamdown for streaming markdown with its KaTeX, Mermaid and Shiki plugins; TanStack Virtual with end anchoring for the transcript; `@git-diff-view/react` for review; CodeMirror 6 for file tabs (P1 editing); Tiptap for the composer; terminal renderer behind an adapter, ghostty-web first with xterm.js and its WebGL addon as the fallback, decided by the spike in §7; electron-vite, electron-builder and electron-updater; Zustand stores fed by IPC events, TanStack Query for request-response data.   - *Reattach checkpoint*: a raw byte tail cannot restore a terminal: the modes a program set before the tail (bracketed paste, the alternate screen, application cursor keys, mouse tracking) are gone, and the tail's first byte can split a UTF-8 or escape sequence (reproduced on xterm.js 6.0.0). A reattach therefore has two sources: a checkpoint, the emulator's own serialised state (`@xterm/addon-serialize` 0.14.0: screen, scrollback, cursor, attributes, the alternate screen and the persistent modes; not cursor visibility, the title or mode 2026) stamped with the stream offset it reflects, sent as `pty.checkpoint` and kept in the host per pty; and the ring's bytes after that offset. The addon keeps no parser or decoder continuation and restores SGR mouse encoding (`?1006`) as the default (verified in a real round trip), so checkpoints are boundary-safe: taken only where the parser is in its ground state with no escape or partial UTF-8 sequence pending (a pure byte-level stream tracker over every written chunk; a checkpoint due mid-sequence waits for the next boundary, and `pagehide` sends none then), with the mouse tracking and encoding modes `?1000`, `?1002`, `?1003`, `?1006`, focus reporting `?1004` and any other the round-trip test finds missing captured by the tracker and re-applied explicitly after `serialize()`'s output. The renderer checkpoints every live terminal on `pagehide` and a dirty one 500 ms after its last parsed byte, never on a byte count (serialising 10,000 lines must not run per chunk in a flood). Contract: exact when the ring reaches back to a boundary-safe checkpoint (guaranteed after a `pagehide` checkpoint by the ring-size invariant of *PTY stream and flow control*): the state, then the replay, nothing reset or redrawn; lossy whenever exactness cannot be established: the emulator is reset, the tail written from the byte after its first line feed, the tab's bar reads "Reconnected; earlier output was not kept", and a full-screen program is nudged to repaint. `TerminalInfo.reconnect` records which path ran. Alternatives rejected: a byte-count cadence, which serialises exactly when the UI thread is busiest; a host-side emulator, a second parser to keep in step. Binding on the two-path contract, boundary safety with the explicitly re-applied modes, and the notice, advisory on mechanism.
  - *Keyboard*: with a terminal focused, every key without ⌘ goes to the pty (Esc, ⇧Tab, Tab, ⌃C, ⌃D, ⌃L, ⌃R, arrows, ⌥-chords with `macOptionIsMeta: true`), except ⌃Tab and ⌃⇧Tab, which stay the app's tab cycle; every ⌘ chord goes to the app, except ⌘C (copy selection; nothing when there is none), ⌘V (paste), ⌘A (select all), which the terminal handles. ⌘K remains the command palette (§5.8): clearing a terminal is ⌃L or the tab's context menu.
