C12 M6: the two resumes that stalled at `initialize` (evidence for a later C3 spike)
====================================================================================

Context: the pre-run's §10.4 test (e2e/c12-prerun.spec.ts, `ensureLive`) resumes the deep session from its sidebar row
(right-click › Resume, C10's resume path) on the owner build (dist/mac-arm64/MAWS.app, unsigned, launched by Playwright
with MAWS_E2E=1). Twice in four such launches the process never answered (the M6 report's "two of five" counted the session's first launch in §10.2, which was not a resume; four is the right count): the test waited 120 s for `ready`, then the
app's cleanup stopped it. The session was the deep session: app id 229dfe14-3cff-4326-876b-6d29f1743cce, engine session
d13ad955-203c-4748-9494-53bfa54788d5. Times below are UTC (the run logs print local time, UTC−7).

What survives: the scratch root /private/tmp/maws-c12-prerun-1790765266 was removed at the end of M6, so neither wire
journal survives and no copy was taken. What follows is from the journal rows printed during the run (quoted in the
M6 executor's working log), the Playwright run logs (/private/tmp/c12-m6-run-104.log and -104c.log, Playwright output
only, no engine output), and the host's source. No owner data is in this file.

The launches that did not stall
-------------------------------
Of the four row Resumes of this session, two answered at once: v6fsandq (the second §10.4 run, about 11:01) and
65dpzxou (the fourth, about 11:09). Other resumes in the pre-run, of other sessions, did not stall either: the §10.1
north `-p` session from its row in §10.5 (ready in 1.96 s) and the released X1 by Send in §10.6 (ready in 0.92 s). Between stall 1 and the second run, a terminal `claude -p --resume` of the same
session (below) also ran. No pattern was found in the gap since the previous exit (stall 1: 96-157 s; stall 2: 62-70 s;
the passing 65dpzxou followed the stalled moyz6bsv's exit by about 3 min, with the standalone probes between).
