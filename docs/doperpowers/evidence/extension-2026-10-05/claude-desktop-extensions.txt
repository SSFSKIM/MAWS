1. SIDE CHATS — THREE DIFFERENT MECHANISMS
User experience: “Start a side chat,” “Send to side chat,” “Ask in side chat,” “Clear side chat,” and “Close side chat”; a staged selection can seed the question. The side-chat panel can pop out. Empty/unsupported copy includes “Open a session to use side chat” and a request to update Claude Code on the computer running the session. This is a quick question alongside the main work, but the newer BTW path is a real child session, not merely the older scratch conversation.
Legacy contract: user opens panel -> LocalSessions.startSideChat(sessionId), then sendSideChatMessage(sessionId,text), interruptSideChat, stopSideChat. The host keeps one helper in sideChats keyed by main session id, requires a cliSessionId/transcript, and starts a separate SDK query through spawnReadOnlyFork. It emits side_chat_error/side_chat_closed and streams the helper answer. Read/Grep/Glob are the narrow fallback; broader parent-tool declarations are guarded by a host PreToolUse read-only policy, default permission mode and other preconditions. The host follows model/permission changes and handles recovery; the engine executes the forked query. There is no special startSideChat engine control request evidenced here.
BTW contract: LocalSessions.startBtwChild(parentSessionId, optional sessionId, openedBy='question'|'selection'|'bare') invokes forkSession(...,{userFork:true,btw:true}), returning {status:'started',sessionId} or disabled/failure. UI puts that child into sidePane='session' with title and btwSince, then sends an ordinary message to it. spawnedFrom.btw/sideSession/userFork bind lineage. The UI falls back to the legacy panel when creation fails or times out; it closes a late unused child. Do not infer that this full child has the legacy helper's read-only restrictions.
Offered side session: a separate agent-initiated workflow. acceptSideSessionOffer(sessionId,taskId,accept) validates an outstanding offer/waiter, records target/worktree/picks, answers the waiter, saves parent metadata, and prepares a child. Local/cloud selection exists; auto-starts are capped at ten since the last user message. The agent then supplies the brief with start_session/proposal_id; an accepted fresh offer requires prompt plus background, rather than silently forking all context. App owns proposal UI, acceptance, lineage, worktree/cloud placement and lifecycle; engine/model proposes and runs the work.

2. FILES SENT TO THE USER — LOCAL OUTPUT VIEWERS, NOT AUTOMATIC UPLOADS
User experience: output paths from completed Write and SendUserFile rows can become clickable deliverables; recognized paths in prose are also collected. File panels support images, audio/video playback, text editing, and document preview, rather than only source-code diffs. Native document preview is capability-gated; cloud conversion is separately policy-gated. A preview may need a connected VM for non-PDF document conversion. Direct open-in-default-app and reveal-in-folder are separate actions.
Contract: user/output-card selection -> LocalSessions.showSessionFilePreview(sessionId,filePath,bounds,consumerId?,targetWindowId?). Host resolves/transfers the file and mounts the preview in the requested bounds. readSessionPanelMediaAsDataUrl(sessionId,filePath), readSessionPanelDocumentAsDataUrl and getSessionPanelMediaStreamUrl use a contained session path, extension/MIME rules and size limits. The non-panel read/stream methods are separate; do not assume they have identical admission rules. Media URLs are host-issued with mtime cache busting.
Editing: LocalSessions.writeSessionFile(sessionId,filePath,contents,expectedHash?) is a HOST filesystem operation, not an engine Write tool call. It checks admitted roots and real-path containment, blocks protected destinations and hook-manager package.json changes, compares SHA-256 when supplied, and returns ok/hash, conflict/currentHash, denied, or failure. The viewer can therefore edit while detecting stale content.
SendUserFile verdict: consumer-side wiring IS present in the Code transcript/output collector. Producer-side availability as a local Claude Code tool is NOT established: no SendUserFile registration or local-session-manager dispatch was found in the main-process JS; main-process occurrences are cloud/remote-file guidance and Dispatch transcript processing. Thus “Desktop can render a SendUserFile result” is supported; “ordinary local sessions expose SendUserFile” is not. A local session can deliver a file via Write plus a local path without that cloud tool. Remote/cloud SendUserFile returns file_uuid, with device_commit_files used separately to write it onto the user's device.
Ownership: model/engine produces bytes and tool results; host owns containment, file IO, rich viewers, native child-view lifecycle, downloads/conversion and conflict-safe human editing. No new engine control request is required for those viewers.

3. COWORK, DOCUMENTS AND ARTIFACTS — SEVERAL STACKS, NOT ONE TOOL
Cowork is a separate agent-mode/session product with local/remote execution, spaces, selected user files, memory and scheduling. LocalAgentModeSessions and CoworkSpaces manage those lifecycles. Its reusable outputs include rich working documents and persisted HTML artifacts; the wider web frame also identifies Document, Presentation and Design objects. Do not equate a generated .pptx attachment with a first-class frame presentation, or an HTML artifact with a local working document.
Documents: the host-injected workflow says new working documents use doc_create under the working-documents directory with .cd extension and appear in Documents with a rich editor and DOCX/PDF/Markdown exports. Existing .docx files are explicitly an exception in the inspected instructions. The doc_* family includes create/edit/resolve_changes/export/read/outline/search/check_layout. DocumentFunnel owns scratch-root creation, base64 writes with optional ifMatchSha256, ingest/conversion/export, and injectDocumentContext; workingDocumentsChanged updates the UI. This is an app/tool-runtime document service, not ordinary transcript markdown.
Local persisted HTML: host MCP tools create_artifact(id,html_path,...), update_artifact, list_artifacts, verify_artifact and screenshot support self-contained HTML. The model writes a file first. The host stores versions/metadata, opens the artifact sidebar, captures console/bridge diagnostics and screenshots, and can permit declared connector calls through window.cowork.callMcpTool(name,args). Imported shared artifacts are read-only; making an editable copy is distinct. These artifacts survive the originating session.

Web artifact frame: source shows metadata for Document/Presentation/Design, version controls, comments, sharing, and export choices including editable .pptx versus slides as pictures. Design-system sharing/default selection is its own UI. Frame chrome, presentation/export UI and comments are web-app concerns; creation, conversion and cloud storage services are not implemented by Claude Code alone. This audit establishes the visible product and client boundary, not the full server-side slide/design generation implementation.
Comments and “Send to Claude”: the frame saves comments through /api/frame/comments/...; delivery uses a distinct /to-claude path, with edit/delete/thread actions and delivery failures. “Comment saved/posted, but not sent to Claude” is a real state, not success. In this macOS build the equivalent close path uses AppleScript, checks the document's full path against the expected session-opened file, and distinguishes workbook/document/presentation for Excel/Word/PowerPoint. Therefore “macOS Office control goes through claude-native” would be an overclaim. Native exports alone are not proof of platform invocation.

11f. Spaces, task orchestration and host UI-navigation tools
CoworkSpaces adds project-like spaces with pinned files/context and session membership, separate from Code's baseline session list. Host session-management tools can start linked work and backlog suggestions; model-driven host navigation is explicit: mcp__ccd_view__show_pane shows a diff/file/terminal/PR/tasks/plan/artifacts pane instead of merely describing where the user should click. These are extension-grade orchestration/context capabilities even when their resulting panes are baseline. Host owns navigation validation and child/session records; engine supplies tool intent. Connector-owned delegation and cloud project collaboration exist in the broader web bundle, but their full server contracts were outside this local Desktop inventory.
