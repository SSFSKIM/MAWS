1. IN-APP BROWSER, SIDEBAR, ANNOTATIONS AND SHARED CONTROL
What the user sees
A real browser page hosted inside the app, associated with a conversation/tab rather than a screenshot-only tool result. Navigation includes Back, Forward, Reload, open link in new tab/external browser, Inspect and Comment (browserSidebar.contextMenu.*). Explicit offline, DNS, timeout, refused and certificate error states live under browserSidebar.loadError.*; zoom controls under browserSidebar.zoomBanner.*.
Comment mode selects an element, area, multiple anchors or a site's virtual object. The overlay offers Add, Send, Save, Delete, Cancel and Adjust; browserSidebarCommentOverlay.placeholder = “Add a comment…”. Annotation controls include layout/spacing/type/color changes, not just textual notes. browserSidebarCommentOverlay.snapshotFailed = “Screenshot unavailable; you can still annotate this object”.
Site-provided prompts are visibly attributed: browserSidebarCommentOverlay.pagePromptExplanation = “The webpage suggested the following prompt. ChatGPT will receive only the text you submit.” Separate review-prompt, review-metadata and combined review instructions exist. browserSidebarDesignEditor.annotationControls.previewSharingWithWebsiteDomain explicitly says selections reach the website while adjusting controls, before sending.
Chrome/Atlas import is real, not just extension onboarding: browserProfileImport.nux.title.chrome = “Import data from Chrome”; modal categories include cookies, saved passwords and history. Host also supports Chrome extension import, requiring explicit allowUnverifiedExtensions confirmation, and rejects extensions for unsupported sources. Managed allowExternalBrowserSettingsImport can disable import. This imports into the in-app browser; it is separate from controlling an already-running external Chrome profile through the browser extension.

Agent/UI contract and ownership
Agent-side browser-desktop runtime drives a peer-authorized native pipe. Electron owns live WebContents, tab/session routing, page debugger/CDP bridge, visibility/viewport, download permission, cursor presentation and navigation-policy checks. The IAB API exposes getTabs/createTab/focusTab, attach/detach, executeCdp, cached expressions, allowDownload, getInfo/getUserHistory, markTab/moveMouse, releaseSessionControl and turnEnded. Session/turn metadata associates actions with the correct conversation; CDP events, detach, page and download events travel back through the pipe. These are native-pipe API operations, not app-server methods.
The browser-session-registry tracks owner WebContents, browserConversationId, Codex session IDs, pending local-work routes and per-session backends. It rebinds routes as work/chat ownership changes and releases browser/MCP-app control at session end. Human and agent use the same underlying page/tab: human navigation/comment UI and runtime CDP resolve to registered WebContents, rather than two browser copies. Exact input-arbitration behavior under simultaneous human/agent input was not live-tested.
The renderer/main bus includes browser-sidebar-command and browser-sidebar-runtime-* events over codex_desktop:message-from-view / message-for-view; the page preload also uses codex_desktop:browser-sidebar-runtime-message and codex_desktop:browser-page-event. Annotation submit captures body, anchor metadata, page URL, optional images/design changes and optional cropped screenshot. Main emits browser-sidebar-direct-comment with conversationId/browserTabId/sessionId and the normalized comment; the thread UI turns that context into a chat submission. Thus an element reference is structured annotation context plus optional visual evidence, not a magical DOM handle inside the model.
Policy is host-owned: codex_desktop:get-browser-annotation-api-policy returns enabled, siteAnnotationFeaturesEnabled, siteAnnotationPermissionGranted, isAgentControllingBrowser and isAnnotationModeActive; non-main-frame callers get disabled defaults. codex_desktop:get-browser-webmcp-policy returns enabled plus maxTools/maxTotalDescriptorBytes. WebMCP tool-invocation activity carries session_id, turn_id, tabId, toolName and optional parentCallId into host activity state. Website-provided annotation behavior and WebMCP are distinct capabilities, not blanket privileged access.
Page screenshots use WebContents.capturePage; “copy screenshot” writes an Electron clipboard image and emits success/failure messages. Annotation screenshots have separate capture/crop/state validation. Browser-use PiP tracks thread/tab presentations and active counts; clicking the native presentation focuses its source. Remote hosted video frames have codex_desktop:remote-hosted-pip-video-frame. PiP is a supervision surface, not a second agent browser.

2. COMPUTER USE: ELECTRON HOST CONTRACT ONLY
What the user sees
Computer use plugin/app access, desktop app picker, permissions/setup, captures and running activity. computerUse.label = “Computer use”; computerUse.nativeApps.mac.title = “Mac apps”; computerUse.nativeApps.desktop.loading = “Loading desktop apps…”. The baseline research already documents the per-app approvals, service policy and native interaction model; those are not re-invented here.
Contract and ownership
Electron provisions/configures the managed computer-use service and the signed runtime bridge; exposes the computer-use native pipe to the node_repl/cua runtime; validates native-pipe requests; resolves sessions/turn metadata; coordinates config and host permission UX. Native-pipe outer methods include ping, close and request; request wraps the actual service method/params/codexTurnMetadata, and end_turn has explicit lifecycle handling.
Electron does NOT itself implement AX traversal or input synthesis. Those belong to @oai/cua / @oai/sky and the native service. Host integration supplies the service pipe and host-services pipe in generated runtime configuration; @oai packages remain a separate runtime layer.
Capture is separately host-orchestrated: requests have requestId, bundleIdentifier, animationTarget and permissionRequestId, with cancellation/timeouts and deduplicated permission association. Main calls capture worker method “start”; updates are routed as computer-use-capture-updated, including failure. Native capture bridges are platform-specific. This capture-to-composer path is not identical to an agent calling getScreenshot in its REPL.
Anchors: M:9772–9864 (pipe request dispatch); M:10469–10656 (runtime/pipe configuration); M:16938–18771 (managed service host); M:64103–64355 (capture lifecycle); M:186507–186685 (native capture bridge).

3. MCP APPS SANDBOX AND DYNAMIC APP TOOLS
What the user sees
An interactive app/widget, not merely tool-result text. It can appear as conversation app activity and open into a thread side-panel tab. mcpApp.activity.status distinguishes Opening, Opened and Couldn’t open; mcpApp.thumbnail.status distinguishes app error, tool cancelled and paused. mcpApp.openInApp / openInNamedApp expose “Open in app” / “Open in {app}”. An app can draft a prompt or request a new chat; mcpApp.newThreadCreated.sourceTitle = “{appName} has started a new chat”.
Contract and ownership
App resources include HTML with MCP Apps profile MIME type text/html;profile=mcp-app. The MCP UI protocol declares ui/initialize, ui/notifications/initialized, tool-input/tool-input-partial/tool-result/tool-cancelled, size-changed, host-context-changed, ui/message and ui/open-link. UI messages can append a composer draft (send:false) or request a new/current-chat follow-up; host checks view capabilities and user-facing confirmation paths rather than blindly executing arbitrary messages.
Electron supplies an isolated sandbox guest, preload, origin/init-ID validation, transferred ports, protocol/network restrictions and permissions. Top-frame navigation must match the registered source URL; downloads are blocked; most permissions are denied, with narrowly implemented exceptions such as local-network sandboxes and gesture-bound sanitized clipboard writes. codex_desktop:mcp-app-sandbox-guest-message and ...-host-message are the sandbox IPC channels.
Do not confuse connect-app-host with the MCP server protocol: the renderer creates a MessageChannel, transfers a port through a connect-app-host postMessage/preload IPC handshake, and obtains host capability services over RPC. This is a general app-host bridge also used outside MCP widgets.
Separately, dynamic-app-tools-native-pipe accepts JSON-RPC tools/list, tools/call, tools/cancel and taskWorkspace/prepare. tools/call includes callerSource (codex/chatgpt), callId, hostId, namespace, threadId, tool and turnId. Peer authorization plus nonce/signing identity protects the bridge. This lets an agent runtime initiate host-provided app tools; it is not proof every third-party MCP tool executes in Electron. Runtime owns model decisions/tool invocation; host owns tool adapters, widget surface and resource isolation.

Electron separately owns bundled/internal plugin acquisition and platform/browser setup. Runtime owns actual skill discovery/config use and MCP lifecycle; UI owns discovery, installation progress, account-choice/permission presentation and entry into chat.

5. PULL REQUESTS ROUTE AND THREAD ↔ PR BINDING
What the user sees
The prior MAWS research's PR inbox/detail/review model still exists in this build: /pull-requests, provider/account-aware PR search, detail activity/reviews/checks/comments and code-review surfaces. Current code adds explicit failing-check repair handoff and PR fix-automation integration. pullRequestsPage.codeReview.showFileTree / hideFileTree and pullRequestsPage.detail.openCommentInReview expose review navigation; comments/replies are first-class rather than a generated markdown report.
Contract and ownership
PR detail has a binding lookup: if a thread is already associated, reuse it; otherwise create a conversation titled from PR title or owner/repository#number and store {hostId, threadId}. “Fix failing checks” filters failing checks and attaches repair instructions to that bound thread. The instructions include PR URL/base/head/repository and explicitly require verifying the checkout, cloning into the chat workspace if necessary, and not modifying an unrelated checkout. This is stronger than an unstructured link in chat.
PR data has github-cli and github-connector provider branches, account-aware query keys and partial-result states (checks/reviews can be incomplete independently). This is host/UI integration with GitHub plus normal thread execution, not a demonstrated app-server “pullRequest/*” protocol. Agent work is initiated when the user opens chat/repair/review; PR fetching/filtering and thread association are app-owned. Exact persistence storage for this binding was not traced, so durable cross-install binding is not claimed.
Anchors: renderer/app/pull-request-route-fbdf404be8d8.js:1310,3470 (route); renderer/app/pull-request-detail-query-3b840bde3e4c.js:2882–2938 (binding and repair prompt); same file:1200,1616,1644 (description/checks/activity); A:207930–207990 (provider/partial/account model); same detail chunk:368–382 (fix-automation integration).

6. AUTOMATIONS, SCHEDULED RUNS AND HISTORY
What the user sees
Two related families ship: local Codex work automations and hosted ChatGPT Scheduled tasks. Do not collapse them into one scheduler. Prior MAWS research already covers the local editor's prompt, project/environment, model/effort and notification fields, run history and sidebar. Current sidebar still uses automations.runs.status: Running now / Run failed / No update from this run / Run completed.
Hosted strings add automations.scheduled.page.title = “Scheduled”, subtitle “Ask ChatGPT to schedule tasks, set reminders, or monitor for updates”, Active/Paused/Completed filters, next-run/recently-updated/name sorting, resume/pause, unread results, and interval/wall-clock cadences. Webhook task copy includes “Task is paused. Resume to process pending events.” Run-history debugging, latest update/no-updates and failure states are separate from task definitions.
Contract and ownership
Host local scheduler calculates next runs from rrule, distinguishing wall_clock and interval; selects/upgrades models, prepares project/worktree execution and read state, creates/resumes threads and starts turns. It marks turnTrigger as automation_cron_<id>. App-server receives ordinary thread/start and turn/start through its client, not a magic renderer timer pretending to be a session. Approval policy is explicitly derived for unattended runs and can become “never” under the scheduled-run conditions; runtime still executes the task under the supplied configuration.
Renderer/main messages include automation-runs-updated and inbox-automation-runs-mark-all-read; “automation-create” is an app fetch-handler command, not established here as an app-server method. Hosted run history uses HTTP /automation/{automation_id}/execution_threads; main's habitat-automations integration has /automation/<id> requests. Cloud scheduling is therefore not solely Electron-owned. UI owns run/task presentation, unread/archive workflow and editing; local host owns wake/run orchestration; cloud service owns hosted scheduling; agent owns task work.
Anchors: M:11444–11520,12274–12299,12451–12488 (schedule/thread/turn); renderer/app/sidebar-6d07d2c68de2.js:1272 (run states); A:618439,650214 (update/create commands); renderer/app/cloud-automation-detail-panel-2beb250b15c1.js:427 (hosted execution history); M:47487 and B:64003–64076,66710 (hosted API and actual app-server thread/turn methods).

7. ARTIFACTS, DOCUMENTS, SLIDES, SHEETS AND SPACES — PRESENT
What the user sees
This build is not limited to code files. It ships artifact preview/annotation, DOCX/PDF panels, editable artifact-session surfaces, slide/sheet resources, native-file handoff, Library and Space destinations. artifactAnnotationComment.placeholder = “Describe a change or ask a question”; artifactAnnotationBatch offers annotation count, Send, Working, Accept all, Undo and latest-change review. artifactTab.preview.downloadCopy = “Save as…”; artifactSession.downloadTitleMenu = “Download”; artifactHandoff.uploadCopyDescription.space says a copy is uploaded to the Space. Space create-menu labels include Canvas, Slide, Sheet, Site, Space and Start from template. These are actual renderer components, not merely accidental occurrences of “workspace” or source-code “document”. Availability is still gated/not live verified; bundled ChatGPT Spaces must not automatically be labeled a universally enabled Codex feature.
Contract and ownership
The Electron artifact-session-host-service connects using runtime-supplied socketPath/token; it is a distinct viewer/host contract, not evidence of app-server documents.* methods. Its methods include host.ping, documents.read/resolveArtifactRef/appendUpdate, subscriptions.open/close, viewer.markDirty, viewer.flush, assets.read and outputs.publishNativeSnapshot. Subscriptions bind artifactRef and threadId, stream updates, append viewer changes, read assets and flush before handoff.
Capability checks require external-documents-v1, presentation v2, or external-whiteboards-v1; optional image/visualization upload and schema capabilities are negotiated. Host exposes externalDocument.capture/apply/readAsset/uploadAsset/uploadImage/uploadVisualization callbacks for externally owned documents. Native metadata in this service explicitly accepts presentation/spreadsheet; that narrow schema should not be generalized to mean all PDF/DOCX previews use this same editable protocol.
Host owns viewer lifecycle, connection reconciliation, native open targets/downloads, snapshot publication and handoff. Runtime/document service owns artifact identity/state and negotiated document operations; UI owns selection/annotations/edit requests. Space/library organization is an additional cloud-facing surface; its complete backend contract was not traced here.

9. OTHER EXTENSION-GRADE SURFACES
9a. Realtime voice and avatar overlay
The avatar is an interactive desktop surface with activity, notification expansion/reply/stop, task mute, microphone mute, output mute and follow-up input—not just decoration. avatarOverlay.statusRunningSubtitle = “Thinking”; avatarOverlay.muteMicrophone = “Mute microphone”; avatarOverlay.muteOutput = “Mute voice chat”; avatarOverlay.replyNotification = “Reply to {title}”.
Host realtime coordinator claims a voice owner, publishes/subscribes snapshots, controls microphone/output/dictation, transfers sessions between surfaces, captures screen context and records real delegations. Control payloads include set-dictation-active, set-microphone-muted, set-output-muted, transfer, record-real-delegation and terminate. These are coordinator/control messages, not established app-server JSON-RPC names. User starts voice/controls it; realtime voice can delegate work to chats. Host owns unique active ownership and surface transfer; voice/model service owns speech/reasoning. Exact upstream realtime transport was not traced.

9d. Open-in targets and language servers
These are extension-grade host services even when their visible entry point lives in an existing file/diff panel. Open-in discovery resolves installed editors/terminals/native handlers and launches the chosen target; artifact native handoff reuses host target discovery/openPath. Do not count the ordinary file panel again as a new feature.
Language-server manager exposes capabilities, hover and locations; lazily finds/starts per-language sessions and owns runtime installation/lifecycle. Hover uses the LSP HoverRequest with document/position; locations supply navigation. The human editor UI initiates these requests, not a model tool call. Host owns server executables/host selection/process lifecycle and failure handling; LSP server owns semantic analysis. Specific UI-string IDs for open-in/LSP actions were not conclusively isolated in this pass, so none are invented.
