1 What the owner saw

In the Archive “hi”? confirmation sheet, pressing Archive produced the red error “no such column: removed_at”. The copy promised to end the engine process, hide the session from its project, and retain the transcript.

Root cause of that SQL error: the session index lacks a column that the archive operation writes. The known cause of this schema shape is an already-released v1 migration amended in place. However, ac8724a6 and the stated master head already contain an unconditional-on-needed-column startup repair for every supported post-v1 schema version. No archive-specific bypass of that repair was found. The strongest explanation for seeing this today is an older/stale main-process build actually running, not a missing migration in current master. That runtime explanation is a hypothesis, not a verified fact: this research did not inspect the running executable, logs, or the owner's database.

Its repair SQL is ALTER TABLE sessions ADD COLUMN removed_at TEXT. Statement caching is lazy inside each Db; no archive statement is prepared at module load or before repair. Searching production connection sites found no alternate MAWS index opener in the engine host or a worker. Browser import has separate SQLite staging databases, unrelated to sessions. The only second connection in the index opener is for a future user_version greater than the known version: the probe closes, the file reopens read-only, and every Db operation is blocked with “index unavailable: user_version … is newer …”, not “no such column”. A repair failure closes the connection and throws; it cannot quietly return an unrepaired usable Index.

Coverage of historical shapes

/Users/new/Developer/GitHub/MAWS/src/main/index/migrations.ts:118 declares REPAIRS for version 1, table sessions, column removed_at, definition TEXT. /Users/new/Developer/GitHub/MAWS/src/main/index/db.ts:163–174 selects a repair when repair.version <= existing user_version AND the column is absent; it enters the transaction when either pending migrations OR missing repairs exist.

- Pre-amendment database at user_version 3: repaired first, then migrations 4 and 5 apply.
- Such a database carried forward to version 4: still repaired, then version 5 applies.
- Such a database carried forward to current version 5 without the column: repaired even though there are NO pending migrations. The repair is not guarded by pending.length alone.
- Fresh database created after the v1 amendment but before the repair: the column already exists; repair correctly does nothing. If “created by that build” instead means that build reused an older database, the preceding cases apply.
- Versions 1 and 2 are also covered by the same predicate. A genuinely fresh version-0 database gets the column from v1. A future version beyond 5 is intentionally unavailable, not repaired. Arbitrarily corrupted/manually mis-versioned schemas are not a supported upgrade history.

/Users/new/Developer/GitHub/MAWS/src/main/index/index.test.ts:186–289 already covers pre-amendment v3 with existing rows, preservation of the owner's archive, disappearance/reappearance, fresh databases, idempotent reopening, repair-before-later-SQL, and rollback when a pending migration fails. It does not explicitly cover a missing-column database already at the current version with no pending migration, nor the archive action on that historical database. Those are useful narrowly targeted additions. These tests were read, not executed.

What current logs can and cannot distinguish

First correlate one main-process launch with its archive failure. Relevant literal lines are:
- “[index] <path>: added sessions.removed_at, which migration 1 was amended to create after this database had applied it” (db.ts:182). Emitted only after successful COMMIT. Its presence proves that opener committed the repair; absence does not prove old code, because a database already containing the column is silent.
- “[ipc] session.archive failed” followed by the Error/stack (router.ts:123). The stack should identify Db.prepare/update and SessionStore.write/update, confirming the operation described above rather than guessing from sheet text alone.
- “[index] fs.sessionChanged could not be applied: no such column: removed_at” (source.ts:221, 418–427). Repeated discovery failures corroborate the same historical missing-column problem.
- “[index] <path>: user_version N is newer than this app knows (5); the index is unavailable this run and the file is left as it is” (db.ts:148) identifies the different, intentionally blocked future-schema case.

These are main-process console messages. The detached supervisor's host.log and “[hosts] connected to supervisor pid … build …” describe the engine host, not proof that main has this repair. Its build identity hashes the engine-host bundle (/Users/new/Developer/GitHub/MAWS/src/main/hosts/identity.ts:1–25), so an old kept supervisor does not explain an unrepaired main index. No main-process git-revision startup stamp or persistent main-log setup was found in the inspected startup/build wiring; current logs alone cannot conclusively identify main's source commit.

A likely operational mechanism is a rebuilt bundle on disk while the old main process remains alive, or launching a different installed copy. /Users/new/Developer/GitHub/MAWS/src/main/index.ts:120–122 explicitly keeps the app running after all windows close. /Users/new/Developer/GitHub/MAWS/src/main/files/profile-lock.ts:5–15 quits a second instance before opening its stores. Thus closing the window or attempting another launch need not run the new opener. This possibility is grounded in code, but the owner's actual process/build remains unverified. If the successful repair line and this archive error genuinely occur in the same main lifetime against the same database, stale-build attribution is insufficient: capture that contradiction before inventing another schema change.
