C — Sessions should feel available, not depend on process residency
Read-only source research, 2026-10-08. MAWS head verified with git log: 5dcddd70. No builds, tests, app launches, owner MAWS data, Chrome profiles, or relay access. Reference source versions: Claude Desktop 2.16120.0; Codex chatgpt-26.928.40906; T3 Code 148e6dee.

1 What the owner saw and what they want

The message is mostly an accurate description of MAWS's implementation, but the wrong product abstraction. A sidebar entry is a durable conversation; most discovered conversations have no MAWS-owned Claude process. Much of the GUI treats that ordinary condition as unavailable instead of acquiring a process when needed. This is not evidence that all those sessions crashed.

Recommendation: combine (c), last-known facts for immediate read-only presentation, with (a), one transparent, guarded resume path for actions needing a current engine. Opening a historical conversation should not start a process merely to display its transcript. Opening an engine-backed widget or requesting a current context reading should obtain a process when facts cannot otherwise answer the action. Sending a prompt should continue any eligible historical conversation, not just a memory-budget-released one. Keep the existing memory-budget lifecycle; do not implement an engine for every sidebar row or a new fixed idle timer.

“Every session behaves as running” should mean the ordinary controls work without a manual Resume ceremony, not that historical approvals become answerable, cached facts become current, or MAWS silently takes a transcript away from a terminal.

Current /plugins includes Installed, Marketplaces and Available sections backed by the CLI even without a live session; only its Loaded-in-this-session section and reload controls depend on live status. Its current footer names “claude plugin list --json · marketplace list --json · system/init,” and confirmed CLI changes. The exact quoted older footer could indicate an older packaged renderer, but this research did not inspect the installed build and cannot establish that. 2 Grounding

2.1 State model: three different meanings of “running”

A. Durable conversation and ownership.
- SessionRecord exists independently of an engine process. It holds app id, optional engine session id, directory, additional directories, worktree, title, model/effort, requested/effective permission mode, archive state and holder. Holder is none, self, terminal, or background_job; self may also be contestedBy a foreign holder. This is not a process-state enum. /Users/new/Developer/GitHub/MAWS/src/shared/graph/session.ts:18-32,48-85.
- Disk discovery inserts an index record; it does not launch an engine. /Users/new/Developer/GitHub/MAWS/src/main/index/sessions.ts:250-287. Critically, discovered rows do not recover a complete launch configuration: additional directories default to [], model/effort are nullable, and permission requested/effective default to auto. Do not describe these defaults as the terminal session's verified last settings. /Users/new/Developer/GitHub/MAWS/src/main/index/migrations.ts:37-41; /Users/new/Developer/GitHub/MAWS/src/main/index/sessions.ts:250-287.
- A new unsent tab has a setup intent and no ordinary record yet. It has editable launch choices, not an engine. The renderer holds records, digests, engine statuses and unstarted entries separately. /Users/new/Developer/GitHub/MAWS/src/renderer/src/stores/sessions.ts:21-50.

B. Host process lifecycle.
- EngineSessionStatus.process is starting → initializing → ready → exiting → exited. Exits include quit, stop, archive, crash, unknown, budget and idle. No engine-map entry is another normal possibility, not an alias for an exited status.
- engineState is independently idle/running/requires_action/unknown; activity is independently compacting/requesting; turn is independently nullable. A ready process with engineState idle is fully usable. “The session is not running” usually means process is not ready, NOT that the model is between turns. /Users/new/Developer/GitHub/MAWS/src/shared/engine/status.ts:18-35.
- Exited status can remain in the host's process history; the host caps exited rows at 24. C. UI availability, currently inconsistently derived.
- The shared literal is /Users/new/Developer/GitHub/MAWS/src/renderer/src/statusline/mode-menu.ts:73. Mode availability is status?.process === 'ready' at :77-89.
- Most reads and controls use that readiness predicate. Some use merely engine.has(id), which incorrectly includes retained exited statuses. 2.3 What actually resumes today

Opening a sidebar session mounts its conversation; it is not a blanket resume. The explicit Resume action first opens the tab and then calls resumeSession. /Users/new/Developer/GitHub/MAWS/src/renderer/src/sessions/actions.ts:84-90. Opening a widget/chip does not run that path; it hits the guards described above.

Sending:
- New unsent tab: setup/start, with its launch choices and held first message.
- Memory-budget/idle released digest: Composer calls the registered releasedResume seam, which is resumeSession; the message goes with the guarded start. /Users/new/Developer/GitHub/MAWS/src/renderer/src/composer/Composer.tsx:175-186,275-290; /Users/new/Developer/GitHub/MAWS/src/renderer/src/sessions/connect.ts:98.
- Ordinary disk-only, stopped, or crashed record without that released marker: Send is disabled. There is NOT a universal existing lazy-send implementation to reuse unchanged. This is larger than removing one sentence.

resumeSession calls main's session.start; start on an existing record is a resume. It docks trust/relay cards and preserves the message on refusal. /Users/new/Developer/GitHub/MAWS/src/renderer/src/sessions/setup-actions.ts:174-188.

Main checks archive, fresh holder authority, missing cwd and trust; returns already_live, held, missing_directory or needs_trust as appropriate. /Users/new/Developer/GitHub/MAWS/src/main/sessions/start-guards.ts:114-140. The asynchronous resume goes through the memory launch gate, optional trust bootstrap, rechecks holders after that bootstrap, unfollows the disk feed, launches, waits for readiness, and only then sends the held first message. A no-output launch gets one bounded retry. /Users/new/Developer/GitHub/MAWS/src/main/sessions/resume.ts:24-103.

Launch configuration: record.directory; record.additionalDirectories; requested model (not simply the last resolved model), effort, requested permission mode; recorded route if verified, otherwise default route; current app-level engine/subagent settings. The main mapping passes --resume <engine id>, without --fork-session or a new --session-id. The engine id stays the same. /Users/new/Developer/GitHub/MAWS/src/main/sessions/launch-mapping.ts:112-136; /Users/new/Developer/GitHub/MAWS/src/engine-host/launch.ts:191-219. Base flags and constructed environment are specified in /Users/new/Developer/GitHub/MAWS/docs/charter.md:100. They include print mode, bidirectional stream-json, verbose, stdio permission prompting, partial messages, subagent forwarding, replayed user messages, hook events and user/project/local settings sources. Neither a record nor a null model means the original terminal flags have all been recovered.

Host readiness is initialize → gateway verification → effective-mode fallback if needed → reapply session grants → recover queue → ready → context sample, without requiring a new prompt. /Users/new/Developer/GitHub/MAWS/src/engine-host/session.ts:655-701. The durable queue/grants/last launch spec live in the host state file, not SQLite. Queue recovery preserves paused state, makes an unacknowledged submission uncertain, and retires interrupted released entries; new Send does not overtake saved queued messages. /Users/new/Developer/GitHub/MAWS/src/shared/engine/session-state-store.ts:1-6,31-42,107-115; /Users/new/Developer/GitHub/MAWS/src/engine-host/queue.ts:99-139. Do not invent an automatic queue-unpause for a widget read.

2.4 Design intent and process/resource policy

The approved design explicitly distinguishes durable sessions from live processes, gives new tabs launch-on-first-send, and supplies explicit Resume for older records. C10's original restart rule says “never auto-resumes.” /Users/new/Developer/GitHub/MAWS/docs/doperpowers/plans/2026-09-28-c10-sessions-worktrees-trust.md:31,45,326,351; /Users/new/Developer/GitHub/MAWS/docs/charter.md:517-542. P1 E10 later changed supervisor survival/reattachment, not all historical rows into running engines. /Users/new/Developer/GitHub/MAWS/docs/doperpowers/plans/2026-10-05-p1-extension.md:174,189 (A-29/A-38).

The explicit transparent-resume promise is currently scoped to memory-released sessions. With the app connected, process retention is memory-budgeted, NEVER a fixed timer: default 25% physical memory; LRU eligible idle processes can be released, but turns, pending requests, queued messages, nonambient background work, held peer messages and listed stateful MCP servers protect a process. Grants alone do not, because they are reapplied. The owner can disable the budget. /Users/new/Developer/GitHub/MAWS/docs/charter.md:150-154; /Users/new/Developer/GitHub/MAWS/src/engine-host/budget.ts:10-12,38-52.

P1 adds an exception only while no app is connected to the detached supervisor or exit-when-idle is armed: its idle release clock is active, default ten minutes until configured. /Users/new/Developer/GitHub/MAWS/src/engine-host/supervision.ts:21,125-132. Do not conflate this with automatic reaping of every idle engine while the owner is using the app.

Measured older pinned-engine evidence: about 270–420 MB per idle engine tree, roughly 550 MB at a tool-call peak, with MCP processes a large part; cold initialize 0.8–1.1 seconds under the measured settings. These are empirical planning bounds, not a fresh 2.1.293 measurement. /Users/new/Developer/GitHub/MAWS/docs/charter.md:119,154; /Users/new/Developer/GitHub/MAWS/spikes/protocol-probe/findings-pass2.md:35-42. This supports process-on-demand rather than one process per indexed session. The source does not establish a single global “no process until Send for every existing session” cost decision: explicit Resume already launches with no prompt.

2.5 Plugins, persistence and the critical initialize/init distinction

The Loaded list means what this process actually loaded, not what is installed or enabled in files. system/init carries plugins, errors and warnings; reload_plugins also returns a plugin list and updates status immediately. initialize is a DIFFERENT control response: current MAWS initializes mode, fast-mode facts, commands and agents, but not plugins. The tracker starts plugins at [] with no “not yet observed” marker. A freshly resumed ready process can therefore misleadingly say “The engine loaded no plugins” until a turn's system/init or a reload response. Simply auto-resuming on widget open is insufficient.
Evidence: /Users/new/Developer/GitHub/MAWS/src/engine-host/session-status.ts:27,46-48,86-91,124-134; /Users/new/Developer/GitHub/MAWS/src/renderer/src/widgets/PluginsWidget.tsx:53-55; /Users/new/Developer/GitHub/MAWS/src/engine-host/session.ts:483-489.

- Index SessionRecord persists model/effort/mode/version and directory choices from MAWS statuses, not the full init/plugin inventory. /Users/new/Developer/GitHub/MAWS/src/shared/engine/status.ts:93-113; /Users/new/Developer/GitHub/MAWS/src/main/index/sessions.ts:409-431.
- Discovery's TranscriptSummary has no plugin list or full context/mode/model fact snapshot. /Users/new/Developer/GitHub/MAWS/src/shared/wire/store.ts:106-133. A copied actual transcript snapshot in /Users/new/Developer/GitHub/MAWS/spikes/protocol-probe/fixtures/pass3/p1-side-thread-live-resume.jsonl contains user/assistant/mode/cost-state/etc., no system/init and no plugin-list field. Do not assume stream-json init is a line in terminal JSONL. Individual mode/assistant model/cost records may support selected historical facts, but that is not a complete replay of startup capabilities.
- MAWS raw journals DO durably save inbound system/init and reload control responses, per app id and launch id, with rotation and retention (20 launches / 30 days). Conclusion: ordinary startup/resume/control reads do not themselves constitute a model turn, and the sources support zero foreground inference tokens before a prompt. They do NOT provide a network/billing proof that every 2.1.293 no-prompt resume produces zero API calls. SessionStart hooks run before initialize; MCP servers start; scheduled/background work may have independent behavior. No fresh probe was run under this read-only assignment. Make a narrowly scoped no-prompt resume + context + plugin-facts probe the first implementation gate; do not send a dummy model prompt to populate a widget or promise universal zero cost.

2.6 One-writer and trust boundaries

Resume is not attaching to an existing terminal's stdin. The engine historically permits two print/interactive writers of the same JSONL. That creates sibling branches; W7's fixture proves a later resume may follow the terminal branch and omit MAWS's sibling work from model context. /Users/new/Developer/GitHub/MAWS/docs/charter.md:125-127; /Users/new/Developer/GitHub/MAWS/spikes/protocol-probe/findings-pass2.md:178-188.

MAWS must keep its fresh registry/own-process authority check, explicit takeover/fork choices, and W7 contested behavior. The follower pins MAWS's branch when a foreign writer would replace it, then refolds after that holder exits. This is display protection, not a lock preventing another writer or a guarantee that a future resume sees both branches. /Users/new/Developer/GitHub/MAWS/src/engine-host/fs/chain-follower.ts:84-86,382-388,463-466. A widget read must never silently take over a terminal-held session.

A cold widget/chip action routed through start may require workspace trust, relay-route decision, memory-budget gate, or a missing-directory recovery. Accepted trust may require a short bootstrap process before the resumed one. Project hooks/settings/MCP initialization are real effects even without an inference prompt. Preserve effective-mode/refusal reporting and bypass confirmation; do not turn an offline requested mode into a falsely confirmed current mode. D-1, D-12, D-18, D-19 and X6 all remain binding.

Alternatives and when they win

(a) Pure lazy transparent resume for every live-backed widget/chip: fewer persistence changes and simplest reuse of current controls; wins as the first implementation slice if a brief cold-start delay is acceptable. Costs one full engine/MCP tree for each touched session and may expose trust/relay prompts on a widget open. It still does not solve plugin inventory on initialize, stale context presentation, or terminal-held read-only sessions by itself.

(b) Eager warm on selected session/tab open plus idle cull: closest to Claude Desktop's ordinary open behavior and Codex's view hydration; wins if the owner prioritizes all controls immediately live and typically visits a small working set. Costs a process for every newly opened cold conversation, hook/MCP startup, possible trust friction while merely browsing, and more collision opportunities. An engine per all restored/open background tabs is unnecessarily expensive. If chosen, warm only the foreground eligible view and retain the current memory budget. A fixed N-minute cull while connected contradicts charter §4.4 and requires an explicit owner-approved policy change; it is not already authorized by E10's detached-idle timeout.

(c) Facts cache alone: zero engine processes/tokens for history browsing; wins for dormant history, read-only terminal-held sessions, and memory-constrained machines. Insufficient alone: current context decomposition, control mutations, plugin reload, peer messaging and side questions still need an engine. The recommended combination supplies this missing action path.

Cost/trust summary: no per-row eager process; cached reads are free of engine startup. Ordinary initialization/control reads need no foreground inference prompt, but exact 2.1.293 no-prompt resume/API behavior remains a probe gate. Hooks/MCP startup can execute code and incur non-model network activity; scheduled/ambient work needs explicit verification. Peer reply, side-question and actual Send are model work and spend tokens.
