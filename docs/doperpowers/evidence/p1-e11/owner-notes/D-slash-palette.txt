The shift is document scrolling, not a slash list inserted into the composer's flex layout. MAWS already mounts the menu outside the composer, under document.body. Its combination of bottom-first/absolute positioning, a mount interval before positioning is applied, unrestricted scrollIntoView on the selected slash row, and an unconstrained document scroll root lets opening/navigating the menu move the entire app.

Both supplied MAWS screenshots show the same important clue: the sidebar's bottom “Local workspace” strip is well above the bottom of the image, with empty page beneath it. The “to-human view” band is not a transcript header and not a slash-menu section. It is the doperpowers engine mod's AbovePrompt content. The button says “full transcript” because that is the action it offers from report-only mode. • /Users/new/Developer/GitHub/MAWS/src/renderer/src/composer/editor/extensions.ts:90–107 creates both suggestion configurations without a placement, container, flip or floatingUi override. Slash is start-of-line only; @ has its own prefix rules.

• The installed, pinned @tiptap/suggestion 3.31.3 supplies the omitted defaults: /Users/new/Developer/GitHub/MAWS/node_modules/@tiptap/suggestion/src/suggestion.ts:60–64 sets placement='bottom-start' and flip=true. /Users/new/Developer/GitHub/MAWS/node_modules/@tiptap/suggestion/src/plugin/floating-ui.ts:23–48 adds a 4px main-axis offset and flip middleware, with strategy='absolute'. • That dependency's floating-ui.ts:81–100,119–168 appends the element to document.body, sets visibility:hidden and width:max-content, then starts computePosition/autoUpdate. Only in the asynchronous .then at 149–164 does it apply position:absolute, left and top and reveal it. Hidden visibility does not remove the initially static block from layout. There is a transient body-flow element after the full-height app, not a permanent in-composer flow element.
• The resulting settled menu is body-portaled in the DOM and absolutely positioned. It requests below the caret first and may flip above when the measured geometry calls for it. There is no explicit viewport-size middleware or shift middleware in our configuration.

Where page movement enters

• /Users/new/Developer/GitHub/MAWS/src/renderer/src/composer/mentions/SlashPalette.tsx:79–82 runs document.getElementById(optionId(active))?.scrollIntoView({block:'nearest'}) whenever active or rows changes. This API may scroll all scrollable ancestors, including the document; block:'nearest' does not mean “only scroll the nearest container.” It is intended to reveal the selected row inside the menu but does not restrict itself to that menu.
• /Users/new/Developer/GitHub/MAWS/src/renderer/src/styles/app.css:75–90 gives html, body and #root height:100%, but no document overflow containment. A body-appended static popup during mounting, or an absolutely positioned popup outside the viewport, can enlarge the document's scrollable extent. The row-reveal operation can then move the window. The initial hidden state prevents a visual flash, not this layout/scroll side effect.
• The ordinary app layout does not protect a body-level popup: /Users/new/Developer/GitHub/MAWS/src/renderer/src/app/Shell.tsx:27–38 is a full-height grid with a clipped main region; /Users/new/Developer/GitHub/MAWS/src/renderer/src/main/Pane.tsx:56–63 clips the pane; both are descendants of #root, not ancestors of the body popup.
• Tiptap also issues an immediate renderer update while fetching suggestion items, even here where items returns []: /Users/new/Developer/GitHub/MAWS/node_modules/@tiptap/suggestion/src/plugin/view.ts:168–185,221–223. Our env/context and row props update through popup.tsx:46–48,58. Do not assume there is only one detached first render and therefore the slash effect cannot run during startup.

This is the exact source-level combination to fix: popup.tsx:54–55 leaves initial positioning to a later promise; extensions.ts:91–107 accepts bottom/absolute defaults; SlashPalette.tsx:81 performs an ancestor-scrolling reveal; app.css:75–90 permits the root to scroll. “Make the palette absolute” alone is not a diagnosis or a sufficient repair—it already becomes absolute.

4 Rough fix plan

Recommendation: keep the existing portal and suggestion lifecycle, make the popups genuinely isolated overlays from the instant they attach, and make slash open above with a constrained internal scroll region. Do not restructure SessionPane or move the plugin band to compensate for scrolling.

1. In the shared suggestion renderer, establish out-of-flow positioning BEFORE p.mount appends the element (prefer a consistent fixed strategy for a body overlay), retain hidden-until-positioned handling, and ensure there is no static body-flow interval. Configure an explicit above-first/top-start placement rather than inheriting bottom-start. For the owner's requested stable behavior, keep slash above and cap it to available space instead of flipping it downward; use viewport padding and horizontal shift. Apply the same safe lifecycle to @, with an explicitly chosen placement policy rather than accidental defaults.

2. Replace the slash row's document-level scrollIntoView with a reveal scoped to the listbox scroll element, using its own scrollTop/row bounds. It must change only the list's scroll offset. Share this helper with @ if adding active-row reveal there, so keyboard navigation actually keeps selected rows visible without moving the page. Use per-popup refs rather than global document lookup. Preserve editor focus, Escape/Enter/Tab behavior, disabled-row behavior, IME handling and outside-dismiss cleanup.

3. Make html/body/#root a non-scrolling workstation viewport; internal transcript/unstarted-pane/list scroll containers remain the only intended scrollers. Add this as a second containment boundary, not as the only fix or a way to hide an offscreen menu. Verify existing dialogs/popovers and narrow windows after changing global overflow.

4. Bound list height by available space on the chosen side, with today's 384px slash / 320px @ caps as maxima, not promises. Retain token-based surface styles and existing light/dark behavior. Avoid adding a replacement popup framework.

5. First land the layout correction without rebuilding the command catalogue. A mature next list would give recognized actions meaningful icons, use user-facing sections while preserving origin information, show chevrons only for real model/mode/MCP-style submenus, and retain explicit disabled reasons rather than silently hiding unsupported commands. Do not infer headless support from a pretty row or expose terminal-only commands as executable. This content redesign is a separate product-sized follow-up, not necessary to stop the page moving.

Alternatives and when they win

• Minimal, charter-preserving route: retain caret anchoring and the current width/cap, configure top-start/fixed plus viewport constraints, and fix the scroll/lifecycle issues. Best immediate repair when the request is specifically “nothing moves and it opens above.” No charter decision changes are needed.
• Exact Codex composition: anchor slash to the composer's top edge/width, so even a multi-line draft always gets a menu wholly above the box, while @ may remain caret-anchored. Best if matching the supplied Codex silhouette is the required acceptance. Reuse Floating UI with an explicit composer reference rather than copying Codex's geometry implementation. This requires updating the explicit CARET-ANCHORED / 240–512px language in charter §5.4 (:202) and its child record; it is not an engine-protocol change or a change to D-1. The owner's new request supplies the direction, but the record should not silently retain contradictory wording.
• A local absolute bottom:100% popup would avoid document positioning, but the pane/main ancestors intentionally clip overflow and centered/small panes need collision handling. Prefer it only if the composer has a deliberate non-clipping overlay host and all split-pane/short-window cases are covered. It is not the default recommendation.
