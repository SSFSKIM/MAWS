G — To-human as a default MAWS mod
Research only, 2026-10-08. Repository supplied as master 5dcddd70. No code/settings changes, builds, tests, engine launches, relay access, Chrome access, or reads of MAWS's real user-data/index. The only authored file is this report.

1 What the owner asked

"integrate to-human mods into our app. let it be default plugins. agent 'sends' message to human (via to-human tag, signal important parts via essential and insights tag, ask async question via need-input) these are default application behavior from now".

The intent is a dependable human-message channel for unattended sessions, not merely XML-tag styling: every MAWS session should know how to send reports, highlight must-read information, explain choices, and leave asynchronous questions the human can answer later. The working transcript remains accessible. The actual educational tag is singular <insight>, not <insights>.

Recommendation: ship a small, built-in MAWS To-human mod, enabled by default, with an app-owned delivery/answer/attention lifecycle and one versioned instruction contract. Supply that contract to owned engine launches with --append-system-prompt unless a verified active compatible output style already supplies it. Do not require installation of the whole doperpowers plugin or silently change the human's Claude settings. The MAWS plugin widget should distinguish built-in MAWS mods from engine-installed plugins rather than falsely listing a native module as a Claude-installed plugin.

Important correction: today there are TWO implementations. The screenshot's "to-human view · full transcript" bar belongs to the live doperpowers engine mod; MAWS's owner Presenter is the offline/unattached fallback. The live mod already has clickable need-input choices, but clicking fills the composer; Enter still sends. The fallback's choices are inert. Neither establishes tag-derived MAWS attention.

3 The output style contract

Source of truth read: /Users/new/.claude/plugins/cache/doperpowers/doperpowers/7.141.2/output-styles/to-human.md:1-50. The earlier cached 7.141.0 file was also read; the installed 7.141.2 file is the citation used here.

- Metadata: name to-human; keep-coding-instructions: true. The normal coding instructions must remain, not be replaced by a tiny formatting prompt.
- The human is away; ordinary prose, tool calls and results are the agent's working record. <to-human> spans, wherever written, are the messages delivered to them (:7-12).
- What the human must not miss uses <essential> instead (:12).
- Blocking questions use AskUserQuestion. Only questions for which the agent can continue other useful work use <need-input>, one question per mark (:14-19).
- Optional choices are flat <choice> lines; the recommended choice has the bare recommended attribute. The answer is a human click or their own words, delivered as the next human message (:21-30). If this is the last remaining work and the agent is waiting, use AskUserQuestion, not an async mark.
- Write directly and literally; do not substitute mannered metaphors for precise statements (:32-40).
- Teach relevant implementation choices around the work: before and after code changes, brief educational explanations of 2-3 codebase-specific points in <insight>. They belong in the conversation, not files, and should appear during work rather than only at the end (:42-50).
- The style itself specifies semantics, not a transport, notification policy, persistent question ID, read receipt, dismissal, or viewport placement algorithm. Those are MAWS product/application responsibilities. It also does not say every to-human span needs an OS notification.

MAWS should carry a short versioned contract preserving these semantics, not unrelated doperpowers workflow instructions. An instruction-only append preserves the base coding prompt and an independently selected output style. The style's coding-instruction preservation must be retained if the alternative output-style mechanism is used.

5 Rough plan

Recommended shape

A built-in MAWS mod, not a dependency on the owner's entire doperpowers installation, and not a general third-party Electron plugin SDK. Give the built-in module a stable ID, contract version, default-enabled flag and app/session settings. Its three responsibilities are (a) behavior contract injection; (b) report/question presentation; (c) semantic attention/read/answer state. Initially a small static registration is sufficient. List it in a truthful "MAWS mods · Built in" section of the plugins widget; retain the engine's own Installed/Loaded sections unchanged.

This is a P2 child, not a P1 bugfix. R4 deliberately made detached choices inert and live drawing engine-owned. The request changes the default agent behavior, makes owner vocabulary general, changes data/state contracts, and adds notification/read semantics. A focused P2 child can own it, with bounded internal waves; no need for a broad extension-platform project first. Overall size L.

Engine side — M

- Add a contract version/source to launch configuration, resolved centrally for every MAWS-owned cold start, resume and fork, including supervisor reconnect/relaunch. Do not inject by prepending an ordinary human message. Exclude non-conversation utility/probe launches unless they explicitly request the behavior.
- Preferred mechanism: --append-system-prompt <contract>, statically verified in exact 2.1.293 as above. Add a typed field to LaunchSpec and append exactly once in buildLaunch. Keep the base prompt, current model configuration and current user output style. The new instructions should define the human channel, not overwrite user taste unrelated to it.
- Detect a known compatible active style before adding instructions: resolve effective outputStyle in the launch's settings context (config-home override, project/local scopes, flag settings and applicable policy) and verify that the supplying plugin/style is actually available. Recognize doperpowers:to-human by versioned compatibility metadata, not by arbitrary substring matches in unrelated files. Merely finding doperpowers installed or one historical <to-human> span is insufficient.
- Record source='external-compatible-style' or source='maws-contract' per launch; compare against the engine's observed output_style before the first user prompt and surface a mismatch. The existing SessionStart timeout settings reader is incomplete for this job (it explicitly omits managed settings/root scopes); do not repurpose its heuristic as an authoritative resolver. If effective style cannot be established, the resolver must make the ambiguity visible rather than silently double-inject.

Alternatives, and when they win

A. A bundled ordinary Claude plugin under /Users/new/Developer/GitHub/MAWS/plugins/to-human/ with output-styles/to-human.md, loaded through --plugin-dir <path>, selected through the existing --settings JSON's outputStyle. This is preferable if the owner wants the same independently installable To-human package for terminal/other hosts and a real engine-loaded plugin entry. It is not necessary merely to inject instructions. Preserve keep-coding-instructions; never pass an invented --output-style flag. Detection can keep a compatible doperpowers style instead of selecting the bundled one. Cost: packaging/discovery/precedence and reconciling two UI mods; selecting outputStyle also competes with a user's different style. Need fixture coverage before shipping.
