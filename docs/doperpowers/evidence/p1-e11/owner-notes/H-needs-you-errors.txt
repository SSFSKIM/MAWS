Recommended convention (design judgment, not a claim of a universal platform standard)

An error occurrence is an outcome worth seeing. An approval or question is an outstanding action. Track acknowledgement separately from whether the failed turn remains failed. Seeing/dismissing the occurrence should end the alert without rewriting history or pretending the turn succeeded. A still-actionable auth/retry/setup remedy may remain a request only when MAWS can name what the human can do.

5 Rough fix plan for H1 and H2

H1 — recommendation

1. First fix the mechanical terminal lifetime mismatch: make proven ordinary disk human turns carry the correct human-origin semantics, so the existing next-human-turn retirement works. Preserve meta/peer/task/interrupt classification. This needs no owner taste decision.
2. Separate actionable requests from unseen problem outcomes while retaining the single attention authority. Keep failed-turn history and an “Ended with an error” session indicator; allow an unseen error to attract attention until it is acknowledged. Recommended acknowledgement: when the user actually sees the session's error/notice, or explicitly clicks Dismiss on the card. Do not treat a background tab opening, a hover, or an unfocused window as having seen it. Do not acknowledge unrelated pending approvals/questions.
3. Do not add an arbitrary time-based deletion initially. Replace “waiting 2w” on an error with “Failed 2 weeks ago” (or “Ended 2 weeks ago” for limits/interruption). Once acknowledged, remove it from Needs you, retain it in the session's history/row, and avoid adding a new “Recent problems” dashboard section unless the owner wants that workflow. Unseen old imported errors are historical outcomes, not fresh requests/OS notifications; use event identity/time plus a documented import policy, not discovery time as failure time.
4. Persist acknowledgement per occurrence, keyed by stable attention/event identity, and suppress replay resurrection. The existing retired state is available, but deleting a row alone is insufficient if a disk replay can recreate it. A new failure must be independently alertable after an older one was acknowledged. Handle persisted legacy pending errors deliberately; do not leave the existing rows permanently outside the new policy.
5. Humanize copy from structured reason/subtype, preserving the raw code in details. Suggested mappings: error_during_execution → “The turn ended with an error”; error_max_turns → “Stopped at the turn limit”; error_max_budget_usd / budget_exhausted → “Stopped at the budget limit”; error_max_structured_output_retries / structured_output_retry_exhausted → “Could not produce the required output format”; success → no failure; aborted_* → “Stopped by you”, not failure. Prefer a useful specific reason over the generic subtype. Unknown errors get a safe generic label plus expandable diagnostics. The max-limit subtypes are mapping targets from the requested engine vocabulary, not new probe observations from this pass.
6. Distinguish event acknowledgement from solving a persistent issue. For example, a current unavailable permission mode with an explicit “Switch mode” remedy need not share the historical-error policy. A failed background task may be acknowledged without dismissing a parent question.

H1 alternatives

- Explicit Dismiss only, never clear-on-view: better if the owner treats Needs you as a work queue where merely reading does not mean handling. Still fix terminal retirement and event-relative copy.
- Auto-demote after a chosen age (e.g. 24 hours), with history retained: better only if keeping the board clear after long absences outweighs guaranteed notice of unseen failures. Make it demotion, not deletion. Never age out permissions/questions by this rule.
- A dedicated Recent problems section/filter: better if the owner regularly audits failures across many inactive sessions; otherwise it is unnecessary extra board architecture.
