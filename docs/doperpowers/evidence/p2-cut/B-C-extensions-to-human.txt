DOPERPOWERS: HOW A HOST ADVERTISES "NATIVE TO-HUMAN"

The mod can observe only: `e.surface` per render, which says "desktop" for MAWS and Claude Desktop alike and is documented as a declared fact, not a trust signal; `session.attach` events carrying surface, clientId and viewport (MAWS attaches as "maws-main", src/shared/engine/surface.ts:12); `$.session.surfaces()` names without ids; and `$.env.get("LITERAL")`, whose names `claude plugin validate` lists. MAWS's `answers` capability list in ui_attach (engine-host/surface.ts:70) is not visible to hooks. The smallest change is therefore one environment variable: MAWS adds `MAWS_NATIVE_TO_HUMAN=<contract version>` to the launch's `extraSettings.env`, a seam that already ships (launch-mapping.ts:70, merged at launch.ts:157-173), and the mod reads it once in registerToHuman and, when it is set and `e.surface` is "desktop", passes AssistantMessage, AbovePrompt and the question presses through with `next(e)`. The shell hook can exit early on the same variable with no declaration. A per-app or per-session switch maps to setting or omitting the variable at the next launch, matching the instruction-contract timing. Observing clientId "maws-main" needs no MAWS change but cannot carry the toggle or reach the shell hook. Unverified: that `$.env.get` inside the function-hook worker sees values that `--settings` env sets (E13 proves only subprocess inheritance, A-52); one scratch probe settles it. On the MAWS side, Rows.tsx:47 must then use the local presenter even when attached, or the deferring mod leaves raw tags on screen.
