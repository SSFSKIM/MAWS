=== 3. SIZING AND RISKS ===

Verdict: the deliverable half plus the shared card is M; the browser half is a second M, or L with an overlay window. As one child: L. Cut two children; the browser one follows #90.

Deliverable half (M)
- New `CommentCard` (anchored, 300-340px) replaces the Sheet for the artifact producer: textarea, a compact Side thread / Send to main toggle, screenshot chip, then the thread.
- Place it from the pick's `rect` (now dropped) inside the viewer body, `relative min-h-0 flex-1` (Viewer.tsx:194); the iframe is renderer DOM, so no cover protocol is involved.
- Thread view: a compact list of the child's transcript rows (`TranscriptList` / `Transcript variant 'child'`, `useTranscriptStore` as ThreadView.tsx:45 does), from the thread's own anchored prompt on (this also covers the disk-history caveat), and a reply field posting `session.send` (composer/editor/submit.ts:52-53). `sendComment`, `adoptFork` and the fork stay; `revealNewThread` is replaced by "show in the card".
- The Side pane listing stays; its chip gains "Show in deliverable" to re-dock the card.
- Backend: none; one additive seam hint (`placement`) amends X10.
- Tests to rework: side/CommentComposer.test.tsx, actions.test.ts, SideTool.test.tsx, deliverables.test.tsx, e2e/deliverables.spec.ts:876, e2e/side.spec.ts, e2e/p1-live.spec.ts:563.

Browser half (M, or L with an overlay window)
- The page is a native view above the renderer, so a card over it is hidden unless the cover protocol hides the page (cover.ts:2-3, 39). A body-portaled card freezes the page to a still for as long as it is up, and a thread card lingers while the agent works; Codex solves it with a separate window. Cheaper and in the spirit of the Sheet: dock the card in the pane's own box (a strip above or below the page; the placement shrinks), which needs no cover.
- An anchored pin needs a viewport position main does not send (browser.ts:95-100): a small additive IPC field. Without it, a docked card with no pin.

Risks
1. cua board #90 changes the browser tab's top chrome (bookmarks bar, extensions bar). A docked strip or a card clamped to the page rect depends on that height and on `placement.ts`; build after #90. The chrome already overflows at a 379px panel (docs/tech-debt-tracker.md:80).
2. The deliverables viewer sizing is an open taste row (docs/tech-debt-tracker.md:95, "Closes when (owner P2, E2's viewers) ... fit to pane, zoom and actual size"). A card positioned from `rect` assumes the frame is unscaled; if the viewer later zooms or fits content, rect-to-card mapping must follow. Sequence them together or anchor the card to the viewer box.
3. The mini view drops SessionPane's duties: the side agent can raise permission requests, questions, trust/relay cards (SessionPane.tsx:48-90). The card needs a "needs you" state with one click to the Side pane or a tab, or the thread stalls unseen. Main design risk.
4. No stored positions: `artifact-element` anchors keep a selector, not a rect. Cut: the card appears at pick time and re-docks from the Side chip; persistent pins (Claude's model) are a P3 candidate.
5. Claude's comment is a stored thread answered in place; MAWS's is a session (X11). The card should read as a thread while keeping "Open as tab". "No change in backend" holds: lineage, fork launch and both sends stay.
6. Tracker line 97: a comment fork cannot update its parent's artifact; a card that reads as a reply inside the artifact makes that more visible, so decide that row at the same sitting.

Recommended cut: E-comment-1 (M): shared `CommentCard`, thread and reply view, deliverable placement, the seam hint; the Sheet stays for the code gutter. E-comment-2 (M, after #90): browser dock, with the picked payload gaining a viewport hint if the owner wants a pin. Owner call: replace the code gutter's Sheet too (cheap once the card exists), or keep it.
