D3 Q3 — Separate-git-dir checkouts are out of scope for worktrees
  Proposal (default answer): Checkouts made with a separate git dir (`--separate-git-dir`) and their linked worktrees are out of scope for the worktree service.
  Background: This is Q3 of the E11 document and tracker rows L36 and L37. A "separate git dir" checkout keeps its repository data in a different folder from its working files. L36: a linked worktree of such a repository, placed outside its main checkout (`git worktree add ../x`), is treated by the worktree service as a project of its own, because git records no path from the repository back to the checkout. L37: the sidebar's sibling-worktree grouping (src/main/index/projects.ts) cannot fold such a worktree under its main checkout unless a directory MAWS already knows names that git dir, and in a very unlikely layout could fold it wrongly. Both rows say the layouts are hypothetical for your repositories. Accepting closes L36 and L37 with a section 19 line recording git's limit; overturning means building the discovery-based fold that L37 describes, which is P3-sized work.

D7 Q12 — Side threads and the dollar cap (--max-budget-usd)
  Proposal (default answer): A side thread inherits its parent's budget when the parent has one.
  Background: This is Q12 of the E11 document and tracker row L82 ("A side thread's launch carries no `--max-budget-usd`"). A side thread is a forked child of your session. As built, a fork takes no dollar cap from its parent, so a parent's cap binds only the parent (seen in E4d's live run, where the thread was unbounded). Said plainly: product launches carry no budget today (src/main/sessions/launch-mapping.ts sets `maxBudgetUsd: null`; only the test harness's launches set one, via src/engine-host/launch.ts), so this ruling changes nothing you would see in the app. It only makes harness launches (the live test runs, which do cap spend) behave consistently. Accepting turns L82 into one wave-S commit in the side-thread launch path (src/main/side/ and launch-mapping.ts) and adds a line to X6. If you want threads capped in the product, a default per-thread cap is a separate P3 product decision (a setting and a settings version), not part of this ruling.
