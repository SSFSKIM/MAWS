## Answers to the follow-up decisions

(a) Confirmed; see the P2 finding above. Defect and fix shape are exactly finding 3's: the link's own savepoint ends before the write's refusals run. Move it into the `inFrame` callback with `linkInWrite`.

(b) Not reachable in ordinary use; a P4 tracker row is right. Every reconnect that reuses a clientID (and only a reused clientID can collide) follows a detach the host has already run: `closeConn` calls `detach(conn)` synchronously after `port.close()` (service.ts:1092-1100), so an eviction, unload or rejection has removed the old connection's presence before the replica even sees the port close and reconnects (`reconnectIfClosed`, replica.ts:59; the renderer's `retry`/`hostReady`, host.ts:172-205). A host death leaves no host state to collide with. A window reload and `AgentReplica.edit()`'s discard path both make a new Doc, hence a new clientID, so the old detach removes the old id only. `PortProvider.connect()` does call `disconnect()` first, but no caller invokes it while the previous port is still open on the host. Even if the crossing did occur, y-protocols' self-protection keeps the client's local state (`@y/protocols/src/awareness.js:261-267`) and the 15 s renewal (`awareness.js:66`) re-sends it at a newer clock, which the host accepts because `detach` now deletes the meta; the loss is bounded to about 15 s. Note that the MAWS provider filters `origin === this` in `onAwarenessUpdate` (port.ts:214), so the self-protection's immediate re-broadcast is not sent — the renewal is what heals it.
