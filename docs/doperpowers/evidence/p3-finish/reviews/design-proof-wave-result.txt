## Findings
- [P3] Exclude exactly 100 Hz from the frame-work precondition — /Users/new/Developer/GitHub/MAWS/.claude/worktrees/agent-af4cd2993bc56e015/e2e/design-scale.spec.ts:478
  The precondition admits a display at exactly 100 Hz (`holds: Number.isFinite(hz) && hz > 0 && hz <= 100`). A 100 Hz frame lasts 10 ms, and `frameWork` clips each slice to its BeginFrame interval, so even a fully busy frame reads at most about 10.0 ms. The frame rows are judged non-strictly (`strict = false`, so `worst <= limit` at design-scale.spec.ts:139). On such a display a long task still reads "met", which is the same defect the panel found at 120 Hz, moved to the boundary. The change's own text contradicts it in two places. design-frames.ts:11 says "a bound at or over the display's frame interval can never be missed". The spec header at lines 18-19 says the precondition makes "a frame … longer than the bound", which is false at 100 Hz. This only matters on a gate host whose display reports 100 Hz (the mini reads about 60 Hz), so it is low severity. The fix is `hz < 100`, with the rule and header text changed to match.

## Verdict
correct — S-RESTYLE now passes only if the same document link and deck title elements, marked while both editors are mounted side by side, paint the new accent with doc and deck revisions unchanged. A remount fails it. The precondition turns every frame-work row into a failure on a fast or unreadable display. The optional `root` parameter is backward compatible. The one gap is the P3 above: a display at exactly 100 Hz still passes the precondition.

## Checked, and not verified
Checked in source at d898af4e0. The e2e files are identical at HEAD.
- **Split.** `splitWithActive` (layout-model.ts:332) moves the focused pane's active tab, the deck, into a new pane 1 and focuses it. In pane 0, `without` activates the right neighbour, else the left one. The library opens the deck after the active reading list, so with the fresh launch's tab set the reading list becomes pane 0's active tab. If that assumption about the initial tab set were wrong, the step goes red, not green: it asserts `pane(0)` shows the doc.
- **Collapse.** With two panes and focus on pane 1, a second `pane.split` sends the deck to the end of pane 0 and activates it. The emptied pane is dropped (`withPanes`), so only one `[data-editor-header]` remains for `headerAction`. The DOM hooks the step uses all exist: the "Right pane tabs" label and `data-focused` (TabStrip.tsx:120,131), `data-tab-id` (Tab.tsx:126) and the `artifact:<id>` id.
- **Restyle route.** `host.open` creates a separate `Replica` for each open (renderer artifacts/host.ts:219). The seam's write therefore reaches the editors' system view through main's store, the same cross-replica route the page's write takes to the fixture in test 2. I judge the departure acceptable: test 1 proves the hex field's write persists, test 2 proves it restyles a live scope in another replica, and this test proves a host-delivered token restyles the real editors in place.
- **Scope lease across the split commit.** `DesignSystemScope` holds its lease in a layout effect, and `DeckEditor.tsx:221`'s `useDesignSystem` holds the shared lease in a passive effect. That passive hold outlives the old deck's layout cleanup within the split's commit, so the shared view is not closed and reopened. The immediate BEFORE read after marking should therefore be stable.
- **Display reading.** The product window is `getAllWindows()[0]`, the existing convention in this spec; it closes with one window left. `getDisplayMatching(bounds)` returns the display with the largest intersection, which on macOS is the screen that paces the window.
- **Backward compatibility of `root`.** The seam's `node(id, root = 'root')` default applies when `undefined` arrives, and Playwright passes `undefined` through the call array intact. The only other callers are artifacts-store.spec.ts and supervisor.spec.ts, which use `json(id)`; nothing outside the new helper calls `setAttr`.

Not verified:

- **The mini's `displayFrequency`.** No committed evidence records it; pair45-dashboard-scale-raw.json has no display field. A 0 reading would make every frame-work row "precondition unmet" and the run fail with "read 0 Hz". That is a red run, never a false pass.
- **Editors redrawing marked nodes.** I could not rule out an editor replacing a marked node for an unrelated reason, such as a y-prosemirror redraw or a stage rebuild. That would be a false red, not a false green.
- **Trace frame intervals.** The precondition reads the reported display rate, not the BeginFrame intervals in the trace. Those intervals come from every thread of the renderer process, so if two BeginFrame sources interleaved, the slices would be capped below 10 ms even on a 60 Hz display. I did not verify whether that happens. It predates this change and is outside its scope.
