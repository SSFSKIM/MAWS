## Findings
- [P2] Keep pairs both sides agree on when forcing the board order — src/artifacts/design/order.ts:106-112
  Under force, the settle loop only collects pairs the agent re-ordered. It then permutes those boards into sent order across the slots they occupy, so a settled board can jump over a board outside that set. That inverts a pair that base, sent and live all agree on, which is the "order neither side asked for" the finding was about. I ran the committed function directly: `mergeBoardOrder(['a','b','c','d'], ['a','c','b','d'], ['b','a','d','c'], [], true)` returns `['c','a','b','d']`. Base, sent and live all put a before c, and the agent only swapped b and c. The parent tree's forced result was `['b','a','c','d']`, which kept a before c. A second case: sent `[a,c,b,d]` with live `[b,d,a,c]` gives `['c','d','a','b']`, inverting both a/c and b/d. The settle step introduces such an inversion in 18 of the 576 four-board sent/live combinations and 1,149 of the 14,400 five-board ones. The new exhaustive test does not catch this because it asserts only pairs where sent differs from base. The scenario is a forced publish after an unforced clash, where the owner re-stacked other boards since the agent's read. The forced publish then writes fractional keys for that order with no clash reported. A fix that held in the same five-board brute force: under force, also count as lost any pair the result orders against the sent order, unless only the live side re-ordered it. This leaves zero agent pairs lost and zero agreed pairs inverted. It terminates by the same argument, and the unforced path is unaffected.
- [P3] Publish the surface without an accessor object; it opts DesignWorkbench out of the React Compiler — src/artifacts/design/editor/DesignWorkbench.tsx:224-235
  The `useMemo` object with `get current()` / `set current()` hits babel-plugin-react-compiler 1.0.0's `Todo` bailout: "(BuildHIR::lowerExpression) Handle get/set functions in ObjectExpression". The compiler then skips the whole component. I ran the plugin from the repo's node_modules on the committed file. The parent version compiles DesignWorkbench with 303 memo slots; the new one reports two CompileErrors and leaves it uncompiled. Nothing in CI catches this: the renderer build compiles `src/artifacts` (electron.vite.config.ts:91, plugin-react's default include), but the build does not fail on a Todo bailout, the react-hooks lint is not applied to `src/artifacts`, and the DOM suites run uncompiled. Behaviour stays correct, and the history test shows the detach/attach sequence works. The cost is that the editor's root component loses compiler memoization in the shipped app. The workbench was written to meet its bounds uncompiled, so this is a performance and maintainability regression, not a break. A callback ref that sets a plain `useRef` and calls `onStage` gives the same lifecycle (DeckEditor.tsx:137's pattern). World can keep reading the ref object, since a callback can be passed to the div's `ref` alongside it.
- [P3] Reset the name field's draft when its commit is refused — src/artifacts/design/editor/BoardInspector.tsx:62,104-107
  The new `writable()` guard stops the write, but `NameField` keeps its `draft` state, and the commit message says the draft is dropped. Scenario: type "Phone, tall" and the replica turns read-only (or the board turns held or missing). The blur writes nothing, but the disabled field keeps showing "Phone, tall" while the board is "Phone". `key={board.title}` does not remount it because the title did not change. When the lock lifts, the field re-enables with the stale text, and the next focus-and-blur commits it. C's `NumberField` does not have this problem: it clears its draft when `onCommit` returns `[]`. Impact is cosmetic plus a delayed write of text the user typed earlier. A fix is to return the result from `onCommit` and run `setDraft(title)` on refusal, mirroring the workbench rename's `false` return.
