- [P2] A concurrent deletion in the dragged block still drops the whole carry and the late text with it — adapter.ts:253, 407-408
  The routing asked for the carry to be matched on the slots the two trees share; the implementation requires the copy to equal the shared units exactly. `deepUnits(live)` skips tombstones, so any character the dragger saw that someone else deleted in the meantime is in the copy but not in `shared`, `now.length !== drag.shared.length` holds, and the loop `continue`s: no carry, no forwards, no replay of `late`. Scenario, the same race as the P1 with the agent's usual op: the agent's `replace_text` 'A'→'B' on p3 reaches the host; a stale human drags p3. shared = 16 units (' plain…'), copy = 17 ('A plain…'), late = ['B']. Result: the copy resurrects 'A', 'B' is gone, and later stale edits into the original are lost too — the agent's edit is fully reverted by a drag, which is what the P1 was rated for. A fix that stays within the invariant: build the dragger's view from the live items in the delete set including tombstoned ones (count-only where gc collected the content), pair the copy positionally against that view, delete from the copy the units whose live item is already deleted, then replay the late runs as now.

- [P3] A losing copy's replayed late text is inserted again into a winner that already holds it — repair.ts:150-151
  `carryCopyEdits` looks a loser character up in `recL.base` only; characters `replay` wrote into the copy (the new P1 path, and the pre-existing `lateEdits` path) are in `extra`/`origins` but not in the base, so they are treated as new and appended. Scenario: a third replica types 'BEFORE ' into p3 (reaches the host); a stale human drags p3 (BEFORE replayed into the human copy as R, `origins[R] = BEFORE slots`); an agent that had seen BEFORE moves the original (arrival later → winner; its base covers the BEFORE slots). The repair finds no base for R, flushes it as pending, and the winner reads 'BEFORE BEFORE A plain…'. Duplication, not loss, behind a triple race, so P3. One-line remedy, since `origin` already follows replays: `const source = recL.base.get(slotKey(slot)) ?? slot;` and match on `originKey(source)` (a plain new character maps to itself and stays pending as today).

- [P3] `unplacedThreads` names block threads, which cannot be re-anchored, and each one costs a full document walk per deletion update — adapter.ts:187-194
  `refreshAnchors` skips block anchors for marks but calls `liveBlockThreads(doc, scope.threads)` → `placeBlocks`, which walks every node of every tab whenever the scope holds a block thread (threads.ts:292-305, 309-320). A block thread whose block was deleted (what item 11 now reports as orphaned; it stays in the threads map, open or resolved) is in `unplacedThreads` on every update that has a deletion, for ever, so every deleting keystroke in the document pays O(all nodes). The worker's cost claim (map lookups plus O(tops)) misses this. Since a block thread carries no mark and nothing in the refresh can move it, filter them out: `!isBlockAnchor(node.getAttr('anchor'))` in `unplacedThreads`. Correctness of the text-thread case checks out: `refreshAnchors` writes only on drift, so there is no write ping-pong, and a thread with no surviving mark stays where it was.

- [P3] Comment marks are reported as 'fmt' in Show editors for any selection inside a commented passage — history.ts:378

- [P3] Reordering identified siblings now reaches the writer's out-of-order path — patch-writer.ts:146 (exposed, not introduced)

## Item 7: comment marks in Show editors
Decision Log 29 states "comment marks are not changes" for "N changes" and history.ts:228-232 implements it (`counted` drops a format run whose every key is a comment). No stated Show editors contract names comments; §4.7 and the function's docstring say "who formatted it". A comment is not formatting, and the sibling exclusion in the same file is the repository's own reading of DL29, so naming the commenter as 'fmt' contradicts the spirit of DL29 and the file's own convention rather than a letter contract. Before the wave the mislabel occurred only when the selection contained the comment's start; now it occurs for any selection inside a commented passage, which is common. The one-line `isCommentKey` exclusion is the right fix (the thread itself already shows who commented); no contract change is needed.
