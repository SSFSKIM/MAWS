## What I checked, and what I could not verify

**Capture lifetime (34b169ebf, f7d12eb58)**
- **Timers and listeners.** `settled` now reads the window's contents once, before arming its timer. After that it only calls `contents.off` and `contents.once`, which are plain JavaScript event methods and still work on destroyed contents. Every read that happens after a destroy (`capturePage`, `setContentSize`) runs inside an async function, so it becomes a rejection rather than an uncaught throw from a bare timer.
- **No double settle, no leaked listener.** Each of `finished`, `failed` and `gone` calls `off()`, which removes all three. A sub-frame `did-fail-load` is ignored without unhooking anything.
- **Callers and the new rejection.**
  - `captureArtifact`: covered by its `Promise.race` against the 20 s guard.
  - The html PDF/PNG exporters, the presentations exporters and the design exporters: their runs go through `runExport`'s `time.within`.
  - Dashboard pictures: the rejection travels through `Promise.all` in `src/artifacts/dashboard/export.ts:159`, then the same `within`.
  - The deadline's own rejection wins each race. It fires in the same timer callback as `abort()`, while the window's rejection takes several hops to arrive (and an `rm` for the deck window).
  - So no caller now shows an error where it used to time out quietly. A destroy from anywhere else, such as quitting the app, now answers at once instead of waiting out the guard.
- **`withDeckWindow`'s abort against its `finally`.** `restrictRequests`' removal only deletes the entry if it still holds this call's own function (`policies.ts:222`), and webContents ids are never reused. So repeating the release can never remove another export's filter. The window destroy is guarded and `rm` uses `force`. If the abort lands during `load`'s `writeFile`, the abort's `rm` and the write can interleave. `use` still settles in that case (`live()` throws), so the `finally`'s second `rm` removes the directory.
