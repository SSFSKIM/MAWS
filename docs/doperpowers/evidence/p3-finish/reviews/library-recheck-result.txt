## Verdict
correct — All three commits close their findings, and I found no regression in existing behaviour. The P3 above is a narrow gap in refilling the mirror; its mechanism is older than the change, and this change adds one new way to reach it.

1. **keyOf.**
   - **Truly away directory: keeps its key.** With an unmounted volume, or a dangling link whose target is also away, `realDirs` holds the last real path and `existsSync` is false, so the key stays the same. The directory stays linked and is never put in `unlinked`, so the mirror keeps owning its files.
   - **Removed or retargeted link while the old target stays on disk: falls back to `S`.** The key becomes `resolve(S)`, and `load(S)` fails as it did before the wave. In `track`, `keyOf(A)` returns `A`, which is not linked, so `cleanUnlinked` runs `remove()` over exactly the files `A`'s manifest names, each under a `realDirsUnder` guard. The manifest file is removed only when it is still the one the mirror wrote.
   - **Pointing back: no owner file is lost or orphaned.** The rewrite refuses any occupied name the mirror does not own. If the cleanup failed part-way, `A` stays pending with the entry at revision -1; relinking takes it off the pending list with the cached manifest, so those files stay owned. Whether every artifact is rewritten depends on the condition in the P3.
2. **Merge.**
   - **Union and revision -1: every file stays owned.** The merged entry holds the files of both entries at revision -1, which `readNow` never treats as current.
   - **Leftovers go only through `write()`'s existing path.** `write()`'s leftover loop (mirror.ts:406-418) removes the names the artifact no longer produces. A case-only variant of a written name is kept by `aliases`. An artifact that is no longer a member goes through `remove()`, which removes the whole union.
   - **No cross-artifact claims.** Mirror slugs end in the artifact id, so a union cannot claim another artifact's names.
   - **Restart before the next save.** The merged manifest lives only in memory until the directory's next save. A restart drops it, but the manifest on disk still describes the directory, so nothing becomes unowned.
3. **Viewer.**
   - **Export now always matches the screen.** `content` is read at `shown.version.seq`, and `contentRef` returns exactly that seq. So an Export by version id exports the same revision that the frame, Reveal, Open externally and Save a copy use. Export goes live only when `row.revision === content.revision`.
   - **The "row above the latest version's seq" state doesn't occur in real data for byte kinds.** At rest, the live revision equals the newest version's seq: `storage.revision` is the maximum seq, every byte write inserts a version, and thinning and "Delete versions older than…" both keep the newest. That state comes from the test fixtures; where it does occur, Export follows the frame.
   - **No steady state where the owner sees the live revision but Export picks an older version.** The one divergence left is the older row lag: a publish not yet reflected in the row makes a followed latest export live.
   - **Nit, not blocking:** the HeaderInput comment at ByteViewer.tsx:394-395 still says the version id is set "when it is not the latest".
