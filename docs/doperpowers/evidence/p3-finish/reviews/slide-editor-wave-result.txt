## Findings
- [P3] Clear stale button focus when the presenter bar is clicked — /Users/new/Developer/GitHub/MAWS/.claude/worktrees/agent-af4cd2993bc56e015/src/artifacts/slides/editor/present/Presentation.tsx:197
  Worker B added the `onMouseDown={(event) => event.preventDefault()}` guard beyond the routing. It means a mouse click never moves focus. It also never clears focus that a bar button already holds, so focus that is stale persists through any number of clicks. Take a presenter who has pressed Tab once (on purpose or not). Focus is now on the first bar button, "←" (Back), because the timer and the count are spans. The presenter then clicks "→" with the mouse and presses Space or Enter to go on. Since b916bb78e, line 167 leaves Enter and Space to the focused button, so the key activates "←" and the show goes back. If "End show" was the focused button, the show ends and its windows close. Without the guard, the click would have moved focus to "→" and the key would have advanced. This only happens once a bar button already has keyboard focus, which is rare in a running show, so the severity is low. The fix is small: in the same handler, also blur `document.activeElement` when it is inside the bar. That keeps the mouse-only case the worker wanted and drops the stale focus. Tab order and screen-reader activation are not affected: an accessibility press sends a simulated click, and cancelling mousedown does not stop that click.

## Answers to the four checks

The next keydown then has body as its target, and the early return at line 167 (`event.target.closest('button')`) does not fire, so the show keys run. One case is outside this fix, and it is not new. Embeds in the current pane are sandboxed iframes ([elements.ts:115-120](/Users/new/Developer/GitHub/MAWS/.claude/worktrees/agent-af4cd2993bc56e015/src/artifacts/slides/canvas/elements.ts#L115)). If the presenter clicks into one, focus moves into the iframe. A later click on the bar is cancelled and the iframe is not inside the bar, so the iframe keeps focus and Space goes to the embed instead of the window listener. The mousedown guard from b916bb78e already behaved this way, and cc8a315a8 does not change it. I am not filing it against this commit. It may be worth a backlog line if embeds in the show are meant to be interactive.
2. **Keyboard use.** Unchanged. A Tab onto a button and then Enter or Space never sends a mousedown. The keydown returns early at line 167, and the button's native activation runs its `onClick`. The tests already in the file still pass in the green log: Space on Black, Enter on End show, and ArrowRight on a focused button.
3. **Blur taking focus from outside the bar.** It cannot. The guard is `focused instanceof HTMLElement && event.currentTarget.contains(focused)`, and `currentTarget` is the `<header className="present-bar">`, which holds only spans and buttons. The bar has no portals and no shadow roots. Each window is its own renderer route (`PresentRoute.tsx`), so `instanceof HTMLElement` is checked in the right realm.
4. **Fidelity of the regression.** It is faithful for Chromium/Electron. `clickOn` focuses the target only when `fireEvent.mouseDown` returns true (not cancelled), then fires mouseup and click. That matches Chromium focusing a button on a mousedown that is not cancelled. Using `Previous.focus()` to stand in for a Tab is a fair setup. The red log shows the reported bug exactly: `expected 'one/0' to be 'two/1'`. The click advanced to two/0, then Space on the still-focused ← went back. The green log shows 28 of 28. After the fix, `pressOn(document.activeElement)` fires on body, the event bubbles to the window listener, and nothing is clicked synthetically because body is not a button.
