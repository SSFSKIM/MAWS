- [P3] Skip TableMap's empty-slot 0 when finding the adjacent cell — /Users/new/Developer/GitHub/MAWS/.claude/worktrees/agent-af4cd2993bc56e015/src/artifacts/document/schema.ts:256-258
  Severity: minor. `TableMap.map` holds 0 for every slot that no cell covers. In a ragged table (rows with unequal cell counts) the sorted list of distinct positions therefore starts with 0. An agent can store such a table through the `:::table` structure form. The editor leaves it ragged until a local edit touches that table, because the guarded table repair skips binding transactions. In that state, Shift-Tab from the table's first cell gets `next = start + 0`, which is the first row, not a cell. `nodeAt` returns the row, so no paragraph is added, and `TextSelection.between` covers the whole first row. I ran a probe against the installed prosemirror-tables with rows [A1, B1] and [A2]: the map is `[1, 7, 15, 0]` and the selection covers "A1|B1". The next keystroke would replace text across both cells. Tiptap's `goToPreviousCell` returned false here, because it walks rows by structure. A cell lost to a span collision is also missing from the map: `indexOf` gives -1 and Tab jumps to the table's start. It only happens with a malformed table and a Shift-Tab from its first cell before any edit in it. Walking sibling cells and rows the way prosemirror-tables' `findNextCell` does fixes it. At minimum, drop 0 from the set.
