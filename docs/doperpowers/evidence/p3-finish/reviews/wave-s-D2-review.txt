## Findings

- [P1] Skip clipped controls in the overlap check, or the document case fails: e2e/support/toolbar-controls.ts:53-56
  **Severity: blocking for the e2e:document-app gate.** The new case at e2e/document-narrow.spec.ts:332 calls `squeezedControls(toolbar)` on the document's Formatting toolbar at 280 px. That toolbar holds two scrolling strips side by side (document/editor/chrome.css: `.doc-toolbar-tools` is `flex: 1 1 0; min-width: 84px; overflow-x: auto`, and `.doc-toolbar-end` follows it). At 280 px the tools strip shows about 84 px. Its other buttons (Bold, Italic, Link and the rest) keep their laid-out rects to the right of what the strip shows, which puts them under the end strip's Comment, Comments, History and Find buttons. `getBoundingClientRect` ignores ancestor clipping, and the pairwise loop runs whether or not `within` is passed. So it will report "Bold overlaps Comments" and similar pairs, for the document and for the dashboard. The product is not affected, but this assertion turns the gate red. The fix is to compare only controls that share a scroll container, or to clip each box to its nearest scrolling ancestor before the overlap and label checks.

- [P2] Keep the toolbar notice from forcing a second row at ordinary widths: src/artifacts/slides/editor/chrome.css:54
  **Severity: should-fix.** `.deck-toolbar` now wraps, and `.deck-notice` (chrome.css:453) still has an automatic flex basis. Flex line-breaking places items at their hypothetical size, which here is the notice's full text width; its `min-width: 0` and ellipsis do not reduce it. So a notice longer than the space left on row 1 moves to a new row, taking the spacer and the zoom controls with it. My rough count of the deck toolbar's fixed controls is about 880 px, which leaves a few hundred px in a typical main tab. Messages such as "A deck holds at most 100 slides: delete one to add another." or "The image could not be uploaded: …" will often be too long for that. Each time one shows, the toolbar grows a row for NOTICE_MS (6 s), the stage moves down and re-fits, and then everything jumps back. Before this change the deck's notice shrank and ellipsized inside its one row. The design workbench already behaved this way; for the deck it is new. Giving the notice a zero basis (e.g. `flex: 1 1 0`) keeps it from ever forcing a wrap.

- [P2] Check typing on a selected element with a Korean input source active: src/artifacts/slides/editor/transform/Overlay.tsx:326
  **Severity: should-fix if confirmed; I could not verify it here.** The only guard against an input method is `isComposing` plus the 'Process' and 'Dead' keys. The stage is not editable, so the input method most likely is not engaged on it (the commit says as much). In that case macOS Chromium most likely delivers the key's layout character, a jamo such as 'ㅎ' or the Latin 'g', with `isComposing` false. The test even pins a Hangul key '한' as typed text. F9 would then type that character raw over the element's text, and the rest of the word would be composed separately in the box: typing 한글 gives something like "ㅎㅏㄴ글" (or "gㅏㄴ글") in place of the heading. The commit's own note claims such keys "enter nothing", which is true only if Chromium reports 'Process' on a non-editable focus. The owner writes in Korean, so this deserves one manual check on the Mac; CDP's imeSetComposition cannot reproduce it. If confirmed, the narrow guard is to ignore jamo keys (U+1100–11FF, U+3130–318F). The Latin-letter case needs the input-sink design planned for S-SLIDE-CLICK-TO-EDIT.

## Verdict
incorrect — Nothing blocks the product, but the new document/dashboard e2e case will fail on false overlaps. Otherwise the CSS keeps a single-row toolbar at the same 36 px (Tailwind preflight makes every box border-box), `.deck-button.deck-text-style` outranks `.deck-button` whichever sheet loads first, and the vitest pattern only matches the new test's `?raw` imports (no other slides or design `?raw` import exists). F9 only acts on a key whose target is the stage itself, never with ⌘ or Ctrl, a composing key, a group, a non-text element, several elements or a read-only stage. Keys pressed before the box mounts land in order, the typed key and the typing after it are one undo step, and Escape returns to the element selected. The three vitest files pass, 56 of 56.
