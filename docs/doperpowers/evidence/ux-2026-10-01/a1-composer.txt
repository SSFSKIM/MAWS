  src/renderer/src/styles/tokens.css:19). User bubble `max-width: min(590px, 85%)` (transcript.css:54).

  Transcript re-pins the end only when its row list changes (`useLayoutEffect(..., [rows])`, src/renderer/src/transcript/view/Transcript.tsx:84-87); whether TanStack's `anchorTo: 'end'` (Transcript.tsx:68)

5. PERMISSION MODE
Facts
- Defaults: a new intent has `permissionMode: null` (src/main/sessions/service.ts:203). MAWS settings v4 have no permission-mode or model default (src/shared/settings/defaults.ts:8-17). With null, no
  `--permission-mode` flag is passed (src/engine-host/launch.ts:203), so the engine uses the user's settings (D-18 "inherited from the owner's settings", docs/charter.md:43;
  src/shared/engine/launch-spec.ts:17).
- The UNSTARTED chip renders null as the literal "default" (`binding.value ?? 'default'`, src/renderer/src/composer/frame/ModeChip.tsx:20,26). ⇧Tab from null goes to 'default'
  (src/renderer/src/statusline/mode-menu.ts:44-47). At launch the record is written with requested=effective='default' (src/main/sessions/setup.ts:201-209) until the status arrives. The host takes the
  init's current_permission_mode when spec mode is null (src/engine-host/session-status.ts:64-65,84-85).
- Gating: unstarted: auto is disabled in the menu when the chosen catalogue row has `supportsAutoMode === false` (bindings.ts:79; src/renderer/src/statusline/ModeMenu.tsx:81-93). Note: haiku's key is
  ABSENT, not false (reads.jsonl seq 3), so this never fires for a live-catalogue haiku (only the built-in list sets false, src/shared/sessions/models.ts:29). Live: `autoUnavailableReason` uses the same rule (mode-menu.ts:52-56). Refusal codes: auto_mode_settings, circuit_breaker, fast_mode,
  model, unavailable (mode-menu.ts:32-38; X6 docs/charter.md:581).
- Live refusal today: `set_permission_mode` error → `{effective, refusal, error}` (src/engine-host/ipc.ts:281-296). The menu shows the words and the mode stays put (mode-menu.ts:81-88). The chip and status
  line show ⚠ plus words (ModeChip.tsx:11,21-26; StatusLine.tsx:119-125). Fixture: set_model haiku then set_permission_mode auto → `error_code:"auto_mode_model"` (pass2/auto-routed.jsonl seq 151-157).
- Launch-time "refusal" is silent: `--permission-mode auto` on haiku yields `current_permission_mode:"default"` with no code (pass2/auto-haiku.jsonl seq 1 args, seq 4;
  spikes/protocol-probe/findings-pass2.md:136). The host keeps requested 'auto' vs effective 'default' with refusal null (session-status.ts:88-96). The record patch then collapses it to requested=effective
  (src/shared/engine/status.ts:76-82), so no warning is ever shown. A breaker or plan-mode move mid-session arrives as `system/status.permissionMode` (session-status.ts:145,169), also without a code.
- `options.autoModeNote` (cannot-hold-auto, gateway local lane) is computed (src/renderer/src/sessions/useSetupIntent.ts:90,183; src/shared/sessions/models.ts:37-46) but rendered nowhere in the composer
  (only consumer is the type, setup-intent.ts:46).
What a "default = auto, fall back to X when refused" rule needs
- A seed: intent.permissionMode='auto' at service.ts:203 (forks copy the source's at src/main/sessions/record-actions.ts:176), or a MAWS settings field. The chip should show the resolved mode, not
  "default" (ModeChip.tsx:26).
- Fallback: the engine gives no code at launch, so decide before launch from the catalogue (`supportsAutoMode !== true`, not `=== false`), or detect requested≠effective after initialize (TrackedStatus,
  session-status.ts:72) before status.ts:82 collapses it. Then set X explicitly and show why. Resume re-passes record.requested (src/main/sessions/launch-mapping.ts:120).
Open questions for the owner
- Fallback mode X when auto is unavailable (Haiku, settings-disabled, breaker): `default` or `acceptEdits`? Pin auto explicitly even when your settings say something else?
