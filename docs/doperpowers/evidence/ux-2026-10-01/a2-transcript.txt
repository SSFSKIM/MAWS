3. Final assistant text reads as a thought (bug level)
Facts (a) the answer/commentary rule
- C6 plan definition (docs/doperpowers/plans/2026-09-28-c6-transcript.md:43): the answer is "the assistant text blocks after the last
  tool use of a turn"; only the answer stays outside the work area.
- Implementation (src/renderer/src/transcript/model/derive.ts:483-494):
    const WORK_ROWS = new Set(['subagent','agent_message','question','plan','request_slot','error']);
    const lastWork = resolved.map((item) => item.kind === 'cell' || (item.kind === 'row' && WORK_ROWS.has(item.row.kind))).lastIndexOf(true);
    ... text with i > lastWork → answer (outside the work area); otherwise → commentary inside the work area.
  Hook executions resolve to items of kind 'cell' (derive.ts:416-427, 462-464; cells.ts:254-268). Notice rows are kind 'error'
  (derive.ts:443-444, 763-765). Both therefore count as "work".
- Wire order: under the owner's settings, every assistant text is followed by hook events. fx:pass3/steer-next.jsonl has a MessageDisplay
  hook at seq 230/231 after the answer's deltas (226-229), the assistant frame at 232, the Stop hook at 236/237, and the result at 239.
  JRNL shows the same: text deltas, MessageDisplay 61/62, assistant 63, Stop 67/68, result 69.
- The text row sits at its first delta's position (derive.ts:268-274), which is before both hooks. lastWork is the last hook, so the final
  answer is classified as commentary: muted and inside the work area. This is the defect.
- Disk-backed history has no hook events: C4's backfill maps none (no "hook" in src/engine-host/fs/backfill.ts). The same turn therefore
  renders correctly after a reload from disk and wrongly live. No test pins answer placement for a turn that ends in hooks;
  journals.test.ts:178-188 checks user rows only.
Facts (b) styling
- AssistantText.tsx:13 chooses .transcript-answer (--fg) or .transcript-commentary (--fg-muted, 62% alpha; transcript.css:91-92). Both
  render at prose size, so commentary reads as greyed-out narration.
- The thinking row is a 12px disclosure; its text is 13px muted, capped at 140px (Thinking.tsx; transcript.css:116-125).
- In screenshot 11 the answer is grey (commentary), placed between "Thought for 1s" and "Ran 2 hooks".
Facts (c) why "to human" and "<to-human>"
- Live: the owner's MessageDisplay hook rewrites the message. JRNL seq 62 hook_response carries hookSpecificOutput.displayContent =
  "\n\u001b[1;36mto human\u001b[0m\n\n…", and the engine's assistant frame (seq 63) carries that transformed text. The streamed deltas
  carry the raw model text "<to-human>Doing fine…</to-human>" (concatenated text_deltas in JRNL). The engine has no to-human logic
  (0 hits in ~/claude-code-bundle/2.1.283/cli.pretty.js).
- MAWS strips ANSI in the reducer (model/ansi.ts:1-3,9-19; reduce.ts:170,470,474), so the completed block is a bare "to human"
  paragraph. During streaming the raw tags are deleted as HTML instead (next bullet).
- Unknown tags in markdown: src/renderer/src/transcript/view/markdown/sanitize.ts:18-20 deletes every mdast `html` node (block and
  inline); rehype-raw is not used (44-48). Text outside the tags survives. Text inside survives only when a blank line separates it
  from the tag, or when the tag is inline in a paragraph.
- Data-loss defect, verified by rendering through the real Markdown component (static and live):
  "<to-human>\nPara1\n\nPara2\n</to-human>" renders only Para2. "<to-human>\nOne paragraph\n</to-human>" renders nothing.
  "<to-human>\n\nPara\n\n</to-human>" and "<to-human>Inline…</to-human>" render correctly. Cause: CommonMark HTML block rule 7 makes a
  tag alone on a line swallow the following lines up to the next blank line, and the whole block is then deleted.
- Sidebar and Overview use a different path: plain first lines, no markdown. Disk-seeded sessions take the first line of the
  transcript's last assistant text (src/main/index/source.ts:245-250; engine-host/fs/summarize.ts:212-217), which is the raw
  "<to-human>" in the owner's older sessions (screenshot 10). Live sessions take firstLine of the completed block
  (src/main/sessions/digest.ts:56-59,133-136), which strips no ANSI; a live row would show the escape-coded label (not seen in a
  screenshot). The tracker row is docs/tech-debt-tracker.md:35.

  assistant message by apiMessageId once turn.ended arrives (X1 turn.ended carries resultText: src/shared/graph/events.ts:105-107).

5. Mid-turn message placement (bug level)
Facts: the three paths
- Enter while busy is Queue: "Sends when this turn ends" (composer/submit/submit-state.ts:54-58,89-92). The queue is MAWS-owned and
  releases the head only at a main-lane turn.ended (src/engine-host/queue.ts:1-13; charter §4.2 "Queue ownership", charter.md:130).
  A queued message genuinely reaches the engine after the turn, so its own next turn after that turn is correct for MAWS's semantics.
- ⌥Enter is Steer with priority 'next' (composer/editor/submit.ts:50-53; submit-state.ts:102-107), and so is the queue row's Steer
  (composer/queue/QueueList.tsx:1-7,62,178). The engine folds the message into the running turn at the next tool boundary. In
  fx:pass3/steer-next.jsonl: the out user frame at seq 46; the engine's replay of it at seq 70, right after the 2nd tool result (69);
  command_lifecycle started at seq 71; six more Bash calls (seq 72-222); then the answer "COUNTED" (232) and the result (239).
- "Interrupt and send" is priority 'now' (submit-state.ts:57,104-107). The engine aborts the running turn (aborted_streaming) and runs
  the message as its own next turn (charter.md:130; journals.test.ts:190-195: 3 turns, stopped, completed, completed). Rendering it
  after the stopped turn matches run order.
Facts: how a steer is placed
- C3 emits user.message at the write (normalizer.ts:501) and dedupes the engine's replay of it (normalizer.ts:341-344). The reducer
  opens a pending turn for it (reduce.ts:451-457). At command_lifecycle started inside the running turn, fold() pushes the message onto
  the running turn's events at that moment (reduce.ts:260-271,411-422). The event therefore sits at the right place in event order:
  after tool #2.
- derive then moves it to the end. A non-opener user.message becomes an item of kind 'steer' (derive.ts:263-264), and
  `if (item.kind === 'steer') answer.push(item.row)` (derive.ts:489) puts every folded prompt into the answer list, which is emitted
  after all work rows (derive.ts:514-516). Expanded, the steer bubble renders after the last tool call, just above the answer, and each
  new work row inserts above it. Collapsed, it renders right under "Worked for …".
- This is the defect: the bubble is keyed to the answer list instead of its event position. The row's `steer: true` flag (derive.ts:212)
  is not used by User.tsx, so nothing marks the bubble as steered.
- The divider's aria-controls stops at the first user row (Divider.tsx:36-45), which reflects the same assumption.
Facts: disk divergence (code read; not verified on data)
- C4's backfill emits turn.started for every non-meta user record (fs/backfill.ts:124-131). A turn.started with no pending turn closes
  the open turn as completed and opens a new one (reduce.ts:388-399). If the engine writes the steer as an ordinary user record (the live
  replay at steer-next seq 70 is a `user` frame with the uuid and a timestamp), a reloaded session splits the turn at the injection point.
  Live and reload then disagree. No fixture shows a main-transcript JSONL with a steer.
- Prompts the terminal itself queues mid-turn are written as attachment {type:'queued_command', origin} records
  (~/claude-code-bundle/2.1.283/cli.pretty.js:940986-941007), and the engine treats a human-origin one as a prompt (cli.pretty.js:43772-
  43774). C4 drops every attachment in a main transcript (backfill.ts:96-97,109-118), so such prompts from terminal-started sessions
  never render in MAWS.
Likely cause / what a fix touches
- derive.ts:488-494: keep a steer at its event position among the work items. Make it visible even when the turn is collapsed, for
  example by splitting the work area at the steer (work before it under the divider, the bubble, then the work after it under its own
  fold), and render the `steer` flag (User.tsx). Pin it with fx:pass3/steer-next.jsonl: the bubble must come between the 2nd and 3rd
  Bash calls.
- Probe what a 'next' steer and a terminal queued prompt write to the main JSONL, then make backfill match the live placement.
Open questions for the owner
- Did the reported case use Enter (Queue, delivered at turn end by design), or Steer/⌥Enter? If Enter should behave like the terminal's
  queue (injected at the next tool boundary), that changes charter §4.2 and the §5.4 labels: a product decision.
- When collapsed, should a steer split the turn into two folds, or show the bubble inline with the work around it collapsed?
