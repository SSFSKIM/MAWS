0. BOTTOM LINE
- ClaudeUsage's menu-bar item already is "one easy universal usage control": a dot and one number, and a panel listing every account with its
  limits. Each account has "Route requests here", the one control that changes where MAWS's gateway sessions draw quota from (every D-19
  session goes through ClaudeUsage's relay).
- ClaudeUsage has no external control channel: no URL scheme, CLI, AppleScript, XPC or HTTP control route (2.6). A MAWS copy of the panel can
  show everything and control nothing: every button would be today's hand-off (`open -b` plus a toast telling the user to click the menu bar).
  Writing pins.json does not work (4.3).
- Recommendation: make ClaudeUsage's own item the single usage surface. In MAWS: remove `5h`, `7d` and `auto` from the status line; keep ctx and
  $ (or move them, Q3); re-home the per-session route switch that lives in the usage popover today; retire or narrow the duplicates
  (near-limit banner, Accounts tab). Add about five lines to ClaudeUsage (a reopen handler) so MAWS's existing "Open ClaudeUsage" drops its
  panel down. Build a MAWS-side copy (toolbar pill or Electron Tray) only if the owner needs control from inside MAWS; that also needs a
  control API in ClaudeUsage (4.4).

2.4 What each control does to routing and pins
- Route requests here: AppModel.routeRequests (AppModel.swift:1690-1726) → Gateway.selectAccount (CUG/Gateway.swift:424-428) →
  Router.selectAccount (CUG/Router.swift:105-125). Sets a manual drain target, persisted to pins.json as drainTarget and
  drainTargetIsManual=true (CUG/SessionPins.swift:3-40, :170-203).
  - Overrides the weekly-resets-soonest election (Router.swift:24-36, :252-270). Existing sessions move at their next request, which costs a
    prompt-cache rebuild (PanelView.swift:629; README.md:241-256).
  - Survives a restart; ends only when the account becomes unusable or is removed (Router.swift:138-147). The panel has no "back to
    automatic" button. Offered only when `isRoutingReady`: the routing preference is on and settings.json points at this port
    (AppModel.swift:1670-1688).
- Route toggle: setRoutingEnabled (AppModel.swift:1728-1766) edits three keys in ~/.claude/settings.json and needs launchd supervision. MAWS
  sessions do not depend on it; each launch carries its own env (charter D-19, line 44). But while it is off, the panel hides Route-here and
  the menu-bar number follows the signed-in account (:2569-2577).
- Switch this Mac: beginSwitch (:908) runs Claude Code's own `claude auth login`. It signs out running sessions; the confirm says so
  (PanelView.swift:653). Add account (:948) and Reconnect (:974): isolated sign-ins in a Chrome profile (sheet: CUS/SwitchSheetView.swift).
  Remove (:834) drops the saved sign-in and its pins (Router.swift:138-147).
- Quit: suspendRoutingForQuit removes the routing keys so sessions are not stranded (CUS/AppDelegate.swift:38-48, AppModel.swift:1768-1777).
2.5 Keyboard: no shortcuts and no global hotkey (grep for keyboardShortcut/keyEquivalent: none); standard focus traversal only (panel-layout.md
  asks it to "preserve keyboard access").
2.6 External interfaces (this decides what MAWS can control)
- Info.plist has no CFBundleURLTypes. No AppleScript, XPC or distributed notification (grep: none). AppDelegate has no
  applicationShouldHandleReopen (grep: none), so `open -b` activates the agent but opens no panel (also observed in the C11 plan, :566).
- Relay: GET /api/hello answers an empty 200 (CUG/RequestPipeline.swift:201-205). GET /v1/models is served only while OpenRouter is configured
  (:175-179). Any other non-/v1 path is forwarded verbatim upstream (:213-220). No endpoint exposes usage, accounts or routing state, or
  accepts a selection.
- Notifications: alerts on severity rises, at a hard 95% (Core Logic/ThresholdTracker.swift:46), and on window resets (README.md:578-586).

4. WHAT "COPY THE WHOLE CLAUDEUSAGE MENUBAR PATTERN INTO MAWS" CAN MEAN
4.1 Three readings. Lead pick: A; B is the upgrade if Q1 says so.
- A. "The top usage menubar" is ClaudeUsage's own macOS menu-bar item. MAWS stops showing usage per session and points to that item. Fits
  "the user only has to look at the top usage menubar"; zero duplication. Gap: MAWS cannot open that panel today.
- B. A MAWS-internal "top menu": a pill in MAWS's own toolbar, which is the title bar (R app/Toolbar.tsx:1-4, :73-80; the right cluster
  beside "Session actions" and "Toggle right panel"). It shows "● 83" for the drain target and opens a Radix popover in ClaudeUsage's panel
  geometry, reusing accountsViewModel. Still works when MAWS is fullscreen, where the macOS menu bar hides. Controls are hand-offs only
  unless ClaudeUsage gains an API (4.4).
- C. An Electron Tray, i.e. a second macOS status item. Electron 44.4.5 (M/package.json:87) offers Tray.setTitle(text,
  {fontType:'monospacedDigit'}) for "83" plus a template or colour dot image. On click: a frameless `type:'panel'` BrowserWindow placed under
  tray.getBounds() and hidden on blur (the NSPopover analogue), or setContextMenu(Menu) as a native NSMenu with radio items per account (no
  bars). While ClaudeUsage runs, this puts the same number twice in the menu bar. Not recommended unless MAWS absorbs ClaudeUsage (line 655).
4.2 Data MAWS already has to fill a copy
- accounts.json: email, displayName, planLabel, rateLimitTier, needsReauthentication, credentialOwnership, lastSeenActive (organizationUUID
  present but unread). pins.json: drain target, manual flag, per-session pins, giving saved-session counts and each open session's account.
  history: percent and resetsAt per window, so the most-binding % = max over windows. Plus relay up or down.
- Missing versus ClaudeUsage's panel: severity colours; the signed-in ("active") account (Keychain); machine chips (SSH remotes); serving
  chips and the health line (in-memory telemetry; gateway-requests.jsonl exists but is ClaudeUsage's private log, about 20 MB/day);
  projections (in-memory BurnRateEstimator; MAWS has its own paceLine in R gateway/routing-facts.ts); Codex and OpenRouter sections
  (codex-accounts.json and openrouter.json unread); locked-credential notices; the routing-toggle state (gateway.json plus settings.json); a
  way to force a refresh.
4.3 Writes: FLAG
- pins.json belongs to ClaudeUsage. It is loaded only at SessionPins init (CUG/SessionPins.swift:65-71), and the live actor rewrites it from
  memory atomically on a 1 s coalesce (:170-203). A MAWS write would be ignored by the running router and overwritten at the next flush.
- Taking effect would need a ClaudeUsage restart, which MAWS must not trigger on its own (the spirit of D-16) and which would cut routed
  sessions. gateway.json and settings.json are the same story, and D-19 puts accounts in ClaudeUsage. So MAWS has no file-level control path.
4.4 Ways to give MAWS real control. Each is a change in the owner's ClaudeUsage repo, not the engine, so D-1 is untouched; it is still the
    owner's call.
- (i) Smallest: add applicationShouldHandleReopen in AppDelegate that calls statusItemController.togglePanel. The existing `open -b`
  (claude-usage-app.ts:78) then opens the panel, so every MAWS "Open ClaudeUsage" drops the real panel down and the toast becomes optional.
  About 5 lines; no MAWS change. Assumption to verify by probe: a running LSUIElement app receives the reopen event from `open -b`.
- (ii) A URL scheme `claudeusage://panel` and `claudeusage://route?account=<uuid>` (CFBundleURLTypes plus a handler calling routeRequests).
  Any local process could then select an account; non-destructive, but it should still be confirmed in ClaudeUsage.
- (iii) A loopback control API on the relay, intercepted before the verbatim forward (RequestPipeline.swift:213-220) the way /api/hello is.
  Example: GET /claudeusage/state (accounts, severity, drain/manual, serving, health, routingReady) and POST /claudeusage/route {uuid},
  guarded by a token file in CUD. This is what B or C need to "control things", and it would replace MAWS's file reading. Route-here would
  still be the only routing control; "back to automatic" does not exist in ClaudeUsage either.
