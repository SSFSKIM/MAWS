BOTTOM LINE
- A "mod" is a Claude Code plugin whose hooks/hooks.json names a hooks module: TypeScript or JavaScript exporting
  register(on), run by the engine inside its own hooks worker. Mods are not a separate format. The phrase "Claude Mods"
  appears nowhere in either engine build.
- There is no "Desktop mod" distinct from a "terminal mod". One plugin draws on whichever surface asks. The hook reads
  e.surface ("terminal", "desktop", "vscode", "mobile") and builds from that surface's element table.
- Claude Desktop does not load, sandbox or toggle mods. The engine does all of that. Desktop 2.16120.0 added one thing:
  a client of a new engine wire protocol, the remote UI surface protocol. Over it Desktop attaches as surface "desktop",
  asks the engine to run the ui.render hooks for each place it draws, and draws the plain-data tree it gets back.
- That protocol is part of the engine's stream-json control channel. MAWS already owns that channel, so MAWS can be a
  "desktop" surface too, with no patching (D-1 holds). The engine MAWS runs (2.1.287) has the protocol, and since 2.1.286
  the function-hooks gate defaults to on.
- In MAWS today, the owner's own mods (doperpowers: to-human view, agents pane, kairos switch) already load and run their
  engine-side hooks. Their UI never appears: MAWS never asks ui_render, and the ui_* pushes they cause are dropped as
  frame.unknown.
- Recommendation: honour mods by implementing the remote-surface protocol, in slices. First a probe plus decoding the
  notice pushes (about 1.5 days). Then the non-transcript sites: panes, band, footer, presses (about 3 to 4 days).
  Then the transcript sites (about 4 to 6 days). Defer Client surface modules. Charter D-9 has to be ruled on first:
  this is an extension surface.

2.5 Sandboxing on Desktop
- The engine sends only plain data, validated before it crosses:

- Code runs on the surface only for `Client` surface modules. Desktop runs them in an iframe with

3. THE CLI'S SIDE

3.1 Packaging: one plugin format with two hook kinds
- hooks/hooks.json has `hooks`, the classic command-hook matchers, and `modules`, at most one hooks module path. It must
  have one or both (SPEC/27-hooks.md:1536-1559).
- Module files must be .ts, .tsx, .jsx, .js, .mjs, .cjs, .mts or .cts, and each is an ES module (reference.md:14).
- A refused key records an earlier design: "hooks.json `surface` is gone: name the module in the Client element"
  (SPEC/27-hooks.md:1552).
- Classic hooks: 33 events, from settings.json `hooks`, plugin hooks.json, managed policy and the session
  (SPEC/27-hooks.md:167-181, 1564-1690).

3.2 Function-hook events. The full contract is the d.ts; this is the map.
- Engine events (d.ts EngineEventOf, 3543-4234):
  - tools: tool.call, tool.check, tool.describe
  - UI: ui.render, ui.resolve, ui.press, ui.input, ui.select, ui.message, ui.scroll, ui.focus
  - agents: agent.offer, agent.spawn
  - prompt: prompt.submit, prompt.fill, prompt.suggest, prompt.edit, prompt.section, prompt.context, prompt.attachment
  - commands and config: command.run, command.describe, config.set, config.describe
  - other: skill.prompt, attribution.text
  - session: session.start, session.receive, session.send, session.compact, session.attach, session.detach,
    session.measure, session.end
  - plugin.register, engine.create
  - turn: turn.start, turn.step (streaming), turn.complete
- Every settings hook event is also hookable as `classic.<Event>`, for example classic.SessionStart
  (d.ts:1060-1067; reference.md:27).
- The `$` API (d.ts OpEventOf, 6015 onward):
  - model.complete, model.classify, model.fork
  - audio.play, audio.speak
  - mcp.call
  - session.*
  - turn.abort
  - prompt.read
  - tool.list, tool.register
  - command.list, command.register
  - config.list
  - agent.list, agent.register
  - ui.toast, ui.status, ui.log, ui.notice, ui.invalidate, ui.open, ui.close, ui.panes, ui.copy, ui.blit
  - plus $.fs, $.process, $.store, $.state and $.clock (reference.md:98-111)
- Runtime: one worker thread, "hooks", hosts every plugin; each module runs in a vm context. Each hook has a time
  budget, and a failed hook is skipped (SPEC/27-hooks.md:4713-4760; reference.md:65-68, 100-108).

3.3 Gate
- 2.1.283 to 2.1.285: GrowthBook flag `tengu_plugin_hooks_modules`, default false, and the env var
  CLAUDE_CODE_ENABLE_FUNCTION_HOOKS overrides it (B283 cli.pretty.js:72589; SPEC/27-hooks.md:5638-5681; the same code
  in the 2.1.284 and 2.1.285 binaries).
- 2.1.286 and 2.1.287: `var RYe="tengu_plugin_hooks_modules";var mUt=!0;var YJ=()=>k(RYe,mUt)` (S287:332577). The
  default is now ON, and this accessor no longer reads the env var. The var still appears in the engine's env-name
  lists (S287:326351, 330319).
- Built-in plugins' modules load regardless of the flag (SPEC/27-hooks.md:5671-5681).

3.4 Where mods load from
- installed plugins
- `--plugin-dir`
- `CLAUDE_CODE_PLUGIN_DIRS`: process env, or the env block of ~/.claude/settings.json, never a project's. This is the
  route "where no flag can be given (a session the desktop app or an SDK host starts)" (reference.md:61).
- skills folders (~/.claude/skills/<name>, .claude/skills/<name>) (reference.md:61)
- the session's dev-mods folder, after the person consents (SKILL:16; SPEC/27-hooks.md:5700-5737)

Hot reload and errors:
- Interactive sessions watch these folders. SDK and desktop hosts watch only with CLAUDE_CODE_PLUGIN_DIR_WATCH=1, and
  then "its reload lines reaching the host as `ui_log` messages" (reference.md:62).
- In a stream-json run, a failed function hook goes to the debug log only (reference.md:67).

3.5 The dev-mods consent dialog (the "Mods" dialog)
- Header "Mods". Question "Enable hot reloading for this session?" Choices "Not now" and "Enable for this session".
  Body: "Mods in ... load ... and reload when their files change. They run with your permissions."
  (SPEC/27-hooks.md:5716-5728; S287:151514-151515, 353489)
- It is person-only, and off where nobody can be asked, as under `claude -p` (SKILL:16).
- Refused when any of these holds: hooks_modules_off, all_hooks_disabled, sideload_disabled, local_dirs_blocked,
  managed_hooks_only, hooks_disabled_in_settings, safe_mode, bare_mode, untrusted (SPEC/27-hooks.md:5710-5716).

3.6 Tooling
- `claude plugin validate`, `claude plugin test`, `/plugin-types` (reference.md:3-5, 40-45, 68;
  SPEC/27-hooks.md:5683-5697). There is no `mod` command.

3.7 The remote-surface wire protocol. This is what Desktop speaks and what MAWS would speak.
- Arrival: grepping the binaries for "ui_surface_v1" gives 0 hits in 2.1.283 and 2.1.284, and 2 hits each in 2.1.285,
  2.1.286 and 2.1.287. The protocol arrived in 2.1.285, installed 2026-09-29. The 2.1.283 bundle has only the subtype
  table (cli.pretty.js:725382). Every schema line is marked @internal.
- Capability: system/init `capabilities` includes "ui_surface_v1" when the gate is on and the session is not on a
  remote transport (S287:353067 `TRn`; 353683). When the gate is off, every ui_* request is refused with "Unsupported
  control request subtype" (S287:353067 `Roo`, 353733, 353400).
- Host to engine control requests (S287:134161-134175; validation messages 287504-287519; semantics 264584-264685):
  - ui_attach: {surface: desktop|mobile|vscode, client_id, viewport?, answers?}. Joins the roster and raises
    session.attach (S287:264588).
  - ui_detach
  - ui_render: {surface, client_id?, component, instance_id, props, viewport?, on_screen?, content_rows?, keyed?}.
    Runs the ui.render chain and answers {tree, hooked, props core was handed, client_modules}. With no module loaded it
    answers {tree:{type:"engine",ref:0}, hooked:false} without running anything. The host re-asks on ui_invalidate
    (S287:264578, 264602-264609).
  - ui_press, ui_input, ui_select: name an element by {plugin, handle} (S287:264617, 264656, 264669)
  - ui_panes, ui_pane_show, ui_pane_focus, ui_close (S287:264676-264687)
  - ui_scroll, ui_focus: Pane or AbovePrompt only
  - ui_prompt_edit
  - ui_client_module, ui_client_press, ui_message: Client frames, "the desktop's alone today" (S287:264627-264645;
    d.ts:3455-3460)
- Engine to host system pushes:
  - ui_invalidate, ui_log, ui_toast, ui_status (S287:142651-142654, 263970-263979)
  - ui_panes, ui_scroll, ui_focus (S287:263998-264008)
- Engine to host control requests: ui_copy, ui_prompt_read, ui_prompt_fill, ui_prompt_suggest. They go only to a client
  whose ui_attach named them under `answers`, with a 5 s timeout (S287:264587, 264714-264740).
- Surface names: the wire accepts only desktop, mobile and vscode. The surface is "What the client declared, a rendering
  fact and not a trust signal" (S287:264584).

3.8 Mods vs plugins
- Mods are plugins. There is no new manifest and no `mod` command. The only new location is the per-session dev-mods
  folder, and it is loaded as a plugin directory.

4. WHAT MAWS ALREADY HONOURS

4.1 Mods already load in MAWS sessions (expected from the source; not probed)
- MAWS launches with `--setting-sources user,project,local` and `--include-hook-events`
  (M src/engine-host/launch.ts:48-59).
- It passes CLAUDE_* env through (launch.ts:84-107) and sets CLAUDE_CODE_ENTRYPOINT=sdk-ts (launch.ts:112). Built-in
  plugins are skipped only for the "local-agent" entrypoint, and modules have no entrypoint gate (SPEC/27-hooks.md:5638-
  5681; B283 cli.pretty.js:392358).
- The engine is 2.1.287: the gate defaults on, and the owner's settings also set the env var.
- So installed plugins' hooks modules load, the owner's doperpowers modules among them, and every engine-side hook runs.

4.2 Hook visibility
- MAWS shows settings and plugin command hooks from hook_started and hook_response frames. It hides successes and shows
  failures as notices (M src/renderer/src/transcript/model/hooks.ts:47-60; derive.ts:451-459;
  src/engine-host/fs/backfill.ts:389-392).
- Function hooks emit no such frames. A failing mod in a stream-json session goes only to the engine's debug log
  (reference.md:67), so MAWS cannot show it today.

4.3 ui_* frames today
- ui_toast, ui_status, ui_log, ui_invalidate and ui_panes are system subtypes. They fall to the default branch:
  `frame.unknown`, journaled and never shown (M src/engine-host/normalizer-system.ts:155-156).
- MAWS records init `capabilities` (normalizer.ts:222; src/shared/graph/events.ts:98), so "ui_surface_v1" would land in
  the graph.
- All protocol fixtures are 2.1.283. All 123 init frames carry ["interrupt_receipt_v1","interrupt_cancel_queued_v1",
  "msg_lifecycle_v1","mcp_read_resource_v1","mcp_tool_ui_meta_v1"], without ui_surface_v1
  (spikes/protocol-probe/fixtures).

4.4 Host hooks are unrelated
- M src/engine-host/host-hooks.ts:1-4 is the SDK `hook_callback` mechanism (initialize.hooks). No production launch uses
  it (docs/charter.md:346). It is not the mods mechanism.

4.5 Charter
- D-1 (docs/charter.md:26) forbids patching. Honouring mods needs no patch: it is control requests on the wire MAWS
  already owns.
- D-5 (:30): "owner-specific workflow as later plugins".
- D-9 (:34): "No extension surface in P0 ... a plugin API for side-panel tabs and commands mirroring Claude Code's own
  plugin host shape ranks above app-specific tools".
- :80: the to-human lane "arrives with the renderer extension API".
- :89: the extension model.
- :608: the extension model is deferred.

4.6 Which Desktop hook points MAWS already sees

| Desktop handles | What reaches MAWS today | What MAWS does with it |
|---|---|---|
| ui_toast, ui_status (EngineNoticesBridge) | Same frames on stdout | frame.unknown, dropped |
| ui_log (transcript hook_notice) | Same frame | frame.unknown, dropped |
| ui_panes push (EnginePanesBridge) | Arrives when a plugin opens a pane, e.g. the agents pane | frame.unknown, dropped |
| ui_invalidate | Arrives | frame.unknown, dropped |
| Every ui.render site (band, footer, panes, transcript rows, spinner, question cards) | Nothing: MAWS never sends ui_render, so the engine never runs those hooks for MAWS | — |

Engine-side effects MAWS sees through existing events:
- tool.call denies or rewrites: tool results and permission_denials.
- tool.check: the can_use_tool request cards.
- prompt.submit rewrites: the replayed user message.
- $.prompt.submit: a turn with plugin origin.
- $.command.register: commands_changed (normalizer-system.ts:54).
- $.tool.register: init tools (mcp__<plugin>__<name>).
- $.agent.register: init agents.
- classic.*: same timing as settings hooks, but no hook frames.

5. ASSESSMENT

(a) What a Desktop mod is
A "mod" is an ordinary Claude Code plugin: .claude-plugin/plugin.json plus hooks/hooks.json, whose `modules` entry names
a TypeScript module exporting register(on). The engine runs that module in its own sandboxed hooks worker, with no DOM
and no Node. Through on(event, matcher, ($, e, next) => ...) the module can:
- block, rewrite or answer tool calls, prompts, prompt sections, commands and subagents
- register tools, agents and slash commands
- run timers, model calls, file and process work
- draw UI by returning plain-data element trees from ui.render for named render sites (transcript rows, the band above
  the prompt, the footer mode slot, the spinner, side panes), plus toasts, status lines and log lines
"Desktop mod" is a misnomer: the same plugin draws on every surface. Claude Desktop 2.16120.0 is one surface. It attaches
to the engine over the remote-surface control protocol (new in engine 2.1.285), asks ui_render for each place it draws,
renders the validated tree natively, and runs only `Client` sub-modules in a sandboxed iframe.

(b) Hook points and capabilities, with MAWS status
Key: AS-IS = runs in MAWS today with no change. DECODE = needs only decoding of a push MAWS already receives. SURFACE =
needs MAWS to attach and ask ui_render (desktop surface). NO = MAWS cannot do it, or should not.

  - New X1 events: src/shared/graph/events.ts

    - ui_log as a notice row: src/renderer/src/transcript/model/derive.ts beside hooks.ts
  - Also surface init plugin_errors and plugin_warnings, which MAWS already carries (charter :703).
- SURFACE, engine host:
  - Add the ui_* subtypes and response schemas to the control catalogue: src/engine-host/controls.ts and
    src/shared/wire/control.ts.
  - Send ui_attach {surface: "desktop", client_id: "maws-<windowId>", viewport, answers} once init carries
    ui_surface_v1: src/engine-host/session.ts, beside the initialize handshake.
  - Answer ui_copy and ui_prompt_*: src/engine-host/normalizer-controls.ts:88 currently turns unknown engine requests
    into frame.unknown.
  - Map ui_invalidate, ui_panes, ui_scroll and ui_focus to events.
  - Add an X2 command set for renderer asks: src/engine-host/ipc.ts and rpc.ts.
- SURFACE, renderer:
  - One element renderer, for example src/renderer/src/engine-surface/: Box and Text as Ink-style flex in character

  - Pane: a PanelTool "plugin-pane" per roster entry in the X5 host (src/renderer/src/panel/host.ts, PanelHost.tsx).
  - AbovePrompt: a band slot in src/renderer/src/composer/Composer.tsx above frame/Frame.tsx.
  - SessionMode and PromptHint: frame/Toolbar.tsx or the status line.
  - Prompt read, fill and suggest: src/renderer/src/composer/editor/controller.ts.
  - AskUserQuestion: src/renderer/src/request-card/.
  - Transcript sites: src/renderer/src/transcript/view/rows/Row.tsx (User.tsx, AssistantText.tsx, Cell.tsx, Group.tsx,

  - Spinner: the live activity and thinking row.

(d) Risks
1. "A mod written for Desktop's DOM or IPC" does not exist.
   - Mods never touch Desktop's DOM or IPC. They return plain data the engine validated (S287:264579).
   - The real fidelity risk: Box and Text use Ink's cell-based flex vocabulary (d.ts:738-790; viewport in character
     cells, d.ts:8994-9000). MAWS must lay these out acceptably in DOM, as Desktop does.
   - A mod can branch on e.surface === "desktop". By claiming "desktop", MAWS inherits whatever the mod assumes about
     Claude Desktop's layout. "desktop" is still the right claim: the wire accepts only desktop, mobile and vscode, and
     desktop has the richest table, the one mods are tested against.
2. Sandboxing.
   - Plain-data elements are safe if drawn as text nodes and allow-listed props. The engine's own rules: text never
     markup; https and http://localhost links; Markdown links https, http or file only (S287:264575).
   - Svg needs a data: img or a sandbox="" frame. MAWS's CSP already allows data: images (M src/main/csp.ts:12-17).
   - `Client` modules execute plugin-authored JavaScript in MAWS's renderer. They need Desktop's
     sandbox="allow-scripts" srcdoc frame, a CSP that admits the importmap of blob: scripts inside the frame, and a
     reimplementation of Desktop's private boot and frame protocol (c95e4d2cf:2380-2450, 2550-2575). That protocol is
     not documented outside Desktop's code. Defer.
   - The mod's engine-side power ($.fs, $.process, model calls) is the engine's existing plugin trust: "They run with
     your permissions" (SPEC/27-hooks.md:5726). MAWS adds no privilege by drawing. It should label what a plugin drew,
     as Desktop does ("Plugin panes", "{plugin} has not drawn in this pane").
3. ~/.claude stays read-only.
   - Honouring mods writes nothing there. The engine reads plugins itself, and enabling or disabling a mod is enabling
     or disabling its plugin through the engine (MAWS's plugins widget and reload_plugins).
   - A MAWS-side "don't draw plugin UI" preference belongs in MAWS's userData. It simply skips ui_attach.
   - The dev-mods consent and its folder are the engine's writes, made at the person's consent. MAWS neither causes nor
     performs them.
4. Protocol churn.
   - Everything is @internal and "EARLY ACCESS ... may change between releases without notice" (d.ts:3).
   - The protocol is 5 days old (2.1.285), and the gate default flipped in 2.1.286.
   - Under D-1 as amended, MAWS runs whatever engine is installed. The defences:
     - gate on the versioned word "ui_surface_v1"
     - validate every frame with zod
     - fall back to MAWS's own drawing whenever an answer is missing or malformed (the `engine` node is that contract)
     - never fail a session over it
     - record 2.1.287 fixtures: today's are all 2.1.283
5. Transcript model mismatch (the largest design cost).
   - MAWS's presentation model folds commentary into the work area and groups activity its own way (X3; owner decision
     T2 in docs/doperpowers/plans/2026-10-01-ux-fundamentals-waves.md:289-293).
   - Mods hooking AssistantMessage or ToolGroup assume the engine's row model. The owner's to-human mod hides and folds
     rows across runs (README.md:27-42).
   - MAWS must choose a mapping, for example a mod's tree replaces the row's body and an empty tree hides it, and
     reconcile it with virtualization and its own folding.
6. Cost.
   - Every mounted instance is re-asked on each ui_invalidate, at most once per 100 ms per plugin (S287:263970).
   - Ask only virtualized, visible rows. Report on_screen, which is coalesced to the frame. Stop asking a component that
     answered hooked:false until the next invalidate (S287:264607).
   - With no modules loaded, answers are free (S287:264602).
7. Scope.
   - D-9 says no extension surface in P0. Implementing the remote surface is the extension model arriving through the
     engine, so it needs the owner's ruling and a dated Decision Log entry.
   - It also partly answers D-9 as written: Claude Code's own plugin host shape, side panes and commands. Its UI half is
     available to MAWS for the price of a renderer.

(e) Recommendation and size

Honour mods by becoming a "desktop" surface of the engine's remote-surface protocol. Do not build a "Desktop manifest":
none exists. Take it in slices. Estimates are agent-days.

| Slice | Content | Size |
|---|---|---|
| R0 | A 2.1.287 probe recording fixtures: init capabilities; ui_attach, ui_render and ui_press round trips against a scratch test plugin loaded with --plugin-dir from spikes/, not ~/.claude; ui_toast, ui_status, ui_log, ui_panes and ui_invalidate pushes; whether the "Mods" consent reaches an SDK host | 0.5 |
| R1 | DECODE: toast, status and log pushes to MAWS's toasts, status line and transcript notices; plugin load errors shown | about 1 |
| R2 | SURFACE core: attach; the element renderer without Client; Pane as panel tabs; the AbovePrompt band; SessionMode and PromptHint; press, input and select; close, scroll and focus; invalidate; answers to ui_prompt_read, ui_prompt_fill, ui_prompt_suggest and ui_copy | 3 to 4 |
| R3 | SURFACE transcript sites: UserMessage, AssistantMessage, ToolUse, ToolResult, ToolGroup, CommandOutput, AskUserQuestion, Spinner, with the engine-props adapter and the mapping onto X3 | 4 to 6 |

What each slice delivers:
- R1 is free of design risk and is useful at once: the owner's mods' toasts and status lines appear.
- R2 brings the owner's agents pane and kairos switch into MAWS.
- R3 brings the owner's to-human view into MAWS through their own mod. That is charter §3's to-human lane (:80) without
  MAWS-specific code.

Defer:
- Client surface modules (Desktop-private frame protocol; about 2 to 3 days if ever)
- mobile and vscode surfaces
- terminal-only elements

Total: about 9 to 12 agent-days. The first useful cut, R0 to R2, is about 5.

Order:
- R0 and R1 now. They are inside current scope: they decode frames MAWS already receives.
- R2 as a charter child once the owner rules on D-9.
- R3 after R2 lands and the protocol has held across a couple of engine releases.

Alternatives:
- Only document that engine-side hooks already apply. This is right if the owner keeps D-9 closed for P0. The owner's
  own mods are mostly UI, so they would stay invisible in MAWS.
- Wait. This is reasonable only if churn worries outweigh value. The capability word lets MAWS ship R2 safely now.

(f) Not verified in this session, and what settles it
- That a MAWS (sdk-ts, -p stream-json) session's init carries "ui_surface_v1" on 2.1.287, and that ui_* pushes arrive
  without any ui_attach. Inferred from S287:353683 and the "push from a headless session" descriptions. Settled by R0.
- That 2.1.286 and later fully ignore CLAUDE_CODE_ENABLE_FUNCTION_HOOKS. Only the accessor's literal text was read. The
  owner's env sets it anyway.
- That the dev-mods consent reaches an SDK host. It goes through a person-only question (S287:353491). SKILL:16 says it
  is off where nobody can be asked.
- Desktop's element-to-DOM layout details. Only the switch sites were read, not each element's styling.
