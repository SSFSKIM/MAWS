## Brief (verbatim at dispatch)

**Purpose.** In C12's §10 pre-run, two of four row Resumes of one session sat at the engine's `initialize` for 120 s with no frame back, while the same spawn from a node script answered in under 0.6 s every time. The owner's sitting follows this work, so a resume that never becomes ready must be either explained and fixed or bounded so the owner sees a failed launch with its reason and can resume again. Deliverable: the cause found or bounded by evidence, the fix, and a record in this ledger.

**What is known** (`docs/doperpowers/evidence/c12/initialize-stall.txt` is the primary source; read it first):
- Both stalled journals held the `reconnect { attempt 1/1, trigger: user }`, `spawn` and `relay_health` meta rows and the `out` row of the `initialize` control request, then nothing in: no `initialize` response, no SessionStart hook frames, no stderr rows (the host does journal stderr lines, `src/engine-host/session.ts:622-630`, so stderr was empty, not lost). The exit row at about 120 s was the test's own cleanup (`SIGTERM`, reason `stop`).
- The host does bound `initialize`: it is in the `long` request class, 120 s (`src/engine-host/controls.ts:44,84`), the same bound as title generation. The test gave up at the same 120 s, so the host's `init_failed` path (`session.ts:778-807`, which carries the stderr tail and runs the ladder without `end_session`) was never observed. Two things follow: the earlier note "the host has no initialize timeout" is wrong in letter but right in effect, since a handshake that normally answers in half a second waits two minutes; and after `init_failed` the row's state must be checked (does the owner get a resumable row with the reason, as C10's failed unstarted tab does?).
- The binary was the installer's source (`MAWS_E2E=1` bypasses custody); args and environment names are listed in the evidence file; cwd the deep session's worktree; the Resume came 62 to 157 s after the previous process exited, so no immediate stop-then-resume race.
- The standalone reproduction (same binary, config dir, cwd, args, the host's constructed variables) answered five of five in 433 to 576 ms, but ran from a node script with an allowlisted shell environment rather than MAWS's login-shell capture, and not from the packaged engine host. Those three differences (the parent process, the captured login-shell values, timing) are the uncontrolled ones.

**Hypotheses, cheapest first.** Test each and record the result even when negative.
1. Host side, the reader or the writer. On the reconnect path, is the new transport's stdout reader attached before the `initialize` write, and is the `OutboundWriter` the new process's (one per process, `session.ts` header) rather than a stale one bound to the previous process's closed stdin? The journal's `out` row records intent, not delivery: find where it is written relative to the OS write and to which stream. An engine that answered and waits on its next stdin line also "sits idle with its connections open", which is what the pre-run saw. Read `session.ts` (spawn → initialize sequence at about line 236 and 470-520), `session-stream.ts`, `transport.ts`, `outbound-writer.ts`; look for any await between spawn and the reader's attachment, and for state that survives from the previous launch of the same session object (flags, writers, abort signals).
2. Engine side, the environment. Reproduce with MAWS's real captured environment: have the host (or a probe using `captureShellEnvironment` and `launch.ts`'s allowlist) dump the exact variables and values it would set into a file under the scratch root, then spawn from a script with exactly those. Suspects are values the allowlisted script did not carry: `PATH` ordering, `SSH_AUTH_SOCK`, `GIT_EDITOR`, `HOMEBREW_*`, `XDG_DATA_DIRS`, `SHELL`.
3. Engine side, state. A stale session lock or state file in the scratch config dir left by the previous process (which the app's cleanup ended with `SIGTERM`): inspect what 2.1.283 leaves under the config dir after a `SIGTERM` mid-idle and whether a `--resume` of that session waits on it silently. Test by ending a resumed session with `SIGTERM` and resuming at once and after 60 s.
4. The parent process. Reproduce through the product itself: the dev app (`pnpm dev` under a scratch `CLAUDE_CONFIG_DIR` and `MAWS_USER_DATA`) or the unsigned owner build as M6 did (`e2e/c12-prerun.spec.ts`'s `ensureLive` shows the resume path), driving row Resume repeatedly (twenty or more) with instrumentation on: a journal row when the reader attaches and on the first byte read; during a stall, `ps -o stat,wchan -p <pid>`, `lsof -p <pid>` (is stdout's pipe full? is it blocked reading stdin?), and `sample <pid> 2` for where it sits. Record the hit rate.

**The fix.** Whatever the cause, bound the handshake: give `initialize` its own request class (about 30 s, the bound the launch gate already uses for custody and the first configure push) so a stall reaches `init_failed` in a time the owner can wait, with the stderr tail in the detail and the row left resumable; pin it in the session tests (a transport that never answers `initialize` reaches `init_failed` after the bound, the ladder runs without `end_session`, the row's status carries the reason). If the cause is host-side, fix it and pin it. If the cause is engine-side and cannot be fixed without patching the engine (D-1 forbids that), record it here and in the fixture set (a probe under `spikes/protocol-probe/scenarios/pass3/` if a frame-level fact is established) and hand back the question of an automatic single retry to the architect rather than adding one.

The `out` row is not intent: `OutboundWriter.write` journals it only when `transport.write` resolved, which is when `child.stdin.write`'s callback ran, so the stalled launches' `initialize` bytes did reach the new process's stdin pipe. The writer is the new process's (`new OutboundWriter(transport, …)` right after the spawn).

## Decisions

- 2026-09-30. **The bound is on silence, not on `initialize`'s total time** (ebd82749, replacing 80e27493's class). The brief asked for `initialize` in its own ~30 s class. 2.1.283 reads `initialize` only after startup, plugin preflight and SessionStart:resume hooks, which it awaits with a 600 s default (research: `HP` awaits `bEr`, L731675; `La = 600000`, L917581), so a 30 s total bound fails a legitimate resume whose project or plugin hook takes longer, and §12 C3's own rejection of "one 30 s timeout" (the owner's settings and MCP prewait) still stands. The observed stall wrote nothing at all, and a healthy start writes within 0.3 s (the hook frames come first when there are hooks). So: an engine that writes no stdout frame and no stderr line within `FIRST_OUTPUT_MS` (30 s) of its spawn is failed as `init_failed { code: 'no_output' }` with the ladder without `end_session`; one that has written anything keeps the `long` class's 120 s. The reason reaches the owner through C10's existing path (the toast "the engine exited before it was ready: the engine wrote nothing in the 30 s after it started; initialize was not answered", the transcript's process error, `exit.reason: crash`), and the row offers Resume at once (pinned in `e2e/sessions.spec.ts` over a stub engine). No X6 or X1 shape changed: `EngineSessionStatus` carries no message field, and adding one would be a contract change, so the reason rides the events it already rode. Where a synchronous plugin install is opted into (`CLAUDE_CODE_SYNC_PLUGIN_INSTALL`, which MAWS never sets) the engine may be silent longer than 30 s before its first hook; that would now fail and say so.
- 2026-09-30. **Main's launch watch counts only the live launch's exit** (80e27493): `LaunchWatch` ignores events whose `seq` is null (X1: null for app-synthesised events; every live event derives from a journal row). Surprise 1 is the evidence; the fix is host-side, so it is fixed and pinned (`service.test.ts`), per the brief.
- For the architect: **an automatic single retry.** Recommended, bounded to exactly this failure: when a launch fails `init_failed { no_output }` (the process never wrote a byte, so nothing of the session was touched: before the first SIGTERM handler, no transcript read, no hook), main's resume path may relaunch once and surface the failure only if the retry also fails. The pre-run's 2 of 4 were each followed by a passing resume, and the retry costs the owner 30 s rather than a second click. Not added here, as the brief reserves it. Also for the architect: §12 C3's timeout-class paragraph and the WATCHDOG comment's charter source now differ from the code by the first-output bound; the charter line is the architect's to amend.
- Recorded, not done: no probe fixture was added under `fixtures/pass3/`, since no frame-level fact was established (the finding is about the process before its first frame); the measuring script is the scenario file.

## Surprises

1. **A resume raced C4's follower and was stopped 2 ms after its spawn** (H4, 15 of 29 row Resumes before the fix; not the pre-run's stall). When the conversation's last turn never ended in its transcript (here, an app closed mid-turn), C4's disk follower synthesises `process.exited { reason: 'unknown' }` with `seq: null` (`chain-follower.ts` `unendedTurnExit`). A read that restarts the follower between the resume's `fs.unfollow` and its `session.launch` (the open tab's `session.events`) delivers that event after main's `LaunchWatch` subscribed, and the watch took it for the new process's exit: the setup failed "the engine exited before it was ready", and `stopQuietly` SIGTERMed the process it had just launched (journal: reconnect, spawn, relay_health, out initialize, exit `SIGTERM` `stop`, 2 to 4 ms apart). Whether it hit was a race: the renderer's capture showed the synthetic exit arriving 5 to 18 ms before `launching` on passing runs and after it on failing ones. Every resume of such a conversation had about even odds of failing, and a retry could fail again. Fixed in 80e27493 (Decisions).
2. **Closing the app leaves the engine running for a moment, orphaned.** After Playwright's `app.close()` the engine process of a ready session was still alive with ppid 1 (1 to 3 s old) after 57 of the 58 closes that had a ready session (44 of 45 after the fix, 13 of 27 before, where the other 14 had no live process), and gone before every next app's Resume (`ps` before each Resume found none) (the quit report read "nothing busy"). It never overlapped a resume here and 2.1.283 does not wait on a live holder of the same session (Progress, H3), so it does not explain the stall; recorded for C12's quit path, which answers quit before its engines have exited.
3. **2.1.283's SIGTERM disposition is a clock.** For about the first 75 ms a SIGTERM kills the engine by the signal; from about 100 ms its handler exits 143. A journal's exit row therefore says whether a process that was ended ever got past early init, which is what bounded this stall without a live capture (`pass3/sigterm-disposition.mjs`).
4. **The engine awaits SessionStart:resume hooks before it reads `initialize`**, 600 s per hook by default (research, above): the `long` class's 120 s can already fail a legitimate resume with a slow hook. Not changed here; for C3's owner.
