## Decisions (in flight)

1. **What a refused run starts** (§2's parenthetical as the test; the architect approved). Skipped: the attention core with its fallback file, replays, the prompt history, the worktree and session services (intents, bootstraps, deletions, every launch), the owner channel, the sweep, yield and side threads. Kept: the read model (in memory, folds host events, writes nothing; the precursor of §7's view), the index's session source and the library (both already inert on an unavailable index), observed facts (reads). The proof is the e2e over the files, not the list, so a writer added later is caught. Rejected: stubbing the read model as well, which needs O3-C's view first and leaves the staying consumers (notifier, quit guard, chat panels, files) without a source.
2. **A first run writes `machine-settings.json` with its defaults** (approved), so "the machine file is absent" means "no split build has started this profile", which the engine host's fallback to the unified `settings.json` assumes. A `settings.json` this build cannot read (unreadable, invalid, or a version it does not know) gets no machine file created over it, and the run refuses machine writes, as today's rule refuses writes over an invalid file. Rejected: creating the machine file only at the first machine-field write, which leaves a client-only `settings.json` without a machine file and the engine host warning "invalid app settings".
3. **A refused run relays none of the machine settings** (engine.configure and the budget's policy, host.configure, the design-system defaults; nor the retired custody copy's removal). Rejected: relaying what it read, which carries the holder's values only until the holder changes one; a refused run's later push would then overwrite the holder's.
4. **The refused index opens no file** (`refusedDb`, a `:memory:` connection with the reason). Rejected: opening `index.sqlite` read-only as the newer-version path does, which takes a reader beside the holder for nothing and fails on a profile with no index yet.
5. **The split's write failures** keep today's "a migration it cannot persist stays in memory": a failed machine write holds the unified file's machine fields in memory for the run with writes refused and splits at the next start; a failed client write after the machine file leaves `settings.json` unified, read and not written. Rejected: retrying the split at a later patch, which would let a client write happen before the machine file exists.
6. **`host.status.spineRefused` is optional** (nullable, absent from a build before O3-A). Rejected: a required nullable field like O2's `daemonUnavailable`, which would make another profile's pre-O3-A app's `host.status` invalid over O6's link.
7. **The engine host's inventory names the file it read** (`machine-settings.json`, or the unified `settings.json` in the fallback), while configured delivery's source keeps naming `settings.json` (§3's identity). The inventory's path is display only (Customize's origin line; app rows carry no target). Rejected: the inventory also naming `settings.json`, which would point a reveal at a file that no longer holds the servers.
8. **The settings' shape** (advisory means of §3): the client half's rules and the composition (`composeSettings`, Electron-free) in `src/main/client/settings-store.ts`, the service with `nativeTheme` in `src/main/client/settings.ts`, the generic file rules in `src/main/settings/store.ts`, the machine half in `src/main/settings/machine.ts`, the split in `src/main/settings/split.ts`, the lock in `src/main/settings/spine-lock.ts`. `migrateSettings` still takes a unified file of any version to the merged settings (now at 21); `splitSettings` and `mergeSettings` cut and join; each file's reader takes only its own versions.
