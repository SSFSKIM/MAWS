## Decisions (in flight)

1. **What a refused run starts** (§2's parenthetical as the test; the architect approved). Skipped: the attention core with its fallback file, replays, the prompt history, the worktree and session services (intents, bootstraps, deletions, every launch), the owner channel, the sweep, yield and side threads. Kept: the read model (in memory, folds host events, writes nothing; the precursor of §7's view), the index's session source and the library (both already inert on an unavailable index), observed facts (reads). The proof is the e2e over the files, not the list, so a writer added later is caught. Rejected: stubbing the read model as well, which needs O3-C's view first and leaves the staying consumers (notifier, quit guard, chat panels, files) without a source.
2. **A first run writes `machine-settings.json` with its defaults** (approved), so "the machine file is absent" means "no split build has started this profile", which the engine host's fallback to the unified `settings.json` assumes. A `settings.json` this build cannot read (unreadable, invalid, or a version it does not know) gets no machine file created over it, and the run refuses machine writes, as today's rule refuses writes over an invalid file. Rejected: creating the machine file only at the first machine-field write, which leaves a client-only `settings.json` without a machine file and the engine host warning "invalid app settings".
3. **A refused run relays none of the machine settings** (engine.configure and the budget's policy, host.configure, the design-system defaults; nor the retired custody copy's removal). Rejected: relaying what it read, which carries the holder's values only until the holder changes one; a refused run's later push would then overwrite the holder's.
4. **The refused index opens no file** (`refusedDb`, a `:memory:` connection with the reason). Rejected: opening `index.sqlite` read-only as the newer-version path does, which takes a reader beside the holder for nothing and fails on a profile with no index yet.
5. **The split's write failures** keep today's "a migration it cannot persist stays in memory": a failed machine write holds the unified file's machine fields in memory for the run with writes refused and splits at the next start; a failed client write after the machine file leaves `settings.json` unified, read and not written. Rejected: retrying the split at a later patch, which would let a client write happen before the machine file exists.
6. **`host.status.spineRefused` is optional** (nullable, absent from a build before O3-A). Rejected: a required nullable field like O2's `daemonUnavailable`, which would make another profile's pre-O3-A app's `host.status` invalid over O6's link.
7. **The engine host's inventory names the file it read** (`machine-settings.json`, or the unified `settings.json` in the fallback), while configured delivery's source keeps naming `settings.json` (§3's identity). The inventory's path is display only (Customize's origin line; app rows carry no target). Rejected: the inventory also naming `settings.json`, which would point a reveal at a file that no longer holds the servers.
8. **The settings' shape** (advisory means of §3): the client half's rules and the composition (`composeSettings`, Electron-free) in `src/main/client/settings-store.ts`, the service with `nativeTheme` in `src/main/client/settings.ts`, the generic file rules in `src/main/settings/store.ts`, the machine half in `src/main/settings/machine.ts`, the split in `src/main/settings/split.ts`, the lock in `src/main/settings/spine-lock.ts`. `migrateSettings` still takes a unified file of any version to the merged settings (now at 21); `splitSettings` and `mergeSettings` cut and join; each file's reader takes only its own versions.

9. **The browser's transfer** (§4's means, the worker's, accepted at the merge `aa2c1d9ef`): the rows pass through the index's own connection inside its migration transaction, not an `ATTACH` (SQLite refuses one inside a transaction; a second connection reads only committed state); the step is an optional `before` on `Migration` 14 in `MIGRATIONS` itself, deriving its target from the index path, so any opener of `MIGRATIONS` stages (rejected: `Index` wrapping the list, which a bare `openDb` would bypass and drop the tables); the browser opens `browser.sqlite` only once it reads the index at 14 or above, and promotes in one transaction with its own migrations (`INSERT OR IGNORE`: live rows win); each `reattach` promotes staging that appeared meanwhile (a restored index migrated again); the known-session check is an in-memory set from the snapshot and the changes the browser hears (rejected: reading the index at each append, which closes before the activity's last flush at quit); a failed reconciliation is logged and appends continue; one connection with no busy timeout on the browser's file (its only writer in O3-A); a `browser.sqlite` of a newer version is left alone and inert, one SQLite cannot read is moved aside.
10. **Acceptance 1's whole-profile proof is a node test of main's data start** (`src/main/profile-upgrade.test.ts`): an O2-era profile built through the index's own stores and rewound to version 13 with the browser's rows, through `takeSpineLock`, the split, both halves, `Index` (migration 14) and `BrowserData`, compared row for row. The app-level path is covered by the e2e groups: `e2e:settings` (a version-2 file split; the refused launch), `e2e:library` (an index at 9 migrated to 14), the browser groups on `browser.sqlite`. Rejected: an app-level e2e seeding sessions without transcripts, which discovery would mark removed (a change the fixture causes, not the upgrade).
11. **The client file is the version fence even where no setting was ever changed** (high review, round 1): the split writes `settings.json` at 21 whenever it is absent, beside the machine file, also when a start finds the machine file without it. Rejected: leaving a first run's `settings.json` absent, which a build before the split reads as a first run and writes a unified file into, whose machine fields the next split would lose to the machine file.
12. **`spine.lock` is released at the process's exit alone** (high review, round 2). Rejected: a last will-quit step, which runs before the steps' promises settle and before a writer still finishing (an intent's rename), so a candidate could take the lock beside a still-writing process. An Electron 44 probe on a scratch profile showed main emits Node's `exit` on a plain quit and on the held `app.exit(0)` path main's shutdown uses.
13. **The browser reads the index's version from its header when no `-wal` is beside it** (hosted `e2e:settings`): with no `-wal` no connection holds the index in WAL mode and the file is whole; with one, a read-only connection reads what the WAL committed beyond the header. Rejected: SQLite's read-only open in every case, which creates the index's `-wal` and `-shm` when no connection holds it (a refused run's write of a spine file, whatever the holder), and the header alone, which misses a version committed to an un-checkpointed WAL (main's own migration, at the browser's start).
14. **`e2e:cross-build`'s `(downgrade, daemon)` scene keys its expectation to the attacher's build** (the architect's direction): an attacher at wire minor 5 or later (P5 O2) ends the keeper's `mawsd` as it leaves the daemon shape (its main logs it; `mawsd` logs `exiting (signal)`); an earlier one takes the engine host ("taken by another client"). Rejected: leaving it to O3-D, which would leave a known-red scene in the peer check every wire-touching landing runs until then.
