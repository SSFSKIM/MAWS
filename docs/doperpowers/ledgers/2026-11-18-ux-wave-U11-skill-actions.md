The skill's switch is not here. **Branch** `ux-wave/U11-skill-actions` from master `8a7f308ff`. **State:** design accepted 2026-11-18 (decision 9); phase 2 built on U6b-4a's head `785e66161`, merged (decision 11).

## Decision Log

**1 · Open is "Open in", the menu U6b-4a builds, on the skill's detail; its last row, Finder, is Reveal.** The detail of a skill in Customize (Show: Skills, or All) gets one button, "Open in", whose rows are U6b-4a's: the editors installed among VS Code, VS Code Insiders, Cursor, Windsurf, Zed and Xcode, then Finder. An editor row opens the skill's `SKILL.md`; Finder shows it selected in its folder (decision 2). No Terminal row: a skill is a file, and U6b-4a's Terminal row opens a folder. *Evidence:* U6's "Open in" (child file, l5-code-10) puts this menu in a file's bar, with main starting the app on an admitted path and nothing run by the window; Customize has no session, and MAWS's own viewer is a session's (U6c and U6e admit a file outside the folders per session: the transcript names it, the agent sent it, or the person chose it for that session). *Alternatives:* (a) MAWS's viewer, editable: the IDE surface MAWS wants, but it needs a new admission in the daemon's files service, for a file a page with no session lists, writing into `~/.claude`; a landing of its own, which this one does not block. (b) "Open" with the system's default app for `.md` (`shell.openPath`): no wait on U6b-4a, but on a stock Mac the app is Xcode or TextEdit and it would be a second launcher beside U6b-4a's; it becomes the better pick only if U6b-4a stalls. **Dependency:** the Open rows wait for U6b-4a on master; Reveal and "New skill…" do not (decision 5).

**2 · Reveal shows the skill's `SKILL.md` in Finder; the path is one main reads from the inventory itself.** The window sends the place (`cwd`, null for the user's page) and the row's `path`; main asks `customization.inventory` for that place over its own client (`bus.invoke(…, { client: mainClient })`, as `src/main/app.ts:575` does), admits the path only when a skill row of that answer has exactly it, takes its real path, checks it is a regular file, and reveals (or, decision 1, opens) that real path. The inventory's `path` is the `SKILL.md` file (`src/engine-host/customization/inventory.ts:164-168`). A refusal reveals nothing and answers why: not listed (the skill moved or was removed since the list was read), or the inventory could not be read. *Alternative:* the existing `settings.reveal` (`src/main/settings/reveal.ts`), which takes the window's string and admits anything under the config home or a session's folders: it would reveal user and plugin skills, but it refuses a project's skill when no session of that folder is known, and it admits far more than skills. No new daemon command, no wire minor: the read already exists; main's command is new and main-owned (`customization.skillFile`, `{ cwd, path, action: 'reveal' | 'open', app? }`).

**3 · A plugin's skill opens like any other, with one line on its detail.** "Comes with the plugin <name>. An update of the plugin replaces this file, and any edit in it." The cache is the engine's (`~/.claude/plugins/cache/…`); an editor cannot be made read-only, so the line is the guard. *Alternative:* no Open for a plugin's skill, Reveal only: it hides the main reason to open one (to read it whole).

**4 · "New skill…" opens a new chat whose composer is filled, not sent.** Claude Desktop's "Create with Claude" (the skills Add menu, `web/app/v1/c5e558aae-B9ytYQi6.js:483-514`, beside "Upload skill" and "Create a skill") opens `/new?q=` (`cc1f3b9f3-CdX8GWbH.js:807`) with "Let's create a skill together using your skill-creator skill. First ask me what the skill should do." (`cc8364258-C9_TOaON.js:7`), and the page fills the composer with it (`c5e8ef052-B4k5f9iO.js:118`); when skill-creator is off for the account it first asks "Turn on skill-creator?" (`c2db9c6e5-giBbOcNa.js:167-172`). The engine at 2.1.322 has no skill creator of its own: `/init` tells the person to install the official plugin (`/plugin install skill-creator@claude-plugins-official`, then `/skill-creator <skill-name>`, `cli.pretty.js:424094`), and its Skillify prompt is registered by a stub that does nothing in this build (`cli.pretty.js:837174`). The plugin's manifest name and skill folder are both `skill-creator`, so P3's rule makes its invocation `/skill-creator:skill-creator`. MAWS already starts a chat with a filled composer: the Library's "Ask Claude" (`library/MakeSomethingNew.tsx:88-100`, `createSession` then `prefillComposer`). So: when the inventory lists skill-creator usable (its row has an invocation and no `unavailable`), the composer holds `/<its invocation> ` and the sentence; otherwise the sentence alone, which works because the model writes a `SKILL.md` unaided. No install wall: Desktop's dialog turns on a skill the account has; MAWS would be sending the person to install a plugin before a chat that works without it. *Alternative:* send the first message at once; lost because the person cannot add what the skill is for before Claude starts.

**5 · Where the skill is made.** On a project's page "New skill…" is a menu of two rows, "In this project" and "Created by you" (the skills groups' own headings, `widgets/copy.ts:499-500`); on the user's page it is a button that makes yours. The chat starts in the page's place (the project, or a chat with no project), and the sentence names the folder: "Let's create a new skill in `.claude/skills/` of this project. First ask me what it should do." or "…in `~/.claude/skills/`, for all my projects…" (the config home shown with `~` when under home). *Alternative:* one target per page (a project's page makes a project skill): fewer words, but a project's `.claude/skills` is usually committed and shared, so a person's own skill would land in the team's repository by default.

**6 · Trust boundaries.** Open crosses one: main starts another app on a path. The path is the inventory's, read by main itself, never the window's string (decision 2), the same rule as U6b-4a's admission. Reveal runs nothing; same admission. "New skill…" crosses none on MAWS's side: MAWS writes no file, and nothing is sent until the person sends; the agent then writes under the engine's permission rules (a write into `~/.claude/skills` from a project's chat is outside its folder and is asked for by the engine).

**7 · Words.** Detail: "Open in" (menu; rows per U6b-4a, last "Finder"); the plugin line of decision 3; a refusal in the danger tone under the head: "This skill's file is no longer here. Refresh, then try again." or "Skills could not be read: <reason>". Head: "New skill…" under Show: Skills and All, beside Refresh (and under All beside "Add custom connector…"); its menu rows "In this project", "Created by you". Composer: the sentences of decisions 4 and 5. Not in the session's `/skills` dialog (U11's scope names Customize's detail).

**8 · Proof (phase 2).** Unit, main: the admission (listed path admitted and real path revealed; unlisted, relative, a directory, a missing file, a failed inventory read each refused and nothing revealed or launched). Renderer: "New skill…" present under Skills and All, absent under Plugins and Connectors and while a detail is open; its menu on a project's page and the button on the user's; the composer's text with and without a usable skill-creator, and with a skill-creator whose plugin is off; "Open in" and the plugin line on the detail; the refusal line. Scene in `e2e/discover.spec.ts` (group `e2e:discover`): on a fixture home with a user skill, a project skill and a plugin skill, open each detail, choose Finder, and read `MAWS_E2E_OPEN_LOG` for exactly the listed `SKILL.md`; a `window.maws.invoke` of `customization.skillFile` with an unlisted path logs nothing; "New skill…" › "In this project" opens a chat whose composer holds the sentence. The editor rows' scene is U6b-4a's seam, added once it lands.

**9 · 2026-11-18, the architect's rulings on the design.** Accepted as written: one "Open in" menu on a skill's detail with Finder as its last row; Open waits for U6b-4a, with no default-app fallback; the two-row "New skill…" menu on a project's page. Order: what does not need U6b-4a first; U6b-4a's menu and launcher are its own, never rebuilt here.

**10 · Means of the first part.** `customization.skillFile` takes `{ cwd, path, action: 'reveal' }` (an `open` action comes with U6b-4a's launcher) and answers `revealed`, or `refused` with `missing` (not listed, gone, or no regular file: one sentence, since the person's remedy is the same), `unreadable` (the inventory's read failed, with its reason) or `no-window` (nothing said). It is graded `client`: this app's Finder and this Mac's inventory, as Customize's page is this Mac's (`customize/CustomizeView.tsx`). The words of a refusal: "This skill's file is no longer here. Refresh, then try again." On a page of a folder no project has, "New skill…" adds that folder as a project first, as the Library's "Ask Claude" does for a Space's folder. The plugin line names the plugin as the row's badge does.

**11 · Open in, on U6b-4a's menu and launcher (merged at `785e66161`).** `customization.skillFile` becomes the one hand-off: `{ cwd, path, app }`, where `app` is an editor row or Finder (the schema's `SKILL_FILE_APPS`, no terminal), and Reveal is its Finder row. Main admits by decision 2's check and hands the real path to U6b-4a's launcher through one method added to it, `launchFile(app, realPath)`: the installed check, the launch and the e2e seam's `open-in <id> <path>` line are its own, and `files.admit` (a session's files) is never asked. The answer is `opened` or `refused` with `missing`, `unreadable` or `launch` (the launcher's sentence: not installed, did not open); `no-window` goes, since the launcher needs no window. The command joins `layout.openIn` under `appPageOnly`. In the window, U6b-4a's `Rows` takes what a row does (`choose`) and which rows stand (`only`) instead of a session and a file, and `OpenInChooser` is its menu button for a caller with its own hand-off; `OpenInButton` and `OpenInSubmenu` keep their behaviour. The skill's detail takes three slots from its caller (`SkillDetailExtras`: the head's actions, an alert under the head, the note); only Customize fills them, so the session's `/skills` dialog is unchanged. The refusal belongs to the detail it was made on and goes when that detail closes. Named insertions in U6b-4a's files: `src/main/open-in/open-in.ts` (`launchFile`) with two cases in its test, `src/renderer/src/open-in/OpenInMenu.tsx` (`Rows`' props, `OpenInChooser`), and the guard list in `src/main/app.ts`.

**12 · 2026-11-19, the review's five findings (reviewer-high on `24952ff2f..36ed64ef7`), fixed.** (1) Main opens only the file the inventory read: each skill row carries `realPath` and `fileId` (`<device>:<inode>`, from the open handle the front matter was read through), and main refuses when the listed path's real path or identity differs now; a skill an older engine host lists, with neither, opens nothing ("the engine host is an older version…"). The window between main's check and the editor's own open is U6b-4a's tracked one and is not narrowed here. (2) A person's skills folder is named whole under the configuration home `plugins.env` reports; "Created by you" is disabled until it has answered, and nothing is shortened to `~`. (3) skill-creator is called only when its plugin is enabled for the place by the engine's own listing (`plugins.list`'s `enabled`, the plugin library's `enabledHere`) and is not off in the launch profile; unknown is the plain sentence. (4) The inventory says whether every skill folder was read (`skillsRead`: no warning outside an MCP section but the coverage note, and no stop); a skill not listed by an incomplete read refuses with the read's latest warning, never "no longer here", and a listed skill still opens. (5) A reply is kept only for the mounted "Open in" that asked and its latest request. Wire minor 53 (the inventory's three optional fields).
