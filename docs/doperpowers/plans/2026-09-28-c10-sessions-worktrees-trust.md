## Purpose

After C10, a session in MAWS has a whole life, and it begins the way Codex and Claude Desktop begin one: a project's "+" (or ⌘N) opens a session tab at once. Nothing has been launched; the tab shows one heading naming the project with C7's ordinary composer centred beneath it, built as Claude Desktop builds a new chat (D-20, §5.4 as amended 2026-09-28), and the composer frame's chips are the setup: location chips above the box (the project directory, a new git worktree with its branch, or one of the repository's existing worktrees; add directory), the permission mode and the model with effort in the toolbar row below it. The owner types and sends. That first send starts the session: the worktree is created if one was chosen; if the directory has never been trusted a trust card docks at the composer and asks, and on the owner's word MAWS attests trust to the engine so the project's settings, hooks, MCP servers and plugins load exactly as they do in the terminal (a trust bootstrap launch under a throwaway identity of its own records the trust first, because the engine's launch-time readers only see trust from the next launch; the home folder, whose trust the engine never keeps, is attested per launch instead and the card says what that cannot load); if the owner declines, the session still starts and shows the engine's own notice that project rules were ignored; if the relay is down a card offers ClaudeUsage or a direct launch; then the engine launches, the session binds its identity, the message becomes the first turn, and the row appears in the sidebar. A worktree MAWS creates lives where the engine's `EnterWorktree` puts its own (`<repo>/.claude/worktrees/<name>`, branch `worktree-<name>`), so the two coexist and the owner's terminal habits keep working. Any session can be resumed after the app restarts (D-16: records, drafts, queued messages, grants and unstarted setups survive; processes do not), forked in place, or forked into a new worktree (a small popover for the name and branch), where the new session starts with the old conversation and resumes from the terminal like any other. Sessions can be renamed (a rename reaches the engine's store when the session is live, and stays MAWS's own until it is), archived (the process stops, the record hides, the worktree is offered for cleanup), and deleted (the transcript and its siblings go to the Trash, never silently, and never half-way). Cleaning up a worktree distinguishes four things the owner means differently: archiving its sessions, removing a clean checkout, discarding uncommitted changes, deleting the branch, each its own command with the worktree's identity revalidated before anything is deleted. A session that a terminal or a `claude --bg` job holds opens read-only with its holder named; a background job offers "Attach in a terminal tab", which opens C9's terminal running the engine's own `claude attach <id>`, and MAWS's own resume guard, fed by a fresh read of the engine's live registry, refuses to become a second writer, with the engine's refusal authoritative for background jobs.

What C10 does not do: render the transcript or the composer (C6, C7; C7 owns the strip's chips and binds them to C10's intent hook), the panel host (C8), the palette widgets or the settings screens (C11), the prewarmed spare (C12; the `claim_session` trust mapping is written here, not exercised), a source-control panel (P1), or any write into `~/.claude` beyond the one this document names (the Trash move of a deleted conversation and nothing else; the fork copies no transcript, see Surprises; trust is recorded only by the engine).

## Terms

- **Trust key**: the path under which the engine records trust for a directory in the global config (`projects[<key>].hasTrustDialogAccepted`): the root of the git repository's main worktree when the directory is inside a repository (linked worktrees share it), else the directory's own NFC-normalised realpath (SPEC §3 15.1–15.4; verified by the pass-3 probe, Surprises). **Global config**: the file the engine resolves by SPEC §3 16.1 (Trust, below); MAWS reads it and never writes it. **Attestation**: telling the engine the human accepted trust, through `initialize.workspaceTrust { accepted: true, directory: <trust key> }` (X6), or `claim_session.workspace_trust` for a prewarmed spare (P1). **Trust decision**: the human's answer to the trust step, a tri-state `unanswered | accepted | declined` kept in the setup intent; only `accepted` maps to an attestation.
- **Trust gates**: what the engine withholds in an untrusted directory: project and local `permissions.allow` and `permissions.additionalDirectories`, hooks, `settings.env`, `.mcp.json` servers, project plugins and marketplaces (SPEC §3 15.5). Two classes (SPEC §45 `workspaceTrust`, the schema text at line 4422): permission rules and hooks **re-derive in the running process** once the attestation is recorded; `.mcp.json` approval, project plugins and agent-frontmatter hooks and MCP servers are **read at launch** and see the recorded trust from the next launch on. The **trust notice** is the engine's stderr line `Ignoring N permissions.allow entries from .claude/settings.json: this workspace has not been trusted. …` (fixture `pass2/trust-no-attestation.jsonl` seq 5). It is printed at settings load, before `initialize` is read, so it appears on attested launches too and means "ignored" only when the attestation did not record trust.
- **Trust bootstrap**: for a never-trusted key whose decision is `accepted`, an extra engine launch that carries the attestation, is confirmed by `workspace_trust_recorded: true`, and is stopped; the session's real launch follows, so every gate, the launch-time ones included, is open on the process the owner actually uses. It runs under a **bootstrap id**, a fresh `appSessionId` minted for it alone (never the conversation's, whose record C4 would otherwise patch with the bootstrap's engine id and default selections), recorded as `progress.bootstrap` and `session.forget`-ed once its reservation releases; occupancy sees it through `EngineSessionStatus.cwd`. Shown as one `trusting` phase. Never run for the home directory (SPEC §3 15.3: its trust is session-only; the engine answers `session_only`, `workspace_trust_recorded: false`).
- **Managed worktree**: a git linked worktree under `<repoRoot>/.claude/worktrees/<name>` on branch `worktree-<name>`, the engine's own convention (SPEC §47 11.1) and MAWS's. **Repository root**: the main worktree's root (the parent of `git rev-parse --path-format=absolute --git-common-dir` when that directory's basename is `.git`), which is where managed worktrees are created whichever worktree the owner started from. A **hand-made worktree** is any other linked worktree; cleanup never assumes its name or branch.
- **Cleanup ladder**: the four distinct operations on a worktree: archive its sessions, remove a clean checkout, discard uncommitted changes (then remove), delete the branch. Each is its own command with its own guard (Interfaces, Cleanup state machine).
- **Holder**: C4's `SessionRecord.holder`: `self` (a process C3 owns), `terminal` (an interactive `claude` with a live registry record), `background_job` (a `claude --bg` job, `jobId` its eight-hex short id), `none`. **Foreign-live**: holder `terminal` or `background_job`. **Holder authority**: at a destructive or exclusive boundary (resume, delete, cleanup) the holder is decided from a fresh read of the engine's live registry (`sessions/<pid>.json`, C4's liveness rule) unioned with C3's process reservations (`engine.sessions`, each carrying its spec's `cwd`, so a reservation with no record counts), never from the index projection, which is asynchronous. **Attach**: the engine's `claude attach <short>` run in a C9 terminal tab.
- **Setup intent**: the persisted description of a session that has not been launched yet: location, branch, model, effort, permission mode, additional directories, gateway, trust decision, first message, fork source; kept under the allocated `appSessionId` at `<userData>/sessions/intents/<appSessionId>.json` until the session is **identity-bound** (C3 reports `ready` with the session's engine id and the first message, when there is one, has been handed to C3's queue). **Handoff**: the moment the first message becomes C3's: `session.send` answered and its `queueId` is recorded as `progress.send`; the intent is removed only after that record. **Reconciliation**: at app start, an intent whose record exists is settled against the record, the pinned id's transcript and C3's persisted queue (Handoff recovery, Interfaces), never re-run from scratch. An **unstarted session** is an app session id with an intent and no record with an engine status (C7's definition): it has a tab and no sidebar row (a reconciled provisional record has a row, exited). **Setup**: the run of one `session.start` from the command to `ready` or `failed`, reported as `session.setup` events. **Rollback**: undoing what a failed setup created (a worktree and its branch, a provisional record), per resource, never what existed before, never by force without the human's consent, and never a transcript: a launch that wrote one has a conversation, which stays.
- **Fork in place** / **fork to a new worktree**: `--resume <id> --fork-session --session-id <new>` launched in the source's directory, or in a worktree created for it; the engine finds the source transcript in any project directory and writes the new session under the launch directory's slug under the pinned new id (Surprises; SPEC §35 16.5–16.6).
- **Catalogue**: the engine's model list (`list_models` / the `initialize` response's `models`), each entry with `value`, `displayName`, `supportsAutoMode`, `supportsFastMode` (fixture `reads.jsonl`). A **gateway model** is an entry whose `value` starts with `claude/` (the relay's aliases for non-Anthropic providers: `claude/astra|sol|luna|terra`, `claude/<vendor>/…`); auto mode on it runs the classifier locally on Sonnet 5 and counts as usage (§19).
- **Session service**: C10's main-process module (`src/main/sessions/service.ts`) that owns the lifecycle commands. **Store file**: C3's per-session state file (`<userData>/engine-host/state/<appSessionId>.json`: queue, grant snapshot, last launch spec). **Deletion manifest**: the list of a conversation's files enumerated and persisted before the first Trash move, so a failure half-way is reported and resumable.

## Interfaces and Dependencies

Code below is code that is itself a decision: shapes, names, state tables and the exact strings siblings and the acceptance depend on. Zod schemas carry the type's name with a `Schema` suffix; types are `z.infer`. Every per-session payload names the session `appSessionId` (ledger ruling 1).

### Shared shapes (`src/shared/sessions/*.ts`)

```ts
// intent.ts
export const BranchChoiceSchema = z.discriminatedUnion('kind', [
  z.strictObject({ kind: z.literal('new'), name: z.string(), base: z.string() }),   // base: 'HEAD', a local branch, or a typed ref; resolved by `git.worktree.add`
  z.strictObject({ kind: z.literal('existing'), name: z.string() }),
]);
export const LocationSchema = z.discriminatedUnion('kind', [
  z.strictObject({ kind: z.literal('directory'), path: z.string() }),                                   // realpathed by the service
  z.strictObject({ kind: z.literal('newWorktree'), repoRoot: z.string(), name: z.string(), branch: BranchChoiceSchema }),
  z.strictObject({ kind: z.literal('existingWorktree'), repoRoot: z.string(), path: z.string() }),
]);
export const TrustDecisionSchema = z.enum(['unanswered', 'accepted', 'declined']);    // the tri-state; only `accepted` attests
export const FirstMessageSchema = z.strictObject({ content: z.union([z.string(), z.array(ContentBlockSchema)]), display: z.string() });   // C7's `start` argument, verbatim
export const SetupIntentSchema = z.strictObject({
  appSessionId: AppSessionIdSchema, projectId: ProjectIdSchema.nullable(), createdAt: z.string(), updatedAt: z.string(),
  kind: z.enum(['create', 'fork']),
  source: z.strictObject({ appSessionId: AppSessionIdSchema, engineSessionId: SessionIdSchema, rewindTo: MessageUuidSchema.nullable() }).nullable(),   // fork only; rewindTo from C7's resubmit seam
  location: LocationSchema,
  additionalDirectories: z.array(z.string()),
  model: z.string().nullable(), effort: EffortSchema.nullable(), permissionMode: PermissionModeSchema.nullable(),   // null = engine default / settings
  gateway: z.enum(['gateway', 'direct']),                       // D-19 default 'gateway'
  trust: TrustDecisionSchema,
  trustKey: z.string().nullable(),                              // the trust key the decision answered (null while `unanswered`); when the effective key changes (a location patch), `trust` resets to `unanswered`, this to null and `progress.trustRecorded` to false, so a decision for A never attests B
  message: FirstMessageSchema.nullable(),                       // retained from `start` until the handoff (`progress.send`) or a hand-back (`session.intent.release`, or a rejected guard); C7 gates Send and the chips on it
  draft: DraftSchema.nullable(),                                // C4's `Draft { doc, attachments, updatedAt }`, held here while unstarted (Ask of C7); never touched by a start, a rejection or a hand-back
  progress: z.strictObject({                                    // what an attempt has already done, so a retry reuses instead of recreating and a restart reconciles instead of re-running
    engineSessionId: SessionIdSchema.nullable(),                // the id pinned for the real launch, minted at the first attempt and kept across retries
    worktree: z.strictObject({ path: z.string(), branch: z.string().nullable(), head: z.string(), createdHere: z.boolean() }).nullable(),   // head: at creation, the `expect` of a later removal; createdHere: the checkout and (for `branch.kind: 'new'`) the branch are this attempt's
    trustRecorded: z.boolean(),                                 // the bootstrap confirmed `workspace_trust_recorded: true` for `trustKey`
    bootstrap: z.strictObject({ appSessionId: AppSessionIdSchema, at: z.string() }).nullable(),   // the bootstrap id in flight or not yet forgotten (Trust bootstrap); forgotten at release, at the next attempt, or at start
    launch: z.strictObject({ launchId: z.string(), at: z.string() }).nullable(),                  // C3 accepted the real launch (`session.launch` answered `launching`): the pin may be in use from here on
    send: z.strictObject({ queueId: z.string(), messageUuid: MessageUuidSchema.nullable(), disposition: z.enum(['sent', 'queued']), at: z.string() }).nullable(),   // the handoff: C3's `session.send` answer for the first message; from here the message is C3's and is never sent again
    lastFailure: z.strictObject({ at: z.string(), phase: z.enum(SETUP_PHASES), message: z.string(), resources: SetupResourcesSchema }).nullable(),
```

**Trust bootstrap** (`bootstrapSpec()`; run by the setup's `trusting` phase, for a create and for a resume alike): needed iff the decision is `accepted`, the key is not the home directory, and `trustStateOf(directory).trusted` is false at the start of the attempt (an already-trusted key attests on the real launch only, which the engine answers `already_trusted` → `true`, harmless). The bootstrap is an ordinary `session.launch` under a **bootstrap id**: a fresh UUID v4 minted for this bootstrap alone, persisted first as `progress.bootstrap { appSessionId, at }` (for a resume, in a transient per-resume note the service keeps in memory and on disk beside the intents, `<userData>/sessions/bootstraps/<bootstrapId>.json`, so a crash leaves it findable), never the conversation's `appSessionId`. ### Worktrees (`src/main/git/worktrees.ts`, X2 `git.worktree.*`, owner `main`)

| State | Definition | Archive sessions | Remove checkout | Discard changes and remove | Delete branch |
|---|---|---|---|---|---|
| `busy` | `worktree.state === 'busy'` (a MAWS process, a foreign holder, an unbound registry holder, or locked) | allowed for `idleAppSessionIds` only; the live ones are skipped and named (never stops a process) | refused `busy: <n> sessions live here` | refused | refused |
| `dirty` | not busy; `dirty.tracked + dirty.untracked > 0` | allowed | refused `dirty: N changes` | allowed with `discard: true` (the dialog's explicit acknowledgement names the count) | after removal only |
| `clean` | not busy; no changes | allowed | allowed | not offered | after removal only |
| `detached` | `worktree === null` and `branch !== null` (the branch exists, no checkout has it) | allowed | nothing to remove | nothing | allowed; `merged` false shows `N commits not on <base>` and needs `acknowledgeUnmerged` |
| `gone` | neither the worktree nor the branch | allowed | — | — | — |

Archive sessions is not a git command and never stops a process: the dialog calls `session.archive` for each id in `occupancy.idleAppSessionIds` only (tabs close on `session.changed`), and reports what it skipped by name: every `liveAppSessionIds` entry with its title and holder (`Working in MAWS`, `terminal · <pid>`, `bg · <short>`) and the `unbound` count, under "Not archived: N live sessions; archive them from their rows" (the ordinary per-session archive dialog is the only place a process is stopped, with its background-work disclosure; this dialog offers no stop). A `busy` worktree therefore stays `busy` after the step, and the remove and delete steps stay refused. Remove and delete branch are the two commands above, invoked one after the other by the dialog when both are checked, each answering for itself; nothing already done is undone, because a removed checkout cannot be restored and an archived session can be unarchived. A hand-made worktree (any name, any branch, detached HEAD included) is handled by the same commands from the identity git reports; a detached checkout has no branch step. Reason for the four distinctions: they are what §4.5 binds and what the owner means by "clean up": a worktree whose sessions are archived is still a checkout the terminal can use; a removed checkout still has a branch to open a PR from; discarding is the only step that loses work, and deleting an unmerged branch is the only one that loses commits, so those two carry the acknowledgement.

### Holder authority (`src/main/sessions/holders.ts`)

```ts
export type HolderVerdict = { holder: SessionHolder; live: 'self' | 'foreign' | 'none'; source: 'reservation' | 'registry' | 'none' };
export async function holderAuthority(deps, q: { engineSessionId: SessionId | null; appSessionId: AppSessionId }): Promise<HolderVerdict>;          // one session
export async function occupancyOf(deps, directory: string): Promise<WorktreeOccupancy>;                                                              // one directory (worktree cleanup)
```

The verdict is computed at the moment it is needed, never read from `SessionRecord.holder`: `engine.sessions` (C3's process table: an entry with `process` not `exited` is `self`, the reservation outliving the process until the OS reports the exit) unioned with a fresh registry read through C4's service (`fs.holders`, the Ask below, which runs `HolderRegistry.refresh()` under C4's liveness rule and answers by session id and by directory). Precedence: a reservation wins (`already_live`), else a live registry holder (`held`), else `none`. C4's `fs.holders` fails closed: any non-ENOENT read or listing error answers `{ ok: false, code: 'internal', message: 'holder registry unreadable: <code>' }` (ENOENT alone means no holders), and `holderAuthority` treats that answer as a refusal of the start, archive or delete it was guarding, surfaced to the human with that message (`refused { reason: 'unknown_session' }` is not it; the outcome is the command's `IpcError` with C4's message), never as "no holders". `occupancyOf(directory)` counts reservations whose `EngineSessionStatus.cwd` realpath equals the directory (`self`; the field is the Ask of C3, present from the reservation onward, so a record-less trust bootstrap counts and `fs.holders` is not asked to know a process that writes no registry record), registry holders whose `cwd` realpath equals it and whose session id the index knows (`foreign`) or does not (`unbound`), and index records whose `worktree.path` or `directory` equals it and that have no process (`idle` / `archived`); `idleAppSessionIds` and `liveAppSessionIds` partition the non-archived records here by whether a reservation or a foreign holder names them. Every path is compared as NFC realpath. What remains: a client that writes no registry record (another SDK host's print-mode process) is invisible to MAWS and to the engine alike (pass-2 item 10); and between the fresh read and the launch a terminal can still start (a window of tens of milliseconds, closed only by the engine's own `--bg` refusal). Both are accepted under D-12 and stated in the residue rather than promised away. MAWS's own lifecycle operations on one `appSessionId` (`start`, `archive`, `delete`, `fork` of it as source, `rename`) are serialised through a per-session promise chain in the service, so two MAWS operations never interleave on one session.

**Ask of C4** (two additive items; the exact shapes, for the architect to relay verbatim):

> (1) `sessions.createForLaunch` accepts an optional caller-supplied `appSessionId` (UUID v4); the record is created under it; a collision with an existing record answers `{ ok: false, reason: 'exists', record }` so a restart reconciliation can reuse the record instead of creating a second one. Without the field the store allocates as today; with it, success answers `{ ok: true, record }`. Reason: `session.create` allocates the durable app id before any record exists, and the tab, the intent, the engine launch (`LaunchSpec.appSessionId`), C3's store file and queue all carry that id; a record allocated under another id would make C4 ignore the launch's statuses as an unknown record's (round-2 finding 1). C10 pins equality of the id across intent, record, launch spec, tab and the discovery binding (`fs.bind`).
>
> (2) One additive engine-host command in `src/shared/ipc/schema/fs.ts`, implemented by C4's `HolderRegistry`: `fs.holders` with input `z.strictObject({ sessionIds: z.array(SessionIdSchema).nullable(), directories: z.array(z.string()).nullable() })` and output `z.strictObject({ refreshedAt: z.string(), holders: z.array(z.strictObject({ sessionId: SessionIdSchema, appSessionId: AppSessionIdSchema.nullable(), holder: HolderSchema, cwd: z.string().nullable() })) })`. The handler awaits `HolderRegistry.refresh()` (the same liveness rule as the poll: `kill(pid, 0)`, `procStart` under `LC_ALL=C TZ=UTC`) and answers every live registry record whose `sessionId` is in `sessionIds` or whose `cwd` (NFC realpath; the field is present on the owner's real records, e.g. `sessions/28679.json`) equals one of `directories`; `appSessionId` from `Bindings.appIdOf`, null for a session the index has not seen. Nothing else changes: `fs.holderChanged` keeps feeding the index projection; this command exists because the projection is asynchronous and C10's exclusive-writer guards need the registry as it is now.

**`session.create`**: allocates the `appSessionId` (UUID v4), persists an intent with `kind: 'create'`, `location` as given (else `{ kind: 'directory', path: <the project's directory> }`, else the last used directory), `additionalDirectories: []`, `model`, `effort`, `permissionMode` null, `gateway` from `settings.gateway.defaultRoute` (C11's ask; `'gateway'` until settings v3 lands), `trust: 'unanswered'`, `trustKey: null`, `message: null`, `draft: null`, `progress` empty, and answers it; the renderer opens the tab. No engine process, no index record, no sidebar row. `session.intent.patch` validates the patch (`invalid` names the field: a location whose directory is missing, a worktree name `validateWorktreeName` refuses or whose path exists, a branch that exists for `kind: 'new'` or is missing or checked out elsewhere for `kind: 'existing'`, an additional directory that is missing or duplicates the session directory) and is refused `starting` while a start is in flight and `retained_worktree` for a `location` patch while `progress.worktree.createdHere` is set (a failed attempt's checkout is still this intent's; the failure card's "Discard changes and remove" or "Keep the worktree" resolves it first, Rollback). A `location` patch that changes the effective trust key resets the trust decision (Trust: `trust: 'unanswered'`, `trustKey: null`, `progress.trustRecorded: false`) in the same write. **Initial validation and retry validation differ**: the exists-checks above are the initial rules; when `progress.worktree` is set with `createdHere` and matches the intent's `newWorktree` by path (`<repoRoot>/.claude/worktrees/<worktreeDirName(name)>`) and branch (`branch.kind === 'new' ? branch.name : <existing name>`), the start's re-run skips them and verifies the checkout's identity instead (`git.worktree.status { repoRoot, path }` non-null, `branch` equal, `managed` true); a mismatch answers `invalid { field: 'location', message: 'retained worktree changed: <what git shows>' }` and the failure card's two resolutions apply. `session.intent.release` clears `message` (the hand-back; the draft is untouched), publishes `session.intent.changed` and answers the intent; refused `starting` while a start is in flight. `session.intent.discard` removes the intent (and its draft), forgets a `progress.bootstrap` id that is no longer reserved, and answers `{ leftover: { worktree: { path, branch } } | null }` naming a worktree a failed attempt created and could not remove, which stays for the cleanup dialog.

**Setup state machine** (one per `appSessionId` in flight; the events, states and transitions are fixed here so the service is a table, not a chain of callbacks). A `session.start` on an id with an intent runs it; on an id with a record and no intent it is a resume (below).

**Rollback** is per resource and never forces: (1) the transcript question first: if `progress.launch` is set and `<projects>/<slugOf(cwd)>/<progress.engineSessionId>.jsonl` exists (C4's `resolveStorePaths` and `slugOf`), the launch wrote a conversation, and rollback stops being a rollback: the record is kept and bound (`sessions.bindEngineId(appId, progress.engineSessionId)`, which also `fs.bind`s so discovery attributes the file to this record and never creates a second), the worktree is kept, the intent is removed, and `failed` carries `{ record: 'kept', transcript: 'kept', worktree: { state: 'kept', … } }`: the session exists, exited, resumable, with C3's exit notice as its explanation (never trash a transcript from an attempt that reached `launching`; only the human's Delete moves one); (2) otherwise a record this attempt created: `sessions.remove(appId)` (emits `session.removed`, cascades drafts and attention; C5 keeps the tab because C10's `retains(id)` is true for the retained intent, Ask of C5) → `record: 'removed'`, `transcript: 'none'`; (3) a worktree `createdHere`: `git.worktree.remove { expect: { branch, head: progress.worktree.head }, discard: false }` → `removed`, then for a `branch.kind === 'new'` created here `git.worktree.deleteBranch { repoRoot, branch, expect: { head }, acknowledgeUnmerged: false }` → `branchState: 'deleted'` (`delete_refused` with the detail when a hook committed on it, `changed`/`unmerged`, so a branch with commits is never deleted by rollback; `delete_failed` with git's message), and `progress.worktree` is cleared so the next attempt creates afresh under the initial rules; or `remove_refused` when the state is `dirty` (a startup hook, `git worktree add`'s `post-checkout` hook, or the engine wrote there) or `busy`, or `remove_failed` with git's message: a refused or failed removal leaves the worktree, keeps `progress.worktree` (so retry validation reuses it and a `location` patch is refused `retained_worktree`), and the failure card offers "Retry", "Discard changes and remove" (the cleanup dialog's acknowledgement, then `remove { discard: true }`, the branch step as above, `progress.worktree` cleared) and "Keep the worktree" (the checkout is detached from the attempt: `progress.worktree.createdHere = false`, the location becomes `{ kind: 'existingWorktree', repoRoot, path }`, the branch stays; the intent stays and its chips are editable again; the worktree is listed for cleanup like any other); (4) `session.forget` (C3's store file and journal) only when the intent is discarded, not on a failure, because the journal is the evidence of what failed; a `progress.bootstrap` id is forgotten as soon as it is not reserved. `session.setup { phase: 'failed' }` carries the whole `resources` object, so the tab says exactly what was undone and what was not. A `session.start` of an existing record rolls nothing back; a fork's rollback touches the fork's resources and never the source. During a rollback the service ignores `session.changed` for the app id (C4's watcher may archive the record when a transcript moves) and finishes with `sessions.remove` or `bindEngineId` regardless.

**Handoff recovery** (`recovery.ts`, `reconcile()` at `start()`, after C3's host answers and before `session.intent.list` does). Persisting the intent before effects and removing it after the handoff is not exactly-once on its own: the app can die between C3 accepting the first message and the intent's removal, and a naive restart would re-run the fresh launch with a pin whose transcript exists (the engine refuses `Session ID <id> is already in use`, SPEC §35 16.5, `statSync` in the current project directory) or send the message twice. So an intent whose record exists (`sessions.get(appSessionId)` non-null: `createForLaunch` ran) is **reconciled, never re-run from scratch**, from three facts: `transcript` = the file `<projects>/<slugOf(cwd)>/<progress.engineSessionId>.jsonl` exists; `queue` = `session.queue.list { appSessionId }` (Ask of C3 (2): the persisted queue of an unreserved id) has any entry; `sent` = `progress.send` is set. (a) `sent || transcript || queue`: the message is delivered or C3's. If `transcript`, `sessions.bindEngineId(appId, pin)` (the record's engine id is the pin; a later resume is `--resume <pin>`; `fs.bind` keeps discovery from creating a second record). If not, the record keeps no engine id (a later resume mints a fresh one: no transcript means the pin was never used) and C3's queue recovery does the rest at that launch (`submitting` → `queued` + `uncertain` with its notice; `released` → retired `interrupted` with its notice; the human decides with the transcript in view). Then remove the intent, `session.intent.changed { intent: null }`; nothing is sent. (b) none of the three: the message never reached C3. The intent stays, `failed`, with `progress.lastFailure { phase: 'launching', message: 'MAWS quit before the session started', resources: { record: 'kept', transcript: 'none', worktree: kept } }`, the record is kept (a retry's `createForLaunch` answers `exists` and reuses it), the pin is kept (no transcript, so no collision), a retained worktree is kept, and the tab shows the failure card with Retry; nothing launches (D-16: never auto-resume). In both branches a `progress.bootstrap` id is `session.forget`-ed (nothing is reserved at start) and cleared. An intent whose record does not exist needs no reconciliation (nothing reached `launching`; its `progress.launch` is null by construction). Pinned in M3 with the service restarted over the same temp store at each crash point: before `session.launch`, after `launching` before `ready`, after `ready` before `session.send`, after C3 persisted the entry before the answer (the fake host's `send` resolves late), after the answer before `progress.send`, after `progress.send` before the intent's removal, and with a transcript present at each of the last four.

**Resume** (`session.start` on a record without an intent): in order, the guards answer synchronously: `archived` (unarchive first), `already_live` and `held` from `holderAuthority` (a reservation, then a live registry holder; the attach object filled for a job with a `jobId`: `attachCommand(binaryInfo.path, jobId)`), `missing_directory` when `record.directory` is not a directory on disk, `needs_trust` when the key is untrusted and `options.trust` is not given (`accepted` runs the bootstrap first, under a bootstrap id of its own with a transient note under `<userData>/sessions/bootstraps/`, never under the record's app id, whose statuses C4 would apply to the conversation; for the home directory no bootstrap runs and the resume launch attests per session; `declined` launches unattested; the decision is per resume and not stored on the record). Then `toLaunchSpec` with `resume: { sessionId: record.engineSessionId, fork: false }` when the record has an engine id (else a fresh pinned session), `cwd: record.directory`, `additionalDirectories: record.additionalDirectories` (the SPEC marks `--add-dir` not persisted, so they are re-passed from the record; discovered sessions have `[]`), `model: 'model' in options ? options.model : record.model.requested`, `effort: 'effort' in options ? options.effort : (record.effort when it is an `EffortSchema` value, else null)` (the overrides are C11's: its Direct switch passes a Direct-compatible model when the session was on a gateway model such as `claude/astra`, which the direct route cannot serve; a resume without them launches the record's values), `permissionMode: record.permissionMode.requested`, `gateway: options.gateway ?? (record.gateway.routed ? 'gateway' : 'direct')` (the record's last route unless the caller says otherwise; C11's ask, its route switch passing `options.gateway`), `inheritGrantsFrom: null` (C3 re-applies the session's own snapshot by app id); the phases `launching` → `ready` stream as `session.setup`, and a `message` given with the resume (C7's Send on an exited session) is sent at `ready` exactly as a first message is. **[refresh]** if C4's `SessionRecord.directory` keeps the original cwd of a relocated session and the effective directory is index-only, C10 asks C4 for an additive `SessionRecord.effectiveDirectory` and launches there.

**`session.fork`**: refused `unknown_session`, `no_engine_session` for a record without an engine id, and `busy` while the source has a turn open in MAWS (C3's `session.status.turn !== null`: a copy taken mid-turn would hold a half-written turn). Allocates a fork intent `{ kind: 'fork', source: { appSessionId, engineSessionId, rewindTo }, location: inPlace ? { kind: 'directory', path: source.directory } : { kind: 'newWorktree', repoRoot, name, branch }, additionalDirectories, model, effort, permissionMode, gateway from the source's record, trust: 'unanswered', message }` and runs `session.start` on it at once; the renderer opens the fork's tab on `{ status: 'starting' }` (the tab shows the setup phases, then the copied conversation). The launch is `--resume <source> --fork-session --session-id <progress.engineSessionId>` (Ask of C3), so the fork's engine id is known from spawn and the record binds it as a new session's does; no transcript is copied: the engine finds the source transcript in the current project directory, then every git worktree's project directory, then all of `projects/*` (SPEC §35 12.5, 17.1), and writes the fork under the launch directory's slug under the pinned id with the history re-written (Surprises; `pass3/fork-worktree-fork.jsonl`, and M1's `fork-pinned-id` fixture for the pin). The rename `<source title> (fork)` reaches the engine's store once `ready` (the engine inherits the source's custom title otherwise, SPEC §35 16.6); an AI-titled source is left to the engine. C7's `ResubmitProvider.forkFrom({ appSessionId, messageUuid, content })` is `session.fork { target: { kind: 'inPlace' }, message: { content, display }, rewindTo: messageUuid }`.

**`session.archive`**: `holderAuthority` first (a foreign holder is not MAWS's to stop: refused `held`); `session.stop { reason: 'archive' }` when live (C3 runs the termination ladder and deletes the journal; the store file with queue and grants is kept, so an unarchived session resumes with them), `sessions.update({ archived: true })`, the renderer closes its tabs on `session.changed`. The dialog names the running background tasks and workflows from `session.status.backgroundTasks` (§4.4: exit never silently discards background work) and, when the session is the last non-archived session of a managed worktree, offers the cleanup dialog afterwards (the ladder's own commands; archive does not run them). Unarchive is `session.update { archived: false }` (C4's command) from the Archived sessions dialog.

**`session.delete`** (delete conversation) answers `DeleteOutcome = { status: 'deleted', trashed: string[] } | { status: 'held', holder } | { status: 'live' } | { status: 'stop_unconfirmed', detail } | { status: 'partial', trashed: string[], failed: { path, error } }`. In order: `holderAuthority` → `held` for a foreign holder; `live` for a MAWS reservation unless `stopIfLive`, in which case `session.stop { reason: 'archive' }` and then **only** `{ exited: true }` continues: `{ exited: false }` (SIGKILL's exit not observed inside C3's 7 s ladder; the reservation stays until the OS reports it) answers `stop_unconfirmed` with nothing moved, and the dialog offers to try again in a moment; after a confirmed exit the holder is rechecked fresh and a new holder aborts with `held`. Then the **deletion manifest**: every path is enumerated and `stat`ed before the first move and the list is written to `<userData>/sessions/deletions/<appSessionId>.json`: the sidecar directory `<projects>/<slug>/<sessionId>/`, the siblings `<sessionId>.precompact.json` and `<sessionId>.ccr-tip.json`, every recording `<projects>/<slug>/<sessionId>-<stamp>.cast` matched by the exact regex `^<sessionId>-[^/]+\.cast$` (recordings are flat, project-level files, not sidecar entries, SPEC §35 lines 494–504), and last the transcript `<sessionId>.jsonl`, where `<projects>` is C4's `resolveStorePaths(env).projects` and `<slug>` is the directory of the record's transcript path (**[refresh]** `transcript_path` is an index-only column; C10 reads it through the store, not the record). Moves run in that order with `shell.trashItem`, the transcript last, so a failure before it leaves the conversation discoverable and the record intact: the answer is `partial` naming the failed path, the manifest keeps what moved, and a retry re-enumerates (already-moved paths are absent). After the last move: `session.forget` (C3: store file, journal), `sessions.remove(appId)`, the manifest deleted. `fs.sessionRemoved` from C4's watcher arrives once the transcript moves and archives the record with `transcript_path` cleared (C4's rule); the service ignores that transition during the operation (the manifest, not the record, holds the paths) and removes the record at the end; a manifest found at start (a crash mid-way) is reported in the session's tab with "Finish deleting" and "Keep". The Trash rather than `unlink`: the owner's mental model, reversible from Finder, no bespoke tombstone; the engine's own quarantine name (`<id>.orphaned-<ms>-<hex>.jsonl`) is its mechanism for unreadable transcripts, not a user deletion, and `claude project purge` is per project.

**`session.rename`**: live (C3 lists a non-exited process) → `session.renameSession { title }` (the engine writes the `custom-title` record and sidecar; C4's index picks it up as the engine's fact and keeps the override consistent, its title rule); not live → `session.update { title: { text, source: 'user' } }` (C4's override). A later `/rename` in the terminal wins over the override by C4's rule, which is the provenance the charter asks for: the record's `title.source` says whose act named it. No write-through on the next resume: it would append a duplicate `custom-title` record to every resumed session with a user title, discovered ones included.

**D-16 reset** at `start()`: every record with `holder.kind === 'self'` is reset to `none` through `SessionStore.resetSelfHolders()` (C10's additive method on C4's store; C3 owns no process at app start, so every `self` is stale), before the read model publishes; the intent files and the bootstrap notes are loaded, every bootstrap id found (`progress.bootstrap`, `<userData>/sessions/bootstraps/*.json`) is `session.forget`-ed and cleared (nothing is reserved at start), then `reconcile()` runs (Handoff recovery) and only then does `session.intent.list` answer, so the renderer's intent snapshot, and C5's hydration through `registerTabRetention.ready`, see the settled set (an unstarted tab restored by C5's layout renders from it; an intent whose tab is gone stays until the owner discards it from the tab it reopens in, or forever harmlessly); a deletion manifest found is surfaced as above. Guards never read `self`: "live in MAWS" is C3's `engine.sessions`, "foreign" is the fresh registry read.

**Attach**: `attachCommand(path, jobId)` where `path` is `engine.binaryInfo.path` (the pinned binary; the owner's login shell may resolve `claude` to a wrapper), shell-quoted with single quotes; the command reaches C9's `pty.spawn.command`, which the PTY host writes after spawn followed by `\n`. The job's `cliVersion` (C4's `JobState`) is shown beside the affordance when it differs from the pinned version; the attach still uses the pinned binary. The affordance appears for `holder.kind === 'background_job'` with a `jobId`, in the session pane's `HolderNotice` and in the row's context menu; never on the Overview card (§5.2: foreign-live cards show the holder and no controls).
