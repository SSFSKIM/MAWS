## Purpose

After C10, a session in MAWS has a whole life, and it begins the way Codex and Claude Desktop begin one: a project's "+" (or ⌘N) opens a session tab at once. Nothing has been launched; the tab shows one heading naming the project with C7's ordinary composer centred beneath it, built as Claude Desktop builds a new chat (D-20, §5.4 as amended 2026-09-28), and the composer frame's chips are the setup: location chips above the box (the project directory, a new git worktree with its branch, or one of the repository's existing worktrees; add directory), the permission mode and the model with effort in the toolbar row below it. The owner types and sends. That first send starts the session: the worktree is created if one was chosen; if the directory has never been trusted a trust card docks at the composer and asks, and on the owner's word MAWS attests trust to the engine so the project's settings, hooks, MCP servers and plugins load exactly as they do in the terminal (a trust bootstrap launch under a throwaway identity of its own records the trust first, because the engine's launch-time readers only see trust from the next launch; the home folder, whose trust the engine never keeps, is attested per launch instead and the card says what that cannot load); if the owner declines, the session still starts and shows the engine's own notice that project rules were ignored; if the relay is down a card offers ClaudeUsage or a direct launch; then the engine launches, the session binds its identity, the message becomes the first turn, and the row appears in the sidebar. A worktree MAWS creates lives where the engine's `EnterWorktree` puts its own (`<repo>/.claude/worktrees/<name>`, branch `worktree-<name>`), so the two coexist and the owner's terminal habits keep working. Any session can be resumed after the app restarts (D-16: records, drafts, queued messages, grants and unstarted setups survive; processes do not), forked in place, or forked into a new worktree (a small popover for the name and branch), where the new session starts with the old conversation and resumes from the terminal like any other. Sessions can be renamed (a rename reaches the engine's store when the session is live, and stays MAWS's own until it is), archived (the process stops, the record hides, the worktree is offered for cleanup), and deleted (the transcript and its siblings go to the Trash, never silently, and never half-way). Cleaning up a worktree distinguishes four things the owner means differently: archiving its sessions, removing a clean checkout, discarding uncommitted changes, deleting the branch, each its own command with the worktree's identity revalidated before anything is deleted. A session that a terminal or a `claude --bg` job holds opens read-only with its holder named; a background job offers "Attach in a terminal tab", which opens C9's terminal running the engine's own `claude attach <id>`, and MAWS's own resume guard, fed by a fresh read of the engine's live registry, refuses to become a second writer, with the engine's refusal authoritative for background jobs.

What C10 does not do: render the transcript or the composer (C6, C7; C7 owns the strip's chips and binds them to C10's intent hook), the panel host (C8), the palette widgets or the settings screens (C11), the prewarmed spare (C12; the `claim_session` trust mapping is written here, not exercised), a source-control panel (P1), or any write into `~/.claude` beyond the one this document names (the Trash move of a deleted conversation and nothing else; the fork copies no transcript, see Surprises; trust is recorded only by the engine).

## Terms

- **Trust key**: the path under which the engine records trust for a directory in the global config (`projects[<key>].hasTrustDialogAccepted`): the root of the git repository's main worktree when the directory is inside a repository (linked worktrees share it), else the directory's own NFC-normalised realpath (SPEC §3 15.1–15.4; verified by the pass-3 probe, Surprises). **Global config**: the file the engine resolves by SPEC §3 16.1 (Trust, below); MAWS reads it and never writes it. **Attestation**: telling the engine the human accepted trust, through `initialize.workspaceTrust { accepted: true, directory: <trust key> }` (X6), or `claim_session.workspace_trust` for a prewarmed spare (P1). **Trust decision**: the human's answer to the trust step, a tri-state `unanswered | accepted | declined` kept in the setup intent; only `accepted` maps to an attestation.
- **Trust gates**: what the engine withholds in an untrusted directory: project and local `permissions.allow` and `permissions.additionalDirectories`, hooks, `settings.env`, `.mcp.json` servers, project plugins and marketplaces (SPEC §3 15.5). Two classes (SPEC §45 `workspaceTrust`, the schema text at line 4422): permission rules and hooks **re-derive in the running process** once the attestation is recorded; `.mcp.json` approval, project plugins and agent-frontmatter hooks and MCP servers are **read at launch** and see the recorded trust from the next launch on. The **trust notice** is the engine's stderr line `Ignoring N permissions.allow entries from .claude/settings.json: this workspace has not been trusted. …` (fixture `pass2/trust-no-attestation.jsonl` seq 5). It is printed at settings load, before `initialize` is read, so it appears on attested launches too and means "ignored" only when the attestation did not record trust.
- **Trust bootstrap**: for a never-trusted key whose decision is `accepted`, an extra engine launch that carries the attestation, is confirmed by `workspace_trust_recorded: true`, and is stopped; the session's real launch follows, so every gate, the launch-time ones included, is open on the process the owner actually uses. It runs under a **bootstrap id**, a fresh `appSessionId` minted for it alone (never the conversation's, whose record C4 would otherwise patch with the bootstrap's engine id and default selections), recorded as `progress.bootstrap` and `session.forget`-ed once its reservation releases; occupancy sees it through `EngineSessionStatus.cwd`. Shown as one `trusting` phase. Never run for the home directory (SPEC §3 15.3: its trust is session-only; the engine answers `session_only`, `workspace_trust_recorded: false`).
- **Managed worktree**: a git linked worktree under `<repoRoot>/.claude/worktrees/<name>` on branch `worktree-<name>`, the engine's own convention (SPEC §47 11.1) and MAWS's. **Repository root**: the main worktree's root (the parent of `git rev-parse --path-format=absolute --git-common-dir` when that directory's basename is `.git`), which is where managed worktrees are created whichever worktree the owner started from. A **hand-made worktree** is any other linked worktree; cleanup never assumes its name or branch.
- **Cleanup ladder**: the four distinct operations on a worktree: archive its sessions, remove a clean checkout, discard uncommitted changes (then remove), delete the branch. Each is its own command with its own guard (Interfaces, Cleanup state machine).
- **Holder**: C4's `SessionRecord.holder`: `self` (a process C3 owns), `terminal` (an interactive `claude` with a live registry record), `background_job` (a `claude --bg` job, `jobId` its eight-hex short id), `none`. **Foreign-live**: holder `terminal` or `background_job`. **Holder authority**: at a destructive or exclusive boundary (resume, delete, cleanup) the holder is decided from a fresh read of the engine's live registry (`sessions/<pid>.json`, C4's liveness rule) unioned with C3's process reservations (`engine.sessions`, each carrying its spec's `cwd`, so a reservation with no record counts), never from the index projection, which is asynchronous. **Attach**: the engine's `claude attach <short>` run in a C9 terminal tab.
- **Setup intent**: the persisted description of a session that has not been launched yet: location, branch, model, effort, permission mode, additional directories, gateway, trust decision, first message, fork source; kept under the allocated `appSessionId` at `<userData>/sessions/intents/<appSessionId>.json` until the session is **identity-bound** (C3 reports `ready` with the session's engine id and the first message, when there is one, has been handed to C3's queue). **Handoff**: the moment the first message becomes C3's: `session.send` answered and its `queueId` is recorded as `progress.send`; the intent is removed only after that record. **Reconciliation**: at app start, an intent whose record exists is settled against the record, the pinned id's transcript and C3's persisted queue (Handoff recovery, Interfaces), never re-run from scratch. An **unstarted session** is an app session id with an intent and no record with an engine status (C7's definition): it has a tab and no sidebar row, and in fact no record at all, because rollback and the start-time reconciliation both remove a provisional record whose launch never reached C3 (so C5's pane rule, "no record", and C7's definition name the same tabs). **Setup**: the run of one `session.start` from the command to `ready` or `failed`, reported as `session.setup` events. **Rollback**: undoing what a failed setup created (a worktree and its branch, a provisional record), per resource, never what existed before, never by force without the human's consent, and never a transcript: a launch that wrote one has a conversation, which stays.
- **Fork in place** / **fork to a new worktree**: `--resume <id> --fork-session --session-id <new>` launched in the source's directory, or in a worktree created for it; the engine finds the source transcript in any project directory and writes the new session under the launch directory's slug under the pinned new id (Surprises; SPEC §35 16.5–16.6).
- **Catalogue**: the engine's model list (`list_models` / the `initialize` response's `models`), each entry with `value`, `displayName`, `supportsAutoMode`, `supportsFastMode` (fixture `reads.jsonl`). A **gateway model** is an entry whose `value` starts with `claude/` (the relay's aliases for non-Anthropic providers: `claude/astra|sol|luna|terra`, `claude/<vendor>/…`); auto mode on it runs the classifier locally on Sonnet 5 and counts as usage (§19).
- **Session service**: C10's main-process module (`src/main/sessions/service.ts`) that owns the lifecycle commands. **Store file**: C3's per-session state file (`<userData>/engine-host/state/<appSessionId>.json`: queue, grant snapshot, last launch spec). **Deletion manifest**: the list of a conversation's files enumerated and persisted before the first Trash move, so a failure half-way is reported and resumable.

The reader has no second source: an entry `Xf()` ignores (an older per-worktree entry under a repository root) is ignored here too (architect's ruling).

**Trust bootstrap** (`bootstrapSpec()`; run by the setup's `trusting` phase, for a create and for a resume alike): needed iff the decision is `accepted`, the key is not the home directory, and `trustStateOf(directory).trusted` is false at the start of the attempt (an already-trusted key attests on the real launch only, which the engine answers `already_trusted` → `true`, harmless). The bootstrap is an ordinary `session.launch` under a **bootstrap id**: a fresh UUID v4 minted for this bootstrap alone, persisted first as `progress.bootstrap { appSessionId, at }` (for a resume, in a transient per-resume note the service keeps in memory and on disk beside the intents, `<userData>/sessions/bootstraps/<bootstrapId>.json`, so a crash leaves it findable), never the conversation's `appSessionId`. The spec is `{ appSessionId: <bootstrap id>, cwd, additionalDirectories, gateway, trust: { accepted: true, directory: trustKey }, model: null, permissionMode: null, resume: null, sessionId: null (C3 mints one), inheritGrantsFrom: null }`. The service waits for `session.status` `process: 'ready'` and reads `status.trust.recorded`: `true` → `session.stop { reason: 'stop' }`, then waits for the reservation to release (`{ exited: true }`, or `process.exited` within 10 s after `{ exited: false }`), `session.forget { appSessionId: <bootstrap id> }` (store file and journal; refused `already_live` only while reserved, which the wait excludes), clears `progress.bootstrap` and records `progress.trustRecorded = true` with `trustKey`; `false` or `null` → stop and forget the same way and fail the setup with `error: 'the engine did not record trust for <trustKey>'` (the outcome is in the engine's debug log, SPEC §45 18.2; the intent is retained). A bootstrap that never reaches `ready` fails as any launch does; one whose stop is not confirmed within 10 s fails the setup and leaves `progress.bootstrap` set, and the next attempt (or the start-time reset) forgets it once it is no longer reserved. Why a second launch: SPEC §45 line 4422 (`workspaceTrust`): rules and hooks re-derive in the running process, but `.mcp.json` approval, project plugins and agent-frontmatter hooks and MCP servers are read at launch and see the recorded trust from the next launch on; `--await-initialize` does not change that (it pre-reads the request for its `plugins` field only, SPEC §45 line 322 and §2 line 947). Why its own id: a resume runs this bootstrap too, and an existing conversation has a record, which C4's `IndexSessionSource` patches from every `session.status` of a known app id (`toSessionRecordPatch`: engine session id, model, effort, permission mode); under the conversation's id the bootstrap's fresh engine id and default selections would overwrite the real conversation's durable identity and settings, and an interruption before the real launch would leave that persisted (round-2 finding 2). Under its own id nothing in the index ever hears of it (C4 applies statuses only for known app ids), C5's read model drops its statuses (Ask of C5), occupancy still counts it through `EngineSessionStatus.cwd` (Ask of C3), and `session.forget` at release leaves no store file or journal for an id that never has a record. Why it leaves nothing behind on disk: an `initialize`-only launch writes no transcript (the pass-2 trust probes' directories hold no file for their no-turn launches, Surprises), and `-p` writes no registry record (C4); the acceptance asserts the absence. Evidence: the `trusting` phase emits two `session.setup` events, `detail: 'Trusting <trustKey>'` at the launch and `detail: 'Trust recorded for <trustKey> (bootstrap <engine id>)'` at release, so the Diagnostics event log names the bootstrap's engine id after its journal is gone; the fixture `pass3/trust-bootstrap-recorded.jsonl` (M1) is the recorded wire shape.

### Worktrees (`src/main/git/worktrees.ts`, X2 `git.worktree.*`, owner `main`)

Every git call goes through C4's runner (`/usr/bin/git` or `MAWS_GIT`, `execFile`, `GIT_TERMINAL_PROMPT=0`, `LC_ALL=C`, 10 s): `createGitRunner({ env? }): GitRun`, `GitRun = (directory, args) => Promise<string>`, with the failures `NotARepositoryError`, `GitCommandError` (git's first stderr line) and `GitTimeoutError` (`src/main/git/runner.ts`), and C4's parsers `parseStatus`, `parseRevParse`, `parseBranches` (`src/main/git/porcelain.ts`). The runner sets `GIT_OPTIONAL_LOCKS=0` on every call (`gitEnv`, runner.ts:50-55); that suppresses only optional locks (`git status` refreshing the index), not the required locks `worktree add`, `worktree remove` and `branch -D` take, so mutations use the same runner (the earlier "without `GIT_OPTIONAL_LOCKS=0` for mutations" is withdrawn). C4's read-only proof asserts the subcommands `GitService` runs (`src/main/git/service.test.ts:199-224`), so `worktrees.ts` sits beside it without touching that proof. No network: no fetch, ever; a base that is a remote-tracking ref is used as it stands. Every command takes `repoRoot` and normalises it to the main root (`rev-parse --path-format=absolute --git-common-dir` from it); a path is matched against `worktree list --porcelain` by NFC realpath on both sides, so a hand-made worktree reached through a symlink or `/tmp` still matches (the engine canonicalises the same way, Surprises).

| Command | Input | Output | Invocation and guards |
|---|---|---|---|
| `git.worktree.list` | `{ repoRoot }` | `{ repoRoot, commonDir, worktrees: WorktreeInfo[] }` | `worktree list --porcelain` (`worktree`, `HEAD`, `branch`, `detached`, `locked`, `prunable` stanzas); `managed` iff the path is under `<repoRoot>/.claude/worktrees/`; the branch is what git says, never derived from the directory name |
| `git.worktree.status` | `{ repoRoot, path }` | `WorktreeStatus \| null` | null when the path is not listed (removed or never a worktree); else the list entry plus `status --porcelain=v2 --branch -z --untracked-files=normal --ignore-submodules=dirty` in the worktree (C4's parser; the engine's own cleanliness probe, SPEC §23 3.2), `occupancy` from holder authority by directory (below), `state`: `busy` when `occupancy.self + foreign + unbound > 0` or `locked`, else `dirty` when `dirty.tracked + untracked > 0`, else `clean` |

| `git.worktree.add` | `{ repoRoot, name, branch }` | `WorktreeInfo` | path `<repoRoot>/.claude/worktrees/<worktreeDirName(name)>`; refused `IpcError internal` with a named message when: the repository has no commit (`rev-parse --verify HEAD` fails: `repository has no commits`), the path exists (`worktree path exists`), the branch exists for `kind: 'new'` (`branch exists`), the branch does not exist or is checked out elsewhere for `kind: 'existing'` (`branch missing` / `branch checked out at <path>`), `validateWorktreeName` fails, `check-ref-format --branch <branch>` fails, or `rev-parse --verify <base>^{commit}` fails (`base not found: <ref>`), all before anything is created. | `git.worktree.remove` | `{ repoRoot, path, expect: { branch: string \| null, head: string }, discard: boolean }` | `{ removed: true, prunedOnly: boolean } \| CleanupRefusal` | a fresh `status`; refused `missing` when null, `changed` when `branch` or `head` differ from `expect` (the owner's terminal moved it since the dialog opened), `busy` / `locked` by the state, `dirty` unless `discard`; then `worktree remove [--force] <path>` (`--force` iff `discard`), then `worktree prune`; a `prunable` entry (directory already gone) skips to `prune` with `prunedOnly: true` |
| `git.worktree.deleteBranch` | `{ repoRoot, branch, expect: { head: string }, acknowledgeUnmerged: boolean }` | `{ deleted: true, wasMerged: boolean } \| CleanupRefusal` | a fresh `branch`; refused `missing` when null, `changed` when `head` differs from `expect`, `checked_out` when `checkedOutAt` is set, `unmerged` when `merged` is false and `acknowledgeUnmerged` is false; then `branch -D <branch>` |

**Cleanup state machine.** Four separately expressible operations; the dialog captures the worktree's identity once (`{ repoRoot, path, branch, head }` from `git.worktree.list`) and every later step revalidates it through `expect`. The state is derived by `cleanupState({ worktree, branch })` from fresh `git.worktree.status` and `git.worktree.branch` reads immediately before each step, never cached.

| State | Definition | Archive sessions | Remove checkout | Discard changes and remove | Delete branch |
|---|---|---|---|---|---|
| `busy` | `worktree.state === 'busy'` (a MAWS process, a foreign holder, an unbound registry holder, or locked) | allowed for `idleAppSessionIds` only; the live ones are skipped and named (never stops a process) | refused `busy: <n> sessions live here` | refused | refused |
| `dirty` | not busy; `dirty.tracked + dirty.untracked > 0` | allowed | refused `dirty: N changes` | allowed with `discard: true` (the dialog's explicit acknowledgement names the count) | after removal only |
| `clean` | not busy; no changes | allowed | allowed | not offered | after removal only |
| `detached` | `worktree === null` and `branch !== null` (the branch exists, no checkout has it) | allowed | nothing to remove | nothing | allowed; `merged` false shows `N commits not on <base>` and needs `acknowledgeUnmerged` |
| `gone` | neither the worktree nor the branch | allowed | — | — | — |

Archive sessions is not a git command and never stops a process: the dialog calls `session.archive { appSessionId, onlyIfIdle: true }` for each id in `occupancy.idleAppSessionIds` (tabs close on `session.changed`). The snapshot alone is not the guard, because a session can resume between `git.worktree.status` and the command: `onlyIfIdle` makes `session.archive` recheck holder authority inside that session's serialised operation and answer `{ status: 'skipped_live', holder }` instead of stopping a session that is live by then (Session service, below). The dialog reports what it skipped by name: every `liveAppSessionIds` entry and every `skipped_live` answer with its title and holder (`Working in MAWS`, `terminal · <pid>`, `bg · <short>`) and the `unbound` count, under "Not archived: N live sessions; archive them from their rows" (the ordinary per-session archive dialog is the only place a process is stopped, with its background-work disclosure; this dialog offers no stop and its step never calls `session.stop`). A `busy` worktree therefore stays `busy` after the step, and the remove and delete steps stay refused. Remove and delete branch are the two commands above, invoked one after the other by the dialog when both are checked, each answering for itself; nothing already done is undone, because a removed checkout cannot be restored and an archived session can be unarchived. A hand-made worktree (any name, any branch, detached HEAD included) is handled by the same commands from the identity git reports; a detached checkout has no branch step. Reason for the four distinctions: they are what §4.5 binds and what the owner means by "clean up": a worktree whose sessions are archived is still a checkout the terminal can use; a removed checkout still has a branch to open a PR from; discarding is the only step that loses work, and deleting an unmerged branch is the only one that loses commits, so those two carry the acknowledgement.

### Holder authority (`src/main/sessions/holders.ts`)


The verdict is computed at the moment it is needed, never read from `SessionRecord.holder`: `engine.sessions` (C3's process table: an entry with `process` not `exited` is `self`, the reservation outliving the process until the OS reports the exit) unioned with a fresh registry read through C4's service (`fs.holders`, the Ask below, which runs `HolderRegistry.refresh()` under C4's liveness rule and answers by session id and by directory). Precedence: a reservation wins (`already_live`), else a live registry holder (`held`), else `none`. C4's `fs.holders` fails closed: any non-ENOENT read or listing error answers `{ ok: false, code: 'internal', message: 'holder registry unreadable: <code>' }` (ENOENT alone means no holders), and `holderAuthority` treats that answer as a refusal of the start, archive or delete it was guarding, surfaced to the human with that message (`refused { reason: 'unknown_session' }` is not it; the outcome is the command's `IpcError` with C4's message), never as "no holders". `occupancyOf(directory)` counts reservations whose `EngineSessionStatus.cwd` realpath equals the directory (`self`; the field is the Ask of C3, present from the reservation onward, so a record-less trust bootstrap counts and `fs.holders` is not asked to know a process that writes no registry record), registry holders whose `cwd` realpath equals it and whose session id the index knows (`foreign`) or does not (`unbound`), and index records whose `worktree.path` or `directory` equals it and that have no process (`idle` / `archived`); `idleAppSessionIds` and `liveAppSessionIds` partition the non-archived records here by whether a reservation or a foreign holder names them. Every path is compared as NFC realpath. What remains: a client that writes no registry record (another SDK host's print-mode process) is invisible to MAWS and to the engine alike (pass-2 item 10); and between the fresh read and the launch a terminal can still start (a window of tens of milliseconds, closed only by the engine's own `--bg` refusal). Both are accepted under D-12 and stated in the residue rather than promised away. MAWS's own lifecycle operations on one `appSessionId` (`start`, `archive`, `delete`, `fork` of it as source, `rename`) are serialised through a per-session promise chain in the service, so two MAWS operations never interleave on one session.

**Rollback** is per resource and never forces: (1) the transcript question first: if `progress.launch` is set and `<projects>/<slugOf(cwd)>/<progress.engineSessionId>.jsonl` exists (C4's `resolveStorePaths` and `slugOf`), the launch wrote a conversation, and rollback stops being a rollback: the record is kept and bound (`sessions.bindEngineId(appId, progress.engineSessionId)`, which also `fs.bind`s so discovery attributes the file to this record and never creates a second; when the record already carries an engine id other than the pin, a `/clear` in the first message rebound it under C4's rule and the record stands as bound, since `bindEngineId` with the pin would rebind it back), the worktree is kept, the intent is removed, and `failed` carries `{ record: 'kept', transcript: 'kept', worktree: { state: 'kept', … } }`: the session exists, exited, resumable, with C3's exit notice as its explanation (never trash a transcript from an attempt that reached `launching`; only the human's Delete moves one); (2) otherwise a record this attempt created: `sessions.remove(appId)` (emits `session.removed`, cascades drafts and attention; C5 keeps the tab because C10's `retains(id)` is true for the retained intent, Ask of C5) → `record: 'removed'`, `transcript: 'none'`; (3) a worktree `createdHere`: `git.worktree.remove { expect: { branch, head: progress.worktree.head }, discard: false }` → `removed`, then for a `branch.kind === 'new'` created here `git.worktree.deleteBranch { repoRoot, branch, expect: { head }, acknowledgeUnmerged: false }` → `branchState: 'deleted'` (`delete_refused` with the detail when a hook committed on it, `changed`/`unmerged`, so a branch with commits is never deleted by rollback; `delete_failed` with git's message), and `progress.worktree` is cleared so the next attempt creates afresh under the initial rules; or `remove_refused` when the state is `dirty` (a startup hook, `git worktree add`'s `post-checkout` hook, or the engine wrote there) or `busy`, or `remove_failed` with git's message: a refused or failed removal leaves the worktree, keeps `progress.worktree` (so retry validation reuses it and a `location` patch is refused `retained_worktree`), and the failure card offers "Retry", "Discard changes and remove" (the cleanup dialog's acknowledgement, then `remove { discard: true }`, the branch step as above, `progress.worktree` cleared) and "Keep the worktree" (the checkout is detached from the attempt: `progress.worktree.createdHere = false`, the location becomes `{ kind: 'existingWorktree', repoRoot, path }`, the branch stays; the intent stays and its chips are editable again; the worktree is listed for cleanup like any other); (4) `session.forget` (C3's store file and journal) only when the intent is discarded, not on a failure, because the journal is the evidence of what failed; a `progress.bootstrap` id is forgotten as soon as it is not reserved. `session.setup { phase: 'failed' }` carries the whole `resources` object, so the tab says exactly what was undone and what was not. A `session.start` of an existing record rolls nothing back; a fork's rollback touches the fork's resources and never the source. During a rollback the service ignores `session.changed` for the app id (C4's watcher may archive the record when a transcript moves) and finishes with `sessions.remove` or `bindEngineId` regardless.

**Handoff recovery** (`recovery.ts`, `reconcile()` at `start()`, after C3's host answers and before `session.intent.list` does). Persisting the intent before effects and removing it after the handoff is not exactly-once on its own: the app can die between C3 accepting the first message and the intent's removal, and a naive restart would re-run the fresh launch with a pin whose transcript exists (the engine refuses `Session ID <id> is already in use`, SPEC §35 16.5, `statSync` in the current project directory) or send the message twice. So an intent whose record exists (`sessions.get(appSessionId)` non-null: `createForLaunch` ran) is **reconciled, never re-run from scratch**, from three facts: `transcript` = the file `<projects>/<slugOf(cwd)>/<progress.engineSessionId>.jsonl` exists; `queue` = `session.queue.list { appSessionId }` (Ask of C3 (2): the persisted queue of an unreserved id) has any entry, where C3's documented `unknown session` answer (no reservation and no store file: the app died between `createForLaunch` and `session.launch`) reads as `queue = false`, and any other error (an unreadable or corrupt store file) propagates as this intent's reconciliation failure: nothing is removed, bound or launched, the intent and record stay as persisted, the tab's failure card names the error, and its Retry re-runs the reconciliation for that id, never the setup; `sent` = `progress.send` is set. (a) `sent || transcript || queue`: the message is delivered or C3's. The facts are about the pin; a `/clear` switches the engine id mid-process and C4 rebinds the record (Ask of C4, landed), so when the record's engine id is non-null and differs from the pin (only a first message that was itself `/clear` can do that before the intent is removed) the record's id stands: nothing is bound or unbound, and the intent is dropped. Otherwise, if `transcript`, `sessions.bindEngineId(appId, pin)` (the record's engine id is the pin; a later resume is `--resume <pin>`; `fs.bind` keeps discovery from creating a second record). If not, `sessions.unbindEngineId(appId)` (Ask of C4 (3)): C4's `IndexSessionSource` binds the pin from the first status that carries it, before any transcript exists, so the record may hold a bound id with no conversation, and a resume would run `--resume <pin>` against nothing; unbinding clears the engine id and its fs binding, leaves C3's queue and grants under the app id untouched, and makes the later user-initiated launch a fresh pinned session (`resume: null`, a fresh pin: no transcript means the old pin was never used), at which C3's queue recovery does the rest (`submitting` → `queued` + `uncertain` with its notice; `released` → retired `interrupted` with its notice; the human decides with the transcript in view). Then remove the intent, `session.intent.changed { intent: null }`; nothing is sent. (b) none of the three: the message never reached C3. The provisional record is removed exactly as rollback step (2) removes it (`sessions.remove(appId)`, `session.removed`; the tab survives through C5's `registerTabRetention`, whose predicate is the retained intent); the intent stays, `failed`, with `progress.lastFailure { phase: 'launching', message: 'MAWS quit before the session started', resources: { record: 'removed', transcript: 'none', worktree: kept } }`, the pin is kept (no transcript, so no collision), a retained worktree is kept, and the tab shows the failure card with Retry, whose `createForLaunch` recreates the record under the same app id; nothing launches (D-16: never auto-resume). In both branches a `progress.bootstrap` id is `session.forget`-ed (nothing is reserved at start) and cleared. An intent whose record does not exist needs no reconciliation (nothing reached `launching`; its `progress.launch` is null by construction). Pinned in M3 with the service restarted over the same temp store at each crash point: before `session.launch` (the fake host's `session.queue.list` throws the documented `unknown session`), after `launching` before `ready`, after `ready` before `session.send`, after C3 persisted the entry before the answer (the fake host's `send` resolves late), after the answer before `progress.send`, after `progress.send` before the intent's removal, and with a transcript present at each of the last four; before each restart from `launching` on, a real launch status carrying the pin is applied through C4's `IndexSessionSource`, so the record is bound as it would be live and the transcript-absent cases assert the unbind.

**Resume** (`session.start` on a record without an intent): in order, the guards answer synchronously: `archived` (unarchive first), `already_live` and `held` from `holderAuthority` (a reservation, then a live registry holder; the attach object filled for a job with a `jobId`: `attachCommand(binaryInfo.path, jobId)`), `missing_directory` when `record.directory` is not a directory on disk, `needs_trust` when the key is untrusted and `options.trust` is not given (`accepted` runs the bootstrap first, under a bootstrap id of its own with a transient note under `<userData>/sessions/bootstraps/`, never under the record's app id, whose statuses C4 would apply to the conversation; for the home directory no bootstrap runs and the resume launch attests per session; `declined` launches unattested; the decision is per resume and not stored on the record). Then `toLaunchSpec` with `resume: { sessionId: record.engineSessionId, fork: false }` when the record has an engine id (else a fresh pinned session), `cwd: record.directory`, `additionalDirectories: record.additionalDirectories` (the SPEC marks `--add-dir` not persisted, so they are re-passed from the record; discovered sessions have `[]`), `model: 'model' in options ? options.model : record.model.requested`, `effort: 'effort' in options ? options.effort : (record.effort when it is an `EffortSchema` value, else null)` (the overrides are C11's: its Direct switch passes a Direct-compatible model when the session was on a gateway model such as `claude/astra`, which the direct route cannot serve; a resume without them launches the record's values), `permissionMode: record.permissionMode.requested`, `gateway: options.gateway ?? (record.gateway.routed ? 'gateway' : 'direct')` (the record's last route unless the caller says otherwise; C11's ask, its route switch passing `options.gateway`), `inheritGrantsFrom: null` (C3 re-applies the session's own snapshot by app id); the phases `launching` → `ready` stream as `session.setup`, and a `message` given with the resume (C7's Send on an exited session) is sent at `ready` exactly as a first message is. **Disk-to-live handoff** (C4's Outcomes): an exited session's tab is fed from disk by C4's follower (`session.events` answers from `diskEvents` while C3 has no stream, `src/engine-host/ipc.ts:161-167`) and nothing stops it at launch, so after the guards and before `session.launch` a resume of a record with an engine id calls `fs.unfollow { appSessionId, agentId: null }` (the session's and its agents' followers; a record with no engine id has no fs binding and so no follower, and `fs.unfollow` would answer `unknown app session`, so it is skipped); the call runs inside the session's serialised operation and its failure fails the resume before anything launches. **One engine id per launch, not per app session**: `record.engineSessionId` is the id the record is bound to now, which a `/clear` inside MAWS moves to the new transcript (C4's rebind), so a resume continues the post-`/clear` conversation, as the engine's own `--continue` would; each earlier transcript is a record of its own and resumes from its own row. A session is resumed only under its own record's app id (C4's rebind assumes it, its Decision Log after M7 hardening); the bootstrap's own id never carries `resume`, and a fork's new id carries `resume.fork` under a pinned id of its own. The directory is settled (the former **[refresh]**): C4's `upsertFromSummary` writes `SessionRecord.directory` from the transcript's last `relocated` record when there is one (`src/main/index/sessions.ts:184-191`), so `record.directory` is the effective directory and no additional field is asked.

**`session.fork`**: refused `unknown_session`, `no_engine_session` for a record without an engine id, and `busy` while the source has a turn open in MAWS (C3's `session.status.turn !== null`: a copy taken mid-turn would hold a half-written turn). Allocates a fork intent `{ kind: 'fork', source: { appSessionId, engineSessionId, rewindTo }, location: inPlace ? { kind: 'directory', path: source.directory } : { kind: 'newWorktree', repoRoot, name, branch }, additionalDirectories, model, effort, permissionMode, gateway from the source's record, trust: 'unanswered', message }` and runs `session.start` on it at once; the renderer opens the fork's tab on `{ status: 'starting' }` (the tab shows the setup phases, then the copied conversation). The launch is `--resume <source> --fork-session --session-id <progress.engineSessionId>` (Ask of C3), so the fork's engine id is known from spawn and the record binds it as a new session's does; no transcript is copied: the engine finds the source transcript in the current project directory, then every git worktree's project directory, then all of `projects/*` (SPEC §35 12.5, 17.1), and writes the fork under the launch directory's slug under the pinned id with the history re-written (Surprises; `pass3/fork-worktree-fork.jsonl`, and M1's `fork-pinned-id` fixture for the pin). The rename `<source title> (fork)` reaches the engine's store once `ready` (the engine inherits the source's custom title otherwise, SPEC §35 16.6); an AI-titled source is left to the engine. C7's `ResubmitProvider.forkFrom({ appSessionId, messageUuid, content })` is `session.fork { target: { kind: 'inPlace' }, message: { content, display }, rewindTo: messageUuid }`. The source is the record's current engine id (after a `/clear`, the new transcript), so a `rewindTo` older than the source's last `/clear` is not in the resumed history: the setup's `session.rewind` refuses it and the fork rolls back as any failed setup does; forking from before a `/clear` is done from the earlier transcript's own row.

**`session.archive`** (inside the session's serialised operation): `holderAuthority` first (a foreign holder is not MAWS's to stop: refused `held`); with `onlyIfIdle: true` (the cleanup dialog's archive step, whose snapshot may be stale) any live verdict, a MAWS reservation or a foreign holder alike, answers `{ status: 'skipped_live', holder }` and nothing is stopped or changed; otherwise `session.stop { reason: 'archive' }` when live (C3 runs the termination ladder and deletes the journal; the store file with queue and grants is kept, so an unarchived session resumes with them), `sessions.update({ archived: true })`, the renderer closes its tabs on `session.changed`. The dialog names the running background tasks and workflows from `session.status.backgroundTasks` (§4.4: exit never silently discards background work) and, when the session is the last non-archived session of a managed worktree, offers the cleanup dialog afterwards (the ladder's own commands; archive does not run them). Unarchive is `session.update { archived: false }` (C4's command) from the Archived sessions dialog. Attention retires on both paths without C10: C3's archive emits `session.forgotten`, and the index turns every committed `archived: true` into the same signal for main's attention service (`src/main/index/attention-service.ts:31-40`). C3's archive branch keeps the state file (architect's ruling, 2026-09-28): `session.stop { reason: 'archive' }` deletes the journal directory only, through a new `SessionStateStore.forgetJournal(id)`, and `forget` stays the whole erase behind C10's `session.forget` (C3's fix, master after 733051f; the refresh pass had found `ipc.ts:168-188` calling `forget` there). This paragraph, the Grant snapshot residue and acceptance item 9 stand as written.

**`session.delete`** (delete conversation) answers `DeleteOutcome = { status: 'deleted', trashed: string[] } | { status: 'held', holder } | { status: 'live' } | { status: 'stop_unconfirmed', detail } | { status: 'partial', trashed: string[], failed: { path, error } }`. In order: `holderAuthority` → `held` for a foreign holder; `live` for a MAWS reservation unless `stopIfLive`, in which case `session.stop { reason: 'archive' }` and then **only** `{ exited: true }` continues: `{ exited: false }` (SIGKILL's exit not observed inside C3's 7 s ladder; the reservation stays until the OS reports it) answers `stop_unconfirmed` with nothing moved, and the dialog offers to try again in a moment; after a confirmed exit the holder is rechecked fresh and a new holder aborts with `held`. Then the **deletion manifest**: every path is enumerated and `stat`ed before the first move and the list is written to `<userData>/sessions/deletions/<appSessionId>.json`: the sidecar directory `<projects>/<slug>/<sessionId>/`, the siblings `<sessionId>.precompact.json` and `<sessionId>.ccr-tip.json`, every recording `<projects>/<slug>/<sessionId>-<stamp>.cast` matched by the exact regex `^<sessionId>-[^/]+\.cast$` (recordings are flat, project-level files, not sidecar entries, SPEC §35 lines 494–504), and last the transcript `<sessionId>.jsonl`, where `<projects>` is C4's `resolveStorePaths(env).projects` and `<slug>` is the directory of the record's transcript path, read through the store: `sessions.summaryOf(appId)` answers the `TranscriptSummary` with `transcriptPath` and `slug` (`src/main/index/sessions.ts:150`; the path is not on the record), and when it answers null (a `/clear` rebind cleared the transcript columns until the new transcript's first summary) the slug is `slugOf(record.directory)` (`resolveStorePaths` and `slugOf` are C4's pure functions in `src/engine-host/fs/paths.ts`, which main already imports from). The manifest is the record's current transcript only: a transcript from before a `/clear` is a record of its own and is deleted from its own row. The Trash rather than `unlink`: the owner's mental model, reversible from Finder, no bespoke tombstone; the engine's own quarantine name (`<id>.orphaned-<ms>-<hex>.jsonl`) is its mechanism for unreadable transcripts, not a user deletion, and `claude project purge` is per project.

**`session.rename`**: live (C3 lists a non-exited process) → `session.renameSession { title }` (the engine writes the `custom-title` record and sidecar; C4's index picks it up as the engine's fact and keeps the override consistent, its title rule); not live → `session.update { title: { text, source: 'user' } }` (C4's override). No write-through on the next resume: it would append a duplicate `custom-title` record to every resumed session with a user title, discovered ones included.

**D-16 reset** at `start()`: every record with `holder.kind === 'self'` is reset to `none` through `SessionStore.resetSelfHolders()` (C10's additive method on C4's store; C3 owns no process at app start, so every `self` is stale), before the read model publishes; the intent files and the bootstrap notes are loaded, every bootstrap id found (`progress.bootstrap`, `<userData>/sessions/bootstraps/*.json`) is `session.forget`-ed and cleared (nothing is reserved at start), then `reconcile()` runs (Handoff recovery) and only then does `session.intent.list` answer, so the renderer's intent snapshot, and C5's hydration through `registerTabRetention.ready`, see the settled set (an unstarted tab restored by C5's layout renders from it; an intent whose tab is gone stays until the owner discards it from the tab it reopens in, or forever harmlessly); a deletion manifest found is surfaced as above. Guards never read `self`: "live in MAWS" is C3's `engine.sessions`, "foreign" is the fresh registry read.

**Attach**: `attachCommand(path, jobId)` where `path` is `engine.binaryInfo.path` (the pinned binary; the owner's login shell may resolve `claude` to a wrapper), shell-quoted with single quotes; the command reaches C9's `pty.spawn.command`, which the PTY host writes after spawn followed by `\n`.
