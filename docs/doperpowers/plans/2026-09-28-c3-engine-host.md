## Purpose

After C3, MAWS can hold a real conversation with the pinned Claude Code binary without any UI to speak of. From the renderer, `window.maws.invoke('session.launch', { spec })` starts one `claude` process in the engine-host utility process with exactly the launch contract of §4.1 and D-19: the absolute pinned binary, the fixed flag set, a constructed environment routed through ClaudeUsage's relay after a health check, dialog expiry "never", `perTaskStopAffordance`, the two dialog kinds, and trust attestation when a caller supplies it. Text and thinking stream in as X1 events; a tool call that needs the human arrives as a `permission.requested` event and an attention item, is answered with `session.answer`, and its result comes back attributed to the right tool use; AskUserQuestion, plan approval with its three outcomes, MCP elicitation and host hook callbacks take the same road. A second message typed while a turn runs is queued by the app, survives the process dying, and is released only when the human's turn ends, never into an engine-initiated follow-up. Steer, Stop and Resume behave as the composer labels them. Every structured read the terminal's menus use is a typed call. Every frame in and out is journaled in the probe's format, and replaying that journal through the normaliser yields the same event graph the live run produced. When a process dies with approvals outstanding the broker says so once ("session interrupted, 2 approvals lost"); when it is resumed, its session grants are re-applied so nothing asks twice.

What C3 does not do: render anything (C5, C6, C7, C8), read `~/.claude` (C4), create worktrees or show the trust sheet (C10), or decide when an idle process may exit (C12; the interim rule is never).

## Terms

- **Engine**, **engine process**: one `claude` child process, launched by absolute path `/Users/new/.local/share/claude/versions/2.1.283`, speaking newline-delimited JSON on stdin and stdout. One per live session.
- **Frame**: one JSON object on that wire. **Control request** and **control response**: the request/response envelopes (`control_request`, `control_response`, `control_cancel_request`) both sides use for RPC; a request has a `request_id` chosen by its sender. **Inbound request**: a control request the engine sends us (`can_use_tool`, `hook_callback`, `elicitation`, `request_user_dialog`). **Outbound request**: one we send (`initialize`, `interrupt`, `get_status`, …).
- **Turn**: from the host's querying `user` frame (a **human turn**, opened the moment the frame is written so the prompt bubble shows on send) or from the `system/init` the engine emits for a turn it starts itself (an **engine-initiated turn**, after a background task or workflow completes; `result.origin.kind` is `task-notification`; never the `system/init` of a pending `!` echo) to the `result` frame that closes it. Inside a human turn the `system/init` frame marks the engine's acceptance (`EngineSessionStatus.turn.acceptedAt`), not the turn's start. An **echo receipt** is the empty `result` (`num_turns: 0`, no `terminal_reason`) that follows a `shouldQuery: false` user frame; it is not a turn.
- **Journal**: the recording of every frame, one row per line `{seq, direction, at, frame}` with `direction` in `in`, `out`, `meta`, `stderr` (X8). **Fixture**: a journal recorded by the protocol probe under `spikes/protocol-probe/fixtures/` (pass 1) and `fixtures/pass2/` (pass 2); C3 adds `fixtures/pass3/`.
- **Normaliser**: the pure function from journal rows to X1 `SessionEvent`s. **Event graph**: the X1 record of a session (`src/shared/graph/`).
- **Broker**: the permission broker of §4.6, the one pending table for every inbound request that needs a human, with the states pending, delivered, confirmed, retired. **Attention item**: the X1 record a pending broker item produces; the broker's items reach main as the internal event `session.brokerItems`, and main's **attention service** (C3's, `src/main/attention/service.ts`) merges them with the non-broker kinds, persists them through the `AttentionStore` port and owns `attention.*`; the Needs-you section reads those.
- **App queue**: the message queue MAWS owns (§4.2 "Queue ownership"): messages typed while a turn runs, persisted, released one at a time. Distinct from the **engine queue**, the engine's in-memory queue of `user` frames it has accepted but not yet folded into a turn.
- **Steer**: a message sent while a turn runs that bypasses the app queue and reaches the engine immediately with `priority: 'now'`, the engine's highest queue priority, so it folds into the running turn at the next opportunity instead of waiting for the turn to end.
- **Grant**: a session-scoped permission rule MAWS issued by answering a permission with `updatedPermissions` whose `destination` is `session`. **Grant snapshot**: the list of those rules kept app-side so they can be re-applied after a resume (§4.4).
- **Process table**: the engine host's in-memory table of live engine processes and what keeps each alive; exposed as `EngineSessionStatus`.
- **Launch spec** (`LaunchSpec`): the input to `session.launch`; the X6 launch contract in code is the function from a launch spec to a binary path, argument list, environment and cwd.
- **Relay**: ClaudeUsage's loopback gateway at `http://127.0.0.1:8641` (D-19). **Routed** and **direct**: an engine process whose inference goes through the relay, or straight to Anthropic with the engine's own login.
- **Lane** (auto mode): the server lane, where the main model's provider judges tool calls and the verdict arrives as `safeguard_results` on `message_delta`; and the local lane, where the engine's own classifier requests (Sonnet 5, charged as usage) decide. `get_status` reports the lane as the "Auto mode server" row.
- **Engine host**: the utility process `src/engine-host/` that C1 forks; **host protocol**: the main ↔ host envelope of `src/shared/ipc/host-protocol.ts`; **X2 command/event**: the renderer ↔ main IPC of `src/shared/ipc/schema.ts`. A command a host owns is routed to it by main; an event a host emits is re-emitted to the renderer after validation.
- **Replay transport**: a test seam in the engine host that stands in for a process and plays a fixture's `in` rows, advancing when the adapter writes the `out` frame the fixture recorded next; a write the fixture did not record is a replay mismatch and ends the replay. Its **handshake prelude** is the synthetic journal `test/fixtures/engine/replay-handshake.jsonl` (rows copied from `pass2/auto-routed.jsonl`) that answers the host's own startup and periodic controls (`initialize`, `get_status`) when the fixture being played did not record them. It exists so the whole adapter runs under vitest and Playwright with no engine; it is not the product's replay mode (C4 owns that, X8).
- **Submission**: one app-queue entry on its way into the engine: persisted as `submitting` before the `user` frame is written, `released` when the engine's `command_lifecycle` names its uuid. A send while the engine is idle is a submission too; the queue is what makes two quick sends serialise.
- **Operation**: an X2 command whose engine round trip may outlast the bridge's 10 s router timeout (C1 Interfaces, X2). It answers a receipt `{ opId }` as soon as the request frame is flushed and completes through the event `session.operation`.
- **Termination ladder**: the bounded sequence that ends a process: `end_session` (skipped when the handshake never completed), wait, close stdin and `SIGTERM`, wait, `SIGKILL`, wait; the process is `exiting` from the first rung until the OS reports the exit, and `exited` only then.

`args`, in this order: the §4.1 flag set verbatim; `--model <m>` when `model` is set; `--permission-mode <mode>` when set; one `--add-dir <d>` per additional directory; `--session-id <uuid>` for a new session (`spec.sessionId` or a fresh UUID v4, so the journal file and the session record know the engine id before the first frame); `--resume <id>` and `--fork-session` when `resume` is set, and for a fork (`resume.fork === true`) also `--session-id <spec.sessionId ?? minted>` after them so the fork is pinned like a new session (C10's ask, SPEC §35 16.5 `ns`: `--session-id` is accepted beside `--resume` when `--fork-session` is set; 16.6 point 1: the startup id is kept and the fork writes under it; C10's own probe records `fixtures/pass3/fork-pinned-id-*.jsonl`); a non-fork resume never carries `--session-id`, and `sessionId` set together with `resume.fork === false` is a `LaunchSpecConflict { key: 'sessionId' }`; `--mcp-config <json>` when set; `--max-budget-usd <n>` when set; last, `--settings <json>` where the JSON is `flagSettings`, built by `mergeFlagSettings(spec)`: start from `extraSettings ?? {}`, then apply the host's **protected keys** last so nothing a caller passes can displace them: `dialogExpiry: 'never'`; `effortLevel` when `effort` is set; `env.ANTHROPIC_BASE_URL: ''` and `env.ANTHROPIC_AUTH_TOKEN: ''` when `gateway === 'direct'` (pass 2 verified that unsetting the variables does not defeat the owner's `settings.json` routing). The merge is nested one level for `env` (a caller's other `env` keys survive beside the two the host sets) and shallow elsewhere (`permissions`, `enableWorkflows`, `fileCheckpointingEnabled` pass through untouched). An `extraSettings` that carries a protected key with a different value is a conflict, not an override: `buildLaunch` throws `LaunchSpecConflict` naming the key and `session.launch` answers `refused { reason: 'settings_conflict' }` without spawning. The protected set is `dialogExpiry`, `env.ANTHROPIC_BASE_URL`, `env.ANTHROPIC_AUTH_TOKEN` under both gateway modes (a settings-level base URL would silently re-route a gateway launch too), and `effortLevel` only when `spec.effort` is set (with `effort: null` the caller may set it, as "null = settings" promises). `--strict-mcp-config` is never passed: the user's MCP servers must load as in the terminal.

### Transport (`src/engine-host/transport.ts`, `replay-transport.ts`)

```ts
export interface EngineTransport {
  readonly pid: number | null;
  frames: AsyncIterable<{ frame: unknown; raw: string }>;   // parsed stdout lines, in order; malformed lines are reported, not thrown
  stderr: AsyncIterable<string>;                            // one line per item
  write(frame: StdinFrame): Promise<void>;                  // resolves when the bytes reached the OS pipe (write callback), rejects on EPIPE/closed
  endInput(): void;                                         // stdin.end()
  kill(signal: 'SIGTERM' | 'SIGKILL'): void;
  readonly exited: Promise<{ code: number | null; signal: NodeJS.Signals | null }>;
}
export function spawnEngine(plan: LaunchPlan, opts: { maxLineChars: number }): EngineTransport;
export function replayEngine(journal: JournalRow[], opts: { prelude: JournalRow[]; answers?: 'recorded' }): EngineTransport;   // plays `in` rows; a row after an `out` control_request/response waits for the adapter's matching write (by subtype + request_id echo); `initialize` and `get_status` the fixture did not record are answered from `prelude`; any other unrecorded write is a replay mismatch that ends the stream; `stderr` rows replay; `meta exit` ends the stream
```

Framing: stdout is decoded with a `StringDecoder('utf8')` so multibyte characters split across chunks survive; the splitter cuts on `\n`, ignores blank lines, strips a leading U+FEFF, and treats an unterminated line over `maxLineChars` (64 Mi characters) as a transport error that kills the process with `error.raised { scope: 'transport' }` (the engine's own budget is 256 Mi; ours protects the host's memory; spilled tool results live on disk and never approach it). A line that fails `JSON.parse` is journaled as `meta { event: 'parse_error', length, typeGuess }` and surfaced as `error.raised { scope: 'transport' }`; the session continues. Writes are serialised through one promise chain (one writer on stdin, §4.2); `write()` is `JSON.stringify(frame) + '\n'` and awaits the socket's write callback, honouring `drain` when `write` returned false, so a caller that awaits `write()` knows the frame left the process. The engine escapes U+2028/2029 on its output for other consumers; its own reader splits on `\n` only, so we do not escape. `keep_alive` is never sent (the engine drops it on input). Stderr is split the same way and journaled as `stderr` rows.

### Control channel (`src/engine-host/rpc.ts`, `controls.ts`)

```ts
export type RequestClass = 'read' | 'mutate' | 'interrupt' | 'long' | 'human';
```

Request ids we mint: `${launchId}-${n}` with `n` a per-process counter from 1 and `launchId` eight base32 characters minted at spawn; the engine's own ids are UUIDs, so a journal reader tells the two namespaces apart at a glance and ids never collide across a resume within one session's journals. Classes: `read` for every `get_*`, `list_*`, `mcp_status`, `export_conversation`, `get_status`, `rewind_files` dry run; `mutate` for `set_permission_mode`, `set_model`, `set_max_thinking_tokens`, `apply_flag_settings`, `rename_session`, `stop_task`, `background_tasks`, `cancel_async_message`, `set_cwd`, `rewind_conversation`, `rewind_files`, `end_session`; `interrupt` for `interrupt`; `long` for `initialize`, `claim_session`, `generate_session_title`, `side_question`, `reload_plugins`, `mcp_reconnect`, `mcp_toggle` (the last two spawn or tear down a server process and take as long as the server does); `human` (no timeout) for the inbound requests we answer. The 8 s bound is comfortable on the evidence: every read and mutation in `pass1/reads.jsonl` (seq 52–90) and the `interrupt` of `pass1/queue-and-interrupt.jsonl` (seq 190–192) answered within a few milliseconds, and `generate_session_title` took 570 ms. On timeout the promise rejects with `ControlTimeout`, the pending entry moves to a late table for 60 s so a late response is journaled and logged rather than treated as unexpected, and a `control_cancel_request` is written (harmless for uncancellable subtypes; the engine "simply completes the request"). A timeout never proves the mutation did not apply (SPEC 45.16.4), so a late success is reconciled, not ignored: the late response is journaled, `notice.posted { level: 'warning', key: 'late_response:<subtype>:<requestId>' }` tells the human the operation applied after the error they saw, and the state the mutation touched is corrected by the next frame that carries it (`system/status` for the permission mode, the next `system/init` for the model, `list_permission_rules` on demand for grants). An `error` response rejects with `ControlError` carrying `error_code` when present (the auto-mode refusal codes ride here). Response payloads are parsed with the typed schema of `controls.ts`; a parse failure rejects (the wire changed under us) and the raw response stays in the journal.

**Deadlines and operations.** C1's router fails a host-owned command with `IpcError { code: 'timeout' }` after 10 s and its `CommandSpec` carries no per-command deadline (C1 Interfaces, X2), so the host never lets a control deadline outlive the bridge. Every X2 command the host answers takes one of three shapes, named per command in the X2 tables below: **immediate**, answered from host state or as soon as a frame is flushed, no control response awaited (`session.launch` at spawn, `session.send`, `session.steer`, `session.queue.*`, `session.answer`, `session.bash` at the `bash_command` write, `session.status`, `session.events`, `session.pendingRequest`, `engine.*` except `shutdown`); **bounded**, awaiting one or more `read`/`mutate`/`interrupt` round trips under one 8 s budget shared across the handler's requests (a handler that issues two requests, `session.rewind` with `files: true` or `session.memoryAppend`, passes the remaining budget as `timeoutMs` to the second), answering `IpcError { code: 'timeout', message: '<subtype> unanswered after 8 s' }` on `ControlTimeout` so the caller can tell the host's deadline from the router's (thrown as a `HostCommandError`, "Typed errors through the host runtime" below); the termination ladder (7 s) makes `session.stop` and `engine.shutdown` bounded too; and **operations**, for the `long` subtypes a command can reach (`session.generateTitle`, `session.reloadPlugins`, `session.sideQuestion`, `session.mcpReconnect`, `session.mcpToggle`): the handler writes the request, answers `OperationReceipt { opId }` once the frame is flushed (`opId` is the minted request id, so the journal correlates it), and the `OperationTable` (`src/engine-host/operations.ts`) emits `session.operation` exactly once when the request settles (typed success, `ControlError`, `ControlTimeout` at the 120 s `long` deadline, write failure, or process exit, in which case every open operation of that process settles with `error.code: 'exited'`); a response that arrives after the timeout, inside the 60 s late table, emits a second `session.operation` for the same `opId` with `outcome.ok: true` and `late: true`, which is how a consumer that showed the failure reconciles. Operations are not events and not in the ring: a renderer reload loses in-flight receipts, acceptable in P0 because each operation's effect is visible through state the ring and the status already carry (the title through `session.status` and the index, plugins through the next `system/init`, MCP through `mcpServers`). `initialize` and `claim_session` are `long` but sit on the launch path, which answers at spawn.

**Typed errors through the host runtime.** C1's `createHostRuntime` (`src/shared/host/runtime.ts`, the `catch` around line 94) turns every error a handler throws into `ipcError('internal', message)`, and a handler that returned an error envelope as its value would fail the command's output validator, so no host-originated code but `internal` could reach the renderer and the `timeout` above could not cross the bridge. The architect authorises a small typed-error extension to that file, which C3 makes as one delimited block and records as a C1 file C3 extends (ledger section (c)): `export class HostCommandError extends Error { constructor(readonly ipcError: IpcError) }`, and the runtime's catch forwards `error.ipcError` intact when the thrown value is a `HostCommandError` whose `ipcError` passes `IpcErrorSchema` (`code`, `message`, optional `issues`), falling back to `internal` for everything else exactly as today. The engine host throws `new HostCommandError({ code: 'timeout', message: '<subtype> unanswered after 8 s' })` from a bounded handler on `ControlTimeout` and `new HostCommandError({ code: 'internal', message: 'unknown session <appSessionId>' })` for an unknown session; no other code is thrown in C3, and nothing changes for the PTY host, which runs the same runtime and throws nothing typed. The regression case added to `src/shared/host/runtime.test.ts` (C1's file, one `it`) pins that a handler throwing `new HostCommandError({ code: 'timeout', message: 'get_usage unanswered after 8 s' })` answers `{ t: 'res', ok: false, error: { code: 'timeout', message: 'get_usage unanswered after 8 s' } }` while a plain `Error` still answers `internal`.

### Normaliser (`src/engine-host/normalizer.ts`)

```ts
export class Normalizer {
  constructor(ctx: { appSessionId: AppSessionId; sessionId: SessionId | null });
  push(row: JournalRow): SessionEvent[];           // pure w.r.t. inputs seen so far; keeps only the correlation state below; the ONLY source of events in the host
  readonly state: { sessionId: SessionId | null; currentTurn: { origin: 'human' | 'engine'; userMessageUuids: MessageUuid[] } | null; toolUseToAgent: Map<ToolUseId, AgentId>; safeguards: Map<ToolUseId, SafeguardVerdict>; lastUserMessageUuid: MessageUuid | null; pendingHumanUuids: Set<MessageUuid>; pendingEcho: MessageUuid | null; outbound: Map<RequestId, { subtype: OutboundSubtype; request: unknown }>;
                    streaming: Map<ParentToolUseId | null, { apiMessageId: ApiMessageId; started: { index: number; type: string }[] }>; completedBlocks: Map<ApiMessageId, number> }
}
```

Every event the host emits derives from a journal row, and the host writes the row before it normalises it: there is no `synthesize()` path. For an `out` frame the row is written when the transport's `write()` resolves (the bytes reached the pipe, §4.6's delivery truth), not before the write is attempted, so the graph never shows as sent a frame the engine never received; a write that rejects journals `meta { event: 'write_failed', frameType, subtype, requestId, message }` instead (→ `error.raised { scope: 'transport' }`), and the caller (broker item left `pending`, queue entry reverted) may retry and produce the real row then (M3 review, 2026-09-28). Because `write()`'s continuation can run after the read loop has already seen the engine's reply, the session buffers every inbound frame that arrives while an out write is in flight and journals the buffer only after that write has settled (the out row or its `write_failed` row first), so a response row never precedes its request row, a `tool_result` never precedes the answer that allowed it, and the broker's states advance strictly pending → delivered (at the flushed row) → confirmed; the broker's `answer_note` row is written after the flush too, beside the answer, so a failed write leaves no note behind (M3 re-review, 2026-09-28). What the design calls app-synthesised (`process.exited`, `session.reconnect`, `error.raised` for transport and process trouble, the rewind boundary) is derived from `meta` rows the host writes for the purpose, or, for the rewind boundary, from the correlated request and response rows. So `seq` is never null for a live event, every id is `${appSessionId}:${launchId}:${seq}:${i}`, and re-reading the journal through a fresh `Normalizer` reproduces the live event list exactly, ids and `seq` included, which is what `session.events` relies on once the ring has evicted a range (M5). `state.outbound` records every `out` `control_request` row by request id so an `in` `control_response` (whose envelope carries only `success`/`error`, never the subtype) can be attributed to its subtype; entries leave the map when the response row arrives. `state.pendingEcho` is the uuid of a `shouldQuery: false` frame the host wrote whose receipt has not arrived: the engine runs the echo through a command lifecycle of its own (`pass2/bash-context-echoed` seq 10–14: `queued`, `started`, `system/init`, the empty `result`, `completed`), so its `system/init` at seq 12 must not read as an engine-initiated turn and its `result` at seq 13 must close nothing. The guard is explicit in the normaliser, not left to consumers, because an engine `turn.started` carries `userMessageUuid: null` and would pass C6's echo-uuid guard (its reducer drops a `turn.started` naming an echo uuid, nothing else); C6's replay stub keeps the same rule ("no `shouldQuery: false` `out` frame since the last `result`").

Block indices (the rule C6 keys live blocks on, `<apiMessageId>:<blockIndex>` from the first delta, paired with the complete event): the engine emits one `assistant` frame per content block, not per message (every one of the 119 `assistant` frames across both passes carries exactly one block; two frames share `message.id` `req_011CfVeJnkqVCt7c4XHwT9sZ` in `pass2/dialogs` seq 14 and 28), and the frame arrives before that block's `content_block_stop` (seq 14 precedes seq 15). So `assistant.block.complete.blockIndex` is not the block's position inside its frame; it is the stream's index: the normaliser keeps, per lane (`parentToolUseId`, null for the main conversation), the current `apiMessageId` from `message_start` and the queue of `{ index, type }` from each `content_block_start`, and an `assistant` frame pops the head of its `message.id`'s queue for each block, in content order, giving the complete event the same `apiMessageId` and `blockIndex` the deltas carried (a type mismatch between the started block and the frame's block is journaled as a `meta block_pairing` warning and the index still assigned). A message whose blocks arrive with no stream events at all (child agents: pass 1 verified no token-level `stream_event` for children) has an empty queue and gets `blockIndex` in content order per `apiMessageId`, 0 for the first block completed under that id, counting up (`completedBlocks`). Across all 40 fixtures this pairing holds with matching types for every streamed block (108) and covers every unstreamed one (11, all children); `pass1/subagent` has both. The one case the rule cannot cover, never observed: a `content_block_start` on a lane with no `message_start` before it, where the deltas would carry `apiMessageId: null`; C6's fallback then pairs a null-keyed delta run with the first following `assistant.block.complete` on the same lane with the same `blockIndex`.

States and transitions (§4.6): `pending` on `accept`; `delivered` when `answer` resolved the flushed write; `confirmed` on the first stdout frame carrying the item's `tool_use_id` (a `tool_result`, `tool_progress`, `hook_callback` request, `system/permission_denied`, or `result.permission_denials`); `retired` on answer confirmation, on an inbound `control_cancel_request` for the id (reason `abort`), on process exit (`exit`), or on `elicitation_complete`. Delivered is not an alarm state. An item whose request carries no tool-use id (MCP `elicitation`, `request_user_dialog`: `pass2/dialogs.jsonl` seq 41 has none, its answer at seq 43 is followed by neither `elicitation_complete` nor a cancellation) can never be confirmed by a frame, so §4.6's confirmation rule is read as applying to items that have an id, and an id-less item takes the other exit the rule allows: it retires (reason `turn_ended`) at the `result` that closes the turn in which it was delivered (seq 55 there), the earliest frame proving the engine moved past it. Until that `result` it stays `delivered`, which is correct: a process that dies mid-turn with the elicitation delivered has lost it. An id-less item delivered outside any turn (none observed) retires at the next `result`. On exit with `n > 0` pending or delivered items the broker retires them and reports `lost: n`, which rides on `process.exited.lostAttentionCount`; main's attention service raises exactly one attention item of kind `interrupted` with summary `Session interrupted, ${n} ${n === 1 ? 'approval' : 'approvals'} lost` (the string is the contract); the resumed process is trusted to have retired the dangling tool calls, so nothing is re-pended, except that an `initialize` response carrying non-empty `pending_permission_requests` or `pending_user_dialog_requests` re-accepts those (cheap, and correct for a process that outlived us).

Answers on the wire:

The broker refuses scopes other than `once` when `suppress_always_allow_rule` is set, when `decision_reason_type === 'rule'`, or when `matched_ask_rule` is present, answering `not_pending`? No: it answers as `once` and records `scopeDowngraded: true` on the resolved event's `message`; the card (C7) must not offer those scopes in the first place, so this is a guard, not a path. Every `session`-destination `addRules` we send is appended to the grant snapshot (`grants.ts`).

- dialog: `{ behavior, result }` verbatim; a `request_user_dialog` whose `dialog_kind` we did not declare is never answered `cancelled` (that would claim the human dismissed it): it stays pending with a `notice.posted` warning, because we declared only kinds we render (SPEC 45.22.13).

Attention items are split between the two processes (ruling 1 of the wave-2 ledger). The broker produces the broker kinds (`permission`, `question`, `plan`, `dialog`, `elicitation`; `kind` from the item kind) and emits the session's whole list as `session.brokerItems { appSessionId, items }` on every change. The service merges both sets per session, persists them through the `AttentionStore` port (`src/main/attention/store.ts`: `list()`, `replaceForSession(appSessionId, items)`, `retireForSession(appSessionId)`; C4's `Index.attention` implements it, and C3 ships `FileAttentionStore` at `<userData>/attention.json` until then, the `SessionStateStore` pattern), emits `attention.changed { appSessionId, items }`, and answers `attention.list` and `attention.request` (the latter by dispatching `session.pendingRequest` to the engine host; `null` for a non-broker kind). `summary` is one line: `${toolDisplayName}: ${first 80 chars of the command or description}` for permissions, the first question for questions, `Plan ready for review` for plans, the dialog kind or the MCP server name otherwise.

### Queue, steer, interrupt (`src/engine-host/queue.ts`, `src/shared/engine/session-state-store.ts`)

```ts

  onLifecycle(ev: Extract<SessionEvent, { kind: 'command.lifecycle' }>): void;     // submitting → released when `commandUuid` is an entry's messageUuid
  recover(): Promise<void>;                                                          // at construction: a persisted `submitting` entry becomes `queued` + `uncertain`, the queue pauses; a persisted `released` entry is retired `interrupted` (below)
```

Submission and release: a send while the session is not `busy` is written at once, and a send while it is busy is queued; both are the same entry going through the same states, which is what closes the race between two quick sends at an idle engine (the turn opens only at `system/init`, so "no turn open" is not "idle"). To submit, the queue mints `messageUuid`, persists the entry as `submitting` with `submittedAt`, and only then writes the `user` frame (`{ type: 'user', uuid, message: { role: 'user', content }, parent_tool_use_id: null, origin: { kind: 'human' } }`); from that persist until the `turn.ended` that closes the turn it started the session is `busy`, so a second send queues behind it. The entry becomes `released` when the engine's `command_lifecycle` with `command_uuid` equal to its uuid arrives (the engine acknowledges every stdin `user` frame this way: `pass2/dialogs.jsonl` seq 5–6, `pass1/init.jsonl` seq 2–3), or, failing that, when a `result.user_message_uuids` names it; a submission neither acknowledged nor named within 5 s of the flushed write stays `submitting` and posts `notice.posted { level: 'warning', key: 'queue:unacknowledged:<queueId>' }`. A `released` entry leaves the list at the `turn.ended` that names it, or at the process's exit: the acknowledgement is only the engine's `queued` (`pass2/dialogs` seq 6), so a process that dies after it and before the `result` (crash, `unknown`, stop, archive or quit alike) leaves an entry the resumed process can never name, and `busy` would hold every later send forever. At exit `MessageQueue.onProcessExited()` retires every `released` entry that no `turn.ended` has named: the entry leaves the persisted list (`released` never survives an exit), `notice.posted { level: 'warning', key: 'queue:interrupted:<queueId>' }` says the message was accepted but the session ended before it was answered, and nothing is re-sent: the dead launch's journal already shows the send (its `turn.started` and `user.message` derive from the `out` row) followed by `process.exited` with no `turn.ended`, which is what the resumed session's transcript shows as an interrupted send; the human re-sends it from the composer prefill (C7) if they still want it, never the queue. A `submitting` entry at exit takes the recovery path below (queued at the head, `uncertain`, paused). Release rule: when a `turn.ended` arrives with `isEchoReceipt: false` and `origin` `human` (or absent) and the queue is not paused, the head `queued` entry is submitted. No entry is ever released *into* an engine-initiated turn (§4.2): a `turn.ended` whose `origin` is `task-notification` (or any non-human kind) that leaves the session idle (no open turn, nothing submitting) with `queued` entries and the queue not paused releases the head exactly as a human turn's end does (`trigger: 'turn_ended'`), because D-20's references send a queued message as soon as the session is idle (coordinator ruling, 2026-09-28, overturning the M4 pause; the charter's C3 acceptance wording is clarified by the coordinator); only when the head cannot be released for another reason at that moment (the process is not `ready`, or a write fails) does the queue pause with `meta queue { action: 'pause', reason: 'engine_turn' }` and `notice.posted { level: 'info', key: 'queue:held_after_engine_turn:<queueId>' }`. A write that fails (EPIPE) reverts the entry to `queued`, pauses the queue and raises `error.raised { scope: 'transport' }`. Recovery: a `submitting` entry found in the store when the queue is constructed (the host or the app died between the persist and the acknowledgement) may or may not have reached the engine, and the host cannot tell; it is neither dropped nor re-sent silently: it reverts to `queued` at the head with `uncertain: true`, the queue pauses, and `notice.posted { level: 'warning', key: 'queue:uncertain:<queueId>' }` says a message may not have been delivered; the human, with the resumed transcript in view (C4's backfill shows the message if the engine wrote it), either removes it or resumes the queue, which re-submits it once and clears `uncertain` (an edit clears it too); a `released` entry found in the store at construction (the host or the app died after the acknowledgement; under D-16 the process is gone) is retired `interrupted` the same way as at exit, with the same notice, and is never re-submitted. `session.interrupt` sets `paused: true` ("queue paused because you interrupted"); the composer's Resume is `session.queue.setPaused(false)`, which submits the head if the session is not busy. Steer (`session.steer`, `session.queue.promote`) writes `{ ..., priority: 'now' }` at once, never enters the app queue, and is reported through `command.lifecycle` and the eventual `result.user_message_uuids`. Every change is saved through the store before `onChange` fires, so the queue survives the process and the app (the acceptance's "queued message survives a process exit").

`file-session-state-store.ts`: one JSON file per app session at `<userData>/engine-host/state/<appSessionId>.json` holding `{ version: 1, queue, grants, launchSpec }`, written to a temp file then renamed; the engine host receives `userData` from main through the `hello` message's existing fields or, until C1 exposes it, from `MAWS_USER_DATA`/`process.env` as the supervisor forwards it (M5 decides which and records it). This adapter is the P0 store and the home §4.4 (as amended 2026-09-28) gives queued messages and grants; the port is async so C12 could move them behind a cross-process adapter without touching the engine host.

The two `rewind_files` answers have different shapes, and the typed `RewindFilesResponse` (`{ canRewind, error?, filesChanged?: string[], insertions?, deletions?, skippedLinks?: number }`) accepts both: a dry run answers `{ canRewind: true, filesChanged, insertions, deletions }` where `filesChanged` is the list of paths the restore would touch, and a restore answers `{ canRewind: true, skippedLinks }` with a count and no statistics (`cli.pretty.js` 2.1.283, `vS` around lines 731401–731416: `n` selects the dry run, whose `jnt` at 970743–970770 collects `filePath`s; the restore's `vTt` at 970719–970742 returns `{ skippedLinks }`); a failed restore answers `{ canRewind: false, error: 'Failed to rewind: …' }`. `RewindFilesOutcome` therefore converts explicitly (`changedFiles` from the dry run's paths, `skippedLinks` from the restore) and a restore's missing counts are never read as checkpointing being unavailable: `enabled` turns on the exact error string alone.

Order: `rewind_conversation { target_message_uuid, last_seen_user_message_uuid, interrupt_if_running: false }` first; on `rewound: true` the normaliser derives `boundary.rewind { targetMessageUuid, precedingAssistantUuid, prefillText }` from the response row (Normaliser above; the engine emits no reset frame) and then, when `files` is true, `rewind_files { user_message_id: targetMessageUuid }` restores the checkpoint, its answer filling `files`; a refused conversation rewind (`stale_target`, `unseen_later_turn`, `turn_running`, `commands_queued`, `prompt_pending`, …) returns `rewound: false` with the engine's `reason` and touches no files. `lastSeenMessageUuid` is required from the caller (the transcript knows what the human has seen); the host never substitutes its own latest uuid, because that would defeat the guard against discarding an unseen turn. `session.rewindFiles` is `rewind_files { user_message_id, dry_run }` alone (no conversation rewind): with `dryRun: true` it answers the receipt's "can Undo" question and lists what would change, with `dryRun: false` it restores the checkpoint; the outcome's `enabled` is false only for the engine's `File rewinding is not enabled.` answer, so C6 hides the affordance exactly when the wire path does not exist.

`!`: `session.bash(command)` writes `bash_command { command, cwd: <session cwd>, uuid }` and answers `{ commandUuid }` at that write; when the two replayed `user` frames (`<bash-input>`, `<bash-stdout>…<bash-exit-code>`) arrive the host writes `user { uuid, shouldQuery: false, parent_tool_use_id: null, origin: { kind: 'human' }, message: { role: 'user', content: '<bash-input>${command}</bash-input>\n' + <the replayed stdout frame's content verbatim> } }` (if they have not arrived after 30 s it posts `notice.posted { level: 'warning', key: 'bash:no_output:<commandUuid>' }` instead and writes no echo); the following empty `result` is the echo receipt (`isEchoReceipt: true`), never a turn and never a queue release. Without the echo the model cannot see the output (`bash-context-alone`). The engine does not replay the echo frame on stdout (only its lifecycle frames, a `system/init` and the empty result follow, `bash-context-echoed` seq 10–14), so the normaliser emits the echo's `user.message` from the host's own `out` row: `{ messageUuid: <echo uuid>, origin: 'bash_echo', isSynthetic: true, isReplay: false, bash: null, content: <the frame's content> }`. On the wire the frame keeps `origin: { kind: 'human' }`: the stdin `origin.kind` vocabulary is the engine's closed union and an absent or unknown origin "fails closed at strict isHuman() trust gates" (SPEC 45.15.1), so the marker lives on the X1 event, where C6 reads it, not on the frame.

`#`: `session.memoryAppend({ text, target })` calls `get_memory_dialog`, chooses `files[]` by `target.kind` (`project` → `kind: 'project'`, `user` → `kind: 'user'`, `path` → the given path, which must be one of the listed files or folders), creates the file when `exists: false`, appends `\n- ${text}\n`, and returns the path. No wire mechanism exists for `#` (§4.2); the engine re-reads CLAUDE.md on the next turn.

The table is keyed by `appSessionId`, and a row is a reservation: it is taken when `session.launch` is accepted and released only when the OS reports the exit (`process: 'exited'`, the `meta exit` row written), never at an error. A second `session.launch` for a reserved `appSessionId` is refused `already_live` with `message` naming the state (`'process is exiting'` for a termination in progress), so a retry after a failed handshake cannot start a second writer on the same engine session while the first is still dying. `exiting` is entered by a requested stop, shutdown or archive, by a failed `initialize` (error response, `ControlTimeout` at the `long` deadline, or transport error before the response) and by the transport's line-budget kill; every entry runs the termination ladder (Exit policy below). ### Journal (`src/engine-host/journal.ts`)


Location `<userData>/engine-host/journal/<appSessionId>/<launchId>.jsonl`, one file per process launch (a resume is a new launch and a new file), rows `{seq, direction, at, frame}` with `seq` from 1 per launch, `direction` `in | out | meta | stderr`, `at` ISO-8601. Meta rows: `spawn` (bin, args with the `--settings` JSON, env key names, cwd, gateway mode, engineVersion, appVersion, charter pin), `relay_health`, `initialize` (the response's `current_permission_mode`, `session_state`, `hooks_applied`, `workspace_trust_recorded`), `status_check` (`baseUrl`, `autoModeServer`, `verified`), `queue` (releases and pauses), `exit` (`code`, `signal`, `reason`, `lostAttentionCount`, `peakTreeRssKiB`). Rotation: at 128 MiB the writer closes the file and continues in `<launchId>.<n>.jsonl`; `seq` continues. Pruning at host start: keep the 20 most recent launches per session and nothing older than 30 days; `session.stop { reason: 'archive' }` and `SessionStateStore.forget` delete the session's directory. Redaction: the production journal is a faithful record, because it is what `session.events` rebuilds live events from (Reload survival, binding) and a redacted frame would normalise differently from the live one; spawn environment values are omitted (the `spawn` row lists env key names only) and conversation content is preserved verbatim, as the engine's own transcript under `~/.claude` already does. The probe's redaction (values of environment keys matching `/TOKEN|KEY|SECRET|PASSWORD/`, `sk-ant-*`, e-mail addresses) is applied by `redactJournal` in `test/live/support/live.ts` when a run's journal is exported as a checked-in fixture (M6), never by the writer in production; the writer's `redact` option stays for that path and tests, and `row()` returns exactly the row the file holds. The journal is the source of `EventBase.seq`, the input to the replay transport, and what `session.events` reads when its ring buffer no longer holds the requested range.

Exit policy: every way out of a process runs the termination ladder, and the process is `exiting` from its first rung until the OS reports the exit. `session.stop` writes `end_session { reason }` (`cli.pretty.js` 2.1.283 around line 729534 aborts the turn, answers and leaves the read loop; no fixture recorded it, the probe closed stdin instead, so M6 is its first observation), waits 3 s for exit, then `endInput()` and `SIGTERM`, waits 3 s, then `SIGKILL`, waits 1 s, and answers with what it observed (7 s worst case, inside the bridge deadline); `process.exited.reason` is `stop` or `archive`. `engine.shutdown { graceMs }` runs the ladder for every live process in parallel with `reason: 'quit'`, `graceMs` being the `end_session` wait capped at 3000 (C5's quit guard passes 5000 and is honoured as 3000; the ladder still answers within the bridge), `stopped` counting exits before `SIGKILL` and `forced` the `SIGKILL`s; it is idempotent. A failed `initialize` (error response, `ControlTimeout`, transport error or exit before the response) enters `exiting` with a `meta init_failed` row (→ `error.raised { scope: 'process' }`, the stderr lines seen so far in the message: the `--resume` refusals "is running as a background session", "No conversation found" arrive there), skips the `end_session` rung (the handshake never completed), runs `endInput()` and `SIGTERM`, 3 s, `SIGKILL`, 1 s, and becomes `exited { reason: 'crash' }` at the real exit; an exit before the response is `exited { reason: 'crash' }` at once. An exit nobody asked for is `crash` when the code is non-zero or a signal killed it, `unknown` when it exited 0; both raise the broker's exit handling, pause the queue, and mark the status `exited`. The `process.exited` event is exactly `{ kind: 'process.exited', code, signal, reason, lostAttentionCount }` with `lostAttentionCount` the broker's `lost` (0 when nothing was pending or delivered), `seq` the `meta exit` row's, `agentId: null`, `parentToolUseId: null`, and `sessionId` the engine id of the process that died. The engine host never relaunches on its own (D-16), so in P0 `session.reconnect` fires only on a user-initiated resume of an app session whose previous process exited, with exactly these payloads: `{ kind: 'session.reconnect', phase: 'attempting', attempt: 1, maxAttempts: 1, trigger: 'user', reason: null }` when `session.launch` with `resume` is accepted; then `{ …, phase: 'reconnected', reason: null }` when the new process's `initialize` response arrives, or `{ …, phase: 'failed', reason: <the launch error message, stderr lines included> }`; each derives from a `meta reconnect` row of the new launch's journal (`attempting` is its first row), so `seq` is that row's and `sessionId` = the resumed engine session id. The triggers `process_exit`, `host_restart` and `transport_error` and `attempt > 1` are reserved for C12's supervisor and are never emitted in P0.

## Residue decisions

Ready to paste into the charter's C3 section as "**Residue decisions (C3, 2026-09-28):** what the design left to the child, settled here; the execution document `docs/doperpowers/plans/2026-09-28-c3-engine-host.md` carries the interfaces, milestones and gates. Grades: binding where a sibling codes against the outcome, advisory where a later child may overturn with a dated line here."

- *Transport framing and backpressure*: stdout is decoded with a UTF-8 `StringDecoder`, split on `\n`, blank lines dropped, a leading BOM stripped; an unterminated line over 64 Mi characters is a transport error that kills the process (the engine's own budget is 256 Mi; ours protects the host); a line that fails to parse is journaled and surfaced as `error.raised { scope: 'transport' }`, never fatal. Stdin has one serialised writer; a write resolves when the OS accepted the bytes (write callback, `drain` honoured), which is the §4.6 delivery truth for a `control_response`. No `keep_alive` is sent (the engine drops it on input); U+2028/2029 are not escaped (the engine's reader splits on `\n` only). Alternative: Node `readline`, rejected because it hides the budget and the decoder boundary. Advisory.
- *Request ids and timeouts*: host-minted ids are `${launchId}-${n}` (eight base32 characters per spawn, then a counter), distinguishable at a glance from the engine's UUIDs. Four timeout classes: `read` 8 s (`get_*`, `list_*`, `mcp_status`, `export_conversation`, `get_status`, `rewind_files` dry run), `mutate` 8 s (`set_*`, `apply_flag_settings`, `rename_session`, `stop_task`, `cancel_async_message`, `set_cwd`, `rewind_conversation`, `rewind_files`, `end_session`), `interrupt` 8 s, `long` 120 s (`initialize`, `claim_session`, `generate_session_title`, `side_question`, `reload_plugins`, `mcp_reconnect`, `mcp_toggle`); inbound human-facing requests have none (dialog expiry is never). The bounded classes are 8 s because X2's router fails a host command at 10 s and C1's `CommandSpec` has no per-command deadline: every X2 command the host answers synchronously runs under one 8 s budget (pass-2 evidence: reads and mutations answer in milliseconds), and the `long` subtypes a command can reach are *operations* (`session.generateTitle`, `session.reloadPlugins`, `session.sideQuestion`, `session.mcpReconnect`, `session.mcpToggle`): an `OperationReceipt { opId }` at the flushed write and completion through the event `session.operation`, emitted once more with `late: true` when a timed-out request answers inside the late table. A timeout rejects the caller, writes a `control_cancel_request` (harmless for uncancellable subtypes), and parks the id for 60 s so a late answer is journaled and reconciled (a warning notice; the state corrected by the next frame carrying it), not treated as unexpected; a timeout never proves the mutation did not apply.
