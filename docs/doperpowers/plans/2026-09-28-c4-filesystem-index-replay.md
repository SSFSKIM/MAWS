## Purpose

After C4, MAWS knows everything Claude Code already wrote to disk, without Claude Code having to be asked. Open the app and, within a couple of seconds, every session the owner ever ran from a terminal is listed under its project directory with its title, the directory it ran in, and whether some other process is holding it right now (a terminal, or a `claude --bg` job). Start `claude` in a terminal and the row turns foreign-live within two seconds; quit it and the row goes idle. Open any such session and its transcript is rebuilt from the engine's own JSONL, following the leaf's parent chain so that a `/rewind` typed in the terminal shrinks the transcript in MAWS while it is being watched, and a subagent's own transcript file resolves to child events attributed to their parent tool call. The app's own state that the engine does not hold, session records, titles with provenance, pins, archive flags, project membership, attention items, composer drafts, replay fixtures, lives in one SQLite file and survives restarts. Any probe fixture or any JSONL transcript can be replayed into the same event graph at 0.25× to 50× speed or instantly, which is how the transcript (C6), the shell (C5) and the panels (C8) are built and tested before and beside a live engine. And a read-only git service answers status, branch, diff and log for a session's directory, telling the toolbar within a second when a file in the worktree changed.

What C4 does not do: it never writes into `~/.claude` (the engine's store is read-only to MAWS, D-12 and §4.3), never launches or talks to an engine process (C3), never renders a transcript (C6) or a sidebar (C5), never creates or removes worktrees (C10), and never stages or commits (P1).

## Terms

Terms C1 defined (main process, renderer, preload, utility process, command, event, frame, journal, transcript record, event graph, token, N-API, asar) keep their C1 meaning. New here:

- **Config home**: the directory Claude Code keeps its state in, `$CLAUDE_CONFIG_DIR` if set, otherwise `~/.claude`, NFC-normalised (SPEC 35.1.1). Written `<configHome>` below. On the owner's Mac it is `/Users/new/.claude`.
- **Store**: the engine's on-disk state under the config home that C4 reads: `projects/`, `sessions/`, `jobs/`, `tasks/`. Everything else under the config home (settings, agents, skills, plugins, commands, daemon, teams, history) is out of C4's scope; C11 reads settings and palette files through the engine's control reads or its own commands.
- **Slug**: the directory name under `projects/` for a working directory: every character outside `[A-Za-z0-9]` of the realpath replaced by `-`, cut at 200 characters with a base-36 hash suffix when longer (SPEC 35.2.1). `/private/tmp/x` becomes `-private-tmp-x`; `/tmp/x` is realpathed first (§4.3, §18).
- **Sidecar directory**: `projects/<slug>/<sessionId>/`, holding `subagents/agent-<agentId>.jsonl` and `.meta.json`, `subagents/workflows/<runId>/journal.jsonl`, `tool-results/<id>.txt|json`, `workflows/<runId>.json`, `workflows/scripts/*.js`, `custom-title.json` (SPEC 35.10).
- **Chain**: the transcript the model sees: from the leaf (the last record in file order that carries a `uuid` and is not `progress`-typed), follow `parentUuid` to the root; records off that path are an abandoned branch. `currentChain` in `src/shared/wire/transcript.ts` (C1) computes it over a whole file; the **chain follower** (M1) maintains it incrementally as lines are appended.
- **Anchor**: a `last-prompt` record. It has no `uuid`, is never on the chain, and carries `leafUuid` (the leaf at that moment) and, after a rewind, `rewound: true` plus `explicit: true`, with `lastPrompt` the prompt that was rewound away (verified against the raw probe transcript, Surprises & Discoveries).
- **Holder**: a process other than MAWS that currently has a session open. Interactive `claude` writes `<configHome>/sessions/<pid>.json` at startup (`kind: "interactive"`), `claude --bg` writes one with `kind: "bg"` and a `jobId`; `-p` sessions write none (SPEC 35.27.1). A session with a live holder is shown foreign-live and read-only (D-12).
- **Tailer**: the per-file reader that keeps a read cursor at the end of what it has already read plus a buffer holding the trailing partial line, reads only what was appended since the cursor, and hands complete lines to the chain follower.
- **Backfill**: producing X1 events from a transcript file's chain, as opposed to from live wire frames (C3). Both produce `SessionEvent`s of the kinds listed under Interfaces.
- **Index**: the SQLite database `<userData>/index.sqlite` owned by main, holding only what the engine does not (§4.4).
- **Read model**: C5's main-process module (`SessionReadModel`, `docs/doperpowers/plans/2026-09-28-c5-shell.md`) that folds digests and observes projects, session records and attention items for main-side consumers (the notifier, the dock badge, the quit guard), answering `session.digests` and `session.setVisible`. A **session source** feeds it through C5's `ReadModelWriter`; C4's `IndexSessionSource` is the production one. The record side of `session.*` (`session.list`, `session.get`, `session.update`, `session.projects.*`; events `session.changed`, `session.removed`, `session.projects.changed`) is C4's, answered from the index (wave-2 ledger, d.7).
- **Binding** (of ids): the pair `appSessionId ↔ sessionId` for one session. Main's index allocates app ids; the engine host learns them through `fs.bind` so the events it emits can carry `appSessionId`, the key every renderer-facing payload uses (C3 and C6 settled on that name).
- **Replay**: feeding a recorded source into the event graph at a chosen speed. Two sources (X8): a probe **journal** (rows of `{seq, direction, at, frame}`), which goes through C3's normaliser; and a **transcript** JSONL, which goes through C4's backfill.

## Architecture: where each piece runs and how they talk

Three places, fixed by §4.1:

- **Engine host** (`src/engine-host/fs/**`): the filesystem state service. One `fs.watch` over `<configHome>/projects` (recursive), one over `sessions/`, one over `jobs/` and one over `tasks/`; the discovery scan; the tailers and chain followers; sidecar, registry, job, task and workflow readers; spill reads; the transcript backfill that produces X1 events; the replay engine (clock and both sources). It registers the `fs.*`, `session.replay.launch` and `session.replay.control` commands it owns through C1's `runHost` registration and emits `fs.*` events, `session.eventBatch` (C3's event, the one carrier of X1 events from any producer) and `session.replay.progress`. It shares the process with C3's engine adapter because §4.1 puts both there; they share the host runtime, the bindings table (`fs.bind`), and two in-process seams: C3's `session.events` handler delegates to `FsService.eventsSnapshot` for an `appSessionId` with no live process, and C4's journal replay runner calls C3's `Normalizer`.
- **Main** (`src/main/index/**`, `src/main/git/**`): the index and the git service. Main subscribes to the engine host's `fs.*` events and C3's `session.status` through `HostSupervisor.onEvent(name, listener)` (C3 adds it to C1's `src/main/hosts/supervisor.ts`, being first in the merge order; C4 consumes it and carries an identical block in its worktree until rebase), folds summaries, holders and engine statuses into session records and projects, and feeds C5's read model as a `SessionSource` (`IndexSessionSource`), receiving its visibility reports (`onSetVisible`) for the unread rule. Main answers the record side `session.list`, `session.get`, `session.update`, `session.projects.*`, and `session.drafts.*`, `session.replay.start`, `session.replay.fixtures`, `git.*`, and emits `session.changed`, `session.removed`, `session.projects.changed`, `git.changed`; attention items are persisted through C3's `AttentionStore` port, which `Index.attention` implements.
- **Renderer**: a diagnostics section (`src/renderer/src/app/StoreDiagnostics.tsx`) that lists discovered sessions with holder badges from `session.list` and `session.changed`, shows the followed session's chain length and last events from `fs.followState` and `session.eventBatch` (hydrated the way C6's protocol does: subscribe and buffer, apply the snapshot, drain the buffer with dedup by id, then live, so a late snapshot never lands after newer batches), and offers replay and git controls. It exists so C4's acceptance is observable before C5 and C6 land; C5 replaces it as the user-facing surface and C4 adds no session store of its own (C5's `sessions` store is the one).

Main ↔ host traffic is C1's host protocol unchanged: main sends `req` for `fs.*` commands (owner `engine-host`), the host answers `res` and emits `evt`; every payload is validated with the X2 schemas at both ends. No new envelope kinds. The renderer never sees a path it did not get from a validated event.

Ids: the engine host discovers sessions by their engine `sessionId`; the index allocates the `appSessionId` (`AppSessionId`) when it first sees a session (discovery, or C3's `createForLaunch`) and tells the host through `fs.scan { known }` at startup and `fs.bind` afterwards. Every renderer-facing payload the host emits for a session carries `appSessionId`; a transcript the host sees before main has bound it produces only `fs.sessionChanged` (keyed by `sessionId`), and main binds before anything follows it.

The heavy-work worker §4.1 names for "transcript indexing and search" is **not forked in C4**. Discovery reads 64 KiB heads and tails, not whole files (about one second for the owner's 3,690 sessions, measured), tailing is incremental, and the index stores records, not transcript text, so nothing here is CPU-bound enough to warrant a third utility process. The worker arrives with its first real consumer (full-text search over transcripts, or the P1 replay scrubber). Advisory; recorded in Residue decisions.

`CLAUDE_CONFIG_DIR` is read by the engine host from its own `process.env` at start, exactly as the engine reads it; C1's supervisor forks hosts with main's environment, which is the login shell's when `pnpm dev` runs and the Dock-launch environment (no shell exports) when packaged. C3's login-shell capture (`shell-env.ts`) runs in the same host, so when it lands the FS service reads `CLAUDE_CONFIG_DIR` from the captured environment through the same accessor the launch contract uses; until then both see `process.env`. `fs.state` reports the resolved config home so a mismatch is visible.

### Chain follower and backfill (`src/engine-host/fs/chain-follower.ts`, `src/engine-host/fs/backfill.ts`)

The chain follower is the concurrency-shaped core, so its states and transitions are fixed here. One follower per transcript file; every method is serialised behind one promise chain per file, so a watcher event, a reconcile tick and a follow request never interleave.

```ts
export interface Skeleton { uuid: MessageUuid; parentUuid: MessageUuid | null; type: string; isProgress: boolean; timestamp: string | null; offset: number; length: number }
export interface FollowerState {
  path: string; ino: number | null; offset: number;          // read cursor: the byte position up to which the file has been read (the size at the last read)
  partial: Buffer;                                          // the bytes of [offset - partial.length, offset): everything after the last '\n' read so far; contains no '\n'
  skeletons: Map<MessageUuid, Skeleton>;                     // every uuid-bearing record, chain or not; payloads are not retained
  chain: MessageUuid[]; leaf: MessageUuid | null;            // root → leaf
  emitted: Set<MessageUuid>;                                 // records whose events have been delivered and that are still on the chain (a cut removes them)
  rewind: null                                                                                            // no anchor outstanding
    | { phase: 'unanchored'; leafUuid: MessageUuid; prefillText: string | null }                          // anchor seen, its leafUuid not on the chain; waits for the branch
    | { phase: 'announced'; leafUuid: MessageUuid; targetMessageUuid: MessageUuid | null; prefillText: string | null };   // chain cut and boundary.rewind emitted; awaiting the continuation
  skippedLines: number; gap: { parentUuid: string; childUuid: string } | null;
}
export type FollowerEvent =
  | { t: 'events'; events: SessionEvent[] }                                       // in chain order, batched
```

Inputs and transitions (the linearisation point is the end of one `poke()`):

| Input | Condition | Effect |
|---|---|---|
| `start` | — | `stat`; read `[0, size)` in 1 MiB pages through the same line dispatch as `poke`; state `backfilling` → `following`. A missing file waits in `following` with an empty chain until a `poke` finds it. Because the dispatch handles anchors, a file whose last line is a `rewound` anchor (a **trailing anchor**: no uuid-bearing record appended after it yet) starts with the chain already cut and `rewind` announced, where C1's `currentChain` alone would report the old leaf; the two agree whenever a uuid-bearing record follows every anchor. |
| `poke` (watcher or reconcile) | `stat.ino !== ino` or `stat.size < offset` | **reload**: the file was rewritten (local GC via temp-and-rename, tombstone removal, CCR hydration, relocation set-aside; SPEC 35.3.1, 35.8, 35.9, 35.23). Run `start` into a fresh state with emission suppressed, so a trailing anchor keeps its cut exactly as on a cold start; then reconcile **old delivered state against the fresh final state, and nothing else**: the uuids on the old chain but not the fresh one become one `boundary.retraction { retractedMessageUuids, reason: 'transcript_rewritten', fallbackModel: null }` and leave `emitted`; the fresh chain's records not in `emitted` are emitted in chain order, **one event group per record — its final mapping** (the suppressed fresh run may have mapped a record more than once while branching away from it and rejoining; only the group that stands on the final chain is delivered, and once-per-follow events such as `session.started` are delivered at most once per follow); the fresh `rewind` state replaces the old; state passes through `reloading`. The fresh run's own anchor-, branch- and reload-derived events (`boundary.rewind`, `boundary.retraction`, the second-writer notice) are never delivered from a reload: they describe history the consumer already holds, and a rewrite that shifts an anchor's byte offset changes its `anchor:<offset>` id without changing its meaning, so replaying them would cut a transcript the fresh chain still contains (M1 review). A file whose rewrite leaves the chain identical therefore delivers nothing but the state transitions. |
| `poke` | `stat.size === offset` | nothing is read; a pending `partial` stays pending. |
| `poke` | `stat.size > offset` | read `[offset, size)` exactly once (in 1 MiB pages, like `start`, so a first poke on an 84 MB file never allocates the whole file; the pages are still contiguous and disjoint); `buf = partial ++ chunk`; every `\n`-terminated line in `buf` is dispatched, its skeleton offset being `offset − partial.length + <its position in buf>`; the remainder after the last `\n` becomes `partial`; then `offset = size`. Each complete line: strip leading `\0` bytes, `JSON.parse`; on failure increment `skippedLines` and continue (a torn fragment sealed by the writer's `\n` prefix parses as garbage exactly once); on success dispatch by record. Invariant: the ranges a follower reads over a file's life are contiguous, ascending and disjoint, so no byte is read twice and a fragment is never prepended to its own re-read — the read cursor, not the last newline, is what advances (a cursor left at the newline while `partial` also kept the bytes after it would re-read those bytes on the next poke and dispatch `partial ++ partial ++ rest` as a corrupt record). |
| line: record without `uuid` | `type === 'last-prompt'` and `rewound === true` | If `leafUuid` is on `chain` and is not `leaf`: **cut** — the chain members after `leafUuid` (the *cut segment*, old-chain order) leave `chain` and `emitted`; `leaf = leafUuid`; emit `boundary.rewind { targetMessageUuid: <first 'user'-typed record in the cut segment>, precedingAssistantUuid: leafUuid, prefillText: lastPrompt ?? null }` (a cut segment with no `user` record is attachments only, invisible to consumers: no boundary); `rewind = { phase: 'announced', leafUuid, targetMessageUuid, prefillText }` — MAWS shrinks at the anchor, before the next turn arrives, and stays announced until the continuation. If `leafUuid === leaf`: nothing to cut; `rewind = null`. If `leafUuid` is not on the chain (an anchor written before the file was complete): `rewind = { phase: 'unanchored', leafUuid, prefillText }` for the branch case. A second `rewound` anchor while announced applies the same rule against the current chain and replaces the state; the earlier cut's records stay in `skeletons`, off-chain, where the continuation rule finds them. Anchors with `leafUuid` and no `rewound` update the `leafUuid` fact only. |
| line: record without `uuid` | `custom-title`, `ai-title`, `relocated` | emit `facts`. `queue-operation`, `mode`, `permission-mode`, `atis-latch`, `file-history-snapshot`, `file-history-delta`, `cost-state`, `summary`, `tag`, `history-suppression`, `ended-by-model`, `continued-in`, `attribution-snapshot`, `fork-context-ref`, `observer-ref`, `agent-name` (a teammate's display name, SPEC 35 `AgentNameRecord`), `bridge-session` (remote-control bridge bookkeeping): known, no event (the last two found in the owner's 84 MB transcript at ~350 records each, M3). Any other type: `frame.unknown { frameType: 'transcript:' + type, subtype: null }`. |
| line: record with `uuid` | `type === 'progress'` | store the skeleton with `isProgress: true`; never becomes `leaf`; no event. |
| line: record with `uuid` | `parentUuid === leaf`, or `parentUuid === null` and `chain` is empty | **extend**: push; `leaf = uuid`; emit the record's events (Backfill mapping below); `rewind = null`. A `parentUuid` that names a `progress` skeleton is resolved through it to that record's own parent first (SPEC 35.12.3: the engine re-points children of progress records), and both walks below skip progress records. |
| line: `system` / `compact_boundary` with `parentUuid === null` on a non-empty chain | — | **restart** (SPEC 35.5.13: the engine writes the boundary as a new root mid-file): `chain = [uuid]`, the old members leave `chain` and `emitted` silently, no retraction and no notice; the record's own `boundary.compaction { logicalParentUuid, historical: true }` is the visible event, and `currentChain` restarts at the same record. Any other null-parent record on a non-empty chain is the branch row (a second writer). |
| line: record with `uuid` | `rewind.phase === 'announced'` and `parentUuid !== leaf`, and the walk from `parentUuid` up through `skeletons` reaches `rewind.leafUuid` without passing a `user`-typed record | **rewind continuation**: the engine resumes a rewound conversation from the last context attachment it had injected after the preceding assistant (in the real fixture `af765f44`, the `prompt_snapshot` after `edf0f954`), not from the assistant itself, so the continuation's parent is a record the cut just removed. The walked records rejoin `chain` in root → leaf order, then this record; rejoined records not in `emitted` are re-read by offset and emitted (attachments carry no events, so nothing is visible); `leaf = uuid`; `rewind = null`; no boundary of any kind. A walk that crosses a `user` record (the rewound-away prompt or later) or ends elsewhere is not a continuation and falls to the branch row: that is a second writer. |
| line: record with `uuid` | otherwise (`parentUuid` names an older chain member, an off-chain record, or nothing) | **branch**: walk `parentUuid` through `skeletons` from this record to a root or a missing parent (C1's `gap` rule: stop, report, never bridge). The walk is the new `chain`; the old chain's members not on it leave `emitted` and become `boundary.rewind` (when `rewind.phase === 'unanchored'`: `precedingAssistantUuid = rewind.leafUuid`, `targetMessageUuid` = the first `user`-typed record after the divergence on the old chain, `prefillText`) or, with no anchor to explain it — `rewind` null, or `announced` with a parent the continuation rule rejected — `boundary.retraction { reason: 'transcript_branch' }` plus `notice.posted { level: 'warning', text: 'Another process wrote a sibling branch into this transcript', key: 'transcript_branch' }` — the pass-2 item 10 second-writer case; the retraction is emitted with an empty `retractedMessageUuids` when nothing left the chain (a re-parenting onto records the cut had removed) and the notice is what the consumer sees; a branch from an empty chain (the gap case) emits neither. New chain members not in `emitted` are re-read by offset and emitted in chain order. `rewind = null`. |
| any | `partial.length > 8 MiB` | a record longer than 8 MiB (the engine's own pre-flush accumulator is far larger, but a single record this size is a torn tail in practice): drop `partial` (the cursor stays where it is), count one skipped line, continue; the bytes up to the next `\n` then parse as garbage once more. |
| `stop` | — | close, state `stopped`; the skeleton and the materialised list are discarded. Cancellation is effective across awaits: a read or reload in flight when `stop` is called delivers nothing when it resolves, emits no further `state`, and `materialized()` is empty afterwards (M1 review). |

Events are delivered in batches: everything one `poke()` produced, split into messages of at most 500 events, in chain order (C3's batch cap). The follower never retains parsed payloads; `emitted` plus `skeletons` (about 120 bytes per record) is the memory cost of following the 84 MB transcript, plus `materialized()`'s event list, which the host keeps per followed session for the snapshot command and drops on `stop`.

**Backfill mapping**, `backfill.ts`, `recordToEvents(record, ctx): SessionEvent[]`, with `ctx = { sessionId, agentId, parentToolUseId, seenToolUses, subagents: SubagentLookup | null }` (`SubagentLookup.byToolUseId(id) → { agentId, meta, prompt } | null`, the sidecar metas M3's reader supplies; `ChainFollower` takes it as an optional fifth constructor argument `{ subagents }`). `EventBase` for every event: `seq: null` (no journal row; X1 defines `seq` as the journal row and null for app-synthesised events, and a disk record is neither), `at` = the record's `timestamp` (ISO) or the previous event's, `agentId`/`parentToolUseId` from `ctx`, and a deterministic `id`: `<uuid>` for a record's first event, `<uuid>#<n>` for its n-th, `anchor:<offset>` for anchor-derived events, `session:<sessionId>:started` for the synthetic start (`session:<sessionId>:agent:<agentId>:started` in a sidecar context, so the parent's and the child's do not collide under dedup-by-id), `branch:<childUuid>:retraction|notice` for a second-writer branch, `rewrite:<ino>:<size>` for a reload retraction, `line:<offset>` for a non-uuid record of unknown type. **X1 id grammar for disk-derived events** (opaque to consumers; the uniqueness pin lives in `chain-follower.test.ts`, M1): an id names a **delivery occurrence**: the first delivery of a record's events carries the forms above, and a record that a `boundary.rewind` or `boundary.retraction` removed and that later rejoins the chain (the rewind continuation, a branch flip, a reload) is re-delivered under `<uuid>@<g>` / `<uuid>@<g>#<n>` with `g` the delivery count (2 for the first re-delivery). The same rule covers every synthesised event: a boundary or notice whose base id (`rewrite:<ino>:<size>`, `branch:<uuid>:…`, `anchor:<offset>`) has already been delivered in this follow is delivered as `<base>@<g>` (a same-inode shrink, regrow and shrink again yields two distinct retractions). So one follower's delivery log never carries an id twice, a consumer deduplicates by `id` alone (a snapshot from `materialized()` overlapping a batch is all duplicates, whatever boundaries lie between), and removals reach it only through the boundary events, which name message uuids, exactly as C3's live `boundary.rewind` does. The same file followed twice from scratch yields the same ids, since the delivery history is a function of the file (M1 re-review). Consumers cannot use `seq` as a cursor for disk-derived events; C6's `ipcSource` is asked to key its dedup on `id` (Cross-child reconciliation).

`IndexSessionSource.start` subscribes to `fs.sessionChanged`, `fs.sessionRemoved`, `fs.holderChanged` and C3's `session.status`, reconciles each into the index inside a transaction (`session.status` → `applyEngineStatus`, plus `bindEngineId` and `fs.bind` when `engineSessionId` first appears; wave-2 ledger d.14), calls `writer.observeProject` / `writer.observeRecord` / `writer.observeRemoved` (C5's `ReadModelWriter`), emits `session.changed` / `session.removed` / `session.projects.changed` with the index's `revision`, and for a discovered session with no live process also `writer.setDigest({ appSessionId, phase: holder is terminal or background_job ? Pin, archive, title and "Mark all read" arrive as `session.update` patches, not through the port.

**Project membership rule** (`projects.ts`): a session belongs to the project whose `directory` equals the realpath of the session's effective directory (`relocatedCwd ?? directory`), or whose `directory/.claude/worktrees/` contains it (then the record's `worktree` is `{ path, branch: <from the summary's gitBranch> }`). Discovery auto-creates a project (`origin: 'discovered'`, `name` = directory basename) for an effective directory that exists on disk and has at least one session with `hasMessages`; a directory that no longer exists yields `projectId: null` and the session lands in "Other sessions"; a hidden project keeps its id so rediscovery does not resurrect it. Reason: §5.1 says sessions MAWS did not start "appear under their project automatically", and the owner's 704 slugs are mostly dead `/private/tmp` probes that would otherwise become 704 groups. Advisory; C5 may change the visibility rule.

**Title rule** (`sessions.ts`): the engine's titles are facts and a rename made in MAWS is an override, stored apart so neither blocks the other. Every summary overwrites the engine-sourced columns `custom_title` (the last `custom-title` tail record, else `custom-title.json`), `ai_title` and `first_prompt`, so a second `/rename` in the terminal and a regenerated AI title both reach the row (the previous rule imported the first terminal rename as `source: 'user'` and then refused every later one, and let a `generated` title never be replaced by a newer generated one). `title_override` (`{ text, source: 'user' | 'tool' }`) is set only by `session.update { title }` (C10's rename of a session with no live engine, which cannot go through C3's `session.renameSession`; MAWS never writes `custom-title.json` itself) and by `createReplay` (`source: 'tool'`), and cleared by `session.update { title: null }`; the engine's `customTitle` at the moment the override was set is kept in `title_override_engine_title`, and a later summary whose `customTitle` differs from it clears the override, so a `/rename` typed in the terminal after a rename made in MAWS wins: the later explicit act wins in either direction, and a MAWS rename of a live session reaches disk through `session.renameSession` as the same text, which keeps the override. Projection: `title` = the override, else `customTitle` with `source: 'user'` (a terminal `/rename` is the user's act), else `aiTitle` with `generated`, else `firstPrompt` with `none`, else `{ text: '', source: 'none' }`; an AI title never displaces a custom title or an override. On `fs.sessionRemoved` the record is kept and marked `archived` with `transcript_path` cleared, never deleted: the owner's index outlives the engine's retention sweep, which is what "keeps only an index" permits.

`readJsonWithRetry` reads the whole file, `JSON.parse`s, applies `accept` (for `sessions/<pid>.json`: `sessionId` present, or `spare: true`, or `parkedJobId`, because the engine patches the record by read-modify-write and a spare has no session id to wait for); a failure at any step schedules the next attempt at the absolute offsets 0, 20, 50, 100, 250, 500 ms from the first; after the sixth failure it resolves `{ status: 'unparseable' }` (the caller can tell exhausted retries from `{ status: 'absent' }`) and the caller keeps its previous value — a torn `custom-title.json` must never clear a valid title (M2 review); `ENOENT` resolves absence at once (the engine's writers never make a file vanish mid-write, and ~3,100 sessions have no `custom-title.json`). A change event on the same path restarts the schedule, realised for the registry as one coalesced, serialised `refresh()` that queues exactly one more pass when a change arrives mid-refresh. This is the §4.3 "parsed with retry": `custom-title.json`, `agent-*.meta.json`, `wf_*.json`, `tasks/*/*.json`, `sessions/*.json` and `jobs/*/state.json` are all written without a documented atomic rename (SPEC 35.10, 35.27.1, 20.2.4, 40.16), and `.key` files (which are atomic) are not read.

**Holder rule** (`HolderRegistry`): for each `sessions/<pid>.json` that parses with a `sessionId`: alive iff `process.kill(pid, 0)` succeeds (EPERM counts as alive) and, when `procStart` is present, `ps -o lstart= -p <pid>` run with **`LC_ALL=C` and `TZ=UTC`** prints exactly that token once trimmed (pid reuse guard; one batched `ps` per refresh). The timezone is the engine's convention, not the host's: its own probe (`modules/chunk-dte0vqga.js`, `rRe`/`b`) spawns `ps -o lstart= -p <pid>` with `env: { …process.env, LC_ALL: 'C', TZ: 'UTC' }` and compares the trimmed strings for equality, so every record carries a C-locale UTC timestamp such as `Mon Sep 28 08:31:32 2026` whatever zone the terminal ran in; verified against all ten records under `~/.claude/sessions/` on the owner's `America/Los_Angeles` host, where the `LC_ALL=C`-only form (`Mon Sep 28 01:31:32 2026` for `78212`) is seven hours off and matches nothing. `procStartFt` is the engine's Windows-only fallback form and never appears on macOS; a record with neither field matches on liveness alone, as the engine's own `P()` treats a missing expected token. `kind: 'interactive'` or no `kind` → `{ kind: 'terminal', pid }`; `kind: 'bg'` → `{ kind: 'background_job', pid, jobId }`; `daemon` and `daemon-worker` → `{ kind: 'background_job', pid, jobId: null }`; a `kind` this document does not know, with a live pid, is still a holder — `{ kind: 'background_job', pid, jobId: record.jobId ?? null }` with one log line naming the value — because X6's launch refusal must hold for a process MAWS cannot classify (M2 review); a record with `spare: true` or a `parkedJobId` is not a holder. A `jobs/<short>/state.json` whose `sessionId` has no live registry record contributes name and state facts but no holder: liveness is decided by pids, never by the job's `state` string. Refresh runs on every `sessions/` change event and every 2,000 ms while at least one holder is known (the record's removal is a `process.on('exit')` unlink, so a killed terminal leaves a stale file until the next `claude` start reaps it); the within-two-seconds acceptance follows from the watcher on start and the poll on exit. A session with no live record has holder `{ kind: 'none' }`; MAWS-owned sessions are `{ kind: 'self' }` set by C3 through the index, never by this registry (a `-p` process writes no registry record).

### Replay engine (`src/engine-host/fs/replay/*.ts`)

```ts

```

A replay run gets a fresh `SessionId` `rp_<uuid>` and a fresh `AppSessionId` so two replays of one fixture never collide, and every frame's or record's `session_id`/`sessionId` is rewritten to it before leaving the source; the index record for the run has `kind: 'replay'`, `holder: { kind: 'none' }`, `title` from the fixture name (`source: 'tool'`, the override). **Start orchestration**, main's `session.replay.start` handler (`src/main/index/replay.ts`): allocate the two ids; `sessions.createReplay` inside a transaction (which emits `session.changed { cause: 'replay' }`); dispatch the host command `session.replay.launch { appSessionId, sessionId, source, speed }` and return its `{ totalRows, spanMs }` with the ids. The host handler (`register.ts`) does everything that can fail before anything can be observed: it reads the source, parses it (`JournalRowSchema` per row for a journal, `parseTranscriptRecord` per line for a transcript), counts rows and computes `spanMs` from the first and last `at` or `timestamp`, binds the ids in `Bindings` itself (no separate `fs.bind` round trip), then starts the runner and answers; so a launch that fails emits no `session.eventBatch` and no `session.replay.progress` for the ids. Failures are `IpcError { code: 'internal' }` with the messages `replay source not found: <path>`, `replay source unreadable: <path>: <errno>`, `replay source empty: <path>`, `replay source is not a journal: <path>: line <n>` (a row fails `JournalRowSchema`), `replay source is not a transcript: <path>` (no uuid-bearing record), `replay already live: <appSessionId>`. On any error from the dispatch — the host's `internal`, or C1's `host_unavailable` or `timeout` — main removes the record again (`sessions.remove`, which emits `session.removed`) and rethrows the same `IpcError` to the caller, so a failed start leaves no `kind: 'replay'` row. A `timeout` does not end the host's work: C1's supervisor drops the pending request after its ten-second deadline without telling the host (`src/main/hosts/supervisor.ts`, `dispatch`), so a source load slower than the deadline would otherwise bind the ids and start the runner afterwards and emit events for the deleted row. **Launch cancellation**: on `timeout`, main posts `session.replay.control { appSessionId, action: 'stop' }` as the explicit cancel for that launch id (an X2 command, so no new envelope kind; main does not await it, and its failure is logged, not rethrown), records the id in its set of cancelled launches, and only then removes the record. The host keeps the ids of launches in flight; `control { action: 'stop' }` for an id that is launching and has no runner adds it to a cancel set and answers at once, and for an id the host knows nothing of it is a no-op, not an error. The launch handler checks the cancel set after the source load resolves and before binding, and again immediately before starting the runner; a cancelled id discards the loaded source, releases any binding it made, clears its cancel entry and answers `internal` `replay launch cancelled: <appSessionId>` (a response the supervisor drops, the request being gone), having emitted nothing. A cancel that arrives after the runner started is an ordinary stop. Main reconciles a late success it cannot see in the dropped response: a `session.replay.progress` or `session.eventBatch` for an id in its cancelled set makes main send `session.replay.control { action: 'stop' }` for it again and never recreates the record; an id leaves the set on its `stopped` progress or when the engine host restarts. `host_unavailable` needs no cancel: the host that would have run the launch is gone. The run may be emitting before `start` returns (`'instant'` finishes within milliseconds, like C3's `session.launch` answering at spawn), so a consumer that wants every event calls `session.events { appSessionId, afterSeq: null }` after `start` and deduplicates by id (`eventsSnapshot` serves replay runs from the runner's materialised list until `stop`); the first `session.replay.progress { state: 'running', index: 0 }` follows the launch response. `session.replay.control { action: 'stop' }` emits `progress { state: 'stopped' }`, unbinds and drops the runner; main removes the record on `stopped` and keeps it on `done`. Journal replay emits `session.eventBatch` after C3's `Normalizer`; the runner takes the normaliser as a dependency so C4's unit tests drive it with a collecting stand-in and the running app wires C3's class at registration time (`register.ts`); if C4 lands before C3, the journal runner is wired to a stand-in that emits one `frame.unknown` per `in` row so the controls and progress are real end to end, and M7 records which state was observed. `'instant'` speed emits everything in batches of 500 with a `setImmediate` between batches. C3's own `ReplayTransport` (a lockstep test seam that stands in for a process and advances when the adapter writes the recorded `out` frame) is a different thing with a different purpose and is untouched.

### Git service (`src/main/git/*.ts`)

Binary: `process.env.MAWS_GIT ?? '/usr/bin/git'` (Apple's shim to the Command Line Tools, present on the owner's Mac; C11's settings screen may add a setting). Every call is `execFile(git, ['-C', directory, …], { maxBuffer: 64 MiB, timeout: 10_000, env: { PATH, HOME, GIT_TERMINAL_PROMPT: '0', GIT_OPTIONAL_LOCKS: '0', LC_ALL: 'C' } })`; `GIT_OPTIONAL_LOCKS=0` keeps `git status` from writing the index (the service is read-only even in side effects).

- `git.status`: `rev-parse --show-toplevel --git-dir --git-common-dir --abbrev-ref HEAD` (one call) then `status --porcelain=v2 --branch -z --untracked-files=normal`; `stash list --format=%H` for the count. Parsing: `# branch.oid/head/upstream/ab` headers; `1 <XY> …`, `2 <XY> … <path>\0<origPath>`, `? <path>`; `isWorktree` when `git-dir !== git-common-dir`.
- `git.branches`: `for-each-ref --format=%(refname:short)%00%(upstream:short)%00%(HEAD) refs/heads`.
- `git.diff`: `diff --no-color --no-ext-diff -U<context> [--cached | HEAD] [base] [-- path]` plus `diff --numstat` for the file table (`-` counts mark binaries).
- `git.log`: `log --format=%H%x00%h%x00%an%x00%aI%x00%s%x00%P -z -n <limit> [-- path]`.
- Watcher: per `repoRoot`, one `fs.watch(repoRoot, { recursive: true })` and one on `gitDir` when it lies outside the root (linked worktrees keep it under the common dir's `worktrees/<name>/`). Events are classified: paths under `.git/` count only for `HEAD`, `ORIG_HEAD`, `MERGE_HEAD`, `index`, `packed-refs`, `refs/**` (reason `head`, `index`, `refs`); everything else under the root is `worktree`; `.git/objects/**` and `*.lock` are ignored. Debounce 250 ms trailing; at most one `git status` in flight per root with a "dirty again" flag that re-runs once after it finishes; `git.changed` carries the fresh status so consumers do not round-trip. Ref-counted by `git.watch`/`git.unwatch` callers; the pinned summary (C8) and the composer strip (C7) are the expected callers.

## Residue decisions (C4, 2026-09-28)

Ready to paste under the charter's §12 C4 section as "**Residue decisions (C4, 2026-09-28):** what the design left to the child, settled here; the execution document `docs/doperpowers/plans/2026-09-28-c4-filesystem-index-replay.md` carries the milestones, the store shapes, the X2 additions, the cross-child reconciliation and the record." Grades: binding where the design binds the outcome, advisory where a later child may overturn with a dated line here.

- *Process placement*: the filesystem state service (watcher, discovery, tailers, sidecar and registry readers, spill reads, backfill, replay clock and sources) runs in the engine-host utility process; the SQLite index and the git service run in main; they talk only over C1's host protocol: the host emits validated X2 `fs.*` events and C3's `session.eventBatch`, which main consumes through a new `HostSupervisor.onEvent(name, listener)` and re-emits to the renderer, and main sends `fs.*` commands as `req`, including `fs.bind`, which tells the host the `appSessionId ↔ sessionId` pairs the index allocated so every renderer-facing payload carries `appSessionId`. The heavy-work worker §4.1 names is not forked in C4: discovery reads 64 KiB heads and tails (about one second for the owner's 3,690 transcripts), tailing is incremental and the index holds records, not text; the worker arrives with its first CPU-bound consumer (transcript search or the P1 scrubber). Alternative rejected: the index in the engine host beside the service, which would put app records behind a process C3 may restart. Binding on placement (§4.1); advisory on deferring the worker.
- *SQLite binding*: `node:sqlite` (`DatabaseSync`), built into Electron 44.4.5's Node 24.21.0 and into the Node 22 vitest runs on, replaces better-sqlite3 (S-4). Evidence: better-sqlite3 13.0.3 publishes no prebuilt binaries and 12.11.1's newest Electron prebuild is ABI 146 (Electron 41), so Electron 44 (ABI 149) would need a node-gyp rebuild plus a second build for tests; `ELECTRON_RUN_AS_NODE=1 electron@44.4.5 -e` shows `node:sqlite` present with SQLite 3.53.4 and FTS5; `node:sqlite` is Stability 1.2 (release candidate) from Node 24.15, the API is synchronous like better-sqlite3's, and the app uses only `exec`, `prepare`, `run`, `get`, `all` and transactions behind a one-file `Db` wrapper. Documented fallback: better-sqlite3 with `electron-rebuild -f -w better-sqlite3`, C1's node-pty treatment, with a dated line here if it ever becomes the default. Advisory.

- *Tail strategy and partial lines*: per followed file a read cursor (the byte position up to which the file has been read) and a partial-line buffer holding the bytes after the last `\n`; on change, `fstat` then read `[cursor, size)` exactly once, so the ranges read are contiguous and disjoint, no byte is read twice and a fragment is never prepended to its own re-read; `size < cursor` or an inode change means the file was rewritten (GC, tombstone removal, hydration, relocation) and triggers a full reload through the same line dispatch (a trailing `rewound` anchor keeps its cut) with uuid re-anchoring; lines are split at `\n`, leading NULs stripped, unparseable lines skipped and counted (the engine's own reader rule), a torn fragment sealed by the writer's `\n` prefix parses as garbage exactly once; the follower keeps a uuid skeleton (parent, type, offset, length) and never the payloads, re-reading records by offset when a branch flip brings them onto the chain; a `rewound: true` anchor cuts the chain at its `leafUuid` immediately, emits `boundary.rewind` and leaves the follower announced until the continuation, whose parent is the last context attachment the engine injected after that leaf rather than the leaf itself (verified on the pass-2 transcript: anchor line 27, continuation line 30, three records cut) and which rejoins without a second boundary; a branch without an anchor, or one an announced rewind cannot explain, emits `boundary.retraction { reason: 'transcript_branch' }` and a warning notice (the second-writer case of pass-2 item 10).
