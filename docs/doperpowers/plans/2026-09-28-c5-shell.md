## Purpose

After C5, the owner opens MAWS and the window is the one they will live in. On the left, a sidebar answers "where am I needed" before anything else: a **Needs you** section lists every session blocked on a human across all projects, longest wait first; below it the pinned sessions, the projects with their sessions (status glyph, title, what it is doing or last said, age, unread dot), and the sessions that belong to no project. The main area opens on the **Overview** board (⌘0): one card per live or unread session, grouped by project with a Needs-you group on top, each card showing activity, last assistant line, context, cost since last seen and child agents, with the pending request inline. Session tabs open beside it, reorder by drag, close with ⌘W, come back with ⌘⇧T, and one tab can be dragged to the right edge to open a second pane. The right region is there for the panel tools (C8) with its width, collapse and pin state already persisted. Every region has a keyboard-operable resizer, sizes and tabs survive a restart, the keyboard map is one rebindable table that also builds the application menu and the ⌘K palette, a macOS notification fires when a session enters Needs-you while the window is unfocused and ⌘⇧J lands on it, the light theme is the default and the dark one switches cleanly, and quitting with turns in flight asks first.

All of this runs with no engine: a stub session source in the main process plays a scenario derived from the protocol-probe fixtures (eleven sessions, ten across three projects and one without a project, one of them foreign-live, requests of every kind arriving on a timeline) through exactly the X2 events that C3's engine host and C4's index will emit later, so the renderer built here is the renderer that ships. What nobody can do yet, and C5 does not attempt: read a transcript (C6), type to a session or answer a docked request with scopes (C7), open a panel tool (C8), start, rename, fork or archive a session (C10), or see real usage windows (C11). Each of those arrives into a slot this document names.

## Terms

- **Region**: one of the three top-level areas of the window, `sidebar`, `main`, `panel`, each carrying the `data-region` attribute C1's `Shell.tsx` already sets. The **toolbar** is the strip above them that doubles as the window's title bar (`titleBarStyle: 'hiddenInset'`, §3).
- **Pane**: a tabbed area inside the main region. There is one by default and at most two (D-8); the second is the **split**. Every pane has its own tab strip and active tab. The **focused pane** is the one the menu-sink pane actions (⌘1..9, ⌘\) act on (§5.7) and the one ⌃Tab cycles, a renderer-sink, pane-scoped chord dispatched only from an eligible element inside a pane (Keyboard runtime); Enter and Esc are owned by the element that actually holds DOM focus (Keyboard runtime), never by a remembered pane index.
- **Tab**: an entry in a pane's strip. Kinds: `overview` (exactly one, never closable), `session`, `file`, `diff`, `diagnostics`. A tab id is deterministic (`session:<appSessionId>`), so a session has at most one tab across both panes.
- **Session record** and **attention item**: the X1 shapes `SessionRecord` and `AttentionItem` from C1's `src/shared/graph/session.ts` and `attention.ts`. **Session status**: a C5 read-side shape (`SessionStatus`, Interfaces) carrying what the record does not, the live facts a card and a status line show: phase, activity, last assistant line, context, cost, child agents.
- **Needs-you row**: one sidebar row per session that has at least one pending or delivered attention item; it shows the session's oldest item. Rows are sessions, not items.
- **Read model**: the main-process module that folds the digest of every live session from the event stream, keeps C3's engine statuses, and observes records and attention items on their way to the renderer, so the notifier, the dock badge and the quit guard have a view without a renderer. The store of record is C4's index; the read model stores nothing durable. **Source**: a producer that writes into it (C3's statuses and events, C4's records, or the **stub source**, a scenario file, in dev and tests). **Launch mode**: `index` (the production wiring: C4's index source, discovery, C3's attention service) or `scenario` (`MAWS_SESSION_SOURCE=stub:<path>`; the stub is the only source and the only answerer of the record side; the index is neither started nor read). The mode is decided once at app ready in `src/main/sessions/select-source.ts`.
- **Scenario**: a JSON file under `test/fixtures/shell/` listing projects, sessions, digests, engine statuses (C3's `EngineSessionStatus` in a compact form the loader expands), attention items and a timeline of changes, validated with the X1 and X2 schemas at load. It plays on the wall clock in dev and on a **manual clock** in the smoke (`MAWS_SCENARIO_CLOCK=manual`), which the test advances explicitly so every timed transition happens when the test says. "Fixture-derived" means its ids, directories, tool inputs and request payloads are copied from the probe journals; what the journals do not contain (titles, a read-only tool request) is synthetic and marked so in the file.
- **Slot**: a React component the shell renders at a fixed place with a fixed prop contract, whose real implementation a later child registers (`registerSlot`); C5 ships a fallback for each. Slots: `transcript` (C6), `composer` (C7), `requestCard` (X4, C7), `panelHost` (X5, C8), `fileTab` and `diffTab` (C8), `newSession` (C10).
- **Action** and **chord**: an entry of the keymap table (`src/shared/keymap/actions.ts`) with an id, a title, a default chord in Electron accelerator syntax (`Cmd+Shift+J`), and a **sink**: `menu` when the application menu registers the chord and dispatches the action as a `layout.action` event, `renderer` when the renderer's key dispatcher matches it. The user's overrides live in settings.
- **Hover card**: the Radix HoverCard that opens from a Needs-you row and previews the request (§5.1).
- **Foreign-live**: a session whose `holder` is a terminal or background job (D-12); shown with its holder and no controls.
- **Unstarted session**: an app session id C10's `session.create` allocated with a setup intent and no engine process (owner design, charter §19, 2026-09-28): it has a session tab and no record in the sessions store; the tab reads "New session" with the project name as its secondary line and no glyph, the pane renders the `newSession` slot above the composer in place of the transcript, and the session never appears in the sidebar. Once the record appears after the first send the tab is ordinary. There is no modal new-session sheet.

### X2 — `session.*`, read side (`src/shared/ipc/schema/session.ts`)

Two siblings fill this module: C3 with the engine-host-owned lifecycle and control entries (`session.launch`, `session.status`, `session.events`, `session.answer`, …; `docs/doperpowers/plans/2026-09-28-c3-engine-host.md`) and C4 with the main-owned record side of its index (`session.list { includeArchived? }` → `{ sessions: SessionRecord[]; revision }`, the index-only columns such as `lastAssistantText` reaching the read model in main through C4's `SessionSource` and never the renderer; `session.get`; `session.update { appSessionId, patch }` with `title`, `pinned`, `archived`, `lastSeen`, `unread`; `session.projects.{list,add,update,remove}`; events `session.changed { record, cause, revision }`, `session.removed { appSessionId, revision }` and `session.projects.changed { projects, revision }`; `docs/doperpowers/plans/2026-09-28-c4-filesystem-index-replay.md`). C5 consumes those as defined: pin and mark-read are `session.update` patches, projects come from `session.projects.list` and stay current through `session.projects.changed`, and the record events feed the sessions store. C5 adds only what neither sibling can answer: the digest of live facts, and the visibility report C4's unread rule needs.

```ts
export const SESSION_PHASES = ['starting', 'working', 'waiting', 'idle', 'exited', 'failed', 'foreign'] as const;
// working: a turn is running · waiting: the turn is blocked on a pending request · idle: process live, no turn
// exited: no live process (resumable from disk) · failed: the last turn or the process ended in error and nothing ran since
// foreign: holder is a terminal or background job (D-12) · starting: process launching, no turn yet
export const SessionDigestSchema = z.strictObject({
  appSessionId: AppSessionIdSchema,
  phase: z.enum(SESSION_PHASES),
  activity: z.string().nullable(),            // while working: "Running bun test", "Editing src/app.ts", "Thinking", "Compacting"; else null
  lastAssistantLine: z.string().nullable(),   // first line of the latest completed assistant text block, ≤ 160 chars; seeded from C4's summary.lastAssistantText for sessions with no live fold
  turnStartedAt: z.string().nullable(), lastTurnEndedAt: z.string().nullable(),
  context: z.strictObject({ percent: z.number(), totalTokens: z.number().int(), maxTokens: z.number().int(), autoCompactThreshold: z.number().int().nullable() }).nullable(),
  cost: z.strictObject({ totalUsd: z.number(), sinceSeenUsd: z.number() }).nullable(),
  childAgents: z.strictObject({ active: z.number().int(), done: z.number().int() }),
  pendingRequests: z.number().int(),
  revision: z.number().int(),                 // per session, monotonic; a consumer keeps the higher of snapshot and event
});

export const commands = {
  'session.digests':    { input: z.void(), output: z.strictObject({ digests: z.array(SessionDigestSchema) }), owner: 'main' },   // snapshot for a page that missed the events
  'session.setVisible': { input: z.strictObject({ appSessionId: AppSessionIdSchema, visible: z.boolean() }), output: z.void(), owner: 'main' },
  'session.launchMode': { input: z.void(), output: z.strictObject({ mode: z.enum(['index', 'scenario']) }), owner: 'main' },   // the page registers the scenario's session creator only in mode scenario (M3)
  // C3's entries (owner 'engine-host') and C4's record entries (owner 'main') follow
};
export const events = {
  'session.digest': SessionDigestSchema,
  // C3's `session.status` and the event batch `session.eventBatch`, C4's `session.changed`, `session.removed` and `session.projects.changed` follow
};
```

`session.setVisible` is the shell's report of which sessions are on screen (the active tab of a pane while the window is focused and the page visible). The read model keeps the visible set and forwards every change to the registered source's `onSetVisible(appSessionId, visible)`; C4's `IndexSessionSource` applies the unread rule there ("`unread` becomes true when `lastRecordAt` advances for a session whose tab is not visible") and, when a visible session's record advances, updates `lastSeen` in the same step so the record never flickers unread (settled in the wave-2 ledger, d.5). The digest model uses the same set for cost since last seen. The project tree stays current without polling through C4's `session.projects.changed { projects, revision }` (whole list; d.6).

Why a digest and not C3's `EngineSessionStatus`, C4's summary or C6's transcript store: `EngineSessionStatus` is the process table's truth (process state, engine state, turn, queue, memory) and says nothing about what the session is doing in words, its context percentage or its cost since the human last looked; C4's `summary` is what the JSONL tail says and stops being current the moment a process is live; C6's `useTranscriptStore.lastAssistantLine` exists only for sessions whose events the transcript store has been fed, and the sidebar must describe sessions nobody has opened. The digest is a pure fold over X1 events plus C3's status, small enough to run in main for every live session (Main modules below), seeded from C4's summary for the rest, and the same shape the stub scripts. When C6 lands, an opened session's secondary line may read C6's store; the digest stays for the rest.

### X2 — `attention.*` (`src/shared/ipc/schema/attention.ts`)

Main owns `attention.list` (void → `AttentionItem[]`), `attention.changed` (`{ appSessionId, items: AttentionItem[] }`, the session's whole list, replace) and `attention.request` (`{ appSessionId, requestId }` → `{ event: SessionEvent | null }`, the originating `*.requested` event for the hover card's full-input preview, §5.1); C3 defines the three in this module and answers them from its attention service in main, which merges the engine host's broker items with the non-broker kinds and persists them through the `AttentionStore` port C4's index implements (wave-2 ledger, ruling 1). C5 consumes the three as C3 defined them and adds two events:

```ts
// C3's block: 'attention.list', 'attention.request' (commands) and 'attention.changed' (event), all owner 'main'
export const commands = {
  // C3's block: 'attention.list', 'attention.request'
  'attention.pendingNavigate': { input: z.void(), output: z.strictObject({ navigate: AttentionNavigateSchema.nullable() }), owner: 'main' },   // snapshot (C1's pattern): a navigation main queued while no page could hear it, cleared on read; the renderer subscribes to attention.navigate first, then calls it (M5 fix wave)
};
export const events = {
  'attention.notified': z.strictObject({ appSessionId: AppSessionIdSchema, attentionId: AttentionIdSchema, delivery: z.enum(['os', 'fallback']), at: z.string() }),
  'attention.navigate': z.strictObject({ appSessionId: AppSessionIdSchema, attentionId: AttentionIdSchema.nullable(), source: z.enum(['notification', 'menu']) }),
};
```

`attention.request` is answered by main's attention service, which asks the engine host through C3's `session.pendingRequest` (the broker holds the pending table with each request's payload). Answering from the hover card uses C3's `session.answer { appSessionId, requestId, answer }` with `answer: { kind: 'permission', decision: 'allow', scope: 'once' }` or `{ kind: 'permission', decision: 'deny' }` (no `message`: C3's schema has it optional, not nullable); the hover card never offers another scope (X4: scopes are the docked card's). `attention.notified` and `attention.navigate` are emitted by main's notifier: the first whenever a notification was posted (or would have been, `delivery: 'fallback'`), which is also what the smoke observes since it cannot see Notification Center; the second when the user clicks a notification (or a menu item) and the renderer must open the session. A click that has to create or reload the window cannot rely on `did-finish-load` (React commits and subscribes later), so the notifier emits `attention.navigate` only when a page has already subscribed and otherwise queues the one navigation, which the page pulls once through `attention.pendingNavigate` right after subscribing (C1's subscribe-then-snapshot rule); the queue holds the latest navigation only.

### X2 — `layout.*` (`src/shared/ipc/schema/layout.ts`)

### Renderer stores (`src/renderer/src/stores/`)

Zustand stores fed by X2 events through one subscription module, `src/renderer/src/ipc/events.ts`, which subscribes to every event the shell consumes before the snapshot commands run (C1's ordering rule) and reconciles each snapshot with the events that raced it: by the higher `revision` for `session.list`, `session.projects.list` and `session.digests` (their payloads carry one), and by **buffer and replay** for `attention.list`, whose agreed payload and whose `attention.changed` carry none (wave-2 ledger rows; unchanged). Buffer and replay: while `attention.list` is outstanding, every `attention.changed { appSessionId, items }` is stored per session, last one wins, an empty `items` included; when the snapshot resolves the store takes it whole, then replays each buffered replacement over it (so a session the snapshot still lists as pending but whose later change emptied it ends empty), sets `loaded`, and drops the buffer; a change arriving after `loaded` replaces that session's list directly. Both arrival orders are unit-tested (M1 pins). Selectors are memoised with `useShallow`; derivations live in plain functions beside the stores so they are unit-testable without React.

| Action | Precondition | Result |
|---|---|---|
| `openTab(ref)` | not open | insert after the target pane's active tab (pinned tabs stay ahead of unpinned; `overview` stays first), activate, focus that pane |

| `closeTab('overview')` | | no-op (the Overview tab is permanent, §5.2) |
| `moveTab(id, toPane, i)` | | remove from source, insert at `i`, activate, focus `toPane`; an emptied source pane collapses as in `closeTab` without a `closedTabs` push |
| `splitWithActive()` | no split | pane 1 created with the active tab moved into it (the source keeps its neighbour active); focus pane 1 |
| `splitWithActive()` | split | move the active tab to the other pane (`moveTab`) |
| `selectTab(n)` | | activate the n-th tab (1-based) of the focused pane; out of range is a no-op |
| `cycleTab(±1)` | | next or previous tab of the focused pane, wrapping |
| `reopenClosed()` | `closedTabs` non-empty | pop and `openTab` into the focused pane |
| `togglePinned(id)` | id ≠ `overview` | flip `pinned`; reorder the pane so pinned tabs precede unpinned |

Digest fold, the rules the reducer implements (unit-tested with hand-written event arrays; the fixtures are frames and the normaliser is C3's). Three rules come before the table. **Partition**: an event whose `parentToolUseId` or `agentId` is non-null is child-agent traffic and never touches the parent's `phase`, `activity`, `lastAssistantLine`, `turnStartedAt`, `lastTurnEndedAt` or `cost`; C3's normaliser already keeps live `turn.*` on the parent conversation, but forwarded child messages (`subagent.message`, child `assistant.block.*`) and C4's sidecar backfill, which emits `turn.started`/`turn.ended` with `agentId` set, arrive in the same `session.eventBatch` and would otherwise set a working parent idle. Child traffic feeds only `pendingRequests` (a child's `permission.requested` blocks the session and is a Needs-you item like any other) and the `childAgents` counts, which come from the parent's own `subagent.started`/`subagent.finished`. **Echo receipts**: a `turn.ended` with `isEchoReceipt: true`, and a `user.message` with `origin: 'bash_echo'`, are not a turn and change nothing. **Deduplication**: the fold keeps the last 2,000 event ids per session and skips an id it has seen, so a backfill overlapping a snapshot, a reload of the re-emit path or a repeated batch never double-counts cost or replays a lifecycle (C4's disk ids and C3's live ids are both deterministic; the ledger's ruling 5 applies to main's fold as it does to C6). Then the table: `turn.started` → `working`, `turnStartedAt`, `activity: 'Thinking'`; `assistant.block.delta` with `thinkingDelta` → `activity: 'Thinking'`; `tool.use` → `activity` from the tool (`Running <command first 60 chars>` for Bash, `Editing <basename>` for Edit/Write/MultiEdit, `Reading <basename>` for Read, `Searching` for Glob/Grep, `Fetching <host>` for WebFetch, `Running <toolName>` otherwise); `tool.result` clears `activity` to `'Working'`; `assistant.block.complete` with a text block → `lastAssistantLine` (first non-empty line, ≤ 160 chars); `session.state` `requires_action` → `waiting`, `running` → `working`, `idle` → `idle`; `permission.requested` and kin → `pendingRequests + 1`, their resolutions `− 1`; `turn.ended` → `idle` (`failed` when `isError` and the terminal reason is not `aborted_streaming`), `lastTurnEndedAt`, `cost.totalUsd` replaced by `costUsd` (the engine reports the process's running total, never a per-turn increment; Surprises), `activity: null`; `context.sample` → `context`; `usage.sample` → `cost.totalUsd` (replace, as above); `subagent.started` → `childAgents.active + 1`, `subagent.finished` → `active − 1, done + 1`; `process.exited` → `exited` (`failed` when `reason` is `crash`); `session.reconnect` `attempting` → `activity: 'Reconnecting'`; `boundary.compaction` while working → `activity: 'Compacting'`. `applyEngineStatus`: `process` `starting`/`initializing` → `starting`, `exited` → `exited` unless the digest is already `failed`; `holder` on the record follows C3's `toSessionRecordPatch`. Unread: the read model keeps the set of visible sessions from `session.setVisible` and forwards each change to the source's `onSetVisible`; the source owns `record.unread` and `lastSeen` (C4's index applies the rule on `lastRecordAt` advances and emits `session.changed`; the stub store applies it on its scenario's `turn.ended` and digest ops); the read model keeps `costAtSeen = cost.totalUsd` at the moment a session becomes visible and recomputes `cost.sinceSeenUsd` on every cost change as `totalUsd − costAtSeen`. Records arrive through the source's writer calls (C4's `IndexSessionSource`, or the stub source); the digest of a record with no live fold is `exited` (or `foreign` by holder) with `lastAssistantLine` from C4's `summary.lastAssistantText` through `setDigest`.

Notifier rules: a notification is posted for an attention item when it first appears in state `pending` with an actionable kind, the main window is not focused (or there is no window), `settings.notifications.enabled`, and, when `settings.notifications.kinds` is present (C11's settings-v3 field, five booleans read through an optional type extension without changing C5's v2 schema), the item's group is on — `approvals` covers `permission`, `dialog` and `elicitation`; `questions` covers `question`; `planReviews` covers `plan`; `errors` covers `error`, `interrupted` and `auto_mode_unavailable`; `heldPeerMessages` covers `held_peer_message` (which is not actionable and never notifies today; the flag is honoured if a later child makes it notify) — and behaves as today when `kinds` is absent; title `<project name> · <session title>` (or the title alone), body `item.summary`, `silent: !settings.notifications.sound`; one per item id ever; `click` focuses (or re-creates) the window and emits `attention.navigate` once the page has loaded; a `failed` event (the unsigned-binary case, Surprises) or `!Notification.isSupported()` switches delivery to `fallback` for the process lifetime: `app.dock.bounce('informational')` and the `attention.notified` event with `delivery: 'fallback'`, which the renderer shows as a toast. Quit guard: on `before-quit`, `midTurn` = `model.midTurnCount()`: sessions whose engine status (C3's `session.status`, the process table's truth) has `process` in `starting`, `initializing` or `ready` and either `turn !== null` or `process` still `starting`/`initializing` (a launch whose first message is on its way). The digest's phase is the UI's vocabulary and is folded from events that a stale batch, a child backfill or an echo receipt can skew; a status exists only for a process C3's host owns, so holder `self` is implied and a foreign-live session never counts. When `> 0`, `event.preventDefault()`, then a native `dialog.showMessageBox` (`type: 'warning'`, buttons `['Quit', 'Cancel']`, `defaultId: 1`, `cancelId: 1`, message `N sessions mid-turn` / `1 session mid-turn`, detail `Quitting stops them. ## Surprises & Discoveries

- Observation: Electron's `registerAccelerator: false` (show a chord in the menu without registering it) is Windows and Linux only, so on macOS the application menu always owns any chord it displays; the keymap therefore has two sinks with a single table, and pane-scoped chords stay out of the menu.
  Evidence: Electron 44 `MenuItem` documentation, option `registerAccelerator` annotated *Linux* *Windows*: "If false, the accelerator won't be registered with the system, but it will still be displayed." (fetched 2026-09-28).
- Observation: macOS notifications need a code-signed binary; the unsigned C1 build cannot deliver them and dev runs can (Electron's release binary is signed), so the notifier needs a fallback and the smoke must observe an app event, not Notification Center.
  Evidence: Electron 44 `Notification` documentation: "This API requires an application to be code-signed in order for notifications to appear." and "Unsigned binaries will emit a `failed` event when notifications are called."
- Observation: no probe fixture carries a read-only tool permission request; every `can_use_tool` in both passes is `Bash` (6 journals) or `AskUserQuestion` (1), because auto mode allows reads; the hover-approve scenario therefore needs a synthetic `Read` request, marked as such in the scenario file.
