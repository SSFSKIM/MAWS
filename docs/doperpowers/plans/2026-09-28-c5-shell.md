## Purpose

After C5, the owner opens MAWS and the window is the one they will live in. On the left, a sidebar answers "where am I needed" before anything else: a **Needs you** section lists every session blocked on a human across all projects, longest wait first; below it the pinned sessions, the projects with their sessions (status glyph, title, what it is doing or last said, age, unread dot), and the sessions that belong to no project. The main area opens on the **Overview** board (⌘0): one card per live or unread session, grouped by project with a Needs-you group on top, each card showing activity, last assistant line, context, cost since last seen and child agents, with the pending request inline. Session tabs open beside it, reorder by drag, close with ⌘W, come back with ⌘⇧T, and one tab can be dragged to the right edge to open a second pane. The right region is there for the panel tools (C8) with its width, collapse and pin state already persisted. Every region has a keyboard-operable resizer, sizes and tabs survive a restart, the keyboard map is one rebindable table that also builds the application menu and the ⌘K palette, a macOS notification fires when a session enters Needs-you while the window is unfocused and ⌘⇧J lands on it, the light theme is the default and the dark one switches cleanly, and quitting with turns in flight asks first.

All of this runs with no engine: a stub session source in the main process plays a scenario derived from the protocol-probe fixtures (nine sessions across three projects, one foreign-live, requests of every kind arriving on a timeline) through exactly the X2 events that C3's engine host and C4's index will emit later, so the renderer built here is the renderer that ships. What nobody can do yet, and C5 does not attempt: read a transcript (C6), type to a session or answer a docked request with scopes (C7), open a panel tool (C8), start, rename, fork or archive a session (C10), or see real usage windows (C11). Each of those arrives into a slot this document names.

## Terms

- **Region**: one of the three top-level areas of the window, `sidebar`, `main`, `panel`, each carrying the `data-region` attribute C1's `Shell.tsx` already sets. The **toolbar** is the strip above them that doubles as the window's title bar (`titleBarStyle: 'hiddenInset'`, §3).
- **Pane**: a tabbed area inside the main region. There is one by default and at most two (D-8); the second is the **split**. Every pane has its own tab strip and active tab. The **focused pane** is the one keyboard shortcuts scoped to a pane act on (§5.7).
- **Tab**: an entry in a pane's strip. Kinds: `overview` (exactly one, never closable), `session`, `file`, `diff`, `diagnostics`. A tab id is deterministic (`session:<appId>`), so a session has at most one tab across both panes.
- **Session record** and **attention item**: the X1 shapes `SessionRecord` and `AttentionItem` from C1's `src/shared/graph/session.ts` and `attention.ts`. **Session status**: a C5 read-side shape (`SessionStatus`, Interfaces) carrying what the record does not, the live facts a card and a status line show: phase, activity, last assistant line, context, cost, child agents.
- **Needs-you row**: one sidebar row per session that has at least one pending or delivered attention item; it shows the session's oldest item. Rows are sessions, not items.
- **Read model**: the main-process module that folds the digest of every live session from the event stream and observes records and attention items on their way to the renderer, so the notifier, the dock badge and the quit guard have a view without a renderer. The store of record is C4's index; the read model stores nothing durable. **Source**: a producer that writes into it (C3's statuses and events, C4's records, or the **stub source**, a scenario file, in dev and tests).
- **Scenario**: a JSON file under `test/fixtures/shell/` listing projects, sessions, statuses, attention items and a timeline of changes, validated with the X1 schemas at load. "Fixture-derived" means its ids, directories, tool inputs and request payloads are copied from the probe journals; what the journals do not contain (titles, a read-only tool request) is synthetic and marked so in the file.
- **Slot**: a React component the shell renders at a fixed place with a fixed prop contract, whose real implementation a later child registers (`registerSlot`); C5 ships a fallback for each. Slots: `transcript` (C6), `composer` (C7), `requestCard` (X4, C7), `panelHost` (X5, C8), `fileTab` and `diffTab` (C8), `newSession` (C10).
- **Action** and **chord**: an entry of the keymap table (`src/shared/keymap/actions.ts`) with an id, a title, a default chord in Electron accelerator syntax (`Cmd+Shift+J`), and a **sink**: `menu` when the application menu registers the chord and dispatches the action as a `layout.action` event, `renderer` when the renderer's key dispatcher matches it. The user's overrides live in settings.
- **Hover card**: the Radix HoverCard that opens from a Needs-you row and previews the request (§5.1).
- **Foreign-live**: a session whose `holder` is a terminal or background job (D-12); shown with its holder and no controls.

### X2 — `session.*`, read side (`src/shared/ipc/schema/session.ts`)

Two siblings fill this module: C3 with the engine-host-owned lifecycle and control entries (`session.launch`, `session.status`, `session.events`, `session.answer`, …; `docs/doperpowers/plans/2026-09-28-c3-engine-host.md`) and C4 with the main-owned record side of its index (`session.list` → `SessionListItem[]`, a `SessionRecord` plus a `summary` carrying the index-only columns such as `lastAssistantText` and `firstPrompt`; `session.get`; `session.update { appId, patch }` with `title`, `pinned`, `archived`, `lastSeen`, `unread`; `session.projects.{list,add,update,remove}`; events `session.changed { record, cause }` and `session.removed`; `docs/doperpowers/plans/2026-09-28-c4-filesystem-index-replay.md`). C5 consumes those as defined: pin and mark-read are `session.update` patches, projects come from `session.projects.list`, and the record events feed the sessions store. C5 adds only what neither sibling can answer: the digest of live facts, and the visibility report C4's unread rule needs.

```ts
export const SESSION_PHASES = ['starting', 'working', 'waiting', 'idle', 'exited', 'failed', 'foreign'] as const;
// working: a turn is running · waiting: the turn is blocked on a pending request · idle: process live, no turn
// exited: no live process (resumable from disk) · failed: the last turn or the process ended in error and nothing ran since
// foreign: holder is a terminal or background job (D-12) · starting: process launching, no turn yet
export const SessionDigestSchema = z.strictObject({
  appId: AppSessionIdSchema,
  phase: z.enum(SESSION_PHASES),
  activity: z.string().nullable(),            // while working: "Running bun test", "Editing src/app.ts", "Thinking", "Compacting"; else null
  lastAssistantLine: z.string().nullable(),   // first line of the latest completed assistant text block, ≤ 160 chars; seeded from C4's summary.lastAssistantText for sessions with no live fold
  turnStartedAt: z.string().nullable(), lastTurnEndedAt: z.string().nullable(),
  context: z.strictObject({ percent: z.number(), totalTokens: z.number().int(), maxTokens: z.number().int(), autoCompactThreshold: z.number().int().nullable() }).nullable(),
  cost: z.strictObject({ totalUsd: z.number(), sinceSeenUsd: z.number() }).nullable(),
  childAgents: z.strictObject({ active: z.number().int(), done: z.number().int() }),
  pendingRequests: z.number().int(),
  revision: z.number().int(),                 // per session, monotonic; a consumer keeps the higher of snapshot and event
});

export const commands = {
  'session.digests':    { input: z.void(), output: z.strictObject({ digests: z.array(SessionDigestSchema) }), owner: 'main' },   // snapshot for a page that missed the events
  'session.setVisible': { input: z.strictObject({ appId: AppSessionIdSchema, visible: z.boolean() }), output: z.void(), owner: 'main' },
  // C3's entries (owner 'engine-host') and C4's record entries (owner 'main') follow
};
export const events = {
  'session.digest': SessionDigestSchema,
  // C3's `session.status` and the event batch `session.events`, C4's `session.changed` and `session.removed` follow
};
```

`session.setVisible` is the shell's report of which sessions are on screen (the active tab of a pane while the window is focused and the page visible). Main hands it to C4's index, whose unread rule is "`unread` becomes true when `last_record_at` advances past `last_seen_at` for a session whose holder is not `self` and whose tab is not visible" and which names visibility as C5's to report; the index therefore needs one API addition, `sessions.setVisible(appId, visible)`, that keeps the visible set and, when a visible session's record advances, updates `lastSeen` in the same step so the record never flickers unread (Reconciliation). The digest model uses the same set for cost since last seen. The project tree needs a change event to stay current without polling: `session.projectsChanged { projects }` (whole list) is proposed to C4 unless its index already emits one.

Why a digest and not C3's `EngineSessionStatus`, C4's summary or C6's transcript store: `EngineSessionStatus` is the process table's truth (process state, engine state, turn, queue, memory) and says nothing about what the session is doing in words, its context percentage or its cost since the human last looked; C4's `summary` is what the JSONL tail says and stops being current the moment a process is live; C6's `useTranscriptStore.lastAssistantLine` exists only for sessions whose events the transcript store has been fed, and the sidebar must describe sessions nobody has opened. The digest is a pure fold over X1 events plus C3's status, small enough to run in main for every live session (Main modules below), seeded from C4's summary for the rest, and the same shape the stub scripts. When C6 lands, an opened session's secondary line may read C6's store; the digest stays for the rest.

The renderer's layout store hydrates by reading the four keys, validates each (an absent or invalid value falls back to its default, and a `main.tabs` whose session or agent tab names an unknown record is repaired), and writes back only the key that changed, 250 ms after the last change and on `beforeunload`. `layout.openTab` is **not** an IPC command (C6 proposed one): tabs are renderer state, so a command would travel to main only to come back as an event. It is the store action `openTab(ref, opts)` in `src/renderer/src/stores/layout.ts` (Stores below), and C6's `TranscriptActions.openFile(path, line)` maps to `openTab({ kind: 'file', path, line, appId }, { pane: 'focused' })` in one adapter line in `App.tsx`. Main-initiated opens (a notification click, a menu item) arrive as `attention.navigate` and `layout.action` events and call the same store action.

### Keymap and action table (`src/shared/keymap/actions.ts`, `chord.ts`)

One table drives the application menu, the renderer's key dispatcher, the ⌘K palette and every tooltip. An action has a sink: `menu` actions are registered as accelerators of the macOS application menu (main), whose click handler emits `layout.action`; `renderer` actions are matched by the renderer's dispatcher on `keydown`. The split exists because Electron's `registerAccelerator: false` (display a chord without registering it) is Windows and Linux only (verified against the Electron 44 MenuItem documentation, Surprises), so on macOS a chord shown in the menu is always registered there and the renderer never sees its keydown; a chord that must know the focused pane or the focused element therefore stays out of the menu. A test pins that no chord appears in both sinks, that every chord is unique, and that every `menu` action has a `menu` placement.

```ts
export type Sink = 'menu' | 'renderer';
export interface ActionSpec { title: string; chord: string | null; sink: Sink; menu: 'file' | 'view' | 'go' | 'help' | null; scope: 'app' | 'pane' | 'composer' }
export const ACTIONS = {

Transcripts stay on disk and can be resumed.`); `Quit` calls `engine.shutdown { graceMs: 5000 }` through `dispatchToHost` (C3's command; an `unknown_command` or `host_unavailable` answer is ignored) and then `app.quit()` with the guard disarmed; `Cancel` does nothing. Under `MAWS_E2E=1` the dialog is not shown: `MAWS_E2E_QUIT_ANSWER` (`quit` by default) answers it and main logs `quit-guard: N mid-turn, auto-answered quit` to stderr, which is what the smoke asserts.

Window state: `WindowState = { bounds: Rectangle; maximized: boolean; fullscreen: boolean }`; restored only when the saved bounds intersect a current display by at least 64×64 px (`screen.getAllDisplays()`), else `1280×820` centred on the primary display; saved on `resize`, `move`, `maximize`, `unmaximize`, `enter-full-screen`, `leave-full-screen`, debounced 500 ms; `minWidth: 960, minHeight: 600`; `trafficLightPosition: { x: 16, y: 15 }` so the lights centre in the 44 px toolbar (`--toolbar-h`).

## Surprises & Discoveries

- Observation: Electron's `registerAccelerator: false` (show a chord in the menu without registering it) is Windows and Linux only, so on macOS the application menu always owns any chord it displays; the keymap therefore has two sinks with a single table, and pane-scoped chords stay out of the menu.
  Evidence: Electron 44 `MenuItem` documentation, option `registerAccelerator` annotated *Linux* *Windows*: "If false, the accelerator won't be registered with the system, but it will still be displayed." (fetched 2026-09-28).
- Observation: macOS notifications need a code-signed binary; the unsigned C1 build cannot deliver them and dev runs can (Electron's release binary is signed), so the notifier needs a fallback and the smoke must observe an app event, not Notification Center.
