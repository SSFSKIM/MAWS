## Purpose

After C7 the owner talks to a session. Under the transcript sits a real editor: type, paste a screenshot or a page of logs, drop a file, mention `@src/main.ts` or `@agent-Explore`, type `/` and pick a command from the engine's own catalogue, and press Enter; while the engine works the same control reads Queue (the message waits, survives a process exit, and goes when the turn ends), ⌥Enter steers it into the running turn, ⌘. stops, and after an interrupt Resume releases the queue. The queued list above the editor edits, deletes and promotes entries. `!ls` runs a shell command through the engine and the model sees its output; `#remember this` appends to the memory file you chose. ArrowUp on an empty editor recalls what you sent, in this session and then across sessions and the terminal. When the engine needs the human, the editor gives way to one card, the same card that appears inline in the transcript, on an Overview card and in a Needs-you hover: a permission with its exact command and the grant scopes the engine will honour, a question form, a plan with its three outcomes, an MCP elicitation form, one of the two dialogs the launch declares (a refusal fallback, the auto-mode server fallback). Enter and Esc answer it, but only in the pane that holds focus. A session that has not started yet (the owner's "+" tab, 2026-09-28 ruling) shows the same composer: its strip chips are the setup (location, branch, model and effort, mode, directories) bound to C10's setup intent, the first Send starts the engine through C10, and C10's trust and relay-down cards dock where a permission would. Under it the status line shows cwd, context, the account's 5h and 7d windows read from ClaudeUsage's own files, cost and mode, each with a popover, and a near-limit banner appears once per window, not once per composer.

What C7 does not do: allocate, launch, start or resume sessions (C10's `session.create` and `session.start`; C7 binds the chips to C10's intent and hands the first message to C10's hook; a dev-only resume affordance exists for acceptance), render the transcript (C6), build the palette widgets behind `/model` and kin or the accounts and settings screens (C11), fork a session from an edited message (C10 supplies the provider; C7 supplies the seam and the explicit-rewind alternative), answer a dialog kind the launch did not declare, or write anything into `~/.claude` (D-12, §4.3).

## Terms

- **Composer**: everything C7 renders in C5's `composer` slot: the context strip above the editor, the editor, the attachment strip, the queue list, the submit control and the mode chrome. **Status line**: C5's container under it (`src/renderer/src/session/StatusLine.tsx`), whose six buttons C7 gives popovers.
- **Editor**: the Tiptap instance. **Document** or **doc**: its ProseMirror document, serialised as Tiptap JSON (`editor.getJSON()`); the shape C4's `Draft.doc` stores. **Atom**: an inline node the cursor treats as one character (a mention chip, a pasted-text chip).
- **Chip**: a small labelled token. In the editor, a **mention chip** (`@file`, `@agent`) or a **pasted chip** (`[Pasted text #1 +40 lines]`); in the strip, a **context chip** (project, location, branch, model, mode, add-dir).
- **Attachment**: an image or PDF held beside the doc and sent as a content block. **Attachment strip**: the row of thumbnails under the editor.
- **Serialisation**: the pure function from doc plus attachments to what `session.send` carries (`string | ContentBlock[]`, C3's `session.send` input) and to the one-line `display` history keeps.
- **Submit control**: the button whose label is one of the five states of §5.4: Send, Queue, Steer, Stop, Resume.
- **Queue entry**: C3's `QueueEntry` (`src/shared/engine/session-state-store.ts`) with states `queued`, `submitting`, `released` and the flag `uncertain`; **paused** is the queue's flag. **Busy**: C3's predicate (a turn is open or an entry is `submitting` or `released`); the renderer approximates it from `EngineSessionStatus.turn` and the entries.
- **Request**: one of the five kinds the engine parks for a human (`permission`, `question`, `plan`, `dialog`, `elicitation`), reaching the renderer as an X1 `AttentionItem` (`src/shared/graph/attention.ts`) plus its originating `*.requested` event. **Card**: the X4 component that renders one request. **Placement**: where the card sits: `docked` (in the composer's place), `card` (inside a C5 Overview card), `hover` (inside C5's Needs-you hover card), `inline` (in C6's `request_slot` row). **Pointer**: the compact inline row shown in the transcript while the same request is docked in that pane.
- **Scope**: what a permission allow grants: `once`, `session`, `local_settings` (C3's `RequestAnswer`). **Downgraded**: a request whose engine flags forbid persistent scopes, so only `once` is offered. **Quick approval**: any path that approves a permission without its full card (hover Approve, Enter on the docked or Overview card, a digit); a request flagged `requiresUserInteraction` has none, in any placement.
- **Declared dialog**: one of the two `request_user_dialog` kinds C3's `initialize` declares (`refusal_fallback_prompt`, `auto_mode_server_fallback`); any other `dialogKind` is **undeclared** and is never answered by C7.
- **Catalogue**: the engine's own list of slash commands, agents and skills for a session, from the `initialize` response and each `system/init`, kept fresh by `system/commands_changed`; held by the engine host with a **revision** per launch and published whole as `session.catalogChanged`.
- **Seen cursor**: the newest user `messageUuid` in the transcript store at the moment the edit flow started; what `session.rewind`'s `lastSeenMessageUuid` carries (C3 requires the caller's value, never the host's).
- **Unstarted session**: a session tab whose app id has a C10 setup **intent** but no engine process yet (owner ruling 2026-09-28); the composer's chips bind to the intent through C10's hook and the first Send starts the engine through C10.
- **Docked card frame**: the chrome, focus and Enter/Esc registration of the docked placement, exported so C10's trust and relay-down cards dock with the same rules as a permission card.
- **Mode** (of the editor): `send` (ordinary), `bash` (a leading `!`), `memory` (a leading `#`).
- **Window**: one rate-limit window of a Claude account: the 5-hour window (ClaudeUsage's `session` key), the 7-day window (`weekly_all`) or a per-model 7-day window (`weekly_scoped#<Model>`). **Drain target**: the account ClaudeUsage's relay routes new sessions to (`pins.json.drainTarget`). **Pin**: the relay's assignment of one engine session id to one account (`pins.json.pins[<sessionId>]`).
- **Provider seam**: a renderer registry through which a later child supplies behaviour C7 needs but does not own: `registerResubmitProvider` (C10's fork) and `registerSlashWidget` (C11's widgets).

## Constraints

Binding on every milestone, from the charter and the sibling contracts:

- §5.4 and §5.5 semantics: the strip's chips and the permission chip showing the *effective* mode with the refusal code in words; the five submit states; the queued list with edit, delete, steer and "queue paused because you interrupted"; `!` through the engine's bash frame with the output as a replayed row; `#` appending to memory; ArrowUp history on an empty editor; pasted text beyond a threshold becoming an attachment; drag-and-drop files attaching and images pasting inline; a pending permission or question replacing the composer with its card, Enter approving and Esc declining, the composer returning afterward; the slash palette listing engine commands, skills, custom commands and MAWS actions marked by origin, commands with a terminal menu opening a widget (C11's); the status line's six fields and their sources; the near-limit banner once per window. (binding semantics, advisory layout)
- §4.2 further engine semantics: the app-owned queue with Steer bypassing it (C3 implements; C7 renders and drives); plan approval's three outcomes; `!` and `#` as C3 implements them; edit-and-resubmit forks by default and rewind is an explicit action. (binding)
- §5.7 and C5's dispatcher contract: Enter and Esc reach a request only from the element that holds DOM focus, through `useKeyChord(id, handler, { within })` (`src/renderer/src/keymap/useKeyChord.ts`); C5 refuses every pane-scoped dispatch whose target is a text-entry element or sits under any `[data-key-sink]`, and delivers `composer`-scope actions only inside `data-key-sink="composer"`; C7 therefore marks only the editor subtree (the contenteditable and its `@`/`/` popups) `data-key-sink="composer"` and keeps the docked card, strip, queue list and submit control outside it; `composer.send` and `composer.cycleMode` are C5's table entries C7 consumes; a keyboard shortcut never approves a request in an inactive pane. (binding)
- §5.1 hover rule and SPEC 45 §45.19.1: in the hover placement, Approve and Deny exist only for `permission` items whose tool is in `READ_ONLY_TOOLS` (`src/shared/attention/read-only-tools.ts`) and whose request is not flagged `requiresUserInteraction`, by click only, with `scope: 'once'` or a plain deny; a request flagged `requiresUserInteraction` has no quick approval in any placement and never becomes a generic allow (the flag means the tool's own card is the interaction surface, or the consent text could not ride the wire). (binding)
- X6 and SPEC 45 §45.22.13: the only dialog kinds C7 answers are the two C3's `initialize` declares, each with the payload and result strings of the pinned binary's schema (`refusal_fallback_prompt` at `cli.pretty.js:545548`, `auto_mode_server_fallback` at `:927997`); an undeclared kind stays pending and visible and is never completed or cancelled by C7. (binding)
- X4: one component for the five kinds, taking an `AttentionItem` and an answer callback, identical in look and behaviour in every placement. (binding, owned here)
- X2: C7 adds entries only in per-namespace modules as delimited blocks (`session.ts`, `settings.ts`, `layout.ts`, `git.ts`), strict objects, validation on both sides; the one touch outside a namespace module is the `MawsBridge` interface in `src/shared/ipc/schema.ts` (`pathForFile`, Interfaces). (binding)
- X1: C7 never renames and never widens an identifier; its one X1 change is additive and optional (`permission.requested` fields with `mcpServer` as a strict object, Interfaces) and is recorded in the wave-2 ledger's "C7 additions" block. (binding)
- X3 and C6's public surface: C7 imports only from `src/renderer/src/transcript/index.ts` (`Transcript` props `renderRequest`, `actions.editAndResubmit`, `useTranscriptStore`, the row types) and adds one export there (`Markdown`, Interfaces); the one X3 change C7 asks of C6 is additive (`Attachment.text`, the Ask of C6) and C7 reads `text` attachments only through the row types. (binding)
- C3's `RequestAnswerSchema` is the answer contract: a permission `allow` carries `scope`, a `deny` carries none; question answers are keyed by question text with multi-select joined `', '`; plan outcomes are `implement`, `clear_and_implement`, `keep_planning`; dialog and elicitation answers are passed verbatim. (binding)
- C3's queue entry states and `uncertain` are rendered as C3 defines them: a `submitting` entry is in flight and not editable; a `released` entry is the running turn and leaves the list at its `turn.ended`; an `uncertain` entry sits at the head with the queue paused until the human resumes or removes it. (binding)
- D-19 and D-17: usage windows come from ClaudeUsage's local files for routed sessions, one shared read for every session; the engine's `get_usage` is read only for a session whose `EngineSessionStatus.gateway.mode === 'direct'`. (binding)
- §4.1 renderer sandbox: the renderer loads nothing by path; files reach it as bytes through main (`layout.pickFiles`) or as `File` objects from paste and drop; a dropped file's path comes only from Electron's `webUtils.getPathForFile` in the preload. (binding)
- D-12 and §4.3: C7 never writes under `~/.claude` (the terminal's `history.jsonl` is read, never appended); MAWS's own history lives under `userData`. (binding)
- C1's conventions: zod 4 (`import * as z from 'zod'`), validators never transform or default, `Schema` suffix, tokens only in components (the guard test), unit tests beside sources, `@shared/*` alias. (binding by inheritance)
- Shared files (wave-2 ledger, section c, extended to wave 3): every addition C7 makes to a file another child owns is a delimited block; C8 runs in parallel on its own branch and touches none of C7's files except `src/renderer/src/App.tsx` (each child one block) and `package.json` (separate keys). (binding)
- Commit rules from `CLAUDE.md` and the owner's global instructions: no attribution footers.

**Catalogue protocol.** The engine host's C7 block keeps one `catalog` per session beside C3's handshake state (C3's `EngineSessionStatus` carries neither `commands` nor `agents`, so the block retains them itself): on the `initialize` response it takes `commands` and `agents`; on every raw `system/init` frame it takes `skills` and `terminal_slash_commands` (X1's `session.init` carries names only and no terminal list, so the block reads the frame, not the event); on every `system/commands_changed` it replaces `commands`. Each of the three bumps `revision` and emits `session.catalogChanged` with the whole catalogue; `revision` restarts at 0 with every launch and the payload carries the `launchId`, so a host restart or a relaunch never leaves the renderer holding a "higher" stale revision. `session.catalog` answers the same state immediately (C3's deadline shapes); before any process it answers `launchId: ''`, `revision: 0` and empty arrays, and the first `session.catalogChanged` that follows the initialize response completes it. The renderer's catalogue store (`stores/catalog.ts`) follows C6's hydration pattern: subscribe to `session.catalogChanged` first and buffer, invoke `session.catalog`, apply the snapshot, drain the buffer, then apply live events; a payload is applied when its `launchId` differs from the held one or its `revision` is greater, and dropped otherwise. The store reads neither `session.init` nor `session.commands`. Mounting before `initialize` therefore shows an empty palette that fills at the handshake; mounting before the first `system/init` shows commands without `terminalOnly` until the first turn's init; a `commands_changed` that races the snapshot is applied or dropped by revision, never by arrival.

`session.history.*` is answered by main from two sources: MAWS's own `<userData>/prompt-history.jsonl` (append-only, one JSON object per line in the terminal's own record shape `{ display, pastedContents, timestamp, project, sessionId }`, so a future append into the terminal's file would be a one-line change) and, read-only, the terminal's `~/.claude/history.jsonl` (`CLAUDE_CONFIG_DIR` honoured; the last 512 KiB of the file, lines filtered to `project === <the session's directory>`), merged newest-last by `timestamp`, de-duplicated on the pair (`display`, SHA-256 of the concatenated resolved `pastedContents` bodies in key order) so two pastes of identical display and different bodies stay distinct, capped at `limit`. **Recallable bodies:** `pastedContents` is stored and returned in the terminal's shape (SPEC 42 §42.15.7): MAWS writes each pasted text atom as `{ id: n, type: 'text', content: <body>, contentHash: null, mediaType: null, filename }` inline whatever its size (its own file, bounded by the composer's 1 MiB text cap) and each image attachment as `{ id: n, type: 'image', content: null, contentHash: null, mediaType, filename }` (a placeholder only: image bytes live in drafts, not history); for a terminal row main returns `content` inline when the record has it (≤ 1024 characters) and otherwise reads `<CLAUDE_CONFIG_DIR>/paste-cache/<contentHash>` read-only, leaving `content: null` when the cache file is absent. An entry whose placeholder has no resolvable body is **unresolved**: the editor shows it as an unavailable chip and never sends the placeholder text (Serialisation). `append` writes MAWS's file with `project` = the session record's `directory` and `sessionId` = the engine session id when known, and never touches the terminal's file or its cache for writing (D-12).

`layout.pickFiles` opens `dialog.showOpenDialog` (`openFile`, `multiSelections` when asked, `defaultPath` = `directory`, filters `Images` for `photos`) and reads the bytes only for image and PDF types under the caps; every other file is answered by path alone. `git.lsFiles` runs `/usr/bin/git ls-files --cached --others --exclude-standard -z` (C4's git invocation conventions: `execFile`, `GIT_OPTIONAL_LOCKS=0`, `LC_ALL=C`, 10 s timeout) in `directory`, caches the list per directory for 10 s, filters by the fuzzy scorer below, and for a directory that is not a repository walks it (`readdir`, depth ≤ 6, ≤ 20,000 entries, `node_modules`, `.git`, `dist`, `.claude/worktrees` skipped) and answers `source: 'walk'`.

### Document model and serialisation (`editor/extensions.ts`, `editor/serialize.ts`)

The editor is plain text with atoms: no marks, no headings, no lists (the model reads markdown from the text; formatting chrome would only fight it). Rules, in order. **Text**: paragraphs joined with `\n`, `hardBreak` as `\n`, trailing whitespace of the whole trimmed; a `mention` of kind `file` renders `@<id>` (wrapped as `@"<id>"` when the path contains whitespace, the terminal's quoted form), kind `agent` renders `@agent-<id>` (the form the engine's `agent_mentions` producer recognises, SPEC 11 §11.8.2, SPEC 42 line 5393). **Pasted framing** (`src/shared/composer/pasted-content.ts`, the terminal's own `Xnt` at `cli.pretty.js:898640`, SPEC 42 §42.15 lines 4495–4524): typed text is first **neutralised** with `text.replace(/<(?!\\)(?=\/?pasted_content)/gi, '<\\')`, which rewrites only the `<` so `<pasted_content` becomes `<\pasted_content` and `</pasted_content` becomes `<\/pasted_content` (the slash is kept; the negative lookahead makes it idempotent; the engine's `h6` regex additionally matches Unicode look-alike spellings, which MAWS does not reproduce, advisory); then each `pasted` atom renders as `\n\n<pasted_content id="hhhh">\n` + the body neutralised the same way + `\n` when the body lacks a trailing newline + `</pasted_content id="hhhh">\n`, so **both tags carry the id**, the block starts after a blank line and ends with a newline, and `hhhh` is the first four lowercase hex digits of SHA-256 of `ctx.sessionId` (four random hex digits when null: an unstarted session's first send). An `unavailable` atom (a recalled placeholder with no body, History) renders nothing and the send reports `1 pasted segment was unavailable and was left out`. MAWS always wraps, although the terminal gates the wrapping and its system-prompt bullet behind `tengu_virtual_pancake` (default `false`, SPEC 09 lines 517–531): the JSONL is the store (D-12), so a pasted segment must be recoverable from the text itself, the model reads the content either way, and the engine's own parser (`vmt`, `cli.pretty.js:666478–666507`) recognises exactly this framing, which is the grammar C6 is asked to use (Ask of C6). **Mode**: `bash` when the text starts with `!` and the doc is one paragraph with no atoms (the command is the text after `!`, trimmed); `memory` when it starts with `#` (the note is the text after `#`, trimmed); `send` otherwise. **Content**: with no attachments, `content` is the text (a string); with attachments, `content` is `[...images as { type: 'image', source: { type: 'base64', media_type, data } }, ...documents as { type: 'document', source: { type: 'base64', media_type: 'application/pdf', data } }, { type: 'text', text }]`, the text block omitted when the text is empty (an image-only send), images before text as the Messages API recommends; SPEC 45 §45.15.1 states the stdin `user` message is a MessageParam whose content may hold text, image and document blocks, so nothing is re-encoded. **Display** (for history and the queue list): the text with each `pasted` atom as `[Pasted text #<n> +<lines> lines]` and each attachment as `[Image #<n>]` or `[PDF #<n>]`, mentions as their text form; bash mode keeps its leading `!`. **PastedContents** (for history): `{ [n]: { id: n, type: 'text', content: body, contentHash: null, mediaType: null, filename } }` per pasted atom and `{ id: n, type: 'image', content: null, contentHash: null, mediaType, filename }` per image, keyed by the placeholder number. **Empty**: no text after trimming and no attachments.

Sizes and caps (advisory): an image is downscaled on a canvas to at most 1568 px on its longest edge (the vision model's working size) and re-encoded as PNG for screenshots (source PNG or GIF) or JPEG at 0.85 otherwise, then refused with a toast when still over 5 MiB (the API's per-image limit); a PDF over 32 MiB is refused; a draft persists image and document bytes up to 4 MiB in total (`persisted: false` beyond that, and the strip labels those "not kept in draft"); a `user` frame's content is refused by C3's schema over 1 MiB of text, which the composer pre-checks and reports as "Message too large (N KB); attach the text as a file instead". Pasted text becomes a `pasted` atom when it exceeds 1024 characters or 10 lines (the terminal keeps inline paste content up to 1024 characters, SPEC 42 §42.19.1); shorter pastes insert as text. Dropped or picked non-image, non-PDF files insert a `file` mention chip with their path (absolute when outside `cwd`, relative otherwise); a dropped file without a path (`pathForFile` answers `''`) is read as text and becomes a `pasted` atom named after the file, or is refused over 1 MiB.

Drafts: the composer restores `session.drafts.get` on mount (C4's `Draft { doc, attachments, updatedAt }`), writes `session.drafts.set` 750 ms after the last change and on unmount with `doc = editor.getJSON()` (the strip rides in `doc.attrs.attachments`) and `attachments` = the path-backed chips as C4's `{ path, kind }` list; an empty doc with no attachments writes `null`. A draft is per app session and never cleared by a tab switch (Claude Desktop lesson, `research/claude-desktop-ux-and-engine.md` A5); it is cleared on a successful `session.send`, `session.bash` or `session.memoryAppend`.

History (`editor/history.ts`): ArrowUp with the cursor on the first line of an empty editor, or while navigating, moves to the previous entry; ArrowDown moves forward and past the newest restores the draft the navigation started from; any edit to a recalled entry ends navigation (the edited text is the new draft, never overwritten by the next arrow); the sources are this session's own human prompts from `useTranscriptStore.rows(key)` (rows of kind `user` with `messageUuid`, oldest first, consecutive duplicates collapsed; their pasted bodies come from the row's `text` attachments, Ask of C6), then `session.history.list { limit: 200 }` entries not already present (same display and same body hash). A recalled entry re-parses `@` and `/` tokens into chips (the terminal reruns its providers on recall, SPEC 42 line 9077) and rebuilds each `[Pasted text #n +L lines]` placeholder as a `pasted` atom from `pastedContents[n]` when its `content` is resolved, and as an **unavailable** atom (chip `Pasted text #n · unavailable`, tooltip `The body of this paste is not stored`) otherwise; `[Image #n]` and `[PDF #n]` placeholders are always unavailable atoms (history keeps no bytes). An unavailable atom never serialises as its placeholder text (Serialisation). After every send, bash run or memory append the composer calls `session.history.append` with `display` and `pastedContents`.

### Edit-and-resubmit and the fork seam (`resubmit-seam.ts`)

C6's user bubble calls `actions.editAndResubmit(row)`, adapted in `App.tsx` to `prefillComposer(appSessionId, { text: row.text, pasted: <the row's text attachments>, images: <the row's image attachments with a data URL>, editing: { messageUuid: row.messageUuid, seenCursor: <the newest user row's messageUuid in the transcript store at this moment> } })`. The **seen cursor** is captured when the edit flow starts, not when the send happens: it is what the person had seen when choosing to edit, which is what C3's `lastSeenMessageUuid` means (c3: "the transcript knows what the human has seen; the host never substitutes its own latest uuid"). The composer enters edit mode: the strip reads `Editing an earlier message · sending forks this session from here`, Esc or the chip's × leaves it. Send in edit mode calls the registered `ResubmitProvider.forkFrom` (C10: a fork launch of this session, a rewind in the fork to that message, then the send, opening the new session's tab) and, when none is registered, offers the explicit alternative the charter names, driven by the state machine `ResubmitState = 'idle' | 'confirming' | 'rewinding' | 'rewound_awaiting_send' | 'sent'` in the composer store:

- `confirming`: the dialog `Forking arrives with C10. Rewind this session to that message and resend instead?`. If the transcript's newest user uuid no longer equals `editing.seenCursor` when the dialog opens or while it is open (a queued prompt or an engine-initiated turn started a later turn since the edit began), the dialog reads instead `A newer turn started after you began editing. Rewinding discards it too. Rewind anyway?` and its confirm first advances `seenCursor` to the current newest uuid; C3's own guard (`unseen_later_turn`) stays the last line.
- `rewinding`: `session.rewind { targetMessageUuid: editing.messageUuid, lastSeenMessageUuid: editing.seenCursor, files: false }` in flight; the editor is read-only. `rewound: false` returns to `idle` with the engine's `reason` as a toast and the draft intact.
- `rewound_awaiting_send`: the rewind succeeded (C3 emitted `boundary.rewind`); the edited content is sent through `session.send`. A send failure (`ok: false`, or main answering `write_failed`) stays in this state with the banner `Rewound · the message was not sent · Retry`; Retry calls `session.send` again and **never** `session.rewind` (the rewind is done; repeating it would answer `stale_target`). Leaving edit mode from this state keeps the edited text as the draft and shows `The conversation was rewound; your edited text is in the editor`.
- `sent`: `session.send` answered `ok`; the store clears `editing` and returns to `idle`.

Rewind is thereby always the explicit action (§4.2) and the fork the default once C10 lands.

- *Editor and document model*: Tiptap 3.31.3 (exact, the whole family on one version) with a plain-text schema: `Document` carrying an `attachments` attribute, `Paragraph`, `Text`, `HardBreak`, `Placeholder`, `UndoRedo`, `Mention` with two triggers (`@` for context, `/` for the palette, the terminal's trigger rules), a `Pasted` atom for long pastes, `FileHandler` for paste and drop, and one keymap extension; no marks, headings or lists (the model reads markdown from the text). Alternative: a textarea with a chip overlay, rejected because atoms, undo and IME are what an editor library exists for. Advisory (§4.7).
