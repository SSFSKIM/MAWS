## 2. Gate reasoning

**Well-defined — fails on four forks the owner must close, and on nothing a spike must settle first.** Purpose and the tool list are binding and clear; acceptance is coarse but observable. Four forks have no owner or answer inside the charter and the siblings: (1) messaging a subagent has no wire path, so §5.6's composer and §10 item 4 are either a relay through the parent model or gone; (2) Sent files has no producer under MAWS's entrypoint; (3) Review's base is undefined (the mockup names two, the engine records none); (4) the Files tool needs a new privileged read surface (directory listing and file bytes outside the engine store) that no sibling exposes, and its security boundary is a decision, not a detail. Each is answerable in one grill round with the evidence above; none needs a child whose deliverable is findings, though two probes belong at the start of the children that use them (§6).

**Well-scoped — fails, narrowly, and not on size.** As one unit C8 is a host plus a summary plus six views over three data paths; a single execution document with seven milestones could carry the code. It fails "one accountable context" on three split signals:

- *Different state owners and verification.* Subagents and Background work read the engine's store and the wire (C4 `fs.*`, C3 `task.*`/`subagent.*`, `session.stopTask`) and are verified with the probe fixtures and a live child; Review and Files read git and the working tree through main-process services (C4 `git.*` plus a new file-read namespace) and are verified with scratch repositories and filesystem fixtures; the host reads only C5's layout store and is verified by persistence and pin behaviour. A reviewer holding all three at once holds agent topology, the git service and a file-access security boundary in one head.
- *Dependency timing.* Everything the host needs is landed (C5 M2/M4). Everything the tools need is not: C3 M5 (every `session.*` command), C4 M6 (every `git.*`), C6 M5 (`ipcSource`, the callback call sites). Three siblings wait on the host and nothing else: C9 M4 adapts to X5 at its refresh, C10's attach affordance (its item 12) needs `addTool`, C11's Session info registration needs `registerPanelTool`. Under the pattern this project runs (one branch per child, whole-branch review, then merge), a single C8 would deliver the host only when its last tool lands, holding three refresh passes behind milestones that cannot yet be pinned.
- *Acceptance by "and".* §12 C8's acceptance chains unrelated behaviours: pinned tabs persist *and* a child receives a message *and* Review opens a file at the line *and* a workflow shows phases. Nothing in that list is an invalid intermediate state without another; each is meaningful and verifiable alone.

**Keep-together checks pass for the parts that stay together.** Subagents and Background work share the task graph (a workflow *is* a task with agents; a background agent appears in both), the same `session.stopTask`, and the same list-and-drill-in anatomy: splitting them would put one data path behind two children. Review and Files share the "open this file at this line" seam (the change receipt → Review → viewer tab), the same main-process read services, and the same viewer libraries: a Review without a viewer to open into is the "diff tab that prints a ref" C5 ships today. The host and the summary share one store and one component tree.

**Verdict: cut.** Three plan children, no spike children; the two empirical probes ride as first gates inside the children that depend on them. The alternative "one plan child with the host as M1" is the runner-up (§3.3) and becomes the right answer only if C3 M5, C4 M6 and C6 M5 have all landed before C8 dispatches, which removes the timing seam.

## 5. Residue for the owner's grill

Only what turns on taste, scope or product. Each has a recommended answer and the scene that makes the difference visible.

**Q1. Messaging a subagent: relay through the parent, or drop it from P0?** The engine offers no host path to a running child (§1.6); the only route is a main-lane message that asks the parent model to `SendMessage`. *Recommendation:* keep the drill-in composer as a **relay**, sent with Steer priority so the parent picks it up at its next tool round, labelled honestly (`Relay via <session title>`), rendered in the drill-in as "Asked <session> to relay…" until the `SendMessage` row appears in both transcripts, and disabled when the parent's turn is not running (a finished child cannot be messaged at all). Amend §5.6 and §10 item 4 to "receives a relayed message". *Scene:* the reviewer agent has been checking `tree.test.tsx` for four minutes; you type "check tree.tsx, not the test" in the drill-in. Relay: one steer to the parent, the parent's transcript shows `Sent message to reviewer`, the child's next tool round reads it. Drop: you type the same thing in the main composer with the agent's name and hope the model routes it; the drill-in is read-only. The relay costs one parent tool round and touches the parent's context; dropping it removes a §10 line.

**Q2. Sent files: redefine as Outputs, or wait for the extension phase?** `SendUserFile` is disabled for MAWS's entrypoint and, when enabled, uploads to claude.ai (§1.6). Faking the entrypoint would invalidate every fixture and route bytes off the machine. *Recommendation:* P0 ships **Outputs** in its place: the files this session created or rewrote (from C6's receipts, `Write` `type: 'create'` first), as a summary section (mockup 01's "Sent files" row) and a filter in the Files tool, opening in the viewer, which is Codex's "Outputs / Recent files"; the per-type renderer for images, markdown and PDF is the viewer's job either way, so nothing is thrown away when the in-process MCP "show a file" tool arrives (D-9). The charter's Sent files tool moves to that phase with a Decision Log line. *Scene:* the agent writes `report.html` and says "open it to see the chart". Outputs: the row is there, click, the viewer renders it in a sandboxed frame. Waiting: nothing in the panel until the extension phase; you find the path in the transcript.

**Q3. What is Review's base?** The mockup says both "against main" and "since session base"; the engine records no session-start commit, and a resumed or terminal-started session has none. *Recommendation:* Codex's scopes (D-20): **Uncommitted** (working tree against `HEAD`; default for a dirty tree), **This branch** (three-dot against the main worktree's branch, C10's `BranchStatus.base`; default when the worktree is clean), **Last turn** (the receipt's files, from the change receipt rather than git), and Staged when the index differs. No invented "session base". *Scene:* a worktree session commits twice mid-way; Uncommitted shows nothing, This branch shows every change since `main`, Last turn shows the three files the last answer touched. A recorded session-start commit would add a fourth scope that only sessions started in MAWS could show.

**Q4. How much file viewer in P0?** §3 puts the editor in P1; "Review opens a file tab at the changed line" needs at least a read-only code view. *Recommendation:* read-only CodeMirror 6 (the P1 editor's base, so no rewrite) with syntax highlighting and line jump; images inline; markdown rendered through C6's `Markdown` with a Source toggle; PDF, HTML and media as "open externally" rows until Outputs needs them. *Scene:* Review → `Open file ↗` lands on line 87 highlighted; Files → `docs/charter.md` reads as a document, not as fenced text.

**Q5. The Pull request row.** §5.6's summary lists "PR row (status, checks, open on GitHub)"; C4 provides branch, upstream, ahead/behind and nothing about remotes or PRs, and source control is P1. *Recommendation:* P0 shows push state only (`2 ahead of origin/main`, `Not pushed`) and `Open on GitHub` when a remote URL read is cheap to add to C4's `git.status` (one `git remote get-url`); PR status and checks wait for the P1 source-control panel or a `gh` read. *Scene:* the row reads `Not pushed · 2 commits` instead of `No pull request yet · Create PR`.

## 6. Risks and spikes

- **R1 — Relay to a child is unverified.** No fixture contains a `SendMessage` call. *Probe:* a pass-3 scenario (`spikes/protocol-probe/scenarios/pass3/relay-to-child.mjs`): start a background agent that loops on `Read` calls; write a `user` frame with `priority: 'now'` reading "Relay to agent <id>: <text>"; assert a `SendMessage` `tool_use` with `to: <id>` and that the child's next assistant record reflects the text; record the latency in tool rounds. Settles Q1's feasibility and the relay's wording; C8b's first gate.
- **R2 — Duplicate rows in a live drill-in.** A child source that snapshots from `fs.agentEvents` (C4 ids `<uuid>`, `<uuid>#<n>`) and subscribes to C3's live batches (ids `<app>:<launch>:<seq>:<n>`) receives the same records under different ids, and C6 deduplicates by id (`source/hydrate.ts:20-50`). *Probe:* a unit test over `attachSource` with both sources for one child. *Likely fix (ask of C6 or C4):* deduplicate child events by `messageUuid`, or C4 declines to follow an agent of a session that is live in C3 and C8's source snapshots from `session.events { afterSeq }` filtered by `agentId` for a live session and from `fs.agentEvents` otherwise.
- **R3 — Background shell output is unreadable through the landed read.** `fs.readSpill` roots exclude `<tmpdir>/claude-<uid>/` where `output_file` lives (§1.4). *Resolution:* ask of C4 (one root added, one test); until then the `Output` action is disabled with the path shown.
- **R4 — `get_workspace_diff` hunks are untyped and unobserved on a dirty tree.** C3 types `perFileStats` and `hunks` as `unknown[]` and `reads.jsonl` #81 is empty. *Probe:* re-run the reads scenario after an edit (`pass3/workspace-diff-dirty.jsonl`) and type both arrays; C11's `/diff` needs the same fixture. Review itself uses C4's `git.diff`, so this affects only the `/diff → Open in Review` hand-off (which passes a path, not hunks).
- **R5 — Nested subagents on the wire are unverified.** Disk nesting is proven (`parentAgentId`, `spawnDepth: 2`); a grandchild's live frames keeping their own `parent_tool_use_id` is SPEC-only. *Probe:* one pass-3 scenario with an agent that spawns an agent under `--forward-subagent-text`; settles whether the Active list can nest live or only after the sidecar appears.
- **R6 — `stop_task` is unfixtured.** *Probe:* in the same pass-3 run, stop a background shell, an agent and a workflow; record the `task.updated`/`task.notification` sequence C8b's acceptance names.
- **R7 — Renderer reuse inside a 380 px panel.** C6's virtualiser expects a scroll container of known height; C5's slot container is `overflow-auto`, not a flex column, and a child's `request_slot` needs C7's inline card. *Probe:* the C8a harness mounts `Transcript` `variant: 'child'` over `pass1/subagent` inside the real region at 280, 380 and 640 px and under maximize; a failing anchor is a one-line container fix, not a design change.
- **R8 — Diff and viewer libraries.** `@git-diff-view/react` must take C4's multi-file unified patch and render split mode; CodeMirror 6 read-only adds bundle weight to a renderer that already carries Streamdown, Shiki and xterm. *Probe:* a scratch-install check like C6's Streamdown check (`patch` from `git diff` over three files, split and unified, a 5,000-line file) and a bundle-size measurement; a failing result swaps the diff view for C6's own hunk renderer (which already renders edit details) rather than delaying C8c.
- **R9 — File-read boundary.** A `files.read` in main with a session-directory allowlist by realpath is the sandbox's new edge. *Mitigation:* the same negative-control pattern C4 used (unit tests with symlinks pointing outside; a guard test that the renderer never constructs a path it did not receive from `git.*`, `files.list`, a receipt or a transcript chip). Design, not a spike.
- **R10 — Panel session-follow and line refresh are C5 asks.** Both are small and both gate acceptance lines (Files → file tab keeps the tools; Review → open at line on an open tab). Relay to the C5 executor now so they land in M6 rather than as a retrofit.
