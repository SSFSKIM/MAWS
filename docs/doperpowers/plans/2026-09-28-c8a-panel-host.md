## Purpose

After C8a the right panel is a real place. Open a session and the panel rests on a card that says what the session is standing on: the branch, how much is uncommitted, whether it is pushed, how many agents are working and done, what runs in the background, and the files the session has touched; every row is a door to the tool that owns it, and a door that is not built yet says which child brings it. Press "+" and the registered tools are offered; open one and it becomes a tab with a pin and a close glyph. Pin a Terminal and it is the first tab in every session; switch sessions and its shell is intact; collapse the panel, come back, and the tab's scroll position is where it was; quit and relaunch, and the pinned tab and every session's own tabs are back where they were. Click the home glyph and the summary returns without closing anything. A tool that is busy can refuse to close and explain itself in place. Three siblings register into this host and nothing else: C9's Terminal and C11's Session info at their refresh passes, C8b's Subagents, Background work and Log, C8c's Review and Files; C10's "attach in a terminal tab" lands a Terminal tab through the same call. Developers see all of it in a harness page, `#panel`, over fake sessions at the panel's three widths and maximized, with C6's child transcript mounted inside the region (R7).

What C8a does not do: build any tool (a stub stands in for each until its child lands), read a file (K1, C8c), render a diff (C8c), list agents or workflows beyond the summary's counts (C8b), persist anything but tab refs and the summary's section expansion (D-10, no fourth store), or write `layout.*` keys that C5 owns.

## Terms

- **Host**: the React component C8a registers into C5's `panelHost` slot (`src/renderer/src/app/slots.ts`; props `PanelHostProps` in `src/renderer/src/panel/host-slot.ts`), plus the module-level registry behind it. C5's region (`panel/PanelRegion.tsx`) keeps the header strip (maximize, hide), the width and collapse, and hands the host `{ appSessionId, tabs, activeTabId, maximized, onChange, onTogglePinned, onToggleMaximize }`.
- **Tool**: a `PanelTool` declaration (X5): id, title, icon, `pinnable`, `multiInstance`, `menu`, a state factory, `open`, `beforeClose`, `dispose`, `render`, an optional `summary` section. **Registered**: known to `registerPanelTool`. **Stub tool**: a harness-only `PanelTool` with a sibling's id standing in for the sibling's tool.
- **Ref**: what C5 persists of a tab, `PanelTabRef { id, toolId, pinned }` (`src/shared/ipc/schema/layout.ts`), in `panel.pinned` (the global pins) or `panel.<appSessionId>` (a session's own list with its `activeTabId`). **Tab**: a ref shown in the strip. **Instance**: the live state of one tab (`createState`'s result and its bookkeeping), kept in the host's registry map keyed by the ref's id, outside React. **Placeholder tab**: a tab whose tool is not registered; it renders its `toolId` and "Arrives with <child>" and has no instance. **Transient tab**: a Log tab (`toolId: 'log'`); never pinned; one restored from `layout.json` is dropped when the strip would first show it, one opened in this launch lives like any tab until closed; reopened from the row that produced it.
- **Shown session**: `PanelHostProps.appSessionId`, the session the focused pane's active tab belongs to (C5's `sessionOfTab`: `session`, `agent`, `diff` and `file` tabs carry one), or null on the Overview, Diagnostics, Accounts and Settings tabs. **Target session**: the `appSessionId` an `addTool` call names; it may differ from the shown session (C10 attaches to session A while B or the Overview is on screen).
- **Pin**: D-10. A pinned tab is in `panel.pinned`, shows first in every session's strip, and its instance's `ctx.appSessionId` follows the shown session. **Home glyph**: the strip's first control; it sets `activeTabId: null` without closing tabs, which shows the **summary**, mockup 01's "Session overview" card. **Section**: one collapsible part of the summary with a sticky muted heading (Codex §3) whose expansion persists.
- **Live session**: one whose `EngineSessionStatus` is in `useSessions().engine` (C3's `session.status` event, applied by C5). **Disk-only session**: a record with no status here. **Seam**: a C5-exported store action the host writes refs through; the host never writes `layout.*` commands for refs itself.
- **Hydration barrier**: the moment C5's layout store turns `hydrated` true (its `hydrate` has read `panel.pinned` and every `panel.<id>` and replaced the panel lists wholesale). A host write before it is a **pending add**, applied at the barrier. **Restored Log set**: the ids of `toolId: 'log'` refs present in the pins and every session's list at the barrier; the only Log refs the host prunes. **Selection repair**: after a pin leaves the pins, the host moves every other session's `activeTabId` off it through `updatePanelTabs`.
- **Harness**: the development page loaded under `MAWS_HARNESS=1` (`pnpm dev:harness`; `src/renderer/harness.html`, router `src/renderer/src/harness/main.tsx`, landed by C6 and extended by C9 with `#probe`). C8a's page is `#panel`; it replaces the `#panel` page the ledger (d.13) had allocated to C9, which does not exist yet and which C9 M4 now targets instead of building.

### The host's state and transitions

Two stores, deliberately split. The **instance map** is a module-level `Map<string, Instance>` in `host.ts`, never React state: `Instance { ref: PanelTabRef; tool: PanelTool; state: unknown; closing: Promise<boolean> | null }`. Beside it, two module-level bookkeeping values: `pending: PendingAdd[]` (`{ id, toolId, appSessionId, params, pin, activate }`, the adds made before the barrier, in call order) and `restoredLogs: Set<string>` (the restored Log set, captured at the barrier). The **host store** (`usePanelHost`, zustand) carries only what React renders: `tools: Map<string, PanelTool>` (registration order), `titles: Record<tabId, string | null>` (from `setTitle`), `focus: Record<tabId, number>`, `closing: Set<tabId>`, and a `version` bumped when the instance map changes so the strip re-reads it. `ctx` is built per render from the props, the layout store's `regions.panel.collapsed`, `useSessions` (`records`, `engine`) and the host store. Two C5 facts the transitions lean on, read from `stores/layout.ts` at 08611d5: the barrier's signal is the store's `hydrated: boolean` (subscribe-able; C5 exposes no promise, and none is needed), and the sessions that hold a panel list are the keys of `panelBySession: Map<AppSessionId, PanelSessionState>` (the enumeration selection repair walks). Neither needs an ask.

| Event | Precondition | Effect |
|---|---|---|
| a ref appears in `props.tabs` | its tool registered, no instance | `createState({ appSessionId: props.appSessionId, session, instanceId: ref.id, params: undefined })`; the instance is created when the tab first appears in the strip, not when it is selected (a pinned Terminal re-adopts at launch; a session's own tabs when the session is shown) |
| a ref appears in `props.tabs` | its tool not registered | a placeholder tab: icon absent, title `toolId`, body "Arrives with <child>" from `ARRIVES_WITH`; close removes the ref; pin follows the ref |
| `registerPanelTool(tool)` | a tool of that id exists | the declaration is replaced; existing instances keep their state and render with the new component (HMR); the returned disposer unregisters only while its own registration is current |
| the returned disposer runs | | every instance of the tool is disposed and its refs removed from every list, with no `beforeClose`, inside selection repair (below) over the set of the tool's pinned ids: the shown list through `onChange`, every session in `panelBySession` whose effective list holds a ref of the tool through `updatePanelTabs(S, refs => refs.filter(r => r.toolId !== id), { activeTabId })` (the pinned refs leave the pins on the first such call), the pins alone through `setPanelTabs(null, …)` when no session holds a list |
| `addTool(id, { appSessionId: T, params, pin, activate })` | unregistered id | throws |
| | T null without `pin: true`; or `pin: true` on a tool with `pinnable: false` | throws |

### Git store (`src/renderer/src/stores/git.ts`)

```ts
export interface GitEntry { root: string | null; status: GitStatus | null; uncommitted: { files: GitDiffFile[]; at: string } | null; error: string | null }   // per directory
export interface GitStore {
  entries: Map<string, GitEntry>;                    // by directory (session.worktree?.path ?? session.directory)
  watch(directory: string): () => void;              // ref-counted here; the first watcher invokes git.watch and git.diff { scope: 'all' }, the last release invokes git.unwatch
  applyChanged(event: EventPayload<'git.changed'>): void;   // every directory whose root matches takes the status and re-runs git.diff
}
export const useGit: UseBoundStore<StoreApi<GitStore>>;
```

`git.watch` answers the status; `git.diff { directory, scope: 'all' }` (Review's Uncommitted: the working tree against `HEAD`) supplies `files` for the change line and is re-run on each `git.changed` for the root, coalesced to one in flight per directory. A `git.watch` that fails sets `error` and no root; the summary shows it in words (`Not a git repository` for C4's message of that name, `Git unavailable` for any other failure, a directory that does not exist included). The composer's location chip (C7) also calls `git.watch`; main ref-counts by root across callers, so both sides call `unwatch` symmetrically and nothing else is coordinated. One limit of the source, found by review round one: C4's watcher emits `git.changed` only when its status projection differs (deep-equal on `files`, `branch`, `head`, `upstream`, `ahead`, `behind`, `stashCount`; C4 document M6), and a further edit to an already-dirty tracked file changes `git.diff`'s sums without changing that projection, so the line goes stale until the next status-changing event. The Ask of C4 below closes it at the source; the store adds no polling and no second trigger (a re-mount of the summary for the session re-runs `git.diff` once through the first watcher, which is the degraded refresh until the ask lands).

- *Host composition and instances*: the slot component is a strip (`role="tablist"`) over a body; tab instances live in a module-level map keyed by `PanelTabRef.id`, never in React state, and a small zustand store carries only what React draws (registered tools, title suffixes, focus counters, closing flags); `ctx` is derived per render from C5's props, the layout store's `collapsed` flag, the sessions store and the host store; unselected tools are unmounted. Alternative rejected: instantiating on selection, which would leave a pinned terminal's pty unadopted until clicked and the strip's titles unknown. Binding on the map, the unmount rule and ensure-instance (X5, every tool codes against it); advisory on the create-on-appearance moment.
- *Session-addressed writes*: `addTool(toolId, { appSessionId, params, pin, activate })` names a target session and writes the ref into that session's list through C5's `updatePanelTabs(appSessionId, fn, { activeTabId })` (landed at 08611d5) whether or not the session is shown, the pins passing through `fn` unchanged; `activate` (default true) selects the tab and, for a target not on screen, first opens the session in the main area through C5's `openSession` so the panel follows; `activate: false` adds without switching anything; `appSessionId: null` targets the pins and needs `pin: true`; single-instance lookup is the target's list plus the pins, never another session's; the shown session's own interactions (select, close, pin, the home glyph) stay on `onChange`; the host never writes `layout.*` commands for refs. **Hydration barrier**: C5's `hydrate` replaces the panel lists wholesale and replays only main-area changes, so an `addTool` before the layout store's `hydrated` flag turns true returns its minted id at once and is held as a pending add, applied in call order at the barrier through the same path as any add, a pending single-instance ref replacing a restored one of its tool in place so the returned id is the tab's.
