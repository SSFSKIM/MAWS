## Purpose

After C8b the owner can see what a session's agents are doing and steer the ones that need it without leaving the panel. Press "+" and choose Subagents: `Active · 2` lists the two agents the session dispatched, each with its glyph, its name (or, since almost no sidecar carries a name, its description), the sentence it is working on and an elapsed count that ticks; a child an agent itself dispatched sits indented under its parent, in whichever list either of them is; an agent waiting on a permission carries a `waiting` badge and `Approval needed`; when one finishes it moves to `Done · 1` with its outcome. Click a row, or a subagent row in the transcript, and the drill-in shows that agent's own transcript with the same renderer the main area uses, its model, `Dispatched by <session>`, and, when the child asks for a permission, the same request card the composer would dock, answerable in place. Under it is a composer labelled `Relay via <session>`: for an agent running in the background, type a message and the panel asks the parent to forward it at its next tool boundary or when its turn ends (at once when the parent is idle); the line reads "Asked <session> to relay…" with the time elapsed until the parent's `SendMessage` row appears, then says the agent gets it at its next tool round, and rests there (on engine 2.1.283 no receipt reaches any host surface of the child, so the line clears only if a later engine forwards one; O3, ruled 2026-09-29). For an agent the parent is waiting on (a foreground agent) the composer is disabled and says why: the parent reads messages only after that agent returns. Choose Background work: a running workflow is a card with its phases (`Solve 3/3`, `Verify 2/3`, `Judge · Queued`), a table of its agents with model, tokens and time updating as progress arrives, and `Stop workflow`; a background shell reads `<command> · running 4m` with `Output`; a monitor is listed with its description; the session's task checklist reads `Tasks · 4/7` with the earlier ones folded away; `Stop` ends any of them and the card says stopping until the engine says stopped. `Output` and the transcript's "Open full log" open a Log tab over the file the engine reports, paged, with the path and size in its header; Log tabs are gone after a relaunch and come back from the same row. The summary's Subagents and Background work sections read the same counts. A session that exists only on disk shows the same agents and workflow runs from the engine's store, with the facts only the wire could give marked unavailable rather than guessed.

What C8b does not do: build a source of its own for a child's events (K2, C6's `ipcSource` owns it), message a child by any host path (none exists; the relay is the design), read a file outside the engine's store (K1, C8c), pause, skip or retry a workflow (wire-absent), edit the task list (P1), show the topology view (§16), or touch the host, the summary's other sections or the code tools (C8a, C8c).

## Terms

- **Task**: anything the engine registers in its task registry (SPEC 20): a background shell (`local_bash`), an agent (`local_agent`), a workflow run (`local_workflow`), a monitor (`monitor_ws` and any `monitor*` type), or another type. On the wire a task is born by `task_started`, updated by `task_updated`, and ended by one terminal `task_notification`; C3 maps a `local_agent`'s frames to X1 `subagent.started/progress/finished` and every other type's to `task.started/updated/notification` (`normalizer-system.ts`), and `background_tasks_changed` to `tasks.snapshot`, which is also what `EngineSessionStatus.backgroundTasks` holds. **Task id**: the engine's id; for an agent it is the same string as the agent id (the sidecar's `agent-<id>` and the task's `task_id` agree in every fixture), so the graph keys agents by it.
- **Task graph**: C8b's model of a session's tasks, `TaskGraph { tasks: Map<TaskId, TaskNode>; order }`, built by a pure reducer over the X1 task and subagent events plus the disk reads, shared by both tools and the two summary sections. **Node**: one task's entry. **Wire fact**: a field a live event or the status gave; **disk fact**: a field the sidecar, a workflow snapshot or a task file gave; anything neither gave is **unavailable** and is shown in words (*Failure semantics*).
- **Live session** and **disk-only session**: the spec's Terms (a live session has `EngineSessionStatus` in `useSessions().engine`). **Live form** and **disk form** of an event: C3's live journal events carry `seq` and ids `<app>:<launch>:<seq>:<n>`; C4's disk events carry `seq: null` and ids from the transcript's uuids. The same fact can reach `session.eventBatch` in both forms, so the graph takes one form per session (Interfaces, *The task-graph store*). **Launch**: one engine process; C3's journal is one file per launch and its `seq` restarts at 1 with each (`src/engine-host/journal.ts:2-3, 29, 59`), and `EngineSessionStatus.launchId` names the current one, so a `seq` cursor is meaningful only within a launch.
- **Live child** and **disk child**: the spec's Terms. **On disk** (a list section): agents known only from `fs.subagents`, whose status is unavailable unless the sidecar carries `stoppedByUser`. **Workflow agent**: a `SubagentEntry` with `runId !== null` (C4 lists `subagents/workflows/<runId>/agent-*` with the run's id, `src/shared/ipc/schema/fs.ts:59-67`; its sidecar's `agentType` is `workflow-subagent`); the engine starts no `local_agent` task for it (`pass2/workflow.jsonl` has one `task_started`, seq 77, of type `local_workflow`), so it is never in the agent lists: its state is the run's `workflow_agent.state` row on the workflow card. **Background child** and **foreground child**: `subagent.started.isBackground` (C3 maps `is_backgrounded`, `normalizer-system.ts:106-108`), overridden by a later `task.updated.patch.isBackground` (C3 maps `patch.is_backgrounded` for every task type, `normalizer-system.ts:126-131`; a foreground Task "has since been backgrounded", SPEC 45:1848), so a foreground child backgrounded while it runs becomes a background child; a foreground child blocks the parent inside its `Agent` call until it returns.
- **Drill-in**: the Subagents tool's view of one agent inside the panel, C6's `Transcript variant: 'child'` over `ipcSource(appSessionId, agentId)` (K2). C5's `agent` main-area tab (`openTab({ kind: 'agent', appSessionId, agentId })`) renders the same transcript without a composer and is C5's route.
- **Relay**: the drill-in composer's send: one `session.steer` to the parent, with `priority: 'next'` (never `'now'`: on this engine a `'now'` steer preempts the parent's running turn, ending it with `terminal_reason: aborted_streaming`, and runs the message as the next turn, C3's `pass3/steer-now.jsonl`; a `'next'` steer folds into the running turn at the parent's next tool boundary, C3's `pass3/steer-next.jsonl`, two identical runs: the frame out at seq 46, `command_lifecycle started` mid-turn at 71, answered at 87, one `result` at 239 naming both prompts; C3's `session.steer` carries `priority: z.enum(['now', 'next']).optional()`, landed on master at `src/shared/ipc/schema/session.ts:82`, the host defaulting an absent priority to `'now'` at `src/engine-host/ipc.ts:200` and writing the frame at `queue.ts:176-181`, whose comment names this relay; the output is `{ messageUuid }`, `session.ts:69`), whose content asks the parent to `SendMessage` the child. **The three observables**: (a) the steer was accepted, (b) the parent's `SendMessage` `tool.use` row with `to` naming the child, (c) the child's **live event stream** shows the message (a `user.message` with the child's `agentId` in the live form; a receipt visible only in the child's disk transcript is not observable while the parent runs here, since C6's live child source starts no disk follower, `source/ipc.ts:46-53`). **Parent round**: one parent `assistant` message that carries at least one `tool_use` block, counted per message (distinct `messageUuid` among the parent's `assistant.block.complete` events whose block is a `tool_use`), in whichever turn it falls; **child tool round**: one of the child's tool calls, the unit at which the engine delivers pending messages (SPEC 18 §18.26.2, `agent-live`). **Peer origin**: C3 passes an engine frame's `origin.kind: 'peer'` through as `peer` on `user.message.origin` and `turn.ended.origin` only (pinned for a message from a subagent into the main session, `conformance/fixtures.test.ts:319-330` on master, from live journal 3.5); the `turn.started` of such a turn reads `engine`, and `EngineSessionStatus.turn.origin` stays `human | engine` (`status.ts:19`); C6 has landed its rendering, a completed peer turn reading `Peer session worked for <t>` (`model/copy.ts:37`). Whether the child's receipt of a relayed message carries `peer` is R1's to record; the task graph ignores `turn.*` and message origins, `matchesReceipt` accepts any origin, the drill-in renders the child's turns as C6 does, and the lists show no turn origin.
- **Stopping**: the state between a `session.stopTask` call and the engine's terminal `task.updated`/`task.notification` for the task (the TUI's own two-phase stop, SPEC 20 §20.12.5). The engine's frames for a stop arrive in the order `background_tasks_changed` without the task, then `task_updated`, then `task_notification` (`pass2/per-task-stop-workflow-off.jsonl` seq 77, 78 `killed`, 79 `stopped`; `pass2/per-task-stop-on.jsonl` 69–71; `subagent.jsonl` 333–335), so a snapshot's silence about a task never means the task is gone (Interfaces, *The task graph*, the resolution rule).
- **Checklist**: the read-only view of a TaskCreate list, read through the client's `tasks(listId)` (`fs.tasks { listId }`) as a TanStack query keyed `['fs.tasks', listId]`; **list id**: the engine's per-call resolution (SPEC 20 §20.2.2), which C3 reports as `EngineSessionStatus.taskListId`; sanitised `[^A-Za-z0-9_-] → -` before use as a path segment.
- **Log**: the seventh tool, `id: 'log'`, `menu: false`, transient (C8a's *Transient Log tabs*), one tab per session and path over `fs.readSpill`, or a tab with no file when the engine reported none for a cell.
- **Agent-work client**: the one object through which the tools and the stores reach X2, its **disk half** (`fs.subagents`, `fs.workflows`, `fs.tasks`, `fs.readSpill` and the `fs.*Changed` events), its **command half** (`session.steer`, `session.stopTask`) and its **wire half** (`session.events`, `session.eventBatch`), defaulting to the app's validated bridge and replaceable by the harness and the tests (C6's `…Over(client)` pattern); the harness binds the wire half to the loaded fixture's player so the task graph and the relay store see one stream.
- **Harness**: C8a's `#panel` page (`src/renderer/src/harness/panel/PanelHarness.tsx`, closed at c3f80e1, landed at b360711) over fake sessions A and B, which main knows because the page runs under `MAWS_SESSION_SOURCE=stub:test/fixtures/panel/harness-sessions.json` (`e2e/panel.spec.ts:17, 84`; `layout.set` refuses `panel.<id>` for a session the read model does not know); C8b adds a delimited block and a left-column block of its own. **Derived fixture**: an `events/*.events.jsonl` file generated from recorded journals by a committed generator with a reproducibility test (C8a's `events/panel-child` pattern); C8b's three are `events/agents-relay`, `events/agents-stop-workflow` and `events/agents-stop-shell`.

### The task graph (`src/renderer/src/tools/agents/model/task-graph.ts`, pure)

```ts
export type TaskKind = 'agent' | 'workflow' | 'shell' | 'monitor' | 'other';   // local_agent, local_workflow, local_bash, /^monitor/, the rest
export type TaskStatus = 'running' | 'completed' | 'failed' | 'stopped' | 'exited' | 'unknown';
//   running: started and not ended; completed/failed/stopped: the terminal task.notification's (or subagent.finished's) status, or task.updated.patch.status with killed → stopped;
//   exited: the parent process exited while the task was running (a fact: process.exited); unknown: known only from disk, and the sidecar says nothing
export interface TaskNode {
  taskId: TaskId; kind: TaskKind; taskType: string | null; toolUseId: ToolUseId | null;
  description: string;                       // the name: task.started/subagent.started description, else the sidecar's description, else the task id
  status: TaskStatus; stopping: boolean;     // stopping: session.stopTask sent, no terminal event yet
  startedAt: string | null;                  // the start event's `at`; null when the task was only ever seen in a snapshot or on disk
  endedAt: string | null;                    // task.updated.patch.endTime as ISO, else the terminal event's `at`
  usage: { totalTokens: number; toolUses: number; durationMs: number } | null;   // subagent.progress, latest
  lastToolName: string | null; summary: string | null; reason: string | null; outputFile: string | null;
  isBackground: boolean | null;              // the start event's, then task.updated.patch.isBackground when a later frame changes it; null for a node with no start event
  agent: { subagentType: string | null; spawnDepth: number | null; parentAgentId: AgentId | null; model: string | null; name: string | null; prompt: string | null; stoppedByUser: boolean | null; runId: string | null; transcript: { path: string; size: number; mtimeMs: number } | null } | null;   // agents only; name is the sidecar's `name` (1 of 3,000 real sidecars carries one) and never the description; runId is set for a workflow's agent
  workflow: { workflowName: string | null; progress: unknown[] | null; runId: string | null; snapshot: WorkflowSnapshot | null } | null;   // workflows only; progress is the latest whole snapshot (wire or disk)
  provenance: { wire: boolean; disk: boolean; snapshot: boolean };
}
export interface TaskGraph { tasks: Map<TaskId, TaskNode>; order: TaskId[]; byToolUse: Map<ToolUseId, TaskId> }   // order: first seen
export function emptyGraph(): TaskGraph;
export function applyTaskEvents(graph: TaskGraph, events: SessionEvent[]): TaskGraph;   // the seven task kinds plus tool.result and process.exited; every other kind ignored (turn.* of any origin, human, engine or peer, among them); returns the same object when nothing changed
export function applySnapshot(graph: TaskGraph, tasks: EngineSessionStatus['backgroundTasks']): TaskGraph;   // tasks.snapshot / status.backgroundTasks; creates, never removes
export function mergeSidecars(graph: TaskGraph, agents: SubagentEntry[]): TaskGraph;
export function mergeRuns(graph: TaskGraph, runs: WorkflowRun[]): TaskGraph;
export function markExited(graph: TaskGraph, at: string): TaskGraph;      // every running node → exited
export function removeTask(graph: TaskGraph, taskId: TaskId): TaskGraph;  // the store's resolution rule is the only caller
export function parseOutputPath(resultText: string): string | null;       // `Output is being written to: <path>` from the background Bash result; the match stops at whitespace and drops one trailing `.` (the sentence continues ". You will be notified…", `pass2/per-task-stop-on.jsonl` seq 44)
// selectors (memoised on the graph object)
export interface AgentRow { taskId: TaskId; depth: number; parentTaskId: TaskId | null; orphan: boolean }   // orphan: the parent is known but sits in another section, or is unknown to the graph; depth 0 then
export function agentRows(graph, section: 'active' | 'done' | 'disk'): AgentRow[];   // one render rule for the three lists: active = running agents; done = terminal, exited and stopped-by-sidecar agents, newest end first; disk = status unknown. Every section nests a child under its parentAgentId (else under byToolUse of its started event's parentToolUseId, R5) when the parent is in the same section, and marks it orphan otherwise. Agents with agent.runId !== null (a workflow's) are in no section
export function workflows(graph): TaskNode[]; shells(graph): TaskNode[]; monitors(graph): TaskNode[];   // running first, then terminal newest first
export function counts(graph): { working: number; done: number; onDisk: number; shells: number; workflows: number; monitors: number };   // over the same exclusion
```

Reducer rules, in the order the events arrive: `subagent.started` and `task.started` create the node (or fill a snapshot-born or disk-born one), set `startedAt` to the event's `at`, `toolUseId`, `kind` from `taskType` (`agent` for `subagent.started`), and record `byToolUse`; a started event that carries a non-null `parentToolUseId` whose tool use is a known agent's sets `agent.parentAgentId` to that agent (live nesting, R5); `subagent.progress` sets `usage`, `lastToolName`, `summary` and `description`; `task.updated` applies `patch.status` (`killed` → `stopped`), `description`, `endTime` (ms → ISO), `error` (as `reason`) and `isBackground` (a foreground child backgrounded while it runs becomes a background child, so its composer loses the "waiting on this agent" reason); `subagent.finished` and `task.notification` set the terminal `status`, `summary`, `outputFile`, `reason`, `endedAt` (if unset) and clear `stopping`; `workflow.progress` replaces `workflow.progress` with the event's `progress` array (each frame is a whole snapshot, C2's finding) and sets `workflowName`; `tasks.snapshot` (and `applySnapshot` from the status) creates unknown-start `running` nodes for ids it names that the graph lacks (`provenance.snapshot`, `startedAt: null`) and removes nothing: the engine emits `background_tasks_changed` without a stopping task before that task's `task_updated` and `task_notification` (`per-task-stop-workflow-off.jsonl` seq 77–79, `per-task-stop-on.jsonl` 69–71, `subagent.jsonl` 333–335), so a snapshot's silence precedes the terminal frames rather than following them, and for an id the engine never knew no later snapshot names it at all; removal is the store's resolution rule below, through `removeTask`; `tool.result` whose `structured` carries `backgroundTaskId` sets that task's `outputFile` to `parseOutputPath(text)` (the engine reports the path in the Bash tool's own result, `pass2/per-task-stop-on.jsonl` seq 44; §4.3 is honoured because the path is the engine's; the `task graph` suite asserts the parsed path equals the same task's `task.notification.outputFile`, seq 71); `process.exited` with `agentId === null` runs `markExited`. Events whose `kind` is none of these return the same graph. `mergeSidecars` adds a node per `SubagentEntry` the graph lacks (`kind: 'agent'`, `status: 'unknown'`, `provenance.disk`, `agent.runId` from the entry) and fills `agent.model`, `agent.spawnDepth`, `agent.parentAgentId`, `agent.name`, `agent.stoppedByUser`, `description` (when unset) and `agent.transcript` on every agent from C4's typed `SubagentMeta` (`parentAgentId`, `name`, `stoppedByUser` optional keys of the loose object, landed at e6fd841 on C4's branch, `src/shared/wire/store.ts:100-102`); a disk node whose sidecar says `stoppedByUser: true` reads `stopped`; a workflow's agent (`runId !== null`) is a node the drill-in can open from the run's table but no list section shows. `mergeRuns` matches a run to a wire workflow node by `snapshot.taskId`, else adds a disk node keyed by `runId` as its task id; a run's `snapshot.status` is a disk fact and becomes the node's status (`completed`, `failed`, `killed` → `stopped`, `running`); `snapshot.workflowProgress` fills `workflow.progress` when the wire has given none.

### The task-graph store (`src/renderer/src/tools/agents/store.ts`)

```ts
export interface TaskGraphEntry { graph: TaskGraph; phase: 'idle' | 'loading' | 'live' | 'disk' | 'failed'; launchId: string | null; lastSeq: number | null; error: string | null; disk: { agents: SubagentEntry[] | null; runs: WorkflowRun[] | null; error: string | null }; pendingStops: Map<TaskId, { requestedAt: string; resolvedAt: string | null; absentAtResolution: boolean }> }
export interface TaskGraphStore {
  entries: Map<AppSessionId, TaskGraphEntry>;
  watch(appSessionId: AppSessionId): () => void;       // ref-counted; the first watcher subscribes the client's batches, reads useSessions.getState().engine.get(appSessionId) once and runs applyStatus with it (the launch check among it), then subscribes C5's useSessions engine status and the fs.*Changed events, then reads the snapshot; the last release stops the subscriptions and keeps the entry
  applyStatus(appSessionId: AppSessionId, status: EngineSessionStatus | null): void;   // from the useSessions subscription: applySnapshot(status.backgroundTasks), the live ↔ disk decision, the launch check, the pending stops' absence check
  applyDisk(appSessionId: AppSessionId, patch: Partial<TaskGraphEntry['disk']>): void;   // fs.subagentsChanged, and re-reads after fs.workflowChanged
  stop(appSessionId: AppSessionId, taskId: TaskId): Promise<{ ok: true } | { ok: false; message: string }>;   // marks stopping, calls session.stopTask, records the resolution; clears stopping with the message on failure
}
export const STOP_SETTLE_MS = 2000;   // after a resolved stop whose id the status no longer lists, how long the store waits for a terminal frame before removing the node
export const useTaskGraph: UseBoundStore<StoreApi<TaskGraphStore>>;
```

Provenance rule: a session with a status (`useSessions().engine.has(id)`) is live, and its entry takes wire events in the **live form only** (`seq !== null`), through the client's wire half: `watch` first subscribes `client.onEventBatch` and holds the session's batches, then reads `useSessions.getState().engine.get(appSessionId)` once and runs `applyStatus` with it, the launch check included, so a session relaunched while nobody watched it has its cursor reset and its old launch's running nodes marked `exited` before any snapshot is read (a re-watch never reads the new launch with the old launch's `lastSeq`), then reads one `client.events(appSessionId, afterSeq: entry.lastSeq)` snapshot (`session.events { afterSeq, limit: null }`; C3 rebuilds beyond its ring from the journal, so the snapshot is this launch's whole list), applies it, sets `lastSeq`, then replays the held batches and every later one **filtering each event by `seq > lastSeq`** (never a whole batch by its first event), so nothing between the snapshot and the subscription is lost or applied twice, and dropping an event whose id's launch segment (`<app>:<launch>:<seq>:<n>`) is not `entry.launchId`, so a late batch of the old launch never lands on the new cursor; every event whose `kind` is not one of the reducer's is discarded before it reaches the graph, whatever its `agentId` (a task frame the engine attributes to a child, `subagent.progress` for the child, is still the parent's fact about that task). The cursor is **per launch**: the entry records `status.launchId`; when a status arrives with another `launchId` (a relaunch of the same app session) the store runs `markExited` over the running nodes (they were the old process's), resets `lastSeq` to null and re-reads the snapshot for the new launch, keeping the old nodes as `exited`. The status itself comes from a subscription to C5's `useSessions` engine map (`useSessions.subscribe` over `engine.get(appSessionId)`, `stores/sessions.ts:27, 40`), the one place `session.status` is applied in the renderer, so the product and the harness (whose `setStatus` writes that store and emits no IPC event) drive `applyStatus` the same way. A disk-only session's entry reads `fs.subagents` and `fs.workflows` and never calls `session.events` (which would start C4's follower over the whole transcript for a list that needs only the sidecars); it refreshes on `fs.subagentsChanged` (the payload carries the list) and on `fs.workflowChanged` (one `fs.workflows` re-read, trailing 250 ms), both through the client's disk half. A live session reads the disk half too, merged after the wire (`mergeSidecars`, `mergeRuns`), because a resumed session's earlier children exist only in the sidecars (§4.2, `--resume` replays nothing) and a workflow's snapshot carries what the wire's progress frames do not (`status`, `startTime`, `totalTokens`). When a status first arrives for an entry that was disk (the session launched from MAWS), the wire half starts; when the status reports `process: 'exited'`, `markExited` runs and the subscriptions stay until the last watcher leaves (the wire facts are this launch's and remain true). The store never reads C6's transcript store: the two reducers see the same events and agree by construction, and a session whose transcript is not mounted still has a task graph. Cost: one `session.events` snapshot per live session per launch, then filtering batches, which the transcript already subscribes to.

Resolution rule for Stop: `stop` marks the node `stopping`, records `pendingStops[taskId] = { requestedAt }` and calls `client.stopTask`. A terminal `task.updated`/`task.notification`/`subagent.finished` for the id at any time sets the status, clears `stopping` and deletes the pending entry. When the call resolves, the store records `resolvedAt` and whether the id is absent from the latest applied `status.backgroundTasks` (the absence check reads the status alone, never a `tasks.snapshot` event, and runs again at each status applied while the stop is resolved and pending); if it is present the node stays `stopping` until its frames arrive or a later status drops it; once it is absent and no terminal frame has arrived, the store waits `STOP_SETTLE_MS` and, when the frames still have not come, runs `removeTask` (the engine answered success for an id it no longer knows, SPEC 20 §20.12.5). The window exists because the engine's own stop emits the absent snapshot before the terminal frames (Terms, *Stopping*); the recorded fixtures show the three frames consecutive, so two seconds is generous, and R6 records `stop_response.ms` against the frames' arrival to confirm it. A rejected call clears `stopping`, deletes the pending entry and returns the message. A snapshot never removes a node on its own. C3 updates `status.backgroundTasks` from the same `background_tasks_changed` frame it emits as `tasks.snapshot`, so in the product the status drops a stopping id at the tail's first frame; the harness, whose `setStatus` is the status, writes the list the same way (the task listed while it runs, the absent list set together with the release of the tail's snapshot batch).

### Log paging (`log/log-model.ts`)

`LOG_PAGE_BYTES = 256 KiB` (one `fs.readSpill { path, offset, length }` per page; C4's cap is 8 MiB, its default 1 MiB), `LOG_WINDOW_PAGES = 4` (at most 1 MiB in the DOM: the window `{ from, to }` of page indices rendered as one `<pre>` per page; `Load more` at the end extends `to` and drops `from` when the window is full; `Show earlier` at the top does the reverse; a page leaving the window leaves `pages` too). The first read is page 0 at offset 0 with `length: LOG_PAGE_BYTES`; each page records the `offset` it asked for and the `length` the answer consumed, and **the next page's offset is `offset + length`**, not `offset + LOG_PAGE_BYTES`: a utf8 page ends on a character boundary and may consume fewer bytes than asked, or up to three more when the page is too short to hold the character it cuts (the second Ask of C4 below, on master: `engine-host/fs/artifacts.ts:40-49` with `utf8Cut`, `FsReadSpillOutputSchema.length` at `schema/fs.ts:84-93`), so pages decode independently without a split character. `Show earlier` re-reads the dropped page at its recorded `offset` (kept in `pages`' metadata even when the text left). `bytes` from an answer is the size in the header, re-read by `Refresh` (which re-requests the last page in the window at its offset, so a growing output file shows its new tail). A page boundary can still split a line; the `<pre>` is `white-space: pre-wrap` with the transcript's mono font and adjacent pages are rendered flush so a line break at a boundary reads as one line. A refusal renders `Refused: <message>` with the path in mono and no retry loop; the landed messages are `path outside the engine store` (also for any path that is not already absolute and normal, refused before the disk is touched since debt wave 1A, and for a missing path whose deepest existing ancestor lies outside or which crosses a dangling link), `spill not found: <path>` and `not a file: <path>` (`artifacts.ts:14, 19, 30-31, 39`), and a reported path is always absolute and normal; a path under the engine's temp root reads through the root C4 landed in M3. With `path: null` (a cell whose output the engine kept in the transcript only) the tool renders `No file to open: the engine reported no output file for this cell; the transcript shows what was kept` and reads nothing.
