## Purpose

After C8b the owner can see what a session's agents are doing and steer the ones that need it without leaving the panel. Press "+" and choose Subagents: `Active · 2` lists the two agents the session dispatched, each with its glyph, its name, the sentence it is working on and an elapsed count that ticks; a child an agent itself dispatched sits indented under its parent; an agent waiting on a permission carries a `waiting` badge and `Approval needed`; when one finishes it moves to `Done · 1` with its outcome. Click a row, or a subagent row in the transcript, and the drill-in shows that agent's own transcript with the same renderer the main area uses, its model and effort, `Dispatched by <session>`, and, when the child asks for a permission, the same request card the composer would dock, answerable in place. Under it is a composer labelled `Relay via <session>`: type a message and the panel asks the parent to forward it; the line reads "Asked <session> to relay…" until the parent's `SendMessage` row appears, then names the child's next tool round, and clears when the message shows in the child's transcript. Choose Background work: a running workflow is a card with its phases (`Solve 3/3`, `Verify 2/3`, `Judge · Queued`), a table of its agents with model, tokens and time updating as progress arrives, and `Stop workflow`; a background shell reads `<command> · running 4m` with `Output`; a monitor is listed with its description; the session's task checklist reads `Tasks · 4/7` with the earlier ones folded away; `Stop` ends any of them and the card says stopping until the engine says stopped. `Output` and the transcript's "Open full log" open a Log tab over the file the engine reports, paged, with the path and size in its header; Log tabs are gone after a relaunch and come back from the same row. The summary's Subagents and Background work sections read the same counts. A session that exists only on disk shows the same agents and workflow runs from the engine's store, with the facts only the wire could give marked unavailable rather than guessed.

What C8b does not do: build a source of its own for a child's events (K2, C6's `ipcSource` owns it), message a child by any host path (none exists; the relay is the design), read a file outside the engine's store (K1, C8c), pause, skip or retry a workflow (wire-absent), edit the task list (P1), show the topology view (§16), or touch the host, the summary's other sections or the code tools (C8a, C8c).

## Terms

- **Task**: anything the engine registers in its task registry (SPEC 20): a background shell (`local_bash`), an agent (`local_agent`), a workflow run (`local_workflow`), a monitor (`monitor_ws` and any `monitor*` type), or another type. On the wire a task is born by `task_started`, updated by `task_updated`, and ended by one terminal `task_notification`; C3 maps a `local_agent`'s frames to X1 `subagent.started/progress/finished` and every other type's to `task.started/updated/notification` (`normalizer-system.ts`), and `background_tasks_changed` to `tasks.snapshot`, which is also what `EngineSessionStatus.backgroundTasks` holds. **Task id**: the engine's id; for an agent it is the same string as the agent id (the sidecar's `agent-<id>` and the task's `task_id` agree in every fixture), so the graph keys agents by it.
- **Task graph**: C8b's model of a session's tasks, `TaskGraph { tasks: Map<TaskId, TaskNode>; order }`, built by a pure reducer over the X1 task and subagent events plus the disk reads, shared by both tools and the two summary sections. **Node**: one task's entry. **Wire fact**: a field a live event or the status gave; **disk fact**: a field the sidecar, a workflow snapshot or a task file gave; anything neither gave is **unavailable** and is shown in words (*Failure semantics*).
- **Live session** and **disk-only session**: the spec's Terms (a live session has `EngineSessionStatus` in `useSessions().engine`). **Live form** and **disk form** of an event: C3's live journal events carry `seq` and ids `<app>:<launch>:<seq>:<n>`; C4's disk events carry `seq: null` and ids from the transcript's uuids. The same fact can reach `session.eventBatch` in both forms, so the graph takes one form per session (Interfaces, *The task-graph store*).
- **Live child** and **disk child**: the spec's Terms. **On disk** (a list section): agents known only from `fs.subagents`, whose status is unavailable unless the sidecar carries `stoppedByUser`.
- **Drill-in**: the Subagents tool's view of one agent inside the panel, C6's `Transcript variant: 'child'` over `ipcSource(appSessionId, agentId)` (K2). C5's `agent` main-area tab (`openTab({ kind: 'agent', appSessionId, agentId })`) renders the same transcript without a composer and is C5's route.
- **Relay**: the drill-in composer's send: one `session.steer` to the parent whose content asks the parent to `SendMessage` the child. **The three observables**: (a) the steer was accepted, (b) the parent's `SendMessage` `tool.use` row with `to` naming the child, (c) the child's transcript shows the message. **Parent round**: one parent `assistant` message containing tool uses; **child tool round**: one of the child's tool calls, the unit at which the engine delivers pending messages (SPEC 18 §18.26.2, `agent-live`).
- **Stopping**: the state between a `session.stopTask` call and the engine's terminal `task.updated`/`task.notification` for the task (the TUI's own two-phase stop, SPEC 20 §20.12.5).
- **Checklist**: the read-only view of a TaskCreate list, `fs.tasks { listId }`; **list id**: the engine's per-call resolution (SPEC 20 §20.2.2), which C3 reports as `EngineSessionStatus.taskListId`; sanitised `[^A-Za-z0-9_-] → -` before use as a path segment.
- **Log**: the seventh tool, `id: 'log'`, `menu: false`, transient (C8a's *Transient Log tabs*), one tab per path over `fs.readSpill`.
- **Agent-work client**: the one object through which the tools and the store call X2 (`fs.subagents`, `fs.workflows`, `fs.tasks`, `fs.readSpill`, `session.events`, `session.steer`, `session.stopTask` and the events), defaulting to the app's validated bridge and replaceable by the harness and the tests (C6's `…Over(client)` pattern).
- **Harness**: C8a's `#panel` page (`src/renderer/src/harness/panel/PanelHarness.tsx`) over fake sessions A and B; C8b adds a delimited block and a left-column block of its own.

### The task graph (`src/renderer/src/tools/agents/model/task-graph.ts`, pure)

```ts
export type TaskKind = 'agent' | 'workflow' | 'shell' | 'monitor' | 'other';   // local_agent, local_workflow, local_bash, /^monitor/, the rest
export type TaskStatus = 'running' | 'completed' | 'failed' | 'stopped' | 'exited' | 'unknown';
//   running: started and not ended; completed/failed/stopped: the terminal task.notification's (or subagent.finished's) status, or task.updated.patch.status with killed → stopped;
//   exited: the parent process exited while the task was running (a fact: process.exited); unknown: known only from disk, and the sidecar says nothing
export interface TaskNode {
  taskId: TaskId; kind: TaskKind; taskType: string | null; toolUseId: ToolUseId | null;
  description: string;                       // the name: task.started/subagent.started description, else the sidecar's description, else the task id
  status: TaskStatus; stopping: boolean;     // stopping: session.stopTask sent, no terminal event yet
  startedAt: string | null;                  // the start event's `at`; null when the task was only ever seen in a snapshot or on disk
  endedAt: string | null;                    // task.updated.patch.endTime as ISO, else the terminal event's `at`
  usage: { totalTokens: number; toolUses: number; durationMs: number } | null;   // subagent.progress, latest
  lastToolName: string | null; summary: string | null; reason: string | null; outputFile: string | null;
  isBackground: boolean | null;
  agent: { subagentType: string | null; spawnDepth: number | null; parentAgentId: AgentId | null; model: string | null; name: string | null; prompt: string | null; stoppedByUser: boolean | null; transcript: { path: string; size: number; mtimeMs: number } | null } | null;   // agents only
  workflow: { workflowName: string | null; progress: unknown[] | null; runId: string | null; snapshot: WorkflowSnapshot | null } | null;   // workflows only; progress is the latest whole snapshot (wire or disk)
  provenance: { wire: boolean; disk: boolean; snapshot: boolean };
}
export interface TaskGraph { tasks: Map<TaskId, TaskNode>; order: TaskId[]; byToolUse: Map<ToolUseId, TaskId> }   // order: first seen
export function emptyGraph(): TaskGraph;
export function applyTaskEvents(graph: TaskGraph, events: SessionEvent[]): TaskGraph;   // the seven task kinds plus tool.result and process.exited; every other kind ignored; returns the same object when nothing changed
export function applySnapshot(graph: TaskGraph, tasks: EngineSessionStatus['backgroundTasks']): TaskGraph;   // tasks.snapshot / status.backgroundTasks
export function mergeSidecars(graph: TaskGraph, agents: SubagentEntry[]): TaskGraph;
export function mergeRuns(graph: TaskGraph, runs: WorkflowRun[]): TaskGraph;
export function markExited(graph: TaskGraph, at: string): TaskGraph;      // every running node → exited
// selectors (memoised on the graph object)
export function agentTree(graph): AgentRow[];        // running agents, nested: children under their parentAgentId (else under byToolUse of their started event's parentToolUseId, R5), orphans at depth 0 with `nested: true`
export function doneAgents(graph): AgentRow[];       // terminal agents, newest end first; a disk child with stoppedByUser is `stopped` here
export function onDiskAgents(graph): AgentRow[];     // status unknown
export function workflows(graph): TaskNode[]; shells(graph): TaskNode[]; monitors(graph): TaskNode[];   // running first, then terminal newest first
export function counts(graph): { working: number; done: number; shells: number; workflows: number; monitors: number };
```

Reducer rules, in the order the events arrive: `subagent.started` and `task.started` create the node (or fill a snapshot-born or disk-born one), set `startedAt` to the event's `at`, `toolUseId`, `kind` from `taskType` (`agent` for `subagent.started`), and record `byToolUse`; a started event that carries a non-null `parentToolUseId` whose tool use is a known agent's sets `agent.parentAgentId` to that agent (live nesting, R5); `subagent.progress` sets `usage`, `lastToolName`, `summary` and `description`; `task.updated` applies `patch.status` (`killed` → `stopped`), `description`, `endTime` (ms → ISO) and `error` (as `reason`); `subagent.finished` and `task.notification` set the terminal `status`, `summary`, `outputFile`, `reason`, `endedAt` (if unset) and clear `stopping`; `workflow.progress` replaces `workflow.progress` with the event's `progress` array (each frame is a whole snapshot, C2's finding) and sets `workflowName`; `tasks.snapshot` (and `applySnapshot` from the status) creates unknown-start `running` nodes for ids it names that the graph lacks (`provenance.snapshot`, `startedAt: null`) and removes a node that is `stopping` and absent from the snapshot (the spec's "the card removes itself on the next snapshot"; a running node never asked to stop is left alone, since the snapshot lists background tasks only); `tool.result` whose `structured` carries `backgroundTaskId` sets that task's `outputFile` from the result text's `Output is being written to: <path>` (the engine reports the path in the Bash tool's own result, `pass2/per-task-stop-on.jsonl`; §4.3 is honoured because the path is the engine's); `process.exited` with `agentId === null` runs `markExited`. Events whose `kind` is none of these return the same graph. `mergeSidecars` adds a node per `SubagentEntry` the graph lacks (`kind: 'agent'`, `status: 'unknown'`, `provenance.disk`) and fills `agent.model`, `agent.spawnDepth`, `agent.parentAgentId`, `agent.name`, `agent.stoppedByUser`, `description` (when unset) and `agent.transcript` on every agent from its sidecar through the narrow parse below; a disk node whose sidecar says `stoppedByUser: true` reads `stopped`. `mergeRuns` matches a run to a wire workflow node by `snapshot.taskId`, else adds a disk node keyed by `runId` as its task id; a run's `snapshot.status` is a disk fact and becomes the node's status (`completed`, `failed`, `killed` → `stopped`, `running`); `snapshot.workflowProgress` fills `workflow.progress` when the wire has given none. The narrow parse of the loose sidecar: `parentAgentId`, `name` and `stoppedByUser` are read through `z.looseObject({ parentAgentId: z.string().optional(), name: z.string().optional(), stoppedByUser: z.boolean().optional() }).safeParse(meta)`, so a sidecar of another shape yields nulls and never throws (the Ask of C4 below types them at the source).

Provenance rule: a session with a status (`useSessions().engine.has(id)`) is live, and its entry takes wire events in the **live form only** (`seq !== null`), from one `session.events { appSessionId, afterSeq: entry.lastSeq, limit: null }` snapshot when the first watcher arrives (C3 rebuilds beyond its ring from the journal, so the snapshot is this launch's whole list) and then `session.eventBatch` for the session with batches at or below `lastSeq` dropped; every event whose `kind` is not one of the reducer's is discarded before it reaches the graph, whatever its `agentId` (a task frame the engine attributes to a child, `subagent.progress` for the child, is still the parent's fact about that task). A disk-only session's entry reads `fs.subagents` and `fs.workflows` and never calls `session.events` (which would start C4's follower over the whole transcript for a list that needs only the sidecars); it refreshes on `fs.subagentsChanged` (the payload carries the list) and on `fs.workflowChanged` (one `fs.workflows` re-read, trailing 250 ms). A live session reads the disk half too, merged after the wire (`mergeSidecars`, `mergeRuns`), because a resumed session's earlier children exist only in the sidecars (§4.2, `--resume` replays nothing) and a workflow's snapshot carries what the wire's progress frames do not (`status`, `startTime`, `totalTokens`). When a status first arrives for an entry that was disk (the session launched from MAWS), the wire half starts; when the status reports `process: 'exited'`, `markExited` runs and the subscriptions stay until the last watcher leaves (the wire facts are this launch's and remain true). The store never reads C6's transcript store: the two reducers see the same events and agree by construction, and a session whose transcript is not mounted still has a task graph. Cost: one `session.events` snapshot per live session per launch, then filtering batches, which the transcript already subscribes to.

### Log paging (`log/log-model.ts`)

`LOG_PAGE_BYTES = 256 KiB` (one `fs.readSpill { path, offset, length }` per page; C4's cap is 8 MiB, its default 1 MiB), `LOG_WINDOW_PAGES = 4` (at most 1 MiB in the DOM: the window `{ from, to }` of page indices rendered as one `<pre>` per page; `Load more` at the end extends `to` and drops `from` when the window is full; `Show earlier` at the top does the reverse; a page leaving the window leaves `pages` too). The first read is page 0 with `length: LOG_PAGE_BYTES`; `bytes` from its answer is the size in the header, re-read by `Refresh` (which re-requests the last page in the window, so a growing output file shows its new tail). A page boundary can split a UTF-8 sequence or a line; the tool joins adjacent pages' text before rendering the window so a boundary is invisible, and the `<pre>` is `white-space: pre-wrap` with the transcript's mono font. A refusal (`path outside the engine store`, `spill not found`) renders `Refused: <message>` with the path in mono and no retry loop; a path under the engine's temp root reads through the root C4 landed in M3.

Decisions local to M1: the probes run first and their verdicts are written before any tool code, so a discarded relay changes M2's plan before it starts; the reducer is a family of pure functions over an immutable-by-convention graph that returns the same object when nothing changed (so React selectors over it are cheap and the tests can assert identity), not a class;
