## Purpose

After C9, the owner opens a session's right panel, adds a Terminal tab, and gets a real login shell in that session's worktree: the prompt shows the worktree path, `claude` and `codex` run in it with their full-screen interfaces drawn correctly (box drawing, Korean and emoji text, IME composition, links that open in the browser), output from `cat` of a large file never freezes the app, and the shell keeps running, with its scrollback, while the owner switches to the Review tab, to another session, or reloads the renderer. Pinning the tab carries that shell across sessions; when the shell belongs to a different worktree than the session now shown, the tab says so and offers a new terminal instead of pretending it moved. If the terminal service crashes, the tab says "Terminal lost" and offers a new one once the service is back. A `claude --bg` job attaches by opening a terminal with a typed command (C10 wires the affordance; C9 provides the call). None of this exists before C9: C1 left a PTY host that spawns one `/bin/sh`, echoes, and knows nothing of rendering, flow control, environment, or lifecycle.

The first milestone is the spike the charter demands (§7.2, C9 G1): both renderer candidates behind one adapter under the real Claude Code and Codex terminal interfaces, with a recorded verdict. Research at authoring (Surprises & Discoveries) makes the expected verdict xterm.js 6 with the WebGL addon; the spike exists to observe it, not to assume it.

## Terms

- **PTY** (pseudo-terminal): the kernel object a shell talks to as if it were a terminal. node-pty (`src/pty-host/`) creates one per terminal; the app writes keystrokes to it and reads the bytes the shell and its programs print.
- **PTY host**: the utility process `src/pty-host/index.ts` from C1 (charter §4.1). It owns every pty; the renderer only ever sees `pty.*` commands and events.
- **Renderer adapter**: the interface `TerminalRenderer` in `src/renderer/src/terminal/renderer.ts` that hides which terminal-emulator library draws the terminal. Two implementations exist during the spike (`xterm.ts`, `ghostty.ts`); the product ships one.
- **xterm.js**: the terminal-emulator library `@xterm/xterm` (a TypeScript VT parser plus a DOM renderer, with a WebGL renderer as an addon). **ghostty-web**: the `ghostty-web` package, Ghostty's terminal core compiled to WebAssembly with a Canvas 2D renderer written in TypeScript.
- **WebGL context**: the GPU drawing handle a `<canvas>` gets from `getContext('webgl2')`. Chromium keeps at most 16 live per renderer process and evicts the oldest beyond that; a lost context fires `webglcontextlost`.
- **Alternate screen**: the second screen buffer full-screen programs switch to (mode 1049) so that leaving them restores the shell's screen and scrollback.
- **Synchronized output**: DEC private mode 2026; a program brackets a frame in `CSI ? 2026 h` … `CSI ? 2026 l` so the terminal draws it in one go instead of tearing.
- **Grapheme cluster**: what a reader sees as one character (a Hangul syllable, an emoji with skin tone and ZWJ joins). Terminals must allocate the same number of cells for it as the program assumed, or box drawing drifts.
- **Flow control**: keeping a fast producer (a program printing) from outrunning a slow consumer (the renderer parsing). Here: the host counts bytes it emitted minus bytes the renderer acknowledged, and pauses the pty (`pty.pause()`, which stops reading so the kernel buffer fills and the program blocks on `write`) above a high watermark, resuming below a low one.
- **Offset**: the byte position of a chunk in a pty's output stream since spawn. Every `pty.data` event carries the offset of its first byte; acknowledgements name an offset; attach replies name the offset at which live events resume.
- **Ring buffer**: the last N bytes of a pty's output kept in the host so a renderer that reconnects (after a reload) can be shown what it missed.
- **Terminal handle**: the renderer-side object (`src/renderer/src/terminal/registry.ts`) that owns one renderer instance, its container `<div>`, and the identity of its pty; it outlives the React tree that shows it, which is how a terminal keeps its state across tab switches.
- **Panel tool**: what X5 calls a right-panel tab type. C8 owns the host; C9 declares the Terminal tool against the interface assumed in Interfaces (`src/renderer/src/panel/tool.ts`).
- **Harness**: a second renderer page, `src/renderer/harness.html`, loaded instead of the app when `MAWS_HARNESS=1`. `#probe` is the spike and performance page (both adapters, workloads, metrics); `#panel` is a fake panel host that mounts the Terminal tool with two fake sessions.
- **TUI**: a full-screen terminal user interface; here the interfaces of `claude` (Ink-based) and `codex` (ratatui-based).
- **XTVERSION**: the query `CSI > 0 q` a program sends to learn the terminal's name and version. Claude Code 2.1.283 sends it and only asks about synchronized output if it is answered (Surprises & Discoveries).
- **Kitty keyboard protocol**: an opt-in key encoding (`CSI > flags u`) that disambiguates modifiers; both TUIs request it and fall back to legacy encoding when the terminal does not answer.

## Residue decisions (C9, 2026-09-28)

What the design left to the child, settled here, formatted for the charter's C9 section. Grades: binding where the design binds the outcome or where siblings depend on the shape; advisory where a later child may overturn with a dated line in the charter. Milestones below point at a decision by its italic title.

- *Renderer*: xterm.js `@xterm/xterm` 6.0.0 with `@xterm/addon-webgl` 0.19.0 is the expected primary, with xterm.js's own DOM renderer as the fallback and ghostty-web discarded; the spike (M1) observes and records this rather than assuming it. Evidence at authoring: `ghostty-web`'s last stable release is 0.4.0 (2025-12-09) with prereleases ending 2026-06-28 and no push since 2026-07-02; on 0.4.0 Korean IME is broken (coder/ghostty-web #119, open; the owner types Korean), `getHyperlinkUri()` always returns null (#137), a WebAssembly heap-corruption fix (commit bec9e16) is unreleased, synchronized output is never honoured by its renderer, the Kitty keyboard encoder is not wired, the WASM ships as a `data:` URI that a strict CSP blocks (#188), and its `write` callback fires on the next animation frame with no backpressure design; those are four charter list items failed on paper (IME, hyperlinks, synchronized output, sustained output) before any measurement. xterm.js 6.0.0 (2025-12-22) supports mode 2026, OSC 8 through `linkHandler`, grapheme clustering through `@xterm/addon-unicode-graphemes` 0.4.0, IME, and `write(data, callback)` flow control. Ghostty's core is measurably faster (libghostty-vt versus xterm.js, 2 to 7× on throughput per xtermjs/xterm.js #5686), which is why the adapter keeps a `RendererKind` seam and the probe page stays: a maintained libghostty package (ghostty-org's signed `ghostty-vt.wasm` has no renderer or npm package yet) re-runs the same spike without touching the tool. Kitty keyboard protocol is deferred: it exists only in xterm.js 6.1 betas, which also drop single-character IME commits under it (#6112); both TUIs fall back to legacy keys. Alternative rejected: shipping ghostty-web `0.4.0-next.20.g1858a59` (the registry's `next` tag, what Coder's Mux pins) for its speed; it carries the same IME and design gaps and no release process. Advisory (§4.7), with the spike's switch rule binding (G1).
- *WebGL policy*: a terminal holds a WebGL context only while visible (mounted and its tab selected); hiding disposes the WebGL addon, showing reloads it, so contexts in flight equal visible terminals (one, two under a split) against Chromium's cap of 16 per renderer process; a budget of 8 concurrent WebGL terminals is enforced in the registry, the rest draw with the DOM renderer. On `webglcontextlost` the addon waits three seconds for a restore, then fires `onContextLoss`; the adapter disposes it, continues on the DOM renderer, and retries WebGL on the next show. The same path covers sleep and resume and is exercised deterministically through the `WEBGL_lose_context` extension in the end-to-end test. Alternative rejected: raising `--max-active-webgl-contexts`, which moves the cliff instead of removing it. Advisory.
- *Scrollback and memory*: 10,000 lines per terminal, a constant `SCROLLBACK_LINES` in `src/renderer/src/terminal/constants.ts`, no settings surface in P0 (C11 may lift it into settings). Bound: xterm.js stores 12 bytes per cell, so a 10,000-line buffer costs 12 × cols × 10,000 bytes at most, 6 MB at the panel's 50 columns and 24 MB at 200; the host additionally keeps, per pty, a 512 KiB ring buffer of raw output and the latest checkpoint the renderer sent (Residue *Reattach checkpoint*), a string the size of the serialised scrollback, at most a few MB. Alternative rejected: xterm.js's 1,000 default, too short for `pnpm test` output. Advisory.
- *PTY stream and flow control*: output crosses X2 as binary (`Uint8Array`) chunks, one `pty.data` event per node-pty read (observed ≤ 64 KiB), each stamped with its stream `offset`; keystrokes stay strings (`pty.write`). Backpressure is credit by offset: the renderer acknowledges the offset it has parsed (`pty.ack`), coalesced to one ack per 32 KiB or 16 ms; the host pauses the pty when emitted-minus-acknowledged bytes reach 256 KiB and resumes at 64 KiB (within xterm.js's flow-control guide, which caps the high mark at 500 KB and drops data past a 50 MB buffer if nobody pauses the producer). A hidden terminal acknowledges at most 1 MiB/s so a runaway `cat` in a background tab blocks its producer instead of starving the UI thread. `pty.attach` returns the latest checkpoint, the ring's bytes from that checkpoint's offset (or the whole ring when none reaches it) and the offset at which live events continue; the renderer drops any event below that offset. The ring is twice the high watermark so that while the pty is paused it always reaches back to the last acknowledged offset, and a checkpoint is never taken below that offset; that invariant is what makes reconnection after a renderer reload exact (Residue *Reattach checkpoint*). Binary because both candidate renderers take bytes, the renderer's decoder then sees exactly what the program wrote, and the host can split on byte counts without caring about character boundaries. Alternative rejected: strings with host-side decoding, which is what C1 shipped and works, but forces two decoders and per-chunk string copies on the hot path. Binding on the X2 shape (siblings validate these entries), advisory on the numbers.
- *Terminal environment*: the shell is the user's login shell (`$SHELL`, else `/bin/zsh`) started with `-l`, so PATH and exports come from the owner's own dotfiles exactly as in Terminal.app; the seed environment is the base (X6's captured login-shell environment, `captureShellEnvironment()` from C3's `src/shared/host/shell-env.ts`, run once at PTY-host start by `baseEnvironment()` in `src/pty-host/env.ts`, with the host's `process.env` as the fallback when the capture fails) minus the parent-session exclusions of §4.1, plus `TERM=xterm-256color`, `COLORTERM=truecolor`, `TERM_PROGRAM=MAWS`, `TERM_PROGRAM_VERSION=<app version>`, `CLAUDE_CODE_FORCE_SYNC_OUTPUT=1` (Claude Code 2.1.283 enables synchronized output only if XTVERSION is answered, which xterm.js 6.0.0 does not, or if this variable or a `TERM_PROGRAM` allowlist says so), and `LC_CTYPE=UTF-8` when no `LANG`, `LC_ALL` or `LC_CTYPE` is present (a Dock-launched app has none; this makes the tty UTF-8 without choosing a language). No gateway variables, no `CLAUDE_CODE_FORK_SUBAGENT`: a terminal is the owner's shell, not an engine launch. Alternative rejected: reusing X6's engine allowlist verbatim, which would route a hand-started `claude` through app-chosen settings instead of the owner's shell. Binding on the exclusions and the no-injection rule (D-12 interop), advisory on the additions.
- *Unicode width*: the terminal must allocate cells the way the program computed them. xterm.js runs with `@xterm/addon-unicode-graphemes` active so ZWJ emoji sequences and Hangul are one cluster of two cells, matching Ink's `string-width` and ratatui's `unicode-width`; the spike verifies with a cursor-position report (`CSI 6 n`) after printing fixture strings and compares the reported column with the expected width. Advisory on mechanism; the CJK-and-emoji item is binding (G1).
- *Search*: not in P0. Nothing in §5.6 asks for it, neither TUI needs it, and Codex's own terminal ships Clipboard, Fit and WebLinks only; `@xterm/addon-search` drops in later behind an adapter method. Advisory.
- *Splits*: no split inside a Terminal tab. The panel is 380 px wide; a second terminal is a second Terminal tab (`multiInstance: true`, titled "Terminal 2"), which also gives "multiple ptys per session" without layout state. A terminal in the main area or a bottom dock is P1 (§3). Advisory.
- *Persistence*: a terminal's renderer instance and container `<div>` live in the terminal registry, not in React state; the tool's render mounts the existing container and detaches it on unmount, so switching tabs, closing the panel or switching sessions under a pinned tab never re-creates the emulator or loses scrollback, and a running process is untouched. A pinned Terminal tab keeps its shells: it does not move to the new session's cwd; when the shell's spawn cwd differs from the shown session's directory (or its worktree path), the tool shows the worktree warning with "New terminal here". After a renderer reload the registry re-adopts live ptys from `pty.list` by `(appSessionId, label)` and restores each from its checkpoint and the ring buffer (Residue *Reattach checkpoint*); after an app restart there are none (hosts die with the app, D-16). Binding on "pinned keeps its shells and warns" (§5.6, D-10), advisory on mechanism.
- *Reattach checkpoint*: a raw byte tail cannot restore a terminal: the modes a program set before the tail (bracketed paste, the alternate screen, application cursor keys, mouse tracking) are gone, and the tail's first byte can split a UTF-8 sequence or an escape sequence (reproduced on xterm.js 6.0.0). So a reattach has two sources: a **checkpoint**, the emulator's own serialised state (xterm: `@xterm/addon-serialize` 0.14.0's `serialize()`, an escape-sequence string that rebuilds the screen, the scrollback, cursor position, text attributes, the alternate screen and the persistent modes DECCKM, DECNKM, bracketed paste, insert, origin, wraparound, reverse wraparound, focus reporting and mouse tracking; it does not carry cursor visibility, the window title or the transient synchronized-output mode) stamped with the stream offset it reflects, sent to the host as `pty.checkpoint` and kept there per pty; and the ring buffer's bytes after that offset. The addon does not serialise everything it claims to, nor any parser or decoder continuation (a real `@xterm/addon-serialize` 0.14.0 plus `@xterm/headless` 6.0.0 round trip, re-review round 2): a checkpoint taken after `ESC[31` followed by the replay `mRED` prints `mRED`, one taken inside the UTF-8 bytes of `한` loses the character, and after `?1000h` `?1006h` the restored terminal tracks the mouse with the default encoding instead of SGR, so an unchanged TUI stops understanding its mouse reports. Checkpoints are therefore **boundary-safe**: the registry takes one only at a parser-quiescent point, where the parser is in its ground state with no escape sequence and no partial UTF-8 sequence pending, which it knows from a byte-level stream tracker run over every chunk it writes (`trackStream` in `replay.ts`, pure, pinned against `@xterm/headless`); a checkpoint due while the stream is mid-sequence waits for the next chunk that ends on a boundary, and at `pagehide`, which cannot wait, none is sent and the host keeps the previous one. The same tracker records the private modes the addon does not restore faithfully, mouse tracking and encoding (`?1000`, `?1002`, `?1003`, `?1006`) and focus reporting (`?1004`), plus any other the round-trip test finds missing (a full reset `ESC c` or soft reset `CSI ! p` clears them), and the checkpoint state is `serialize()` followed by explicit DECSET or DECRST sequences for their current values. The registry checkpoints every live handle on `pagehide` (a reload or a closing window, synchronous, the reply ignored) and a dirty handle 500 ms after its last parsed byte (quiescence), never on a byte count: serialising 10,000 lines costs tens of milliseconds and must not run per chunk during a flood. Reconnect contract: **exact** when the ring reaches back to a boundary-safe checkpoint's offset (`replayFrom === checkpoint.offset`), which the ring-size invariant of *PTY stream and flow control* guarantees after a `pagehide` checkpoint: the renderer writes the checkpoint, then the replay, and nothing is reset or redrawn; **lossy** whenever exactness cannot be established (no checkpoint yet, no boundary-safe checkpoint the ring still reaches, a renderer that cannot serialise, or a renderer crash mid-flood): the renderer resets the emulator, writes the tail from the byte after its first line feed (a CSI or ESC sequence never contains one and it is never a UTF-8 continuation byte, so what follows is whole), shows "Reconnected; earlier output was not kept" in the tab's bar, and nudges a full-screen program to repaint by resizing to `rows − 1` then `rows`. `TerminalInfo.reconnect` records which path ran, and the harness's debug strip shows it. Alternative rejected: a byte-count checkpoint cadence, which makes the exact path likelier after a crash at the cost of a serialise every few hundred KiB of output, exactly when the UI thread is busiest; and a host-side terminal emulator to produce the state, a second parser to keep in step with the renderer's. Binding on the two-path contract, boundary safety with the explicitly re-applied modes, and the user-visible notice (it defines what "keeps running across a reload" promises), advisory on the mechanism.
- *Keyboard*: with a terminal focused, every key without ⌘ goes to the pty (Esc, ⇧Tab, Tab, ⌃C, ⌃D, ⌃L, ⌃R, arrows, ⌥-chords with `macOptionIsMeta: true`), except ⌃Tab and ⌃⇧Tab, which stay the app's tab cycle; every ⌘ chord goes to the app, except ⌘C (copy selection; nothing when there is none), ⌘V (paste), ⌘A (select all), which the terminal handles. ⌘K remains the command palette (§5.8): clearing a terminal is ⌃L or the tab's context menu. This is the focused-pane rule of §5.7 applied to a terminal: the app's Enter/Esc/⇧Tab meanings belong to the composer and request card, which are not focused. Implemented as one key filter installed through the adapter, plus a contract with C5's window-capture dispatcher (`src/renderer/src/keymap/dispatcher.ts`), which runs before xterm's own `keydown` listener on its helper textarea and would otherwise answer a pending request with the Enter a shell command needed: the registry stamps every terminal container with `data-key-sink="terminal"`, and C5's dispatcher refuses pane-scoped dispatch (`request.accept` on Enter, `request.decline` on Escape, `tab.next`/`tab.previous` on ⌃Tab) for a keydown inside a `[data-key-sink]` element or on any text-entry element (xterm's helper textarea is one, whatever its content), and delivers composer-scoped actions (`composer.cycleMode` on ⇧Tab, `composer.send` on ⌘Enter) only inside `data-key-sink="composer"`. The chords the app must keep from a terminal survive by construction or by forwarding: menu-sink ⌘ chords (⌘K, ⌘W, ⌘1..9, ⌘⇧J, ⌘B, ⌘⇧B, ⌘N, ⌘\) reach main through the application menu before the page sees them; ⌃Tab and ⌃⇧Tab are renderer-sink and pane-scoped, so the terminal forwards them itself, the key filter answering `false` and the registry calling C5's `runAction('tab.next' | 'tab.previous')`, the one entry point buttons and the palette already use. `macOptionClickForcesSelection: true` so ⌥-drag selects while a TUI tracks the mouse. Kitty keyboard protocol off (see *Renderer*). Binding on the rule and on the marker contract with C5 (wave-2 ledger), advisory on the chord list.
- *Copy, paste and links*: ⌘C copies the selection as plain text; ⌘V pastes, bracketed when the program asked for it; the tab's context menu offers Copy, Paste, Select all, Clear. OSC 8 links and detected URLs open on ⌘-click through `pty.openLink` (owner main; its handler calls C5's `openExternalUrl` in `src/main/open-external.ts`, the one scheme-checked `shell.openExternal`: `http`, `https`, `mailto`; anything else is logged and answered `opened: false`). `file:` links and bare paths that should open a viewer tab are P1 (they need C8's Files tool). OSC 52 clipboard writes from programs are not honoured. Advisory.
- *Fonts and palette*: 21 new X7 token names, added to `mockups/tokens.css`, `tokens-light.css` and `src/renderer/src/styles/tokens.css`: `--term-bg` (light: `var(--bg-raised)`), `--term-fg` (`var(--fg)`), `--term-cursor`, `--term-cursor-fg`, `--term-selection`, and `--term-ansi-<name>` and `--term-ansi-bright-<name>` for `black red green yellow blue magenta cyan white`. Values are advisory (light: a VS Code-light-derived readable set on a white ground; dark: the same family on `#1a1a1a`). The adapter reads them with `getComputedStyle(document.documentElement)` and rebuilds the theme on every `settings.changed`, so the terminal recolours with the app and no component holds a colour literal. Font: `--font-mono` and `--text-code`, line height 1.2. Names accepted into X7 (wave-2 ledger, ruling 6) and binding, values advisory.
- *Lifecycle and close*: a terminal is `starting`, `running`, `exited` (with code and signal) or `lost` (the host crashed or restarted: main's supervisor emits `pty.exit` with null code and null signal for every pty it knew, C1 M4). `exited` and `lost` keep the dead screen visible and show a bar: "Process exited (code N)" or "Terminal lost, the terminal service restarted", with "New terminal" (enabled once `pty.hostState` is `ready`, same cwd) and "Close". Closing a `running` terminal asks `pty.foreground`; when a program other than the shell is in the foreground the tool shows an inline bar "A command is running: `<name>`. Close anyway?" with "Close" and "Keep" (no dialog dependency), otherwise closes at once; closing kills the pty with SIGHUP. The tab title follows the program's OSC 0/2 title, falling back to the foreground process name. Binding on the behaviours G2 names, advisory on copy.
- *Terminal tool and X5*: the tool is `src/renderer/src/tools/terminal/index.ts` exporting `terminalTool: PanelTool<TerminalTabState>` and `openTerminal({ appSessionId, cwd, command? })` for C10's attach affordance (the command is written to the shell followed by a newline; the tty buffers it until the shell reads). ### PTY host internals (`src/pty-host/`)

`table.ts` holds `PtyEntry { info: PtyInfo; pty: IPty; ring: RingBuffer(512 KiB); checkpoint: { offset: number; state: string } | null; acked: number; flow: 'flowing' | 'paused'; initialCommand?: string }`. The ring is `2 × HIGH` on purpose: while the pty is paused, `total − acked ≤ HIGH` plus the few chunks node-pty had already read, so the ring always reaches back to `acked`, and a checkpoint's offset is never below `acked` (the renderer parses before it acknowledges), which is the guarantee behind the exact reattach of Residue *Reattach checkpoint*. The host refuses a second live pty under the same `(appSessionId, label)` and removes a dead entry under that key on respawn, so `pty.list` never shows two entries for one tab (M2). node-pty on macOS delivers at most 1 KiB per read (M2 Surprises), so the host coalesces consecutive reads per pty into one `pty.data` event over a 5 ms leading-edge window (a read after 5 ms of quiet flushes at once, reads inside the window wait for it to close, 64 KiB pending flushes immediately; `setImmediate` coalesced nothing because a flood delivers one small read per event-loop turn, M2), and always before that pty's `pty.exit` and before a `pty.attach` reply is computed; the transition table below sees flushed events only. All state changes happen on the host's single thread in the order messages arrive, which is the linearization; the transition table is the contract M2's tests pin:

| State | Event | Guard | Action | Next |
|---|---|---|---|---|
| flowing | data(n) | `total + n − acked ≥ HIGH` (256 KiB) | append ring; emit `pty.data{offset: total}`; `total += n`; `pty.pause()` | paused |
| flowing | data(n) | otherwise | append ring; emit; `total += n` | flowing |
| paused | data(n) | (node-pty may deliver chunks already read) | append ring; emit; `total += n` | paused |
| paused | ack(o) | `total − max(acked, o) ≤ LOW` (64 KiB) | `acked = max(acked, o)`; `pty.resume()` | flowing |
| paused | ack(o) | otherwise | `acked = max(acked, o)` | paused |
| flowing | ack(o) | | `acked = max(acked, o)` | flowing |
| any | checkpoint(o, s) | `o ≤ total` (else clamped and logged) | `checkpoint = { offset: o, state: s }` (the previous one is dropped) | same |
| any | attach | | `acked = total`; resume if paused; `from = max(checkpoint?.offset ?? 0, ring.start)`; reply `{ info, checkpoint, replay: ring.since(from), replayFrom: from, nextOffset: total }` | flowing |
| any | resize(c, r) | alive | `pty.resize`; update info | same |
| any | write(s) | alive | `pty.write(s)` | same |
| any | exit(code, sig) | | `info.alive = false; info.exit = …`; emit `pty.exit` | dead |
| dead | kill | | remove entry | — |
| dead | (1 h since exit) | | remove entry | — |

An ack with an offset above `total` is clamped and logged (a renderer bug, not a crash). `pty.write` and `pty.resize` on a dead pty answer `{ ok: false, error: { code: 'internal', message: 'pty exited' } }`; on an unknown id, C1's `unknown pty`. Node-pty is spawned with `encoding: null` (raw `Buffer`s, forwarded as `Uint8Array` views without copying), which leaves the tty without `IUTF8` (node-pty sets it only for `encoding: 'utf8'`), so every pty starts through `/bin/sh -c 'stty iutf8 2>/dev/null; exec "$0" "$@"' <shell> <args>`: the exec keeps the pid and `$0`, and canonical-mode programs erase a whole Korean character on Backspace as in Terminal.app (M2); `handleFlowControl: false` (the host pauses the pty itself; the in-band XOFF/XON matching is for programs, not for us), `name: 'xterm-256color'`. `initialCommand` is written immediately after spawn (the tty line discipline buffers it until the shell reads; M2's test proves it with zsh and bash).

`env.ts`: `baseEnvironment(): Promise<NodeJS.ProcessEnv>` resolves to X6's captured login-shell environment (`captureShellEnvironment()` from `src/shared/host/shell-env.ts`, C3's, started once at host load; the capture runs the owner's interactive login shell, 645 ms measured and up to 5 s, so it is awaited by the first `pty.spawn` rather than run synchronously at load, M2) and falls back to `process.env` when the capture fails; `terminalEnvironment(base, { appVersion }): Record<string, string>` applies Residue *Terminal environment*: the exclusion list `PARENT_SESSION_VARIABLES` (exported, tested), the additions, the locale rule, and drops the capture shell's own `SHLVL`, `OLDPWD` and `_` so a terminal shell starts at level 1 as in Terminal.app (M2); it never adds `ANTHROPIC_*`, `ENABLE_TOOL_SEARCH` or `CLAUDE_CODE_FORK_SUBAGENT`.

`foreground.ts`: `foregroundOf(entry): { process: string | null; busy: boolean }` reads node-pty's `pty.process` (the foreground process name on macOS) and decides `busy` by process group: `ps -o tpgid= -p <shell pid>` differing from the shell's pid (the shell leads its own group at a prompt); the name rule `process !== basename(entry.info.shell)` is only the fallback when `ps` fails, because macOS's `/bin/sh` re-executes as `bash` and would read busy at an idle prompt (M2).

### Terminal registry and store (`src/renderer/src/terminal/registry.ts`, `src/renderer/src/stores/terminals.ts`)


The registry is the only subscriber of `pty.data`, subscribed at construction before any `pty.spawn` or `pty.attach` leaves the page; it dispatches by `ptyId`. A chunk for a pty no handle has claimed yet is held in a per-pty **pending list** (bounded to the ring's size, oldest dropped, because anything that old is in the replay), so nothing that the host emits between its snapshot and the handle's readiness is lost; a `pty.exit` for an unclaimed pty discards its list. The claim always precedes the request (M3): `adopt` creates each handle and claims its `ptyId` in the dispatch map, pending list armed, before it sends `pty.attach`; `open`, whose `ptyId` the host assigns, marks its handle awaiting a pty before it sends `pty.spawn`, so the new pty's first chunks wait in the pending list the dispatcher keeps for any unclaimed id, and the reply binds that list to the handle and drains it from offset 0. When `pty.attach` resolves: exact path (`replayFrom === checkpoint.offset`) writes `checkpoint.state` then `replay`; lossy path calls `renderer.reset()`, writes `alignReplay(replay)` (`replay.ts`: the bytes after the first line feed, or nothing) and sets `reconnect: 'lossy'`; then `nextOffset = attach.nextOffset` and the pending list drains in arrival order, dropping chunks with `offset < nextOffset` (the replay covered them; a chunk never straddles `nextOffset`, because the host stamps offsets and computes the reply on one thread) and writing the rest. After that, a claimed handle's chunk with `offset < nextOffset` is dropped the same way; every other chunk goes to `renderer.write(data, () => ackUpTo(offset + data.byteLength))`, and acks coalesce (Residue *PTY stream and flow control*); hidden handles ack on a 250 ms tick, capped at 256 KiB per tick. Checkpoints (Residue *Reattach checkpoint*): `pagehide` on `window` serialises every live handle whose renderer can and whose stream tracker is at a boundary, and sends `pty.checkpoint` with the offset of its last parsed byte and the state `serialize()` plus the explicit mode sequences; a handle with bytes parsed since its last checkpoint is checkpointed 500 ms after the last one (`CHECKPOINT_QUIESCENCE_MS`), or at the first chunk after that which ends on a boundary; `setCheckpoints(false)` is the test hook that disables both. The key filter from `keys.ts` is installed on every renderer; the two ⌃Tab chords it classifies as the app's are forwarded through C5's `runAction('tab.next' | 'tab.previous')` (`src/renderer/src/keymap/actions-runtime.ts`), and every container is created with `data-key-sink="terminal"` (Residue *Keyboard*). `settings.changed` rebuilds the theme through `theme.ts` and pushes it to every handle. `pty.hostState` transitions to `crashed` or `restarting` mark every live handle `lost` (the supervisor's `pty.exit` events arrive too; both paths converge). The Zustand store holds `TerminalInfo[]` only; handles are never in React state.

### X5 — the panel tool interface C9 assumes (`src/renderer/src/panel/tool.ts`)

The charter's list (id, title, icon, pinnable, per-session state factory, render) is extended by `multiInstance`, `beforeClose`, `dispose` and the context's session record.

```ts
export interface PanelToolInit { appSessionId: AppSessionId; session: SessionRecord | null; instanceId: string }
export interface PanelToolContext {
  appSessionId: AppSessionId;         // the session the panel currently shows; changes under a pinned tab
  session: SessionRecord | null;      // its X1 record: `directory` and `worktree.path` feed the worktree warning
  pinned: boolean;
  visible: boolean;                   // this tab is selected and the panel is open
  focusRequest: number;               // increments when the host wants the tool to take focus (tab selected, ⌘⇧B)
  setTitle(suffix: string | null): void;   // "Terminal · claude"
  close(): void;                      // host runs beforeClose, then disposes
}
export interface PanelTool<S> {
  id: string; title: string; icon: ComponentType<{ className?: string }>;
  pinnable: boolean; multiInstance: boolean;
  createState(init: PanelToolInit): S;          // once per tab instance; kept across visibility, panel close and session switches under a pin
  beforeClose(state: S): Promise<boolean>;      // false vetoes; the tool shows its own inline confirmation and calls ctx.close() when the user confirms
  dispose(state: S): void;
  render: ComponentType<{ state: S; ctx: PanelToolContext }>;
}
```

### The Terminal tool (`src/renderer/src/tools/terminal/`)

`terminalTool: PanelTool<TerminalTabState>` with `id: 'terminal'`, `title: 'Terminal'`, `pinnable: true`, `multiInstance: true`; `TerminalTabState = { terminalId: TerminalId; confirmClose: boolean }`; `createState` calls `terminals.open({ appSessionId, label: instanceId, cwd: session.worktree?.path ?? session.directory })` (the harness supplies fake records; C8 supplies real ones); `render` is `TerminalView`: mounts the container into a full-height flex box, shows the status bars of Residue *Lifecycle and close*, the worktree warning when `handle.info.cwd` differs from the context session's `worktree?.path ?? directory` ("This terminal is in `<cwd>`; the session now runs in `<dir>`." with "New terminal here", which opens a second instance in the new directory through the host's "+" path or, absent a host, the registry directly), the context menu, and sets the tab title from `info.title`. `beforeClose` resolves `!busy` from `terminals.foreground`, setting `confirmClose` when busy. `openTerminal({ appSessionId, cwd, command })` is what C10 calls for "attach in a terminal tab": it asks the host to add a Terminal tab (`panelHost.addTool('terminal', init)` in C8's API, the harness's equivalent until then) with the command in its init.

- Observation: ghostty-web is not a viable primary as of authoring, on paper, before the spike runs: last stable 0.4.0 (2025-12-09), prereleases to `0.4.0-next.20.g1858a59` (2026-06-28; the registry's `next` tag, every prerelease carries its commit hash and the bare `0.4.0-next.20` is a 404), no push since 2026-07-02, 62 open issues; on 0.4.0 Korean IME fails (#119), OSC 8 `getHyperlinkUri()` returns null (#137), a WASM heap-corruption fix (bec9e16) is unreleased, synchronized output is never honoured by its renderer, the Kitty encoder is unwired, WASM ships as a `data:` URI that a strict CSP blocks (#188), and `write`'s callback fires on the next frame with no backpressure.
  Evidence: research pass 2026-09-28 against npm metadata, the repository and the 0.4.0 tarball (`ghostty-vt.wasm` 423 KB, `ghostty-web.js` 682 KB with the WASM inlined); issue numbers as cited. The spike still runs it, because G1 binds and the observed failure is the record.
- Observation: xterm.js 6.0.0 (2025-12-22) supports mode 2026 (#5453, one-second safety timeout) and OSC 8, but answers XTVERSION and offers the Kitty keyboard protocol only in the 6.1 betas (through `6.1.0-beta.304`, 2026-08-30), where Kitty mode drops single-character IME commits (#6112).
