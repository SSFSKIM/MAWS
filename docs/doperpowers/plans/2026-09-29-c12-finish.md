## Purpose

C12 makes P0 a daily driver and hands the owner a sitting that can close it. After C12:

- **Many sessions stay cheap.** MAWS keeps every session live that memory allows. When the sum of the engine process trees passes a budget (25% of physical memory by default, 8 GB on the owner's 32 GB Mac), it releases the least recently used idle session that holds nothing the owner could lose and has been quiet for a sample period. A released session reads idle in the sidebar and on the Overview with a quiet "released" mark, raises no notification and no Needs-you item, and Session info says when and why. Typing in it and pressing Send resumes it through C10's resume path, with its session grants re-applied, in about a second. When the budget is exceeded and every live session holds work, nothing is stopped: one app-wide banner says so and offers each session's stop behind C10's disclosure of what would end.
- **The engine cannot vanish under MAWS.** The installer keeps five versions and the pin (2.1.283) is already the third oldest (grounding §0 item 4). MAWS copies the pinned binary into its own `userData` at pin time and launches from the copy, with a checksum recorded; a missing or altered copy is a clear refusal, made by main before any launch, that names the fix.
- **Quitting never ends work silently.** The quit question counts sessions mid-turn, sessions running background tasks or workflows, and terminals running a command, and offers "Quit when idle". The same question, worded "Restart to update" and "Restart when idle", is ready for the updater that P1 brings.
- **An owner-only build exists.** `pnpm build:app` produces `dist/mac-arm64/MAWS.app` from source, development-signed when the owner names an identity in `MAWS_SIGN_IDENTITY`, unsigned otherwise. Signing, notarization and the updater are written below as deferred P1 milestones with their preconditions.
- **The residue is swept.** A "Worktrees…" dialog on the project menu is the lasting entry point to every worktree of a repository. The launch environment mirrors the owner's terminal after a probe. A placeholder waits for the split-pane items the owner names after the sitting.
- **The sitting is ready.** Agents pre-run every §10 item they can under a scratch config home through Playwright over the owner build and commit an evidence pack. The owner gets a numbered script for the items only the real home or human hands can observe, and the architect gets a recomposition checklist against §10.

What C12 does not do: the prewarmed spare (P1, D2); a user-facing spend cap (D3); signing, notarization, DMG, ZIP, the updater or a feed (P1, D7); re-pinning the engine (after P0, D6); the keyboard map editor (C11's); the title defect, the composer's stale "Arrives with" reasons and the Workspace gear, the `highlight.js` override check, and the other debt-wave-4 rows (the architect's wave 4, which lands on master before C12's executor is dispatched; the review rulings (1)); split-pane polish beyond what the owner names after the sitting (D11); the owner's sitting itself, C8's and the charter's recomposition, the scale review and §20 (the architect's closing act, §12 C12's Cut line).

## Terms

- **Tree**: an engine process and every descendant, measured as the sum of their resident set sizes by C3's sampler (one `ps -axo pid=,ppid=,rss=` every 10 s, `src/engine-host/process-table.ts:14,31-61`), reported as `EngineSessionStatus.memory.treeRssKiB`. Shared pages are counted once per process, so the sum overstates what the machine loses; the grounding measured one idle owner-settings tree at 418,688 KiB alone and three together at about 270 MB each (grounding §1.2). The budget uses the sum as measured, which errs toward releasing early.
- **Budget**: the limit on the sum of the trees of every live engine process MAWS owns that is not already exiting. Default: 25% of physical memory (`os.totalmem()`), 8 GiB on the owner's Mac; a setting overrides it.
- **Hard reason**: something a process holds that an exit would lose or interrupt: an open turn (any origin), host-side work in flight without an open turn (`busy`: a message written but not yet started, a `!` command still running, a held clear-and-implement), background tasks or workflows, a pending request (a broker item, or a clear-and-implement plan kept for retry), queued messages (paused or not), a held peer message, and a listed stateful MCP server that is connected or still connecting. Session grants are not a hard reason, because the snapshot re-applies on resume.
- **Stateful server**: an MCP server name the owner lists in Settings › Engine because the server keeps state that dies with its process. Names are matched exactly as `system/init.mcp_servers[].name` reports them (for example `plugin:ptc:ptc`). ptc's own documentation says its namespace persists across `--resume` until its idle TTL, so it is probably not stateful; the owner decides the list in a script step before the sitting (the review rulings (10)).
- **Quiet**: a live row whose `lastEventSeq` is unchanged since the previous sample. A row with no previous sample is not quiet.
- **Candidate**: a live process in state `ready`, with `engineState === 'idle'`, no hard reason, a memory sample, and quiet. **Release**: MAWS ending a candidate's process through C3's termination ladder with the new exit reason `budget`, least recently used first, at most one per evaluation and none while a release is still exiting. **Released session**: one whose last exit was a release and which has not launched, been archived, or been taken by a terminal or background job since. **Last used**: the latest of the launch, a turn's end, and any command the human sent to the session (send, steer, answer, interrupt, `!`, `#`, a mode, model or effort change); viewing a session is not use.
- **Over budget with no candidate**: the sum exceeds the budget with no candidate on two consecutive samples. The host computes it (`BudgetState.overWithoutCandidate`); the only response is the banner.
- **Custody copy**: `<userData>/engine/<version>/claude`, a copy of the installer's `<source>/<version>` where `<source>` is `dirname(ENGINE_BIN)`, `/Users/new/.local/share/claude/versions` (C3's `src/engine-host/launch.ts:11`), beside a `manifest.json` recording version, SHA-256, size, source path and copy time. **Pin time**: the first start at which the pinned version has no verified custody copy, and every re-pin. **Re-pin**: moving `settings.engine.pinnedVersion` to another engine version after the re-probe §15 requires; documented here, not run (D6).
- **Busy work** (D8): a session mid-turn or still launching, a session with running background tasks or workflows, and a terminal whose shell has a foreground command (C9's `pty.foreground` answering `busy: true`).
- **Owner build**: `dist/mac-arm64/MAWS.app` from `pnpm build:app`.
- **Pre-run**: the agents' run of §10 under a scratch `CLAUDE_CONFIG_DIR` through Playwright over the owner build (M6). **Evidence pack**: what the pre-run commits under `docs/doperpowers/evidence/c12/`. **Owner's script**: the numbered steps only the owner can run, on the real config home or by hand. **Recomposition checklist**: the table the architect completes from the evidence pack and the owner's results.
- **Scratch home**: a throwaway `CLAUDE_CONFIG_DIR` with `{}` settings, made by C3's `scratchConfigHome()` (`test/live/support/live.ts:92`) or the shell blocks below and checked by `assertConfigHomeSafe` before anything spawns; with it, a throwaway `MAWS_USER_DATA` and scratch repositories under `/private/tmp`. `launchMaws` sets its own `CLAUDE_CONFIG_DIR` and `MAWS_USER_DATA` unless told otherwise (`e2e/support/launch.ts:54,57,64`), so every gated spec passes the exported values through its `userData` and `env` options. It makes `claude-config` inside a given `userData` without creating parents (`mkdirSync` with no `recursive`, `e2e/support/launch.ts:57-58`), so every block below creates its `userData` with `mkdir -p` first.

## Interfaces and Dependencies

### The policy (`src/engine-host/budget.ts`, new)

```ts
export const DEFAULT_BUDGET_FRACTION = 0.25;
export const EXITED_RING = 500;          // events an exited stream keeps in memory; older ranges rebuild from the journal
export const EXITED_ROWS_MAX = 24;       // exited rows the host keeps; the oldest exit goes first
export type { HardReason } from '@shared/engine/status';   // 'turn' | 'busy' | 'background_tasks' | 'pending_request' | 'queued_messages' | 'held_peer_message' | 'stateful_mcp'
export interface BudgetPolicy { limitKiB: number; statefulMcpServers: readonly string[] }
export function hardReasons(s: EngineSessionStatus, stateful: ReadonlySet<string>): HardReason[];
export interface BudgetInput {
  rows: readonly EngineSessionStatus[];
  policy: BudgetPolicy;
  quiet: ReadonlySet<AppSessionId>;       // rows whose lastEventSeq is unchanged since the previous sample
  releasing: AppSessionId | null;         // a budget ladder still in flight
  previousOverWithoutCandidate: boolean;  // the previous sample's `over && candidates === 0`
}
export interface BudgetVerdict {
  totalKiB: number; limitKiB: number; over: boolean; unmeasured: number; // live rows with no sample yet (counted as 0)
  release: AppSessionId | null;                                          // at most one per evaluation; null while `releasing`
  blocked: { appSessionId: AppSessionId; reasons: HardReason[] }[];      // live rows with a hard reason, with why
  settling: number;                                                      // rows with no hard reason that are not yet candidates (engine not idle, not quiet, unmeasured, launching)
  candidates: number;
  overWithoutCandidate: boolean;                                         // over with no candidate now and at the previous sample
}
export function evaluate(input: BudgetInput): BudgetVerdict;
```

Rules, each pinned by a unit test in `budget.test.ts`:
- The sum covers every row whose process is `starting`, `initializing` or `ready`; `exiting` and `exited` rows are excluded, so a tree already in its ladder (up to 7 s) is never counted twice.
- `hardReasons` maps `turn !== null` → `turn`; `busy && turn === null` → `busy`; `backgroundTasks.length > 0` → `background_tasks` (ambient tasks included unless C3's definition of `ambient` shows they are not the owner's work; the executor records which); `pendingRequests > 0 || pendingPlan !== null` → `pending_request`; `queue.length > 0` → `queued_messages`; `heldPeerMessages.length > 0` → `held_peer_message`; a server whose name is in the set and whose status is `connected` or `pending` → `stateful_mcp`. Grants and non-stateful servers never appear.
- A candidate is `process === 'ready'`, `engineState === 'idle'`, no hard reason, `memory.treeRssKiB !== null`, and in `quiet`. Each exclusion is pinned alone: a `busy` status (a written message not yet started, a `!` command pending, a held clear-and-implement), `engineState` `running`, `requires_action` or `unknown` (the window after `background_tasks_changed []` in which the engine starts its own follow-up turn), and a row whose `lastEventSeq` moved since the previous sample.
- `release` is the candidate with the oldest `lastUsedAt` (ties by `appSessionId`), non-null only when `over` and `releasing === null`.
- `overWithoutCandidate` is `over && candidates === 0 && previousOverWithoutCandidate`.
- The function is pure and never reads the clock.

The exited-history caps (`EXITED_RING`, `EXITED_ROWS_MAX`) belong to the same policy: both apply at every exit, whatever its reason (revised 2026-09-29 at M1's review): the stream trims its ring to `EXITED_RING` when it forwards the exited status, and the table's status listener drops the oldest other exited rows beyond `EXITED_ROWS_MAX` the first time a row reads `exited`, never at a sample tick or a policy change.

**The table's side** (`process-table.ts`, pinned in `process-table.test.ts`): after each `sampleMemory` and at `engine.policy.set`, the table builds `quiet` from the `lastEventSeq` it recorded per row at the previous sample, calls `evaluate`, and, when `release` is non-null, calls `session.stop('budget')` on it in the same synchronous step, with no `await` between reading the statuses and the call, so no event can land between the verdict and the stop. It holds `releasing` until that session's exit and records the verdict's `overWithoutCandidate` for the next sample. Pinned cases: evaluate-then-stop with no interleaving (an event queued behind the sample does not reach the session before `stop`), no second release while one is exiting, an `exiting` tree excluded from the sum, and the debounced flag needing two consecutive samples.

### Engine custody (`src/main/engine/custody.ts`, new)

```ts
export interface CustodyManifest { version: string; sha256: string; size: number; source: string; copiedAt: string }
export type Custody =
  | { state: 'ok'; path: string; manifest: CustodyManifest }
  | { state: 'missing' | 'mismatch' | 'version'; path: string; message: string };
export function custodyPath(userData: string, version: string): string;   // <userData>/engine/<version>/claude
export async function ensureCustody(o: { userData: string; version: string; sourceDir: string }): Promise<Custody>;
export function custodyRefusal(c: Custody): { status: 'refused'; reason: 'binary_missing' | 'binary_version'; message: string } | null;
```

- **The copy.** At pin time `ensureCustody` copies `<sourceDir>/<version>` to a temporary name beside the target with `fs.copyFile(…, COPYFILE_FICLONE)` (an APFS clone when both paths are on one volume, a full copy otherwise), sets mode 0755, runs `--version` on the copy by absolute path, computes SHA-256, writes `manifest.json`, then renames into place.
- **At every start** it re-hashes the copy and compares with the manifest (the cost is measured and recorded; if over one second, the size and mtime are compared at start and the hash in the background before the first launch). A copy that is missing or fails verification is made again from the source when the source exists and answers `--version` with the pin (logged, the manifest rewritten), which is what makes "reinstall that version" a fix. Otherwise the answer is `missing` (neither a copy nor a source), `mismatch` (the hash differs and no source to copy from) or `version` (`--version` disagrees and no source).
- **The message** names the version, the custody path and the fix: `Claude Code 2.1.283 is missing from MAWS's copy at <path>. Reinstall Claude Code 2.1.283 (it belongs at ~/.local/share/claude/versions/2.1.283) and restart MAWS, or choose a binary path in Settings › Engine.` (with `has been altered` or `answers a different version` for the other two). Re-pinning is after P0 (D6) and is never offered.
- **The launch gate.** Main refuses a launch itself when custody is not `ok`: `custodyRefusal` answers the launch's existing `refused` shape (`LaunchResultSchema`, `src/shared/ipc/schema/session.ts:59-64`), reason `binary_missing` for `missing` and `binary_version` for `mismatch` and `version`, with custody's message. The gate awaits custody's start promise and the answer to main's first configure push before it reads the verdict, so a launch in the first seconds after a first start (a 225 MB copy and a hash of it) neither finds no answer nor runs from the host's default path before the push lands. C10's service checks it when a setup or a resume begins, before anything it would have to undo: at the top of `runIntentSetup` (`src/main/sessions/setup.ts:137`, before the worktree step, the trust bootstrap and `createForLaunch` at `:193`) and of `runResume` (`resume.ts:19`, before the trust read, the bootstrap and `fs.unfollow` at `:49-53`). A refusal is thrown as the `SetupFailure('launching', …)` a refused `session.launch` already produces (`setup.ts:210`, `resume.ts:58`), so no worktree is added, no record is created, no tab is unfollowed and nothing is spawned; the bootstrap's own launch (`setup.ts:70`) runs inside both and is covered. C3's own probe (`binary-info.ts`) knows only `missing` and `version`, so an altered binary that still answers `--version` would otherwise launch. If a renderer surface shows only the reason and not the message, the executor adds `binary_custody` to `LAUNCH_REFUSALS` additively instead and records it.
- **Configure.** Main is the only sender of `engine.configure`. Main awaits `ensureCustody` before `startEngineConfigure`'s first push, and every push sends `binaryPath: settings.engine.binaryPath ?? custody.path`; no push goes out with `binaryPath: null`, since the host then falls back to the installer path (`engineBinaryPath()`, `launch.ts:40-42` on C11's branch at `ba76a470`). C12 removes that call: `EngineSection` writes settings, awaits `settings.engineApplied`, and re-reads `engine.binaryInfo`. A path the owner chose in Settings is used as chosen, without custody or the gate.
- **Tests, e2e and replay.** Under `MAWS_E2E=1` and `MAWS_ENGINE_REPLAY=1` custody is not run: the gate passes and configure sends `binaryPath: null`, so the host uses `ENGINE_BIN` as today.
