## Purpose

After E5 the owner edits a file by hand without leaving MAWS. A file tab that showed code read-only is an editor: type, and the tab's title gains a dot; press ⌘S (File › Save file) or the bar's Save, and the file on disk has the text, written only if the file is still what the tab last read, so an agent's write underneath is never overwritten blind. When the agent (or anything) changes the file while the tab has unsaved edits, the bar says *Changed on disk* and offers Reload (take the disk's version), Keep mine (go on, the next save wins) or Compare (see the disk's lines against the tab's in one editor). A save that finds the file changed opens that merge view at once: the disk's lines against the tab's, each change with *Keep mine* and *Take theirs*, and Save writes the resolution. A file that carries git's conflict markers opens with each conflict block laid out as mine, base (when present) and theirs, with *Accept mine*, *Accept theirs* and *Accept both* above it and a *N conflicts* counter with next and previous in the bar. Closing a dirty tab asks *Save changes to app.ts?* with Save, Don't save and Cancel. Hovering a line's gutter shows a comment mark; clicking it produces a `file-line` anchor (X10) and opens the comment composer, which until E3 lands is a plain sheet naming the anchor. Everything the viewer did read-only is unchanged: markdown rendered, images inline, "Open externally" rows, a 20 MB head, the line jump, lazy loading; and Review's `Open file ↗` lands the editor at the changed line (G5).

What E5 does not do: create files, rename, delete or move them (the Files tool stays read-only beyond opening); edit a file larger than `CODE_CAP` (a head stays a head), a binary, a markdown file in its rendered view (Source edits), or a file the allowlist refuses; a three-pane merge editor (the conflict-marker view is inline, Decision Log); guard app quit against unsaved edits (tracker row, Decision Log); run `git` (E6); the comment composer itself (E3); the diff view Review uses (`@git-diff-view`, untouched).

## Terms

- **Entry**: the viewer store's per-tab record (`ViewerEntry`, `src/renderer/src/tools/code/viewer/viewer-store.ts`): the file's text as last read, its kind, its load state. E5 adds the editing fields to it (Interfaces, *The entry's editing fields*). **View state** (`viewState(tabId)`): what a code view leaves behind when its tab is hidden, opaque to the store (the CodeMirror `EditorState`, scroll offsets); E5 adds the document getter and the clean document to it.
- **Baseline**: the content the tab believes is on disk: the entry's `text` with its `hash`. **Dirty**: the editor's document differs from the baseline. **Theirs**: the disk's content when it differs from the baseline while the tab is dirty, learned through `files.changed` (shown as the *notice*) or through a save's `conflict` answer (shown as the *merge view*). **Mine**: the editor's document.
- **Hash**: SHA-256 of a file's bytes as hexadecimal, 64 lowercase characters, computed by main from the bytes it read or wrote; never by the renderer. `files.read` answers it when asked; `files.write` compares the file's current hash with `expectedHash` and answers the hash it wrote or the one it found.
- **The open-first boundary** (C8c, `src/main/files/service.ts`): the service opens a path with `O_NOFOLLOW_ANY` before trusting it, confirms the descriptor's `(dev, ino)` against a fresh realpath under an allowlist root, then judges its type. `files.write` reuses it with a read-write open and serves the compare and the write from that descriptor.
- **Merge view**: `@codemirror/merge`'s `unifiedMergeView`, one editor whose document is mine with theirs as the `original`, drawing each differing chunk with theirs' lines inline and two controls. **Conflict markers**: git's `<<<<<<< `, optional `||||||| ` (diff3 base), `=======`, `>>>>>>> ` lines; a **conflict block** is one balanced run of them. `@codemirror/merge` 6.12.2 has no marker support (its typings carry no export about conflicts; verified 2026-10-05), so the block view is MAWS's own CodeMirror extension.
- **Anchor**: X10's object; E5 produces the `file-line` kind. **Composer seam**: `registerCommentComposer` / `openCommentComposer` (`src/renderer/src/tools/code/anchor/anchor.ts`): E3 registers the shared composer; until then the placeholder sheet opens.
- **Close guard**: C5's per-kind registry (`registerCloseGuard(kind, guard)`, `actions-runtime.ts`); every user close (`×`, middle-click, ⌘W, the tab menu) runs `requestCloseTab`, which closes only when the kind's guard answers true. E5 registers the `file` guard.
- **Stub mode**: the product launched with `MAWS_SESSION_SOURCE=stub:<scenario.json>` over the scratch repository `e2e/support/code-scratch.ts` builds, so `files.*` runs for real (C8c's e2e pattern).

## Interfaces and Dependencies

### `files.write` and the read hash (`src/shared/ipc/schema/files.ts`, owner main)

```ts
export const FILES_WRITE_MAX_BYTES = FILES_READ_MAX_LENGTH; // 8 MiB: the file before the write and the content after it
export const HashSchema = z.string().regex(/^[0-9a-f]{64}$/); // SHA-256, lowercase hex

// files.read: `hash: true` asks for the whole file's hash with this chunk. The service then reads the whole file into one
// buffer (bounded by FILES_READ_MAX_LENGTH), hashes that buffer and slices the chunk from the same buffer (the settle
// rules applied against the buffer, not the handle), so the bytes answered and the bytes hashed are one read; a file past
// the cap answers `hash: null` (a head is never edited), as does a read not asked for it.
FilesReadInputSchema  gains  hash: z.boolean().optional()
FilesReadOutputSchema gains  hash: HashSchema.nullable()
                      and    utf8: z.boolean().nullable()   // with the hash: whether the hashed bytes are valid UTF-8 (a strict decode of
                                                              // the whole buffer succeeds), so the renderer knows the text it holds
                                                              // re-encodes to the file's bytes exactly; null when not hashed

export const FilesWriteInputSchema = z.strictObject({
  appSessionId: AppSessionIdSchema,
  path: z.string(),
  content: z.string().max(FILES_WRITE_MAX_BYTES), // characters here; main refuses when the UTF-8 bytes exceed the cap
  expectedHash: HashSchema,
});
export const FilesWriteOutputSchema = z.discriminatedUnion('status', [
  z.strictObject({ status: z.literal('ok'), hash: HashSchema }),       // the hash of what was written
  z.strictObject({ status: z.literal('conflict'), hash: HashSchema }), // the file's current hash; nothing written
]);
commands['files.write'] = { input: FilesWriteInputSchema, output: FilesWriteOutputSchema, owner: 'main' }
```

`names/files.ts` adds `'files.write'`. `files.write` is not a read: it is not in `QUERY_COMMANDS`.

### The write (`src/main/files/service.ts`)

`write(input): Promise<FilesWriteOutput>` on `FilesService`, registered by `registerFilesHandlers` as the others are. Steps, each a decision:

1. `precheck` as for `read` (absolute, normal, no trailing separator, known session, under a root by realpath, no final-component symlink), then open `real0` with `O_RDWR | O_NONBLOCK | O_NOFOLLOW_ANY` and nothing else: no `O_CREAT` (the editor edits files it opened; a file gone since answers `not found: <path>` under the leak rule, exactly as `read` does), no `O_TRUNC` (nothing is destroyed before the compare). `EACCES`/`EPERM` on the open answer `not writable: <path>` (the path is in-root after step 1, so naming it leaks nothing); any other failure follows `read`'s rules (`ENOENT` through `missing`, else the refusal).
2. `fstat`, `confirm` (the fresh realpath under a root whose `stat` names the descriptor), `isFile()` else `not a regular file: <path>`; `size > FILES_WRITE_MAX_BYTES` answers `too large to edit: <path>`; `Buffer.byteLength(content, 'utf8') > FILES_WRITE_MAX_BYTES` answers `content too large`.
3. Enter the file's critical section: writes are serialised per confirmed identity (`${dev}:${ino}`, a promise chain in the service), so two `files.write` calls on one file (two tabs, two sessions, a hard-link alias) compare and write one after the other and the second finds the first's hash. Inside it, `fstat` again (the size cap applies to the current size), read the whole file from the descriptor (`readFully`), hash it; a mismatch with `expectedHash` answers `{status:'conflict', hash}` with nothing written.
4. Still inside: `handle.truncate(0)`, `handle.write(bytes, …)` looped until every byte is written, `handle.sync()`, answer `{status:'ok', hash: sha256(bytes)}`; leave the section.

Why in place through the descriptor and not temp-and-rename (`atomic-write.ts`): the rename is by path into a directory confirmed earlier, so an ancestor swapped to a symlink between the confirmation and the rename lands the file outside, the race the boundary exists to close; a rename also replaces the inode (hard links break, the mode becomes `atomic-write.ts`'s 0o600, extended attributes go). Two limits, recorded: a crash between the truncate and the write leaves a truncated file (the tab keeps its content and stays dirty until `ok`, so the owner saves again); and the serialisation covers MAWS's own writers only, so an external writer between the compare and the write is not caught (the descriptor boundary guarantees containment, not an atomic compare-and-swap; the window is the compare's and the write's own duration).

### The entry's editing fields (`viewer-store.ts`)

```ts
interface ViewerEntry {                       // existing fields unchanged; added:
  hash: string | null;                        // the baseline's hash: the last hashed read's, or the last save's; null until one answers
  editable: boolean;                          // derived at each load: kind 'code' (or 'markdown' shown as Source), complete, encoding 'utf8',
                                              //   hash !== null, and the read's `utf8` is true (main's strict decode; a byte-length comparison
                                              //   is not a lossless check: a truncated 3-byte sequence decodes to U+FFFD, also 3 bytes)
  dirty: boolean;                             // the editor's document differs from `text`
  saving: boolean;
  saveError: string | null;                   // the last save's failure, word for word; cleared by the next edit or save
  theirs: { text: string; hash: string; view: 'notice' | 'merge' } | null; // the disk's content past the baseline while dirty
  baseline: number;                           // bumped when `text` and `hash` move while the editor's document must stay (a save, Keep mine);
                                              //   `epoch` keeps today's meaning: `text` replaces the document
}
interface ViewState {                         // added:
  docOf: (() => string) | null;               // the editor's current document as a string; set by the code view at mount, a closure over the state left behind at unmount
  clean: unknown;                             // the view's own: the CodeMirror Text equal to the entry's `text`, kept current by the view (never written by the store)
}
```

Two counters tell the code view what a `text` change means. `epoch` (existing): the document is replaced by `text` (an open load, a change load while clean, Reload). `baseline` (new): `text` and `hash` moved but the editor's document stands (a save completed, Keep mine); the view sets `clean = state.toText(text)` and recomputes `dirty`, touching no document. The two never move together, and `baseline` moves only on a complete entry, so the append path (same epoch, longer text, an open load's continuation) and the baseline path cannot be confused: the view keys its bookkeeping on `{epoch, baseline, length}`.

Store actions added: `save(tabId): Promise<'ok' | 'conflict' | 'error' | 'noop'>`, `reload(tabId)` (take theirs), `keepMine(tabId)`, `compare(tabId)` (notice → merge), `setDirty(tabId, dirty)` (the code view's listener), `setSaveError`. `markdown` entries are editable only while `sourceView` is true (the rendered view has no editor); toggling to Rendered with a dirty buffer keeps the buffer (the state is in `viewState`), and the dot stays.

### The editing state machine

Events and transitions for one entry; anything not listed leaves the fields alone. "Baseline" is `{text, hash}`. Every load passes `hash: true` on every chunk it reads, and a continuation whose `hash` differs from the first chunk's ends the load with `hash: null` (the text shows read-only until the follow-the-file reload, which the change that caused it triggers, makes it consistent). A load's answer is judged **when it completes**, against the entry as it is then, not as it was when the read was issued: the dirty rule below is a commit-time rule. Every answer (a load's, a save's, a conflict read's) is scoped to the entry's incarnation: the store numbers each entry it creates for a tab, and an answer whose incarnation is not the entry's now (the tab was closed and reopened, or the entry replaced) lands nowhere.

| State before | Event | After |
|---|---|---|
| any | an `open` load completes | `text`, `hash` from the read (`null` on a chunk mismatch); `editable` derived; `dirty:false`, `theirs:null`, `saveError:null`, `epoch+1` |
| clean, no theirs | a `change` load completes | as today: `text`, `hash`, `epoch+1`, `updated+1`; except that a read whose `hash` equals the entry's lands nothing (an own save, a spurious event; `updated` unchanged) |
| dirty or theirs | a `change` load completes (whenever it was issued, a rebind's included) | `hash === entry.hash` → nothing; `hash === theirs?.hash` → nothing; else `theirs = {text, hash, view: theirs?.view ?? 'notice'}` (an open merge view takes the new original); `not found` → `removed:true`, text kept |
| editable | code view transaction with `docChanged` | `dirty = !doc.eq(clean)`; `saveError:null` |
| dirty, or theirs | `save` | `saving:true`; `content = docOf()` captured now; `files.write(content, expectedHash = theirs?.view === 'merge' ? theirs.hash : hash)` — from the notice the stale baseline is sent on purpose, so an unseen change is never overwritten and the answer is `conflict`; from the merge view the hash of what the view shows is sent, so a resolution saves, and a newer change still conflicts |
| saving | `ok {hash}` | `text:=content`, `hash`, `saving:false`, `theirs:null`, `baseline+1` (the view keeps its document, sets `clean = toText(content)` and reports `dirty = !doc.eq(clean)`: typing during the save stays dirty against the saved content); the load generation is bumped, so a read issued before the answer lands nowhere |
| saving | `conflict {hash}` | `saving:false`; `theirs?.hash === hash` → `theirs.view:='merge'`; else read the whole file with its hash → `theirs = {text, hash, view:'merge'}` (a read whose hash differs from the answer's is newer and wins) |
| saving | error | `saving:false`, `saveError:message` |
| theirs | `reload` | `text:=theirs.text`, `hash:=theirs.hash`, `theirs:null`, `dirty:false`, `epoch+1` (the view replaces the document whole, scroll kept, no flash, no `updated` bump: it is the owner's own act); the load generation is bumped |
| theirs | `keepMine` | `text:=theirs.text`, `hash:=theirs.hash`, `theirs:null`, `baseline+1` (the document stands; `clean` becomes the disk's text, so `dirty` is true unless the document equals the disk, and an undo to the old baseline is still dirty; the next save sends the disk's hash and wins; a third change still conflicts) |
| theirs.view notice | `compare` | `theirs.view:='merge'` |
| saving, or clean with no theirs | `save` | `'noop'` |
| dirty, tab rebound to another session (`mount` with the same path, another `appSessionId`) | rebind | the entry keeps its document, `text`, `hash`, `dirty` and `theirs`; `appSessionId` moves, the old directory hold is released and a new one taken under the new session, then a `change` load runs under it and commits by the row above (a refusal shows as today's error body with the dirty mark kept; the guard still asks; a save then fails with the refusal). Today's reset-to-fresh applies only to a clean entry. |

Pruning: `prune()` never evicts a dirty entry whose tab the layout still holds (the LRU bound passes over it); an entry whose tab the layout dropped is removed as today, since the close guard already asked. The one gap left open: a tab dropped without a user close (a session removed, a hydration that drops a tab) loses its buffer; recorded in the tracker.

### The code view's modes (`CodeView.tsx` and `editor/*`)

Four compartments beside the existing three: `editing` (read-only set, or `EditorState.readOnly.of(false)`, `EditorView.editable.of(true)`, `history()`, `keymap.of([...defaultKeymap, ...historyKeymap, indentWithTab])` ahead of the search keymap, `indentOnInput()`, `bracketMatching()`, `drawSelection()`, `dropCursor()`, the dirty listener), `merging` (`unifiedMergeView({original: theirs.text, mergeControls: ourControls, highlightChanges: true, gutter: true, collapseUnchanged: {margin: 3, minSize: 4}})` while `theirs?.view === 'merge'`, else empty; a new `theirs.text` reconfigures it), `conflicts` (the block extension while the document holds a conflict block and no merge view is open, else empty), `comments` (the gutter, always). The view's bookkeeping of which store text it holds grows to `{epoch, baseline, length}` (today's `editorAt`, kept in `viewState` across a hidden tab); its sync effect takes the `baseline` branch first (set `clean = state.toText(text)`, report `dirty`, touch no document), then today's epoch and append branches, and after any document it applies sets `clean = state.doc`. `clean` is the view's alone. `docOf` is set at mount over the live view and replaced at unmount by a closure over the state left behind. ### Conflict blocks (`editor/conflicts.ts`)

```ts
export interface ConflictBlock {
  from: number; to: number;                   // the block's first line start to the end of the `>>>>>>>` line (inclusive of its newline when present)
  mine: { from: number; to: number; label: string | null };   // the lines between `<<<<<<< ` and `|||||||`/`=======`; label: the text after `<<<<<<< `
  base: { from: number; to: number } | null;  // the lines between `||||||| ` and `=======`, when present
  theirs: { from: number; to: number; label: string | null }; // the lines between `=======` and `>>>>>>> `
}
export function findConflicts(doc: Text): ConflictBlock[];   // pure; a run that does not balance is not a block
export function resolve(view: EditorView, block: ConflictBlock, choice: 'mine' | 'theirs' | 'both'): void; // replaces the block with the chosen lines; 'both' is mine then theirs
```

The marker grammar: a line equal to `<<<<<<<` or beginning `<<<<<<< `, then optionally one equal to `|||||||` or beginning `||||||| `, then one equal to `=======`, then one equal to `>>>>>>>` or beginning `>>>>>>> `, in that order with no other marker line between; nested or unbalanced runs are left alone. Decorations: marker lines `cm-conflict-marker`, mine `cm-conflict-mine`, base `cm-conflict-base`, theirs `cm-conflict-theirs` (backgrounds from the three new tokens), and one block widget above each block with the three buttons and the two labels (`mine (HEAD)`, `theirs (feature)` when the markers carry names). Save with blocks remaining writes the document as it is (the owner may save partial work); nothing refuses it.

### M1 — `files.write` and the read hash

At the end of M1 main answers `files.write`: a renderer can write a session's own file through the open-first boundary with a hash it was given, and is told `ok` with the new hash or `conflict` with the current one; `files.read` answers the file's hash when asked. Nothing in the product changes visibly.

Touches: `src/shared/ipc/schema/files.ts`, `src/shared/ipc/names/files.ts`, `src/shared/ipc/schema.test.ts` (the C8c `files.*` case), `src/main/files/service.ts`, `register.ts`, `service.test.ts`, and the renderer fakes that build `files.read` answers (`src/renderer/src/tools/code/viewer/viewer.test.tsx` and any other suite the typecheck names), which gain `hash: null`.

Exposes: `files.write`, `FilesWriteInputSchema`, `FilesWriteOutputSchema`, `HashSchema`, `FILES_WRITE_MAX_BYTES`, `files.read`'s `hash`. Consumes: C8c's `precheck`, `confirm`, `readFully`, `missing`, the boundary hooks.

Decisions local to M1: `openConfirmed` grows a `'write'` kind whose flags are `O_RDWR | O_NONBLOCK | O_NOFOLLOW_ANY` and whose type check is `isFile()`; the hash is computed with `crypto.createHash('sha256')` over the bytes read through the descriptor and never over a path; the `before-open` and `after-open` boundary points fire in `write` as in `read`, so the service tests substitute at them and show the refusal (the swap at `before-open`, the `(dev, ino)` mismatch at `after-open`); a hashed read is one buffer: the whole file (≤ the cap) read from the descriptor, hashed, and the chunk sliced from it with the settle rules (`utf8Cut`, the CRLF rule) applied to the buffer, so `read`'s settle step takes a byte source that is either the handle (today) or the buffer; the per-identity critical section is a `Map<string, Promise<void>>` chained per `${dev}:${ino}` and removed when its chain drains, entered after `confirm` and left after the answer or the failure; a write whose `handle.write` returns fewer bytes than asked loops until done; `handle.sync()` runs before the answer.

Does not touch: any renderer component or store beyond the test fakes; the Files tool; e2e.

Proves: acceptance 1's `files service write` and `files.* schema` suites. Pins beyond acceptance: `files.write` on a path whose final component is a symlink to an in-root file answers the refusal, and on a path through a stable in-root symlinked ancestor answers `ok` (as `read` reads through it); a link substituted at `before-open` is refused; a write of content whose UTF-8 length exceeds the cap answers `content too large` before any open; `write` answers `conflict` with the hash of the current bytes and the file's mtime is unchanged; two consecutive writes with each answer's `hash` as the next `expectedHash` both answer `ok`; two concurrent writes with the same `expectedHash` (started together, the second released by the test at the first's `after-open` point) answer one `ok` and one `conflict`, and the file holds the `ok` one's content exactly; the mode `0o644` and a hard link's shared inode survive a write; `files.read` with `hash: true` on a 2 MiB file answers the same hash for `offset: 0` and `offset: 1048576`, and when the test replaces the file between those two reads the hashes differ and each chunk's bytes are its own hash's file (the chunk is never the old file's bytes with the new file's hash).
