## Purpose

After this child, the owner manages Claude Code plugins without a terminal: in the `/plugins` widget of a MAWS session they see the marketplaces the engine knows and add one from a GitHub repository, a URL or a folder, refresh it or remove it; they see the plugins installed in the engine's registry with their marketplace, scope and enabled state, and install, update, uninstall, enable or disable one; and they reload mods (`reload_plugins`) and skills (`reload_skills`) in the running session from the palette or the panel. Every one of those changes runs the engine's own command-line (`claude plugin …`) in a process MAWS owns, after a sheet that names the exact command and the files it will write; MAWS itself never writes `~/.claude` or `~/.claude.json`. The running session reflects the change because MAWS reloads it afterwards, which G0 showed the engine does not do on its own.

How to see it working: open a session, type `/plugins`, add the scratch marketplace of Concrete Steps "Live run" as a folder, install `e8-probe@e8-scratch`, confirm the sheet, and watch the row go from `Working…` to the engine's success line and the "Loaded in this session" list grow by `e8-probe`.

## Acceptance

The parent's gates, phrased as what is observed. G0 is met by the evidence under `docs/doperpowers/evidence/p1-e8/` (see Surprises & Discoveries). G1 to G4 are observed on the owner's Mac in the live run of Concrete Steps, against the scratch marketplace under a scratch home, with the screenshots and the text log under the same directory.

1. **G1 marketplaces.** `/plugins` lists the engine's marketplaces as `claude plugin marketplace list --json` answers them (name, source, repository or path). Typing a folder path (or choosing one with "Choose folder…"), a `owner/repo` or a URL into "Add marketplace" and confirming the sheet runs `claude plugin marketplace add <source> --json`; the row shows `Working…`, then the engine's message (`Successfully added marketplace: e8-scratch (declared in user settings)`), and the list gains the marketplace. "Refresh" runs `marketplace update <name> --json`; "Remove…" runs `marketplace remove <name> --json` after its sheet and the row leaves. An error is the engine's own words in red under the row (`Path does not exist: /tmp/e8-does-not-exist`), with its `failureCode` (`invalid_source`).
2. **G2 plugins.** `/plugins` lists installed plugins as `claude plugin list --json` answers them (id, version, scope, enabled) and, per marketplace and collapsed, the plugins available to install. "Install…", "Update", "Uninstall…", and the enable switch each run the matching `claude plugin <verb> <id> --json` after its sheet; the row shows the CLI's progress line while it runs, then the engine's result (`Successfully installed plugin: e8-probe@e8-scratch (scope: user)`, `e8-probe is already at the latest version (0.1.0).`) or its failure (`Plugin "nope" not found in marketplace "e8-scratch"…` · `not_found`). After a successful mutation MAWS reloads plugins in every running session the change applies to and says so on the row (`Reloaded in 1 session · reflected`); the "Loaded in this session" list and the panel's `Plugins · N loaded` count follow the reload's answer at once, before any new turn, and the next turn's `/skills` lists `e8-probe:e8-hello` after an install. A session whose reload failed is named on the row with the engine's error, beside the CLI's success, with `Reload again`.
3. **G3 reload.** "Reload mods" in `/plugins` and in the panel's Plugins section runs `reload_plugins` and says `Reloaded · N commands · N agents · N plugins · N errors`; "Reload skills" there and in `/skills` runs `reload_skills` and says `Reloaded · N skills`. An error is R1's notice words in red on the same line (the operation's message and code), never a toast of MAWS's own.
4. **G4 announced writes.** Every mutation opens a sheet before anything runs; the sheet names the binary, the exact argument list, the files the engine will write (per action and scope, from the one manifest `writesOf` in Interfaces: `<config home>/settings.json` and `<config home>/plugins/…` at user scope, the project's `.claude/settings.json` at project scope, its `.claude/settings.local.json` at local scope) and that running sessions will be reloaded; Cancel runs nothing. The live run records the config home's file tree before and after each action and `live-run.txt` shows each delta inside its manifest. Listing (`plugin list`, `marketplace list`, `list --available`) writes no configuration; the engine's CLI refreshes its own catalogue caches on a listing (`plugins/plugin-catalog-cache.json`, `plugins/plugin-directory-cache-v2.json`), which the widget's foot says and D-12 records. The CLI stub's call log in the e2e records exactly the argument list the sheet showed. Over the whole live run the owner's `~/.claude.json` `/tmp` project-key set is identical before and after (A-15), and nothing under the owner's `~/.claude` changes (the run's config home is the scratch).

Checks that are not acceptance but pin behaviour: `pnpm typecheck`, `pnpm lint`, `pnpm test --maxWorkers=4` green; the `widgets`, `settings` and `panel` e2e groups green under the load rule.

## Constraints that bind every milestone

- **The engine is the user's installed Claude Code, never patched** (charter D-1). - **`~/.claude` and `~/.claude.json` are read-only to MAWS** (the standing rule; parent G4). MAWS never writes under the config home itself; the engine's CLI does, in a MAWS-owned child process, after the confirm sheet. No `-y`: a marketplace-declared command is shown to the person and accepted only through `--accept-command <sha256>` after a second sheet (SPEC 30 §25.3a). A listing is not a configuration write (D-12): the CLI's reads refresh the engine's own cache files under `plugins/`, which the engine refreshes at every session start anyway, and touch no settings or registry; the widget says so in its foot and reads the catalogue only when the owner opens the Available section.
- **Every live test runs under a scratch `CLAUDE_CONFIG_DIR` under `/tmp`** with a scratch local-directory marketplace, routed through ClaudeUsage's relay (`ANTHROPIC_BASE_URL=http://127.0.0.1:8641`, `ANTHROPIC_AUTH_TOKEN=claudeusage-local-gateway`); the owner-file delta (A-15) is recorded before and after. ## Plan of Work

Terms used below. **Config home**: the directory the engine reads its user settings from, `$CLAUDE_CONFIG_DIR` or `~/.claude` (`claudeConfigDir` in `src/main/history/prompt-history.ts`). **Registry**: the engine's `plugins/installed_plugins.json` and `plugins/known_marketplaces.json` under the config home, written only by the engine (SPEC 30 §9). **The runner**: the engine-host module that spawns `claude plugin …` and parses its one `--json` result line. **Operation**: an X2 command that answers a receipt `{ opId }` at once and completes through an event, the shape C3 gave `session.reloadPlugins` (`src/shared/engine/operations.ts`). **Settle**: the pause between the CLI's exit and the first `reload_plugins`, so the engine's own settings-file watcher has refreshed its snapshot (G0: ~1.3 s on this machine; MAWS waits 3 s).

How the parts fit: the renderer's `/plugins` widget (`src/renderer/src/widgets/PluginsWidget.tsx`) reads three lists through X2 and starts operations; main's router (`src/main/ipc/router.ts`) dispatches `engine-host`-owned commands to the host over the supervisor's port; the host (`src/engine-host/ipc.ts`) owns the runner, the binary probe and the live sessions, so it can run the CLI and then issue `reload_plugins` to every ready session; the host's events reach the renderer as the existing host events do (`emit` in `ipc.ts`, bridged by `src/main/hosts`). Nothing new crosses main except names in the registries.

Decisions for this milestone:
- The child's environment is the host's **whole** captured login-shell environment (not `buildEnvironment`'s allowlist, which drops `SSH_AUTH_SOCK` and the like a git clone of a private marketplace needs) plus `DISABLE_AUTOUPDATER=1`, `TERM=dumb`, minus `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SSE_PORT`, `ELECTRON_RUN_AS_NODE`, `ELECTRON_RENDERER_URL`, `NODE_OPTIONS`. `CLAUDE_CONFIG_DIR` travels in the capture as it does to the engine, which is how the e2e and the live run point the CLI at a scratch home with no seam of their own. The cwd is the input's `cwd` (the session's directory): project and local scope write there, and `plugin list` reports project-scoped installs for it.
- The result is the **last line of stdout that parses as JSON** carrying `command` and `outcome`; `plugin list` and `marketplace list` print pretty-printed JSON across lines, so reads parse the whole stdout. Exit 1 with no JSON line (an argument error, SPEC 30 §25.3a) fails `no_result` with stderr's last non-empty line as the message. A spawn failure (`ENOENT`) fails `spawn_failed`. A child still running at 10 minutes is killed (SIGTERM, then SIGKILL after 5 s) and fails `timeout`; `plugins.cancel { opId }` does the same with `cancelled`.
- Mutations are **serialised** in one queue per host (two CLI writers racing on `settings.json` is the engine's problem to avoid, not MAWS's to cause); reads run freely. A read's 10 s bridge deadline is accepted: the CLI answers `list` in about a second on this machine, and the widget shows the timeout words if it does not.
- **No `-y`, ever.** When the result's `failureCode` is one of `command_source_refused`, `command_source_declined`, `entry_helper_unconfirmed`, `entry_helper_declined` and carries `shownCommand`, the outcome carries it verbatim (`{ sha256, command, … }` as the CLI printed) so M2 can show it and rerun with `acceptCommand: sha256`. Nothing else is retried.
- **The reload after a mutation** (`reload-after.ts`): after a successful `install`, `update`, `uninstall`, `enable`, `disable`, `marketplace update` or `marketplace remove`, wait the settle (3 s), then send `reload_plugins {}` to every session whose process is `ready` (through `controls.reloadPlugins`), in parallel. Each reload **settles independently**: a success is applied to that session's status (`applyReload`, below) and compared against the session's expectation; a rejection (timeout, exit, engine error, the codes `operations.ts` already maps) is recorded for that session and never fails the operation, whose `outcome` stays the CLI's. The **expectation per session**: for `install` and `enable`, the plugin's name present; for `uninstall` and `disable`, absent; for `update` and the marketplace verbs, none (an update changes no enabled state, a catalogue refresh loads nothing by itself). It **applies** to a session only when the operation's scope is `user`, or the scope is `project` or `local` and the session's launch directory equals the operation's `cwd` (realpaths compared); any other session is reloaded but holds no expectation. A session that disagrees is reloaded once more after another settle; one that still disagrees is reported `not_reflected` (a narrower project or local setting may override a user-scope change, and the words say so), never retried further. The completion carries `reload: { sessions: [{ appSessionId, outcome: 'reflected' | 'not_reflected' | 'no_expectation' | 'failed', error }] }`. `marketplace add` reloads nothing (an added catalogue loads no plugin). Timers are injectable, so the test runs with fake time.
- **`applyReload`** (`session-status.ts`): a successful `reload_plugins` answer replaces the session status's `plugins` with the answer's `plugins[]` (the items carry `name`, `path`, `source`, `version` exactly as `system/init` does: fixture seq 31 against seq 26), publishing the status as an init frame would; `pluginErrors` and `pluginWarnings` stay as the last init left them (the answer carries only `error_count`), and the operation line words the count. Both the widget's own `session.reloadPlugins` and the fan-out go through it, so the "Loaded in this session" list and the panel's count move without a new turn (the reviewer's third finding).
- `plugins.changed {}` is emitted after every completed mutation, success or failure (a failed install may still have refreshed a catalogue), so the widget rereads.
- `plugins.available` answers `plugin list --json --available`'s `available` array **reduced** to `{ pluginId, name, description, marketplaceName, version }`, and `plugins.list` the `list --json` rows reduced to the fields the widget shows (Interfaces); the raw rows are not forwarded (the directory marketplace alone is 1.5 MB of JSON).
- `reload_skills` is a `long` control answering `{ skills: [{ name, description?, argumentHint?, aliases? }] }` (fixture `e8-plugins-reload.jsonl` seq 35); `reload_plugins`' answer is `{ commands, agents, plugins, mcpServers, error_count, held?, cache_impact? }` (seq 32, 41), typed `looseObject` with those keys. The `OperationEvent` value union gains the skills shape.
- Pitfall seen in the code: `src/shared/wire/control.ts`'s C3 block says "later children rebase over this block and never edit inside it", and its own comment types `reload_plugins` "from the SPEC's lower bound" because no fixture answered it then. The fixture answers it now, so the two lines `ReloadPluginsResponseSchema = VoidResponseSchema` and `type ReloadPluginsResponse = VoidResponse` are **replaced in place** by the typed schema and its inferred type (D-14: a deliberate correction of a lower-bound guess, not a reordering, and nothing else in the block moves); the block's comment drops `reload_plugins` from its list of never-answered subtypes and names the fixture. `ReloadSkillsResponseSchema` and the `reload_skills` request type are appended after the block. `test/fixtures/widgets/reload-plugins.json` already carries the typed shape; the test that reads it pins that it parses.

Does not touch: any renderer file; main except the registries' shared lists; the engine's launch line.

Proves: the engine-host half of G1, G2 and G3 (the runner's argument lists, result parsing, error mapping, the settled and verified reload); the mechanics of G4 (the argument list is the one the sheet will show: `commandLine()` is one pure function the sheet and the runner both call). Tests to pin beyond acceptance: a mutation during a mutation waits; a `shownCommand` failure is surfaced and `acceptCommand` adds `--accept-command <sha>` and never `-y`; the reload compares names per applicable session and retries that session once (two sessions in two directories and a project-scope install: one expectation, one `no_expectation`; an installed-but-disabled plugin's `update`: `no_expectation`); one session answering and one timing out complete as `reflected` and `failed` beside a CLI `ok: true`; `applyReload` replaces the status's plugins and leaves its errors; a `cancel` kills the child and completes `cancelled`; the environment never carries `CLAUDECODE`; `writesOf` names, for every action and scope, the files the probe's "files after" snapshots show changing (`g0-cli-probe.txt`).

## Surprises & Discoveries

- Observation: the engine's CLI writes two places per change, not one. `marketplace add` writes `settings.json` `extraKnownMarketplaces` **and** `plugins/known_marketplaces.json`; `install` writes `settings.json` `enabledPlugins` **and** `plugins/installed_plugins.json` plus the cache tree; the CLI's own global config (`.claude.json`) lands inside `CLAUDE_CONFIG_DIR` when set.   Evidence: `docs/doperpowers/evidence/p1-e8/g0-cli-probe.txt`, "files after: marketplace add (directory)" and "files after: install e8-probe@e8-scratch".
- Observation: every mutating subcommand answers one `--json` line `{command, outcome, message, failureCode?}` with exit 0/1, including the marketplace verbs (`command: "marketplace-add" | "marketplace-update" | "marketplace-remove"`, which SPEC 30 §25.3a does not list); a no-op is a failure (`already_in_goal_state`, exit 1); `marketplace add` of an already-added source succeeds with `already on disk`.

  Evidence: the G0 session's help captures (the first run of this child).
- Observation: `plugin list --json --available` answers `{installed, available}` (an object), while plain `list --json` answers an array; `available` on an empty home already holds the engine's built-in `anthropic-plugin-directory` catalogue, about 1.5 MB of JSON.
