## 1. Purpose

**Higher purpose.** MAWS is a general workstation for supervising Claude Code agents, built to the baseline of three reference apps (Codex desktop for UX quality, Claude Desktop for engine integration, T3 Code for source readability) and then past it, with the owner's own workflows arriving as plugins on a strong base (charter §1, D-5, D-20). P0 reached the baseline and closed on daily use (charter §20).

**What this phase is for.** MAWS becomes the owner's whole workstation. Everything the agent workflow needs that today lives in a terminal moves into the app, and the agent gains a surface to reach the GUI: tools it can call, places it can put things, a channel through which the human answers in place. Inside that, the move past the baseline: human and agent share the same surfaces (a browser, delivered files and artifacts, later documents), with comments pinned to things as the feedback channel, and orchestration (workflows, subagents, cross-session messages) is visible.

**The measure (P-3).** "The GUI is good enough that nothing in my workflow sends me to a terminal." The owner named what still did at the start of this phase: live workflow progress, plugin and marketplace management, voice, editing a file by hand. The ptc kernel and background jobs do not. The sminos family chat is a later integration, not this phase's measure.

**What it must not be.** Not a dependency on claude.ai's services: the co-work layer is MAWS's own and local-first ("We'll build our own for these", P-4). Not a second plugin API: the display surface stays the engine's `ui_surface_v1` (D-9); MAWS adds tools the agent can call, which is the in-process MCP server D-9 always named. Not a browser or an IDE as products: the browser and the editor serve the session.

## 2. Acceptance

P1 closes when, on the owner's Mac with the installed engine, every item below is observed in one sitting. Items are observable behaviour; the children's acceptance refines them.

1. A Workflow run shows live in the panel widget, phases on the left and agents on the right with model names. Clicking an agent opens its transcript. Stop works where the engine allows it. The subagent topology tree shows nested agents with running and done states.
2. From MAWS the owner adds a marketplace, installs, updates, enables and disables a plugin, and reloads mods. The running session reflects it.
3. The owner holds a key, speaks, and the text lands in the composer.
4. The owner edits a file in a MAWS tab and saves. A conflict opens the merge view.
5. The agent delivers a file through MAWS's tool. It appears as a row and opens in the viewer: PDF, HTML, image, video, audio, markdown. Artifacts keep versions.
6. The owner pins a comment to an element in the in-app browser or in a delivered artifact. A side thread opens, the agent edits and replies there, the main conversation is not interrupted. "Send to main" works.
7. The in-app browser imports a Chrome profile the owner chooses. The agent drives a tab through MAWS's browser tools. The owner takes over by clicking, and the agent resumes after.
8. The agent asks a batch question through MAWS's tool. A capsule in the transcript opens the sheet in the panel with choices, free text, files or folders, a repository and "decide for me". An async question does not block the turn. (The design-system input waits for the editors composite, P-13.)
9. The owner quits MAWS with a turn in flight and relaunches. The session is still there and still streaming.
10. `/btw` opens a side pane with the answer; the main conversation is untouched.
11. From the panel the owner stages, commits, pushes and opens a PR from the session's worktree. The summary row shows PR state and checks.
12. The Tasks panel shows a session's task list read-only, opened by `show_pane 'tasks'`; edits through the engine's task tools are dropped (P-20). Cross-session messages show as rows and can be answered.
13. The three gaps carried from P0 close in recomposition: the panel and reference taste sitting (C8-S), the native terminal hands (C9), the scale review of the integrated app (S).

## 3. Design

Three primitives are shared by most of the work and are the reason this phase was designed as a whole before it is cut: the tool server (A), the deliverables store and viewer (B), and anchored messages with side threads (C). The surfaces D to I build on them.

Authority grades. **Binding**, because only the joint view could settle them: A's one server named `maws` served from the host with fallback-bearing descriptions; B's local-first store and sandboxed frames with no network; C's one mechanism with the side thread as default; D's agent control through MAWS's own tools over CDP, the copy-only profile import and the human-click takeover; I's detached process over a Unix socket; and every decision P-n in §7. Everything else in this section is advisory inheritance a child may overturn with evidence through a dated entry in §7.

### A. The MAWS tool server (the spine)

One SDK-hosted MCP server named `maws`, declared in the initialize handshake (`initialize.sdkMcpServers`, SPEC 45 §45.21 of the engine library) for every MAWS-launched session and served from the engine host over the protocol's `mcp_message` round trip. This is how Claude Desktop builds every one of its extensions (its `ccd_pr`, `ccd_view.show_pane`, `preview_*`, scheduled-task and local artifact tools are all host MCP servers; `docs/doperpowers/evidence/extension-2026-10-05/claude-desktop-extensions.txt`). Codex does the same over native pipes.

- **Tools in this phase:** `send_file` (files, caption, urgency; replaces the engine's SendUserFile, which is gated to Desktop entrypoints, SPEC 23 §23.4.2); `ask` (a general batch-question sheet, the vault's "ask me for visual references" shape: questions with modalities, each a choice set with "Other", free text, a file or folder pick, a repository pick or "decide for me"; `blocking: true | false`; the result is the answers or, for an async ask, an acknowledgement with the answers delivered later as a user message; the design-system modality arrives with the editors composite, P-13); `show_pane` (open a panel tool: diff, file, terminal, tasks, browser, deliverable); the browser tools (D); `artifact_create`, `artifact_update`, `artifact_list` (B). PR binding and scheduling tools wait for the next composite.
- **Data flow:** a tool call arrives in the engine host as an MCP request; the host emits an X1 event the renderer draws as a row (a capsule for `ask`, a delivery row for `send_file`, a browser action row); the surface answers through IPC; the host returns the MCP result. Fire-and-forget tools answer at once.
- **Terminal interop (D-12):** a session resumed in the terminal lacks these tools and nothing breaks: each tool's description names its fallback (Write a file and name its path; AskUserQuestion; describe where to look). A session started in the terminal and taken over by MAWS gains them at the next launch only (the engine adds SDK servers at initialize and through `mcp_set_servers`, which is authoritative over the whole SDK server map; tools on a running server change through `notifications/tools/list_changed`; E0a Q1, A-18).
- **Contract X9 (binding once the cut lands):** the server name, tool names, input and output schemas, and the row each tool produces. The owner's skills and plugins may target `mcp__maws__*` names; they do not change without a dated Decision Log entry here.
- **Permissions:** tool calls run under the session's permission mode like any MCP tool; `ask` and `send_file` are read-only and concurrency-safe; browser actions that navigate or act are not.

### B. Deliverables and the viewer

A per-session record of what the agent delivered: files (`send_file`), artifacts with versions, screenshots the browser tools took. The record points at delivered files in place and copies only artifact versions, under the app's data directory.

- **Panel tool "Deliverables"** (the vault's "Context"): the list, newest first, grouped by kind; a row opens the viewer; a back control returns to the list (the vault's Cowork-like flow).
- **The viewer**, in the panel by default and in a main tab on demand: sandboxed frames for PDF and HTML (no network by default; a content-security policy that blocks scripts' egress; later, declared connectors as Claude Desktop's `window.cowork.callMcpTool` allows), native players for video and audio, images inline, the existing read-only viewer for markdown and code. "Open externally" and "Reveal in Finder" always.
- **Artifacts:** a self-contained HTML file the agent writes, then registers with `artifact_create {id, html_path, title}`; `artifact_update` adds a version; MAWS keeps versions and metadata, draws the artifact in the viewer, can screenshot it for the agent, and surfaces its console errors (Claude Desktop's local artifact model, local-first already). Imported or shared artifacts are out of scope.
- **Transcript:** every delivery and artifact version is a row (C6's `SendUserFile` cell row is replaced by this row); the row opens the viewer.
- **The next composite** (docs, slides and design editors, the design system) builds on this store: a document is a deliverable kind with an editor instead of a viewer.

### C. Anchored messages and side threads

An **anchor** names what a message is about: `{ kind: 'browser-element' | 'artifact-element' | 'file-line' | 'pr-line' | 'none', locator, label, pageUrl?, screenshot? }`. Comment mode in the browser (D) and in the artifact viewer (B), a line gutter in the editor (F) and a PR line (F) produce anchors; the comment composer attaches to one.

- **Default destination, the side thread (P-6):** a child session forked from the parent at the current point (C10's fork path; the engine's `fork_conversation` request is probed first, §4), marked in its record as a side thread of the parent with the anchor; shown in a side pane with its own composer; able to edit (it carries the parent's permissions and directory); its outcome summarised back into the main transcript as a MAWS row ("Side thread on <label> finished: …") with a link to the thread. Side threads list in the panel and in the sidebar under their parent.
- **"Send to main":** the comment goes to the main session as a steer at the next tool boundary with the anchor serialised as context (text plus the screenshot as an image block).
- **`/btw`:** the engine's own `side_question` control request (SPEC 45; the slash command routes to it); drawn in the same side pane; no new process. A side question that becomes work is promoted to a side thread.
- One mechanism serves comments on artifacts, comments on web pages, review comments on code and the quick side question; the destination is the one product choice, made once (P-6).

### D. The in-app browser

Browser tabs as a panel tool and as main tabs: a `WebContentsView` per tab with Codex's navigation chrome (back, forward, reload, address, open externally, inspect) and its load-error and zoom states (`codex-extensions.txt` §1). Owned by the main process; one browser session partition per imported profile, one default partition otherwise.

- **Comment mode:** the pointer selects an element, an area or several; the overlay adds a comment and a cropped screenshot; the anchor's locator is the element's accessibility path and a CSS selector; the submission is an anchored message (C). The page is told nothing unless it declares annotation support; a page-suggested prompt is attributed as such.
- **Chrome profile import (P-7, owner's note):** the user picks a Chrome profile; MAWS copies cookies and history from its on-disk stores, decrypts saved passwords with Chrome's Safe Storage key after one Keychain consent, and loads the profile's extensions where Electron supports them, each category opt-in and reported ("N cookies, M passwords, K extensions, J skipped: unsupported"). The import is a copy; Chrome is never driven or modified. A spike precedes the design (§4). Amended 2026-10-05 after E0b (A-19, A-20): the Keychain consent gates cookies as well as passwords, since Chrome encrypts every cookie value; passwords are held out of P1 by the owner's ruling (P-17; a credential store with autofill is the next composite's child); extensions load per directory and the import reports which backgrounds ran.
- **Agent control, MAWS's own (P-5):** browser tools on the spine, built on Playwright over CDP against our own view (`playwright-core` connected through a `webContents.debugger` bridge that whitelists page-session methods, A-19; the remote-debugging port never ships): `browser_tabs`, `browser_navigate`, `browser_snapshot` (an accessibility snapshot with element refs, the same refs comment mode uses), `browser_act` (click, fill, select, press by ref or locator), `browser_eval` (read-only by policy), `browser_screenshot`. Each action is a row with the tab and the target; the human sees the agent's cursor and the acting tab.
- **Takeover:** the human clicking into the page pauses agent actions on that tab; the agent's next action waits with a visible "You have the page" state and resumes when the human stops for a moment or clicks "Hand back". No input arbitration beyond this in P1.
- cua stays for native apps and for the owner's real Chrome through its own browser surface; its planned Phase D adapter to a MAWS browser is not needed (A-7), and the cua repository's backlog is told so.

### E. Orchestration views

- **The workflow widget** (the vault's design): a Workflow run opens from Background work into a widget with phases on the left, agents on the right with model names and states; click an agent for its transcript (C8b's drill-in); stop, and resume where the engine allows (`perTaskStopAffordance`).
- **The topology tree:** nested subagents under their parents with running and done states, done agents folded under their parent, click for the transcript; replaces the flat Subagents list's resting state.
- **Cross-session messages:** `SendMessage` and inbox rows draw with sender and recipient, and a reply composer answers from the row; `ListAgents` results draw as a list. Teams (SPEC 39) draw as teammates under the lead. The sminos family chat integration is deferred.
- **Tasks panel:** the read-only checklist becomes an editable list (create, update status, reorder) through the engine's task tools or the task files it reads (SPEC 20 §20.2.3); the child grounds which.
- **Scheduled loops:** listed where the engine exposes them (CronCreate records, SPEC 22); a routines editor is deferred.

### F. Editor and source control

- **Editor:** CodeMirror 6 editing in file tabs (the read-only viewer is its base), save with stale-content detection (hash on read, compare on write, as Claude Desktop's `writeSessionFile`), the merge view for conflicts, a line gutter that produces anchors (C).
- **Source control panel:** status, stage and unstage, discard with confirmation, commit with message, push, open a PR through the GitHub CLI when present; branch and upstream shown; PR state and checks join the summary row (C8's push-state row). Mutations run through C4's git service with the same trust gate; nothing runs `core.fsmonitor` before trust.

### G. Plugins, marketplaces and mods

Claude Desktop's model (`claude-desktop-extensions.txt` §8): marketplaces added, removed and refreshed; plugins installed, updated, uninstalled, enabled and disabled; mods reloaded through the engine's `reload_plugins` request; skills through `reload_skills`. The palette's `/plugins` widget grows into this surface. First grounding question for the child: whether installs and enables go through the engine's CLI (`claude plugin …`) in a MAWS-owned process or through announced settings writes; the standing rule holds either way: no user settings written silently, every write named and confirmed.

### H. Voice

Dictation into the composer: click the mic button to start and again to stop (P-18), or hold a key you bind yourself; the text lands at the caret. Local Apple speech recognition first (A-8), through a small Swift helper the app bundles; the microphone and speech-recognition permissions (macOS asks for both, E9's finding) are requested on first use with the reason stated. Realtime voice conversation is deferred.

### I. The detachable supervisor

The engine host leaves the app's utility process for a detached supervisor process the app reaches over a Unix socket under the app's data directory, so sessions outlive app restarts and updates (D-16 amended). The app starts the supervisor if absent, reconnects at launch, and the transcript catches up from the host's event stream and the disk. Quit offers "Quit and keep sessions running" beside the existing busy report; the supervisor exits itself when it holds no session. The memory budget (charter §4.4) moves with the host. Terminal interop is unchanged: the supervisor is one more holder in the registry.

## 4. Delegated unknowns (spikes before the cut binds them)

Each is a findings-only spike recorded under `spikes/` with fixtures where the engine is involved; none merges product code.

- **S1 Chrome profile import on Electron:** cookies and history from the profile's stores; saved passwords through the Safe Storage key with one Keychain consent; which extension kinds Electron loads. Deliverable: what imports, what does not, and the consent and copy surface.
- **S2 Playwright over CDP against a WebContentsView:** connect, snapshot with refs, act, screenshot; element refs shared with comment mode; the cost of keeping the debugger attached.
- **S3 The SDK MCP round trip under MAWS's launch:** a `maws` server with one tool, declared at initialize, called by the model, its result drawn; `mcp_set_servers` mid-session; recorded as `spikes/protocol-probe/fixtures/pass3/sdk-mcp-*` on the installed engine.
- **S4 Fork and side-question shapes:** `fork_conversation` and `side_question` on the installed engine (both have no published schema); whether a fork can start a side thread without a new launch; fixtures recorded.

## 5. Ordering (advisory; decomposing fixes the edges)

The spine (A) first, with S3. Deliverables (B) after A; anchored messages (C) after S4, independent of A. The browser (D) after S1 and S2, after A for its tools and after C for comment mode. Orchestration (E), editor and source control (F), plugins (G), voice (H) and the supervisor (I) are independent of each other and of A. A finish child closes §2 item 13 and runs recomposition against §2.

## 6. Deferred and out of scope

**Explicitly out of scope** (standing exclusions): claude.ai's Artifact, Docs and Cowork services (P-4); patching the engine (D-1); MAWS writing under `~/.claude` or `~/.claude.json` (the standing rule; E8 lets the engine or its CLI write); a MAWS plugin API beside the engine's `ui_surface_v1` (D-9); Windows and Linux (D-11); the Codex agent runtime as an engine (D-7).

**Deferred** (the composite after this one). A credential store with autofill for the in-app browser, so imported Chrome passwords have a consumer (P-17). The docs, slides and design editors and the design system (on B's store; the design system is "what's extracted from existing projects or artifacts or what user and agent build together", the owner's definition of 2026-10-05, and the `ask` sheet gains it as an input then); the sminos family chat integration; a PR inbox; a routines editor; the prewarmed spare session; realtime voice; a Spaces-like organiser of deliverables across sessions; plugin JavaScript modules on the engine surface; remote control; the replay scrubber; the all-accounts usage view (likely already met by the usage pill's popover; verify at recomposition).

## 12. Risks and mitigations

- **Protocol churn.** The engine ships weekly and the installed version already exceeds the spec library; `fork_conversation` and `side_question` have no published schema. Mitigation: E0a records fixtures on the installed version; a child re-probes before it binds; the conformance suite admits new frames explicitly.
- **Egress from sandboxed content.** HTML artifacts and PDFs run in frames. Mitigation: no network by default, no top-level navigation, downloads blocked, a content-security policy per frame (E2 G3); declared connectors are a later slice.
- **Imported credentials.** Electron has no password manager; imported passwords have no consumer without autofill. Mitigation: E0b answers what a password import needs; E4's cut may ship cookies and history first and hold passwords until autofill exists; nothing imported is logged or copied outside the view's partition.
- **Git with credentials.** Push and PR run with the user's helpers. Mitigation: a confirm naming remote, branch and command before every remote action (P-12); the mutating runner never runs remote commands.
- **Orphan processes.** A detached supervisor can outlive its reason. Mitigation: idle exit, Stop all, a lock with the owning PID, a `doctor` row in Diagnostics (E10 G3).
- **Load on the owner's machine.** Mitigation: A-13; the e2e load rule; heavy runs through the slot script.
- **Terminal interop of new rows.** Deliveries, asks and side threads are MAWS rows a terminal never shows. Mitigation: each is also a plain tool call in the JSONL, so the terminal shows the call and its result text; the disk path draws the same rows from those calls (E2 G5, E3 G5).

## 14. Surprises and discoveries

- 2026-10-05, grounding: the engine's SendUserFile and Artifact tools are both gated away from MAWS's launch (Desktop entrypoints; a first-party provider), which turned "integrate the engine's tools" into "build MAWS's own" before the owner ruled the same for product reasons (P-4).
- 2026-10-05, grounding: Electron ships no password manager or autofill, so Codex's "import saved passwords" implies a consumer MAWS does not have; E0b measures what one would take.
- 2026-10-05, grounding: the task store lives under `~/.claude`, which the standing rule keeps read-only to MAWS; the Tasks panel therefore edits through the session (P-11).
- 2026-10-05, grounding: MAWS's git runner forbids transport and credential helpers by design; remote mutations need a second runner under the shell environment (P-12).
- 2026-10-05, grounding: fork lineage is not persisted on the session record today; side threads need an index migration (X11).
- 2026-10-05, E0a on 2.1.290: `fork_conversation` is unsupported under MAWS's launch (a success envelope `{forked:false, error:"unsupported", reason:"unsupported"}`; the engine's own fork needs a Remote Control bridge or `--sdk-url` and spawns a cloud process), so the launch flag `--fork-session` is the only fork; its child JSONL rewrites the parent's history under the new session id with the parent's record uuids and no `forkedFrom` (that key is written only by the terminal's `/branch`), so the disk carries no lineage signal but the reappearing uuids.
- 2026-10-05, E0a: `mcp_set_servers` is authoritative over the whole SDK server map (sending `{maws2}` alone removed `maws`), and the engine re-handshakes every server; the cheap way to add tools to a running `maws` server is the client-sent `notifications/tools/list_changed`, which makes the engine re-list at once. Under `ENABLE_TOOL_SEARCH` the model ToolSearches an MCP tool before calling it, so tool descriptions are what the index sees. `system/init` is re-emitted each turn with the current tool list. A JSON-RPC request from the engine has no timeout, so a blocking `ask` can wait.
- 2026-10-05, E0a: `side_question` answers whole in the control response after one `system/control_request_progress {status:"started"}`, in 1.6 to 2.7 s, while a 20 s Bash tool ran in the main turn; MAWS's typed `SideQuestionResponseSchema {text}` is wrong (the answer is `{response, synthetic}`), pinned as an expected failure until E3 fixes it.
- 2026-10-05, E0a: the AskUserQuestion preview format is a launch variable, `CLAUDE_CODE_QUESTION_PREVIEW_FORMAT` (`markdown` or `html`), not a handshake field; under `html` the engine refuses a non-HTML preview before any permission request; MAWS's `buildEnvironment` passes the owner's `CLAUDE_`-prefixed shell variables through, so MAWS must set or delete it explicitly. The installed engine moved to 2.1.290 during the probe.
- 2026-10-06, E8 on 2.1.290 and 2.1.291: the engine applies a CLI plugin change to a running session only on `reload_plugins`, and a reload sent within about 1.3 s of the write answers from the previous settings snapshot, so MAWS reloads after a settle; `claude plugin marketplace add --help` prints the parent's help; `plugin list --json --available` is an object of 1.5 MB with the built-in directory while `list --json` is an array that omits installed plugins on 2.1.291; an empty home loads three `@builtin` plugins; `uninstall` leaves the cache entry; a marketplace removal uninstalls its plugins and clears their overrides at every scope; the engine's update message says "Restart to apply changes" after MAWS's reload has already applied it. The installer moved the engine to 2.1.291 during E1 and E8.
- 2026-10-06, E6 author: C4 runs git reads anywhere with hooks and fsmonitor off; trust gates launches and worktree creation, not reads, so E6 applies the trust gate to mutations and remote commands; the runner drops stdout on a non-zero exit (`runner.ts:94-98`), which an untracked diff (exit 1) needs kept; `/etc/zprofile`'s `path_helper` reorders PATH after the inherited value, so an e2e PATH stub needs a prepared scratch shell home; `GIT_CONFIG_PARAMETERS` outranks `GIT_CONFIG_COUNT` pairs.
- 2026-10-06, E9: macOS asks two permissions for dictation, Microphone and Speech Recognition, not one; under `pnpm dev` the responsible app is Electron.app, whose Info.plist lacks the speech usage key, so a dev-mode first speech request may terminate the helper while the packaged app carries both keys through `extendInfo`. The load rule held E9's gates for about twelve hours on 2026-10-05 while the machine sat at a one-minute load of 70 to 436 from nProtect's `nosmain` and a `tart` VM, cleared by the owner.
- 2026-10-06, E3 M2 (outside P1's scope, fixed on master at 8e6f5cbc): the owner's real index lacks `sessions.removed_at` because C4's v1 migration was amended in place after the database existed; every discovery update of an existing record had been throwing since. A `REPAIRS` list beside `MIGRATIONS` now adds a declared column an applied entry lacks. Lesson for every child that migrates: a released entry is never amended, and a measurement on a copy of the owner's store is how such a gap is found before the owner is.
- 2026-10-06, E1 whole-branch review: the engine's MCP client sends `notifications/cancelled` when it abandons a `tools/call` (an interrupted turn while a blocking ask waits; confirmed in the 2.1.291 binary), which no fixture had recorded; a server that ignores it leaves the ask pending and a later Submit journaled as answered though the model never receives it. E1 treats it as a cancel; E11 records the fixture.
- 2026-10-06, E7 author: the engine offers no `TaskCreate`/`TaskUpdate` on the owner's default model under MAWS's launch (C12's X6 ruling keeps `CLAUDE_CODE_ENABLE_TODO_TOOLS` unset to mirror the terminal), so P-11's "edit through the session" has nothing to steer on `claude-opus-5-5` unless MAWS opts in; `CronCreate`'s session-only jobs are never written to disk (durable ones go to the project's `.claude/scheduled_tasks.json`), so the transcript's tool pairs are the only record; `ListAgents` answers prose, not a structure; a nested sidecar's meta already names its parent (`parentAgentId`, `spawnDepth`), so the tree needs no new disk fact.
- 2026-10-06, E5: `@codemirror/merge` 6.12.2 has no conflict-marker support, so the marker blocks (mine, base, theirs; Accept mine, theirs, both) are MAWS's own over the unified merge view; the one-buffer hashed read, incarnation-scoped answers and the merge-view save's hash came out of the adversarial document review, and the whole-branch review found two cross-milestone defects (the close sheet still saving a merge-view tab; the caret jumping to line 1 after an agent's write) that five per-milestone reviews structurally could not, which is A-14's case made again.
- 2026-10-05, E0b: every cookie value in the owner's Chrome profile is encrypted with the Safe Storage key (5,112 rows, `value` empty), so the one Keychain consent gates cookies, not only passwords; the saved passwords live in `Login Data For Account` (228 rows), not `Login Data` (91 blocklist rows). Unmodified Electron has no consumer for imported passwords; Codex's importer runs inside its Electron fork with compiled password-manager and autofill components. The remote-debugging port exposes every WebContents in the app, the MAWS renderer included, and Electron's debugger client is trusted and can reach every target, so the CDP bridge must filter Target, Browser and Storage methods and unknown sessions.
