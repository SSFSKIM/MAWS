## Purpose

After E10 the owner quits MAWS while an agent is mid-turn, chooses **Quit and keep sessions running**, and relaunches a minute later: the session is in the sidebar with its working glyph, the transcript shows every row that streamed while the app was closed, and the turn is still streaming. The same holds across an app update whenever the update changed nothing on the main ↔ host wire (an update that did is told apart at connect and stops the kept sessions at the owner's word or when they go idle), because the engine processes no longer live inside the app: they live in a small background process, the **supervisor**, which the app starts when it is absent and connects to when it is present, over a Unix socket under the app's data directory. When the supervisor holds no session and no app is connected it exits by itself after a configurable idle time.

To see it working: `pnpm dev`, start a session and send a prompt that runs for a while; press ⌘Q; the quit question lists the mid-turn session and offers "Quit and keep sessions running" (the default button); choose it; `ps -axo pid,command | grep maws-supervisor` shows the supervisor; relaunch; the session is live and the transcript continues. Help › Diagnostics shows the supervisor's row (pid, build, sessions held, idle exit); Settings › Engine › Background supervisor has the idle time, the quit default and **Stop all sessions**.

## Terms

- **Engine host**: the code under `src/engine-host/` that owns the Claude Code processes, their journals, the permission broker, the `maws` tool server, the filesystem state service and the memory budget. Today it runs as an Electron utility process forked by main (`src/main/hosts/supervisor.ts`). After E10 the same code runs in one of two **modes**: `utility` (as today) or `detached` (the supervisor).
- **Supervisor**: the engine host running detached: a plain Node process (the Electron binary as Node) in its own session, reparented to launchd when the app exits, serving the host protocol over a Unix socket.
- **Host protocol**: C1's envelope on the main ↔ host wire (`src/shared/ipc/host-protocol.ts`): `hello`, `req {id, name, input}`, `res {id, ok, value | error}`, `evt {name, payload}`, each end validating names, inputs, outputs and payloads against the X2 registries. E10 keeps it as the inner protocol of the socket and adds a thin **socket layer** around it (the handshake and framing, §Design 2).
- **Client**: whoever holds the socket's other end: main, through `HostSupervisor`. There is at most one client at a time (one app per data directory, the single-instance lock).
- **Row**: an entry of the host's process table (`src/engine-host/process-table.ts`), one per app session the host has launched, live or exited (the last 24 exits stay).
- **Launch**: one engine process start; its journal file; its `launchId`. A resume is a new launch. Event sequence numbers (`seq`) count journal rows within a launch, from 1.
- **Ring**: the per-launch in-memory tail of normalised events the host keeps for `session.events` (`src/engine-host/session-stream.ts`: 5,000 events while live, 500 once exited; older ranges rebuild from the journal).
- **Connect burst**: what the host sends a client when the client says it is ready: every row's current state as ordinary events, and the events no client has received yet (§Design 3).
- **Ready line**: the socket layer's `{t: 'ready'}`, sent by the client after it has pulled what it needs; the host emits no event to a client before it (§Design 2, 3).
- **Resync**: what main does between the handshake and its ready line: re-derive its own digests from each row's events, as the renderer re-hydrates a transcript after a reload (§Design 3).
- **Build id**: a content hash of the engine host's bundled entry file, computed by main and by the supervisor from the same file; two processes built from the same `pnpm build` agree, a rebuild changes it (§Design 6).
- **Wire fingerprint**: a hash of the X2 registry's schemas (every command's input and output, every event's payload); two builds that changed nothing on the main ↔ host wire share it (§Design 2, 6).
- **Hard reason**: what keeps an engine process alive under the memory budget (charter §4.4; `src/engine-host/budget.ts` `hardReasons`): a turn, work in flight, a non-ambient background task, a pending request or ask, a queued message, a held peer message, a stateful MCP server.
- **Lock, token, socket**: the three files under `<userData>/supervisor/` (§Design 1).

## Design (the residue §3 I leaves open, with reasons)

### 1. The process model and its lifecycle

**One bundle, two modes.** The engine host's entry (`src/engine-host/index.ts`) decides its mode at load: `process.parentPort` present → `utility` (today's `runHost`, unchanged); argv carries `--detached <supervisorDir>` → `detached`. One bundle means one X2 surface, one set of tests and no drift between modes; a second entry was rejected for that reason. Main picks the mode from `MAWS_HOST_MODE` (`utility | detached`), defaulting to `utility` under `MAWS_E2E=1` or `MAWS_HARNESS=1` and to `detached` otherwise (G5 without a script change).

**The binary.** The supervisor is spawned from `process.execPath` with `ELECTRON_RUN_AS_NODE=1` in dev and in the packaged app alike: in dev that is `node_modules/electron/dist/Electron.app/Contents/MacOS/Electron`, packaged it is `MAWS.app/Contents/MacOS/MAWS`; the script is the engine-host chunk's path from `?modulePath` (inside `app.asar` when packaged, which Electron's Node mode reads, §Grounding "Packaging"). Facts: `ELECTRON_RUN_AS_NODE` "starts the process as a normal Node.js process" and is ignored only if the `runAsNode` fuse is disabled (Electron docs, environment-variables and tutorial/fuses; the fuse defaults to enabled and electron-builder flips fuses only under an `electronFuses` key, which the repository does not set). The Electron binary as Node registers no Dock entry (checked 2026-10-06 through `lsappinfo`). Alternatives rejected: a bundled Node binary (a second runtime to sign and update, and a second module ABI for any native module), and a second Electron app instance without `RUN_AS_NODE` (a Dock icon, Chromium's startup cost, a singleton conflict). Consequence recorded as a guard: the fuse must stay enabled; M4 adds a packaged check that `@electron/fuses read` (devDependency `@electron/fuses`, exact) reports `RunAsNode is Enabled` on `pnpm build:app`'s output, so a later hardening child that disables it sees this document's reason first.

**The spawn.** `spawn(process.execPath, [modulePath, '--detached', supervisorDir], { detached: true, stdio: ['ignore', logFd, logFd], env, cwd: process.cwd(), argv0: 'maws-supervisor' })` then `child.unref()`. `detached: true` makes the child "the leader of a new process group and session" (Node docs, `options.detached`; setsid(2): no controlling terminal), so a terminal's SIGHUP, `pnpm dev`'s Ctrl-C and launchd's process-group kill at the app's exit never reach it; a `stdio` not connected to the parent is what lets it outlive the parent ("the process will not stay running … unless it is provided with a stdio configuration that is not connected to the parent"); `unref()` lets main exit without waiting. `argv0` names the process in `ps` (`command` and `-c`); `top` and, very likely, Activity Monitor read the kernel's name, which is the executable's (`MAWS` packaged, `Electron` in dev; M0 Q3, Decision Log); `process.title` is never set (under Electron's Node mode libuv's title setter checks the process into LaunchServices as a foreground app). `logFd` is `<supervisorDir>/host.log` opened for append, where stray stdout and stderr land; the supervisor's own logger appends to the same file through `fs` and rotates it at 8 MiB to `host.log.1`; Diagnostics offers "Open log". The environment is main's `process.env` with: `ELECTRON_RUN_AS_NODE=1`; `MAWS_USER_DATA`; `MAWS_HOST_MODE` and `NODE_OPTIONS` removed (Decision Log, M0); `MAWS_ENGINE_REPLAY`, `MAWS_E2E`, `MAWS_E2E_ENGINE_BIN`, `CLAUDE_CONFIG_DIR`, `SHELL`, `HOME` passed as they are (the host reads them today, §Grounding); `MAWS_RELAY_URL` deleted when `app.isPackaged`, as the utility fork does. The supervisor's environment is fixed at its spawn; a later app run with a different environment is served by the same supervisor until it restarts (the build handshake restarts it on a rebuild, which is when the environment of a dev run changes in practice).

**The directory.** `<userData>/supervisor/`, created with mode `0o700` (the default umask 022 leaves that as it is) and `chmod`ed `0o700` after creation so a pre-existing directory is corrected too. Files: `host.sock` (the socket), `host.lock` (JSON `{pid, procStart, protocol, buildId, socketPath, startedAt}`), `host.token` (32 random bytes as hex, `0o600`), `host.log`, `live.json` (the orphan ledger, §below). The socket path is `<supervisorDir>/host.sock` when its UTF-8 length is at most 103 bytes (`sockaddr_un.sun_path` is 104 bytes on macOS, `sys/un.h`; Node documents 103 as the typical macOS maximum; `/Users/new/Library/Application Support/MAWS/supervisor/host.sock` is 64 bytes), else `${os.tmpdir()}/maws-supervisor-<sha1(userData) first 12 hex>/host.sock` in a `0o700` directory (Chromium places its own singleton socket under `$TMPDIR` for the same reason); the lock records `socketPath`, so a client never computes the fallback itself. `/tmp` is never used (shared and world-writable).

**Start-or-connect (main).** `HostSupervisor` gains a transport per host: `utility` (today's code, untouched) and `detached`. The detached transport is a state machine; two engineers must build the same one, so its states, events and transitions are fixed here. Timeouts: `CONNECT_TIMEOUT_MS = 1_000`, `HELLO_TIMEOUT_MS = 2_000`, `START_TIMEOUT_MS = 15_000` (one budget for the whole attempt, exit-3 loops included), `PID_POLL_MS = 200`, `WAIT_RETRY_MS = 5_000`.

| State (`HostState.state` shown) | On | Next |
|---|---|---|
| `connecting` (`starting`): read `host.lock`; connect to its `socketPath`, else the default path | connected | `handshaking` |
| | `ENOENT`/`ECONNREFUSED`/connect timeout, and the lock names no live pid (dead, or `procStart` differs, or no lock) | `spawning` |
| | connect refused but the lock's pid is alive with its `procStart` (a supervisor between its lock and its `listen`, or one exiting) | retry the connect every `PID_POLL_MS` until the attempt budget ends; then `crashed` with the reason "a supervisor (pid N) holds the lock and does not answer" (Diagnostics shows it; `host.restart` offers to kill it by pid after a `procStart` check) |
| `handshaking` (`starting`): read `host.token`, send `hello`, hand the socket's leftover bytes after the first line to the `SocketPort` | `welcome`, same wire fingerprint | `ready` (then the resync and the `ready` line, §3); a different build id with the same wire arms the update path of §6 |
| | `refuse {reason: 'token'}` | re-read the token and retry once (a supervisor rotated it while starting); a second refuse → `crashed` with the reason |
| | `refuse {reason: 'wire' \| 'protocol'}` | §6's table: `exit {when: 'now'}` and `spawning` once the pid is dead when nothing is live; else `waiting` |
| | hello timeout, or close before `welcome` | the lock's pid alive → `connecting` (retry); dead → `spawning`; past the attempt budget → `crashed` |
| `spawning` (`starting`): spawn the candidate as above | the candidate exits 3 | `connecting` (another supervisor holds the lock) |
| | the candidate exits with any other code before a hello succeeded | an unexpected exit: C1's ladder (backoff 0.5 s, 2 s, 5 s; three within 60 s → `crashed` for good) |
| | the socket accepts a connect | `handshaking` |
| | the attempt budget ends with the candidate alive and never answering | kill the candidate (SIGTERM, 2 s, SIGKILL, after a `procStart` check of its pid); `crashed` with `HostStatus.reason: 'held_lock'` |
| `ready`: serving | close after main sent `exit`, `host.stopAll` (through `restartSupervisor`), or armed `exit {when: 'idle'}` (main remembers which) | `restarting` without a crash count; `spawning` once the welcomed pid is dead (polled every `PID_POLL_MS`, bounded by the attempt budget) |
| | close after `stopAllForQuit()` (the quit path, §5) | `stopped`: terminal, nothing respawns during a quit |
| | `refuse {reason: 'replaced'}` | `crashed` with `HostStatus.reason: 'replaced'`, no respawn and no toast: another client holds the supervisor (the single-instance lock makes this a probe or a bug, never a second app on this profile); a relaunch of the app connects anew |
| | close with the welcomed pid still alive and `procStart` unchanged (the 256 MiB backpressure close, a socket error) | `restarting` without a crash count and without the crash toast; `connecting` after the first backoff step |
| | close with the welcomed pid dead | an unexpected exit: the crash count, the toast (§"The crash"), `restarting`, `spawning` after the backoff |
| `waiting` (`crashed`, with `HostStatus.reason: 'incompatible'`): an incompatible supervisor still runs sessions (§6) | every `WAIT_RETRY_MS` | `connecting`; `engineHostSettled` (`src/main/sessions/service-register.ts`) settles so `session.*` handlers answer `host_unavailable` instead of hanging |
| `stopped` (after `stop()` or `stopAllForQuit()`) | — | terminal: the socket closed, no `exit` sent, nothing restarts |

A **client**, everywhere in this document, is a connection whose `hello` was answered with `welcome`; a connection that has not sent a valid `hello` within `HELLO_TIMEOUT_MS` is closed by the host and never counts as connected (so it cannot hold off the idle clocks or invalidate the shell capture).

Requests made while `starting` or `restarting` are held (each still under the 10 s `REQUEST_TIMEOUT_MS` from its dispatch) and sent at `ready`; they fail `host_unavailable` only on `crashed` or `stop()`. Today's utility path has this property for free (the `MessagePortMain` exists before the child answers, `supervisor.ts:103-116`), and the renderer's connect-time reads (`engine.sessions`, the transcript's first `session.events`) depend on it.

**The lock.** The candidate takes it, never main, so two starters (a dying supervisor and a new app, or `pnpm dev` restarting main twice) have one arbiter. Atomic creation with content: write `host.lock.<pid>` (the JSON of §"The directory" with the candidate's pid and `procStart`), then `link(host.lock.<pid>, host.lock)` and unlink the temporary; `link` fails `EEXIST` when a lock exists, and a reader never sees an empty lock. On `EEXIST` the candidate reads the lock: the pid dead (`process.kill(pid, 0)` throws `ESRCH`), or `ps -o lstart= -p <pid>` under `LC_ALL=C TZ=UTC` (C4's holder check, `src/engine-host/fs/holders.ts`) differing from the recorded `procStart`, or the file unparseable → stale; a pid alive with its `procStart` (`EPERM` reads as alive) → live, exit 3, whatever its socket does. A live pid is never stale: a supervisor between its lock and its `listen`, or one in its exit order, must not lose its files to a candidate; main's attempt budget bounds the wait for one that never answers. Breaking a stale lock is serialised, since two candidates that both read the same stale lock would otherwise unlink each other's fresh locks: the breaker creates `host.lock.break` with `wx` (a break file older than 10 s is itself stale and is unlinked first), re-reads `host.lock` under it, unlinks it only if it still names the same stale pid and `procStart`, removes the break file, and retries the link; a candidate that cannot create the break file waits `PID_POLL_MS` and retries the link. The breaker never touches the socket file. The winner writes a fresh token, unlinks any leftover socket file (the kernel never removes one, unix(4); at this point no live supervisor can own it, since a live one holds the lock), listens, `chmod`s the socket, and only then is reachable; the orphan sweep runs after `listen`. Liveness for every later decision is a successful hello, never the pid alone (pid reuse is what `procStart` guards).

**Lifecycle in the supervisor.** `starting` (lock, token, listen, sweep) → `serving` (zero or one client) → `exiting`. One exit order for every reason: (1) `server.close()` so no new client connects; (2) the ladder for every live row through `engine.shutdown`'s body with `graceMs: 3000`, and the plugin runner stopped; (3) `live.json` cleared only if its `owner` is this pid and `procStart`; (4) the socket file and the lock unlinked only if the lock still names this pid and `procStart` (a successor that replaced a stale lock keeps its files); (5) the client connection closed; (6) exit 0. Exit reasons: `idle`, `stopAll`, `exit` (the socket layer's `exit {when: 'now'}`), `exitWhenIdle` armed and the last live row gone, a fatal error (exit 1, which skips (3) and (4) so the successor's staleness check finds the lock and the ledger).

**Idle exit, and idle rows.** The supervisor exits after `idleExitMs` with **no client connected and no live row** (live: `process` in `starting | initializing | ready | exiting`). The clock starts at the later of the last client's disconnect and the last live row's exit, resets whenever a client connects or a row is launched, and is checked when it fires, not trusted blindly; the exit order above makes a connect in the window see a closed socket, so that client treats the supervisor as absent and starts a fresh one. `idleExitMs` comes from `host.configure` (main pushes `settings.supervisor.idleExitMinutes × 60_000`, or `null` for never) and defaults to 10 minutes before the first push. Kept idle sessions must not hold the supervisor and their memory forever: **while no client is connected**, and always while `exitWhenIdle` is armed, a row that has had no hard reason (budget.ts `hardReasons`: no turn, no work in flight, no non-ambient background task, no pending request or ask, no queued message, no held peer message, no stateful MCP server) for `idleExitMs` is stopped with reason `idle`, a release like the budget's: `process.exited.reason` and `EngineSessionStatus.exit.reason` gain `'idle'` beside `'budget'` (`src/shared/graph/events.ts`, `src/shared/engine/status.ts`), and everything keyed on `reason === 'budget'` today (the digest's released mark and idle phase in `src/main/sessions/digest.ts`, the normaliser's exit row, the process table's `released` set that exempts the row from exited-row pruning, `process-table.ts`) treats `'idle'` the same, with the `budget` detail `null`; the session resumes from disk at the next use as a released one does (§4.4). The clock for a row starts when its last hard reason clears or the client disconnects, whichever is later. A row with a hard reason is kept as long as it holds one (a turn in flight, a question waiting). The release runs whether or not `engine.memoryBudget.enabled` is on: its reason is that no app is connected to use the process, not memory (ruled by A-29 (1), which amends charter §4.4's "never a fixed timer" for exactly this clock). Exited rows alone never hold the supervisor: their rings are a convenience and the journal and the disk path answer them after an exit. (Residue 11 and 21, ruled by A-29.)

**Stop all.** `host.stopAll {graceMs}` runs the quit ladder for every live row and stops the plugin runner (the body of `engine.shutdown`), answers `{stopped, forced}`, then exits as `stopAll`. Main treats the disconnect that follows as deliberate (state `restarting` without a crash count) and starts a fresh supervisor once the welcomed pid is dead, because `dispatch` answers `host_unavailable` while no host is connected and the next launch would otherwise fail; the fresh one idles out if the app quits. `engine.shutdown` closes the process table's admission for good (`ProcessTable.shuttingDown`, `process-table.ts:75, :110, :314`) and the plugin runner's (`runner.ts:180, :221`), so a host that ran it can never launch again: in detached mode every path that stops all sessions exits the supervisor (Stop all, an ordinary quit, §5), and in `utility` mode `host.restart {stopSessions}` kills the utility host and forks a fresh one (C1's `launch`) instead of calling `engine.shutdown` on a host that stays.

**The orphan ledger and sweep.** The process table maintains `<supervisorDir>/live.json`: `{owner: {pid, procStart}, rows: [{appSessionId, pid, procStart, launchId}]}` for every live row, rewritten (temp file and rename) at every launch and exit. A starting supervisor reads it after `listen`: when the `owner` is dead (or its `procStart` differs), for every row whose pid is alive with the recorded `procStart` it sends SIGTERM, waits 5 s, sends SIGKILL, counts the result in `host.supervisorStatus.orphansKilled`, and then writes its own ledger; when the owner is alive the sweep is skipped (that supervisor's engines are its own). Those orphans lost their stdio with the dead supervisor and no process can reach them again. M0 Q1 records whether the engine exits on its own when its stdin closes; if it does within a few seconds, the sweep still runs (it finds nothing) and the finding goes into Surprises & Discoveries.

**Long-lived host hygiene.** Journal pruning (today at host start) also runs every 24 h; the login-shell capture (today cached per host process) is invalidated when a client connects, so the next launch recaptures the owner's shell once; the models cache and the state store are per-file and unaffected.

**The crash of a supervisor** (G3). Main sees the socket close without a `stopAll`, an `exit` or a restart it asked for → the C1 ladder as today (`crashed`, backoff, restart; three in 60 s → `crashed` for good); every main-side listener already handles a host leaving `ready` (statuses forgotten, broker items cleared, self holders reset, re-sync at `ready`). New: main records the fact (`host.status` carries `lastExit: {code, signal, at, interrupted}`; `code` and `signal` are known only for a supervisor this app run spawned, `null` otherwise) and the renderer shows one toast through `src/renderer/src/stores/notices.ts` (`toast()`, level `warning`, id `supervisor.crashed`): "The session supervisor stopped unexpectedly (exit <code>); N sessions were interrupted. Their transcripts are on disk; open one to resume.", the parenthesis omitted when the code is unknown, where N is the count of rows that were live at the last status; the successor's sweep handles the orphans; sessions resume from disk through the paths that exist (the index record, `diskEvents`, C10's resume).

### 2. The socket protocol

**Framing.** Newline-delimited JSON over the Unix socket, one message per line, UTF-8, a 64 MiB line cap on both ends (the engine transport's cap, `MAX_LINE_CHARS`); a line over the cap closes the connection with a log line. Inside the lines, after the handshake, the messages are the host protocol's `req`, `res` and `evt` exactly as `src/shared/ipc/host-protocol.ts` defines them, so `createHostRuntime(...).serve(port)` serves a `SocketPort` (an object implementing `HostPort` over a `net.Socket`) with no change to a handler, and main's `receive`/`answer`/`dispatch` run unchanged over the same `SocketPort` on the client side. Backpressure: the writer respects `socket.write`'s return value only for logging; a client whose `socket.writableLength` exceeds 256 MiB is stalled and is closed by the host (the client reconnects and the connect burst and resync restore it). Unix sockets have no Nagle and no partial-message problem beyond the splitter.

**The socket layer** (`src/shared/host/socket-protocol.ts`, zod schemas, `SOCKET_PROTOCOL = 1`):

```ts
ClientHello   = { t: 'hello', protocol: number, token: string, buildId: string, wire: string, appPid: number }
ServerWelcome = { t: 'welcome', protocol: number, buildId: string, wire: string, pid: number, startedAt: string, liveSessions: number, rows: number }
ServerRefuse  = { t: 'refuse', reason: 'token' | 'protocol' | 'wire' | 'replaced', protocol: number, buildId: string, wire: string, liveSessions: number }
ClientReady   = { t: 'ready' }                        // the client has pulled what it needs; stream from here (§3)
ClientExit    = { t: 'exit', when: 'now' | 'idle' }   // only on a connection whose token checked out; stable across protocol versions by rule
```

`wire` is the **wire fingerprint**: the first 16 hex of the SHA-1 over `JSON.stringify(z.toJSONSchema(…, { unrepresentable: 'any' }))` of what crosses the main ↔ engine-host wire and nothing else: every command of `src/shared/ipc/schema.ts`'s `commands` whose `owner === 'engine-host'` (input and output), and every event in `HOST_EVENTS`, a new exported list beside `events` naming the events the engine host emits (`session.*` host events, `engine.budget`, `fs.*`, `plugins.*`, `deliverables.changed`, `maws.pane.show`, `maws.artifact.capture`, `side.*` host events, `host.supervisorStatus`; the runtime's `emit` refuses an event not in the list, so the list cannot drift from the emitters), in name order, computed once per process at the first hello. Main-owned commands and main-emitted events (settings, layout, git, scm, attention, `host.status`) never cross the socket and are left out, or every settings version bump would strand kept sessions. Two builds that changed no host shape share it even when their build ids differ; a build that changed a `strictObject` on the wire does not, which is what decides whether an older supervisor can be served (§6). zod 4.6.5 exports `toJSONSchema` with that option; over the whole registry it takes about 40 ms and is deterministic (the document's second review measured 212 commands and 44 events).

The first line a client sends is `hello`; the first line the server sends is `welcome` or `refuse`. The server checks in this order and stops at the first failure: (1) the token: wrong or missing → `refuse {reason: 'token'}` and the connection is closed; nothing further on that connection is read; (2) the protocol: a different `protocol` → `refuse {reason: 'protocol'}`; (3) the wire: a different fingerprint → `refuse {reason: 'wire'}`; after (2) or (3) the connection stays open for one `exit` and nothing else (§6); (4) replacement: a second client whose token checked out replaces the one connected, which receives `refuse {reason: 'replaced'}` and is closed (the single-instance lock makes this the stale-connection case: an app that crashed whose socket the kernel is still closing, or a reconnect racing the old socket's close); (5) `welcome`. After `welcome` the server answers `req`s but emits no `evt` until the client's `ready` line; at `ready` it emits the connect burst synchronously and then live events (§3). `exit` is honoured only on a connection whose token checked out, before or after a `welcome`: `exit {when: 'now'}` runs the exit order; `exit {when: 'idle'}` arms exit-when-idle (the supervisor exits as soon as no row is live, client or not, with §1's idle-row release making "live" end).

**Disconnect semantics.** The host learns a dead client promptly (the kernel closes the descriptor; the server sees `end`/`close`); it drops the client, keeps every row running, drops events as the runtime does today when no port is connected, and lets the idle clock start if no row is live. A request in flight when the client dies completes in the host (its effect stands: a `session.send` is journaled and queued; a `session.stop` stops) and its answer is dropped; the client that reconnects reads the state back (`session.queue.list`, statuses). Main's pending requests fail `host_unavailable` exactly as on a utility host's exit.

### 3. Streams, sequence numbers and catch-up (X13 made precise)

This is the text the architect folds into §10 X13:

> **X13 — host transport invariance** [owner E10; binds E1, E2, E3, E7, E8 and anyone touching the host]. The engine host's request and event surface is transport-agnostic: the host serves X2 commands and emits X2 events through C1's envelope (`hello`/`req`/`res`/`evt`) on whatever port carries it (a `MessagePortMain` in `utility` mode, a Unix socket in `detached` mode), and no host API assumes the host dies with the app, that a client is connected, or that it shares memory with main. **Sequence numbers.** Every live launch's events carry the launch's journal `seq` (monotonic within the launch; several events may share a row's seq; `seq: null` marks an event main synthesised); the stream's identity is `(appSessionId, launchId)`, read from `session.status`; a client that holds events of another launch of the same session discards them when the launch changes. **The tail request** is `session.events {appSessionId, afterSeq, limit}`: `afterSeq: null` means the launch's start; the answer comes from the ring (5,000 events while live, 500 once exited) and beyond it from the launch's journal through a fresh Normalizer (ids and seq reproduced), `complete: false` with `lastSeq` as the next cursor; a session with no stream in the host answers from the disk (`seq: null`). **Consumers deduplicate by event id, never by seq.** **Connect.** A client that connects or reconnects first pulls what it needs by command after the handshake (`engine.sessions`, then each row's `session.events` from the launch's start; the renderer's own reads too), then sends the socket layer's `ready` line; the host emits no event to a client before it, and at it emits the host's current state as ordinary events: for every row `session.status`, `session.queue`, `session.brokerItems`, `session.catalogChanged` (when a catalog exists), then one or more `session.eventBatch` carrying the events of that row no client has received yet (the host keeps a delivered cursor per stream), then `engine.budget`, `plugins.changed`, and the latest `plugins.operation` of every operation still running; live events follow. A client re-derives everything else it shows by command (`maws.asks.list`, `side.question.list`, `deliverables.list`, `fs.state`). **Host-held state** is host memory or host-written files, listed per piece with how it survives the app's absence (this document's §Design 4); events emitted while no client is connected are dropped, never queued, because the state they announce is re-derivable at connect and the undelivered tail covers the events themselves. **Bridges** from the host to the app (`maws.pane.show`, `maws.artifact.capture`) fail fast with a tool error naming that MAWS is not open when no client is connected, and otherwise keep their deadlines (8 s, 45 s). **Main** folds each row's digest from `session.events {afterSeq: null}` before its `ready` line and thereafter drops, per `(appSessionId, launchId)`, every event at or before the position its fold reached, so no digest folds an event out of order or twice; its other listeners of `session.eventBatch` see the undelivered tail once.

**The delivered cursor.** `SessionStream` records, per stream, the last event written to a connected client as its ring position and event id (`delivered: {index, id} | null`); a seq is not enough because one journal row can yield several events and a live batch may split a row at 500 (`session-stream.ts:79`). `trim()` splices the ring's front in chunks (`:77, :99-101`), so it subtracts the dropped count from `delivered.index` and clears `delivered` when the index falls below zero (the ring rolled past it); before a burst the stream checks `ring[delivered.index]?.id === delivered.id` and treats a mismatch as rolled too. At the client's `ready`, after the row's status, queue, broker items and catalog, the stream cancels its batch timer and clears `pending` (those events are in the ring and undelivered; delivering them in the burst and again at the flush would duplicate them), emits the ring's events after `delivered` in batches of 500, and sets `delivered` to the ring's last event. If `delivered.id` is no longer in the ring (the ring rolled), the burst emits what the ring holds and logs the gap (`meta` line `tail_gap` with the ids); main's fold and the renderer's hydration rebuild from the journal, and derived state for the gap (an attention item from an exit inside it, a side-thread summary) is not raised, which §9 records. "Written" is not "read": a client that dies with bytes in flight loses them for its derived listeners the same way; a batch still pending at a disconnect was never written and counts as undelivered. Because the burst carries only events no client received, a window never sees an event twice through it (a window exists only while a client is connected, and every event delivered while it was connected reached it), so the burst is relayed to windows exactly as live batches are. The utility transport uses the same cursor and the same `ready` step (main sends it over the `MessagePortMain` too), so the harness exercises the code.

**Why the undelivered tail is delivered as live batches.** Every main-side listener of `session.eventBatch` (the digest fold, the attention service's derivations, E3's side-thread summary tap, launch-watch, replay progress) then sees exactly the events that happened while no client watched, once, in order, as if the app had been there: a turn that ended while the app was away is summarised once, an exit that lost approvals raises its Needs-you item, and the renderer's hydration dedupes the overlap by id. The alternative, replaying the whole launch to every listener, was rejected because derivations are not all idempotent across a replay of history (an attention item retired last week would be re-derived); replaying nothing was rejected because derived state would silently miss what happened while the app was closed.

**Main's resync, and why it comes before `ready`.** The digest fold is order-dependent (`foldEvents`, `src/main/sessions/digest.ts`: a `turn.ended` folded before the `turn.started` it follows leaves the session working; a request folded after its resolution leaves `pendingRequests` above zero), and its id window is 2,000 (`SEEN_WINDOW`), smaller than a tail. So main pulls before it streams: at `welcome` the transport transitions to `ready` (so `dispatch` works and `engine.configure`, `engine.policy.set` and `host.configure` push), then `hostEventSource` (`src/main/sessions/index.ts`) runs the resync: `engine.sessions`; for every row `session.events {afterSeq, limit: 2000}` paged until `complete`, where `afterSeq` is `null` for a row main has not folded this app run or whose `launchId` changed, and `folded.lastSeq` for a row of the same launch main already holds (an in-run reconnect after a backpressure close must not re-fold a live digest's history), each page folded through `writer.fold` with the row's status applied first (from `engine.sessions`) so `live(appSessionId)` is right; it records per row `folded: {launchId, lastSeq, idsAtLastSeq}` (the ids of the last row's events, since a row's events share a seq); then the transport sends the `ready` line. The burst and every later batch pass a filter before `writer.fold`: an event of a folded launch with `seq < lastSeq`, or `seq === lastSeq` with its id in `idsAtLastSeq`, is dropped for the fold only (every other listener and the windows still receive the batch, since for them the events are new); `seq: null` events pass. The resync is bounded at `RESYNC_BOUND_MS = 30_000`: past it the `ready` line goes anyway, the rows not yet folded are logged, and their digests fold from the tail with the filter empty (today's degraded-start behaviour). A host transition before `ready` cancels the resync. The resync never emits to windows. The renderer needs no new hydration: a fresh page hydrates every transcript from `session.events` as today and reads `engine.sessions` at connect. After a reconnect with windows open (a supervisor crash and restart, Stop all, Restart now), the renderer re-reads `engine.sessions` when `engine.hostState` regains `ready` (`src/renderer/src/ipc/events.ts`'s connect-time read, run again at the transition; Task 3.3), and a transcript already live keeps applying batches and dedupes by id. What a reconnect cannot restore is stated in §4.

### 5. The quit flow

The question gains an answer. `QuitAnswer` becomes `'quit' | 'when_idle' | 'cancel' | 'save_all' | 'keep'`. In `detached` mode, when the report is non-zero and no files are unsaved, the buttons are `['Quit and keep sessions running', 'Quit', 'Quit when idle', 'Cancel']` (macOS lays four buttons out vertically); `defaultId` is the keep button when `settings.supervisor.keepRunningDefault` is true, else Quit; `cancelId` stays Cancel. With unsaved files E5's question comes first and is unchanged; after Save all, the ordinary question (with keep) follows as the loop does today. In `utility` mode and when the report is all zero, nothing changes: an unbusy quit stops every live session through `engine.shutdown` as today (idle sessions resume from disk transparently, and a supervisor holding nothing idles out), which is the reading of "the keep-running default" that keeps the setting a dialog default rather than a silent behaviour change (ruled by A-29: an unbusy quit stops idle sessions as today and Keep is offered only when the busy report is non-zero; the owner may overturn it).

`keep` skips `shutdownEngine` and `killEngines`, logs `quit-guard: … answered keep, N sessions kept`, and calls the one final `app.quit()`. `hosts.stop()` at `will-quit` stops the pty host as today and, for a detached engine host, closes the socket without any `exit` message, so the supervisor keeps serving; for a utility engine host it kills it as today. Every other quit in detached mode (`quit`, a wait that reached zero, an all-zero report) calls the supervisor's `stopAllForQuit()` in place of `engine.shutdown`: it sends `host.stopAll {graceMs: 5000}`, awaits the answer bounded by the same `SHUTDOWN_BOUND_MS`, and moves the transport to `stopped` first, so the close that follows spawns nothing (a respawn during a quit would leave a detached, unconfigured supervisor behind every ordinary quit); the sessions stop and the supervisor exits at once rather than idling out, because a supervisor that ran `engine.shutdown` can never launch again (§1 "Stop all") and a relaunch inside the idle time would otherwise connect to one that refuses every launch. `killEngines` past the bound still works unchanged: the engines are the supervisor's children and `hostPid()` is the supervisor's pid. Under `MAWS_E2E=1`, `MAWS_E2E_QUIT_ANSWER=keep` is accepted when offered. The `terminalsUnknown` and busy-terminal counts stay in the report: terminals cannot be kept, and the question's detail gains the line "Terminals close with the app." when any terminal is busy and keep is offered.

**Startup recovery with kept sessions.** `SessionService.start` (`src/main/sessions/service.ts`, after `host.ready`) assumes every session died with the app: it marks in-flight starts failed ("MAWS quit before the session started", `recovery.ts`), forgets every bootstrap id, and removes the record of a launched session whose first message was never recorded. A kept session can be any of those. In detached mode, recovery first reads `engine.sessions` once the transport is `ready` (the `host.ready` wait, `engineHostSettled`, also settles on `crashed`, which includes `waiting` and `held_lock`): when it answers, an intent whose row is live (`process` not `exited`) is handed off, never failed or removed; its record stays bound to the row's engine id, and a first message still queued in the host's state file is left to the host (C3's queue persists it); a live **bootstrap** row (a trust bootstrap with no record) is stopped (`session.stop`) and forgotten, since nothing will drive it. When `engine.sessions` cannot be answered (`host_unavailable`: the host is `crashed`, `waiting` or `held_lock`), recovery runs none of its destructive steps (no failure marked, no record removed, no bootstrap forgotten) and runs again at the next `ready`; the kept sessions it would have destroyed are live on a supervisor main cannot yet reach. Everything with no live row recovers as today.

**Terminals are lost on relaunch (G4).** The pty host dies with the app on every quit, kept sessions or not. Today a restored terminal tab whose pty cannot be adopted opens a new shell silently (`src/renderer/src/tools/terminal/index.ts`, `leave()` and the re-adoption path). After E10 the same respawn happens, and the pane says what happened: a terminal tab restored from the layout that carried a `ptyId` from a previous app run (the persisted fact: the tab's `ptyId`; the trigger: adoption found no pty for it after a relaunch, as opposed to a renderer reload, which re-adopts) shows one dismissible line above the new shell, `TERMINAL.lostAtQuit` ("The previous shell closed when MAWS quit"), with no other change of behaviour; the action is the shell already respawned. It applies after every relaunch. `e2e:terminal`'s restore expectations are re-run in M4 and amended only for the line's presence. No toast: the pane is the report.

### 6. The version handshake and updates

**Build id.** `buildId` is the first 16 hex characters of the SHA-1 of the engine-host entry file's bytes, computed by main from the `?modulePath` path and by the supervisor from `process.argv[1]` (the same file, in dev or inside `app.asar`), cached per process. It changes with every rebuild of the host (electron-vite re-emits the chunk; `pnpm dev` restarts main with a new hash when host code changed) and with every app update, and agrees between a main and a supervisor from one build. `__MAWS_VERSION__` (package.json's version) alone was rejected: it does not change between dev rebuilds, which is when a stale supervisor is most likely and most confusing.

**Rules at connect.** Serving an older supervisor is safe only when the wire is unchanged: every X1 event is a `strictObject` and one invalid event drops its whole batch, a changed `EventsSnapshot` fails `session.events` with `internal` and the transcript never hydrates. The wire fingerprint (§2) is the test; the build id decides only whether to restart when idle.

| `welcome`/`refuse` says | Main does |
|---|---|
| same protocol, same wire, same build id | serve; state `ready` |
| same protocol, same wire, different build id, `liveSessions === 0` | send `exit {when: 'now'}`, wait for the welcomed pid to die, start a fresh supervisor (state stays `starting`); nothing is shown |
| same protocol, same wire, different build id, `liveSessions > 0` | serve; send `exit {when: 'idle'}`; show the banner `supervisor.updated`: "MAWS was updated. N sessions are still running on the previous version's supervisor; MAWS moves to the new one when they become idle." with **Restart now** (stops them: `host.stopAll`, then a fresh start) and no other action; new sessions launched meanwhile run on the old supervisor, and the banner says so in its detail |
| `refuse {reason: 'wire' \| 'protocol'}`, `liveSessions === 0` | `exit {when: 'now'}`, then a fresh start once the pid is dead |
| `refuse {reason: 'wire' \| 'protocol'}`, `liveSessions > 0` | `waiting` (§1's table: no host, `session.*` answers `host_unavailable`, the connect retried every 5 s); the banner `supervisor.incompatible`: "MAWS was updated and cannot talk to the previous supervisor, which still runs N sessions." with **Restart now** (`exit {when: 'now'}`, then a fresh start) and **Wait** (`exit {when: 'idle'}` is armed; §1's idle-row release ends "live" for sessions that go idle, so the wait ends by itself) |

Consequence stated for the Purpose: a session survives an app update when the update changed no X2 shape; an update that changed the wire stops kept sessions at the owner's Restart now or when they go idle, and their transcripts resume from disk.

Main remembers that it armed `exit {when: 'idle'}` (or sent `exit {when: 'now'}`, or `host.stopAll`): the next close of that connection is deliberate (state `restarting`, no crash count, a fresh start at once), not a crash. The socket layer promises, for every future protocol version, that `hello`'s first three fields, `refuse`'s shape and `exit` keep their meaning; a child that bumps `SOCKET_PROTOCOL` owns the migration. The app's binary may be replaced under a running supervisor: the running process keeps its mapped executable and its loaded modules (the bundle is one chunk plus `zod`, both loaded at start), so nothing is read late from a replaced asar; the executor checks the chunk still has no dynamic `import()` at M1 (a guard test greps the built chunk).

### 7. What moves into the host and what stays in main

Nothing moves between processes: everything G4 names (the memory budget, the holder registry, the launch environment capture) already runs in the engine host (`ProcessTable`, `fs/holders.ts`, `shell-env.ts`); what moves is the host itself, out of the app's process tree. Main keeps the index (SQLite), the git and scm services, the attention service and its store, the read model, the layout, settings, the pty host (terminals), voice, the browser (E4) and the quit guard. Main's own login-shell capture (E6's runners) is unaffected. The ClaudeUsage relay and the owner's gateway settings pass through unchanged: `RELAY_URL` is resolved in the host from its environment as today, and the gateway fields reach each launch through `engine.configure` and the launch spec as today.

### 8. The harness flag (G5)

`MAWS_HOST_MODE` is read once in `createHosts()`: `utility` keeps today's fork for both hosts; `detached` uses the socket transport for `engine-host` and the fork for `pty-host`. The default is `utility` when `MAWS_E2E === '1'` or `MAWS_HARNESS === '1'`, else `detached`; `e2e/support/launch.ts` sets nothing, so every existing suite runs unchanged and E10's own spec passes `MAWS_HOST_MODE: 'detached'` through `opts.env`. The detached transport is unit-tested with a real socket in a temp directory (fast, no Electron) and e2e-tested by `pnpm e2e:supervisor` (M4).

### 9. Failure semantics

| Failure | Behaviour |
|---|---|
| The socket cannot be created (path too long after the fallback, `EACCES`) | the supervisor exits 1 with the reason in `host.log`; main reaches the crash limit and shows `crashed` in Diagnostics with "Open log"; `MAWS_HOST_MODE=utility` is the escape hatch |
| A stale lock and socket (SIGKILLed supervisor) | the candidate's staleness check (dead pid, or `procStart` mismatch, or an unparseable lock; never a refused connect) breaks the lock under `host.lock.break`, links its own, unlinks the stale socket and takes over |
| Two starters at once | one `link` wins; the loser reads a live pid and exits 3; main connects to the winner. Two breakers of one stale lock: one holds `host.lock.break`, the other retries and then finds a live lock |
| A quit while the supervisor exits (`stopAllForQuit`) | the transport is `stopped` before the close; nothing respawns |
| The client dies | the host drops it, keeps rows, starts the idle clock if nothing is live; requests in flight complete, answers are dropped |
| The supervisor dies | main's C1 ladder restarts it; the successor sweeps orphans from `live.json`; the notice names the interrupted sessions; sessions resume from disk |
| The supervisor is flapping (three unexpected exits in 60 s) | `crashed` for good as today; Diagnostics shows it; a relaunch of the app tries again |
| A request outlives the 10 s router deadline | `timeout` as today (bounded host commands answer their own `timeout` under 8 s) |
| Backpressure past 256 MiB | the host closes the stalled client; the reconnect's burst and resync restore state |
| The idle exit races a connect | `server.close()` and the unlinks come first in the exit order; the client sees a refused connect with the lock's pid alive, retries, then spawns once the pid is dead |
| A hello timeout, or a close before `welcome` | the lock's pid alive → retry the connect; dead → spawn; the attempt budget (15 s) bounds both |
| A close while the welcomed pid is alive (backpressure, `replaced`, a socket error) | reconnect without a crash count or a toast |
| An incompatible supervisor holds live sessions (`waiting`) | `session.*` answers `host_unavailable` (the settled waiter), the banner offers Restart now and Wait, the connect is retried every 5 s |
| A kept session the app's recovery would have failed or forgotten | recovery reads `engine.sessions` first; a live row is handed off (§5) |
| A client exits with the resync unfinished | nothing: the resync is main's; the host emitted no event before `ready` |
| `host.configure` never arrives (an old main) | the idle default of 10 minutes holds |
| The ring rolled past the delivered cursor | the burst sends what the ring holds, logs the gap, and the resync and the renderer's hydration rebuild from the journal; derived attention for the gap is not raised (documented) |
| `live.json` unreadable | the sweep is skipped with a log line |
| `runAsNode` fuse disabled in a later build | the spawn exits at once (Electron ignores the variable and runs the app) → the packaged check in M4 fails; Diagnostics shows `crashed` |

### 10. Security

The directory is `0o700`, the token and lock `0o600`; the socket file is `chmod`ed `0o600` right after `listen` (connect(2) on a Unix socket requires write permission on the file, unix(4)), and the directory's mode denies traversal to other users regardless. The token is the authentication a same-user process must present: it guards against another program on the owner's account connecting by mistake (Node exposes no peer credentials, so there is no stronger same-user check without a native addon, and cross-user access is already denied by the directory). No `req` is served before a `welcome`; a malformed line, an oversized line, an unknown `t` or a schema failure closes the connection. The socket layer logs the client's `appPid` in `host.log` at every connect. The supervisor's environment carries the owner's shell variables as the utility host's did (the launch allowlist `buildEnvironment` decides what an engine sees, unchanged); `host.log` holds no environment values (the journal's redaction posture holds: key names only in the spawn row, which the journal already keeps).

### 11. Settings, Diagnostics and the banner; copy

Settings version 10 (A-29 (4)) adds `supervisor: { idleExitMinutes: number | null; keepRunningDefault: boolean }` (defaults `10`, `true`; `idleExitMinutes` is an integer 1 to 1440 or `null` for never). The Engine section gains a **Background supervisor** group (no new section, so X14's `settings` enum is untouched): a status line ("Running since 14:02 · pid 48213 · 3 sessions · exits 10 min after the last session ends" / "Not running" / "Starting"), the idle time control (minutes; empty means never), the quit default control ("When quitting with work in flight: Keep sessions running / Stop them"), and **Stop all sessions and the supervisor** behind an inline confirm naming the live count. Diagnostics gains a `Supervisor` row beside the host rows: mode, pid, build (matches / differs), socket path, sessions held, idle exit, orphans killed at start, the last unexpected exit, and "Open log" (`shell.openPath` on `host.log` through a main handler). The update and incompatibility notices are banners of `src/renderer/src/stores/notices.ts` (`banner()`, ids `supervisor.updated` and `supervisor.incompatible`, replaced in place on every `host.status`, dismissed when the mismatch ends); the crash notice is a toast (above). All copy in `settings-tab/copy.ts` (`SUPERVISOR`), `src/renderer/src/app/copy.ts` (new; `SUPERVISOR_ROW`, `SUPERVISOR_NOTICES`), `src/renderer/src/tools/terminal/copy.ts` (new; `lostAtQuit`), and the quit guard's strings in `src/main/lifecycle/copy.ts` (new, main-side, since the native dialog's words live in main).

### 12. Replay parity

Replay sessions (`spec.replay`, `MAWS_ENGINE_REPLAY=1`) run in the host like live ones, as rows with a stream and a status; in detached mode they keep streaming while the app is away, paced by the e2e seam `MAWS_E2E_REPLAY_ROW_MS`, which is what `pnpm e2e:supervisor` uses to prove G2 without an engine. Nothing E10 adds is a transcript row, so the disk path draws the same rows as before; the one new X1-adjacent fact, `session.reconnect`'s reserved trigger `host_restart`, stays unproduced (a reconnect of the app to a running host is not an engine reconnect; the engine never restarted), recorded in the Decision Log.

### The host runtime (`src/shared/host/runtime.ts`, extended additively)

```ts
export type HostEmit = <N extends EventName>(name: N, payload: EventPayload<N>) => boolean;   // true when written to a connected, ready client
export interface HostRuntime {
  serve(port: HostPort): void;        // a second serve replaces the port (the previous client was closed by the caller)
  detach(): void;                     // no client: emits return false and are dropped
  setReady(): void;                   // the client sent `ready`: the onConnect hooks run synchronously, then events flow
  hasClient(): boolean;               // connected and ready
  onConnect(hook: () => void): void;  // registered by the engine ipc: the connect burst (statuses, queue, broker items, catalog, the tails, budget, plugins)
}
```

`runHost` (utility mode) calls `serve` at `hello` as today and `setReady` at main's `ready` line, which main's utility transport posts on the `MessagePortMain`: for a host with a registered `resync` (the engine host) after the resync, exactly as the detached transport does on the socket; for a host without one (the pty host) right after `hello`, so no `pty.*` event is ever held. For that, `src/shared/ipc/host-protocol.ts` gains, additively to C1's envelope, `HostReadySchema = z.strictObject({ t: z.literal('ready') })` and `HostMessage` gains `{ t: 'ready' }` (main → host); the runtime's `serve` accepts `HostRequestSchema | HostReadySchema` on the port and still drops anything else with a log line; `HostHelloSchema` is untouched. The bridges (`PaneBridge`, E2's `HostBridge`) take `hasClient` and answer `TOOL_ERRORS.appNotOpen` at once when it is false.

## Deferred

- Several app instances sharing one supervisor (a second client while one is connected is replaced, not served): one app per data directory holds (the single-instance lock), and a multi-window app is one client.
- A supervisor surviving user logout, and launching at login: unverified and out of scope (the supervisor is not a launchd agent).
- `Restart` (the updater's wording and flow, C12's deferred P1-R1 to P1-R4): the handshake and the banner are ready for it; the updater child wires them.
- Attention derived from a span the ring rolled past while no app was connected (a gap wider than 5,000 events of one launch): logged, not raised; a journal-driven derivation at connect is a later child if the gap is ever seen.
- Peer credentials on the socket (a native addon) if a stronger same-user check is ever wanted.
- A `session.reconnect` row for app reconnects, if the transcript should ever show "MAWS reconnected at 14:02".
