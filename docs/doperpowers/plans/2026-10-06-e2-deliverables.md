## Purpose

After E2 the agent has somewhere to put things and the owner has one place to find them. A file the agent delivers with `send_file` opens inside MAWS: a PDF or an HTML page in a frame that can reach nothing, a video or an audio file in a native player, an image inline, markdown and code in the viewer the owner already uses. An HTML page the agent registers with `artifact_create` becomes an artifact MAWS keeps a copy of, version by version, so `artifact_update` never loses the previous one and the owner can flip between them; the agent can ask MAWS for a screenshot of its own artifact and read the page's console errors, so it can check its work without the owner. The right panel gains a Deliverables tool: everything delivered in this session (or in every session), newest first, by kind; a row opens the viewer in the panel, Back returns to the list, and the viewer opens as a main tab when the owner wants room. Every delivery and every artifact version is a row in the transcript that opens the viewer, and a session opened from its transcript on disk shows the same rows. When E3's comment composer exists, the owner can click an element of an artifact and comment on it.

To see it: in a MAWS session, send *Write a self-contained HTML page dashboard.html with a red heading, register it with the maws artifact_create tool as "dash" titled "Dashboard", then take an artifact_screenshot and tell me what you see*; the artifact row appears, the Deliverables tool opens it, the model describes a red heading. Send *Make the heading blue and update the artifact*; the viewer offers v1 and v2.

## Terms

- **Record**: one X12 `DeliverableRecord` (`src/shared/maws/deliverable.ts`), a JSON file at `<userData>/deliverables/<appSessionId>/<id>.json`, written by the engine host (E1 residue 7). **Store**: those files, plus an artifact's version copies beside them. **Reader**: main's read-only view of the store (`src/main/deliverables/reader.ts`, new).
- **Deliverable**: what a record names: a delivered file (`kind: 'file'`, referenced in place, A-3), an artifact (`kind: 'artifact'`, versions copied under the data directory) or a screenshot (`kind: 'screenshot'`, E4's). **Artifact id**: the short name the agent gives an artifact (`artifact_create {id}`), unique within a session; distinct from the record's uuid (**deliverable id**).
- **Version**: one entry of `record.versions`, numbered from 1 in array order; `record.path` is the latest version's path.
- **Scheme**: `maws-deliverable:`, the privileged custom scheme main serves the store's files through (Design §3). **Frame**: the sandboxed `<iframe>` the viewer draws an HTML or PDF deliverable in. **Capture window**: the hidden offscreen `BrowserWindow` main renders an artifact in for `artifact_screenshot`.
- **Deliverables tool**: the X5 panel tool with id `deliverables` (`PANES.deliverable.toolId`, `src/shared/maws/panes.ts:16`). **Viewer**: its record view, also the body of the `deliverable` main tab.
- **Capture bridge**: the host→main request `artifact_screenshot` needs (the host has no window), E1's pane bridge generalised: an IPC event out, a host command back, a deadline.
- **Engine host**, **main**, **renderer**, **control request**, **`mcp_message`**, **tool result**, **tool error**, **X1 event**, **meta row**, **replay**, **fixture**, **conformance suite**, **scratch home**: as E1's Terms define them.

## Design (the residue §3 B leaves open, with reasons)

### 1. Ownership and data flow

The host owns the writes (X13): `send_file` already writes a record; `artifact_create` and `artifact_update` copy the HTML under the store and write or rewrite the record; after each write the host emits the IPC event `deliverables.changed`. Main owns the reads: a `DeliverableReader` over the same files serves `deliverables.list`, `deliverables.listAll` and `deliverables.get`, admits delivered paths to the files service, and serves the scheme. The renderer holds a `useDeliverables` store (records per session, the cross-session list, the console ring buffer) fed by the commands and the two events, and draws the tool, the tab and the rows from it. The agent's screenshot crosses the boundary twice: the host asks main through the capture bridge, main renders and answers through a host command, the host returns the image block. Nothing in the host waits on a window; everything that could wait has a deadline.

### 2. The store (G1)

The store stays files; no index table (Decision Log 1). Layout under `<userData>/deliverables/<appSessionId>/`: `<recordId>.json` (E1's record) and, for an artifact, `<recordId>/v<n>.html` (the copy of version `n`). `FileDeliverableStore.list` lists `.json` names only, so the version directories are passed over. One module holds the layout and the parsing for both processes, `src/shared/maws/deliverable-files.ts` (new; node-only, imported by the host's store and main's reader): `recordPath`, `versionPath`, `readRecords(dir)` (E1's `list` body: a vanished or malformed file passed over, other read errors rejected), `writeRecord` (temp file and rename).

The record is extended additively, every new field optional so E1's files parse unchanged: `artifactId?: string` (the agent's id; present on `kind: 'artifact'`), `updatedAt?: string` (the last version's time), and per version `toolUseId?: ToolUseId` (the call that added it) and `sourcePath?: string` (the path the agent named; the copy is `path`). `record.path` is the latest version's path. `title` is the tool's title; an artifact has no `caption`.

The host's `DeliverableWriter` gains `update(record)` (a rewrite through the same temp-and-rename), `get(appSessionId, id)`, `findArtifact(appSessionId, artifactId)` (the session's records filtered by `kind` and `artifactId`) and `copyVersion(appSessionId, recordId, n, sourcePath)` (reads the source whole with the size cap, writes `v<n>.html` through a temp file and a rename, answers the copy's path). Writes for one session are serialised in the host (one promise chain per `appSessionId`), so two `artifact_update` calls that overlap never interleave their version numbers; `readOnlyHint: false` on the two writers keeps the engine from running them in parallel in the first place (Design §6). `MemoryDeliverableStore` implements the same surface for tests.

The change event: `deliverables.changed { appSessionId, id, change: 'created' | 'updated' }`, emitted by the store itself: `FileDeliverableStore` (and `MemoryDeliverableStore`) takes an `onWritten(record, change)` callback and calls it after every settled `write` or `update`, so every writer announces its writes, `send_file` included (`send-file.ts` is untouched; it writes through the same store). The session wires the callback to a new `Listeners` channel `deliverableChanged`, relayed in `registerEngineIpc` as `paneShow` is. It is an IPC event, not an X1 event, for E1 residue 3's reason: a reload or a disk replay must not re-announce. The renderer's store re-reads the one record on it.

Main's reader keeps no cache: `list`, `get` and `admitted` read the session's directory on every call (a `readdir` and a few small JSON parses, milliseconds; the viewer's reads are per chunk of a megabyte and the admission check is a fraction of each), so a record written a moment ago by this host or by another MAWS process (E10's detached host) is found at the next read with no invalidation protocol. The cross-session list (G1) is `deliverables.listAll { limit? }`: main walks `<userData>/deliverables/*/*.json`, parses, sorts newest first, answers at most `limit` (default 200, maximum 500); on demand, when the tool's scope is All sessions.

### 3. The scheme, the frames and their policies (G3)

**The scheme.** `maws-deliverable://<recordId>/<appSessionId>/<n>`: the record's uuid as the host (lowercase hex and dashes, so URL case-folding changes nothing), the app session id as the first path segment (it may carry uppercase, `src/shared/engine/app-session-id.ts:7`, so it cannot be a host) and the version number as the second. `deliverableUrl(appSessionId, id, version)` and `parseDeliverableUrl(url)` live in `src/shared/maws/deliverable.ts` (pure strings) so the renderer builds the URL and main attributes frames and console messages by parsing it. Registered before `app.whenReady()` with `protocol.registerSchemesAsPrivileged([{ scheme: 'maws-deliverable', privileges: { standard: true, secure: true, supportFetchAPI: false, corsEnabled: false, stream: true } }])`, and handled on the window's default session and on the capture partition (`session.fromPartition('maws-capture')`) with one handler, `src/main/deliverables/protocol.ts`.

**The handler** serves exactly one file per URL and nothing else: GET and HEAD only (405 otherwise); the URL parsed; the record read through the reader (404 when absent, when `n` is not `1..versions.length`, or when the appSessionId fails `isSafeAppSessionId`); the file at `versions[n-1].path` opened by that recorded path, never by anything in the URL; a file no longer there answers 404 with a one-line plain-text body (the viewer never shows this body: it checks `deliverables.get` first, Design §4). Headers on every answer: `Content-Type` from `mimeOf(basename(path))` (`application/octet-stream` when unknown), `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`, `Cache-Control: no-store`, `Accept-Ranges: bytes`. A `Range` header is honoured with `206` and `Content-Range` from a bounded `fs.createReadStream` (video and audio seek through it); without one the whole file streams. For `text/html` the answer also carries `Content-Security-Policy: sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline' 'unsafe-eval' data: blob:; style-src 'unsafe-inline' data: blob:; img-src data: blob:; font-src data: blob:; media-src data: blob:; connect-src data: blob:; worker-src blob:; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'` (no `'self'`: a self-contained page needs nothing from any origin, and the only thing `'self'` would admit is another request to the handler, which 404s). The leading `sandbox allow-scripts` directive sandboxes the document wherever it loads: redundant with the viewer frame's attribute, and the whole sandbox for the capture window, whose document is top-level (Design §7). For an artifact's HTML (`kind: 'artifact'`) the handler also inserts the bridge script (Design §10) as the first element of `<head>`, or, when there is no `<head>`, right after the doctype (never before it: a script ahead of `<!doctype>` would put the page in quirks mode); a delivered HTML file (`kind: 'file'`) is served byte for byte. The app-wide policy `installContentSecurityPolicy` (`window.ts:33-41`) overwrites `Content-Security-Policy` on every response of the default session; its callback leaves a response whose URL begins with `maws-deliverable://` untouched, so the handler's per-answer policy reaches the frame (an e2e asserts an inline script runs in a viewer frame).

**Why not `file://`.** A `file:` document can load any local file as a subresource, carries no per-record admission, gives main no header to attach a policy to and no URL prefix to attribute console messages and requests by; the custom scheme admits exactly the store's records, one file per URL, with a policy per answer.

**The HTML frame** (`<iframe sandbox="allow-scripts" src={deliverableUrl(…)} referrerPolicy="no-referrer">`): scripts run (an artifact is interactive); no `allow-same-origin` (an opaque origin: the page can read nothing of the app, and nothing of its own storage), no `allow-top-navigation*`, no `allow-popups`, no `allow-downloads`, no `allow-forms`, no `allow-modals`. The CSP header blocks every fetch and every subresource that is not `data:` or `blob:`.

**The PDF frame.** The same scheme URL in an `<iframe>`; Chromium's own PDF viewer draws it, which needs `webPreferences.plugins: true` on the window (Electron's PDF viewer sits behind it; the window has no other plugin to enable) and may refuse to instantiate inside a sandboxed frame (the HTML specification's sandboxed plugins flag; whether Chromium 152's MimeHandlerView honours it for its own viewer is not documented). M3's first task decides by trial, in this order, stopping at the first that draws a PDF: (a) `sandbox="allow-scripts"`; (b) `sandbox="allow-scripts allow-same-origin"` (the frame keeps its `maws-deliverable://<recordId>` origin, which is the record's alone); (c) no `sandbox` attribute, the frame still a distinct origin and still under the main-side policies below; (d) pdf.js (`pdfjs-dist`, an exact devDependency, its viewer served through the scheme's own origin) only if Chromium's viewer draws in none of a, b, c. The outcome is a Decision Log line; the e2e pins whichever the executor chose.

**Main-side policies, for every frame whatever its sandbox** (defence in depth, and the whole defence for case c): on the window's session and the capture partition, `webRequest.onBeforeRequest({ urls: ['<all_urls>'] })` cancels any request whose `frame?.url` or `initiatorOrigin` begins with `maws-deliverable://` and whose own URL does not (http, https, ws, wss, file: all refused; `data:` and `blob:` never reach `webRequest`); `webContents.on('will-frame-navigate')` prevents a subframe navigation from a `maws-deliverable://` frame to any URL that is not `maws-deliverable://`; `session.on('will-download')` cancels an item whose URL or referrer begins with `maws-deliverable://`; `setWindowOpenHandler` already denies every new window (`window.ts:76`) and `will-navigate` every top-level navigation (`:77`); `webContents.setWebRTCIPHandlingPolicy('disable_non_proxied_udp')` on the app window and the capture window, since CSP does not govern WebRTC and STUN traffic never passes `webRequest` (the renderer uses no WebRTC; E9's dictation is a native helper). Under `MAWS_E2E=1` with `MAWS_E2E_OPEN_LOG` set, a cancelled navigation and a cancelled download append `blocked-navigation <url>` and `blocked-download <url>` to the seam log, so the e2e asserts the policies ran on the real session and webContents, not only that their predicates compute. The renderer's CSP (`csp.ts`) gains `frame-src 'self' maws-deliverable:` and `media-src 'self' maws-deliverable:` (`'self'` keeps the request card's `srcdoc` frame, which inherits the document's policy). Residual, recorded in the tracker: a page could still reach a TURN relay over TCP that it names; Chromium offers no per-session switch to disable WebRTC that this child knows of, and the agent's own artifact is the only author of such a page.

**Media.** `<video controls src={url}>` and `<audio controls src={url}>` against the scheme (the `media-src` addition), seeking through the handler's `Range` support, `preload="metadata"`.

**Images, markdown and code** draw through the existing viewer: `FileViewer.tsx`'s body is extracted as `FileBody({ tabId, appSessionId, path, readOnly })` (the mount, `Body`, the notices and the Wrap and Source controls; the path bar and E5's `EditorControls` stay in `FileViewer`), and the viewer store's `mount` takes `readOnly?: boolean`, kept on the entry and folded into `editable` (false whenever `readOnly`). The Deliverables viewer mounts `FileBody` with `tabId = 'deliverable:<id>:v<n>'` and `readOnly: true` (Decision Log 7). The reads go through `files.read`, which today refuses a delivered file outside the session's roots (`service.ts:147`): the service gains `admitted?: (appSessionId, realpath) => Promise<boolean>` in `FilesServiceOptions`, and `precheck` takes a purpose: `precheck(appSessionId, path, { admitDelivered })`. Only `read`, `openExternal` and `reveal` pass `admitDelivered: true`; `write` (E5's save), `list` and `watch` never do, so a delivered file outside the roots can be looked at and opened but never written through MAWS (a `send_file` of `~/.claude/settings.json` followed by Open as file and a save would otherwise write under `~/.claude`), and MAWS's own version copies under `userData` are never edited in place. With the flag, `precheck` consults `admitted` when no root contains `real0` and, when it answers true, treats `real0` as a root of its own for the rest of the boundary (`roots` extended with `[real0]`, which `under` accepts as equal), so `openConfirmed`'s step 5 and every later confirmation hold for exactly that file. Main wires `admitted` to the reader: true when the session's records name that realpath as a record's `path` or a version's `path` (realpathed at the check; the reader has no cache, Design §2). The same admission serves `files.openExternal` and `files.reveal`, which closes the tracker row at `docs/tech-debt-tracker.md:78`. `opensExternally` is unchanged (Decision Log 17): Open externally is offered for the kinds it names, wherever the file lives, and Reveal for everything. The admission is for the file alone, never its directory: the viewer store's mount watches `dirname(path)` first (`viewer-store.ts:429-436`), and for an outside file that watch is refused; the hold's `ready` settles on a refusal as on an install (`files/store.ts:20`), so the read still runs and the file is shown once, not followed. A deliverable is finished output, so the missing follow costs nothing the owner expects; Reload in the viewer re-reads it.

### 7. The capture (G4's `artifact_screenshot`)

The host cannot render; main can. `artifact_screenshot` parses, finds the artifact, picks the version (the two texts of Design §6), and asks main through the **capture bridge**: E1's `PaneBridge` generalised into `HostBridge<Request, Answer>` (`src/engine-host/tool-server/bridge.ts`; the pane bridge becomes `new HostBridge({ send: deps.paneShow, answerMs: PANE_ANSWER_MS })`, its tests unchanged in meaning), with `CAPTURE_ANSWER_MS = 45_000`. The request is the IPC event `maws.artifact.capture { appSessionId, requestId, deliverableId, version, width, height }` (a new `Listeners` channel `artifactCapture`, relayed by `registerEngineIpc`; registered so the supervisor admits it, not bridged to the renderer, which has no use for it); the answer is the host command `maws.artifact.captured { appSessionId, requestId, result: { ok: true, png: base64, width, height, consoleErrors: string[] } | { ok: false, error } } → { outcome: 'delivered' | 'not_pending' }`. Silence answers the timeout text; a refusal answers `MAWS could not capture the artifact: <reason>`; a withdrawn call or an exited process settles the bridge with nothing written (the pane bridge's rule). The PNG is capped at `ARTIFACT_SCREENSHOT_MAX_BYTES = 4 MiB` in main: a larger capture is resized to half its width once (`NativeImage.resize`), and if still larger answers `screenshot too large (<n> bytes); ask for a smaller size`.

Main (`src/main/deliverables/capture.ts`) listens to the event through `hosts.onEvent('maws.artifact.capture', …)`, runs at most two captures at once (a third waits; with the 20 s guard below a queued request is answered within 40 s, inside the host's 45 s; the engine may batch two screenshots, since the tool is read-only), and answers through `hosts.dispatch('engine-host', 'maws.artifact.captured', …)`. A capture: `new BrowserWindow({ show: false, width, height, webPreferences: { offscreen: true, sandbox: true, contextIsolation: true, nodeIntegration: false, webSecurity: true, partition: 'maws-capture', backgroundThrottling: false, disableDialogs: true } })` (no preload; the partition's session carries the scheme handler and the policies of Design §3; `setWindowOpenHandler` deny, `will-navigate` prevent, `setWebRTCIPHandlingPolicy('disable_non_proxied_udp')`). The document it loads is top-level, so the viewer frame's `sandbox` attribute does not reach it; the handler's `Content-Security-Policy: sandbox allow-scripts` directive does (Design §3), so the page runs under the same opaque origin, with no storage and no navigation, as in the viewer; `disableDialogs` makes `alert`, `confirm` and `prompt` return at once instead of blocking the load until the guard. `console-message` entries of level `error` are collected into the result (at most 20, each cut at 500 characters) and are not emitted as `deliverables.console` (Design §8: the row shows what the owner's viewer logged, not the agent's capture). Then `loadURL(deliverableUrl(…))`; on `did-fail-load` the error names the code and description; after `did-finish-load`, a settle of one `paint` event or 500 ms, whichever comes first (fonts and first animations); `webContents.capturePage()` → `toPNG()`; the window destroyed in `finally`; a 20 s guard on the whole, so main's answer always precedes the host's deadline. The window is offscreen (`offscreen: true`) for its deterministic `paint` events and because it never touches the desktop; the named fallback, should offscreen rendering misbehave, is a hidden window captured with `capturePage({ stayHidden: true })` after `incrementCapturerCount()`, which Electron documents as the way a hidden page is painted for a capture (`electron.d.ts:18095-18100`). The device scale factor is 1 (the capture is for the model, not a Retina display).

**The capture window is not an app window.** Main treats every `BrowserWindow` as the app's today: `startAttention` hooks `did-start-loading` on each one (`src/main/attention/index.ts:18-27`, which would reset the navigation relay on every capture load and queue attention navigations until the app page reloads), `focusWindow` takes `getAllWindows()[0]` (`:26`), and `activate` opens a window only when none exists (`src/main/index.ts:401-402`), so with the app window closed a capture window could be focused or keep the app from reopening one. ### 10. Comment mode on an artifact element (G6)

The frame is an opaque origin: the page's DOM is unreachable from the app, so the pick happens inside the page. The handler prepends the **bridge script** to every artifact HTML it serves (`src/main/deliverables/bridge-script.ts`, a string; Design §3): it listens for `message` events from `window.parent` only; `{ type: 'maws:pick', on: boolean }` turns picking on or off; while on, an overlay box follows the element under the pointer (positioned from `getBoundingClientRect`, never touching the element's styles), `click` in the capture phase is swallowed and posts `{ type: 'maws:picked', selector, label, text, rect }` to `window.parent` (`targetOrigin: '*'`: the frame cannot know the app's origin), `Escape` posts `{ type: 'maws:pick-cancelled' }`. `selector` is the element's id when unique, else a `tag:nth-of-type` chain from `body` (depth at most 12); `label` is `<tag>#<id>` or `<tag>.<first class>` with the first 40 characters of its text. The script writes nothing to the page's state and runs before the artifact's own scripts; a page that spoofs a picked message can only hand the owner an anchor they see before sending (Design §12).

The viewer's **Comment** action (artifacts only) sets `picking`, posts `maws:pick` to the frame's `contentWindow`, shows the hint "Click an element to comment on it · Esc cancels", and listens for `message` events whose `source === iframe.contentWindow` and whose data parses as a picked or cancelled message (a zod schema; anything else ignored). The seam's anchor type is the union E3 owns: if E3 has landed when M6 runs (its `anchor.ts` re-exports the shared type and `openCommentComposer` takes `Anchor`), the artifact anchor already fits the union and the composer opens with the destination control; if E3 has not landed, the stub is: the union widened in E5's `anchor.ts` beside `FileLineAnchor`, `openCommentComposer` falling to E5's placeholder sheet `showAnchor`, which the executor checks renders the new kind's `label` (extending it minimally if it reads `path` and `line`), and a Decision Log line plus a hand-back item naming the stub. ### 11. Failure semantics

- A tool refusal (a path that is not a regular HTML file, an unknown artifact id, a duplicate id, invalid arguments) is an `isError` result with the exact text of Design §6; nothing is written and no `maws.delivery.artifact` is emitted (the error is visible as the row's error).
- A store failure mid-call: the record is never half-written (temp and rename); `artifact_update` leaves the record as it was; the error names the path and the cause.
- A capture with no main (LiveHost, a detached host, main busy past the deadline): the tool error after 45 s; the engine withdrawing the call or the process exiting settles the bridge silently.
- A page that never finishes loading or fails to load: `MAWS could not capture the artifact: <reason>` within main's 20 s guard.
- A record whose file is gone: the viewer's missing state; `files.openExternal` and `files.reveal` answer their refusal text inline; the handler 404s; the transcript row still opens the viewer (which shows the state).
- A record that is gone (the owner deleted the JSON): the list no longer shows it; `show_pane` answers `deliverableNotFound`; a `deliverable` tab restores to the list with the notice; a row's Open shows the list with the notice.
- A renderer reload: records re-read on mount; the console buffer forgotten; nothing pending is lost (the host holds no renderer state for this child).
- A host crash and restart: records are on disk; a capture pending at the crash is lost with its session (the call ends with the process, as every `maws` call does).
- A frame that tries the network, a navigation, a download or a popup: refused silently by the sandbox and the main-side policies; the attempt shows as a console error on the row when the page logs it.

### 12. Security

- Every path from the agent is resolved and checked in the host before the store references it: a regular file (`stat().isFile()`), the extension and the size cap for artifacts, the whole call refused before any write.
- The scheme handler serves exactly one recorded file per URL, located by record id and version index, never by a path in the URL; unknown ids, versions and methods answer 404 or 405 with no detail.
- Frames: `sandbox="allow-scripts"` for HTML (no same-origin, no navigation, no popups, no downloads, no forms, no modals), doubled by the handler's `sandbox allow-scripts` CSP directive so a top-level load (the capture window) is sandboxed the same way; a per-answer CSP with no network source, which the app-wide policy leaves alone for the scheme; the session-level request filter, `will-frame-navigate`, `will-download`, `setWindowOpenHandler`, `will-navigate` and the WebRTC policy cover whatever a sandbox fallback leaves (Design §3). The capture window is offscreen, sandboxed by that directive, on an in-memory partition with the same handler and policies, `disableDialogs`, not an app window, destroyed after every capture, and loads nothing but the scheme.
- The files admission widens `read`, `openExternal` and `reveal` to the store's files and nothing else: `write`, `list` and `watch` keep the roots, so a delivered file is never written through MAWS and the version copies under `userData` never edited in place.
- Residual egress the policies do not close: a TURN relay over TCP a page names (CSP and `webRequest` do not govern WebRTC; `disable_non_proxied_udp` removes UDP). Recorded in the tracker with the Chromium switch as the closing condition if one exists; the page's only author is the owner's own agent.
- `plugins: true` enables Chromium's built-in PDF viewer and nothing else (Chromium 152 ships no other plugin).
- The bridge script is MAWS's own, inline under the artifact's CSP; the app accepts only messages from the frame it is listening to and only the two shapes; a spoofed pick yields an anchor the owner reads in the composer before anything is sent.
- The screenshot's bytes travel host←main over the message port and host→engine inside one journal line (a few hundred KB; the 4 MiB cap bounds it); the engine persists the original under its own config home (SPEC 31 `:5142`), the scratch home in every run of this child.
- Nothing in this child writes under `~/.claude`; the store lives under `userData`.
