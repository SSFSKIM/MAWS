## Purpose

After E3 a comment pinned to something reaches the agent without interrupting the main conversation. The owner hovers a line in a file tab, clicks the comment mark the editor already shows, and a sheet opens naming the line; they type, leave *Side thread* selected (the default), and press Send. A child session forks from the main one at that point, opens in the right panel's **Side** pane with the line named at its head, and the agent answers and edits there while the main conversation keeps running. When the side thread's turn ends, the main transcript gains one row, "Side thread on `src/x.ts:42` finished: …", that opens the thread; the sidebar lists the thread under its parent. Choosing *Send to main* instead steers the main session at its next tool boundary with the comment and what it is about, and the main transcript shows the comment pinned to the line it was about. Typing `/btw why is this null-checked twice?` in the composer asks the engine a side question beside the running turn and draws the answer in the same pane, with nothing added to the conversation; "Continue as a side thread" turns that exchange into a thread. A side thread resumed in a terminal is an ordinary forked session, and a fork found on disk is listed under the session it was forked from. This closes the parent's §2 items 6 (the side thread half: "A side thread opens, the agent edits and replies there, the main conversation is not interrupted. 'Send to main' works.") and 10 ("`/btw` opens a side pane with the answer; the main conversation is untouched"), and gives E2 (artifact comments), E4 (browser comment mode) and E6 (PR-line comments) the one composer they call.

To see it working: `pnpm dev`, open a session, open a file from Files, hover a line's gutter and click its comment mark; or type `/btw <question>` in the composer. Everything the agent receives is an ordinary user message (a first prompt, or a steer) in the engine's own transcript, so a terminal resuming the side thread sees the parent's history it was forked with and then the comment as the thread's own first prompt.

## Terms

- **Anchor** (X10): what a message is about: `{kind, locator, label, pageUrl?, path?, line?, screenshot?}`; `kind` is one of `browser-element`, `artifact-element`, `file-line`, `pr-line`, `none`. E5 produces `file-line` (`src/renderer/src/tools/code/anchor/anchor.ts`); E6, E2 and E4 produce the others later. The shared type and schema live in `src/shared/anchor/anchor.ts` after M1.
- **Comment composer**: the one sheet (C10's `Sheet`, `src/renderer/src/sessions/Sheet.tsx`) that takes an anchor, a comment and a destination, and sends. Producers open it through E5's seam `openCommentComposer(anchor, {appSessionId})`; nothing else sends an anchored message.
- **Destination**: *Side thread* (the default, P-6) or *Send to main*.
- **Side thread**: a child session launched with `--fork-session` from the parent's current transcript (C10's fork path: `src/main/sessions/service.ts` `fork`, `src/main/sessions/launch-mapping.ts` `intentLaunchSpec`, `src/engine-host/launch.ts`), whose record carries **lineage** `{kind:'side-thread', …}`.
- **Lineage** (X11): `SessionRecord.lineage`: `{kind: 'side-thread' | 'fork', parentAppSessionId, parentEngineSessionId, anchor?, openedBy: 'comment' | 'btw' | 'fork'}`, null for a root session; persisted in the index (migration 4), filled from the launch intent for MAWS's own forks, and from the disk rule (below) for forks MAWS did not launch.
- **Disk rule** (A-16): a transcript whose first message record (the first `parentUuid: null` record) carries the same uuid as another transcript's in the same project is a `--fork-session` copy of it; the family's original is the member whose file was born first; every other member is drawn as `kind:'fork'` of the original, no anchor.
- **Side pane**: the X5 panel tool with id `side`, one per session, that hosts a side thread's transcript and composer (`SessionPane` for the child session) or the side-question view.
- **Side question**: the engine's `side_question` control request: a one-shot model call over the conversation with no tools and no transcript record (SPEC 11 §11.11.6), answered whole in the control response as `{response, synthetic}`; `synthetic: true` means the engine substituted the text (the model tried a tool, an API error, a cut-off).
- **Summary row**: the `side_thread` transcript row in the parent: "Side thread on `<label>` opened" then "… finished: <text>", one row per thread, updated as the thread's turns end; a link opens the pane on that thread.
- **App-synthesised event**: an X1 event main makes for a session, `seq: null` and an id under `<appSessionId>:` (`src/shared/sessions/app-events.ts`), kept by main's read model and served by `session.appEvents` for a transcript's snapshot. The side-thread rows are these.
- **Steer**: a user message written while a turn runs; `priority: 'next'` folds it in at the next tool boundary (W1; `src/engine-host/queue.ts` `steer`).

## Design (the residue §3 C leaves open, with reasons)

### 1. Ownership and data flow

Main owns lineage and the side-thread rows; the host owns the side-question log; the renderer owns the composer and the pane. One flow per gate:

- **Comment → Side thread (G2):** the gutter → `openCommentComposer(anchor)` → the sheet → `side.thread.open {appSessionId: parent, from: {kind:'comment', anchor, text, screenshot}}` (main) → `SessionService.openSideThread` builds a fork intent with `lineage` and the first message (Design §3), `startSession` as `fork` does → the record is created with `lineage` (`createForLaunch`) → at ready, main renames the child, emits `side.thread.opened` into the parent's stream and answers the outcome → the renderer opens the `side` pane on the child. On every later `turn.ended` of the child, main writes the summary and emits `side.thread.summarised` (Design §5).
- **Comment → Send to main (G3):** the sheet → `side.sendToMain {appSessionId, anchor, text, screenshot}` (main) → main validates the screenshot, builds `[image?, text]` content with the anchored text (Design §2) → the host's `session.steer {priority:'next'}` → the parent's transcript draws the prompt with its anchor chip, live and from disk, from the text alone.
- **`/btw` (G4):** the composer's typed seam → the `btw` widget's `apply` → `session.sideQuestion {appSessionId, question}` (host) → the host appends to its log, sends `side_question {question, history?}` and completes through `session.operation` → the pane's question view lists the host's log (`side.question.list`) and patches on completions. "Continue as a side thread" → `side.thread.open {from: {kind:'btw', exchanges}}`.
- **Disk (G5):** discovery's summary gains the transcript's root uuid and birth time; `upsertFromSummary` runs the disk rule over the project's family of that root (Design §4).

Strongest alternative rejected: the host owning lineage and emitting the rows itself (lineage on the X6 launch spec, a host-written sidecar under `userData` for replay). It keeps main out of the loop, but the host would then hold a second copy of a record fact main already persists, and the disk path would need a second reader. Main already sees every `turn.ended` (`src/main/sessions/index.ts:40`) and already synthesises per-session events the renderer splices in; reusing that makes the index the one source for both the sidebar and the rows.

### 2. The anchor, its serialisation and its parse (X10)

`src/shared/anchor/anchor.ts` holds X10: `AnchorSchema` (strict) with the parent's fields and, because E6's document declares them (`docs/doperpowers/plans/2026-10-06-e6-source-control.md:158`), the optional `side: 'old' | 'new'` and `prNumber` of a `pr-line` anchor; `screenshot` is `{path, width, height}`; `kind:'none'` is the anchorless comment (a `/btw` promotion). E5's `FileLineAnchor` becomes `Extract<Anchor, {kind:'file-line'}>` re-exported from `src/renderer/src/tools/code/anchor/anchor.ts`, so E5's `fileLineAnchor()` and E6's `prLineAnchor()` keep compiling and `openCommentComposer` takes the whole union. E4's structured locator (A-19: `css`, `role`, `name`, an accessibility path) is E4's to propose as an X10 extension through the ledger; until then `locator` is one string and E4 encodes into it.

**The text the agent receives** (`src/shared/anchor/message.ts`) is three parts in one text block, exact strings in Interfaces: a **lead line** that names what the comment is about in words (`Comment on "src/x.ts:42" (file /abs/src/x.ts, line 42):`; the label is always quoted), the **comment** as typed, and, for a side thread, a **preamble paragraph** telling the model it is in a side thread forked to handle this comment and that the main conversation continues separately; then a blank line and one self-closing **tag** `<maws_anchor kind="file-line" label="src/x.ts:42" locator="/abs/src/x.ts#L42" path="/abs/src/x.ts" line="42"/>` carrying the anchor's fields as attributes (values HTML-attribute-escaped). With a screenshot, the lead line gains ` A screenshot of it is attached.` and the content is `[{type:'image', source:{type:'base64', media_type, data}}, {type:'text', text}]`, image first as the composer's own serialisation orders blocks (`serialize.ts:124-137`). The screenshot's `path` is not written into the tag (it is a MAWS-private file; the image block carries the pixels).

**The parse** (`parseAnchoredText(text)`, the same module): if the last non-empty line of the joined text is a `<maws_anchor …/>` tag whose attributes parse into an `Anchor` (without `screenshot`), the tag is removed; the first line is removed only if it equals the lead line regenerated from that anchor (with or without the screenshot sentence), and the preamble paragraph only if it equals the constant, whose presence is what says the destination was a thread. What remains is the comment. A tag anywhere else, a malformed tag, or a lead line that does not match stays as text, so nothing a human typed in that shape is taken for an anchor beyond the one exact form MAWS produces. The renderer applies it in `userTextOf` (Design §6) for the live, disk and queued forms alike; the title rule's `promptTitle` sees the lead line, which is a fine title for a side thread's first prompt (the record is renamed anyway, Design §3).

Why a tag and not E1's `[MAWS …]` first line plus a fenced JSON block: the anchor must be recovered exactly (five fields), the tag is one line the model has seen the engine use (`<pasted_content>`, `<system-reminder>`) and the transcript hides it; a fenced JSON block renders as code wherever the parse does not run (another client, the terminal) and doubles the message. Why the lead line is first and the tag last: the model reads what the comment is about before the comment; the renderer needs an exact anchor, which the tag gives.

### 3. The side thread's launch, lineage from the intent, and its title (G2)

`SessionService.openSideThread(parent, from)` (`src/main/sessions/service.ts`, beside `fork`) is `fork` with four differences: the guard is `sideThreadRefusal` (`src/main/sessions/start-guards.ts`, beside `forkRefusal`), which keeps `unknown_session` and `no_engine_session` and drops `busy`, because C10's `forkRefusal` refuses a source with a turn running (`start-guards.ts:92-99`: "fork it once the turn ends") and a side thread exists for exactly that moment (the engine allows the fork, SPEC 35; M0 (a) proves it; C10's Fork keeps its own guard unchanged); the intent is built by `forkIntentOf(s, source, {kind:'inPlace'}, {message, rewindTo: null})` and then given `lineage: {kind:'side-thread', parentAppSessionId: source.appId, parentEngineSessionId: source.engineSessionId, anchor (comment only, without screenshot), openedBy: 'comment' | 'btw'}`; the first message is the anchored text of Design §2 (a comment) or the side-question transcript (a promotion, Interfaces); and the outcome carries the child's id as `fork` does. `SetupIntent` gains an optional `lineage` (`src/shared/sessions/intent.ts`), optional because persisted intents are parsed strictly; `createForLaunch` takes `lineage` from the intent (`src/main/sessions/setup.ts` at the `LaunchInit`), so the record carries it before the engine runs; `finishBinding` renames the child through the engine as the `(fork)` rename does, to the anchor's `label` for a comment and `Side question` for a promotion, so the terminal's picker and the sidebar say what the thread is, then emits `side.thread.opened` (Design §5). A plain `session.fork` (C10's Fork action) now also fills `lineage {kind:'fork', openedBy:'fork'}` from its intent, so MAWS's own forks list under their parent too; no other behaviour of `fork` changes.

The side thread carries the parent's directory (an `inPlace` fork), its additional directories, model, effort, requested permission mode and route, and inherits its grants (`intentLaunchSpec`'s `inheritGrantsFrom`), as `forkIntentOf` already does; it can edit because it is an ordinary session under that mode. A fork is always taken "at the current point": `rewindTo` is null, and the engine copies the transcript up to its last flushed record (SPEC 35 §35.16; a tool whose result the parent had not written gets the engine's "not in this copy" placeholder, which is why `forkRefusal`'s half-written-turn worry does not apply here: the comment carries its own context and the thread's first prompt is a fresh turn). M0 proves the mid-turn case on the installed engine; if the engine refused it, the fallback named in M0 applies (`openSideThread` keeps the intent and starts it on the parent's next `turn.ended`, and the sheet says "opens when the current step ends"); nothing else in the design changes.

A fork of a parent that has exited is allowed (the engine resumes from disk; C10's Fork does this today); a fork of a parent with no engine id (never bound) is refused by `forkRefusal` as today, and the sheet shows the refusal.

### 4. Lineage from the disk (G5, A-16)

`summarize()` (`src/engine-host/fs/summarize.ts`) gains `rootUuid`: the `uuid` of the first head-window record with `parentUuid === null` (the conversation's root; in the fork child of `p1-fork-session-flag.jsonl` it is the parent's `b1277739-…`), null when the head holds none; and `birthtimeMs` from the file's `stat` (APFS's birth time; the summary already stats the file). `TranscriptSummary` gains both (`src/shared/wire/store.ts`, strict: both required, nullable `rootUuid`). Migration 4 adds `root_uuid TEXT`, `transcript_birthtime_ms REAL` and `lineage TEXT` (X11 as JSON, null for a root) to `sessions`, an index on `(project_id, root_uuid)`, the `side_threads` table (Design §5), and nulls `transcript_size`/`transcript_mtime_ms` for every `kind = 'engine'` row with a transcript path so the next sync re-summarises the owner's transcripts once and fills the new columns (`src/main/index/source.ts:216-227` treats a row without size and mtime as bare and rescans it; the executor measures the one-time cost on the owner's store and records it in Surprises).

**The disk rule** runs in `SessionStore.upsertFromSummary` after the write, when the summary has a `rootUuid`, and recomputes the whole family: the family is every session row in the same project with that `root_uuid` and a birth time; the **original** is the member with the earliest `transcript_birthtime_ms` (ties by `created_at`); every other member whose lineage is null or disk-derived (`lineage_source = 'disk'`, a column beside `lineage`) is set to `{kind:'fork', parentAppSessionId: original.appId, parentEngineSessionId: original.engineSessionId, openedBy:'fork'}` with `lineage_source = 'disk'`; a member whose lineage was filled from an intent (`lineage_source = 'intent'`) keeps it; the original's disk-derived lineage, if it had one from an earlier pass, is cleared, and an intent-filled one is kept (it may itself be a side thread of something else). Each change notifies `changed()`. Discovery summarises newest-modified first, sixteen at a time (`src/engine-host/fs/discovery.ts:100-116`), so forks usually arrive before their original; because disk-derived lineage is recomputed and never fixed, the family converges to the same reading whatever the order (a fork that briefly pointed at a sibling is re-pointed when the original arrives). A session MAWS launched as a side thread passes through this rule unchanged (its lineage is intent-filled); a `--fork-session` child the terminal made, or one of C10's forks from before this child, gains `kind:'fork'`; a `/branch` fork (the terminal's, which writes `forkedFrom`) is caught by the same uuid signal. `lineage_source` is index-only; the record's `lineage` (X11) does not carry it.

Why the earliest birth time and not "the member most recently born before this one": in a chain A → B → C both are wrong in one case each (C forked from A after B existed; C forked from B); pointing at the family's original never points at a sibling and is the stable reading of "forked from this conversation's line". Known limit, recorded in Deferred: a parent compacted before the fork writes the compaction boundary as the child's first record, whose uuid sits mid-file in the parent, outside its head window; such a fork is not detected and lists as a root. The head window also misses the root when a `file-history-snapshot` before it exceeds 64 KiB, the same limit `firstRecordAt` has today.

### 5. The side-thread rows: trigger, content, persistence and parity (G2)

Two X1 events, appended after E1's block in `src/shared/graph/events.ts`: `side.thread.opened {childAppSessionId, childEngineSessionId, anchor, openedBy}` and `side.thread.summarised {childAppSessionId, text, isError, turns}`. Both are app-synthesised by main (`seq: null`, ids `<parentAppSessionId>:side-thread:<childAppSessionId>:opened` and `…:summarised:<turns>`), emitted with `emit('session.eventBatch', {appSessionId: parent, events})` as the yield notice is, so the renderer's live subscription draws them, `emittedAppEventsSource` keeps them in the read model, and `session.appEvents` serves them to a snapshot.

- **The index row.** The table `side_threads` (migration 4; one row per side thread, keyed by the child) mirrors the two events exactly: `opened_at` (written once), `summarised_at`, `text`, `is_error`, `turns` (0 until the first turn ends). Both events are re-synthesised from this row, so what a snapshot gets after a restart has the ids and `at`s the live run emitted.
- **`opened`** is written and emitted by `finishBinding` (`SideThreadStore.opened(child, parent, now)` then the event with `at = opened_at`); it is never emitted for a launch that failed before binding, so no row points at a thread that never started.
- **`summarised`** is emitted by a tap on `session.eventBatch` in `src/main/side/side-threads.ts` (started from `src/main/index.ts` beside `startYield`, which has the index): for every **live-form** `turn.ended` (`seq !== null`; the disk follower re-emits a session's whole backfill as batches with a synthesised `turn.ended` per `turn_duration` record, `origin` null and `resultText` null, `src/engine-host/fs/backfill.ts:355-375`, `src/engine-host/fs/follow.ts:144-168`, which must never count) of a session whose record has `lineage.kind === 'side-thread'`, with `agentId === null`, `parentToolUseId === null`, `!isEchoReceipt` and `origin` `'human'` or null, and whose event id differs from the row's `last_turn_event_id` (live batches can repeat on a reconnect; main's digest deduplicates by id the same way, `src/main/sessions/read-model.ts:272-279`), main updates the row (`summarised_at: event.at, text: resultText capped when non-null else the previous text, is_error, turns: previous + 1, last_turn_event_id: event.id`) and emits the event. `text` is the result's text capped at 400 characters at the first sentence or line end past 200; `isError` is the turn's `isError`.
- **Replay parity:** `session.appEvents {appSessionId}` answers the read model's kept events merged with `sideThreadEvents(appSessionId)` from the index (an `opened` per `side_threads` row with `parent_app_id = appSessionId` at its `opened_at`; a `summarised` at `summarised_at` with its `turns` when `turns > 0`), deduplicated by id; `startSessions` takes the provider through its options since it has no index of its own (`src/main/index.ts:147`). `emittedAppEventsSource` excludes `side.thread.*` from the read model's 20-per-session store (they come back from the index; keeping them would push the relay and yield notices out). The renderer's live-wins filter passes them because they are app-synthesised (`ipc.ts:108-122`); the snapshot splices them by `at`, and the live path appended them at arrival, which is the same place since `at` is the emit time.
- **The row** (`side_thread`, Design §6) is one per child, and the reducer routes it explicitly, since rows are derived per turn and memoised on the turn's version (`src/renderer/src/transcript/model/derive.ts:173-178`) and a notice-like event lands in the turn current at its arrival (`reduce.ts:648-651`): the reducer's index gains `sideThreads: Map<childAppSessionId, owner>` recording the turn or loose block the thread's first event landed in; `opened` creates the row there; a `summarised` routes to the recorded owner with `pushRouted(owner)` and bumps that turn's version so its rows re-derive, and when it is the first event seen for its child (a fast thread, or a snapshot that holds only the latest summary) it creates the row where it lands and the later `opened` adopts that owner and fills the label and anchor. Each `summarised` updates text, state and turn count in place; a thread with many turns is one row that says "finished (3 turns)", not three rows. Deleting a child record cascades its `side_threads` row away (`ON DELETE CASCADE`), and the next snapshot omits the thread.

Why not host-emitted meta rows in the parent's journal: the disk path never reads the journal (`fs/backfill.ts`), so the rows would vanish after a restart; the app-synthesised path exists precisely for events the engine's files do not hold.

**The `side` panel tool** (`src/renderer/src/side/SideTool.tsx`; X5): `multiInstance: false`, `pinnable: false`, `menu: true` (offered from "+" as "Side"), params `{view?: {kind:'thread', childAppSessionId} | {kind:'btw'}}`; `open` re-targets the view. ### 7. `/btw`: the slash widget, the host's log and the round trip (G4)

**Interception.** `btw` joins `WIDGET_COMMANDS` (`src/renderer/src/composer/mentions/widgets.ts`) with the description "Ask a side question beside the running turn", and is registered once, through C11's `registerAllWidgets` (`src/renderer/src/widgets/index.ts:54-57`), by adding `btw` to `WIDGETS` (`BtwWidget`), `WIDGET_TITLE` ("Side question") and `TYPED_APPLY` (`applyBtw`), both exported from `src/renderer/src/side/` and imported by `src/renderer/src/widgets/`; E3's own `register.ts` registers no widget, so no second registration can win without `apply`. `applyBtw(appSessionId, args)` returns false when the session has no ready process (so the widget opens and says "Start the session to ask a side question") and otherwise opens the pane in its question view, starts `sideStore.ask(appSessionId, args)` without awaiting the receipt, and resolves true, so the typed `/btw <question>` never trips the 300 ms bound. `BtwWidget` is the palette path (choosing the `/btw` row, or a bare `/btw`): one field "Ask a side question" with Ask, which does the same and closes. The typed seam runs only for `plain` drafts (one line, string content, no pasted content, `controller.ts:301-303`), so a two-line question or one with an attachment would reach `session.send` as a prompt and touch the main conversation: `controller.submit()` gains one guard before the `plain` test for a draft whose trimmed display starts with `/btw` and is not `plain`: text-only (several lines, or pasted text) is asked through `applyBtw` with the display text after `/btw `; anything with an image or document attachment is refused with the toast "Side questions take text only; remove the attachment" and the draft kept. A `/btw` draft never reaches `session.send` or `session.steer`. Strongest alternative rejected: intercepting in `Composer.onSubmit`, which would run after the steer decision and would not give the palette a row.

**The host's log** (`src/engine-host/side-questions.ts`, `SideQuestionLog`, one per `EngineSession`, X13): entries `{id, question, state: 'pending' | 'answered' | 'failed', response: string | null, synthetic: boolean, error: string | null, askedAt, answeredAt}`. The `session.sideQuestion` handler becomes `session.sideQuestion(question)` on the session: it appends a pending entry, sends `side_question {question, history?}` through `operations.start` where `history` is the log's answered, non-synthetic exchanges as `{question, response}[]` (omitted when empty, the shape of `p1-side-question-session.jsonl` seq 88 and 95; the engine's own `btwHistory` keeps only non-synthetic answers, SPEC 11 §11.11.6), and records the minted `opId` as the entry's id. The operation table's `emit` in `src/engine-host/ipc.ts` settles the entry on a `session.sideQuestion` completion (ok → answered with `response`, `synthetic`; a late success too; an error → failed with the engine's message) before the event goes out. `side.question.list {appSessionId}` answers the log; `side.question.clear {appSessionId}` empties it (a new side conversation; pending entries stay). The log lives for the process: `handleExit` marks pending entries failed with "The session ended" and keeps the log readable until the session is forgotten. Nothing is journaled beyond what the writer already journals (the `out` request and `in` response rows), and no X1 event is emitted: the main transcript stays untouched, as the engine's own transcript does.

`system/control_request_progress` (`{request_id, status:'started' | 'api_retry', …}`, SPEC 45 §45.14.4; only `side_question` produces it) joins the `none` list of `normalizer-system.ts`: journaled, no event. The renderer already knows the question is pending from the receipt; a `started` 0.3 s later changes nothing it draws.

**The pane's question view** (`BtwView.tsx`; the store `useSidePane`): lists the log newest last as question and answer pairs; a pending entry shows the question with a spinner; a `synthetic: true` answer carries the notice "The engine substituted this answer" in the notice style; a failed entry shows the engine's message with Retry (re-asks the same text); the bottom holds a one-line field with Ask (Enter asks, Shift+Enter breaks a line), a Clear action, and "Continue as a side thread", enabled when at least one answered exchange exists, which calls `side.thread.open {from: {kind:'btw', exchanges}}` with the answered exchanges and switches the pane to the new thread. The store hydrates from `side.question.list` on mount and whenever the host returns to ready, patches entries from `session.operation` events for `session.sideQuestion` (matching `opId`), and re-lists after each `ask`'s receipt. A reload of the renderer mid-question therefore shows the question pending and then answered.

### 8. Send to main (G3)

`side.sendToMain {appSessionId, anchor, text, screenshot}` is main-owned (`src/main/side/send-to-main.ts`): it validates the screenshot (Design §9), builds the content `[imageBlock?, {type:'text', text: anchoredMessage({anchor, text, destination:'main'})}]`, reads the parent's `session.status` from the host and mirrors the composer's own rule (`src/renderer/src/composer/Composer.tsx:275-280`, `submit/submit-state.ts`): a turn running (`status.turn !== null`) → `session.steer {content, priority:'next'}`; otherwise `session.send {content}`, which honours the app queue (a paused or held queue leaves it queued, as a typed message would). It answers `{messageUuid, disposition: 'steered' | 'sent' | 'queued'}`. The composer's sheet names the semantics in its destination control's caption ("Sent at the next step of the running turn", the composer's own `SENDS_AT_NEXT_STEP` wording, or "Sent now" when the parent is idle). When the parent's process is not ready, the destination is disabled with "The main session isn't running" and Side thread remains available (a fork resumes from disk). Why main and not the renderer calling `session.steer` itself: the renderer cannot read the screenshot file (E5's `files.read` is allowlist-bound and a screenshot lives under `userData`), and the one place that validates the path should be the one that builds the block.

### 9. Failure semantics and security

- **A fork that fails to launch.** `side.thread.open` answers C10's `StartOutcome`: a `refused`, `invalid` or `missing_directory` outcome keeps the sheet open with the message and offers Retry and "Send to main instead" (the latter enabled when the parent is ready); the dropped intent is `fork`'s own behaviour. A failure after the outcome (a setup phase failing, the engine exiting before ready) is C10's: the child record exists with lineage and the pane's `SessionPane` shows the setup failure with its Retry, as a main tab would; no `opened` row was emitted, so the parent's transcript shows nothing for it until it binds.
- **A side question the engine refuses or cancels.** The operation completes `{ok:false, error}` with the engine's message ("Session is shutting down", "Side question cancelled") or the 120 s timeout; the entry reads failed with Retry; a late success inside the client's late table settles it answered (`OperationTable`'s `late: true` path).
- **A parent that has exited.** Side thread: allowed (a fork from disk). Send to main and `/btw`: refused in the renderer before any IPC, with the reason, since both need a ready process; `/btw`'s widget opens with that reason.
- **A parent mid-turn.** Side thread: M0's verdict; the default design forks at once. Send to main: the `next` steer folds in at the next tool boundary; the sheet says so.
- **A screenshot that fails validation**: `side.sendToMain` and `side.thread.open` answer `invalid_input` naming the reason (`screenshot: not under an allowed root`, `larger than 5 MiB`, `not a PNG, JPEG, GIF or WebP`); the sheet shows it and offers to send without the screenshot.
- **Security.** `side.thread.open` and `side.sendToMain` run in main under `registerMainHandler` with strict schemas: `text` ≤ 20,000 characters, `label` ≤ 200, `locator` and `pageUrl` ≤ 2,000, `path` ≤ 1,000; `appSessionId` must name a record. The only path main opens is `screenshot.path`: it is realpath-resolved, must be a regular file under `<userData>/` (where E2's and E4's captures live) or under the parent session's directory or one of its additional directories (E5's `files.*` containment check, reused from `src/main/files/`), at most 5 MiB (the API's per-image bound, `MAX_SEND_IMAGE_BYTES`), and its type is read from its magic bytes (PNG, JPEG, GIF, WebP), never from its extension. The anchor's `path` is never opened by main in E3; it is text the model reads. The renderer opens a file-line anchor's path through C8's `openTab({kind:'file'})`, which E5's `files.read` allowlist governs as today.
