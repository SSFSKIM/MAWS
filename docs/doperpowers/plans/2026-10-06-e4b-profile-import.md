## Purpose

After E4b the owner brings a Chrome profile into MAWS's browser once, by copy, with one consent. Settings › Browser offers "Import a Chrome profile…"; the sheet lists the profiles Chrome's `Local State` names (or the ones in a folder the owner points at), shows what the chosen profile holds (so many pages of history, so many cookies, these extensions) and three checked categories, History, Cookies and Extensions, with Saved passwords shown disabled: "a credential store comes later" (P-17). Import runs: Chrome's stores are copied into a staging folder inside MAWS's data directory (Chrome's own files are locked and change under a running Chrome), the history goes into E4a's `browser_history` table as `imported` rows, macOS asks once for Chrome's Safe Storage password (the owner clicks Allow; MAWS holds the key in memory for this import only and never writes it), every cookie is decrypted and set into the profile's own partition, `persist:maws-chrome-<profileDir>` (A-31), the partitioned (CHIPS) rows through a tab debugger's `Network.setCookie` and verified through `Network.getAllCookies` (A-33 item 8), and the extensions the owner confirmed as unverified files are copied into the partition's folder and loaded, each reported as loaded, background running, or failed on an absent `chrome.<api>`. The report reads "N cookies, M history entries, K extensions, J skipped: reasons". The imported profile becomes the active one; E4a's chrome shows its name in the partition pill because imported cookies make the agent the owner on every site. Per-extension toggles follow the import, with wallet extensions off by default (P-21). "Remove imported profile" drops the partition's storage, its history rows, its tabs and its extensions cleanly. Chrome is never driven or modified; nothing from the profile runs except the extensions the owner confirmed; no cookie value, key or URL is ever logged.

To see it: Settings › Browser › Import a Chrome profile…; pick a profile; leave History, Cookies and Extensions checked; Import; click Allow on the Keychain dialog; read the report; open a Browser tab: the partition pill names the profile and a site that had you signed in in Chrome has you signed in here.

## Terms

- **User data directory**: Chrome's folder holding `Local State` and the profile directories (`~/Library/Application Support/Google/Chrome` by default on macOS). **Profile directory** (`profileDir`): a key of `Local State`'s `profile.info_cache` (`Default`, `Profile 1`, …), a directory under the user data directory. **Profile**: the owner's Chrome profile as `info_cache` names it (`name`, `gaia_name`, `user_name`).
- **Store**: one of Chrome's SQLite files inside a profile directory: `History` (table `urls`, schema version 70 on the owner's machine), `Cookies` (at `<profile>/Cookies` or `<profile>/Network/Cookies`; schema version 24, every value encrypted). The password stores (`Login Data`, `Login Data For Account`) are never opened (P-17; Decision Log 6). `Web Data` is never read.
- **Staging directory**: `<userData>/browser/import/<uuid>/`, the private copy of the chosen stores and extension directories an import works from; deleted on every exit path (Design §4).
- **Inspection**: the step that stages the two stores, counts their rows and lists the profile's extensions so the consent sheet shows what it asks about; identified by `inspectionId`, one at a time. **Import**: the run the owner confirmed, identified by `importId`.
- **Category**: History, Cookies, Extensions (Passwords is shown disabled). **Consent**: the one sheet's confirmation of the categories, the extension selection and the unverified-files acknowledgement.
- **Keychain step**: the one `security find-generic-password -s "Chrome Safe Storage" -a "Chrome" -w` run through a child process while cookies are being imported; macOS shows its consent dialog and the owner clicks Allow. **Safe Storage key**: PBKDF2-HMAC-SHA1(password, `saltysalt`, 1003, 16 bytes), held in a `Buffer` for the import and zeroed after.
- **Partitioned (CHIPS) row**: a cookie row whose `top_frame_site_key` is set; it is set only through `Network.setCookie` with a `partitionKey` on a debugger session of the partition (A-33 item 8). **Import view**: the one unattached `WebContentsView` main creates in the target partition for the import's CDP commands (Design §8); it is not a tab.
- **Partition**: E4a's `persist:maws-chrome-<profileDir>` (`profilePartition(profileDir)`, `src/shared/browser/tab.ts`). **Partition folder**: `<userData>/browser/<partitionDirName>/`, `partitionDirName` being the partition without `persist:` (Decision Log 15); it holds `extensions/<id>/`. **Storage directory**: Electron's own directory for the partition, `ses.storagePath`, under `<userData>/Partitions/`; its name is Chromium's transform of the partition name (lower-cased and percent-escaped: `maws-chrome-profile%201` for `Profile 1`), so it is never derived from `profileDir` but recorded from `ses.storagePath` at import (Decision Log 24).
- **Imported profile record**: an entry of `<userData>/browser/profiles.json`, the file E4b writes and E4a reads (`browser.profiles.list`, the partition pill, Settings › Browser's select). **Extension toggle**: the record's per-extension `enabled`. **Wallet extension**: one a known-id list or the manifest heuristic names (Design §9); off by default (P-21).
- **Report**: the `ImportReport` an import ends with, kept on the record and shown in the sheet and in Settings. **Removal**: "Remove imported profile", Design §12.
- **Main**, **renderer**, **harness**, **scratch profile**, **cover**, **tab**, **`TabDebugger`**: as E4a's document defines them. E4b touches the engine host nowhere.

## Design (the residue §3 D and E4's cut leave open, with reasons)

### 1. Ownership and data flow

Main owns the import: the staging directory, the Keychain child, the decoders, the writes into E4a's history store and the partition, the import view, the extension folders and their loading, `profiles.json`, removal and the boot sweep (`src/main/browser/import/`, started by `startBrowserImport` from an E4b block beside E4a's `startBrowser`). The renderer owns the sheet and Settings › Browser's imported-profiles block; it asks main through `browser.import.*`, mirrors progress from `browser.import.progress`, and writes the one setting it changes, `browser.profile`, through `settings.set` as every Settings row does (`parts.tsx:13`). Every string the renderer shows about a profile (its name, an extension's name) comes from main as data and renders as text. The agent is never told about an import (no X1 event, no tool; E0b S1e: imported data reaches the agent only through the live page). The engine host is untouched. One inspection and one import run at a time, app-wide; a second `inspect` discards the first's staging, a second `start` while one runs answers `invalid_input` ("an import is running").

### 2. The picker (`Local State`)

`browser.import.profiles { userDataDir: string | null }` reads `<userDataDir>/Local State` (the default `join(homedir(), 'Library/Application Support/Google/Chrome')` for `null`; under `MAWS_E2E=1` the default is `MAWS_E2E_CHROME_USER_DATA`, so no test ever lists the owner's Chrome) and answers `{ userDataDir, found, chromeRunning, profiles, error }`: `profiles` from `profile.info_cache`, one per key, as `{ profileDir, name, gaiaName, userName, lastUsed, imported }` (`name` is `info.name`, shown; `gaia_name` and `user_name` shown muted when present, E0b S1e; nothing else of the 29 fields is read; `lastUsed` from `profile.last_used`; `imported` when `profiles.json` has the record). `Local State` is a small JSON file Chrome rewrites atomically (write-then-rename), so it is parsed in place under a 16 MiB cap, one of the enumerated read-only JSON reads (Constraints "Never"; the others are Design §9's); every SQLite store is copied first and never opened in place. `chromeRunning` is `lstat(join(userDataDir, 'SingletonLock'))` succeeding, the symlink Chrome holds while it runs; it is a hint ("Quit Chrome for the most complete copy"), never a block: E0b copied every store under a running Chrome. "Choose another Chrome folder…" runs `browser.import.chooseUserData` → `dialog.showOpenDialog(win, { properties: ['openDirectory'], defaultPath, message })` through `openDialogFor(env, …)` (`e2e-pick.ts:13`; the e2e answers it with `MAWS_E2E_PICK_PATHS`), and the picker re-lists from that folder; a folder without `Local State` answers `found: false` and the sheet says so. **Validation**: `userDataDir` must be absolute and a directory; a `profileDir` is admitted only if it is a key of `info_cache`, matches `/^[A-Za-z0-9][A-Za-z0-9 ._-]{0,63}$/`, and `join(userDataDir, profileDir)` is a directory; any `realpath` escaping `userDataDir` is refused. The picker preselects `lastUsed`, else the first; a profile already imported shows "Imported <date>" and is not importable again until removed (Decision Log 2).

### 3. The consent sheet

One `Sheet` (`src/renderer/src/tools/browser/import/ImportSheet.tsx`, `data-browser-import`), rendered by Settings › Browser's block on its own state as E8's `ConfirmSheet` is (Decision Log 21), width `w-[min(560px,90vw)]`, in five states the same component walks: **pick** (Design §2; Continue runs `browser.import.inspect`), **consent**, **running** (Design §4 to §9; Cancel), **report** (Design §10; Done), **failed** (the failure sentence and Close). The consent state shows the profile's name line, the Chrome-running hint when set, then the four category rows and the extension list from the inspection:

- **History** — checkbox, checked: `IMPORT_COPY.history(rows)` "17,554 pages. Read from a copy; needs no password. Shown in the address bar's suggestions." (the count from the staged copy; an unreadable store shows its error in the row and the box disabled).
- **Cookies** — checkbox, checked: `IMPORT_COPY.cookies(rows, partitioned)` "5,112 cookies (1,005 partitioned). macOS will ask once for Chrome's Safe Storage password from your login keychain; choose Allow. MAWS reads it once, keeps it in memory only while the cookies are decrypted, and never writes it anywhere. Nothing is written back to Chrome." and, on its own line, `IMPORT_COPY.cookiesAgents(name)` "New browser tabs, including the ones agents open through MAWS's browser tools, will be signed in as <name> wherever Chrome was." (the one trust-boundary widening of this child, said before the consent, not after; Decision Log 7 and 29). The sentence names Allow and nothing else (the never-do list, E0b S1e).
- **Saved passwords** — checkbox **disabled**, unchecked: `IMPORT_COPY.passwords` "Saved passwords — a credential store comes later" (P-17), no count (Decision Log 6).
- **Extensions** — checkbox, checked when the list is non-empty: `IMPORT_COPY.extensions(n)`; under it the **extension list**, one row per candidate (Design §9): an "Import" checkbox (checked, except `chromeState === 'disabled'`, Decision Log 9), the resolved name, the version, a `Chip` per fact: "Wallet · off until you turn it on" for a wallet, "Disabled in Chrome", "MV2", "No background", and `IMPORT_COPY.unsupported(n)` ("3 permissions MAWS doesn't support") with the names in the row's `title`. Under the list, the **unverified-files acknowledgement** (`CHOICE` checkbox, required while any extension is checked): `IMPORT_COPY.unverified(profileName)` "MAWS can't verify these extensions or their saved permissions. Imported extensions run code inside MAWS's browser pages for this profile. Continue only if you trust what this Chrome profile installed." (Codex's confirmation, reworded for MAWS; `allowUnverifiedExtensions` is sent true only when checked).

Import (`PRIMARY`, `canSubmit` = at least one category checked and, if extensions are checked, the acknowledgement) runs `browser.import.start`. **Lifecycle** (Decision Log 28): the sheet's state is read from the renderer store `useBrowserImport` (the standing inspection, the running import's progress, the last report), not from the opener; the opener holds only `open`. In **pick** and **consent**, Escape, the overlay and Cancel run `browser.import.discard` for a standing inspection (the staging is deleted) and close. In **running**, the dialog is **not dismissible**: `onOpenChange(false)` is ignored, Escape does nothing, and only Cancel (`browser.import.cancel`) ends the run; closing the Settings tab or reloading the window unmounts the sheet but the import continues in main, the Settings block shows `BROWSER.importing(phase)` with "Show" reopening the sheet in **running**, and the `finished` report lands in the store whether or not a sheet is mounted. In **report** and **failed**, any close just closes. The sheet is a Radix `Dialog`, so E4a's cover protocol hides any placed browser view while it is open; macOS draws the Keychain dialog above everything.

### 4. Staging: the copy and its deletion

`browser.import.inspect { userDataDir, profileDir }` creates `<userData>/browser/import/<uuid>/` (`randomUUID()`, mode 0700) and copies into it, with `fs.copyFile` (`COPYFILE_EXCL` on the destination) after an `lstat` of the source that admits regular files only (a symlinked or special store is refused as `storeUnreadable`; `copyFile` would otherwise follow the link), each present store with its companions: `History` (+ `History-journal`, `-wal`, `-shm`), and `Cookies` or `Network/Cookies` (+ companions), whichever exists (`Network/` first). The copies are opened with `node:sqlite` read-write (they are MAWS's private copies, so a hot `-journal` or `-wal` is rolled forward on open; MAWS runs no write statement; Decision Log 23), counts are read (`SELECT count(*) FROM urls`; `count(*)` and `count(*) WHERE top_frame_site_key <> ''` from `cookies`; `meta.version` of each), the extension candidates are listed from the profile's `Extensions/` and `Secure Preferences`/`Preferences` **in place** (JSON reads only, Design §9; nothing is copied before consent), and the inspection answers. A store that fails to copy or open (`EBUSY`, `SQLITE_CORRUPT`, `SQLITE_NOTADB`, a missing `meta`) fails its category only, with `IMPORT_COPY.storeUnreadable(store)` "History couldn't be read from the copy. Chrome may have been writing it; quit Chrome and try again." (Codex's recovery line). At `start`, the chosen extension directories are copied (Design §9) into `<staging>/extensions/<id>/` before anything loads. The staging directory is deleted (`rm -rf`) at every exit of an inspection or an import: `discard` (the sheet's close in **pick** or **consent**), `start`'s end whatever the outcome, `cancel`, a thrown error (the service's one `finally`); at `will-quit` synchronously; and at boot a **sweep** removes every `import/*` left by a crash (Design §14). A sheet unmounting while an import **runs** deletes nothing (Design §3's lifecycle). Nothing under `import/` is ever read by anything but the import that created it.

### 5. The Keychain step

Runs once per import, at the start of the cookies phase, only when Cookies is checked and the cookie store copied: `execFile('/usr/bin/security', ['find-generic-password', '-s', 'Chrome Safe Storage', '-a', 'Chrome', '-w'], { encoding: 'buffer', timeout: 120_000, killSignal: 'SIGKILL', maxBuffer: 64 * 1024, env: {} })` (`encoding: 'buffer'` so stdout arrives as a `Buffer`, never a string) (`src/main/browser/import/keychain.ts`). macOS shows its consent dialog for the `security` tool; the sheet meanwhile shows `IMPORT_COPY.keychainWaiting` "Waiting for the Keychain… choose Allow in the macOS dialog" with Cancel (which kills the child). Outcomes: exit 0 → `allowed`; stdout less its trailing newline is the password, taken as a `Buffer` (never a string, so it can be zeroed), the key derived with E0b's `deriveKey` (PBKDF2-HMAC-SHA1, `saltysalt`, 1003, 16 bytes), the password buffer zeroed at once and the key buffer zeroed at the end of the cookies phase; exit 44 (`errSecItemNotFound`; confirmed on this machine against a nonexistent item name, which raises no dialog) → `missing` ("No Chrome Safe Storage item in your login keychain; cookies were not imported"); any other exit → `denied` ("Keychain access was not allowed; cookies were not imported"; `security`'s stderr first line is kept in the report's `error`, it carries no secret); the timeout → `timeout`. Every outcome but `allowed` skips the cookies category with its reason and the import continues with the others. A **wrong key** is not detected here but by the decoders: every row fails (`BAD_DECRYPT` or the host-hash mismatch) and the report says `wrongKey` (Design §7). The key is never written, never logged, never sent over IPC, never passed to another process; it lives in the import's closure. Under `MAWS_E2E=1` the child is never spawned: `MAWS_E2E_KEYCHAIN` must be set, as `file:<path>` (the password read from that file: the fixture's `safe-storage-password.txt`, or a file holding a wrong one), `deny`, `missing` or `timeout` (the outcome simulated), and an unset variable under e2e answers `denied` with "no keychain under e2e" so no forgotten seam ever raises a dialog on a test machine. Only Google Chrome's item is read in P1; another Chromium browser's folder decrypts nothing and the report says the password did not match this profile (Deferred).

### 6. History

`src/main/browser/import/chrome/history.ts` (pure over an opened `DatabaseSync`): `readHistoryRows(db)` yields `{ url, title, visitCount, typedCount, lastVisitMs, hidden }` from `urls` with `setReadBigInts(true)` and Chrome time converted (microseconds since 1601 → Unix ms; E0b `crypto.mjs:61-70`). `importHistory` filters: `hidden = 1` → skipped `hidden`; a URL `validateBrowserUrl` refuses (E4a `src/shared/browser/url.ts`: not http(s), `chrome://`, `file:`, unparsable) → skipped `unsupportedScheme`; else the row goes to `BrowserHistoryStore.importRows(partition, rows)` (the one method E4b adds to E4a's store, Interfaces: one transaction, batches of 500, `INSERT INTO browser_history (partition, url, title, visit_count, typed_count, last_visit_ms, source) VALUES (?, ?, ?, ?, ?, ?, 'imported') ON CONFLICT(partition, url) DO UPDATE SET visit_count = excluded.visit_count, typed_count = excluded.typed_count, last_visit_ms = max(last_visit_ms, excluded.last_visit_ms), title = coalesce(excluded.title, title), source = 'imported'`; the conflict branch **replaces** rather than adds, so a repeated import of the same rows is idempotent and never doubles a count (Decision Log 16); the partition is fresh at every import, so the branch is reached only by a row visited in it between inspection and import). Chrome's counts are carried, not reset to 1, so E4a's `suggest` order (`typed_count DESC, visit_count DESC, last_visit_ms DESC`) ranks the imported rows as Chrome's omnibox would. The owner's 17,554 rows read in 185 ms (E0b) and insert in one transaction; progress reports per batch.

### 7. Cookies (unpartitioned rows)

`src/main/browser/import/chrome/cookies.ts` (pure): `readCookieRows(db)` (E0b's column list; `meta.version`), `decodeCookieRow(row, key, storeVersion)` → `{ kind: 'plain', details: CookiesSetDetails } | { kind: 'partitioned', cdp: NetworkSetCookieParams } | { kind: 'skipped', reason: CookieSkipReason, decrypted: boolean }` with the rules, **decrypt first, classify after** (Decision Log 25): an `encrypted_value` that does not start with `v10` → `corruptRow`; a decrypt that throws `BAD_DECRYPT` or fails the store-version-gated SHA-256(host_key) check → `wrongKey` (both guards from E0b: at version 24 and later the prefix is required, so a wrong key that survives CBC padding cannot fall through as a bare value); a row with a plain `value` and an empty `encrypted_value` is taken as it is (`decrypted: false`); then, on a decrypted row, `expires_utc` in the past (`has_expires` and the converted time before now) → `expired` (E0b: dropped before set); `samesite === 0 && !is_secure` → `sameSiteNoneInsecure` (Chromium would reject it: `EXCLUDE_SAMESITE_NONE_INSECURE`); an unparsable `url` → `corruptRow`. The mapping is E0b's `toElectronCookie`: `url` = `${is_secure || source_scheme === 2 ? 'https' : 'http'}://${host_key without its leading dot}${path || '/'}`, `domain` only when `host_key` starts with `.` (a host-only cookie is set by omitting `domain`, which is what Electron does), `sameSite` -1/0/1/2 → `unspecified`/`no_restriction`/`lax`/`strict`, `expirationDate` (seconds) only when `has_expires` (a Chrome session cookie becomes an Electron session cookie, not retained past the app's exit, Chrome's own semantics for a profile without "continue where you left off"; Decision Log 10), `secure`, `httpOnly`, `name`, `value`. The import sets each `plain` row through `ses.cookies.set(details)` on `session.fromPartition(partition)` (the partition obtained through E4a's partition module so its preparation runs once as E4a does it; re-pinned: `browser.partitions.session(partition)`, Decision Log 31); a rejection (`__Host-` prefix rules, an invalid domain, Chromium's own exclusions) counts as `rejected` with Chromium's reason class, never the row; after the loop, and again after the partitioned phase (Design §8), `ses.cookies.flushStore()` so persistent cookies reach disk before the report. Progress every 200 rows. **The wrong-key verdict** (Decision Log 25): `cookies.keychain` is `wrongKey` when at least one decrypt was attempted and **every attempted decrypt failed** (rows with a plain `value` do not count); then nothing is set and the report says "0 cookies · 5,112 could not be decrypted: the Safe Storage password did not match this profile". Because decryption comes first, a wrong key fails every encrypted row of a real store too, expired and insecure-None rows included (the probe's 5 of 5, `main.mjs:300-310`, decrypted every row without filtering). A few `wrongKey` rows among many decrypted ones are reported as `corruptRow`-class skips, because the key is one key. The cookie values exist decrypted only in the loop's scope.

### 8. Partitioned (CHIPS) rows through the import view's `TabDebugger`

A `partitioned` row (`top_frame_site_key` set) is set through CDP only (A-33 item 8): `Network.setCookie { name, value, domain? (the same dotted-host rule as §7, else omitted so the cookie is host-only), path, secure: true, httpOnly, sameSite: 'None' | 'Lax' | 'Strict' (from `samesite`), url, expires? (seconds), partitionKey: { topLevelSite: top_frame_site_key, hasCrossSiteAncestor: Boolean(has_cross_site_ancestor) } }` (E0b `main.mjs:319`, E4-0 `pass2/main.mjs:767`). **Which tab, and how one exists during an import** (Decision Log 3): none of the session's tabs. At the start of the cookies phase, when at least one partitioned row decoded, main creates the **import view**: `new WebContentsView({ webPreferences: { partition, sandbox: true, contextIsolation: true, nodeIntegration: false, webSecurity: true } })` (no preload; never added to any window; never in E4a's tab map, `tabs.json`, the cap, or `browser_tabs`), `void loadURL('about:blank')` and `did-finish-load` awaited (10 s deadline), then `new TabDebugger(view.webContents)` as E4a's `debugger.ts` constructs it (re-pinned: `constructor(webContents: Pick<WebContents, 'debugger' | 'isDestroyed'>, now = Date.now)`, `debugger.ts:55-58`; `send` attaches first when detached), `attach()`, and every `Network.setCookie` goes through `TabDebugger.send` (the only CDP path, E4a Design §10; no `Network.enable` is needed, the probe set cookies on `about:blank` without it). A `__Host-`-prefixed row is host-only by definition and Chrome stores it with an undotted `host_key`, so the rule above omits `domain` for it; Chromium's sanitiser refuses a `__Host-` cookie with a `domain` (the document review's experiment: `Sanitizing cookie failed` with `domain: '.embed.test'`), which `chips-import.test.ts` pins. After the loop, one `Network.getAllCookies` through the same `send` lists the partition's cookies with `partitionKey`; a set row is **verified** when a cookie with its `name`, `domain` (dot-insensitive), `path` and `partitionKey.topLevelSite` is listed; a set row not listed counts as `notVerified` (the report shows `partitioned: { imported, verified }`). The import's `TabDebugger` has **no `onCommand` observer** (E4c's logging observer is attached to tabs' debuggers, never to this one, so no `Network.setCookie` parameter or `getAllCookies` reply reaches a log). Then `detach()`, `view.webContents.close()`, and the view is dropped; a throw anywhere destroys it in the phase's `finally`. E4-0 proved a cookie set this way is sent on the embedded request in its partition and nowhere else; `cookies.set` with a `partitionKey` is never called (a unit test pins that no `partitioned` decode ever reaches the `cookies.set` path). Under `FOCUS_EMULATION === 'on'` nothing changes for the import view (it is never shown).

### 9. Extensions: inspection, wallets, copy, loading, status, toggles

Electron scopes extensions to their session: content scripts run in the partition's pages only, never in MAWS's renderer (the default session); `chrome.tabs.query` sees the partition's WebContents only (E0b: "WebContents appear as tabs"); the e2e checks the app window carries no content-script marker.

### 10. The report

`ImportReport` (Interfaces): per category a block or `null` (not chosen); `outcome: 'done' | 'cancelled' | 'failed'` with `failure` for a run that could not continue (the staging failed, the partition could not be created). ### 11. The active profile, `profiles.json` and Settings › Browser

`<userData>/browser/profiles.json` is E4b's store (`profiles.ts`, written through `atomicWriteFile`, read once at boot and then **held in memory as the one owner of the list**; `ImportedProfilesFileSchema`, Interfaces): one record per imported profile with E4a's four fields first (`profileDir`, `name`, `partition`, `importedAt`) and E4b's after (`storageDirName`: the basename of `ses.storagePath` recorded at import, Decision Log 24; `userDataDir`, `extensions: ImportedExtension[]`, `report: ImportReport`). **E4a's two reads go through this store** (Decision Log 27): `browser.profiles.list` and main's `partitionFor(settings.browser.profile, profiles)` must see a record in the boot that imported it, so both read `profiles.list()` from E4b's store instead of the file (re-pinned, Decision Log 33: E4a landed one accessor, `BrowserDeps.profiles`, read per call, behind both reads; the redirect is one E4b-marked line in main's `startBrowser` call, nothing in `partition.ts` or `register.ts`; E4a's schema is loose and stays E4a's). ### 12. Removal

`browser.import.remove { profileDir }`, after the confirm sheet (`IMPORT_COPY.removeTitle(name)`, the sentence naming what goes: "Removes <name>'s cookies and site data, M history entries, K extensions and its N open tabs from MAWS. Chrome is untouched." and the acknowledgement checkbox gating `DANGER` "Remove", `DeleteDialog.tsx:63-70`'s shape), in this order: (1) every E4a tab whose `partition` is the profile's is closed through E4a's store (`tabs.close(tabId)` per tab; re-pinned: `browser.store.all()` filtered on `tab.partition`, then `browser.store.close(tabId)`, synchronous, with each `entry.view` captured first for the `destroyed` wait, which destroys the view, detaches its debugger, drops its `tabs.json` entry and selects a neighbour; a `browser` main tab pointing at it then shows E4a's "That tab was closed"), awaiting each view's `destroyed`; (2) every loaded extension of the record `removeExtension(id)`; (3) `ses.clearStorageData()` (every storage type, every origin), `ses.clearCache()`, `ses.clearAuthCache()`, and `ses.cookies.flushStore()`; (4) `rm -rf <partitionFolder>` (the extensions); (5) `BrowserHistoryStore.removePartition(partition)` (E4a's method; it returns nothing, so the count is `countPartition(partition)` read just before, re-pinned); (6) the record dropped from `profiles.json` and `browser.import.changed` emitted; (7) the answer `{ removed: { tabs, historyRows, extensions } }`; the renderer then writes `browser.profile: null` if the setting pointed at this profile, and E4a's chrome shows Default for new tabs. Electron cannot destroy a `Session` object or delete an open partition's directory, so the storage directory (`<userData>/Partitions/<storageDirName>/`, Chromium's lower-cased, percent-escaped name: `maws-chrome-default`, `maws-chrome-profile%201`) stays as an emptied shell until the **boot sweep** (Design §14) deletes every `Partitions/maws-chrome-*` directory whose name is no listed record's `storageDirName`, before any session is created for it (Decision Log 18, 24). A removal while an import of another profile runs is refused (`invalid_input`, "an import is running"); a removal of the profile being imported is impossible (its record does not exist yet; Cancel is the way).

### 13. Failure semantics

- **Chrome running with a locked database**: the copy succeeds (E0b) and the import proceeds; if the copied store cannot be opened or read (`SQLITE_CORRUPT`, `SQLITE_NOTADB`, `SQLITE_BUSY` on the copy, a missing `meta`), that category fails with `storeUnreadable` naming the store and the Chrome-running recovery line; the others continue. The hint "Quit Chrome for the most complete copy" shows whenever `SingletonLock` exists.
- **A profile without a Keychain entry** (`security` exit 44): cookies skipped with `keychain: 'missing'`; history and extensions import.
- **Keychain denied or timed out**: cookies skipped with `denied` or `timeout`; the others import.
- **A wrong key** (another installation's key): every row `wrongKey`, 0 set, the report says so (Design §7).
- **A corrupt cookie row** (a bad prefix, an undecodable blob, an unparsable URL): skipped as `corruptRow` or `rejected`; the loop continues; nothing of the row is logged.
- **An extension that fails to copy** (a symlink, `ENOSPC`, `EACCES`): `copyFailed` with the error's code; the rest continue. **An extension that fails to load** (`loadExtension` throws: a bad manifest, a missing file): `loadFailed` with the message's first line; it stays in the record with `enabled: true` so the owner can turn it off or remove the profile; the next boot tries again and reports again.
- **A background that fails on `chrome.<api>`**: `background: 'failed'` with the member named; the extension stays loaded (its content scripts may still work, E0b's partially running five).
- **Cancel mid-way** (Design §14): the run stops at its next row or extension, the Keychain child is killed, the import view destroyed, everything written so far rolled back, the staging deleted; the sheet shows `outcome: 'cancelled'` with the counts reached.
- **The partition cannot be created** (`session.fromPartition` throws): `outcome: 'failed'`, `failure` set, nothing written.
- **A removal while a tab of that partition is loaded**: the tab is closed first (Design §12); a page mid-navigation is closed like any other (E4a's `beforeunload` never blocks).
- **`profiles.json` unreadable**: moved aside as `profiles.json.broken-<epoch>`, started empty, logged once; the imported partitions' storage then belongs to no record and the boot sweep removes it (so the owner re-imports), which is why the move-aside is also announced through `browser.notice { kind: 'profilesFileBroken' }` in the first Browser tool opened (an E4b `kind`, Interfaces).
- **The history store unavailable** (`Index.readOnly`): the history category fails with `indexUnavailable`; the others import.
- **A second `inspect` while one stands**: the earlier staging is deleted and the new one answers. **A second `start` while one runs**: refused.
- **App quit mid-import**: `will-quit` cancels (best effort, synchronous parts only: the child killed, the staging removed); a half-imported partition has no record, so the next boot's sweep removes its storage directory, its partition folder **and its `browser_history` rows** (the history phase commits before the cookies phase, so orphaned `imported` rows are the sweep's to remove, Design §14).

### 14. Cancel, rollback and the boot sweep

An import holds an `AbortController`; each phase checks it between rows, batches and extensions, and the Keychain child and the import view are killed and destroyed on abort. **Rollback** (Decision Log 2): because a profile is importable only when it has no record (a re-import is a removal and an import), the partition is fresh at `start`, so a cancel or failure undoes everything safely: `BrowserHistoryStore.removePartition(partition)`, `ses.clearStorageData()` on the partition, `removeExtension` of anything loaded, `rm -rf <partitionFolder>`, and no record written. **The boot sweep** (`sweep.ts`, exported as `sweepBrowserImports({ userData, profiles, history })` and called from the E4b block in `src/main/index.ts` **before** E4a's `startBrowser`, so it runs before any partition session exists; Decision Log 24): `rm -rf` every `<userData>/browser/import/*`; every `<userData>/browser/maws-chrome-*/` folder whose `partitionDirName` is no listed record's; every `<userData>/Partitions/maws-chrome-*/` directory whose name is no listed record's `storageDirName` (never a name derived from `profileDir`: Chromium lower-cases and percent-escapes it, so `Default` lives at `maws-chrome-default`, and a sweep comparing against `profileDir` would wipe every live partition at every boot); and every `browser_history` row whose `partition` starts with `persist:maws-chrome-` and is no listed record's `partition` (`BrowserHistoryStore.removeImportedExcept(prefix, keep)`, an E4b method). The sweep touches nothing named in `profiles.json` and nothing outside those four patterns; `sweep.test.ts` pins each (a listed `Profile 1` with `storageDirName` `maws-chrome-profile%201` kept; an unlisted `maws-chrome-default` removed; unlisted history rows removed, listed ones kept; a `persist:maws-browser` row untouched).

### 15. Security

- **Nothing from the profile is executed except the extensions the owner confirmed.** `Local State`, `Preferences`, `Secure Preferences`, every `manifest.json` and `messages.json` are parsed with `JSON.parse` under size caps; the stores are read through `node:sqlite` on MAWS's private copies; cookie values and history rows are data written into the partition and the index, never evaluated. No extension loads before `allowUnverifiedExtensions: true` arrives with the start (the service refuses `extensions: true` without it, as Codex's facade does), and never from Chrome's directory.
- **Paths are validated** (Design §2): the user data directory absolute and real; `profileDir` from `info_cache` and the regex; extension ids `/^[a-p]{32}$/`, version directories by regex; every join checked to stay under its root after `realpath`; a store is `lstat`ed and copied only when it is a regular file (`copyFile` follows a symlinked source, so the check comes first); an extension tree is copied with `dereference: false` and a filter that throws on a symlink (Design §9); destinations are created fresh (`COPYFILE_EXCL`, `errorOnExist`). The staging and partition folders are created 0700 under `userData`.
- **The import directory is deleted on every exit path** (Design §4): `discard` (the sheet's close in pick or consent), the end of `start`, `cancel`, a throw, `will-quit`, and the boot sweep; never under a running import.
- **The Safe Storage key**: a `Buffer`, zeroed; never serialised, logged or sent; the `security` child runs with an empty environment, an absolute path, a timeout, `maxBuffer` 64 KiB; its stdout is the only thing read.
- **IPC**: `browser.import.*` is main-owned and accepted only from an app window's top frame (`router.ts:130-140`); a browser view or an imported extension can never invoke it. Inputs are strict zod objects; `userDataDir` and `profileDir` are re-validated in the handler, not only by the schema. Every handler catches whatever its work throws and rethrows a `CommandFailure` (`router.ts:39-43`) whose message went through `redactMessage` (Design §16): the router returns a `CommandFailure` silently (`:122`) but logs any other throw whole (`:123`, and hands its message to the renderer, `:124`), and a `SyntaxError` from `JSON.parse` quotes the input.
- **Partitions**: an import writes only into `profilePartition(profileDir)` (never `DEFAULT_PARTITION`, never another profile's; a unit test pins `partitionOf(record)`); partitioned rows never reach `cookies.set` (pinned).
- **Extensions**: loaded with `allowFileAccess: false`; scoped by Electron to the partition's session; the import records the loaded `Extension.id` and refuses to proceed with an extension whose loaded `path` is not under the partition folder (a defence against a manifest that tricks the loader; `Extension.path` is checked after `loadExtension`).
- **The agent** never sees the import, the stores, the report or the toggles (no tool, no X1 event, no `show_pane`).

### 16. The logging discipline ("nothing logs a value")

One logger, `src/main/browser/import/log.ts`: `importLog(event: ImportLogEvent)` takes a **typed** event (`{ kind: 'phase', importId, phase, done, total }`, `{ kind: 'skip', category, reason, host? }`, `{ kind: 'keychain', outcome, exitCode? }`, `{ kind: 'extension', id, status, background? }`, `{ kind: 'error', where, code, message }`), formats it itself (`[browser-import] cookies skipped wrongKey host=example.test`), and is the only `console.*` call site under `src/main/browser/import/` (an ESLint `no-restricted-syntax` rule scoped to that directory forbids direct `console.*` there, pinned by `log.test.ts` reading the directory); `message` fields are passed through `redactMessage(text)`, which replaces anything that parses as a URL with its host, strips `value=` and `password=` fragments defensively, and caps at 200 characters. Under `MAWS_E2E=1` with `MAWS_E2E_IMPORT_LOG` set, every formatted line is also appended to that file (E2's seam pattern). IPC errors thrown by the handlers are `CommandFailure`s built through `redactMessage` (Design §15), carrying reason codes and counts, never a row. The import's `TabDebugger` carries no observer (Design §8). Acceptance G1 asserts the discipline from outside: the e2e collects main's `stdout` and `stderr` (Playwright launches Electron with piped stdio and `app.process()` is the child; the scene attaches `data` listeners at its start, and the `MAWS_E2E_IMPORT_LOG` mirror is the fallback if a stream turns out drained) and the app window's console from launch to close and checks none of the fixture's **sentinel** values appear: every cookie value, history path and title in the fixture is a long unique string (`e4b-sentinel-<kind>-<random>`), never a two-letter needle (Design §17).

## Decision Log

1. **No settings field; the toggles and every per-profile fact live in `profiles.json`.** The ledger reserved "`browser.profile` setting fields" for E4b, and E4a defined `browser.profile` itself. What E4b must persist is a per-profile list keyed by extension id, discovered by import, dropped with the profile: data, not configuration the owner authors. A settings field for it would mean version 12 (version 11 lands with E4a and may be on the owner's disk before E4b; a strict schema never gains a required field in place, `migrations.ts:29-31`'s lesson applies to settings too), a patch merge for a nullable profile's list, and a second place a removal must clean. `profiles.json` is the file E4a already reads for the pill, written whole and atomically, and the removal drops the record in one write. The reservation is released; the architect may overrule, in which case the fields take version 12 with `fromV11`.
2. **A profile is importable only when it has no record; re-import is remove-then-import; cancel and failure roll back whole.** Merging a second import into a live partition (which cookies to keep, which history counts to add) has no right answer and would make a cancel unsafe (clearing the partition would destroy the owner's live state). With a fresh partition at every start, rollback is `removePartition`, `clearStorageData`, `removeExtension`, `rm -rf` the folder, and no record, and a record always describes a whole import.
3. **The CHIPS rows ride an import view, not a session tab.** A-33 item 8 wants a tab debugger on the partition; an import belongs to no session (tabs are a session's, P-21) and should not open a tab the agent would see or `tabs.json` would persist. An unattached `WebContentsView` in the partition on `about:blank`, wrapped in E4a's `TabDebugger` (so `send` stays the one CDP path), exists for the cookies phase and is destroyed after; E2's capture window is the precedent for a main-owned page that is not a tab (`deliverables/capture.ts`). Cost: one renderer process for a few seconds.
4. **Extensions are staged then renamed into place, never copied twice.** The binding text has every file copied into `import/<uuid>/` first and the extensions ending in the partition's folder. A rename on the same volume is atomic and free, so both hold without copying 600 MB twice (E0b's figure for the owner's 21), and a half-copied extension can never be loaded (it is renamed only after the copy completed).
5. **Inspection stages the two stores before consent, for the counts; extension manifests are read in place.** The consent sheet is meaningful only with "17,554 pages" and "5,112 cookies" on it (E0b S1e; Codex shows categories without counts, and its users cannot tell what they consent to). Copying two SQLite files (38 MB) is cheap and the copy is deleted on Cancel; copying 600 MB of extensions before consent is not, and `manifest.json` and `messages.json` are plain files Chrome does not lock.
6. **The password stores are never opened; the Passwords row shows no count.** E0b suggested a count ("228"); showing it means copying and reading `Login Data For Account`. Nothing in P1 consumes a password (P-17), and "MAWS never opens your password store" is a cleaner promise than "reads it to count". The row reads "Saved passwords — a credential store comes later".
7. **A successful import makes the profile active.** The owner imported it to browse with it; leaving `browser.profile` as it was would make the import look like it did nothing until Settings is visited. The report's last line says so and names where to change it; the pill shows the name on every new tab (A-31's reason). *The owner may prefer an explicit "Use this profile" step.*
8. **Wallets by a verified id list plus a manifest heuristic; the toggle is the owner's.** P-21 wants wallets off by default. Ids are exact and cheap; names catch the rest ("wallet", "metamask", "phantom", "ethereum", "solana", "web3", "crypto", "bitcoin", "defi", "dapp"). A false positive costs one toggle; a false negative loads a wallet the owner then turns off. The executor verifies each seed id against its Chrome Web Store page and drops any it cannot confirm, because an unverified id list is worse than a shorter one.
9. **Extensions Chrome has disabled are unchecked by default, best effort.** `Secure Preferences`/`Preferences`'s `extensions.settings.<id>` tells which of the owner's extensions Chrome itself is not running; importing them by default would surprise. Current Chromium records disablement in `disable_reasons` (a list; a bitmask in older versions) and the legacy `state` key may be absent, so `disable_reasons` non-empty rules first and `state === 0` is the fallback; unreadable or absent → `unknown` → checked. The fixture writes both; G2's checklist (3) is where the real file's shape is confirmed, since no executor may read it. No other key of those files is read.
10. **Chrome session cookies become Electron session cookies.** `has_expires = 0` rows get no `expirationDate`, so they live until MAWS quits (`CookiesSetDetails.expirationDate`, `electron.d.ts:21482-21485`), which is Chrome's own default for a profile without "continue where you left off". Persisting them would outlive what Chrome promised their sites.
11. **Expired rows are dropped before set** (E0b's advice): Chromium would refuse or drop them, and counting them as rejected would blame Chromium for Chrome's housekeeping.
12. **Only "Chrome Safe Storage" is read in P1.** Chrome Beta, Canary, Chromium, Brave, Edge and Arc keep their own Keychain items and folders; mapping the chosen folder to an item name is a small table nobody can test here. A pointed folder of another browser decrypts nothing and the report says the password did not match this profile. Deferred.
13. **The Keychain seam under e2e is `MAWS_E2E_KEYCHAIN`, and an unset seam answers `denied`.** The alternative, letting the child run and fail, would raise a real Keychain dialog on any machine with a Chrome profile. Under `MAWS_E2E=1` the child never spawns.
14. **The Chrome-running hint is advisory.** E0b copied every store under a running Chrome with plain `cp`; blocking would send the owner to quit Chrome for nothing. `SingletonLock` is the cheap, read-only signal; the copy's failure modes are reported per store with Codex's recovery line.
15. **The partition folder's name drops `persist:`.** A colon in a directory name is legal on APFS but shows as "/" in Finder and confuses shell paths; `maws-chrome-<profileDir>` is also the name Electron uses under `Partitions/`, so the two directories read alike.
16. **Imported history rows carry Chrome's counts, and a conflict replaces.** E4a's `suggest` ranks by `typed_count`, `visit_count`, recency; resetting imported rows to 1 would rank the owner's thousand-visit sites under yesterday's one-off. The conflict branch replaces the counts rather than adding, so an import repeated over rows that survived (a crash before the sweep ran, a row visited between inspection and import) never doubles them; the document review found the adding branch would have.
17. **One typed logger; the e2e reads main's own streams.** A discipline that lives in review comments fails at the first `console.error(error)`; a typed event formatter with a directory-scoped lint rule cannot print a row, and the e2e asserting the absence of the fixture's known values in `stdout`, `stderr` and the app console proves it from outside.
18. **Removal clears storage in place and the boot sweep deletes the shell.** Electron cannot destroy a `Session` or delete an open partition's directory; `clearStorageData()` empties it now, and the sweep removes `Partitions/maws-chrome-*` for unlisted profiles at the next boot before any session touches them. The same sweep removes stale `import/*` and unlisted partition folders after a crash.
19. **Background status from `console-message`, `getAllRunning` and `running-status-changed` after a 1.5 s settle.** E0b: "loads is not works"; the probe's wait was 1.5 s and found 13 running and 8 dead; the error text names the absent member (`reading 'onClicked'`), which the report shows as "chrome.contextMenus.onClicked is not available in MAWS" when the manifest's unsupported permissions name the namespace, else the member alone. `running-status-changed` is experimental and only adds a `stopped` reading.
20. **Extension ids come from the manifest's `key`; a mismatch is recorded, never corrected.** Chrome writes `key` into an installed extension's `manifest.json`, so Electron derives Chrome's id (E0b matched workers by directory id). An unpacked, sideloaded extension has no `key` and gets a path-derived id; the record keeps both and the toggles use Electron's.
21. **The sheet is rendered by Settings › Browser's block, not through the dialog store.** `dialogs.ts`'s `OpenDialog` union is C10's and C12's; E8's `ConfirmSheet`, E5's and E6's sheets render from their opener's state with `onClose`, and the import sheet has one opener. No shared file is touched for it.
22. **Reports list hosts per reason, capped at 20, never names, values, paths or titles.** A host tells the owner which site's cookies were skipped; a cookie name can hint at a session token; a URL path is the owner's reading history.
23. **Staged copies are opened read-write, and MAWS runs no write statement.** A copy taken while Chrome holds a hot journal or WAL needs the journal applied on open, which a read-only open refuses; the copy is MAWS's own under `import/<uuid>/`, so nothing of Chrome's is at risk.
24. **The storage directory's name is recorded from `ses.storagePath`, never derived; the sweep runs before `startBrowser`.** Chromium lower-cases and percent-escapes a partition name for its directory (`persist:maws-chrome-Profile 1` → `Partitions/maws-chrome-profile%201`; the document review measured it on 44.4.5), so a sweep comparing `Partitions/maws-chrome-*` names against `profileDir` would have deleted every live imported partition at every boot, silently, and case-insensitive APFS would have hidden it from an `existsSync` check. Recording the basename at import is exact without reimplementing Chromium's escaping; running the sweep before E4a creates any session keeps "before any partition is prepared" true; and the relaunch step of Acceptance case 1 proves the cookies survive a boot.
25. **Decrypt first, classify after; the wrong-key verdict is "every attempted decrypt failed".** Filtering expired and insecure-None rows before decryption would make a wrong key fail four of the fixture's five rows and, on a real store (which always has such rows), turn "the password did not match" into a pile of `corruptRow` skips. Decrypting every encrypted row first costs microseconds and matches the probe's 5 of 5. The verdict counts attempted decrypts only, so a store of plain-value rows is never called `wrongKey`.
26. **Orphaned `imported` history rows are the sweep's to remove.** The history phase commits before the Keychain and cookies phases, and a quit or crash between them leaves `source = 'imported'` rows for a partition no record names; nothing else would ever remove them. `removeImportedExcept('persist:maws-chrome-', listed)` at boot closes that, and the replacing conflict branch (Decision Log 16) makes a later import of the same profile correct even if the sweep did not run.
27. **E4b's `profiles.ts` is the one in-memory owner of the list, and E4a reads through it.** E4a's document says it "reads `profiles.json` when present" without saying when; two readers of one file would let main's `partitionFor` miss a record written in the same boot, so the first tab after an import would fall back to the default partition with a `profileMissing` notice while the pill claimed otherwise. One owner, read through by E4a's two call sites in an E4b block, removes the question; M0 re-pins the call sites.
28. **The running sheet is not dismissible, staging is deleted only in pick and consent, and the active-profile write lives in the store.** A sheet whose close deleted staging under a running copy would corrupt the import; a sheet whose opener unmounted (Settings closed, a window reload) would otherwise lose the `done` write and make "New tabs browse as …" false. The run belongs to main, the renderer store mirrors it app-wide, and the sheet is a view of the store that can be closed and reopened.
29. **The consent says that agents' tabs will be signed in as the profile.** Cookies are the one trust-boundary widening of this child: after the import every tab, the agent's included (`browser_*`, E4c), carries the owner's sessions. A pill after the fact is not consent; one line under the Cookies row is, and the activation stays automatic (Decision Log 7) with the explicit-step alternative put to the owner in the hand-back.

The delta from the pin this document cites is A-36 to A-41, P-23 to P-25 and status rows; A-36 accepts this Decision Log with its precisions, P-23 makes Decision Log 7 and 29 the owner's ruling (automatic activation, the consent's agents line), A-41 records E4a as landed with additive names (among them `BrowserDeps.profiles`, the single accessor E4b redirects, and `Partitions.registerRequestRule`, the one `webRequest.onBeforeRequest` composition point). 31. **2026-10-06 (M0) `startBrowserImport`'s `browser` argument is E4a's `Browser` handle, gaining one field, `partitions`.** Its type in E4b is `{ store: Pick<TabStore, 'all' | 'close' | 'onViewCreated'>, partitions: Pick<Partitions, 'session' | 'registerPreparer'> }` and main passes the handle itself. E4a's handle already carries the tabs store (`index.ts:48-52`), whose `all()` and `close(tabId)` close a partition's tabs without a new function (the filter on `tab.partition` lives in E4b's `remove.ts`), and whose `onViewCreated` gives `profilesFileBroken` its session (Concrete Steps, `browser.notice`). What the handle lacks is the partitions, which `startBrowser` constructs privately (`index.ts:66-69`); an E4b block adds `partitions: Partitions` to `Browser` and to the returned object. `partitions.session(partition)` is exactly "open and prepare once, as E4a does" (Design §7, §9), which the cookies phase, the import view's partition, `ses.storagePath` and `setExtension` need; it throws when Electron cannot open the partition (Design §13's `failed`). Lands with the wiring (Task 2.5); Tasks 2.3 and 2.4 code against the `Pick` types over fakes.

## Surprises & Discoveries

- 2026-10-06 (M0): E4a's partition preparation is synchronous and `loadExtension` is not, so at every boot the first page of an imported profile's partition could load before its extensions register (Concrete Steps (e)). Task 2.4 settles it: Acceptance case 1's relaunch asserts the content-script marker in a new tab, so the per-boot load must be complete (or the first page must wait for it) before an imported partition's first page loads; the choice and its proof go in the Decision Log.
- 2026-10-06 (M0): copying the `slowCopy` padding (64 MiB) took about 140 ms on this machine, likely too short for Acceptance case 3's e2e to press Cancel during the extensions phase; `SLOW_COPY_BYTES` in `test/support/chrome-profile.ts` is the one constant to raise, or the e2e takes a deterministic seam (M4 decides).
- 2026-10-06 (M0): E4a's `BrowserHistoryStore.removePartition` returns void, so the removal's history count needs an E4b `countPartition`; `browser.notice` for `profilesFileBroken` is emitted from E4b's own `onViewCreated` subscription since E4a's notice route lives in `tabs.ts`; E4b's Settings sentences go in a sibling `BROWSER_IMPORT` const beside E4a's `BROWSER` in `settings-tab/copy.ts` (Concrete Steps).
