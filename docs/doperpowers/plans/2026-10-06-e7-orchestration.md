## Purpose

After E7 the owner supervises orchestration without the terminal (P-3's first item, "live workflow progress"). A Workflow run opens from the summary's Background work row or its card into a **widget**: phases on the left with `done/total`, the selected phase's agents on the right with model, state and elapsed; a click on an agent opens its transcript in the Subagents drill-in; Stop stops the run where the engine allows it; the widget draws the same from the live wire and from the engine's files, so a run from yesterday reads as it did while it ran. The Subagents tool's resting state becomes a **tree**: running agents first with their nested children under them, each parent's finished children folded under a count, finished roots under a folded Done section, orphans marked as today. Cross-session traffic becomes legible rows: a `ListAgents` result draws as a list, a `SendMessage` to another session draws as a message between sessions naming the recipient, a message from another session draws with its sender and a **Reply** control whose text the session's agent sends with `SendMessage`; teammates draw under their lead. The **Tasks panel** (`show_pane 'tasks'`) edits a task list through the session: a status change, a reorder or a new task sends one steer the agent executes with the engine's task tools; the edit shows as pending until the task files confirm it, and an edit the agent does not act on is shown as such after a bounded wait; MAWS never writes under `~/.claude` (P-11). **Scheduled loops** the engine exposes in the transcript (`CronCreate` calls and the durable `scheduled_tasks.json` of the project) are listed with their next run and a link to the creating turn. This closes the parent's §2 items 1 and 12.

To see it working: `pnpm dev`, open a live session that ran a Workflow, click the summary's Background work row, then the run's card; open Subagents for the tree; in the Tasks panel change a task's status and watch the row go pending, then confirmed; send the session a message from a second session (`claude` in a terminal, same `~/.claude`, `SendMessage {to: <this session's name>}`) and reply from the row.

## Terms

- **Task graph**: the renderer's one reducer over the X1 task and subagent events, the status's background list and the engine store's sidecars and workflow runs (`src/renderer/src/tools/agents/model/task-graph.ts`), kept per session by the task-graph store (`store.ts`) and fed only through the **agent-work client** (`client.ts`). It is **wire-only and current-launch**: a disk-only session never reads `session.events` and a live one takes only the current launch's events (`store.ts:2-5, 153, 173`).
- **Activity**: the transcript's disclosure-independent per-turn record, `TurnActivity` (`src/renderer/src/transcript/model/activity.ts:33-39`), served by `useTranscriptStore.activity(key)` (`src/renderer/src/stores/transcript.ts:56`), built from backfill and live events alike; the summary's Sources read it (`panel/summary/derive.ts:89-105`), so does `openSubagent` (`tools/agents/actions.ts:32`). Facts a transcript carries (cron calls, listings) live here.
- **Run**: one workflow execution: the `local_workflow` task on the wire (`task.started`, `workflow.progress`, `task.notification`) and on disk `<session>/workflows/<runId>.json` plus `subagents/workflows/<runId>/journal.jsonl` and the agents' sidecars (`src/engine-host/fs/workflows.ts`, `subagents.ts`).
- **Progress snapshot**: one whole array of `workflow_phase` and `workflow_agent` rows (`model/workflow-progress.ts:9-13`), the wire's `workflow.progress.progress` or the disk snapshot's `workflowProgress`, the same shape (`fs/workflows.ts:4-6`).
- **Widget**: the Background work tool's drill-in view for one run (Design §2). **Tree**: the Subagents tool's resting view (Design §3).
- **Peer message**: a `user` frame or record whose origin kind is `peer` (SPEC 11 §11.11.5), carrying either the `<cross-session-message from=…>` envelope of another session (SPEC 38 §38.23.1) or the `<agent-message from="<agentId>">` wrapper of an in-process agent's `SendMessage` to the main conversation (C8b's finding, `task-graph.ts:335-348`).
- **The two emission sites**: the live normaliser (`src/engine-host/normalizer.ts`, the user-frame branch at 342-358) and the disk backfill (`src/engine-host/fs/backfill.ts`, `userEvents` at 174-233 and the attachment branch at 109-134). Both turn user records into `user.message`; a fact derived from a user record must be derived at both, else it exists live and vanishes from disk.
- **Steer**: `session.steer {content, priority: 'next'}` (`src/shared/ipc/schema/session.ts:96`): a user message the engine folds into the running turn at its next tool boundary, or starts a turn with when idle (`pass3/steer-next.jsonl`); the relay composer's mechanism (`relay-store.ts:184`). Every edit E7 asks of the session is one steer.
- **Pending edit**: a Tasks panel edit between its steer and the task files' confirmation (Design §6). **Cron job**: one `CronCreate` record, session-only (in memory, listed from the transcript) or durable (`<project>/.claude/scheduled_tasks.json`, SPEC 22 §22.5).
- **Listing**: the `ListAgents` result's `listing` text, sections `Subagents (n):`, `Teammates (n):`, `Peer sessions (n):`, rows `"  " + [primary, ...extras].join("  ·  ")` (SPEC 38 §38.26.3).

## Design (the residue §3 E leaves open, with reasons)

### 1. Ownership and data flow

One renderer owner for every surface: the agents tool (`src/renderer/src/tools/agents/`). Two models feed it, each for what it is built to see: the **task graph** for runs and agents (wire plus the sidecar and run files; current launch when live, disk when not), and the transcript's **activity** for facts the transcript itself carries, on both paths and across launches (cron calls and deletions, `ListAgents` listings), since the task graph never sees disk events or an earlier launch's (Terms). The transcript's derive remains the one model of rows. The host changes at its **two emission sites** only: the normaliser and the backfill each emit two X1 events from the peer records they already turn into `user.message` (§4), through one shared parser, so a row exists live and from disk alike. No new IPC command: every edit is `session.steer` from the renderer, as the relay is (`relay-store.ts:184`); every read is an existing `fs.*` or `files.*` command. - status: `[MAWS tasks] Using TaskUpdate, set task #<id> (<"subject">) to status <pending|in_progress|completed|deleted>. Do it now, then continue what you were doing.`
- create: `[MAWS tasks] Using TaskCreate, create a task with subject <"subject"> and description <"description">. Do it now, then continue what you were doing.`
- reorder: `[MAWS tasks] Using TaskUpdate, merge metadata {"order": <n>} into task #<id>. Do it now, then continue what you were doing.` — **one move is one call**: the moved task gets the midpoint between its new neighbours' effective orders (a missing order is the numeric id; above the first row, `first − 1`; below the last, `last + 1`). Only when the midpoint can no longer be represented distinctly (the neighbours' orders differ by less than 1e-6, or tie) does the steer renumber every open task 1..n (`… into these tasks: #a → 1, #b → 2, …`), the one multi-task steer.

The `[MAWS tasks]` prefix mirrors E1's `[MAWS ask <askId>]` steer and tells a reader of the transcript who asked. Reorder is MAWS's `metadata.order` key (Decision Log 3): the engine's record has no order field, `TaskList` sorts by id, and dependency edits (`addBlockedBy`) are irreversible on the wire, so the only reversible, agent-respected place for an order is the metadata merge the engine documents; the agent's own `TaskList` ignores the key, which is harmless.

**The state machine** (`tasks-edit-store.ts`, zustand, memory; pure transitions in `model/task-edit.ts`): `TaskEdit { id; appSessionId; listId; kind: 'status' | 'create' | 'reorder'; taskId: string | null; want: { status } | { subject; description } | { order: Record<taskId, number> }; idsAtSend: string[]; state; messageUuid; sentAt; startedAt; message }` with states `sending` → `asked` (the steer answered with its uuid) → `started` (`command.lifecycle started` for that uuid) → `confirmed` | `unconfirmed` | `failed`:

- **confirmed**: a **fresh** list satisfies the want: the task's `status` equals the wanted one (a `deleted` want: the id is absent); a created task with the wanted `subject` exists **under an id absent from `idsAtSend`**; every task in the order map carries `metadata.order` equal to it. Freshness: on `fs.tasksChanged {listId}` the store itself `await`s `queryClient.fetchQuery({ queryKey: ['fs.tasks', listId], queryFn: () => agentWorkClient().tasks(listId), staleTime: 0 })` (a forced read that needs no mounted observer; the invalidation `ipc/events.ts:197` makes alone is asynchronous and observer-dependent), and it also subscribes to `queryClient.getQueryCache().subscribe` for `updated` events of that key with fresh data (an observer's refetch), checking every pending edit against the data in any state from `asked` on (an idle agent may act before the lifecycle frame reaches the renderer).
- **unconfirmed** ("the agent did not act on it"): in `started`, the steer's own turn ends without confirmation: `command.lifecycle completed` for `messageUuid`, or a parent `turn.ended` whose `userMessageUuids` contains it (`isEchoReceipt` ignored; another turn's end, an E1 ask steer's, a cron fire's, is not this edit's), or 120 s pass since `startedAt`. In `asked` there is **no clock**: a `'next'` steer legitimately waits behind a long tool call or a pending permission (`RELAY_COPY.askedLongWait`'s case); the line shows the elapsed and the relay's clause instead.
- **failed**: the steer refused by the host (`session.steer` rejected: not ready, content refused), `command.lifecycle` `cancelled` | `discarded` | `refused` before `started` (the relay's rule, `relay-store.ts:96`), or `process.exited` of the parent (`agentId === null`).
- **`unconfirmed` and `failed` are not terminal**: a later fresh list that satisfies the want confirms the edit (a slow agent, a late write), so a Retry after a false unconfirmed never doubles an edit the first steer did land; the edit leaves the store only on `confirmed` or `Dismiss`.
- One pending edit per task and one pending reorder per list; a second edit on the same task while one is `sending`, `asked` or `started` is refused by the view (the control is disabled with `Waiting for the last edit`); a `create` is never refused by another create.

The store watches the session's batches through `agentWorkClient().onEventBatch` only while an edit of that session is pending (the relay store's subscribe-while-pending pattern, `relay-store.ts:156-164`), reading `turn.ended`, `command.lifecycle` and `process.exited` of the parent lane, and `onTasksChanged` for the fetch above.

**What the panel shows.** A pending edit (`sending`, `asked`, `started`) is drawn optimistically: the row in its wanted status with a pending mark (spinner) and the line `Waiting for <session> · <elapsed>` (with the relay's turn clause while `asked` and the parent's turn is open); a reorder shows the rows in the wanted order with the mark on the moved row; a create shows a ghost row at the end. `confirmed` drops the overlay (the list now says it) and the edit leaves the store. `unconfirmed` drops the overlay and shows under the row `<session> did not apply this edit` with `Retry` (a new steer) and `Dismiss`. `failed` shows `Couldn't ask <session>: <message>` with `Retry` and `Dismiss`. Edits are disabled, with the reason as a line under the heading, when the session is not live here (`Editing needs the session running here`), when the list id is not known yet (the checklist's sentence), and when the session's engine offers no task tools: the task-graph **store** records `tools: string[] | null` on the entry from the `session.init` events of the launch (read before the graph's `TASK_EVENT_KINDS` filter, which is unchanged) and a list without `TaskUpdate` reads `The engine offers no task tools in this session` (the owner's default model is outside the allowlist, Grounding; Residue 2). Reading is never disabled.

### 8. Replay parity and the disk path

Every surface derives from X1 events available on both paths plus disk reads both paths share: `workflow.progress` is emitted on the disk path per snapshot change (`fs/workflows.ts:66-80`) and `fs.workflows` is read by both; sidecars and `parentAgentId` come from `fs.subagents` for both; `peer.message` and `subagent.message` are emitted at both emission sites from the same parser (the normaliser for the live stream, `backfill.ts` for a JSONL); `SendMessage`, `ListAgents`, `CronCreate` and `CronDelete` are tool pairs the JSONL carries and the activity folds on both paths; the task list and the durable cron file are files. The parity proof is `backfill.test.ts` over M0's recorded JSONL (the same two events and rows as the live frames give) and a disk-only e2e case (M7). What a terminal-resumed session lacks: pending edits and pending replies (renderer memory), by design (§1).

### 9. Failure semantics

- A progress snapshot row that fails the parse is dropped, never thrown (`workflow-progress.ts:3`); a run with no phases shows `Phases arrive with the first progress frame`; a journal that names no agent id leaves the row inert; a ref id that resolves to nothing leaves the list with `Run not found yet`.
- A sidecar meta that cannot be read leaves the agent at its wire facts (today's rule); an unknown parent is an orphan, never a dropped row.
- An envelope the parser refuses leaves the raw user bubble as today (no silent loss); a reply whose steer the engine drops reads `Reply failed: the engine <state> it before starting it` with the text back in the composer (the relay's O1 rule, `RelayComposer.tsx:84-92`); a `SendMessage` the engine answers `success: false` reads failed with its message.
- A `ListAgents` result the parser does not recognise draws the result's text as one note.
- A task edit never writes a file; its worst case is `unconfirmed` with Retry, and a late write still confirms it. A list that fails to read shows `Tasks unavailable: <message>` and no controls. A steer refused by the host is `failed` at once with the host's message.
- A durable cron file that fails to parse shows `Scheduled jobs unavailable: <message>` for the file and keeps the transcript's rows; an invalid cron expression in a record shows the row with `next run unknown`.
- Nothing E7 adds blocks a render: every parser returns `null` or a partial, every read has an unavailable sentence.
