## 1. Purpose

Today `/plugins` is a 560 px dialog of four stacked sections (Installed, Marketplaces, Available, Loaded) that prints one row per installation record: on the owner's machine 130 rows for 29 plugins, with absolute project paths, "unknown" versions and three competing buttons on every row. `/skills` is an undifferentiated list of slash names with Use links. - `/plugins` opens a library-sized centred dialog: "My items" and "Browse" beside the title, then search, filter, sort and an Add menu. My items lists each plugin once, under "In this project", "From Anthropic & Partners" or "From marketplaces you added", with its display name, author, description, version and date. Selecting one opens its detail: what it is, who made it, its version and source, the scopes it is installed at as chips, the enable control for the selected scope, Update, Uninstall behind E8's confirmation, whether it is enabled for this project and whether it is loaded in this session (and when that was observed), and what is inside it (commands, skills, agents, hooks, MCP servers and the rest), read from the installed files and marketplace entry without running any of them.
- Browse shows what the engine's configured sources offer, one card per plugin, truthfully marked installed or not, with an install count only where the engine supplies one.
- The Add menu holds Add marketplace and Manage marketplaces; the latter says that removing a marketplace uninstalls its plugins.
- `/skills` is the same kind of library: grouped rows with the plugin a skill comes from, "Use in chat" as the primary action, Reload kept.
- `/sandbox` keeps telling the truth and offers no toggle.
- When P2-C's built-in to-human mod exists, My items lists it under "MAWS mods · Built in" with its switch.

Every change still runs the engine's own CLI after E8's confirm sheet; MAWS writes nothing under `~/.claude`.

How to see it working: open a session, type `/plugins` (a wide dialog opens; My items lists each plugin once, grouped); select a plugin (its detail shows the scope chips, "Enabled for this project", "Loaded in this session · Loaded now" or "Loaded last time, 2 days ago", and What's inside); switch to Browse (cards from the configured marketplaces, installed ones marked); open Add › Manage marketplaces; type `/skills` ("Use in chat" puts `/<skill> ` into the composer). §6.3 gives the exact runs.

## 5. Residue design

### 5.1 Terms

- **Installation** — one record of `claude plugin list --json`: a plugin id (`name@marketplace`) at one scope (`user`, `project`, `local`, or a pseudo-scope the engine lists: `session` for `--plugin-dir` folders, `synced` for claude.ai sync, and skills-directory plugins `name@skills-dir`), with its project for project and local scope. E8's identity `(id, scope, projectPath)`; unchanged.
- **Plugin identity** — a plugin id. The library draws one row per identity, whatever its number of installations (the owner's doperpowers has 47).
- **The session directory** — the CLI's `cwd` (E8 D-16: the status's `cwd`, else the record's `directory`). The CLI's `enabled` is the plugin's effective state in the settings that directory reads, and `projectEnabled` whether its `.claude/settings.json` enables it (U3 F1).
- **Here** (an installation) — its `projectPath` is the session directory exactly (realpaths compared in the host). Only an installation here, or a user one, can be changed from this session (E8's whole-branch rule: another project's installation is managed from a session there). **Covers here** — its `projectPath` is the session directory or an ancestor of it (Desktop's own rule for "In this project", `readable/app-2.16120.0/main-process/index.chunk-kXuYPTnM.js:168269-168282` `readRegistryWithResolver`); a worktree under the project is covered.
- **Library** — the second widget size (X19) and the composition drawn in it: a header, a list pane that scrolls on its own, and a detail that replaces the list.
- **Source group** — the section a plugin is drawn in (§5.4).
- **Manifest view** — what `plugins.manifest` answers for one installation or available entry: what the plugin says about itself and an inventory of its components, read from files, nothing executed (§5.5).

### 5.2 The library size (X19)

`SlashWidget` (`src/renderer/src/composer/mentions/widgets.ts`) gains `size?: 'utility' | 'library'`, utility by default; `/plugins` and `/skills` register `library`. `WidgetDialogHost` (`src/renderer/src/composer/WidgetDialog.tsx`) keeps its one Radix dialog, its one open widget, its overlay and its `onCloseAutoFocus` (focus back to the session's composer) and only chooses the content box by size, from one exported table so P2-D's chooser host can reuse the library box: utility `w-[min(560px,calc(100vw-48px))] max-h-[85vh]` (today's); library `w-[min(960px,calc(100vw-48px))] h-[min(85vh,800px)]`. The width is §4.8's; the 800 px cap is Desktop's (its library shell is `w-[calc(100vw-2rem)] max-w-[1024px] h-[calc(100dvh-2rem)] max-h-[50rem]`, `readable/app-2.16120.0/web/app/v1/shared-25-C_M72Q4j.js:1455-1505`). The library height is fixed, not a maximum, so switching tabs, filtering to nothing or drilling into a detail never resizes the dialog under the pointer.

`WidgetFrame` gains `size` (default utility) and, for library, two slots: `heading` (drawn after the title, at the left: the My items | Browse switch) and `toolbar` (drawn at the right of the head, before the `/name` code and the close button: Search, Filter, Sort, Add or Reload). So the library's header is the frame's head, the title drawn once (Desktop's in-dialog header: title and switch in one cluster, actions `ml-auto`, `readable/app-2.16120.0/web/app/v1/ccefd43d9-CoNZ8js5.js:18-57`). Utility keeps its body's `max-h-[60vh]` scroll; library gives the body the remaining height (`min-h-0 flex-1`) with no scroll of its own, since the list pane and the detail scroll inside it.

Keyboard, the charter's rule with Desktop's refinements (`readable/app-2.16120.0/web/app/v1/c13348442-Cgf_p4WP.js:23-77`, `:266-277`): the dialog's own Radix layer dismisses on Escape from a document-level capture listener before any React handler runs (`@radix-ui/react-dismissable-layer` 1.1.19, `dist/index.mjs:91-105`), so the search field's clearing lives in `WidgetDialogHost`'s `Dialog.Content onEscapeKeyDown` (`WidgetDialog.tsx`, B's dated block): when the event's target is a field marked `data-escape-clears` and holds text, it calls `event.preventDefault()` and clears the field, and the dialog stays; inner Radix layers on top (the Filter, Sort and Add menus, the two marketplace dialogs, E8's confirm sheet) take their own Escape first; `WidgetFrame`'s own Escape handler gains only a guard for E8 D-16's case, ignoring an event already `defaultPrevented` or whose target lies outside the frame's DOM subtree (a portalled layer's Escape bubbling through React); on open the frame takes focus as today and `/` (no modifier, focus not in a text field) focuses the search field; Back (a button) and ⌘[ return from a detail to the list with its search, filter and scroll intact. The guard is a dated block in `WidgetFrame.tsx`, which A's M3 also edits.

Rejected: a separate library host (a second one-open rule and focus return; the parent's Decision Log 12); a maximum height (the dialog would jump as the list grows and shrinks); a duplicated title (the frame's head plus a library header); a right-panel or tab destination (a §5.4 amendment the owner did not ask for).

### 5.3 The data: what the CLI gives and what MAWS keeps

`claude plugin list --json` rows carry `installedAt`, `lastUpdated` and `projectEnabled` (U3 F1), which `installedOf` (`src/engine-host/plugins/cli-result.ts`) drops; `--available` rows carry `source` and, for one marketplace, `installCount` (U3), which `availableOf` drops. The reductions keep them, additively:

- `InstalledPlugin` gains `installedAt: string | null`, `lastUpdated: string | null` (ISO times as printed; null when absent), `projectEnabled: boolean` (false when absent), `here: boolean` and `coversHere: boolean` (§5.1, computed in the host from realpaths: `fs.promises.realpath` of the `cwd` and of `projectPath`; a project that no longer exists is neither). When the row names `readFromFolder` (a directory marketplace's plugin the engine loads in place), `version` is the row's `folderVersion` when it has one, since that is the copy that loads (2.1.292 `cli.pretty.js:207456`). Nothing else of the row crosses: the row's `mcpServers` carries header and environment values verbatim (U3 F1) and stays dropped.
- `AvailablePlugin` gains `source: PluginSourceRef | null` (the entry's source reduced to `{kind, url, repo, path}`, or the relative path string an in-repository entry has) and `installCount: number | null` (only the CLI's own number; null when the row has none).
- `Marketplace` is unchanged (its `source` kind and `locator` decide the source group).

A version reading `unknown` or nothing is no version: the row shows none and the detail "Version not reported". A 12-character commit prefix (2.1.295 writes one for a manifest with no version, U3 F1) is a version the engine reports and is shown as it is. No version is ever inferred from a directory name.

### 5.4 Plugin identity and grouping

A pure module, `src/renderer/src/widgets/plugins/library.ts`, turns the reads into the list.

- **Relevance.** An identity is listed by default when any of: a `user` installation; an installation that covers here; the CLI reports it `enabled` here or `projectEnabled` (a plugin committed to this project's settings and recorded for another worktree of it loads here, U3 F1 and the review's finding; the owner's doperpowers has 46 project records under one repository's worktrees); it is in this session's loaded list; a pseudo-scope installation. An identity with none of these (installed only for other projects, not enabled here) is listed only under Filter › "Other projects", read-only.
- **The representative installation** of an identity, used by its row (version, date, the overflow's target scope) and as the detail's default chip: the narrowest installation here (local, then project), else the user one, else one that covers here, else a pseudo-scope one, else the most recently updated of the others. A row's or detail's mutations act only on an installation here or a user one; an identity with neither shows no switch, Update or Uninstall, and says where it is managed ("Installed for <project> · manage it from a session there", E8's words).
- **Groups**, Desktop's headings in Desktop's order (`readable/app-2.16120.0/web/app/v1/c27f32a39-QZ0BG6_X.js:843-859` `Ze`; the priority rules `c08f249ae-BvqdxSI4.js:407-439`), MAWS drawing those its data can fill:
  1. **"In this project"** — an installation covers here, or the CLI reports `projectEnabled`.
  2. **"Created by you"** — a skills-directory plugin (`name@skills-dir`) or a folder loaded with `--plugin-dir` or `CLAUDE_CODE_PLUGIN_DIRS` (Desktop's heading for the user's own local plugins).
  3. **"Synced from claude.ai"** — a `synced` installation (the engine's own heading for them; Desktop's claude.ai groups "From your organization" and "Shared with you" rest on account data MAWS does not read).
  4. **"From Anthropic & Partners"** — a plugin of the marketplace whose repository is `anthropics/claude-plugins-official` (by `repo`, or a `https://github.com/anthropics/claude-plugins-official` URL with or without `.git`), Desktop's rule (its default marketplace repository, `readable/app-2.16120.0/web/app/v1/cf0e8a0d3-CPfiobm4.js:154-187`; `main-process/index.chunk-kXuYPTnM.js:348393-348408` `isDefaultMarketplaceSource`), or of the engine's built-in directory (`anthropic-plugin-directory`, whose entries Anthropic reviews, U3 Method 1). Every other marketplace, the community one (`anthropics/claude-plugins-community`) included, is not in this group.
  5. **"From marketplaces you added"** — everything else.
  Desktop's "Needs attention" (security-scan grades), "From your organization" and "Shared with you" rest on claude.ai data and are not drawn. With Sort › "Last updated" and Show › "All plugins", an empty "In this project" is still drawn, saying "No plugins installed for this project yet." (Desktop, `c6a2a31c4-DlHruLy-.js:2346-2384`, `:4434-4471`); any other empty group is not drawn. MAWS mods · Built in comes last (§5.12).
- **The row** (Desktop's row, `c27f32a39-QZ0BG6_X.js:130-293`, `:325-395`, `:536-678`): a `size-9` icon tile with a neutral plugin glyph (Desktop's fallback; the engine's manifest has no icon field, U3 F2, and MAWS has no category icon set); the name (the manifest's `displayName`, else the name with its first hyphen-separated word capitalised and the words joined by spaces, Desktop's rule: "code-review" → "Code review"); "New" when the representative installation's `lastUpdated` is within 14 days (tooltip "Added or updated in the last 14 days"); "Disabled" when the CLI's `enabled` is false here; a second line "by <author> · <description>" (either part omitted when absent; with no description, "<n> skills" from the inventory); at the trailing edge the version when there is one (the parent's §2 item 2 asks for it; Desktop shows it only in the detail's byline, §10 Q4) and the date of `lastUpdated` (relative under seven days, "3 days ago"; then "Oct 3", the year added when not this year; full date and time in the tooltip); and the overflow (`⋮`, "More actions for <name>"): "Turn on" or "Turn off", "Update", a separator, "Uninstall…" (danger). The whole row is one target, "View <name>", opening the detail.

### 5.5 The manifest service (`plugins.manifest`)

A narrow host-owned read that answers, for the installations and available entries the renderer names, what each plugin says about itself and what it contains, by reading files only: no plugin code is loaded or run, no hook, monitor or server is started, nothing is fetched or written.

**Where.** `src/engine-host/plugins/manifest.ts` (the reader, injectable `fs`) and `front-matter.ts`, registered in `src/engine-host/ipc.ts` after E8's block; owner `engine-host`, like every `plugins.*` read (E8 D-2).

**Input and admission.** `{cwd, items: ({kind: 'installation', id, scope, projectPath} | {kind: 'available', pluginId})[]}` (at most 256). The renderer never names a path. The host keeps, per `cwd` (the last 16, least recently listed dropped first), the rows of its own last `plugin list --json` and the rows of its own last `plugin marketplace list --json` (the ones `plugins.list` and `marketplaces.list` answered). An installation resolves to the row's `installPath`, or its `readFromFolder` when it has one (the copy the engine loads); a row with no `installPath` answers `unknown` (never `path.resolve('')`, which is the host's own cwd). A plugin's marketplace resolves to that marketplace row's `installLocation`. An item the kept rows do not name is resolved once more by running the listing; still absent, it answers `unknown`. These paths are the trust anchors: the engine says this directory is the plugin and this one its marketplace. Every file read is confined to the realpath of its anchor (a file whose realpath leaves it is skipped as a problem), read only if `lstat` says it is a regular file, and bounded (below). Rejected: the renderer passing paths (they would need the same check against the listing anyway); reading `installed_plugins.json` or `known_marketplaces.json` directly (E8 D-12: one reader of the engine's registry, the CLI).

**The manifest, as the engine composes it** (2.1.292 `cli.pretty.js:806207-806240`): the plugin's `.claude-plugin/plugin.json` when present, and its marketplace entry (the object named after the plugin in `<installLocation>/.claude-plugin/marketplace.json`, which can be large: read up to 8 MiB) when its marketplace is known. With no `plugin.json`, the entry is the manifest (the four LSP plugins of `claude-plugins-official` the owner has installed are entries with `"strict": false` whose install directories hold only `LICENSE` and `README.md`; the review's finding). With both, the entry's `displayName`, `description`, `author`, `homepage`, `repository`, `license` and `keywords` overlay the file's, and its component fields add to the file's. Parsed with a tolerant schema keeping only `name`, `displayName`, `version`, `description`, `author.name`, `license`, `keywords` and the component fields; unknown keys ignored. An available entry's view is its marketplace entry, plus its files when its source is a path inside the marketplace's own clone (`./plugins/x`); an entry whose plugin is not on disk (a `git-subdir`, `url` or directory entry) has no inventory, and its detail says "What's inside is listed once it is installed".

**Components, per kind as the engine's manifest schema defines them** (2.1.292 `cli.pretty.js:673281-673299`):

| Kind | Default | A manifest field | Item drawn |
|---|---|---|---|
| Commands | `commands/**/*.md` (a nested directory is `dir:name`) | `commands` (a path, a list, or an object of name → `{source | content}`) **replaces** the default | name; description from front matter |
| Agents | `agents/**/*.md` (recursive, 2.1.292 :729782-729814) | `agents` (a path to a file or a folder, or a list of them, :753347-753359) **replaces** the default | name and description from front matter, else the file name |
| Skills | `skills/*/SKILL.md` | `skills` (paths) **adds** to the default | name and description from front matter, else the directory name |
| Hooks | `hooks/hooks.json` | `hooks` (a path, an object, or a list of either) **adds** | "<event> · <matcher>" per matcher; a hooks module (`modules`) counted as one "hooks module" |
| MCP servers | `.mcp.json` | `mcpServers` (a path or an object) **adds** | name and transport (`stdio`, `http`, `sse`, `ws`); an MCPB file or URL entry counted as one "MCP bundle", never read or fetched |
| Language servers | `.lsp.json` (2.1.292 `Eje` :708910-708930) | `lspServers` (a path, an object, or a list of either) **adds** | name |
| Monitors | `monitors/monitors.json` | `monitors` (a path or an inline list) **replaces** the default (`FLr` :805026-805040) | name and description, never its command |

The engine also reads each component field under `experimental.<kind>` beside the top-level one (`Ls` :149842); the reader does the same.

Front matter is read from the first 8 KiB of a Markdown file by a small reader of the leading `---` block (plain, single- and double-quoted, and `>`/`|` block scalars for `name` and `description`; anything else reads as no description); no YAML dependency. Bounds, per plugin: 1,000 files, 200 items per kind, a file over 256 KiB (8 MiB for `marketplace.json`) skipped; per call: 2.5 s of reading, the representative installations first, so a call that also had to list fits the bridge's 10 s bound (`src/engine-host/ipc.ts` head comment); past a bound the plugin's view carries `partial: true` with what it read.

**Redaction (G3's "secrets redacted").** The answer carries names, descriptions, kinds and counts only. Never: a hook's or monitor's command, an MCP server's `command`, `args`, `env`, `headers` or URL, an LSP server's command, `userConfig` values, any value read from settings. **Problems** use a fixed vocabulary, `<relative path>: not valid JSON | too large | outside the plugin | not a regular file | could not be read | unknown shape`, and never carry an exception's message or a file's value (Node's `JSON.parse` error message quotes the input it failed on: the review measured `Unexpected token 's', "{"a": sk-secret-123}" is not valid JSON` on this repository's Node 22.23.2). Descriptions are drawn as plain text (never Markdown or HTML), so a plugin's words cannot become a link or an action.

**Output** (`PluginManifestView`, §7): `{key, state: 'read' | 'missing' | 'unknown', name, displayName, version, marketplaceVersion, description, author, license, keywords, components, partial, problems}`. `missing` means only that the anchor directory is absent (an uninstall in flight); a missing `plugin.json` is not `missing`. `marketplaceVersion` is the entry's `version` when it names one (it lets the detail's Update say "Update to <version>").

**Rejected:** `claude plugin details <name>` (U3 F3: the engine's own inventory, but text only with no `--json`, and it counts a `commands/` file as a skill); the engine's catalog cache (`plugin-catalog-cache.json`; engine-private and one marketplace only); homepage and repository links (Desktop's local library returns neither, `main-process/index.chunk-kXuYPTnM.js:352882-352903` `pXi`, so the composition has none).

**When it is read.** The renderer derives its request from the `plugins.list` answer it holds (never from the `plugins.changed` event itself, whose arrival can precede the host's re-listing): My items asks for the representative installations of the listed identities in one call when the list first renders and again whenever a new `plugins.list` answer differs; the detail asks for its identity's other installations; Browse's detail asks for its entry. It caches a `read` view by `(cwd, key, lastUpdated)`; an `unknown`, `missing` or `partial` view is never cached. Like E8's CLI reads, the call honours the passive harness policy (`WidgetReadPolicyContext`).
