## 1. Purpose

**Higher purpose.** MAWS is a general workstation for supervising Claude Code agents, built first to the baseline of three reference apps and then past it, the owner's own workflows arriving as plugins on a strong base (charter §1, D-5, D-20). P0 reached the baseline on daily use; P1 moved everything the agent workflow needed out of the terminal and into the app (P1 §15, closed 2026-10-08).

**What this phase is for.** The owner started living in MAWS at P1's close, and the first days of use found the surfaces where Claude Desktop is still better: a discovered session answers "not running" to every control until a manual Resume; `/plugins` and `/skills` are terminal menus in a dialog where Desktop has a library; `/resume` is a flat list where Desktop has a picker with search, groups and a preview; the to-human lane is a plugin's drawing that MAWS cannot answer, fold or notify from; a comment on a deliverable opens a whole session view where Desktop opens a small comment thread beside the element. P2 fixes the daily driver on those surfaces. Each child builds Desktop's composition where Desktop's is better (D-20) and MAWS's own where the owner's notes ask for it.

**The measure (Decision Log 1).** On the surfaces the owner uses every day, MAWS is at least as good as Claude Desktop, and nothing in daily use sends the owner to Desktop or to a terminal. The owner named what still did on 2026-10-05 and 2026-10-08: sessions that say they are not running, the plugins and skills interface, the resume list, to-human as a plugin's view, comments opening as a new tab.

**What it must not be.** Not Desktop's services: no claude.ai Docs, Artifacts or Cowork (P1 P-4 stands). Not a plugin platform: one built-in, disableable communication mod is application behaviour, not an API beside the engine's `ui_surface_v1` (D-9). Not a redesign: the shell, the transcript and the composer stay as P0 and P1 built them. Not the co-work layer: the docs, slides and design editors, the design system, a Spaces-like organiser and stored comment threads with persistent pins are P3 (charter §3 as amended today). Not the browser's top chrome: the bookmarks bar, the extensions bar, the avatar and the profile popover are the cua_repl session's work on the cua repository's board #90, landing on this master beside P2.

## 4. Design (thin; the shared surface, graded)

Everything below is advisory inheritance unless marked **[binding]** with its joint-view reason. Children expand their own sections in place; a child that overturns advisory content records a dated line in §12 under its id.

**4.1 Availability, apart from process status** **[binding — A, B, C and D all read it, and the owner's decision 4 fixes the policy].** Main derives one `availability` per session record from the record, the holder registry and the host's process status: `usable | starting | resumable | foreign_held | archived | missing_directory | needs_trust | failed`. Process absence is not an error. One acquisition entry in main (X16; `session.acquire`, or `session.start` extended to join) is what every engine-needing action calls: it joins a launch already starting instead of refusing it, runs the existing guarded resume with E13's `browserBackend`, and answers the same outcome shape to every waiter so each executes its intended operation once. Acquisition follows explicit gestures only: a Send, a chip change, a Refresh or "Load now" in a widget (the fresh read), `/btw`, Send to main, a peer reply, a resubmit, an answer from a question or comment card. Opening a transcript, opening a widget, switching sessions (the panel's tools, summaries and the context ring mount then, D-10), reading cached facts and any timer acquire nothing. A U1 verdict that would change a trigger (a no-prompt start that spends, writes the JSONL or runs the owner's hooks) goes to the owner before A binds it; the pending-choice alternative (Desktop's) is not the child's to pick. The memory budget and keep-alive rules of charter §4.4 are unchanged; no fixed idle timer while an app is connected; no engine per sidebar row; no wake from mounted widgets or polls. A terminal-held session stays read-only with the existing Take over (owner decision 4). The C10 restart rule "never auto-resumes" means no blanket replay of indexed history, not a ban on owner-action-driven acquisition (A records the charter line).

**4.2 Observed facts** **[binding on the owner and the exposure; advisory on fields].** The host owns a last-observed engine-facts snapshot per session (X17): launch id, engine version, observed-at, effective model, effort and mode, `output_style`, the loaded plugin list, the last context reading, each field known or unknown. It is written from `system/init`, `reload_plugins` and the context sample; recovered once from the raw journal for sessions MAWS ran before; absent for terminal-only sessions. Storage is a separate per-session file beside the state file, never a key in the strictly parsed state file or its stored launch spec, which an older build would move aside with the queue and grants (the owner's development and packaged builds share one `userData`); the stored launch spec gains no key in P2 before P2-0's tolerant reader is in the owner's running build. Main exposes the snapshot as one read beside `session.digests` (the read is binding; the storage advisory). Surfaces label freshness ("Loaded last time, <when>" against "Loaded now"); unknown is never shown as empty; a record's defaults are never labelled observed; an old effective mode never confirms a new requested one.

**4.3 The human send seam** **[binding — C's answers and E1's card send through it, and A makes it resumptive].** One renderer seam, `sendHumanPrompt(appSessionId, content, {origin, display?}) → {disposition: 'sent' | 'steered' | 'queued' | 'held' | 'refused', started: boolean, messageUuid?, queueId?, reason?}` (X22, owned by P2-0 and reshaped by A's M1 per Decision Log 17, P2-0 landing the interim flat `started` member; extracted from the composer's own decision in `Composer.tsx:275-280` and `editor/submit.ts:51-53` with no behaviour change), is the only way a human-origin prompt leaves the renderer outside the composer's box: composer Send, a choice click, the question card's Reply, the comment card's Reply (Send to main stays main's `side.sendToMain`, which builds the anchored content with the screenshot under main's root checks and applies the same steer-or-send policy in main; the card maps its answer to the seam's dispositions; Decision Log 18). While a turn runs the seam steers with `session.steer {priority: 'next'}`, the composer's own queue action (the owner's "through the queue"), and the host answers the uuid (`steered`); when idle it sends with `session.send`, which the host answers with a uuid (`sent`) or, when its own queue is paused or non-empty, with a queue id and no uuid until it submits the entry (`queued`; Decision Log 16). The seam passes the host's distinction through, never collapsing it. Three states follow from it: queued (the seam returned `steered` or `queued`), delivered (the engine's `command.lifecycle` `started` or `completed` for that uuid, never the host's write: the host's normaliser emits the `user.message` at the write and suppresses the engine's replay; from disk, the transcript's `user` record for an idle prompt, or for a steer the engine took the `queued_command` attachment carrying the uuid as `source_uuid`, a cancelled steer leaving no record at all (C's M4 probe on 2.1.295, `pass3/p2-to-human-steer-cancel-disk.jsonl`); for a host-queued prompt, once the host has submitted it and the uuid is known; Decision Log 19), failed (`refused`, or the host's error). Answers are human prompts, never plugin-origin submissions. A puts acquisition inside the seam (`started: true`; `held` when a trust or relay card takes a composer message, the text staying in the draft), so every caller continues any eligible record once A lands; until then the seam refuses on an exited session as the composer does today.

**4.4 The owner channel** **[binding — one grammar feeds presentation, previews and attention across C, D and E1].** The four marks (`to-human`, `essential`, `insight`, `need-input` with flat `choice` lines, one `recommended`) have one grammar, `src/shared/owner/to-human-parser.ts`, versioned; only finalized assistant text produces durable items, never user prompts or tool output. A question's identity is `(appSessionId, source message uuid, block index, span ordinal)`, not its first line. Question states: unanswered, queued, delivered (answered), with a cancel returning to unanswered; an essential is unread until Mark read (owner decision 3). Two attention kinds, `async_input` and `essential_unread`, each with a source anchor; the engine may still be running while a question waits; an unrelated next turn retires neither. OS notifications for those two kinds only; hydration and replay are silent; items are watermarked by the mark's message time against the time the lane was enabled for that session (never by discovery time), so nothing is notified for history on upgrade or for a session first indexed later; a foreign-held session's marks are presented but produce no `async_input` item and no notification (its card offers Take over), since the owner cannot answer from MAWS. Grammar 2 (C, Decision Log 19): tags inside fenced code and inline code are literal, versioned, and the contract tells the model so.

**4.5 The contract and its advertisement** **[binding on the mechanism; advisory on wording].** MAWS carries a short versioned contract text of its own preserving the style's semantics (to-human spans are the delivered messages; essential is must-not-miss; need-input is one question per mark with choices; insight teaches; keep the coding instructions). It is passed as `--append-system-prompt` on every MAWS-owned launch, resume and fork whose desired state carries it, resolved centrally in the launch mapping. U2 found (Decision Log 19) that the engine records the rendered system prompt in the transcript (`prompt_snapshot`) and reuses it on resume and fork, so the text takes effect when the prompt renders: at once for a new session, otherwise at the next compaction, unless MAWS reads the session's recorded prompt and passes `--system-prompt-snapshot off` for that launch while the recorded state differs from the desired one (a lane switched, a contract version changed), the flag only where the binary declares it, else the change applies at the next compaction and the session's row says so. Nothing is appended when the launch's effective settings select a style that declares the MAWS to-human contract version it implements (a front-matter key such as `maws-to-human-contract: 1` on the style; the doperpowers PR adds it to `output-styles/to-human.md`), and the launch records `source: 'external-compatible-style'`; the signal is the declared contract version, never a plugin's name or release (D-5: no owner plugin hard-coded in the base); the observed `output_style` in `system/init` is compared and a mismatch surfaced. Whenever the native lane is on, MAWS advertises `MAWS_NATIVE_TO_HUMAN=<contract version>` to the engine's hooks; the doperpowers mod reads it once and passes its to-human drawing, its toggle and its question presses through, keeping its terminal UI and its other mods (a small change in the owner's repository, prepared by the architect as a PR for the owner's review; owner decision 4 of this cut). The advertisement's transport is the existing `extraSettings.env` seam, verified by U2 at the function-hook worker and at command hooks (Decision Log 19); the constructed launch environment (X6's allowlist) and the mod's own reading of `session.attach`'s client id `maws-main` stay unused fallbacks. A per-app default on and a per-session override set or omit the variable and the prompt at the next owned launch; nothing is written under `~/.claude`; a foreign-live session is never changed. U2 verified the mechanism on 2026-10-09 (Decision Log 19).
