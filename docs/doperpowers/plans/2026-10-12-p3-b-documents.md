## Terms

- **The schema module:** `src/artifacts/document/schema.ts`, the one Tiptap extension list and the ProseMirror `Schema` built from it, importable in Node (no React, no DOM at import time); every writer, editor, importer, exporter and the history renderer build from it. **Schema parity** is the invariant that one module is the only source and that its storage keys (`name--<hash>` for overlapping marks) are a committed fingerprint CI compares.
- **A tab:** one body fragment of the document. **The tabs map:** the root node `tabs` whose attributes are `tabId → Node('tab') {title, order, body}`, `body` the `Node('doc')` the editor binds (S3's model, `s3/lib/artifact.mjs`); the first tab is created with the document.
- **A thread:** a nested node under the root `threads` keyed by `threadId`, `{tabId, blockId, quote, anchor: {start, end}, status, createdBy, createdAt, resolvedBy?, resolvedAt?, reopenedBy?, reopenedAt?}` with its messages as the node's child sequence (S5's model). **Orphaned** is derived: open and no live text carries the mark.
- **The writer:** the patch writer, pure code over the schema and a Y.Doc, applying an `artifact_edit` batch. **The sandbox:** the agent's replica, on which a batch is applied in one transaction and from which the update ships only when every op validated.
- **The adapter:** the document `KindAdapter` (A's `src/artifacts/host.ts`): `beforeApply` (forwarding), `afterUpdate` (the id repair, move detection, the anchor refresh, the markless-comment strip, the threads mirror), `revertScope` (text, marks and thread statuses; conversations kept), `afterRestore` (orphans, the mirror).
- **History mode:** the editor bound to a throwaway version doc through `configureYProsemirror({ytype, renderer})`, read-only, undo refused.

## Acceptance

The parent's §5 P3-B acceptance, refined to what M9 observes:

1. **The editor (§2 item 2).** In e2e on the product build (A's port route, utility mode): a document created through `artifact_create` opens in the panel tool and in a main tab as two replicas of one host doc; click-and-type works; every block kind of the schema can be inserted and edited (headings, the three list kinds, quote, code with highlighting, table with row and cell editing, image, divider, callout, math, diagram, the three chips, pending); tabs can be added, renamed, reordered and switched; find highlights matches and steps through them; the editor's CSS reads `--ds-*` and falls back to the app's tokens when D's `tokens.css` is absent.
2. **The live run (§2 item 2, the agent).** On the installed engine under a scratch config home (P1 §15's rule), the agent, asked in the session, creates a document, reads it back with ids, then in one `artifact_edit` batch replaces one sentence, inserts a section after a heading and sets one table cell while the test types in another paragraph (Korean composition included); only the targeted blocks change; the human's text is intact; the inserted blocks carry ids the next read shows; provenance credits the agent's characters to the session and the human's to the human; the agent's cursor and its editing blocks were visible in the editor while the batch ran; a second batch with a stale quote is refused naming the block and its current text, and nothing of it landed (atomicity).
3. **Comments (§2 item 3, the document half).** A selection commented from the editor opens P2's card with `CardTarget {kind: 'artifact'}`; Side thread and Send to main deliver the quote and the thread id to the agent; the mark survives typing around and inside it, a paragraph split, a type change to heading and the agent's rewrite of the sentence (the pin stays on the new words); the agent's reply through `artifact_reply` appears in the thread; Resolve removes the mark's display and lists the thread under Resolved, Reopen brings it back; a copy of commented text pasted elsewhere in the same document does not duplicate the comment, a cut-paste moves it (the OS clipboard round trip, through the real pasteboard), a drag-move keeps exactly one.
4. **History (§2 item 4).** The rail lists `auto`, `turn` and `named` versions grouped by day with runs folded and author chips in `--author-*` colours; "Save version" takes a name and a note; the preview is read-only with Show changes on (inserts in the author's colour, deletions struck, "N changes" with ↑ ↓ counting merged runs, comment marks not counted); Restore brings back a deleted tab and the earlier text as a new `restore` version while a reply posted after the version stays and a thread whose passage is gone shows as orphaned (Decision Log 32); Make a copy duplicates the version into a new artifact; Compare takes two by shift-click; "See N new changes" appears after an agent edit while the owner was elsewhere and opens that comparison; right-click "Show editors" names who edited the selection and when, including an edit older than a compaction.
5. **Import and export.** Markdown and HTML import into a document with every block kind round-tripping; a DOCX fixture imports with headings, lists, a table and bold runs; exports: Markdown (ids stripped, GFM), HTML (standalone, tokens inlined), DOCX (headings as Word styles, lists, a table, comments as Word comments; opens in LibreOffice headless without error), PDF through A's print path (`%PDF-` and the page count); `artifact_export` and the editor's Export menu reach them.
6. **The scale gate (Decision Log 37).** On S7b's 200-page seed in the product build with two windows and two agent sessions: an agent batch of five ops occupies the host loop at most 50 ms (the host's `monitorEventLoopDelay` max over the batch); keystroke → frame p95 ≤ 16 ms; first sync to interactive ≤ 1 s; history preview enter ≤ 1 s; the renderer under 500 MB; S7a's storage numbers are A's and F's to re-run, this child only keeps the writer sentence-level (Decision Log 36).
7. **Schema parity in CI.** `pnpm test` fails when the schema fingerprint changes without the fixture being updated, when a second `getSchema` or `Mark.create` appears for the document outside the schema module, or when the host's writer and the renderer's editor resolve different schema modules.

### D2. The schema (advisory block list in §4.4, fixed here)

Nodes: `doc`, `paragraph`, `heading {level 1..3}`, `bulletList`, `orderedList {start}`, `listItem`, `taskList`, `taskItem {checked}`, `blockquote`, `codeBlock {language}` (highlighting by a decoration plugin over shiki in the editor, never in the schema), `table`, `tableRow`, `tableCell`, `tableHeader` (rows and cells carry ids), `image {src, alt, assetId}` (inline, the ledger's row), `horizontalRule`, `callout {tone: note | tip | warn | danger}` (rendered with `data-callout-tone`, the ledger's canon name), `math {latex}` (inline, atom) and `mathBlock {latex}` (a block; ProseMirror fixes inline or block per node type, so one node cannot switch by attribute), `diagram {source}` (mermaid), `chart {source, spec}` (E's Dashboard block: present from day one for parity, drawn as a labelled placeholder with its source until E lands), `pending {intent}` (a block drawn as a labelled placeholder), a root `meta` node whose attributes hold the document's own settings (`dsOverrides: TokenOverrides` per the X28 row, so the version pin covers it; nothing else yet); the chips `date {iso}`, `mention {kind: person | session | artifact, ref, label}`, `dropdown {options[], value}` (inline, atom), `hardBreak`, `text`; the `--attributed` variants of `blockquote`, `listItem`, `taskItem` and `callout` (S3's schema). Every block node has `id` (nanoid 8, `[0-9a-z]`); UniqueID's `types` lists them and the `--attributed` variants (S1 pitfall 5).
Marks: `bold`, `italic`, `underline`, `strike`, `code`, `link {href, title}`, `highlight {color?}`, `comment {threadId}` (frozen, overlapping allowed, non-inclusive, allowed on `codeBlock`, applied with `tr.addMark`; Decision Log 31), `y-attributed-insert`, `y-attributed-delete`, `y-attributed-format`, `y-attributed-attrs` (on every node type). `code`'s `excludes` is left at Tiptap's default (S1 pitfall 4: `excludes` changes the storage key); `comment` has exactly one attribute, forever.
Rejected: `diagram` as `codeBlock {language: 'mermaid'}` (the agent's markdown would then be ambiguous between a fenced mermaid source and a diagram, and the history renderer could not mark a diagram change as one); a `chart` left to E (its absence would re-key nothing but would mean a schema change at E's landing, which S5's pitfall 1 says is a normalization write per document).

### D3. The theme: the design system's ground, `--ds-*` with fallbacks, the author colours

The editor's root carries `.ds-doc` (the ledger's canon name; D's `components/document.css` scopes under it) and is wrapped, once D lands, in D's `<DesignSystemScope system medium="document" overrides={meta.dsOverrides} className="ds-doc">` with the system from `governingSystem(artifact, {owner, spaces, house})` (X28's apply API, Decision Log 39): one theme per system, so the document draws its system's ground under the dark app theme as a Google Doc stays white (binding). `editor/theme.css` reads only the ledger's `--ds-*` names, each with a fallback to the app's token (`var(--ds-color-text, var(--fg))`, `var(--ds-font-body, var(--font-prose))`, `var(--ds-type-body-size, var(--text-prose))`, and so on for every name in the X28 row): until D's scope exists the editor is MAWS's own look following the app theme (an interim that ends at D's landing; the house system is light); once the scope supplies every name the fallbacks never fire and the app theme no longer reaches the page. The author colours `--author-1` … `--author-8` are defined in `src/renderer/src/styles/tokens.css` for both themes (eight hues at equal lightness steps, readable as a 2 px underline and as a 12 % background; light first), mapped into Tailwind's `@theme inline` as `--color-author-N`, and the editor's attribution marks and awareness cursors colour by `actorDisplay(actor).color`; they are app tokens, not system tokens, so they follow the app theme by design (a chip beside the page, not on it). **D's token conventions (D's M1, ledger X28, binding on the theme and the exporters):** the editor's type styles read `var(--ds-type-<role>-{size,line,weight})` always, and set `font-family` and `letter-spacing` through `var()` only where they alias a ledger-named token (`--ds-font-*`; a typography token's `letterSpacing` is required, `0px` when absent), so an override restyles them; a colour's hex is six digits with alpha separate; a group's base token is referenced as `{group.$root}`, never `{group}`; the page size is a system token, Letter by default (D12). Rejected: hard-coding `--fg` in the editor and swapping at D's landing (every rule would be touched twice); an own `prefers-color-scheme` rule in the editor (the ruling is one theme per system).

### D4. Schema parity in CI

`fingerprint.ts` computes, from `schemaFor()`, the sorted node and mark names with their attribute names and defaults and, for every mark, its Yjs storage key as `@y/prosemirror` derives it (`pmnodeToDelta` over a one-node fixture per mark, reading the delta's attribute keys) and writes a canonical JSON; `fingerprint.json` is the committed fixture; `fingerprint.test.ts` fails with the diff and the instruction to regenerate (below) only when the change is deliberate. A second test asserts by lint that `getSchema(`, `Mark.create(` and `Node.create(` for the document appear only under `src/artifacts/document/schema.ts`: the selectors run as ESLint's core `no-restricted-syntax` registered under this child's own plugin name (`p3b/no-restricted-syntax`), so A's per-block options and the renderer block's postfix rule stand untouched (M1's as-built route, Decision Log 13; the first draft composed the selectors into A's options), with the composer's own extensions under `src/renderer/src/composer/` excluded as a different schema; `test/artifacts/portability.test.ts`'s pattern (lint the whole of `src/` through the repository config inside `pnpm test`) enforces it on production source, with a negative fixture proving the rule fires and A's existing negative fixtures still failing. A third test asserts that the host's document tool module and the editor's module resolve one schema object (`schemaFor()` a cached singleton; the editor half in M3, the host half in M7). The fixture is regenerated only by `MAWS_UPDATE_FINGERPRINT=1 pnpm -C <wt> exec vitest run src/artifacts/document/fingerprint.test.ts`, which writes the file and fails if nothing changed. Rejected: comparing serialised ProseMirror specs alone (the storage key is what breaks a document, and S1 pitfall 4 shows a spec-level change can re-key).

### D5. The sentence rule's threshold (parent Decision Log 36, B's)

The writer segments both texts with `Intl.Segmenter(undefined, {granularity: 'sentence'})` (Node 24 and Chromium), pairs sentences by the word diff's hunks, and when a hunk set touches at least half the words of a sentence (`changed ≥ ceil(words / 2)`, words by the word segmenter) it emits one hunk for the whole sentence instead, re-applying on the retained words the marks they carried (comments included, so S5's "orphaned only when all its words go" still holds) and the formatting the agent's markdown expresses. Below the threshold the word hunks stand. Rejected: a character ratio (a long word changed would count as a sentence rewrite); always sentence-level (per S5, a comment on a fixed word would be re-inserted by every agent edit nearby and its characters re-credited).

### D6. The batch's route to 50 ms (parent Decision Log 37's advisory route, taken) and all-or-none without a clone

The writer keeps an id → `{node, parent, path}` index per document, rebuilt lazily from the applied update's changed top-level blocks (the `afterUpdate` hook's view) rather than walked per op; `replace_text` without `block` searches the index's text cache, never a re-serialisation of every block. **All-or-none is settled before any Yjs write:** the writer first computes, in ProseMirror space, the resulting node of every touched parent (the ops applied as PM transforms over the indexed nodes: the quote's uniqueness, the row structure, the move rule against the human carets, `createChecked` on each resulting touched parent, binding per Decision Log 35) and only when every op validated does it open one Yjs transaction on the agent's replica (A's Decision Log 9: synced from the host at a read) that applies the planned `Y.XmlText` operations; a Yjs transaction cannot roll back and the provider ships every local update, so the pre-validation is the atomicity, and the whole-document clone of S4 is dropped. The backstop for a throw inside the transaction (a bug, never a validation failure) is A's replica API `AgentReplica.edit(fn)` (H1 request i): outbound updates are suppressed while `fn` runs, flushed as one update when it returns, and on a throw the replica is discarded and recreated from the host's state so nothing of the failed transaction is ever sent. M2 measures the batch on S7b's seed headless (the bar: p95 under 40 ms in Node on this machine, a pre-gate for M9's 50 ms host-loop max in Electron). A `worker_thread` is not built unless M9 is still over. Rejected: the clone dry run (27 to 36 ms p50 at 200 pages, S7b); validating after mutating (unrevertable).

### D7. The agent's read: ranges and `sinceRevision`

`artifact_read` for a document returns `{revision, kind: 'document', tabs: [{id, title, blocks}], markdown}`: the markdown of one tab (`tab` defaults to the first), ranged by `from` (a block id, inclusive) and `count` (blocks, default 200, max 1,000), every block ending in ` ^id` (lists one marker per item, a table one marker for the table and one per row as `<!-- ^id -->` trailing comments, cells positional), chips as `<chip kind="date" iso="…"/>` and the like, comments as `<c:ID>…</c:ID>` milestones, a footer listing open threads (`id · quote · N messages`) and orphans; `sinceRevision` returns only the blocks whose text or attributes changed since that revision (from the host's provenance maps between the revisions, through the attribution's item ids resolved to block ids) plus the ids of deleted blocks, or the whole range when the revision is older than the head's log window (then `complete: true`). Every read captures the session's base (A's Decision Log 9).

### D8. The adapter's bodies on A's hook points

- `beforeApply(live, incoming, {actor, step2})`: S4's `receive` and `forward`, both branches: read the incoming update's content ids; replay onto the live copy each text insertion whose parent is a tombstoned block a recorded carry re-inserted, and, **only for an incremental update (`step2 === false`)**, each deletion that targeted such a block (a sync step 2 carries the sender's whole delete set and must never be replayed, or a reconnect would replay the move's own deletion). The carry registry it reads is per artifact, fed by the writer's `Applied.carries` from the tool handler in the same host process (`adapter.registerCarries(artifactId, carries)`, S4's `registerCarry`), and pruned when the carried blocks are garbage-collected.
- `afterUpdate(live, {update, actor})`: S4's `repair` and move detection (a delete and an insert of one id in the update is a move; duplicates keep the later insertion after `carryCopyEdits`, others re-id, never delete); S5's `refreshAnchors` for threads whose extent drifted (one walk); strip a `comment` mark whose thread is absent; return the thread mirror rows (D8a) and the provenance carries (D8b); refresh the id index.
- `revertScope(live, old)`: the body fragments, the tabs map, and of each thread that exists in both states its `status`, `resolvedBy/At`, `reopenedBy/At` and anchor attributes; **never** a thread's existence or its messages: a thread created after the version stays with its messages (its passage gone, it shows as orphaned) and a reply posted after the version stays on its thread (S5's `restoreKeepingConversation` recreates what a plain revert would remove; the owner's Decision Log 32). M2 proves both cases against the model, M9 against A's real restore.
- `afterRestore(live, {versionId})`: recompute derived orphans, rewrite the mirror, run the id repair once.
- **The hooks' arguments as A built them (A's M2, edc6c5d2, the ledger's X24 row):** `beforeApply` receives the live document read-only; `afterUpdate` and the forwarding callback receive a per-actor host replica identical in content to the live document, so the adapter writes repairs and forwarded edits into that replica, never into `live`; the host-originated write is `writeAs(artifactId, actor, edit)` and the restored frame is emitted by `announceRestored`; a savepoint that cannot roll back fails the whole batch and drops the open documents, so an adapter hook must not throw after a partial write of its own (validate, then write).
- **D8a, the threads mirror.** `KindAdapter` has no storage handle; the adapter returns the mirror rows from `afterUpdate` through a `threads?: ThreadRow[]` field on its result (a request to A, H1c) and A's store writes `artifact_threads`; until A exposes it the renderer reads threads from the doc directly, so nothing in B's acceptance waits on the mirror.
- **D8b, provenance carries.** A credits inserted structs to the clientID's actor, so a move or a type change would credit every retained character to the agent; the writer's `Carry` pairs (`from` item → `to` item, kind `move | retype`) must reach the provenance map. The adapter returns them from `afterUpdate` as `provenance?: Carry[]` (H1 request j) and A's attribution step re-attributes each `to` id to the `from` id's author and time before the ContentMap row is written (S4's `registerCarry` effect); the carry's kind is kept on the map (`y-attributed-attrs`-style `moved | retyped` entries) so M5's history preview can mark retyped and moved blocks (parent Decision Log 34). Until A ships it the history shows the agent as the author of moved text, recorded as a known gap, never as done.

### D9. Comments in the editor and the card's artifact target

Creating a comment writes the thread node first, then the mark with `tr.addMark` (Decision Log 31's order); the thread's `anchor` is the relative-position pair from the mark's extent, `quote` the selected text, `blockId` the start block, `tabId` the active tab. `CommentDisplay` (S5) decorates live marks with `class="comment comment-<threadId>"` (ids in classes, never attributes: overlapping decorations merge) and the active thread with `comment-active`; `CommentPaste` deduplicates a pasted comment whose thread already has live text and keeps a mark whose thread is in this document (Outline's rule), guarded by `view.dragging?.move` so a drag-move keeps exactly one (the P3-0 open item). The mark's `renderHTML` writes `data-thread` and `parseHTML` reads it, so the OS clipboard round trip carries the thread id (Chromium keeps `data-*` in `text/html`); M9 proves it on the real pasteboard. Resolve and reopen write the threads map only and sit outside undo (`UndoManager.trackedOrigins` excludes the threads origin). The threads list (open and resolved, reopenable) is the editor's right rail tab beside History. **The card:** `CardTarget` gains `{kind: 'artifact', artifactId, threadId}`, `CardHostKind` and `CommentPlacement.host` gain `'artifact'`; the editor mounts `CommentCardHost host="artifact" layout="anchored"` with a `CardFrame.locate` that resolves a thread id to the mark's rect; the anchor the routes carry is a new `Anchor` kind `'artifact-comment'` with `artifactId` and `threadId` fields, `locator` the quote and `label` the title and tab; `anchorLead` says "a comment on <title>, <tab>: "<quote>"" and `TAG_FIELDS` gains the two fields; Side thread and Send to main go through the existing `openCommentComposer` and `sendComment` unchanged; the agent's reply posted with `artifact_reply` (or an `artifact_edit` with `answering`) appears in the thread.
