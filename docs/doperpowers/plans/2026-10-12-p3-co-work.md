## 1. Purpose

**Higher purpose.** MAWS is a general workstation for supervising Claude Code agents, built to the baseline of the reference apps and then past it (charter §1, D-5, D-20). P0 reached the baseline, P1 moved the agent workflow out of the terminal, P2 made the daily surfaces at least as good as Claude Desktop's. What the owner still does elsewhere is the making of things with the agent that are not code: documents, slide decks, designs. Claude's Artifacts suite (Docs, Slides, Design, Design System, Dashboard) is where that happens today, in claude.ai's services.

**What this phase is for.** A self-hosted Google Docs and Google Slides for MAWS (the owner's words, Decision Log 2): the co-work layer the charter deferred since 2026-10-05, local-first, with the agent editing through MCP tools the way Claude's own tools edit Claude Docs and Claude Slides, the person editing in-app the way they edit in Google Docs, every change attributed to who made it and when, and a version history as good as Google's. It is built for the owner's daily work now and, later, as the base of a product for teachers (P4: sharing, simultaneous editing, a web-hosted MAWS), so its store and editors are designed to grow there without a rewrite.

**The measure (Decision Log 1).** Parity with Claude Desktop's Artifacts suite: on documents, decks, designs, design systems and dashboards, with their library, comments, versions and exports, MAWS does what Claude's artifacts do, and where the two differ MAWS is the one with a real history (diff, attribution, restore) and a real organiser. The owner's artifact work ends in MAWS.

**What it must not be.** Not claude.ai's services (P1 P-4 stands: nothing is stored in or fetched from Claude Docs; the formats are ours, shaped like Claude's so skills transfer where U1 confirms the shape). Not a plugin platform: the editors are the app's own code, not sandboxed type pages (Decision Log 16); only untrusted content (free HTML, embeds, artboards' support files) runs in frames. Not multi-user: sharing, simultaneous editing and a cloud MAWS are P4 (Decision Log 4), but nothing built here may foreclose them (§4.10). Not a redesign of the shell beyond the three shell items the owner asked for (§4.9). Not the browser's chrome (the cua session's).

## 2. Acceptance

Items are observable behaviour; the children's gates refine them.

1. **The library.** An Artifacts tab (main area, like Overview) lists every artifact across sessions: All, Pinned and By Space; a type filter with counts (Document, Presentation, Design, Design System, Dashboard, HTML, File); groups Today, Yesterday, the days of the last week, months, Older; search over titles and text; "Make something new" cards per kind; each row's title, kind, Space, project, last editor and time, the sessions that touched it; Pin, Rename, Move to Space, Duplicate, Export, Delete. A Space is a named folder the owner creates, optionally linked to a project directory. The artifacts the owner's sessions delivered before P3 are there as File and HTML artifacts with their sessions. With every window closed and the host detached, an agent's edits still persist, and the library is right again when a window opens.
2. **A document.** From a session, the agent creates a document and the owner opens it in the panel (or a main tab). It is a Google-Docs-like editor: click anywhere and type; headings, lists, task lists, tables with row and cell editing, code with highlighting, images, dividers, math, diagrams, date and mention chips; tabs within the document; find; the design system's look applied. The agent, asked in the session, replaces one sentence, inserts a section after a heading and edits one table cell, and only those blocks change on screen while the owner keeps typing elsewhere (Korean composition included); the agent's cursor and the blocks it is editing are visible while it works; the same document open in the panel and in a main tab shows one state.
3. **A comment.** The owner selects a passage, comments, and sends it to the agent: a thread pinned to that passage opens as a side thread (or goes to main) exactly as P2's card does; the pin survives the owner's later edits around it, a restart, the agent's rewrite of the sentence, and a change of the paragraph's type; the agent's reply appears in the thread; Resolve closes it and the mark disappears; resolved threads are listed and reopenable. The same on a slide: a comment pinned to an element follows it when it moves and shows as orphaned when it is deleted.
4. **History.** The artifact's version history lists automatic versions (at human idle, during activity, at the end of each agent turn that touched it) and named ones ("Save version" with a name and a what-changed note), grouped by day with runs folded, each row with its author chips; a version previews read-only with Show changes on: insertions in the author's colour, deletions struck through, "N changes" with ↑ ↓; it renders with the design system and assets of its time; Restore brings back the whole artifact (its tabs, threads and properties, or its slides and deck properties) as a new version and never destroys; Compare takes any two; a "See N new changes" pill appears when an agent changed the artifact since the owner last looked and opens that comparison. Right-clicking a selection says who edited it and when, including edits older than the last compaction.
5. **A deck.** The agent builds a deck from a brief: deck.json and one slide file per slide in the dialect (§4.5). The owner opens it: a filmstrip, a fixed 16:9 canvas with zoom, every element selectable, movable, resizable and restyleable, text edited in place, snapping guides, z-order, grouping, add, delete and reorder slides, speaker notes, a presenter window. The owner moves a box and retitles a slide; the agent, asked to change a font deck-wide, fetches, edits and publishes; its publish of a slide the owner changed meanwhile is refused with the slide's name, and after a re-read succeeds; a publish of several files lands whole or not at all. History works per slide (changed slides marked in the filmstrip, changed elements outlined). Export gives a PPTX that opens in PowerPoint and Keynote with editable text and shapes in the right places (the deck's fonts named, or basic faces, or slides as pictures, the owner's choice), a PDF, a standalone HTML, and a Claude-compatible deck with tokens resolved. A deck written for Claude Slides (its own skill's examples) opens in MAWS with no slide held.
6. **A design system.** The owner picks one of the built-in defaults, or the agent extracts one from a codebase, a deck or a website (colours, type, spacing, components, logos, fonts) into a Design System artifact with a preview page; the owner edits a colour and the preview follows; a document and a deck set to it restyle; the default system per Space and for the owner is honoured by the agent without asking; the `ask` sheet can offer design systems as an input (P1 P-13).
7. **Design and Dashboard.** A design artifact holds artboards of any size on a pannable canvas in the same dialect and editor as slides, exported as PNG and PDF; a dashboard is a document whose chart and table blocks are bound to data files the agent wrote (and, if P3-H's spike proves the route, to a declared connector's tool, user-gated, refreshed on a schedule), each block showing its source. ## 4. Design

Everything below is advisory inheritance unless marked **[binding]** with its joint-view reason. Children expand their own sections in place; a child that overturns advisory content records a dated line in §12 under its id.

**4.1 The artifact entity and the library** **[binding — every child reads and writes it, and it replaces X12's per-session records].** An artifact is a top-level entity independent of sessions (Decision Log 5): `{id, kind, title, spaceId?, projectId?, createdBy: Actor, createdAt, updatedAt, lastViewedAt, pinned, designSystemId?, linkedPath?}` with kinds `document | presentation | design | design_system | dashboard | html | file`. **The engine host owns the durable store** (Decision Log 20a): one SQLite database of its own, `<userData>/artifacts/store.sqlite` (WAL; tables `artifacts`, `spaces`, `artifact_sessions`, `artifact_updates`, `artifact_versions`, `provenance`, `actors`, `artifact_threads`, `artifact_assets`; its own schema version, a slot per X15), opened by the host alone, with bytes under `<userData>/artifacts/<id>/` (assets, version states, the file of a File artifact in place as today). Main holds only derived library state in its index (the list rows and the FTS text index), rebuilt from the host's `artifact.changed` events and reconciled by one host read at every connection, so the library is right after a detached edit, a host restart or an upgrade; main never opens the host's database. Sessions are linked, not owners: `artifact_sessions {artifactId, appSessionId, role: created | edited | viewed | commented, lastAt}`; a side thread's scope rule (X9's ancestor resolution) becomes "the artifacts its ancestors are linked to". A Space is a named folder, at most one per artifact, optionally linked to a project directory, in which case the Space's linked artifacts mirror to `<dir>/artifacts/` on every save as read-only exports (`.md` for a document, a deck folder for a presentation; Decision Log 8); `projectId` is a fact from the creating session, filterable, never a Space. Today's deliverables import at the cutover as `file` and `html` artifacts with their session links; the `deliverables.*` IPC and the panel tool are replaced by `artifacts.*` and an Artifacts tool (Decision Log 9: the word is Artifacts everywhere); `send_file` stays and creates a File artifact. The library is a main tab beside Overview (§2 item 1), and the panel's Artifacts tool is the session's own list with "All artifacts" one click away; an editor opens in the panel by default and in a main tab on demand (P1 A-2 carried), both replicas of one document (§4.2). Search is a local FTS index over titles and extracted text, maintained on save.

**4.2 The document store** **[binding on the model — the editors, the agent tools, history, attribution and P4's collaboration all stand on it; advisory on table layout].** Every artifact of kind document, presentation, design, design_system or dashboard is one Yjs `Y.Doc` (Decision Log 2, 11). The authoritative copy lives in the engine host's document service (`src/engine-host/documents/`), which already hosts the MCP tool server and outlives windows in detached mode (E10); the renderer's editors are replicas synced over one `MessageChannelMain` port per open document carrying y-protocols sync and awareness frames (the thin provider of `research/p3-yjs-store.md` §2; two windows or a panel and a main tab are two replicas of one host doc); each writing agent session edits through its own replica synced in-process by the same protocol, never straight into the host doc, so authorship is known per update. Persistence is the `artifact_updates` log (one row per update: `seq, actor, at, bytes`, appended under WAL with `synchronous=FULL` before the update is acknowledged or broadcast) compacted into `artifact_versions` states (full V2 states, gc on); **compaction keeps provenance** (Decision Log 20c): a `provenance` table of `(clientID, clock range) → (actor, at)` rows and the per-update delete sets, written as each update lands and never merged away, so "who edited this selection and when" and the author colours of a diff survive compaction and thinning (older rows bucket to the minute after 30 days). Versions are rows of `artifact_versions {seq, at, actor, kind: auto | turn | named | restore | import, label?, note?, summary?, state, designSystemRef: {id, versionSeq}?, assetRefs[]}`, thinned by age for `auto` rows; an `auto` version is also written when the owner views an artifact whose live revision moved since its last version, so "see N new changes" has a state to diff from after compaction (Decision Log 29); a retained version pins the design-system revision and the assets it referenced, and assets and design-system states are kept while any retained version references them (Decision Log 20g). History renders with v14's `DiffRenderer(prevDoc, nextDoc, {attributions})` over two throwaway gc-off docs loaded from version states; the editor enters through `configureYProsemirror({ytype: the version's fragment, renderer})` and leaves with `{ytype: live, renderer: null}`, the live doc never written; undo and redo refuse while the binding is not on the live doc, and a transaction filter refuses local changes in history (Decision Log 29, S3). **Restore is artifact-wide** (Decision Log 20b): one kind-agnostic host operation that reverts the changes since the version (`Y.undoContentIds` on a scratch gc-off doc holding the version and the live state), shipped as one update credited to the restorer, an `auto` version before and a `restore` version after, `restored` signalled to the replicas, every bound editor clearing its UndoManager on landing; per-kind adapters handle only the after-effects (the threads mirror, orphans, the id repair); a concurrent edit in content the restore keeps survives, and an agent batch whose targets a restore removed is rejected naming the blocks "removed by restore"; y-prosemirror's `restore` meta is not used (Decision Log 29 replaced Decision Log 20b's per-kind diff-apply: a name-paired structural diff grafts a concurrent edit into a replaced block). **The live revision** is the host's update sequence per artifact, returned by every read and every write; checkpoints are rows in the log, not the only reference points. The four `y-attributed-*` marks (insert, delete, format, attrs) on every node type and the `--attributed` variants of the strict containers (blockquote, listItem, taskItem, callout) are in every schema from day one, and schema parity between every writer and editor is an invariant checked in CI (one schema module, importable in Node, no React node views). Undo is Yjs's `UndoManager` scoped to the local binding and blocked while history is shown. **Yjs v14 (Decision Log 25, S1's verdict 2026-10-12): `@y/y` 14.0.0-rc.28 and `@y/prosemirror` 2.0.0-15 pinned exactly, one `@y/y` forced by a pnpm override, the binding code in one module, S1's suite the gate for any re-pin, every document tagged with its binding version; provenance is v14's native attribution maps, persisted as one encoded `ContentMap` per update with times floored to the minute at write and merged by the host only when bucketing (Decision Log 29) (the custom clock-range rows of Decision Log 20c are superseded); suggestion mode is the agent's opt-in (`mode: 'suggest'` on a write, or an artifact set to "agent edits as suggestions"), direct edits the default (the owner's ruling, Decision Log 27); the verdict flips back to v13 only if S3, S4 or S7 finds a v14-only failure.** The detached host's transport gains a binary, length-prefixed channel for document frames (an X13 amendment through the ledger); until it lands, detached mode serves documents through the live host only, labelled. Awareness carries the human's and each agent's cursor and the blocks an agent is editing (§2 item 2).

**4.3 The agent's formats and tools** **[binding — one protocol shaped like Claude's so skills transfer, and one namespace the ledger owns].** The `maws` server gains one artifact namespace (names fixed in the P3 ledger before any sibling codes against them; the shapes here): `artifact_list` (the library, filters, a Space), `artifact_describe_type` (the kind's guide and format reference, printed on create as Claude Code prints a type's `format.md`), `artifact_create` (a kind, a title, initial content in that kind's format; the existing free-HTML create keeps its name and becomes kind `html`), `artifact_read` (a document as markdown with block ids, ranged; a deck as its files; versions by number; always returning the live revision), `artifact_edit` (documents: one atomic batch of block operations, §4.4), `artifact_publish` (file kinds: a files map with `null` removals, `baseRevision`, the three concurrency layers of Claude's protocol: the "you haven't read the latest revision" guard, a merge when no sent file changed, a refusal naming the changed files; `force` as the last resort; the whole map lands as one transaction or not at all), `artifact_upload_asset` and `artifact_list_assets`, `artifact_comments`, `artifact_reply`, `artifact_resolve`, `artifact_screenshot` (kept), `artifact_export`. **Every write is idempotent** (Decision Log 20d): the call's tool-use id is the operation's identity; the host records each applied batch or publish with its result and replays the result for a repeated id, so a crash between commit and reply never duplicates content. Each kind's guide (`SKILL.md`-shaped) and format reference are MAWS files under `src/artifacts/types/<kind>/`, versioned, returned by `artifact_describe_type` and attached to the creating turn, so the agent learns the dialect the way it learns Claude's. The default design system's guide is attached on create without asking (Claude's rule). Every tool call carries the session as the actor (§4.2) and ends the turn's edits as one `turn` version when the turn ends (§4.7).

**4.4 Documents** **[binding on the schema invariant, ids, comment marks and the edit tool's semantics; advisory on the block list].** A document is a Y.Doc with a `tabs` map (ordered; Claude's project → tab → node, Google Docs' tabs) and one `Y.XmlFragment` per tab bound through Tiptap 3's Collaboration; its schema (one module) has paragraph, heading 1 to 3, bullet, ordered and task lists, quote, code (shiki), table (row and cell ids), image (an asset), divider, callout, math (KaTeX, as the transcript renders it), diagram (mermaid), chart (a Dashboard block, bound to data), and inline marks bold, italic, underline, strike, code, link, highlight, `comment {threadId}` (overlapping allowed, non-inclusive; BlockNote's shape; the mark's attributes are its storage key on both Yjs versions, so the mark is frozen at one attribute and orphaned is derived: open, and no live text carries the mark; Decision Log 31) and the four `y-attributed-*` marks; chips are inline nodes: date, mention (a person, a session, an artifact), dropdown (a status). Every block carries a short id (`^` syntax in the agent's markdown, an 8-character nanoid in the doc; UniqueID keeps them through split and paste, the host repairs missing and duplicate ids after each applied update, and every writer ids what it writes). The agent reads GFM with `^id` markers and `<chip …/>` markers, ranged ("from `^h7`, 40 blocks"); a read may ask `sinceRevision` for only what changed (Claude Docs' `sinceRev`); it writes `artifact_edit(artifact, baseRevision, ops[])` with `replace_text {block?, old, new, all?}` (exact and unique, else an error listing candidate blocks), `replace_block {id, markdown}`, `insert {after | before, markdown}`, `delete {id}`, `move {id, after}`, `set_cell {table, row, col, markdown}`, and two shapes borrowed from Claude Docs (Decision Log 21): a `pending {intent}` block the agent inserts as a placeholder and fills section by section (drawn as a labelled placeholder until filled), and `answering: <threadId>` on a batch, which posts the edit as the thread's answer. **The batch is atomic** (Decision Log 20d): the host validates every op's target against `baseRevision` first (only the targets, so the human's typing elsewhere never conflicts) and applies all or none; a rejection names the conflicting blocks with their current text; the response carries the new revision, one line per op and new ids. **The patch writer** (Decision Log 20e) applies every op on the agent's replica and never through `updateYFragment`: same-type text changes as a multi-hunk word diff of `Y.XmlText` operations with explicit attributes; a block whose type changes keeps its id and its marks, which are re-mapped onto the new text by the diff (a comment whose text is gone becomes an orphan with its stored quote); `move` re-inserts the block's node with its id and marks and records a move in provenance (authorship of the text unchanged), and the host's id repair resolves a duplicate created by a concurrent move by keeping the later insertion and tombstoning the other, which S4 proves; validation against the renderer's exact schema. Comments are the mark plus a `threads` map in the Y.Doc (threads sync, version and restore with the text) mirrored to `artifact_threads` for the library and the side-thread link; a thread is a nested node `{tabId, quote, anchor, status, messages}` with its messages as a sequence (one JSON value lost a resolve racing a reply), storing its quote and a relative-position pair for orphan display that the host refreshes from the live mark at its per-update hook when it drifted (it collapsed in 10 of 30 edits); resolve and reopen write only the threads map, and comment create, resolve and reply sit outside undo; a paste deduplicates a comment that already exists and a drag-move counts the source as gone (Decision Log 31); P2's card (X21) is the UI, with `CardTarget {kind: 'artifact', artifactId, threadId}` beside the existing two and the Side thread or Send to main routes unchanged; Resolve and reopen are new. The design system applies as a theme: the editor's CSS reads `--ds-*` tokens (§4.6) and the built-in default system is MAWS's own look (Decision Log 7). Import: Markdown and HTML into a document (B owns the schema, so B owns the importers); DOCX through a tolerant reader. Export: PDF (the print path), DOCX (an in-house serializer over `docx` mapping the design system to the Word theme and named styles, comments as Word comments, optionally the changes since a version as tracked changes), Markdown (GFM, ids stripped), HTML (standalone, tokens inlined).

**4.6 Design systems** **[binding on the object's shape, the token format and the CSS names — documents, decks, designs, the exporters and the agent all read them; the owner's choice of definition, Decision Log 22].** A design system is the designer skill's object, not Claude's: *a project's committed visual law that new work must obey* (`~/Developer/GitHub/designer/skills/designer/SKILL.md` 2.3.1, `references/guidelines-authoring.md`), the triad of a stance, a token file and `DESIGN.md`, with a precedence chain (the brief per surface > a supplied reference, local > the design system, global > sampled ingredients > defaults) and a QA protocol that checks built work against its own law. ## 8. Risks and mitigations

- **The scale.** P3 is the largest phase: four editors, a store, a protocol, exporters. Mitigation: the spikes first and the S1 and S7 gates; the frontier rule (E is cut at its dispatch; B and C are reassessed at theirs; D's and H's scope is bounded); children land independently so the owner uses documents before decks exist.
- **Two processes, one truth.** The host owns the store and main owns the library's view. Mitigation: main never opens the host database; derived rows rebuild from events and one read at reconnect; A's acceptance includes main absent, reconnection and an upgrade.
- **The frozen snapshot path.** y-prosemirror 1.x's history has five "not planned" bugs (attribute changes invisible, code blocks). Mitigation: S3 measures them on the real schema; the history renderer is one module so v14's `DiffRenderer` can replace it; S1 may choose v14 outright.
- **Schema drift deletes content.** A binding that cannot build a node deletes it in the live doc. Mitigation: one schema module, the CI parity check, writers validate before applying, the host repairs ids after each update.
- **Human and agent in one block.** Mitigation: the patch writer's word-level hunks, the batch's target-only validation and all-or-none rule, idempotent writes, S4 with Korean IME composition under remote updates (the terminal's C1 lesson), structural edits with comments and concurrent moves as S4 and S5 gates, awareness showing the agent's blocks.
- **History that lies.** A restore that brings back prose but not threads, a diff coloured by a forgotten author, an old version drawn in today's colours. Mitigation: artifact-wide restore per kind (S3), provenance kept through compaction, the design-system and asset pins on retained versions.
- **PPTX fidelity.** PowerPoint wraps differently and never recomputes autofit. Mitigation: embedded fonts, explicit sizes, width slack, an optional "lock lines" mode, render-and-compare in CI, "Slides as pictures" as the fallback export.
- **The dialect drifts from Claude's.** Claude's list may change weekly. Mitigation: the list is adopted property for property with U1's record as the corpus; the loader's warnings name every dropped thing; held slides lose nothing; the format reference is attached on create; a token-using deck resolves to literals for Claude.
- **The connector bridge may have no route.** Mitigation: H is a spike first; E's dashboards bind to files regardless.
- **The detached host.** Documents need a binary channel the JSON-lines socket lacks. Mitigation: S2 builds it; until then detached mode serves documents through the live host only, labelled.
- **Scale on the owner's machine.** A 200-page document with two windows and agent replicas may make typing or engine supervision unusable while being correct. Mitigation: S7 with bounds, blocking B and C.
- **Storage growth.** Mitigation: gc on, version thinning with provenance kept, S7's soak with a published policy.
- **Portability drift.** An editor that imports Electron once is never web-hosted. Mitigation: `src/artifacts/` with a lint rule against Electron, Node and `window.maws` imports; connector calls through the adapter.
- **The owner's time.** Three sittings' worth of surfaces. Mitigation: F's sitting sheet is written as children land; documents can be sat on before decks exist.
