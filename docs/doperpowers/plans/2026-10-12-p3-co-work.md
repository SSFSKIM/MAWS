## 1. Purpose

**Higher purpose.** MAWS is a general workstation for supervising Claude Code agents, built to the baseline of the reference apps and then past it (charter §1, D-5, D-20). P0 reached the baseline, P1 moved the agent workflow out of the terminal, P2 made the daily surfaces at least as good as Claude Desktop's. What the owner still does elsewhere is the making of things with the agent that are not code: documents, slide decks, designs. Claude's Artifacts suite (Docs, Slides, Design, Design System, Dashboard) is where that happens today, in claude.ai's services.

**What this phase is for.** A self-hosted Google Docs and Google Slides for MAWS (the owner's words, Decision Log 2): the co-work layer the charter deferred since 2026-10-05, local-first, with the agent editing through MCP tools the way Claude's own tools edit Claude Docs and Claude Slides, the person editing in-app the way they edit in Google Docs, every change attributed to who made it, and a version history as good as Google's. It is built for the owner's daily work now and, later, as the base of a product for teachers (P4: sharing, simultaneous editing, a web-hosted MAWS), so its store and editors are designed to grow there without a rewrite.

**The measure (Decision Log 1).** Parity with Claude Desktop's Artifacts suite: on documents, decks, designs, design systems and dashboards, with their library, comments, versions and exports, MAWS does what Claude's artifacts do, and where the two differ MAWS is the one with a real history (diff, attribution, restore) and a real organiser. The owner's artifact work ends in MAWS.

**What it must not be.** Not claude.ai's services (P1 P-4 stands: nothing is stored in or fetched from Claude Docs; the formats are ours, shaped like Claude's so skills transfer). Not a plugin platform: the editors are the app's own code, not sandboxed type pages (Decision Log 16); only untrusted content (free HTML, embeds, artboards) runs in frames. Not multi-user: sharing, simultaneous editing and a cloud MAWS are P4 (Decision Log 4), but nothing built here may foreclose them (§4.10). Not a redesign of the shell beyond the three shell items the owner asked for (§4.9). Not the browser's chrome (the cua session's).

## 2. Acceptance

P3 closes when, on the owner's Mac with the installed engine and a development-signed build, every item below is observed in one sitting (the agents' live runs under scratch config homes stand for what the owner does not run, P1 §15's rule), and the owner then declares the measure met after a week of daily use. Items are observable behaviour; the children's gates refine them.

1. **The library.** An Artifacts tab (main area, like Overview) lists every artifact across sessions: All, Pinned and By Space; a type filter with counts (Document, Presentation, Design, Design System, Dashboard, HTML, File); groups Today, Yesterday, the days of the last week, months, Older; search over titles and text; "Make something new" cards per kind; each row's title, kind, Space, project, last editor and time, the sessions that touched it; Pin, Rename, Move to Space, Duplicate, Export, Delete. A Space is a named folder the owner creates, optionally linked to a project directory. The artifacts the owner's sessions delivered before P3 are there as File and HTML artifacts with their sessions.
2. **A document.** From a session, the agent creates a document and the owner opens it in the panel (or a main tab). It is a Google-Docs-like editor: click anywhere and type; headings, lists, task lists, tables with row and cell editing, code with highlighting, images, dividers, math, diagrams, date and mention chips; tabs within the document; find; the design system's look applied. The agent, asked in the session, replaces one sentence, inserts a section after a heading and edits one table cell, and only those blocks change on screen while the owner keeps typing elsewhere; the agent's cursor and the blocks it is editing are visible while it works.
3. **A comment.** The owner selects a passage, comments, and sends it to the agent: a thread pinned to that passage opens as a side thread (or goes to main) exactly as P2's card does; the pin survives the owner's later edits around it, a restart, and the agent's rewrite of the sentence; the agent's reply appears in the thread; Resolve closes it and the mark disappears; resolved threads are listed and reopenable.
4. **History.** The document's version history lists automatic versions (at human idle, during activity, at the end of each agent turn that touched it) and named ones ("Save version" with a name and a what-changed note), grouped by day with runs folded, each row with its author chips; a version previews read-only with Show changes on: insertions in the author's colour, deletions struck through, "N changes" with ↑ ↓; Restore creates a new version and never destroys; Compare takes any two; a "See N new changes" pill appears when an agent changed the artifact since the owner last looked and opens that comparison. Right-clicking a selection says who edited it and when.
5. **A deck.** The agent builds a deck from a brief: deck.json and one slide file per slide in the dialect (§4.5). The owner opens it: a filmstrip, a fixed 16:9 canvas with zoom, every element selectable, movable, resizable and restyleable, text edited in place, snapping guides, z-order, grouping, add, delete and reorder slides, speaker notes, a presenter window. The owner moves a box and retitles a slide; the agent, asked to change a font deck-wide, fetches, edits and publishes; its publish of a slide the owner changed meanwhile is refused with the slide's name, and after a re-read succeeds. History works per slide (changed slides marked in the filmstrip, changed elements outlined). Export gives a PPTX that opens in PowerPoint and Keynote with editable text and shapes in the right places and the deck's fonts, a PDF, and a standalone HTML.
6. **A design system.** The owner picks one of the built-in defaults, or the agent extracts one from a codebase, a deck or a website (colours, type, spacing, components, logos, fonts) into a Design System artifact with a preview page; the owner edits a colour and the preview follows; a document and a deck set to it restyle; the default system per Space and for the owner is honoured by the agent without asking; the `ask` sheet can offer design systems as an input (P1 P-13).
7. **Design and Dashboard.** A design artifact holds artboards of any size on a pannable canvas in the same dialect and editor as slides, exported as PNG and PDF; a dashboard is a document whose chart and table blocks are bound to data (files the agent wrote, or a declared connector's tool through the artifact bridge, user-gated, refreshed on a schedule), each block showing its source. (Coarse by design: P3-E is cut at its dispatch.)
8. **The shell.** Dragging the session/panel divider past the panel's maximum turns the session into a card at the panel's bottom-left (transcript, composer, expand, close; a chord and a header button toggle it; × leaves a pill with an unread dot; over a Browser tab the card reserves a live column instead, per the owner's ruling); the panel header shows the open tool's title, its saved state and its actions instead of an empty bar; Mark-up mode draws on a browser page, a document or a slide and attaches the marked screenshot to the composer.
9. **The finish.** The tracker's P3-owned rows triaged and landed in waves; the scale review clean; the owner's sitting on a development-signed build covering items 1 to 8; the owner's open questions decided; then the declaration.

## 4. Design

Everything below is advisory inheritance unless marked **[binding]** with its joint-view reason. Children expand their own sections in place; a child that overturns advisory content records a dated line in §12 under its id.

**4.1 The artifact entity and the library** **[binding — every child reads and writes it, and it replaces X12's per-session records].** An artifact is a top-level entity independent of sessions (Decision Log 5): `{id, kind, title, spaceId?, projectId?, createdBy: Actor, createdAt, updatedAt, lastViewedAt, pinned, designSystemId?, linkedPath?}` with kinds `document | presentation | design | design_system | dashboard | html | file`. It lives in the index (tables `artifacts`, `artifact_versions`, `artifact_updates`, `artifact_threads`, `artifact_assets`, `artifact_sessions`, `spaces`; the migration number is a slot per X15) and its bytes under `<userData>/artifacts/<id>/` (assets, version states, the file of a File artifact in place as today). Sessions are linked, not owners: `artifact_sessions {artifactId, appSessionId, role: created | edited | viewed | commented, lastAt}`; a side thread's scope rule (X9's ancestor resolution) becomes "the artifacts its ancestors are linked to". A Space is a named folder, at most one per artifact, optionally linked to a project directory, in which case the Space's linked artifacts mirror to `<dir>/artifacts/` on every save as read-only exports (`.md` for a document, a deck folder for a presentation; Decision Log 8); `projectId` is a fact from the creating session, filterable, never a Space. Today's deliverables import at the migration as `file` and `html` artifacts with their session links; the `deliverables.*` IPC and the panel tool are replaced by `artifacts.*` and an Artifacts tool (Decision Log 9: the word is Artifacts everywhere); `send_file` stays and creates a File artifact. The library is a main tab beside Overview (§2 item 1), and the panel's Artifacts tool is the session's own list with "All artifacts" one click away; an editor opens in the panel by default and in a main tab on demand (P1 A-2 carried). Search is a local FTS index over titles and extracted text, maintained on save.

**4.2 The document store** **[binding on the model — the editors, the agent tools, history, attribution and P4's collaboration all stand on it; advisory on table layout].** Every artifact of kind document, presentation, design, design_system or dashboard is one Yjs `Y.Doc` (Decision Log 2, 11). The authoritative copy lives in the engine host's document service (`src/engine-host/documents/`), which already hosts the MCP tool server and outlives windows in detached mode (E10); the renderer's editors are replicas synced over one `MessageChannelMain` port per open document carrying y-protocols sync and awareness frames (the thin provider of `research/p3-yjs-store.md` §2); each writing agent session edits through its own replica synced in-process by the same protocol, never straight into the host doc, so authorship is known per update. Persistence is an `artifact_updates` log (one row per update: `seq, author, at, bytes`, appended under WAL with `synchronous=FULL` before the update is acknowledged) compacted into `artifact_versions` states (full V2 states, gc on; the author log folded into a durable clientID → actor table with per-author delete sets), the AFFiNE layout. Versions are rows of `artifact_versions {seq, at, author, kind: auto | turn | named | restore | import, label?, note?, summary?, state}`, thinned by age for `auto` rows; history renders in y-prosemirror's state-pair mode inside a throwaway doc, exits only through `unrenderSnapshot()`, restores through the `restore` meta as a new version. The `ychange` mark and the block attribute are in every schema from day one, and schema parity between every writer and editor is an invariant checked in CI (one schema module, importable in Node, no React node views). Undo is Yjs's `UndoManager` scoped to the local binding and blocked while history is shown. **Yjs v13 with `@tiptap/y-tiptap` by default; spike S1 decides v14 before any document is persisted, because migration is one-way** (Decision Log 11). The detached host's transport gains a binary, length-prefixed channel for document frames (an X13 amendment through the ledger). Awareness carries the human's and each agent's cursor and the blocks an agent is editing (§2 item 2).

**4.3 The agent's formats and tools** **[binding — one protocol shaped like Claude's so skills transfer, and one namespace the ledger owns].** The `maws` server gains one artifact namespace (names fixed in the P3 ledger before any sibling codes against them; the shapes here): `artifact_list` (the library, filters, a Space), `artifact_describe_type` (the kind's guide and format reference, printed on create as Claude Code prints a type's `format.md`), `artifact_create` (a kind, a title, initial content in that kind's format; the existing free-HTML create keeps its name and becomes kind `html`), `artifact_read` (a document as markdown with block ids, ranged; a deck as its files; versions by number), `artifact_edit` (documents: one atomic batch of block operations, §4.4), `artifact_publish` (file kinds: a files map with `null` removals, `baseVersion`, the three concurrency layers of Claude's protocol: the "you haven't read the latest version" guard, a merge when no sent file changed, a refusal naming the changed files; `force` as the last resort), `artifact_upload_asset` and `artifact_list_assets`, `artifact_comments`, `artifact_reply`, `artifact_resolve`, `artifact_screenshot` (kept), `artifact_export`. Each kind's guide (`SKILL.md`-shaped) and format reference are MAWS files under `src/shared/artifacts/types/<kind>/`, versioned, returned by `artifact_describe_type` and attached to the creating turn, so the agent learns the dialect the way it learns Claude's. The default design system's guide is attached on create without asking (Claude's rule). Every tool call carries the session as the actor (§4.2) and ends the turn's edits as one `turn` version when the turn ends (§4.7).

**4.4 Documents** **[binding on the schema invariant, ids, comment marks and the edit tool's semantics; advisory on the block list].** A document is a Y.Doc with a `tabs` map (ordered; Claude's project → tab → node, Google Docs' tabs) and one `Y.XmlFragment` per tab bound through Tiptap 3's Collaboration; its schema (one module) has paragraph, heading 1 to 3, bullet, ordered and task lists, quote, code (shiki), table (row and cell ids), image (an asset), divider, callout, math (KaTeX, as the transcript renders it), diagram (mermaid), chart (a Dashboard block, bound to data), and inline marks bold, italic, underline, strike, code, link, highlight, `comment {threadId, orphan}` (overlapping allowed, non-inclusive; BlockNote's shape) and `ychange`; chips are inline nodes: date, mention (a person, a session, an artifact), dropdown (a status). Every block carries a short id (`^` syntax in the agent's markdown, an 8-character nanoid in the doc; UniqueID keeps them through split and paste, the host repairs missing and duplicate ids after each applied update, and every writer ids what it writes). The agent reads GFM with `^id` markers and `<chip …/>` markers, ranged ("from `^h7`, 40 blocks"); it writes `artifact_edit(artifact, baseVersion, ops[])` with `replace_text {block?, old, new, all?}` (exact and unique, else an error listing candidate blocks), `replace_block {id, markdown}`, `insert {after | before, markdown}`, `delete {id}`, `move {id, after}`, `set_cell {table, row, col, markdown}`, conflicts checked per block (an op fails only if its own target changed since `baseVersion`, returning that block's current text), the response one line per op with new ids. The host applies each op through a patch writer: a multi-hunk word diff as `Y.XmlText` operations with explicit attributes for same-type blocks, `updateYFragment` per child for structure, from the agent's replica, validated against the renderer's exact schema; never a whole-block delete-and-insert (attribution and anchors). Comments are the mark plus a `threads` map in the Y.Doc (threads sync and version with the text) mirrored to `artifact_threads` for the library and the side-thread link; a thread stores its quote and a relative-position pair for orphan display; P2's card (X21) is the UI, with `CardTarget {kind: 'artifact', artifactId, threadId}` beside the existing two and the Side thread or Send to main routes unchanged; Resolve and reopen are new. The design system applies as a theme: the editor's CSS reads `--ds-*` tokens (§4.6) and the built-in default system is MAWS's own look (Decision Log 7). Export: PDF (the print path), DOCX (an in-house serializer over `docx` mapping the design system to the Word theme and named styles, comments as Word comments, optionally the changes since a version as tracked changes), Markdown (GFM, ids stripped), HTML (standalone, tokens inlined).

**4.5 Presentations** **[binding on the dialect being the agent's interface, the Y.Map element model, the publish protocol and the export route; advisory on the editor's internals].** The deck's files are Claude's shape so decks and skills transfer: `project/deck.json` (v4-compatible: `title`, `order`, `sections`, `faces`, `designSystems`, `attachments`) and `project/slides/<id>.html`, each exactly one `<section id>` on a 1920×1080 canvas, no `html`/`head`/`style`/`body`, inline styles only from a closed list (px lengths; hex or rgb colours; flex, grid and `position:absolute`; no classes, style blocks, margin, z-index, em or arbitrary CSS variables), the element set h1 to h3, p, ul, ol, table, b, i, a, span, div, img, inline svg, `<x-shape>`, `<x-icon>`, `<x-connector>`, `<x-embed>` (sandboxed, 16 KB, 8 per slide), a trailing plain-text `<aside>` for notes; everything else is dropped on load and reported back to the agent as warnings (the owner's Claude Desktop report, Decision Log 6; the exact list is MAWS's, written in the kind's format reference, revised if U1 shows Claude's). **The owner's ruling (Decision Log 12):** the dialect additionally permits `var(--ds-*)` references for colours, fonts and spacing (a superset of Claude's rule), so a design-system change restyles a deck; export reads computed values and is unaffected. Inside MAWS the live model is a Y.Doc: a `deck` map (title, sections, faces, design system, attachments), a `slides` map id → slide (`order` a fractional index, `notes` a Y.Text, `elements` a Y.Map id → element with one key per property, `style:*` keys, a fractional `z`, text as a nested Y.XmlFragment bound to a Tiptap instance on double-click); a canonical parser and serializer round-trip the dialect byte-identically, and a publish applies only the changed properties as the agent's transaction (`research/p3-yjs-store.md` §6). The editor is DOM over the dialect with MAWS's own transform layer: a handles overlay outside the scaled slide, drag, resize, rotate, marquee and multi-select, snapping to slide and sibling edges, centres and equal gaps, free (absolute) and in-flow (flex or grid children, moved by reordering, "Detach" to absolute) elements, groups as absolute divs, z-order as DOM order, text fit as `data-fit` (none, shrink, grow), one deck-level undo stack, a filmstrip (dnd-kit), speaker notes, a presenter window (current and next slide, notes, timer), layouts as design-system templates with placeholders, the Theme and Text style menus reading the design system. Export: PPTX by measured geometry in a hidden 1920×1080 window over pptxgenjs (`LAYOUT_WIDE`, 1 px = 0.5 pt, one-to-one mapping of text boxes with runs, shapes, pictures, SVG with PNG fallback, native tables and charts, notes; explicit sizes, fonts embedded and the 12 theme colours written by post-processing the zip; `shapeName` = `data-id`); PDF by the print path (`@page 1920px 1080px`); standalone HTML. History per slide: a version's changed slides edged in the author's colour in the filmstrip, changed elements outlined, deleted ones ghosted, notes diffs below.

**4.6 Design systems** **[binding on the token format and the CSS names — documents, decks, designs, the exporters and the agent all read them].** One directory per design system under its artifact: `tokens.tokens.json` (W3C DTCG 2025.10, the only source: semantic roles `color.bg | text | accent.*`, `type.title | subtitle | h1 to h3 | body | caption | quote`, `space.*`, `radius.*`, `shadow.*`, and `$extensions["dev.maws.office"]` mapping the 12 Office theme slots and the major and minor fonts), `tokens.css` (generated: `--ds-*` properties and type classes), `DESIGN.md` (generated for the agent, front matter from the tokens, the guide below it), `layouts/*.html` and `components/*.html` (dialect snippets with placeholders), `assets/` (logos, font files, which embedding and PDF need). Sources: three built-in defaults (one is MAWS's own look and the document default), extraction by the agent from a codebase, a deck, a PDF or a website through a MAWS skill that writes the tokens file, and building together through the `ask` sheet (P1 P-13's design-system input arrives here). A default per owner (settings) and per Space; a document or deck references one by id and restyles by token swap; the Design System artifact's page previews palette, type scale, components and layouts and edits tokens in place.

**4.7 Version history** **[binding on the behaviour — it is §2 item 4 and the differentiator].** Automatic versions at 2 minutes of human idle and every 10 minutes of activity, at the end of every agent turn that touched the artifact (authored by that session, summarised by the turn), and before any restore or import; named versions by "Save version" (name, what changed), any automatic one nameable; the list grouped by day with runs folded, author chips (the human, each session in its own colour), a one-line summary, a "Named only" filter; the read-only preview with Show changes on by default (inserts in the author's colour, deletions struck, block gutter marks, "N changes" ↑ ↓); Restore as a new version "Restored from …", Make a copy beside it; Compare any two by shift-click; "See N new changes" when an agent changed the artifact since the owner last looked; "Show editors" on a selection. Authors come from the actor table (§4.2): the human, or a session by its title with "Claude" as the fallback.

**4.8 Export** (advisory). One export service in main, `artifact_export` for the agent and the library's Export for the owner: a hidden `BrowserWindow` on the `maws-capture` partition renders a document or a slide for PDF (`printToPDF`, margin boxes from tokens, `generateDocumentOutline`), the PPTX mapper (§4.5) and PNG; DOCX and Markdown are pure serializers. A LibreOffice render-and-compare test gates the PPTX mapper in CI where LibreOffice is present. Import: Markdown and HTML into documents; DOCX into documents through a tolerant reader; PPTX import is deferred (§9).

**4.9 The shell** **[binding on the floating card's ruling; advisory on the rest].** The floating session card is the owner's design of 2026-10-10 as recorded in the seed: a third panel state `floating` beside collapsed and maximized (a `regions` schema version 4, slot per X15), entered by dragging the divider past the panel's maximum, a chord and a Float button in the panel header, the card at the panel's bottom-left with the transcript, the composer, expand and close, resizable by its top and right edges, size remembered per tab, × leaving a pill with an unread dot, the docked request and tab notes kept in the card's stack; **over a Browser tab the card reserves a live left column instead of floating (the owner's ruling, binding).** The panel header bar (the owner's `feedback.md`, 2026-10-10: "bar above sidebar tabs are completely empty") shows the open tool's title and breadcrumb, an artifact's saved state (`saved | saving | unsaved | readonly`), its version history, export and "Open in tab" actions, and the Float and Maximize buttons. Mark-up mode: a drawing overlay (pen, box, arrow, text) over a browser page, a document or a slide; Done captures the region with the marks as an image attached to the composer with the anchor's label; Escape discards; no change to the artifact.

**4.10 Web portability and the teachers product** **[binding — P4 must not rewrite the editors or the store].** The editors, the schema module, the dialect parser and serializer, the token tools and the history renderer live under `src/artifacts/` with no Electron, Node or `window.maws` import; the renderer adapts them through one `ArtifactHost` interface (open a document's provider, assets, export, awareness identity); the host's document service sits behind a `DocumentStorage` interface with the local SQLite backend now and a network backend later (AFFiNE's `DocStorage` shape), so P4 adds a WebSocket provider and connection-bound actors without touching the model.

## 8. Risks and mitigations

- **The scale.** P3 is the largest phase: four editors, a store, a protocol, exporters. Mitigation: the spikes first and the S1 gate; the frontier rule (E is cut at its dispatch; D's and H's scope is bounded); children land independently so the owner uses documents before decks exist.
- **The frozen snapshot path.** y-prosemirror 1.x's history has five "not planned" bugs (attribute changes invisible, code blocks). Mitigation: S3 measures them on the real schema; the history renderer is one module so v14's `DiffRenderer` can replace it; S1 may choose v14 outright.
- **Schema drift deletes content.** A binding that cannot build a node deletes it in the live doc. Mitigation: one schema module, the CI parity check, writers validate before applying, the host repairs ids after each update.
- **Human and agent in one block.** Mitigation: the patch writer's word-level hunks, per-block conflict rules, S4 with Korean IME composition under remote updates (the terminal's C1 lesson), awareness showing the agent's blocks.
- **PPTX fidelity.** PowerPoint wraps differently and never recomputes autofit. Mitigation: embedded fonts, explicit sizes, width slack, an optional "lock lines" mode, render-and-compare in CI, "Slides as pictures" as the fallback export.
- **The dialect is ours, not Claude's.** Skills written for Claude Slides may emit what our loader drops. Mitigation: U1 when the owner allows; the loader's warnings name every dropped thing; the format reference is attached on create.
- **The detached host.** Documents need a binary channel the JSON-lines socket lacks. Mitigation: S2 builds it; until then detached mode serves documents through the live host only, labelled.
- **Storage growth.** Mitigation: gc on, version thinning, S7's soak with a published policy.
- **Portability drift.** An editor that imports Electron once is never web-hosted. Mitigation: `src/artifacts/` with a lint rule against Electron, Node and `window.maws` imports.
- **The owner's time.** Three sittings' worth of surfaces. Mitigation: F's sitting sheet is written as children land; documents can be sat on before decks exist.
