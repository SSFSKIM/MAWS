# Gate offload: hardware-independent gates on GitHub Actions

Living spec (doperpowers:execspec), authored 2026-10-14 by the architect at the owner's decision after P3-B's M9: "start the GitHub Actions offload now as a small spec; the dedicated quiet Mac for timing gates at P3-F". Not a P3 child; tooling for every child's gates. Cites the P3 composite spec `docs/doperpowers/plans/2026-10-12-p3-co-work.md` Decision Log 54, 63 (the load rule for measured bounds, unchanged here) and 64 (this split). Branch `gate-offload`; the architect lands it through a master gate.

## 1. Purpose

One Mac carries three child executors, their workers, their reviewers and the owner's running MAWS, so every gate run raises the machine's load and every measured bound waits for the load to fall (two slots machine-wide, `waitload20.sh`, the marginal band of Decision Log 54 and 63; one child waited seven hours for a quiet minute). The gates split into two classes. Hardware-independent gates (typecheck, lint, the unit suite, the build and bundle guard, the protocol probes, most e2e groups) can run anywhere; they are most of the CPU minutes but none of the hardware dependence. Hardware-bound gates (measured bounds on Apple Silicon, macOS-only behaviour, the paid live runs) stay on the Mac. This spec moves the first class to GitHub Actions on Linux, behind one local script that an executor calls the way it calls `with-slot.sh` today, so the Mac's load comes from measured runs and the owner's app alone. The dedicated quiet Mac for the second class is P3-F's.

## 2. Constraints

- The repository is private (`SSFSKIM/MAWS`, Actions enabled, no workflow yet). Linux minutes bill at the plan's rate beyond the free allowance; the script runs only the gates asked for, so a child reruns the groups it touched, not the matrix.
- Children's branches are not pushed; each run pushes one sha to a `ci/<label>-<short>` ref and deletes it after (`--keep` to leave it).
- Timing and measured bounds never run on Actions: a runner's CPU and GPU-less renderer make a frame time or a loop latency noise, not a measurement. Decision Log 54 and 63 govern those runs locally, unchanged.
- No test is deleted, weakened or re-timed to pass on Linux. A test asserting a macOS fact (APFS case folding, `ps` or `zsh` job control, a Keychain, the packaged app) is guarded with `skipIf(process.platform !== 'darwin')` and one comment naming the fact; the guarded list is in this document and reported at the hand-back. A Linux failure that is a real defect is reported, not guarded.
- The package scripts stay the one source of truth for what a gate is: the workflow runs `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm test:probes`, `pnpm build` and `pnpm e2e:<group>` verbatim (under `xvfb-run -a` for e2e), so a gate means the same thing on the Mac and on the runner.
- Rules binding every milestone: absolute paths with `git -C` and `pnpm -C`; `pnpm_config_verify_deps_before_run=false`; before any local `pnpm test`, e2e or build `/tmp/maws-review/waitload20.sh && /tmp/maws-review/with-slot.sh <cmd>` (local runs here are typecheck, lint and targeted vitest files only; the suites run on Actions); never touch the owner's running MAWS, `dist`, the user-data directory or `~/.claude`; never stage `node_modules`, `spikes/gws-onboarding/`, `.playwright-cli/`; no attribution in commit messages; never amend or reset; commit as you go; the execution document is this file (the executor appends to Decision Log, Surprises and Outcomes; the architect owns the rest).

### 3.2 The workflow `.github/workflows/gate.yml`

Triggers: `push` on `ci/**` (the script's refs; the workflow file travels with the pushed tree, so a branch carrying the workflow tests itself before it lands), `push` on `master` (the `warm` job alone, Decision Log 26) and `workflow_dispatch` with the same `gates` input for a manual run. Input `gates`: a comma list over `static`, `unit`, `unit:darwin`, `probes`, `e2e:<group>`, …, read from the ref's last commit message trailer `Gates: …` for the push trigger (the script writes it onto an empty commit when the caller narrows the set) or defaulting to the whole class-1 set.

Jobs, each with `timeout-minutes: 30` under `concurrency: {group: gate-<ref>, cancel-in-progress: true}`; class 1a on the runner of §3.6, the e2e jobs on the lane the plan resolves, `unit:darwin` always on `[self-hosted, macOS, ARM64]`:

- `static`: `pnpm typecheck`, `pnpm lint`.
- `unit`: `pnpm build` (the bundle guard reads the engine-host chunk), then `pnpm test` with vitest's workers at the runner's cores; the timing projects keep their 30 s.
- `unit:darwin` (Decision Log 25): on the macOS runner, after the shared setup, `pnpm exec vitest run --maxWorkers=<cores> $(scripts/darwin-unit-files.sh)` over the files with §6's guards, found by the guard itself (`grep -rlE "platform !== 'darwin'"` over `src` and `test`), no build; in the macOS lane's default set, and by `Gates: unit:darwin` on either lane.
- `probes`: `pnpm test:probes`.
- `e2e`: a matrix over the requested groups, `fail-fast: false`; each job `xvfb-run -a --server-args="-screen 0 1920x1080x24" pnpm e2e:<group>` with `MAWS_E2E_QUIET=1`; Playwright's HTML report and `test-results/` uploaded as an artifact on failure (`if: failure()`), retention 7 days.

Shared setup (a composite action `.github/actions/setup` so the jobs do not repeat it), after `actions/checkout` at the pushed sha: pnpm at `packageManager`'s version (`pnpm/action-setup` on hosted runners; `corepack enable` into the job's own directory on every self-hosted one, the pool and the Mac, Decision Log 35 and 42); `actions/setup-node` with Node 22; `pnpm install --frozen-lockfile` (whose postinstall fetches Electron into `~/.cache/electron`). On Linux the pnpm store (`cache: pnpm`) and the Electron download (`actions/cache` keyed by OS, architecture and Electron version) come from the Actions cache; the self-hosted macOS runner uses no Actions cache, its own disk keeping both between jobs (Decision Log 26). Caches are readable from the saving branch and the default branch only, so a push to master runs the job `warm` alone (`ubuntu-24.04`, checkout and setup, nothing else): every `ci/` ref then restores master's caches exactly and the Linux jobs skip their saves, a tree with a changed lockfile saving its own until it lands. For Linux e2e jobs the setup adds `apt-get install xvfb fonts-noto-cjk` (Korean text in the renderer) and the Inter and JetBrains Mono faces and zsh, and, for the groups that render documents through LibreOffice, `libreoffice-writer libreoffice-impress` (B's DOCX-to-PDF case, C's render-and-compare); Electron's sandbox on the runner: the apparmor restriction on unprivileged user namespaces lifted with `sysctl kernel.apparmor_restrict_unprivileged_userns=0` (the documented runner fix), never `--no-sandbox` in the app. Each gate job writes its counts to `$GITHUB_STEP_SUMMARY`.

The class-1a runner (Decision Log 41): the dispatch input `class1a` (`linux`, `macos` or `pool`) or the pushed commit's `Class1a:` trailer, else `GATE_RUNNER`, else `linux`; `static`, `unit` and `probes` take `runs-on: ${{ fromJSON(needs.plan.outputs.<job>_runner) }}`; the `plan` job runs `pool-ensure` when its `pool` output is true. The unit summary patterns no longer expect a `Type Errors` line: vitest's `typecheck` block is gone from the node project, since `pnpm typecheck` already covers the four `*.test-d.ts` files (Decision Log 35's P5, proven by a deliberate `expectTypeOf` break failing `tsc`).

### 3.3 The Linux adaptations

- `postinstall` is `chmod +x node_modules/node-pty/prebuilds/darwin-arm64/spawn-helper && install-electron`, which fails where the darwin prebuild is absent: it becomes `node scripts/postinstall.mjs`, chmod of the darwin spawn helper only when it exists (node-pty 1.1.0 ships Linux prebuilds), then `install-electron`; behaviour on the Mac unchanged.
- Tests asserting macOS facts gain the guard of §2 with the fact named; the list lives in §6 of this document.
- Node 22.13 or later is required for `node:sqlite` unflagged (the Mac runs 22.23); the workflow pins the Node major to 22 and `engines` stays `>=22.12` unless M1 finds the store tests need the bump recorded.

### 3.4 The local script `scripts/ci-gate.sh`

`scripts/ci-gate.sh <worktree-or-sha> [--gates static,unit,probes,e2e:side,…] [--label <name>] [--keep]`. It resolves the sha (a worktree path's `HEAD`, or a sha), pushes `<sha>:refs/heads/ci/<label>-<short>` (force, since a child reruns on a moved tree), finds the run (`gh -R SSFSKIM/MAWS run list --branch ci/<label>-<short> --json databaseId,headSha`, retried until the run for the sha exists), `gh run watch <id> --exit-status`, prints `gh run view <id>` with each job's conclusion, downloads failed jobs' artifacts to `/tmp/maws-review/gates/ci-<short>/`, writes the whole transcript to `/tmp/maws-review/gates/ci-<short>.log`, deletes the `ci/` ref unless `--keep`, and exits with the run's status. It passes `-R` to every `gh` call so it works from any directory. A narrowed `--gates` writes the trailer of §3.2 onto an empty commit on top of the sha before pushing, so the pushed tree is the tested tree plus one message.

`--class1a linux|macos|pool` writes the `Class1a:` trailer the way `--runner` writes `Runner:` (Decision Log 41); `--gates packaged` asks for the Mac's packaged job (Decision Log 38); `--evidence` writes the `Evidence: yes` trailer, so the run's e2e jobs upload their `test-results/` and `playwright-report/` on success too (Decision Log 48). `--live` writes the `Live: yes` trailer (a `live` dispatch input beside it), so the e2e job runs with `MAWS_LIVE`, `MAWS_LIBRARY_LIVE` and `MAWS_LIVE_DOCUMENT` at `1` and the paid live groups `gate.yml` lists in `LIVE_E2E` run rather than skip, each spec within its own cap; the plan refuses a live run unless every gate it asks for is a `LIVE_E2E` group, since `e2e:default`'s bare set collects every live spec, and refuses a `LIVE_E2E` group in any other run, since `e2e:design-live` and `e2e:dashboard-live` set `MAWS_LIVE=1` in their own scripts (Decision Log 75).

Before the push, a run that puts jobs on a Mac reads ci-kit's open alerts and MAWS's runners (`scripts/ci-gate-alerts.mjs`, #28; Decision Log 62): when no online Mac runner is free of an open `ci-kit-alert` issue (a system dialog holding that Mac's front, which the runner's job-started check would refuse) it pushes nothing and exits 2 naming each alert; with a healthy Mac left it goes ahead and names the blocked one; a failed read warns and goes ahead; `MAWS_GATE_IGNORE_ALERTS=1` skips the check, the architect's call, recorded in the transcript.

### 3.5 What changes for a child

Its brief says: class-1 gates through `scripts/ci-gate.sh <worktree> --gates <what you touched>`; class-2 gates locally under the load rule as today; a Linux-only failure is reported to the architect, never guarded by the child. The P3 spec's Decision Log 64 records the split; the P2 and P3 briefs in flight keep their local gates until their executors are told.

The brief's wording as landed (Decision Log 13, 16):

- Class 1a through the script, from any directory: `scripts/ci-gate.sh <worktree>` runs static, unit and probes (12 to 18 minutes of wall clock, the unit job's range on the 2-core runner); `--gates static`, `--gates unit` or `--gates probes` narrows it to what you touched. The script prints each job's conclusion and the run's URL, keeps the transcript in `/tmp/maws-review/gates/ci-<short>.log` and exits 0 only when the run is green.
- Class 1b, the e2e groups, are macOS work and run on the Mac mini runner (`GATE_E2E_RUNNER=macos` since 2026-10-16, Decision Log 45): `scripts/ci-gate.sh <worktree> --gates e2e:<group>` (the default set on the macOS lane is `unit:darwin` and every `CLASS1_E2E` group), a failed group's HTML report and `test-results/` coming down to `/tmp/maws-review/gates/ci-<short>/`; the Linux lane (`--runner linux`) takes only the groups green there (`LINUX_E2E`, the list in §3.1). Nothing but named-file vitest, `pnpm typecheck` and `pnpm eslint` runs on the architect's MacBook, through the slot script (Decision Log 35's P7, retired), with one exception: a child's single paid live e2e run (`e2e:<kind>-live`, under its US$1 cap), which needs the owner's engine login and so runs there through the slot, never on the mini (Decision Log 48). A landing onto a master that moved since the branch's last gate takes a class-1a gate on the merged tree before the push, or the confirmation run right after it (Decision Log 45). The mini runs one job at a time and a whole class-1b set holds it for about 45 minutes, so the whole set runs at the architect's landing gates and once at a child's hand-back; a development gate names its groups (`--gates e2e:<own group>,e2e:<the sibling groups whose files it touched>`) and never the default set (Decision Log 46).
- The unit cases §6 guards run on the macOS runner as `unit:darwin` (Decision Log 25); when your change touches one of those files, or before a landing, run `scripts/ci-gate.sh <worktree> --gates unit:darwin --runner macos` (under a minute on the mini since Decision Log 26, fifteen seconds of it tests). The local fallback, for a mini outage: `/tmp/maws-review/with-slot.sh pnpm -C <worktree> exec vitest run $(<worktree>/scripts/darwin-unit-files.sh <worktree>)`.
- On this Mac, unit and DOM vitest runs on named files, typecheck and eslint take no load wait (Decision Log 24); they hold one of the two machine-wide slots (`/tmp/maws-review/with-slot.sh`), one at a time, and a timing-based case that fails under load is rerun alone once before it counts. Electron e2e groups, `pnpm build` and every measured bound wait for a 1-minute load under 20 (`/tmp/maws-review/waitload20.sh &&` before the slot; the P3 spec's Decision Log 54).
- A failure on the runner that does not reproduce on the Mac is reported to the architect with the run URL, never guarded by the child.
- A refusal before the push (`ci-gate: not pushing: …` and exit 2, naming a machine, a dialog and its first-seen time; Decision Log 62) is reported to the architect with that line, and the waiter is stopped; `MAWS_GATE_IGNORE_ALERTS=1` is the architect's call, never the child's. While ci-kit's watcher drains an alerted Mac, a run with Mac jobs queues instead of being refused, and a queue wait past 30 minutes goes to the architect with the run id, as before.
- A change that adds an e2e spec file or a group moves `default`'s own-spec pin in `.github/scripts/e2e-default-specs.test.mjs` on the same branch (the count and, where it changes, the list); since Decision Log 64 the `static` job runs that file and the other gate-script tests, so a stale pin goes red in class 1a rather than unseen.
- A relaunch after a completed run (Decision Log 59) uses the relaunch line `scripts/ci-gate.sh` prints, which carries `DefaultBeside: <groups>` naming the original run's e2e set, so the relaunch's `default` runs only its own specs (Decision Log 67); a hand-written narrowed `--gates` without that trailer widens `default` to the absent groups' specs, and a failure there is read against the whole run's own group for that spec.
- An explicit `--gates` list runs class 1a only if it names `static`, `unit` or `probes`; `--class1a pool` chooses the runner, not the selection (Decision Log 67). A brief that wants class 1a with named groups writes `--gates static,unit,probes,<groups>`; a run without them is an e2e-only run and the landing still needs class 1a on the tree.
- A soak, a measurement job or any heavy run that is not on a landing's critical path launches in the lane's idle half (12 to 24Z) when the schedule allows (Decision Log 68); landing gates and the wave gates of a child on a deadline take the queue as it comes.
- The groups in `gate.yml`'s `POOL_E2E` (desk-web) never run on a Mac: on either lane they run on the pool's cpus-4 box when class 1a resolves to the pool, else on hosted `ubuntu-24.04`; every other e2e job takes the lane's runner (Decision Log 68, 69, 73). A pool job, class 1a or POOL_E2E, that GCE preempts (runner `ci-kit-gce-*`, conclusion failure, the annotation 'The operation was canceled.' with no timeout annotation, the run not itself cancelled) is re-run alone by `scripts/ci-gate.sh`, once per job per run and one at a time as a new attempt, and the script reports the final attempt: `ci-gate: run <id> attempt <n>` on the line before the unchanged status line `ci-gate: run <id> <conclusion>`, with a `ci-gate: preempted by GCE (n): …` summary before those; a landing record cites the run id and the attempt; a job the summary calls 'preempted twice, red' is relaunched alone after the run (Decision Log 58, 59), never a baseline row (Decision Log 71).
- The pushed tree must carry the workflow: merge master at or after the landing (2fefbd24) before the first run. The script pushes only `ci/<label>-<short>` refs and removes them; never push a branch for it.

### 3.6 The macOS runner (Decision Log 13 and 14)

The owner's choice (Decision Log 18) kept the e2e lane on the MacBook until the Mac mini's sessions were freed; the mini was registered 2026-10-15 (Decision Log 23) and took the lane 2026-10-16 (`GATE_E2E_RUNNER=macos`, Decision Log 45); the setup below is its record.

The workflow has two lanes and runs only on `ci/**` pushes and dispatches (a push to master runs nothing: the `warm` job of Decision Log 26 and master's push trigger left with Decision Log 53); `plan` runs on `ubuntu-slim`. Class 1a (`static`, `unit`, `probes`) runs on `ubuntu-24.04`, on the Mac when the repository variable `GATE_RUNNER` is `macos`, or on CI-opt's pool when it is `pool` (Hetzner today, GCE spot once the kit's backend lands, the owner's choice in Decision Log 43; static on `[self-hosted, ci-kit-pool, cpus-4]`, unit on `cpus-8`, probes on `cpus-2`; per run the `Class1a:` trailer written by `ci-gate.sh --class1a linux|macos|pool`, or the `class1a` dispatch input, wins over the variable; the plan writes `static_runner`, `unit_runner`, `probes_runner` and `pool`); `plan` stays hosted whatever the lane except under `GATE_RUNNER=macos`, and when `pool` is true it runs `SSFSKIM/ci-kit/pool-ensure@v1` with `secrets.HCLOUD_TOKEN` first. On every self-hosted runner the setup action takes pnpm from `corepack enable` at `packageManager`'s version, never `pnpm/action-setup`, whose version switch on the Mac spawned `open` into the owner's browser (Decision Log 42), and on self-hosted Linux it skips every Actions cache (the pool's store is baked and shared); the unit job's `--maxWorkers` is `nproc` on Linux (a container's cpuset) and `getconf _NPROCESSORS_ONLN` on macOS (Decision Log 35, 41). The e2e jobs take the lane the plan resolves: the run's `Runner:` trailer (`ci-gate.sh --runner linux|macos`, or `MAWS_GATE_RUNNER` in the caller's environment) or the dispatch input `runner`, else the variable `GATE_E2E_RUNNER`, else `GATE_RUNNER`, else `linux`. The macOS lane is `runs-on: [self-hosted, macOS, ARM64]`; on it the default set adds `unit:darwin` and every class-1b group (`unit:darwin` runs on `[self-hosted, macOS, ARM64]` whatever the lane, also when `Gates:` names it on a Linux lane; the lane governs the e2e jobs alone), and every Linux-only step (apt packages, xvfb, the apparmor sysctl, `/private/tmp`) is skipped by `runner.os`, and so is every Actions cache: the mini's disk keeps its pnpm store and Electron download between jobs (Decision Log 26). The recommended setting once the Mac mini is registered: `GATE_E2E_RUNNER=macos` (e2e on the Mac, class 1a still in parallel on Linux); `GATE_RUNNER=macos` moves class 1a there too and spends no Linux minutes, at the price of one job at a time. The macOS lane's e2e groups build through `scripts/e2e-build.sh harness|plain` (every `e2e:*` script calls it in place of its inline `electron-vite build`; `plain` forces `MAWS_HARNESS=0`), which restores `out/` from a per-commit cache on the runner's disk (`~/Library/Caches/maws-e2e-build/<sha>/<variant>/`, the run's `GITHUB_SHA`, four keys kept, a digest checked on every restore) when the e2e step sets `MAWS_E2E_BUILD_CACHE` and `MAWS_E2E_BUILD_KEY`, which only the macOS step does: a gate builds each variant once (two builds of 33 to 41 s instead of 26; a restore takes 1 s; `e2e:default`'s own `pnpm build` step is not cached; Decision Log 38). The explicit gate word `packaged` (never in a default set; `ci-gate.sh --gates packaged`) runs one job on `[self-hosted, macOS, ARM64]`: `xcode-select -p` then `xcrun swiftc --version` (the shim would otherwise raise an install dialog), `build:app` unsigned, `verify:fuses`, `e2e:packaged`, `e2e:supervisor:packaged`, `e2e:voice:packaged` (voice's packaged case alone, by `--grep packaged:` against `MAWS_E2E_EXECUTABLE`); the plan refuses `e2e:packaged`, `e2e:supervisor:packaged` and `e2e:voice:packaged` asked for as e2e groups.

## 8. Surprises & Discoveries

- node-pty 1.1.0 ships no Linux prebuild (`prebuilds/` holds darwin-arm64, darwin-x64 and win32 only), contrary to §3.3's note: on the runner its install script falls back to `node-gyp rebuild` (python3 and build-essential are on the `ubuntu-24.04` image). The postinstall design holds unchanged.
- The private repository's standard Linux runner has 2 cores, and its speed varies from run to run: the unit job took 11 to 18 minutes across the green runs (the suite alone 533 to 920 s), `static` 3.5 to 4.5 and `probes` about 1; the vitest summary reads 885 files and 12,636 tests. The unit job's 30-minute ceiling keeps a margin, but it is the job to watch as the suite grows (sharding it across two jobs is the move when it nears 25).
- `src/renderer/src/tools/agents/model/scheduled.test.ts` (`createdCrons and sessionCrons over e7-cron > lists the session-only jobs the engine resurrected on resume…`) depended on the machine's zone despite its header: it passed in America/Los_Angeles and failed in UTC and in Asia/Seoul (measured on the Mac with `TZ=`). On the runner, in UTC:

  ```
  AssertionError: expected [ '8d1a2582' ] to deeply equal [ '8d1a2582', '1040f3a5' ]
   ❯ src/renderer/src/tools/agents/model/scheduled.test.ts:46:79
  ```

  The recording (`e7-cron.jsonl`, its `e7_cron_setup` frame names `timezone: America/Los_Angeles`) created the one-shot `15 4 6 10 *` at 04:12 local, three minutes before its fire; read in UTC or Seoul its creation falls after that day's 04:15, so its fire moves a year on, past the nightly job's seven-day life. Fixed in the test at the architect's direction (671d6d84): the describe over the recording sets `process.env.TZ` to the recording's zone and restores it after, so the cases read the recording as it was made in any machine zone; passes on the Mac under UTC, Asia/Seoul and America/Los_Angeles.
- `test/support/git-env.test.ts` raced the runner's git once in three runs:

  ```
  Error: ENOENT: no such file or directory, open '/tmp/maws-git-oracle-qz307V/foreign/.git/objects/maintenance.lock'
   ❯ test/support/git-env.test.ts:29:23
  ```

  Its snapshot of the foreign repository listed the lock that the detached auto-maintenance `git commit` starts (git 2.47 and later) holds, and the maintenance dropped it before the read. - `src/renderer/src/sessions/resource.test.tsx` (`a focused switch across 20 exited sessions starts nothing`) overran the renderer project's 5 s in 2 of 3 runs on the 2-core runner (`Error: Test timed out in 5000ms.`): a whole-tree mount in a 5 s project. - The first e2e job (`side`, run 38661816432) proved the runner's Electron: under xvfb, with the apparmor restriction lifted and the app's sandbox on, 10 of its 12 cases passed. The failed job's HTML report and `test-results/` came down as the `e2e-side` artifact.
