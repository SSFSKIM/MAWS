# Gate offload: hardware-independent gates on GitHub Actions

Living spec (doperpowers:execspec), authored 2026-10-14 by the architect at the owner's decision after P3-B's M9: "start the GitHub Actions offload now as a small spec; the dedicated quiet Mac for timing gates at P3-F". Not a P3 child; tooling for every child's gates. Cites the P3 composite spec `docs/doperpowers/plans/2026-10-12-p3-co-work.md` Decision Log 54, 63 (the load rule for measured bounds, unchanged here) and 64 (this split). Branch `gate-offload`; the architect lands it through a master gate.

## 1. Purpose

One Mac carries three child executors, their workers, their reviewers and the owner's running MAWS, so every gate run raises the machine's load and every measured bound waits for the load to fall (two slots machine-wide, `waitload20.sh`, the marginal band of Decision Log 54 and 63; one child waited seven hours for a quiet minute). The gates split into two classes. Hardware-independent gates (typecheck, lint, the unit suite, the build and bundle guard, the protocol probes, most e2e groups) can run anywhere; they are most of the CPU minutes but none of the hardware dependence. Hardware-bound gates (measured bounds on Apple Silicon, macOS-only behaviour, the paid live runs) stay on the Mac. This spec moves the first class to GitHub Actions on Linux, behind one local script that an executor calls the way it calls `with-slot.sh` today, so the Mac's load comes from measured runs and the owner's app alone. The dedicated quiet Mac for the second class is P3-F's.

## 2. Constraints

- The repository is private (`SSFSKIM/MAWS`, Actions enabled, no workflow yet). Linux minutes bill at the plan's rate beyond the free allowance; the script runs only the gates asked for, so a child reruns the groups it touched, not the matrix.
- Children's branches are not pushed; each run pushes one sha to a `ci/<label>-<short>` ref and deletes it after (`--keep` to leave it).
- Timing and measured bounds never run on Actions: a runner's CPU and GPU-less renderer make a frame time or a loop latency noise, not a measurement. Decision Log 54 and 63 govern those runs locally, unchanged.
- No test is deleted, weakened or re-timed to pass on Linux. A test asserting a macOS fact (APFS case folding, `ps` or `zsh` job control, a Keychain, the packaged app) is guarded with `skipIf(process.platform !== 'darwin')` and one comment naming the fact; the guarded list is in this document and reported at the hand-back. A Linux failure that is a real defect is reported, not guarded.
- The package scripts stay the one source of truth for what a gate is: the workflow runs `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm test:probes`, `pnpm build` and `pnpm e2e:<group>` verbatim (under `xvfb-run -a` for e2e), so a gate means the same thing on the Mac and on the runner.
- Rules binding every milestone: absolute paths with `git -C` and `pnpm -C`; `pnpm_config_verify_deps_before_run=false`; before any local `pnpm test`, e2e or build `/tmp/maws-review/waitload20.sh && /tmp/maws-review/with-slot.sh <cmd>` (local runs here are typecheck, lint and targeted vitest files only; the suites run on Actions); never touch the owner's running MAWS, `dist`, the user-data directory or `~/.claude`; never stage `node_modules`, `spikes/gws-onboarding/`, `.playwright-cli/`; no attribution in commit messages; never amend or reset; commit as you go; the execution document is this file (the executor appends to Decision Log, Surprises and Outcomes; the architect owns the rest).

### 3.2 The workflow `.github/workflows/gate.yml`

Triggers: `push` on `ci/**` (the script's refs; the workflow file travels with the pushed tree, so a branch carrying the workflow tests itself before it lands), `push` on `master` (the `warm` job alone, Decision Log 26) and `workflow_dispatch` with the same `gates` input for a manual run. Input `gates`: a comma list over `static`, `unit`, `unit:darwin`, `probes`, `e2e:<group>`, …, read from the ref's last commit message trailer `Gates: …` for the push trigger (the script writes it onto an empty commit when the caller narrows the set) or defaulting to the whole class-1 set.

Jobs, each with `timeout-minutes: 30` under `concurrency: {group: gate-<ref>, cancel-in-progress: true}`; class 1a on the runner of §3.6, the e2e jobs on the lane the plan resolves, `unit:darwin` always on `[self-hosted, macOS, ARM64]`:

- `static`: `pnpm typecheck`, `pnpm lint`.
- `unit`: `pnpm build` (the bundle guard reads the engine-host chunk), then `pnpm test` with vitest's workers at the runner's cores; the timing projects keep their 30 s.
- `unit:darwin` (Decision Log 25): on the macOS runner, after the shared setup, `pnpm exec vitest run --maxWorkers=<cores> $(scripts/darwin-unit-files.sh)` over the files with §6's guards, found by the guard itself (`grep -rlE "platform !== 'darwin'"` over `src` and `test`), no build; in the macOS lane's default set, and by `Gates: unit:darwin` on either lane.
- `probes`: `pnpm test:probes`.
- `e2e`: a matrix over the requested groups, `fail-fast: false`; each job `xvfb-run -a --server-args="-screen 0 1920x1080x24" pnpm e2e:<group>` with `MAWS_E2E_QUIET=1`; Playwright's HTML report and `test-results/` uploaded as an artifact on failure (`if: failure()`), retention 7 days.

Shared setup (a composite action `.github/actions/setup` so the jobs do not repeat it), after `actions/checkout` at the pushed sha: `pnpm/action-setup` reading `packageManager`; `actions/setup-node` with Node 22; `pnpm install --frozen-lockfile` (whose postinstall fetches Electron into `~/.cache/electron`). On Linux the pnpm store (`cache: pnpm`) and the Electron download (`actions/cache` keyed by OS, architecture and Electron version) come from the Actions cache; the self-hosted macOS runner uses no Actions cache, its own disk keeping both between jobs (Decision Log 26). Caches are readable from the saving branch and the default branch only, so a push to master runs the job `warm` alone (`ubuntu-24.04`, checkout and setup, nothing else): every `ci/` ref then restores master's caches exactly and the Linux jobs skip their saves, a tree with a changed lockfile saving its own until it lands. For Linux e2e jobs the setup adds `apt-get install xvfb fonts-noto-cjk` (Korean text in the renderer) and the Inter and JetBrains Mono faces and zsh, and, for the groups that render documents through LibreOffice, `libreoffice-writer libreoffice-impress` (B's DOCX-to-PDF case, C's render-and-compare); Electron's sandbox on the runner: the apparmor restriction on unprivileged user namespaces lifted with `sysctl kernel.apparmor_restrict_unprivileged_userns=0` (the documented runner fix), never `--no-sandbox` in the app. Each gate job writes its counts to `$GITHUB_STEP_SUMMARY`.

### 3.3 The Linux adaptations

- `postinstall` is `chmod +x node_modules/node-pty/prebuilds/darwin-arm64/spawn-helper && install-electron`, which fails where the darwin prebuild is absent: it becomes `node scripts/postinstall.mjs`, chmod of the darwin spawn helper only when it exists (node-pty 1.1.0 ships Linux prebuilds), then `install-electron`; behaviour on the Mac unchanged.
- Tests asserting macOS facts gain the guard of §2 with the fact named; the list lives in §6 of this document.
- Node 22.13 or later is required for `node:sqlite` unflagged (the Mac runs 22.23); the workflow pins the Node major to 22 and `engines` stays `>=22.12` unless M1 finds the store tests need the bump recorded.

### 3.4 The local script `scripts/ci-gate.sh`

`scripts/ci-gate.sh <worktree-or-sha> [--gates static,unit,probes,e2e:side,…] [--label <name>] [--keep]`. It resolves the sha (a worktree path's `HEAD`, or a sha), pushes `<sha>:refs/heads/ci/<label>-<short>` (force, since a child reruns on a moved tree), finds the run (`gh -R SSFSKIM/MAWS run list --branch ci/<label>-<short> --json databaseId,headSha`, retried until the run for the sha exists), `gh run watch <id> --exit-status`, prints `gh run view <id>` with each job's conclusion, downloads failed jobs' artifacts to `/tmp/maws-review/gates/ci-<short>/`, writes the whole transcript to `/tmp/maws-review/gates/ci-<short>.log`, deletes the `ci/` ref unless `--keep`, and exits with the run's status. It passes `-R` to every `gh` call so it works from any directory. A narrowed `--gates` writes the trailer of §3.2 onto an empty commit on top of the sha before pushing, so the pushed tree is the tested tree plus one message.

### 3.5 What changes for a child

Its brief says: class-1 gates through `scripts/ci-gate.sh <worktree> --gates <what you touched>`; class-2 gates locally under the load rule as today; a Linux-only failure is reported to the architect, never guarded by the child. The P3 spec's Decision Log 64 records the split; the P2 and P3 briefs in flight keep their local gates until their executors are told.

The brief's wording as landed (Decision Log 13, 16):

- Class 1a through the script, from any directory: `scripts/ci-gate.sh <worktree>` runs static, unit and probes (12 to 18 minutes of wall clock, the unit job's range on the 2-core runner); `--gates static`, `--gates unit` or `--gates probes` narrows it to what you touched. The script prints each job's conclusion and the run's URL, keeps the transcript in `/tmp/maws-review/gates/ci-<short>.log` and exits 0 only when the run is green.
- Class 1b, the e2e groups, are macOS work. Until a macOS runner is registered, run them on the Mac under the load rule as today; the Linux lane takes only the groups green there (`--gates e2e:library`, …, the list in §3.1). Once the runner exists: `scripts/ci-gate.sh <worktree> --gates e2e:<group> --runner macos`, and a failed group's HTML report and `test-results/` come down to `/tmp/maws-review/gates/ci-<short>/`.
- The unit cases §6 guards run on the macOS runner as `unit:darwin` (Decision Log 25); when your change touches one of those files, or before a landing, run `scripts/ci-gate.sh <worktree> --gates unit:darwin --runner macos` (under a minute on the mini since Decision Log 26, fifteen seconds of it tests). The local fallback, for a mini outage: `/tmp/maws-review/with-slot.sh pnpm -C <worktree> exec vitest run $(<worktree>/scripts/darwin-unit-files.sh <worktree>)`.
- On this Mac, unit and DOM vitest runs on named files, typecheck and eslint take no load wait (Decision Log 24); they hold one of the two machine-wide slots (`/tmp/maws-review/with-slot.sh`), one at a time, and a timing-based case that fails under load is rerun alone once before it counts. Electron e2e groups, `pnpm build` and every measured bound wait for a 1-minute load under 20 (`/tmp/maws-review/waitload20.sh &&` before the slot; the P3 spec's Decision Log 54).
- A failure on the runner that does not reproduce on the Mac is reported to the architect with the run URL, never guarded by the child.
- The pushed tree must carry the workflow: merge master at or after the landing (2fefbd24) before the first run. The script pushes only `ci/<label>-<short>` refs and removes them; never push a branch for it.

### 3.6 The macOS runner (Decision Log 13 and 14)

The owner's choice (Decision Log 18): the e2e lane stays on the MacBook until the Mac mini's sessions are freed, then the mini is registered as below.

The workflow has two lanes, and on a push to master the `warm` job alone (`ubuntu-24.04`; `plan` and everything behind it skip there; Decision Log 26). Class 1a (`plan`, `static`, `unit`, `probes`) runs on `ubuntu-24.04`, or on the Mac when the repository variable `GATE_RUNNER` is `macos`. The e2e jobs take the lane the plan resolves: the run's `Runner:` trailer (`ci-gate.sh --runner linux|macos`, or `MAWS_GATE_RUNNER` in the caller's environment) or the dispatch input `runner`, else the variable `GATE_E2E_RUNNER`, else `GATE_RUNNER`, else `linux`. The macOS lane is `runs-on: [self-hosted, macOS, ARM64]`; on it the default set adds `unit:darwin` and every class-1b group (`unit:darwin` runs on `[self-hosted, macOS, ARM64]` whatever the lane, also when `Gates:` names it on a Linux lane; the lane governs the e2e jobs alone), and every Linux-only step (apt packages, xvfb, the apparmor sysctl, `/private/tmp`) is skipped by `runner.os`, and so is every Actions cache: the mini's disk keeps its pnpm store and Electron download between jobs (Decision Log 26). The recommended setting once the Mac mini is registered: `GATE_E2E_RUNNER=macos` (e2e on the Mac, class 1a still in parallel on Linux); `GATE_RUNNER=macos` moves class 1a there too and spends no Linux minutes, at the price of one job at a time.

Setting up the Mac mini (about ten minutes; the owner's, since registering a runner is a repository setting):

1. A user account for the runner, logged in at boot (System Settings › Users & Groups › Automatically log in as), with the screen lock off. Electron's windows need that user's GUI session: the runner runs as a LaunchAgent in it, never as a LaunchDaemon.
2. Keep it awake on power: `sudo pmset -c sleep 0 disksleep 0 displaysleep 0` (or run the service under `caffeinate -dims`).
3. In that account: the Xcode command line tools (`xcode-select --install`, for git and the compilers), Homebrew, then `brew install node` and `brew install --cask libreoffice` (P3-B's and P3-C's groups convert through it). The `plan` job runs `node` from the runner's PATH; the gate jobs get Node 22 from `setup-node` and pnpm from `pnpm/action-setup`, as on Linux.
4. Register: GitHub › SSFSKIM/MAWS › Settings › Actions › Runners › New self-hosted runner › macOS ARM64, and run the shown `config.sh --url https://github.com/SSFSKIM/MAWS --token …` in `~/actions-runner` (the labels `self-hosted`, `macOS`, `ARM64` are the defaults). Before `./svc.sh install && ./svc.sh start`, run `./env.sh` from a login shell so the service's `.path` carries `/opt/homebrew/bin`.
5. Set the repository variable (Settings › Secrets and variables › Actions › Variables): `GATE_E2E_RUNNER` = `macos`.
6. First run: `scripts/ci-gate.sh <worktree> --gates e2e:library --runner macos`, then the whole class-1b set once, watching the Mac for a first-run prompt (a Keychain access, a notifications permission) to allow by hand; a runner runs one job at a time, so the matrix queues on it (expect about an hour for every group).

The mini's facts (Decision Log 29): its languages are Korean (AppleLanguages ko-KR, AppleLocale ko_KR) and the runner's environment has no LANG, so every e2e launch passes `--lang=en-US` and the test process sets `LC_MESSAGES=en_US.UTF-8` in playwright.config.ts (the app and the specs format in en-US on any machine; the owner's Korean UI is untouched outside e2e). The app's first e2e window is 1280×820 pt at 2x on every machine (`DEFAULT_WINDOW_SIZE` in src/main/window-state.ts, not window.ts's 1440×900; side and library set 1440×900 themselves); the virtual display paces frames at about 54 Hz (18.4 ms intervals), so a frame budget is class 2. An e2e app launches in the background (shown inactive, quiet) as on the MacBook; `MAWS_E2E_FOREGROUND=1` (the app activated, its window key) exists in the app but the gate does not set it, because to-human.spec.ts:29 and document.spec.ts:436 fail with the window key (the tracker's row); the launch is quiet only while a windowed app such as Terminal is frontmost, since once Finder is frontmost (the state after any front app quits) every e2e instance takes front on launch (Decision Log 34). A system alert frontmost holds key focus from every app; the runner's pre-job check (ci-kit #9) fails such a job within about 13 s with "a system dialog (UserNotificationCenter) holds focus on the mini".

Class 1a runs green on `ubuntu-24.04` (M1's [38663019400](https://github.com/SSFSKIM/MAWS/actions/runs/38663019400)); the Linux lane's whole class 1, class 1a with the five e2e groups green there, ran green through the script in 17 minutes 19 seconds of wall clock ([38667569129](https://github.com/SSFSKIM/MAWS/actions/runs/38667569129)); the script showed green narrowed to `static` ([38668889607](https://github.com/SSFSKIM/MAWS/actions/runs/38668889607)) and red on a scratch tree with a failing library case, its report downloaded and its ref removed ([38668891701](https://github.com/SSFSKIM/MAWS/actions/runs/38668891701)). The macOS lane is wired and documented (§3.6) and waits on a registered runner.

**Against the purpose.** §1 wanted the Mac's load to come from measured runs and the owner's app alone. Class 1a, the CPU bulk (typecheck, lint, the 885-file unit suite, the build, the probes), now leaves the Mac for about 26 billed Linux minutes a run (plan 1, static 5, probes 2, unit 18 in the slowest green run); the whole Linux-lane class 1 is 49 billed minutes (44 raw). Electron e2e did not move: on Linux 17 of its 22 groups fail or flake on platform facts (§3.1's table), so it stays on the Mac until the macOS runner exists, and that runner is the piece that finishes §1. The unit cases §6 guards are a Mac gate now, with the exact command in §3.5.

**Defects the runner found, fixed in their tests.** Two zone dependences over the same recording (the unit e7-cron case and its e2e twin), a race between a git fixture and git's detached auto-maintenance, and a load-sensitive renderer suite in a 5 s project; one timing budget is a tracker row (§8).

**What I would do differently.** Discovery would have been cheaper with the debug launcher (a screenshot and the window and focus state at each cleanup) from the first e2e run: the two facts that explained most of the geometry and focus failures, the in-window menu bar and the WM-less focus, showed up only in the fourth e2e run, after about 200 job-minutes of failing groups. The whole spec spent about 620 billed Linux minutes, two thirds of it on e2e discovery.
