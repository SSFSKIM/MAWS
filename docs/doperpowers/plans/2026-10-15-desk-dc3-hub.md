## Constraints that bind every milestone

- **The composite has one writer**, the session that dispatched this plan,
  and it commits in this same worktree: commit by explicit paths, never
  `git add -A`, and never rewrite history. The controller records this
  plan's decisions in its own Decision Log below and messages that session
  at M1's end with the Interfaces drafts (DX2, DX3, the DX4 envelope, the
  DX6 shapes, DX7, and DX1's vectors), at each later milestone's end with
  whatever extended them, and with any decision that touches a contract; it
  does not edit the composite. G1's "reviewed" is that session's: it folds
  the drafts into the composite's Interfaces and has them reviewed, and
  DC4 and DC5 start on what it folded.
- **Where the code lives.** `apps/desk-hub` in MAWS's pnpm workspace:
  `pnpm-workspace.yaml` gains `packages: ['apps/*']` (DC5 adds
  `apps/desk-web` under the same glob). The protocol module,
  `apps/desk-hub/src/protocol/`, is exported for the web app and the fake
  machine and stays runtime-neutral: WebCrypto and plain TypeScript, no
  Workers, Node, or DOM API, so a browser imports it as it stands.
- **MAWS's gates cover the app.** The class-1a gates run through
  `scripts/ci-gate.sh <worktree>` (static, unit, probes; 12 to 18 minutes;
  `docs/doperpowers/plans/2026-10-14-gate-offload.md` §3.5), and the
  workflow runs the package scripts `pnpm typecheck`, `pnpm lint`, `pnpm
  test`, and `pnpm build` verbatim, so those root scripts must reach the
  app; the unit job appends `--maxWorkers=N` to `pnpm test`, and whatever
  composes the app's tests into it must keep that working. A failure on the
  runner that does not reproduce on the Mac goes to the composite's writer
  with the run URL, never guarded here. Local heavy runs follow MAWS's load
  rule (`/tmp/maws-review/waitload20.sh && /tmp/maws-review/with-slot.sh …`).
  Nothing in the Electron app changes beyond what admitting the workspace
  app needs (the workspace file, root scripts, an ESLint block, the
  lockfile); MAWS's charter contracts (X1–X8, D-1–D-20) govern that app and
  must stay unbroken.
- **Runtime.** Cloudflare Workers and Durable Objects with SQLite storage
  (`new_sqlite_classes`), wrangler pinned in the app's devDependencies.
  `@cloudflare/vitest-pool-workers` 0.23.0 (current) peers vitest `^4.1.0`
  while MAWS runs vitest 5: the app either keeps its own vitest 4 inside
  the workspace (`nodeLinker: hoisted` then places it under the app) or
  drives Miniflare from MAWS's vitest; M1 decides and records why.
  `pnpm-workspace.yaml`'s `allowBuilds` admits an install script only by
  name; an entry wrangler's tree needs is recorded with its reason, as the
  file's comments do.
- **The hub never holds the org key** and never verifies, alters, or
  re-serializes what a code covers: an event is stored exactly as received
  (a `hub/` event gains only `writer`, `seq`, and `ts`), the project offset
  travels beside it (DX1), and comparisons of payloads use the canonical
  form. The hub enforces what it can without the key: a machine's writer
  prefix, one payload per `(writer, seq)`, and a web `human`'s `member`
  matching the signed-in member.
- **Frames.** Every frame in either direction is at most 1 MiB; a larger
  payload (a snapshot, a large transcript row) is split into numbered parts
  (§2).
- **Nothing that stores or relays project data is reachable without
  Access.** Before M5, only a throwaway probe Worker holding no data may be
  deployed to the owner's account, and it is deleted after. Worker secrets
  go in with `wrangler secret put` and are never committed or echoed; a
  credential the owner stores is read only inside the command that uses it,
  as `"$(cat ~/.config/claude-secrets/<KEY>)"`.
- **Owner actions** — anything in Cloudflare's dashboard or Zero Trust the
  logged-in wrangler cannot do (an API token with Access scopes, an Access
  application or policy, a team setting) — go to the composite's writer in
  a checkpoint message that names the exact steps, sent as early as the
  need is known; the controller continues with what does not depend on
  them.
- **Fixtures.** No real session of the owner's is committed. A recorded
  session is recorded from a throwaway session (a trivial prompt that
  starts two subagents, raises one permission prompt and one
  AskUserQuestion; haiku or sonnet) under a throwaway `CLAUDE_CONFIG_DIR`,
  with `HOME` and `SMINOS_HOME` temporary, or synthesized. Never modify
  `~/.claude/settings.json`, `~/.claude.json`, the plugin store, or the
  real `~/.claude/sminos`; stop every `--bg` job started.
- No `Co-Authored-By` trailer.

## Plan of Work

### M1 — The protocols and the hub's skeleton

**At its end:** `apps/desk-hub` is a workspace app whose typecheck, lint,
and tests run in the gate and pass through `scripts/ci-gate.sh`; a Worker
routes to three Durable Object classes with SQLite storage — `Project`
(one per project, named by org and project id), `Machine` (one per
enrolled machine), and `Registry` (one per org); the protocol module holds
the types of DX2, DX3, the DX4 envelope, the DX6 shapes, and DX7, and
DX1's canonicalization and code on WebCrypto, pinned by vectors; the
Interfaces drafts are sent to the composite's writer.

**Decisions:**
- *Transport (DX2's, fixing the transport half of §8 unknown 2).* A machine
  holds one SSE stream down (`GET`), opened outbound and held by its
  `Machine` object, and sends batched frames up by `POST`, each frame
  addressed to a project, which the Worker routes to that `Project`
  object. Browsers hold WebSockets with the Hibernation API: to a
  `Project` for a project's view, to the `Registry` for the grid. Rejected:
  WebSockets for machines, which the stdlib-Python daemon (DC4) would need
  a hand-written RFC 6455 client for. The cost the composite records (an
  object holding an open stream never hibernates and is billed while it is
  open) falls on `Machine` objects only. The SSE stream carries a
  heartbeat often enough that no proxy on the path closes it as idle.
- *Topology.* A `Project` reaches a machine only through that machine's
  `Machine` object (Durable Object RPC), which writes to the stream or
  answers "offline" at once. *Liveness is a lease, not a close callback*
  (plan review, 2026-10-15): Cloudflare guarantees no shutdown callback,
  and an object can restart without running cleanup. A `Project` holds a
  machine online only while that machine's lease is fresh. The `Machine`
  object renews the lease on its stream's heartbeat, sending it to each
  project the machine serves. Every lease carries the stream's connection
  generation, so a late close or renewal from an older stream is ignored.
  When a lease lapses, the machine is marked offline, its subscriptions
  end, and its forwarded RPCs without a result become `uncertain` (DX6).
  The lapse is found by an alarm or by a check on read, whichever the
  builder prefers. An explicit close from the current generation ends the
  lease at once. `Project` objects report their summary (machines online, sessions
  working and waiting) to the `Registry` on change, and the `Registry`
  streams it to the grid. Rejected: D1 for the registry (a second storage
  system for a handful of rows), and a socket per project from the grid.
- *Identity at the edge.* Humans arrive with Access's
  `Cf-Access-Jwt-Assertion`, machines with a service token that Access
  turns into an assertion whose `common_name` is the token's client id.
  The Worker verifies the assertion on every request (signature against
  the team's certificate endpoint, `aud`, expiry) and maps it to a member
  or a machine through the `Registry`; nothing behind the Worker trusts a
  header the Worker did not verify. Access's service-auth policy admits
  any service token in the account (M5), so the `Registry` refuses a
  `common_name` it never enrolled: an admitted token is not, by being
  admitted, a machine. Locally, a stand-in for Access (M2)
  signs assertions with a test key served from a stub certificate
  endpoint, and the Worker verifies them through the same code: no bypass
  switch exists for a deployed config to leave on. The org is
  created from deploy configuration (the owner's identity as admin), never
  by whoever signs in first; member ids are stable random ids, since
  `hub/<member-id>` is written into logs for good.
- *Codes.* DX1's canonical JSON is RFC 8785 (JCS). Each authenticated
  shape has its own domain string (`smns-hub-log-v1` for log events, per
  DX1; DX6's RPCs and DX4's `raised`, `settled`, and `delivery` get their
  own), so a code for one shape never verifies as another. The code
  covers the nonce (plan review, 2026-10-15; the composite's DX1): the
  bytes it covers are the domain prefix, then the JCS of the shape with
  `mac` reduced to `{"nonce": …}`, so only `mac.value` is left out, and
  for a `hub/` writer `writer`, `seq`, and `ts` too. Otherwise a hub could
  re-sequence a web `human` under a fresh nonce and pass a daemon's
  seen-nonce check. The same rule holds for every authenticated shape. The vectors
  (`apps/desk-hub/src/protocol/vectors/`) give, for each case, the org key,
  the project id, the input, the canonical bytes, and the code: an ASCII
  `say`; a `message` with Korean text, an emoji, and control characters; a
  `hub/` `human` (whose code leaves out `writer`, `seq`, `ts`); a nested
  object; an RPC; a `raised` and a `settled`. They also include negative
  vectors that must fail: a changed nonce, a changed field, and a `hub/`
  event moved to another project. They are written into DX1's
  Interfaces subsection as text, which DC4 tests its Python against.
- *The log handshake (DX2).* Per project, each side sends `{writer: max
  seq}`; the hub streams to the machine every writer's missing suffix, and
  the machine uploads the suffix of its own writers only (`<machine>/…`,
  sminos's `writer_id`). A `legacy/` feed (pre-`.smns` chats, which
  sminos's `_import_chat` names by a seat id, not a machine) is accepted
  only from the project's designated archive machine; it is frozen, so the
  one-payload rule keeps it intact. A machine syncing a project id the
  registry does not know registers it (name from its `.smns`); any enrolled
  machine of the org may.

**Touches:** `pnpm-workspace.yaml`, root `package.json` scripts,
`eslint.config.js` (a block for the app), `pnpm-lock.yaml`,
`apps/desk-hub/**`.

**Interfaces:** produces the drafts of DX2, DX3, the DX4 envelope, the DX6
shapes (the RPC set of §5 with arguments, results, and errors), DX7 (the
registry's records, enrollment, revocation, the archive designation, push
subscriptions), and DX1's vectors.

**Does not touch:** the log's storage and sync, routing, push, deployment.

**Proves:** DC3.G1. Before writing DX2, a throwaway probe Worker deployed
to the owner's account (no data, deleted after; the logged-in wrangler
suffices) shows an SSE stream held by a Durable Object for at least ten
minutes with heartbeats, a write reaching it from another object's RPC,
the stream's close seen by the object, and a hibernating WebSocket woken
by a message; the findings go into this plan's Surprises. Tests pin the
vectors and the assertion verifier (valid, wrong `aud`, expired, unknown
key, a machine's `common_name`).

### M2 — Enrollment, the local stand-in for Access, and the log plane

**At its end:** on the local runtime, a machine enrolls and its client
speaking DX2 syncs a project's log in and out across reconnects and
object restarts with no loss and no duplicates; a browser client resumes
after its offset; a web `human` enters the `hub/<member-id>` feed;
refusals are reported. DC4's daemon can develop against this.

**Decisions:**
- *Enrollment (DX7), as §6 has it.* The browser asks the hub for a
  one-time token (short-lived, single use) and builds the enrollment code
  itself — hub URL, token, machine name, org key — so the hub never sees
  the key. Redeeming the token, on a path Access does not guard, claims
  the machine name (refused when enrolled in the org, with how to pick
  another) and mints the machine's own Access service token through
  Cloudflare's API, returning its client id and secret once; the registry
  maps the client id to the machine. Revoking a machine deletes its
  service token and its record.
  *Enrollment recovers* (plan review, 2026-10-15): it is a durable state
  machine in the `Registry`. Before the API is called, the name is
  reserved and the intent to mint is recorded, and the service token is
  named `desk-<org>-<machine>` so an orphan can be found by name. The
  enrollment stays `pending` until the machine's first authenticated
  connection confirms it. A second redemption of the same token while it
  is pending rotates the credential: the minted token is deleted, and a
  fresh one is minted and returned. So a redeem response lost on the way
  back is recovered by redeeming again. A pending enrollment that expires
  deletes its token and releases the name. A token used for one machine
  can never enroll another. The registry also records each project's
  designated archive machine, which DX2's handshake tells that machine.
- *The local stand-in for Access* is a small proxy in front of `wrangler
  dev` that does what Access and Cloudflare's service-token API do for
  the hub: it admits test identities and the service tokens it minted,
  adds the signed assertion, and serves the certificate endpoint. The
  Worker reaches the Cloudflare API and the certificates through
  configured URLs, which the deployed config points at Cloudflare, so the
  same Worker code runs in both. DC4 and DC5 develop against it.

**Decisions on the log:** a `Project` stores each event once, keyed by `(writer,
seq)`, with an offset in arrival order; a gap (a `seq` not one past the
last) asks the uploader to resend from the gap; an event at an existing
`(writer, seq)` whose canonical form differs is refused, reported to the
uploading connection, and recorded in the project's audit record, where a
browser can see it; an event whose writer the connection may not write is
refused the same way. A web `human` is accepted only when its `member` is
the signed-in member's id; the hub assigns `writer`, `seq`, and `ts`.
New events fan out at once to the project's browsers and, through their
`Machine` objects, to every connected machine syncing the project.

**Touches:** `apps/desk-hub/**`.

**Interfaces:** extends DX2 (handshake, resend, refusal frames), DX3
(resume by offset, the frame carrying `{offset, event}`), and DX7
(enrollment, revocation, archive designation) in place, with how to run
the local hub and its stand-in; sent at the end.

**Does not touch:** the session plane.

**Proves:** DC3.G2 on the local runtime, and enrollment: a name already
enrolled is refused, a confirmed token cannot be redeemed again, a revoked
machine's connection is refused. Tests also pin, for recovery: two
redemptions of one token at once; a failure from the service-token API;
a mint whose response is lost; a redeem whose response is lost; a used
token offered for a different machine; a pending enrollment expiring.
Tests pin: two machines and a
`hub/` writer interleaving, then every per-writer count and last seq equal
on all sides; a dropped connection mid-suffix; an object restart between
two uploads; a forged writer refused; a conflicting payload refused and
reported; a browser resuming at offset N receives exactly the events after
N. The same run against the deployment is M5's.

### M3 — The session plane: routing, requests, outcomes, push

**At its end:** RPCs reach the named machine and return `done` or
`failed`; session subscriptions relay; the pending set, presence, the
audit record, and delivery outcomes behave as DX4 and DX6 say; Web Push
fires as §4 says.

**Decisions:**
- *RPCs.* A `Project` records each RPC by its nonce (forwarded, `done`,
  `failed`, `uncertain`, with the result); an RPC to a machine without a
  stream fails at once with "machine offline"; an RPC older than 60
  seconds is not forwarded; when a machine's lease lapses or its current
  stream closes (M1, Topology), its forwarded RPCs without a result become
  `uncertain` and resolve from the results
  the daemon republishes on reconnect, which the hub acknowledges; a
  browser retry with a known nonce is answered from the record, or
  forwarded again when the machine is back (the daemon's ledger answers it
  without executing twice, DX6).
- *Subscriptions.* Each browser subscription is its own `sub` at the
  machine (DX4 numbers `n` per `sub`); the hub relays and keeps at most a
  reconnect buffer; a browser's disconnect unsubscribes its subs at the
  machine; a machine's disconnect ends its subs at the browsers, which
  subscribe again when it returns. Older rows on request travel the same
  way. If G6 shows per-browser subs dominating the cost, a shared stream
  is recorded as the next step, not built here.
- *State that must survive eviction.* Presence, the pending set, delivery
  outcomes (the latest per event and recipient), the RPC records, and the
  audit record live in the object's storage, not only in memory (§2); a
  reconnect's republish reconciles them, and a request the daemon no
  longer republishes is dropped.
- *Hibernation-safe routing* (plan review, 2026-10-15). Each browser
  socket's identity (its member), its visibility, and its subscription ids
  are kept in the socket's attachment (`serializeAttachment`); what does
  not fit goes in storage. A `Project` woken from hibernation rebuilds its
  routes from these before it handles anything, so the routes survive a
  real hibernation and not only an eviction.
- *Contract items folded into the composite since dispatch* (2026-10-15).
  The protocol module, routing, and M4's fake machine follow the
  composite's current DX3, DX4, and DX6 text:
  - DX6 results from DC2's M2 (744eae81). `interrupt` answers
    `{turnId, stopped, running}`. `model` takes an id, a family alias, or
    `"default"`, and answers `{model, effort}` in force. A steer with no
    turn running fails with `idle`. `compact` answers `{at}`, and its
    outcome follows as compact events.
  - DX3 `diff {sub}` (05870451) is answered as a DX4 `diff` on that sub.
    Main-transcript subs only, computed on request, never pushed.
  - DX4 `usage {context: {tokens, window, percent}, cost}` (d349a87a) is
    sent on main-transcript subs after each main turn. The snapshot gains
    `usage`: null without a bridge or before the first one, absent on a
    subagent's sub.
  - Pending-request facts from DC2's M3 (c0fb2ccd, 8f7e09d3):
    - Request ids are opaque: `toolu_…` or `request-…`.
    - `by: "terminal"` and `by: "bridge"` are reserved.
    - A decision after another has won gets a 409 naming the winner;
      one within 200 ms of a background deadline gets 409
      `{terminalOnly: true}`.
    - Async questions are raised with `async: true`, never denied, and
      settle `answered` or `withdrawn`.
  - The snapshot's streaming entry is `{turnId, agentId, step, model?,
    upTo, blocks: [{index, kind, text, upTo, id?, name?}]}`. The
    message-level `upTo` is the watermark, and a block's own `upTo` is
    informational. `kind` ∈ `text | thinking | tool`. A row that no
    `block-row` named settles nothing.
- *The audit record* is written from `settled` — the side the bridge says
  won, who answered, and when — never from the web's attempt.
- *Web Push.* VAPID (ES256) and RFC 8291 payload encryption on WebCrypto,
  checked against RFC 8291's worked example. Browsers report their
  project's visibility over their socket; a raised question or permission
  prompt, or a `<message>`, pushes once to each subscribed device of every
  member with no visible browser on the project, and to none when one is
  visible. The payload carries only what points to a card (project,
  session alias, kind, request or event id): the service worker has no org
  key (§4). A push service's 404 or 410 deletes the subscription.

**Touches:** `apps/desk-hub/**`.

**Interfaces:** extends DX2, DX3, DX4's envelope, DX6, and DX7 (push
subscriptions, the VAPID public key) in place; sent at the end.

**Does not touch:** deployment, the fake machine's replay.

**Proves:** DC3.G3 on the local runtime, each clause of G3 a test,
including presence and the pending set surviving an object's eviction
while sockets stay open. Also tested: the Machine object terminated after
forwarding an RPC, with the daemon kept from reconnecting, after which
presence goes offline, subscriptions end, and the RPC becomes `uncertain`
within the lease; a renewal or close from an older generation ignored;
after a real hibernation, an established subscription keeps receiving
frames with correct `n`, and a visible browser still suppresses the
push. Also: once a machine's lease has lapsed, the hub never hands a
browser that machine's stored session presence as current, neither on
connect nor in `machines`: the machine shows offline and its sessions'
presence is null (DX8), and a test pins it. Stored presence itself never
expires (M2 builds it per machine and session).

### M4 — The fake machine

**At its end:** a tool — a library the web children's tests import, and a
command — replays a recorded session through DX2 under DX4's semantics
with the org key, against the local runtime or a deployment, so DC5 and
DC6 build and test against the real protocol without a Mac.

**Decisions:** the recording holds a transcript's JSONL, its two
subagents' transcripts and `meta.json`, a presence timeline, pending
requests with their settlements, and delivery outcomes, recorded from a
throwaway session (Constraints); stream chunks come from DC2's `sminos
watch` output when that has landed, and are otherwise synthesized from the
recorded text, so the format admits both. The fake machine answers RPCs
from a script with its own nonce ledger, which claims each nonce before
the effect and records the outcome before the result as DX6 has it. It
can drop its connection on command, can crash after an effect and before
recording its outcome, and can deliver a chunk while a snapshot is being
built, which DX4's watermark rule must absorb.

**Touches:** `apps/desk-hub/**` (the tool under the app, its recording
beside it).

**Interfaces:** consumes everything M1–M3 produced; produces the fake
machine's API, described for DC5 and DC6 in the message at the end.

**Proves:** DC3.G5: replaying the recording into a project with a browser
client subscribed reproduces the transcript's rows, both subagents, the
requests and their settlements, and the outcomes; the snapshot race ends
with no gap and no duplicated text; a crash after an RPC's effect and
before its outcome is recorded, then a retry with the same nonce,
produces no second effect.

### M5 — Deployed behind Access, enrollment, the measured run

**At its end:** the hub runs in the owner's Cloudflare account behind
Access; enrollment works; the fake machine runs against the deployment;
the throughput is measured and the threshold recorded.

**Decisions:**
- *Access, as Cloudflare documents it* (plan review, 2026-10-15). The
  application is hostname-level and self-hosted, on the Worker's
  `workers.dev` host (`<worker>.<sub>.workers.dev`, the form the docs show
  as an application domain). It is not the Worker-level Access toggle,
  which refuses WebSocket upgrades with a 403. Its policies: Allow for the
  owner's identity; Service Auth with "Any Access Service Token" (the
  hub's own token can mint service tokens but cannot edit policies, so
  the `Registry` refuses client ids it never enrolled, M1); and Bypass on
  the enrollment-redeem path alone, which the one-time token guards. It is
  created by script with `CF_ACCESS_SETUP_TOKEN` (Decision Log). The
  Worker's own Cloudflare API token, which mints and deletes machines'
  service tokens, is scoped to service tokens and nothing else
  (`CF_DESK_HUB_SERVICE_TOKENS`).
- *The admission probe.* Once Access exists, a deployed probe checks five
  cases: a signed-in browser's WebSocket upgrades to a `Project` and to the
  `Registry`; a freshly minted machine token is admitted; a token minted
  but never enrolled is refused by the Worker; an unauthenticated request
  is refused by Access; and the redeem path is reachable without Access.
- *Enrollment for real.* M2's enrollment, pointed at Cloudflare's API and
  certificates instead of the stand-in, enrolls a machine through Access.
- *The measured run (G6).* Against the deployment: three fake machines
  each posting a batch of chunks every 100 ms into one project, several
  browsers subscribed. The rate rises until p95 latency from a machine's
  post to a browser's receipt passes one second or the object errors; the
  report gives chunks per second per object, the cost of fanning out per
  subscriber, CPU time from the account's analytics where available, and
  the threshold at which the session plane moves to one object per
  session (§8 unknown 3), set with margin below the measured limit.

**Touches:** `apps/desk-hub/**` (wrangler config, deploy notes), this
plan.

**Proves:** DC3.G4 and G6, and G2 against the deployment: a redeploy in
the middle of a fake machine's sync loses and duplicates nothing. The
admission probe's five cases are part of G4's acceptance.
