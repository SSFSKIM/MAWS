**Decisions:**

- *DX8* is copied from `rs/app/slots.ts` and `rs/transcript/shell.tsx`

### M2 — The org key and enrollment

**At its end:** the org key derives in the browser from the owner's

### M3 — The conversation and its actions

**At its end:** the group chat and direct channels draw a project's log
as §4 says, and every action of §5 the web offers is wired: send, steer,
interrupt, model, effort, compact, answering a question, allowing or
denying, spawn, retire, resume.

**Decisions:**
- *The group chat:* messages, questions (answerable in place), permission
  prompts while pending (decidable in place), lifecycle as system lines,
  what humans posted; agent-to-agent traffic folded into one row per run,
  expandable; posting follows `sminos say`'s grammar (untagged records,
  `@alias` delivers, `@all` wakes every live member).
- *A direct channel:* one session's exchange with the human, the working
  record between folded (the unfolded transcript is DC6's); an ended
  session keeps its history and offers Resume; a message the bridge
  submitted as the human's words is drawn as the human's.
- *Request cards* reuse MAWS's request-card variants behind a copied card
  that answers through DX6 with the digest of exactly what it drew; a
  request the hub marks `terminal_only` is drawn as waiting in the
  terminal, without Allow or Deny; a background subagent's window is
  shown while it is open.
- *Capabilities:* the §5 table decides what is drawn disabled and why, from
  presence (bridged, `--bg` seat without a bridge, terminal without a
  bridge, machine offline).
- *RPC states:* `forwarded`, `done`, `failed`, and `uncertain` drawn as
  such; a retry of an `uncertain` RPC reuses its nonce.
- *Delivery:* a send shows its DX4 delivery outcome per recipient,
  including after a reload.
- *Offline:* a machine whose lease lapsed shows its sessions' presence and
  depth as unavailable while the conversation stays.

**Proves:** DC5.G2 against DC3's fake machine: each clause of G2 an
end-to-end test in a browser, including an event whose code fails not
being drawn and a reload keeping delivery outcomes.

### DX8 — The web shell's slots (draft for the composite)

Owner DC5, written at M1 (DC5.G1); binds DC6. The reference is the code under
`apps/desk-web/src/shell/` (`slots.ts`, `slot-fallbacks.tsx`,
`session-plane.ts`, `sessions.ts`, `layout.ts`): where this text and those
types ever differ, the types decide and the text is corrected. A later
change is a Decision Log entry that flags DC6.

**Slots** (`slots.ts`, copied from MAWS's `src/renderer/src/app/slots.ts`).
`registerSlot(name, component)` returns its unregistration and the last
registration wins; `useSlot(name)` gives the registered component or the
shell's fallback (a quiet note of what will be there); `resetSlots()` for
tests. DC6 registers both slots from one `connectDepth()` called once from
`apps/desk-web/src/main.tsx`, as MAWS's `connectTranscript()` is called
from `App.tsx`.

| slot | props | where the shell mounts it |
| --- | --- | --- |
| `depth` | `{project, session: DeskSession \| null, plane: SessionPlane}` | the project view's right column while it is open; `session` is the selected direct channel's, null on the group chat and while the browser is locked |
| `transcript` | `{project, session: DeskSession, plane: SessionPlane, range: {from: string \| null, to: string \| null}}` | a direct channel's working record, unfolded in the center at one fold (DC5's M3 mounts it); `range` is that fold's bounds, below |

**The working record's range.** The `transcript` slot draws a session's
`<message>` marks through the to-human Presenter, and each fold hands it
`range: {from, to}`: each end is the `src` of the exchange item bounding the
fold — a `<message>` span's `<transcript row uuid>#<span index>`, or a
question's call id (a `question` event's `src`; a raised question's
`toolUseId ?? request`, DX4, since the ask mod's blocking question is raised
under the engine dialog's id while the transcript holds the outer call) — or
null for an open end (the first fold's `from`; a live
session's last fold, after its last item, has `to` null). The slot draws only
what lies strictly between, at span granularity: a bounding message's marked
span is excluded, and unmarked text in the same row is drawn. The shell passes
the bounds and trims nothing.

**The session plane** (`session-plane.ts`), handed to both slots as `plane`:

```ts
type SessionTarget = { machine: string; session: string; agentId: string | null }; // agentId null: the main thread
type SubscriptionMessage = SessionMessage<'snapshot' | 'row' | 'chunk' | 'block-row' | 'step-end' | 'rows' | 'subagents' | 'diff' | 'usage'>;
interface SubscriptionListener {
  message(message: SubscriptionMessage): void; // snapshot (n 0) first, then n = 1, 2, … with no gap (or an `end` first, below)
  reset(): void;                                // a discontinuity the client recovers from: drop what was delivered
  end(body: SessionBodies['end']): void;        // the hub ended it, or the client cannot serve it; nothing follows
}
interface Subscription { rows(before: string, limit: number): void; diff(): void; close(): void }
interface SessionPlane { subscribe(target: SessionTarget, listener: SubscriptionListener): Subscription }
const transcriptKey: (project: string, target: { session: string; agentId: string | null }) => string;
```

The hub client keeps a subscription whole: a gap in `n`, a dropped socket,
a hub restart, and the hub's `end {reason: "discontinuity"}` (the bridge's
own stream lost events) each become `reset`; the client gives the broken
sub up, subscribes again under a fresh `sub` once the socket is up, and a
fresh snapshot follows; a message of a given-up sub is never delivered.
Any other `end` (machine offline, session ended, unsubscribed, error) ends
it for good: the consumer subscribes again when it wants to, for instance
when `DeskSession` shows the machine back. An `end` may also come first, at
`n` 0, with no snapshot before it, when the sub ended before one could be
taken (the session unknown, the bridge not ready, a cut row not yet on
disk), carrying the reason it would have carried later: it reaches `end`
like any other, and a `discontinuity` at `n` 0 is `reset` and subscribed
again after a growing wait (the socket's backoff), not at once, so a bridge
still starting is not asked in a loop. `diff()` asks for the working tree's
diff on a main-transcript subscription (nothing on an agent's), answered
as a `diff` message; `usage` arrives through `message` like any kind. `close()` ends it silently and
it is never re-subscribed. Older rows arrive as a `rows` message through
`message`. The target's `agentId` scopes the subscription to one
transcript, as DX3's `subscribe` carries it; per-block streaming
(`block-row` settling a block when its row arrives) is the consumer's,
passed through as DX4 has it, and so is `step-end {turnId, agentId, step}`,
which follows every `block-row` of its step. A main-scope sub carries no subagent rows: a
subagent's `block-row` seen there settles that block at once and its
partial text is dropped, since the agent's own sub draws the row (DC6's to
draw; the client passes it through). Within a transcript, rows arrive in
disk order.

**The session** (`sessions.ts`): `DeskSession` is what the log says of a
session joined with what the session plane says now —
`{project, session, alias, machine, cwd, worktree, member, ended: {by,
reason} | null, charge, status, state: {word, ts} | null, joinedAt, group:
"waiting" | "working" | "idle" | "ended", presence: SessionPresence |
null, machineOnline: boolean | null}`. `presence` is null until the hub
sends one and while the machine is offline. Model, context use, and cost
are not on it: they come from the transcript, DC6's. Inside an open project
`useDeskSessions(connection)` and `useDeskSession(connection, id)` serve
any view; `useProjectConnection(project)` (`project/registry.ts`) gives the
project's connection.

**The layout** (`layout.ts`): `useDeskLayout` holds `route` (`{view:
"grid"}` or `{view: "project", project, channel: {kind: "group"} |
{kind: "session", session}}`, mirrored in the URL as `/`, `/p/<project>`,
`/p/<project>/s/<session>`) and `depth: {open, width}` (default open, 380
px, kept in the browser's `localStorage`), with `navigate(route)` and
`setDepth(partial)`. The depth column's own tabs (transcript, subagents,
diff, info) are DC6's state.

**The transcript store.** DC6 imports MAWS's transcript model and
`useTranscriptStore` as they stand (the renderer survey) and keeps each
transcript under `transcriptKey(project, target)`. A `TranscriptSource`
built over `SessionPlane` maps `reset` to `onReset`. A transcript is live
while its `DeskSession` has `presence.record` non-null and `machineOnline`
not false; DC6 tells the store through `setLive(key, live)`, as MAWS's
`transcript/shell.tsx` does.

## Surprises & Discoveries

- On DC3's local hub (`pnpm --filter desk-hub local`), a machine whose
  stream ends is not offline at once: the grid, the RPC's `uncertain`, and
  the view's offline banner all followed only after ~29.7 s, the lease's
  lapse (two runs, 29,722 and 29,656 ms). The fake machine's `drop()`
  cancels its fetch body, which closes the connection within 13 ms (a Node
  probe against a plain server), and the stand-in's proxy destroys its
  upstream request when the client goes; so the close is lost between the
  proxy and the `Machine` object, in the local runtime. DX2 says the close
  reaches the project at once. Reported to DC3; the suite keeps the
  composite's assertion.
  Date: 2026-10-15, executor (task 6).

- Chrome's virtual authenticator (CDP `WebAuthn`, `hasPrf: true`) cannot
  stand in for a second browser holding the same passkey:
  `WebAuthn.getCredentials` exports a credential without its PRF secret, and
  that credential added to another page's authenticator evaluates no PRF
  (`prf: {}`). The browser suite proves "the same key from the passkey
  alone" with one authenticator and the browser emptied of everything it
  held (`Storage.clearDataForOrigin`) between two derivations; the
  passphrase is proved across two browser contexts; that one iCloud
  Keychain passkey gives the same PRF output in Safari and Chrome is the
  owner's probe (`spikes/desk-prf/`).
  Date: 2026-10-15, M2 executor.
- Headless Chromium dispatches a push from `ServiceWorker.deliverPushMessage`
  and the worker's `showNotification` resolves, but
  `registration.getNotifications()` lists nothing (run 38776303667: the
  case waiting on it timed out with an empty list; recording the worker's
  calls instead passed in run 38777343710). What the platform draws is the
  owner's walk.
  Date: 2026-10-15, M4 executor.
- Vite's chunk warning counts every JS chunk over the limit, lazy ones
  included (`vite` 7.3.6, `config.js`'s reporter), and three of the desk's
  are single third-party modules (mermaid's parser, the emacs-lisp grammar)
  or a library that only loads with them (mermaid's core): splitting alone
  cannot clear it.
  Date: 2026-10-15, M4 executor.

- Observation: the owner's walk found no defect in the web. PRF works
  with an iCloud Keychain passkey in Safari and Chrome on the Mac and in
  the iOS installed app; the Access session carries into the standalone

  the Mac. A push from a session with no alias reads "a session is waiting
