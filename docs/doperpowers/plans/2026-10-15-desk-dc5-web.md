## Constraints that bind every milestone

  The controller records this plan's decisions in its own Decision Log,
  messages that session with DX8 at M1's end, with any decision that
  touches a contract, with every owner action as soon as it is known, and
  at each milestone's end; it does not edit the composite. A contract that
  proves wrong goes to that session, never around it: DX3, DX4, DX6, and
  DX7 are DC3's, being built in parallel.
- **Where the code lives.** `apps/desk-web` in MAWS's pnpm workspace,
  beside `apps/desk-hub`; served by the hub's Worker (static assets). The
  protocol, the canonical JSON, and the codes come from `desk-hub/protocol`
  as they stand, never re-implemented. This child works in its own MAWS
  worktree on a branch from `smns-erb`, and merges `smns-erb` in as DC3
  moves (never rebases it); the desk-hub app is DC3's to change.
- **MAWS's components.** Import what the survey ranks importable as it
  stands; reach the rest through the seams it names (`TranscriptSource`,
  `TranscriptActions`, injected clients); copy and adapt only what it ranks
  copy-and-adapt, into `apps/desk-web`. A change to a MAWS module to make
  it importable (cutting an import edge such as `DEFAULT_ACTIONS` out of
  `transcript/view/context.tsx`) is allowed when it keeps MAWS's own
  behavior and tests unchanged, and is named in the milestone's message;
  MAWS's charter contracts and decisions govern that code. Session depth
  — the transcript stream, the subagent tree, the diff — is DC6's; this
  child leaves its slot (DX8).
- **Visual design** follows MAWS's tokens and density (`styles/tokens.css`,
  `app.css`; light first; components use tokens only) and afleet's
  Slack-like layout. **Taste-heavy surfaces go to the owner as mockups
  before polish**: the grid card, the folded agent-traffic row, the request
  cards, and the phone's layouts. A mockup is a page the owner can open
  (a static HTML page under `mockups/desk/`, or a screenshot of the running
  app), sent through the composite's writer; work that does not depend on
  the verdict continues meanwhile.
- **The org key never leaves the browser except inside an enrollment
  code** the owner carries by hand (§6); it is never sent to the hub,
  logged, or put in the service worker. Every log event and request card
  is verified before it is drawn (the code, and for a `hub/` event the
  shape checks DX1 adds for what the code leaves out); one that fails is not drawn and is
  reported in the view.
- **MAWS's gates cover the app** (`scripts/ci-gate.sh <worktree>`: the
  root `pnpm typecheck`, `lint`, `test`, `build`, which must reach the

## Plan of Work

### M1 — The shell and the hub client

**At its end:** `apps/desk-web` builds as a web app the hub's Worker
serves; signed in through the local stand-in for Access, the owner sees
the grid of the org's projects (machines online, working and waiting
counts, from the registry's grid stream) and opens a project into the
three-column view of §4 — `# <project>` and the sessions as direct
channels grouped waiting on you / working / idle / ended, each with its
machine and in-charge line; the selected channel in the center; the depth
slot on the right, empty for DC6. DX8 is written and sent.

**Decisions:**
- *The hub client* speaks DX3: a project socket that resumes after the
  last offset it holds, joins `part` frames, and reconnects with backoff;
  the registry socket for the grid. Every discontinuity re-resumes; nothing
  is assumed delivered that the hub did not acknowledge.
- *State* follows MAWS's (Zustand stores, TanStack Query where a request
  fits); the log is kept per project by offset, so a reload resumes from
  the browser's own record, never from the start.
- *DX8* is copied from `rs/app/slots.ts` and `rs/transcript/shell.tsx`
  (the survey's copy-and-adapt), with the slot, layout, session, and
  transcript-store interfaces DC6 plugs into.

**Proves:** DC5.G1 against the local hub, with a machine fed by DC3's
fake machine once its M4 lands (a DX2 test client until then): the grid's
counts change within 2 seconds of a change on the machine side.

### M2 — The org key and enrollment

**At its end:** the org key derives in the browser from the owner's
passkey through the WebAuthn PRF extension (HKDF over the PRF output with
the org id), or from a passphrase where PRF is unavailable, and every
browser holding the passkey derives the same key; the browser generates
an enrollment code (DX7) that enrolls a machine through DC4's `sminos hub
enroll`.

**Decisions:** the key is held as a non-extractable WebCrypto key for the
HMAC and kept only as long as the owner chooses (a session, or the
device's IndexedDB); the passphrase path uses a memory-hard derivation
with the org id as salt, its parameters recorded; the enrollment code is
built only after the owner confirms the machine name, and shown once.
How PRF behaves in the owner's browsers with an iCloud Keychain passkey
is §8 unknown 4's first half: probe it here, in Safari and Chrome on the
Mac, and record what you find.

The enrollment half needs DX7's token-creation endpoint, which DC3's M2
fixes (the composite's writer relays its contract); the key derivation
does not wait for it.

**Proves:** DC5.G3: the same key from two browsers; a code that enrolls a
machine (against DC4 when its enrollment lands; against DC3's local hub
with a DX7 test client before then).

### M3 — The conversation and its actions

**At its end:** the group chat and direct channels draw a project's log
as §4 says, and every action of §5 the web offers is wired: send, steer,
interrupt, model, effort, compact, answering a question, allowing or
denying, spawn, retire, resume.

**Decisions:**
- *The group chat:* messages, questions (answerable in place), permission
  prompts while pending (decidable in place), lifecycle as system lines,
  what humans posted; agent-to-agent traffic folded into one row per run,
  expandable; posting follows `sminos say`'s grammar (untagged records,
  `@alias` delivers, `@all` wakes every live member).
- *A direct channel:* one session's exchange with the human, the working
  record between folded (the unfolded transcript is DC6's); an ended
  session keeps its history and offers Resume; a message the bridge
  submitted as the human's words is drawn as the human's.
- *Request cards* reuse MAWS's request-card variants behind a copied card
  that answers through DX6 with the digest of exactly what it drew; a
  request the hub marks `terminal_only` is drawn as waiting in the
  terminal, without Allow or Deny; a background subagent's window is
  shown while it is open.
- *Capabilities:* the §5 table decides what is drawn disabled and why, from
  presence (bridged, `--bg` seat without a bridge, terminal without a
  bridge, machine offline).
- *RPC states:* `forwarded`, `done`, `failed`, and `uncertain` drawn as
  such; a retry of an `uncertain` RPC reuses its nonce.
- *Delivery:* a send shows its DX4 delivery outcome per recipient,
  including after a reload.
- *Offline:* a machine whose lease lapsed shows its sessions' presence and
  depth as unavailable while the conversation stays.

**Proves:** DC5.G2 against DC3's fake machine: each clause of G2 an
end-to-end test in a browser, including an event whose code fails not
being drawn and a reload keeping delivery outcomes.

### M4 — The phone

**At its end:** installed to an iPhone's home screen, the app signs in
through Access, derives the org key, and draws the grid, the group chat, a
direct channel, and request cards in mobile layouts; a question raised by
the fake machine pushes a notification that opens its card, and the answer
from the phone reaches the fake machine authenticated.

**Decisions:** a PWA (manifest, service worker); the service worker draws
a push from its payload alone (it holds no org key: a push only points to
a card, §4) and opens the card; push subscriptions register through DX7.
§8 unknown 4's second half is probed here and recorded: PRF inside the
standalone app (whose storage is separate from Safari's), Access sign-in
inside the standalone app, and an Access session against a push tapped
hours later.

**Owner actions:** installing the app on the owner's iPhone, signing in,
and the passkey prompts are the owner's hands; the controller sends the
exact steps through the composite's writer when the deployed hub (DC3's
M5) is ready.

**Proves:** DC5.G4 against the deployed hub with the fake machine.
