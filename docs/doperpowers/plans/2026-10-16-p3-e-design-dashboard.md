## Purpose

The measure (§2 item 7): a design artifact holds artboards of any size on a pannable canvas in the same dialect and editor as slides, exported as PNG and PDF; a dashboard is a document whose chart and table blocks are bound to data files the agent wrote (and, through P3-H's bridge, to a declared connector's tool, user-gated), each block showing its source. Both are the co-work layer's last two kinds: the owner and an agent work on one visual artifact and one data artifact the way they already work on documents and decks (edits by both merge, comments pin to objects, history and restore keep the whole, exports carry the truth). Everything here stands on what P3-A, B, C, D and L landed; E adds two kind adapters, one workbench, one dataset layer and one chart renderer, and nothing that duplicates a sibling.

**Terms.** A **board** (artboard) is one rectangle of content on the design's canvas, any size, at a position; its contents are C's slide dialect. The **canvas manifest** is the design's index file, `project/canvas.json`, naming the boards, their geometry and order. The **workbench** is the design editor: the pannable, zoomable surface the boards sit on, with C's element engine inside the selected board. A **dataset** is a named table bound into a dashboard: a **descriptor** (title, source, columns, update time, state) in the dashboard's Y.Doc plus a **snapshot**, the immutable bytes it names (an uploaded asset). A **view** is a chart or bound-table block drawing one dataset through a declarative **view spec**. A **source label** is the caption every view carries: the dataset's title, its file or tool, and the snapshot's time and author.

### 1. The Design artifact

**What it is.** A design is one Y.Doc holding a canvas manifest and boards. Its agent-facing files are `project/canvas.json` and `project/boards/<id>.html`, one `<section id>` per file in C's slide dialect unchanged (`src/artifacts/types/presentation/format.md`'s elements, styles and limits; `var(--ds-*)` admitted per Decision Log 12), the board's size *not* in the file: the manifest gives it. Claude Design's `canvas.json` keys are borrowed where meanings match (`title`, `boards` with `{x, y, w, h}` in CSS px, `order` back to front, `designSystems`; `research/p3-claude-type-formats.md` §"Design (canvas)"), its `.dc.html` documents, `support.js`, holes, `<sc-for>` and the component runtime are not read or written (Decision Log 78(1)); a converter from Claude Design's files is deferred (§"Deferred"). The manifest is MAWS's: `{v: 1, title, boards: {<id>: {x, y, w, h, title?}}, order: [<id>…], faces?, designSystems?, dsOverrides?}`, every unknown key kept as C keeps deck.json's.

**The model (advisory default; E0 verifies, E1 builds).** The design Y.Doc reuses C's roots and seam verbatim: `deck` holds the manifest's keys (`title`, `faces`, `designSystems`, `dsOverrides`, `v`), `slides` holds the boards (a board is C's slide node with four more plain scalar keys `x`, `y`, `w`, `h` on the node itself, not `attr:*`, so the dialect's attribute space is untouched; `order` the fractional index; `elements` the element map; `held`; and C's `notes` node, empty by default, hidden by the workbench and kept when a board file carries an `<aside>`, since `model.ts:195-197` always reads it and `yjs/slides.ts:144-150` dereferences it), `threads` holds the comments with `slideId` reading a board id. The reason: C's writers, repair, undo scope (`slides-undo.ts:37` already tracks these three roots, so a board move is undone with ⌘Z and a thread key written in a gesture goes with it), per-slide history (a board's own keys are its changes: a move or resize shows in the preview), restore scope (`conversationsSince`), anchors and the canvas patching all work on a board with no second model, and "a new geometry root must join the undo and history scopes" (the grounding's risk) does not arise. The alternative, a `canvas` root of its own beside `slides`, costs a second undo scope, a second history walk and a second restore adapter for four numbers, and buys nothing a board attribute does not. E0 proves two replicas converge on concurrent `x`/`w` writes of one board and that history and restore show them; if it finds a reason against, E1 may add a root with a dated entry.

**Identity [binding].** A board's id (`[A-Za-z0-9_-]{1,64}`, the file name) and an element's id are the keys of publish, anchors and history, minted as C mints them (`src/artifacts/slides/parse.ts:86-97`'s `mint`, `taken`); a board duplicated gets a new board id and new element ids; an element moved across boards always takes a new id, derived from the source board, the destination board and the old id (C's minter if that collides), because keeping the id loses an element when another replica or an agent publish inserts the same id into the destination at the same time (Yjs keeps one value per key; E0 (c) reproduced it in both clientID orders, the thread then pinned to the agent's element; Decision Log 10); the model deletes it from one board's map and inserts it in the other's in one transaction, every thread anchored to it is rewritten to the new `{slideId, elementId}` in that transaction, and history credits a move; never a copy that leaves anchors behind. The alternative (a cross-board move as a copy with new ids) orphans comments and breaks the agent's publish keys for no gain.

**The workbench.** One editor, `src/artifacts/design/editor/`, around C's `DeckSession` (the current board, selection, undo, awareness) and C's element engine (the transform overlay, inspector, text box, menus, element bar). What is new: a **world layer**, a `div` transformed by the view's pan and zoom, on which each board sits at `(x, y)` as its own `SlideCanvas` mount (C's `SlideView` given the board's size); **visible-board mounting**: a board whose world rectangle meets the viewport (plus a margin) is a live canvas, one far outside it is a cached picture or an empty frame (E0 measures which, on 24 and 100 boards); **board frames**: a board is itself selectable (click its title or frame) and moves and resizes by the same handle gestures as an element, snapping to sibling boards' edges and centres and to equal gaps (C's `snap` over board boxes), with size presets (phone 390×844, tablet 834×1194, desktop 1440×1024, slide 1920×1080, custom); **the board list** in the rail in place of the filmstrip (names, order by drag, add, duplicate, delete, zoom-to-board); **zoom** from 2 % to 400 %, fit all, fit selection, pinch and ⌥-scroll; pan by space-drag and two-finger scroll. Element editing is C's: the selected board is the one the overlay and inspector act on, in board coordinates scaled by the zoom (`Overlay` takes the board's size, `candidates()` its extents). Element snapping guides are C's `slideLines(w, h, margin)` with the board's size and a margin of 0 (a board has no 128 px margin). The design renders in the design system's **`document` medium**, not `deck`: the deck medium's `dev.maws.deck` scales are presentation type, and a 390 px board must not inherit them; E0 checks the document roles read well on screens, and a third medium is a proposed X28 row only if they do not. The board's own base type defaults are screen defaults stated in the design format reference (body 16 px / 1.5, h1–h3 32/24/20 px at 600; C's slide defaults are 32 and 96/64/44, `css.ts:10-11`), set by a `.maws-slide[data-board]` rule E owns beside `CANVAS_CSS`; the dialect is one, the defaults per kind, and export reads computed values so both exporters are unaffected.

**Publish, repair, restore, history.** `artifact_create kind: 'design'` with files, `artifact_read` returning the files (and `warnings?`, `held?` as C's answers do), `artifact_publish` three-way at property level: `publishCanvas(live, base, sent, force)` reuses `publish.ts`'s element and text machinery for board files and adds the manifest's keys (a board's `x`, `y`, `w`, `h`, `title`, `order`, the deck-level keys) compared per key, so the owner moving a board and the agent restyling an element in it merge, both writing one board's `x` conflicts as `board hero: x changed since your read`, a board removed by one and edited by the other `board hero: removed since your read`. A board file that fails structurally is held read-only with its reasons (C's `held`), never trimmed; a board whose manifest geometry is missing takes a default (`w, h` of the file's `data-size` if present, else 1920×1080, placed after the last board) with a warning; a manifest naming a missing file holds the manifest entry with a warning; a file without a manifest entry is placed with a warning. Repair is C's, scoped to touched boards. **Migration:** a design created before E1 holds its files in the generic `files` root (§"Grounding Baseline"); a read-time repair cannot migrate it, since `artifact_read` runs `readFiles` on a temporary document (`artifact-tools.ts:222-229`), so the host migrates such a document into the model explicitly, once, in its own committed write credited to the actor whose open or write triggered it, before any read answers; the migration is idempotent (a second run finds the model and writes nothing), its earlier versions still read as the files they were, and the generic root is left empty rather than deleted. Restore is artifact-wide (§4.2); the design adapter's `revertScope` keeps conversations and `afterRestore` orphans and un-orphans as C's does. History per board on C's `history.ts`: changed boards edged in the author's colour in the board list and on the canvas, moved or resized boards marked as changed, changed elements outlined, deleted ones ghosted.

**Comments.** C's `{slideId, elementId}` anchors on boards and elements (a board-level comment anchors `{slideId: board, elementId: ''}`, C's `ROOT`); the card's lead line gets a `design` entry (`element "<quote>" in design <id>, thread <id>`; a board's `board "<title>" in design <id>`), the anchor's `artifactKind: 'design'`; the three thread tools wrap C's `threadTool` helper as the deck does.

**Export [binding on the policy].** `design × png`: exactly one board per export (`board?: id`, default the first in order; the editor exports the selected board), at native size, or at `scale` (0.1 to 4) or `width`; a side that would exceed the picture cap (8,192 px, `EXPORT_SIZE_MAX`) with no scale given is refused naming the board, its size and the largest scale that fits; the editor's Export sheet offers that scale; never a crop and never the silent clamp of `export.ts:479`. `design × pdf`: one page per selected board (`boards?: id[]`, default all in order), each page the board's native size in CSS px (`@page <w>px <h>px`) with the board drawn at 1:1 as C's PDF draws a slide; a board above 19,200 px a side (14,400 pt, the PDF readers' limit; the printer itself paged 16,384 squared and 1080×20,000 natively in E0 (e), so under the model cap every board prints at native size) is refused naming the board and the limit, or printed at the explicit `scale` the request gives; never Letter fitting. Both reuse C's capture-window measure and standalone page (`src/artifacts/slides/export/{standalone,measure}.ts`, `src/main/presentations/export.ts`'s `withDeckWindow`, `measurePass`) with per-board sizes. `html` and `claude` are not built for designs in P3 (§2 item 7 asks PNG and PDF; Claude Design's format is not the dialect).

**Mirror and library.** `registerMirrorWriter('design', …)` writes `<slug>/canvas.json` and `<slug>/boards/<id>.html` with tokens resolved and `dsOverrides` dropped, declaring `inputs` as C's writer does so a design-system change rewrites it; the library's text extractor is the generic one; the row kind `Design`.

**Limits (E1 states them in the format reference).** Boards per design 200; per-board element limits C's `SLIDE_LIMITS`; files 512, 256 MB, 16 MB per publish (C's `DECK_LIMITS`). Board size: the measure says "artboards of any size" and Decision Log 78(3) authorises scale or refusal for *output* only, and the owner ruled at approval (Decision Log 5) that the model has a finite cap: E0 measured them (Decision Log 10): a side of at most 16,384 px (above it the capture window silently cuts a picture at 16,384, and PDF readers stop at 14,400 pt, 19,200 px) and an area of at most 2^26 px (8,192 squared, a native bitmap of 256 MiB), although Chromium itself edits, draws and prints boards up to 65,536 px a side; E1 states these in the format reference, and a board outside them is refused at creation or publish naming the board and the limit, never clamped.

**Not built.** Pages (U1's `pages`), U1's stickies and canvas `notes` (a board's own `<aside>` notes stay in the model, hidden), `expand: "fill"`, `is_interactive`, Tweaks and `data-props`, Claude Design's component runtime, a presenter, PPTX of a design, transitions and builds on boards (the attributes are kept in the model and ignored by the workbench), suggestions on designs (as decks, Decision Log 53).

### 2. The Dashboard artifact

**What it is.** A dashboard is B's document (tabs, blocks, marks, comments, history, the design system's look, `artifact_edit` block by block) whose `chart` atoms draw datasets. One Y.Doc: B's roots (`tabs`, `threads`, the root attributes B uses) plus one root `datasets`, id → descriptor node. Nothing in the dashboard is a page runtime: no `index.html`, no d3 callbacks, no `db`, no watchers (Decision Log 78(2)).

**Datasets [binding on the descriptor's semantics; the shape is XE5's].** A descriptor is `{title, description?, source, columns: [{name, type: 'string' | 'number' | 'boolean' | 'date' | 'null'}], rows: number, rowKey?: column, updated: {at, by: Actor}, state: {status: 'ok' | 'error' | 'stale' | 'paused', message?, at}}`; `source` is `{kind: 'file', ref: 'assets/<name>', name, format: 'csv' | 'tsv' | 'json', sha256, size}` (E2) or `{kind: 'query', server, tool, args, schedule?: seconds, staleAfter?: seconds, snapshot: {ref, at}}` (E3). The bytes are the uploaded asset the `ref` names: content-addressed and immutable (`store.ts:664-666`); a replacement is a new asset and a new `ref`, the descriptor's `updated` moving; the old bytes stay reachable at any retained version that pins them (`store.ts:718, 778`; `assetUrl(…, revision)`, Decision Log 46 and 59), so a version's preview renders the data it had. A view always renders the snapshot its descriptor names at the revision being shown, never a later one. Deleting the artifact deletes its assets with it; Duplicate copies them (`store.ts:429-443`); Restore reverts the descriptor and the view finds the old snapshot again. The agent updates a dataset explicitly and only through the tool below; MAWS never watches a path.

**The agent's writes.** One new tool, `artifact_dataset {artifact, baseRevision, id, path? (a file under the session's cwd), ref? (an uploaded asset), title?, description?, rowKey?, remove?}`: the host reads the file (the upload's 16 MiB bound), parses and validates it (CSV and TSV with a header row per RFC 4180, JSON an array of flat objects; at most 200,000 rows and 256 columns, the candidates E2 settles against the renderer's measurements), infers column types, uploads the bytes as an asset and writes the descriptor in one operation (idempotent by tool-use id, the session the actor, the dataset's `updated.by`), answering `{status: 'dataset', artifactId, id, revision, columns, rows, warnings?}` with the new live revision (X25: `baseRevision` on every write, the live revision on every answer). The stale rule is descriptor-level: the write is refused `conflict` only when *that dataset's* descriptor changed since `baseRevision` (another session replaced or removed it), so prose edits and other datasets' changes merge, and two sessions replacing or removing one dataset cannot silently overwrite each other; a malformed file is refused naming the line and the reason and nothing is written, the previous snapshot staying; `remove: true` deletes the descriptor (views naming it show the "no dataset" error; the bytes remain for history). A dataset's id is `[A-Za-z0-9_-]{1,64}`; a dashboard holds at most 64. The dashboard's `artifact_read` footer lists its datasets (id, title, columns, rows, updated); the guide tells the agent the sequence: create the dashboard with its blocks, bind the datasets, read back. **Dispatch for the kind:** B's tools select their adapter through `documentAdapterOf(store)`, which answers the `document` adapter alone (`kinds/document.ts:51-54`) and on which the edit registers its provenance carries (`documents.ts:268, 303`), and B's create wrapper hardcodes the kind, its answer and the guided-kind bookkeeping (`documents.ts:672, 681, 696`); E2 owns making adapter selection and the create, read and guide dispatch kind-aware for `dashboard` (P3-E-marked in B's file, B's tests unmodified, with provenance regression cases proving carries land on the right adapter for both kinds), and A's `artifact-publish.ts` refuses `dashboard` as it refuses `document`: a dashboard is edited block by block and never published.

**Views.** B's `chart` atom carries `source` = a dataset id and `spec` = a view spec: `{view: 'bar' | 'line' | 'area' | 'scatter' | 'pie' | 'table', x?: column, y?: column | column[], series?: column, agg?: 'sum' | 'mean' | 'count' | 'min' | 'max', sort?: {by, dir}, limit?: n, filter?: [{column, op: 'eq' | 'ne' | 'lt' | 'gt' | 'in', value}], columns?: column[] (table), format?: {<column>: 'number' | 'percent' | 'date' | 'text'}, title?}`: a closed declarative grammar, no expressions, no URLs, no code, validated by the schema parser E owns (unknown keys dropped with a warning in the agent's answer; an unknown view kind drawn as an error). The dialect form is B's as built (`format.md:40`; `markdown-syntax.ts:397-413` reads the fence body into `source` and writes it back, ignoring a `source` attribute): `:::chart {spec-json='{…}'}` with the body the dataset id, B's dialect unchanged; the caption is E-owned `spec.title`. **The renderer [binding on its grade — the editor, main's exporters and the Node-built schema module all read one output]:** its input is the closed declarative spec and the dataset's rows; its output carries no script, URL or network reference; equal inputs give byte-equal output; and the editor and every exporter show one and the same rendering of a view. **Advisory default:** a DOM-free pure function `renderView(spec, table, theme) → {svg: string, warnings}`, so the editor injects its SVG, the PDF and HTML exporters inline it (the print window runs no script, `export.ts:79-81`), the DOCX exporter rasterises it in the capture window or embeds the SVG, Markdown writes the view's data as a GFM table under its caption; E2's comparison milestone validates the default, and if it picks a DOM library instead, main's exporters render the views in C's capture window (`withDeckWindow`) and the grade still holds. Every view draws a **source label** under the figure: the dataset's title, "from <file name>" (or "<server> · <tool>"), "updated <time> by <actor>", and the state when not `ok`; clicking it opens the **source sheet**: the descriptor, the columns with types, the rows in a virtualised table (the whole snapshot, sortable, copyable, read by the snapshot's `ref`, so a replacement while the sheet is open never mixes its rows with the earlier label), a Download of the file, and in E3 the grant and refresh controls. Keyboard and screen-reader access to the figure's data is the source sheet, named in the SVG's `aria-label` and `<desc>`.

**Error and stale states (named, drawn in place, never silent).** `no dataset "<id>"` (the block names nothing bound), `dataset "<id>" has no column "<name>"`, `<n> of <rows> values in <column> are not <type>` (a validation warning carried in the descriptor and shown as a note), `the file of "<id>" could not be read` (the asset unreadable at this revision), `stale since <time>` and `paused: no live session` (E3; the last snapshot stays drawn). These states bind in meaning (XE5); their wording is E2's, in one module (`src/artifacts/dashboard/states.ts`) that the editor, the exporters and E3 reuse. A view in error keeps its caption and its block id, so comments and edits on it survive.

**Comments.** Block-level: B's `comment` mark needs text, a `chart` atom has none, so a chart's comment is a thread whose `anchor` is the block's id (`{tabId, blockId, quote: the caption}`), drawn as a pin on the block, orphaned when the block is deleted (the quote kept), following a move; B's thread tools unchanged, one additive anchor variant in B's thread model (P3-E-marked). Data-point comments are deferred (§"Deferred").

**Exports.** B's four exporters run for `dashboard` through the chart hook above: PDF and HTML with the SVGs and labels inline, DOCX with pictures and the labels as captions, Markdown with data tables; each label carries the snapshot time of the revision exported: the exporter reads the descriptors from the state it captured as the export started (`export.ts:267-290`) and the rows by those descriptors' snapshot refs, so a replacement landing after the export started changes nothing in it. The mirror writes `<slug>.md` as B's does plus `<slug>/data/<name>` for every bound snapshot.

**Not built.** Parameters (`{{param}}`), schedules and stale-after before E3; data-point comments; a KPI tile; computed columns and joins; editing data in the table view (snapshots are immutable; the agent replaces them); U1's page runtime.

### 3. Live datasets (E3)

A `query` source names a server and a read-only tool the engine's `mcp_status` reports (route E) or MAWS's own client reaches (route D); the dashboard holds a **grant** per tool, created by the owner from the source sheet or the header and revoked there, stored in the host's artifact store beside the artifact (H's brief names the table and the IPC); a refresh calls the tool through H's `ArtifactHost` bridge, validates the result as a `file` dataset is validated, uploads it as the new snapshot and moves the descriptor's `source.snapshot` and `updated`; the actor of a page-owned refresh is the human whose page watches, of an agent-asked one the session (X29 has no system actor). Snapshot retention is resolved at E3's checkpoint with A's and H's owners before any implementation (§"Risks"); no fallback is pre-authorised. E3 adds nothing to the view spec: a `query` dataset is a dataset.

### 4. Portability and the seams

Everything of E but main's exporters, the IPC and the host wiring lives under `src/artifacts/design/` and `src/artifacts/dashboard/` with no Electron, Node or `window.maws` import (§4.10's lint rule); C's slide module is imported, never copied; shared changes to C's files are additive with deck defaults and P3-E-marked (XE3).
