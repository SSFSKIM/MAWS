## Purpose

P5 moves MAWS's machine-bound services out of Electron main into a per-machine daemon, `mawsd`, so sessions keep their services with the app closed and other machines can drive them. Before anything moves, main's services have to become movable where they stand, and the wire between processes has to stop demanding an exact build match. O1 does that and changes nothing the owner sees.

After O1:

- A handler in main learns who asked through a `ClientRef`, a small value that names the asking page and says when it is gone. It no longer gets Electron's `WebContents`. So the same handler can later run in `mawsd`, where the asker is a socket connection.
- Every effect only a client can perform goes through one injected **client port** (OX4): open and save dialogs, a yes/no question, reveal in Finder, opening a URL or a file, notifications, the dock badge and focus. No file of a machine-bound service imports `electron`, and lint enforces it.
- A registry owner value, `machine`, lets the router send a namespace either to handlers inside main (the embedded root, which is every production namespace's binding in O1) or to another process, with the asker's `ClientRef` carried across. A test drives one fixture namespace both ways and gets the same answers.
- Every namespace declares the grade a remote caller needs to use each of its commands (OX9). The build fails when one doesn't.
- The app and the engine host greet each other with a major version (the socket preamble's `protocol`, now 3), a `minor`, a `build` and `capabilities` (OX1). Builds of one major interoperate. A committed manifest of the wire's schemas makes every change either additive, with a minor bump, or a declared major. A test runs one registry against another a minor apart, in both directions, over the real socket. A supervisor that a pre-O1 app left running, if its wire fingerprint matches, keeps serving its sessions to the O1 app through the protocol-2 form, which is kept for one major.
- A bench (OX7) measures a lane B session's delta-to-paint (as delta to frame: from the engine's write to the end of the frame that renders it) and command round trip on the local path, on the gate's Mac lane. It records the baseline of the app at `c3507722d`, which is the app code at O1's base. At O1's head the numbers are within 2 ms at p50 and 5 ms at p95 of it.

**How to see it working.** The app is used as before: every e2e group is green. Seven checks show the new parts: the bench's lines in the `e2e:local-latency` job log; `pnpm lint` refusing an `electron` import planted in `src/main/scm/`; `pnpm typecheck` refusing a namespace with its grade deleted; the forwarding test; the cross-minor test; the manifest test refusing an unbumped schema change; and the supervisor e2e group's update cases. The commands and their expected output are in Concrete Steps.

### Orientation

- **The IPC boundary.** Renderer calls cross into main at the router, `src/main/ipc/router.ts`. It checks the sender, validates the input against the X2 registry (`src/shared/ipc/schema.ts`, composed from `src/shared/ipc/schema/<namespace>.ts`; zod-free name lists in `src/shared/ipc/names/`) and dispatches on the entry's `owner`:
  - `main` goes to a handler registered with `registerMainHandler`;
  - anything else goes to `hosts.dispatch` (`src/main/hosts/supervisor.ts`).
  The engine host is either a utility process or a detached supervisor reached over a Unix socket (`src/main/hosts/detached-transport.ts`; `src/main/hosts/mode.ts` picks). The pty host is always a utility process.
- **The host side.** A host serves its commands through `createHostRuntime` (`src/shared/host/runtime.ts`). It speaks C1's envelope (`src/shared/ipc/host-protocol.ts`): `req`, `res`, `evt`, `ready`, `doc`. Over the socket it adds a handshake and its own lines (`src/shared/host/socket-protocol.ts`, `src/shared/host/socket-server.ts`; `src/engine-host/detached.ts` runs it).
- **Validation.** Three places validate what they receive:
  - the host runtime, inputs;
  - main's supervisor, outputs and events;
  - the renderer, outputs and events.
  They use `src/shared/ipc/validate.ts`, and the schemas are mostly `z.strictObject`.
- **The composition root.** Main's services are wired in `src/main/index.ts`. Most take injected `register`, `emit` and `call`.
- **Test support to reuse.** `test/support/fake-supervisor.ts` runs the real socket server and runtime on a real socket. `src/main/hosts/detached-transport.test.ts` shows how to run `createHostSupervisor` against it with `electron` mocked. `src/main/ipc/router.test.ts` fakes `ipcMain`. `e2e/browser-cua.spec.ts` (its seventh scene) shows a stub engine run as a live session's engine through `MAWS_E2E_ENGINE_BIN`, with `launchDefaults` from `src/shared/composer/launch-defaults.ts`.
- **The gate's lists.** In `.github/workflows/gate.yml`:
  - `MEASURED_E2E` lists the groups whose time bounds were calibrated on the mini;
  - `HOSTED_MAC_E2E` lists the groups GitHub's hosted Macs take;
  - `CLASS1_E2E` is the default Mac set.
  The plan's tests are `.github/scripts/gate-plan.test.mjs` and `.github/scripts/e2e-default-specs.test.mjs`. A measured spec must skip without its `MAWS_<NAME>_PERF` switch, because the bare `pnpm e2e` of `e2e:default` collects every spec.

**Decisions.**
- **No app code.** M1 changes nothing under `src/`, so the app the bench measures at M1's commit is `c3507722d`'s app. Check it with `git diff --stat c3507722d HEAD -- src`, which must print nothing. All instrumentation lives in the stub and the spec.
- **The engine stand-in is a real child process.** The engine host launches the stub as a live session's engine through `MAWS_E2E_ENGINE_BIN`, using a shell wrapper the spec writes, as `e2e/browser-cua.spec.ts` does. It answers `--version` with `FIXTURE_ENGINE_VERSION` (`test/support/engine-pin`).
  - On stdin it reads stream-json. It answers each `control_request` with a recorded response for that subtype, carrying the host's own `request_id`.
  - **The prelude.** The answers must cover every control the host sends from launch to ready. Enumerate them by reading `Session`'s initialization in `src/engine-host/session.ts`; the stub's table lists each with its source fixture. At the base they include:
    - `initialize` (`spikes/protocol-probe/fixtures/init.jsonl`), whose recorded `capabilities` decide whether the surface attach runs;
    - `set_max_thinking_tokens`, which `Session` always sends after `initialize`, from `spikes/protocol-probe/fixtures/p4/p4-tool-summaries-thinking-edits.jsonl`;
    - whatever else the gateway check, the auto-mode fallback, grant reapply and queue recovery send for the bench's launch spec.

    Reads (`get_context_usage` and the rest) come from `spikes/protocol-probe/fixtures/reads.jsonl`. For a subtype the table doesn't hold, the stub writes one stderr line naming it and exits 70, so a missing answer shows as a launch failure, not a hang.
  - **The stub's own test.** `test/support/latency-engine-stub.test.ts` (vitest, no Electron, class 1a) proves the conversation before any Mac run. It spawns the stub and drives it through the engine host's real `Session` over its process transport, as `src/engine-host/transport.test.ts` spawns processes, if that harness can host a `Session`. Otherwise it writes the prelude frames itself and checks every answer against the host's response schemas (`src/engine-host/controls.ts`) and every turn frame with `parseStdoutFrame`. Either way it must reach ready, complete one `get_context_usage` round trip and one whole turn, and find all 300 markers in the turn's completed text.
  - The session is created and started as `e2e/bench-edit-live.spec.ts` starts its sessions: `session.create`, then `session.start` with the first turn's prompt. Turns 2 and 3 go by `session.send`. The spec opens the session's tab the way `e2e/supervisor.spec.ts` does before it observes.
  - **The turn.** For each `user` message the stub plays one successful text turn's `in` rows from `spikes/protocol-probe/fixtures/queue-and-interrupt.jsonl`: the user echo, `message_start`, one text block, the `assistant` frame and the `result`. Its table names the slice by seq. It maps ids to the host's as the replay transport does (`src/engine-host/replay-transport.ts`), and gives each turn fresh message and block identities.
    - In place of the recorded text deltas it writes 300 `content_block_delta` text deltas, one every 10 ms, the k-th carrying the text `⟦t<turn>:<k>⟧ `.
    - It rewrites the completed `assistant` frame's text to the concatenation of those 300 marker texts. The renderer replaces the streamed buffer with the completed block (`completeBlock` in `src/renderer/src/transcript/model/reduce.ts`), so a recorded completion would wipe the last markers before the observer sees them.
  - It appends `{turn, k, writtenAt}` to the JSON-lines file the wrapper names, just before each delta's write, where `writtenAt = performance.timeOrigin + performance.now()`.
  - Why a process and not the replay transport: the replay runs inside the engine host and skips the engine's pipe. O16 puts a session host on exactly that stretch, and OX7 must catch it. Why not the real engine against a fake API: it needs provisioning and the login keychain, and it adds the engine's own variable cost.
- **The endpoint: the marker's frame, after its main-thread rendering.** In the page, through `page.evaluate`, the spec installs a `MutationObserver` on `document.body` (`childList`, `characterData`, `subtree`) once the session's transcript is shown. At each mutation it scans for markers it has not yet seen. For each new one it does two things:
  - it schedules a `requestAnimationFrame` callback, which posts one message on a `MessageChannel`;
  - when that message arrives, it records `performance.timeOrigin + performance.now()` and checks the marker is still in the DOM.

  The message runs after that frame's style, layout and paint steps on the renderer's main thread. GPU compositing and presentation come after it and are not measured.
  - Why this endpoint: every hop P5 adds (mawsd, the session host) sits upstream of the renderer, and the renderer's own work is the same build on both sides of any comparison. Ending at the frame's main-thread work catches each added hop. Rejected: Chromium tracing over CDP. Tying one marker to one presented frame is fragile, and tracing adds load to the very path it measures.
  - What to call it. OX7 says "delta-to-paint"; this is its measured proxy, delta to frame. The report and the annotation call it `delta-to-frame`. The Decision Log flags it for the architect.
  - Delta-to-frame is the recorded time minus the stub's `writtenAt`. A marker gone from the DOM when its message arrives is not a sample, and is counted.
  - **After each turn,** the spec checks the transcript holds all 300 of its markers.
  - **The clocks.** The stub and the Playwright runner are both Node and read the same clock (`performance.timeOrigin + performance.now()`). Before the first turn, the spec brackets five renderer clock reads between runner clock reads. The tightest bracket must place the renderer's clock within ±1 ms of the runner's. Otherwise the run is invalid. A negative sample also makes the run invalid.
- **Round trip.** In the page, 220 sequential `window.maws.invoke('session.getContextUsage', { appSessionId, detail: 'summary' })` calls run, each timed with `performance.now()` around the `await`. The first 20 are discarded. The call crosses renderer, main, engine host and engine and back, and the stub answers at once. Reaching the engine makes the call a real control round trip, which every later hop (mawsd, the session host) sits on.
- **Samples.** Three turns of 300 deltas. The first turn warms the path and is discarded, leaving 600 markers. p50 and p95 are nearest-rank over the markers that were samples. A run is invalid in any of four cases:
  - fewer than 570 samples (95%);
  - a turn missing a marker after completion;
  - the clock check failing;
  - a negative sample.

  An invalid run fails, saying which.
- **The group.**
  - Script: `scripts/e2e-build.sh plain && MAWS_LOCAL_LATENCY_PERF=1 MAWS_HOST_MODE=detached playwright test e2e/local-latency.spec.ts`. It runs detached, the shape the owner runs daily (`src/main/hosts/mode.ts`), and in a fresh profile from `launchMaws`.
  - The spec skips without `MAWS_LOCAL_LATENCY_PERF=1`.
  - `local-latency` joins `MEASURED_E2E` and no other list. It runs only when named, on the mini, behind the measured-job guard.
  - It spends nothing and touches no keychain: the stub makes no network call, and `MAWS_E2E` brings the mock keychain.
- **The output.** The spec prints the line acceptance 1 quotes and adds it as an annotation. It writes the raw samples, the summary and the 1-minute load to `test-results/local-latency.json`, which the e2e report keeps.
- **Recording the baseline.**
  - Run the group three times at M1's commit.
  - `LOCAL_LATENCY_BASELINE` takes the median of the three runs' p50s and p95s per metric, the three run ids, the commit, and each metric's spread (the largest minus the smallest across the runs).
  - `OX7_BUDGET_MS = { p50: 2, p95: 5 }`.
  - If a metric's p50 spread across the three runs exceeds 2 ms, or its p95 spread exceeds 5 ms, the bench cannot resolve OX7's budget. Record that in Surprises with the numbers. Message the architect before going on, because it is U1's question (P5 §13).
  - The numbers always come from runs at M1's commit, by its sha, whatever has landed on the branch since. The commit that records them touches only `test/support/local-latency.ts`, and lands whenever the three runs are done.
- **Asserting the budget.** It applies once `LOCAL_LATENCY_BASELINE` is non-null: each metric's p50 must be at most the baseline's plus `OX7_BUDGET_MS.p50`, and its p95 at most the baseline's plus `OX7_BUDGET_MS.p95`. Use the latency helpers (`e2e/support/latency.ts`, `test/support/latency-budget.ts`) only for the load annotation. The settle guard already holds the load under 5, so the budget is never loosened.

- **One `ClientRef` per page instance.** A page instance is a window's top-frame document from its load until it ends. It ends on `destroyed`, on `render-process-gone`, or on `did-start-navigation` with `isMainFrame && !isSameDocument`.
  - `clientOf(contents)` returns the live instance's ref, minting one, with id `page:<contents.id>.<generation>`, on the first call after the previous instance ended.
  - `onGone` listeners run once, at the end. A listener added after the end runs at once.
  - `pageOf(client)` answers the `WebContents` while the instance lives, and `null` after.
- **One gone moment for all per-client state.** Today's handlers release on different subsets of those three events:
  - git and files watches release on destroy only;
  - connector leases and dataset holds also on a crash;
  - visibility, viewing, voice and chords also on navigation.
  After O1 they all release when the page instance ends. A reloaded page loses what its previous document held, which no new document can still use. So the old document's git and files watches stop leaking until the window closes. Nothing the owner sees changes, because the new document asks again on mount. Rejected: a gone reason the handlers filter on. That keeps today's inconsistency, and it carries an Electron notion into code that must run in mawsd, where a client's end is one event.
- **In-flight requests.** A request the old document sent after its navigation started is attributed to the new instance, as today's visibility handler already does. Don't try to tell them apart; record the race in the file's comment.
- **Keys.** Keys that were `sender.id` numbers become `client.id` strings, including the doc relay's `postDocPort` key.
- **Early returns.** A handler that returned early on `sender.isDestroyed()` returns early when `pageOf(client)` is `null`. Machine-bound handlers that only key state need no such check, since `onGone` runs at once on a gone ref.

**Does not touch.** The client port (M3): dialogs and `shell` calls stay as they are, reaching the window through `pageOf`. The router's sender check. Owners.

**Proves.** Acceptance 2. `src/main/ipc/clients.test.ts` uses a fake `WebContents` (an `EventEmitter` with `id`). It pins: the same ref across calls; gone once on each of the three events; a subframe or same-document navigation not ending it; a fresh ref after a navigation; and immediate `onGone` on a gone ref. The existing handler tests pass with the context changed. ### M4 — Namespace grades (OX9)

**At its end.** `src/shared/ipc/grades/<namespace>.ts` (zod-free, one per namespace, beside `names/`) declares each namespace's grades. `src/shared/ipc/grades.ts` composes them under a `satisfies` that covers every namespace, and exports `gradeOf(name)` and `missingGrades(registry)`. Every command in the registry (397 at the base), the main-only ones included, resolves to a grade.

**Touches.** `src/shared/ipc/grades.ts`, `src/shared/ipc/grades/*.ts`, `src/shared/ipc/grades.test.ts` (all new).

**Decisions.**
- **The vocabulary.** It is RL §5.5's grade table with three additions:
  - `client`: served by the app itself and never sent to a daemon;
  - `internal`: sent only by a daemon's own services to its hosts (main's main-only commands today), and refused from every client;
  - `shell`: OX9's shell right for `pty.*`.
- **Three kinds, not one order** (the architect, 2026-10-27). The grades are three disjoint kinds, and the types keep them apart, so no later code can rank one kind against another:
  - the session ranks `list`, `view`, `converse`, `approve` and `manage`, in RL §5.5's order, each including the ones before it;
  - the machine grades `spawn`, `shell` and `machine-admin`, held per machine and outside the session order;
  - the routing classes `client` and `internal`, which no caller holds and the endpoint refuses from every caller.

  O1 compares no grades. O10 defines the comparison, and a command graded by a routing class can never be satisfied by a rank.
- **The form.** A namespace declares either one `GradeSpec` for all its commands, or a complete per-command map whose keys TypeScript checks against `names/<namespace>.ts`'s `commands` and `mainOnlyCommands`. So a new command in a mixed namespace fails the typecheck until it is graded. A new command in a uniform namespace inherits the namespace's grade, which its author must keep true or turn into a map. Rejected: a `grade` field on every `CommandSpec`. It touches 397 entries for the same check, and it puts a policy field into the zod schema modules the wire manifest hashes.
- **Commands graded by effect.** A command whose grade depends on its input declares `{ floor: Grade; byEffect: true }`. `session.answer` is one: a question takes `converse`, a permission `approve`. `session.send` is another: a slash command is graded by its effect (RL §5.5). O10's endpoint refines it, and refuses a `byEffect` command it has no rule for.
- **The rubric.** Record each judgment call in this document's Decision Log as one line.

  | Commands | Grade |
  |---|---|
  | Reads of one session, or of a path in its checkout (status, events, get, catalog, usage and context reads, transcript and subagent reads, `fs.*` reads, `git.*`, `scm.*` and `files.*` reads, artifact reads) | `view` |
  | Listings: `session.list`, `session.digests`, `session.projects.list`, `machine.identity` (O6) | `list` |
  | Send, steer, queue edits, interrupt, side question, a session-only model, effort or thinking change | `converse` |
  | Permission-mode changes, stop, rewind, archive, delete, rename, `setCwd`, writes to a checkout (`files.write`, git and scm mutations, artifact edits) | `manage` |
  | launch, create, start, fork, take over, replay launch, worktree creation for a new session, machine-wide reads that feed a spawn (`engine.models`, `plugins.list`, `marketplaces.list`, `customization.inventory`) | `spawn` |
  | `pty.*`, except `pty.openLink` and `pty.hostState` (`client`) | `shell` |
  | `settings.*`, `engine.configure`, `engine.policy.set`, `host.configure`, `host.stopAll`, `host.exitWhenIdle`, plugin and marketplace mutations, `connectors.*` (the owner's grants and leases), the catalog's machine half | `machine-admin` |
  | `layout.*`, `voice.*`, `browser.*`, `attention.viewing`, `attention.pendingNavigate`, `host.status`, `host.restart`, `host.openLog`, `presentations.present`, `artifacts.downloadAsset`, `library.saveAs` (survey §2's "stay with the client") | `client` |

**Does not touch.** Enforcement (O10). The registry's schemas. Owners.

### M5 — The `machine` owner and forwarding with the client

**At its end.**
- `Owner` gains `'machine'`.

**Decisions.**
- **The same handler code in both roots.** A `machine` handler's signature is `(input, ctx: HandlerContext) => output`, the same in main's embedded table and in a host runtime. A service of a `machine` namespace takes `register` injected: `registerMachineHandler` in main's root, `runtime.on` in mawsd's (O3). That sameness is what "transparently" means here. Engine-host and pty-host handlers get the context too, and ignore it.
- **One typed failure for both roots.** The router answers a thrown `HostCommandError` (`src/shared/host/runtime.ts`) with its `IpcError` intact, as it already does for `CommandFailure`. A `machine` handler throws `HostCommandError`, and both bindings then give the same error. `CommandFailure` stays for main's own handlers.
- **The envelope.**
  - `req` gains an optional `client: string`. Main sets it only on requests for `machine`-owned commands, so the engine host never receives it. That keeps M6's protocol-2 window exact against a pre-O1 supervisor's strict envelope.
  - `{ t: 'clientGone', client: string }` is a new main-to-host message. The sending side posts it once, the first time a given `ClientRef`'s `onGone` fires after a request carried it on that link. Its subscription is dropped when the link closes.
- **The receiving side.**
  - The runtime keeps one remote `ClientRef` per `(served connection, client id)`, with id `<connection>/<client id>`, where `<connection>` is a per-serve counter. It ends that ref on `clientGone`, and ends every ref of a connection when the connection is detached or replaced.
  - A `machine` request with no `client` gets the connection's own ref, which ends with the connection. Main's own requests (O3's notifier, for one) then own their state per link.
- **Without a machine host.** `createHosts` registers no `machine` host in O1. A dispatch to it answers `host_unavailable`; add that answer for an owner with no host if the supervisor lacks it. Production never chooses the `host` binding in O1.
- **The registry.** `WireRegistry = { commands, events, hostEvents, mainOnly }` (Interfaces).
  - The bridged-name check (`isBridgedCommandName`) becomes the registry's commands minus `mainOnly`, so a fixture registry's names are bridgeable.
  - **Registry-bound typing.** The router and the host runtime are built per registry and typed by it: `createRouter<R>({ registry: R, … })` and `createHostRuntime<R>(register, { registry: R })`. Their registration functions take `keyof R['commands']` names, with each handler's input and output inferred from `R`'s schemas. A fixture registry declared `as const` therefore gets typed `probe.*` handlers with no cast. The owner check (`registerMainHandler` refusing a name not owned by `main`, `registerMachineHandler` one not owned by `machine`) reads the bound registry.
  - **Production stays as it is.** Today's module-level exports (`installRouter`, `registerMainHandler`, `interceptCommand`, `registerMachineHandler`) are one router bound to `REGISTRY`, with today's `CommandName` typing. `createHostRuntime`'s `R` defaults to `typeof REGISTRY`. Main's supervisor takes `registry?` the same way for its readers. Every production call site is unchanged.

**Does not touch.** Any production namespace's owner. `createHosts`. The handshake (M6). mawsd. Events emitted by a `machine` host: O3 adds their list beside `HOST_EVENTS`, and the fixture namespace emits none.

**Proves.** Acceptance 4. `machine-forward.test.ts` fakes `ipcMain` and windows as `router.test.ts` does. It uses a fixture registry with a `probe` namespace owned by `machine`:
- `probe.echo` answers `{ text, client: ctx.client.id }`;

- `probe.fail` throws a `HostCommandError` with code `timeout`, the same code in both roots.

The same handlers run embedded, and remotely in `createHostRuntime` behind `FakeSupervisor`-style real-socket serving, with `createHostSupervisor` as main's sending side. The test asserts:

### M6 — Wire compatibility (OX1)

**At its end.**
- **Protocol 3.** The socket preamble's `protocol` is the major, now 3. The hello and welcome carry `minor`, `build` and `capabilities` (Interfaces).
- **Accepting peers.** The server welcomes any minor of its major. A client serves any welcome of its major. A different build within the major takes today's other-build path: replaced when nothing is live, otherwise served with its exit armed for idle, `matches: 'build'`.
- **Tolerant reading.** Every cross-build receiver reads tolerantly: an object key its own schema doesn't know is dropped, logged once per message name and path, and the value is then validated strictly. The receivers are the host runtime for inputs, main's supervisor for outputs and events, and both ends' envelope and handshake parses.
- **The manifest.** `src/shared/ipc/wire-manifest.json` records the cross-build wire at `{ major: 3, minor: 0 }`. `wire.test.ts` holds the code to it.
- **The protocol-2 window.** Both ends still speak protocol 2's exact-fingerprint form for one major.

**Touches.**
- `src/shared/host/socket-protocol.ts` (the v3 schemas; the v2 ones kept and named as such; the stability comment);
- `src/shared/ipc/wire.ts` (new: `WIRE_MAJOR`, `WIRE_MINOR`, `WIRE_CAPABILITIES`, `wireManifestOf`, `classifyWireChange`);
- `src/shared/ipc/wire-manifest.json` (new, generated);
- `src/shared/ipc/wire.test.ts` (new);
- `src/shared/ipc/tolerant.ts` (new: `readTolerant`);
- `src/shared/ipc/validate.ts` (the tolerant readers in `codecOf`);
- `src/shared/host/runtime.ts`, `src/shared/host/socket-server.ts`;
- `src/engine-host/detached.ts` (its identity);
- `src/main/hosts/detached-transport.ts` (the hello, the fallback, the peer facts), `src/main/hosts/supervisor.ts` (the readers), `src/main/hosts/identity.ts`, `src/main/hosts/status.ts` (`matches`);
- `test/support/fake-supervisor.ts` (a speaks-protocol-2-only mode);
- `src/shared/host/wire-compat.test.ts` (new);
- `package.json` (`wire:manifest`);
- `e2e/supervisor.spec.ts` (case (g)'s seam);
- the existing socket, transport and status tests.

**Decisions.**
- **Additive within a major** means a new command, a new event, or a new optional property of an object schema at any depth: a key added to `properties` and not to `required`. Everything else is breaking and takes a major:
  - a removed command, event or property;
  - a property made required, or made optional;
  - a changed type, `const`, `enum` or union member set (an added enum member included, since an older reader refuses it);
  - a changed numeric, length or pattern bound;
  - a changed `additionalProperties`;
  - a changed owner.

  `classifyWireChange(old, current)` applies this rule to the JSON Schemas (`z.toJSONSchema(schema, { unrepresentable: 'any' })`, the rendering `wireFingerprint` already uses). It answers `{ additive: string[], breaking: string[] }`, each entry a path such as `commands.session.status.output.properties.foo`. Rejected: counting an added enum member as additive with a capability gate on the writer. It can't be checked mechanically, and every writer would have to remember it.
- **The manifest's scope** is the wire between builds:
  - every command whose owner is `engine-host` or `machine`, input and output;
  - every event in `HOST_EVENTS`;
  - the envelope messages (`req`, `res`, `evt`, `ready`, `doc`, `clientGone`);
  - the socket-layer messages (the v3 hello and welcome, `refuse`, `exit`, `documents.open`, `documents.close`, `documents.closed`).

  The pty host is always the app's own build and stays out. So does main-to-renderer traffic. When O3 retags a namespace `machine`, it joins the manifest as additive commands.
- **The manifest's form.** One JSON file with `major`, `minor` and one minified entry per line, so a diff shows which entries changed. About 0.55 MB at the base. Only the latest minor is kept, and git keeps the rest. `wire.test.ts` checks four things:
  - the manifest's `major` equals `WIRE_MAJOR`, which equals `SOCKET_PROTOCOL`;
  - an unchanged wire passes when `WIRE_MINOR` equals the manifest's `minor`;
  - an additive change fails until `WIRE_MINOR` is the manifest's `minor` plus one and the manifest is rewritten;
  - a breaking change fails, naming each breaking path and saying it takes a major.

  `pnpm wire:manifest` is `MAWS_WIRE_MANIFEST_WRITE=1 vitest run src/shared/ipc/wire.test.ts`. It writes the manifest only when the change is additive and the minor was bumped by one, or when `WIRE_MAJOR` was raised (and then `WIRE_MINOR` must be 0). It refuses anything else. A JSON Schema rendering change with no shape change, after a zod upgrade, is rewritten with `MAWS_WIRE_MANIFEST_WRITE=rebase`, which keeps the minor; its review checks the diff is rendering only. Two branches that each bump the minor conflict on `WIRE_MINOR` and the manifest, and the second to land re-runs `pnpm wire:manifest`.

  Rejected: one file per minor, which grows by 0.5 MB per change. Rejected: diffing against a git ref in CI, which needs history the pool's clones don't keep.
- **Tolerant reading.** `readTolerant(schema, value)` parses strictly. If the parse fails, it computes the keys to strip from the issue list with a recursive rule:
  - An issue list is **strippable** when every issue in it is either an `unrecognized_keys` issue, or an `invalid_union` issue with at least one option whose issue list is itself strippable.
  - For an `invalid_union`, the first strippable option is followed.
  - Nested option issues carry paths relative to the union's own path, so they are rebased onto it before their keys are collected. Check this against the pinned zod (4.6.5) in `tolerant.test.ts`, not from memory.

  If the list is strippable, the reader deletes the collected keys from a copy and parses again, for at most 8 passes. It answers `{ ok: true, value, dropped }` or the strict failure.

  The nested-union case must pass: an outer union whose option holds `inner: union(strictObject({x}), strictObject({y}))`, given `{ inner: { x, newField } }`. The flat rule fails it, because the outer option's issue is itself an `invalid_union`. Validators in `src/shared/` "never transform" (charter §12 C1, advisory), and this is the one deliberate exception: the accepted value is what was sent, less the keys this build doesn't know. Apply it only where a peer may be another build, never at the renderer boundary. Same-build traffic is unaffected: every sender validates strictly before sending, so a same-build receiver never sees an unknown key. Rejected: switching the wire schemas to `z.looseObject`. That would keep unknown keys in values the renderer then refuses, and it would lose the strictness that catches a sender's bug at its source.
- **Capabilities.** A capability names an optional behaviour a peer of the same major may lack, as `<area>.<feature>`. `WIRE_CAPABILITIES` is empty at minor 0, and adding one is a minor change. Main keeps the peer's `{ major, minor, build, capabilities }` from the welcome on the host link, readable as `HostSupervisor.peer(owner)`, so later code can gate on it. Main logs it at connect: `connected to supervisor pid <p> build <b> wire 3.<minor> capabilities [<…>]`. A newer peer's code gates a new optional field's effect on `peer.minor` or a capability, because an older peer drops the field and does the old thing.
- **The protocol-2 window** (OX1: "the old form served for one release", read as one major; it is removed when major 4 lands).
  - **The client.** It sends the v3 hello. On `refuse protocol` with `refuse.protocol === 2` and `refuse.wire === wireFingerprint()`, it reconnects and sends the v2 hello, `{ t, protocol: 2, token, buildId, wire, appPid }`, and then serves the connection as protocol 2.
