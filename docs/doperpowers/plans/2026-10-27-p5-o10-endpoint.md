## Purpose

P5 makes MAWS one app over many machines and people. A machine is reachable from outside through exactly one door: the endpoint module inside its machine daemon, `mawsd`. O10 builds that door. After it:

- A machine enrolls with its own key. It holds the org's signed member and machine list, refuses a forged or rolled-back one, and keeps its own record of who may do what on it.
- A MAWS app on another Mac, or the owner's phone, opens an encrypted, mutually authenticated channel to the machine, relayed through the hub or straight over the tailnet. The hub carries the bytes and can read none of them.
- Over that channel a device subscribes to a session and resumes by cursor after any drop, and sends discrete actions (send, answer, approve, spawn) that run once, never twice, and never after they have gone stale.
- The machine decides every request itself, by the member's grades on the session, the machine's grants and its own policy. A namespace that declares no grade is unreachable from outside.
- sminos stops being a network party. It hands its hub link, its HMAC coding and its policy gate to the endpoint, and keeps the project log, local delivery and lane A control, talking to the endpoint over a local socket (RL10).
- One protocol package carries both halves of the channel and the action, with shared test vectors, so the app, the phone and the machine run the same code.

What someone can do afterwards: on the staging hub, a test device opens a channel to a machine running this `mawsd`, watches a terminal session, answers its question, has a replayed or stale answer refused, loses its link to a hub deploy and to a `mawsd` restart and resumes without a lost or doubled event; the devcloud acceptance VM does the same after O14's first cutover. The owner's own MacBook and mini change nothing until O14 moves them.

### M1 — The protocol package: the channel, the action, the subscription, the attestation

**At its end.** `apps/org-protocol` carries RL2, RL3, RL4, RL7 and RL9 as Interfaces §A–§C define them, both halves: a device's `openChannel` and an endpoint's `acceptChannel` over any byte duplex, the action's canonical form, fingerprint, digests, step-up and WebAuthn verification, the subscription and call messages, the device capabilities record, and the owner attestation with its proofs. Vectors pin every byte, and the suite runs under Node and workerd.

**Touches.** `apps/org-protocol/src/channel.ts`, `action.ts`, `messages.ts`, `webauthn.ts`, `attest.ts` (new), `types.ts` (`SIGNING_DOMAINS` gains `smns-rl2-v1` and `smns-action-v1`), `records.ts` (`verifyGrant` for certificate machines), `org-state.ts` (`verifyRewind`), `index.ts`; `vectors/scenario.ts`, `generate.ts`, `replay.ts`, `vectors.json`; `test-support/` (`TamperRelay`, `TestDevice`); `test/channel.test.ts`, `test/action.test.ts`, `test/attest.test.ts`, `test/encodings.test.ts`.

**Decisions.**
- **The handshake is SIGMA's sign-and-MAC with the identities in the clear** (Interfaces §A). Each side signs the transcript of both ephemeral keys, both nonces and every identity field with its long-term key, and MACs its own identity under a key derived from the shared secret, so a signature proves who and the MAC proves this exchange. The hub sees device, member and machine as routing metadata already (RL §5.9), so SIGMA-I's identity hiding buys nothing here and its extra encryption round would only add code. Rejected: Noise XX, which needs a static Diffie-Hellman key per party where RL5 lists signing keys, and has no WebCrypto implementation to share; TLS, which WebCrypto can't terminate inside a relayed byte stream.
- **One sequence per direction for the channel's life.** Each frame carries its sequence and its key epoch in a clear header covered as associated data, with the nonce built from a per-direction salt and the sequence. The sequence never resets, so the receiver accepts exactly the next one, under the current epoch or the next; anything else closes. A rekey keeps counting, so dropping an epoch's last frame is a gap like any other, which a per-epoch reset would hide (the security review reproduced that). The sender rekeys after 2²⁰ frames in an epoch or 24 hours, and the receiver needn't infer either boundary. Rekey is a one-way ratchet (HKDF over the old key), so a later key reveals no earlier traffic and needs no message of its own.
- **Org-state catch-up rides the handshake.** A side behind the other's `stateVersion` cannot verify the other's key yet. So `h2` and `h3` may carry the successors and transitions that bring the peer up to the sender's head, checked by `verifySuccessor` / `verifyTransition` before the signature. A hub that withholds a state from a machine cannot keep it from a device that talks to the machine. Rejected: refusing until the hub delivers, which lets the hub hold a revocation back from a machine an admin is talking to.
- **The canonical action binds org, machine and device** besides RL4's fields, because a step-up signature outlives its channel as an `ownersProof` that other machines check (RL9). Its signing input is the package's `signingInput('smns-action-v1', action)`, the step-up signature is ECDSA over it by the device's `stepUpPub`, and a WebAuthn challenge is SHA-256 of the same bytes. Its **fingerprint** is SHA-256 of the canonical action without `nonce`, `created`, `stepUp` and `webauthn`: what every reseal keeps, so an executing side can bind an `opId` to one operation and one sender (M7).
- **`requestDigest` is DX6's `Digest`** (`{session, request, tool, input_sha256}`, `desk-hub/protocol`'s `rpc.ts` with `inputSha256` from `codes.ts`), not a new hash. Lane A's `check_digest` already compares it, and lane B compares the same four fields with its broker's item.
- **Times are ISO-8601 milliseconds** (`isIsoMillis`), as everything else in the package; RL10 converts for sminos.
- **Recovery behind the head** (O11's open question, `verifySuccessor` following only the verifier's head). `verifyRewind(org, transition, pinnedRecovery, accepted)` accepts a root transition signed by the pinned recovery key whose `fromVersion` is at or below the machine's head, provided its `issued` is later than every transition the machine has accepted and it isn't one of them. The machine then drops every state after `fromVersion` and takes the first state under the new root as its head, whose `revoked` is authoritative (RL5). The recovery key is the root of every machine's pins, so a transition it signs from an earlier version is the statement that the states after it are forged; the stolen admin key that forged them cannot sign one. Replay of an older genuine transition is refused by the `issued` rule. Rejected: no rewind, where a machine that accepted a forged chain can be rescued only by a transition issued at its own, possibly forged, head.
- **`verifyGrant` covers certificate machines.** A grant for a VM under a delegation is signed by one of the delegation's owners' devices (or an admin's, for an org-owned delegation) for the certificate's key. O11 left it to enrolled machines only.
- **The owner attestation** (RL9). An event a session writer (`<name>/<session>`) uploads carries `attest {owners, ownersProof, origin, stateVersion}`, covered by the event's v2 signature, which is the machine key's, so it needs no second signature. `verifyAttestation(state, certificates, event)` accepts each claimed owner that is one of the sending machine's owners in that state (its member owners, the admins for an org-owned machine, or its delegation's owners for a certificate), or that `ownersProof` proves. Every proof is a step-up-signed action that names the sending machine and whose step-up key verifies by RL8's key rule against the action's `created` (current, or retired at a `notAfter` no earlier, never revoked). A spawn (`sminos.spawn`, and later `session.launch`) proves its signer's member. An owner-add action (`record.owners {add, member}`, built with O8) proves the member it names, provided its signer's member is itself an owner by the machine or by an earlier proof in the same list, so a chain of additions verifies transitively. Grants play no part (RL §5.8).
- **WebAuthn counters.** `verifyWebAuthn` requires the counter to rise when the stored or the received counter is non-zero, and accepts zero to zero: an authenticator that keeps no counter always sends zero (RL §5.10's "where the authenticator keeps one"), and replay stays bounded by the action's nonce and `opId`.

**Proves.** Acceptance 1. Vectors for: a full handshake with fixed ephemeral keys and nonces, each side's transcript bytes, the derived keys and salts; a handshake carrying successors in `h2` and in `h3`; frames at sequence 0, 1, and across a rekey at 2²⁰ with the sequence continuing; a JSON message; an action's canonical bytes, its fingerprint, its SHA-256, its step-up signature, and a WebAuthn assertion made by a software authenticator in the generator (`authenticatorData` with UP and UV, a counter, `clientDataJSON` with the challenge and origin), and two consecutive assertions from a counterless one; attestations. Negatives, each named by the first check that refuses it: a wrong `h2` signature, a wrong MAC, a device key the state doesn't list or lists for another class, a revoked device, a sequence skipped, repeated or reordered, an epoch's last frame dropped before the next epoch's first, a tag altered, a frame over 256 KiB of plaintext, an epoch jump of two, an action with `opCreated` more than 60 s after `created`, a WebAuthn assertion with the wrong challenge, origin, `rpId` hash, a cleared UV flag, or a non-zero counter that didn't rise; an attested owner with no proof, a proof naming another machine, a proof from a revoked device (one from a device retired after the action's `created` passes); Alice adding Bob, Bob adding Carol (transitive), and an addition signed by a non-owner refused. `verifyRewind`'s cases: accepted from a forged head, refused for an older transition, refused when signed by anything but the pinned recovery key. `TamperRelay` flips a byte, drops, repeats and reorders frames, and holds one for a given time.

### M2 — The endpoint module: its state, enrollment and the org state

**At its end.** `src/endpoint/` exists with its entry (`createEndpoint(): EndpointModule`), its state directory (Interfaces §E), attended and delegated enrollment, the org-state sync and verification with the durable high-water mark and rewind, the policy, and the command line (`enroll`, `keys`, `revoke`, `grant`, `policy`, `status`), all against `fake-services.ts` and a local hub.

**Touches.** `src/endpoint/index.ts`, `services.ts`, `state/*.ts`, `enroll.ts`, `org-sync.ts`, `policy.ts`, `cli.ts`, `status.ts` (new); `test/endpoint/*.test.ts`, `test/endpoint/fake-services.ts`, `test/endpoint/local-hub.ts` (new); `eslint.config.js`; the root `vitest.config.ts`'s Node project (adds `src/endpoint/**` and `test/endpoint/**`); `tsconfig.node.json` if its globs need it.

**Decisions.**
- **The state is written atomically and checked at start.** Each file is written to a same-directory temporary file, `fsync`ed, renamed, and the directory `fsync`ed. At start the endpoint refuses (exit path: `status()` says why, nothing remote is served) a state directory or file that is a symlink, owned by another uid, or more open than 0700 / 0600 (`src/shared/host/private-path.ts`). The machine key and the grant ledger are present together or not at all: either alone means unenrolled, both are moved aside to `stale-<time>/`, and `status()` says so (the remote layer's Decision Log 24).
- **Enrollment** (`mawsd enroll`, reading the code from O2's `secret` field):
  1. decode `smns-enroll-v2.` (`desk-hub/protocol`'s decoder): hub URL, token, roots, recovery key, pairing secret `k`;
  2. generate the machine key (P-256, extractable, so it can be written as a JWK);
  3. `POST /machine/enroll {token, machine: <name>}`; retry `busy` and `mint-failed` with backoff (2 s doubling, 60 s total);
  4. `POST /machine/key {pub, ref, mac}`, the MAC being `enrollmentMac(k, {name, machinePub, ref, tokenId: enrollment})`, retrying Access's 401 for up to 90 s;
  5. write `machine-key.json`, `grants.json` (holding the new key's id), `enrollment.json` (`hub-confirmed`, credentials) and `org.json` (pins from the code);
  6. read `GET /machine/org/state` until the head lists `ref` with this key, or `--wait`'s deadline; then `org-listed`, exit 0, else exit 4.
  `--replace` keeps the ref (it is the profile's, `machine.json`), generates a new key and adds its id to the ledger's held keys. Grants already in force stay in force (each was verified once, RL §6.3); a grant arriving from then on must name the new key, since `verifyGrant` checks `machineKey` against the head. A daemon that lost its state has no ledger, so it holds only the new key and refuses every earlier grant. The code and `k` are never written anywhere.
- **Delegated enrollment** is a function, `enrollDelegated({hub, org, roots, recoveryPub, token, delegation: {id, prefix, privateJwk}, name})` (Interfaces §F), the flow `apps/desk-hub/fake-machine/org.ts` runs: redeem the provisioning token (`POST /machine/enroll`) for the service token and the delegation's `use`; check the ref starts with `<delegation id>_` (O2 M5's prefix mint, from `mawsd install --delegation-id`); sign the machine's own certificate with the delegation key and that `use`, post it (`POST /machine/cert`), and be live once `verifyMachineCert` accepts it against the state. These fields are what O14's provisioning code must carry; its text form, codec (in `org-protocol`) and redemption command are O14's (P5 Decision Log 35).
- **The org state.** At `welcome`, at each `state {version}` notice, and every 10 minutes, the endpoint reads `GET /machine/org/state?since=<head>` with its service token, verifies each successor and transition against its head and pins (`verifySuccessor`, `verifyTransition`, `verifyRewind`), and only after the new head is on disk applies it: closes every channel and subscription the new state removes, re-reads grants against revocations, re-issues `@machine` listings when the machine's owners or the admins changed, and sends `revoked` down RL10. A version below the high-water mark is refused (`rollback`) and logged. A head whose `issued` is more than 30 days old stops every remote action (`state-too-old`, RL §5.2's backstop) until a newer state arrives; reads and subscriptions continue.
- **The policy** is the endpoint's: `policy.json {read_only, ceiling}`. When it doesn't exist, the endpoint takes sminos's current policy from RL10's `hello` (M6), else read-only off and ceiling `settings`. `mawsd endpoint policy` prints and sets it as `sminos daemon policy` does today, and every change goes down RL10 at once, because sminos's local delivery reads `read_only` too.
- **Status** (`status()`): `{enrollment: 'none' | 'hub-confirmed' | 'org-listed', name?, org?, stateVersion?, headHash?, hub: {connected, generation?}, channels: {relayed, direct}, rl10: {connected}, listener: {bound}, legacyKey: boolean, refusing?: string}`. No path, no address, no key material, no credential: a test walks the object field by field, allows the public `headHash`, and fails on any other string that looks like a path, an IP address or a base64url run of 43 characters or more.

**Does not touch.** RL1 (M3). `mawsd` (M10).

**Proves.** Acceptance 6's machine half. Tests: attended enrollment and `enrollDelegated` (with a delegation the local `OrgAdmin` signs) against the local hub end to end, including a hub that substitutes the key (the MAC check at the member's side refuses it: the local hub's `OrgAdmin` does the member's part), a `--replace`, a `busy` answered on the second try; the state files' modes and atomic writes (a crash between temp write and rename leaves the old file); key-without-ledger and ledger-without-key starting unenrolled; the org-state sync accepting a successor, refusing a fork and a rollback, applying a root transition and a rewind; a revocation applied only after `fsync` (a fault injected before the rename leaves the old head and sends nothing down); the backstop age; `status()`'s redaction test.

### M3 — The hub link (RL1)

**At its end.** The endpoint holds one RL1 socket to its hub while enrolled, keeps its lease, survives every cut the hub makes, and offers the rest of the module a send path for log-plane frames, listings, its endpoint record and notifications, and a channel multiplex.

**Touches.** `src/endpoint/hub-link.ts`, `listings.ts`, `notify.ts` (new); tests.

**Decisions.**
- **The socket** is Node's global `WebSocket` (undici) with the service token's headers, as `FakeEndpoint` does: no new dependency. `hello` carries RL1's protocol `{major: 1, minor: 0}`, `build` (`mawsd`'s build id) and the ref; `leaseGeneration` is sent as the last welcomed generation (the hub only logs it).
- **Liveness.** `hb {generation}` every `heartbeat_ms`; two missed `hb-ack`s, or no frame for three periods, close and reconnect. Reconnect backs off with jitter from 1 s to 30 s, reset by a welcome that holds for a minute. A 4409 (replaced) reconnects once and, if replaced again within a minute, stops with `status().refusing = 'replaced'`: another daemon holds this machine's name (two `mawsd`s under one key), which a retry loop would only fight.
- **Verdicts** (P5 Decision Log 41). 503 `busy` / `hub-updating` / `hub-unavailable`: retry with the backoff. 409 `stale-generation`: reconnect at once. 409 `not-listed` after a rename, or 409 `no-ref`: stop and report `re-enroll` (`mawsd enroll --replace`), never a transient. 403 `not-enrolled` or close 4403: stop, `revoked`. 1009 and 4412: logged with the frame kind, reconnect.
- **In-band versions, not reconnects.** A hub deploy is not assumed to cut RL1 (O11 M8 saw hibernatable sockets survive 420 s), so the endpoint never depends on a reconnect to pick up a protocol change: any frame it doesn't know is ignored with one log line per kind, and the welcome's fields are read tolerantly.
- **The endpoint record** (RL6) `{machine, addresses[], issued}` is signed with the machine key (`signRecord`, domain `smns-endpoint-v1`) and sent at each welcome and whenever the direct listener's addresses change (M4). An empty `addresses` is valid: the machine is relay-only.
- **Listings and notify** (RL6, RL §7.4). For each session sminos reports (M6) that isn't `private`, the endpoint signs `{org, machine, session, revision, issued, fields: {owners, project, lane, state, title}}` with `owners` resolved from `@machine` against the head it stamps (RL §5.8), and sends it when a field changes, with `revision` kept per session in `listings.json`. A `private` session is never listed (it goes over channels only, M8). `notify` is sent on a session's move into `waiting` (with its pending count), on its move out (`settled`), and on a to-human message (`wrote`, as O12's phase 2 reports it up RL10).
- **The log plane passes through.** RL1 carries DX2's log-plane vocabulary unchanged (P5 Decision Log 17), so M6's RL10 relay forwards sminos's log-plane frames to RL1 and back, adding signatures up and verifying down; M3 provides the per-project ordering and the lease renewal (`hb` renews it in every project the connection opened).

**Proves.** Tests against the local hub (Miniflare, forced eviction with `unsafeEvictDurableObject`): welcome and state notice; heartbeat and lease; a forced cut and reconnect under a higher generation; `stale-generation`; `not-listed` after a rename stopping with `re-enroll`; `503` retried; a 4409 twice stopping with `replaced`; the endpoint record and a listing stored and served (`GET /api/listings` as the test member); a notify reaching the listing owner's push subscription and not another member's.

### M4 — Channels on both carriers (RL2)

**At its end.** The endpoint accepts channels from devices over RL1's multiplex and over its own direct listener on the tailnet, authenticates each against its org state, tells the device its capabilities (RL7), and runs a per-channel message loop whose `call`, `act`, `query` and `sub` routes M5–M8 fill.

**Touches.** `src/endpoint/channels.ts`, `direct-listener.ts`, `tailnet.ts` (new); `package.json` (`ws` 8.22.0, already in the tree through desk-web, as a dependency of the root for the listener's server); tests and `test/endpoint/channel-suite.ts`.

**Decisions.**
- **One channel table** keyed by carrier and number. A relayed channel's number is the hub's; a direct one is its WebSocket. Both run `acceptChannel` from M1 and then the same loop, so nothing above the channel knows its carrier.
- **Admission.** The device's entry must be in the head, of the class it claims, not revoked, under a member still in the state. Classes the endpoint serves: `native-mac` and `web-cards` (RL §5.10). After the handshake the endpoint sends `caps` (Interfaces §B) and sends it again whenever the device's grades on the machine change.
- **Removal closes at once.** When a new head removes a device or a member, every channel it held closes with `removed` before the endpoint acknowledges anything else. A change that narrows a member's access without removing them (a share, an owner or a session's access, a grant) is re-evaluated per subscription (M8).
- **The direct listener** (RL §4.1; P5 Decision Log 39). Only a `unit` daemon binds it by default; a `private` one binds only when `MAWS_ENDPOINT_DIRECT=1` (tests, O6's two-profile scene stays unbound). It binds a `ws` server to each tailnet address it finds (IPv4 in `100.64.0.0/10`, IPv6 in `fd7a:115c:a1e0::/48`, from `os.networkInterfaces()`), on port 47830 by default (`MAWS_ENDPOINT_PORT` overrides), never to `0.0.0.0` or `::`. It re-reads the interfaces every 30 s and on a bind error, rebinds when they change, and re-sends the endpoint record. Before the handshake verifies it reads only `h1` and `h3`, each capped at 64 KiB, within 10 s; anything else closes. Handshakes are limited per source address (5 a minute, burst 3) and overall (60 a minute), answered `busy`.
- **Liveness on a channel.** Both ends send `ping` every 5–7 s of silence and close after two missed `pong`s (RL §4.5). Over the relay this is on top of RL1's `hb`, because the hub's liveness says nothing about the device.
- **Holds.** While any remote channel is open the endpoint holds `mawsd` (`services.hold('channel')`), so a private daemon doesn't exit under a viewer.

**Proves.** Acceptance 9, and the admission half of acceptance 3's last case. `channel-suite.ts` runs over the relay (through the local hub) and over the direct listener: handshake and `caps`; an unknown device, a wrong class and a revoked device refused; a device added in a state the endpoint hasn't seen admitted through `h3`'s successors; a channel closed with `removed` when a new state drops its device, and one when the state arrives over another device's channel; `TamperRelay`'s altered frame closing the channel. Direct-listener tests: it binds only to a tailnet-shaped address (a fake interface table), never to a wildcard; a pre-handshake `call` closes the connection; the rate limit answers `busy`; an address change rebinds and re-sends the endpoint record.

### M5 — Authorization: grades, grants, policy and classes

**At its end.** Every `call`, `act`, `query` and `sub` is decided at the endpoint by one function, `authorize(request, who, now)` (Interfaces §G), from the endpoint's offer table, O1's declared grades, the session's record, the machine's grants, the machine's policy and the device's class. A name the table doesn't offer, or one with no grade, is refused. The records and the known checkouts come through two injected sources M5 defines and M6 fills from RL10, so M5 lands with its tests on fakes.

**Touches.** `src/endpoint/authorize.ts`, `offers.ts`, `grades.ts`, `by-effect.ts`, `grants.ts`, `targets.ts`, `step-up.ts`, `sources.ts` (new); tests, `test/endpoint/grades.test.ts`.

**Decisions.**
- **Only what is offered crosses.** A remote request is decided in this order: is its name in the endpoint's offer table (`not-offered` otherwise); does it have a grade (`ungraded`); does the caller's class, policy and rank satisfy it. The table (`offers.ts`, Interfaces §G) names each offered command with its executor, its target rule and, where it has one, its by-effect rule, so every command that crosses has had its input, its target and its effect read for remote use. O10 offers what its acceptance and the phone need: lane B's conversation and its reads, lane A's bridge-fenced actions and spawn, and the endpoint's own. O7, O8 and O9 add rows, each with its own tests, when they open remote surfaces, sharing and lane A control. Rejected: forwarding every graded command, which the second review round showed exposes inputs nobody had read for remote use (a holder read that returns other sessions by directory, a spawn whose spec the executor can't take, a queue release whose content changes after its check). The grade check itself is proved over a fixture table holding one command of each grade class (acceptance 8).
- **The comparison** (O1 left it to O10). A session rank satisfies a request when the member's rank on that session is at or above it. A machine grade is a right, never ranked: `spawn`, `shell` and `machine-admin` are each held separately, by the machine's owners (all three) or by a grant naming it. A routing class is never satisfied: `client` and `internal` are refused from every caller. A request whose kind doesn't match the holder's (a session rank asked of a machine grade) is refused. The member's rank on a session is the highest of: `manage` when the member is an owner (`@machine` resolved against the head: the machine's member owners, or the admins of an org-owned machine); the grade of the member's share; `view` for `org-view` and `converse` for `org-converse`; `list` for `listed`; nothing for `private`.
- **The sources.** `RecordSource` answers a session's RL6 record by lane and id and says when one changes; `CheckoutSource` answers the machine's known checkouts. M6 implements both from RL10's `member` and `machine` frames; O3 adds MAWS's projects to the second.
- **Targets.** A command's session is read from its input by its offer row's target rule: `appSessionId` for lane B, `session` for lane A, none for the machine's own reads. An `appSessionId` maps to the engine session through `session.status` (its `engineSessionId`), then to the record. A command with a session rank and no session in its input is refused (`no-target`), with two kinds of exception: the machine's content-free reads that O2 and O6 grade `list` (`daemon.status`, `machine.identity`), which any member of the org may call, and the endpoint's own `endpoint.listings` (M8). So `session.list`, `session.digests` and `engine.sessions` are not served remotely: they would list private sessions, and a device gets listings from RL6's signed records instead. Path-only commands (`git.*`) and mixed ones (`fs.holders`, whose `directories` match sessions the caller may not see) are not offered until O7 gives them a session or checkout rule.
- **By effect.** `by-effect.ts` holds one row for every by-effect command in the composed registry, either a rule or an explicit `no-rule`; `by-effect.test.ts` fails when the registry gains a by-effect name the table lacks. The rows at master `957658290`:
  - `session.send`, `session.steer`, `session.queue.edit`, `side.sendToMain`: text that doesn't start with `/` takes `converse`; `/model`, `/effort`, `/fast` and the read-only `/cost`, `/context`, `/status`, `/help` take `converse`; `/compact`, `/clear`, `/rewind`, `/resume` and every other slash command take `manage` (RL §5.5);
  - `session.queue.promote` and `session.queue.setPaused`: `manage` when they release queued entries (a promote; an unpause), since the queue can change between the endpoint's read and the host's release and no fence binds them; a pause takes `converse`. A content fence in the host would let a release take its entries' grade; it is debt, not built here;
  - `session.answer`: the broker item's kind, read with `session.pendingRequest`: a question `converse`; a permission, plan, dialog or elicitation `approve`;
  - `session.acquire`: under the session's stored spec `converse`; a spec that changes the permission mode, directory or worktree `manage`; one that changes only the model or effort `converse` (P5 Decision Log 36);
  - `session.memoryAppend`: a project or path target `manage`; the `user` target `machine-admin` (P5 Decision Log 36);
  - `session.ui.promptEdit`: a text-only edit at its floor; a keyed edit `no-rule` until a probe shows what it triggers (P5 Decision Log 43);
  - `session.ui.press`, `session.ui.input`, `session.ui.select`, `session.applyFlagSettings`: `no-rule` (O7 adds rules for what it uses);
  - `session.update`: `no-rule` remotely. Its reader fields are columns of the owner's own row until O8 keeps them per member (P5 Decision Log 36), and it is main-owned until O3.
- **Lane A's actions** are sminos's RPC names, `sminos.<rpc>`, graded here (Interfaces §G's table). Rejected: a lane-neutral action vocabulary mapped at the endpoint, which puts each lane's meaning inside the trust boundary and duplicates the client-side adapter that turns both into one vocabulary (RL §3.3).
- **Grants** (RL §6.3). A grant arrives as an `act` of `endpoint.grant {grant}` from any device of the org, or out of band (`mawsd endpoint grant <file|->`): its own signature is its authority. The endpoint verifies it once, against the head at arrival (`verifyGrant`), requires its `machineKey` to be a key the ledger holds, and keeps it only if its `version` is above the member's current one. It ends when replaced by a higher version or when its signer's key is revoked; a member is then grantless until a higher version arrives.
- **Policy applies to effects, not envelopes.** Read-only refuses every request graded above `view`, whatever message carries it (`read-only`), and serves `list` and `view` calls and subscriptions, as sminos does today. The ceiling bounds a spawn's permission mode (`sminos.spawn`'s `permission_mode`; `session.launch` when O7 offers it) by the order `plan` < `default` < `acceptEdits` < `auto` < `dontAsk` < `bypassPermissions`, with `settings` reading the machine's `defaultMode`. A spawn's `checkout` must be one `CheckoutSource` knows. A spawn's args may carry no field outside an allow-list (Interfaces §G): no flags, environment or shell.
- **Queries are bound to their sender.** A `query` is answered only to a device of the member who sent the operation, and only while that member holds `view` on its target. The executing side returns the operation's stored member and fingerprint with its answer, and the endpoint compares them before it says anything (M7). An `opId` is a de-duplication key, never a capability.
- **Step-up** (RL §5.6) is required for a spawn, an approval on a session the member doesn't own, a change of owners or shares, a machine-admin action, and a `shell` request by a member who isn't a machine owner (P5's O10 item 8). The endpoint verifies the step-up signature over the canonical action against the device's `stepUpPub`. A machine owner's own approvals need none (RL §10.5).
- **Classes.** `web-cards` may: read listings; subscribe to the `cards` view (Interfaces §B) of a session its member owns; answer a question and approve or deny a permission on such a session, each `act` carrying a WebAuthn assertion that `verifyWebAuthn` accepts against the device's passkey, with the counter kept in `webauthn.json`. Its answer may only take or refuse what was asked: a lane B permission answer carries no `updatedInput` and only `scope: 'once'`, and a lane A `decide` carries no `scope`, so a phone can neither run a command other than the pending one nor write a lasting permission rule; anything more is refused `class`. Everything else from that class is refused (`class`), which is O13's acceptance 3 at the machine. The browser's prompt doesn't show what is signed (RL §5.10), so this is what keeps a hostile deploy of the phone's code to RL's accepted residual: approving a pending request as it stands.

**Proves.** Acceptance 8 and acceptance 4's ceiling and checkout cases. `grades.test.ts` through a real channel (fake services answering `session.status`, `session.pendingRequest` and `session.queue.list`; fake sources): each class of refusal, `ungraded` for a fixture namespace, the routing classes refused for an owner too, each by-effect row including a slash command, a permission answer, an unpause of a queue holding `/clear`, and `no-rule` for `session.ui.press`; read-only refusing a `converse`-graded call and serving a `view` one; step-up demanded and accepted, a machine owner's `pty.spawn` authorized without one and a `shell`-grant holder's only with one (authorization only: M7 withholds its execution); a grant raising a member to `spawn` and a lower-version grant ignored, a grant for a key the ledger doesn't hold refused, a revoked signer ending a grant; `web-cards` refused a `send` and accepted an owned-session answer with a good assertion and refused one with a replayed counter; a `web-cards` permission answer with a valid digest and assertion but a changed Bash command in `updatedInput`, or with `scope: 'local_settings'`, refused `class`.

### M6 — The sminos socket (RL10)

**At its end.** The endpoint serves RL10 (Interfaces §D) on a 0600 socket, writes `rl10.json`, and stands where the hub stood for sminos: it relays the log plane to RL1 with signatures and attestations added and verification done, refuses replayed events, takes the session lane, routes lane A actions with their context, and sends identity, policy, revocations and the org directory down. It fills M5's sources. A conformance fixture pins the conversation for O12's phase 2.

**Touches.** `src/endpoint/rl10/server.ts`, `log-relay.ts`, `signature-ledger.ts`, `inbound-index.ts`, `attest.ts`, `legacy.ts`, `members.ts`, `words.ts`, `org-directory.ts` (new); `test/endpoint/rl10/*.test.ts`, `test/endpoint/rl10/fake-sminos.ts`, `test/endpoint/rl10/conversation.json` (new).

**Decisions.**
- **RL10 is DX2's frame vocabulary on a local socket, with no HMAC coding, plus what the endpoint now owns.** sminos's uplink already speaks DX2 to the hub, so its phase-2 client keeps its frame handlers and swaps the transport (SSE and POST for a socket) and drops the codes. Rejected: a new vocabulary, which rewrites sminos's uplink for no gain in what the frames say.
- **Discovery and authentication.** `rl10.json` (O2's Interfaces) gains `token` (64 hex, from 32 random bytes) and `protocol` (the major, 1); it stays 0600 and names the socket's path after O2's long-path fallback. sminos's first line is `hello` with the token; the endpoint writes nothing before the token checks out, and closes on a wrong one. The socket is created at a temporary name, `chmod 0600`, renamed, in a directory `assertPrivateDirectory` accepts.
- **Signed once, kept, resent byte-identical** (RL §5.7). An event sminos uploads is signed by the endpoint as it leaves (`signEvent`, before DX1's seal), and its `sig`, its `attest` block (below) and the DX1 `mac` while dual-coding are kept in the signature ledger keyed by `(project, writer, seq)` with the canonical body's hash. A resend rebuilds the uploaded bytes from sminos's event and the stored parts; a different body at a stored position is refused to sminos as `conflict` and logged, never re-signed.
- **The owner attestation** (RL9; O12's item 3, "built by the endpoint"). An event a session writer (`<name>/<session>`) uploads gains `attest {owners, ownersProof, origin, stateVersion}` from that session's record, with `@machine` resolved against the head whose version it names, covered by the event's v2 signature. If the hub's v2 shape check refuses the field, M6 admits it there additively (the Project DO's courtesy check, in `apps/desk-hub`), with a vector. An arriving event's attestation is checked with `verifyAttestation` and goes down with the event as its verified `owners`; one that fails goes down with `owners: []` and a log line, so sminos labels the sender's owners unverified.
- **Proofs travel with their actions.** A lane A spawn's signed action is carried to sminos as its `rpc`'s `proof`, and sminos keeps it in the new session's record as `ownersProof` (O12's phase 2), so the next attestation carries it. Owner additions, and their proofs, come with O8's sharing, executed by sminos under its ledger like any lane A action (Decision Log).
- **Dual-coding until the org key retires** (RL §9). Outbound events carry the v2 signature and DX1's `mac` so machines not yet moved can read them. The DX1 key is handed over once: at RL10's first `hello` on an endpoint that holds no `legacy.json`, the endpoint asks for it (`legacy-key?`), sminos answers from its `hub.json` when the org matches, and the endpoint keeps it at 0600. O14's final brief deletes it (`mawsd endpoint legacy retire`). With no legacy key, events go out v2-only and legacy events can't be checked.
- **Verified before import.** An arriving event is verified by `verifyEvent` against the head and certificates. One that verifies goes down with `signer` (`{kind: 'device', member, device}` or `{kind: 'machine', ref, name}`). A v1-only event from a machine not yet moved, whose DX1 code verifies under the legacy key, goes down with `signer: {kind: 'legacy'}`, and sminos delivers it only as a peer message marked unverified (RL §9). Anything else is refused up the log plane as `rejected` and never reaches sminos.
- **A signed event is imported once.** The v2 signature covers a `hub/<member>` event's body and `created` but not the position the hub gives it, so a hostile hub could repost a person's signed words at the next sequence as a new instruction; sminos's DX1 nonce index stopped that until now (`sminos_hublog.py:517`) and leaves with the codes. So the endpoint records each arriving v2 event's signed content, keyed by SHA-256 of its signing input (which binds org and project), with the first position it arrived at, in `inbound/<project>.idx`. A copy at another position is refused (`replayed`) and never reaches sminos. The index keeps 30 days, and a `human` event whose signed `created` is more than 24 hours old is never delivered as words, so the window bounds both.
- **Words are decided at delivery** (RL §5.7; O12's item 2). Before it delivers a `human` event as words, sminos sends `words? {id, session, event}` with the event exactly as it stored it. No answer is no words, and the delivery stays owed and is retried as a failed push is. The endpoint verifies the event again against the head at that moment and checks the inbound index holds it at that position, then answers `words` only when a device signed it and its member holds `converse` on the session (M5), or the machine signed it as its operator path and the session is on this machine and owned by the machine's owner; `peer` otherwise; `refuse` for a revoked signer or a replay. A new head's removals also go down as `revoked {version, devices, members, keys}`, so sminos can stop retrying owed words at once.
- **The session lane stops at the endpoint.** sminos's `session` messages (presence, `raised`, `settled`, `delivery`) and `machine` message come up RL10 and never reach the hub: requests and their tool input travel only over channels (RL §6.2, §7.1). The endpoint derives listings and `notify` from them (M3) and serves them to subscribers (M8).
- **Members.** sminos sends `member` for every session it knows, at `hello` and on each change: the session record's provenance and ownership, the lane, state, title, project, alias, directory and the bridge's launch, and for lane B the engine session id. This is the machine-held RL6 record behind M5's `RecordSource`, and what the endpoint lists and attests from. A lane B session is addressed by MAWS's `appSessionId`, stable across `/clear`; the endpoint joins it to sminos's member by `engineSessionId`, read from `engine.sessions` through `dispatch`. Nothing in O10 writes a record's `access`, `shares` or owners: O8 adds those actions (absent means `listed` and none, O12).
- **Lane A actions keep their context to the effect.** An authorized `act` on a lane A session goes down as DX2's `rpc` frame without its `mac`, carrying `opId`, `opCreated`, `created`, the member and device, the operation's fingerprint, its `context` (`{lane: 'A', session, launch}`), its `requestDigest` and, for a spawn, its `proof`. O12's phase 2 keeps member, device, fingerprint and target in its ledger entry, and fences every remote RPC against the context's `launch` at its effect, whatever path carries it: the bridge immediately before it acts, and every path that bypasses the bridge (steer's supervisor or inbox fallback, for one) refuses a remote RPC `context` rather than run it unfenced. O10 offers lane A only the RPCs that path covers (Interfaces §G); `resume`, `retire` and `stop`, which run outside the bridge, are not offered until a child that needs them fences them. sminos's `rpc-result` comes back and is acknowledged with `rpc-ack`, as today. `query` and `tombstone` go down to sminos's `Rpcs.query` and `Rpcs.tombstone` (O12 M2), which nothing called until now.
- **The org directory.** RL1 carries no `org` frame, so the endpoint sends sminos DX2's `org` shape built from the head: `projects` from the state's `projects`, `machines` from its machine entries and live certificates by name. A machine's `online` is unknown on RL1 and goes as `false`, with `seen` the newest event time the endpoint has relayed from that machine's writers.
- **Identity.** The `welcome` carries what sminos reads from `hub.json` today: `org`, `hub`, `name`, `former` (every other name `machineNames` binds to this ref) and `enrolled`, plus the ref and the policy. sminos needs them in local-only mode (O12's phase 2).

**Proves.** Acceptance 5's endpoint half. `fake-sminos.ts` replays `conversation.json` (each line a frame, its direction and the endpoint's expected answer) against the real server and the local hub: the token refused and accepted; the log plane relayed with a v2 `sig`, an `attest` block and a DX1 `mac` (the dual-coded event verifies under both, as O11's vector does), a forced resend byte-identical, a body change at a stored position refused; arriving events verified and annotated with signer and verified owners, a forged one refused up as `rejected`, a legacy one annotated `legacy`, the same signed `human` event reposted at the next sequence refused `replayed` after an endpoint restart too; `words?` answered words, peer and refuse, including import → endpoint restart → one of a member's two devices revoked → an owed event from the revoked device refused and one from the other still words; `revoked` sent after a head that drops a device; an RPC down carrying its context, and a case where the launch changes after admission, which the fixture marks for the bridge's refusal on sminos's side; `query` and `tombstone` passed through; the legacy key handed over once and never logged. `conversation.json` is the fixture O12's phase 2 copies into doperpowers' `sminos/tests/` with this commit's sha, as `codes_parity.py` copies DX1's vectors.

### M7 — Actions to their executing side (RL4), with their ledgers

**At its end.** An `act` is checked at the endpoint for freshness and replay, authorized (M5), and handed to the side that runs it, which keeps the one durable ledger for its `opId`, bound to the operation and its sender: sminos for lane A (O12 M2, extended by its phase 2), the engine host for lane B (new here), and the endpoint for its own actions (new here). An action whose executor keeps no ledger is withheld. `query` reaches the same ledger and answers `not-received` only once a late copy can no longer run.

**Touches.** `src/endpoint/actions.ts`, `freshness.ts`, `endpoint-actions.ts`, `queries.ts` (new); `src/shared/host/op-ledger.ts` (new), `src/engine-host/ipc.ts` (the `host.op` commands), `src/engine-host/supervisor-files.ts` (the ledger's file), `src/shared/ipc/schema/host.ts`, `names/host.ts`, `grades/host.ts`, the wire manifest; tests.

**Decisions.**
- **The endpoint's checks, in order:** the shape (`opId` 16–128 base64url as sminos's `OP_ID_RE`, `nonce` 16 bytes, times in ISO milliseconds); `created` within 60 s of the machine's clock either way (`stale`); `opCreated` no later than `created` + 60 s (`malformed`); `opCreated` within `OP_HORIZON = KEPT_S − 3600` s (`expired`); the nonce unseen from this device in the last 120 s (`replayed`); authorization (M5); the session's `context` against the member state (lane A: the bridge's launch; lane B: `launchId` and `engineSessionId`) (`context`). The endpoint keeps no ledger for others' actions (RL §4.7): only the nonce window, in memory, which a restart loses safely because freshness outlasts nothing past 60 s.
- **Every ledger binds an `opId` to one operation and one sender.** An entry holds the member, the device, the target and the operation's fingerprint (M1: the canonical action without what a reseal changes). A known `opId` with another fingerprint or member is refused `op-conflict` and reveals nothing of the stored one. One module, `src/shared/host/op-ledger.ts`, keeps the engine host's and the endpoint's ledgers (append, `fsync` before the run, compaction to `KEPT_S` at start, a torn last line ignored, unreadable means every op `unavailable`), and O3's services in `mawsd` can keep theirs the same way when main's commands move there. sminos's ledger gains member and fingerprint in O12's phase 2.
- **Lane B's ledger lives in the engine host, beside the session** (RL §4.7: claim and result in one process, so no crash window splits them). No such ledger exists today, and no other child names it; O10 builds it because RL4 ends at the executing side. `host.op {opId, opCreated, member, device, fingerprint, name, input, context, requestDigest?}` claims the id in `<profile>/supervisor/ops.jsonl` before it runs the named engine-host command through the engine host's own handler table, then appends the result. A known id answers its stored entry (after the binding check) and runs nothing; a claimed id with no result after a restart answers `in-progress` until `KEPT_S`, and the device sees *outcome unknown*. It runs only engine-host-owned commands; a main-owned one (`session.start`, `archive`, …) is refused `unavailable` remotely until O3 moves it. **The architect's area:** this changes `src/engine-host/`, and the PR names it.
- **Lane B's context** is `{lane: 'B', launchId, engineSessionId}`, rechecked by `host.op` against the session's current status, so an action sealed before a resume (a new launch) or a `/clear` (a new engine session id) is refused `context`. O16's holder adds its own fields additively. `host.op` also checks a `session.answer`'s `requestDigest` against the broker's pending item (`request`, `tool`, and `input_sha256` of its input) and refuses `digest-mismatch`.
- **The endpoint's own actions** run under its own ledger, `<stateDir>/ops.jsonl`: `endpoint.grant` (M5) and `endpoint.state` (an admin delivering a signed state, RL §5.2's direct revocation; `done` only after the head is on disk, M2). Both take effect inside the endpoint's own process, so claim and effect never cross a process boundary. Changes to a session's owners, access or shares are written by sminos into its record, so they are sminos-executed actions under sminos's ledger, with an acknowledgement only once the record is on disk; O8 adds them with its sharing, and O12's phase 2 builds their sminos side.
- **No ledger, no action.** An `act` for any other executor (a `pty-host` command such as `pty.spawn` or `pty.kill`, a `machine`-owned one such as `daemon.restart`) is refused `no-ledger`, so acceptance 3's once-only rule holds for everything the endpoint runs. O3 (`mawsd`'s services) and O7 (remote terminals) lift it for their commands when their executors keep ledgers.
- **Queries, and the late copy.** A `query` names the executor its `act` went to (`sminos`, `engine-host` or `endpoint`), so it routes without the endpoint remembering anything. The executor answers with the operation's stored binding: member, device, fingerprint and target. The endpoint answers the asker only when the asker's member is the stored member and still holds `view` on the stored target (the stored member's `spawn` right, for a spawn's machine target), and otherwise answers `refused {reason: 'grade'}`, revealing nothing; the asker's own words about the target are never trusted. When the executor has no entry, the endpoint asks it to tombstone the id, and answers `not-received` only if the tombstone took; if the original claimed the id in between, the tombstone fails and the endpoint returns the claim's state instead (after the same binding check). `host.opQuery {tombstoneIfAbsent: true}` and the endpoint's own ledger do both under one lock; for lane A it is sminos's `query` then `tombstone`, whose claim check is atomic under `op_lock`. Only after `not-received` may the device resend under a new `opId`.
- **Holds.** Each action in flight holds `mawsd` (`hold('op')`) until its result is recorded; `stop()` stops taking actions, waits up to 2 s for in-flight ones to record, and closes channels with `restart`.
- **Outcomes.** `ack {opId, state: 'accepted'}` once the endpoint's checks pass and the action is handed to its executing side, or `refused {reason}`; `done {opId, outcome}` when the executing side answers, its own refusals (a tombstoned id, `op-conflict`, `digest-mismatch`, `context`) included.

**Proves.** Acceptance 3's action cases against fakes and the real engine host, for each executor (sminos through the fake, the engine host, the endpoint): `stale`, `malformed`, `expired` (also for an id the ledger no longer holds), `replayed`, a reseal answered from the ledger with the session showing one effect, `op-conflict` for a reused `opId` with other arguments, another member's query and a same-member query after the member's `view` on the stored target was withdrawn (naming another session they still see changes nothing) refused, `query` answering each state after an endpoint restart, a lost acknowledgement for a lane A spawn resolved by query, `not-received` given only after the tombstone took, the original arriving between the lookup and the tombstone (the tombstone fails and its state is returned), a late copy refused after a tombstone, `context` after a relaunch, `digest-mismatch`, `unavailable` with an unreadable ledger, `in-progress` after the engine host is killed between claim and result, and `no-ledger` for `pty.spawn` and `daemon.restart` (through the fixture offer table, since production's doesn't offer them). `op-ledger.test.ts` covers the file: `fsync` before run, compaction, a torn last line ignored.

### M8 — Subscriptions and remote reads (RL3)

**At its end.** A device subscribes to a lane A or lane B session with a cursor and gets `replay`, `snapshot` or `missing`, then live events under credit, for as long as it keeps the grade the subscription needs; it reads through `call`; its subscriptions count as interest.

**Touches.** `src/endpoint/subscriptions.ts`, `plane-a.ts`, `plane-b.ts`, `calls.ts`, `interest.ts` (new); `src/engine-host/ipc.ts` and `src/shared/ipc/schema/session.ts`, `names/session.ts`, `grades/session.ts` (`session.pendingItems`); tests.

**Decisions.**
- **Lane A's cursor is the endpoint's.** sminos's plane has no ring and numbers each subscriber's messages from a snapshot at `n` 0. So each remote subscription holds its own upstream sminos subscription (RL10 `subscribe`), whose id is the cursor's `epoch` and whose `n` is its `seq`; the endpoint keeps a ring of that subscription's last 2 MiB of messages. A resubscription with the same epoch whose `seq` is still in the ring is a `replay`; otherwise the endpoint opens a fresh upstream subscription and answers `snapshot` under its new epoch. The upstream subscription outlives a dropped channel for the resume window (120 s), then ends. A `mawsd` restart loses every ring, so every resume after it is a snapshot: no loss, no duplicate. Rejected: one shared upstream subscription per session with a materialized state, which needs the endpoint to understand every plane message.
- **Lane B's cursor is the engine host's:** `epoch` is the `launchId`, `seq` the journal row. A resubscription on the current launch reads `session.events {afterSeq}` through `dispatch`: `complete` is a `replay`; otherwise, and on another launch, a `snapshot` of `session.status`, `session.queue.list`, `session.pendingItems` and `session.catalog`; a launch whose journal is pruned is `missing` with a snapshot. Live events come from `onEvent`, which until O3 delivers lane B events only while an app is attached: without one, the subscription sends `paused {reason: 'no-app'}` and, when `onAttachment` says an app is back, catches up by `session.events` and sends `resumed`. O3 replaces the source with its per-client subscriptions and the pause disappears; this is the only part of M8 O3 changes.
- **Pending items get a read.** The broker's items reach a client today only as the unsequenced `session.brokerItems` event in the connect burst, and `session.pendingRequest` needs an id already known. So M8 adds `session.pendingItems {appSessionId} → {items}` (engine-host-owned, `view`, additive under M7's `WIRE_MINOR` bump).
- **Replace-whole state is refreshed on every resume.** The broker's items, the queue and the catalog change outside the journal's sequence (`SessionStream` emits them as their own events), so a `replay` of events alone can leave a settled card or an edited queue stale. On every subscription and resume, `replay` included, the endpoint first starts holding the session's live events, then reads `session.pendingItems`, `session.queue.list` and `session.catalog`, sends them, then releases what it held. A live replace-whole event that arrives while those reads are in flight triggers one more read of its kind after them, so an older read never overwrites a newer change.
- **Credit.** Each subscription has a byte credit the device grants (initially its `sub`'s `credit`, at most 4 MiB) and tops up with `credit`. A subscription out of credit for longer than its ring holds is moved to a snapshot. Control messages (`ack`, `done`, `result`, `caps`, `paused`) never wait behind events (RL §4.4).
- **Snapshots are paged** at 256 KiB of plaintext per message, `last` on the final page.
- **The `cards` view** (for `web-cards`, M5) is a subscription that carries only a session's pending requests and their settlement: lane A's `raised` (which holds the tool and input) and `settled`; for lane B, each pending item hydrated by the endpoint with its originating request (`session.pendingRequest`: the tool and input, or the question and its choices) and the context an answer needs (`launchId`, `engineSessionId`, the request digest's fields). Its snapshot and every refresh carry the same projection, so a cold subscription can show and answer a request already pending, and it never carries the queue, the catalog or the transcript. The phone gets no general read for this: hydration is the endpoint's.
- **A session's capabilities** (RL7's per-session half) ride its plane: lane A's in the presence body's `capabilities.controls`, as sminos sends them today; lane B has none yet, and O7 defines them from the session's status and catalog. The device's own half is `caps` (M4).
- **Access is re-checked whenever it can change.** Each subscription records the grade it needs (`view`, or ownership for `cards`). On every change of the session's record (owners, access, shares: `RecordSource`'s change event) and every new head, the endpoint re-evaluates every open subscription and resumable cursor against the member's current rank, closes those that no longer qualify with `ended {reason: 'removed'}`, and drops their upstream subscriptions and retained cursors, so a resume can't restore what was withdrawn. Removing a `view` share from a `listed` session leaves `list`, which ends the subscription.
- **Interest** (OX5). A lane B subscription reports its session through `interest.report(<device>/<channel>, sessions)` and drops it when unsubscribed. A channel that closes keeps its report for the resume window, then drops it, so a vanished phone never keeps the MacBook's engine host from its idle release. Lane A sessions are sminos's and aren't in MAWS's interest union.
- **Calls.** `call` forwards a `list`- or `view`-graded command through `dispatch` (or, for `sminos.rows`, `sminos.diff`, `sminos.output` and `sminos.read`, down RL10 as DX2's frames) and returns its result; a `call` of anything graded higher is refused `act-required`. `daemon.status` answers `remoteDaemonStatus` (O2's local-only fields dropped). `endpoint.listings` answers the signed listing records of every session on the machine the member holds `list` or more on, `private` ones included for their owners and shares: the only way a private session's listing leaves the machine (RL §6.2).
- **Not here: remote terminals and documents.** A remote `pty.*` stream and a remote document channel need their own authorization (which session an artifact belongs to, read against edit, an actor the endpoint sets rather than the caller, read-only for a byte stream, step-up for a shell grant) that is part of the remote surfaces O7 builds. Until then `doc.*` is not in the channel vocabulary, and every `pty.*` and `documents.*` command is refused remotely (`not-offered`). O2's seam pieces for them (`onFrame`, the endpoint's document channels, the forced `credit: false`) stay for O7.

**Proves.** Acceptance 2 against the fake services and fake sminos: lane A replay inside the ring, snapshot after the ring and after an endpoint restart, the 120 s resume window; lane B replay by `afterSeq`, snapshot on a new launch, `missing` for a pruned journal, `paused` with no app and the catch-up when one attaches; a subscription made while a question is already pending, with no later broker change, showing the question; a card settled and a queue edited only while the channel was down, both current after a same-launch `replay`; a cold `cards` subscription, and one resumed by snapshot, rendering a question and a permission already pending and answering them, with no queue or catalog in the view; a broker change during the snapshot's read ending in the newer set; no event lost or doubled across a forced channel drop on either carrier (each event's cursor checked against the source's own numbering); credit exhausted moving to a snapshot; a share removed and a session made `private` each ending a live subscription and refusing its resume; `act-required`; `not-offered` for `pty.attach` and `documents.open`; `remoteDaemonStatus`; interest reported, held through a resume window and dropped after it.

**Decisions.**

**§A. The channel (RL2), `apps/org-protocol/src/channel.ts`.**

Domain `smns-rl2-v1`. Every signature is ECDSA P-256 over SHA-256, IEEE P1363 (`r ‖ s`), by `signInput` / `verifyInput` with that domain; bytes in JSON are canonical base64url; JSON is `canonicalize`d wherever it is hashed or signed.

    h1 (device → endpoint, the first payload):
      { t: 'h1', protocol: { major: 1, minor: 0 }, build, capabilities: string[], org, machine: <ref>, member, device,
        clientClass: 'native-mac' | 'web-cards', stateVersion: <device's head version>,
        e: <ephemeral P-256 public key, raw 65 bytes>, n: <32 random bytes> }
    h2 (endpoint → device):
      { t: 'h2', protocol: { major: 1, minor: 0 }, build, capabilities: string[], stateVersion, keyId: <machine key id>, e, n,
        states?: Signed<OrgState>[], transitions?: RootTransition[],
        sig: Sign(machineKey, { role: 'machine', h1, h2: <h2 without sig and mac> }),
        mac: HMAC(kmR, { role: 'machine', machine, keyId }) }
    h3 (device → endpoint):
      { t: 'h3', states?, transitions?,
        sig: Sign(channelKey, { role: 'device', h1, h2: <h2 without sig and mac>, h3: <h3 without sig and mac> }),
        mac: HMAC(kmI, { role: 'device', member, device }) }

    Z     = ECDH(own ephemeral private key, peer's e)            // 32 bytes
    salt  = SHA-256(canonical(h1) ‖ canonical(h2 without sig and mac))
    PRK   = HKDF-Extract(salt, Z)
    kmR, kmI      = HKDF-Expand(PRK, 'smns-rl2-v1 mac r' | 'mac i', 32)
    kI2R, kR2I    = HKDF-Expand(PRK, 'smns-rl2-v1 key i2r' | 'key r2i', 32)     // AES-256-GCM
    ivI2R, ivR2I  = HKDF-Expand(PRK, 'smns-rl2-v1 iv i2r' | 'iv r2i', 4)
    channelId     = HKDF-Expand(PRK, 'smns-rl2-v1 id', 16)                      // logs and caps only

    frame  = header ‖ AES-256-GCM(key[epoch], nonce = iv[epoch] ‖ u64 BE seq, aad = header, plaintext)
    header = u8 version (1) ‖ u8 keyEpoch ‖ u64 BE seq                           // 10 bytes
    seq: one counter per direction for the channel's life, from 0, never reset
    plaintext = u8 kind ‖ body ; kind 0 JSON message (UTF-8); other kinds are reserved for O7's remote surfaces and close the channel until defined
    plaintext ≤ 256 KiB; a larger JSON message travels as { t: 'part', id, index, count, data } messages
    receiver: seq = last + 1, with keyEpoch = current or current + 1 (mod 256); anything else closes
    rekey: after 2^20 frames in an epoch or 24 h, key' = HKDF-Expand(key, 'smns-rl2-v1 rekey', 32),
           iv' = HKDF-Expand(key, 'smns-rl2-v1 rekey iv', 4), epoch + 1; the sequence keeps counting

    export function openChannel(io: ByteDuplex, me: DeviceIdentity, org: OrgView): Promise<Channel>;     // the device
    export function acceptChannel(io: ByteDuplex, me: MachineIdentity, org: OrgView): Promise<{ channel: Channel; peer: DevicePeer }>; // the endpoint
    export interface ByteDuplex { send(bytes: Uint8Array): void; onBytes(listener: (bytes: Uint8Array) => void): void; close(reason: string): void }
    export interface Channel { send(message: ChannelMessage): Promise<void>; onMessage(listener): () => void; close(reason: string): void; readonly id: string }
    // OrgView: the verifier's head, pins and certificates, with an `advance(states, transitions)` that verifies and adopts successors

The endpoint processes nothing but `h1` and then `h3` until `h3` verifies; it checks `h1.machine` is its ref and `h1.org` its org. The device checks `h2` against the machine entry (or live certificate) for its ref in its head, after adopting any `h2.states`.
