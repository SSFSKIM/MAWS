## Purpose

Today the desk hub is a party to trust. Every machine and every browser holds one shared org key, any holder can write as anyone, and the hub can't tell people apart. After this child, the hub is a relay and a store of signed things:
- it keeps the org's signed, hash-chained member and machine list, and refuses forks and rollbacks;
- it carries sealed channel frames between a person's MAWS app and a machine without being able to read them;
- it stores the project log with each writer's own signature;
- it pushes a notification only to the people who own the session it concerns.

Machines and the phone not yet moved keep working on today's paths throughout. What someone can do afterwards: on the staging hub, a test device and a fake machine prove the whole flow. A signed org of one is set up. A machine enrolls with its own key. Frames cross the hub sealed. A v2-signed log event is stored and refused when forged. A push reaches only an owner's device. The relay's latency is measured. Production keeps serving the owner's machines and phone unchanged.

## Constraints that bind every milestone

- **The trust model is RL's.** The hub's checks are courtesy (RL §5.5, §7.1): it refuses early to save a round trip, but nothing it accepts confers authority. Machines and apps verify for themselves (O10, and the app's side).
- **One protocol package.** Every RL shape, signing input and verification rule lives in `apps/org-protocol` (M1). The hub, desk-web (O13), `mawsd` (O10) and the app's main import it, and nothing reimplements it. This child creates it with RL5 and RL8; O10 extends it with RL2–RL4 and RL10. It uses WebCrypto only (`globalThis.crypto.subtle`), which the Workers runtime, Node 22 and browsers all provide. Its relative imports carry `.ts` extensions, so Node's type stripping loads it unbundled.
  - It lives under `apps/`, not a new `packages/`. The workspace glob, the gate's tree selection (`.github/scripts/gate-affected.mjs`) and the eslint layout then take it with no root rework.
- **`desk-hub/protocol` stays stable.** Desk-web, the fake machine and the deploy tool import 104 names from it. Nothing is removed or renamed. Its RFC 8785 canonicalizer moves into the package and `desk-hub/protocol` re-exports it, so there is one canonical form.
- **No new Durable Object class.** RL §7.1 maps onto Registry, Machine and Project, and a new class or a renamed one needs a wrangler migration tag (an owner gate). Tables change only in constructor code: `CREATE TABLE IF NOT EXISTS` plus additive columns, never a transform of existing rows.
- **Every call between objects tolerates the other version.** After a deploy, objects holding connections run the old code for about 5 minutes, and calls between Registry, Project and Machine cross versions (`src/objects/retry.ts`). A new RPC method is called with a fallback when the callee lacks it. A changed one keeps its old signature beside the new one.
- **Today's paths stay whole for machines and the phone not yet moved** (acceptance 8): DX2 (`/machine/stream`, `/machine/frames` and their frames), DX3 (the project and grid sockets), DX6 (`rpc`), DX7 (wrapped keys, the v1 enrollment and provisioning codes, push to members). Desk-web's reader requires `mac` on every event (`apps/desk-web/src/log/verify.ts`). The hub therefore never strips a `mac`, and v1 events keep flowing unchanged.
- **Live tests run on staging only.** Production gets this child's code only through O13's and O14's deploys, by the desk's pre-approved scripts and after acceptance 8 holds. No agent runs wrangler against `desk-hub`. The deploy tool refuses a target that doesn't match its config (M2).
- **Secrets.** The Access setup tokens are read only inside a script, from `~/.config/claude-secrets/projects/-Users-new-Developer-GitHub-doperpowers/`, and never printed. The same goes for any Access token taken from `cloudflared`. No log line, test fixture or committed file holds a token.
- **Tests** are vitest in Node, driving Miniflare as the hub's existing suites do (`apps/desk-hub/test/support/local.ts`). Hibernation is forced with `unsafeEvictDurableObject` where a behaviour depends on it. Verify on CI with `ci-gate`, not by running the gate's commands locally. Before `ci-gate`, run `npx eslint` on the touched files: the local typecheck and vitest don't lint (MAWS #92).

## Plan of Work

### M1 — The protocol package: signed state and signed events

**What exists at its end.** `apps/org-protocol` builds, typechecks under the neutral-runtime rules, and its tests pass in Node and in Miniflare's workerd. It provides:
- P-256 key handling;
- RL5's org state with its verification, including root transitions, grants and delegation certificates;
- RL8's event signature with the writer-to-signer rule;
- the listing record;
- vectors in `apps/org-protocol/vectors/`, which every consumer's tests replay.

**What it touches.** `apps/org-protocol/` (new). The root `package.json`'s `typecheck` script and the root `vitest.config.ts` projects. `apps/desk-hub/src/protocol/canonical.ts`, which moves and is re-exported from `index.ts`. `apps/desk-hub/types/neutral-runtime.d.ts`, gaining ECDSA, ECDH, HKDF and AES-GCM (it moved to `apps/org-protocol/types/`, Decision Log). The eslint neutrality rule's path list.

**Interfaces.** Exposes everything in Interfaces §A to M3–M7, to O10 and to O13.

**Decisions.**
- **Verification is pure and complete.** Each verification function takes everything it needs as arguments: the previous state, the pinned roots and the recovery key. It returns `{ok: true}` or `{ok: false, code}` with the codes in Interfaces §A. Machines (O10) use these same functions as their real check, so a hub-only shortcut would become a machine bug.
- **The writer-to-signer rule** lives in the package:
  - `<machine>/…` writers are signed by that machine's key in the state, or by a machine certificate of a live delegation whose prefix covers the name;
  - `hub/<member>` writers are signed by a device of that member;
  - `legacy/…` writers are v1-only and are never v2-verified.
- **What a v2 signature covers** is exactly what DX1's `covered` covers for the same writer kind (`apps/desk-hub/src/protocol/codes.ts`), minus both `mac` and `sig`. So hub-assigned positions (`writer`, `seq`, `ts` for `hub/<member>`) are outside a device's signature, as they are outside today's code.
- **A v2 log signature binds org and project** (Interfaces §A's exception), so `signEvent` and `verifyEvent` take `{org, project}`, and a vector proves that an event signed for one project fails in another.
- **An endorsement signs a payload that excludes itself:** `DeviceEndorsement {org, member, device}`, where `device` is the entry without its `endorsement` field. The containing state's signature still covers the finished entry.
- **Dual coding order.** The v2 signature is made first. The v1 `mac` is then computed over the event with `sig` present, because DX1 covers everything but `mac`. Old sminos and desk-web verify such an event unchanged. A vector pins it.
- **The canonical move is byte-for-byte.** `desk-hub/protocol`'s vectors (`codes.json`, `machine-project.json`) must still pass unchanged after the canonicalizer moves.

**Not touched.** No hub behaviour, no route, no DO. RL2–RL4 and RL10 are O10's.

**Proves.** The vector suite, run from `apps/org-protocol`. It includes a successful second-device endorsement, its rejection when a covered device field changes, and a cross-project replay rejection. A vector-replay test in `apps/desk-hub` that imports the package through the workspace, proving the bundling path works for the Worker.

### M2 — The staging hub

**What exists at its end.** `desk-hub-staging` serves at `https://desk-hub-staging.opencognita-platform.workers.dev`, with its own Access applications and policies, its own `VAPID_KEY`, the same service-token API token as `CF_API_TOKEN`, and the org id `staging-ssfskim`. It runs master's hub and desk-web. The owner has signed in once in a browser and run `cloudflared access login` for it once. `deployment probe --config deploy/staging.json` passes.

**What it touches.** `apps/desk-hub/deploy/` (config.ts, deploy.ts, redeploy-check.ts, the commands that read `config.host`, README.md) and a new `apps/desk-hub/deploy/staging.json`. A script `/tmp/dsk-scripts/deploy-staging.sh`, modelled on `/tmp/dsk-scripts/deploy-master.sh` and kept out of the repository because it reads the secrets directory.

**Decisions.**
- **Every wrangler call names its target.** `deploy`, `secret list` and `secret put` pass `--name <config.worker>`. `deployHub` first reads the wrangler target it is about to use and refuses when it isn't `config.worker`. `redeploy-check` takes the same path. Without this, a staging config would push staging's variables onto the production Worker. That is today's behaviour, since no call passes `--name`.
- **The staging org id is `staging-ssfskim`, never `ssfskim` and never `ssfskim-<suffix>`.** Machine service tokens are named `desk-<org>-<machine>` in the account-wide namespace, and redemption deletes every token of that name first. A staging org named `ssfskim` would delete production machines' credentials, and so would `ssfskim-staging`: its machine `x` makes the same token name as production's machine `staging-x` (Decision Log, 2026-10-27).
- **Member admission.** Access sits in front of the whole host, so an email the policy doesn't list never reaches `Registry.resolve`. Staging's people policy is therefore an email list that M3's new command `deployment access-sync` reconciles to the org state's member emails: it reads the head with the owner's Access token and upserts the policy by name. Until a state exists it lists the owner alone, as production's does. A member added, or an email changed, is admitted only after `access-sync` runs. On production that is an Access change and waits for the owner. Rejected: admitting any identity the team's login accepts and leaving membership to the Registry alone, which opens the hub's surface to every email that can authenticate. One-time PIN login is not a required step (Decision Log, 2026-10-27): staging's app lists it among its allowed methods only if the account already has one, and creating one is an account-level change outside the owner's approval. Agents' test clients use the owner's Access app token from `cloudflared access token -app=<staging url>`, read inside a script and piped to the tool. The fake machine uses a staging service token it enrolls for itself.
- **The README** documents both deployments and stops hard-coding the production URL in commands.

**Not touched.** Production's Worker, Access objects, secrets and Durable Objects. Verify this by listing them before and after.

**Proves.** Acceptance 1.

### M3 — The Registry's org-state chain, members and devices

**What exists at its end.** The Registry stores RL5's chain and serves its head and its history. It accepts a genesis state once and successors only on the head, and it keeps root transitions. Its `members` table becomes the hub's projection of the head, mapping email to member id for Access admission, with role. Machines are projected keyed by `ref`, with the key and name as attributes (P5 DL 21). A new `devices` projection maps device id to member, class and optional Access client id (for U9). Member management happens by signed successors, with no new admin-only mutation routes. The device pairing exchange exists.

**What it touches.** `apps/desk-hub/src/objects/registry.ts` (new tables, `resolve`, `ensureOrg`), `apps/desk-hub/src/worker.ts` (the routes in Interfaces §B) and `apps/desk-hub/src/identity/`. New tests in `apps/desk-hub/test/`.

**Interfaces.** Consumes §A. Exposes the §B routes to M4, M7, O10 and the app. Exposes a `Registry.head()` RPC and the `Project.stateAdvanced` announcement to M5. Adds `deployment access-sync` to the deploy tool (M2's policy, reconciled from this milestone's state).

**Decisions.**
- **Genesis.** A genesis state is accepted only when the Registry holds no state, when it comes from the Access identity of `ORG_ADMIN_EMAIL`, and when that email's member entry in the state carries the id the `members` table already holds for it. Every log carries `hub/<id>` for good. A genesis that renames the bootstrap member is refused `409 genesis-member`.
- **Successors are verified by the package** against the stored head (`verifySuccessor`). The hub refuses with the package's code as `409 <code>` and keeps nothing. A successor that loses a race is refused `409 not-head`, and its writer retries on the new head (RL §5.2, "Writers are serialized").
- **Root transitions** are stored beside the chain, and a successor after one must verify against the new roots.
- **Machines read the state too.** `GET /machine/org/state[?since=<v>]`, with the machine principal, returns the same head, chain, transitions and certificates as the member route, since the Worker keeps member and machine routes apart. RL1's `state {version}` notice points there. It is proved with the fake endpoint's own service token.
- **Every accepted state is announced to the Projects.** The Registry calls `Project.stateAdvanced(version)` on each project it holds, retried as `retry.ts` retries, with a fallback for a callee on old code (M5 uses it).
- **Projection.** After each accepted state, `members` and `devices` are rebuilt from it in the same transaction. Before any state exists, `ensureOrg`'s bootstrap admin row keeps admitting the owner, so desk-web and DX2 work as today. A member removed from the state loses Access admission at once, and with it every socket the hub can close: the member's Project and Registry sockets are closed with `4403 removed`.
- **The pairing exchange.** A new device signed in as a member posts `{deviceId, class, keyStorage, channelPub, stepUpPub?, passkey?, mac}` as pending. Pending entries expire after 10 minutes. The member's other devices list them, and the hub never checks the MAC: the approving device does (RL §5.3). Accepting a successor that lists the device removes its pending entry.
- **The org-key routes are untouched**, `GET /api/org/keys` included. O14's final brief retires them.

**Not touched.** The DX7 key, enrollment codes v1, the grid, push. Delegations, listings and machine enrollment are M4.

**Proves.** Acceptance 2's chain, member and device parts. Tests also pin:
- a successor signed by a removed admin's key is refused;
- rollback after a transition is refused;
- the projection after a member's email change admits the new email and refuses the old;
- a pending device expires.

### M4 — Enrollment, delegations, listings and owner-only push

**What exists at its end.**
- **Machines enroll v2.** After redeeming as today, a machine posts its public key, its MachineRef and `MAC(k, name ‖ machinePub ‖ ref ‖ tokenId)`, and the enrolling member's device fetches it. The hub marks the machine `listed` once a state lists that key.
- **Delegations.** Provisioning keys re-issued as RL5 delegations carry `pub` and `owners` from the state. A VM booting under one posts a delegation-signed machine certificate, which the hub stores, serves beside the state and counts against `maxUses`.
- **Listings.** Machine-signed listing records (RL6's projection) are stored per `(machine, session)` at the highest revision and served to members.
- **Endpoint records.** Each machine's signed endpoint record (RL6: `{machine, addresses[], issued}`, the direct tailnet carriers of RL §4.1) is stored at the newest `issued` and served with the machine's listing.
- **Push.** Push subscriptions can bind to a device. `Registry.push` for a v2 notice selects the owners' devices from the session's listing.

**What it touches.** `registry.ts` (enrollment, the provisioning keys, the new listings table, `push`), `src/objects/provisioning-keys.ts` and `src/protocol/identity.ts`. The latter gets only additions: a v2 enrollment code `smns-enroll-v2.` that carries `{hub, token, roots, recoveryPub}` and no org key. The pairing secret `k` is added to the code by the app and never reaches the hub.

**Interfaces.** Exposes the §B enrollment, delegation, listing and push routes, plus `Registry.storeListing`, `Registry.notify` and `Registry.ownersOf` RPCs to M6.

**Decisions.**
- **Two machine states.** A v2 machine counts as hub-confirmed on its first authenticated request, as today. It is org-listed only once the state lists its key, and the two are kept apart (RL §5.3). Re-enrolling in place under the same name is allowed for an `active` machine when the code names it. Today only `pending` rotates.
- **Listing and endpoint rules.** A record's machine key is found in the head's `machines`, or in a live delegation certificate whose prefix covers the name. A certificate is live while its delegation is in the head and unexpired, and its use is counted. A listing whose `revision` isn't above the stored one is refused `409 stale-listing`. An endpoint record older than the stored one is refused `409 stale-endpoint`. One whose machine has neither key is refused `403 not-listed`, and one whose signature fails `bad-signature`. Removing the delegation from the state stops its machines' records from being accepted.
- **Owner-only push.** A notice for a session with a listing goes to the devices of its listed owners. A notice for a DX2 machine's session has no listing and keeps today's rule: every member not looking, which today is the owner alone. Notices carry `{project, machine, session, kind}` only (`PushNotice` gains `kind: 'waiting' | 'wrote'`, additively).
- **The offline sweep** keeps revoking the hub credential of a delegation's machine. Revoking the delegation itself is a state edit.

**Not touched.** The Project and Machine DOs. Where `notify` comes from is M6.

**Proves.** Acceptance 2's delegation part, carried through a delegated VM publishing a listing and an endpoint record, and their refusal after the delegation's removal. Acceptance 5 with a test-injected notice; M6 proves it end to end.

### M5 — The Project DO's v2 events

**What exists at its end.** The log store accepts v1, dual-coded and v2-only events.
- A v2 signature is verified against the org-state head the Project caches from `Registry.head()`. The cache is refreshed on every `stateAdvanced` announcement (M3), on an unknown key id (at most once a second), and whenever it is older than 60 s at the moment it is needed. A missed announcement therefore costs at most a minute of staleness, never acceptance against a state that is known to be old.
- `hub/<member>` v2 events from a device carry their own `nonce` field for resend dedupe.
- The conflict rule compares the full canonical body, signature included.

**What it touches.** `src/objects/log-store.ts` (`eventShapeError`, `byNonce`), `src/objects/project.ts` (`upload`'s writer rule, `human`) and `src/protocol/log.ts`. The last gets additions only: `sig` and `nonce` are optional fields.

**Interfaces.** Consumes M1's `verifyEvent` and M3's `Registry.head()`.

**Decisions.**
- **Shape.** An event needs a `mac` or a `sig`, or both. `sig` is `{kid, value}`, with `value` 64 bytes, P1363 r‖s, base64url. A v2-only `hub/<member>` event needs `nonce`, 16 bytes.
- **What is checked.** A v2 failure is refused `bad-signature`, and the uploader's refusal path reports it as today's `rejected`. A v1 `mac` is still unchecked by the hub. The writer rule (a machine uploads only `<itself>/…`) stays as it is.
- **A browser's `human`** keeps today's path. A device's v2 `human` arrives on the same socket message with `sig` and `nonce` instead of `mac`. The hub assigns the position as today and verifies against the member's devices.
- **No cache, no acceptance.** If the cache is older than 60 s and `Registry.head()` is unreachable, the v2 event is refused `503 state-unavailable`, and its sender retries. A v2 event is never stored unchecked.

**Not touched.** DX4/DX6 session-plane frames, which keep requiring their 32-byte `mac`; for moved machines those paths fall idle (RL §7.1). Desk-web.

**Proves.** Acceptance 4. Tests also pin:
- a dual-coded event's `mac` still verifies with DX1's `verify` (from M1's vector);
- desk-web's verify accepts a dual-coded event;
- a v2 event from a removed device is refused after the head moves, with the Project's cache already warm and the device's member still on an open socket, and no unknown signer seen first;
- the same refusal when the announcement is lost, once the cache passes 60 s.

### M6 — RL1 and the Machine DO relay

**What exists at its end.** A machine can hold one WebSocket, `GET /machine/socket`, admitted by its Access service token as today. Over it travel:
- the log plane in DX2's vocabulary;
- `hb` and `hb-ack` with the lease;
- `listing` and `notify` frames;
- the channel multiplex.

An app or device can hold a WebSocket to a machine, `GET /api/machines/<name>/socket`. The Machine DO relays channel frames between the two without reading them, keeps presence and pending counts, and calls the Registry for listings and push. DX2's SSE/POST link keeps working beside it.

**What it touches.** `src/objects/machine.ts`, `src/worker.ts`, `src/protocol/machine.ts` (additive) and the RL1 frame definitions in `apps/org-protocol` (Interfaces §C). `apps/desk-hub/fake-machine/` gains an RL1 client, the fake endpoint, which tests and M8 use.

**Interfaces.** Exposes RL1 (§C) to O10, and the app socket to M7, O7 and O9. Consumes M4's `storeListing`, `notify` and `ownersOf`.

**Decisions.**
- **RL1 reuses DX2's log-plane vocabulary.** Project `hello`, `have`, `log`, `resend`, `hb`/`hb-ack` and the paged backlog travel as JSON text messages. Leases stay in the Project DOs and are renewed by `hb-ack` as now. RL1 machines send no DX4/DX6 session-plane frames, and none are sent to them: those travel in channels, and the hub refuses such frames on RL1 `422 not-on-rl1`.
- **One generation counter for both transports.** A newer connection of either kind ends the older one, with cause `replaced`.
- **Hibernation.** Both socket kinds use the Hibernation API, and the DO keeps nothing in memory that it can't rebuild after an eviction:
  - the endpoint socket's attachment is `{kind: 'endpoint', generation}`;
  - the projects its stream opened are stored under `rl1-projects:<generation>`;
  - each app socket's attachment is `{kind: 'app', member, device?, channels: number[]}`, at most 64 channels per socket, inside the 2 KiB limit;
  - after an eviction, the channel-to-socket map is rebuilt from `getWebSockets()` and those attachments.

  The ends drive heartbeats, and the DO keeps no timers. The endpoint sends `hb {generation}` every `heartbeat_ms`. The DO renews the lease in every stored project of that generation, which is DX2's `renew` with the trigger reversed, and answers `hb-ack`. The app sends a ping. A code update drops hibernatable sockets, so after a deploy every socket reconnects and the generation rises. That replaces SSE's replacement probe for RL1, and M8's `redeploy-check` on staging measures it.
- **The channel multiplex** is binary messages, `[u8 type][u32 channel][payload]`:
  - `open` (app → DO; the DO assigns the id and tells the endpoint);
  - `data` (either way);
  - `close` (either way, with a u16 reason).

  The DO forwards at once, holds no buffer and applies no flow control: credit is RL3's, end to end. A send that throws closes that socket and every channel on it. When the endpoint disconnects, the DO closes every channel on it with reason `endpoint-gone`.
- **Size.** A message over 1 MiB is refused (`1009`). Channel payloads are expected at or under 256 KiB plus RL2's overhead (RL §4.2).
- **Presence and pending counts** come from the endpoint's `notify {session, kind, pending}`. The DO keeps the latest count per session for badges and calls `Registry.notify` for push when `kind` is `waiting` or `wrote`.
- **Who can open a channel.** The admission check is Access as a member or device of this org. The DO doesn't check grades: RL2's handshake and the endpoint's authorization do (RL §5.5).

**Not touched.** DX2's SSE/POST code paths, apart from the shared generation. The Project DO beyond receiving log frames from RL1 machines through the same `fromMachine` path.

**Proves.** Acceptance 3, and acceptance 5 end to end. Tests also pin:
- a DX2 stream and an RL1 socket for one machine replace each other by generation;
- an app's channel is closed when the endpoint reconnects;
- a session-plane frame on RL1 is refused;
- with both socket kinds open, a forced eviction (`unsafeEvictDurableObject`) followed by frames both ways delivers every frame on the right channel;
- heartbeats after an eviction keep the lease past a full `LEASE_MS`;
- a replacement by a newer generation, and a revocation, both close the old sockets after an eviction as before one.

## Interfaces and Dependencies

### A. `apps/org-protocol` (M1; O10 extends it)

Encodings: public keys are base64url of the uncompressed P-256 point (65 bytes). A signature is `{kid, value}`, where `kid` is the base64url of the first 16 bytes of SHA-256 over the 65-byte point, and `value` is the base64url of P1363 `r‖s` (64 bytes). The signing input is UTF-8 `"<domain>\n" + canonicalize(body)`. The one exception is the log event: its input is `"smns-hub-log-v2\n<org>\n<project>\n" + canonicalize(covered)`. Ordinary events and `HumanDraft` carry no project, and DX1 binds the project outside the body too (`codes.ts` `coveredBytes`). Without it, a relay could replay valid words into another project.

| Domain | Signed body |
|---|---|
| `smns-org-state-v1` | `OrgState` |
| `smns-org-transition-v1` | `RootTransition` |
| `smns-org-grant-v1` | `Grant` |
| `smns-machine-cert-v1` | `MachineCert` |
| `smns-device-endorse-v1` | `DeviceEndorsement`, signed by an existing device of the same member |
| `smns-listing-v1` | `Listing` |
| `smns-endpoint-v1` | `EndpointRecord` |
| `smns-hub-log-v2` | the event as DX1 covers it, without `mac` and `sig` |

  retired: RetiredKey[];                                 // RL DL 21; a retired key is never current again

type MachineCert = { org: string; machine: string; name: string; pub: B64; delegation: string; use: number; issued: string };   // machine: the ref, `<delegation id>_<>=128 random bits b64url>`; name: under the delegation's prefix
type KeyHolder = { machine: string } | { member: MemberId; device: string; class: 'native-mac' | 'web-cards'; key: 'channel' | 'step-up' };
type RetiredKey = { keyId: string; pub: B64; notAfter: string; holder: KeyHolder };
type RevokedKey = { keyId: string; holder: KeyHolder | { delegation: string; prefix: string } };   // a revoked delegation's id and prefix stay reserved (RL DL 26)
type CertRetirement = { org: string; keyId: string; notAfter: string };   // smns-cert-retire-v1: the certificate's own delegation key only (admin acts are state edits)
type Certificates = { certs: Signed<MachineCert>[]; retirements: Signed<CertRetirement>[] };
type Signer = { pub: B64; notAfter: string | null };
type Listing = { org: string; machine: string; session: string; revision: number; issued: string;
  fields: { owners: MemberId[]; project: string | null; lane: 'A' | 'B'; state: string; title: string } };
type EndpointRecord = { org: string; machine: string; addresses: string[]; issued: string };   // RL §4.1's direct carriers

verifyGrant(state: OrgState, g: Signed<Grant>): Promise<Verdict>

Genesis: `version` 1, `prev` null, and signed by a kid in its own `root.keys`.

## Surprises & Discoveries

- Production's Worker secrets are not checked for acceptance 1. `wrangler secret list` on `desk-hub`, even read-only, is a wrangler call against the production Worker, which the owner's rule forbids without exception. The other three proofs (the guard's logged target, the unchanged build header, the unchanged Access objects) stand in; a secret put on the wrong Worker would have to pass the target guard first. (2026-10-27)
- Every deploy upserts the people policy `<worker> owner` to the owner alone (`deploy/deploy.ts`), so once M3's `access-sync` has listed the state's members, the next staging deploy would undo it. M3 settles which of the two owns the list. Renaming the policy is no fix: production's next deploy would create a second one. (2026-10-27, M2's executor)
- `probe --config deploy/staging.json` refuses the config's own org, as it does production's, so staging's probe runs against a deploy under a throwaway org id and staging is then redeployed under `staging-ssfskim`. The throwaway id starts with `staging-` too (`staging-probe-<n>`) for the same collision reason, and every service token and Access object it created is deleted after the probe. (2026-10-27, M2's executor; the dispatching session's ruling)
- Cloudflare offers an app every login method the account has when the app names none, and this deployment's apps name none. An existing one-time PIN method would therefore already appear on production's sign-in page; a staging-only PIN needs production's apps to name their methods, which is the owner's call. (2026-10-27, M2's executor)
- The deploy tool's target guard first trusted its own `--name` read-back, but wrangler 4.151 also takes the Worker name from `WRANGLER_CI_OVERRIDE_NAME`, the config section from `CLOUDFLARE_ENV`, the account from other `CLOUDFLARE_*` variables or a `wrangler.jsonc` `account_id`, the whole config from a `.wrangler/deploy/config.json` redirect, and loads `.env` files; and with `WRANGLER_LOG_SANITIZE=false` it writes a `secret put` body to its disk log. The runner now builds wrangler's environment from an allow-list, passes `--name`, `--config` and `--env-file /dev/null` on every call, forces sanitized logs with no disk log, and refuses `--cwd`, `--env-file`, `--profile`, a repeated `--config`, a foreign `account_id` or a redirect. OAuth through `HOME` keeps working, so production's own deploy is unaffected. (2026-10-27, M2's review)
- WebCrypto's verify is a Promise, so §A's verifications can't be synchronous; every consumer (M3–M7, O10, O13) awaits them. §A is revised. (2026-10-27, M1)
- Today's provisioning keys hold `null` for "no cap" (`maxUses`) and "never" (`offlineRevokeS`), but §A types them as numbers and the package requires `maxUses >= 1` and `offlineRevokeS >= 0`. M4's re-issue as delegations has to map them to numbers. (2026-10-27, M1)
- Recovery against an already-accepted forged chain is not covered: `verifySuccessor` follows only the verifier's head, so a machine that accepted states signed with a stolen key past a transition's `fromVersion` refuses it as `rollback`. The working route is a transition issued at the machine's current head. Whether machines need a rewind path is O10's question (carried to P5 through the PR body). (2026-10-27, M1)
- ECDSA signatures are malleable (s → n−s): a third party can make a second valid signature of a stored event. M5's conflict rule refuses such a resend as `conflict`, which is safe; dedupe stays by canonical bytes. (2026-10-27, M1)
- The gitleaks scan (`.github/scripts/maws-app-scan.sh`) flags a vector key under a `*Key` field as `generic-api-key`; the vectors use DX1's allow-listed vector key bytes. Future vector keys will meet the same rule. (2026-10-27, M1)
- The recreated machine's per-writer seqs (the question carried to M5). The Project DO already refuses loudly: an upload at a stored `(writer, seq)` with different canonical bytes (mac included, `log-store.ts:193-195`) is refused `conflict` (`project.ts:413-418`), the writer stops for that batch, and the machine gets a `refused` frame (`project.ts:1151-1153`); only a byte-identical resend passes as a duplicate. sminos on a fresh machine continues from the hub's copy, but only as a side effect: `have` sets `sent[w] = N` for its own writers (`sminos_hublog.py:390`) and the backlog import lands them verbatim, so the next local append is N+1 (`sminos.py:1846-1851`). Session writers are `<name>/<new uuid>`, so only non-UUID writers such as `<name>/human` can collide. A race remains on the sminos side: a `<name>/human` appended before the backlog import lands takes seqs 1..k locally that are never uploaded (they sit at or below `sent`), so the local log forks silently while the hub stays consistent. The hub needs no protocol change; M5 keeps the conflict rule for v2 events (full canonical body, `sig` included). The race is an O14/O12 item for sminos (hold own non-UUID writers until the first `have` and its own-writer backlog have landed). (2026-10-27, controller's code read)

- Decision: M5's build decisions.
  - **The cache.** The head cache lives in memory, not storage. An eviction forgets it, and the next v2 event reads the head afresh. A fresh read is never older than any announcement already made, because the Registry commits before it announces.

## Outcomes & Retrospective

**What exists (2026-10-27).** The hub is a relay and a store of signed things, as the Purpose asked.
- **The org-state chain.** The Registry keeps the org's signed, hash-chained state. It refuses forks (`not-head`) and rollbacks, and projects the state onto members and devices. A removed member loses every socket the hub can close.

- **Review cost.** Fix waves ran seven on M1, four on M3, and two each on M4, M5, M6, M7 and M8. - **Live runs found what offline suites can't.**

  - The quick tunnel's API is unreliable.
