## Purpose

Desk Web is the owner's phone: when a session on the mini asks a question or wants a permission while the owner is away from a Mac, the phone buzzes, the card opens, and the answer moves the session on. P5 cuts each machine over to the endpoint module, which refuses every DX6 request card and answer from the day it enrolls (RL §9). Without this child, the first cutover of a machine the owner answers from the phone, the mini's, would end the phone loop.

After this child:

- the phone is a device of the org in its own right, class `web-cards`: a channel key the browser holds and cannot export, and a passkey, both listed in the signed org state after one approval from the owner's Mac;
- a question or a permission prompt on a cut-over machine reaches the phone as a push, opens as a card drawn from the machine's own sealed channel (nothing the hub can alter), and is answered with a Face ID gesture whose assertion the machine checks against the exact request still pending;
- the phone can do nothing else on a cut-over machine: send, steer, spawn and every other action are refused at the endpoint, which is the owner's protection against a hostile deploy of the hub-served code (RL §5.10);
- machines not yet moved keep their DX6 cards on the same phone, side by side, through every deploy;
- desk-web's other views freeze: they stay as they are, unmaintained, and stop pretending to control a machine that has moved;
- hub v2's first production deploy, and the org's root and the phone's approval, run from steps committed beside O11's staging runners, never from a wrapper under `/tmp` (P5 Decision Log 40).

What someone can do afterwards, on staging first and on production once O14 cuts the mini over: with the Mac closed, a `claude` in a terminal on the mini asks a question; the phone shows "A session is waiting for your answer"; the card opens with the question's choices; a tap and Face ID answer it; the terminal shows the answer within a second or two of the gesture. The same for a permission prompt, Allow or Deny. A push for a session the owner doesn't own never arrives.

2. **A full round trip.** On a cut-over machine, with the phone's app closed, a permission prompt and a question each: push to the phone (a notification reading *A session is waiting for your answer*); on a tap, show their card contents over the phone's channel (the question's text and choices; the tool, its verb and its input); are answered with a passkey gesture, after which the card settles and the machine's session shows the answer. Live, with a third session on the same machine owned by a second member: the owner's devices (the phone, and a second `web-cards` device of the owner's subscribed at the run's push sink) each receive one notice per owner's session and none for the second member's, as O11 M8 framed the clause for its sink. The live run is M7's, on staging against the real endpoint module enrolled there and the owner's real phone; lane B's engine is M7's harness until `mawsd` exists (O2, O10 M10), and the run on production is O14's mini brief, with this document's rollout steps.
3. **The class's bound.** From the phone's identity, an `act` of `session.send`, `session.steer`, `sminos.steer`, `sminos.spawn`, `sminos.command`, `endpoint.grant`, a `sub` of view `full`, a `call` of `session.events`, a lane B permission answer carrying `updatedInput` or a scope other than `once`, and a lane A `decide` with a `message` are each refused `class` at the endpoint, and a `query` of a lane A operation is refused `grade` (a lane B query of the device's own `session.answer` is answered, as O10 M8 landed it; the phone never sends one, Decision Log 2026-10-28). The phone's code is served by the hub, so nothing in this child relies on that code for anything but drawing and asking: the machine decides (O10 M5), and the accepted residual is RL §5.10's.

**At its end.** Hub v2's first production deploy can run from two committed scripts beside O11's staging runners, `apps/desk-hub/deploy/production-deploy.sh` and `production-run.sh`, with the same mechanism the staging scripts use (names checked before anything runs, secrets read by path inside the script, output filtered, logs outside the repository), aimed at production: a config that is not exactly production's is refused, and the deploy runs only for the commit the owner names. No deploy runs in this milestone.

**Touches.** `apps/desk-hub/deploy/production-deploy.sh`, `production-run.sh` (new), `README.md` (a "Production runs" section), `apps/desk-hub/test/deploy/production-scripts.test.ts` (new).

**Decisions.**
- **The guard, inverted.** Each script reads `deploy/config.json` first and stops unless it names exactly `desk-hub`, `desk-hub.opencognita-platform.workers.dev` and org `ssfskim` (the constants `config.ts` holds), and refuses any staging name or a preview alias (`<alias>-desk-hub.…`) as not production; the same python check as the staging scripts, with the roles swapped. The commit confirmation is the deploy's alone: `production-deploy.sh` refuses unless `--confirm <sha8>` equals the checkout's HEAD short hash, so a command copied from a note cannot deploy a commit other than the one the owner read. `production-run.sh`'s steps take no `--confirm`: none deploys; the ones that change production (`access-sync`, `admin genesis`, `admin pair`, `admin remove-device`) print what they are about to change as their first line, and the admin command confirms from `/dev/tty` before it signs anything (a shell with no controlling terminal, an agent's, fails there with *Device not configured* and nothing is sent) and refuses a genesis where a state exists. Rejected: an interactive prompt for the deploy, which a wrapper could feed; a plain `--yes`, which names no commit; and a confirmation on every runner step, which the published rollout would then have to carry for steps that deploy nothing.
- **The checkout.** `production-run.sh checkout [<path>]` is `prep-deploy.sh` in the repository: it adds or updates a detached worktree of `origin/master` at `<path>` (default `~/.local/share/maws-desk-deploy`, never under `/tmp`) from the worktree the script is in (`git -C <here> worktree add -f --detach`, or `git -C <path> fetch` and `checkout --detach origin/master` when it exists), refusing to run git in a worktree with uncommitted changes, then installs with `pnpm install --frozen-lockfile --filter 'desk-hub...' --filter 'desk-web...'` under `DESK_HEAVY_WRAPPER` when set. `production-deploy.sh --checkout <path> --confirm <sha8>` requires the checkout clean (tracked files) and its HEAD equal to `origin/master` after a `fetch`; `--allow-head` lets the owner deploy a commit that is not master's head (a hotfix branch), still named by `--confirm`.
- **The deploy.** As `deploy-master.sh`: desk-web's build with `VITE_DESK_WEB_BUILD=master.<sha8>` exported (the label the phone's `h1.build` carries, M4), then `deployment deploy --assets <checkout>/apps/desk-web/dist --web master.<sha8>` with `CF_ACCESS_SETUP_TOKEN` and `CF_DESK_HUB_SERVICE_TOKENS` read by path from `DESK_PRODUCTION_SECRETS` (default the owner's secrets directory) inside the pipe, output through the staging scripts' filter, the `wrangler target` lines counted and every one required to name `desk-hub`; production's `X-Desk-Build` printed before, then polled after for up to 2 minutes until it carries `hub@<sha8>` (`poll-build.sh`), and the script fails if it never does. Logs go to `DESK_PRODUCTION_DIR` (default `~/.local/state/desk-hub-production`, 0700), one per run.
- **`production-run.sh`'s steps:** `checkout [<path>]`; `build` (production's `X-Desk-Build`, credential-free); `wait <sha8>` (the 2-minute poll alone); `access-sync` (`deployment access-sync` against production, which reads the head as an enrolled machine: `DESK_PRODUCTION_DEVICE/machine.json` holds `{"DESK_MACHINE_CLIENT_ID", "DESK_MACHINE_CLIENT_SECRET"}` of a production machine enrolled v2, which exists only once O14 enrolls one, written by the owner from that enrollment's credentials; the step refuses without the file and says so; the checkpoint under `DESK_PRODUCTION_DIR/access-sync`: an Access change, the owner's); `admin <args…>` (M2's `deployment admin` against production with the owner's Access token from `cloudflared access token -app=https://desk-hub.opencognita-platform.workers.dev` read inside the script and the keys from `DESK_PRODUCTION_DEVICE`, default `$DESK_PRODUCTION_DIR/device`; a pairing code goes to the terminal alone, never to the step's log, §F). Every step that changes production says so in its first line and is the owner's to run (Constraints).
- **What stays outside.** `with-slot.sh` (the Mac's slot limiter) stays the owner's: `DESK_HEAVY_WRAPPER` names it. Nothing of this milestone reads production's Access objects.

**Does not touch.** `deploy.ts` and the other commands; `staging-*.sh`; `config.json` (the owner adds `orgGenesis` after M7's genesis, by a commit of their own).

**Proves.** Nothing of acceptance 1–5 directly; it is Decision Log 40's fold. `production-scripts.test.ts`, offline with stubs on `PATH` as `staging-scripts.test.ts` does: each script refuses `staging.json` and a config naming a preview alias before reading a token or running anything (an empty secrets directory, a `pnpm` and a `wrangler` stub that record and fail); `production-deploy.sh` refuses without `--confirm`, with a `--confirm` that is not HEAD's, with a dirty checkout, and with a HEAD off `origin/master` without `--allow-head` (a temporary repository with a bare `origin`); `production-run.sh admin genesis` and `access-sync` print their change line before anything else and stop at the first credential they lack; `--dry-run` on a clean checkout prints the commands it would run with no token in them and runs none; the filter drops a line holding `token`, `secret`, `bearer` or `eyJ`; `checkout` refuses a worktree with uncommitted changes; the README names every environment variable the scripts read.

### M2 — The pairing code, its MAC, and the owner's admin command

**At its end.** A new device can be paired the way RL §5.3 describes: the approving side shows a one-time code carrying the org's root pins and a pairing secret; the device posts its keys with a MAC under that secret; the approving side checks the MAC and signs the device into a successor. The approving side is a command on the owner's Mac, `deployment admin`, which can also root an org, keep its state fresh, list devices and revoke one, pending O8's Org page. It is proved against the suites' local hub and on staging with the staging admin device.

**Touches.** `apps/org-protocol/src/pairing.ts` (new), `src/index.ts`, `vectors/` (a pairing vector), `test/`; `apps/desk-hub/deploy/admin.ts` (new), `bin.ts` (the command), `org-admin.ts` (reused: `successor`, `deviceEntry`, the state's signing), `staging-run.sh` (an `admin <args…>` step: the staging admin keys and the owner's staging token read inside, a pairing code to the terminal alone, never the log), `README.md`; `apps/desk-hub/test/deploy/admin.test.ts` (new).

**Decisions.**
- **The code and the MAC are the package's** (§A), not desk-web's or the hub's: both ends must agree byte for byte and O8's app will be the third consumer. The MAC input is length-prefixed under its own domain, as the enrollment MAC is, over the org, the member and the device entry's fields, so a key, class, storage kind or passkey the hub substituted fails on the Mac. Rejected: reusing `enrollmentMacInput` with a device's fields in a machine's slots, which would let a machine's MAC and a device's collide.
- **The admin command is the owner's hand before O8** (P5 §8 names the Org page as the admin's app, and it is unbuilt). It lives beside `org-admin.ts` because the signing it needs is already there, and it is reached through `deployment` so the README stays the one place. It differs from the test commands in its scope: it acts on the deployment `--config` names, production by default, and refuses a throwaway org; `checkTestHub` does not apply to it, and so the Constraints make it the owner's alone against production. Its device is its own (`init`: a channel key and a step-up key, generated once into `<keys>` 0600, never overwritten), class `native-mac`, `keyStorage: 'software'`: a software-keyed first root, which the remote layer accepts (RL DL28). `init` refuses a `--keys` path under `/tmp`, `/private/tmp` or `$TMPDIR`, inside a git work tree, or under `~/.claude`, `~/Library/Mobile Documents` or `~/.config/claude-secrets` (a sweep, a commit, a sync or a backup would carry the key), and runs `tmutil addexclusion` on the file. Rejected: reading MAWS main's device keys (`<profile>/device/keys.json`, O10 M9), which couples a script to the app's private files as O6 refused for sminos, and would make the app's Touch ID-gated step-up key sign root states from a terminal; and rooting the org from desk-web's browser, whose storage belongs to hub-served code (RL §5.10). The device has a set end, and it is O8's: once the app's device is a root, the app signs the successor that revokes the deployment admin device (RL DL28: it signs no log events and an endorsement is checked only in the step that adds its device, so revoking it discredits nothing, the phone's entry included), and its key file is deleted, whatever the key class.
- **`genesis --recovery <path | paper>`** makes the org's recovery key and writes its private half only to the offline destination the owner names, never to the admin key's disk: a path on a removable volume mounted for the step (refused unless the path is on a volume other than `<keys>`' and outside the sync and backup scopes above), or `paper`, which prints the key once and keeps no file **[owner, 2026-10-28: a removable volume mounted at genesis]**. The destination is a parameter and the check-back runs either way: the command reads the private half back from the path (or takes it typed back, for paper), derives its public point and refuses unless it equals `recoveryPub`, before it signs anything; `recoveryPub` never changes after genesis (`org-state.ts`), so this is the one moment the pair is checked. It then builds version 1 (`prev` null, `issued` now, `root.keys` the admin device's step-up key, `recoveryPub`, one member: the signed-in person as `/api/me` names them with `role: 'admin'` and the admin device, no machines, delegations or projects, `machineNames`, `retired` and `revoked` empty), confirms from `/dev/tty` (*root <org> at <hub>? [y/N]*), signs it with the step-up key (`signOrgState`) and posts it; it prints the genesis hash (`stateHash`) for `orgGenesis` in the deployment's config, which the owner commits, and keeps `recoveryPub` in the anchor. It refuses when the hub already holds a state. A rerun (below) mounts the volume again and runs the same check-back.
- **`pair --class web-cards|native-mac [--ttl <s>]`** makes `k` (16 bytes), prints the code once and copies it to the Mac's clipboard (`pbcopy`, so Universal Clipboard pastes it on the phone **[owner, 2026-10-28: the clipboard, no QR]**), then polls `GET /api/devices/pending` every 2 s for up to `PENDING_DEVICE_TTL_S` for an entry of the requested class whose MAC verifies under `k` (others are ignored and named in the log as not this pairing's); shows the entry (id, class, storage, the passkey's `rpId`) and the entry's fingerprint (§A's `pairingFingerprint`, over the org, the member and the canonical entry the MAC covers (device id, class, `keyStorage`, `channelPub`, `stepUpPub` where present, the passkey's `credentialId`, `publicKey` and `rpId`)), which the phone's panel shows too, and asks `approve? [y/N]` from `/dev/tty` only once the owner has compared the two: the clipboard exposes `k` to every process under the uid and to clipboard history (RL DL28), so `k` alone admits nothing, the fingerprint does. Two entries verifying under one `k` are refused outright (*two devices answered this code: start over*), and the code is spent. Then it signs a successor adding the device to the member's entry with an `endorsement` by the admin device (the member's earlier device) and the root signature, posts it, and prints the version. A `not-head` answer leaves the proposal pending and signs nothing more: the next run finds the other successor and refuses `fork` (Decision Log, "No two successors of one parent").
- **`adopt`** initializes the anchor for an org rooted before this command existed (staging's, whose genesis `staging.json` pins; a production rooted by O8 later): it reads the chain from its genesis, verifies it with the package, refuses unless the genesis hash equals the config's `orgGenesis` (required here; a config without one is refused), checks that `--keys`'s device is listed under the signed-in member in the head and that its step-up key is one of the head's `root.keys` (it will sign successors), and writes `<keys>.org.json`. `pair`, `devices` and `remove-device` refuse with *no anchor: run genesis or adopt* until one exists.
- **`genesis`, interrupted.** `genesis` writes the state it will post to `<keys>.genesis.json` before it posts, posts it, then writes the anchor; a rerun that finds the file posts those same bytes again, so the hub either takes them (no state yet), or already holds a head whose genesis hash equals theirs (the first run's POST landed and its anchor write did not), in which case the command writes the anchor and succeeds; a hub holding another genesis is refused. So a genesis that committed at the hub is never lost to a local failure, and no second genesis is ever built.
- **`devices`** lists the member's devices from the head; **`remove-device <id>`** confirms from `/dev/tty` and signs a successor dropping the device, its key into `revoked` (RL5), and prints the version; the direct RL4 revocation to each machine is O8's app's, and until then machines learn it at the hub's `state` notice (O10 M2's sync), within its 10-minute poll at worst.
- **`refresh`** signs and posts a no-change successor (RL §5.2's weekly successor, which no admin app signs while this command is the only admin device). The endpoint refuses every remote action once the head is more than 30 days old (`src/endpoint/org-sync.ts` `BACKSTOP_MS`) and `rl10/words.ts` drops remote words to peer, so without it the phone's answers stop 30 days after the last admin run. Every subcommand prints the head's age (*head version n, issued d days ago*) first, so the owner sees the clock on every run.
- **Confirmations** (`genesis`, `pair`, `remove-device`) are read from `/dev/tty` whenever the command acts on a deployment: an agent's shell has no controlling terminal, so opening it fails with *Device not configured* and the command stops before any request. Against the suites' local hub (`--hub/--user`) a test may confirm another way (`--yes`, refused without `--hub`).
- **Where it may write.** The deployment's own org, only when the hub serves a chain whose genesis is the command's anchor, or no state yet for `genesis`; a throwaway org is refused (`--test-org` is not an option). The anchor is `<keys>.org.json` `{hub, org, genesis, version}`, written by `genesis` or by `adopt` (an org rooted before, verified against the config's `orgGenesis`) and, where the config pins `orgGenesis`, checked against it; every other subcommand reads the chain from its genesis, verifies it with the package (`verifyPinnedChain` over the anchor's roots), refuses a chain whose genesis differs, and moves `version` forward as `access-sync` moves its checkpoint, so an older head served as the head is refused. Against the suites' local hub the anchor is the one `genesis` just wrote; against staging it is staging's pinned genesis.

**Does not touch.** desk-web; the hub; machine enrollment (O14 extends the command with a machine's code if it needs one before O8).

**Proves.** Acceptance 1's Mac half, against the local hub (`test/endpoint/local-hub.ts`'s runner from desk-hub's own suites, or `local/run.ts` directly): `init` makes the file 0600, refuses to overwrite, refuses a `--keys` under `/tmp`, `/private/tmp` or `$TMPDIR`, inside a git work tree, or under `~/.claude`, `~/Library/Mobile Documents` or `~/.config/claude-secrets`, and asks `tmutil addexclusion` for it (the call recorded by a stub); `genesis` roots a fresh local org and prints its hash, writes the recovery key only to the named destination (nothing under `<keys>`' directory holds it, and the anchor holds `recoveryPub` alone), refuses a destination on the keys' volume or inside the sync and backup scopes when acting on a deployment, refuses when the read-back's public point is not `recoveryPub` (the test corrupts the file between write and read), takes `paper` with the key typed back and refuses a wrong one, and refuses a rooted one; `genesis`, `pair` and `remove-device` against a deployment stop before any request when `/dev/tty` cannot be opened (the test runs them with no controlling terminal), and `--yes` is refused without `--hub`; `refresh` posts a no-change successor and every subcommand prints the head's age first; a `genesis` killed between its POST and its anchor write (the test kills the child after the hub answers 201) finishes on a rerun with the same hash and no second genesis; `adopt` on a rooted local org with its genesis pinned in a config writes the anchor, and refuses a wrong pin, a device not in the head and a device whose step-up key is no root; `pair` ignores a pending entry whose MAC is under another secret, shows the fingerprint of the one that verifies (equal to the package's `pairingFingerprint` over the org, the member and the whole entry; a pending entry that keeps the phone's `channelPub` but swaps `stepUpPub` or the passkey, its MAC recomputed under a leaked `k`, shows a different fingerprint, RL DL28), approves it, and the head then lists the device with its endorsement verifying; two entries verifying under one `k` are refused and the code spent; a `web-cards` entry with a `stepUpPub` is refused by the hub and the command says so; `remove-device` puts the key into `revoked`; the package's vector replays the pairing code and MAC under Node's WebCrypto and workerd's. On staging, by the executor with the staging admin keys: `adopt` against `staging.json`'s pinned genesis first (staging was rooted by O11 M3), then a `web-cards` test device (the package's `TestDevice` with a `SoftwareAuthenticator`) paired and removed under `staging-ssfskim`, the versions printed.

### M3 — The phone registers as a `web-cards` device

**At its end.** desk-web on a phone can become a `web-cards` device of the org: a Device panel takes a pairing code, makes a non-extractable WebCrypto channel key and a passkey, posts the pairing entry with its MAC, waits to be listed, and from then holds the signed org state verified from the code's pins; its push subscription is bound to the device. The panel says what state the device is in and lets the owner forget it.

**Touches.** `apps/desk-web/src/cards/device-store.ts`, `register.ts`, `org-store.ts`, `cards-passkey.ts` (new); `src/store/idb.ts` (`DESK_DB` version 2, stores `device` and `org`); `src/push/device.ts` (`device` on the subscription); `src/hub/grid-client.ts` (`?app=1` and the two frame kinds), `src/cards/listings-store.ts` (new); `src/views/cards/DevicePanel.tsx` (new), `src/App.tsx` (the panel reached from the phone menu and the top bar); `package.json` (`org-protocol`); tests, `e2e-hub/cards-device.spec.ts` (new); `e2e/fixtures.ts` (`seedKey`'s upgrade handler creates the two new stores too).

**Decisions.**
- **The channel key** is `crypto.subtle.generateKey(P-256, extractable: false, ['sign'])`, kept as a `CryptoKey` in IndexedDB (§B) beside the org key, which already lives that way. Its public point is exported raw (the package's `B64` of 65 bytes). The device id is 16 random bytes base64url, chosen by the phone.
- **The passkey** (`cards-passkey.ts`: `createCardsPasskey()` at registration, and `assertWith(record)`, the `Assert` M4's answers take, which runs `navigator.credentials.get` with the challenge it is given) is a credential of its own, made at registration with `navigator.credentials.create` (`rp.id` the hub's hostname, `alg -7` only, `userVerification: 'required'`, `residentKey: 'discouraged'` since every assertion names the credential, no PRF), and its public point taken from `response.getPublicKey()`'s SubjectPublicKeyInfo (the last 65 bytes). The org key's PRF passkey (`src/key/passkey.ts`) is not reused: it retires with the org key at O14's final brief, and its assertions are never sent anywhere. Pitfall checked: `getPublicKey()` is a WebAuthn level 2 method, in Safari and iOS Safari from 16 (ES256 only, which is the one algorithm asked for; WebKit answers null for others), in Chromium from 85; the registration refuses with a plain reason on a browser that answers null rather than parsing the attestation object.
- **The pins** come from the code (§A: `roots`, `recoveryPub`), never from the hub. The org store (`org-store.ts`) holds the head, the chain window and the transitions it has adopted in IndexedDB, syncs from `GET /api/org/state?since=<held>` on each app start and on a channel's `state` message, and verifies the first sync with `verifyPinnedChain` and every later one with `advanceHead`, as the endpoint does (O10 M2). It implements the package's `OrgView` for the channel (M4). A head that stops listing the device, or a member removal, moves the device to `removed`, which the panel says; the keys stay until the owner forgets them.
- **Registration's states** (§B): `none` → `pending` (posted, `expires`) → `listed {version}` | `expired` | `removed`. The phone polls the head every 5 s while `pending`, for the entry's TTL; the panel says *waiting for approval on your Mac — fingerprint xxxxx-xxxxx* (§A's `pairingFingerprint` over its own whole entry, for the owner to compare with the Mac's), then *listed, version n*. A pairing code for another org or member than `/api/me`'s is refused before anything is generated.
- **The app's registry socket** (P5 Decision Log 38): once the device record exists, `src/hub/grid-client.ts` opens `/api/registry/socket?app=1` instead of the bare socket, hands each `state {version}` notice to the org store's pinned sync and each `listings` page and `listing` frame to a listings store (`src/cards/listings-store.ts`: records by `(machine, session)`, verified against the head as `apps/org-protocol/src/app-hub.ts` says, a `gone` revision dropping its session), and keeps drawing the grid from `grid` and `summary` as today. So a phone open with no channel learns of a machine enrolled, a device removed or a session listed without a restart. Certificates move without a state change (a delegated VM's `POST /machine/cert` advances no version and raises no notice), so the org store also re-reads `GET /api/org/state` (its `certificates` come with the head, version unchanged or not) whenever a `listing` frame or a push landing names a machine ref it cannot resolve, and whenever the Cards view opens, at most once a minute; a listing whose signer it cannot resolve is held unverified until that read and dropped if the read does not resolve it. Rejected: refreshing the head only at start and on a channel's `state`, which leaves a phone with no channel stale until it restarts, and never shows a VM certified while it is open.
- **Push binds to the device**: once listed, `PUT /api/push/subscriptions` carries `device`, and the phone's `resyncPush` at start hands it over again with it, so revoking the device ends its pushes at the hub (P5 Decision Log 41). A phone not yet registered keeps today's unbound subscription.
- **The Device panel** is new UI (the maintained part), reached from the phone menu and the top bar's dot menu: the state, the pairing field, the fingerprint while pending, the passkey's relying party, Forget (deletes the record and the key; the org-state entry stays until `remove-device`), and the push state as the Notifications dialog shows it. It draws nothing of the org state but the version and the head's age: past 21 days it warns *the org state is d days old; run `deployment admin refresh` on your Mac before day 30, or this phone's answers stop* (RL DL28: the endpoint's 30-day backstop, `src/endpoint/org-sync.ts`), since while the admin command is the only admin device nothing else signs a successor.

**Does not touch.** The channel (M4); the cards (M5); the service worker (M6); any frozen view.

**Proves.** Acceptance 1's phone half: unit suites for the state machine and the store (`// @vitest-environment happy-dom` where a DOM is needed) with a fake hub; `e2e-hub/cards-device.spec.ts` in Chromium with the virtual authenticator against the local hub rooted by `deployment admin genesis`: the code pasted, `pair` run by the test as a child process approving the entry, the panel showing the fingerprint while pending, equal to the one `pair` printed, then reaching *listed*, the head's entry matching the phone's keys, the panel's age warning absent on a fresh head and shown on a head whose `issued` the test backdates 22 days (the org store's clock injected), `extractable === false` on the stored key, a second registration refused while one is listed, Forget emptying the store; a code for another member refused; the pinned sync refusing a chain whose genesis differs (a hub serving a throwaway org); the subscription record at the hub carrying `device`; with the phone open and no channel, a successor posted by the test (a machine added) reaching the org store through the socket's `state` notice within 5 s, and a listing posted by a test endpoint reaching the listings store; with the org version fixed, a delegated machine certified by the test (`apps/desk-hub/fake-machine/org.ts`'s `certify` against the local hub) whose listing then arrives being resolved and shown within 5 s, through the certificate re-read.

### M4 — The channel from the phone, and the cards client **[needs O10 M7/M8]**

**At its end.** From the browser, desk-web opens an RL2 channel to a machine through the hub's relay with the package's `connectChannel`, subscribes to the `cards` view of a session on either lane, draws the pending set into cards, and answers a card with an action carrying a WebAuthn assertion, seeing `ack`, `done` and the card's settlement. Nothing else crosses the channel. The client is a library with no view, proved under vitest against the real endpoint on the local hub.

**Touches.** `apps/desk-web/src/cards/carrier.ts`, `client.ts`, `cards.ts`, `answers.ts` (new); tests, `apps/desk-web/test/local/endpoint.ts` (new: the in-process endpoint on the local hub) and `src/cards/*.local.test.ts` (the suites that start the local hub, a wrangler dev child, named `.local.test.ts` and run in a project of their own as the root `vitest.config.ts` isolates `test/endpoint/*.local.test.ts`); `apps/desk-hub/deploy/staging-deploy.sh` (exports `VITE_DESK_WEB_BUILD=<label>` before the web build).

**Decisions.**
- **The carrier** (§C) is one WebSocket per machine to `/api/machines/<ref>/socket` (the ref from the notice or the org state; the hub takes a ref or a name), `binaryType: 'arraybuffer'`, speaking the multiplex with the package's `encodeChannelFrame`/`decodeChannelFrame`: `open` with a tag, then one `ByteDuplex` per channel. `connectChannel` dials once per catch-up page; a dial reuses the machine's socket while it is open and reconnects it with `src/hub/socket.ts`'s backoff otherwise. `presence` frames are kept per machine for the cards list (M5). The phone stays on the relay (P5 Decision Log 39): no direct dial, no endpoint record read.
- **The identity** is `DeviceIdentity {org, member, device, clientClass: 'web-cards', channelKey, build: 'desk-web/<label>', capabilities: []}`, `label` the web build's (`import.meta.env.VITE_DESK_WEB_BUILD`, exported by the deploy scripts before the build as the `--web` label; `dev` otherwise). The `OrgView` is M3's store. `caps` is read for `stateVersion` only.
- **A subscription** is `sub {sub, session: {lane, id}, view: 'cards', cursor: null, credit: 1 MiB}`; `snap` replaces the card set whole (both lanes are snapshots, M8); lane A's `ev` of `raised` adds and `settled` removes; `ended {reason}` ends it with the reason shown (`removed`: the session is no longer the member's; `unavailable`: the session or its bridge is gone; `restart`: `mawsd` is restarting, resubscribe after backoff). Credit is topped up at half. A channel's close resubscribes through a new channel after backoff, every resubscription a snapshot.
- **A card** (§D) is drawn from what the snapshot carries and nothing else: lane A from `raised` (the tool, its input, the session), lane B from `request` (the `permission.requested` or `question.requested` event) and `item`. Its digest is computed by the phone from what it draws: lane A `desk-hub/protocol`'s `inputSha256` over `raised.input` as the card does today; lane B by `laneBDigest(appSessionId, request)` in `cards.ts`, which applies `src/shared/host/request-digest.ts`'s field rule (a `permission.requested` its `toolName` and `input`; a `question.requested` `AskUserQuestion` and `{questions}` as the event carries them; a `plan.requested` `ExitPlanMode` and its `input`; any other `*.requested` its kind and `payload`) and hashes with `inputSha256`. `requestDigestOf` itself cannot run in the browser: it hashes with `node:crypto`'s synchronous `createHash`, and the engine host's claim path calls it synchronously, so it stays Node's; the mirror is four rules, and a vitest case pins byte equality between the two over all four kinds, a normalized question included. The endpoint's `requestDigest` beside a lane B card is compared with the phone's and a mismatch makes the card not answerable with the reason *the request changed*, since an answer sealed to either would be refused `digest-mismatch`; M5's browser answers are accepted by the real endpoint, which is the browser's proof of equality.
- **An answer** builds the action with the package's shape (§D): lane A `sminos.answer {session, answers, digest}` or `sminos.decide {session, decision: 'allow' | 'deny', digest}` with `context {lane: 'A', session, launch}` and `session` the engine session id; lane B `session.answer {appSessionId, requestId: item.request.requestId, answer}` (the attention item's id is nested, `src/shared/graph/attention.ts`, and nullable: a card whose item names no request is drawn but not answerable) with `context {lane: 'B', launchId, engineSessionId}` and `session` the `appSessionId`, the `answer` one of exactly three `RequestAnswer` forms (`src/shared/engine/answers.ts`, whose schema the endpoint checks before anything runs, `malformed` otherwise): Allow `{kind: 'permission', decision: 'allow', scope: 'once'}`; Deny `{kind: 'permission', decision: 'deny'}` with no `scope` (the schema requires `scope` for allow and forbids it for deny); a question `{kind: 'question', answers}`, the answers as MAWS's `Question` stepper hands them to today's card (`RequestCard.tsx`), keyed by question text. Never `updatedInput`, `message` or `deny_and_stop`, which the endpoint refuses `class`. Then `navigator.credentials.get` with `challenge` = `actionDigest(action)`, `rpId` the hub's hostname, `allowCredentials` the device's one credential, `userVerification: 'required'`; the assertion's `credentialId`, `authenticatorData`, `clientDataJSON` and `signature` go into `action.webauthn` base64url; `act` is sent. The outcome is `ack` then `done` within 60 s. A `done` is an envelope, not a success: its `outcome` (O10 §B) is `{state: 'done', result}`, `{state: 'failed', error}` (the command ran and failed), `{state: 'refused', reason}` (the executor's own refusal: `tombstoned`, `op-conflict`, `digest-mismatch`, `context`), `{state: 'in-progress'}` (a reseal reached an operation still running) or `{state: 'unknown', reason}` (the host unreachable once handed on), and the client normalizes it to its `Outcome` (§D) before any view sees it: `done` → done; `failed` → failed; the executor's `refused` → refused by its reason, as an `ack {state: 'refused'}` is; `in-progress` and `unknown` → uncertain, keeping the retained operation. A refusal is shown by reason (`class`, `grade`, `stale`, `context`, `digest-mismatch`, `step-up` for a bad assertion, `read-only`, `unavailable`, `op-conflict`).
- **The fresh lane B session** (O13 carry): a card whose `context.engineSessionId` is null is drawn but not answerable, with the reason *this session hasn't been prompted locally yet*; the next snapshot after its first turn makes it answerable.
- **A lost acknowledgement** (O13 carry; P5 Decision Log 64): the phone never sends `query`, which its class is refused. A card whose `act` got no `ack` within 10 s, or no `done` within 60 s, is `uncertain` with Retry, as today's card is: Retry reseals the **retained operation**: the client keeps, per card, the action it first sent minus `nonce`, `created` and `webauthn` (its `opId`, `opCreated`, `action`, `session`, `context`, `args` and `requestDigest`, the fields the ledgers' fingerprint binds, `actionFingerprint` in O10 §C), in memory for the tab's life and across channel reconnects, and a reseal is that operation with a fresh nonce, `created` and assertion (a new gesture: the challenge covers them) and nothing else changed, so its fingerprint equals the first copy's and the ledger answers the stored result if the first copy ran; an action rebuilt from the current card or given a new `opCreated` would be refused `op-conflict`. A snapshot showing the card gone settles it as `closed`. A card still pending after `failed`, or after a refusal other than `digest-mismatch` or `context`, may be answered anew under a new `opId` (the ledger holds the first operation's result, so the first never runs again); `digest-mismatch` and `context` make the card *the request changed* until the next snapshot. A reload loses the retained operations: a card still pending then is answered anew, and an answer the first copy already delivered is refused `not_pending` by the broker or `digest-mismatch` at the host, never applied twice. Rejected: adding `name` to sminos's RL10 binding so a `web-cards` query could be answered (an O12 change), which the reseal makes unnecessary.
