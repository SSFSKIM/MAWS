## Purpose

P5 makes MAWS one app over the owner's machines. Every child before this one builds the new way in beside the old: the hub serves the desk's phase-1 protocols and the new ones side by side, the endpoint module runs unenrolled on every machine that runs master, and sminos keeps its own uplink until an enrolled endpoint welcomes it. O14 is the move itself. After it:

- each of the owner's machines, the devcloud acceptance VM first, then the mini, then the MacBook, is enrolled under its own key and its own name in the signed org state, talks to the hub only through its endpoint, and runs its sminos local-only, with the phone still answering and the logs still readable on every machine not yet moved;
- a devcloud VM enrolls itself at boot under a delegation and retires itself when it is deleted, with no hand in it;
- the shared org key of desk phase 1, the one secret every machine and browser held, is retired: no wrapped copy at the hub, no phase-1 route, no machine coding anything with it.

**How to see it working.** On a cut-over machine, `sminos daemon status` says `uplink: RL10 (local-only)` and `mawsd keys --json` says `"enrollment": "org-listed"`; a `sminos say` from it reaches a session on a machine not yet moved, and one from that machine comes back labelled `(unverified, legacy)`; its daemon runs no DX2 uplink, and the hub lists it `listed`. After the final brief, `mawsd endpoint status --json` on every machine says `"legacyKey": false`, and `curl -sI -X POST https://desk-hub.opencognita-platform.workers.dev/machine/stream` answers 404.

The document has two parts. **The shared build** (M1 to M5b, one PR each) is what a `doperpowers:plan-executor` builds from this document and the code. **The briefs** (B0 to B4) are the runbooks the owner's session runs, one machine at a time, each step with its check and its undo, the owner at every gate; a brief is run by the session that owns this document, never by a plan-executor, and the mini only through `mini-ops` at the owner's request.

## Terms

- **DX1** is desk phase 1's coding: HMAC-SHA-256 under the shared **org key** over every log event, RPC, request and settlement (`sminos_codes.py`, `apps/desk-web/src/log/verify.ts`). **DX2** is sminos's own uplink to the hub, SSE down and `POST /machine/frames` up (`sminos_uplink.py`). **DX6** is the browser's RPCs and cards through the hub. **DX7** is phase-1 enrollment: a code carrying the org key, redeemed by `sminos hub enroll` into `~/.claude/sminos/daemon/hub.json`, which holds the machine's Access service token and the key. In this document "the legacy key" is that org key.
- **The endpoint** is `src/endpoint/`, the module inside `mawsd` that holds the machine's key and its only hub connection (**RL1**), serves device channels (**RL2**) and the sminos socket (**RL10**). Its state is `<profile>/mawsd/endpoint/` (O10's Interfaces §E); `<profile>` is `~/Library/Application Support/MAWS` on macOS and `${XDG_CONFIG_HOME:-~/.config}/MAWS` on Linux.
- **Enrollment states** are the endpoint's: `none`, `hub-confirmed` (the hub minted its credential) and `org-listed` (a signed org state lists its key, or a live certificate covers it). The endpoint serves RL10, writing `rl10.json` and binding the socket, only while `org-listed` (P5 Decision Log 55).
- **The cutover** of a machine is sminos's switch: the first RL10 `welcome` whose identity is complete (`org`, `hub`, `name`, `ref`, `enrolled`) writes `~/.claude/sminos/daemon/identity.json`, and from then on the daemon starts no DX2 uplink, codes nothing, and refuses `hub enroll`, `hub check` and `hub leave` (O12 M5). A machine with that file is **cut over**. Its `hub.json` stays until B4, because sminos answers the endpoint's `legacy-key?` from it.
- **Dual-coding** is the endpoint signing each outbound event v2 and adding the DX1 `mac` as well, so machines not yet moved can read it; **single-trust inbound** is the cut-over machine taking execution input only through RL2 and RL4, never from a DX1 code (RL §9). **Re-attestation** is a cut-over machine signing its own phase-1 history once, so it stays verifiable after the key retires.
- **A delegation** is an org-state entry `{id, pub, prefix, expires, maxUses, offlineRevokeS, owners}` whose private key lets a booting VM certify itself under a name beginning with `prefix` (RL §5.3); **a certificate** is the VM's own signed `MachineCert`; **a provisioning code** is the text a secret store holds so the boot can redeem one. **A pairing code** is the one-time secret an approving device shows and a new device types in (RL §5.3), under which the new device MACs its keys.
- **A brief** is a runbook: ordered steps, each with what to do, how to check it held, and how to undo it. **`[owner]`** marks a step that waits for the owner's word or hand. **`[mini-ops]`** marks a step the owner asks the mini-ops session to run on the mini; nothing in this document runs on the mini any other way. A step marked **irreversible** has no undo, and says so where it stands.

## Acceptance

P5's O14 items 1 to 5 hold per machine, and its final brief's five effects hold at the end. They are checked as follows (commands in Concrete Steps and in the briefs), with four items this document adds (6 to 9).

1. **Re-enrollment.** Each machine is `org-listed` under the name it had on DX2 (`mawsd keys --json`), by a member's code for the Macs and by a certificate under the devcloud delegation for the VM; the VM's ref starts with the delegation's id and `_` (`mawsd status` prints `machine <id>_…`); `deployment org show --production` lists each attended machine `listed` and each certificate machine `certified` (the certificates the state read serves); until listed, `mawsd endpoint status` shows `hub-confirmed` and the machine executes nothing from outside (O10 acceptance 3's cases hold).
2. **History.** For every project the machine wrote to and every writer under its current and former names, the hub holds a history attestation signed by the machine key covering every DX1 event: `mawsd endpoint attest-history --check` prints `verified` for each writer of the hub's inventory and no `missing` or `uncovered`. A reader that holds the records and the events draws such an event "attested at migration by `<machine>`" by Interfaces §D's consumer contract; the readers are O7's log views and O8's project channel, and B4 waits for one of them to draw a migrated event (its step 0; Q10).
3. **Single-trust inbound, dual-coded outbound.** A `sminos say` from a cut-over machine arrives on a machine not yet moved as readable words (`sminos chat` there shows it with no `(unverified)` mark); one the other way arrives on the cut-over machine as `(unverified, legacy)`; a DX6 RPC at a cut-over machine fails `unsupported` at the hub, which the hub's own test pins (`apps/desk-hub/src/objects/project.ts`'s browser `rpc` on an RL1 machine) and no brief exercises, since the VM has no card and the mini's cards are on web-cards before it moves.
4. **The phone.** A question from a cut-over mini reaches the phone through O13's web-cards and is answered there within the window the owner approved (B2 steps 4 to 7; Q3); the VM is answered by nobody and needs nothing; the MacBook's own sessions are local.
5. **sminos.** `sminos daemon status` says `uplink: RL10 (local-only), running (<pid>)`, `sminos hub show` prints the identity marked `cut over`, and `GET /api/machines` shows the machine with its DX2 presence `online: false` once its last lease lapses (an RL1 machine's presence reaches the relay alone, P5 Decision Log 37); the sminos installed is at or above 1.26.0 before the endpoint enrolls; `hub.json` is present until B4 and `mawsd endpoint status --json` says `"legacyKey": true` until B4.
6. **A VM provisions and retires itself.** A devcloud VM created with `--project maws` under M3's devcloud boots, installs `mawsd` with its delegation's prefix, redeems the provisioning code from Secret Manager, is `org-listed` under a certificate and cut over, with no hand in it, and comes back from an interruption between its redemption and its listing without redeeming again; `devcloud vm down` retires its certificate and frees its hub row, so `show` no longer lists it and a recreated VM may take its name; a forced delete prints the admin command that does the same from the Mac.
7. **Production is administered only on purpose.** Every `deployment org` command refuses production unless `--production` is given and `config.json`'s `orgGenesis` matches the hub's genesis; staging and loopback work as before; nothing prints a key, a token, a pairing secret or a code: codes go to 0600 files the owner carries.
8. **The undo of each brief step works as written**, exercised at least once in B1: a cutover undone leaves the VM on DX2 with a working credential (path 1a) or unenrolled and waiting (path 1b), and redone cuts it over again.
9. **The final state.** On every machine `mawsd endpoint status --json` says `"legacyKey": false, "legacyRetired": true` and `mawsd endpoint legacy status` says `purged` (no key bytes in `legacy.json` or under `stale-*/`), `hub.json` is gone, an event from one machine arrives at another verified v2-only (the imported line carries `verified` and no `mac`; `sminos chat` shows it plain); at the hub, probed inside an authenticated script, `GET /api/org/keys` answers `410 retired` with no copies, `POST /api/org/keys`, `DELETE /api/org/keys/<id>`, `GET /machine/stream` and `POST /machine/frames` answer 404 from the Worker (`X-Desk-Build` naming M5b's build), and an `rpc` frame on a project socket is answered `refused retired`; the phase-1 provisioning key is revoked and the v1 secret deleted; a VM born after it imports an old project's history as inert records (`sminos chat` shows them `(unverified, legacy)` at once, no hold).

- **MAWS first, fields optional.** M3 (doperpowers) consumes M1's code and M2's output and lands after them; every new RL10, hub, org-state or descriptor field is optional, and a machine, VM or hub without it behaves as it did (P5 §Ordering).
- **Production is touched by the briefs alone, at the owner's word.** No milestone's test, and no step of a brief that isn't marked `[owner]`, writes to `desk-hub` (the production Worker), its Access objects, its secrets or its org state. ### Orientation

- **The hub, as O11 and O13 leave it.** One Worker, `desk-hub`, serves both protocol families until B4: the phase-1 routes (`/machine/stream` and `/machine/frames` for DX2, the Project DO's browser `rpc` for DX6, the v1 codes `smns-enroll-v1.` and `smns-provision-v1.`, and the org-key routes `GET|POST /api/org/keys`, `DELETE /api/org/keys/<id>`, whose wrapped copies live in the Registry's `wrapped_keys` table, `apps/desk-hub/src/objects/org-keys.ts`, and whose last copy `DELETE` refuses, `409 last-key`) and the v2 routes O11 added (its Interfaces §B: the org-state chain, enrollments, `POST /machine/key`, `POST /machine/cert`, the certificate retirements `POST /api/org/cert-retirements` and `POST /machine/cert-retirements`, the pairing exchange `POST|GET /api/devices/pending`, listings, RL1 at `GET /machine/socket`). One generation counter per machine name covers DX2 and RL1 (`apps/desk-hub/src/objects/machine.ts`): a DX2 stream and an RL1 socket under one name replace each other (close 4409). Service tokens are named `desk-<org>-<machine>` and a redemption deletes every token of its name before it mints (`registry.ts`, `mint`). Production's org is `ssfskim`; its Access admits the owner by email; `apps/desk-hub/deploy/config.json` names it and pins no `orgGenesis` yet, because **production has no signed org state**: the only code that signs one is `OrgAdmin` in `apps/desk-hub/deploy/org-admin.ts`, which refuses production by name (`deploy/config.ts`'s `checkTestHub`) and refuses a configuration with no pin, and whose genesis has `projects: []`. The Registry keeps the phase-1 project directory and each machine's phase-1 row (with the former names a `--replace` rename recorded) apart from the signed state. The Org page that would sign the state in the app is O8's, not dispatched.
- **Enrollment, as O10 M2 built it.** Attended: `mawsd enroll` reads a `smns-enroll-v2.` code (its codec is `apps/desk-hub/src/protocol/identity.ts`, not `org-protocol`), redeems `POST /machine/enroll {token, machine}`, posts `POST /machine/key {pub, ref, mac}`, and is `hub-confirmed`; the enrolling member's device fetches `GET /api/enrollments/<id>/key`, checks the MAC with the pairing secret `k` that only the code carried, and signs a successor state listing `{ref, name, pub, owners}` and the `machineNames` pair; then the endpoint is `org-listed`. Re-enrolling an existing name needs a token minted with `{machine: <name>}` (`POST /api/enrollments`, admin), and its redemption fences the old credential and deletes the old service token at Cloudflare: **sminos's DX2 credential in `hub.json` dies at the moment the endpoint redeems.** Delegated: `enrollDelegated(input)` (`src/endpoint/enroll.ts`, `DelegatedInput = {hub, org, roots, recoveryPub, token, delegation: {id, prefix, privateJwk}, name}`) refuses a ref not starting with `<id>_` and any existing enrollment (`hub-confirmed` included), redeems the delegation's token, signs the machine's own `MachineCert` with the delegation key, posts it, and is live once `verifyMachineCert` accepts it; no command reaches it yet, and no `smns-provision-v2.` code exists. **A delegated name has no re-enrollment in place**: a held name, a DX2 row's included, is `409 name-taken` until its hub row is gone (`DELETE /api/machines/<name>` by an admin, or the machine's own `DELETE /machine/enrollment`). O2's `mawsd` command line (`src/mawsd/cli.ts` on `origin/p5-o2`) forwards `mawsd endpoint <cmd>` as `{command, args}` alone; only its `enroll` path reads a secret from stdin or a hidden prompt, sends it as `secret`, and stretches the request's deadline to `--wait`. The endpoint's `keys --json` answers `{enrollment, name?, org?, ref, keyId?, heldKeys?, refusing?}`. Device pairing (O11 M3): a new device, signed in as its member, posts `{deviceId, class, keyStorage, channelPub, stepUpPub?, passkey?, mac}` to `POST /api/devices/pending` (entries expire after 600 s); the approving device lists them, checks the MAC against the pairing code it showed (the hub never does), and endorses the device (`DeviceEndorsement`, domain `smns-device-endorse-v1`) into a successor. No code mints a pairing code or defines the device MAC's input yet; `org-protocol`'s `enrollmentMac` is the machine's.
- **The ref.** `<profile>/machine.json` is minted at first run by whichever of the app and `mawsd` runs first, never rewritten; `mawsd install --delegation-id <32 hex>` (O2 M5, on `origin/p5-o2`) mints it with the prefix before the unit's first start, and a well-formed id is silently ignored when the file already exists, so a VM that ran `mawsd` before it had its delegation keeps an unprefixed ref for good and can't be certified. O2's `devenv/setup.sh` passes `--delegation-id "$MAWS_DELEGATION_ID"` when that variable is set at the first `devenv up`; on a devcloud VM created with `--project maws` that run is boot step 12, as the owner, with `/etc/devcloud/env` in its environment.
- **sminos, as O12 phase 2 left it (1.26.2).** `sminos_rl10.py` finds `rl10.json` at `$SMINOS_RL10`, else `$MAWS_USER_DATA/mawsd/endpoint/rl10.json`, else the platform default profile's; the daemon's service records no `MAWS_USER_DATA`, so a machine's `mawsd` must run the default profile. The supervisor re-reads what it wants every 0.2 s: with `identity.json` present it runs the RL10 child only and waits, logging hourly, while `rl10.json` is absent (`daemon status`: `uplink: cut over; the endpoint is not running`); with it absent it runs DX2 from `hub.json` and probes RL10 whenever `rl10.json` appears, so **removing `identity.json` while the endpoint still serves RL10 re-cuts the machine over within about a second**, resetting `cutover`'s time. There is no `sminos daemon restart` verb and none is needed. `hub enroll`, `hub check` and `hub leave` exit 1 on a cut-over machine with "this machine's enrollment is its endpoint's". sminos answers `legacy-key?` from `hub.json` every time it is asked, so **deleting the endpoint's `legacy.json` alone is undone at the next RL10 hello**. `daemon status` reports the uplink child's state and the last tick, not the owed deliveries or the pending questions; `sminos list --json` reports each member's state (`waiting` is a pending question). `sminos/tests/bench_scale.py` drives the DX2 uplink only and has no RL10 mode. A `human` event imported over DX2 before the cutover and still owed is asked `words?` after it, for an event the endpoint never relayed. No test exercises the undo branch ("identity.json is gone … restarting it on the hub").
- **devcloud, as it is (0.12.0).** A VM's descriptor (`/etc/devcloud/boot.env`) carries secret ids, never values, and refuses unknown keys (`boot/devcloudlib/descriptor.py`). Boot step 11 (`sminos_host.py`) enrolls sminos on DX2 whenever the driver profile's `[desk] provisioning_secret` names the v1 code's Secret Manager id, piping the code to `sminos hub enroll --name <DEVCLOUD_NAME>`, and installs the daemon only when `hub.json` exists; it reads `hub check`'s exit 1 as "not enrolled" and would re-enroll a cut-over VM three times and fail the step at every boot and every half-hourly `refresh-secrets`. Departure (`departure.py`) runs `sminos hub leave` as its only word to the desk, and prints "it stays in the desk's Machines until someone removes it" when that fails; it stops no `mawsd`. The driver on the Mac (`driver/ops.py` `down`, `driver/reaper.py`) deletes the server, removes the tailnet node and prints `reaper.desk_note`; it holds no desk authority. Names are drawn as `dc-<label>-<4 hex>` by `driver/names.py` `draw`, the prefix fixed in code. Every VM's service account can read every secret of the Secret Manager project. A VM's tailnet name is `<name>.tail112c3f.ts.net`; its firewall admits every port on `tailscale0`, and the tailnet ACL has been verified for port 22 only. The boot's code is streamed from the Mac's installed plugin copy, so a devcloud change is version-bumped and installed on the Mac before any VM sees it.

### M1 — The v2 provisioning code, its redemption, the certificate's retirement and the local unenroll (MAWS)

**At its end.** A `smns-provision-v2.` code exists as a codec in `apps/org-protocol`; `mawsd endpoint provision` redeems one from stdin into a live certificate under the delegation, keeping what the retirement later needs, and resumes an interrupted or not-yet-listed provisioning without redeeming again; `mawsd endpoint retire` retires that certificate and frees the machine's hub row; `mawsd endpoint unenroll` takes any endpoint, attended or delegated, back to `enrollment: none` locally, so a brief can stop RL10 before it undoes a cutover. A code that carries the legacy key leaves the endpoint dual-coding from its first event, with no `hub.json` on the machine at all.

**Touches.** `apps/org-protocol/src/provisioning.ts` (new; exported from the package's index), `apps/org-protocol/test/provisioning.test.ts` and the vectors; `src/endpoint/cli.ts`, `src/endpoint/enroll.ts`, `src/endpoint/state/store.ts`, `src/endpoint/status.ts`, `src/endpoint/index.ts`; `test/endpoint/enroll.test.ts`, `test/endpoint/cli.test.ts`, `test/endpoint/status.test.ts`. **[needs O2]** `src/mawsd/cli.ts` and `src/mawsd/cli.test.ts`: the half that carries the secret. Nothing in `apps/desk-hub` (its routes exist).

**Decisions.**
- **The codec lives in `org-protocol`, beside `enrollment.ts`**, as `smns-provision-v2.` + base64url of UTF-8 JSON, the shape Interfaces §A fixes: `enrollDelegated`'s fields but `name`, plus an optional `legacy`. P5 Decision Log 35 said "beside `smns-enroll-v2.`", which turns out to live in `apps/desk-hub/src/protocol/identity.ts` with the phase-1 vocabulary that retires at B4; a code that outlives the retirement belongs with the enrollment MAC in the package every consumer imports. Unknown fields are refused, `privateJwk` must be a P-256 private JWK whose public point equals the delegation's `pub` in the state (checked at redemption, not at decode), and the decoder's refusals are named strings as the v1 decoder's are (`not smns-provision-v2`, `damaged`, `no <field>`, `bad <field>`). The hub never sees the code: it sees the token.
- **The code may carry the legacy key during the migration window** (`legacy: {org, key}`, the DX1 org key as base64url, the same bytes today's v1 code carries). `provision` stores it as `legacy.json` exactly as RL10's handover would, so the endpoint never asks `legacy-key?` and dual-codes from its first event. This is what lets a VM born after M3 skip DX2 entirely: no `sminos hub enroll`, no `hub.json`, no DX2 row at the hub to go stale (the carry note's stale machine), no credential to die at redemption. Rejected: enrolling new VMs on DX2 first so sminos can hand the key over, which creates the very row the delete hook was asked to clean up, and which has no path to a certificate while it exists (`409 name-taken`). The field leaves the code at B4 (M2's `code strip-legacy`). RL §5.3's rule that a code carries no org key is the member code's; the provisioning code is a secret-store artifact that holds the org key today.
- **`mawsd endpoint provision [--name N] [--wait [s]] [--json]`.** The code comes on stdin or a hidden prompt, never argv. The name defaults to the machine's host name lower-cased (on a devcloud VM that is `DEVCLOUD_NAME`, which is also sminos's name), and `--name` overrides it; a name outside the prefix is refused before any hub call, as is a ref without `<id>_` (`enrollDelegatedInto`'s checks, surfaced with their reasons: `ref-prefix`, `name-prefix`). It is a resumable transaction in four states, each read from the state directory, so a boot step may rerun it after any interruption, no run redeems twice, and no hub row is ever created that the machine can't later remove:
  1. *nothing held:* write `delegation.json` (Interfaces §B: the delegation's id, prefix and private JWK, 0600) and, when the code carries one, `legacy.json`, both from the decoded code and before any hub call; then redeem (`POST /machine/enroll`), generate the machine key and sign the certificate, and **write `provisioning.json` (Interfaces §B: the whole `Redeemed` answer, `enrollment` id included, the machine key, the signed certificate and the code's pins) before the first authenticated request**; `enrollDelegatedInto` today posts the certificate before anything is written, so a crash there left a hub row and a live certificate with no local credential to remove them, and `name-taken` for ever after;
  2. *`provisioning.json` held, no `enrollment.json`:* post the certificate (`POST /machine/cert`; the hub answers an identical signed record as already held, `OrgRecords.storeCert`'s `stored: false`, and another key under the name as `409 contested`, which is a refusal, never a retry), then write the same set `enrollAttended`'s writer writes, from `provisioning.json` alone (`machine-key.json`, `grants.json` holding the key's id, `enrollment.json` `hub-confirmed` with `cert` and the redemption's `enrollment`, `org.json`'s pins), each file atomic and the set idempotent, and delete `provisioning.json` last; a restart between any two of those writes reruns the set. **The endpoint's start completes a pending `provisioning.json` before its key-without-ledger rule runs** (`EndpointState.open` moves a `machine-key.json` with no `grants.json` to `stale-*/`; a half-written set would otherwise leave a private copy of the very key the recovery then rewrites), so the recovery owns the directory until the set is whole;
  3. *`hub-confirmed` with a `cert` and a `delegation.json`:* redeem nothing; run the org-state sync and wait for the certificate to be live (`syncAndPromote`, which `enrollDelegatedInto` today runs once and refuses to re-enter: the refusal of an existing enrollment is narrowed to an attended one or a delegated one under another delegation id);
  4. *`org-listed`:* exit 0, nothing posted.
  It waits up to `--wait` (default 300 s), exiting 0 when live, 4 while `hub-confirmed`, 1 on refusal, 2 with no endpoint module, 3 with no daemon. A `delegation.json` whose id differs from the code's is refused (`other-delegation`): the machine is unenrolled first. Rejected: teaching `enroll` both prefixes under one verb, which would make the attended flags (`--replace`) meaningless for a certificate and the certificate's (`--not-after`) meaningless for a member code.
- **The `mawsd` side carries the secret [needs O2].** O2's CLI reads a secret and stretches the deadline for `enroll` alone (`src/mawsd/cli.ts`, `enroll()`); M1 generalizes that path to a table of secret-reading commands (`enroll`, `provision`), each with its `--wait` deadline, so `mawsd endpoint provision` reaches `Endpoint.cli('provision', args, secret)` with the code read from stdin or the hidden prompt and never from argv. This half lands in M1's PR if O2 is on master by then, else as M1's follow-up PR on the same branch name with `-mawsd`; until it lands, `provision` is reachable in tests through `Endpoint.cli()` and in no brief.
- **The endpoint keeps the delegation key.** RL §5.3 accepts that a VM under a delegation holds its key (every VM under it can read the secret store anyway, and the remedy for a compromised VM is revoking the delegation), and the retirement record must be signed by it (RL §5.2). Rejected: re-reading the secret store at departure, which fails exactly when departure is already in trouble (a reclaimed spot VM, a VM whose ADC is gone).
- **`mawsd endpoint retire [--not-after <ISO>] [--json]`** signs `CertRetirement {org, keyId, notAfter}` with `delegation.json`'s key under `smns-cert-retire-v1`, `notAfter` defaulting to now plus 60 s of skew margin (RL §5.2: set once the key is gone, with a margin), and **writes `retirement.json` (the signed record, `posted: false, deleted: false`) before any hub call**, so a rerun reuses the same record and `notAfter`; posts it to `POST /machine/cert-retirements` (marks `posted` on 2xx; an identical repost is accepted), then `DELETE /machine/enrollment` so the hub row and its credential go too (both are needed before a recreated VM may take the name: `apps/desk-hub/test/org-delegations.test.ts`; marks `deleted` on 2xx), then, both marked, **destroys `machine-key.json` and `delegation.json`** rather than archiving them (RL §5.2: a retirement is trusted because the retired key is destroyed, so it can sign nothing backdated), runs `unenroll`'s local part for the rest, and exits 0 printing `retired: <name> (certificate <keyId> not after <ISO>); the hub row is gone; the keys are destroyed`. A lost answer is reconciled on the rerun: a `401`/`403` to the retirement's post or to the `DELETE` while `retirement.json` says `posted` means the hub already invalidated the credential, which is the `DELETE`'s effect, so `deleted` is marked from that evidence and the run completes locally; a `401`/`403` while `posted: false` is a refusal (exit 1, nothing destroyed, the admin's `machine drop` is the remedy). It refuses on a machine with no `delegation.json` (`not-delegated`, exit 1): an enrolled machine's key is retired by an admin's state change, never by itself. It is idempotent: a second run with no `retirement.json` and no credential exits 0 saying so. After it, the endpoint is unenrolled and sminos, cut over, waits for an endpoint that never comes; the VM is about to be destroyed, which is the only reason to run it.
- **`mawsd endpoint unenroll [--json]`** is local and talks to no hub: it stops the hub link and the direct listener, closes every channel `removed`, removes `rl10.json` and the socket (so sminos sees no endpoint), **destroys the private material of `machine-key.json` and `delegation.json`, and of every `machine-key.json` and `delegation.json` under an earlier `stale-*/`** (keeping each key id in `<stateDir>/stale-<ISO>/keys.json` for the record; `retire` does the same), moves `grants.json`, `enrollment.json`, `org.json`, `legacy.json`, `listings.json`, `notified.json`, `signatures/` and `inbound/` to that `stale-<ISO>/` (the key-without-ledger rule's directory, O10 M2), leaves `<profile>/machine.json` untouched, and reports `enrollment: none`. The private key is destroyed at once because nothing can use it again: a later `enroll` or `provision` generates a new key under the same ref (as `--replace` does), and the hub-side entry is dropped by M2's `machine drop` (which retires or revokes the old key by its id, never needing the private half) or by `retire`; a retired key that lingered on disk could sign backdated events that its retirement would verify (RL §5.2). `unenroll` refuses nothing: an unenrolled endpoint is the state O10 M10 ships in. This is the first half of every cutover undo in the briefs, because O12's switch re-probes RL10 within a second of `identity.json`'s removal (Orientation). Rejected: relying on the hub's `4403` to stop RL10, which reaches only an endpoint that is connected at that moment and leaves a disconnected one holding `org-listed`; archiving the private key, which keeps what retirement assumes gone.
- **Status and keys** gain `delegated: boolean` (`keys --json` and `status --json` both; M3's departure predicate and the briefs read `keys`).

**Does not touch.** The admin side that mints a delegation and emits the code (M2). devcloud (M3). The attended `enroll`'s own flow. The hub.

**Proves.** Acceptance 1's delegated half and item 6's machine half. Tests: the codec's vectors (round trip, each refusal, the optional `legacy`); `provision` against the local hub with a delegation the local `OrgAdmin` signs, end to end to `org-listed`, the certificate served beside the state; a code whose key doesn't match the state's `pub` refused at redemption with nothing posted; a ref without the prefix and a name outside it refused before any hub call; `legacy` kept at 0600 and no `legacy-key?` asked at the first RL10 hello (the fake sminos sees none; `status().legacyKey` true); the four states of the transaction, each resumed by a fresh process over the reopened state directory and nothing held in memory: a wait that times out (exit 4) then a rerun that lists without a second redemption (the local hub's `use` count unchanged), a kill between `delegation.json` and the redemption then a rerun that redeems once, a kill between `provisioning.json`'s write and the certificate's post then a rerun that posts once and lands `hub-confirmed`, a kill between the post and each of the write set's files then a rerun whose second post the hub answers as already held and whose set is complete (`enrollment.json` carrying the redemption's `enrollment`, `grants.json` the key id, `org.json` the pins), a listed machine's rerun posting nothing; `retire` destroying `machine-key.json` and `delegation.json` only after both hub calls are marked in `retirement.json` (a `DELETE` that fails before mutating leaves them and exits 1 for a rerun; a `DELETE` the hub completed whose answer was lost, simulated by a proxy that drops the response, is reconciled on the rerun from the `401` and the run completes), the same signed record and `notAfter` on every rerun; `unenroll` destroying the private key and keeping its id, a following `enroll` under the same ref with a new key accepted by the local hub (`POST /machine/key` under the recorded name); the crash-recovery scene carried through to `retire`: a provisioning killed between `machine-key.json` and `grants.json`, restarted (the pending record completed before the orphan rule), listed, then retired, after which no file under the state directory, `stale-*/` included, holds a private key (a walk of every `*.json` for `"d"` finds none); `other-delegation` refused; `retire` freeing the name (a recreated fake VM under the same delegation enrolls under it) and leaving no row in `GET /api/machines`; `retire` refused on an attended enrollment; `unenroll` on an attended and on a delegated endpoint: RL10 unserved at once (the fake sminos's socket closes and `rl10.json` is gone), the state moved aside, `machine.json` kept, a following `enroll` working under the same ref; `delegated` in both outputs with the status redaction test extended; **[needs O2]** a CLI test under a real pty that `mawsd endpoint provision` reads the code from stdin and from the hidden prompt, sends it as `secret`, and stretches the deadline to `--wait`, beside O2's `cli-prompt.test.ts`.

### M2 — Org administration for production before O8 (MAWS, `apps/desk-hub/deploy/`)

**At its end.** The owner can administer the production org from the MacBook with one command family, `pnpm --filter desk-hub deployment org <verb>`, under a guard that makes a production write deliberate: make the genesis and the recovery key, enroll and list a machine by a code carried by hand, create the devcloud delegation and emit its provisioning code, show a pairing code and approve the device that MACs under it (O13's phone), drop a machine or a delegation, and, at B4, retire the org key in the state and purge its copies. Staging and the local hub run the same verbs unguarded.

**Touches.** `apps/desk-hub/deploy/org-admin.ts` (its `OrgAdmin` grows the verbs; its `open` learns production mode), `deploy/org.ts` (new: the command's argument parsing and output), `deploy/bin.ts` (registers `org`), `deploy/config.ts` (the production rule below), `deploy/README.md` (the verbs and the production rule); `apps/org-protocol/src/pairing.ts` (new: the pairing MAC and its vector), `apps/org-protocol/test/pairing.test.ts`; `apps/desk-hub/test/deploy/org.test.ts` (new) against the in-process local hub.

**Decisions.**
- **Production mode is explicit and pinned.** `--production` is required for any write to `config.json`'s deployment, and every verb but `genesis` also requires that `config.json`'s `orgGenesis` equals the hub's genesis hash (`OrgAdmin.open`'s existing pin check, now a refusal on mismatch rather than on absence alone), or that `--genesis <pin>` is given explicitly for the read-only `show` (so B0 can check the genesis it just made before the pin is committed). `genesis` runs only while the hub holds no state and `config.json` pins none, prints the pin, and the brief commits it (B0). Without `--production`, `checkTestHub` refuses production by name as today. Rejected: lifting the guard for the staging-named verbs alone, which leaves a production write one typo away.
- **The tool verifies the chain it signs on, as a machine would.** `OrgAdmin.read()` takes the hub's head as given and `amend()` signs over it; a hub could hand back a genuine older head from before a revocation this very tool signed and get a signed fork, which a machine enrolled afterwards, holding only its pins, would accept. So the production tool keeps its own checkpoint beside its keys (`desk-hub-org-admin.chain.json`: the version and hash of every head it adopted, a durable high-water mark, and the one signed successor it has proposed but not seen adopted), reads the chain since its mark (`GET /api/org/state?since=`), verifies each successor and transition with `org-protocol`'s functions (`verifySuccessor`, `verifyTransition`, `verifyRewind`, as the endpoint's `org-sync.ts` does), and refuses to sign on a head below or beside its mark (`rollback`, `fork`). **A proposal is durable before it is sent**: the signed successor is written to the checkpoint as pending, then posted; the mark advances when the hub accepted it. An invocation that finds a pending proposal reconciles before it signs anything: the hub's chain since the proposal's parent either holds the proposal (adopt it, clear pending), holds nothing past the parent (resend the same signed proposal), or holds another successor of that parent (`fork`: refused, named to the owner, nothing signed), so a hub that kept a revocation but answered with an error can't obtain a second, revocation-free successor from the same parent. Staging and the local hub run the same code with a checkpoint under `DESK_STAGING_DIR`. Rejected: trusting the hub's head in production, which RL §5.5 forbids ("the hub never decides") and RL §5.2's rollback rule exists for.
- **The admin device is the tool's own.** The tool generates a P-256 channel key and step-up key once, kept as a device keys file `{version: 1, keyStorage: 'software', channel, stepUp}` (the app's `src/main/device/keys.ts` shape, so `OrgAdmin`'s reader takes either file) at `~/.config/claude-secrets/projects/-Users-new-Developer-GitHub-MAWS/desk-hub-org-admin.json`, 0600, and lists it in the genesis as the owner member's first device (`class: 'native'`, `keyStorage: 'software'`) with its step-up key in `root.keys`. O8's app devices then join through the pairing flow (`device pair` and `device approve`, below), and the owner retires the tool's device from the Org page once the app is root. Rejected: signing with the MacBook app's `<profile>/device/keys.json`, which makes a CLI the app's device, skips the app's step-up prompt, and binds O8 to a device id convention this tool would have to invent; the one cost of the choice taken, an extra device the owner retires later, is a line on the Org page.
- **The recovery key** is made at `genesis` as a P-256 key written to a path the owner gives (`--recovery-key-out <path>`, 0600, refused if the path exists or lies under the repository or `~/.config/claude-secrets`); the tool prints the path and nothing of the key, and the owner moves the file to an offline medium (B0). Rejected: keeping it beside the admin keys, which puts the root and its recovery in one directory.
- **Pairing has two halves and one MAC** (RL §5.3, O11 M3's exchange). `device pair --label L --code-out <path>` mints a pairing secret `k` (32 random bytes), writes its base64url as the pairing code to the path, and keeps `{label, k, expires}` in a local pending file beside the admin keys (`desk-hub-org-admin.pending.json`, 0600; entries expire with the hub's `PENDING_DEVICE_TTL_S`, 600 s). The new device (O13's phone) posts `PendingDeviceRequest` with `mac = pairingMac(k, {member, deviceId, class, keyStorage, channelPub, stepUpPub?, passkey?})`, Interfaces §C's function in `org-protocol` under domain `smns-pair-mac-v1`, each field length-prefixed as `enrollmentMac` does, absent fields encoded as empty, so no two inputs encode alike. `device approve [--device ID]` lists `GET /api/devices/pending`, verifies each entry's MAC against every unexpired `k` it holds, shows the verdicts, and endorses the one the owner names (or the only verified one) into a successor as a device of the owner member, dropping the `k` used. It refuses to endorse an entry whose MAC no held `k` verifies, so an approval never rests on hub-supplied keys. Rejected: approving by eye from the hub's listing, which is exactly the substitution the MAC exists to catch. O13 consumes the code's form and the MAC (flagged in the Decision Log); until O13 lands, the test's fake device is the consumer.
- **The other verbs** (Interfaces §C): `enroll <name> [--replace]`, `delegation create`, `delegation drop <id>`, `machine drop <name>`, `code strip-legacy`, `code inspect`, `keys retire`, `keys purge`, `provisioning revoke <id>`, `show`. `enroll` is two phases in one invocation: it mints the token (with `{machine: <name>}` when `--replace`, which is every re-enrollment in place), builds the code with a fresh `k`, writes it to `--code-out <path>` (0600, under `~/.config/claude-secrets/`, refused elsewhere or if the path exists) and prints the path, then waits up to `--wait` (default 1800 s, the brief's hand-carry) polling `GET /api/enrollments/<id>/key` every 5 s, verifies the MAC, signs and posts the successor listing the machine with `owners: [<the owner's member id>]`, and prints the state version. An interrupted `enroll` leaves a token that expires (TTL 900 s unless `--ttl`) and the code file, which the brief deletes; nothing else. `delegation create --label devcloud --prefix dc- --code-out <path> [--ttl <s>] [--max-uses <n>] [--legacy-from-v1-code]` mints the provisioning key v2 at the hub (`POST /api/provisioning-keys`), generates the delegation's key pair, signs the successor with the delegation (`owners: [<owner>]`), and writes the `smns-provision-v2.` code to the path; with `--legacy-from-v1-code` it reads a v1 provisioning code on stdin and copies its `key` into the code's `legacy`, so the org key is read from the artifact that already holds it and from nothing else. A code never goes to stdout: a session's transcript would keep it. `machine drop <name>` resolves the name three ways and says which: an attended machine the head lists gets a successor that moves its key to `retired` (`--revoke` to `revoked`) and the `DELETE /api/machines/<name>`; a certificate machine (a live certificate under the name in the state read's `certificates`) gets an admin retirement of that certificate's key into `retired` with the certificate's ref as holder (RL §5.2: an admin's retirement of a certificate is a state change) and the DELETE, so a forced-deleted VM's name is free for a recreated one; a phase-1 row with no key gets the DELETE alone. `code inspect` reads a code on stdin and prints its fields with every key and token elided. `keys retire` and `keys purge` are M5a's (Interfaces §E): the first signs the successor that carries `legacyRetired` and the second calls the hub's purge. `show` prints the head's version and, as tables, its members and devices, its machines (name, listed, ref, the DX2 `online` and `seen` the hub reports; a certificate machine from the state read's `certificates` as `certified`, with its ref and `notAfter` if retired), its delegations, and its `legacyRetired` if set, which the briefs read.
- **Access admission is not touched.** The owner is production's only member and is admitted already; `access-sync` is first run when a second member exists, which is O8's.

**Does not touch.** The hub's code. The app. desk-web.

**Proves.** Item 7, and items 1 and 6's admin halves. Tests against the local hub: `genesis` with the pin printed and the recovery key written at the mode asked, refused on a hub with a state; every other verb refused with no pin or a wrong one, `show --genesis <pin>` allowed; the checkpoint: a hub that answers an older genuine head after the tool signed a revocation is refused `rollback` and nothing is signed, a head beside the mark is refused `fork`, a correct genesis with an invalid head is refused, the mark advances only after an accepted successor, across two invocations, and the lost answer: a hub that keeps the posted successor but answers an error leaves a pending proposal, the next invocation finds it adopted and clears it, while a hub that kept it and then serves the parent again gets the same proposal resent and never a second one; `machine drop` on a certificate machine retiring the certificate's key with its ref as holder so a recreated fake VM takes the name; `enroll` end to end with the endpoint's `enrollAttended` as the machine (the code read from the `--code-out` file), a substituted key refused by the MAC; `--replace` on a listed name; `delegation create` with and without `--legacy-from-v1-code`, the file decoding to M1's shape, the delegation in the head; `--code-out` refused outside the secrets directory and on an existing path; the pairing MAC's vector; `device pair` then a fake device posting under the code and `device approve` endorsing it, an entry under a wrong `k` or none refused, an expired `k` dropped; `machine drop` retiring and revoking, and a phase-1 row's DELETE alone; `code strip-legacy` dropping the field and nothing else; `code inspect` eliding; `show`'s tables with an attended and a certificate machine; a redaction test over every verb's stdout and stderr that fails on anything shaped like a key, a token or a code.

### M3 — devcloud: the v2 seed, the first `devenv up`, provisioning at boot and retirement at departure (doperpowers)

**At its end.** A VM created with `--project maws` enrolls itself under the devcloud delegation at boot and cuts its sminos over, with no DX2 enrollment and no hand; `devcloud vm down` retires it; a forced or unreachable delete prints the admin command that does so from the Mac. VMs without the MAWS project boot as before with a local-only sminos. A replacement delegation under another prefix is one profile line away.

**Touches.** `devcloud/driver/profile.py`, `compose.py`, `names.py`, `up.py` (the `devcloud-enroll` label's producer), `reaper.py`, `ops.py`, `adopt.py`; `devcloud/boot/devcloudlib/descriptor.py`, `steps.py`, `sminos_host.py`, `departure.py`, and a new `maws_host.py`; `devcloud/tests/unit/` (the existing files plus `test_maws_host.py`); `devcloud/README.md` (the desk section); `devcloud/.claude-plugin/plugin.json` through `scripts/bump-version.sh --plugin devcloud`.

**Decisions.**
- **The profile names the v2 code, the delegation's id and the name prefix.** `[desk] provisioning_secret_v2 = "<Secret Manager id>"`, `[desk] delegation_id = "<32 hex>"` and `[desk] name_prefix = "dc-"` (the default, which `names.draw` today has in code) in `~/.claude/devcloud/driver.toml`; the descriptor carries the first two as `DEVCLOUD_MAWS_SECRET` and `DEVCLOUD_MAWS_DELEGATION_ID` (both optional), and `names.draw` takes the prefix from the profile so a replacement delegation under `dc2-` (a dropped delegation's prefix is reserved for the life of the org, P5 Decision Log 31) yields names under it. ### M4 — History re-attestation (MAWS)

**At its end.** A cut-over machine signs its DX1 history once, per project and writer, against the hub's own inventory of what it wrote; the hub keeps and serves the attestation beside the project's log; anyone holding the org state and the certificates can verify that a writer's phase-1 events up to a sequence number are the ones the machine wrote, and a check compares the attestations against the inventory rather than against themselves. After B4 the attestation is the only thing that vouches for those events.

**Touches.** `apps/org-protocol/src/history.ts` (new), `types.ts` (the domain), its vectors and tests; `apps/desk-hub/src/objects/project.ts` and `objects/registry.ts` (the table, the inventory and the routes), `src/worker.ts` (routing), `apps/desk-hub/test/history-attestations.test.ts` (new); `src/endpoint/cli.ts`, `src/endpoint/history.ts` (new), `src/endpoint/hub-http.ts`; `test/endpoint/history.test.ts` (new).

**Decisions.**
- **A record per (project, writer), not a re-upload.** Stored positions are immutable at the hub (`log-store.ts`'s `sameEvent`; a re-signed resend is a `conflict`), so history can't gain a `sig` in place. The record is Interfaces §D's `HistoryAttestation {org, project, writer, upTo, digest, created}` signed by the machine key under `smns-history-attest-v1`, where `digest` is the running SHA-256 over the canonical body of each event from seq 1 to `upTo`, `mac` excluded (`h_0 = ''`, `h_i = SHA-256(h_{i-1} ‖ canonical(event_i without mac))`), so a verifier with the stored events recomputes it in one pass. RL8 offered a per-event path or a checkpoint; the checkpoint costs one signature per writer and one hash per event, and binds the whole prefix, so a hub that dropped or altered an event inside it fails the check as a whole. The machine attests only events whose `mac` it verifies under the legacy key as it builds the digest; a writer whose events include one that fails is reported and not attested (`attest-history` prints `skipped <writer>: seq N fails its code`), since the machine can't vouch for a body it didn't write.
- **The inventory is the hub's, the names are the machine's.** The genesis has `projects: []`, nothing imports the phase-1 directory into the state, the state can't carry a former name without a machine entry (`machineNames`' rule), and the Registry's phase-1 machine row holds no former names either: they live on the machine alone, in sminos's `hub.json` and, after the cutover, `identity.json` (`former`, the names and the sessions held under them), which `sminos hub show` prints. So the machine names itself: `attest-history` takes `--former <name>` for each former name the brief reads from `sminos hub show` (none for a machine never renamed), and asks the hub for its inventory by name, `GET /machine/history-inventory?names=<current,former…>` (Interfaces §D), which answers every project of the org whose log holds a writer under one of those names, with each such writer's highest DX1 seq, from what the Registry's project directory and the Project DOs already hold. `attest-history` walks that and nothing else; `--check`, given the same names, compares the stored attestations against the same inventory and reports `uncovered <project>/<writer>` for any writer with no attestation at its `upTo`, so a check over an incomplete set can't pass; a name nobody claims (a deleted VM's, a Mac wiped before this child) is history that stays inert, and the brief records which. Rejected: reading `projects` from the state, which is empty; reading `former` from a hub row that has none; reading sminos's files from the endpoint, which O6 and O10 refused to couple to.
- **Who signs, for which writers, and how a former name binds.** The machine key signs, for every writer under its current name and every former name it claimed, and the record carries the claim: `names: [current, …former]`, inside the signature. A verifier binds a writer's name to the signer's ref by `machineNames` or a live or retired certificate (RL8), or, for a phase-1 former name no state ever held, by the record's own claim; the hub's courtesy check and every verifier refuse a claimed name that `machineNames` binds to another ref or that any certificate, live or retired, holds for another ref (a retired certificate ended its name's contest, not its history's ownership: `org-protocol/src/records.ts`), so the only claimable names are ones no machine ever owned under the new protocol. A false claim over an orphaned name mislabels a reader's history and confers no authority (a `human` event's words were never decided by a label), which is the trust phase-1 history had. `hub/<member>` writers (desk-web's words) are nobody's to attest: RL §9's "history is imported as inert records" is what they stay.
- **The source of the events is the hub.** The endpoint reads its own writers' stored events with its service token through a new machine-principal read, `GET /machine/projects/<id>/log?writer=<w>&after=<seq>`, paged at about 1 MiB like the org-state read (Interfaces §D); it does not read sminos's files, and the log plane's `hello`/`have` is sminos's connection, not a reader. If the Project DO already serves a member read of the same shape, the executor opens it to the machine principal rather than adding a second; the payload is the same.
- **`mawsd endpoint attest-history [--former <name>]… [--project <id>] [--check] [--json]`.** Without `--check`: fetch the inventory for the current and claimed names; for each project and writer, page the events, verify each code, fold the digest, sign, post `POST /machine/projects/<id>/attestations`, and print one line per writer (`attested <project>/<writer> through <upTo>`), `skipped` lines as above, and a summary; it is idempotent (a stored attestation at the inventory's `upTo` is left alone; after a cutover no DX1 event is added under an own writer, so a rerun changes nothing). With `--check`: fetch the inventory and the stored attestations (`GET /machine/projects/<id>/attestations`), recompute each from the stored events and print `verified`, `mismatch`, `missing` (a record whose events the hub no longer serves) or `uncovered` per writer, exit 0 only when every inventory writer is `verified`; this is acceptance 2's check and B4's precondition. It needs the legacy key for the first form (held until B4) and the org state for both.
- **The hub keeps the newest per writer** (`attestations(writer, upTo, record)` in the Project DO's SQLite, `CREATE TABLE IF NOT EXISTS`, no migration tag), accepts a record only when its signature verifies against the head's machine key or a certificate for the signer's ref and `writer`'s name binds to that ref by the rule above (a courtesy check, as every hub check is; `403 not-bound` for a claimed name another ref owns), refuses a lower `upTo` than stored (`409 stale-attestation`), and serves them to members (`GET /api/projects/<id>/attestations`) and machines. Verification by readers is `org-protocol`'s `verifyHistoryAttestation(record, events, head, certificates)`, `certificates` being the package's `Certificates {certs, retirements}` so a retired certificate's `notAfter` bounds its signatures and a recreated VM's live certificate is told from its predecessor's retired one.
- **Readers draw it by a contract this document fixes** (Interfaces §D): a reader shows an event as "attested at migration by `<name>`" when a stored attestation for its project and writer verifies and covers its seq, and as `(unverified, legacy)` otherwise. O7's log views and O8's project channel are the readers; sminos labels nothing by it, because a DX1 event is a peer message on every machine whatever its attestation says. The endpoint's inbound path is unchanged by M4; M5a is where "no legacy key" meets a v1 event.

**Does not touch.** The endpoint's inbound verification (`log-relay.ts`). sminos. desk-web.

**Proves.** Acceptance 2. Tests: the record's vectors (sign, verify, a changed event, a dropped event, a wrong writer binding, a retired key at and after `notAfter`, a claimed former name accepted when unowned and refused when `machineNames`, a live certificate or a retired certificate owns it for another ref (a different current machine claiming a retired VM's name can't replace that VM's attestation), a retired certificate and a recreated VM's live one under the same name); the inventory route from a seeded Registry and two Project DOs (a current and a claimed former name, a project with none of the named writers left out); the hub storing, refusing a lower `upTo`, a bad signature and an unbound writer, and serving; the endpoint attesting two projects with a current and a former name against the local hub and a seeded DX1 log, skipping a writer with a bad code, idempotent on rerun; `--check` reporting `verified`, `mismatch` after the test alters a stored event in the local hub, `missing`, and `uncovered` when the test removes one writer's attestation.

### M5a — The org key's retirement in the state, the endpoint and the hub (MAWS; deployable at any time)

**At its end.** The signed org state can say the legacy key is retired, every endpoint that sees such a head stops asking for the key and signs v2-only for good, a v1 event after it is inert rather than held, and the hub can purge the wrapped copies once the head says so. Nothing in this build changes a machine or a hub whose head carries no retirement.

**Touches.** `apps/org-protocol/src/types.ts`, `org-state.ts`, its vectors and tests; `src/endpoint/rl10/legacy.ts`, `rl10/link.ts`, `log-relay.ts`, `org-sync.ts`, `state/store.ts`, `status.ts`, `cli.ts`; `test/endpoint/cli.test.ts`, `org-sync.test.ts`, `rl10/*.test.ts`; `apps/desk-hub/src/worker.ts`, `objects/registry.ts`, `objects/org-keys.ts`, `objects/org-chain.ts`; the hub's tests; `apps/desk-hub/deploy/org-admin.ts` (`keys retire`, `keys purge`).

**Decisions.**
- **The retirement is in the signed state.** `OrgState` gains an optional `legacyRetired: {version, at}` (Interfaces §E), and the package's exact-field validator (`isOrgState` and `wellFormed` in `org-state.ts`, which refuse an unknown field) learns it, as does the hub's courtesy copy in `org-chain.ts`. **Every deployed verifier must carry this package before the field is published**: an older `isOrgState` refuses the whole state, and with it every later revocation; that is B4's step 0 for the hub, the three endpoints, O13's web-cards build and O8's app if landed, and the test below pins the skew. A successor may add it or drop it until the hub has purged (so B4's rehearsal is reversible); the hub refuses a successor that drops it after the purge (`409 key-purged`, since the key is gone and a machine that re-asked would get nothing). Rejected: a per-machine `legacy retire` verb as the switch (the state O10 M6 shipped): it is undone by the next hello while `hub.json` holds the key, and a machine enrolled after the retirement (B4's throwaway) would never learn of it; the state reaches every machine, present and future, through the sync it already runs.
- **The endpoint follows its head, and keeps the bytes until told to purge.** When the head it adopts carries `legacyRetired`, the endpoint rewrites `legacy.json` as the tombstone `{org, retired: <ISO>, key}`, keeping the key's bytes under the mark: it sends no `legacy-key?`, logs and drops a `legacy-key` frame, signs v2-only, verifies no v1 code, and `status` says `"legacyKey": false, "legacyRetired": true`. When a later head carries none (B4 step 1's undo), the mark goes and the retained bytes are the key again at once, with no hello and no `hub.json` needed, so a v2-born VM and a connected Mac come back inside the undo's bound alike. `mawsd endpoint legacy purge` (B4 step 5, irreversible) deletes the bytes from the tombstone and from every `stale-<ISO>/legacy.json` an `unenroll` left, and prints what it deleted; `legacy status` prints the four states (`held`, `retired (bytes kept)`, `purged`, `none`). `provision` writes the tombstone without bytes (`{org, retired}`) instead of the code's `legacy` when its first head carries the retirement, and an attended `enroll` likewise at its first sync: a machine that never held the key has nothing to keep. `mawsd endpoint legacy retire` is removed from the command line: O10 shipped it as the switch and this build makes the state the switch; its one caller was this document's final brief.
- **A v1 event after retirement is inert, not held.** With the tombstone, a v1-only event with no key is delivered down at once as `signer: {kind: 'legacy', checked: false}` (a new optional field; sminos labels a `legacy` signer `(unverified, legacy)` and never delivers it as words, so it needs no change) and spends nothing: a machine enrolled after B4 reading an old project's history imports it as inert records (RL §9), which M4's attestations vouch for where a machine attested them. Rejected: spending such positions, which would hide the org's history from any machine enrolled afterwards.
- **The hub purges on the head's word.** `POST /api/org/keys/purge` (admin) is refused `409 not-retired` unless the head carries `legacyRetired`; it deletes every row of `wrapped_keys`, clears `org.key_check` and `org.key_auth`, records `org.key_purged`, and from then on `GET /api/org/keys` answers `410 retired` with no copies and `POST /api/org/keys` is refused `409 retired`; the `last-key` refusal of `DELETE /api/org/keys/<id>` stays for the single-copy case, since the purge is the only way to zero. The admin tool's `keys retire` signs the successor and `keys purge` calls the route (M2's verbs, built here).

**Does not touch.** Any phase-1 route (M5b). sminos. devcloud. The app. The Machine DO's RL1 path.

**Proves.** Item 9's state half. Tests: the field's vectors (added, kept, dropped, refused after a purge by the hub's check); the version skew: the package at the previous commit refuses a state carrying the field (the reason B4 step 0 exists), the new one accepts a state without it; the endpoint rewriting the tombstone with the bytes kept at a head that carries the field, sending no `legacy-key?` across a reconnect, dropping a `legacy-key` frame, its status, the key in use again at once when a head drops the field with no hello in between, `legacy purge` deleting the bytes from the tombstone and from `stale-*/` and the status after; `provision` and `enroll` writing a byteless tombstone at a retired head; a v1 event delivered as `{kind: 'legacy', checked: false}` with no hold and no spent; the hub's purge refused before the field, zeroing the table after it, the later refusals, and a successor dropping the field refused after the purge; `pnpm --filter desk-web test` green (desk-web is untouched).

### The briefs

Each step is **Do**, **Check**, **Undo**. A `[owner]` step waits for the owner's word, and its Do is the owner's hand where it says so. Steps run in order; a check that fails stops the brief at that step, and the undo of that step and of every step after the last one whose check held is run before anything else, in reverse order; a step marked **irreversible** is taken only after every check before it has held and the owner has said so again at that step. **The cutover undo** is one idempotent sequence, the same whether the failure came before or after sminos's welcome, because an endpoint that becomes `org-listed` serves RL10 at once and sminos's probe can write `identity.json` before the enrolling step has finished its own checks: (i) `mawsd endpoint unenroll` on the machine (RL10 unserved, the private key destroyed, the rest of the local state aside, `machine.json` kept); (ii) `rm ~/.claude/sminos/daemon/identity.json` if it exists; (iii) the hub-side drop (`deployment org machine drop <name> --production`, which retires the key whose private half (i) destroyed); (iv) DX2 back, where there is a DX2 to go back to (a one-time v1 code from desk-web's Machines page, carried as the v2 code was, into `sminos hub enroll --replace` on stdin). A certificate machine runs `mawsd endpoint retire` for (i) and (iii) together, then (ii), then (iv) where its path has a DX2 (B1's 1a: step 3's undo).
