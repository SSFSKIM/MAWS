## Purpose

P5 turns MAWS into one app over many machines. Every machine needs a process that is always there, whether or not an app runs on it: the home of the machine's endpoint (O10) and, from O3 on, of MAWS's machine-bound services. O2 builds that process, `mawsd`, the **machine daemon**: a plain Node program, run at login by a LaunchAgent on macOS and by a systemd user unit on Linux, which owns the engine host (E10's supervisor, the process that holds every lane B session's `claude`) and the pty host (the process that owns terminals). Services stay in Electron main until O3.

After O2:

- On the MacBook, MAWS connects to the `mawsd` the LaunchAgent runs. The engine host and the pty host are `mawsd`'s children, not the app's. Quitting MAWS leaves terminals running; reopening it shows each terminal alive, with what it printed meanwhile. Restarting `mawsd` ends no session and no terminal.
- A session nobody has open is released 10 minutes after its last tab closed on a laptop, and after 24 hours on the mini or a VM. It is never released while it holds background work: a Bash job, a subagent, a Monitor, a scheduled job, an MCP task or a workflow, or any work the daemon can't read. The owner can mark a session **Keep running**.
- Every profile other than the default one (a dev run, an e2e run) gets a private `mawsd` the app starts, which exits when idle. Tests never touch the owner's daemon.
- On a devcloud Linux VM with no app, `devenv up` installs `mawsd`; it stays up across logout, and `mawsd status` answers with the machine's `MachineRef`, the stable id OX2 addresses machines by.
- O10 plugs its endpoint module into `mawsd` through a named seam.
- If the daemon shape breaks daily use or OX7's latency budget, the owner flips the profile back to today's shape in Settings.

**How to see it working.** On a Mac with a build of this branch: `ps -axo pid,ppid,command | grep -E 'mawsd|maws-supervisor|maws-pty-host'` shows `mawsd` with the engine host and the pty host beside it, none of them a child of MAWS. Open a terminal tab, run `sleep 30; echo done`, quit MAWS, wait, reopen: the tab shows `done` and the same shell. `mawsd status` prints the daemon, its machine ref and its hosts. The `e2e:supervisor-daemon`, `e2e:daemon-unit` and `e2e:daemon-idle` groups and the unit tests named in each milestone prove the rest. Concrete Steps has the commands.

## Acceptance

Numbered as O2's section in P5 numbers them, with four items the contracts add (8 to 11). Concrete Steps has each command.

1. **The daemon owns the hosts.** On a hosted Mac, `e2e:daemon-unit` installs a LaunchAgent with a test label for a scratch profile; launchd starts `mawsd` at load, restarts it after a `kill -9`, and `mawsd restart` gives `mawsd` a new pid while the engine host keeps its pid. On the VM, the systemd user unit runs `mawsd` for the default profile (item 6). In `e2e:supervisor-daemon`, the app connects to the running `mawsd` or starts one; the engine host and the pty host are `mawsd`'s children, each in its own process group; the app holds no connection to either host except through `mawsd`. A scratch profile's private `mawsd` exits by itself once the app has quit and both hosts are idle.
2. **Terminals survive the app.** In `e2e:supervisor-daemon` case (h): a terminal running a command when the app quits is alive at the next launch, with the same shell pid, and its tab shows the output written while the app was closed (within the pty host's 512 KiB ring). A command that writes more than the ring while the app is closed is never paused for want of a reader, and has run to its end by the next launch.
3. **The release is per role, on interest, with a keep mark, and strict.** `src/engine-host/work-state.test.ts` and `src/engine-host/process-table.test.ts` show:
   - a session holding a non-ambient background task of each kind is never released, by the idle release or the memory budget: a Bash job (`local_bash`), a subagent (`local_agent`), a Monitor (`local_bash` from the Monitor tool, and `monitor_mcp`), an MCP task (`mcp_task`) and a workflow (`local_workflow`);
   - a session whose last Stop listed a session cron is never released;
   - a session holding only ambient tasks (an auto-started `monitor_ws` watcher, a `dream`) is released;
   - each of P5 §2's three unreadable states blocks release until it is read: a cron tool in a turn that ended without Stop (until the next Stop); a `--resume` after an exit that was not a release (until the first Stop); an adopted process (until a task snapshot or change and a Stop);
   - interest holds a session, and its end starts the clock; a laptop releases after the configured idle time (10 minutes by default), a server after 24 hours; a kept session is never idle-released.
   `e2e:supervisor-daemon` case (m) shows it in the app: with the app open, a session with no tab is released after the idle time, one in a tab is not, and one marked Keep running is not. The cron source is a Stop hook callback in the engine host, proven by a replay of the recorded probe fixture (M2).
4. **The supervisor suites run on the daemon shape.** `e2e:supervisor-daemon` (every case of `e2e/supervisor.spec.ts`, with the daemon shape's expectations, and cases (l) and (m)) is green, and `e2e:supervisor` (the embedded shape) stays green. `e2e:supervisor-daemon:packaged` is green on a packaged build.

### Orientation

- **Today's process model.** Main forks the pty host as an Electron utility process (`src/main/hosts/supervisor.ts`, `utilityProcess.fork`) and reaches the engine host either as a utility process or as E10's detached supervisor, chosen by `src/main/hosts/mode.ts`. The supervisor is the engine-host bundle run by the Electron binary as Node (`ELECTRON_RUN_AS_NODE=1`), spawned by main's detached transport (`src/main/hosts/detached-transport.ts`) in its own session, serving one client over `<profile>/supervisor/host.sock` (`src/engine-host/detached.ts`, `src/shared/host/socket-server.ts`). Its files and lock are in `src/engine-host/supervisor-files.ts`. Its lifecycle clocks are in `src/engine-host/supervision.ts`; the idle-row release is in `src/engine-host/process-table.ts` over `isIdleRow` and `hardReasons` in `src/engine-host/budget.ts`.
- **E10's single-client machinery.** The engine host serves one client at a time. A client is served first and sends `{t: 'ready'}` after main's resync (`src/main/sessions/resync.ts`); the host then sends its connect burst: every row's state as events, then every event no client has received yet (`SessionStream.republish` in `src/engine-host/session-stream.ts`). Events with no ready client are dropped and stay undelivered. `e2e/supervisor.spec.ts` case (b) depends on that undelivered tail reaching main.
- **Host hooks.** `src/engine-host/host-hooks.ts`'s `HostHookRegistry` puts callbacks into `initialize.hooks`; `EngineSession.runHook` answers `hook_callback`. No production launch registers one today. App replays project launch-owned `initialize` fields in `src/engine-host/replay-handshake.ts` and match every other field exactly (`matches` in `src/engine-host/replay-transport.ts`).
- **Background tasks.** `SessionStatusTracker` (`src/engine-host/session-status.ts`) replaces its task set at each `background_tasks_changed`; `hardReasons` counts the non-ambient ones.
- **Where interest comes from.** `src/main/layout/open-session-tabs.ts` reads `main.tabs` from the layout store; `session.setVisible` keeps the read model's on-screen set (`src/main/sessions/index.ts`). The inactive sweep combines them today (`src/main/index.ts`).
- **The pty host.** `src/pty-host/table.ts` keeps a 512 KiB ring per pty and answers `pty.attach` with a replay from the last checkpoint. The renderer's `src/renderer/src/terminal/registry.ts` ends every running terminal when `pty.hostState` leaves `ready`.
- **e2e support.** `e2e/support/launch.ts` gives every launch a scratch profile; `e2e/support/processes.ts`' `killScratchProcesses` kills every process whose command line names the profile's root, which is why every process O2 starts carries its directory in argv.
- **The daemon shape, as O2 leaves it:**

```
launchd / systemd --user
 └ mawsd run --unit --dir <profile>/mawsd           (the app binary as Node on a Mac; the pinned Node on Linux)
    ├ engine host   argv0 maws-supervisor, own session      <profile>/supervisor/      (unchanged files)
    │   └ claude -p …  (lane B sessions)
    └ pty host      argv0 maws-pty-host, own session        <profile>/mawsd/pty-host/
        └ login shells
MAWS main ── engine-host.sock ─┐
          ── pty-host.sock    ─┼─ mawsd   (relays two hosts; serves the `daemon` namespace)
          ── machine.sock     ─┘
mawsd CLI ── machine.sock (status, restart, enroll, keys); `logs` reads the files
```

`<profile>/mawsd/` (mode 0700) holds `mawsd.lock`, `mawsd.token` (0600), the three sockets (0600), `mawsd.log` (rotated to `.1` at 8 MiB), `mawsd.out`, `endpoint/` (0700, O10's), `pty-host/` (0700: the pty host's lock, token, socket and log) and `bin/mawsd`: the daemon's runtime state. The machine's identity is the profile's, `<profile>/machine.json` (0600), shared with the app (M5). A socket path longer than 103 bytes falls back to `$TMPDIR/maws-mawsd-<12 hex of the profile's sha1>/` as `socketPathFor` does today.

### M1 — The idle-cost baseline

**At its end.** A measured e2e group, `daemon-idle`, records the idle RSS and CPU of today's supervisor: the detached engine host for a scratch profile after the app has quit with **Quit and keep sessions running**, holding one idle kept session. Three runs at M1's commit fix the baseline in `test/support/daemon-idle.ts`, with the bound P5's acceptance 14 uses. The spec records only, until M9 adds the daemon-shape run that asserts the bound.

**Touches.** `e2e/daemon-idle.spec.ts`, `test/support/daemon-idle.ts` and `test/support/daemon-idle.test.ts` (new); `package.json` (`e2e:daemon-idle`); `.github/workflows/gate.yml` (`MEASURED_E2E`) and the gate-plan tests it then requires.

**Decisions.**
- **No app code.** `git diff --stat <O2 base> HEAD -- src` prints nothing at M1's commit.
- **What is measured.** The scene: launch in detached mode (`MAWS_HOST_MODE=detached`, a scratch profile whose `settings.json` sets `supervisor.idleExitMinutes: null`, so neither the idle release nor the idle exit fires), start one replay session from `spikes/protocol-probe/fixtures/permission-roundtrip.jsonl` and let it hold at its permission request, answer it, let it end its turn and hold at its next prompt, then quit with the keep answer (`MAWS_E2E_QUIT_ANSWER`). Settle 120 s. Then, for 600 s, read `ps -o rss= -p <pid>` every 30 s and `ps -o time= -p <pid>` at the start and the end, for every process whose argv0 is `maws-supervisor` (at M9 also `mawsd` and `maws-pty-host`). The `claude` children are excluded (a replay has none, and a real one is the session's cost, not the daemon's). One kept idle session is the laptop's costly steady state: with no live session, today's supervisor exits after its idle time and costs nothing.
- **A run is valid** when the 1-minute load stays under 5 throughout (the settle guard of `test/support/latency-budget.ts`) and the measured processes live for the whole window. An invalid run fails, saying why.
- **The output.** `[daemon-idle] rss <r> KiB (median of 21) · cpu <c> s over 600 s · processes <names> · load <l>`, as a line and an annotation; raw samples to `test-results/daemon-idle.json`.
- **The baseline and the bound.** `DAEMON_IDLE_BASELINE` holds the median of three runs' RSS and CPU, the run ids and the commit. `DAEMON_IDLE_BOUND` is derived from it: the daemon shape's processes together stay within 1.5 × the baseline RSS and within the baseline CPU plus 1.0 s per 600 s. The reason: the daemon shape adds one Node process that loads less than the engine host, and adds no periodic work. Rejected: a fixed number of MiB, not tied to the measurement P5 asks for. The recording commit touches only `test/support/daemon-idle.ts`, from runs at M1's sha whatever has landed since.
- The spec skips without `MAWS_DAEMON_IDLE_PERF=1`; `daemon-idle` joins `MEASURED_E2E` and no other list.

**Does not touch.** Anything under `src/`.

**Proves.** Acceptance 7's first half. `test/support/daemon-idle.test.ts` pins the statistics (median, CPU-time parsing of `ps -o time=` in both `m:ss.cc` and `hh:mm:ss` forms) and the bound's derivation.

### M3 — Host supervision outside Electron

**At its end.** The machinery main uses to reach a host (the host supervisor with its held requests, crash ladder, resync and ready line, and the detached transport with its lock, spawn and update rules) runs in a plain Node process. It gains what `mawsd` needs: an externally driven ready line, a deliberate reconnect, hosts started on demand, raw forwarding and other start strategies. Every local socket path is checked before it is listened on or connected to. Main's behaviour is unchanged.

**Touches.**
- `src/shared/host/host-supervisor.ts`, `src/shared/host/detached-transport.ts`, `src/shared/host/identity.ts` (moved from `src/main/hosts/`, without their Electron imports) and their tests;
- `src/main/hosts/supervisor.ts` (main's wrapper: the utility launcher, Electron's `userData` and `packaged`), `src/main/hosts/index.ts`;
- `src/shared/host/private-path.ts` and its test (new); `src/shared/host/socket-server.ts` (`badToken`, the many-clients mode, `onClientEnd`), `src/shared/host/socket-port.ts` (`onEnd`), and the listen paths in `src/engine-host/detached.ts`.

**Decisions.**
- **The split.** The core takes its Electron facts injected: `launchUtility(spec)` (main's: `utilityProcess.fork` with a `MessageChannelMain`), `userData()`, `packaged()`. A plain Node caller passes no utility launcher, and a host spec asking for one fails at construction. The files keep O1's edits (M5's `machine` owner and `req.client`, M6's protocol 3 and `peer()`) **[needs O1]**.
- **The detached transport, generalized** (Interfaces). It takes the host's file set (directory, lock, token, socket, log; the supervisor's are the default), a start strategy (`spawn` with its command, arguments, environment and argv0; `unit`, a function that asks launchd or systemd to start the daemon; or `none`), and a build policy: `replace` is E10's rule (another build with nothing live is replaced; with sessions live it is served and asked to exit when idle), and `serve` serves any build of the major and never asks it to exit. Every default reproduces today's transport.
- **A relayed peer.** With `relayed: true` the transport knows that the process holding the lock (`mawsd`) is not the host its welcome names. So after it writes `exit {when: 'now'}` on a refused connection (Restart now, or a refusal with nothing live), it reconnects after `PID_POLL_MS` instead of waiting for the lock holder to die, and the relay's held hello answers once the replacement is up. Rejected: waiting for the lock holder's death, which never comes, since `mawsd` stays up while it replaces its upstream. `DetachedEvents.waiting` carries the whole `ServerRefuse` line (protocol, build, wire, live count), not only its reason and count, so that `mawsd` can reflect it.
- **New host-supervisor capabilities** (Interfaces):
  - `readyBy: 'external'` on a host: the ready line waits for `sayReady(owner)` instead of the resync;
  - `recycle(owner): Promise<void>`: close the served connection with E11's draining close (the socket port's `close({drain: true})`: this end stops writing and keeps reading, so every line the host wrote before it saw the end still reaches the listeners), and once the close has ended, or the port's grace has run out, reconnect at once, with no backoff and no crash count; it resolves when the fresh connection is welcomed;
  - `onDemand` on a host: a deliberate exit parks it (`parked`, which is internal: the `HostState` it reports stays `restarting` until the next launch) and it launches again at `wake(owner)` or the next dispatch; `adopt(owner)` makes one connect attempt with no spawn, to a host whose lock names a live process, and leaves the host parked when none answers;
  - `onEnd` on the served link: the peer's FIN, reported before `close`, for a relay whose own server is half-open (M5);
  - `forward(owner, request)`: send an envelope request as received and answer the host's response as received, with no input or output validation, so a field this build does not know passes through;
  - `onRaw(owner, listener)`: every event as received, before and without the registry's name and payload checks, beside the validated `onEvent`.
- **A pty host's death, as main sees it.** When a detached pty host's welcomed pid is gone (a crash), the supervisor emits `pty.exit` for every pty it was told of, as the utility path does today; a quiet loss (the pid lives, the link closed) emits none, since the shells live on.
- **Private paths** (RL §5.11). `assertPrivateDirectory(dir)` before a listen or a token read: the directory, by `lstat`, is a directory (not a symlink), owned by the process's uid, with no group or other bits. `assertPrivateSocket(path)` before a connect: by `lstat`, a socket owned by the uid; its directory passes the first check. A failure throws with the path and the reason, and the caller logs it and treats the host as unreachable. Every socket O2 creates or connects to uses them, the supervisor's included. Rejected: a peer-credential check, which Node's `net` cannot do without a native addon (Decision Log, the uid boundary).
- **Nothing before the token.** `serveSocketClients` gains `badToken: 'refuse' | 'close'`. `close` ends a connection whose token is wrong or missing with no line; main's transport already treats a close before any answer as unanswered and retries within its budget, reading the token again each time. `mawsd`'s sockets and the pty host's use `close`; the engine host's keeps `refuse`, E10's behaviour, which writes its protocol, build and live count to the refused peer. That peer can only be the same uid, so the change is left to the architect (Decision Log). It also gains a many-clients mode for `machine.sock` (M5): no replacement, and a host runtime per connection from a factory.

**Does not touch.** The pty host's entry (M4). `mawsd` (M5). Main's shape selection (M7).

**Proves.** Acceptance 9, and the base of 1. The moved tests (`supervisor.test.ts`, `detached-transport.test.ts`, `identity.test.ts`) pass with only their imports changed. New tests: an external ready line (no burst before `sayReady`; a resync is not run); `recycle` (a line the host wrote just before it saw the end still reaches `onRaw`; then a fresh connection, no crash count, held requests sent on the new one); `relayed` (after `exit now` on a refused connection, a reconnect while the lock holder lives, and a welcome once the relay answers one); `onDemand` (a deliberate exit parks, `wake` and a dispatch both launch; `adopt` connects to a live lock holder and spawns nothing when none answers); `onEnd` (on a half-open server, the peer's FIN arrives before `close`, and a line written after it still reaches the peer); `forward` passing an output with a key the registry lacks and an event the registry lacks, which `onEvent` drops; `buildPolicy: 'serve'` never writing `exit`; each start strategy; `private-path.test.ts` for a symlinked directory, a symlinked socket, a 0755 directory, and a foreign owner (faked through an injected `lstat`); `socket-server.test.ts` for `badToken: 'close'` (no byte written to a wrong token) and the many-clients mode (two clients served at once, neither replaced).

### M4 — The pty host on a socket, with binary output frames

**At its end.** The pty host has a socket mode beside its utility mode, with a lock and a token. Its `pty.data` events travel as binary frames to a peer that declared it reads them. Its commands and events are on the cross-build wire. The renderer keeps a terminal across a reconnect to the same pty host.

**Touches.**
- `src/pty-host/index.ts` (the mode at load), `src/pty-host/detached.ts` (new);
- `src/shared/host/socket-host.ts` (new: the private directory, the lock through `takeLock` over a given file set, the token, the listen, the exit order, factored out of `src/engine-host/detached.ts`, which keeps its sweep and `Supervision` on top);
- `src/shared/host/socket-protocol.ts` (`PTY_MARK`, `splitRecords`), `src/shared/host/socket-port.ts` (encode and decode), `src/shared/host/socket-server.ts` (the capability gate), `src/shared/ipc/wire.ts` (`WIRE_CAPABILITIES`, the manifest's scope), `src/shared/ipc/wire-manifest.json` and `src/shared/ipc/schema.ts` (`PTY_HOST_EVENTS`) **[needs O1]**;
- `src/pty-host/table.ts` and `src/shared/ipc/schema/pty.ts` (`pty.attach`'s `credit`);
- `src/renderer/src/terminal/registry.ts` and its test.

**Decisions.**
- **An attach that takes no credit.** `pty.attach` gains an optional input field `credit` (default `true`; additive, under M2's bump). With `credit: false` the pty host answers as today (it flushes, replays from the checkpoint or the ring, and names `nextOffset`) but does not apply the flow reducer's `attach` step, so the reader that holds the credit keeps it. This is how a remote viewer (O10, through M5's seam) reads a terminal: from frames and the ring, lossy past 512 KiB, never as a second crediting reader. Rejected: a rule in `mawsd` alone, which cannot stop a remote attach from resetting the credit once it reaches the pty host.
- **The mode.** `process.parentPort` present → utility, unchanged. `--detached <dir>` → socket mode: `socket-host.ts` with the pty host's file set under `<dir>`, argv0 `maws-pty-host`, logging to `<dir>/host.log`. One bundle for both modes, as the engine host has.
- **The pty host's life in socket mode.** `exit {when: 'now'}` and SIGTERM end every live pty through its existing ladder and exit. It never exits on its own and has no exit-when-idle: its client decides when it is idle (M5 parks it when no app is attached and no pty is alive), so no new command is needed to disarm one.
- **The pty host joins the wire manifest.** O1's M6 left the pty host's commands and events out of `wire-manifest.json` because the pty host was always the app's own build. Under the daemon shape it is `mawsd`'s build, which may be another, so every `pty-host`-owned command and the events it emits (`pty.data`, `pty.exit`, as a `PTY_HOST_EVENTS` list beside `HOST_EVENTS`) join the manifest's scope, and the readers O1 made tolerant read them tolerantly too **[needs O1]**. The entries arrive as additive under M2's bump. This extends O1's manifest scope; the Decision Log flags it.
- **The frame** (Interfaces). After the handshake a record whose first byte is `0x01` is a pty frame, beside `0x00`'s document frames and `{`'s JSON lines; JSON escapes every control character, so a line never starts with either mark. The socket port writes an `evt` named `pty.data` as a frame when its peer declared the capability `socket.ptyFrames`, and decodes a frame into the same `{t: 'evt', name: 'pty.data', payload}` message, so neither the runtime nor the supervisor sees a difference. The server lists the capability in its welcome; the client lists it in its hello; the server writes frames only to a client that listed it. Rejected: frames always on, since an older peer would read `0x01` as a broken line and close.
- **The renderer across a reconnect.** On `pty.hostState` `restarting`, running terminals wait rather than end. On the next `ready`: the same pid → each waiting terminal reattaches through its existing reattach path (`pty.attach`, replay from the checkpoint or the ring); another pid, or `crashed` → each ends as today. A utility pty host always comes back with a new pid, so the embedded shape behaves as before.

**Does not touch.** Main's hosts (M7). `mawsd` (M5). The terminal's UI.

**Proves.** Acceptance 2's host half. Tests: the frame codec round trip; a frame split across reads at every byte; frames, document frames and lines interleaved; a frame over `DOC_FRAME_CAP` closing the connection; the capability gate both ways (a client without it gets JSON lines); `src/pty-host/detached.test.ts`: spawn through the socket, `exit now` ending a live pty, the lock held by a second candidate (exit 3), a wrong token closed with no output; `wire.test.ts`: the manifest lists the pty host's commands and events; `table.test.ts`: an attach with `credit: false` on a paused pty returns the replay and leaves it paused, with `acked` unchanged, and a crediting attach afterwards resumes it; `registry.test.ts`: the same pid reattaches, a new pid ends.

### M5 — `mawsd`

**At its end.** `mawsd run` is a working daemon for a profile: its files, its lock, its machine ref, its two upstream hosts started on demand, a relay socket per host for one app at a time, its own `daemon` namespace on a third socket, the interest union, its clocks, and the endpoint seam with no module behind it.

**Touches.**
- `src/mawsd/index.ts` (the entry: `run` and M6's commands), `src/mawsd/daemon.ts` (the composition root), `src/mawsd/relay.ts`, `src/mawsd/clocks.ts`, `src/mawsd/endpoint-seam.ts`, and tests (new);
- `src/shared/daemon/files.ts`, `src/shared/daemon/profile.ts` (new); `src/shared/machine/ref.ts` and `src/shared/machine/identity-file.ts` (new, unless O6 has landed them, in which case import them);
- `src/shared/ipc/schema/daemon.ts`, `names/daemon.ts`, `grades/daemon.ts` (new) and the composed registry **[needs O1]**;
- `electron.vite.config.ts` (main's second input: `out/main/mawsd.js`), `src/engine-host/bundle-guard.test.ts` (extended to `mawsd.js` and the pty-host chunk), `eslint.config.js` (`src/mawsd/**`).

**Decisions.**
- **The build.** `mawsd` is a second input of main's electron-vite build, so its `?modulePath` imports of the engine host and the pty host emit the same files main's do, and both compute one build id. The guard requires `mawsd.js` and its chunks to load everything at start (no dynamic `import()`) and to require only Node builtins and the externals the engine host already allows, plus `node-pty` (for the pty host's chunk). If Rollup's chunking puts an `electron` import in `mawsd`'s graph, build `src/mawsd` with its own config instead, and note that its host bundles then carry their own build ids.
- **The process.** `mawsd run --unit|--private --dir <profile>/mawsd`, with `MAWS_USER_DATA=<profile>`, spawned with `--disable-sigusr1` and a `SIGUSR1` listener of its own, as the supervisor is. Start, in order:
  1. `assertPrivateDirectory`;
  2. `takeLock` over `mawsd`'s file set (held → exit 3 for `--private`, exit 0 for `--unit`, so launchd does not loop against a live holder);
  3. the token and the machine ref;
  4. on macOS, the backup exclusion of `<profile>/mawsd/` (below);
  5. the log, and `<profile>/mawsd/endpoint/` created or corrected to 0700, which `mawsd` never reads inside;
  6. the sockets;
  7. the endpoint module's `start`, so the machine is reachable from outside even while both hosts are parked;
  8. the adoption of hosts already running.

  Exit order: stop accepting; the endpoint module's `stop`, awaited up to 2.5 s (it stops taking remote work, makes its RL4 ledger durable within about 2 s, and closes its channels with a restart reason); close the client connections; leave both hosts running (`mawsd` never stops a session); remove the sockets and the lock if they are still ours; exit 0, 75 for a requested restart (the units restart on it), 1 on a fatal error.
- **Out of backups** (RL §5.3, the remote layer's Decision Log 24). On macOS, `mawsd` excludes `<profile>/mawsd/` from Time Machine at every start with `tmutil addexclusion <profile>/mawsd`, the sticky form, which follows the directory and needs no root (skipped when `tmutil isexcluded` already says so; a failure is logged, not fatal). A restore must not bring back an old machine key with an old grant ledger. `<profile>/machine.json` stays at the profile's root and in backups, so a restored daemon keeps its ref and re-enrolls under a new key, its old grants refused. Linux has no system backup to exclude from; a VM restored from a snapshot is its operator's residual (the remote layer's Decision Log 24).
- **The machine ref** (OX2; the identity file P5 Decision Log 27 makes one interface for the app and `mawsd`, as O6's execution document, M1, specifies it). `mawsd` calls `readOrMintMachineRef(profileDir)` from `src/shared/machine/identity-file.ts` at its first run, before it serves. The file is the profile's, `<profile>/machine.json` (the app's `userData` root, not `<profile>/mawsd/`), because the ref is the profile's identity in either shape and the app may already have minted it; it holds `{ "version": 1, "ref": "<ref>", "mintedAt": "<ISO time>" }`, mode 0600. A mint is 16 random bytes as 22 base64url characters (128 bits, inside RL5's `[A-Za-z0-9_-]{16,64}`), written whole to a same-directory temporary file `machine.json.<pid>.<random>` (0600), `fsync`ed, published with `link(temp, machine.json)` (`EEXIST`: another process won, so read the winner's), then the temporary file is unlinked; a stray `machine.json.*` older than a minute is deleted at start. So the mint is race-safe between the app and `mawsd` with no shared lock (`mawsd`'s own lock does no harm). A file that exists but does not parse, or whose ref breaks the format, stops `mawsd` (exit 1, the log names the path); nothing ever rewrites it. `src/shared/machine/ref.ts` (`MachineRefSchema`, `MachineRef`) and `identity-file.ts` have no Electron import, so main and `mawsd` share them; whichever of O2 and O6 lands first creates them, and the other imports them (if O6 created them, O2 adds the option below). A machine that enrolls through a devcloud delegation needs a ref beginning with the delegation's id (RL5, the remote layer's Decision Log 25): `readOrMintMachineRef(profileDir, { prefix })` mints `<prefix>_<22 base64url characters>`, where the prefix is the delegation id, 32 lowercase hex digits (55 characters in all, inside RL5's 64); a prefix of any other form is refused. `mawsd` itself never knows a delegation and mints without one, and an unprefixed ref is 22 characters, so it can never take a delegation's `<id>_` shape (P5 Decision Log 31); M8's install passes the prefix at the first run, from the devcloud seed (O14's input). A file that already exists is never rewritten, prefix or not. Rejected: minting again over a bad file, which gives one machine two identities, and a file under `<profile>/mawsd/`, which the embedded shape would not see.
- **The upstreams.** One host supervisor (M3) with two hosts. The engine host: the detached transport over `<profile>/supervisor/` (the same files and lock as the embedded shape, so one engine host per profile in either shape), spawning `mawsd`'s own engine-host bundle with `process.execPath`, build policy `replace` (E10's update rule, now `mawsd`'s), `readyBy: 'external'`, on demand. The pty host: the detached transport over `<profile>/mawsd/pty-host/`, spawning the pty-host bundle with `--detached`, build policy `replace`, ready at connect, on demand.
- **The relays.** `engine-host.sock` and `pty-host.sock` each serve one app at a time, the socket layer of `src/shared/host/socket-server.ts` with protocol 3 **[needs O1]**; a second welcome replaces the first, as today. Per connection:
  - **The handshake reflects the upstream.** Once the upstream is connected, `mawsd` welcomes with the upstream's facts: its pid, start, build, minor and live counts, and its capabilities together with `mawsd`'s (`socket.ptyFrames`). While the upstream waits for an incompatible host still running sessions, `mawsd` answers with that host's refusal line as it received it (M3's `waiting` carries it), and an `exit {when: 'now'}` on the refused connection makes `mawsd` replace it (`replaceIncompatible`); main's relayed transport (M3) reconnects without waiting for `mawsd` to die, and its next hello is held until the replacement welcomes `mawsd`. While the upstream is starting (an on-demand host waking), the hello waits until the upstream is connected or 15 s pass, then the connection closes and the app retries within its own start budget; main's daemon-shape transports wait for a welcome as long as their start budget (M7). So main's crash detection by pid, its update banner and Diagnostics read the engine host, as they do today. Rejected: `mawsd`'s own facts, which would make an engine-host crash look like a quiet reconnect, with no toast.
  - **Requests are forwarded raw.** Every `req` goes upstream through `forward`, and its response comes back as received. Rejected: a validating relay, since the relay's registry would cap every field at `mawsd`'s minor, and tolerant reading would drop a newer peer's fields on the way through.
  - **Intercepted, on the engine host's relay:** `host.interest` (kept per connection; the union goes upstream); `host.stopAll` (the upstream is told the close is deliberate, then forwarded; the exit that follows parks the host until the next attach or request, so a quit spawns nothing and Settings' Stop all gets a fresh host when main reconnects); `host.configure` (its `idleExitMs` becomes `mawsd`'s idle time, then forwarded); `host.exitWhenIdle` (forwarded and tracked); and the socket layer's `exit` lines (`now` → the upstream exits now and parks, as after `stopAll`; `idle` → ignored, since `mawsd`'s clocks decide).
  - **Replaced upstream.** If the engine host replaces `mawsd`'s connection (`refuse replaced`: an embedded-shape app took it), `mawsd` stops reaching that host, closes its relays and exits 0, so neither launchd nor systemd restarts it into a tug of war. Rejected: reconnecting, which would take the host back from the app.
  - **Ready and events.** The app's `ready` line calls `sayReady('engine-host')`; from then on, every raw upstream event reaches the app. The pty relay's upstream is ready from its connect; its events reach the app after the app's own `ready`.
  - **Document channels.** `documents.open`, `documents.close` and their frames pass to the engine host's upstream with the app's channel numbers, and `documents.closed` and frames come back. Channel numbers are split between the two users of the one upstream connection until O3: the app's are below 2³¹ (main's relay counts up from 1 today), and the endpoint's are 2³¹ and above. `mawsd` closes an app's `documents.open` at or above 2³¹ with `documents.closed {reason: 'host'}`, and frames on a channel go back to whichever side opened it. The split is a value convention inside `Channel`'s existing range, enforced in `mawsd`'s code and never as a narrowed schema bound, because the three `documents.*` lines are frozen for protocol major 3 (P5 Decision Log 42). A recycle ends every channel on the upstream, the endpoint's included; the endpoint hears each end (`documents.onClosed`) and reopens its own when `onUpstream` reports the fresh link.
- **One upstream connection per app attachment.** When an app is welcomed on `engine-host.sock`, `mawsd` recycles its engine-host connection, and it recycles it again when the app leaves. So the engine host sees one client per attachment, exactly as with main today: its resync, its ready line and connect burst, its undelivered tail (case (b)), its `onClientGone` hooks, its per-connection interest and its login-shell recapture all keep their meaning. Between attachments `mawsd` holds a connection that never says ready, for its own requests (interest, configure, exit-when-idle, the CLI's status), and the engine host's events stay undelivered for the next app. O3 replaces this with a permanently ready connection and per-client cursors, when the services consume events. Rejected: one always-ready connection now, which delivers to `mawsd` the events the app missed and loses them, since per-client cursors are O3's. The pty relay is not recycled: the ring and `pty.attach` cover a reattach.
- **The departure drains both hops, in order.** The engine host counts an event delivered once it has written it to the socket (`SessionStream`'s delivered cursor), so an event `mawsd` has read must reach the app or it is lost. Main leaves with E11's draining close: it stops writing and keeps reading until `mawsd` closes. So when `mawsd` sees the app's end:
  1. it takes no more of the app's requests;
  2. it starts the upstream's draining close (`recycle`);
  3. it forwards to the app every event the engine host wrote before it saw that end, while the app is still reading;
  4. once the upstream has closed, or 500 ms have passed, it ends the app's side, and only then waits for the fresh connection's welcome.
  The engine host counts nothing written after its end as delivered, so those events wait for the next app's burst. Three pieces of plumbing make this possible, since a Node server by default ends its writable side the moment its peer's FIN arrives:
  - `engine-host.sock`'s server is created with `allowHalfOpen: true` (that relay only);
  - `serveSocketClients` and `SocketPort` report a peer's `end` (its FIN) apart from `close`, and the relay starts step 1 at `end`;
  - `recycle` reports when its drain is complete (M3), so step 4 ends the app's side before the reconnect, not after.
  The 500 ms bound sits inside main's own: `CLOSE_GRACE_MS` (1 s, `src/shared/host/socket-port.ts`) is both main's socket grace and its quit's outer bound (`shutdownSteps` in `src/main/index.ts`), and neither changes. Events the upstream had not delivered past the bound are counted in one log line, as a consumer's death would lose them. An app that vanishes without a close (a `kill -9`) loses whatever was in flight to it, as it does today. A `kill -9` of `mawsd` loses the events it had read and not yet forwarded, as a `kill -9` of main loses the events main had read and not yet processed: E10 promises no more for a consumer's death, and O3's per-client cursors, which replay from the engine host's ring, close both cases. Rejected: an acknowledgement protocol now, which is O3's cursor work brought forward.
- **The pty host's output credit while no app is attached.** The pty host pauses a pty once 256 KiB are unacknowledged (`src/pty-host/flow.ts`), and only a renderer acknowledges. So, with no app on `pty-host.sock`, `mawsd` owns the credit: at the app's departure it acknowledges each live pty at its current offset (`pty.list`'s `offset`), and it acknowledges each `pty.data` it hears at the chunk's end offset (`pty.ack`, an existing command). A program then never stops for want of a reader; output beyond the 512 KiB ring overwrites it, and the next reattach takes the registry's lossy path. At an app's welcome, `mawsd` stops acknowledging before it forwards anything, and the renderer's `pty.attach` resets the credit to its own (`stepFlow`'s `attach`), which fences the handover; an acknowledgement of `mawsd`'s still in flight can only move the acknowledged offset forward, never past what was emitted. A paused pty emits nothing that would prompt an acknowledgement, so `mawsd` also settles the credit on every pty-host connection while no app holds it: a `pty.list`, then a `pty.ack` of each live pty at its offset, which resumes a pty that paused while `mawsd` was down (`stepFlow`'s `ack`). A remote viewer never holds the credit: it stays with the app, or with `mawsd` while no app is attached. So `mawsd` sends every `pty.attach` that arrives through the endpoint's `dispatch` with `credit: false` (M4), whatever the request said, and refuses `pty.ack` and `pty.checkpoint` from it (`internal`, "the credit is the app's or the daemon's"); the remote viewer reads frames and the ring, lossy past 512 KiB. The pty host never sees a second crediting reader. Rejected: a detached-consumption mode in the pty host, which needs a new command and a second notion of who reads.
- **Hosts already running are adopted at start.** On demand means `mawsd` never spawns a host that nothing needs. At its start, `mawsd` connects to each host whose lock names a live process, with no spawn (M3's `adopt`), so after a restart with no app attached it holds the engine host (and its park clock runs) and the pty host (whose credit it settles at once). A host whose lock names nothing stays parked.
- **`machine.sock`.** It serves the `daemon` namespace (Interfaces), a `machine`-owned namespace (beside O6's `machine.identity`, whichever lands first being the first) **[needs O1]**: `daemon.status`, `daemon.restart`, `daemon.endpoint`. Many clients at once (the app and any CLI), in M3's many-clients mode: each connection served by its own host runtime over the same handlers, with O1's `ClientRef` per connection. O3 replaces this with the services' front.
  - **Grades** (OX9's three kinds, settled with O10; P5 Decision Log 29). `daemon.status` is `list`, like O6's `machine.identity`: O1 has no machine-scoped view, and a listing read of the machine is the nearest. `daemon.restart` is `machine-admin`: a remote restart drops its own channel, and the device resumes by cursor. `daemon.endpoint` is `internal`. All three stay main-only (the renderer never invokes them), so this departs from O1's rubric line "every `mainOnlyCommands` entry is `internal`": a main-only command a remote caller reaches through the endpoint takes its effect's grade. Record it as an O1 rubric line, and change `grades.test.ts`'s `internal` set to the main-only entries less `daemon.status` and `daemon.restart` **[needs O1]**.
  - **Local-only status fields.** What `daemon.status` returns to a remote caller carries no file path, no log location, no tailnet address and no key material. The schema marks each such field local-only (`localOnly(...)`: `.optional()` with `.meta({ localOnly: true })`; `profile`, `logPath`, and any later one). Every local answer carries them; `remoteDaemonStatus(status)` drops every marked field by walking the schema, so the endpoint drops them for a remote caller without knowing O2's fields. Since a marked field is optional, the redacted answer still validates against the one `DaemonStatusSchema`, the registry's output schema, at every boundary (a remote app's supervisor included), and the wire manifest keeps one shape. Rejected: a second, public schema, which a remote receiver validating against the registry would not know. The endpoint's own `status()` (enrollment state, state version, hub connection, channel counts) is O10's and keeps to the same rule.
- **The clocks** (`src/mawsd/clocks.ts`):
  - the engine host parks after `idleExitMs` with no app on `engine-host.sock` and an empty interest union (no remote viewer either): `mawsd` arms `host.exitWhenIdle {armed: true}`; the host exits once no row is live and its plugin runner is idle; the exit parks it. An app's attach, or any session entering the interest union (a remote viewer's report included), disarms it first and restarts the clock. Under an armed exit-when-idle, M2's release ignores interest, which is meant for the upgrade path (an old engine host serving until idle). The park clock never arms while anything holds interest, so a remote viewer's session is never released through it;
  - the pty host parks when no app is on `pty-host.sock` and no pty is alive: at the app's departure `mawsd` asks `pty.list`, and again at each `pty.exit` while no app is attached (its pty link is always ready, so it hears them); with none alive and still no app, it sends `exit {when: 'now'}`; an attach cancels the check;
  - a private `mawsd` exits 0 once no client has been on any socket for `idleExitMs`, both hosts are parked and no hold is out (the endpoint's `hold`, below); a unit `mawsd` never exits by itself;
  - `idleExitMs` is the last `host.configure` an app sent, 10 minutes until then; `null` arms nothing.
  Rejected: keeping both hosts up under the unit, which costs the laptop their idle memory for nothing.
- **The interest union.** The union over the relay connections' sets and the endpoint's remote viewers, whose subscriptions count as interest (OX5; P5 Decision Log 29) and arrive through the seam's `interest.report`, never as a raw `host.interest`. It is sent upstream at every change and after every recycle.
- **The endpoint seam** (Interfaces; its shape settled with O10, which owns the module). `daemon.ts` holds `endpoint: EndpointModule | null`, `null` at O2; O10 replaces `loadEndpointModule()`'s body.
  - **When it runs.** It starts as soon as `mawsd`'s own sockets are up (start step 7), not at a host's first connect: hosts start on demand, so a restarted `mawsd` with both hosts parked would never make one, and the machine would be unreachable from outside. A remote request that needs a host wakes it through `dispatch`, as an app's request does. It stops first in the exit order, bounded as above.
  - **What `mawsd` gives it:**
    - `machine`: the ref, the profile, the state directory, and `kind` (`unit` or `private`). Only a unit daemon binds the tailnet direct listener by default, so the two profiles of O6's scene on one Mac never both bind it;
    - `dispatch` and `onEvent`, raw, as M3 forwards them; until O3, lane B events reach it only while an app is attached (P5 Decision Log 29: that half of O10's acceptance 2 waits for O3), and `onAttachment` says when that changes, so it can tell a remote subscriber why a stream paused;
    - `onFrame` for binary frames: the pty host's `pty.data` frames, and document frames on the endpoint's own channels, which it opens and closes through `documents` in its own number range (2³¹ and above);
    - for those channels, `documents.onClosed(channel, reason)`, and `onUpstream({connected, generation})` for the engine host's link. `reason` is the host's own `documents.closed` (`host`: a refusal or an eviction; `reset`: the socket's high-water mark) forwarded for an endpoint channel, or `upstream` when the link it rode ended. When the engine-host link ends for any cause (a recycle, a crash, a reconnect), `mawsd` reports `onClosed(…, 'upstream')` for every endpoint channel open on it, then `onUpstream({connected: false})`; once a fresh link is welcomed, it reports `onUpstream({connected: true, generation: n + 1})`, and the endpoint reopens what it needs. `documents.open` and `documents.frame` answer `false` while no link is up. So a channel's end reaches the endpoint whether or not the app's attachment changed;
    - `hold(reason)`, released by the function it returns: a private `mawsd`'s idle exit waits while any hold is out. Being enrolled holds nothing; the endpoint holds while a remote channel is open or an RL4 op is in flight;
    - `interest.report` and `interest.drop`, for remote viewers;
    - `log`.
    No hub configuration and no tailnet address pass through the seam: both are the endpoint's own state.
  - **Its state** (the remote layer's Decision Log 24). `<profile>/mawsd/endpoint/` (0700) holds the machine key (0600) and, beside it, the grant ledger; a daemon that finds the key without the ledger, or the ledger without the key, starts unenrolled, which is the endpoint's own logic, and `mawsd`'s start order leaves the directory to it. The endpoint writes `<profile>/mawsd/endpoint/rl10.json` (`{socket, pid, build}`, 0600) for the sminos daemon, which has no MAWS code and finds it by the literal default paths in Interfaces, or under `MAWS_USER_DATA` in tests; the RL10 socket itself takes M5's long-path fallback, and the file names the path it took.
  - `daemon.endpoint` delegates the CLI's endpoint commands to `cli` (M6); `daemon.status` reports `status()` as `endpoint.detail`.

**Does not touch.** Units and the CLI's client commands (M6). Main (M7). Any service.

### M6 — The command line and the units

**At its end.** `mawsd` has its command line, and an installer that writes, loads and removes its LaunchAgent or systemd user unit for any profile, under any label.

**Touches.** `src/mawsd/cli.ts`, `src/mawsd/units/launchd.ts`, `src/mawsd/units/systemd.ts`, `src/mawsd/install.ts` and tests (new); `src/mawsd/index.ts`.

**Decisions.**
- **The commands.** `mawsd run …` (M5); `status [--json]`; `restart`; `logs [--follow] [--host daemon|engine|pty]`; `endpoint <command> …`, with `enroll` and `keys` as its aliases; `install [--delegation-id <id>]`; `uninstall`. The profile is `--profile <dir>`, else `MAWS_USER_DATA`, else the platform's default (Interfaces). Exit codes: 0 done, 1 failed, 2 not available here, 3 not running, 4 enrolled with the hub but not yet listed in the org state.
- **`status`.** Running: from `daemon.status` (sample in Concrete Steps). Not running: whether the unit is installed and loaded, the log's path, and the machine ref read from `<profile>/machine.json` (`readMachineRef`), so enrollment can read the ref before the daemon has ever answered; exit 3. The machine ref line is always `machine <ref>`, and `--json` carries it as `machine`.
- **`restart`.** A unit daemon: `launchctl kickstart -k gui/<uid>/<label>` or `systemctl --user restart <unit>`. A private one: `daemon.restart`, after which the next client start spawns it.
- **`logs`** reads the files directly, so it works with the daemon down: `mawsd.log`, the engine host's `<profile>/supervisor/host.log`, the pty host's log.
- **`endpoint`, `enroll` and `keys`** (settled with O10). `mawsd endpoint <command> …` passes its command and arguments through `daemon.endpoint` to the module's `cli`, so O10 adds commands (`revoke` and the like) without touching O2; `enroll` and `keys` are aliases of `endpoint enroll` and `endpoint keys`. What O10's module answers, as O10 has asked for it:
  - `mawsd enroll [--name N] [--replace] [--wait [<seconds>]] [--json]` reads the enrollment code from a hidden prompt when stdin is a terminal, else from stdin to its end, never from argv, since the code carries a token and a pairing secret. The CLI sends it as `daemon.endpoint`'s `secret` field over `machine.sock` (0600), and nothing logs it. It exits 0 when the machine is listed in the org state, and 4 when the hub has confirmed but the state does not list it yet. `--wait` blocks until it is listed or the timeout passes (default 300 s); the CLI's request takes that deadline instead of the 10 s default.
  - `mawsd keys [--json]` prints the machine ref, the name, the key's id and storage, the enrollment state (`none`, `hub-confirmed`, or `org-listed v<N>` with the head's hash), the org id and the hub's URL, and exits 0.
  Until O10, with no module: `enroll` prints "this daemon has no endpoint module yet (P5 O10)" and exits 2; `keys` prints the machine ref and "no machine key: not enrolled", exit 0; any other `endpoint` command exits 2 with the same line. This narrows O2's acceptance 5 for these commands to the seam; O10 makes them work.
- **`install --delegation-id <id>`.** On a devcloud VM enrolled through a delegation, the install mints the profile's ref with the delegation's id as its prefix (M5) before the unit's first start, if no ref exists yet. M8 takes the id from the devcloud seed, whose location and field are O14's to fix.
- **The units** (Interfaces). The label is `dev.maws.mawsd` (systemd: `mawsd.service`) for the default profile; any other profile, and every test, passes its own. `install` writes the unit file, loads it (`launchctl bootstrap gui/<uid>`; `systemctl --user daemon-reload` and `enable --now`), enables lingering on Linux (`loginctl enable-linger <user>`, through `sudo -n` when the plain call is refused), and restarts the daemon when the file's content changed. It is idempotent. `uninstall` unloads and removes the file; sessions keep running in the engine host, which the next app connects to in either shape.
- **The wrapper.** `install` also writes `<profile>/mawsd/bin/mawsd`, a shell script that runs the unit's program with the profile, and links `~/.local/bin/mawsd` to it when that directory exists and holds no other `mawsd`.

**Does not touch.** Main (M7). The Linux release directory and its runtime (M8): on Linux, M6's installer takes the program and runtime paths as arguments; M8 supplies them.

**Proves.** Acceptance 5's command behaviour, and the units the app and M8 install. Tests: the exact plist and unit text for a given profile, label and program; the command sequence of `install` twice (the second changes nothing) and of `uninstall`, through fake `launchctl`, `systemctl` and `loginctl`; a stale program path rewritten and the daemon restarted; process-level CLI tests against a private daemon (`status` running and stopped, `restart`, `logs`, `enroll` and `keys` with no endpoint module, `endpoint revoke` with no module exiting 2), in class 1a on Linux; `enroll` reading its code from piped stdin and never from argv (an argument after `enroll` that is not a known flag is refused, exit 1); `install --delegation-id` with a malformed id refused, and with a good one minting a 55-character ref once.

- **The shape setting.** Settings version 19 adds `supervisor.shape: 'embedded' | 'daemon'`; new profiles and the 18 → 19 migration take `daemon`, so the owner's profile moves at O2's landing, as P5 §2 intends. Settings › Engine › Background supervisor gains the switch ("Run sessions under the machine daemon"), which applies at the next launch, and a line for the daemon (kind, pid, machine ref). The mode, read once before `createHosts`: `MAWS_HOST_MODE` (`utility`, `detached` or `daemon`) wins; under `MAWS_E2E=1` or `MAWS_HARNESS=1` it is `utility`; otherwise `daemon` for the daemon shape and `detached` for the embedded one. Rejected: an environment variable or a profile file for the flip-back, which the owner would have to find.
- **The default profile.** It is the profile whose real path equals the platform default (Interfaces). A packaged app installs or repairs the LaunchAgent before it creates its hosts, so the unit runs this app bundle, then starts it; the first install makes macOS show its "Background Items Added" notice once, which the owner sees at their first launch of a build of this branch. An unpackaged run (`pnpm dev`) uses the unit when it is installed, never writes it, and otherwise runs embedded for that launch, saying so in the log and in Diagnostics. A unit the system will not run (MAWS turned off in Login Items) also runs embedded for the launch, with the reason. Switching the setting changes nothing in the running launch, which keeps its daemon and its three links. The next launch of a packaged app on the default profile with the shape embedded finds the LaunchAgent, uninstalls it before it creates its hosts (which ends `mawsd`, whose hosts keep running), then ends the socket-mode pty host, whose terminals end as an embedded app's terminals do at quit, and connects to the engine host directly, with its sessions. Rejected: uninstalling at the switch, which cuts the running launch off its own daemon.

Rejected: never restarting it, which leaves an old daemon running until the next login.

On the daemon shape the update banner's `matches` compares the engine host's build with the engine-host build the daemon would start (`daemon.status.build.engineHostBuildId`), since the engine host's updates are `mawsd`'s to make; the embedded shape keeps comparing with the app's own.

### M8 — The Linux package, the devenv step and U8

**At its end.** A Linux machine with no app installs `mawsd` from a checkout through `devenv up`, into a release directory with its own Node runtime, as a systemd user unit with lingering, and it stays up across logout. The package decisions are recorded. The macOS TCC question has a verdict or a scheduled owner run.

**Touches.** `scripts/mawsd-pack.mjs` (new; `pnpm mawsd:pack`), `packaging/mawsd/node.json` (new), `src/mawsd/install.ts` (the Linux release directory), `devenv/setup.sh`, `devenv/validate.sh` (new), `spikes/mawsd-tcc/` (the probe and `findings.txt`, new), this document's Decision Log and Surprises.

**Decisions.**
- **The pack.** `pnpm mawsd:pack` runs `pnpm build:main-preload` and assembles `dist/mawsd/<version>-<commit>/`: `out/main/**`; the production closure of the externals the bundle guard allows (`zod`, `@modelcontextprotocol/sdk`, `node-pty`, and their dependencies), from the installed tree; a minimal `package.json`; and on Linux `runtime/`, the pinned Node, downloaded from nodejs.org and checked against `packaging/mawsd/node.json`'s sha256 for the architecture (`linux-x64`, `linux-arm64`) before it is unpacked. A mismatch refuses the pack.
- **The Linux runtime and the Node floor.** The runtime is the Node release equal to Electron 44.4.5's `process.versions.node` (24.21.0, per E10's grounding), so the Mac and Linux run one Node line; if nodejs.org has no such release, the newest 24.x, recorded in Surprises. The floor `mawsd` asserts at start is Node 24.11.0, the first 24 LTS, which has `node:sqlite` without a flag (O3's index), type stripping on by default, and `--disable-sigusr1`. The pack's smoke check runs, with the runtime: `node -e "require('node:sqlite')"`, `node --disable-sigusr1 -e 0`, and a `.ts` file importing another by its `.ts` extension. Rejected: the host's Node, whose version drifts between hosts and with apt; a single-executable build, which does not carry a native addon simply.
- **`apps/org-protocol` and the loader.** The package's relative imports carry `.ts` extensions and use erasable TypeScript, so Node can load it unbundled (P5 Decision Log 16). `mawsd` bundles it, as it bundles everything, so no runtime stripping is needed; the floor above also loads it unbundled with Node's default type stripping, and nothing in `mawsd`'s launch passes `--no-experimental-strip-types`. Whether Electron's Node mode strips types is checked once on the Mac (Concrete Steps) and recorded; the Mac relies on the bundle either way.
- **node-pty's Linux build.** node-pty 1.1.0 ships no Linux prebuild, so `pnpm install` builds it with node-gyp (allowed by `pnpm-workspace.yaml`'s `allowBuilds`), against the installing Node's headers; it is an N-API addon, so it loads under the pinned runtime. `devenv/setup.sh` installs `build-essential` and `python3` with apt when `make`, `g++` or `python3` is missing. Rejected: a prebuilt fork of node-pty, a second implementation for one platform; a vendored `.node`, an unreviewable binary in the repository.
- **The uid boundary without peer authentication.** The darwin-only peer-auth addon checks a connecting process's code identity on the cua socket; on Linux, and on every socket of `mawsd`, the boundary is the uid: 0700 directories, 0600 sockets, a token readable only by the uid, and M3's owner and symlink checks on every listen and connect. Nothing weaker is offered, and nothing claims more. Rejected: a peer-credential check, which Node's `net` cannot make without an addon of its own.
- **The unit's program path from a checkout.** The unit never runs code from a working checkout. On macOS it runs the app bundle that installed it (`<bundle>/Contents/MacOS/MAWS` as Node, its entry inside `app.asar`), rewritten when another bundle takes over (M7); a bundle kept under the checkout's `dist/` works but is rewritten by every build, so `/Applications` is the recommended place. On Linux, `mawsd install` copies the pack into `~/.local/share/maws/mawsd/releases/<version>-<commit>/`, points `current` at it, writes the unit against `current`, and keeps the two previous releases. Rejected: the checkout's `out/` and `node_modules/electron`, which would make a branch switch or a half-finished build the owner's daemon at its next restart.
- **The login-shell capture under a unit.** A unit has no login shell, and its environment is minimal. The capture (`src/shared/host/shell-env.ts`) keeps running `$SHELL -ilc 'env -0'` with stdin closed and its 5 s bound, and its shell is `$SHELL`, else the passwd entry's shell (`os.userInfo().shell`), else `/bin/zsh` on macOS and `/bin/sh` on Linux. A failed capture falls back to the process environment and logs it, as today. It is recaptured once per app attachment, since M5's recycle is a new client. Rejected: freezing the installing shell's `PATH` into the unit, as sminos's LaunchAgent does, which goes stale when the owner's rc files change.
- **The Linux profile directory.** `${XDG_CONFIG_HOME:-$HOME/.config}/MAWS`, the directory Electron's `userData` would be for productName MAWS, so a machine's layout does not depend on whether an app runs there. Rejected: the XDG data directory, a different layout from the app's.
- **Surviving logout and restart (U8, Linux).** `mawsd` runs in the user manager (`user@<uid>.service`), not in the login session's scope, so `KillUserProcesses` does not reach it, and lingering keeps the user manager up after the last logout and from boot. The unit sets `KillMode=process`, so stopping or restarting it ends only `mawsd`, and the engine host, the pty host and their children stay in the unit's control group. `Restart=on-failure` restarts it after exit 75 or a crash. Rejected: the default control-group kill, which would end every session at a `mawsd` restart; a transient scope per child, which O16 may adopt for its session hosts.
- **The devenv step.** `devenv/setup.sh` (header `# devenv-inputs: pnpm-lock.yaml package.json pnpm-workspace.yaml packaging/mawsd/node.json`) installs missing system tools by `uname -s`, runs `pnpm install --frozen-lockfile` (on Linux with `ELECTRON_SKIP_BINARY_DOWNLOAD=1`, set in the script's Linux branch, since `devenv/env` applies on the Macs too), and on Linux runs `pnpm mawsd:pack` and `mawsd install` for the default profile, with `--delegation-id <id>` when the devcloud seed names the VM's delegation (the seed's location and field are O14's input; with none, the ref has no prefix). Where `systemctl --user` has no user manager (a container), it says so and installs no unit. On macOS it never touches launchd: the app installs its own LaunchAgent (M7). `devenv/validate.sh` runs one focused unit test and, on Linux, `mawsd status`. Both are safe to re-run.
- **TCC under launchd (U8, macOS).** Which app macOS's TCC attributes a file access to when `claude` runs under `mawsd` under a LaunchAgent. The probe (`spikes/mawsd-tcc/`): a LaunchAgent with a probe label runs the same program the unit runs, which spawns `/bin/ls ~/Documents` and `/bin/ls ~/Desktop` and records each result and any prompt's named app; then the same through the real engine host's spawn path. It raises TCC dialogs, so it runs only on a Mac with the owner present and the architect's go, never on this MacBook unattended. Its verdict goes to Surprises, with the decision it implies (for example `AssociatedBundleIdentifiers` in the plist, or nothing). Until then, the plist carries `AssociatedBundleIdentifiers: [dev.maws.app]`, which only groups it under MAWS in Login Items.

**Does not touch.** Signing, notarization or an updater (deferred in P5). The VM's own provisioning.

**Proves.** Acceptance 5 and 6 on the VM, and U8. Tests: the pack's assembly against a fixture tree (the externals' closure present, the runtime refused on a wrong sha256); `install`'s release directory, `current` flip and pruning. The VM proof and the TCC probe are Concrete Steps 9 and 10.
