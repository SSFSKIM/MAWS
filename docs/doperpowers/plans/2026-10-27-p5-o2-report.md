## What landed

`mawsd` is a per-profile daemon outside Electron that owns the engine host and the pty host. How it runs depends on the platform and the profile:
- on macOS, the default profile's LaunchAgent runs it; a packaged app installs or repairs that agent;
- on Linux, a systemd user unit with lingering runs it, installed by `devenv up` into a content-named release directory with its own Node 24.21.0;
- any other profile starts a private `mawsd`.

Main reaches the two hosts and `daemon.*` through three relayed sockets.

Sessions are released strictly, by interest. A session with no tab and no keep mark is released after the idle time, even while the app is open. A session is never released while it holds any of these:
- crons, from Stop and from the durable `scheduled_tasks.json`;
- background tasks;
- work it cannot read.

Terminals outlive the app. Settings version 20 makes the daemon shape the default, and the owner can switch back to embedded. A test or harness launch refuses the default profile (O3's planner P9).

## The idle cost and the bench

- **Baseline** (the detached supervisor at M1's `d14e92991`): physical footprint median 64481 KiB, CPU 0.11 s (P5 Decision Log 48). The combined bound derived from it is 96721 KiB and 1.11 s (P5 Decision Log 57).
- **Runtime floor** (a diagnostic): 13153 KiB for a bare Electron 44.4.5 run as Node.
- **Early check** (M5, `mawsd` alone with no hosts): median 26481 KiB.
- **At the head** (M9, the daemon shape): 94947 KiB combined (`mawsd` 28865, engine host 66081), CPU 0.11 s, load 2.9. That leaves 1.8% to spare against M1's fixed bound.
- **After the landing merges** the first daemon run read 101411 KiB (40640136886, load 3.6) against M1's fixed 96721: `mawsd` grew to about 31 MiB with O10's endpoint wiring, and the engine host spread 66 to 70 MiB run to run. The architect ruled that the bound is re-derived on the landing tree: 1.5 times the detached supervisor measured there, re-measured when a landing misses.
- **The landing window** (CI-opt's quiet window, 2026-10-28 10:05–11:29Z, tree `d6037a48a`): the supervisor read 65729 (40650181035), 70881 (40669418019) and 67409 KiB (40673974571), median 67409 KiB and 0.11 s, so the bound is 101113 KiB (1.5 × 67409 = 101113.5, floored by DL57's "never above 1.5x") and 1.11 s. The daemon shape read 97683 KiB (40671838782, load 3.4; `mawsd` 31361, engine host 66321) and 99219 KiB (40676048769, load 3.8; 31073 and 68145). Both are within the bound, with about 1.9% to spare. A third run (40678158535, 96675) is invalid on load 7.6. CPU was 0.11 to 0.13 s.
- **The later merges** changed no code under `src/mawsd`, `src/engine-host` or `src/pty-host`. The daemon's graph gained only schema data: O7's two optional machine-state fields (+523 B in `mawsd`'s load closure) and #292's optional `lastPrompt`, which is read only when a transcript is parsed. The window's runs therefore stand.
- **The bench** (`e2e:local-latency-daemon`, M9): delta-to-frame p50 25.9 / p95 38.4 ms, against limits of 26.45 / 42.56 (O1's baseline 24.45 / 37.56 plus 2 / 5 ms). Round trip 1.1 / 1.6 ms, against limits of 2.9 / 6.3.

The architect accepted the thin margin and recorded it in P5's Risks row for acceptance 14 (`27dda37d5`). The follow-up lever is `mawsd`'s eager start-up graph; Outcomes & Retrospective describes it.

## For the lander

- **A canonical `mawsd` on the mini cannot collide with the job's own:**
  - The e2e labels are `dev.maws.mawsd.e2e-<run>-<attempt>-<case>`, and the sweep touches only `dev.maws.mawsd.e2e-*`.
  - Sockets are per profile, and the temporary-directory fallback is hashed per profile.
  - `mawsd` listens on no TCP port at O2.
  - The packaged job runs on a scratch `MAWS_USER_DATA`.
  - The packaged check (`e2e/support/canonical-mawsd.ts`) snapshots the canonical plist, the default profile's sockets and lock, and its `mawsd/` tree before the job, and fails on any change the job could cause.
