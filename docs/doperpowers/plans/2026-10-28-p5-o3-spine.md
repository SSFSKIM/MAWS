## Purpose

P5 makes MAWS one app over several machines, and each machine's authority is its daemon (RL §1). O2 gave every machine that daemon, `mawsd`, but MAWS's services still live in Electron main: the session index and read model, settings, attention, the owner channel, the session service, git, scm and files. So today, with the app quit, nothing folds a session's events into the index, attention stops deriving, a remote device's subscription to a lane B session pauses `no-app`, and none of main's commands can be served to another machine.

O3 moves those services into `mawsd`. After it:

- **Quitting MAWS leaves the machine's services running.** A lane B session keeps working with the app closed, its events keep folding into the index and attention, and reopening shows the session with no gap (parent acceptance 2).
- **Every client is a client of the machine.** The app on the same Mac, a second local client and the endpoint's remote devices all read the same services, each with its own subscriptions and cursors (RL3). O7's remote panes, O8's per-member reads and O10's app-less subscriptions have a machine to talk to.
- **Nothing regresses locally.** Signed out, the app does everything it did, on the daemon shape, within OX7's latency budget, with every project, session, draft and setting from before the upgrade present (parent acceptance 1), and an upgrade of `mawsd` or the app mid-turn loses nothing (parent acceptance 13).

The work is mostly relocation (about 13,400 lines of the spine and 4,400 of git, scm and files), but three things are not: one writer per piece of machine state across builds that run side by side, the app's view of state that now lives in another process, and the engine host's one client becoming permanent.

## Parent-level acceptance

O3 closes when all of these hold on the MacBook, checked by the named gate or by hand and recorded in Outcomes:

1. **Local parity, data included.** Signed out, on the daemon shape, MAWS does everything it did at P5's baseline. Every project, session, draft, attention item, library row, browser entry and setting from before the upgrade is present after it, with no re-index (parent acceptance 1's local half).
2. **The services outlive the app.** With the app quit, a lane B session's artifact write completes, the index and attention keep deriving, and reopening shows no visible gap, the journal re-serving what the ring dropped (parent acceptance 2, but for its dataset refresh, which runs through the connectors' broker and so is O4's: finding P1 below).
3. **Upgrades mid-turn.** With a lane B session mid-turn and running a background shell, restarting `mawsd`, and upgrading the app one minor, each leaves the turn completing, no input applied twice and the pending permission shown once (parent acceptance 13's `mawsd` case).
4. **Clients of the machine.** Two local clients of `mawsd` (in a test, the app's link and a second socket client) and the endpoint each receive every event of a lane B session exactly once across their own disconnects, resuming by RL3 cursor, with `historyUnavailable` when the journal can't serve a range (P5 Decision Log 77). A remote device's subscription to a lane B session on a machine with no app attached is never `paused {no-app}` (O7's C1).
5. **One writer.** No two processes ever write one profile's `index.sqlite` or any other spine file among builds from O3-A on: a second writer is refused, never raced. A build from before O3-A is refused as §2 says, with §2's stated residual, which P5's writer rules on as a change to OX1's promise (Decision Log 7).
6. **Every e2e group is green on the daemon shape,** O6's two-machine scene included, rerun against a second profile's private `mawsd` with O6's serve adapter in main deleted.
7. **OX7 within budget** at every landing that changes the local hop (§10); **acceptance 14's bound** read on the daemon shape after the spine moved (§11).
8. **The sweep reads interest (OX5), not `layout.json`,** and a session a remote viewer is watching is never archived or released as idle (O7's C9).
9. **The measurements O3 owes are recorded:** native rewind across `--resume` (U6's half, RL §12.3) and the recursive repository watch's limits on Linux (survey §2 item 5).

### 1. Where the machine's data lives

**[binding — every child and O4, O5 read the same table; a second location would need a cross-directory migration with crash windows.]** The daemon's data directory is the profile, as O2 made it. Nothing moves between directories. Each file has one owner:

| File (under `<profile>/`) | Owner | Writer |
|---|---|---|
| `index.sqlite` (and its WAL) | the machine (the spine) | the spine's process, under `spine.lock` |
| `machine-settings.json` (new, O3-A) | the machine | the spine's settings service, under `spine.lock` |
| `sessions/intents/`, `sessions/bootstraps/`, `sessions/deletions/` | the machine | the session service, under `spine.lock` |
| `prompt-history.jsonl`, `attention.json` (the attention fallback) | the machine | the spine, under `spine.lock` |
| `settings.json` | the client | main |
| `layout.json`, `browser/` (tabs, crops, and the new `browser/browser.sqlite`) | the client | main |
| `machine.json` | the profile | minted once by whichever of the app and `mawsd` runs first (P5 Decision Log 27) |
| `artifacts/`, `engine-host/`, `supervisor/` | the engine host | the engine host |
| `mawsd/` | `mawsd` (excluded from backups, RL Decision Log 24) | `mawsd`, its endpoint and its pty host |

Rejected: moving the machine's files into `<profile>/mawsd/`, which O2 excludes from Time Machine, so the owner's sessions, settings and index would leave the backup; and a new `<profile>/machine/` directory, which moves files for no reader's benefit, adds a migration with a crash window, and would show an older build an empty index rather than a refused one.

### 2. One writer: the spine lock and the version fence

**[binding — the guard spans every landing of O3 and every build in the OX1 window; P5's O3 acceptance names it.]**

- **The lock.** The process that runs the spine takes `<profile>/spine.lock` before it opens any file the table above gives the spine, and holds it for its life. It is O2's `takeLock` (`src/engine-host/supervisor-files.ts:90`) over its own file name, so liveness is a pid with its start time and a stale lock is broken the way the supervisor's is. Until O3-D that process is always main, in either shape; from O3-D it is `mawsd` on the daemon shape and main on the embedded one.
- **When it is taken.** Main reads the client file's `supervisor.shape` without the lock (it is the client's), settles the launch's shape (O2's `prepareLaunch`, which may replace a daemon), then takes `spine.lock`, waiting a few seconds for a holder that is exiting, before it migrates or writes either settings file or opens the index.
- **A refused writer writes nothing of the spine's.** A candidate that still finds the lock held by a live process runs with the spine refused for its run: none of the spine's services starts (so nothing writes the index, the machine settings, intents, bootstraps, deletions, prompt history or the attention fallback, and no session is launched), the index is opened unavailable (its existing degraded mode, `src/main/index/db.ts`), the machine settings are read but never written, and the client half runs. The reason (the holder's pid and build) is logged once and carried in `host.status` for Diagnostics. Its next start tries again.
- **Until O3-D no two spines can run at once.** The spine runs only in main, and Electron's single-instance lock (`src/main/files/profile-lock.ts`) keeps a second app off the profile. The lock is in place from O3-A so that every build from O3-A on already obeys it when O3-D makes a second kind of spine process possible.
- **Builds from before O3-A are outside the supported transition once O3-D lands.** They take no lock. Migration 14 makes such a build open the index read-only and unavailable (`openDb`'s rule for a newer `user_version`), and the client file's new version makes it run on default settings with writes refused (the settings store's rule), as any downgrade across a migration does today. It still writes its attention fallback (`src/main/index/attention-service.ts:27-29`), intents, bootstraps and prompt history when it runs; before O3-D it runs alone, so that is a downgrade's cost, not two writers.
- **The daemon side (O3-D).** From O3-D a post-O3 `mawsd` can run the spine while an app runs its own. An app from O3-A on takes `spine.lock`, so the cross-build peer at O3-D's landing is refused by the lock like any second candidate. For a pre-A app O3-D adds two refusals: `mawsd` yields its spine at start while a live app on the profile has neither taken the lock nor recorded that it delegates the spine (candidate signal: Electron's `SingletonLock` in the profile naming a live pid; O3-D verifies it on a scratch profile first); and `mawsd` refuses a pre-O3 app's hello at the relay by its missing capability, so such an app reaches no engine host. What such an app can still write by hand while a post-D `mawsd` runs the spine (a new chat's intent, a prompt's history line) is the transition's stated residual. O3-D's acceptance runs an O2-era app on a post-D profile.

Rejected: SQLite's own locking as the guard, which makes two writers safe for the file but not for the state (two session services, two attention services, two folds of one event); and an exclusive `locking_mode`, which an older build would meet as a busy error mid-run rather than at its start.

### 3. The settings split

**[binding — the field table: mawsd, the app and O7's remote settings read it.]** One `settings.json` mixes the client's fields and the machine's (survey §2 item 12). It splits into two files with two writers. The person's settings (P5 §2: catalog sources, Send-to destinations, connector accounts) are not in `settings.json` and are untouched.

| Section | Field | Owner | Why |
|---|---|---|---|
| `theme`, `keymap`, `notifications`, `appearance`, `voice`, `browser` | all | client | drawn or acted on by the app |
| `usage` | `nearLimitPercent` | client | the status line's banner threshold |
| `supervisor` | `shape` | client | read by the app before it reaches any daemon (O2 M7) |
| `supervisor` | `keepRunningDefault` | client | the quit question's default button |
| `supervisor` | `idleExitMinutes` | machine | the engine host's idle time; `mawsd` reads it with no app |
| `engine` | all | machine | every launch on the machine reads them |
| `gateway` | all | machine | the inference route is per machine (RL6, P5 §2) |
| `permissions` | `autoFallback` | machine | applied at launch by the session service |
| `mods` | `toHuman.enabled` | machine | the owner channel's launch decision |
| `artifacts` | `defaultDesignSystem`, `spaceDesignSystems` | machine | relayed to the engine host's artifact store |
| `artifacts` | `commentsView` | client | a view preference |
| `artifacts` | `exportAuthorName` | client | the person's name on exports, which run in the app until O5 |
| `sessions` | `archiveInactiveDays` | machine | the sweep |

- **The renderer keeps one settings API (advisory means; the binding part is that the renderer contract does not change in O3).** `settings.get`, `settings.set` and `settings.changed` keep their merged `Settings` shape, its `version` the client file's; main composes it from its client store and the machine half, routes each field of a patch to its owner (field by field: `supervisor` and `artifacts` have both kinds), and publishes on a change to either. Rejected: two renderer APIs now, which rewrites every Settings surface for no reader that needs them apart until O7 shows another machine's settings.
- **The machine half is its own Electron-free service** (state, update, on-change), part of the spine; until O3-D it runs in main. `nativeTheme` and the window background stay with the client half.
- **Versions.** `settings.json` takes the next settings version (P5's writer assigns it; O2 holds 20) and holds only client fields. `machine-settings.json` starts its own version line at 1.
- **The migration is once and idempotent:** if `machine-settings.json` is absent, write it from the unified file's machine fields (migrated to the last unified version first), then rewrite `settings.json` as the client file. A crash between the two leaves the machine file present and authoritative, and the next start finishes the client file. A file of a version this build doesn't know keeps today's rule (defaults in memory, writes refused).
- **The machine file keeps the unified file's nesting** for its fields (`engine.mcpServers` stays at `engine.mcpServers`), so readers that address an entry by its path in the file keep working.
- **Out-of-main readers move to the machine file:** the engine host's customization inventory and configured delivery read `engine.mcpServers` from `machine-settings.json`, and while that file is absent (a profile no split build has started yet) from the unified `settings.json` as today; the catalog watches the machine file. An older engine host kept running across the update reads a client-only `settings.json` as invalid and lists no app-scope MCP servers until it is replaced at idle; accepted as transient.
- **Saved MCP sign-ins survive.** Configured delivery's app-scope source carries the config file's path into its identity (`src/engine-host/connectors/configured-delivery.ts:95-116`), and main saves each OAuth grant under that identity and adopts it only on an exact match (`src/main/connectors/oauth-types.ts:47-55`, `oauth-provider.ts:292-309`). So the app scope's identity keeps naming `<profile>/settings.json`, a stable name for MAWS's own MCP servers, while the bytes are read from `machine-settings.json`. Rejected: migrating the sealed grant records, which are route D's `safeStorage` ciphertext (O4's U7).

### 4. The browser's tables leave the index

**[binding — P5's silent decision; the index must hold only machine data before it moves.]** `browser_history`, `browser_bookmarks` and `browser_activity` move to a client database, `<profile>/browser/browser.sqlite`, owned and written by main. Index migration 14 drops them.

- **The transfer is staged, and the index's version is the handoff** (binding: a crash, a pre-A build writing to a version-13 index in between, or the browser starting while another process copies, must lose nothing). Whichever process applies migration 14 replaces the browser database's staging tables with a full copy of the index's three tables, in one transaction there, every time it finds the index below 14; then migration 14 drops them from the index (`DROP TABLE IF EXISTS`). Staging is therefore final once the index is at 14. The browser writes its live tables only after it has read the index's `user_version` at 14 or above (one `PRAGMA` on a read-only connection, a reader and not a second writer), at its start and again at each available snapshot of the spine's view; reading 14 with staging present, it first promotes staging into its live tables and drops it, in one transaction. Until then it reads nothing from its tables and records no visit, a window of the spine's load in the one case it exists. A crash at any step repeats an idempotent step. In O3-A the migrator is main, which opens the index before it starts the browser, so the window is empty; a profile that skipped O3-A's build reaches the same steps with O3-D's `mawsd` migrating and the app's browser waiting on the version.
- **The cross-table coupling is replaced, not lost:** `browser_activity`'s FK cascade to `sessions` becomes the browser deleting a removed session's rows from the `removed` change it already hears (`src/main/browser/index.ts:214`), plus a reconciliation whenever the browser gets a complete, available snapshot of the spine's sessions (at its start and at each reattach): rows of sessions the spine doesn't know are deleted before any activity write, so a session deleted while the app was closed, or in a crash before the browser heard it, leaves nothing behind. An unavailable spine reconciles nothing. The append's `EXISTS (SELECT 1 FROM sessions …)` becomes a known-session check through main's view of the spine (§7).
- **`e2e/library.spec.ts`'s rewind changes with it:** it asserts the first launch left the index at 13 and compares the rewound file with a fresh version-9 schema, which holds the browser tables (`:244-255`). It now expects 14 and restores the three browser tables' schema before the exact comparison, keeping the assertion.

Rejected: leaving the tables in the index and opening it from main beside `mawsd`, which is the two-writer state §2 forbids; and the browser reading them remotely, which puts a process hop on the address bar's per-keystroke suggestions.

### 6. Two roots, one library

Advisory, O3-C's. The spine becomes a library composed by one function (the services root) that both roots call: main's embedded root on the embedded shape, `mawsd`'s on the daemon shape (P5 §2; O15 deletes the embedded root). The library imports nothing from `src/main/ipc/`: the 29 files that import main's IPC singletons take them from a services bus that each root binds (main's to its router and `emit`, `mawsd`'s to its services front), the pattern O6 used for `bindLocalMachine`. The spine's files may move to their own directory (`src/services/` is the suggestion) so the boundary is a path, with `MACHINE_BOUND`'s exceptions gone; a rename keeps history. The intercepts the spine installs on engine-host commands (`session.answer`'s pending check, O9's lane A reroute, the scenario stub) become intercepts on whichever path carries engine-host requests in each root.

### 7. Main's view of the spine

**[binding — the interface every staying consumer reads through, in both shapes; O4 and O5 code against it.]** Staying code reads the spine only through one view (called `SpineView` here): records and projects, digests, attention with its restored marks in band, engine statuses and the mid-turn count, a session's lineage, intents (each record and the list; the files allowlist reads an intent's location, additional directories and worktree, `src/main/files/allowlist.ts:18-29`, and `git.lsFiles` lists them, `src/main/index.ts:432-437`), `known(id)` (a record or an intent), the changes to each (record, removed, attention, digest, engine, intent), `acquire`, and one asynchronous read, the paths of File artifacts linked to a session or its ancestors (`fileLinkedPaths`, files' admission, `src/main/library/admission.ts`). That last read exists only for files between O3-D and O3-E; the daemon shape backs it with an internal `machine` command that O3-E deletes when files joins the library in `mawsd`. Rejected: moving files and `git.lsFiles` into O3-D, which would also move `library.read`'s in-process reach into the files service (O4's) a child early and enlarge the panel-reviewed landing. On the embedded shape the spine satisfies it in process; on the daemon shape a mirror in main fed by the services front's events and snapshot reads satisfies it, synchronous for its readers. Hot paths (the browser's per-status `knownSession` and per-tab lineage, the chat panels' `known(id)` on every panel `layout.set`, the notifier's per-digest record read) read memory, never a socket. The full list of readers is in the grounding map O3-C inherits (this Decision Log, entry 2).

### 8. `mawsd` as the engine host's permanent client

**[binding — O4, O5, O10 and O16 build on it; P5 Decision Logs 6 and 29.]**

- `mawsd` stays the engine host's single client (E10's single-client machinery unchanged), and from O3-D its connection is permanently ready: the spine in `mawsd` folds every event, with or without an app, and E10's burst and undelivered tail now cover `mawsd`'s own restarts. O2's recycle per app attachment ends. Rejected: several engine-host clients, which rewrites every single-client row of survey §4.1 (P5 Decision Log 6).
- **The app's attachment becomes an explicit signal to the engine host.** What the engine host keys on its connection today (`hasClient` for the pane, capture and export bridges and dataset refresh; `onClientGone` for connectors' route E and direct operations, connection holds, document channels and dataset refresh) keys on the app's attachment instead, which `mawsd` reports (an additive engine-host command under a capability, O3-D's to name). An app-bound request reaches the attached app through `mawsd`, settles `noClient` when none is attached, and ends with the app's departure, as with main today.
- **The permanent connection is gated on the engine host's capability.** O2's update rule keeps an older engine host serving its live sessions until it is idle (`src/shared/host/detached-transport.ts:472-488`), so a post-D `mawsd` will meet engine hosts that can't hear the attachment signal. To such a host `mawsd` keeps O2's one connection per app attachment, recycled at attach and departure, and its spine folds each attachment's burst; only a host that lists the capability gets the permanent connection. Rejected: restarting an old host at the cutover, which ends its sessions mid-turn (parent acceptance 13).
- **Event availability follows the capability everywhere.** With an old host, events still reach `mawsd` only while an app is attached, so the endpoint seam keeps O2's meaning for that host: `onAttachment` reports availability, a remote lane B subscription is `paused {no-app}` while there is none and catches up from its cursor when it returns (`src/endpoint/plane-b.ts:139-145`). With a capable host `mawsd` reports events available for good, and the pause never happens. So O3's acceptance 2 and 4 and O7's C1 hold from the first engine host started at or after O3-D's landing; until an old host is replaced at idle, that host's sessions behave as at O2.
- **Fan-out with a cursor per stream and client.** `mawsd` serves every local client on its services front and the endpoint through `onEvent`; each client's session streams carry RL3 cursors `(launchId, seq, idx)`, a client that reconnects resumes from its own cursor through `session.events`, and `historyUnavailable` is kept. The endpoint's lane B subscriptions (`src/endpoint/plane-b.ts`) then never pause `no-app`.
- **One services front** for local clients carries the spine's commands, its events to every client, and the client port's requests back to the client that asked (OX4). Its transport is advisory: `machine.sock`, which already serves many clients, is the suggestion; engine-host and pty-host requests keep their relay sockets.
- **Local subscriptions reuse the endpoint's cursor logic** (advisory): the catch-up from a cursor through `session.events` with live events held and deduplicated is O10 M8's (`src/endpoint/plane-b.ts`); O3-D lifts it to a module both the endpoint and the services front use, with O10's owner. Rejected: a second implementation of the same rules.

### 11. The laptop's cost

**The numbers (O2's final tree, the architect, 2026-10-28).** Acceptance 14's bound, re-derived today, is 101,113 KiB of physical footprint and 1.11 s of CPU per 600 s for what stays after the app quits holding one idle kept session. The daemon shape measured 97,683 and 99,219 KiB in two valid runs: `mawsd` 30.7 to 31.4 MiB, the engine host 66.0 to 68.1 MiB. The headroom is 1.9 to 3.4 MiB. The spine is about 14,000 lines with a SQLite connection, the read model and attention behind it, so it can't simply be resident in `mawsd` while the app is closed.

**[binding — acceptance 14 is the owner's statement, and every child that moves code into `mawsd` budgets against it.]** The spine is not resident in `mawsd` while nothing needs it. Acceptance 14's condition (no app, no session working) is exactly when it isn't needed, and acceptance 2's (a session working with the app quit) is when it is, so both hold:

- **A cold core.** `mawsd` starts without the spine: its idle core is what O2 built (the relay, the clocks, the interest union, the endpoint seam) plus O3's attachment and fan-out plumbing. The spine's modules are imported only when first needed, never at start.
- **Loaded on need.** The spine loads when an app attaches, when a remote request or subscription needs it, or when a session works (the engine host sends a session's event batch), and `mawsd` holds what arrives in order until the spine has loaded and folded it. Advisory for O3-D: replace-whole events (a session's status, queue, broker items, catalog) coalesce to the latest per session in the core and replay into the spine when it loads, so a periodic status from an idle session never wakes it.
- **Released when quiet.** After a quiet period with no app, no remote subscriber and no working session, the spine closes its SQLite connection and drops its caches. Code once loaded stays mapped, so if the measured idle footprint still misses with the data released, `mawsd` re-executes itself into the cold core after the quiet period: a restart ends no session (O2 keeps the hosts running across it), drops remote channels that resume by cursor, and is the restart O2 already tests.
- Rejected: the spine in a child process of `mawsd`, spawned on demand. It costs nothing at idle too, but adds a fourth supervised process and a hop on every spine command, and P5 §2 chose one daemon process; it stays the fallback if re-execution proves unreliable.

**The measurement, at each landing that moves code into `mawsd`.** `e2e:daemon-idle` on the mini, by gate-offload Decision Log 133's procedure (#273: settle, prebuild, settle again, then the window), three runs, with the bound re-derived on the same tree by `e2e:daemon-idle-baseline` (O2's last Decision Log entry), a miss in two of three runs being a finding for P5's writer. O3-C adds an earlier, diagnostic reading: the spine composed alone, idle, under the same runtime (`e2e:daemon-idle-spine`, measured only), so O3-D starts from a number. If O3-D or O3-E misses with the cold core and re-execution in place, the bound is the owner's call (owner question Q2); no child settles it.
