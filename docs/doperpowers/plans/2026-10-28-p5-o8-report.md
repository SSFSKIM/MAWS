### M3's owner sitting: `root add`, on staging and then production

Prepared 2026-10-28 for the owner's next sitting. Every string below is quoted from the landed code: `src/renderer/src/settings-tab/copy.ts` and `apps/desk-hub/deploy/admin.ts`.

**Before** (staging; the app signed in to staging as at M1's sitting, built from master at or after 716a2675d). Settings › Org has a **Signer** row that reads:

> Make this Mac a root: run `deployment admin root add -- <device id>`

The row's note reads "Its confirmation names this Mac's fingerprint, `<fingerprint>`. Compare the two before you confirm." The id comes after `--` because a base64url id can start with `-`. If the row instead reads "This Mac's keys weren't kept out of Time Machine backups when they were made, so it signs nothing. Make new keys with a pairing code.", stop. The Mac needs new keys first (rekey with a pairing code), and `root add` waits for them.

**Staging, from the owner's terminal at a checkout of master at or after 9fe9a164c (#316, `show`'s root lines):**

    apps/desk-hub/deploy/staging-run.sh admin show                      # head version N; one root line, the admin's
    apps/desk-hub/deploy/staging-run.sh admin root add -- <device id>
    apps/desk-hub/deploy/staging-run.sh admin show                      # head version N+1; two root lines, the app's device among them

- It asks: `make <device> of <email> (fingerprint <fingerprint>, step-up <kid>) a root of <org>? [y/N]`. Compare the fingerprint with the Org section's note. They must be equal. Then answer `y`.
- It prints `root added: <device id>, step-up <kid> (version N+1)`.
- Refusals, any of which means nothing was signed:
  - `<member> has no device <id> in the head (version N)`: the wrong id, or another member's device.
  - `<id> is a <class> device: only a native-mac device with a step-up key signs org states`.
  - `<id> is a root already (step-up <kid>)`.

**The check of record**, read from `admin show` before and after the add, and from the app:
- Before: the first line reads `head version N, issued d days ago`, and after the members block there is one `root <kid> (<email> device <id>)` line, the deployment admin's.
- After: the first line reads `head version N+1` (the add's own successor), and there are two root lines. One names the app's device, `root <step-up kid> (<your email> device <the Signer row's device id>)`, and its kid matches the `step-up` in the add's question.
- The app: once it adopts version N+1 (at its next feed notice, within seconds), the Signer row reads "This Mac signs the org state." and the root-add guidance is gone.

**Then the app signs once itself.** Press **Re-sign now**. Touch ID asks "re-sign the org state (no change)". The row then reads "Signed version N+2.", and the next `admin show` reads `head version N+2` with the same two root lines. That proves the app signs as a root.

**Record in O8's Outcomes:** the versions, the fingerprint match, the two root lines, and the Signer row's line.

**Production**, the owner's alone, from the owner's own MAWS:
1. Settings › Org shows the production device's own id and fingerprint.
2. Run `apps/desk-hub/deploy/production-run.sh admin show`. Note the first line (`head version N`; it read `head version 3` on 2026-10-28) and the one root line. Then run `apps/desk-hub/deploy/production-run.sh admin root add -- <that id>`. The wrapper names production and asks at the terminal, as its other changing verbs do.
