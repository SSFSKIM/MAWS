## Purpose

Today a lane B session is a child of the engine host: the process that holds its Query also holds its pipes. So an engine host cannot be replaced while a session runs, and `mawsd` serves an older engine host "until its sessions are idle" (O2 M3, E10 §6). On a server that never idles, with a session kept by a background shell or a cron, that day never comes: an upgrade either never takes effect or, at the owner's Restart now, ends every lane B session and reopens each with `--resume`, losing its background shells, its Monitors and its MCP tasks (`background-work-handoff.md` §2). An engine-host crash loses the same.

After O16, every lane B process the engine host launches runs under a **session host**: a small native process that owns `claude`'s pipes, numbers its output, applies its input exactly once and signals it only on a fenced request. The engine host keeps the Query, the `maws` tool server and the hooks, and can be stopped and started around a running session: a new engine host, of another build or the same, finds the session hosts in a roster, re-attaches as the one writer, replays what it missed from each host's ring, re-initializes the engine and goes on. An engine-host upgrade, a `mawsd` restart and an app upgrade, each mid-turn, leave the turn completing, no input applied twice and a pending permission shown once (P5 acceptance 13). The servers' idle release stops being a wall clock: a session is released after 24 hours only once its work state is verified empty, with the release armed through the observer bridge's `turn.step` gate so no turn from any origin is lost in the window between the verdict and the signal (OX10, owner F2).

**How to see it working.** On a scratch profile on the daemon shape, start a session and ask it to run `sleep 300 &` in the background; `mawsd status` lists the session's host (`session hosts  1 (adopted 0)`); run `mawsd restart --engine-host`: the engine host's pid changes, the session's pid and launch id do not, the transcript keeps streaming, the shell's pid lives, and `mawsd status` reads `session hosts  1 (adopted 1)`. Then replace the app bundle with another build and relaunch: the same. Concrete Steps has each command; the e2e groups named in Acceptance prove each behaviour on the gate's Macs and the acceptance run on a devcloud VM proves it with the real engine.

### Orientation

Terms used throughout:

- **The engine host:** E10's detached supervisor (`src/engine-host/index.ts` dispatching to `detached.ts`), one per profile, holding each lane B session's `EngineSession` (`session.ts`: the Query, the `maws` tool server, the hooks, the broker, the queue) in the process table (`process-table.ts`), served over `host.sock` to its one client, `mawsd` (`src/mawsd/daemon.ts`, the relay and the permanent link). Its files are `<profile>/supervisor/` (`supervisor-files.ts`). **The manager**, in holder design terms, is this process.
- **A session host:** the new native process (`native/session-host/`, binary `maws-session-host`) that spawns one `claude -p` with piped stdio, numbers every stdout and stderr line into a ring, applies stdin by offset, holds the writer fence, writes its roster entry and serves one Unix socket (Interfaces §A, §B). One per launch; its id is the launch id (`launch.ts` `mintLaunchId`), so the journal, the roster and the request ids name one process by one id (D5).
- **The host transport:** `src/engine-host/holder/transport.ts`, an `EngineTransport` (`transport.ts`'s interface: `frames`, `stderr`, `write`, `endInput`, `kill`, `exited`) over a session host's socket instead of a child's pipes, so `EngineSession`, `OutboundWriter`, `ControlClient`, the ladder and the normaliser run unchanged (Interfaces §C).
- **The roster:** `<profile>/supervisor/hosts/<launchId>.json`, written by each session host at every state change; the manager reads the directory at start to adopt (Interfaces §B, §D).
- **The checkpoint:** the contiguous frontier of host sequences the launch's journal holds (every record at or below it journaled), computed from the host map, an append-only sidecar beside the journal that records each host sequence with the journal sequence of its row, written before the row; the session host keeps every record above the acknowledged frontier, so a new manager replays from the checkpoint exactly, or learns of a gap (Interfaces §C).
- **The restore fold:** the pass an adopter makes over the launch's whole journal (every file of the launch, in order) through the session's readers with every emission and reaction suppressed, so the normaliser, the status tracker, the broker and bash mode hold the state the old manager held before any new record is consumed (Interfaces §D).
- **The handover:** an engine host's exit that detaches its hosted sessions instead of ending them, once its own in-flight work has drained, and its successor's adoption of them; asked by `mawsd` with `host.handover` on a welcomed link, or by the socket layer's stable `exit {when: 'idle'}` from an adopting client on a refused one, and deferred, never forced, while a drain does not settle (Interfaces §D, D9).
- **The gate:** OX10's server, `<profile>/supervisor/gate.sock`, where sminos's observer bridge inside a lane B process connects and answers the reap fence's `arm` and asks `turn` (Interfaces §E).
- **The reap:** the release of an idle session (`idle`, the role's clock; `budget`, memory pressure) as a state machine over the gate: verified empty → armed → final check → signalled; an `idle` reap is `end_session` then SIGTERM on a path of its own that leaves the session usable if the engine ignores both (Interfaces §F).
- **Verified empty:** `work-state.ts`'s snapshot with `unknown === null` and `crons.length === 0`, no non-ambient task in `backgroundTasks`, and no process under `claude` beyond the registered infrastructure, read at the moment of the verdict (Interfaces §F); `budget.ts`'s `isIdleRow` already says most of it.
- **Registered infrastructure:** the processes under `claude` that are not its work: the sminos bridge child, named by pid in the observer's gate `hello`, and the stdio MCP servers of the launch's configuration, matched by command line; everything else under `claude` is work (holder design §3.2).
- **The stub engine:** M2's fixture-playing process (`test/support/stub-engine.mjs`, selected by `MAWS_E2E_ENGINE_BIN`), which speaks stream-json over real stdio from a journal fixture as the in-process replay transport (`replay-transport.ts`) does in memory; it is what the hosted scenes spawn under a real session host, since the in-process replay spawns nothing and today's `writeReplayEngine` (`test/support/replay-engine.ts`) answers `--version` alone and refuses a real invocation.

How the parts fit on master. `launcher.ts` builds a `LaunchPlan` (`launch.ts` `buildLaunch`: the binary, the flags, the environment with `SMNS_MEMBER` and `MAWS_LANE=B`, the pinned `--session-id`) and reserves an `EngineSession` whose `spawn` is `ipc.ts`'s `spawnEngine(plan)`; `session.ts` `run()` spawns, wraps the transport in an `OutboundWriter` and a `ControlClient`, journals every row through `record` (`journal.ts`, synchronous appends), initializes, and ends the process through `session-ladder.ts` (end_session, SIGTERM, SIGKILL). The table writes `live.json` (`live-ledger.ts`) at every launch and exit; `detached.ts` sweeps a dead predecessor's rows at start. `supervision.ts` sets the idle release's policy from the role (`role.ts`; `SERVER_RELEASE_MS` 24 h, the laptop's the idle exit's), `idle-release.ts` fires `session.stop('idle')` when a row's clock is due and `isIdleRow` still holds, `budget.ts` names the hard reasons, and `work-state.ts` keeps the crons from the Stop callback (`host-hooks.ts`) and the tasks from `background_tasks_changed`, unknown on an `adopted` launch until the first signal. `mawsd` reaches the engine host through `@shared/host/detached-transport` with `buildPolicy: 'replace'`: another build with nothing live is replaced at once, with sessions live served and asked `exit {when: 'idle'}`; a crash is the ladder's restart; `beforeSpawn` refuses a spawn from a replaced bundle (Decision Log 161). sminos's bridge (`bridge.tsx`) observes a marked session, refuses every control and rewrites nothing in `turn.step`.

**Decisions.**
- The language is Go (D3), std only, one module, no cgo (`CGO_ENABLED=0`), so the Linux builds are static ELF and the Mac build links `libSystem` alone.
- The protocol is NDJSON control lines plus two length-prefixed byte records for output and input (Interfaces §A), so a 64 MiB line is never JSON-escaped on the hot path; the line cap is the engine host's `MAX_LINE_CHARS` (64 MiB): an unterminated line past it is dropped with a `problem` record, the child left to the manager's verdict (today's transport kills it: `transport.ts`).
- The ring holds what the writer has not acknowledged, up to `RING_CAP` 8 MiB; the manager acks after each journal write (D6). Past the cap the oldest lines go and `firstSeq` moves, so a `read` below it answers a gap, never a guess.
- stderr lines share the ring's sequence (`err` records), so one checkpoint covers both streams and the journal's `stderr` rows are replayed too.
- The writer fence is a `uint64` the host keeps from its first writer (1); `attach writer` with a fence at or under the current is refused, a superseded writer's connection is told `fenced` once the records it had queued are applied, and every later write from it refused; the fence is written to the roster at each change and read back at the host's own restart never (a host does not restart: its death ends the session, D7). Observers read only.
- The child is forked as the leader of its own process group (`Setpgid` at the fork), what `detached: true` gives the engine today, so `signal {group: true}`, the host's own SIGTERM relay and the sweep's SIGKILL reach the group as they do now.
- Stdin is one writer goroutine over a bounded queue, whole records only, never recalled (Interfaces §A, D30).
- Output to a connection is written from the ring at that connection's cursor as its socket drains, each record as it is read, no batching on the hot path; a connection more than `CONN_WRITE_CAP` 32 MiB behind is closed, and its client re-reads from the ring on reconnect.
- The host's own signals: SIGTERM, SIGINT or SIGHUP to the host sends SIGTERM to the child's process group, waits `HOST_EXIT_GRACE` 5 s, and exits; a host whose death would leave an unreachable engine (E10 M0 Q1: an engine with no stdio finishes its turn and runs on) takes the session down cleanly instead (D7). SIGKILL of the host is the manager's case while it lives (M2) and the sweep's at the next start (M3).
- A host with no child (`ready`, or `committed` with a spawn that failed) whose writer connection has ended exits after `HOST_NO_CHILD_MS` 30 s, removing its files: it protects nothing.
- The host stats its socket path every 60 s and listens again at the same path when the file is gone (the tmpdir fallback's directory is subject to macOS's periodic cleanup of untouched files; the profile path, 8 characters of launch id, is the common case).
- After the child's exit the host serves `hello`, `read` and the exit record for `LINGER` 10 minutes, or until the writer sends `release`, then removes its socket, token and roster entry and exits 0.
- The roster entry is written with a temp file and rename, 0600, at `ready`, `committed`, `running` and `exited` (Interfaces §B); the socket is 0600 in the 0700 `hosts/` directory, made and checked as `@shared/host/private-listen` makes them (the host re-implements the checks: lstat, the uid, the mode, no symlink).
- Peer identity: the uid boundary and the token, as every socket of `mawsd` (O2 M8); no peer-credential check.
- Process start identity: the host records its own and the child's `procStart` as `supervisor-files.ts` reads them (`ps -o lstart=` under `LC_ALL=C TZ=UTC`, on both platforms), so `isSameProcess` compares like with like.
- Logging: `<hosts>/<launchId>.log`, 0600, one line per state change and problem, capped at 1 MiB (truncated at open past it).
- Build: `go.version` pins the toolchain; the script refuses another; the three targets are built from one machine (`GOOS`/`GOARCH`, `CGO_ENABLED=0`, so a Linux runner builds the darwin target too); the CI check rebuilds all three on the pool's Linux runner and compares bytes, Go's builds being reproducible across build hosts under `-trimpath`; `unit:darwin`'s real-binary tests run the committed darwin build besides.
- The binary is resolved at each spawn from the engine host's own build location (`sessionHostBinary()`, §H). After an app bundle swap an old engine host spawns the new bundle's session host, which speaks the same protocol major; a protocol major bump is its migration's to handle (OX1's rule, applied to this protocol).

**What it does not touch.** The engine host's launch path (M2). `mawsd`. The gate.

**Proves.** Acceptance 4's build half. Tests: `go test` (the ring's cap, gap and ack; offsets' duplicate and gap; the fence's CAS; the roster's atomic writes; signal relay; the linger). `binary.test.ts` drives the committed binary with `/bin/cat` as the child: auth before anything (a wrong token gets no byte), `hello` after auth, `launch` and `commit` spawning `cat` with the given argv, cwd and env (the env read back through the child), `out` records sequenced from 1, `read` exact and `gap` after the cap, `stdin` applied once and `duplicate` on a resend, `busy` past the queue's cap and a blocked pipe never blocking the reader, a second writer at fence+1 superseding the first after the first's queued record was applied (`fenced`, its next write refused, the new writer's `stdinApplied` counting it), `stdinClosed` with its `partial` when the child closes stdin mid-record, `signal SIGTERM` ending `cat` and the `exit` record, the linger and `release`, SIGTERM to the host ending `cat`, a no-child host exiting after its writer leaves, a lagging connection closed at the cap, the socket re-bound after its file is removed, and the socket's fallback path when the directory's path is long.

### M3 — Adoption and the handover

**What exists at its end.** An engine host that starts over a profile with live session hosts adopts them: for each roster entry whose host answers `hello` with the right token, it attaches as writer at the host's fence + 1, opens the launch's journal in append mode continuing its `seq`, folds the launch's whole journal into a fresh session's readers with nothing emitted (the restore fold), replays the ring from the sidecar's checkpoint (exact, or with a gap row and a notice) with live dispatch held, classifies every request still outstanding (orphaned tool calls answered, asks re-raised, hook callbacks answered, permission and dialog requests left to the engine's redelivery), seeds the work state from the durable records, sends an owed interrupt, re-initializes, and then serves the session as before with the same launch id and pid, its new control requests named apart from the old manager's. An engine host's exit detaches its hosted sessions once their MAWS-owned work has drained, never on a timeout alone; `host.stopAll` and the quit path's stop still end them. `mawsd` asks a capable engine host of another build to hand over as soon as its welcome arrives, sessions live or not, serves it while the handover is deferred, and `mawsd restart --engine-host` asks the same on demand. **Decisions.**
- Adoption order at start (D10): in `listening`, synchronously before the first hello can be answered, the roster is read and a row reserved for each entry with a live host, so `liveSessions` counts them from the first welcome and `mawsd`'s connect burst sees them; then each is adopted (bounded `ADOPT_MS` 60 s per host, in parallel; the fold of a day-long journal is the bound's reason); then the sweep over `live.json`'s rows that no adopted host holds, and over roster entries whose host is dead but whose child (pid and `procStart`) lives (SIGTERM, the grace, SIGKILL, as today's sweep). Journal pruning (`scheduleJournalPruning`, `index.ts`) is scheduled only after adoption has ended, and its `keep` set is the table's launches plus every roster entry's launch id, adopted or not (a failed or unadoptable host keeps its journal while it lives), so a hosted launch older than `JOURNAL_MAX_AGE_DAYS` is never pruned under a live host (D25).
- The checkpoint is the host map's (Interfaces §C, D23). The journal writer resumes `seq` and the rotation index from the latest file's tail, first truncating the file to its last newline so a torn last row (a crash mid-`writeSync`) never stays as an interior line `JournalReader.rows` would throw on; the map is truncated to its last newline the same way. The frontier `F` is the greatest host sequence such that every sequence at or below it has a map line whose journal sequence is at or below the journal's last row (a map line written before a row that never landed is dropped: its record is replayed); the set of mapped sequences above `F` is `above`. The adoption attaches and starts `read {fromSeq: F + 1}` at once, holding the records in memory (bounded by `ADOPT_HOLD_CAP` 64 MiB) while the fold runs, so the ring only covers the restart's gap, not the fold's; it then skips every record in `above` and journals the rest. No row is identified by its content. `caughtUp {gap}` writes `meta host_attach {replayed: 'gap', firstSeq}` and reseeds (holder design §3.3): the session reads the engine's own transcript from the last message uuid the journal holds to its end, through the disk reader's normaliser (`fs/service.ts`'s `eventsSnapshot` path, which serves a session with no process today), journals the gap's conversation rows as `meta transcript_reseed {rows}` and emits their events marked `reseeded: true`, then a `session.notice` ("Some output was lost while the engine host was restarting; the conversation was restored from the transcript."); stream events and tool progress inside the gap are not reconstructed (the transcript has none), and the normaliser's lane state is reset so the next message start re-anchors it. In that order and then the map's lost-range line `<firstSeq - 1> *`, so the frontier moves past the lost sequences, the acks resume, and a later adoption reads the gap as accounted for rather than finding it again (D23).
- The restore fold and the recovery barrier (D24): before any held record is consumed, the adopted session reads every journal file of the launch in order and feeds each row to the normaliser, the status tracker, the broker, bash mode and the side-question log through a `restore` entry that observes and emits nothing (no X1 event, no reaction, no write); the fold also builds the outstanding set: every inbound `control_request` with neither a `control_response` out nor a `control_cancel_request` in naming it, less the `tools/call`s an MCP `notifications/cancelled` withdrew (correlated in the fold by server and JSON-RPC id, over the journal and the held records alike, since the tool server's own `abandoned` correlates against an in-memory map the adopter has not filled) and less the asks the journal records as retired, and every outbound request with no response in. Live dispatch (`inbound()`, the tool server's `accept`, the hook callbacks) is held while the held records are journaled and folded the same way, the barrier ensuring no replayed `mcp_message` runs a tool again; the one exception is the `maws` server's protocol service (`initialize`, `tools/list`, notifications), answered at once from the tool server as today, since the engine's MCP handshake may interleave with its initialization. At `caughtUp` the outstanding inbound requests are disposed by Interfaces §D's table: a `tools/call` of a `maws` tool that acts on something (every tool but `ask`) is answered with a tool error whose text is exactly "MAWS's engine host restarted while this tool ran. Its result is unknown and its effect may have completed; check before retrying." (holder design §3.3: never a retryable error); an `ask` call is re-raised from its journaled input as a pending ask under its original request id, so the human's answer settles the engine's own call, and an ask whose MCP call already returned and that waits as an async ask is restored the same way; a `hook_callback` is answered `{}` (what `session.ts` answers an unknown callback today; the engine may have retired it, M0's question 3); `can_use_tool`, `request_user_dialog` and `elicitation` requests are left to the engine's redelivery at re-initialize, which the broker already dedups by request id (a `request_user_dialog` or `elicitation` the re-initialize's answer does not list in its `pending_*_requests` is re-raised from the journal as an ask is, D49); the UI surface's requests are re-attached by `surface.attach` at the handshake as a `system/init` re-attaches them today; any other inbound form is answered with the engine's own unsupported-request error. Then the owed interrupt goes if marked, `initialize` runs as a resume's handshake (the app's hooks, `get_status`, the grant re-application skipped, the queue recovered), and live dispatch opens, the records held meanwhile processed in order.

A tool call counts as in flight from its dispatch until the `applied` of its response write, or, for a call the engine withdrew (its signal aborted: `call()` writes no response), until its tool's execution settles, or until its response write fails (not the tool server's `calls` map, which `call()` clears before it queues the response); at the first moment the count is zero (checked at each of those retirements and at the freeze) the row is detached: the writer's in-flight writes awaited (`OutboundWriter.whenIdle`, bounded by `EOF_WRITE_WAIT_MS`), the final ack, the `host_detach` row, the journal and the map closed, the host connection closed without `release`. ### M5 — The gate and the verified-empty release

**What exists at its end.** The engine host serves OX10 on `gate.sock` (Interfaces §E) through a server of its own: observers connect with `hello`, heartbeat, answer `arm` with `armed` and ask `turn`. The idle release (`idle`) and the budget release (`budget`) run through the reap state machine (Interfaces §F): a due row that is verified empty arms the fence when an observer is healthy, re-checks everything in the same synchronous step as the signal, and signals; an `idle` reap sends `end_session` and then SIGTERM through the host on a path of its own, leaving the session usable if the engine ignores both; a `budget` reap keeps today's ladder. A `turn` before the signal is answered `proceed` and cancels the reap; after it, `stop` with the exact reason text. An observer that was seen and went silent or away blocks the release until it is heard again. The descendant veto counts every process under `claude` but the registered infrastructure. The server role's rule is the verified-empty rule on the 24-hour clock; the laptop's rule keeps its 10 minutes with the same gate. A row on which no observer was ever seen is released on verified-empty alone (owner Q1's default). The status's `release` gains `gate` and `mawsd status` shows it.

**What it touches.** `src/engine-host/holder/{gate,reap,descendants}.ts` (new), `idle-release.ts` (fires the reap instead of `stop('idle')` directly), `process-table.ts` (the budget's release through the reap, its `releasing` cleared when a reap is cancelled; the registered infrastructure per row), `budget.ts` (`holdsWork` includes `descendants !== 0`), `work-state.ts` (`descendants`, the `reap_term_ignored`, `descendants_unreadable` and `observer_unhealthy` unknowns), `session.ts` (`reap()`: the signal path apart from the ladder; the `reap` meta rows; `mcp_status` once per launch for the MCP commands, D48), `supervision.ts` (the gate's path in the status), `launch.ts` (`MAWS_HOLDER_SOCKET`, if M2 has not set it), `@shared/engine/status.ts` and `@shared/ipc/schema/host.ts` (additive fields), `src/mawsd/cli.ts`, `e2e/supervisor.spec.ts` case (m). Their tests, with a fake observer (`src/engine-host/holder/fake-observer.ts`, test support) over a real Unix socket that records the frames it sees into `spikes/protocol-probe/fixtures/p5/p5-o16-gate.jsonl` for O12 M4's bridge test to replay.

**Decisions.**
- The fence is armed on the laptop role too (**[parent-impact]** P5 §2 scopes the verified-empty rule to the servers and keeps the laptop's clock; strictness on the laptop is already P5's, and a turn lost in the window is lost on either role, so the laptop's release arms the same fence; the architect may fold it into §2 at landing).
- The gate is the engine host's, not the session host's (D13): the final check's inputs (the work state, interest, the queue, the descendant count) live in the engine host, so the decision and the signal order are one event-loop turn there; the session host only relays the signal. Its server is `holder/gate.ts` over `node:net` with `@shared/host/private-listen`'s path and directory checks and `socket-protocol.ts`'s `splitLines`, not `@shared/host/socket-server`, whose two modes both speak the token-authenticated host protocol (D27).
- An observer is keyed by the engine session id its `hello` carries, against each row's lineage (`durable-crons.ts` keeps it); `pid` is a cross-check when the row's `pid` is known, never the key, since a replay row has none and the mod reads no pid of its own. A `hello` whose session matches no row is closed at once, so a `claude` a tool starts under the engine, which inherits `MAWS_HOLDER_SOCKET`, gets nothing; O12 M4 is asked to drop the variable in `launch_env` as M3 dropped `MAWS_LANE`.
- The reap's linearization point is `IdleRelease.fire()`'s synchronous step: it re-reads the row's status, the interest union, a fresh descendant read and the gate's state, and calls `session.reap(reason)` in the same step; an event that landed before the step is reflected, one after it meets `signalled`. Arming is asynchronous (the observer answers over a socket): `fire()` with a healthy observer and no `armed` fence sends `arm` and returns, and the `armed` answer schedules the step again at once; a `turn` that arrives meanwhile cancels (`proceed`, the clock restarts at the turn's end as a turn does today; a cancelled `budget` reap also clears the table's `releasing`, so `evaluate` may pick another candidate). The lease is `LEASE_MS` 10 000, renewed by a second `arm` when the step runs later than `armedAt + LEASE_MS - 1000`.
- An observer is healthy while its last `hb` is under `OBSERVER_SILENCE_MS` 15 000 old. One that was seen on the process and went silent, or whose connection closed, makes the row `observer: 'unhealthy'`: no arm, no signal, no release, and `work.unknown` reads `observer_unhealthy`, until a `hello` for the same session is heard again (holder design §3.2 step 1: an unhealthy gate holder leaves the work state unknown; D29). The first `hello` of a launch writes `observerSeenLaunch: <launchId>` into the session's state file (additive), so an adopter restores a seen observer as `unhealthy` until its fresh `hello` and never takes Q1's path for a process whose bridge was there (D37); O12 M4's observer reconnects with a 5 s backoff whenever its connection closes and sends `hello` again, since the gate's socket is replaced with the engine host. A row on which no observer was ever seen since the process started is `observer: 'absent'` and follows Q1.
- `turn.origin` adds `peer` beside O12's four, with `delivery` the inbox delivery id (Interfaces §E; D14): the settlement O16 defines is that sminos defers settling a `peer` delivery to a marked session only while the observer holds an armed fence, settling it when the observer reports the turn `proceed` (or proceeds on the lease's expiry) and keeping it owed on `stop`; with no fence armed the delivery settles at the turn's start as today. The observer's `hello` carries `childPid`, the bridge child's pid, which registers it as infrastructure for the descendant veto. O12 M4 builds the observer and the settlement.
- `stop`'s reason text is exactly "The holder ended this session; reopening it continues the conversation." (O12 M4's text), which the bridge streams as the turn's one chunk.
- An `idle` reap is its own path, `session.reap('idle')` (D15), never the ladder: `end_session` with the ladder's grace (`LADDER_MS.endSession`, 3 s), then one `signal SIGTERM` through the host, then a wait of `REAP_TERM_MS` 5 s for the host's `exit` record, which ends the session with reason `idle` through the existing exit path; stdin is never closed and no SIGKILL follows. Past the wait with the process alive, nothing else happens to it: the row stays `ready` with its stdin open, its process state unchanged and its ladder untouched, `work.unknown` reads `reap_term_ignored`, a `reap {phase: 'term_ignored'}` row is journaled, the fence is disarmed, and the clock starts again from that moment (holder design §3.2 step 5). The reap sets the session's `stopReason` to `idle` at its first rung and `term_ignored` keeps it, so an exit that comes later (an `end_session` the engine honours after its turn) is an `idle` release, never the crash path and its auto-resume; the next Stop clears the unknown and the mark as any Stop clears an unknown, and an explicit stop afterwards runs the ladder whole as it would have. A `budget` reap signals through today's ladder (end_session, SIGTERM, SIGKILL; charter §4.4), gated the same way.
- The descendant veto (D17): every process under `claude` (the tree from `ps -axo pid=,ppid=,command=`, re-read synchronously at the step) counts as work unless it is registered infrastructure: the bridge child named by the observer's `hello.childPid`, and a direct child of `claude` whose command line equals, argument for argument, a stdio MCP server of the launch's effective configuration (the launch spec's `--mcp-config` and each server's `config.{command,args}` as `mcp_status` reports them, asked once per launch at the handshake for that purpose; `get_settings` carries no `mcpServers`, M0's question 4, D48). A `ps` that fails, or a tree the host cannot read, is `work.unknown = 'descendants_unreadable'`, never zero. M0's question 4 says what a resting tree holds; anything the two registrations cannot name is a finding that extends them with evidence, never a rule by group or start time.
- The budget release runs through the same state machine, so a memory-pressure release never signals into a turn either; its candidate choice (`budget.ts` `evaluate`) is unchanged.

**What it does not touch.** The session host binary. Adoption. sminos.

**Proves.** Acceptance 2, and the OX10 fixture for O12. Tests pin, over a fake observer on a real socket and a fake session: no release while any of a client's interest, a kept mark, a turn, a non-ambient task, a listed cron, unknown work, an unregistered descendant (a same-group `sleep` under `claude`; a background job started before the last Stop that the task list no longer names) or an unreadable tree holds; a registered MCP server's process and the bridge child do not hold; a release with no observer ever seen on verified-empty alone; a `hello` for a session no row holds is closed; with an observer: `arm` before any signal, no signal before `armed`, no signal past the lease, a `turn` before the step answered `proceed` with the reap cancelled and the fence disarmed (and `releasing` cleared for a budget reap), a `turn` after the step answered `stop`, heartbeat loss during `arming`, `armed` and with a `turn` pending each leaving the row unreleased and `observer_unhealthy` until the observer's next `hello`; an ignored `end_session` and SIGTERM leave the session able to take a turn and an explicit stop afterwards ends it through the ladder; the budget release armed the same way. `e2e:supervisor-daemon` case (m): with a fake observer on `gate.sock` for the no-tab session, the release's `arm` arrives, the scene answers `armed`, the session is released; repeated with a `turn` sent after `armed`, the scene reads `proceed` and the session stays live for another period; repeated with the observer silent, the session stays live past two periods.

### Interfaces and Dependencies

#### A. The session host protocol (M1; the engine host's client in M2)

Over the host's Unix socket, newline-delimited JSON, one object per line, plus two byte records. The first line the client writes is `auth`; a wrong or missing token within 2 s closes the connection with nothing written. Every object has `t`. Unknown fields are ignored and unknown `t`s answered `{"t":"error","message":"unknown t"}`, so the protocol grows additively within its major (`hello.protocol` 1); a client refuses to adopt a host of another major and leaves it running.

Client → host:

    {"t":"auth","token":"<64 hex>"}
    {"t":"attach","role":"writer"|"observer","fence":<uint64>}                              writer: fence must exceed the host's; the previous writer is told `fenced` once its in-flight stdin record, if any, has been applied
    {"t":"launch","appSessionId","engineSessionId","argv":["<bin>",…],"cwd","env":{…}}     writer, once, before commit; the host records the ids in its roster and keeps env in memory only
    {"t":"commit"}                                                                            writer; the host forks; never twice (a second commit is `error`)
    {"t":"read","fromSeq":<uint64>}                                                           replay from max(fromSeq, firstSeq), then live records on this connection
    {"t":"ack","seq":<uint64>}                                                                writer: the ring drops every record at or below seq (the client sends only a contiguous frontier, §C)
    {"t":"stdin","offset":<uint64>,"len":<n>}\n<n bytes>                                      writer: queued iff offset == stdinAccepted; whole or not at all
    {"t":"end"}                                                                               writer: closes the child's stdin after every queued record is applied
    {"t":"signal","name":"SIGTERM"|"SIGINT"|"SIGKILL","group":<bool>}                         writer: to the child, or its process group
    {"t":"release"}                                                                           writer, after the child's exit: the host removes its files and exits now
    {"t":"hb"}                                                                                optional; the host keeps no liveness clock on its clients

Host → client:

    {"t":"hello","protocol":1,"holderId","pid","procStart","appSessionId","engineSessionId","state":"ready"|"committed"|"running"|"exited",
     "child":{"pid","procStart"}|null,"fence":<uint64>,"writer":<bool>,"stdinApplied":<uint64>,"stdinAccepted":<uint64>,"stdinQueued":<bytes>,"ring":{"firstSeq","lastSeq","bytes"},"exit":{"code","signal","at"}|null}
    {"t":"spawned","pid","procStart"} | {"t":"spawnFailed","message"}                       the answer to commit
    {"t":"attached","fence","stdinApplied","stdinAccepted","ring":{…}} | {"t":"refused","reason":"fence"|"role"}
    {"t":"out","seq":<uint64>,"len":<n>}\n<n bytes>                                          one stdout line, without its newline
    {"t":"err","seq":<uint64>,"len":<n>}\n<n bytes>                                          one stderr line, in the same sequence
    {"t":"caughtUp","lastSeq":<uint64>,"gap":<firstSeq>|null}                                 after a read's replay; gap when fromSeq < firstSeq
    {"t":"applied","offset":<stdinApplied after>} | {"t":"duplicate","accepted","applied"} | {"t":"gap","accepted"} | {"t":"fenced","fence"} | {"t":"busy","queued"}
    {"t":"stdinClosed","applied":<uint64>,"partial":<bytes>}                                  the child's stdin closed under a write: `partial` bytes of the record reached the pipe
    {"t":"exit","code":<int>|null,"signal":<string>|null,"at":<iso>}                          the child's exit, from waitpid
    {"t":"problem","kind":"line_budget","length":<n>}                                         a line over 64 MiB dropped
    {"t":"error","message"}

Input semantics (D30). The host keeps two offsets: `stdinAccepted`, the byte after the last record it queued, and `stdinApplied`, the byte after the last record fully written to the pipe. One goroutine writes the child's stdin from the queue in arrival order; a record is `applied` only once every byte of it reached the pipe, and both offsets advance by whole records. A `stdin` is queued iff its `offset` equals `stdinAccepted`; one below it is `duplicate {accepted, applied}` (a resend of a record still queued or already applied: the original's `applied` is the one answer that counts, and the resend is never queued); one above it is `gap {accepted}`; with one writer a resend carries the same bytes, and the host does not compare them. The queue is bounded by `STDIN_QUEUE_CAP` 64 MiB of queued bytes: a record is refused `busy {queued}` only when the queue is not empty and the record would take it past the cap, so one record of any size the frame cap allows is always accepted into an empty queue (a 48 MiB send is a valid message, `session-state-store.ts`); the client retries after the next `applied`. A record cannot be recalled once queued. A writer superseded while its records are queued or in the pipe keeps them: the host applies the queue it already accepted, then fences the old connection and answers the new writer's `attached` with the offsets that count them, so a successor's rebase never sees an offset move under it. The pipe closing under a record is `stdinClosed {partial}` to the writer; the record counts as applied for the offsets, and the client ends the session as it ends a `stalled_write` today.

Constants, in `native/session-host/host/limits.go` and mirrored in `src/engine-host/holder/protocol.ts`: `LINE_CAP` 64 MiB, `RING_CAP` 8 MiB, `STDIN_QUEUE_CAP` 64 MiB, `LINGER` 10 min, `HOST_EXIT_GRACE` 5 s, `AUTH_WINDOW` 2 s, `FRAME_CAP` 64 MiB + 256 bytes for the byte records.

#### C. The host transport, the checkpoint and the journal (M2)

`src/engine-host/holder/transport.ts`:

    export function spawnHosted(plan: LaunchPlan, deps: { hostsDir: string; binary: string; gateSocket: string; maxLineChars: number; log(line: string): void }): EngineTransport
    export function adoptHosted(entry: RosterEntry, deps: { token: string; checkpoint: Checkpoint; fence: number; maxLineChars: number; log(line: string): void }): Promise<{ transport: EngineTransport; hello: Hello; replayed: 'exact' | 'gap'; firstSeq: number | null }>

`EngineTransport` as `transport.ts` declares it, with two changes: `stderr` becomes `AsyncIterable<{ text: string; hseq?: number }>` (the direct and replay transports yield no `hseq`; `session.ts`'s `stderrLoop` and the replay transport change with it), and the optional `readonly holder?: { pid: number; holderId: string; fence: number }` and `journaled?(seq: number): void` (absent on the direct and replay transports). `TransportItem` gains `hseq?: number` (the host's sequence of the line, on frames and parse problems).

The checkpoint (D23). `src/engine-host/holder/checkpoint.ts` keeps, per hosted launch, the host map `<launchId>.hseq`: one line `<hostSeq> <journalSeq>\n` appended (a synchronous append, as the journal's) *before* the row it names is written, for every `in`, `stderr` and `parse_error` row of a hosted record; rotated with the journal. Two more line forms: `<hostSeq> -`, a retraction, appended when the row's append failed after its map line (the writer's sequence is not advanced on a failed append, so the next row would reuse it: the retraction says this record is not journaled and the sequence belongs to whatever row lands next), and `<hostSeq> *`, a lost range, appended after a gap's reseed rows (M3) to say every sequence at or below it is accounted for. A failed append of a hosted row is a journal failure for every kind of row, stderr included (today's `stderrLoop` is lenient; under the map a silent miss would certify the wrong row): the session appends the retraction and ends the process through the ladder as `inboundJournalFailed` does for an `in` row; a retraction that cannot be appended closes the launch's journal first (`journalClosed`, the exit path's own mark, so no later row, the `transport_error` meta and the exit row included, can reuse the sequence) and reports to the supervisor log, and the ladder runs. At adoption, `Checkpoint.read` appends a retraction for each provisional line it drops (a line whose journal sequence is past the tail) before the resumed writer appends anything, so a sequence the tail's successor reuses never matches a stale line at a later adoption. In memory it keeps the contiguous frontier `F` (every record with a sequence at or below `F` journaled) and the journaled sequences above it; `journaled(seq)` from the session (called right after the row is written) advances `F` while the next sequence is journaled and sends the host `ack {seq: F}` coalesced (at most one per 50 ms or 64 records, and one at each write's settle), so an ack covers only records whose map line and row are both on disk. The journal's row schema is unchanged. The stream's and the normaliser's order is the journal's as today; the host sequence only decides what the ring may drop and what an adopter replays. `pruneJournals` removes a launch's map files with its journal files. `Checkpoint.read(dir, launchId, journalLastSeq)` truncates the map to its last newline, drops the lines whose journal sequence is past `journalLastSeq` (a map line written before a row that never landed) and every line a later retraction names, takes a lost-range line as accounting for every sequence at or below it, and returns `{frontier: F, above: number[]}`; a launch with no map (never hosted, or crashed before its first record) reads `{frontier: 0, above: []}` and the ring holds everything from 1. No record is identified by its content.

`JournalWriter` gains `static resume(dir, launchId, opts): JournalWriter`, opening the launch's latest file for append with `seq` and the rotation index continued from its tail (a torn last line, a crash mid-`writeSync`, is ignored and the next row appended after a newline), and `journal.ts` a reader over every file of a launch in order, for M3's fold. New meta events: `host_attach {holderId, fence, frontier, replayed, firstSeq}`, `host_detach {reason: 'handover' | 'exit', frontier}`, `transport_error {code: 'host_lost'}`, `reap {phase}`; the normaliser maps `host_attach` with `replayed: 'gap'` to a `session.notice` and the others to nothing. `session.reconnect` rows carry `trigger: 'host_restart'` (already in `RECONNECT_TRIGGERS`).

`buildEnvironment(spec, captured, relayUrl, spawnerPid, holder: { gateSocket: string })` sets `MAWS_HOLDER_SOCKET`; on a hosted launch the launcher builds the plan before any host exists, so `spawnerPid` is a placeholder (`0`) and `spawnHosted` rewrites `SMNS_MEMBER` to the host's pid after its `hello` and before `launch`, as M2 says.

The state file (`@shared/engine/session-state-store`): `owedInterrupt?: boolean` (additive), with `saveOwedInterrupt(appSessionId, owed)` and read by `load`.

Write semantics in the transport (D30): `write(frame, signal)` resolves at `applied` (or at the original's `applied` for a `duplicate`) and rejects with `TransportClosed` on `gap`, `fenced` or `stdinClosed`; `busy` is retried after the next `applied` within the write's own deadline. The abort signal is honoured only while the record has not been handed to the socket (today's transport discards only a queued frame); a record handed to the socket is irrevocable, its write settles on the host's answer whatever the signal, and `OutboundWriter`'s settlement, `preface`, `flushed` and the inbound gate run as today on that one outcome. The transport hands a record to the socket as one `write` of header and bytes.

#### D. Adoption and the handover (M3)

    |---|---|

    | `mcp_message` `tools/call` of `maws.ask`             | re-raised as a pending ask under its request id; an async ask already answered at the MCP level is restored from the journal's ask rows |

#### E. OX10 as adopted: the gate (M5; the observer is O12 M4's)

On `gate.sock`, newline-delimited JSON, many clients, no token (the uid boundary; the socket reveals no session data and takes no control), served by `src/engine-host/holder/gate.ts`, a server of its own over `node:net` with `@shared/host/private-listen`'s checks (D27). The engine host sets `MAWS_HOLDER_SOCKET=<its path>` in every hosted launch's environment.

Observer → host:

    {"t":"hello","protocol":1,"session":"<engine session id>","pid":<claude's pid>|null,"childPid":<the bridge child's pid>|null}     first; the host keys the observer by session against each row's lineage (pid a cross-check when known), closes a hello no row matches, and registers childPid as infrastructure
    {"t":"hb"}                                                                            every 5 s; silence past 15 s makes the observer unhealthy
    {"t":"armed","fence":<n>}                                                             the fence is installed in turn.step
    {"t":"turn","fence":<n>,"origin":"query"|"cron"|"task"|"peer"|"unknown","delivery":"<id>"?}   before next() in the main loop's turn.step, while a fence is installed

Host → observer:

    {"t":"welcome","protocol":1}
    {"t":"arm","fence":<n>,"leaseMs":10000}                                               renewed with the same fence before the lease ends
    {"t":"disarm","fence":<n>}
    {"t":"proceed","fence":<n>} | {"t":"stop","fence":<n>,"reason":"The holder ended this session; reopening it continues the conversation."}

Rules (O12 M4's, with O16's additions): the host signals only after `armed` and within `leaseMs` by its own clock less 1 s; the observer, on `stop`, calls no `next` and streams the reason as the turn's one chunk; with no answer to `turn`, it proceeds after the lease has expired by its own clock plus one heartbeat; a `turn` whose fence is not the armed one is answered `proceed`. The settlement: while the observer holds an armed fence, sminos defers settling an inbox delivery to a marked session until the observer reports the turn it started as `proceed` (or proceeds on the lease's expiry), carrying the delivery's id as `delivery`; on `stop` the delivery stays owed and is delivered after resume; with no fence armed the delivery settles at the turn's start as today. O12 M4's `launch_env` drops `MAWS_HOLDER_SOCKET` as M3's dropped `MAWS_LANE`. A row on which no observer was ever seen since its process started is released on verified-empty alone (owner Q1's default; a `no` makes such a row never release and its status say `gate: 'absent'`); one whose observer was seen and is silent or gone is never released until it is heard again (`observer_unhealthy`), and the fact that one was seen is kept in the session's state file (`observerSeenLaunch`) so an adopter restores it. The observer reconnects with a 5 s backoff whenever its connection closes (the gate's socket is replaced with the engine host) and sends `hello` again.

#### F. The reap and the release rule (M5)

`src/engine-host/holder/reap.ts`:

    export type ReapState = 'idle' | 'arming' | 'armed' | 'signalled' | 'term_ignored';
    export type ObserverState = 'absent' | 'healthy' | 'unhealthy';
    export interface ReapDeps { gate: Gate; current(): EngineSessionStatus | null; interest(): boolean; descendants(): number | 'unreadable'; reap(reason: 'idle' | 'budget'): Promise<'exited' | 'ignored'>; observerSeen(): boolean; now(): number; log(line: string): void }
    export class Reap { constructor(session: EngineSession, deps: ReapDeps); due(reason: 'idle' | 'budget'): void; cancel(why: string): void; readonly state: ReapState; readonly observer: ObserverState }

Transitions: `idle` --due, verified empty, observer healthy--> `arming` (send `arm`); `arming` --`armed`--> `armed` (the step runs at once); `arming`/`armed` --`turn`, or any veto at the step, or the observer unhealthy--> `idle` (`proceed` for a turn, `disarm`, the row's clock restarts); `armed` --step: verified empty, lease live--> `signalled` (reap); `idle` --due, verified empty, observer absent--> `signalled`; `idle` --due, observer unhealthy--> stays `idle` (`work.unknown = 'observer_unhealthy'`); `signalled` --`turn`--> `stop` answered, state unchanged; `signalled` --exit--> the row is released (the table's `released` set, as today); `signalled` --SIGTERM ignored (`idle` only)--> `term_ignored` → `idle` after the journal row, with `work.unknown = 'reap_term_ignored'` until the next Stop.

Verified empty, in one function `isVerifiedEmpty(status, stateful, descendants)`: `isIdleRow(status, stateful)` and `status.work.unknown === null` and `status.work.crons.length === 0` and `descendants === 0`. `EngineSessionStatus.work` gains `descendants: number | null` (additive; 0 for a row with no process, `pid` null, the replay transport's, since there is no tree to veto; null only for a live pid whose `ps` fails, which `work.unknown` then names `descendants_unreadable`) from `src/engine-host/holder/descendants.ts`: `countWork(tree, claudePid, registered: { pids: Set<number>; mcpCommands: string[][] })` over `ps -axo pid=,ppid=,command=`, re-read synchronously at the step, where a direct child whose command line equals one of `mcpCommands` argument for argument, and any pid in `registered.pids` (the bridge child), are infrastructure, and every other process under `claude` is work. `holdsWork` (`budget.ts`) includes `descendants !== 0`.

`IdleRelease.fire()` calls `reap.due('idle')` instead of `session.stop('idle')`; `process-table.ts`'s budget release calls `reap.due('budget')` and clears its `releasing` when the reap is cancelled. `session.reap('idle')` is the signal path of M5's decision (`end_session` with its grace, then one SIGTERM through the host, the `REAP_TERM_MS` wait, `'exited' | 'ignored'`, stdin never closed); `session.reap('budget')` runs `stop('budget')`'s ladder. `SERVER_RELEASE_MS` and the laptop's idle time are unchanged; the verdict is the reap's. `SupervisorStatus.release` gains `gate: { armed: number; observed: number; unhealthy: number; absent: number }` (optional, additive), and `EngineSessionStatus` gains `reap?: { state: ReapState; observer: ObserverState }`.

## Owner questions

- **Q1. A lane B session on which no observer was ever seen.** The sminos plugin may be absent from a machine, or a session's bridge may never have connected. May such a session be released on verified-empty alone, on both roles? **Recommended: yes.** Without the bridge no peer message can reach the session, and verified empty rules out a cron fire and a task notification; what remains is an engine-started turn in the milliseconds between the final check and the signal, and that turn's trigger is in the engine's own transcript. The alternative, never releasing such a session, keeps every unbridged session on a server for good, which is the cost F2 exists to give back. The question is the never-seen case alone: an observer that was seen and went silent or away is the holder design's unhealthy gate, and that session is never released until it is heard again (D29). The document plans the yes; a no changes one branch in `reap.ts` and the status's `gate: 'absent'` wording.

The host protocol carries output and input as length-prefixed byte records beside NDJSON control lines.** A 64 MiB line is the engine host's own cap; JSON-escaping it on the relay would double its memory and time on both ends. - **D5.
