## Purpose

Today a lane B session is a child of the engine host: the process that holds its Query also holds its pipes. So an engine host cannot be replaced while a session runs, and `mawsd` serves an older engine host "until its sessions are idle" (O2 M3, E10 §6). On a server that never idles, with a session kept by a background shell or a cron, that day never comes: an upgrade either never takes effect or, at the owner's Restart now, ends every lane B session and reopens each with `--resume`, losing its background shells, its Monitors and its MCP tasks (`background-work-handoff.md` §2). An engine-host crash loses the same.

After O16, every lane B process the engine host launches runs under a **session host**: a small native process that owns `claude`'s pipes, numbers its output, applies its input exactly once and signals it only on a fenced request. The engine host keeps the Query, the `maws` tool server and the hooks, and can be stopped and started around a running session: a new engine host, of another build or the same, finds the session hosts in a roster, re-attaches as the one writer, replays what it missed from each host's ring, re-initializes the engine and goes on. An engine-host upgrade, a `mawsd` restart and an app upgrade, each mid-turn, leave the turn completing, no input applied twice and a pending permission shown once (P5 acceptance 13). The servers' idle release stops being a wall clock: a session is released after 24 hours only once its work state is verified empty, with the release armed through the observer bridge's `turn.step` gate so no turn from any origin is lost in the window between the verdict and the signal (OX10, owner F2).

**How to see it working.** On a scratch profile on the daemon shape, start a session and ask it to run `sleep 300 &` in the background; `mawsd status` lists the session's host (`session hosts  1 (adopted 0)`); run `mawsd restart --engine-host`: the engine host's pid changes, the session's pid and launch id do not, the transcript keeps streaming, the shell's pid lives, and `mawsd status` reads `session hosts  1 (adopted 1)`. Then replace the app bundle with another build and relaunch: the same. Concrete Steps has each command; the e2e groups named in Acceptance prove each behaviour on the gate's Macs and the acceptance run on a devcloud VM proves it with the real engine.

### Orientation

Terms used throughout:

- **The engine host:** E10's detached supervisor (`src/engine-host/index.ts` dispatching to `detached.ts`), one per profile, holding each lane B session's `EngineSession` (`session.ts`: the Query, the `maws` tool server, the hooks, the broker, the queue) in the process table (`process-table.ts`), served over `host.sock` to its one client, `mawsd` (`src/mawsd/daemon.ts`, the relay and the permanent link). Its files are `<profile>/supervisor/` (`supervisor-files.ts`). **The manager**, in holder design terms, is this process.
- **A session host:** the new native process (`native/session-host/`, binary `maws-session-host`) that spawns one `claude -p` with piped stdio, numbers every stdout and stderr line into a ring, applies stdin by offset, holds the writer fence, writes its roster entry and serves one Unix socket (Interfaces §A, §B). One per launch; its id is the launch id (`launch.ts` `mintLaunchId`), so the journal, the roster and the request ids name one process by one id (D5).
- **The host transport:** `src/engine-host/holder/transport.ts`, an `EngineTransport` (`transport.ts`'s interface: `frames`, `stderr`, `write`, `endInput`, `kill`, `exited`) over a session host's socket instead of a child's pipes, so `EngineSession`, `OutboundWriter`, `ControlClient`, the ladder and the normaliser run unchanged (Interfaces §C).
- **The roster:** `<profile>/supervisor/hosts/<launchId>.json`, written by each session host at every state change; the manager reads the directory at start to adopt (Interfaces §B, §D).
- **The checkpoint:** the contiguous frontier of host sequences the launch's journal holds (every record at or below it journaled), with the set of records journaled above it, kept in a sidecar beside the journal; the session host keeps every record above the acknowledged frontier, so a new manager replays from the checkpoint exactly, or learns of a gap (Interfaces §C).
- **The restore fold:** the pass an adopter makes over the launch's whole journal (every file of the launch, in order) through the session's readers with every emission and reaction suppressed, so the normaliser, the status tracker, the broker and bash mode hold the state the old manager held before any new record is consumed (Interfaces §D).
- **The handover:** an engine host's exit that detaches its hosted sessions instead of ending them, once its own in-flight work has drained, and its successor's adoption of them; asked by `mawsd` with `host.handover` on a welcomed link, or by the socket layer's stable `exit {when: 'idle'}` from an adopting client on a refused one, and deferred, never forced, while a drain does not settle (Interfaces §D, D9).
- **The gate:** OX10's server, `<profile>/supervisor/gate.sock`, where sminos's observer bridge inside a lane B process connects and answers the reap fence's `arm` and asks `turn` (Interfaces §E).
- **The reap:** the release of an idle session (`idle`, the role's clock; `budget`, memory pressure) as a state machine over the gate: verified empty → armed → final check → signalled; an `idle` reap is `end_session` then SIGTERM on a path of its own that leaves the session usable if the engine ignores both (Interfaces §F).
- **Verified empty:** `work-state.ts`'s snapshot with `unknown === null` and `crons.length === 0`, no non-ambient task in `backgroundTasks`, and no process under `claude` beyond the registered infrastructure, read at the moment of the verdict (Interfaces §F); `budget.ts`'s `isIdleRow` already says most of it.
- **Registered infrastructure:** the processes under `claude` that are not its work: the sminos bridge child, named by pid in the observer's gate `hello`, and the stdio MCP servers of the launch's configuration, matched by command line; everything else under `claude` is work (holder design §3.2).
- **The stub engine:** M2's fixture-playing process (`test/support/stub-engine.mjs`, selected by `MAWS_E2E_ENGINE_BIN`), which speaks stream-json over real stdio from a journal fixture as the in-process replay transport (`replay-transport.ts`) does in memory; it is what the hosted scenes spawn under a real session host, since the in-process replay spawns nothing and today's `writeReplayEngine` (`test/support/replay-engine.ts`) answers `--version` alone and refuses a real invocation.

How the parts fit on master. `launcher.ts` builds a `LaunchPlan` (`launch.ts` `buildLaunch`: the binary, the flags, the environment with `SMNS_MEMBER` and `MAWS_LANE=B`, the pinned `--session-id`) and reserves an `EngineSession` whose `spawn` is `ipc.ts`'s `spawnEngine(plan)`; `session.ts` `run()` spawns, wraps the transport in an `OutboundWriter` and a `ControlClient`, journals every row through `record` (`journal.ts`, synchronous appends), initializes, and ends the process through `session-ladder.ts` (end_session, SIGTERM, SIGKILL). The table writes `live.json` (`live-ledger.ts`) at every launch and exit; `detached.ts` sweeps a dead predecessor's rows at start. `supervision.ts` sets the idle release's policy from the role (`role.ts`; `SERVER_RELEASE_MS` 24 h, the laptop's the idle exit's), `idle-release.ts` fires `session.stop('idle')` when a row's clock is due and `isIdleRow` still holds, `budget.ts` names the hard reasons, and `work-state.ts` keeps the crons from the Stop callback (`host-hooks.ts`) and the tasks from `background_tasks_changed`, unknown on an `adopted` launch until the first signal. `mawsd` reaches the engine host through `@shared/host/detached-transport` with `buildPolicy: 'replace'`: another build with nothing live is replaced at once, with sessions live served and asked `exit {when: 'idle'}`; a crash is the ladder's restart; `beforeSpawn` refuses a spawn from a replaced bundle (Decision Log 161). sminos's bridge (`bridge.tsx`) observes a marked session, refuses every control and rewrites nothing in `turn.step`.

### M1 — The session host binary

**What exists at its end.** `native/session-host/`: a Go module (std only, `go 1.25`, no dependency) building `maws-session-host`, which, given a token on its stdin and its socket path on argv, serves Interfaces §A over the socket, spawns the launch it is given at `commit`, keeps the ring, the offsets, the fence and the roster of §B, signals its child on request, records the child's exit and lingers, then removes its files and exits. `native/session-host/prebuilds/{darwin-arm64,linux-x64,linux-arm64}/maws-session-host` committed, built by `scripts/build-session-host.sh` (`pnpm build:session-host`) with `-trimpath -buildvcs=false -ldflags='-s -w'` from the private toolchain, reproducible byte for byte; `scripts/check-session-host.sh` rebuilds each from source and compares bytes, run by the gate's static job through `actions/setup-go` at the version `native/session-host/go.version` names (a `.github` hunk for CI-opt). `electron-builder.yml` carries the darwin build into `Resources/session-host/` through `extraResources` (the `peer-auth` precedent); `scripts/mawsd-pack.mjs` copies the pack's platform build into `bin/` (M4 proves it). `src/engine-host/holder/files.ts` names the binary per shape (packaged: `process.resourcesPath`; a checkout: the prebuilds directory; `mawsd`'s Linux release: `<release>/bin/`).

**What it touches.** `native/session-host/` (new: `main.go`, `host/` for the process, `ring/`, `proto/`, `roster/`, each with tests), `scripts/build-session-host.sh`, `scripts/check-session-host.sh`, `package.json` (`build:session-host`), `electron-builder.yml`, `scripts/mawsd-pack.mjs`, `.github/workflows/gate.yml` (the static job's step), `src/engine-host/holder/{files,protocol}.ts` and `src/engine-host/holder/binary.test.ts` (the real-binary tests, darwin and linux; skipped where no prebuild matches the platform).

**Decisions.**
- The language is Go (D3), std only, one module, no cgo (`CGO_ENABLED=0`), so the Linux builds are static ELF and the Mac build links `libSystem` alone.
- The protocol is NDJSON control lines plus two length-prefixed byte records for output and input (Interfaces §A), so a 64 MiB line is never JSON-escaped on the hot path; the line cap is the engine host's `MAX_LINE_CHARS` (64 MiB): an unterminated line past it is dropped with a `problem` record, the child left to the manager's verdict (today's transport kills it: `transport.ts`).
- The ring holds what the writer has not acknowledged, up to `RING_CAP` 8 MiB; the manager acks after each journal write (D6). Past the cap the oldest lines go and `firstSeq` moves, so a `read` below it answers a gap, never a guess.
- stderr lines share the ring's sequence (`err` records), so one checkpoint covers both streams and the journal's `stderr` rows are replayed too.
- The writer fence is a `uint64` the host keeps from its first writer (1); `attach writer` with a fence at or under the current is refused, a superseded writer's connection is told `fenced` once the records it had queued are applied, and every later write from it refused; the fence is written to the roster at each change and read back at the host's own restart never (a host does not restart: its death ends the session, D7). Observers read only.
- Stdin is one writer goroutine over a bounded queue, whole records only, never recalled (Interfaces §A, D30).
- Output to a connection is written from the ring at that connection's cursor as its socket drains, each record as it is read, no batching on the hot path; a connection more than `CONN_WRITE_CAP` 32 MiB behind is closed, and its client re-reads from the ring on reconnect.
- The host's own signals: SIGTERM, SIGINT or SIGHUP to the host sends SIGTERM to the child's process group, waits `HOST_EXIT_GRACE` 5 s, and exits; a host whose death would leave an unreachable engine (E10 M0 Q1: an engine with no stdio finishes its turn and runs on) takes the session down cleanly instead (D7). SIGKILL of the host is the manager's case while it lives (M2) and the sweep's at the next start (M3).
- A host with no child (`ready`, or `committed` with a spawn that failed) whose writer connection has ended exits after `HOST_NO_CHILD_MS` 30 s, removing its files: it protects nothing.
- The host stats its socket path every 60 s and listens again at the same path when the file is gone (the tmpdir fallback's directory is subject to macOS's periodic cleanup of untouched files; the profile path, 8 characters of launch id, is the common case).
- After the child's exit the host serves `hello`, `read` and the exit record for `LINGER` 10 minutes, or until the writer sends `release`, then removes its socket, token and roster entry and exits 0.
- The roster entry is written with a temp file and rename, 0600, at `ready`, `committed`, `running` and `exited` (Interfaces §B); the socket is 0600 in the 0700 `hosts/` directory, made and checked as `@shared/host/private-listen` makes them (the host re-implements the checks: lstat, the uid, the mode, no symlink).
- Peer identity: the uid boundary and the token, as every socket of `mawsd` (O2 M8); no peer-credential check.
- Process start identity: the host records its own and the child's `procStart` as `supervisor-files.ts` reads them (`ps -o lstart=` under `LC_ALL=C TZ=UTC`, on both platforms), so `isSameProcess` compares like with like.
- Logging: `<hosts>/<launchId>.log`, 0600, one line per state change and problem, capped at 1 MiB (truncated at open past it).
- Build: `go.version` pins the toolchain; the script refuses another; the three targets are built from one machine (`GOOS`/`GOARCH`, `CGO_ENABLED=0`, so a Linux runner builds the darwin target too); the CI check rebuilds all three on the pool's Linux runner and compares bytes, Go's builds being reproducible across build hosts under `-trimpath`; `unit:darwin`'s real-binary tests run the committed darwin build besides.
- The binary is resolved at each spawn from the engine host's own build location (`sessionHostBinary()`, §H). After an app bundle swap an old engine host spawns the new bundle's session host, which speaks the same protocol major; a protocol major bump is its migration's to handle (OX1's rule, applied to this protocol).

**What it does not touch.** The engine host's launch path (M2). `mawsd`. The gate.

**Proves.** Acceptance 4's build half. Tests: `go test` (the ring's cap, gap and ack; offsets' duplicate and gap; the fence's CAS; the roster's atomic writes; signal relay; the linger). `binary.test.ts` drives the committed binary with `/bin/cat` as the child: auth before anything (a wrong token gets no byte), `hello` after auth, `launch` and `commit` spawning `cat` with the given argv, cwd and env (the env read back through the child), `out` records sequenced from 1, `read` exact and `gap` after the cap, `stdin` applied once and `duplicate` on a resend, `busy` past the queue's cap and a blocked pipe never blocking the reader, a second writer at fence+1 superseding the first after the first's queued record was applied (`fenced`, its next write refused, the new writer's `stdinApplied` counting it), `stdinClosed` with its `partial` when the child closes stdin mid-record, `signal SIGTERM` ending `cat` and the `exit` record, the linger and `release`, SIGTERM to the host ending `cat`, a no-child host exiting after its writer leaves, a lagging connection closed at the cap, the socket re-bound after its file is removed, and the socket's fallback path when the directory's path is long.

The manager polls the socket path with connect attempts for up to `HOST_START_MS` 5 s; the host's `hello` is the ready signal.
- `commit` is sent only once the writer is attached, so the first frames of the engine are held in the ring for a connection that already reads: nothing is lost between spawn and attach.
- The manager's offset starts at 0 on a fresh launch and at `stdinApplied` on an adoption (M3); the `OutboundWriter`'s `write` resolves at the host's `applied` (the §4.6 delivery truth moves one hop: the bytes reached the host, which reached the pipe before answering), a `duplicate` resolves as delivered, a `gap`, `fenced` or `stdinClosed` rejects with `TransportClosed`, a `busy` is retried after the next `applied` within the write's deadline; an abort after the record left for the host rejects the write and journals its `out` row when `applied` arrives (Interfaces §C, D30).
- The acknowledgement is the contiguous frontier (D6, D23): the session tells the transport `journaled(seq)` right after each `in`, `stderr` or `parse_error` row is written; the checkpoint advances the frontier while the next sequence is journaled, acks it coalesced (at most one per 50 ms or 64 records, and one at each write's settle) and rewrites the sidecar with the same coalescing, so the ring's unacknowledged bytes stay near zero at idle (the session host's footprint then reads the binary's own, D3's 3 MiB) and a record held behind an in-flight write is never acknowledged ahead of its journaling.
- `MAWS_HOLDER_SOCKET` is set on every hosted launch from M2, though nothing listens until M5 (O12 M4's observer, when built, treats a refused connect as no gate); if M5 lands first it sets the same line.
- The owed interrupt (D12): `session.interrupt` sets `owedInterrupt: true` in the state file before its control request is written and clears it when the response arrives or the write failed; an adoption that finds it set sends `interrupt` before anything else (M3).
- The crash of a session host (its pid gone, the socket closed): the transport reports `exited` with the host's last exit record if any, else `{code: null, signal: 'SIGKILL'}` and a `transport_error {code: 'host_lost'}` row; the session ends as a crash, and the manager, which knows the child's pid and `procStart` from `spawned`, signals the child itself (SIGTERM, the sweep's grace, SIGKILL to its group) rather than leaving it to a successor's sweep.
- The stub engine (D31): `test/support/stub-engine.mjs` is spawned as the engine by the harness's existing selection (`MAWS_E2E_ENGINE_BIN`, set by `e2e/support/stub-engine.ts`'s `writeStubEngine(userData, fixture)` as `writeReplayEngine` sets it today), reads its fixture (a journal fixture of `test/fixtures/engine/`, the replay transport's own format) and plays it over real stdio with the replay transport's rules (an `in` row written once the `out` rows before it have arrived on stdin, paced by `MAWS_REPLAY_ROW_MS`), honours two fixture directives, `spawn-child` (a `sleep` it parents, whose pid it prints as a stderr line) and `count-stdin` (the frames it read, printed at its exit), and answers `--version` with `TESTED_ENGINE_VERSION`. The hosted scenes (`e2e:supervisor`, `e2e:supervisor-daemon`, the daemon-idle session-host case) launch with it in place of `replaySpec`; the in-process replay stays for every other scene and for the embedded shape.

### M3 — Adoption and the handover

**What exists at its end.** An engine host that starts over a profile with live session hosts adopts them: for each roster entry whose host answers `hello` with the right token, it attaches as writer at the host's fence + 1, opens the launch's journal in append mode continuing its `seq`, folds the launch's whole journal into a fresh session's readers with nothing emitted (the restore fold), replays the ring from the sidecar's checkpoint (exact, or with a gap row and a notice) with live dispatch held, classifies every request still outstanding (orphaned tool calls answered, asks re-raised, hook callbacks answered, permission and dialog requests left to the engine's redelivery), seeds the work state from the durable records, sends an owed interrupt, re-initializes, and then serves the session as before with the same launch id and pid, its new control requests named apart from the old manager's. An engine host's exit detaches its hosted sessions once their MAWS-owned work has drained, never on a timeout alone; `host.stopAll` and the quit path's stop still end them. `mawsd` asks a capable engine host of another build to hand over as soon as its welcome arrives, sessions live or not, serves it while the handover is deferred, and `mawsd restart --engine-host` asks the same on demand. Journal pruning never runs before adoption and never prunes a launch a roster entry names. The sweep stops only what no live host holds. `WIRE_MINOR` 13 with `host.holder` on the engine host's welcome and on the client hellos.

**What it touches.** `src/engine-host/holder/{roster,adopt,restore}.ts` (new), `detached.ts` (the start order: the roster read and the rows' reservation synchronously in `listening`, the adoption, then the sweep; the exit order's detach mode), `index.ts` (journal pruning scheduled after adoption, its keep set from the roster), `live-ledger.ts` (rows with a holder are skipped by the sweep while the holder lives; **Decisions.**
- Adoption order at start (D10): in `listening`, synchronously before the first hello can be answered, the roster is read and a row reserved for each entry with a live host, so `liveSessions` counts them from the first welcome and `mawsd`'s connect burst sees them; then each is adopted (bounded `ADOPT_MS` 60 s per host, in parallel; the fold of a day-long journal is the bound's reason); then the sweep over `live.json`'s rows that no adopted host holds, and over roster entries whose host is dead but whose child (pid and `procStart`) lives (SIGTERM, the grace, SIGKILL, as today's sweep). Journal pruning (`scheduleJournalPruning`, `index.ts`) is scheduled only after adoption has ended, and its `keep` set is the table's launches plus every roster entry's launch id, adopted or not (a failed or unadoptable host keeps its journal while it lives), so a hosted launch older than `JOURNAL_MAX_AGE_DAYS` is never pruned under a live host (D25).
- The checkpoint is the sidecar's (Interfaces §C, D23): a contiguous frontier `F` and the set `above` of records journaled past it; the journal writer resumes `seq` and the rotation index from the latest file's tail, ignoring a torn last line and appending after a newline. The adoption's replay is `read {fromSeq: F + 1}` skipping every record in `above`, and, for a record whose sequence lies above `F` and outside `above`, the fold's last rows after `F` are checked for an equal row (the same direction and the same serialized frame): an equal one is a row journaled after the sidecar's last write, skipped too (D23). `caughtUp {gap}` writes `meta host_attach {replayed: 'gap', firstSeq}` and a `session.notice` ("Some output was lost while the engine host was restarting; the conversation on disk is complete."), and the normaliser resets its lane state so the next message start re-anchors it; the reseed of the pane from the engine's transcript (holder design §3.3) is not built here: a gap needs more than `RING_CAP` of unacknowledged output during a restart, and the existing disk read serves the session on its next open (a tracker row, D23).
- The restore fold and the recovery barrier (D24): before any record of the ring is consumed, the adopted session reads every journal file of the launch in order and feeds each row to the normaliser, the status tracker, the broker, bash mode and the side-question log through a `restore` entry that observes and emits nothing (no X1 event, no reaction, no write); the fold also collects every inbound `control_request` with no `control_response` out and every outbound request with no response in. Live dispatch (`inbound()`, the tool server's `accept`, the hook callbacks) is held while the ring replays; a replayed record is journaled (unless skipped) and folded the same way, the barrier ensuring no replayed `mcp_message` runs a tool again. At `caughtUp` the outstanding inbound requests are classified: a `tools/call` of a `maws` tool that acts on something (every tool but `ask`) is answered with a tool error whose text is exactly "MAWS's engine host restarted while this tool ran. Its result is unknown and its effect may have completed; check before retrying." (holder design §3.3: never a retryable error); an `ask` call is re-raised from its journaled input as a pending ask under its original request id, so the human's answer settles the engine's own call; a `hook_callback` is answered `{}` (what `session.ts` answers an unknown callback today; the engine may have retired it, M0's question 3); `can_use_tool` and `request_user_dialog` requests are left to the engine's redelivery at re-initialize, which the broker already dedups by request id. Then the owed interrupt goes if marked, `initialize` runs as a resume's handshake (the app's hooks, `get_status`, the grant re-application skipped, the queue recovered), and live dispatch opens, the records held meanwhile processed in order.
- The work state of an adopted row is seeded from the durable records (D32): `WorkState.adoptedWith(record, tasks)` takes the state file's cron record as `resumedWith` does (no cron tool since the last Stop: the listed crons are known, empty or not; a tool since: unknown until the next Stop) and the tasks from the last `background_tasks_changed` the fold and an exact replay saw (known; after a `gap`, unknown until the next change or Stop). An idle session adopted after a clean handover is then released at its due time, instead of being held until a turn runs. **[parent-impact]** P5 §2 lists "a re-adopted process until a task snapshot or change arrives" among the states the daemon cannot read; with the journal and an exact replay the daemon can read it, and the clause narrows to a re-adoption with a gap; the architect may amend §2 at landing (evidence: `work-state.ts`'s `adopted` constructor against the fold).
- Request ids (D26): an adopted writer's `ControlClient` names its requests `${launchId}-${fence}-${n}` (the first writer keeps `${launchId}-${n}`), so a late response or cancellation of the old manager's request can never match a new one; a `control_response` or `control_cancel_request` naming a request this client never sent is logged and dropped. Every reader that takes a launch from a request id's prefix reads both forms.
- The handover is drain-then-exit, deferred while the drain does not settle (D9): `host.handover` on a welcomed link, or `exit {when: 'idle'}` from a client whose hello listed `host.holder` on a *refused* link (another wire major, where no command can be sent; `socket-server.ts` tells a refused link's `exit` apart), arms the host to exit as soon as no session holds MAWS-owned work in flight (`toolServer.inFlight` of tools other than `ask`, the dataset refreshes and captures in flight; asks and permission requests do not count: they wait on a human and are carried by re-raise and redelivery). On a welcomed link `exit {when: 'idle'}` keeps E10's meaning whatever the hello listed, since `mawsd`'s park clock sends it to a host with sessions live and parks the host (D33). The host stops admitting launches at once and keeps answering tool calls that arrive; at the first moment the count is zero (checked at every tool-server change; at once if it already is) it detaches every hosted row and runs the exit order, whose shutdown step has nothing left to stop, exit 0, `live.json` cleared as at any clean exit (the roster names the hosted rows; the ledger serves a pre-M2 predecessor's rows alone). A row's detach: the writer's in-flight writes awaited (`OutboundWriter.whenIdle`, bounded by `EOF_WRITE_WAIT_MS`), the held frames processed, the final ack and the sidecar's final write, the `host_detach` row, the journal closed, the host connection closed without `release`. `host.handover` answers `{state: 'detaching'}` when the drain is already settled and the exit follows the answer, else `{state: 'deferred', inFlight}` at once and the exit follows later; a `graceMs` names how long the caller is willing to wait before being answered `deferred` (default 10 s), never how long a tool call may run. `exit {when: 'now'}` from any client detaches at once without a drain, since it is the crash-class path (a caller that wants the drain uses `host.handover`). `host.stopAll` and `engine.shutdown`'s quit-with-stop keep today's ladder for every row.

### Interfaces and Dependencies

#### A. The session host protocol (M1; the engine host's client in M2)

Over the host's Unix socket, newline-delimited JSON, one object per line, plus two byte records. The first line the client writes is `auth`; a wrong or missing token within 2 s closes the connection with nothing written. Every object has `t`. Unknown fields are ignored and unknown `t`s answered `{"t":"error","message":"unknown t"}`, so the protocol grows additively within its major (`hello.protocol` 1); a client refuses to adopt a host of another major and leaves it running.

Client → host:

    {"t":"auth","token":"<64 hex>"}
    {"t":"attach","role":"writer"|"observer","fence":<uint64>}                              writer: fence must exceed the host's; the previous writer is told `fenced` once its in-flight stdin record, if any, has been applied
    {"t":"launch","appSessionId","engineSessionId","argv":["<bin>",…],"cwd","env":{…}}     writer, once, before commit; the host records the ids in its roster and keeps env in memory only
    {"t":"commit"}                                                                            writer; the host forks; never twice (a second commit is `error`)
    {"t":"read","fromSeq":<uint64>}                                                           replay from max(fromSeq, firstSeq), then live records on this connection
    {"t":"ack","seq":<uint64>}                                                                writer: the ring drops every record at or below seq (the client sends only a contiguous frontier, §C)
    {"t":"stdin","offset":<uint64>,"len":<n>}\n<n bytes>                                      writer: applied iff offset == stdinApplied; whole or not at all
    {"t":"end"}                                                                               writer: closes the child's stdin after every queued record is applied
    {"t":"signal","name":"SIGTERM"|"SIGINT"|"SIGKILL","group":<bool>}                         writer: to the child, or its process group
    {"t":"release"}                                                                           writer, after the child's exit: the host removes its files and exits now
    {"t":"hb"}                                                                                optional; the host keeps no liveness clock on its clients

Host → client:

    {"t":"hello","protocol":1,"holderId","pid","procStart","appSessionId","engineSessionId","state":"ready"|"committed"|"running"|"exited",
     "child":{"pid","procStart"}|null,"fence":<uint64>,"writer":<bool>,"stdinApplied":<uint64>,"stdinQueued":<bytes>,"ring":{"firstSeq","lastSeq","bytes"},"exit":{"code","signal","at"}|null}
    {"t":"spawned","pid","procStart"} | {"t":"spawnFailed","message"}                       the answer to commit

Input semantics (D30). One goroutine writes the child's stdin, from a queue the host fills in arrival order; a record is `applied` only once every byte of it reached the pipe, and `stdinApplied` advances by whole records; the queue is bounded by `STDIN_QUEUE_CAP` 16 MiB, past which a `stdin` is answered `busy {queued}` and not queued (the client retries after the next `applied`). A record cannot be recalled once queued. A `stdin` whose `offset` is behind `stdinApplied` by exactly one queued or applied record is `duplicate`; one that is ahead is `gap`; neither is queued. A writer superseded while its record is queued or in the pipe keeps it: the host applies the queue it already accepted, then fences the old connection and answers the new writer's `attached` with the `stdinApplied` that counts it, so a successor's rebase never sees an offset move under it. The pipe closing under a record is `stdinClosed {partial}` to the writer; the record counts as applied for the offset, and the client ends the session as it ends a `stalled_write` today.

Constants, in `native/session-host/host/limits.go` and mirrored in `src/engine-host/holder/protocol.ts`: `LINE_CAP` 64 MiB, `RING_CAP` 8 MiB, `STDIN_QUEUE_CAP` 16 MiB, `LINGER` 10 min, `HOST_EXIT_GRACE` 5 s, `AUTH_WINDOW` 2 s, `FRAME_CAP` 64 MiB + 256 bytes for the byte records.

## Owner questions

- **Q1. A lane B session on which no observer was ever seen.** The sminos plugin may be absent from a machine, or a session's bridge may never have connected. May such a session be released on verified-empty alone, on both roles? **Recommended: yes.** Without the bridge no peer message can reach the session, and verified empty rules out a cron fire and a task notification; what remains is an engine-started turn in the milliseconds between the final check and the signal, and that turn's trigger is in the engine's own transcript. The alternative, never releasing such a session, keeps every unbridged session on a server for good, which is the cost F2 exists to give back. The question is the never-seen case alone: an observer that was seen and went silent or away is the holder design's unhealthy gate, and that session is never released until it is heard again (D29). The document plans the yes; a no changes one branch in `reap.ts` and the status's `gate: 'absent'` wording.

  Go wins on the build: `GOOS`/`GOARCH` cross-compiles the three targets from any machine with the stock toolchain and nothing else, the Linux builds static ELF (shown: `statically linked, stripped`), one `go build` per target, reproducible byte for byte across build hosts with `-trimpath`, so the committed-prebuild pipeline of `native/peer-auth` runs from one machine and CI verifies the bytes on another; its footprint (3 MiB idle, 16 MiB with 4.8 MB unacknowledged) is within 2 MiB of Rust's at idle and far under a Node host's 13 MiB footprint and 44 MiB RSS; goroutines fit a reader per pipe and a handler per connection; and it is the holder design's own lean and claude-ssh's choice, whose transport the holder borrows. Rejected: Rust, the smallest and the toolchain this MacBook has: a Linux build from the Mac needs a cross target and a linker beyond the stock toolchain (`rustc --target aarch64-unknown-linux-musl`: "can't find crate for `std`"; `rustup target add` plus a zig or musl linker makes it one machine, so the gap is a setup, not a wall), and its cross builds are not reproducible across hosts without more care than Go's; the decision rests on the reproducible cross build, the footprint table and the precedent, not on the setup. Node under the Electron binary (the engine host's and pty host's shape, zero new toolchain), because 13 MiB of footprint and 44 MiB of RSS per session, 1.9 s cold, is the cost the design built the host to avoid, and a host launched from `app.asar` inherits Decision Log 161's swap hazard; Bun, the same class plus a third runtime. The ring's cap (8 MiB, D6) bounds the loaded case for either native language. The committed prebuilds cost the repository about 7 MB per rebuild (three static binaries); the host is small and changes rarely, and the app build and the pack must not depend on a fetch, so this is accepted in writing; a tracker row follows if rebuilds become frequent.
- **D4. The host protocol carries output and input as length-prefixed byte records beside NDJSON control lines.** A 64 MiB line is the engine host's own cap; JSON-escaping it on the relay would double its memory and time on both ends. Rejected: NDJSON for everything (simple, but the hot path pays), and a binary codec throughout (the engine's PTY-host frames: a second codec with no reader in the repository).
- **D5. One `claude` process per session host, named by the launch id.** The holder design's four identifiers map onto what MAWS already names: `holderId` is the launch id (`mintLaunchId`, one per process, the journal's and the request ids' prefix); `processEpoch` is constant (a host never respawns: a resume after a release is a new launch, a new host); `engineSessionId` is the lineage `durable-crons.ts` already keeps; `bindingGeneration` is the writer fence. Rejected: a host that respawns `claude` (a second process state machine for a case nothing asks for).
- **D6. The ring holds what the writer has not acknowledged, up to 8 MiB; the manager acknowledges a contiguous frontier after its synchronous journal writes, with no fsync.** The journal is MAWS's durable record of every frame, which claude-ssh lacks, so holding acknowledged output in the host is waste: an idle session's host then carries the binary alone. The acknowledgement is the frontier below which every record is journaled, never the highest record seen: `session.ts` holds stdout records behind an in-flight write while stderr is journaled on its own loop, so a cumulative ack of the highest sequence would let the host drop a held record (R1 finding 1). 8 MiB covers about 10 s at 800 KB/s, more than the handover's gap (sub-second) or a crash's (the restart ladder's first step, 0.5 s, plus adoption); past it the gap is exact and noticed. The ack after the page-cache write is enough: a process crash keeps the page cache, and a machine crash ends everything. Rejected: claude-ssh's unconditional 16 MiB (its only copy of recent output); an fsync per line (the journal does none today); the highest sequence as the ack (loses a held record).
- **D7. No transient scope on Linux; a session host's own SIGTERM takes its child down.** O2's `KillMode=process` and the user manager already keep every child of the unit across a `mawsd` restart and a logout (O2 M8), so the session host inherits the engine host's protection with nothing added; M4's VM run proves it. A host told to exit by signal sends SIGTERM to its child's group first, because an engine with no stdio runs on unreachable (E10 M0 Q1) and the sweep would have to find it. Rejected: `systemd-run --user --scope` per host (O2 rejected it for the children; it buys nothing under `KillMode=process`); a host that exits leaving its child (the sweep's case, left for SIGKILL alone).
- **D8. No direct spawn after M2.** A launch whose session host fails to start is refused `host_unavailable` with a notice naming the host's log, never spawned directly: two shapes of row in one engine host would make adoption, the sweep and the exit order each two-way. Rejected: a fallback to today's spawn.
- **D9. The handover is a drain, then an exit that detaches; a drain that does not settle defers the handover, never forces it.** Holder design §3.3: a planned restart drains with a timeout, and the timeout alone never authorizes an interruption. So the engine host exits for a handover only at a moment no session holds MAWS-owned work in flight (asks excepted: they wait on a human and are carried by re-raise), and until then it keeps serving and tells its client `deferred`; the socket host's own 10 s shutdown bound is never reached, since the exit order starts only after the detach. `host.handover` is the command on a welcomed link (it has an answer, which the deferral needs); `exit {when: 'idle'}` from an adopting client is the same request on a refused link alone (D33); `exit {when: 'now'}` detaches at once with no drain, the crash-class path. Rejected: a `handover` value for `exit`'s `when` (a frozen protocol-2 enum, a major); a drain with a deadline after which the exit proceeds and orphans answer "unknown" (the design's rule for a sudden restart, not a planned one; R1 finding 6).
- **D10. Adoption runs before the sweep, and the sweep kills only what no live host holds.** A row of `live.json` naming a holder with a live host is that host's; a roster entry whose host is dead and whose child lives is swept by the child's recorded identity; a row with no holder is a pre-M2 process, swept as today. Rejected: a sweep that trusts `live.json` alone (the roster is written by the host and survives the manager's crash between a launch and the ledger's rewrite).
- **D11. Across a wire major, a capable engine host hands over on the client's `exit {when: 'idle'}` when the client's hello listed `host.holder`.** The refusal line is frozen and carries no capability, so the client cannot tell a capable refused host from an older one and keeps writing `exit {when: 'idle'}`; the host can tell an adopting client from its hello, and an adopting client's "when idle" is served as a handover (the drain, then the exit), since the sessions survive it. A client that listed no `host.holder` gets E10's wait: it would sweep what it cannot adopt. So the client's hellos (`PEER_CAPABILITIES.app` and `daemonToEngineHost`) list `host.holder` from M3 as well as the host's welcome. **[parent-impact]** P5 §2's "an upgrade across an OX1 major ends its lane B sessions" no longer holds after O16 for an engine host at or after M3; the architect may amend it at landing. Rejected: reading the roster directory as the capability signal on the client side (true of the host's state, but a host of a build before M3 never wrote one, and a client's guess should not decide an exit).
- **D12. The owed interrupt is a state-file mark.** Set before the interrupt's control request is written, cleared at its response or failed write, sent first by an adopter; the queue's `uncertain` already covers submissions. Rejected: re-sending every unanswered host-issued request (a `set_permission_mode` applied twice is harmless but a second `interrupt` after a completed one cuts the next turn).
- **D13. The gate is the engine host's.** See Surprises. Rejected: the session host serving `MAWS_HOLDER_SOCKET` (the final check's inputs would cross a socket; a separate token-free socket per host for the bridge, since the manager's token never reaches `claude`'s environment).
- **D14. OX10 gains `origin: 'peer'`, `delivery` and `hello.childPid`, and the settlement is the observer's report.** The architect asked O16 to define the settlement P5 Decision Log 19 named; the bridge reads the delivery's id from the inbox row it starts a turn for, and sminos settles on `proceed`; the bridge child's pid registers it as infrastructure for the descendant veto. Rejected: a settlement message from the engine host to sminos (the engine host knows no delivery ids).
- **D15. An `idle` reap is `end_session` then one SIGTERM on its own path, never the ladder; `budget` keeps the ladder.** The ladder (`session-ladder.ts`) is memoised, marks the process exiting and closes stdin before SIGTERM, so a session whose engine ignored the signal could not be used again (R1 findings 10 and S4); the reap therefore sends `end_session` with the ladder's grace (the SDK's own graceful end, what today's `idle` release sends first), then one SIGTERM through the host, waits `REAP_TERM_MS`, and otherwise changes nothing about the process, so the session goes on and an explicit stop later runs the ladder whole. Holder design §3.2 step 5 for the idle release; charter §4.4's budget release is the memory's and not O16's to soften. Rejected: the ladder with `escalate: false` (irreversible); no SIGKILL for either (a budget release that fails leaves the machine over its budget with nothing to do).
- **D16. `WIRE_MINOR` 13 at M3, re-read at landing and set one past master's.** The sibling children each take the next free number; the manifest is regenerated from master's entries at each merge.
- **D17. The descendant veto is the design's rule, read synchronously at the step: every process under `claude` is work but the registered infrastructure, and an unreadable tree vetoes.** Registration is by identity, not by heuristic: the bridge child by the pid its observer's `hello` names, and the launch's stdio MCP servers by command line against the launch's effective configuration (`get_settings` once per launch, and the launch's own `--mcp-config`); M0 shows what a resting tree holds, and a process neither registration names is evidence for extending them. One `ps` per release attempt (about 10 ms), a rare event, rather than a 10 s-stale sample at the moment of truth. Rejected (R1 finding 8): descendants outside `claude`'s process group (misses same-group work), and descendants started after the last turn (misses a background job started during it); a zero for an unreadable tree.
- **D18. The session host's cost is read by its own measured case with its own bound, outside acceptance 14's two-process bound.** P5 defines the bound as `mawsd` plus the engine host; a session host exists only with a live session, which the idle scene's replay never spawns. Rejected: folding it into the idle bound (which would change the bound's definition P5 fixed).
- **D19. The gate's fixture is the conformance artifact for O12 M4.** A recorded exchange both repositories replay, the pattern P5 §2 set for the org-project rule. Rejected: prose alone.
- **D20. `--await-initialize` is added only if M0 finds the pinned engine takes it and it holds a resurrected cron's fire.** Behind the binary probe's declaration, as `--system-prompt-snapshot` is (charter D-1: an undeclared flag never reaches a binary that does not know it).
- **D21. The crash toast keeps its id and changes its copy by the adopted count.** The renderer's one notice path (`notices.ts` `toast()`); no new surface.
- **D22. The spike's engine is both the fixture pin and the VM's installed engine.** The fixtures must replay on `test:probes` (the pin); the answers must hold for the engine `mawsd` runs; a difference is a finding, and the newer engine's answer rules the build.
- **D23. The checkpoint is a sidecar beside the journal, and the journal's rows are unchanged.** `JournalRowSchema` is strict, so a top-level field on a row would make every hosted launch's journal unreadable to a build before O16 after a downgrade (`JournalReader`, `session-stream.ts`, `prompt-history.ts`; R1 finding 11). The sidecar carries the contiguous frontier and the records journaled above it, coalesced with the acks and written after the rows it covers; a record journaled after the sidecar's last write is told from a new one at adoption by an equal row in the fold's tail (the same direction, the same serialized frame; the engine's lines carry no whitespace, so `JSON.stringify(JSON.parse(line))` is the row's frame). The pane's reseed from the engine's transcript after a gap stays unbuilt (a tracker row): a gap needs more than `RING_CAP` of unacknowledged output during a restart. Rejected: `hseq` on every row (the downgrade reads nothing); a periodic `meta` checkpoint row (an unknown meta event to an old normaliser, and the same duplicate window); an fsync-backed checkpoint before each stdin write (claude-ssh's barrier; the journal is already synchronous).
- **D24. An adopter restores the readers' state by folding the launch's journal before it consumes anything, and holds dispatch until the ring's replay is classified.** The normaliser, the tracker, the broker, bash mode and the side-question log keep stream state (the open turn, the lanes, the block starts, the pending requests) that a new `EngineSession` starts without; a delta that follows a handover between a block's start and its next delta would be unattributed (R1 finding 2). The fold is side-effect free (a `restore` entry per reader) over every file of the launch, so a request outstanding across a rotation is found (R1 finding 4), and the recovery barrier means a replayed `mcp_message` is classified, never run. Its cost, seconds for a day's journal, is paid once per adoption. Rejected: a persisted normaliser snapshot (new state with its own staleness); the journal's tail alone (misses a request across a rotation).
- **D25. Journal pruning runs after adoption, keeping every roster entry's launch.** `scheduleJournalPruning` runs at register today with an empty table, so the long-running session O16 exists for would lose its journal at its first restart past the retention age (R1 finding 5).
- **D26. An adopted writer's request ids carry the fence.** `ControlClient` counts from zero per instance, so a successor would reuse `${launchId}-${n}` while the engine still answers the predecessor's (R1 finding 3); `${launchId}-${fence}-${n}` is unique by construction and tells a journal reader which writer asked. Rejected: a counter resumed from the journal (an id used but not journaled before a crash collides).
- **D27. The gate has a server of its own.** `@shared/host/socket-server` speaks the token-authenticated host protocol in both its modes (R1 finding 12); the gate's clients hold no token and speak four frames. `node:net` with `@shared/host/private-listen`'s checks is the whole of it.
- **D28. The scenes drive the stub engine as a real process.** `replaySpec` launches spawn nothing, so nothing of theirs survives a manager's exit (R1 finding 13); the stub under `MAWS_E2E_ENGINE_BIN` is a real child the host holds, and two fixture directives let it parent a `sleep` and count its stdin. The two-capable-build crossing waits for the first `WIRE_MINOR` bump after O16's landing, when the merge-base peer lists `host.holder`.

An observer seen and then silent or gone blocks the release; only one never seen is absent.** Holder design §3.2 step 1 and §8 item 6: an unhealthy or disconnected gate holder leaves the work state unknown and nothing is armed or signalled; Q1 decides the never-seen case alone (R1 findings 9 and S7). Rejected: dropping a silent observer to the absent rule; treating a clean close as absent (a bridge that turned itself off is the gate the design says not to trust).
- **D30. Stdin is applied whole or not at all by one writer goroutine from a bounded queue, a queued record is never recalled, and a superseded writer's queue is applied before the fence turns.** `EngineTransport.write`'s abort and partial-write contract (`transport.ts`) rests on the host owning the pipe; the host keeps the offset exact under supersession, and the client's abort after a record left is a rejection whose `out` row is journaled when `applied` arrives (R1 finding 7). Rejected: an abort that recalls a queued record (a record the engine may already be reading).
- **D31. The stub engine is a process M2 builds.** The repository's `writeReplayEngine` writes a `--version`-only script that refuses a real invocation, and the hosted e2e groups run the in-process replay transport, which spawns nothing (S3); a holder scene needs a child the host holds, so M2 re-hosts the replay transport's fixture rules as a stdio process with two directives. Rejected: moving acceptance 1's Mac leg to the VM alone (the gate's Macs would prove nothing of the handover).
- **D32. An adopted row's work state is seeded from the durable records.** `work-state.ts`'s `adopted` constructor leaves tasks and crons unknown until a snapshot or Stop, and an idle session gets no Stop until a turn runs, so every upgrade would hold every idle session for good (S2), the cost F2 exists to remove; the state file's cron record (P5 Decision Log 49) and the journal's last `background_tasks_changed` with an exact replay are the daemon reading the state, and a gap keeps the unknown. **[parent-impact]** on P5 §2's list of unreadable states (M3). Rejected: the unknown as it stands (a permanent hold); the Stop's `background_tasks` alone (needs a turn).

The handover-on-idle is the refused link's alone, where no command can be sent. Rejected: the first draft's "idle means now for an adopting client".
