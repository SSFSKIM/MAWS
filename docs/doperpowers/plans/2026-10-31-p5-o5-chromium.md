## Purpose

After O5, a session on a machine with no MAWS app open keeps the agent capabilities that need Chromium. `artifact_screenshot` and `artifact_export` run on the session's machine through a render service the machine daemon owns and starts on demand, so a session on the mini or on a Linux VM with no app, and a session on the MacBook after the app quit, still gets its pictures and files; the library's Export from any app, remote included, renders on the artifact's machine with the machine's fonts and the machine's copy of the artifact. Artifact pages are served by the daemon over one HTTP endpoint on a unix socket, which the app, the render service and (through O7) a remote app all read, so there is one source of an artifact's bytes. Browser control follows the session's machine: the daemon owns a stable per-session cua socket, so a session launched with no app, or one whose app quit and relaunched, gets a browser the moment a tab engine is attached, and is told cleanly, by capability, when none is. How to see it working is the acceptance below: an export written on a machine whose app is closed, a screenshot taken on a VM with no app, a browser refused and then offered on one socket.

Terms used throughout: the **daemon shape** is MAWS with `mawsd` running the machine's services (the profile setting `daemon`; the **embedded shape** is main composing them in-process, kept until O15). The **render host** is the process this document adds: the app's own binary run as a windowless Electron process by `mawsd`, holding the capture and export code main holds today, alive only while there is something to render. The **render seam** is `mawsd`'s side of it: what starts the render host, hands it work, answers the engine host and ends the host when quiet. The **artifact endpoint** is the daemon's HTTP server over `artifacts.sock` serving `maws-artifact:` URLs' bytes. The **scheme proxy** is the `protocol.handle` in an Electron process (the app, the render host) that answers `maws-artifact:` loads by asking the endpoint. A **tab engine** is a Chromium that holds the agent's browser tabs and serves cua's primitives: today the app's in-app browser; after U3, possibly the render host too. The **render runtime** is the Electron build a machine renders with: the app bundle's binary on a Mac, the pinned Electron's Linux build installed beside `mawsd`'s releases on Linux.

## Acceptance

O5 closes when these hold, each checked as written and recorded in Outcomes with its evidence.

1. **A screenshot and an export on a machine with no app** (P5 acceptance 10). On a Linux VM running `mawsd`'s unit with no app ever attached, a lane B session's `artifact_screenshot` of an `html` artifact answers an image block, and its `artifact_export` of a `document` as `pdf` answers a file under `<profile>/artifacts/<id>/exports/`, both through the machine's render host; `mawsd.log` shows the render host started for the first request and exited after its quiet period; `mawsd status` between the two shows no render host running.
2. **The app's quit changes nothing.** On a Mac on the daemon shape, with an `html` artifact in a session: quit the app, keep the session; a `library` Export asked by a second client over `machine.sock` (the e2e's, in the test; `mawsd`'s command line in a sitting) writes the PDF; relaunch the app: the library row shows the export, and `artifact_screenshot` in that session answers as before, rendered by the render host, never by the app (the app's main has no capture window on the daemon shape).
3. **Browser control is offered or refused by capability, never failed mid-call** (acceptance 10's second clause). A session launched with no app attached has a cua socket path in its `CUA_BROWSER_BACKENDS` that `mawsd` owns; while no tab engine is attached nothing listens there and `session.capabilities` reads `browser: {available: false, reason: 'no browser is attached on <machine>'}`; when the app attaches, the socket listens within 1 s, cua's host (which retries every 5 s) connects, and the agent's next browser call works; when the app quits mid-session the socket stops listening, the capability reads unavailable again, and the next browser call answers "no browser" from cua's host, not a hang. The app that quit and relaunched while the engine lives gets the agent's browser back on the same socket (D-16). An engine of one session cannot reach another session's tab engine directly: the app's socket for a session admits that session's engine's descendants and the daemon's relay by its exact identity, nothing else.
4. **The artifact endpoint is the one source** (P5 §5, §6; acceptance 15's local boundary). On the daemon shape the app's `maws-artifact:` loads and the render host's both come from `mawsd`'s `artifacts.sock`: a 0600 socket in the 0700 daemon directory, owner-checked, refusing symlinks, with no loopback port; a `Range` request answers 206; every answer carries the `sandbox allow-scripts` policy, `nosniff`, `no-store` and the CORS header the scheme carries today; a URL that is not exactly the scheme's shape is 404. `e2e:artifacts`'s two scheme cases pass on the daemon shape unchanged.
5. **Export on another machine, the machine side** (P5 acceptance 4's carve-out). In the two-profile scene (`e2e:machines`), with profile B running as a daemon alone, `artifacts.export` dispatched to B from A's side (A's router forwarding the machine-owned command with B's target to A's connection manager, or the scene's bare `machine.sock` client to B) is rendered by B's render host (B's `mawsd.log` shows its start), the file is under B's profile, and B's `library.list` names it. A's library row for B's artifact, and the live check from the MacBook against the mini, are O7 M5's, which consumes this and the capability entries (the renderer's export call names no machine today, `src/renderer/src/artifacts/host.ts`, and artifacts across machines are O7's).
6. **One or two Electron processes decided by P5 §2's criterion** (U4). The verdict and both halves' numbers are in `spikes/u4-render-service/FINDINGS.md` and P5's Decision Log: whether a windowless Electron runs reliably under a LaunchAgent and on a devcloud VM, headless Chromium's fidelity for export on Linux, and the idle memory each shape would add to `mawsd` against acceptance 14; the first run of the app binary itself (not the repository's Electron) as a render host under a unit is `e2e:daemon-unit`'s case (M6), the verdict's second half.
7. **The agent's browser for a remote session follows U3** (P5 §13). U3's findings are recorded with the promote-or-cut verdict; if promoted, M8 is re-planned into an executable milestone and reviewed before it is built; if cut, this document says what O5 ships (the relay and the refusal) and what the new child carries.
8. **Nothing runs at `mawsd`'s start or idle, and nothing stays after use.** `e2e:daemon-idle` on the mini reads within the 99,145 KiB bound with O5 landed, by the two-of-three rule, and so does the new warm-to-idle case `e2e:daemon-idle-render` (a render completed through the seam and an artifact fetched through the endpoint, then the quiet period, then the window), whose process set at the window's start is `mawsd` and the engine host alone; `e2e:local-latency-daemon` stays within OX7; `runPathOf(out/main/mawsd.js)` holds none of the render seam's chunk, the endpoint's handler chunk or any `electron` import (the bundle guard).
9. **Capabilities light up.** `session.capabilities` for a lane B session reports `artifact_screenshot`, `artifact_export` and `browser` with `{available, reason?}`, changes when the render runtime or a tab engine comes or goes, says why on a machine without the runtime or a sandbox and on a session whose engine host predates the render service, and O7 M5 can draw from it.
10. **Both update directions keep working** (OX1). `e2e:cross-build`'s two directions: a pre-O5 app against a post-O5 `mawsd` captures and exports through the seam and hears no capture event; a post-O5 app against a pre-O5 `mawsd` (whose welcome lists no `machine.render`) keeps today's handler and services in main, so an artifact page loads and `artifact_screenshot` answers from the app.

### Constraints (bind every milestone)

- **P5's binding content, cited by id.** The render service is the daemon's (P5 §2, §6); the attached client never renders on the daemon shape once the daemon can (§6: "the attached client is the wrong home"); the artifact scheme is an HTTP endpoint on the daemon that the local app's `protocol.handle` proxies to (§6); the daemon owns the per-session cua socket, checked against the engine pid it holds, relayed to whichever tab engine is attached (§6, survey §7.5); `show_pane` and notifications stay client-bound (§6; RL §3.1). The endpoint is reachable only through a unix socket or a per-boot token, never an open loopback port (acceptance 15). **Decisions.**
- Unix socket, not a per-boot token on loopback: a page load cannot add a header, a token in a URL leaks through referrers and logs, and `private-listen.ts` already gives the owner check and the symlink refusal. The proxy is Node's `http.request({socketPath})` inside the Electron process, so the scheme's standard, secure, streamed origin per artifact (`STORE_SCHEME_PRIVILEGES`) is unchanged for the page; Chromium never sees the socket.
- The endpoint reads the file through the same opened descriptor the check used (`scheme-handler.ts`'s rule) and never builds a path from the URL; the HTTP adapter maps `Range` and `HEAD` one-to-one and carries every header the handler sets. `Content-Length` and `Content-Range` must survive the proxy byte-exact: the e2e's media-seek case is the proof.
- The endpoint's handler loads at the first accepted connection (a deferred `import` of `src/services/artifacts/scheme/`), never at start; a connection while the engine host is parked wakes it through `dispatch` as a remote request does (the first paint of a page after a quiet night costs the host's start: accepted, it is today's behaviour for any read).
- Resolution asks the engine host, never the spine: the endpoint works while the spine is cold, so a remote viewer's artifact page never loads the spine.
- The presenter's live embeds (`src/main/presentations/present-embeds.ts`) answer in the app and stay there: the proxy asks the embeds' responder first and the endpoint for the rest, so a presenter's page in the app is unchanged; the render host asks the endpoint alone (it presents nothing).

**Does not touch.** The render code (M3). The engine host. The renderer. Remote carriage of the endpoint (O7 M5).

- **Not listening is the refusal.** cua's host retries an unreachable backend every 5 s for the process's life (`cua/src/chrome/client-mode.mjs`, `CLIENT_RETRY_MS`) and lists a backend only after its hello, so a socket that does not listen while no tab engine is attached is already "refused by capability": `listBrowsers` finds no `maws:` browser and the browser tools say so. Rejected: accepting and answering a refusal frame, which needs a protocol addition in the cua repository (a cross-repo change like MW1–MW5) for no gain. The listener comes up within 1 s of a tab engine's attachment and goes down at its departure (the relay's departure drain ends the relayed connections, so cua's host sees `lost` and retries).
- **The peer check moves to `mawsd`, and the app admits the relay by exact identity.** `mawsd` holds an accepted socket unread until its peer runs as this uid and descends from the session's engine (the pid read from each raw `session.status` on `hosts.onRaw('engine-host')`, as the app's `engineSeen` reads it, never from the spine's view, so a browser connection on a machine with no app loads nothing), through the addon loaded from the app's Resources. The app's own socket for the session then sees `mawsd` as the peer: it admits the connection only when the peer's pid is the attached daemon's pid and its kernel start time (the addon's `process(pid).start`) equals the start the app captured for that pid when it attached (`rootOf(pid, addon)`, re-read at each reconnect); never by ancestry, since every engine on the machine descends from the daemon and `descends` would admit any session's engine at any session's socket (both reviews' P1). The welcome carries the daemon's `pid` (its `startedAt` is wall-clock text, not the kernel's start); the start comes from the addon on the app's side. On Linux the addon is absent: the socket is 0600 in a 0700 directory and the uid is the boundary (O2), one log line per socket says so.
- **Byte relay.** The daemon relays frames unparsed between the engine-side connection and the tab engine's socket, so cua's protocol never changes on either side; backpressure follows each socket's own (`pipe` both ways, the pair ended together). The daemon connects from its own process, never a child, so the exact check holds.
- **The capability's reasons** are exact strings the renderer and O7 show: `no browser is attached on <machine name>` (no tab engine), `the render service is unavailable on <machine name>: <reason>` (M4's failure reasons: the runtime absent, the sandbox unconfigured, two start failures), `the engine host on <machine name> predates the render service; it is replaced when idle` (M4's old-host case); `this build of MAWS cannot export a <kind> as <format>` stays the tool's own.
- **Session end.** The socket is removed when the session is removed, as the app's is; a session released idle keeps its socket (its next launch names the same path).

**Does not touch.** The tab engine itself (the app's browser code beyond the relay's admission). A headless tab engine (M7, M8). The remote app's view.

**Proves.** Acceptance 3 and 9. Tests pin: the listener exists only while a tab engine is attached; an accepted peer that is not a descendant of the session's engine is destroyed unread and counted; the app's socket admits the daemon's exact instance and refuses the daemon's pid with another start time and any descendant of the daemon that is not the daemon; a relayed connection's frames arrive byte-exact both ways and end together; the cua directory falls back by its own path's length; `session.capabilities` flips with the attachment and with the render seam's state, and the event follows each flip once. `e2e:browser-cua` on the daemon shape: its existing scenes through the daemon's socket; a new scene launches the session with no app attached (the app started after the engine, the harness's unit `mawsd` first), connects the fake host, sees it refused until the app attaches, then served; another quits the app mid-lease, sees cua's host lose the connection and no hang, relaunches the app over the same profile and sees the fake host connect again on the same path (D-16); a third runs two sessions and shows session A's engine-side peer (the stub engine's child) cannot connect to B's app socket directly while the daemon's relay for A can.

#### M6 — The render runtime on Linux; acceptance 10 on a VM

**At its end.** A Linux machine can hold the render runtime, the pinned Electron's Linux build, as an immutable, content-addressed install beside `mawsd`'s releases (Interfaces §J): `mawsd render install` fetches and verifies it, sets the sandbox helper where root is available, and `mawsd render status` says what is present; `devenv/setup.sh` installs it with the packages and fonts FINDINGS §1 found on a devcloud VM; the render host runs under the unit on Linux under Xvfb with Chromium's sandbox (the SUID helper set root:root 4755 at install, since Ubuntu 24.04 refuses the user-namespace sandbox), and refuses to render without one; `session.capabilities` on a Linux machine without the runtime reads the render tools unavailable with the reason. Acceptance 10 is checked on a VM made for it, and the app binary's own first run as a render host under a unit is `e2e:daemon-unit`'s (acceptance 6's second half).

**Touches.** `packaging/mawsd/electron.json` (new), `scripts/mawsd-pack.mjs` (`--render`: the zip beside the pack, checked against its SHASUMS as Node's is, so a pack can carry the runtime for an offline install), `src/mawsd/render-runtime.ts` (new: the cache, the install transaction, the status), `src/mawsd/{install,cli}.ts` (`render install|uninstall|status`; the sandbox helper's mode set during install where `sudo -n` works, recorded in the cache's manifest), `src/mawsd/render-seam.ts` (the Linux spawn, Interfaces §E; the runtime check reads the cache), `devenv/setup.sh`, `src/render-host/root.ts` (the sandbox check at start: a render host that finds no sandbox exits with a code the seam turns into the capability's reason), `e2e/daemon-unit.spec.ts` (the unit scene gains the render host on both platforms where the lane has the runtime: on the Mac lane the app binary under the LaunchAgent, on Linux the cache's Electron under Xvfb), `spikes/u4-render-service/FINDINGS.md` (§4, the acceptance run).

**Decisions.**
- **The runtime is a cache of its own, not part of a release.** Releases are immutable and content-addressed (`src/mawsd/release.ts`) and the two previous ones are kept, so an unpacked Electron inside each release would be 290 MB three times over and copied at every rebuild; nothing is added to or removed from `current`. The runtime lives at `~/.local/share/maws/mawsd/render/<electron version>-<sha256 of the zip, 12 hex>/` with a `manifest.json` (the version, the sha256, the sandbox helper's mode as set, the install time); a release names the version it needs (`packaging/mawsd/electron.json`), and the seam resolves the cache entry for `current`'s pin at each spawn, so a flip to a release pinning another version makes the seam report the runtime absent until `mawsd render install` fetches that version. An install is a transaction: download to `<cache>/.staged-<version>-<sha12>/`, verify, unpack, set the helper, then one `rename` into place; an entry is published only once its helper is configured, so without privilege the install keeps the verified, unpacked staging directory, reports `sandbox missing: run mawsd render install with sudo`, and a privileged retry completes it (the chown and chmod, then the rename) rather than finding an entry and doing nothing; a second installer that finds the entry present does nothing, and one that finds a staging directory verifies and completes it; an entry nothing pins and no render host runs from (`/proc/<pid>/exe` under it, as `release.ts` reads a running process's release) is pruned by `mawsd render uninstall` or by a later install; `uninstall` refuses while a render host runs from the entry (the seam's state, read through `daemon.status.render`) and otherwise removes it and tells the running daemon, which reports the runtime absent at its next check. Root is used for one thing: `chown root:root && chmod 4755` of the verified `chrome-sandbox` inside the cache entry, never anything under `current`.
- **The runtime is optional per machine, installed by default on devcloud VMs** (owner question Q1, planned on its recommendation): a 123 MB download and the packages buy acceptance 10 on every VM; a machine that renders nothing runs `mawsd render uninstall`.
- **The display.** Electron's `BrowserWindow` needs a display connection for GTK on Linux whatever `--headless` says (FINDINGS §1.2), so the render host runs under `xvfb-run` (the `xvfb` package, 15 MiB RSS for the server), one Xvfb per render host's life, started by the seam's command line (Interfaces §E) and ended with it (the seam spawns the line in its own process group and kills the group at the host's end, since a SIGTERM to `xvfb-run`'s shell does not reliably reach Electron); `--headless` keeps Chromium's compositing in software (without it, or with `--disable-gpu` alone, a whole-page capture fails with `UnknownVizError`; SwiftShader through `--use-gl=angle --use-angle=swiftshader` is the slower alternate), and `--hide-scrollbars` keeps the classic scrollbar out of captures. Rejected: a Wayland compositor (`weston --backend=headless`), heavier and no better; a CDP-driven headless Chromium, which would need a second render implementation.
- **The pack's entry under Electron.** The render host runs `<release>/out/main/index.js` (the dispatcher) under the cache's Electron, not under the pack's Node; the dispatcher's shared bootstrap requires none of the hosts' native modules, so the pack's `node-pty`, built for the pinned Node's ABI, never loads in it. M6's first proof runs that line by hand on the VM before the seam is wired to it.
- **Fonts.** The pack installs no fonts; devenv installs `fonts-noto-core`, `fonts-noto-cjk` and `fonts-noto-color-emoji` beside the image's `fonts-dejavu-core`, so that system-font text, CJK and emoji render as FINDINGS §1.4 shows (a bare VM has DejaVu alone and would draw CJK and emoji as tofu); the render host's capability carries no font claim. A design system's own faces reach a render as `data:` URLs, as the exporters inline them today (the store frame policy's `font-src data: blob:` admits no scheme load of a font).
- **The sandbox is required.** `--no-sandbox` is never passed (owner question Q2, planned on its recommendation): artifact HTML is model-authored and runs scripts; a renderer with no OS sandbox would reach the uid. The helper the zip ships aborts Electron on Ubuntu 24.04 (`apparmor_restrict_unprivileged_userns` is 1, so the user-namespace sandbox is refused and the SUID helper is not configured); `chown root:root && chmod 4755 chrome-sandbox` at install makes it work under the shell and under the unit (FINDINGS §1.3). Where the helper cannot be set (no root at install) the render tools are unavailable on that machine with the reason `Chromium's sandbox is not configured on <machine>: run mawsd render install with sudo`.
- **The acceptance run.** A VM made with `devcloud vm up --label o5accept --project SSFSKIM/MAWS@<branch> --ttl 6h`, its devenv installing the runtime; a lane B session started over `machine.sock` with the engine the scene provides (O10's acceptance-2 run's `vm/lane-b.mjs` is the template) and a scripted engine that issues an `mcp_message` for `artifact_screenshot` and one for `artifact_export` against the `maws` server, taken from `spikes/protocol-probe/fixtures/` or recorded for this run; the live check with a real `claude` on a credentialed machine is the owner's (Q3), run on `dc-acceptance-7f80` once its inference route is set, and recorded in Outcomes when it is.

**Does not touch.** The macOS spawn (M4). The app. The hub.

**Proves.** Acceptance 1, 6's second half and 8's Linux half. Tests pin: an install is a transaction (a staging directory left by a killed install is verified and completed or cleaned; two installers at once leave one entry; an install without privilege publishes no entry and says so, and a privileged retry completes it so that `runtime()` reads available); the pack with `--render` carries the zip and an install from it copies rather than downloads; `uninstall` refuses while a host runs from the entry; the seam's Linux command line and its process-group kill; a render host started without a sandbox exits with the reason and the seam reports it; `mawsd render status` on a machine without the runtime. The VM run's transcript (the two tool answers, `mawsd.log`'s start and quiet-exit lines, `mawsd status` between them) goes into FINDINGS §4.

#### B. The render seam (`src/mawsd/render-seam.ts`)

    export type RenderState = 'off' | 'starting' | 'ready' | 'ending' | 'unavailable';
    export interface RenderSeamOptions {
      spawn(): RenderChild;                                   // the platform's command line (§E); a test brings a fake
      post(request: RenderRequest): boolean;                  // the front: to the ready render.client; false with none
      answerEngine(name: 'maws.artifact.captured' | 'maws.artifact.exported', input: unknown): Promise<unknown>;
      quietMs(): number;                                      // MAWS_RENDER_QUIET_MS, default 120_000
      startDeadlineMs: { capture: number; export: number };   // 40_000 and 55_000: inside the bridges' 45 s and 60 s
      runtime(): { available: true } | { available: false; reason: string }; // §J on Linux (the cache entry for current's pin, its sandbox); always available on a Mac with the app binary
      engineHostRenders(): boolean;                           // the engine host's welcome lists host.render (§A); false for an older host kept across an update
      onState(state: RenderState, detail: string | null): void; // daemon.status.render, session.capabilitiesChanged
      log(line: string): void;
    }
    export interface RenderSeam {
      state(): RenderState;
      capture(request: MawsArtifactCapture): void;            // from the engine host's raw event; answered through answerEngine
      export(request: MawsArtifactExport): void;              // likewise
      exportForLibrary(input: CommandInput<'artifacts.export'>): Promise<CommandOutput<'artifacts.export'>>; // artifacts.export's handler, and §G (the Notion dialect rides the input)
      clientReady(): void; clientGone(): void; answer(input: { id: string; answer: unknown }): void; // from the front
      capabilities(): { artifact_screenshot: SessionCapability; artifact_export: SessionCapability }; // §I's render entries, from runtime() and engineHostRenders()
      stop(): Promise<void>;                                  // the exit order, after the endpoint's stop and before spine.stop() (which ends the engine-host link): admission closed, the table answered ok: false over the live link, render.exit, then SIGTERM after 5 s (Linux: the process group, Xvfb included)
    }

States: `off` → `starting` at the first request (the spawn, the hello awaited); `starting` → `ready` at the client's ready, → `unavailable` at a spawn failure or a second start failure within a minute (every request answered with the reason; a request after a minute tries again); `ready` → `ending` after `quietMs()` with no request in flight, → `off` at the child's exit; any state → `off` at an unexpected exit, with in-flight requests answered `ok: false` and the next request starting again. A request while `runtime()` is unavailable is answered with its reason at once and spawns nothing. The seam never waits past the bridge's deadline: a request still unanswered at its start deadline is answered with the start's reason and dropped from the table.
