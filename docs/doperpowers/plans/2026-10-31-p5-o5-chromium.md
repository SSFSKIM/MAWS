## Purpose

After O5, a session on a machine with no MAWS app open keeps the agent capabilities that need Chromium. `artifact_screenshot` and `artifact_export` run on the session's machine through a render service the machine daemon owns and starts on demand, so a session on the mini or on a Linux VM with no app, and a session on the MacBook after the app quit, still gets its pictures and files; the library's Export from any app, remote included, renders on the artifact's machine with the machine's fonts and the machine's copy of the artifact. Artifact pages are served by the daemon over one HTTP endpoint on a unix socket, which the app, the render service and (through O7) a remote app all read, so there is one source of an artifact's bytes. Browser control follows the session's machine: the daemon owns a stable per-session cua socket, so a session launched with no app, or one whose app quit and relaunched, gets a browser the moment a tab engine is attached, and is told cleanly, by capability, when none is. How to see it working is the acceptance below: an export written on a machine whose app is closed, a screenshot taken on a VM with no app, a browser refused and then offered on one socket.

Terms used throughout: the **daemon shape** is MAWS with `mawsd` running the machine's services (the profile setting `daemon`; the **embedded shape** is main composing them in-process, kept until O15). The **render host** is the process this document adds: the app's own binary run as a windowless Electron process by `mawsd`, holding the capture and export code main holds today, alive only while there is something to render. The **render seam** is `mawsd`'s side of it: what starts the render host, hands it work, answers the engine host and ends the host when quiet. The **artifact endpoint** is the daemon's HTTP server over `artifacts.sock` serving `maws-artifact:` URLs' bytes. The **scheme proxy** is the `protocol.handle` in an Electron process (the app, the render host) that answers `maws-artifact:` loads by asking the endpoint. A **tab engine** is a Chromium that holds the agent's browser tabs and serves cua's primitives: today the app's in-app browser; after U3, possibly the render host too.

## Acceptance

O5 closes when these hold, each checked as written and recorded in Outcomes with its evidence.

1. **A screenshot and an export on a machine with no app** (P5 acceptance 10). On a Linux VM running `mawsd`'s unit with no app ever attached, a lane B session's `artifact_screenshot` of an `html` artifact answers an image block, and its `artifact_export` of a `document` as `pdf` answers a file under `<profile>/artifacts/<id>/exports/`, both through the machine's render host; `mawsd.log` shows the render host started for the first request and exited after its quiet period; `mawsd status` between the two shows no render host running.
2. **The app's quit changes nothing.** On a Mac on the daemon shape, with an `html` artifact in a session: quit the app, keep the session; a `library` Export asked by a second client over `machine.sock` (the e2e's, in the test; `mawsd`'s command line in a sitting) writes the PDF; relaunch the app: the library row shows the export, and `artifact_screenshot` in that session answers as before, rendered by the render host, never by the app (the app's main has no capture window on the daemon shape).
3. **Browser control is offered or refused by capability, never failed mid-call** (acceptance 10's second clause). A session launched with no app attached has a cua socket path in its `CUA_BROWSER_BACKENDS` that `mawsd` owns; while no tab engine is attached nothing listens there and `session.capabilities` reads `browser: {available: false, reason: 'no browser is attached on <machine>'}`; when the app attaches, the socket listens within 1 s, cua's host (which retries every 5 s) connects, and the agent's next browser call works; when the app quits mid-session the socket stops listening, the capability reads unavailable again, and the next browser call answers "no browser" from cua's host, not a hang. The app that quit and relaunched while the engine lives gets the agent's browser back on the same socket (D-16).
4. **The artifact endpoint is the one source** (P5 §5, §6; acceptance 15's local boundary). On the daemon shape the app's `maws-artifact:` loads and the render host's both come from `mawsd`'s `artifacts.sock`: a 0600 socket in the 0700 daemon directory, owner-checked, refusing symlinks, with no loopback port; a `Range` request answers 206; every answer carries the `sandbox allow-scripts` policy, `nosniff`, `no-store` and the CORS header the scheme carries today; a URL that is not exactly the scheme's shape is 404. `e2e:artifacts`'s two scheme cases pass on the daemon shape unchanged.
5. **Export from a remote app** (P5 acceptance 4's carve-out, the machine side). In the two-profile scene (`e2e:machines`), profile A's app opens a session of profile B's daemon and runs the library's Export; the file is written by B's render host under B's profile; A's library row reads it. The live check from the MacBook against the mini is O7 M5's acceptance run, which consumes this and the capability entries.
6. **One or two Electron processes decided by P5 §2's criterion** (U4). The verdict and both halves' numbers are in `spikes/u4-render-service/FINDINGS.md` and P5's Decision Log: whether a windowless Electron runs reliably under a LaunchAgent and on a devcloud VM, headless Chromium's fidelity for export on Linux, and the idle memory each shape would add to `mawsd` against acceptance 14.
7. **The agent's browser for a remote session follows U3** (P5 §13). U3's findings are recorded with the promote-or-cut verdict; if promoted, M7's behaviour holds; if cut, this document says what O5 ships (the relay and the refusal) and what the new child carries.
8. **Nothing runs at `mawsd`'s start or idle.** `e2e:daemon-idle` on the mini reads within the 99,145 KiB bound with O5 landed, by the two-of-three rule; `e2e:local-latency-daemon` stays within OX7; `runPathOf(out/main/mawsd.js)` holds none of the render seam's chunk, the endpoint's handler chunk or any `electron` import (the bundle guard).
9. **Capabilities light up.** `session.capabilities` for a lane B session reports `artifact_screenshot`, `artifact_export` and `browser` with `{available, reason?}`, changes when the render runtime or a tab engine comes or goes, and O7 M5 can draw from it.

#### M2 — The artifact endpoint on `mawsd` and the scheme proxy in the app

**At its end.** `mawsd` serves `maws-artifact:` URLs' bytes over HTTP on `artifacts.sock` (Interfaces §C), with the ranges, the policy, the CORS header and the bridge script exactly as `src/main/artifacts/scheme-handler.ts` serves them today, resolving each URL through the engine host's `artifacts.content` as `protocol.ts` does, and answering the presenter's live embeds through the same responder-first chain (`createArtifactHandler`'s `first`). **Touches.** `src/services/artifacts/scheme/` (new: `scheme-handler.ts` and `protocol.ts`'s resolver and responder chain moved there, the Electron `protocol`/`session` calls left behind in `src/render/scheme.ts` for the embedded root); `src/mawsd/artifacts-endpoint.ts` (new, with tests: the listener and the Node `http`-to-`Request`/`Response` adapter, loaded deferred); `src/mawsd/daemon.ts` (start step 6 adds the socket; the exit order removes it; `daemon.status.artifacts`); `src/mawsd/endpoint-seam.ts` (`DaemonServices.artifacts`; `endpoint-seam.test.ts`'s equality with O10's `EndpointServices` updated together, as O3-D did); `src/main/artifacts/scheme-proxy.ts` (new) and `src/main/index.ts` (the daemon-shape root installs the proxy on the default session and the capture partition); `e2e/artifacts-store.spec.ts` (its two scheme cases run on the daemon shape; the seam `__maws_exports.print` stays until M3 moves it); `src/engine-host/bundle-guard.test.ts` (the endpoint handler's chunk admitted as a deferred load).

**Decisions.**
- Unix socket, not a per-boot token on loopback: a page load cannot add a header, a token in a URL leaks through referrers and logs, and `private-listen.ts` already gives the owner check and the symlink refusal. The proxy is Node's `http.request({socketPath})` inside the Electron process, so the scheme's standard, secure, streamed origin per artifact (`STORE_SCHEME_PRIVILEGES`) is unchanged for the page; Chromium never sees the socket.
- The endpoint reads the file through the same opened descriptor the check used (`scheme-handler.ts`'s rule) and never builds a path from the URL; the HTTP adapter maps `Range` and `HEAD` one-to-one and carries every header the handler sets. `Content-Length` and `Content-Range` must survive the proxy byte-exact: the e2e's media-seek case is the proof.
- The endpoint's handler loads at the first accepted connection (a deferred `import` of `src/services/artifacts/scheme/`), never at start; a connection while the engine host is parked wakes it through `dispatch` as a remote request does (the first paint of a page after a quiet night costs the host's start: accepted, it is today's behaviour for any read).
- Resolution asks the engine host, never the spine: the endpoint works while the spine is cold, so a remote viewer's artifact page never loads the spine.
- The presenter's live embeds (`src/main/presentations/present-embeds.ts`) answer in the app and stay there: the proxy asks the embeds' responder first and the endpoint for the rest, so a presenter's page in the app is unchanged; the render host asks the endpoint alone (it presents nothing).

**Does not touch.** The render code (M3). The engine host. The renderer. Remote carriage of the endpoint (O7 M5).

**Proves.** Acceptance 4. Tests pin: a request whose URL is not the scheme's exact shape is 404 before any dispatch; a `Range` past the end is 416 with `Content-Range: bytes */<size>`; a PDF's answer carries no CSP, every other answer the frame policy; an `html` page gets the bridge script once, an asset byte-for-byte; the socket refuses a symlink in its path and a directory of another owner or a wider mode (the `private-listen` cases); the proxy relays 206 with the same `Content-Range`; the proxy answers 503 with a one-line body, never hangs, when the socket is absent; the handler chunk is absent from `mawsd.js`'s run path.

**Decisions.**
- **The render host is a `machine.sock` client, not a fourth socket.** It connects with the daemon's token and a hello listing `machine.render`, takes work as `render.request` events and answers with `render.answer`, the client port's request-and-answer shape inverted (O3-D Interfaces §E), and calls the engine host's commands (`artifacts.content`, `artifacts.state`, `artifacts.assets`, `designSystems.governing` and the rest `src/main/artifacts/export.ts` calls today) forwarded raw through the front as any client's are. Rejected: a third host under the `HostSupervisor` with a socket of its own, which would need the hello machinery of a served host inside an Electron process and a second token; the pty host's pattern fits a host `mawsd` is the client of, and here `mawsd` is the server.
- **Spawned by `mawsd`, on demand, ended when quiet.** The seam spawns `process.execPath` without `ELECTRON_RUN_AS_NODE` (the unit's environment sets it; the child's environment deletes it) and with `--render-host <profile>`; from a packaged app `execPath` is the bundle's binary and loads `app.asar`'s entry by itself; from a checkout (`electron-vite dev`, the e2e builds) the app root is passed as the script argument as the e2e harness passes it. The quiet period is `MAWS_RENDER_QUIET_MS` (default 120 s after the last answered request), and the host is ended with `render.exit` then SIGTERM after 5 s; a crash restarts at the next request with the detached transport's backoff (`restartBackoffMs`), and two failures within a minute answer every request `ok: false, error: 'the render service could not start on <machine>: <reason>'` until the next minute. A unit daemon's restart (exit 75) ends its render host first: a render host outliving its `mawsd` would hold the wrong build.
- **`userData` of its own.** `<profile>/mawsd/render-host/`, so Chromium's profile lock, its caches and its `maws-capture` partition never meet the app's; it is cleared at each start (nothing in it is kept). The app's default-session policies (`installStorePolicies`) apply to the render host's capture partition as they apply to the app's today; its default session gets `guardPermissions('all')`.
- **The hold and the deadlines.** A request arriving while the host starts waits in the seam; the engine host's own deadlines (`CAPTURE_ANSWER_MS` 45 s, `EXPORT_ANSWER_MS` 60 s) bound the whole wait, so the seam answers `ok: false` with the start's reason at 40 s and 55 s respectively if the host is not ready by then, and never later than the bridge's deadline. The render library's own budgets (`EXPORT_BUDGET_MS`, `CAPTURE_QUEUE_MS`) run inside the host unchanged.
- **One answerer.** From M3 the front posts `maws.artifact.capture` and `maws.artifact.export` to no client: a pre-O5 app hears nothing and the seam answers; `e2e:cross-build` adds the case. The engine host's `appNotOpen` refusal remains for `show_pane` and the asks, which stay client-bound.

Its answer keeps `src/shared/ipc/schema/artifacts.ts`'s shape; the file lands under the store's directory on the machine, which the local app reads as today and a remote app through O7's `files.readResolved`.
- **Main's `--render-host` branch runs first.** `src/main/index.ts` reads the flag before `app.setPath('userData', …)`, `registerStoreSchemes()` and the stdio guard, so the render host registers the scheme (it needs it) and nothing else of the app's start (no windows, no menu, no spine, no browser, no LaunchAgent install). `app.setActivationPolicy('accessory')` precedes `whenReady`; `app.dock?.hide()` follows it (M1's probe is the reference).

On the embedded shape main is the client and renders, so nothing changes there. The engine host never learns which process renders.

**Does not touch.** The cua socket (M4). The Linux pack (M5). The renderer, but for the library's Export reading its answer unchanged. The remote carriage (O7).

#### M4 — The daemon-owned cua socket; `session.capabilities`

**At its end.** Every lane B session's `CUA_BROWSER_BACKENDS` names a socket `mawsd` owns, `<socketDir>/cua/<appSessionId>.sock` (Interfaces §H), listening only while a tab engine is attached and relaying each accepted connection, after the peer check, to that tab engine's own socket for the session; the app's cua backend accepts relayed connections from the daemon it is attached to. A session launched with no app, or whose app quit and relaunched, gets its browser the moment the app attaches, and loses it cleanly when the app goes. `session.capabilities` and `session.capabilitiesChanged` (Interfaces §I) report `artifact_screenshot`, `artifact_export` and `browser` per session; the renderer greys the Browser tool's agent-side affordances from it where it drew them from the lane before.

**Touches.** `src/mawsd/cua-socket.ts` (new, with tests: the per-session listener, the peer check, the relay, the listening gate); `src/mawsd/daemon.ts` (the sockets created at a session's launch and removed at its end, from the spine's session events; `front.browserSocket()` becomes the relay target; the socket directory under `daemonPaths`' socket dir, since a profile path can exceed `sockaddr_un`); `src/services/spine-root.ts` and `src/services/sessions/launch-mapping.ts` (`browserSocket` answers the daemon's path on the daemon shape; the embedded shape keeps the app's); `src/main/browser/cua/{index,peer}.ts` (a trusted root for the attached daemon's process instance, read from the `machine.sock` welcome; the relayed connection carries the session in its path as today); `src/main/index.ts` (`machine.client` keeps reporting the app's directory as the relay target); `src/shared/browser/cua-socket.ts` (the daemon's path rule beside the app's); `src/shared/ipc/schema/session-capabilities.ts` (new) and `wire.ts` (the next free `WIRE_MINOR`); `src/mawsd/front.ts` (`session.capabilities` answered cold from the seam's and the socket's state); the renderer's Browser tool (`src/renderer/src/tools/browser/`: the agent-browser affordances read the capability); `e2e/browser-cua.spec.ts` (the daemon shape: its scenes run through the daemon's socket; two new scenes below).

**Decisions.**
- **Not listening is the refusal.** cua's host retries an unreachable backend every 5 s for the process's life (`cua/src/chrome/client-mode.mjs`, `CLIENT_RETRY_MS`) and lists a backend only after its hello, so a socket that does not listen while no tab engine is attached is already "refused by capability": `listBrowsers` finds no `maws:` browser and the browser tools say so. Rejected: accepting and answering a refusal frame, which needs a protocol addition in the cua repository (a cross-repo change like MW1–MW5) for no gain. The listener comes up within 1 s of a tab engine's attachment and goes down at its departure (the relay's departure drain ends the relayed connections, so cua's host sees `lost` and retries).
- **The peer check moves to `mawsd`.** The accepted socket is held unread until its peer runs as this uid and descends from the session's engine (the pid the spine holds from each `session.status`), through the addon loaded from the app's Resources (`peerAddonPath` with `mawsd`'s `packaged` and `appPath`); the app's own check then sees `mawsd` as the peer and accepts it as a trusted root, the daemon's process instance `{pid, start}` from the `machine.sock` welcome. On Linux the addon is absent: the socket is 0600 in a 0700 directory and the uid is the boundary (O2), one log line per socket says so.
- **Byte relay.** The daemon relays frames unparsed between the engine-side connection and the tab engine's socket, so cua's protocol never changes on either side; backpressure follows each socket's own (`pipe` both ways, the pair ended together).
- **The capability's reasons** are exact strings the renderer and O7 show: `no browser is attached on <machine name>` (no tab engine), `the render service is unavailable on <machine name>: <reason>` (M3's failure reasons), `this build of MAWS cannot export a <kind> as <format>` stays the tool's own.
- **Session end.** The socket is removed when the session is removed, as the app's is; a session released idle keeps its socket (its next launch names the same path).

**Does not touch.** The tab engine itself (the app's browser code beyond the trusted root). A headless tab engine (M6, M7). The remote app's view.

**Proves.** Acceptance 3 and 9. Tests pin: the listener exists only while a tab engine is attached; an accepted peer that is not a descendant of the session's engine is destroyed unread and counted; a relayed connection's frames arrive byte-exact both ways and end together; `session.capabilities` flips with the attachment and with the render seam's state, and the event follows each flip once. `e2e:browser-cua` on the daemon shape: its existing scenes through the daemon's socket; a new scene launches the session with no app attached (the app started after the engine, the harness's unit `mawsd` first), connects the fake host, sees it refused until the app attaches, then served; another quits the app mid-lease, sees cua's host lose the connection and no hang, relaunches the app over the same profile and sees the fake host connect again on the same path (D-16).

### Interfaces and Dependencies

#### A. The render host's hello and its work (`src/shared/host/socket-protocol.ts`, `src/shared/ipc/schema/render.ts`)

    export const RENDER_CAPABILITY = 'machine.render';                 // a machine.sock client that renders
    PEER_CAPABILITIES.renderHost = [RENDER_CAPABILITY];                 // the render host's hello to machine.sock

    // machine, posted by the front to the one ready machine.render client (the seam's request table keeps the order)
    'render.request': { id: string; kind: 'capture' | 'export' | 'libraryExport'; request: MawsArtifactCapture | MawsArtifactExport | CommandInput<'artifacts.export'> }
    // machine, internal: accepted from a machine.render client alone; refused for an id the seam did not post
    'render.answer': { input: { id: string; answer: MawsArtifactCapturedResult | MawsArtifactExportAnswer | CommandOutput<'artifacts.export'> | { ok: false; error: string } }, output: void }
    'render.exit': {}                                                   // machine event, posted to the render client alone: end after in-flight work, then exit 0

The render host answers each request once; the seam settles a request whose client ends with `ok: false, error: 'the render service ended on <machine>'`. `MawsArtifactCapture`, `MawsArtifactExport` and the answers are `src/shared/ipc/schema/maws.ts`'s, unchanged.

    }

States: `off` → `starting` at the first request (the spawn, the hello awaited); `starting` → `ready` at the client's ready, → `unavailable` at a spawn failure or a second start failure within a minute (every request answered with the reason; a request after a minute tries again); `ready` → `ending` after `quietMs()` with no request in flight, → `off` at the child's exit; any state → `off` at an unexpected exit, with in-flight requests answered `ok: false` and the next request starting again. The seam never waits past the bridge's deadline: a request still unanswered at its start deadline is answered with the start's reason and dropped from the table.

## Surprises & Discoveries

- Observation: cua's host already treats an unreachable MAWS backend as "no browser" and retries it every 5 s for the life of the process, so the daemon's socket can refuse browser control by not listening, with no change in the cua repository.
  Evidence: `~/Developer/GitHub/cua/src/chrome/client-mode.mjs` (`CLIENT_RETRY_MS = 5000`; "a refused or lost connection … is retried every CLIENT_RETRY_MS for the life of the process"; a backend is listed after its hello).
- Observation: the app's capture and export code is already composed through one injected `call` to engine-host commands and a content lookup (`startArtifacts`, `startExportService`, `registerHtmlExporters`), so it moves into the render host without a render protocol of its own: the render host is a `machine.sock` client calling the same commands.
  Evidence: `src/main/artifacts/index.ts` (`call = hosts.dispatch('engine-host', …)`, `content = call('artifacts.content')`), `src/main/artifacts/export.ts` (`ExportServiceDeps.call`).
- Observation: GCE's `us-west1-a` had no 50 GB pd-balanced disk at 09:1xZ on 2026-10-31 (`ZONE_RESOURCE_POOL_EXHAUSTED`); `--location us-west1-b` worked. Recorded for the friction tracker.
  Evidence: `devcloud vm up … --dry-run` passed caps; the create was refused; the `us-west1-b` create reached ready in 6m25s.
- Observation: on Linux, Electron's `BrowserWindow` needs a display connection for GTK whatever `--headless` says; `--headless` alone reaches `ready` and aborts at the first window. A virtual X display (Xvfb) is the condition; `--headless` beside it keeps Chromium's compositing in software, and without it (or with `--disable-gpu` alone) a whole-page capture fails with `UnknownVizError`.
  Evidence: round 1, every variant `Gtk-ERROR **: Can't create a GtkStyleContext without a display connection` (SIGTRAP); round 2 x4 under Xvfb with `--headless`: capture 576 ms, whole page 353 ms, PDF 262 ms, no error; x1, x2, x5, x6 `UnknownVizError` at the whole-page step (`spikes/u4-render-service/FINDINGS.md` §1.2).
- Observation: the zip's sandbox helper aborts Electron on Ubuntu 24.04 (unprivileged user namespaces restricted), and `chown root:root && chmod 4755 chrome-sandbox` makes the sandbox work under the shell and under a systemd user service; `--no-sandbox` is never needed.
  Evidence: round 1 r2's FATAL line; round 3 y1, y2 and y4 with `noSandbox: false` and no error (FINDINGS §1.3).
- Observation: Electron quits on `window-all-closed` on Linux, so a render host that opens and destroys a window per request must handle the event; a viewport capture carries a classic scrollbar unless `--hide-scrollbars` is passed; the hidden-window fallback is one pixel short on both axes under X.
  Evidence: round 2's exit 0 after the offscreen steps with the hidden steps missing; `evidence/round2-x4-offscreen.png` (scrollbar) against `evidence/round3-unit-offscreen.png`; `hidden-window capture … width 1279, height 799` in every round-3 run.
- Observation: the idle cost of the shapes on the VM: plain Node 43 MiB RSS; Electron run as Node 98 MiB; a windowless Electron at `ready` 137 MiB working set (263 MiB RSS over its tree) and 450 MiB after one render with the GPU process kept. A bare VM carries DejaVu alone; with the Noto packages the PDFs embed every face (the bundled Noto Serif KR, Noto Sans CJK, colour emoji included) and the pictures draw CJK and emoji.
  Evidence: FINDINGS §1.4, §1.5; `evidence/round3-summary.json`; `pdffonts` on round 3's PDFs.
