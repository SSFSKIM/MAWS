## Executive answer

1. **The embedded root is not gone.** It is a live, selectable branch of Electron main's `startMain` in `src/main/app.ts`, calling the same `openSpineData` / `startSpine` library that `mawsd` calls. It runs the index, sessions, attention, git/scm/files, connectors, library and other spine services inside main. `supervisor.shape: embedded`, `MAWS_HOST_MODE=detached`, and `MAWS_HOST_MODE=utility` select it. **Even a daemon-default launch can fall back to it automatically** if the default profile's LaunchAgent is absent, disabled, cannot install, or cannot start.
2. **O15 is branch removal and test migration, not a second extraction of the services.** The shared services are already in `src/services/`, the daemon already composes them, and ordinary e2e/component-harness launches already default to daemon. The remaining work spans launch/failure policy, settings migration/UI, main composition, quit/status distinctions, embedded sentinels, cross-build scenes, and a few embedded-only probes. Rough planning size: **35–55 files, about 1,500–3,000 removed/replaced lines**, plus roughly 500–1,200 lines of replacement tests/migration checks. These are estimates, not a diff. Retiring older-daemon rendering/delivery fallbacks at the same time expands the scope and needs an explicit compatibility-window decision.
3. **Both native-Mac signing private keys are software keys in plaintext private JWKs in `<userData>/device/keys.json`.** Neither is in the Keychain or Secure Enclave. The channel/device key has no per-use person-presence gate. The step-up key is normally gated by an app sheet and Electron `promptTouchID` (LocalAuthentication per the source commentary), but this is an application control-flow gate, not key-bound access control. A same-uid process able to access the profile can read **both** keys' private material from disk. Non-extractable WebCrypto handles in main do not change that fact.

### 1.2 Additional machine work still composed in main — Read, with scope distinction

These are not all removed merely by eliminating `startSpine` from main.

- **Artifact render root:** [src/main/artifacts/index.ts:83](../../../src/main/artifacts/index.ts#L83) always installs the artifact scheme and composes `composeRender` at 103, registers `artifacts.export` at 108, and subscribes to engine-host export/capture requests at 104–113. [src/main/app.ts:906](../../../src/main/app.ts#L906) calls it on **both** shapes. On a current daemon, production machine export/capture is handled by the daemon/render host; main's copy remains for embedded execution, older-daemon compatibility, and direct e2e seams.
- **Artifact local-file serving fallback:** [src/main/artifacts/index.ts:90](../../../src/main/artifacts/index.ts#L90) chooses the artifact endpoint per request if the welcomed daemon advertises `machine.artifacts`; otherwise the scheme can serve locally, including before a welcome. A null endpoint configuration is also the embedded path. This is distinct from the spine root.
- **Older-daemon export/delivery dispatch:** [src/main/app.ts:515](../../../src/main/app.ts#L515)–526 and [src/main/ipc/router.ts:70](../../../src/main/ipc/router.ts#L70)–72 intentionally answer `artifacts.export` and `delivery.send` in main when the daemon lacks `machine.render` or `machine.delivery`. [src/main/app.ts:927](../../../src/main/app.ts#L927)–943 composes the delivery shim **only on daemon mode**. Removing it because it says “main” or “embedded” would remove a daemon compatibility feature, not just the fallback shape.
- **Machine identity startup:** [src/main/app.ts:221](../../../src/main/app.ts#L221) invokes [src/services/machine/identity.ts:20](../../../src/services/machine/identity.ts#L20) on both shapes, reading/minting the profile ref and registering a local `machine.identity` handler. Daemon-mode routing forwards the command instead. The ref/name are still required by main; the local machine-command registration and its placement under the services entry can be separated from that bootstrap.
- **Legitimate app services:** layout, client settings, UI browser tabs, presentation windows, artifact document ports, client-port answers, notifications, org sign-in/signing keys, remote-machine clients and the app's own usage/catalog UI remain client/app responsibilities. Their existence in main is not evidence that O15 failed. Main's normal UI composition root itself must not be deleted.

**Recommendation:** define O15's required cut as “no selectable/fallback full machine spine in main.” Inventory the artifact/delivery shims explicitly, but retain the ones required by the supported older-build window unless that window has separately closed. If the desired acceptance is stronger—“main composes no machine-rendering or machine-command implementation at all”—include their retirement as an additional, compatibility-reviewed substep. Do not silently conflate those scopes.

**Inference / required decision:** once local execution is removed, the no-unit/disabled-unit/install-failed/start-failed cases require a new explicit outcome. Recommend a clear startup failure with repair guidance rather than quietly bypassing a disabled LaunchAgent with a private daemon on the owner's default profile. Development can use a scratch `MAWS_USER_DATA` (already the harness/stub convention) or the installed unit. This changes currently promised fallback behavior and needs to be recorded in the P5 Decision Log.

## 4. Deletion plan

### 4.1 Recommended sequence — Inference / recommendation

1. **Set the exact post-O15 failure/compatibility contract first.** Decide default-profile unit failures without embedded fallback, what to do with old `supervisor.shape`/`keepRunningDefault` fields, how current/old app crossings work, and how future idle-bound re-derivations work without a current-tree embedded comparator. Record dated P5 decisions rather than silently weakening acceptance or bypassing disabled Login Items.
2. **Move the remaining tests off app-embedded ownership.** Migrate the two mocked app startups, artifacts performance cold-start setup, cold-delivery client-loss test and optional live keep-quit. Change cross-build current-side defaults, preserve peer-side modes. Ordinary harness groups need no architectural migration; c7 and supervisor already have daemon coverage.
3. **Make daemon the only application machine root.** In `app.ts`, remove `openSpineData`/`SpineData` and `startSpine` imports/calls, always build the mirrors and `{kind:'host'}` router binding, always tell the daemon browser/connector state, and delete the embedded `session.capabilities` registration. Keep app client behavior, routing, bus invoke/taps, shutdown drain and org services. Move ref/name bootstrap and command budget constants onto a neutral import path so main no longer needs an exception permitting service-root imports.
4. **Remove selectors and reverse transitions.** Delete the embedded/utility app modes from `hosts/mode.ts`; simplify host creation to daemon specs; remove `planShape`/`prepareShape`'s local fallbacks, embedded uninstall and `leaveDaemonShape` transition, retaining needed unit install/repair/status logic. Check references before deleting shared teardown helpers (the transition module is mixed-purpose). Keep default-profile harness refusal.
5. **Migrate settings deliberately.** Remove the UI shape switch/copy. Normalize legacy embedded to daemon without discarding unrelated client/machine settings; if removing schema fields, add a settings version/read migration, not just a stricter enum that would make existing files unreadable and default/reset them. Keep historical input schemas where needed for supported old profiles. `keepRunningDefault` is embedded quit policy only, so either remove/migrate it too or record its temporary retention as ignored compatibility data.
6. **Simplify status and quit wiring, then retire gates.** App quit always leaves machine sessions/terminals alive; keep unsaved-file guard. Status comes from daemon. Remove duplicate sentinel scripts/list entries, daemonize canonical script names if desired, adjust packaged matrix and static gate tests. Keep the daemon latency/idle, packaged unit, process cleanup and cross-build gates.
7. **Separately retire the bounded render/delivery compatibility surface if in scope.** Prove the oldest supported daemon always has the required capabilities before removing `answeredHere`, local export/delivery handlers and local artifact fallback. Port app-main render-seam tests first. Keep the render library itself and the render-host root. The safe minimal O15 can leave explicit capability fallbacks without leaving a selectable full spine root.
8. **Close with ownership and absence assertions.** Add a source/lint/bundle check that application main cannot import/construct the service root; app launch on fresh and formerly embedded profiles must show `spine.lock` belongs to `mawsd`, while app close leaves session/index work alive. Verify that failed daemon startup never begins machine writes in main.

### 4.3 Principal risks / verification — Inference / recommendation

- **Loss of automatic fallback changes availability.** Default-profile development with no unit currently works via embedded; disabled/broken Login Items currently still opens the app. A daemon-only app must diagnose this before touching machine files and offer a clear repair path. Do not introduce an unauthorized private fallback just to keep tests green.
- **Data migration / single writer.** Preserve split settings, profile identity and lock ownership; stale embedded settings must not select old code or silently drop user preferences. Existing daemon migration/process-yield tests are the foundation, not replaceable by a regex test.
- **Upgrade/downgrade window (OX1).** Cross-build still deliberately runs old embedded apps and capability fallbacks. Delete the current-build mode, not the ability to interoperate with a supported old peer. Recheck the actual supported window before deleting daemon yield/old-hello behavior or changing wire schemas. Neither narrowing wire enums nor changing manifest names is required just to remove the launch choice.
- **Detached is not obsolete.** Daemon links and engine/session-host keepalive/adoption still require detached processes, sockets and cleanup. An `rg detached` deletion would break the intended architecture.
- **Measurement integrity.** Artifact cold host lifetime must remain explicit; OX7 recorded baseline stays. Idle baseline re-derivation is the one real design gap created by removing its live comparator—resolve it openly, not by increasing the bound.
- **App-versus-machine responsibilities.** Keep app-owned org/device keys, browser UI, document ports, client settings and notifications. Render compatibility tests have main-window assumptions that need migration only if local render composition is also removed.
- **Validation proposed, not performed:** typecheck/lint/unit/probes through `scripts/ci-gate.sh` under project offload rules; daemon-default e2e set including settings, c7, c12, supervisor, machines, delivery, artifacts, document, deliverables and render-host; packaged/daemon-unit checks; cross-build with the oldest required peer; daemon OX7 and affected measured bounds on a Mac under the load rule. No build, suite, live engine or measured run was launched for this research.

## 5. Native-Mac device and step-up signing keys (separate risk-review fact)

### 5.1 What the current implementation does — Read

“Device key” here is the **channel signing key**, not a third key. The native-Mac device id is `keyId(channel.pub)`. [src/main/org/org-session.ts:352](../../../src/main/org/org-session.ts#L352)–354 constructs the device entry with `class: 'native-mac'`, **`keyStorage: 'software'`**, `channelPub` and `stepUpPub`. Production key loading defaults to `loadDeviceKeys` at 395. There is no alternative native-Mac Keychain/Secure-Enclave key provider in this path.

| Property | Channel / device key | Step-up key |
|---|---|---|
| Algorithm and storage | Software P-256. `<userData>/device/keys.json`, `channel.jwk` including private material. | Software P-256. Same file, `stepUp.jwk` including private material. |
| Concrete storage proof | [src/main/device/keys.ts:64](../../../src/main/device/keys.ts#L64)–73 defines the private-JWK record, key files and modes; 290–305 generates extractable keys, exports JWK, and JSON-writes **both** records. | Same code; stepUp is generated/stored separately at 299. No encryption call occurs around the JSON write. |
| At-rest protections | `device/` created 0700, file 0600; owner/mode/type/symlink checks. [src/main/device/keys.ts:208](../../../src/main/device/keys.ts#L208), 247–271, 303. Time Machine exclusion attempted at 101–105. | Same. Backup exclusion is not encryption or a signing-use gate; its failure is logged and initial key loading continues. Rekey requires exclusion at 126–147. |
| Normal use gate | None requiring a person per signature in this app path. Passed directly as `identity.channelKey` at [src/main/org/org-session.ts:543](../../../src/main/org/org-session.ts#L543), for routine channel authentication. | App confirmation normally precedes signing: production confirm binding at [src/main/app.ts:318](../../../src/main/app.ts#L318)–320, step-up at 351, org-state signer at 374, record/grant signer at 392. Sheet Continue→Touch ID at [src/main/device/step-up-sheet.ts:13](../../../src/main/device/step-up-sheet.ts#L13)–24; `promptTouchID` call at [src/main/device/step-up.ts:81](../../../src/main/device/step-up.ts#L81)–89. |
| Hardware / OS key-use enforcement | No Keychain item, `SecAccessControl`, or Secure Enclave binding in this key provider. | Also none. LocalAuthentication confirmation is separate app control flow; the key is already loaded as a software CryptoKey. |
| Same-user private-material readability | **Yes, from the profile file** (inference from plaintext private JWK plus same-uid-readable Unix modes). | **Yes, identically.** Touch ID does not gate file read/import by another same-uid process. |

Further load-bearing details:

- [src/main/device/keys.ts:335](../../../src/main/device/keys.ts#L335)–342 imports the stored JWK with `importSigningKey`; [apps/org-protocol/src/keys.ts:94](../../../apps/org-protocol/src/keys.ts#L94)–99 explicitly requires a P-256 private JWK with **`d`** and defaults `extractable=false`. Thus the **in-memory handles** cannot be exported through WebCrypto, as tested at [src/main/device/keys.test.ts:105](../../../src/main/device/keys.test.ts#L105)–109. It does **not** make the original disk JWK unreadable; the writer exported it first with `generateSigningKey(true)`.
- The comment at [src/main/device/step-up.ts:75](../../../src/main/device/step-up.ts#L75) describes Electron's prompt as LAContext user presence, accepting Touch ID or login password; code directly verifies only that `prefs.promptTouchID(summary)` resolves before approving. This research did not independently probe OS behavior or claim Secure Enclave mediation.
- Normal action signing calls confirmation then seals with the software key at [src/main/device/step-up.ts:183](../../../src/main/device/step-up.ts#L183)–206. **Exception:** an owned-machine `session.spawn` can be signed **without asking**; predicate at 110–123 and bypass at 188. Batch actions still ask. Org-state/root signing always passes confirmation at 246 before `signOrgState` at 249; record/grant signing does so at 296–298.
- Unpackaged e2e can inject acceptance with `MAWS_E2E=1 MAWS_E2E_STEP_UP=accept`; packaged builds refuse that harness bypass ([src/main/device/step-up-sheet.ts:28](../../../src/main/device/step-up-sheet.ts#L28)–31). This is a test seam, not keychain ACL protection.
- Rekey may temporarily also hold `keys.next.json` and `keys.retired.json`, with the same file mechanism; names at [src/main/device/keys.ts:70](../../../src/main/device/keys.ts#L70), promotion/destruction at 164–177. They are not hardware-keystore slots.
- `org/signing.json` is **signing state**, not private-key custody: pending proposal, delivery obligations, abandoned proposals, weekly dates ([src/main/org/signing-store.ts:1](../../../src/main/org/signing-store.ts#L1)–12). Do not cite that file as the key store.

**Risk conclusion — inference:** possession of same-user read access to this profile is sufficient to obtain both signing private keys and sign outside MAWS's confirmation flow. Touch ID meaningfully protects the legitimate app's normal step-up UX, but does **not** establish a security boundary against another process with the owner's uid/profile-file access. This statement is about the examined implementation, not an inspection of what keys the owner's currently installed binary has on disk. O15's service-root deletion neither fixes nor worsens that key-custody design by itself; key custody is separate work if the risk model requires same-user resistance.
