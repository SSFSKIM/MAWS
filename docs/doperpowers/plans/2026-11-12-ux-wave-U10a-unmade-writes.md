## Purpose

Two things write to a document today though nobody made them.

The first is a tidy-up inside Yjs, the library that holds a document's content. When a copy of a document takes in someone else's edit, Yjs afterwards removes formatting markers that no longer change anything, as a second write of that copy's own which names no writer. In the engine host's copy that write is refused: the agent's edit that caused it fails with "the live doc … was edited outside a replica", the document is reset for everyone who has it open, and the agent's next edit is refused as stale. In a copy that only received the edit (a person's open editor, an agent's own copy) the tidy-up is sent on as that reader's edit.

The second is the editor's trailing paragraph. A document whose last block is not a paragraph gets an empty one appended by the editor at its next transaction of any kind, and that can be a pure redraw: an agent's presence arriving, the keyboard entering the editor, the undo history attached a moment after every mount. So opening an agent's document that ends in a list, a table or a chart, or leaving one open while an agent works in it, writes a revision credited to the person at the window.

After this landing an agent's edit that takes the bold off part of a bold run lands at the first call, as one revision credited to the agent, and the next edit made from the revision that call returned is accepted. Accepting a suggestion, restoring a version and duplicating a document across such an edit each land as one revision of the person who did it. A copy that only receives writes nothing. A document loaded from disk holds exactly what its log holds.

And looking at a document writes nothing to it. Opening it, scrolling, clicking in it and selecting text leave its history as it was. The editor adds its trailing paragraph only together with a change the person makes to the content. The empty paragraph was also how a person got a caret under a final chart, so that place is now given directly: where a document ends with a chart, a table or another block that holds no text, a click under it, or an arrow key from it, shows a caret there, and nothing is written until the person types.

**What a trial leaves in the artifact store, and what crosses between builds.** Nothing about the stored form of a document or a deck changes: no table, column, key, encoding or version, and the recorded binding version stays `y14-rc28/ypm2-15`. What can differ is content: a document written by this build can hold formatting markers that change no character's format and that Yjs's tidy-up would have deleted. Build F (commit `f1852de3a`, on the owner's machines) opens such a document as it opens its own, with no refusal and no revision; while it loads the rows it may remove some of those markers in memory. A replica of this build attached to a host of build F, which happens for a document on another machine and in the minutes after a build swap, sends for a deletion what F's own would send. An editor of build F attached to a host of this build can still send its tidy-up as its reader's edit; that is F's defect and ends with F. Interfaces §D has each case, how it was measured and what was not.

**How to see it working.** In the suites: the tests named under each milestone, first of all `src/engine-host/tool-server/documents-format-cleanup.test.ts`, which the check of 2026-11-12 wrote with its expected behaviour as cases that fail today. On the wave's build by hand, in a session MAWS runs: ask the agent for a document whose list items begin with bold text and which ends with a table, and open it (no revision is added, and no empty line appears under the table); click in the text and select some of it (still no revision); ask the agent to rewrite one item so that part of the bold text stays without the bold (the answer names a new revision and nothing is refused); click under the table (a caret shows there and nothing is written) and type (your words are in a new paragraph under the table, as a revision of yours).

## What the code holds today

Checked at master `48619c824` and in `@y/y` 14.0.0-rc.28 (the pin). Master moved to `6e8c72738` while this was written; no file this document names under `src/`, `e2e/` or the repository's root changed between the two. Terms used below: the *live copy* is the one authoritative Y.Doc per open artifact in the engine host (`DocumentService` in `src/engine-host/documents/service.ts`). A *replica* is a copy of it synced over a port: a person's open editor, an agent session's own replica, or the host's replica of one actor, through which every host-side write is made. A *row* is one entry of the update log (table `artifact_updates`: sequence, actor, bytes) and is one revision. A *marker* is a formatting marker, Yjs's `ContentFormat` item: a zero-width item in a text that turns a format on or off from that point. A marker is *redundant* when removing it changes no character's format.

**Yjs's two clean-ups, and the one flag.** Yjs removes redundant markers at two moments, and `doc.cleanupFormatting` gates both.

- *The writer's own.* When a transaction deletes text, `deleteText` (`src/ynode.js`) calls `cleanupFormattingGap` on the gap it leaves. This runs inside the writer's transaction and its deletions are part of that transaction's update.
- *The post-apply one.* When a transaction that is not local (an applied update) changes a text that holds formatting, the type's `_callObserver` sets `transaction._needFormattingCleanup`. After the `afterTransaction` event, `cleanupTransactions` (`src/utils/Transaction.js`) reads that field and the flag and calls `cleanupYTextAfterTransaction`, which opens a new transaction with origin `null` and deletes what it finds. This second transaction emits its own update. What it finds in practice is narrow (measured): a marker beside text that the applied transaction deleted, when the gap that text leaves holds two markers of one key and the transaction itself put no marker into that text. That is the shape every test of M1 uses.
- An update applied inside a transaction already open on the same doc joins it and makes it not local (`readUpdateV2` in `src/utils/encoding.js` sets `transaction.local = false`), so the post-apply clean-up then runs when the enclosing transaction ends.
- `cleanupFormattingGap`, `cleanupContextlessFormattingGap` and `cleanupYTextFormatting` each return at once when `doc.cleanupFormatting` is false (`src/utils/transaction-helpers.js`, `src/utils/Transaction.js`). So the flag switched off removes the writer's own clean-up as well as the post-apply one. `Doc`'s constructor sets it to `!isSuggestionDoc`: suggestion documents already run with both off.

**Where the product builds a Y.Doc.** ESLint allows `@y/y` only under `src/artifacts/yjs/` (the binding module, charter X24). In it, `new Y.Doc` is called in five files: `doc.ts` (`newDoc`, gc on; `newSuggestionDoc`, gc off and flagged as v14's suggestion doc), `suggest.ts` (`scratch`, the docs an accept or a reject is planned on), `revert.ts` (the scratch doc a restore's update is computed on, and an empty doc for the empty answer), `versions.ts` (`canonicalV2`) and `document.ts` (`newDocGcOff`, history's throwaway docs). `newDoc` has about fifty call sites in about forty files: the live copy and every replica (`service.ts`: `loadDoc`, `hostReplica`, `writeCopy`; `replica.ts`; the renderer's `Replica` in `src/renderer/src/artifacts/host.ts`), and scratch copies that are read once (export, search, retention, the library's mirror, the kinds' readers).

**The host.** `integrated`, the live copy's update listener, accepts a row only from a connection or a host replica and throws "the live doc of … was edited outside a replica" for any other origin; loads and a main doc's updates flowing into its suggestion doc are exempt by their own origins. `inFrame` then takes the frame's rows back and evicts the document, and the caller answers "… failed and the document was reset: …". The listener is attached in `open` after `loadDoc` returns, so a clean-up during the load changes the live copy without a row. A host replica forwards every update of its own doc but the mirror's (`hostReplica`, `writeCopy`), whatever its origin; so does `PortProvider.onDocUpdate` in `src/artifacts/provider/port.ts`, which skips only the frames it applied itself. No test names the refusal's message, and no test pushes a formatting change through the live copy and a replica.

**Applies that run inside a transaction.** The restore's revert (`restoreArtifact` in `restore.ts`), the accept's deletions and the reject's copy (`planAccept` and `planReject` in `suggest.ts`, which call `Y.applyUpdate` directly), the proposal's removal in `settle` (a suggestion doc), and, beyond the check's list, the source's state applied by a duplicate (`copyOf` in `store.ts`). Any `initial` a create is given, and a kind's `migrate`, may do the same.

**Two builds on one document.** A document on another machine opens through the same replica, its port bridged to that machine's document service (`src/renderer/src/artifacts/host.ts`, the P5 O7 M5b note). And after a build swap the app of one build is served by the kept engine host of the other until that host is idle (`e2e/cross-build.spec.ts`, its head comment). So an editor of this build on a host of build F, and the reverse, are ordinary states. `src/artifacts/yjs/`, `src/artifacts/provider/` and `src/engine-host/documents/` are byte for byte the same in F and at this base (`git diff f1852de3a 48619c824 -- <those paths>` is empty).

**The editor's repairs.** `guard` in `src/artifacts/document/schema.ts` wraps the `appendTransaction` of four plugins (the link's, `linkRepair`, the table's, Tiptap's `TrailingNode`) and returns null when an attribution is rendered, when any transaction of the batch is the binding's (`isBindingTransaction`), or when every transaction is the provisional layer's redraw. `TrailingNode` is the only one armed by state: its plugin state says whether the last block is something other than a paragraph, and it inserts at any call. The transactions that change neither the document nor the selection and reach it today are: the presence redraw (`editor/awareness.ts`), the binding's cursor plugin on any awareness change (`@y/prosemirror`, `cursor-plugin.js`), the comment threads' redraw (`editor/comments/plugins.ts`), history's paint (`editor/history/paint.ts`), Tiptap's focus and blur, and the undo manager swapped into the plugin a microtask after every mount (`collab.ts`, and `keepUndoManager` in `src/renderer/src/tools/document/view-carry.ts`). Two dispatches set the selection with no gesture of the person's in that editor: a reveal asked from outside (`TabEditor` in `editor/DocumentEditor.tsx`: a link's fragment, or the `at` of an agent's `show_pane`) and the selection put back after a pane move (`restoreDocumentView` in `view-carry.ts`). **The place to type under a final block.** The trailing paragraph is today how a person gets a caret under a final chart, and `editorExtensions` installs no gap cursor. ## The write path, caller by caller

Every document and deck write is applied to docs that the binding module builds, so every one passes through the change of M1, though no caller's code changes. "Before" is master; "after" is this landing. A *row* is a row of the main document's log unless it says otherwise.

| caller | how it writes | before | after | the write that must still happen |
|---|---|---|---|---|
| A person's open editor: a document, a dashboard, a deck's text box, a design | the renderer's replica, over its port, to `content` | Its own edits, one row each. Also: after it receives an update that deletes text lying between two markers of one key, its copy's deletion of a marker, sent as the person's row (measured: the third row of S1's second order). And when the person's own edit is such a deletion in the live copy (S1's first order), the frame is refused and the document evicted. | Its own edits, one row each, and nothing else. | Every edit of the person's, with the editor's repairs of that edit in the same row (M2). |

## The sequences that must hold

The landing adds no act that waits for something. What it changes sits under three sequences that already exist and one it adds (S4), and each gets a test that holds the sequence open, not only a test of the final state.

**S1 · Two writers at once.** Events: writer A's update reaches the live copy; writer B's update, made before B's replica had A's, reaches it; each is relayed to the other. States: each replica and the live copy hold a set of structs and deletions. Linearization point: the live copy's apply, in arrival order. What must hold: (1) after the first update, one row credited to its writer; (2) after the second, one row credited to its writer, no eviction and no closed connection; (3) after both relays, the three docs hold the same structs and the same deletions and render the same text and formats, no replica has anything unsent (`unsaved` 0), and the log holds two rows and no third. The case: one writer bolds a word while the other deletes that word, which leaves the word's two markers around nothing in every doc. Both orders are tested, because they fail differently today (measured, Surprises & Discoveries): when the bold lands first, the deleter's frame is refused and the document is evicted for everyone; when the deletion lands first, both land and the bolder's replica then writes a third row, its clean-up, credited to the bolder.

**S2 · A write during a redraw.** Events: a remote write that leaves a block that is no paragraph last reaches an open editor (the binding's transaction); a redraw is dispatched (presence, the provisional layer, focus, the undo manager's swap); the person clicks or selects; the person composes; the person makes a plain change. §B's table says what each batch gets. What must hold: after the remote write, after each redraw and after each selection, the replica has sent nothing, the host's revision has not moved and the last block is unchanged; during a composition and at its end there is still no paragraph, while the composition's own input is sent; at the person's first change outside a composition exactly one update leaves the replica, and it holds that change and the paragraph; a redraw after that writes nothing. The tests dispatch in this order and assert after each step, in the editor's DOM suite and, with the rows read from disk, through the real store.

**S3 · A write that fails.** (a) A frame whose work throws after its apply is still taken back whole and the document evicted, and after the replicas re-sync neither the store nor any replica holds anything of it. `service.test.ts` holds this today ("rejects a write whose edit throws, takes back its rows and evicts the doc"; "evicts a doc left with pending state …"; "drops a loaded suggestion doc with its main doc when a main write is taken back …") and those cases stay as they are and green. (b) A transaction on the live copy that names no writer is still refused by `integrated`: the throw stays as the tripwire for a later re-pin that brings a clean-up back, and M1 pins it by a new case, since no test names it today and the "today" cases that exercised it are deleted. (c) A replica whose connection drops re-sends in its next step 2 only its own unacknowledged edits (`port.test.ts`, "moves unacked updates to carried on disconnect …", as it stands); the new case beside it: a replica that had received another writer's deletion of formatted text and had written nothing itself carries nothing into the next connection.

**S4 · The gap caret.** Events: a click in the room under a final block that holds no text, or an arrow key from that block; a remote write; a key typed; a composition begun. What must hold: the caret is set by a transaction that only sets the selection, also when the click leaves the selection as it was, and nothing is sent; a remote write elsewhere leaves it at the document's end with nothing sent; a key typed at it is one update of the person's that keeps the block and puts the character in a paragraph after it; a composition begun at it finds a paragraph made for it, and its text arrives there whole. The first three are held by unit tests. Where a click lands, and what a real input method does, need a layout and are decision 16's scene.

### M2 — A repair answers only the person's change to the content, and a caret after a final block

**What exists at its end.** Opening a document whose last block is not a paragraph, focusing it, scrolling it, clicking in it, selecting text in it, an agent's presence arriving or leaving, a provisional layer redrawn, a block revealed by a link or by the agent's `show_pane`, a pane moved with its selection, an undo that leaves such a block last: none of these writes. A change the person makes to the content through the editor carries the editor's repairs in the same update. The trailing paragraph is among them unless the change is part of a composition; then it comes with the person's next change outside one. Where a block that holds no text (a chart, a table, a rule, a math block, a diagram, a pending upload) has no text position beside it, a click in the room beside it, or an arrow key from it, shows a caret there, called the gap caret below. Nothing is written until the person types, and what they type or compose goes into a new paragraph at that place, with the block kept.

**What it touches.** `src/artifacts/document/schema.ts` (the guard); `src/artifacts/document/editor/extensions.ts` (the gap cursor's plugin); `src/artifacts/document/editor/chrome.css` (the caret's drawing, the room); `src/artifacts/document/editor/nodes/atom.ts` (leaving a field); `src/renderer/src/tools/document/view-carry.ts` (a carried gap caret comes back as one; joined 2026-11-13, decision 12a); a comment in `editor/provisional.ts`. Tests: `src/artifacts/document/schema.test.ts`, `editor/collab.dom.test.tsx` or `editor/awareness.dom.test.tsx`, `editor/DocumentEditor.dom.test.tsx`, `editor/nodes.dom.test.tsx`, a new suite for the gap caret beside them, and a new `src/main/artifacts/document-repairs-store.dom.test.tsx`.

**Interfaces.** Exposes §B. Consumes nothing: no test of M2 involves formatting, so M2 does not wait for M1.

**Decisions.**

6. **What a repair answers (ruled 2026-11-13, "rule II").** A repair changes the document only in answer to a change of the person's to the content. No selection triggers one, wherever it is: the owner's complaint is that looking at a document writes to it, and selecting text to copy is looking. `guard` in `schema.ts` wraps the same four plugins as today and decides by what the plugin answers (§B gives the code). It returns null for an attribution render and for any batch that holds the binding's transaction or one appended to it, as today. Otherwise it lets the plugin answer; an answer that only sets the selection passes, and an answer that changes the document passes only when the batch holds a change of the person's. `isLayerRedraw` and its import leave `schema.ts`; the rule covers the provisional layer's redraws with every other. Rejected: the section's rule, which also counted a move of the caret (it fails the section's own A2, in which the owner selects text); a rule on the resulting selection (a selection that touches the last block gives no caret under an atom, and a click under a final chart can resolve to earlier text, so it neither gives the place to type nor stays out of the way of reading); and refusing every answer to a batch without a change of the person's, which would also stop the table plugin from putting a selection right (`normalizeSelection` in prosemirror-tables answers a selection with a selection: a cell selected as a node becomes a cell selection).
7. **A transaction is read at its root.** ProseMirror hands a plugin only the transactions it has not seen, and marks each appended one with the transaction that started the batch (the meta `appendedTransaction`, set in `EditorState.applyTransaction`); it copies nothing else from the root. So a plugin can be asked about a batch that holds only what other plugins appended. `guard` therefore reads whose a transaction is, and whether it belongs to a composition, on `tr.getMeta('appendedTransaction') ?? tr`. Without this the guard is wrong twice, and both were seen: the caret fix-up that `caretFollowsId` appends to a remote write is not marked as the binding's, and the table repair appended to composed input is not marked as a composition's.
8. **The trailing paragraph waits out a composition.** `TrailingNode`, alone of the four, does not answer a change whose root carries ProseMirror's `composition` meta (set on every transaction a composition's input makes, in `prosemirror-view`'s `domchange.ts`). It answers the person's next change outside a composition. Nothing is written when a composition ends: if the person composes and stops, the paragraph is not there, and the gap caret gives the place to type. Reason: under rule II the first change a person typing Korean makes in an agent's document is composed input, so without this the editor would add a block to the document in the middle of nearly every first composition, and this repository has paid for composition defects before. The other three keep answering composed input as today, because what they repair is the change itself and cannot be made later. Rejected: leaving it to a fallback after a red scene, as the first revision had it, when rule II makes the case the common one; and a write at the composition's end, which would be a write no transaction of the person's carries.
9. **The caret after a block that holds no text is the library's gap cursor.** ProseMirror's gap-cursor plugin (`gapCursor()` from `@tiptap/pm/gapcursor`, which is prosemirror-gapcursor 1.4.1; `@tiptap/extensions` 3.31.3 ships it wrapped as `Gapcursor`) is added by `editorExtensions`, so the editor of a document and of a dashboard has it, and the schema module, the writers and the exports do not. It is added as a local extension that returns the plugin and nothing else: Tiptap's wrapper also adds a field to every node's spec, which nothing here needs. What it gives was read in its source and measured through the real store (Surprises & Discoveries):
   - A click that lands in the editor outside any node, at a place with no text position, sets the gap caret there, whatever the selection was before, in a transaction that only sets the selection. Such places are: after a final chart, table, rule, math block, diagram or pending upload, before a first one, and between two.
   - ArrowRight or ArrowDown from a selected chart with nothing after it sets it too.
   - A key typed at it makes a paragraph there that holds the character, in one update of the person's, and the block stays.
   - A composition begun at it: the plugin's own `beforeinput` handler makes the paragraph and puts the caret in it before the composition's text arrives.
   - A click on a chart still selects the chart: the plugin's click handler steps aside when the click is inside a selectable node.

The binding's cursor plugin publishes it to the other replicas as it publishes any selection's two ends (`cursor-plugin.js` in `@y/prosemirror` 2.0.0-15; read, not run).

   Rejected: a paragraph made by a click under the last block. It writes on a click, which may be a person putting the keyboard in the document to read it, and that is the complaint rule II answers; it gives no route by keyboard; and it needs a hit test of MAWS's own. Rejected before it: the agent's writer adding the paragraph (the section's "Why this, not that").

No export, preview or stored document changes: the HTML export inlines `theme.css`, not `chrome.css`, and the preview's root is not `live`. Rejected: a handler for a click in the page's margin (more code in `DocumentEditor.tsx`, which other landings of the wave edit, for a wider target than the empty paragraph ever was); room only when the last block holds no text (the gap caret's own element is the root's last child while it shows, so the room would come and go with it).

Today something always follows a block atom, because the paragraph is written at the open. ### §A. The constructors (M1; `src/artifacts/yjs/doc.ts`)

      transaction._needFormattingCleanup = false; // Yjs reads this next and would open a transaction of its own

The contract the callers and the tests rely on: **a doc from these constructors runs no transaction and emits no update that its caller did not start, and a writer's own deletion still removes the markers it empties, in its own transaction.**

Three limits, stated so that nobody takes them for covered.

- *The pin is behavioural.* M1's case applies the same update to a doc built with Yjs's defaults, which must delete a marker in a transaction of its own, and to a doc from each constructor, which must not. A case that only read the field after the event would still pass if a later Yjs ran its clean-up before `afterTransaction`; this one fails.
- *What lint holds.* The rule refuses `new Y.Doc(…)` and `new Doc(…)` in `src/artifacts/yjs/` outside `doc.ts`, tests and fixtures, and the existing import rule keeps `@y/y` out of the rest of `src/`. So "every Y.Doc the product makes" is held by lint for the names the module uses today and by review beyond them.
- *Docs the library makes itself* (`createDocFromSnapshot`, `cloneDoc`, the update-to-doc helpers of `@y/y`'s `encoding.js`, a sub-document's `ContentDoc`) carry no listener. No product code calls any of them today; a later use must pass its doc through the same step.

### §B. The repair rule and the gap caret (M2)

`guard` in `src/artifacts/document/schema.ts`; the subtlety is the root and the order, so the code is given:

    const rootOf = (tr: Transaction): Transaction => (tr.getMeta('appendedTransaction') as Transaction | undefined) ?? tr;
    /** A change of the person's to the content: the batch's root changes the document and is not the binding's. */
    const isPersonsChange = (tr: Transaction): boolean => rootOf(tr).docChanged && !isBindingTransaction(rootOf(tr));
    const inComposition = (tr: Transaction): boolean => rootOf(tr).getMeta('composition') !== undefined;

    // guard(plugin, waitsOutComposition = false); only TrailingNode is wrapped with true
    appendTransaction(trs, oldState, newState) {
      if (renderingAttribution(newState) || trs.some((tr) => isBindingTransaction(rootOf(tr)))) return null;
      const answer = append.call(this, trs, oldState, newState);
      if (!answer || !answer.docChanged) return answer ?? null; // a selection put right writes nothing
      return trs.some((tr) => isPersonsChange(tr) && !(waitsOutComposition && inComposition(tr))) ? answer : null;
    }

What each kind of batch gets, for a document that ends with a block that is not a paragraph:

| the batch's root | the trailing paragraph | the other three plugins |
|---|---|---|
| the binding's: a remote write, an undo or redo, a rebind; and anything appended to it | not written | not asked, as today |
| a redraw or a selection: presence, the provisional layer, focus, the undo manager's swap, a click, a drag, a reveal, a restored view; and anything appended to it | not written | may put the selection right; change no document |
| a change of the person's inside a composition; and anything appended to it (a table repair) | not written, and nothing is written when the composition ends | repair that change, as today |
| a change of the person's outside a composition | written in the same update | repair that change, as today |

The gap caret is ProseMirror's `GapCursor` selection (`@tiptap/pm/gapcursor`), set by the library's plugin, which `editorExtensions` adds through a local extension. No name is exported for it; `atom.ts` asks `GapCursor.valid` for the place after a node.
