## Purpose

Two things write to a document today though nobody made them.

The first is a tidy-up inside Yjs, the library that holds a document's content. When a copy of a document takes in someone else's edit, Yjs afterwards removes formatting markers that no longer change anything, as a second write of that copy's own which names no writer. In the engine host's copy that write is refused: the agent's edit that caused it fails with "the live doc … was edited outside a replica", the document is reset for everyone who has it open, and the agent's next edit is refused as stale. In a copy that only received the edit (a person's open editor, an agent's own copy) the tidy-up is sent on as that reader's edit.

The second is the editor's trailing paragraph. A document whose last block is not a paragraph gets an empty one appended by the editor at its next transaction of any kind, and that can be a pure redraw: an agent's presence arriving, the keyboard entering the editor, the undo history attached a moment after every mount. So opening an agent's document that ends in a list, a table or a chart, or leaving one open while an agent works in it, writes a revision credited to the person at the window.

After this landing an agent's edit that takes the bold off part of a bold run lands at the first call, as one revision credited to the agent, and the next edit made from the revision that call returned is accepted. Accepting a suggestion, restoring a version and duplicating a document across such an edit each land as one revision of the person who did it. A copy that only receives writes nothing. A document loaded from disk holds exactly what its log holds. And the editor adds its trailing paragraph only with an act of the person's own in that document: a change to it, or a move of the caret.

**What a trial leaves in the artifact store, and what crosses between builds.** Nothing about the stored form of a document or a deck changes: no table, column, key, encoding or version, and the recorded binding version stays `y14-rc28/ypm2-15`. What can differ is content: a document written by this build can hold formatting markers that change nothing and that Yjs's tidy-up would have deleted. Build F (commit `f1852de3a`, on the owner's machines) opens such a document as it opens its own, with no refusal and no revision; while it loads the rows it may remove some of those markers in memory. An editor of this build attached to a host of build F, which happens for a document on another machine and in the minutes after a build swap, writes what F's own editor writes. An editor of build F attached to a host of this build can still send its tidy-up as its reader's edit; that is F's defect and ends with F. Interfaces §D has each case and its proof.

**How to see it working.** In the suites: the tests named under each milestone, first of all `src/engine-host/tool-server/documents-format-cleanup.test.ts`, which the check of 2026-11-12 wrote with its expected behaviour as cases that fail today. On the wave's build by hand, in a session MAWS runs: ask the agent for a document whose list items begin with bold text and which ends with a table, and open it (the opening adds no revision, and no empty line appears under the table); ask the agent to rewrite one item so that part of the bold text stays without the bold (the answer names a new revision and nothing is refused); click into the text (one revision of yours, the empty paragraph under the table) and leave the document open while the agent edits again (each edit one revision, the agent's, and none of yours).

## What the code holds today

Checked at master `48619c824` and in `@y/y` 14.0.0-rc.28 (the pin). Master moved to `6e8c72738` while this was written; no file this document names under `src/`, `e2e/` or the repository's root changed between the two. Terms used below: the *live copy* is the one authoritative Y.Doc per open artifact in the engine host (`DocumentService` in `src/engine-host/documents/service.ts`). A *replica* is a copy of it synced over a port: a person's open editor, an agent session's own replica, or the host's replica of one actor, through which every host-side write is made. A *row* is one entry of the update log (table `artifact_updates`: sequence, actor, bytes) and is one revision. A *marker* is a formatting marker, Yjs's `ContentFormat` item: a zero-width item in a text that turns a format on or off from that point. A marker is *redundant* when removing it changes no character's format.

**Yjs's two clean-ups, and the one flag.** Yjs removes redundant markers at two moments, and `doc.cleanupFormatting` gates both.

- *The writer's own.* When a transaction deletes text, `deleteText` (`src/ynode.js`) calls `cleanupFormattingGap` on the gap it leaves. This runs inside the writer's transaction and its deletions are part of that transaction's update.
- *The post-apply one.* When a transaction that is not local (an applied update) changes a text that holds formatting, the type's `_callObserver` sets `transaction._needFormattingCleanup`. After the `afterTransaction` event, `cleanupTransactions` (`src/utils/Transaction.js`) reads that field and the flag and calls `cleanupYTextAfterTransaction`, which opens a new transaction with origin `null` and deletes what it finds. This second transaction emits its own update. What it finds in practice is narrow (measured): a marker beside text that the applied transaction deleted, when the gap that text leaves holds two markers of one key. That is the shape every test of M1 uses.
- An update applied inside a transaction already open on the same doc joins it and makes it not local (`readUpdateV2` in `src/utils/encoding.js` sets `transaction.local = false`), so the post-apply clean-up then runs when the enclosing transaction ends.
- `cleanupFormattingGap`, `cleanupContextlessFormattingGap` and `cleanupYTextFormatting` each return at once when `doc.cleanupFormatting` is false (`src/utils/transaction-helpers.js`, `src/utils/Transaction.js`). So the flag switched off removes the writer's own clean-up as well as the post-apply one. `Doc`'s constructor sets it to `!isSuggestionDoc`: suggestion documents already run with both off.

**Where the product builds a Y.Doc.** ESLint allows `@y/y` only under `src/artifacts/yjs/` (the binding module, charter X24). In it, `new Y.Doc` is called in five files: `doc.ts` (`newDoc`, gc on; `newSuggestionDoc`, gc off and flagged as v14's suggestion doc), `suggest.ts` (`scratch`, the docs an accept or a reject is planned on), `revert.ts` (the scratch doc a restore's update is computed on, and an empty doc for the empty answer), `versions.ts` (`canonicalV2`) and `document.ts` (`newDocGcOff`, history's throwaway docs). `newDoc` has about fifty call sites in about forty files: the live copy and every replica (`service.ts`: `loadDoc`, `hostReplica`, `writeCopy`; `replica.ts`; the renderer's `Replica` in `src/renderer/src/artifacts/host.ts`), and scratch copies that are read once (export, search, retention, the library's mirror, the kinds' readers).

**The host.** `integrated`, the live copy's update listener, accepts a row only from a connection or a host replica and throws "the live doc of … was edited outside a replica" for any other origin; loads and a main doc's updates flowing into its suggestion doc are exempt by their own origins. `inFrame` then takes the frame's rows back and evicts the document, and the caller answers "… failed and the document was reset: …". The listener is attached in `open` after `loadDoc` returns, so a clean-up during the load changes the live copy without a row. A host replica forwards every update of its own doc but the mirror's (`hostReplica`, `writeCopy`), whatever its origin; so does `PortProvider.onDocUpdate` in `src/artifacts/provider/port.ts`, which skips only the frames it applied itself. No test names the refusal's message, and no test pushes a formatting change through the live copy and a replica.

**Applies that run inside a transaction.** The restore's revert (`restoreArtifact` in `restore.ts`), the accept's deletions and the reject's copy (`planAccept` and `planReject` in `suggest.ts`, which call `Y.applyUpdate` directly), the proposal's removal in `settle` (a suggestion doc), and, beyond the check's list, the source's state applied by a duplicate (`copyOf` in `store.ts`). Any `initial` a create is given, and a kind's `migrate`, may do the same.

**Two builds on one document.** A document on another machine opens through the same replica, its port bridged to that machine's document service (`src/renderer/src/artifacts/host.ts`, the P5 O7 M5b note). And after a build swap the app of one build is served by the kept engine host of the other until that host is idle (`e2e/cross-build.spec.ts`, its head comment). So an editor of this build on a host of build F, and the reverse, are ordinary states. `src/artifacts/yjs/`, `src/artifacts/provider/` and `src/engine-host/documents/` are byte for byte the same in F and at this base (`git diff f1852de3a 48619c824 -- <those paths>` is empty).

**The editor's repairs.** `guard` in `src/artifacts/document/schema.ts` wraps the `appendTransaction` of four plugins (the link's, `linkRepair`, the table's, Tiptap's `TrailingNode`) and returns null when an attribution is rendered, when any transaction of the batch is the binding's (`isBindingTransaction`), or when every transaction is the provisional layer's redraw. `TrailingNode` is the only one armed by state: its plugin state says whether the last block is something other than a paragraph, and it inserts at any call. The transactions that change neither the document nor the selection and reach it today are: the presence redraw (`editor/awareness.ts`), the binding's cursor plugin on any awareness change (`@y/prosemirror`, `cursor-plugin.js`), the comment threads' redraw (`editor/comments/plugins.ts`), history's paint (`editor/history/paint.ts`), Tiptap's focus and blur, and the undo manager swapped into the plugin a microtask after every mount (`collab.ts`, and `keepUndoManager` in `src/renderer/src/tools/document/view-carry.ts`). The last one runs at every open of an editable document, so opening is enough to write the paragraph. Two dispatches set the selection with no gesture of the person's in that editor: a reveal asked from outside (`TabEditor` in `editor/DocumentEditor.tsx`: a link's fragment, or the `at` of an agent's `show_pane`) and the selection put back after a pane move (`restoreDocumentView` in `view-carry.ts`). A click where the caret already is dispatches no selection (`prosemirror-view`, `updateSelection`).

## The sequences that must hold

The landing adds no act that waits for something. What it changes sits under three sequences that already exist, and each gets a test that holds the sequence open, not only a test of the final state.

**S1 · Two writers at once.** Events: writer A's update reaches the live copy; writer B's update, made before B's replica had A's, reaches it; each is relayed to the other. States: each replica and the live copy hold a set of structs and deletions. Linearization point: the live copy's apply, in arrival order. What must hold: (1) after the first update, one row credited to its writer; (2) after the second, one row credited to its writer, no eviction and no closed connection; (3) after both relays, the three docs hold the same structs and the same deletions and render the same text and formats, no replica has anything unsent (`unsaved` 0), and the log holds two rows and no third. The case: one writer bolds a word while the other deletes that word, which leaves the word's two markers around nothing in every doc. Both orders are tested, because they fail differently today (measured, Surprises & Discoveries): when the bold lands first, the deleter's frame is refused and the document is evicted for everyone; when the deletion lands first, both land and the bolder's replica then writes a third row, its clean-up, credited to the bolder.

**S2 · A write during a redraw.** Events: a remote write that leaves a non-paragraph block last reaches an open editor (a binding transaction); a redraw is dispatched (presence, the provisional layer, focus, the undo manager's swap); the person types or moves the caret. What must hold: after the remote write and after each redraw, the replica has sent nothing, the host's revision has not moved, and the last block is unchanged; at the person's first transaction, exactly one update leaves the replica and it holds both the person's change and the paragraph; a redraw after that writes nothing. The test dispatches in this order and asserts after each step.

**S3 · A write that fails.** (a) A frame whose work throws after its apply is still taken back whole and the document evicted, and after the replicas re-sync neither the store nor any replica holds anything of it. `service.test.ts` holds this today ("rejects a write whose edit throws, takes back its rows and evicts the doc"; "evicts a doc left with pending state …"; "drops a loaded suggestion doc with its main doc when a main write is taken back …") and those cases stay as they are and green. (b) A transaction on the live copy that names no writer is still refused by `integrated`: the throw stays as the tripwire for a later re-pin that brings a clean-up back, and M1 pins it by a new case, since no test names it today and the "today" cases that exercised it are deleted. (c) A replica whose connection drops re-sends in its next step 2 only its own unacknowledged edits (`port.test.ts`, "moves unacked updates to carried on disconnect …", as it stands); the new case beside it: a replica that had received another writer's deletion of formatted text and had written nothing itself carries nothing into the next connection.

## Plan of Work

Three milestones. M1 and M2 share no code and no test and differ in what they verify (the host and Yjs; the editor and ProseMirror), so each is one executor's unit and one reviewer's pass; M2 does not consume M1. M3 holds what needs both: the e2e scenes, the record and the acceptance run. Each leaves the tree green.

### M1 — No document MAWS builds writes after an apply

**What exists at its end.** In a session MAWS runs, an agent's `replace_text` or `replace_block` that takes the bold off part of a bold run lands as one row credited to the session, and a second edit from the returned revision lands. An accept, a restore and a duplicate across such an edit each write one row of the person's. A replica that receives another writer's update, or first syncs a state that holds redundant markers, sends nothing. A document reloaded from the store holds what it held. One writer bolds a word while another deletes it: both land, in either order, as two rows. Every Y.Doc in the product comes from one of three constructors in `src/artifacts/yjs/doc.ts`.
