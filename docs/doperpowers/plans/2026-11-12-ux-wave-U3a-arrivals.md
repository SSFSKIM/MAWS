## Purpose

After this landing, what enters a session from elsewhere reads the same whichever way the session reaches the window, and takes one line:

- A message from another session or from a subagent is one dim line led by `›`. A click shows the whole message under it, and the line folds with its turn. A subagent's hand-back report is that one line for its agent's end.
- The owner's own `sminos send` or steer is the owner's bubble with sminos's frame line cut, never a message "from human". A peer's delivery is never the owner's bubble, on any route. That includes the one the owner saw: a peer's message that sminos typed in as the prompt of a background session it resumed, which today is the owner's bubble with Copy and Edit and the frame line raw.
- The end of a background command or of a monitor is one line where the agent was told, in the engine's own sentence, led by a dot in green, red or yellow. A failed background task raises no error card, no Needs you entry and no notification.
- A scheduled prompt's firing is one line. An answer to an asynchronous question and the sminos bridge's wake keep the line they have today on the route that had it, and gain it on the other.
- A slash command's output is an output on every route: in a session MAWS runs it stops reading as an answer paragraph. It keeps today's "Command output" card until the second landing restyles it.
- A turn that a subagent's hand-back opened reads "Continued for …", no longer "Peer session worked for …".

Behind that is one pure reader, `src/shared/engine/arrival.ts`, asked by the three places that turn the engine's frames and rows into events: the engine host's normaliser for a session MAWS runs, the transcript-file backfill for a terminal session on this Mac, and the reader of another machine's rows. Each turns a class into the same events, so the transcript's model cannot tell the routes apart. U1, U2 and U4 build on the names this landing exposes (Interfaces and Dependencies), which is why it lands first in the transcript's model (UC-3).

How to see it working: the table test of the reader over the probes' recorded carriers fails at the commit that adds it and passes at the head; one recorded session, mapped from its journal, from its transcript file and from the same rows as another machine sends them, gives the same arrival rows but for the differences Acceptance 7 lists; in a running build the scenes of Acceptance 13 read as the child's A1 to A5 say.

## Decisions settled at authoring

Each is a point the section leaves to this document. The reason and the alternative that lost are with it; the exact shapes are in Interfaces and Dependencies.

1. **The fixtures come from master.** The probe branches land first as one pull request (the architect's ruling of 2026-11-12; the owner agreed). M1 opens with a merge of master and checks that `spikes/protocol-probe/fixtures/uxwave/` and the four `findings-uxwave-u3-*.txt` files are there; it does not merge `origin/ux-wave/probe-arrivals`. In that pull request the arrivals scenarios' shared helper is `scenarios/pass3/uxwave-common-arrivals.mjs`. Rows this landing writes by hand stay inline in its tests (Constraints, UC-11, for what the static job's secret scan refuses).
2. **The reader is shared code.** `src/shared/engine/arrival.ts` imports nothing from `src/renderer/` or `src/engine-host/`. The parsers it needs move under `src/shared/engine/` and the modules that held them call them; an export another module imports stays where it is as a thin caller (the desk web app imports `askAnswers` and `deliveredLines`; `deliveryFrame`, `supersededDeliveries`, `isBridgeRow`, `bridgeRowKind` and `BRIDGE_PLUGINS` serve placement). Lost: the reader importing the renderer's modules, which the engine host cannot load.
3. **`arrival` on X1 is a list.** One carrier can hold several arrivals (rule 3), so the field is a list of the carried classes, absent when the carrier holds none. An empty list has one meaning (decision 8).
4. **An arrival that is not the person's is never a prompt.** Every caller emits with `isSynthetic: true`, whatever the carrier's own flag says: every `user.message` the reader claims as `peer` or `subagent`; every `user.message` that carries `arrival` under an origin other than `human`; and every `user.message` of origin `task-notification`, whether or not it carries one. Without it a peer's row that has no `isMeta` (one the bridge submitted as the user, one typed in as a background session's prompt) opens a second, pending turn of the person's beside the peer's turn and draws there as a bubble with Edit (the review's finding 2), and a replayed notification frame opens a turn that waits for ever, unseen. A text of origin `peer` that no class claims keeps the flag and the bubble it has today, and so do messages of the other origins (`local-command`, the interrupt marker, a channel's or a coordinator's). Lost: a new branch in the reducer for these messages, where the existing rule for a synthetic message already keeps one on the running turn.
5. **Where a row sits is read from the events' order, not from a new field.** An arrival that stands before all of its turn's work is at the turn's head; one after work began stands at that point. At the head, a `task` notice with an outcome and a `schedule` notice go above the divider (in a turn the person's prompt opened, directly above the prompt), and every other class is the first row under it. This one rule gives the child's "Where a row sits" on all three routes: a turn's opener, a task the host stopped (delivered at the head of the person's next turn), and what a running turn took in.
6. **An engine turn that held nothing is no turn.** The reducer removes a turn the engine opened that held nothing (no event that draws a row and no model output; in both recorded cases it holds its own start alone), in two cases: its end says it ran nothing (`numTurns` 0), or another turn starts over it. The first is the empty turn the engine reports after an idle hand-back (rule 5: "no turn beyond the one the arrival opens"). The second is what lets the owner's own send, which reaches a session MAWS runs through the inbox, open the person's turn although `system/init` had already opened the engine's (pitfall 5 of the section). Lost: holding `turn.started` back in the normaliser until the next frame says what the turn is, which would send every event between `init` and that frame to the model with no turn open; leaving both to U2's "a turn in which nothing happened draws no line", which would leave the callers disagreeing until U2 lands. Accepted by the architect on 2026-11-12: U2's rule keeps the drawing only (Surprises & Discoveries, 5).
7. **How the live caller keeps a task's end until the model is told** (the state, the transitions and the points where a line is placed, settled, withdrawn or given up) is the table of Interfaces, E. Three choices in it are this document's: only a `local_bash` task that was in the background is kept, the two forms the probe ran (a workflow run, an MCP task and a remote agent were not run, and by law 6 nothing here depends on their frames; their lines appear once the session is read from its file); a scheduled fire is held from its `command_lifecycle` frame to the `init` after it and no kept notice is placed on that turn; and a kept notice is given up when the engine next goes idle after a turn opened that did not name it. The last is the bound that keeps a line the engine never tells from being placed on every later turn; `system/session_state_changed` with `state: 'idle'` is sent only when the engine's queue is empty: where a turn follows a result with nothing new between them, no `idle` stands between (`u3-tasks-r1`, seq 157 to 159, 354 to 355, 739 to 740, 752 to 753, 762 to 763; `u3-tasks-r2`, 589 to 590, 599 to 600, 609 to 610), and where an `idle` does stand, what opens the next turn arrived after it (`u3-tasks-r1`, the `idle` at 56 and the frame at 58).
8. **A placed line is withdrawn by a second event, not by a new event kind.** Two arrival-bearing synthetic messages under one `messageUuid` are one arrival: the first stands; a later non-empty carrier is another form of it and changes nothing; one whose `arrival` is empty withdraws it, and the next non-empty carrier then places it anew (revised 2026-11-13 by the architect's ruling, Decision Log; it was "the later stands where it arrives"). Lost: an event kind for the withdrawal (a build that does not know it draws a gap, UC-2); drawing only at the `result` (the root's Decision Log rejects it).
9. **The words of the `answer` line are the model's.** The event carries the arrival (`call`, `summary`); `derive.ts` words the line from `summary` and the questions of the call it finds in the transcript, with the function that words it on the remote route today (`answeredWords`), which moves beside the model. Lost: wording it in the caller, which would put the model's words in three places.
10. **The `consent` line is a `user` row with a `consent` field, and this landing draws it.** UC-2's table fixes its look ("You approved `<subject>`", never a bubble, in view through a fold as the person's words are) and UC-3 gives the `user` row to U3. The `notice` row cannot hold it: its classes are the four the contract lists, and a notice is the engine's fact where this is the person's act. U1c then only sends the sentence, built by `consentMessage` so that the sentence has one definition. Lost: leaving the line to U1c, which would have U1 edit U3's row.
11. **A notice's id is what both forms of a session share.** `notice:<run id>` when the arrival names a run, else its message's uuid with its place in the carrier. The model already drops a row whose id is shown, which is what keeps one line when a session's history reaches the store from its journal and from its file.
12. **An unlisted `<status>` word claims no end.** `error` stays `failed`, as the parser that moves reads it today; a word rule 6 does not list gives `outcome: null`. Lost: today's default of `completed`, which the section's pitfall 1 names.
13. **Task state is not an arrival.** A notification still ends its task for the task graph and for the subagent's row (`subagent.finished`, `task.notification`) whether or not the reader yields an arrival for it; a block with no outcome ends nothing. The notification rule 5 leaves out after a hand-back therefore still finishes its agent on the file and remote routes.
14. **`revealed` lands here.** UC-3 has U3 write it and U2 read it; this landing's own asks must honour it, and U2 starts from this landing. It is one optional field of the tab's `ui` (Interfaces, F).
15. **Which rows ask a site.** A row asks only when its event came from a frame or row the engine wrote (its text is the site's `text`): an arrival the engine host made itself (a task's end told while idle, a scheduled fire) asks none, as the section says. The classes asked are the ones the engine's own transcript passes through its `UserMessage` site, read in the engine's bundle before the mounts are written (M5).
16. **The tail's proof in two e2e specs changes its vehicle.** `e2e/supervisor.spec.ts` and `e2e/cross-build.spec.ts` prove that events journaled while no app ran reach main's listeners by the "Background task failed" item, which O-34 removes. They take another item that only that derivation raises and that every build of a cross-build pair raises: the "auto mode unavailable" item, which the review confirmed at build F (M6). It does not carry the ruling that a seen error retires; the unit suite holds that for a turn's error.
17. **`own` keeps the guard of pitfall 3 as today's code has it.** When the words alone are the engine's interrupt marker, `words` keeps the frame line before them; the caller emits them with origin `human`, which the model never reads as a marker.
18. **A dismissed question is an `answer` with `dismissed: true`, and its line says `dismissed`.** The sminos bridge's dismissal (doperpowers pull request #497, to ship as sminos 1.47.0; verified live by its author on 2026-11-12, not by U3's probes) delivers, by the same carriers as an answer, the head every answer has and then "The human dismissed these questions without answering them; no answer will come. Do not wait for one." The reader splits a carrier at each head, takes what follows as `summary`, and sets `dismissed` when that text is this sentence whole; the `answer` class gains that one field (the architect adds it to the child's union). The line's words for it are the root's (UC-2, "or 'dismissed'"). The engine's own refusal sentence, which a declined dialog in the terminal delivers, is not a dismissal: it reads "Skipped" as today.
19. **A delivery typed in as a background session's prompt is a delivery** (the architect's ruling of 2026-11-12, from the trace of the O-41 sighting; the architect writes it into the child's carrier table). A `user` row of origin `human` whose own `sessionKind` is `'bg'`, with string content whose first line `sminosFrameSender` reads as a whole frame line and words after it, is class `peer` when the frame's sender is not `human` and class `own` when it is. Both frame forms (chat and message); `promptSource` `typed` and `queued` alike, never a reason to reject. sminos makes such rows two ways: it resumes a stopped background session (a seat) with the frame and words as its prompt, whoever sent them, and an owner's event to a background job with no bridge goes through the engine supervisor's reply. The carrier exists on the file route and in another machine's rows, never on the live wire of a session MAWS runs. `peer.via` gains the value `'prompt'` for it. The `sessionKind` condition stays: without it an ordinary prompt in a terminal that opens with a pasted frame line would be reread. With it one ambiguity remains and is accepted: a person who types or pastes a whole frame line as the first line of a prompt in a background session is read as that delivery. This is attribution for display, not an authenticated sender. The row stays the engine's prompt row for everything that is not drawing (M3, the follower's predicates).
20. **How `arrival` grows.** U3b will add a `command` entry so that `run` can travel (the architect's ruling on Surprises & Discoveries, 3). So the rule for a later class is fixed now: a reader ignores an entry whose `class` it does not know and validates the classes it knows strictly, and a list that holds only entries it does not know is not the empty list that withdraws a line. Without it one unknown class fails the whole event, which the tolerant reader cannot strip and the machine link then draws as a gap (`src/shared/ipc/tolerant.ts`; `src/main/lane-b/remote-session.ts`).
21. **A provisional line does not outlive its launch.** A notice placed when a turn opened is unconfirmed until that turn's `result` (Interfaces, E). When the launch ends first, the normaliser withdraws it on the launch's exit row, before `process.exited`. When a launch has no exit row (its host died and the exit the model sees was made outside the journal, or the next launch simply starts), no row can carry a withdrawal, so the reducer holds the same rule from its side: a turn that is closed without a `turn.ended` of its own, by the process's exit or by a later turn's start, loses a `task` arrival the host made that stands at its head. An interrupt marker's close does not: the turn's `result` still comes and settles or withdraws it. Lost: the normaliser's withdrawal alone, which leaves the line for good above the wrong turn whenever a host dies (the review's finding 3).
22. **"Open output" is an optional action of the transcript, and a notice draws it only where the mount gives an act** (Interfaces, I; the review's finding 4). The app's adapter gives one for a session MAWS runs, on this Mac or another machine, through the Log tool the background work list's Output button opens. For a terminal session it gives none, as that list passes no Output handler for one today ("a lane A job's tail is remote-only"), and the desk web app registers none: its Jobs pane stays the way to a job's output there. Lost: a default that does nothing behind a button that is always drawn.

### B. X1 (`src/shared/graph/events.ts`)

`user.message` gains `arrival: z.array(ArrivalEntrySchema).optional()`, and `task.notification` gains `arrivals: z.literal(true).optional()` (the whole-branch review's finding 3, the architect's ruling; Decision Log, Fix B): set by every producer that reads arrivals (the live normaliser, `normalizer-system.ts`, and the backfill, which also serves another machine's rows), whose task's end an arrival tells, and absent on an older host's events, whose `task.notification` is the end's one telling. The model draws its fallback line only for an unmarked event, and not while the window holds the same task's end arrival (Interfaces, D; Decision Log, Fix D and Fix E). Nothing else in the file changes. The rules of reading `arrival`, for every consumer:

- absent: the message carries no arrival of the five classes;
- an entry whose `class` this build does not know is ignored, and an entry of a class it knows is valid field for field or the event is refused; consumers read the field through `carriedOf`;
- on a message whose origin is not `human`: the message is synthetic and never a prompt; each entry is one row;
- on a message whose origin is `human`: only `consent`, on the person's own prompt or steer;
- two synthetic messages with one `messageUuid`: one arrival, the first standing; a later non-empty carrier is another form of it and changes nothing; an empty list withdraws it, and the next non-empty carrier then places it anew; a list that holds only entries of unknown classes does neither and leaves what stands. A caller that moves a line withdraws it before placing it again (Interfaces, E).

### E. The live caller: keeping a task's end until the model is told

State added to `NormalizerState` (the names are the executor's):

- the reader's `OpenArrivals`;
