## Purpose

An agent often links a file by its absolute path, and the file is often outside the folders its session works in: another repository, a downloads folder, a temporary folder. Today a click on such a link opens a tab that says "Refused: path outside the session's directories", on every machine, because MAWS's files service reads only a session's own folders.

After this landing, on this Mac, that click opens the file, read-only. The rule is the click itself: a file outside the folders opens when the session's own transcript writes its path, whole, as a link or a file chip the window can be clicked on. Text, code and images are drawn in the tab as a file inside the folders is drawn; a kind MAWS does not draw (a PDF) gets today's row, and its "Open externally" button works. The process that reads the file checks the path against the transcript before it reads. Nothing can be written through MAWS to such a file, and its folder is never listed or watched. A session on another machine keeps today's refusal.

How to see it working: in a session whose transcript holds a link to a text file outside its folders, click the link. The file's text shows in a file tab; typing changes nothing and the editor's title says the file is outside the session's folders. A link to a PDF outside the folders shows "PDF files open outside MAWS" with "Open externally". Asking for a path the transcript does not write as a link still shows the refusal, and so does a path that only begins a longer name the transcript links.

## What the code holds today

Read at master `c0e7b2ae8`; build F is `f1852de3a`.

1. **The click.** A Markdown link with no scheme becomes `maws-path:<url>` (`remarkTranscriptSources`, `src/renderer/src/transcript/view/markdown/sanitize.ts`). `TranscriptLink` (`markdown/Link.tsx`) draws it as a chip and on a click calls `actions.openFile(path, line, session)`: `path` is the href after `decodeURI`, less a trailing `#L<n>` or `:<n>`; `session` is the row's session (`useRowSession`, `view/context.tsx`), which for a subagent's rows is the parent's. Tool rows open files the same way (`ReadDetail.tsx`, `EditDetail.tsx`); "The click sources" lists every place and what each reads.
2. **The tab.** `openFile` (`src/renderer/src/tools/code/open-file.ts`) collapses `.` and `..` without touching the disk (`normalizeLexically`) and calls `openTab({ kind: 'file', path, line, appSessionId, machine })`. The tab's id is `file:<machine>:<path>` (`tabId`, `src/shared/ipc/schema/layout.ts`): one tab per machine and path, whichever session opened it.
3. **The read.** `FileViewer` mounts `FileBody`, which mounts the tab's entry in the viewer store (`viewer/viewer-store.ts`). The store first takes a watch on the file's folder (`files.watch`, through the Files store), then reads: `files.read { appSessionId, path, offset, length, hash? }` (`readChunk`). For a file outside the folders the watch is refused and the read goes on. A failed read sets the entry to `error` with the message, drawn by `Refused` in `FileViewer.tsx` as `VIEWER_COPY.refused(message)`: "Refused: path outside the session's directories". Nothing reads again until the tab is closed and reopened (the store's header: "nothing retries it").
4. **The route.** Renderer client, preload, main's router (`src/main/ipc/router.ts`), which validates the input strictly and, for a session on this Mac, sends it to `mawsd` over `machine.sock`; `mawsd`'s front (`src/mawsd/front.ts`) reads the input with the tolerant reader and calls the handler `registerFilesHandlers` registered (`src/services/files/register.ts`) with the context `{ client }`. For a session on another machine main's lane B adapter sends the input as it is over the machine link (`src/main/lane-b/remote-files-read.ts`); that machine's endpoint checks it strictly against the schema (`src/endpoint/authorize.ts`) and its front calls the same handler with `remote: true` in the context, which only the front's two entries for the endpoint set (`front.ts`, `dispatch` and `intercepted`). What decides the route is the machine in the session's address. (A terminal session on another machine goes through the lane A route and the machines manager, which was not traced here; the window sends it nothing new either.)
5. **The process.** The files service runs in `mawsd` only. `startCheckouts` (`src/services/checkouts-root.ts`) composes it in the spine's root (`src/services/spine-root.ts`), which only `src/mawsd/spine-seam.ts` starts; the "embedded" binding is the suites'. (The comment at the head of `checkouts-root.ts` still names main.)
6. **Where the service decides.** `precheck` (`src/services/files/service.ts`): the path must be absolute and already normal; the session must have a record (or a setup intent: `allowlistOf`, `allowlist.ts`); `rootsOf` gives the real paths of the record's directory, added directories and worktree, less the machine's home for a remote caller; the path's real path must lie under a root, or, for `read`, `openExternal` and `reveal` only (`DELIVERED_TOO`), be a file the session's delivered files name (`fileAdmission`, `admission.ts`), which then stands as a root of one for the rest of the boundary; a path that ends in a link is refused. `write`, `list` and `watch` take roots only. A path that does not resolve answers `not found` only inside a root, else the refusal (`missing`). After the check `read` opens the real path with no link on its way, and confirms the opened object again under the roots (`openConfirmed`, `confirm`).
7. **The row that opens a file outside MAWS.** For a kind MAWS does not draw, `ExternalRow.tsx` offers "Open externally" when the name is on the list (`opensExternally`). It calls `openSessionFile` (`src/renderer/src/lane-b/open-copy.ts`, U9's file): `files.openExternal { appSessionId, path }` unless the session is a session MAWS runs on another machine (then a copy is fetched here). In `mawsd`, `openExternal` runs `precheck` with `DELIVERED_TOO` and no `remote` argument, requires a regular file with no execute bit, and asks the client port, which reaches main, where `shell.openPath` runs (`src/main/client/electron-port.ts`). The endpoint does not offer `files.openExternal` or `files.reveal` to another machine (`src/endpoint/offers.ts` has no row).
8. **A terminal session.** The same on every point above. The window reads its rows from the transcript file; the link, the tab, the request and the service's decision do not differ, and its record has the same three kinds of folder.
9. **Where a transcript is.** `<config home>/projects/<slug of the folder>/<engine session id>.jsonl`, one store for a session MAWS runs, a terminal session and an ended one. The spine finds it by one rule, spelled three times in `spine-root.ts`: the path the index keeps for the session (`index.sessions.summaryOf(appId)?.transcriptPath`, which the engine host reported), else `transcriptPathOf(engineEnv, record.directory, record.engineSessionId)` (`src/services/sessions/context.ts`). Three spine-side readers already open the file by that rule: `readRecentTurns` (the last 256 KiB), `readRestoredCost` (backwards in chunks, 16 MiB at most) and `TranscriptJobs` (the whole file, by offset).
10. **What a transcript holds.** One JSON object per line. The agent's text and a tool call's input are in `assistant` rows; the person's message, a tool's result (twice: in the message and in `toolUseResult`) and what arrives from elsewhere are in `user` rows. Non-ASCII is written as itself; a quote, a backslash and control characters are escaped. Other types hold no conversation: the `api-request` records the engine writes per model request (three types whose names begin so) repeat the conversation, and with `file-history-snapshot` are two thirds of a 625 MB transcript (`src/engine-host/fs/chain-follower.ts`); `TranscriptJobs` skips them unparsed by the line's first bytes, `{"type":"api-request`; `queue-operation` records hold a message as typed, also one that was taken back before the engine read it (`test/fixtures/transcripts/w1-steer-next-cancelled.jsonl`: the text of the cancelled message is in its `enqueue` record alone). A draft that was never sent has no row. A compaction appends a boundary and a summary and leaves the earlier rows in the file. A fork's file holds its parent's conversation rows again. `/clear` gives the app session a new engine session id and a new file.
11. **A transcript that moves.** When the agent enters or leaves a worktree the engine renames the file into another project folder (the inode stays) and the index learns the new path from the engine host. U8c-1 (`origin/ux-wave/U8c`) keeps the engine host's follows and `TranscriptJobs` reading across the move; it "exposes no name to a sibling".
12. **Build F and the wire.** Master's wire is major 3, minor 36; F's is minor 33. `files.read`'s input is a strict object. A `mawsd` of another build of the major serves this build's window from the connection until `watchDaemon`'s restart lands (`src/main/hosts/daemon.ts`, `checkBuild`), and for the whole launch when the profile's unit runs another bundle; the reverse holds for F's app on this build's `mawsd`. F's front reads a command's input with the tolerant reader (`git show f1852de3a:src/mawsd/front.ts`, `codec.readCommandInput`; `src/shared/ipc/tolerant.ts`, unchanged since F): a key it does not know is dropped and the rest is served. A command it does not know answers `unknown_command`. F's endpoint, strict, answers `malformed` to an input with a key it does not know.
13. **What pins today's behaviour and changes.** `src/renderer/src/tools/code/viewer/viewer.test.tsx` ("renders a refusal in words with the path, and reads no more than once"); every renderer test that asserts a read's exact input for a session on this Mac (`viewer.test.tsx`, `editor/editor.test.tsx`, `src/renderer/src/tools/artifacts/viewers/viewers.test.tsx`, through `src/renderer/src/test-support/code-disk.ts`); `ExternalRow.test.tsx` (the call's input); `src/services/files/service.test.ts` and `register.test.ts` (`openExternal`'s arguments); `src/shared/ipc/wire.test.ts` with the two generated files. E2e specs that cross the code: `e2e/code-tools.spec.ts` and `e2e/code-editor.spec.ts` (`e2e:code`), `e2e/deliverables.spec.ts` (`e2e:deliverables`), `e2e/remote.spec.ts` (`e2e:remote`, the read over the link), `e2e/sessions.spec.ts` (the default `e2e` group), which gains the scene.

**Not clickable today, checked.** A bare path in prose. A path in inline code or in a code fence. An autolink (the bracketed kind needs a scheme; the literal kind matches web addresses and mail only). An image, `![…](…)`: drawn as a chip that names its source and opens nothing. A shell's output, a search's, a web fetch's and any other tool's all-text result: a `pre` (`Output`, `cells/Truncated.tsx`).

A landing that makes another string of a row clickable as a file adds its form here and to the rule in the same change, or that click keeps the refusal outside the folders.

## Decisions settled at authoring, as the rulings leave them

Each names the alternative it beat. The numbers are cited as "decision N". The exact shapes are in Interfaces and Dependencies.

1. **A search of the transcript by the reading process; the request carries no place.** The request says only that the caller knows the rule (decision 9); `mawsd` finds the session's transcript itself and looks for the path in it. *Beat:* a row's or a message's id in the request, checked against that one row. The id buys nothing: the transcript has no index from an id to a place in the file, so finding the row costs the same pass as finding the path, and the window would be trusted with nothing less (it could name any row that writes the path).
2. **Which records count, and which of their strings** (ruling E.1). Of the session's own transcript file:
   - an `assistant` row: its `text` blocks, and every string of its `tool_use` blocks' inputs;
   - a `user` row that is not marked `isMeta` or `isCompactSummary` (the window draws no bubble for those: `userEvents`, `backfill.ts`): its text, which is `message.content` when a string and its `text` blocks otherwise, never a `tool_result` block;
   - an `attachment` record that is a person's message taken into a running turn (click source 1b): its `prompt`;
   - of a tool's result, two things and no other: the text of an MCP call's result, for the link form; an edit call's `toolUseResult.filePath`, for the value form. Which call a result answers is read from the call's own block (its `tool_use` in an `assistant` row, found by the result's `tool_use_id`), never from the result.

   Nothing else counts: the engine's request records, queue records (a message as typed, delivered or not, which is how a path typed and never sent is refused), other attachments, snapshots, titles and summaries, system rows, and every other string of a tool's result. Rows written before a compaction stay in the file and count. A fork's file holds its parent's conversation rows again, and they count for the fork. A subagent's own rows are in its own file and do not count for the session; a side thread is a session of its own, with its own transcript, and a link in it is checked against that transcript and no other: one session's transcript names nothing for another. *Beat:* every string of every `user` and `assistant` row (the first writing): a tool's result is written by neither the agent nor the person, and a search's or a shell's output can list any path on the machine.
3. **What "names" means** (ruling A). A path is named when a counted string writes it whole in a form of "The click sources": as the destination of an inline Markdown link (the link form), as the whole value of a chip's field (the value form), or as the path of an anchored comment's tag (the anchor form). The daemon reads each form's string as the click reads it (for a link: Markdown's escapes, `normalizeUri`, `decodeURI`, the line suffix off, `.` and `..` collapsed) and compares the result with the request's path, whole, byte for byte. A bare mention, a path inside a longer name, and a path with `host:` or any other scheme in front name nothing. *Beat:* "occurs with a boundary on both sides" (the first writing): it admitted `/vault/.env` from a link to `/vault/.env backup`, `/vault/key` from `/vault/key,backup` and from `/vault/key:backup`, and the local `/vault/key` from `host:/vault/key`; no boundary test can tell a path from the start of a longer name. *Beat:* running the renderer's Markdown pipeline in the daemon: a dependency of the window inside the machine's daemon, for what a local check of the text around `](` decides. One limit is kept and stated: a link to an unqualified absolute path that its writer meant for another machine opens this Mac's file of that path, if there is one; the tab's title shows the path.
4. **What is compared and what is read.** Compared: the request's path string and the path each form yields, as decision 3 says, case-sensitive. Read: the object at the path's real path, through the boundary `files.read` already has. So a path through a folder that is a link (`/tmp` on macOS) is read where it leads, as inside the folders today; a path whose last component is a link is refused, as inside the folders today (the transcript names the link, not its target); on a volume that ignores case, a path the transcript writes in another case than the disk's is read, and the same path in a case the transcript does not write is not named. The admitted real path stands as a root of one for the rest of the boundary, as a delivered file's does, so every later confirmation holds for that file and nothing beside it.
5. **What the check stops, and what it does not** (ruling D). It stops a direct request for a path the session's transcript does not write as a link or a chip: from a fault in the window, from a mod's surface, from a caller on another machine. It does not stop a caller that can also put a message into that session, which could write the link first; that message then stays in the transcript, where the person can see it. A read under this rule uses the daemon's access to the file system: that the transcript names a path does not show that the engine was allowed to read it. The card's sentence "so the window cannot ask for other files" said more than this, and the architect tells the owner so.
6. **The cost of one search.** It reads the transcript from its end backwards and stops at the first record that names the path (a link the person clicks is usually among the newest). It parses only the lines whose bytes hold the pieces of the path every naming record must hold (Interfaces §A, `needlesOf`), and never the engine's request records. It reads back 1 GiB at most: that is a bound on completeness, which fails towards the refusal (a path written only in older rows is refused), not the cost design, which is decision 7. A read inside the folders, and a delivered file, never open the transcript. *Beat:* the index's stored text of the session (`session_text`, cheap to ask): prose only, no tool input, behind the file, unarchived sessions alone. *Beat:* asking the engine host: its follow keeps no raw rows, it may be parked or restarting, and an ended session has no follow.
7. **One queue for every use of a transcript** (ruling C). Per daemon: one job runs at a time; requests for the same session and path share one job; at most `NAMED_WAITING_MAX` (8) distinct jobs wait, and a request beyond that gets the ordinary refusal at once; a waiter leaves when its client ends or after `NAMED_WAIT_MS` (8 s, inside a host request's ten), with the refusal; a job with no waiter left stops at its next read and remembers nothing. Why 8: a window asks for the tabs it has mounted, which is one per pane and one beside the chat, and each open file's reads share one job; eight leaves room for two windows and is still a queue a person outwaits in seconds. A scan does not hold the daemon's event loop: it gives the loop back after every read and after every parsed line, and one step is bounded (a read of 1 MiB searched, one line of at most 4 MiB parsed). *Beat:* a worker thread, where the engine host's search parses: that worker is built from functions turned into text, which cannot carry the rule's imports (the anchor's parser and its schema), and `mawsd` has no worker entry; M1's measurement decides whether the yielding is enough. *Beat:* one search per path with no bound on all of them together (the first writing).
8. **What is remembered, and how it is proven again** (ruling B). A found path remembers where its naming record is (offset and length, and the same for the call's record when the name rests on a result form). It is used only after those bytes are read again and still name the path, with the file's identity as before; if they do not, the entry is dropped and the search runs again. A path not found remembers the offset it was searched to (the end of a whole line) with a fingerprint of the bytes before it, taken as the engine host's search takes one (`fingerprint`, `src/engine-host/fs/search-text.ts`: the first and the last 4,096 bytes before the offset); the next ask searches only what was written since, and a fingerprint that no longer matches discards the checkpoint. *Beat:* trusting the file's identity and that it is no shorter (the first writing): a rewrite in place keeps both.
9. **The request's shape: one optional key on the existing commands.** `files.read` and `files.openExternal` take `named: true`; `files.read` answers `named: true` when the file was admitted by name. The key means "this caller knows the rule: admit a file the transcript names, and tell me when you did, because I hold it read-only". *Beat:* a command of its own. A `mawsd` of build F answers `unknown_command` to a command it does not know, which the window would have to turn into today's refusal; it drops an optional key it does not know and answers the plain read, which is today's refusal with no code here. A second command would also be a second boundary to keep equal to the first. *Beat:* no key, the service deciding for every caller. Build F's window, served by this build's `mawsd` (possible on one Mac, "What the code holds today" 12), would then open such files and show them as editable.
10. **The window sends the key only for a session on this Mac.** For a session on another machine the request is today's, to the byte. A key sent there would be refused as `malformed` by an endpoint of build F, an error where today's refusal belongs; and the answer there is the refusal whatever is sent (decision 11). The two call sites are the viewer's read and the "Open externally" button; no other reader of `files.read` in the window sends it.
11. **A caller from another machine is refused where the read runs, before the transcript is opened.** `precheck` reads `remote` from the handler's context (the value the roots are already computed with) and, when it is set, never asks whether the transcript names the path. `files.openExternal`'s handler starts passing the context's `remote` too; the endpoint offers that command to nobody, and the check does not rest on that.
12. **The three routes on this Mac are one.** A session MAWS runs, a terminal session and an ended or archived session whose transcript is still on disk are told apart by nothing in this landing: the rule needs the session's record, its engine session id and the file. A session with no engine session id yet, and one in launch mode `scenario` (whose sessions are a scenario's and whose index is not read), has no transcript and so no named file. One difference is real and is in decision 15: only for a session MAWS runs can the window draw a link before the engine has written its row.
13. **Which transcript.** The file the index keeps for the session when its name is `<the record's engine session id>.jsonl`, else `<config home>/projects/<slug of the record's directory>/<that id>.jsonl`: the rule `spine-root.ts` already uses for the three readers, with the name test added so that a session `/clear` has just given a new id is not read from its old file. It is asked at every request, before the request looks for a job, and a job's key holds the transcript it reads (Decision Log 19), so a request never joins a search of another transcript than its session's, and a transcript the engine moved is found where the index now says; between the move and the index's news the file is at neither place and the answer is the refusal until the next ask (decision 15 has the retry).
14. **Read-only, exactly.** In the service nothing changes for `write`, `list`, `watch` and `reveal`: they take roots only (and `reveal` a delivered file), so the admitted file cannot be written, its folder cannot be listed or watched, and a neighbour is refused unless the transcript names it too. In the window the entry of a file admitted by name is never editable, so the editor is read-only, no Save appears and `save` sends nothing; the reason is the editor's title. Kept, as for a file inside the folders: Wrap, Source, the image's zoom, Load more, "Open externally", and a comment on a line (it sends the path and the line to the session and reads nothing; its chip is click source 4). Not kept: the watch (it is on the folder, and its events name the neighbours); decision 15 replaces it. The tab offers no Reveal and no Copy path today and gains none.
15. **Asked for again, read again.** `revisit`: when the entry's last read failed, or the entry is named, and no load of it is in flight, the file is read again: at once when its tab is mounted, else when it is next mounted. It runs when the tab is mounted again and when `openFile` opens a file whose tab is already open. Whether the file is named is set from every load's answer, also from one that finds the same bytes and lands nothing else; and a load that answers the refusal clears what was shown under an earlier admission. *Why:* a refused read must not stay refused after its cause is gone (the row not yet written, the daemon restarting onto this build, the transcript mid-move, the queue full), and a named file has no watch. *Beat:* the service waiting for the row when a turn is running: latency on every honest refusal, and a second source of truth about the session. *Beat:* a watch on the one file: a new kind of watch in the service for a file read on a click (law 4).
16. **A named path that is gone answers `not found`**, when the failure is `ENOENT` or `ENOTDIR`; a directory the transcript names answers `not a regular file: <path>`, as a directory inside the folders does. A path that is not named answers the refusal whatever is or is not on disk, as today.
17. **Errors of the search are a refusal, and say nothing.** No transcript, an unreadable one, a line that does not parse, a locator that throws, a full queue, a waiter that left: the path is not named, the answer is the service's refusal sentence, and no message carries the transcript's path.
18. **What is withheld outside is what is withheld inside.** By shape: a path that ends in a link, a directory, a special file; for "Open externally", a file with an execute bit or a name off `opensExternally`'s list. Nothing by name: a `.env` or a key file the transcript links opens read-only. The reason is the owner's choice, "any file the transcript names, read-only"; the architect tells the owner what that includes.

## Acceptance

Observable behaviour; the proof of each is named in the milestone that carries it.

- **A1 · The click.** On this Mac, in a session whose transcript holds a link to a text file outside the session's folders, a click on the link opens a file tab that shows the file's text. Typing in it changes nothing, no Save appears, and the editor's title reads "Read-only: the file is outside the folders this session works in". A Markdown file is drawn rendered, an image inline, as inside the folders. The same for a file chip of a read or an edit, and for an anchored comment's chip.
- **A2 · A kind MAWS does not draw.** A link to a PDF outside the folders shows "PDF files open outside MAWS" with its size and "Open externally"; the button hands that file to the system.
- **A3 · What stays refused.** Each answers "path outside the session's directories" and reads nothing: a path the transcript does not write; a path it writes only in prose, in a tool's output or as part of a longer name (`/vault/.env` when the link is to `/vault/.env backup`; `/vault/key` when it is to `/vault/key,backup` or `/vault/key:backup`; `/vault/key` when the text says `host:/vault/key`); a path only another session's transcript links; a path linked only in a message that was typed and never delivered; a path whose last component is a link; a request without the key; a request from another machine, for which the transcript is not opened at all. A directory the transcript links answers "not a regular file".
- **A4 · Nothing beside the file.** With the file open, a listing or a watch of its folder, a read of a neighbour the transcript does not link, a reveal and a write of the file itself are refused, and the file's bytes are as they were.
- **A5 · The routes.** The same holds for a session MAWS runs, a terminal session and an ended or archived session. A session on another machine shows what it shows today, and its request is today's.
- **A6 · Another build.** This build's window served by a `mawsd` that does not know the key shows today's refusal, not an error. A window that does not send the key (build F's) is answered as today by this build's `mawsd`.
- **A7 · Asked again.** A link clicked before its row is written shows the refusal; once the row is written, clicking the link again, or showing the tab again, opens the file.
- **A8 · What a remembered answer costs, and what it rests on.** After a path is found, a later ask reads the naming record's bytes again and no more; a path found in the newest rows is found without reading the older ones; after a miss, only what was written since is searched. A transcript rewritten in place so that it no longer names the path stops naming it at the next ask.
- **A9 · The daemon is not held.** While a search that finds nothing runs over a transcript of the bound's full length, fifty other requests to the files service, one after another, are each answered within 100 ms (M1's measurement). More searches than the queue takes are answered the refusal at once.
- **A10 · Nothing gated got worse.** Typecheck, lint and the unit suite pass; the e2e groups that cross the code pass on a Mac.

## The sequences that must hold

The acts that await something, what the person or the disk can do meanwhile, and the test that holds each open. The service's suite holds its points open with `BoundaryHooks` (it gains the point `before-named`); the search with its own hooks (Interfaces §B); the window's suites with a client whose answers the test releases.

**The search's states and the points everything hangs from.** Per session and path, the search remembers nothing, a hit (where its record is) or a miss (how far it searched, with a fingerprint). A hit is trusted only at the moment its record's bytes are read again and name the path: at the end of the search that found it, and at every later use. A miss is written only when the file, at the end of the search, has the identity and the size the search began with. One job runs at a time in the daemon; a job is a search or the proof of a hit.

## Interfaces and Dependencies

### §A. The rule (M1; `src/shared/files/named.ts`)

Pure, with no import but `parseAnchoredText`; shared so that the daemon's search and the window's test read the same functions.

    export function normalizeLexically(path: string): string;      // moved from `tools/code/open-file.ts`, unchanged
    export function hrefOf(destination: string): string;           // remark's `normalizeUri` (micromark-util-sanitize-uri 2.0.1), mirrored
    export function clickPath(destination: string): string | null; // the path a link with this destination asks for; null: not a path chip, or not recognised
    export function linkPaths(text: string): string[];             // the click path of every inline link the local check finds in `text`
    export const READ_TOOLS: ReadonlySet<string>;                  // Read, NotebookRead, LS
    export const EDIT_TOOLS: ReadonlySet<string>;                  // Edit, MultiEdit, Write, NotebookEdit
    export function chipPath(toolName: string, input: unknown): string | null;
    export function isMcpTool(toolName: string): boolean;          // the window's `MCP_TOOL`
    export function anchorPath(text: string): string | null;       // `parseAnchoredText(text)?.anchor.path`

    export interface PendingCall { toolUseId: string; when: 'mcp' | 'edit' }
    export type RowClaim = { names: true } | { names: false; pending: PendingCall[] };
    export function rowClaim(row: unknown, path: string): RowClaim;
    export function callClass(row: unknown, toolUseId: string): 'mcp' | 'edit' | 'other' | null;
    export function needlesOf(path: string): string[];

**The three forms.** Below, a value *is* the path when `normalizeLexically(value) === path`, which is what `openFile` does to what a click hands it.

- **The link form: `linkPaths(text)`.** At each `](` of the text, a local check, with no knowledge of the blocks around:
  - *before it:* walking back from the `]`, square brackets balance (escaped ones do not count) to an opening `[`, with no blank line crossed; that `[` is not escaped and is not preceded by an unescaped `!` (an image);
  - *after it:* spaces or tabs and at most one line ending; then the destination, which is either `<…>` with no line ending and no unescaped `<` or `>` inside, or a run with no space and no control character that does not begin with `<` and whose unescaped parentheses balance; then, optionally, whitespace and a title in `"…"`, `'…'` or `(…)`; whitespace; `)`.

  Each destination found gives `clickPath(destination)`:
  1. Markdown's reading: a backslash before an ASCII punctuation character is dropped. A destination that holds a character reference (`&name;`, `&#…;`) is not recognised: null.
  2. A scheme in front (`/^[a-zA-Z][a-zA-Z0-9+.-]*:/`, the window's `SCHEME`): not a path chip: null.
  3. A `%XX` escape that stands for an ASCII letter or digit: not recognised: null. (This is what lets the search pass a line over by its bytes; see `needlesOf`.)
  4. `hrefOf`, then `decodeURI`. A destination `decodeURI` cannot read is not recognised: null. (The window then asks for the href as it stands, escapes and all, which names no file.)
  5. A trailing `#L<digits>` or `:<digits>` is taken off, once.
  6. `normalizeLexically`.
  7. The window's URL step (Decision Log 12). Call the result of steps 3 to 6 on `hrefOf(destination)` P(href). The window parses `maws-path:<href>` as a URL before the click reads it (rehype-harden's `transformUrl`); with U(href) the serialisation `new URL('maws-path:' + href).href` less its scheme, the answer is P(href) when the same steps on U(href) give the same path, and null when the parse throws or the two paths differ. The two paths are compared, not the two strings: `/a/b/../d` and `/a/%2e%2e/b` serialise to other strings and stay named.
- **The value form: `chipPath(toolName, input)`.** For a tool of `READ_TOOLS` or `EDIT_TOOLS`: the first of `input.file_path`, `input.notebook_path`, `input.path` that is a string (the window's `filePathOf`); for any other tool, null. An edit's structured result is the second place of this form: `toolUseResult.filePath`, a string, at the top of the result's `user` row.
- **The anchor form: `anchorPath(text)`.** The `path` of the tag `parseAnchoredText` accepts at the end of the text; null when it accepts none.

**`rowClaim(row, path)`**, by the record's own `type`; every other record, and a value that is not an object, names nothing and waits for nothing.

| the record | names the path when | waits for a call when |
|---|---|---|
| `assistant` | a `text` block's text has it among `linkPaths`; or a `tool_use` block's input has a string, at any depth, with it among `linkPaths`; or a `tool_use` block's `chipPath(name, input)` is the path | never |
| `user`, with neither `isMeta` nor `isCompactSummary` true | its text has it among `linkPaths`, or `anchorPath` of its text is the path. Its text is `message.content` when that is a string, and otherwise the `text` of each block of type `text`; never a `tool_result` block | for each `tool_result` block with a `tool_use_id`: `when: 'mcp'` if the block's text (its `content` when a string, else its `text` blocks) has the path among `linkPaths`; `when: 'edit'` if the row's `toolUseResult.filePath` is the path |
| `attachment`, when `attachment.type` is `queued_command`, `attachment.origin.kind` is `human`, `attachment.commandMode` is `prompt`, `attachment.isMeta` is not true and `attachment.source_uuid` is a non-empty string (`humanQueuedPrompt`'s conditions) | `attachment.prompt`, a string or `text` blocks, has it among `linkPaths`, or its `anchorPath` is the path | never |

**`callClass(row, toolUseId)`**: for an `assistant` record with a `tool_use` block of that `id`: `'mcp'` when `isMcpTool(name)`, `'edit'` when `EDIT_TOOLS` has the name, else `'other'`; for any other record, null. A waiting claim becomes a name exactly when the class is the one it waits for.

**`needlesOf(path)`**: the runs of `[A-Za-z0-9]` in the path that are three characters or longer, longest first; when there is none, its longest run. Every record that names the path holds each of them in its bytes as written: JSON escapes no letter or digit, Markdown's backslash applies to punctuation, the tag's attribute escapes are punctuation, `normalizeLexically` removes whole segments and joins none, and a letter or digit written as `%XX` is refused by `clickPath`. So a line that lacks one of them need not be parsed.

### §B. The search, its memory and its queue (M1; `src/services/files/named.ts`)

    export const NAMED_SCAN_BYTES = 1024 ** 3;        // read back from the transcript's end, at most: completeness, not cost
    export const NAMED_CHUNK_BYTES = 1024 * 1024;      // one read
    export const NAMED_ROW_BYTES = 4 * 1024 * 1024;    // a longer line is passed over, its bytes not kept
    export const NAMED_CACHE_ENTRIES = 256;
    export const NAMED_WAITING_MAX = 8;                // distinct jobs waiting behind the running one
    export const NAMED_WAIT_MS = 8_000;                // a waiter's patience, inside a host request's ten seconds
    export const NAMED_FINGERPRINT_BYTES = 4096;       // as the engine host's search
    export const NAMED_PATH_MAX = 4096;                // bytes of an asked path; a longer one is not named, before its transcript is looked for (Decision Log 26)
    export const NAMED_CLAIM_STEPS = 64;               // steps of the rule on one row between two turns of the event loop (Decision Log 19)
    export const NAMED_PENDING_MAX = 256;              // results waiting for their call, at most; past it an older one is not waited for (Decision Log 13)

    export interface NamedPathsOptions {
      transcript: (appSessionId: AppSessionId) => Promise<string | null>; // decision 13; null: the session has no transcript
      open?: OpenTranscript;                                               // tests: `(path, flags: number) => Promise<FileHandle>`; the search opens `O_RDONLY | O_NONBLOCK` and checks the type on the descriptor (Decision Log 19); the suite counts the bytes read
      bounds?: { scan?: number; chunk?: number; row?: number; entries?: number; waiting?: number; waitMs?: number }; // tests
      hooks?: { at?(point: 'opened' | 'searched', appSessionId: AppSessionId): Promise<void> }; // tests: after a job has opened the file and read its size; after a search, before its answer is proven and remembered
    }
    export interface NamedPaths {
      names(appSessionId: AppSessionId, path: string, signal?: AbortSignal): Promise<boolean>;
    }
    export function createNamedPaths(options: NamedPathsOptions): NamedPaths;

`names` answers whether some record among the newest `NAMED_SCAN_BYTES` of the session's transcript names the path by §A, calls resolved. It never throws and never puts a path in a message.

- **The queue.** One job at a time for the whole service. A job is a search or the proof of a remembered hit. Asks for one session and path join that pair's job, running or waiting. At most `NAMED_WAITING_MAX` distinct jobs wait; an ask that would be one more answers `false` at once. A waiter answers `false` and leaves when its signal ends or `NAMED_WAIT_MS` have passed; a job left with no waiter is dropped if it waits, and stops at its next read if it runs, remembering nothing. A running job gives the event loop back after every read and after every parsed line.
- **A hit** remembers the file's identity (device and inode) and where its naming record is, and its call's record when the name waited for one. It answers `true` only when, in the file the locator gives now, with that identity, those byte ranges are still whole lines that parse and still name the path by §A. A search that finds a name proves it the same way before it answers. Otherwise the hit is dropped and a search runs.
- **A miss** remembers the identity, the offset searched to (the end of the last whole line read) and the fingerprint of the first and the last `NAMED_FINGERPRINT_BYTES` before that offset. It is written only when the file, after the search, has the identity and at least the size the search began with. The next ask searches from that offset on, when identity and fingerprint still match and the file is no shorter; a call a result form waits for is looked for below the offset too. Otherwise the miss is dropped and the whole window is searched.
- **Bounds, for the service and not for one job.** Memory: one read (`NAMED_CHUNK_BYTES`), one line (`NAMED_ROW_BYTES` at most) with its parsed form, `NAMED_WAITING_MAX` waiting keys with their waiters, `NAMED_CACHE_ENTRIES` entries of a few numbers each. Work: one job at a time; one search reads the window once; a proof reads two lines at most. What is read: the session's own transcript file, never its folder, never an agent's file; nothing is written.
