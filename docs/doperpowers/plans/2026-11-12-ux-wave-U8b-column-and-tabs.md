## Purpose

Beside a session the person sees what matters about it without opening anything: where it works and what it changed, and, only while there is any, what it has running, as a tree of its subagents and a list of its background tasks. Finished work no longer takes the top of the Subagents and Background tasks panels, and a panel for watching work opens narrow. The tools opened beside the chat are tabs of one strip, one in view; nothing is placed under another by itself, and the person can move tabs into a second group under the first.

How to see it working, on the wave's build: open a session with nothing running and see Environment open with Context and Connectors folded under it; start a background shell and see a Background tasks card come and go; open Review, a terminal and Session info and see three tabs with one tool in view; choose "Move below" on one and see two groups; quit, relaunch, and see the same tabs, groups and folds. Then open the same profile with build F and see its two stacked surfaces, its sidebar and its tabs as F draws them. In the suites: the unit tests named under each milestone, and the e2e scenes of M9.

## Words used here

- **The side column:** the column of tools opened beside the chat, right of the main area (`#region-panel`, `src/renderer/src/panel/`). **A tab** of it: one tool instance open for a session, a `PanelTabRef` (`id`, `toolId`, `pinned`) in that session's list (`panel.<session>`) or among the global pins (`panel.pinned`). **The strip:** the row of tabs over the column. **In view:** the tab whose body is drawn. **A group:** a strip with one tab in view under it; the column has one, or two with the second (**the lower group**) under the first.
- **The card column:** the cards that float over the right of the main area while no tab is in view (`[data-region="cards"]`, `src/renderer/src/panel/summary/`).
- **A scope:** the key the side column's stored state is filed under: a session's address, or `@none` while no session is shown (`surfaceScope` in `panel/surface-model.ts`).
- **Build F** (`f1852de3a`): the build on the owner's machines, which may open the same profile after a trial of the wave's build. **Its reader:** the schemas of `src/shared/ipc/schema/layout.ts`, which are F's byte for byte at this document's base (`git diff f1852de3a 48619c824 -- src/shared/ipc/schema/layout.ts src/main/layout/store.ts src/renderer/src/panel src/renderer/src/stores/layout.ts` is empty).
- **The three routes** (law 5): a session MAWS runs, a terminal session, a session on another machine.
- **The VM**, **class 1a**, **the controller** (the plan executor that runs the milestones, reviews each at its boundary and is this document's one writer while they run).

## What the code holds today

Read at `48619c824`. Only what the milestones lean on and the code does not say in one place.

- **The stacking rule is one function in the store.** Every write of a scope's refs or selection passes `setPanelTabs` (`stores/layout.ts`), which recomputes `panelSurfaces.stacks[scope]` with `stackAfterSelection` (`panel/surface-model.ts`). So a second tool stacks whoever opens it: an icon, `addTool`, a transcript row, a card's button, the agent's `show_pane`. It takes `next.tabs` as the scope's whole list, the pins among it, and a strip's own `select` submits the tabs it was given (`TabStrip.tsx`). It is not the only writer of refs: `setPanelTabPinned` moves one between the pins and a session's list directly. The host tells an add that activates from one that does not (`applyAdd`, `activate`), and a plugin's roster adds its panes without activating.
- **An icon closes nothing today either.** `toggleSurface` and `closeSurface` (`panel/SurfaceRow.tsx`) only take a tool out of the stack; its ref stays in the session's list for good. That is why the first read must prune (Interfaces §A).
- **An empty stack means "show the cards".** `toggleSessionCards` writes `stacks[scope] = []`; the card column is drawn when no tab is in view, `regions.panel.collapsed` is false, and there is room (`Shell.tsx`; the same rule is written again twice in `SurfaceRow.tsx`). `collapsed` turns the cards off with the column.
- **Only the tab in view is mounted** (`panel/ToolBody.tsx`); a tool's state lives outside React in the host's instance map and restores its own view state on mount.
- **Two stacked surfaces split the height equally**, with no bar and no stored share (`PanelHost.tsx`). A tool has no `header` of its own in its declaration; a header row's content comes from a body's X32 registration (`useEditorHost`, `panel/editor-host.ts`).
- **One width.** `shellGeometry` reads `regions.panel.width`, and reads exactly 380 as "automatic" (60 % of the room for Review, Files or the browser, else 420).
- **The cards.** `Summary.tsx` draws Environment, Context, Connectors, Artifacts; `FloatingCard.tsx` keeps each fold in component state, so every card is folded again at each change of session. `panel/summary/BackgroundWork.tsx` and `Subagents.tsx` are imported by nothing. The Environment card's change line is drawn by Review's `summary` component, `tools/code/review/ReviewSummary.tsx`.
- **"More surfaces"** lists every registered tool whose `menu` is not false, except `artifacts`, by an explicit filter in `SurfaceRow.tsx`. The surface rows of the keymap are written by hand in three places (`actions.ts`, `app/shell-actions.ts`, `SURFACE_ACTIONS`); `artifacts` has none and needs none.
- **The task graph** (`tools/agents/store.ts`, `model/task-graph.ts`) holds agents, workflows, shells, monitors and tasks of any other kind; nothing lists the last, and `counts()` ignores them. An agent knows its parent (`agent.parentAgentId`); a shell or a monitor does not know who started it: the engine's `owned_by_subagent` and `parent_task_id` are read nowhere in `src/`.
- **Who feeds the graph.** A session MAWS runs: its journal and status. A session not running here: sidecars and runs from disk, every agent "status unavailable". A terminal session on another machine: its plane transcript's tree with each agent's reported status laid over it (`lane-a/remote-agents.ts`, `lane-a/agents/task-feed.ts`). A terminal session on this Mac: the disk reading only. Its shells and monitors come beside the graph, from a ledger over its transcript's rows (`src/services/lane-a/jobs.ts`, a port of sminos's, pinned by DX4's vectors; `lane-a/jobs/` in the renderer), and that ledger derives no agents on purpose (`derive` answers `subagents: []`), so its Subagents panel shows no agent as running.
- **An exit ends agents in two models,** the graph (`process.exited` → every running node `exited`, read "ended with the session") and the transcript's reducer (`endAgents`, after which an agents row reads its agents stopped). The transcript draws no row for an exit that is disk-derived with reason `unknown` and `seq: null` (`derive.ts`). The one place such an exit is made is the end of a transcript follower's backfill, and only when the session has no live holder at that moment and its last turn never ended (`src/engine-host/fs/chain-follower.ts`).
- **"Waiting".** `src/shared/attention/kinds.ts` exports `isOpen` and `waitsOnAnswer`; `waits` arrives with U1a. The renderer's one selector of a session's open items is `selectPendingOf` (`stores/attention.ts`), which `AgentList.tsx` reads for "Approval needed".

### M2 — One strip, one tab in view

**What exists at its end.** The side column's first row is a strip with a tab for every tool instance open for the session in view, the pins first, and one tab is in view under it. A tool that is opened or chosen is shown in place of the one in view; nothing is placed under another by itself, whoever opens it (an icon, a chord, a transcript row, a card, the agent's `show_pane`). A tab that arrives without being asked for (a plugin's pane added by its roster) joins the strip and replaces nothing. A click on a tool's icon in the title bar shows that tool's tab, and a click on the icon of the tool in view hides the column and closes nothing. A tab's close glyph closes that tab through the tool's own check. Terminals and plugin panes are tabs of the column and draw no strip of their own. (A11's first half, with one group.)

**What it touches.** `stores/layout.ts` (`setPanelTabs`'s rule, `updatePanelTabs`; `setSurfaceStack` removed); `panel/surface-model.ts` (`stackAfterSelection` removed) and its test; `panel/host.ts` (`writeRefs`, `applyAdd`, `selectTab`, `showSummary`, the cross-session repair: the intent passed, not inferred); `panel/PanelHost.tsx`; `panel/PanelHeader.tsx`; `panel/SurfaceRow.tsx` (`toggleSurface`, `closeSurface`, `toggleSessionCards`, the context menu's last item); `panel/TabStrip.tsx` (U6's file: selection by id, the strip used without `inline`, the home glyph gone, a tab's width when the strip is too narrow); `panel/copy.ts`; `keymap/shell-navigation.ts` (U6's file: the strip as a stop); the unit tests named below.

**Interfaces.** Consumes §A, §B. Exposes §C.3 to U6b (the strip's markers and `toggleSurface`'s rule).

**Decisions.**

1. *A strip never submits its own tabs as a list.* Today `TabStrip`'s `select` calls `onChange({ tabs, activeTabId })` with the tabs it was given, and the store takes `next.tabs` as the scope's whole list, the pins among it. Drawn over one group's tabs, that would delete the other group's refs and unpin its pins, with no `beforeClose`. So a tab is chosen by id: `select` calls `panelHost.selectTab(id)`, which is `showSurfaceTab`. `PanelHost`'s `onChange` stays for changes of the inventory (a prune, a close) and is always given the scope's whole list; nothing that a group displays is ever `setPanelTabs`'s `next.tabs`.
2. *Maintaining the refs is not choosing a tab* (M1, decision 4). The host already tells the two apart: `applyAdd` writes the ref and names the tab to activate only when `activate` is true, and the plugin-roster reconciler adds its panes with `activate: false` (`engine-surface/panes.ts`). That intent now reaches the store: `updatePanelTabs(…, { activate?: tabId, group? })` maintains the refs and, only when `activate` is given, calls `showSurfaceTab`; `selectTab` calls `showSurfaceTab`; an unchanged `activeTabId` in `setPanelTabs`'s argument is never read as a request. So a ref added without `activate` joins its group's strip and comes into view nowhere, and an update of the inventory never shows a hidden column. This is the one place where "no opener is edited" has an exception, and it is in the host, not in an opener: what an agent or a plugin may open, and when, stays U12's.
3. *`toggleSurface(toolId)` stays the one entry* of the icons, the three-dot menu, the context menu and the `surface.*` actions (so ⌘J, ⇧⌘D and ⇧⌘F, which U6a bound to those actions, follow without an edit). The tool has a tab in view and the right side is not collapsed: `hideSurfaces`. Else the tool has a tab: `showSurfaceTab` of, in this order, the tab of that tool last in view in this run when it is still a ref of the scope (a module map by scope and tool); else the tab of that tool that a group remembers as shown (`SideGroup.shown` of either group, a hidden column's included), which is what a relaunch restores; else its last tab in strip order. Else `panelHost.addTool`. Then `setPanel({ collapsed: false })` as today. The Questions tool's `settleWaitingAsks` call stays where it is.
4. *What the column draws.* `PanelHost` draws, for each group of `sideGroups` (one in this milestone): the strip (`TabStrip` over that group's tabs), then the tool's own header row only when the tab in view has an X32 registration (`useEditorHost`: a breadcrumb, a saved state, actions, exports), then the body. A tool without a registration has no row under the strip: its title is the tab's. The region's controls (Float, Maximize or Restore, Hide) sit at the right end of the first strip, drawn by `PanelHeader.tsx`'s `RegionControls`, which stays the one place they are defined (U10 inserts its control there). Hide is `hideSurfaces`. The strip's home glyph goes: Hide is that act.
5. *A strip too narrow for its tabs* (the owner's answer of 2026-11-12, "Shrink to icons", and the architect's ruling on what comes after the icons; Decision Log 4). While the tabs do not fit, three things happen, in this order. First the tabs not in view give up their titles, the rightmost first, and stand as their icons alone (28 px, the title as tooltip and accessible name); until every one of them is an icon the tab in view keeps its title whole. Then the tab in view shortens: its title is cut with an ellipsis and its glyphs stay, down to today's minimum of 72 px. Only when that does not fit either does the strip scroll sideways, as today, with no scrollbar. The whole of it is `TabStrip.tsx`'s width rule.
6. *Only the tab in view is mounted,* as today (`ToolBody`'s rule: a tool keeps the view state it would miss in its own state and restores it on mount). That is what "as it was left" rests on for Review's scroll and a terminal's process, and it is not changed. `ctx.visible` stays "the right side is not collapsed".
7. *The markers U6b and the keyboard read.* The column's container keeps `data-surface-stack`; each group is `section[data-side-group="upper"|"lower"]`; a group's body keeps `data-surface={toolId}` and `role="tabpanel"`, so `regionStops` in `keymap/shell-navigation.ts` still finds a surface's content. This milestone adds each group's strip (`[role="tablist"]`, its selected tab) as a stop before that group's body, as the main panes' strips are.
8. *The context menu of an icon* reads "Open surface" when the tool is not in view and "Hide surface" when it is; "Close surface" is gone, since the icon closes nothing.
9. *"+"* keeps offering what `menuTools` offers today (a single-instance tool only while it has no tab), and a tab made from it comes into view.

**What it does not touch.** The second group (M3: `sideGroups` may already answer two groups for a stored layout, and this milestone draws both groups' strips and bodies in the plain equal split it has today, so a stored two-group layout is never drawn as one). The drags and the scroll of a tab into view (U6b). The browser's own page tabs. Which tools exist and what a tool draws.

**What it proves.** A11's first three sentences and the icon's rule, by unit tests: from one tab in view, opening a second tool by its icon, by `addTool` and by `selectTab` leaves one `[data-surface]` and two tabs in the strip, the first tool's state object unchanged; a click on the icon of the tool in view leaves no `[data-surface]`, the cards' condition true and both refs in the list, and a second click on either icon brings back the tab that was in view; closing a tab asks `beforeClose` and, on a pass, shows its right-hand neighbour; two terminals are two tabs of the strip and no strip is drawn inside the header; a tool with an X32 registration draws its header row under the strip and a plain tool draws none. Decision 1: with two groups stored (M1's state) and the other group holding an ordinary tab and a global pin, a tab chosen in each strip in turn leaves every ref, every pin and every instance in place. Decision 2: with Review in view, a ref added with `activate: false` and a ref removed elsewhere leave Review in view; with the column hidden, the same two leave it hidden. Decision 3: terminals T1 and T2, T1 in view, hide, re-hydrate from what was written (a relaunch), the Terminal icon shows T1; an id in the run's map that is no longer a ref is passed over. Decision 5, over six tabs: at a width that fits all but one title, the rightmost tab not in view is an icon and the rest are whole; at a width that fits the tab in view whole beside five icons, the five are icons and the tab in view is whole; at a narrower width that still fits five icons and 72 px, the tab in view is cut to what is left and no tab lies beyond the edge; narrower than that, the tab in view is 72 px and the strip scrolls. Tests that pinned the old rule and change here, by title: in `panel/panel.test.tsx`, "plain icon clicks stack two surfaces, a third replaces only the lower slot, and closing an icon leaves the other open", "a same-tool tab click selects it; closing the surface preserves every tab for reopening", "on the Overview, clicking an open pinned surface clears its selection without removing the pin", "primary tools have icons and More lists other menu tools; opening a singleton makes it an open icon, not another tab"; in `panel/surface-model.test.ts` the five cases about slots and stacks (rewritten over `sideGroups`); in `panel/PanelHeader.test.tsx`, "puts an unregistered multi-instance tool's tabs and surface controls in one header, naming the terminal only once"; in `app/Shell.panel.test.tsx`, "keeps pins first in the inventory, shows only the selected tool's tabs, and the pin glyph moves its ref"; in `panel/TabStrip.test.tsx` the cases that pass `toolId`.

### M3 — The second group

**What exists at its end.** "Move below" in a tab's menu splits the column into two groups, one above the other, each with its own strip and one tab in view; a bar between them is dragged, or moved from the keyboard, to share the height, and neither group goes under 120 px. "Move above" and "Move below" move a tab between the groups. A group that loses its last tab closes. With two groups a tab that is opened goes where `groupForOpen` says, and a tab that is chosen is shown in its own group. Hiding the column and showing it again, and a relaunch, bring back the tabs, the two groups and the tab in view of each. (The rest of A11.)

**What it touches.** `panel/PanelHost.tsx` (two groups, the bar); `panel/TabStrip.tsx` (U6's file: the two menu items, beside "Move to main area"; the group a strip belongs to, handed to its "+"); `panel/copy.ts`; `panel/host.ts` (`AddToolOptions` gains `group`); the unit tests.

**Interfaces.** Consumes §A, §B. Exposes §C.3 to U6b: `moveSurfaceTab`, `setGroupShare`, the markers.

**Decisions.**

1. *The menu, and only the menu* (the owner's answer of 2026-11-12, "Menu only"; Decision Log 4). A tab's context menu holds, in this order: "Move to main area" where `panelTabMoves` offers it today; "Move below" for a tab of the upper group, shown when the column has two groups or its one group has more than one tab; "Move above" for a tab of the lower group. Each calls `moveSurfaceTab`. They are menu items with no action id and no chord (Constraint 7). The menu opens on a right click and on Shift+F10, as an icon's does. No visible control offers the split.
2. *The bar.* A `role="separator"` with `aria-orientation="horizontal"`, `aria-valuenow` the share in percent, focusable; a drag and the arrow keys (8 px a step, 32 with Shift, as the app's resizers) call `setGroupShare`. The share is clamped to 0.2..0.8 in the store and, when drawn, so that each group keeps 120 px; in a column too short for both it is the lower group that gives way down to its strip. It reuses `app/Resizer.tsx` if that takes a vertical axis without a new mode of more than a prop; otherwise a small bar of its own in `panel/`.
3. *The group an open comes from is said, not guessed.* A strip knows its group and hands it to its "+" menu, whose items call `addTool(toolId, { appSessionId, group })`: the menu's items are drawn in a portal, so by the time one is chosen the keyboard's focus is in the portal and no longer inside the group. An opener with no origin of its own (an icon, a chord, a transcript row, the agent) passes none, and the host then looks for the group whose `section[data-side-group]` contains `document.activeElement`, and passes none when focus is elsewhere; `groupForOpen` then falls to the upper group.
4. *The region's controls* stay on the first strip of the column; the lower group's strip has none.
5. *Widths.* Nothing to add: M1's rule already reads the tabs in view of both groups.

**What it does not touch.** The drags (U6b). More than two groups, groups side by side, a setting for stacking by default: not in the child's file.

**What it proves.** The rest of A11, by unit tests: with three tabs and the third in view, "Move below" on the second leaves the third in view above and the second in view below, each group with its own strip; a tab of a tool opened next joins the group that holds that tool's tab; a new tool chosen from the lower group's "+" goes below, once with the pointer and once with the keyboard alone (the menu opened and the item chosen by keys); one opened by an icon with focus outside the column goes above; closing the lower group's last tab leaves one group; "Move below" is absent on the only tab of a single group; the bar's keys move the share and it stops at the bounds; hide then show restores both groups and both tabs in view; a hydration from the values just written restores the same (the relaunch); the written values parse with F's frozen schemas, and read by F's rule (`normalizeSurfaceStack` as it is at `f1852de3a`, transcribed in the test) they give the two tabs in view as its stacked pair.

### M6 — The exit a gone terminal leaves (X-168)

**What exists at its end.** When a terminal session's process is known to be gone and its transcript holds no exit, its agents end. The transcript's agents row no longer stays in view as working, on this Mac and for a session on another machine; there, where the graph holds the session's agents, they read "ended with the session" in the panel and the Subagents card leaves. A session that is resumed in a terminal, works again and ends again, ends again. No new row is drawn in the transcript, and the word its agents row uses for an agent ended this way is today's (U3's second landing has that word).

**What it touches.** `src/engine-host/fs/service.ts` and `chain-follower.ts` (the exit made on this Mac) and their tests; `src/renderer/src/lane-a/plane-transcript.ts` and `lane-a/remote-source.ts` (the exit for another machine, from its presence, and its precedence over a status) and their tests (as corrected by Decision Log 13; `agents/task-feed.ts` needed no change).

**Interfaces.** Consumes the graph's `process.exited` handling as it is. Exposes nothing new.

**Decisions.**

1. *The event.* `process.exited` with reason `unknown` and `seq: null` (the property present and null, as `fs/backfill.ts` builds a disk-form event). The transcript's reducer ends agents on it and `derive.ts` draws no row for it, so no file under `src/renderer/src/transcript/` is edited (UC-3).
2. *This Mac: when it is made.* Today the follower makes this exit only at the end of its backfill, only when no holder is live then, and only when the last turn never ended. It now also makes it when the session's last live process goes while the follow is open, and whether or not the last turn ended, since X-168's case is a process that ends after its turn; and at the end of a backfill with no live process it is made where the last turn ended too, so a session read from disk after its terminal closed ends its agents alike.
3. *This Mac: once per process, not once per session.* A session id outlives several terminal processes while its follower stays open. The exit is made at most once for each stretch of the transcript that follows the last exit, real or supplied: after one is made, a later row in the file, or a holder that returns, arms it again. So exit, resume, a new background agent, exit again ends that agent too, and a holder count that changes twice with nothing written between makes one exit.
4. *This Mac: decided in the follower's own order.* When the registry says the session's live processes fell to zero, the follower does not emit from that callback. It queues one step behind whatever it is reading: drain the file to its end, ask the registry again, and only if no process is live then, and the drained transcript holds no exit after its last row, emit. A read still pending, or a holder that came back during the drain, therefore cannot be ended by a stale callback. "Live" is the registry's count of every live process of the session (`liveCount`), not the mark for a holder that is another program's.
5. *Another machine: which signal counts, and what outranks what* (as corrected by Decision Log 13). The session's process is known gone when its presence says no live record (`record: null`) while its machine is up: `lane-a/remote-source.ts` hands the main watch's presence (the snapshot's and each `presence` message's) to `lane-a/plane-transcript.ts`, which then supplies the same event to its rows and its tree. A machine that goes offline publishes no presence (its link pauses the watch), so it supplies nothing, and while the link is down the rows keep their last state and the machine's own offline mark says why; no `end` of the subscription counts (since DC8 a machine ends none when the process goes, and `remote-source.ts` passes no `end` to the transcript). The statuses a machine last reported are laid over the tree after every reduction; they would publish an agent the exit ended as running again. So the exit takes precedence: once supplied it is kept through every rebuild of the tree and no status overlay turns an agent it ended back to running, until a fresh live snapshot or a live record that returns clears it.
6. *The graph of a terminal session on this Mac* holds no running agent (M5, decision 5), so there the exit reaches the transcript alone. Its jobs already end with the process: the ledger reads a job no word ended as `exited` once the session's process is gone. *A session MAWS runs* has its exit on the wire; nothing changes.

**What it does not touch.** The transcript's model and views. The word the transcript's agents row uses. U3a also edits `fs/backfill.ts` and may touch a boundary predicate the follower reads; whichever lands second merges, and this milestone's proofs are run after that merge.

**What it proves.** A7's test that fails before, for each of the two readers. *The follower:* a terminal session whose last turn ended, with a background agent still running and no exit in the transcript, whose process then goes, delivers one exit of reason `unknown` with `seq: null`, and the transcript's agents row no longer stays in view as working; a second change of the holders with nothing written delivers nothing; exit, resume, a new agent, exit delivers a second exit that ends the new agent; a holder that returns while the final drain is queued makes no exit; a row still unread when the count falls is read before the decision. These sit beside the follower's existing test of a duplicate notification. *The plane transcript:* a feed whose metadata says `status: 'running'`, whose presence then says no live record while its machine is up, leaves the agent `exited` in the published tree and its agents row out of view, through a status overlay and a rebuild; presence lost with the machine (an interruption, an end `machine-offline`, the link's pause) supplies nothing; a fresh live snapshot clears the exit; presence that goes to null and comes back within one subscription leaves no exit behind and no doubled row. *Through `remote-source.ts`:* a `presence` message with no live record on the main watch ends the agent, a pause of the link does not, a status reported after it does not bring it back, and a live record clears it.

**The reading rule** (`sideGroups` below), applied at every hydration and wherever the groups are derived, so that whatever F wrote in between is read the same way as a first read. For one scope, with `refs` its tabs in strip order (the pins, then the session's own), `stack` the stored `stacks[scope]`, `active` the stored `activeTabId`, and `lower` the stored entry of `panelTools.groups` or none:

1. `S` is `stack` without ids that are no tab of `refs` and without a repeated id, cut to two. Two tabs of one tool may both be in `S` (two terminals).
2. `S` has two ids: two groups. The lower group's tabs are `S[1]`, then `lower.tabs` that are still tabs, less `S[0]` and `S[1]`. The upper group has every other tab. In view: `S[0]` above, `S[1]` below. The share is `lower.share`, or 0.5.
3. `S` has one id: one group with every tab, `S[0]` in view. A stored `lower` entry is dropped.
4. `S` is empty and `stack` is absent (a scope from before stacks were stored): one group, `active` in view when it is a tab, as today.
5. `S` is empty otherwise: the column is hidden for the scope. What it shows when shown again: two groups when `lower.tabs` still names a tab and at least one tab is outside it (above: `active` when it is an upper tab, else the first upper tab; below: the first of `lower.tabs` that is a tab); else one group with `active` in view when it is a tab.

**The first read** (hydration finds no `panelTools.groups` key in the file), at most once per profile: at the first launch at which the listing and every read answered, and only if no earlier launch of this build has written the side column's state (amended at M1's boundary review; Decision Log 3):

- every scope is read by the rule above with no `lower` entry, so two ids in a `stacks` entry open as two groups with those two in view;
- in every session's list, a tab of a single-instance tool that is not in view by that reading is dropped (under the old rule such a tab was never removed, and every tool ever opened would otherwise stand in the strip). Pins are kept. Tabs of a multi-instance tool (a terminal, a plugin pane) are kept. A tab whose tool is not registered at that moment is kept. The dropped tabs' entries in `panelTools.params` go with them, by the rule that already prunes params of tabs no list holds;
- `panelTools.widths` is `{ wide: regions.panel.width, narrow: null }`, with `wide: null` when that width is 380 (the old default cannot be told from a drag to exactly 380, so it is automatic once more, as it is today); after that no value is special (X-165);
- the three new keys are written at once, so the next launch is not a first read;
- a launch at which the listing or a read failed defers it: nothing is pruned, nothing is written over a key it could not read (a key the failed listing left unread among them), and no default of the three keys is written.
