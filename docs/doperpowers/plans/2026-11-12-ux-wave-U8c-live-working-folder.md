## Purpose

**U8c-1.** When an agent enters or leaves a git worktree through the engine's worktree tool, the engine moves the session's transcript file, with its folder, to another place in its store. Today (build F included) three things go wrong at that moment: a terminal session's Background tasks stop changing, an open transcript of one of the session's agents stops reading, and the session is told removed and listed as archived for an instant. After this landing the readers go on reading across the move and nothing is told removed.

**U8c-2.** The owner's agents usually move themselves into a worktree soon after a session starts, by the worktree tool or by a shell `cd` into a worktree made with `git worktree add`. Today the window follows the first kind only by re-filing the session, and the second kind not at all: after a `cd` the Environment card names the launch folder, Review and Source control diff it, Files lists it and a new terminal opens in it, while the agent works somewhere else. After this landing the card says where the agent is (the folder, the branch git reports there, and one muted line "moved from …"), Review, Source control and Files show that folder, a new terminal starts in it, the sidebar marks the session as in a worktree, and all of it returns when the agent comes back. It is the same for a session MAWS runs and a session started in a terminal, here, and for a session MAWS runs on another machine.

How to see it working. U8c-1: the test that renames a real transcript under the real readers fails on master and passes on the branch, on Linux and on macOS. U8c-2, on the wave's build: in a session whose repository has a worktree, have the agent enter it (by `EnterWorktree`, then again by `cd`); within the turn the card shows the worktree's folder and branch with "moved from <the launch folder's name>", Review lists the worktree's changes, Files opens on it, a new terminal starts in it, a terminal opened before says it is still in the launch folder, and the session's sidebar row carries the worktree mark; have the agent leave, and all of it returns. In the suites: a test that replays the probe's two recorded sessions through the summary and the index and asserts one answer for both (M2), and the suites named under each milestone.

### M1 — A moved transcript keeps its readers (U8c-1)

**What exists at its end.** When the engine moves a session's transcript and its folder to another project folder, in either direction, the session's follow, the quiet follow of its older pages, a follow of one of its agents and a terminal session's job reader go on reading, the session's agents are listed at their new paths, and the session is not told removed. **What it touches.** `src/engine-host/fs/service.ts` and `discovery.ts`; a new suite `src/engine-host/fs/move.test.ts`; `discovery.test.ts`; `service.test.ts` only where a removal is asserted; `src/services/lane-a/transcript-jobs.ts` and `transcript-jobs.test.ts`; one scene in `e2e/sessions.spec.ts`, compiled and not run. **Interfaces.** Exposes no name to a sibling. Consumes nothing unbuilt.

**Decisions.**

(c) A follow of an agent (`fs.agentEvents`, over the suite's sidecar fixture) delivers a row appended to the agent's transcript at its new path: red. Rejected: looking each agent up in the new listing first, which needs the walk to finish before a follow can read.
4. *A session is told removed only after its transcript was looked for* (Decision Log 3, finding E; it replaces the first writing's fixed delay). The two places that forget a session today, `summarizePath` when the file at the listed path is missing and `pass` for a session its listing does not hold, call one function instead. It notes the session as leaving, with its generation: a count per session that the service raises at every transcript event naming the session and at every summary that lists it. Then a look runs: the names in every project folder are read once (`readdir`, no `stat`), for every session noted leaving when the look begins, and for each of them:

   - it is found nowhere and the session's generation is the one noted: the session is forgotten and told removed, once.
   - the generation moved while the look ran: this look decides nothing for it; if the session is then still listed at the path it left, it is noted again and looked for again.

   No delay is part of the rule. A single move is always found: the look begins after the file was seen missing, and a rename leaves the file somewhere. `pass` waits for the look of what it found gone before it answers, so a scan's removals are told before the scan's answer, as today. The look lives in `Discovery` (`find`, beside `list`). Its cost is one `readdir` per project folder per look, whatever the number of sessions leaving. What it leaves: two moves inside one look (an enter and an exit within the milliseconds a look takes) can still be told as a removal and a return, as every move is today.

On screen, the surfaces that already ask the selector follow a `cd` (the card's folder and git watch, Review, Source control, a new terminal); what a move does to work in hand is M4's, which is why the two do not land apart.

**What it touches.** `src/engine-host/fs/summarize.ts`; `src/shared/wire/store.ts`; `src/services/index/sessions.ts`, `projects.ts`, `migrations.ts`, `source.ts`; `src/shared/graph/session.ts`; `src/shared/sessions/working-folder.ts`; `src/shared/ipc/wire.ts` and the two generated wire files; `test/one-working-folder.test.ts`; a new `test/working-folder-routes.test.ts`; the suites beside each changed file (`summarize.test.ts`, `store.test.ts`, the index suites, `working-folder.test.ts` and the hook's); `test/support/index-fixture.ts` if the routes test wants a helper.

**Decisions.**

1. *One producer for every route: the summary.* The engine host already re-reads the head and tail of every transcript that changes, whoever runs the session, and the index already turns that into the record; the newest row's folder is one more fact of the tail window (§A). So a session MAWS runs and a terminal session are served by the same code, and a session MAWS runs on another machine by that machine's copy of it, its record carried here as records are today. Rejected: the engine's per-turn `system/init` folder for a session MAWS runs (the section's own outcome 1 names the follower there): it exists on one route and is a turn late; the chain follower's facts: a follow exists only for a session someone has open.
2. *The change is additive* (Decision Log 3, finding C). `upsertFromSummary` writes every column it writes today by the rule it has today: the record is filed at the home, and re-filed on a `relocated` row. Build F's readers that derive a transcript's path from the record's directory, on this profile or across a link, therefore keep finding it, and a window of build F on a host of this build keeps following a worktree entered through the tool in everything it draws from the record (what this build's services answer that window for a session whose agent moved is §C's second table). 3. *The launch folder* (§B; Decision Log 2, ruling 2). It is the filed folder, except while the engine has re-homed the session inside one repository: then it is the folder the transcript's first row names, located as the index locates a record's folder today. Whether the first row's folder and the home are in the same repository is asked of git's own files (decision 4), not of the index's project grouping. A home in another repository, or in none, is the launch folder itself: a session the person moved with `/cd` to another repository is launched there, as far as the window is concerned, and is filed there as today. "The launch folder stops moving" is thereby a statement about the selector's `launch`.
4. *The working folder is judged by repository identity* (§B; Decision Log 3, finding D). `checkoutIn(launch, folder)` reads the nearest `.git` above the newest row's folder and above the launch folder: the same common git directory is the same repository, and the work tree the folder is in is the checkout. It does not ask `locate`, whose project directory for a session launched in a sub-folder of a repository is that sub-folder. A folder that is gone, in another repository, or in none under a launch folder that is in one, gives no working folder: the record answers the filed folder. A linked work tree counts only if its git directory names it back (§B): a folder that holds a copy of a worktree's `.git` pointer is in no repository for this purpose. So a fact is written only for a folder that passes the admission's own predicate at the write (§G; Decision Log 8), which is what the consumers that take the record's word, and the calls that bound no folder, then rest on.

6. *What is stored: two nullable columns, each stamped, each present only where it differs* (§C). `sessions.launch_folder` holds the launch folder when it is not the filed folder; `sessions.agent_folder` holds the working checkout, the agent's folder, the branch and whether the checkout is a linked worktree, when the checkout is not the filed folder or the agent's folder is not the stored directory. Both facts are functions of one summary and need nothing remembered from an earlier one. Rejected: no stamp (after a stay in F a column would name a folder the agent left while F ran, or a launch folder of a session F has since filed under another repository); deriving the facts from the stored summary at every read (git's files read on every `get`).

## Interfaces and Dependencies

### §A. The summary's field (M2)

In `TranscriptSummarySchema` (`src/shared/wire/store.ts`):

    newestCwd: z.string().nullable().optional(),

The `cwd` of the newest row in the tail window that carries one and is not a sidechain row (`isSidechain !== true`); null when the tail window holds no such row; absent from a producer that does not read it. `summarize` takes it from the tail only, newest first, and never from the head: a head's newest folder in a long file is old. A last line still being written counts by its start, as the summary's other tail facts do. It is optional because the summary is sent between builds (`fs.sessionChanged`) and kept as JSON in the index.

### §B. The index's rule (M2)

`upsertFromSummary` writes every column it writes today, by today's rule, from today's inputs. It then writes two more (§C), from three folders of the summary: **H**, its first row's (`directory`); **R**, the home its tail names (`relocatedCwd`), which may be null; **C**, its newest row's (`newestCwd`).

- **C absent**, or the location the record was filed at has no realpath (the home is gone): both columns null.
- **H, `R ?? H` and C are one string:** both columns null, and nothing is read.
- **Otherwise.** Let *home* be the location the record was filed at (`locate(R ?? H)`), *filed* its `worktreePath ?? realpath`, and *directory* its `realpath`.
  - *launch* is filed; except when R is not null and is another string than H, the first row's folder resolves, and `repositoryAt` answers one `commonDir` for it and for directory: then launch is `first.worktreePath ?? first.realpath`, with `first = locate(H)`.
  - *at* is `checkoutIn(launch, C)` when C is a folder, else null.
  - `launch_folder` is written when launch is not filed, else null.
  - `agent_folder` is written when *at* is not null and `at.checkout` is not filed or `at.cwd` is not directory; else null. Its `branch` is `branchName(summary.gitBranch)` when `at.workTree` is null or is the work tree `repositoryAt` answers for directory, else `headBranch(at.workTree)`; its `linked` is `at.linked`.

`index/source.ts` warms H as well as `R ?? H` for a summary whose R is not null and differs from H, so that `locate(H)` runs no git on main's thread.

In `src/services/index/projects.ts`:

    export interface Repository { commonDir: string; workTree: string; linked: boolean }   // each path a realpath
    export function repositoryAt(folder: string): Repository | null;
    export function checkoutIn(launch: string, folder: string): { checkout: string; cwd: string; workTree: string | null; linked: boolean } | null;
    export function headBranch(workTree: string): string | null;

`repositoryAt` resolves the folder and takes the nearest `.git` at or above it. A directory: `commonDir` is its realpath, `workTree` the folder that holds it, `linked` false. A file `gitdir: <G>`: `commonDir` is the realpath of what `<G>/commondir` names (relative to `<G>`), or of `<G>` when it has none; `workTree` is the folder that holds the file; `linked` is whether `commonDir` is not `<G>`'s realpath; and a linked work tree is one only if `<G>/gitdir` names this `.git` file back (compared as realpaths), else null: a copied pointer file gives no repository. None up to the root, or anything unreadable: null. It is synchronous, as `locate`'s reads are, and mirrors only this much of git (no `core.worktree`, no bare repository, no mount boundary). It is the admission's predicate (§G) read once, when the fact is written: it decides what the record says, which the consumers that take the record's word show. What may be read, written or listed is decided again at each act by §G, with git's fuller reader. `headBranch` reads the `HEAD` of the work tree's git directory and answers the name after `ref: refs/heads/`, else null (detached, unreadable, no repository).

`checkoutIn`, with `c` the folder's realpath, `rc = repositoryAt(c)` and `rl = repositoryAt(launch)`; "at or under" is at a segment boundary:

| the folder | answer |
|---|---|
| does not resolve | null |
| `rl` null (the launch folder is in no repository): `rc` null and `c` at or under launch | `{ checkout: launch, cwd: c, workTree: null, linked: false }` |
| `rl` null, anything else | null |
| `rc` null, or `rc.commonDir` is not `rl.commonDir` (no repository, or another) | null |
| in the launch folder's own work tree, at or under launch | `{ checkout: launch, cwd: c, workTree: rl.workTree, linked: rl.linked }` |
| in the launch folder's own work tree, elsewhere | `{ checkout: rl.workTree, cwd: c, workTree: rl.workTree, linked: rl.linked }` |
| in another work tree of the same repository | `{ checkout: rc.workTree, cwd: c, workTree: rc.workTree, linked: rc.linked }` |

    export function workingFolder(record: Folders): WorkingFolder {
      const filed = record.worktree?.path ?? record.directory;   // where the engine files the session: build F's folder
      const launch = record.launchFolder ?? filed;
      const path = record.agentFolder?.checkout ?? filed;

    export function workingWorktree(record: Folders): { path: string; branch: string | null } | null {
      const at = record.agentFolder;

    export function workingBranch(record: Folders & Pick<SessionRecord, 'branch'>): string | null {
      const at = record.agentFolder;
      return at === undefined ? (branchName(record.worktree?.branch) ?? branchName(record.branch)) : branchName(at.branch);
    }

### §G. What may be read there (M3)

**The invariant** (Decision Log 7). A folder that comes from one of the two facts becomes the root of a read or a write only through the one admission, evaluated at the act. A consumer that only labels, offers or counts takes the record's word. Which of the two a consumer is, is decided by one test: does it cause a file-system read, a file-system write or a git call at that folder? The invariant binds every command that checks a folder against a session; a command that checks none, for a record's own directory either, is outside it and is named in the table (Decision Log 9, point 2). **The admission.** In `src/services/files/allowlist.ts`:

For the selector's `launch` or `path` of the record:

- it is the string `record.directory` or `record.worktree?.path`: `{ folder: that string, checked: false }`. It is one of the record's own roots, trusted and resolved by each caller as it is today.
- otherwise it comes from a fact, and the predicate decides. Let `real` be its realpath and `anchor` the realpath of `record.directory`. It is admitted when: both resolve; git finds a work tree for `real` (the folder that holds the nearest `.git` at or above it); and that work tree is itself one of the work trees of the repository `anchor` is in, its main one or one that repository's `worktrees/` entries name. Then `{ folder: real, checked: true }`: the caller uses that realpath, the value the check ran on. Otherwise null. Any failure to read is null.

The predicate has two readers and one table of cases. *Git's own files*, for the files service, uploads, `git.lsFiles` and Source control: `discoverRepo` and `worktreeList` in `src/shared/machine/git-reads.ts`, given plain file access (its `GitFiles` interface over `node:fs/promises`); no second reader of git's layout is written for the boundary, no process is started and nothing is kept between calls. *The machine's `git.worktree.list`*, for the endpoint (below). `rootsOf(record, remoteHomes)` keeps its signature and its order for the record's own roots, and appends the two folders it admits.

**The cases.** Both readers' suites run every row, over the same repositories on disk (`allowlist.test.ts`; `test/endpoint/checkout-rule.test.ts`). *One narrow exception to the two readers' agreement (Decision Log 16):* a nested repository whose `.git` or `HEAD` cannot be read. The files reader meets a read failure and refuses. Both answers hold under the rule ("the work tree git finds"; "any failure to read is null"); the case is pinned in `allowlist.test.ts` only, and no second metadata reader is written into the endpoint to force one answer. *Two more places where the readers differ (Decision Log 21):* a per-worktree `core.worktree` (with `extensions.worktreeConfig`) that sends git to another folder: the files reader admits the registered linked checkout, while git works in the redirected folder and the endpoint, which asks git, refuses (a configuration the machine's owner sets on their own repository; nothing remote is admitted by it; a tracker row, closed when the files reader reads the per-worktree configuration or asks git).
