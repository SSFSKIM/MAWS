## Purpose

Today every place that opens a file (a path in the transcript, Review's Open, a row of Files' tree, the agent's `show_pane`) opens a tab in the main area and selects it, so the conversation leaves the screen at the moment the person wants to read a file beside it.

After this landing a file opens beside the chat: as a tab of the side column, among Review's and the terminals' tabs, with Files' tree at its left. The transcript keeps its place and the main tab strip gains nothing. A single click shows the file in the session's one preview tab, whose title is in italics and which the next single click reuses; a double-click, an edit or a move keeps the tab. The file moves to the main area only when the person asks: by dragging its tab onto the main strip, by "Move to main area" in the tab's menu or in the file's bar, or by ⌘-click on a path link or a tree row. It moves back the same ways. A move keeps the scroll position, what was typed and its undo history, and asks nothing. After a relaunch the files beside the chat and the one in the main area are where they were. A side tab can also be dragged between the column's two groups, and a strip with more tabs than fit keeps its selected tab in view.

How to see it working: in a session, click a file path in the transcript: the file shows at the right of the chat with the tree at its left, the transcript has not moved, and the main strip holds the same tabs as before. Click another row of the tree: the same tab now shows that file. Double-click its tab: the title is no longer italic. Type in the file, then drag its tab onto the main tab strip: the file is a main tab with the text typed, and ⌘Z undoes it. Choose "Move to side surface" in that tab's menu: it is back beside the chat. Quit and relaunch: it is still there.

Read at `c6a22fe89`. Paths are under `src/renderer/src/` unless they begin with `src/`.

2. **A main file tab** is `{ kind: 'file', path, line, appSessionId, machine }`, one per machine and path whatever its session (`tabId` in `src/shared/ipc/schema/layout.ts`: `file:<machine>:<path>`); opening it again takes the line and the session of that open (`openIn`, `stores/layout-model.ts`).
3. **The viewer** (`viewer/viewer-store.ts`) keeps one entry per key, the main tab's id, with the file's text, its load and its editing state, and beside it what a code view leaves behind when it unmounts (`viewState(key)`: CodeMirror's state with its undo history, the scroll offsets). `FileBody` (`viewer/FileViewer.tsx`) draws an entry by its key; the File artifact's view mounts the same component under a key of its own. 4. **A code view** (`viewer/CodeView.tsx`) makes its editor in a passive effect from `viewState(key).editor` and writes its state back in that effect's cleanup. Within one React commit the cleanup of a view that goes runs before the effect of a view that comes.
5. **The side column** (U8b). A tab is a `PanelTabRef { id, toolId, pinned }` in the session's list (`panel.<session>`) or among the pins; what a tool keeps of a tab is `panelParams[tabId]`, stored under `panelTools.params` (`setPanelParams`). `panelHost.addTool` (`panel/host.ts`) adds a tab or, for a tool that is not `multiInstance`, re-targets its one tab. `sideGroups`, `groupForOpen`, `showSurfaceTab`, `moveSurfaceTab` (`panel/surface-model.ts`, `stores/layout.ts`) hold the two groups. 7. **Only an artifact moves** between the column and the main area (`panelTabMoves`, `moveArtifactToTab`, `moveArtifactToPanel` in `shell/transfer.ts`); the drag state's panel form carries an artifact id (`dragging` in `stores/layout.ts`). The side strip scrolls only once every tab is cut to its least width (`fitTabs`), and nothing scrolls its selected tab into view: the shared focus helper of F6 passes `preventScroll: true` (`keymap/shell-navigation.ts`).
8. **The editor's registrations** (`tools/code/editor/register.ts`): the close question for a main `file` tab (`guardFileClose`), `file.save` and `file.commentLine` on the tab on screen, and the verdict that keeps a dirty file tab from being replaced. The quit question's "Save all" walks the viewer's entries, not the tabs (`saveAll`, `viewer-store.ts`).

## Decisions settled at authoring

Each is a means the child's file leaves open, decided here with its reason and what it beat.

1. **A file's side tab is a tab of the Files tool.** `files` becomes `multiInstance`; a tab of it either holds a file or is the tree alone. That is what U8b built for (its §C.3: "a ref of U6's tool in the session's list, its path among that tab's params"): `groupForOpen` already sends an open to the group that holds a tab of the tool, and the Files icon and ⇧⌘F already show the tool's tab last in view. Lost: a second tool for a file. Build F would draw it as a tab of a tool it does not know, and "the first file opened takes that tab" would be a close and an open across two tools, which the store does not read as a replacement.
2. **What a tab stores** is `{ file, line, preview? }` under `panelTools.params` (Interfaces §A). The key is `file`, not `path`: build F's Files tool reads `params.path` as a path to reveal and then open as a main tab, so under `path` a stay on F would open a main tab for every Files tab it showed. Under `file` F ignores it.
3. **One document per file in the window.** The viewer's key for a file beside the chat is the id its main tab would have (`fileKey`, Interfaces §B). So a move changes no key, and the entry, the unsaved text and what the code view left behind need no re-keying. That alone does not keep them (the first writing said it did, and the review showed two ways it would not: Decision Log 4): the viewer's prune must count a side file's key as open, and a key that is moving must be held out of the prune and out of the 20-entry cap until its destination has mounted (Decision 20; sequences 1 and 11). Lost: a key per side tab with a re-keying at each move, which would have to move seven maps of the viewer store in step. What follows from one key: the main area and the side column never both hold a file (rule 3 of Interfaces §B), because two views of one key under two sessions would take the entry from each other at every render.
4. **Build F reads what this stores** (Interfaces §A): answered by reading F's source, proven by the cross-build scene (R9).
5. **The open rule is one pure function** (`placeOpen`, Interfaces §B) and `openFile` is its only caller, so every opener behaves alike and the rule is tested as a table.
6. **Preview and kept.** A tab opened by one click is the preview tab; the session has at most one. It becomes kept by a double-click on its tree row or on the tab, by the first edit, by a move (to the main area, or to the other group), and for an opener that says so (`keep`). A kept tab is never reused for another file. This is the child's file's rule; what is decided here is where it lives: `preview: true` in the tab's params, absent once kept, so a relaunch keeps the difference.
7. **Closing the last file's tab closes the tab.** No tree-only tab is left behind; the Files icon and ⇧⌘F add one when the session has no Files tab, as today. "+ ▸ Files", the Files icon and ⇧⌘F show the tree-only tab the session has (its own, or the pinned one) and add one only when it has none, never a second: by the tool's `reuse` (Decision 21), so the strip needs no case of its own for Files.
8. **The tree marks, and does not follow.** The row of the file in view is marked as selected when it is listed; the tree does not open folders by itself to reach it. The Files tool's `params { path }` reveal, which nothing in the window uses, is removed with its two waiting states. Lost: opening the file's folders at every open, which would move the tree under the person each time the agent or a link opens a file.
9. **A person's open leaves a page; an agent's does not** (root UC-12). `openFile` closes an open destination before it opens beside the chat, as a side-surface key does; with `asked: 'agent'` (the `show_pane` call) it does not, and the open is carried to the panel host with that mark.
10. **An open made before the layout is read waits for it, and so does `show_pane`'s answer.** The open rule reads the session's list, which is empty until hydration; an open decided on an empty list would add a second tab for a file a restored tab already holds. So `openFile` before `hydrated` is kept, once, and decided at the moment the layout is read, in call order. `showPane` does not answer until then: it answers with the id of the tab that exists after the open was made, never an id made up beforehand, and it keeps one open per request however long it waits. Two ends without a tab. The session is not one the hydration keeps: the kept open is dropped, and the answer is `{ ok: false }` with today's `TOOL_ERRORS.paneUnavailable('file')` (nobody reads it: the session is gone). The layout is not read within `PANE_LAYOUT_WAIT_MS` = 5,000 ms: the kept open is withdrawn, so it does not open later unannounced, and the answer is `{ ok: false }` with a text of its own, because the agent reads it and "not available in this build" would teach it to stop trying (ruled, Decision Log 10): `TOOL_ERRORS.paneNotReady`, exactly `show_pane: the MAWS window was still loading its layout; try again`, with its dated line under the frozen-texts contract (X9; "The pull request"). The bound is under the host's own 8,000 ms (`PANE_ANSWER_MS`), so the window's answer arrives before the host gives up.
11. **The two direct openers go through `openFile`** (the Sources card's row, a side thread's anchored file): one call each, in U8's and U5's files (Interfaces §F). `transcript/shell.tsx` knows no session and stays.
12. **The two View-menu actions** keep their ids and titles (`artifact.moveToTab`, `artifact.moveToPanel`: rebindable rows build F knows) and act on a file as on an artifact (the child's file).
13. **Where a moved file lands.** To the main area: the end of the focused pane's strip, or the place a drag chose; in front; kept. Unpinning is never refused. There is no second gate in the store (ruled).
    **The fourth way, read against the opener** (the architect's question of 2026-11-14; What the code holds, 10). A file open's reservation can never take the pinned tree-only tab's restored slot, by two things. First, `applyAdd` in `panel/host.ts` reaches `replaceRestored`, and any re-targeting of an existing tab, only inside `if (!tool.multiInstance)`, and Files is `multiInstance` from this milestone (Decision 1): through the host an add of Files with a file always gets a tab of its own, unpinned unless the add asks a pin. Within a session's own list the tree-only Files ref, when there is one, stands before every ref that holds a file: the older build shows and pins the first Files ref it finds, and so meets the tree. A list holds at most one tree-only tab, so one act can break the order, adding a tree-only tab to a list that already holds file tabs: it is put before the first of them, not at the end. The repair at the read restores the order where a stored list lacks it. It runs inside hydration, before its one `set`, so no state is ever published unrepaired, and what it changed joins hydration's write-back.
18. **Reopen closed tab is a caller of the one-view rule** (Decision Log 3). The `tab.reopen` handler, which is U6's (`app/shell-actions.ts`) and `reopenClosed`'s one caller, runs the second half of a move to the main area in the same synchronous run when the tab that came back is a file's: `dropSideViews` (Interfaces §D). `reopenClosed` itself (U13's) already places the tab where it stood and needs no edit; the insertion the ruling authorises there is not used.
19. **A move's stored layout** (Decision Log 4). On screen a move is one step (sequence 1). In the stored layout it is two or three keys, each written by itself (What the code holds, 12). The rule: the destination's keys are written, and answered, before the source's removal is written, by an ordered flush of `persistLayout` (`writeInOrder`, Interfaces §D); and the read resolves a file found in both by keeping the main tab and dropping the side ref (Decision 17). So a reload between the writes, or a second write that fails, leaves the file in both lists, never in neither, and the next launch shows it once, in the main area. Lost: one multi-key write, a new command of main's and a change to how every key is written, for a gain the read's rule already gives.
20. **The viewer store counts side files and holds a moving key** (Decision Log 4). (a) The prune's set of open keys is the main tabs' ids and the key of every file a side tab holds, in every session's list and among the pins, so an entry whose side tab is not in view stays, unsaved or not. (b) `holdKey(key)` keeps a key out of the ownership prune and out of the cap until the key is next mounted, or until no tab holds it; every move and the reopen take the hold before their first write.
21. **A tree-only add resolves to the tree-only tab there is** (found while reading the fourth way; Decision Log 10). Making Files `multiInstance` takes it out of the host's own rule for a single-instance tool (an add re-targets the tool's one tab, and a reservation made before hydration takes the restored slot). Without a replacement, the Files icon or ⇧⌘F pressed before the layout is read (`toggleSurface` then calls `panelHost.addTool('files', …)` with no params, since the lists are still empty) would add a second tree-only tab beside the restored one at the barrier, and "+ ▸ Files" would add one at every use. So a tool may say which existing tab an add re-targets: `PanelTool` gains one optional member, `reuse`, and `applyAdd` asks it for a `multiInstance` tool before it makes a tab (Interfaces §B; `panel/tool.ts` and `panel/host.ts`, U8's: two insertions, Interfaces §F). Files answers: for an add with no file, the first tab of the scope (the pins, then the session's own) that holds no file; for an add with a file, none. A re-targeted tab keeps its pin and its params, which is right here because both sides are tree-only. Lost: a repair after the fact in `tabs.ts` (a second tab made and removed in one step, depending on the order of two subscribers at the hydration edge); a case for Files in the strip's "+" (it would not cover the icon, the key or the barrier).

## The sequences that must hold

Each act below awaits something or spans more than one write. For each: what happens when the person acts in between, what happens when the awaited thing fails or never comes, and the test that holds the sequence open (not only the final state).

1. **A move is one step on screen.** The move's writes (the main tab opened and the side tab's ref removed, or the reverse) are made in one synchronous run with no `await` between them, so that React commits both in one pass and the code view that goes writes its state back (What the code holds, 4) before the one that comes reads it. The key is held first (`holdKey`, Decision 20), so neither the prune that the going view's unmount runs nor the cap can take the entry between the two views. The side tab is removed by a write of the list (`updatePanelTabs`), which the panel host answers by disposing the instance without its close question; `panelHost.closeTab` is not used for a move, because it awaits. *Test:* type, move, type again in the new place, undo twice: the text is the one before the first typing; in both directions and by each way; with the list write and the tab write observed to land before any microtask runs.
2. **A close that asks.** Closing a side tab whose file has unsaved edits awaits the person's answer. *In between,* the person can move the tab to the main area, switch session, type more, or save with ⌘S. *After the answer:* "Don't save" and "Save" act only if the same side tab still exists and still holds the same file; if it does not, the answer changes nothing (the main tab that now holds the file keeps its edits). "Save" closes only when the save answered `ok` and left the entry clean, as `guardFileClose` does today; a save that fails or conflicts keeps the tab with its message. A dialog never answered keeps the tab. *Test:* the dialog held open while the tab is moved; then "Don't save": the main tab still holds the edit.
3. **A preview replaced while its file loads.** The preview tab's file changes from one to another while the first read is in flight. The first file's entry goes with the prune; its late answer lands nowhere. *Test:* the first read's promise held, the second click made, the first answered: the tab shows the second file and the store holds no entry of the first.
4. **An open, and `show_pane`, before the layout is read** (Decision 10). *Test:* an `openFile` made before `hydrated` for a file a stored tab holds selects that tab after hydration; two such opens are decided in call order; a `show_pane` made before `hydrated` is answered after it, once, with the id of a tab the layout then holds (the test reads the tab by that id), and the same request never opens twice; for a session the hydration does not keep the answer is the `paneUnavailable` error, and when the layout is not read within `PANE_LAYOUT_WAIT_MS` (fake timers) it is `paneNotReady`, word for word; in neither case does a tab open then or later. *The barrier* (Decisions 16 and 21): a pinned tree-only Files tab restored and an add of Files with a file reserved before hydration leave the pinned tab pinned and tree-only and the file in its own unpinned tab; a tree-only add reserved before hydration (the Files icon pressed early), once and twice, leaves exactly the restored tree-only tab, brought into view.
5. **A restored tab whose file is gone or refused.** The tab is restored and shows the viewer's refusal or "not found", as any open does; it is not removed. A restored tab whose params this build cannot read is the tree alone. *Test:* both.
6. **A session that goes** (R5). The viewer's prune and this rule must not race: an entry whose tab is not mounted (another tab is in view) would be dropped by a prune that ran first. So one subscriber does both, in order: when the side tabs change it first opens a main tab for each file that left unasked with unsaved edits or a save under way, and only then runs the prune. The viewer store gets no second subscriber of its own on the side tabs. *Test:* a dirty entry whose tab is not in view, `dropSession`: the entry and its text stand, under a main tab that is not in front; the same with the file's tab in view.
7. **A drag whose source changes.** A tab closed, moved or replaced while it is dragged ends its drag (`endDragFrom`, as today); a drop that arrives for a tab no list holds does nothing. *Test:* the tab removed mid-drag, then the drop.
8. **The read of a layout** (Decisions 17 and 19; L8). `repairFileTabs` runs inside hydration, before its one `set`: a pinned ref that holds a file becomes the pinned tree-only tab; a side ref whose file a main tab holds is dropped, the main tab kept; a list's tree-only ref is put before its file refs. It is idempotent, and what it changed is written back by hydration. *Test:* a stored layout with each of the three, and with all three at once; a second read of the result changes nothing; and the cross-build scene.
9. **Reopen closed tab** (Decision 18). Close a file's main tab (its close asked, or it was clean); open the file beside the chat; edit it; Reopen closed tab. In one synchronous run the main tab comes back where it stood and every side tab of the file goes, the key held across it. *In between* there is nothing to await. *Test:* with the real editor: the reopened main tab holds the typed text, one undo removes it, no side tab of the file is left in any session's list, and Reopen closed tab's own history has lost the entry.
10. **A move's stored writes** (Decision 19). After the step of sequence 1 the destination's keys are written at once and the source's key is held until they are answered. *The person reloads between the two:* the stored layout holds the file in both lists; the read keeps the main tab (sequence 8). *The destination's write fails:* the source's removal is not written, the stored layout still holds the file where it was, and the next change of the destination's key writes both in order. *The source's write fails after the destination's landed:* both lists, as a reload. *At `beforeunload`* both are sent, the destination's first. *Test:* a reload simulated between the two writes (the stored map read back through hydration) in each direction; the second write made to fail; the first made to fail, then a later write; the order of the calls at `beforeunload`.
11. **The cap, a settling save, and a tab not in view** (Decision 20). *Test (the cap):* twenty entries with unsaved edits and one clean file with an undo history; that file is moved, in each direction: after the move its undo still works and its scroll is where it was. *Test (a save that settles):* a save answers `ok` in the turn before the going view unmounts, making the entry clean and evictable at that instant, with the store over its cap: the entry and its history stand. *Test (not in view):* a side file with unsaved edits whose tab is not the one in view, while another file is opened beside the chat and mounts: the first file's entry and text stand. The hold ends: after the destination's mount a later prune treats the key like any other, and a hold whose destination never mounts ends when no tab holds the key.
