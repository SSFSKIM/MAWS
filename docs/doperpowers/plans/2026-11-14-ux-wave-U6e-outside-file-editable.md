## Purpose

On this Mac a file outside the folders a session works in opens today when the session's transcript links it (U6c), and only to be read: typing changes nothing, and the editor's title says "Read-only". A person who wants to fix a line in a note, a configuration file or a file of another repository has to leave MAWS for it. And a file that no link names cannot be opened at all, because nothing in MAWS shows a file chooser for one file.

After this landing both are possible. Any file MAWS shows from outside the session's folders can be edited and saved, and nothing is written until the person presses Save. The file's bar says that the file is outside the session's folders and shows its path, so the person knows what they are editing before they save. A new command, Open File… (File menu, ⌘O, and a row in the Files list's menu), shows the system's file chooser and opens the chosen file in a tab beside the chat, editable. Which files may *open* does not change here: a file opens from outside the folders when the session's transcript links it, when the agent sent it, or, new, when the person chose it in the chooser. No tab looks editable and then fails at Save: MAWS's own files (its profile folder and its app) open read-only wherever they are, and a file that only the Library holds opens read-only with a sentence that says how to edit it. A session on another machine is as it is today.

How to see it working: in a session whose transcript links a text file outside its folders, click the link. The bar of the file's tab reads "Outside this session's folders" before the path. Type a word: Save appears, and the file on disk is still what it was. Press ⌘S: the file on disk now holds the word. Then press ⌘O, choose a text file from any folder: it opens beside the chat with the same bar; edit and save it; quit and relaunch: the tab is there, shows the saved text, and saves again.

## Words used here

- **The folders**: the folders a session works in, which the files service calls its roots (`rootsOf`, `src/services/files/allowlist.ts`): the session's directory, its added directories, its worktree, and the folders U8c-2 admits. **Outside**: a file whose real path is under none of them.
- **The daemon**: `mawsd`, the machine's background process. The files service (`src/services/files/`) runs there and nowhere else, and it is the only code that reads or writes a session's file for the window.
- **Main**: the app's Electron main process. Every command of the page passes its router (`src/main/ipc/router.ts`), which forwards a files command to the daemon.
- **The page**, or the window: the app window's renderer. **The top frame**: the page itself, as distinct from a frame inside it (an artifact's frame, a preview) and from a page of the in-app browser, which is another web contents.
- **Named**: the session's transcript writes the file's path whole as a link or a file chip (U6c's rule, `src/shared/files/named.ts`, searched by the daemon in `src/services/files/named.ts`). **Named by a counted form**: in a person's message, the agent's own text or a tool call's input. **Named by a result form only**: in nothing but what a tool returned (decision 22 has the table).
- **A grant**: the daemon's record that the person chose one file, for one session, in the system's file chooser. **Chosen**: a file that has a grant.
- **Sent**: a file the session's agent delivered by a call of its own (`send_file`, or `artifact_create` for a file), which the Library records with that session as its maker. **Added**: a file some other record of the Library points at (the person's "Add a file…", or anything the page created).
- **The real path**: a path with every link on it resolved (`realpath`). **The pin**: the real path of the document a tab holds, kept by the page with that document.
- **MAWS's own folders**: the profile folder, the bundle the daemon runs from, and the bundle of each app attached to the daemon.

## The landing's edge

**In.**

- A file outside the folders that the daemon admits for reading on this Mac because the transcript names it by a counted form (decision 22), the person chose it or the agent sent it is editable in its tab and is saved by a command of its own, `files.writeOutside`, under the rule of "The write rule".
- Open File…: the row `file.open` (File menu, ⌘O), the row in the Files list's menu, the system's chooser run by main, the grant the daemon keeps, the chosen file opened beside the chat as a kept tab.
- The bar of an outside file: that it is outside, and its path; the "Read-only" title gone wherever the file can be saved.
- MAWS's own files, never written by the files service, from inside the folders or from outside, and read-only with a sentence in the tab.
- A file that only an added record of the Library admits: read-only with a sentence, in place of today's tab that takes typing and fails at Save.

- An open the agent asked for (`show_pane`): admitted by the transcript or by the agent's own delivery, never by a grant.
- After a relaunch: a restored tab of a chosen file reads and saves as before (the grants are a file of the profile).

Any change to what an agent may write: the engine's own tools and permission rules are not touched, and no tool of MAWS writes a file through this route.

## The write rule

Five lines. Each has a test that tries to break it; the milestone that carries the test is named.

1. **The daemon writes a file outside a session's folders only when it holds, itself, evidence that admits the file for that session:** the session's transcript names the path by a counted form (a person's message, the agent's own text, a tool call's input), the person chose the file in the system's chooser, or the session's agent sent it. What a tool returned never counts. *Tests (M1):* through `files.writeOutside`, a named, a chosen and a sent file are written; a path with none of the three, a path admitted only for another session, and a file only an added record of the Library points at are refused with the bytes read back. *And for the narrowing (M1, M3):* a path that only a tool's result holds (a link in an MCP call's result) opens on a click, read-only, with its sentence; `files.writeOutside` of it is refused and the bytes are unchanged; once the agent's own text links it, it saves.
2. **The request comes from the app window's own top frame, which sends it only when the person presses Save.** Main cannot see a press. What it checks is the sender: its router answers no command of a frame, of a web contents that is no window's page, or of a page at another origin; and, after it has validated the input and before it forwards anywhere (to another machine's link, to this Mac's daemon, or in process), it lets an outside save and the chooser through only for a live page of an app window. *Tests (M2):* each such sender is refused `forbidden_sender` and nothing is forwarded, a window that is no app window aiming at a second profile's link included; *(M3):* in the page, opening, typing, a re-read, an agent's open and a tab shown again send no save; Save, ⌘S, the close question's Save and the quit question's Save all do.
3. **The save names the real path the file had when it was shown, and is refused when the path no longer resolves there.** The daemon resolves the path again at the save, opens it with no link on the way, and compares the opened file's real path with the one the save names. The save is a command of its own, so a daemon that cannot make the comparison does not know the command and writes nothing. *Tests (M1):* a folder on the path swapped for a link to a folder holding a file of the same name and the same bytes, and the last component swapped for a link, each between the read and the save and between the daemon's check and its open: refused, both files unchanged; *(M1, M3):* an edited tab held while the daemon is replaced by one of `f1852de3a` and one of `2c7044231`, with the same retarget: `unknown_command`, both files unchanged, and the page sends no `files.write` in its place.
4. **The save carries the hash of the content the person was shown; other content on disk answers `conflict` and nothing is written.** This is the save inside the folders, unchanged, and it claims what that writer does and no more: the compare and the write run inside a section MAWS holds per file, through the confirmed descriptor; a writer outside MAWS between the compare and the write is not caught, and a crash between the truncate and the last write leaves the file short (the limits `service.ts` records). *Tests (M1):* a file changed on disk since it was read answers `conflict` with its bytes unchanged; *(M3):* the page then shows the merge view.
5. **Never:** for a caller from another machine; a file in one of MAWS's own folders, by any write, whatever admits it, a root included; through `files.write`, which takes the folders alone as on master; a file only an added record admits; a create, a rename, a listing, a watch or a reveal outside the folders. *Tests (M1):* each refused; for another machine, with the transcript, the grants and the Library not asked at all; for MAWS's own folders, with a root that contains the profile and one that contains a bundle, through both commands, and with a forged grants file that a restart must not load.

**What the rule stops.** A frame of an artifact or of a preview, and a page of the in-app browser: they are not the top frame (line 2). A presentation window or the repair window, also when it aims at another profile of this Mac: no app window (line 2). A path that hostile content hands the page (a link in a Markdown file or in an artifact's text, a mod's surface, the target of an agent's `show_pane`): the page only opens a path, the daemon reads it only on its own evidence, and nothing writes until Save. Text the agent only read (a fetched page, a file's contents, an MCP call's result): a path it holds opens a file read-only, as on master, and admits no save (line 1). A caller on another machine (line 5). A made-up grant, and a grants file rewritten through a session whose folders hold the profile (lines 1 and 5). A link swapped in, also across a daemon of an older build (line 3). The agent: it can make the transcript name a file or send one, which lets the person open it; it cannot press Save, and its own writes stay the engine's.

**What it does not stop.** A fault in the app window's own page code: such code can send a save for any file that stands admitted for a save (named by a counted form, chosen or sent), with content of its choosing, since it can read the file's hash first. It cannot write a file no evidence admits, cannot grant one, and cannot write MAWS's own folders. And a process of this user that holds the token of the daemon's socket (`machine.sock`): it already has the daemon's whole reach, the terminal host's included, and this landing neither widens nor narrows that.

**What is the page's ordinary behaviour and no boundary.** That an open the agent asked for is not admitted by a grant (decision 19): the mark is the page's own, a page at fault could leave it out, and what it would then show is a file the person chose in that session.

One tracker row names the exit (a main-run "Add a file…" whose answer is both the artifact and a grant for the session it is opened under).
2. **R5, for an attached app of an older build.** The daemon learns an app's bundle from that app (`machine.client`, a command only main sends). An app of `f1852de3a` or `2c7044231` attached to this build's daemon tells none, so its bundle is protected only when it is the daemon's own. Such an app's page has no outside save; what stays open is its save of a file inside a session's folders that contain that app's bundle, which is today's behaviour of that build. Accepted as written (Decision Log 7): one tracker row, and no reading of an app's path from a process id.

## Decisions settled at authoring, as the rulings leave them

Each names what it beat. The numbers are cited as "decision N". The exact shapes are in Interfaces and Dependencies.

1. **The save is the act, and its admission is the read's.** The outside save asks the same question as `files.read`: is this path, outside the roots, admitted for this session by a grant, by the agent's delivery or by the transcript. One step in `precheck` answers for both, so whatever a later landing teaches the rule to name by a counted form is at once readable and writable, and nothing is writable that is not readable. Two kinds of evidence admit a read and no save: a name that only a tool's result holds (decision 22) and an added record of the Library (decision 20). This is the architect's reading of the condition (Decision Log 3), and it holds for a file the agent opened by itself: the agent's `show_pane` only opens a tab; the daemon reads the file because the transcript names it, and writes it when the page's top frame sends a save. *Beat:* making the open the act (a grant issued when a person's click opens the tab): the owner made a linked file the agent opened by itself editable too.
2. **The grant is held by the daemon and made by a command only main sends.** `files.grant { appSessionId, path }`: main-only, refused for a caller from another machine where it runs, answered by the files service, which resolves the path itself and records its real path. The process that decides (the daemon) reads the record itself. *Beat:* a file main writes and the daemon reads (two processes on one file with no order between them). *Beat:* a mark main adds to each request ("this path was chosen"): a key of a request's input is a key the page can set. *Beat:* a record in the page's stored layout: the page writes that.
3. **Main runs the chooser.** `layout.openFile { appSessionId }` is main's own command, as `layout.pickFiles` is: its handler shows the system's panel through the client port, then sends `files.grant`, then answers the page with the path. The session's id reaches the handler bare, and its machine as the router's `ctx.target`; the grant takes the bare id (R4). *Beat:* a daemon command that asks the client port for the pick: a request to the daemon has ten seconds, and a person takes longer.
4. **What a grant is.** One real path, for one session, with the time it was made. It admits that file and nothing beside it, for that session and no other, and it is asked only where the transcript is asked: a request that carries the key, on this machine, that the agent did not ask for (decision 19). The grants are a file of the profile, `sessions/file-grants.json`, written whole and atomically by the daemon before its memory changes, read once at the spine's start; so a relaunch, of the app or of the daemon, changes nothing. A session holds at most `GRANTS_PER_SESSION_MAX` (256), the oldest going first; a session's grants go when its record is removed. Decision 21 has the failures. *Beat:* a grant for the whole window: a session's agent could then be shown, and the person could save, a file chosen in another session. *Beat:* ending a grant when its tab closes: Reopen closed tab and a tab another build restored would be refused.
5. **The keys and the command** (R3). A read keeps U6c's request key, `named`, whose meaning widens to "admit a file outside the folders that stands admitted for this session, and tell me", and gains `agent` (decision 19). Its answer keeps `named: true` for any such file and gains `outside: { real, writable }`; any read's answer gains `own: true` for a file of MAWS's own. The save of an outside file is a command of its own, `files.writeOutside`, which takes what `files.write` takes and the real path, and shares its writer. `files.write` keeps master's input and takes the folders alone. So a daemon of either older build, which would drop a key it does not know and write by the folders, instead does not know the command and answers `unknown_command`; nothing is negotiated. A page that gets `named` without `outside` (a daemon of `2c7044231`) holds the file read-only, as U6c does. *Beat:* a key on `files.write` (the first writing): both older builds read inputs tolerantly, so a tab edited under this build and saved through an older daemon would lose the real path and could write another file of the same bytes (the review's finding 3). *Beat:* the daemon remembering which real path each read answered: state that a restart loses, where the save can simply say it.
6. **The pin and the admission are two things** (R6). The page keeps, per entry: the **pin**, the real path of the document it holds; and the **latest admission**, what the last answered read said of the file now (`named`, and `locked`: MAWS's own, only added, or named only by a tool's result). The pin is set when a read puts a document on screen (an open, or a re-read that lands on an entry with no unsaved edits), when Reload replaces the document with the disk's version (the pin is then that version's real path), and, for an entry that has none, by the first read that carries one; otherwise it does not move while the document has unsaved edits. The latest admission follows every answered read, under unsaved edits too: a file that became MAWS's own or only added stops being editable at once, the document stands, and Save sends nothing. A refused read changes neither: the bar shows the refusal over the edits as today, and Save, still shown, asks the daemon, which decides. The save sends the pin, and the daemon refuses it (`FILES_MOVED`) unless the file it opened, by a fresh `realpath` of the path whose `stat` is the descriptor's, is at that real path. The answer is `FILES_MOVED` only for a file the daemon still admits; a chosen file whose path leads elsewhere has no grant there, and a path whose last component became a link is refused before any of this, so both answer the service's refusal sentence and no answer says how an unadmitted path resolves. *Why the page does not simply read again and save to the new place:* that would let a link swapped in redirect the save after one more press.
7. **The order of the evidence** ("Reported" 8; R7). For a request that carries the key and is not remote, a path outside the roots is asked, in this order: a grant (a lookup; skipped for an open the agent asked for); the agent's delivery (a read of the Library's index); the transcript (the search, which answers a counted form, a result form only, or nothing); the grant once more, because the search awaits and a grant may have been made meanwhile. A counted form, a grant or a delivery admits a read and a save. Failing those, a result form admits a read and an open outside MAWS, and then any other record of the Library does; neither admits a save. The first that holds decides the mark.
8. **MAWS's own folders, at every write** (R1, R5). `own()`: the real path of the profile folder; of the outermost folder named `*.app` that holds the daemon's executable, when there is one; and of the bundle each attached app told the daemon. The files service writes no file under one of them: `files.write` and `files.writeOutside` both refuse it after the open, on the confirmed real path, whatever admitted the file. A read of such a file answers `own: true`, inside the folders too, and the page holds it read-only with the sentence. An app tells its bundle on a route only main can use: `machine.client`, which main already sends at each streaming, gains `bundle`. A value told is believed only as a folder to protect, so a false one can make a folder read-only and can open nothing. *Why these:* the profile holds the grants, the daemon's token and the settings, so a page that could write there could grant itself anything, and it can make a session whose folders hold the profile ("What the code holds today" 20); the bundles are the code. The owner's words keep everything else editable ("Reported" 10). *Beat:* the first writing's test for an outside admission only.
9. **The sender's guard, in the router** (R2). `isAppSender` holds for every command and already refuses a frame and a foreign web contents. The router gains one mechanism, `guardCommand(names, guard)`: a guard runs after the input is validated and before anything is forwarded, for the page's route, `dispatchLocal` and `invokeOwn` alike, and its refusal is the route's answer. One guard is registered, for `files.writeOutside` and `layout.openFile`: the asker must be a live page of a window in `appWindows()`. So a presentation window, the repair window and main's own in-process callers cannot save an outside file or raise the chooser, on this profile or through a link to another. *Beat:* `beforeCommand` (the first writing): its hooks run after the branch that forwards to another machine, and another profile of this Mac is such a machine, reached with no `remote` ("What the code holds today" 16, 17).
10. **No watch outside the folders; a change on disk is met at the save.** As U6c decided, a file outside the folders is read again when its tab is shown again or opened again, while it has no unsaved edits. A save over a file that changed meanwhile answers `conflict` and opens the merge view, which exists; nothing is overwritten unseen. *Beat:* a watch on the one file (U6c's decision 15 rejected it).
11. **What the bar and the editor's title say** ("The look"). The bar of an outside file starts with a label, "Outside this session's folders", before the path; its tooltip names the real path a save writes. The editor's title is gone for a file that can be saved. A file that cannot be saved reads "Outside this session's folders · read-only", with the reason as the editor's title and the label's tooltip. A file of MAWS's own inside the folders has no label (it is not outside) and the same title. The path is drawn as for any file. *Beat:* a line under the bar (law 3). *Beat:* marking the tab's title in the strip: the strip is U8's and U6b-1's, and a tab is narrow.
12. **`list`, `watch` and `reveal` are not touched.** The code forces none: the tab reads one file, the save writes one, and the folder of an outside file stays unlisted and unwatched.
13. **The chord is ⌘O.** Free in the table, in the menu's roles and in every editor of the page; the convention of macOS for Open; Claude Desktop's File ▸ "Open File…" has it (`main-process/index.chunk-BV3uOqbK.js:325087-325097` of `app-5.1231.2`; what its page then does was not traced). The row `file.open` stands before `file.save` in the table, so the File menu reads New chat; Close tab, Reopen closed tab; Open File…, Save file, Comment on this line. It takes no rebinding while build F can be gone back to (UC-6). It joins `SHELL_FOCUS_ACTIONS`, so that a page of the in-app browser does not keep the keyboard after the file opens.
14. **A kind MAWS does not draw, a folder, a package.** The chooser is asked for one file, so a folder cannot be chosen. A package (an app, a document bundle) can be chosen and is a directory: the daemon grants only a regular file, and the page says "Open File opens one file. A folder or an app's package cannot be opened here." Any regular file is granted and opens in its tab as that kind opens today.
15. **Where it is offered** (R10). The row `file.open` is registered while a session's chat is in front: no page covers the tab (`pageOpen` is false) and the session in front (`shownSession()`) is one the page knows on this Mac. Otherwise it is disabled as every unregistered action is: on the Overview, behind a page (Customize, the Library), with no sessions at all. For a session on another machine the Files list's row is drawn disabled and reads "Open File… (this session runs on <machine>)" (UC-7; Decision Log 6: until U6f).
16. **How the chosen file opens.** `openFile(appSessionId, path, null, { keep: true })` (U6b-1): beside the chat, as a kept tab. The path is the real path the daemon granted. A file chosen from inside the session's folders opens the same way; its grant is recorded and is not needed.
17. **`files.write` is master's, but for MAWS's own folders.** Its input and its admission (the folders alone) are unchanged, so both older builds' pages, a caller on another machine and the save of a file inside the folders are answered as today, with one difference that R1 makes: a file of MAWS's own inside the folders is no longer written by it. An older page, which does not read `own`, then shows that file as editable and its save answers `not writable: <path>`.
18. **Errors say nothing more than today, and a refused save says what to do.** A refused outside save answers the service's refusal sentence, `not writable: <path>` for a file of MAWS's own, or `FILES_MOVED`; none names what is at another path. The evidence is asked at the save, so a file that was admitted when it was opened can be refused when it is saved: the conversation was cleared and its new transcript does not name the file, the path moved, the transcript's search did not answer in time, or the session's 257th grant took this file's place. The edits are then still in the tab, so the page words that refusal as a way on: "Could not save: MAWS may no longer write this file for this session. Choose it with File ▸ Open File… to save it". Choosing the file grants it, and the same tab saves (when the tab's path is the file's real path; otherwise the chosen file opens in a tab of its own, and the edits are copied by hand). A daemon that does not know the save answers `unknown_command`, and the page says "Could not save: MAWS's service on this Mac is from an earlier version and cannot save a file from outside the session's folders. Try again in a moment"; it never sends `files.write` in its place. A grant that cannot be recorded fails the command, and nothing opens.
19. **An open the agent asked for is never admitted by a grant** (R8; the owner's rule: the agent by itself opens only what the conversation links). U6b-1's opener carries `asked: 'agent'` for `show_pane`. When the session already has a tab of the file, beside the chat or in the main area, the agent's show selects it and reads nothing new. Otherwise the tab it opens is marked (`agent` in the tab's params), its reads carry `agent: true`, and the daemon skips the grants for them: the file opens when the transcript names it or the agent sent it, and is otherwise refused as any file the conversation never linked. The first open of that file by the person (a click, Open File…, a move of the tab) removes the mark and reads again. The mark is stored with the tab, so a relaunch keeps it. *This is the page's ordinary behaviour and no security boundary:* the key only narrows, and what a page that left it out would show is a file the person chose in that session.
20. **A file from the Library** (R9). The Library admits a path for reading by two kinds of record, and the daemon can tell them apart. *Sent:* a file artifact whose maker is a session of the asking session's line (the session, or a side thread's ancestor). Only the engine host's tool server writes that maker, from the calling session of the agent's own `send_file` or `artifact_create`; every command the page has for making or copying an artifact records `human`, and no command changes a record's path ("What the code holds today" 19). Such a file is admitted for a save, with the mark `sent`. *Added:* any other record that `fileAdmission` reads. The page can make one, so it admits no save; the read's answer says `writable: false` and the tab is read-only with "Read-only: this file is in the Library, not in this session's folders. Choose it with File ▸ Open File… to edit it". *Beat:* letting `fileAdmission` carry a save (the first writing's card D, option 1, as it stood): the page can make that admission. *Beat:* moving "Add a file…" to main's chooser as a grant: "What could not be done as ruled", 1.
21. **The grants' failures** (R14). *A file the daemon cannot read as its own version* holds nothing for the run, is logged once (its size, never its content), and is replaced only by the next change. *At the start*, once the view can be read, the grants of every session the view no longer knows are dropped (a session deleted while another build ran). *A removed record* drops its grants; a failure to write the file then is caught and logged, memory is dropped all the same, and the file is written again at the next change. *An add that meets a removal:* `add` asks the view, in the same synchronous step as its write, whether the session is still known, and refuses when it is not; a removal after that step drops what the add wrote.
22. **Which names count for a save** (the architect's narrowing, Decision Log 7). The rule's own table (`rowClaim`, `src/shared/files/named.ts`) already separates the forms, and this landing changes one of them, a `user` row's text, by the ruling of Decision Log 8:

    | the link form in an `assistant` row's `text` block | the agent's own text | names | counts |
    | the link form in any string of a `tool_use` block's input; the value form (`chipPath`) of a read's or an edit's `tool_use` input | a tool call's input | names | counts |
    | the link form and the anchor form in a `user` row's text that is no tool result and that the person wrote (no arrival, or only `own`, by `readArrivals`), and in a person's queued prompt (`attachment`) | a person's message ("Reported" 17) | names | counts |
    | the same forms in a `user` row's text that carries any other arrival (a peer session's message, a notification, a subagent's message, a scheduled prompt, a command's output, MAWS's own answer or consent text) | text someone other than the person wrote (Decision Log 8) | names, as on master | never |

**`precheck`, in order**; a step not marked new is today's.

1. The path is absolute; the session has a record; the path is normal.
2. The roots, less the home for a remote caller.
3. *May the outside rule admit?* Only when the operation is `read`, `openExternal`, or, **new**, `writeOutside`; the request asked (`named` for a read and an open; always for `writeOutside`); and the request is not remote. Settled from the request's own context, before a grant, the Library or the transcript is touched.
4. The path's real path. When it does not resolve: the answer `missing` gives. When that is the refusal, the failure is one `missing` reads as absence, and step 3 said yes: `not found: <path>` when, **new**, the path as given is the real path of a grant of the session (and the request carries no `agent`), or the transcript names it by either kind of form.
5. The real path is under a root: go on, unmarked. Else, when step 3 said yes, **new**, the first of these that holds makes it a root of one with its mark: the session has a grant for this real path and the request carries no `agent` (`chosen`); `sent(appSessionId, real)` (`sent`); the transcript names the path as given by a counted form (`named`); the grant once more, by the same test (`chosen`). Else, for a request that asked and is not a save: the transcript named the path by a result form only (`result`); else a delivered file admits it (`added`). Else, for `read`, `openExternal` and `reveal` without the key, a delivered file admits it unmarked, as today. Else the refusal. `writeOutside` is never admitted by `result` or by `added`.
6. A path whose last component is a link is refused.

The transcript is asked at most once per `precheck`, after everything that does not need it. The rest of the boundary (`openConfirmed`, `confirm`, the type's judgement) is unchanged and runs with the roots step 5 left.

**`read`.** Every answer of a marked file carries `named: true` and `outside: { real, writable }`: `real` is the confirmed real path, and `writable` is false, with `why`, for the marks `result` and `added`. Every answer of a file whose confirmed real path is under one of `own()` carries `own: true`, marked or not, for every caller.

**`write`** (unchanged but for one test). After `openConfirmed` and before the file's section: the confirmed real path under one of `own()` answers `not writable: <path>`.

**`writeOutside`.** `openConfirmed` for a write with the outside rule allowed; then, before the file's section: the same test of `own()`; and the confirmed real path must equal `input.real`, else `FILES_MOVED`. Then the compare and the write, the code `write` runs. A file under a root is written by it too, with the real path compared.

**`grant`.** In order: a remote caller is refused (the service's refusal); the path is absolute and normal and the session has a record, as `precheck`'s step 1; no grants were given: the refusal; `real = realpath(path)`, a path that is gone answers `not found: <path>`; `lstat(real)` is not a regular file: `{ status: 'refused', reason: 'not-a-file' }`; `grants.add(appSessionId, real)`; `{ status: 'granted', path: real }`. A file inside the session's roots, and one of MAWS's own, are granted like any other.

**The grants' file.** Read once when the store is opened; decision 21 has the cases. `add` asks `known`, drops the session's oldest entries past `GRANTS_PER_SESSION_MAX`, writes the whole file with `atomicWriteFileSync`, then changes memory; no step of it awaits. `drop` and `reconcile` change memory first and then write; a failed write is logged and left for the next change.
