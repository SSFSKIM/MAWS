## Purpose

After this landing a request no longer takes the composer away. Today the session's oldest request stands in the composer's place under a frame that reads "… · Composer paused · draft preserved": to say anything the person must first answer, and to stop the turn they must choose "Deny and stop". A question that blocks nothing (a terminal session's asynchronous question) takes the composer all the same, and MAWS's own ask shows three times: a capsule, a notice above the composer, and a side sheet that opens by itself over whatever was open there.

After it:

- **A question's form is in the transcript, in the row of the call that asked it**: the engine's AskUserQuestion, the sminos ask (blocking or not), MAWS's own ask and a plan. Submitting turns the form into the row's answer lines.
- **A permission prompt is one card at the transcript's end**, with the others that wait as one line each under "Also waiting". The call's own row reads "Waiting for approval: `cmd`" with no spinner and no timer.
- **The composer and Stop are there the whole time.** A message sent while a request waits is a message; it answers nothing.
- **What waits out of view is named**: a card "Waiting for you" in the card column lists the session's waiting requests, and the jump button reads "Needs your input". Either one scrolls to the request and puts the keyboard on it.
- **A terminal session's asynchronous question shows its answer on its own row** ("header → answer", or "Dismissed"), on this machine, on another machine and after a reload, in place of the row reading "Not answered" for good.
- **Nothing above the composer reminds of a question, and the Question sheet opens only when the person opens it.**

How to see it working: the unit suites named per milestone, and the Electron e2e groups under "Proof that an executor does not run", whose scenes hold a prompt open and type into the composer beside it, answer a question in its row twenty rows above the end, and find the answer of an asynchronous question on its row after a reload.

## Words used here

- **The list:** a session's waiting requests: every attention item of the session for which `waitsOnAnswer` holds (`src/shared/attention/kinds.ts`: it waits, and it names a request), oldest first. It is the predicate U8b's column already uses to decide whether the waiting-requests card is present.
- **A form:** what a question, MAWS's ask or a plan is answered in. **A prompt:** a permission prompt. **A card:** the one request card component (`src/renderer/src/request-card/RequestCard.tsx`), whatever it shows.
- **The call's row:** the transcript row of the tool call that raised a request: a `question` row (the engine's AskUserQuestion and the sminos ask), an `ask` row (MAWS's ask; its view is the capsule, `transcript/view/rows/AskCapsule.tsx`) or a `plan` row. **A waiting row** is such a row while a request of the list joins it by the call's id.
- **The end row:** one row with no turn, appended after every other row of a transcript while a request of the list has its place at the end. It is the child's "region at the transcript's end".
- **A place:** where a request of the list is drawn in one transcript: `row` or `end` (Interfaces §A).
- **The host seam:** the transcript's one way to let its host draw a row: a row of kind `request_slot` is drawn by the function the host gave as `renderRequest` (`TranscriptProps`, `registerRequestRenderer`). Desk web draws the tail of its session view through it.
- **The dock:** `DockedCardFrame` in the composer's place (`src/renderer/src/composer/docked/`). After this landing only the trust, relay-down and failed-start cards use it (`sessions/SetupCard.tsx`).
- **A mod's site:** an ask of the engine's surface for a component (`SurfaceRow`, `src/renderer/src/engine-surface/`), by which a mod can rewrite or draw a row (law 2).
- **The routes** (law 5): *runs* (a session MAWS runs on this machine), *terminal* (a terminal session, through its sminos bridge), *remote* (a session on another machine, of either kind). **Build F** is `f1852de3a`; **the master build** is `2c7044231`; the owner's machines run the second and keep the first to go back to.

1. **The transcript's end is a row.** The end row is appended after every other row and drawn by the virtual list like any row, so the list measures it, follows it and anchors around it by the rules it already has. The alternative, an element after the list's sizer inside the scroller, lost: the follow rule reads the sizer as the scroller's first child and compares its committed height with the virtualiser's total (`pinEnd` in `transcript/view/Transcript.tsx`), and a second height beside it would have to be taught to each of those comparisons, in the code the owner marked keep.
2. **The mark is in the model; the drawing is read from the list.** Which rows are waiting rows is an input of the transcript's derivation (`ui.waitingForms`, Interfaces §B), so that every fold decides from the row alone (C13). What the row then draws is the card for the list's item, read in the view as the run's line already reads it (C8). The alternative, the view alone, lost: a plan row inside a turn the reader collapsed, or inside the to-human view's working record, would be folded away with its form.
3. **One seam, unchanged.** The form of a waiting row and the end row are both drawn through the host seam that exists (C6): the row's view hands the renderer a slot value for its request; the end row is a slot row with a reserved request id. No export is added to `transcript/index.ts` and `TranscriptProps` does not change, so desk web and U6d's frozen-surface test are untouched. The alternative, a second registered renderer for forms and a component slot for the end, lost: two more public names for the same act.
4. **The list is `waitsOnAnswer`.** One predicate decides the list, the column's presence line (C14) and the jump button, so the card is never mounted with nothing to show. An item of the to-human view (a question left there, a must-read) names no request and is not in the list: its card stands at its mark, as today.
5. **A request's place** is decided per transcript: `row` when this transcript draws a waiting row for the call it names; else `end` (Interfaces §A). So a question whose row's page is not loaded, a subagent's question seen from its parent, and a request the bridge gave no call id are at the end without a rule of their own, and move to their row when it is drawn.
6. **The keyboard goes to the request's row, not to a control inside it.** "Puts focus on it" is the transcript row that holds the request (the waiting row, or the end row), which is focusable already and is the element the store's jump focuses. From there every key of the request acts, and Tab enters its controls. The child says "the open card's primary button, or the form's first option"; that lost because the dispatcher refuses a request's key from a button or a radio by design (C15), so Esc, the digits and ↩ would be dead exactly after a jump (Reported, 2).
7. **A prompt's keys stay in the keymap.** The three chords reach a prompt from the composer and from an unfocused page through one option of a binding, `claims` (Interfaces §F), an insertion in U6's dispatcher like U1a's `fresh`. The binding itself says whose focus the press may come from: its own row, its session's composer, or nothing with its pane active (the ruling of 2026-11-15). The first draft bound the chords within the whole pane, which let a press made on another request's row answer the prompt. The alternative is Claude Desktop's own capture listener on the card; it lost because it would be a second path beside the one keymap (UC-6): a rebinding would not follow it, and the order between it and the composer's keys would rest on which listener was added first.
8. **Between the answer and the transcript's own row, the row says what is known**, in this order: the transcript's answer; the answers this window sent; for a terminal session, the bridge's settlement, found by the call's id (C17): withdrawn by other than the bridge reads "Dismissed", answered elsewhere reads the settlement's own words ("Answered in the terminal"); else "Not answered". The settlement survives a reload and is the same in every window of the machine, which is why it is read before giving up; the window's own answers are the only source of the answer's text before the delivery. All three reach the row as one value in the attention store (Interfaces §G), because a row's view must not import the lane A store: it imports MAWS's IPC client, and desk web bundles the rows.
8a. **A request answered elsewhere while its row still waits says so** (the architect's ruling of 2026-11-15, on M2's `closed` phase). When a card's delivery ends as answered elsewhere (`not_pending`, then `closed` after two seconds) the item can stay in the list until the list drops it, and nothing bounds that gap. (1) A row never draws an empty form slot: a row whose item's delivery is `closed` draws no form and no control, and each question line reads what decision 8's order gives. (2) That order must not give "Not answered" there, which would be false: the store writes, where the delivery turns to answered elsewhere, a receipt whose words are the existing sentence "Already answered elsewhere" (a `settled` receipt, the same kind of value as a settlement's words; no new sentence). It follows the receipt's lifetime rule (the ruling on M1's D-2): it lasts until the row carries its own answers, which then win, or the session leaves; like every `settled` receipt it never replaces an `answers` or a `dismissed` one, so a terminal session's settlement keeps its own words ("Answered in the terminal"). (3) In the row the sentence does not go after two seconds: the two-second timer is what closes a card (the docked card until M3, the column's card and the end's after), and the row keeps the receipt. (4) A permission prompt's row in the same gap draws no form and reads as its tool row reads without a prompt; nothing is added there. (5) At the end, a `closed` card counts as nothing to draw when the region picks which card is open. Pinned in M3; a scene in M7 only if one can reach it without a second window, else it rests on unit tests.
8b. **A plan's row keeps the known answer too** (the architect's ruling of 2026-11-15 (UTC)). The lasting-receipt rule of decision 8a holds for a plan's row as for a form's: while the row has no outcome of its own it reads the call's receipt from the attention store and shows that receipt's words (`settledWords`, e.g. "Answered in the terminal"; or "Already answered elsewhere") in the place of the Pending badge, never beside it; the row's own outcome wins when it arrives; the receipt goes when the session leaves. The three-second settling line is the end region's notice only; the plan row does not draw it. No new sentence. A plan with no receipt and no outcome still reads "Pending". Reason: a known answer must never read as unanswered again because a timer ran out.
9. **The answer's own line stays derived and folds with its turn.** U3a's `answer` notice leaves the rows a fold keeps (the hand-over) and nothing else about it changes: it stands at the head of the turn in which the answer reached the agent, visible when that turn is open; when it is the turn's only work it stays in view and the turn gets no line (the ruling of 2026-11-15, Decision Log). Not deriving it where the row carries the answer is what the child recommends to U3; it lost here because the notice is the head row a turn's `opener` is read from (C11), because a page of history loaded later would have to take a line away from a turn already drawn, and because where the answer reached the agent is a fact the row above cannot say (Reported, 3).
10. **A question dismissed or declined whole keeps its lines, each reading "Dismissed".** An answered receipt is one line per question; a dismissed one keeps the shape and says the one word (the owner's card 2 can change it to a single line). On MAWS's ask the capsule's state word reads "Dismissed" and its lines read "Skipped", as the child says.
11. **The frame's later-commit focus hand-over goes with the dock.** U1a's decision 17 kept a mark alive for a frame so that the next prompt's frame could take the focus a commit later. No request mounts a frame now; the three setup cards keep the same-commit hand-over C7 built. The tracker row of 2026-11-13 on that mark is closed as moot.
12. **`state.pending` stays** in the transcript's state (U2's `groupInput` reads it); only the rows made from it go.
13. **Which card is open at the end** is the transcript's state (`WaitingView.open`), not the end region's: the oldest by default; a request shown or chosen stays open until it leaves the list; then the oldest remaining. It is not stored and not shared between two panes of one session. It moved out of the component so that the one operation of decision 19 can set it.
14. **What the composer still shows above itself** is the oldest waiting notice that names no request: an error, an interruption, "auto mode unavailable". A request the app cannot read or answer (an undeclared dialog, a request whose read failed) is in the list and is drawn at the end, with the card's own "The request could not be read" and Retry.
15. **A child's transcript lists the requests that carry its agent's id**; the parent's lists all of the session's, the agents' among them at its end, named "from <agent>" by the card as today. It is conditional on the producer sending the id: one recorded fixture shows it for the engine's route, none was read for the bridge's (Interfaces §A). A request with no agent id is the session's, at the parent's end.
16. **The harness's `docked` placement for a request becomes a transcript's end** (C20), so that `e2e:requests` stands where the app draws.
17. **A card's delivery is held by the request, not by the element.** The answer in flight, its failure with Retry and "Already answered elsewhere" live in the attention store under the item's id (Interfaces §G). A row of the list unmounts when it is scrolled far away, and a card whose answer was in flight would otherwise come back looking unanswered, or lose a failed write without a word. The alternative, pinning every waiting row mounted in the virtualiser, lost: it changes which rows the list mounts, in the code whose behaviour is a keep, to save a move of three values into a store. It is built as a milestone of its own, before any placement changes (M2).
18. **The guard is per request and re-arms.** Whether a key may answer a prompt is not one timer from the mount: the grace starts again when the card comes back into view, when its row of buttons becomes wholly visible after it was not, when an overlay closes, and when the card becomes answerable again (Interfaces §F, with what of Claude Desktop's guard is built and what is not). The first draft checked the buttons at the press alone, so a card partly in view for seconds could expose its buttons and take ⌘↩ at once.
19. **One operation shows a waiting request.** Each transcript has `show(id)`: it checks that the request still waits, selects it at the end when it is there, scrolls, and puts the keyboard on its row; when the request is gone it says so and focuses nothing that answers. The "Also waiting" lines, the pill, the column's card, a Needs-you row (its session's oldest item: a row is its session's, so it never names a younger request), a notification's open and ⇧⌘J all go through it (corrected 2026-11-15, the architect's ruling on M5). The first draft scrolled to the end and focused its row, which with two prompts waiting left the keyboard on the one that was open, not the one chosen.
20. **The settling receipt is held outside the end row.** "Answered in the terminal: Allowed" stays three seconds where the request stood, as a receipt with no control that counts as nothing waiting, kept in the attention store by a timer of the follower's; the end row is present while one is held (Interfaces §G). A component's timer inside the row would die with the row when the last request leaves.
22. **The window never withdraws a request the engine still holds** (the architect's ruling of 2026-11-15 (UTC), on probe 8). A request's card leaves on that request's own settlement or cancel frame (`control_cancel_request` with its request id), or when its child ends, exactly as the engine reports it; never on Stop itself, a turn's end or idle. On Stop the engine cancels the main loop's pending request at once and keeps a subagent's live (`spikes/protocol-probe/findings-uxwave-u1b-interrupt-pending.txt`); so a child's card does not leave on Stop and its buttons still answer. The code holds this already: the broker retires an item only on its cancel frame, its answer's confirmation, or the process's exit (`src/engine-host/broker.ts` 234-248, 277-292), and nothing in the window clears a pending request on Stop.
21. **A receipt's identity is the addressed session with the call.** One engine session and call id can exist on two machines; a receipt keyed by the call alone would show one machine's answer on the other's row (Interfaces §G).

## Acceptance

Each is behaviour a person or a test can see. The child's line it satisfies is in brackets. Unit proofs are named in the milestones; scenes in "Proof that an executor does not run".

1. **A prompt at the end** [A2, A9, A16]. In a mode that asks, the agent runs a shell command. One card stands after the transcript's last row; the composer takes text and Stop is there; the call's row reads "Waiting for approval: `cmd`" with the waiting glyph and no spinner, timer or line counts; when the call is inside a folded run the run stays folded and its line reads the same (U2a's, unchanged). There is no pointer row, and "Composer paused" is drawn for no request. A message typed and sent while the prompt waits joins the composer's stack as at any time a turn runs and the prompt still waits. Stop withdraws the prompt and its card leaves (the main loop's request: the engine cancels it with `control_cancel_request`; a subagent's request stays live and answerable, and its card stays, decision 22). Deny with a reason and Deny and stop work as before, and the card for a one-line command is at most 200 px tall at the column's width (U1a's scene, now at the end).
2. **Keys on a prompt** [A3]. With the open prompt armed and the composer empty: ⌘↩ allows once, ⇧⌘↩ gives the lasting scope its button names, Esc denies, when the keyboard is in that session's composer, on the prompt's own row, or on nothing with that pane active. From the keyboard on another request's row, on any other transcript row, or inside a child transcript in the same pane, they answer nothing. With text in the composer ⌘↩ is the composer's and the prompt stays. *Armed:* the prompt has been in view for 400 ms, no menu or dialog closed in the last 400 ms, and, for the two chords that allow, its row of buttons is wholly visible and has been for 400 ms; each of those 400 ms starts again when its condition is lost and comes back. So a prompt whose buttons scroll into view does not take ⌘↩ at once, and neither does one a closing menu uncovers. No key answers while an input method, the composer's own popup or dictation has the keyboard. A key held through one answer answers nothing else. ⌘. stays Stop.
3. **A question from MAWS's ask** [A4]. With a file open in the side column the agent asks. The capsule's row holds the Question sheet's form under its title line; nothing appears above the composer; the side column still shows the file. Submit turns the form into the capsule's answer lines. "Open beside" on the row opens the sheet with the same form and the same draft.
4. **A terminal session's asynchronous question** [A5]. Its form is in the row of the call; the composer is free and the agent works on; the session reads "Question waiting". A Skip that would leave every question unanswered is disabled with its reason; Esc ends nothing; Dismiss is there (enabled on this Mac where the bridge declares it). Stop ends the turn and leaves the question open.
5. **Its answer** [A6]. Answered in MAWS: the row reads "header → answer" at once; after a reload it reads the same once the delivery is in the rows (for an idle session the plugin delivers at once). Answered in the terminal: the row reads "Answered in the terminal" until the delivery lands, then "header → answer". No bubble holds the engine's framing text. In the transcript view, with the turn that received the answer folded, no "answered: …" line stands outside the fold (what the to-human view keeps is its own rule, U2b's once it lands).
6. **Finding what waits** [A7]. An asynchronous question is asked and the agent produces a screenful more. The card column shows "Waiting for you" with the question's line; the jump button reads "Needs your input" though the reader is at the end. Either one scrolls to the form and puts the keyboard on its row. With two prompts waiting, choosing the second's line (or opening it from a notification that names it) opens the second at the end, and an answer then is the second's; a line whose request was answered meanwhile says the request is no longer waiting and puts the keyboard on nothing that answers. Once answered the card is absent and the button is gone. With nothing waiting the card is never present.
7. **Several wait** [A8]. With two prompts and a question waiting: one card is open at the end and one line stands under "Also waiting"; the question's form is in its row; the column's card lists three, oldest first; choosing the line opens that prompt, folds the other, and it can be answered first.
8. **Dismiss** [A18]. While a blocking question waits, a message sent from the composer is delivered as a message and the question still waits. Dismiss on the form closes it and the row reads "Dismissed"; MAWS's ask reads "Dismissed" on its capsule with its lines "Skipped". A terminal session's asynchronous question dismissed in MAWS or in the terminal reads "Dismissed" at the press and after the delivery.
9. **Double-click** [A10] acts in the row's forms as U1a built it for the docked ones.
10. **A session shown without its transcript.** The compact composer of a closed floating card shows one line above itself, "Waiting for you · N", while N requests wait; a click opens the card.
11. **Outside the session nothing changes** [l4-approvals-07, "Unchanged placements"]: the Overview card answers in place, the hover card previews and answers by U1a's rule, the project channel's waiting cards answer MAWS's ask in place, Needs you lists what it listed.
12. **After the answer** [UC-1, S-07]. At the write of an answer the card or form is gone and no "Answered" line stands in its place; a failed write leaves it with "Couldn't deliver the answer" and Retry; a request the terminal answered first says so for three seconds where it stood, also when it was the only one at the end: the line has no control, and nothing counts it as waiting.
13. **A far row** [the child's check]. In a transcript of several hundred rows, a form that mounts in a row above the viewport does not move what the reader sees, and a waiting row scrolled out and back returns with its draft.
14. **Nothing else moves.** A transcript with no waiting input derives the rows it derives today (the fixture and snapshot suites of `transcript/model/` pass unedited but for the cases that pinned the slot row), desk web's session view draws its tail as before, and the three setup cards dock as before.

### §F. A prompt's keys (M4)

The rule is the child's (UC-6, "A permission prompt's keys"), made exact by the rulings of 2026-11-15 on whose focus counts and on when the guard arms.

**One option of a binding** (`keymap/useKeyChord.ts`, `keymap/dispatcher.ts`; U6's files, §I):

```ts
// ChordBinding, and useKeyChord's options
claims?: (event: KeyboardEvent) => boolean;
```

A binding with `claims` is asked at the press, once the chord matched and the refusals that hold for every binding passed (an input method composing; an open menu, dialog or popover; the chord capture). True: it takes the key, whatever element holds the focus; the row's own refusal of a text field, a key sink or a button is not applied to it, and `within` is not consulted. False: it is passed over as if it were not bound: the dispatcher prevents nothing, tries the row's other bindings by containment as today, and goes on to the next row of the table, so the key reaches the composer's own row or the page. Of two bindings that claim one press, the later registration. `fresh` applies after the claim, as today. No other binding changes behaviour.

**The binding** (`RequestCard` with `keys="pane"`, the open card of an end row): `request.allowOnce`, `request.allowLasting`, `request.decline`, each `fresh`, each with `claims`, enabled as today (live; the key bound by the variant; no allow key on a request flagged "default to no"; no key for an answer the port cannot carry).

**Two tests decide a press: whose focus it is, and whether the guard is armed.**

*Whose focus.* With `row` the open card's own transcript row (its keyboard owner) and `pane` the nearest `[data-pane]` element of that row (a transcript outside a pane: none), the press is this prompt's only when the focused element is one of:

1. `row` itself, or an element inside `row` that is not a text field, a button, a link or a button-like input (their keys are their own, as on every card today);
2. inside the session's own composer in `pane`: the box the pane's `Composer` registered as the session's focus target. Not a reply field or an inline edit drawn inside a transcript row, not the composer of another pane, and not while the composer's own popup (mentions, slash commands, history search) is open or dictation is live in it;
3. nothing (the active element is the body or none), and `pane` is the pane the shell says holds the keyboard.

Everything else is refused, and three of those by name, each with its test (M4): the keyboard on **another request's row** (a question's or a plan's waiting row, or the end row of another transcript); on **any other transcript row**; **inside a child transcript drawn in the same pane**. A transcript outside a pane has case 1 only.

*The guard* (`request-card/prompt-guard.ts`, new): one per mounted `keys="pane"` card, watching that card's element and its row of decision buttons.

```ts
export interface PromptGuard { mayDeny(now: number): boolean; mayAllow(now: number): boolean; dispose(): void }
export function watchPrompt(card: HTMLElement, buttons: HTMLElement, graceMs?: number /* 400 */): PromptGuard;
```

It holds four times and two facts, each moved by the event named:

| | what it is | set to now when |
|---|---|---|
| `shownAt` | the card last came into view | the watch starts; the card passes from out of view to in view |
| `wholeAt` | the buttons' row last became wholly visible | the row passes from not wholly visible to wholly visible; also at a press that finds it wholly visible while the last observed state was not (the press then counts as that moment) |
| `clearedAt` | an overlay last closed | an open menu, dialog or popover (the dispatcher's own selector) is seen open and then is no longer |
| `liveAt` | the card last became answerable | the card passes from not live (sending, failed, settled, concealed) to live |
| *in view* | any sliver of the card is visible | — |
| *whole* | the buttons' row is wholly visible | — |

*In view* and *whole* are the reference's two tests (`shared-192`:22930-23031 and :22950-22981): the element passes `checkVisibility`; its rectangle is clipped by every scrolling ancestor and by the window; in view when what is left is not empty, whole when what is left is the whole rectangle to within half a pixel **and** the element at each of its four inner corners (`elementFromPoint`) is the row or inside it, so a row covered by another element is not whole. *(As built, after the rulings of 2026-11-15 on M4.)* Between its start and a press the guard reads no geometry: one intersection observer of the card and the buttons gives *in view* and the buttons' clip; the four hit tests run again when the buttons come wholly into view and when an element is added to or taken from the body; a `data-state` observer gives `clearedAt`; every press reads the page in full. So the guard re-arms 400 ms after a cover it observed; a cover no observer saw is caught only if it is still there at a press, as in the reference. This rests on one fact of the app, pinned by a source guard: an overlay that takes keys is portalled to the body. They are watched as the reference watches them (`shared-192`:23033-23075): an `IntersectionObserver` on the element, and capture `scroll` and `resize` listeners, each re-testing on the next animation frame.

    mayDeny(now)  = in view  and  now − max(shownAt, clearedAt, liveAt) ≥ grace
    mayAllow(now) = in view  and  whole  and  now − max(shownAt, wholeAt, clearedAt, liveAt) ≥ grace

So the two tests meet the dispatcher like this. A binding **claims** the press when the focus test holds and the card is in view, and for `request.allowOnce` also when the session's composer is empty, read through one new member of the composer's port, `FocusTarget.empty(): boolean` (`stores/composer.ts`; registered in `composer/Composer.tsx` as the box's own emptiness, the one that greys Send; no composer mounted: empty). A claimed press **answers** only when `mayDeny` (for `request.decline`) or `mayAllow` (for the two that allow) holds; otherwise it is taken and answers nothing, as a press inside U1a's timer is today, so that an Esc or a ⌘↩ meant for a prompt that is not yet armed does not fall through to the composer as a Send now, a Stop or a queue. A press that is not claimed (the focus is not this prompt's, the card is out of view, ⌘↩ with a draft) is passed.

**What of the reference's guard is built, and what is not** (`ccbc7e432-C0cBrkw9.js:160-350`, read for this revision):

| the reference | here |
|---|---|
| not enabled, not active: no key | the binding is enabled only while the card is live |
| a repeat, or a held key: swallowed | `fresh` |
| an input method composing; Alt held with ⌘↩: passed | the dispatcher's refusal; the keymap matches a chord's modifiers exactly |
| the card off screen (any sliver counts): passed | *in view* |
| dictation live, or owning Esc: passed | focus test, case 2 |
| the composer's popup open: passed | focus test, case 2 |
| ⌘↩ yields to its own composer's draft; ⇧⌘↩ does not | `empty()`, for `request.allowOnce` alone |
| ⌘↩: 400 ms from the later of the card coming back into view and an overlay over it closing | `shownAt`, `clearedAt`. **Wider here:** any overlay that closed, not only one over the card, because the dispatcher's selector does not say where an overlay was |
| ⌘↩: 400 ms from the card becoming active, and from the pressed button becoming live | `liveAt`, one time for the card |
| ⌘↩ with the focus outside the card: held unless the row of decision buttons is wholly visible, and for 400 ms after it became so | `wholeAt` and *whole*. **Stricter here:** it holds with the focus inside the card too, and the press itself is checked against a stale watch |
| Esc: 400 ms from an overlay closing, and no grace from the card's arrival | `clearedAt`; **stricter here:** Esc also waits 400 ms from `shownAt` and `liveAt`, the child's "no key answers a prompt that appeared less than 400 ms ago" |
| seven predicates on the focused element (`ccbc7e432`:228-271: which element may hold the focus for the key to act) | **not built one by one, and not claimed:** their bodies were not read. The focus test above stands in their place and names three places only |
| one press recorded against one card, so it cannot answer two | the dispatcher runs one binding per press |
| typed letters on a focused card go to the composer; an element that owns Esc while focused; clicks swallowed while the card moves | **left out:** not asked by the child; the card does not move here |

**Order.** The dispatcher runs before the composer's editor (C15). `request.allowOnce` stands before `composer.queue` in the table, so with a prompt armed and an empty box ⌘↩ allows, and with a draft the claim is false and the composer's row takes it. Esc reaches `request.decline` before the editor's own Esc, so with a prompt in view it is the prompt's (denying, or inside a grace period doing nothing) and the composer's Esc does not run; with none in view the claim is false and the editor handles it as today. ⌘. is untouched. The Overview card's keys keep U1a's binding and timer.

### §G. What the attention store holds for a request (M1, M2, M3)

**The receipt** (M1; decision 8). What is known of a question's answer before the transcript's own row carries it.
