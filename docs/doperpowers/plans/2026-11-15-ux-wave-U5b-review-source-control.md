## Purpose

Today Review shows one file at a time under a list, has no way to say anything about a line, and loses its place when the window changes size. Its "This branch" compares a worktree with whatever the main checkout happens to have checked out, is switched off for a session in the main checkout, and leaves out uncommitted and new files. Source control is a pane for doing by hand what the agent does anyway (stage, discard, commit, push, open a pull request), and it never says which commits the branch holds, which of them are pushed, or which check of the pull request failed.

After this landing the owner reads an agent's whole change in one scroll: every changed file is a section with a header that stays at the top while its diff is under it, and a section folds. Pointing at a line shows an add-comment button; the comment is written in the wave's one comment card under that line, starts as "Send to main", and several comments go to the agent as one message that quotes each line. Review comes back to the file and line it was left at. "This branch" means one thing for every session: the working tree, new files included, against the merge base with the repository's default branch. Source control is a page that is read and changes nothing: where the work is, what is uncommitted, the branch's commits under "Not pushed" and "Pushed to …", and the pull request with its title, its state, whether it can merge and its checks by name. A commit's row opens that commit in Review, where it is read and commented on like any other change. The window no longer stages, discards, commits, pushes or opens a pull request.

How to see it working, on the wave's build: in a session whose agent changed several files and made a few commits, open Review and scroll through all of it without a click; comment on two lines, see "Send 2 comments", send, and find one message with two chips and the two quoted lines in the transcript; show another side surface, resize the window and come back to the same line. Open Source control: the four parts, in order; click a commit's row and read that commit in Review under a chip "Commit a1b2c3d"; click "This branch" and see the whole branch, the uncommitted edit and the new file included. Do the same for a terminal session on this Mac and for a session on another machine. In the suites: the unit tests named under each milestone and the e2e scenes of M6 and M11.

## What the code holds today

The child's statements, read against master `93905c9ef`. Lines move; functions are named.

**They hold as written.** Review is a file list (at most 40 % of the height) above one file's diff, with the mode toggles, the hunk counter and the previous and next file buttons belonging to that one file (`ReviewShell.tsx`: `FileList`, `FileSection`). `ReviewView.tsx` is the vertical scroller of one file, assigns the saved `scrollTop` once at mount and draws `DiffView` with no widget. The base of "This branch" is `git.worktree.branch`'s `base`, the main checkout's branch (`lookupBase` in `review-store.ts`; `branch()` and `baseOf` in `src/services/git/worktrees.ts`), so the chip is off for a session in the main checkout (`REVIEW_COPY.mainWorktreeBranch`). An untracked file is a row with zero counts, listed under Uncommitted only (`gitScopeFiles`), drawn as added when selected through `git.diff`'s `untracked` scope (`FileSection`, `loadFile`). Last turn lists absolute paths (`turnScopeFiles`); the file header is one truncating span (`REVIEW_COPY.fileHeader`); the "Last turn" chip is drawn only while `turnId` is set (`ScopeChips`). A held diff re-reads 250 ms after a new status and when the tool is shown again (`statusChanged`, `HELD_DIFF_REFRESH_MS`; the effect on `visible` in `ReviewShell`); a failed scope or file is kept until the scope re-reads (`createHeldDiffs`). The watcher drops a move of a remote-tracking ref that is not the status's upstream and emits only when the status's projection moved (`refMatters` and the emit in `src/services/git/watcher.ts`). `readPrView` answers a remote that is not on GitHub with the first line of `gh`'s stderr as the error, where `planPr` maps the same failure to `no_remote` (`src/services/scm/pr-state.ts`, `plans.ts`). Source control is the acting pane the child describes (`ScmShell.tsx`), `ScmDiff.tsx` is the one importer of `ReviewView` outside Review's folder, and `git.status.isWorktree` has no reader in the renderer. A daemon reads a command's input with the tolerant reader, also inside a union's matched member (`src/shared/ipc/tolerant.ts`; `tolerant.test.ts`, "follows a discriminated union into the branch that matches"), and answers a name it does not know `unknown_command` (`src/mawsd/front.ts`).

## Words used here

- **The stack:** Review's one scroller holding every changed file of a scope as a *section* (a header and a body). **Folded:** a section drawn as its header alone.
- **The band:** the part of the stack whose bodies are drawn: the sections within two viewports of the scroll position.
- **The live place:** where the person is reading in the stack: a file, a line of its diff and an offset; always kept. **A reveal:** a place the stack is still bringing into view (after a return, a request for a file, a hunk jump), which the person's input cancels.
- **Scope:** what Review compares: Uncommitted, This branch, Last turn, Staged, and from M9 one commit.
- **The pass, a flight, the card's host, the place line:** U5a's terms (`side/card/store.ts`): every unsent comment one surface holds for one session; one send of them; the component a surface mounts for the card; the line the host draws after a send to the main conversation.
- **The quote:** the text of the commented diff line, sent inside the comment's words as an inline code span on a line of its own.
- **Lineage:** what a session was forked from, kept in its record (`LineageSchema`, `src/shared/graph/session.ts`); for a side thread opened from a comment it holds that comment's anchor, and it is the one place an anchor is stored as a structured value.
- **The reads:** the three new `git.*` commands of §C. **The branch read** answers the base and the branch's commits; **the commit read** one commit's diff; **the working-tree read** the working tree against a commit.
- **The base:** the ref "This branch" and the commit list are measured against, by the default-branch rule (§C). **The merge base:** the commit that ref and `HEAD` share.
- **The machine link, an offer, the checkout rule, a capability:** U9's terms. The link is the connection from this window to another machine's daemon; an offer is a row of `OFFERS` (`src/endpoint/offers.ts`) saying a command is accepted over it; the checkout rule admits a `git.*` read whose `directory` lies in a repository of the session the caller may view; a capability is a name a machine lists when its build serves something (`ENDPOINT_CAPABILITIES`).
- **The daemon:** `mawsd`, the process that serves a machine's commands; on this Mac it can be of an older build than the window.
- **The two builds that bind:** `2c7044231` and `f1852de3a` (§K).
- **Kept:** said of a commit's diff: read once and not read again while it is held.

### §A. The text of a line comment (`src/shared/anchor/`; M1, M9)

**A quoted line (M1).** A comment made on a line of a diff carries that line's text. It travels inside the comment's words, so no command, schema or reader changes (decision 3):

```ts
// src/shared/anchor/message.ts
export const QUOTE_MAX = 400; // UTF-16 units; a longer line is cut and ends with "…"
export const BEFORE_THE_CHANGE = 'Before the change:';
/** A comment's words as they are sent: the quoted line above them; unchanged when `quote` is null. */
export function quotedComment(anchor: Anchor, quote: string | null, text: string): string;
```

The quote is written as **one inline code span on a line of its own**, then the words: `<ticks><line><ticks>\n<text>`. `<ticks>` is a run of backticks one longer than the longest run in the line, one at least; when the line begins or ends with a backtick or a space, one space is added at each end inside the span, which is how Markdown lets a span hold such a line and what a reader strips again. The quote is one line (a line break or another control character but a tab is replaced by U+FFFD), cut to `QUOTE_MAX`. **A line that is empty or holds only spaces has no quote.** For a removed line outside a commit's scope (a `file-line` anchor with `side: 'old'` and no `commit`) the caption comes first, whether or not a quote follows: `Before the change:\n<ticks><line><ticks>\n<text>`. With an empty `text` nothing is sent (the pass sends only comments with text, as today).

Why a span and not a fence (the architect's ruling on the drawn example, D4): the transcript's bubble draws a comment's words through the shared markdown pipeline (`CommentParts` in `transcript/view/rows/User.tsx` hands them to `Markdown`), and that pipeline draws a fenced block as a code block with a header row and a copy button, about 110 px for one line. An inline span is one compact line of code with no edit under `transcript/`. Both builds that bind draw a comment's words through the same pipeline, so they draw the same span; the agent receives the lead, the caption where there is one, the line between backticks, and the words.

The lead and the tag of a `file-line` anchor without a commit **do not change by a byte**: the caption is where a removed line "says before the change" (decision 2). The anchor carries `side: 'old'` for a removed line and no `side` otherwise; `AnchorSchema` and `TAG_FIELDS` hold `side` already, in this build and in both builds that bind, and `leadParts` ignores it for this kind in all three.

**A commit (M9).** `AnchorSchema` gains `commit: z.string().regex(/^(?:[0-9a-f]{40}|[0-9a-f]{64})$/).optional()`, and `TAG_FIELDS` gains `'commit'` after `'artifactTarget'`, so a tag without it is written as before. For a `file-line` anchor that has it, `path` is the path as that commit's diff names the file, relative to the repository, `side` is always given, and `leadParts` answers:

| `side` | the lead's parenthetical |
|---|---|
| `new` | `(file <path>, line <n>, new side, commit <full hash>)` |
| `old` | `(file <path>, line <n>, old side, the first parent of commit <full hash>)` |

The anchor's `label` is `<file name>:<line> · <sha7>` and its `locator` `<path>#L<line>@<full hash>`. `quotedComment` is used as in any scope, without the caption (the lead says the side). The producer is `commitLineAnchor` beside `fileLineAnchor` in `src/renderer/src/tools/code/anchor/anchor.ts`.

**Where a commit's anchor may go, and where it may not** (the architect's ruling on the review's first finding; §K lists every place). The field is an unknown key to both builds that bind, whose anchor schema is strict. It therefore lives in exactly two forms: in the words and the tag of the message, which every build stores and reads as text; and in this window's memory. It never enters a structured value that is written to disk or read by another process. The one place an anchor is persisted as a structured value is a side thread's lineage (`openSideThread` in `src/services/sessions/service.ts`, which writes it to the setup intent and, through the record, to the index, and from which the `side.thread.opened` event is made): the call that strips the screenshot there, `withoutScreenshot(from.anchor)`, becomes a call of a new `lineageAnchor` in the same module (`src/shared/anchor/content.ts`), which for an anchor that carries `commit` drops `commit` and, with it, `path`. `withoutScreenshot` itself stays as it is: `commentsContent` makes the first message's tag with it, and that tag must keep the commit. What is left (`kind`, `locator`, `label`, `line`, `side`) holds to both older schemas, and no reader of lineage is handed a repository-relative path it would open as a file (`side/ThreadView.tsx` makes a file button from a lineage anchor's `path`). Whatever this build shows of a side thread's commit it reads from the thread's first message with `readAnchoredMessage`, never from lineage; the label already says `· <sha7>`.

**Tests that pin it** (`src/shared/anchor/message.test.ts`, `anchor.test.ts`; no existing case is edited to pass): a `file-line` anchor with `side: 'old'` has the lead of the same anchor without `side`; `quotedComment` for a line holding three backticks (a span of four), for a line that begins with a backtick and for one that begins with four spaces (each read back exactly by a CommonMark reading of the span), for an empty line and a line of spaces (no span; the caption still stands for a removed line), for a line over the cap; a quoted line that reads `<maws_anchor …/>` cannot begin a line of the message, since the span's backticks do; with `commit`, the two leads above, the tag's last attribute, and a round trip through `readAnchoredMessage`; a tag without `commit` byte for byte as before; a `commit` of 39 characters or with an upper-case letter refused by the schema. `lineageAnchor` of a commit's anchor has neither `commit` nor `path` and parses under the anchor schema as it stood before this landing (a copy of the key list of `2c7044231`, held in the test); of any other anchor it is today's `withoutScreenshot`, to the key.

### §C. The three reads (`src/shared/ipc/schema/git.ts`, `src/services/git/`; M7)

All three: owner `machine`, grade `view`, in `PATH_COMMANDS`, addressed by `directory`. Their names are decision 12.

```ts
export const GIT_READS_CAPABILITY = 'rl2.git-reads';
export const UNTRACKED_COUNT_FILES = 200;          // P5 sets it; the starting value
export const UNTRACKED_COUNT_BYTES = 1024 * 1024;  // the per-file cap Review draws by
const FullHash = z.string().regex(/^(?:[0-9a-f]{40}|[0-9a-f]{64})$/);

// git.branchCommits: the branch read (l5-code-03's base and l5-code-06's list)
input  { directory: string; limit: number /* 1..200 */ }
output {
  base: { ref: string; mergeBase: string } | null;          // the default-branch rule below; null when none is found
  upstream: string | null;                                    // as git.status names it
  commits: Array<GitCommit & { pushed: boolean | null }>;     // <mergeBase>..HEAD, newest first, at most `limit`; with no base, the newest of HEAD
  counts: { all: number; notPushed: number | null; pushed: number | null } | null;   // of the whole range, whatever `limit` cut
  behind: number | null;                                      // commits the base ref holds that HEAD does not
}

// git.commitDiff: the commit read
input  { directory: string; commit: FullHash; path?: string; context?: number /* 0..20 */; patch?: boolean }
output { commit: GitCommit; onHead: boolean; patch: string; files: GitDiffFile[] }

// git.changesSince: the working-tree read (R1)
input  { directory: string; against: 'HEAD' | FullHash; path?: string; context?: number }
output { patch: string; files: GitDiffFile[]; untracked: Array<{ path: string; insertions: number | null; binary: boolean }> }
```

**The default-branch rule** (one function, `defaultBase`, in a new `src/services/git/default-base.ts`; decision 13). The remote is the branch's upstream remote, else `origin`, else the only remote. The base ref is the first of these that names a commit: the branch `refs/remotes/<remote>/HEAD` points to, as `<remote>/<name>`; `<remote>/main`; `<remote>/master`; local `main`; local `master`. It is null when none does, when it has no merge base with `HEAD`, and when it is a local branch that is the one `HEAD` is on (the default branch with no remote copy). `mergeBase` is `git merge-base <ref> HEAD`. A detached `HEAD` is compared like any other.

**`git.branchCommits`.** `pushed`: the upstream holds the commit; false with no upstream; null for every row, and null halves in `counts`, when the status names an upstream git cannot resolve. `counts` is of the whole range. With `base` null: `commits` are the newest `limit` of `HEAD`, `counts` and `behind` null. A repository with no commit answers no commits and a null base.

**`git.commitDiff`.** The commit against its first parent; a merge commit so too, never a combined diff; a commit with no parent with every line added. `path` reads one file of it. `patch: false` answers `commit` and `onHead` with an empty `patch` and no `files`, and reads no diff. `onHead` is whether `HEAD` holds the commit. A hash that names no commit is an error whose message says so. Pitfall seen while designing: the empty tree's id differs between a SHA-1 and a SHA-256 repository, so the root commit is read by a form that needs no literal id.

**`git.changesSince`.** The working tree against `against`, with `git.diff`'s arguments and prefixes (`patch`, then `files` from `--numstat -z`). `untracked` is filled only without `path`: for the first `UNTRACKED_COUNT_FILES` entries a fresh status lists as untracked files (a `dir/` entry is not one), in the status's order, the added-line count. It is read by the service itself, not by a git run per file (decision 15), **through the boundary the files service reads by** (`src/services/files/service.ts`, its opening comment, from "The boundary opens before it trusts"; `src/services/fs/no-link.ts`): open first, judge after, never check and then open.

1. The path is the repository's real root joined with the status's path, and nothing else names it.
2. It is opened read-only and non-blocking with no link on the way (`NO_LINK`; where `WALKED`, the ancestors walked first and the opened descriptor confirmed with `confirmOpened`). Where `OPENS_CONFIRMED` is false the file is not read and its count is null.
3. An open the kernel refuses for a link is not followed. The entry is then counted 1 only when an `lstat` says its last component is a symbolic link (its diff shows one line: the target's path); its target is never opened. Any other refusal is a null count.
4. The type is judged on the descriptor (`fstat`): a regular file, else a null count.
5. The bytes are read from the descriptor, and at most `UNTRACKED_COUNT_BYTES + 1` of them are ever read: a file that holds more, whatever its size said when it was opened, has a null count. A NUL in the first 8,000 bytes read makes it `binary` with a null count; otherwise `insertions` is the number of lines as `git diff --numstat` counts an added file.

The reader is one function in a new `src/services/fs/` module beside `no-link.ts`, built from that module's pieces; `src/services/files/service.ts` is not edited (U6e's write rule is built in that folder, and is in the tree). No file's content leaves the service through this read.

**What stays as it is.** `git.diff`, `git.log` and `git.worktree.branch` keep their meaning (the worktree clean-up dialog reads the last); the body of one untracked file is still `git.diff` with scope `untracked`. The service's opening comment gains `merge-base`, `rev-list` and `symbolic-ref`; all three only read. The service never fetches.

**Where a new `git.*` read is entered** (each beside `git.log`'s entry): `src/shared/ipc/names/git.ts`; `grades/git.ts` (`'view'`); `routes.ts` (`PATH_COMMANDS`) and `routes.json` beside it (the committed snapshot of every route class, which `routes.test.ts` holds equal to the registry: rewritten by that test under `MAWS_ROUTES_WRITE=1`, never by hand); the exported `commands` table of `schema/git.ts`; `src/services/git/register.ts`; `src/services/command-budgets.ts` and its test's `EXPECTED` (a budget that covers the read's sequential runs: the table's `STATUS` class for the branch read); `test/support/spine-lists.ts` (`SPINE_COMMANDS` and `CHECKOUTS_COMMANDS`, sorted); `src/shared/ipc/schema.test.ts` (the pinned list of `git.*` keys); `src/shared/ipc/wire.ts` (`WIRE_MINOR`, its comment) and the regenerated `wire-manifest.json`. `src/shared/machine/address-paths.json` needs no entry: no input or output of the three carries a machine-bound id.

### §F. The stack (`tools/code/review/`; M2, M3, M4)

Files, by responsibility (names are the executor's but for the three exported to tests): `stack-model.ts` (pure: sections, folds, the band, the place, the hunk order), `Stack.tsx` (the one scroller), `FileSection.tsx` (a header and a body), `FileBody.tsx` (one file's `DiffView` blocks, the successor of `ReviewView.tsx`, which stays untouched until M11; decision 23), `Toolbar.tsx`, and `ReviewShell.tsx` (the chips, the toolbar, the stack, the footer).

**Order and folding.** Sections are the scope's files in the list's order. A section is folded when the person's own choice says so (`folds`), else when it is marked Viewed, else when the scope is past `REVIEW_SCOPE_BYTES_CAP`; a click on the header or its fold mark sets the choice. Marking Viewed removes the choice, so the mark folds the file; a mark that drops because the file changed unfolds it again unless the person folded it. "Collapse all" sets `closed` on every file; it reads "Expand all" while every file is folded, and then sets `open` on every file. A file's diff is read alone (`loadFile`) only when its section is unfolded, inside the band and has no hunks yet, so "Expand all" on a scope past the cap reads what is near the scroll position and no more.

**The band, and what a folded section weighs.** `bandOf(tops, heights, scrollTop, viewport)` answers the unfolded sections that intersect the viewport extended by two viewports above and below. Three cases, and no fourth: an unfolded section inside the band draws its body; an unfolded section outside it draws a spacer of its last measured body height (before a first measure, an estimate from its line count); **a folded section has no body and no spacer**, so its height is its header's. After "Collapse all", and at first paint of a scope past the cap, the stack's height is the sum of its headers. The component feeds the function from the scroller's scroll and resize and each drawn body's `ResizeObserver` (decision 6). A8's test stubs the measures and counts drawn bodies.

**The place** (X-072; decisions 7 and 8) has two parts that are kept apart.

- *The live place* is where the person is reading: the section at the scroller's top edge, the diff row at that edge (side and line, read from the row's `data-line-*` attributes) and the pixels below that row's top; with no row there (a folded or undrawn section) the offset is from the section's top. It is **always kept**: read by `placeAt` after every scroll the person makes, written to `places` under the `placeKey`, and applied again at every layout change (a body drew or changed height, the scroller's width changed, the zoom changed), so the same file and line stay at the top whatever moves around them. The person's input never ends it.
- *An outstanding reveal* is a place the stack is still bringing into view: the saved place after a mount, a request's file, a hunk jump's row. While one stands, a layout change applies **it** instead of the live place. It ends in one of two ways: it is *reached* (its target is drawn and the scroller is on it), and then the place actually reached becomes the live place and is written to `places`; or the person's input *cancels* it, and the live place is whatever the person's scroll then reads.

| event | effect |
|---|---|
| mount, with a saved place for this `placeKey` | a reveal of that place |
| a request that names a file (`reveal`) | a reveal of that section's top; the section is unfolded |
| ↑ or ↓ | a reveal of the target hunk's first row; its section is unfolded (and read, if it has no hunks yet) |
| a layout change with a reveal outstanding | the scroller is set from the reveal; a hunk or a file not drawn yet is scrolled to by its section's estimate, then exactly once when it draws; reached, the reveal ends and its place is the live place |
| a layout change with none outstanding | the scroller is set from the live place |
| the person's wheel, touch, key or pointer press inside the scroller | an outstanding reveal is cancelled; the live place is untouched until the scroll that follows |
| a scroll event the person caused | the live place is read and saved |
| a scroll event the stack caused itself | ignored |
| unmount | the place then in force is in `places`: a reveal that was reached, else the live place |

**The hunk counter** counts the hunks of every loaded file that is not marked Viewed and not past the per-file cap, in stack order; scrolling by hand sets it to the hunk at the scroller's top edge; at the end of the scroller a hunk jumped to stands, as today. The words are today's `REVIEW_COPY.hunkOf`.

**The header** of a section (sticky at the scroller's top), left to right: the fold mark; the path, relative to the repository, the folder part shortening first (for Last turn a file outside the repository keeps its absolute path); a kind badge; the counts; Viewed; "Open file ↗" (absent for a deleted file, whose row keeps the Viewed control's column in line with the others).

- *A rename* reads `old → new` only when both paths fit whole. Otherwise the header shows the new path, shortened like any path, with the badge "Renamed", whose tooltip reads "Renamed from `<old path>`". "Collapse all" follows the same rule (D2).
- *Badges:* Added, Deleted, Renamed, Binary, Untracked and Conflict, and none for Modified (Conflict from the status's unmerged entry; the predicate moves here from `tools/scm/groups.ts`).
- *Counts:* a new file shows `+N` alone; a pure rename and a binary file show none; every other kind shows both sides as today. Counts print with the locale's thousands separator, here and in the totals.
- *Viewed* keeps today's words: "Mark viewed", then "Viewed". In the narrow form (card 2) it is a check box whose tooltip is those words, and "Open file ↗" is "↗" with its words as tooltip.

**The bodies:** a diff; "Binary file"; today's "Diff too large to display. Open the file"; nothing for a rename without a change; today's note for an untracked folder; "Diff unavailable: …" with **Retry** in the same row for a file whose own read failed (from M3 for every scope: a failed file read is asked again by Retry).

**The toolbar** holds the totals; the unsent-comments chip and the place line (the card host, §B; the chip is drawn as a chip, not as a quiet text button); "Collapse all"; the hunk counter with ↑ and ↓; and one menu, View, holding Unified, Split and Wrap, which are the stack's. **It wraps by measure, not by a width** (D1; at 720 px too it does not fit once comments wait or new files are uncounted): one line when everything fits; otherwise the totals on the first line and the controls on the next; the unsent-comments chip takes a line of its own when it does not fit beside the totals. The totals' words are built in one function, `totalsWords`, so that the owner's answer to card 1 is one edit: at the default they are "`N` files changed · +`A` −`R`" without "· `<scope>`" (the pressed chip directly above names the scope), and the counter reads "`n` of `m`" where "Showing hunk `n` of `m`" does not fit. The hunk counter and its arrows are not drawn while no file is loaded (a scope past the cap before any file is unfolded).

**Split needs room** (D9): where the stack is narrower than `SPLIT_MIN_WIDTH` (480 px: under it a side shows fewer than about twenty characters of code), the View menu's Split item is disabled with the tooltip "Split needs a wider column", and a stack whose stored choice is Split draws Unified until it is wide again. The stored choice does not change.

**Last turn's chip** (l5-code-12 c) is always listed. Chosen with no turn set, it shows the latest turn of the session's own transcript whose divider row lists files; with none it is disabled with `REVIEW_COPY.noTurnChangedFiles`. **A diff tab** is the same `ReviewShell` with `chips={false}`.

**Per-file data.** Each file's `DiffView` `data` object is kept while that file's hunks are text-equal (P2: a new object unmounts an open card), in a cache that lives with the mounted stack.
