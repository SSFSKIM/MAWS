## Purpose

Today a PDF, an HTML page, a video or a sound that a session's file path names is not drawn in MAWS: its tab shows "PDF files open outside MAWS" and a button, while the same kinds delivered as artifacts are drawn in the app. The debt tracker has held the difference since 2026-10-08.

After this landing such a file is drawn in its own tab, beside the chat or in the main area, by the frames artifacts already use: Chromium's PDF viewer, a sandboxed frame for an HTML page, the media player. No artifact is made, so a click writes nothing to the Library. "Open externally" stays in the file's bar. It holds on every route: for a session MAWS runs and for a terminal session on this Mac the bytes are read by the daemon's files service at every request; for a session on another machine the file is copied here by the read "Open externally" already uses and drawn from the copy, up to 64 MiB.

How to see it working: in a session, click a path link to a PDF inside the session's folder. The PDF is drawn at the right of the chat, the transcript has not moved, and the Library holds nothing new. Click a `.html` file in Files' tree: the page is drawn and its inline script has run; a page that needs a stylesheet beside it is drawn without that style, a line under the bar says "Shown without the files beside it", and "Open externally" in the bar hands the file to the system. Click a video: it plays and seeks. Change the PDF on disk: the tab draws the new one.

The route that serves these bytes is the delicate part (root UC-10): a frame loads `maws-artifact://<token>/<the file's name>`, a URL that names no folder, and main answers it only after the files service has read that file for that session, at every request. A PDF and an HTML page by a path need not have been written by the session's agent (a file of a cloned repository), so this document states, per kind, what a hostile file can and cannot do and which test and which scene on a Mac shows each.

## Words used in this document

- **Session** always means a MAWS session (an agent's conversation with its folders). An Electron session, the browser-side store of cookies, handlers and filters that a window belongs to, is called a **partition**: the app windows use Electron's default partition; captures use `maws-capture` (`CAPTURE_PARTITION`, `src/render/capture.ts`); the render host is a separate process with partitions of its own.
- **The daemon** is `mawsd`, the per-Mac background process that runs the machine's services; the files service (`src/services/files/`) runs in it. **Main** is the Electron main process of the app; it has no files service and reaches the daemon's through the router (`invokeOwn`, `src/main/ipc/router.ts`).
- **The store's scheme** is `maws-artifact:`, registered once as a standard, secure, streamed scheme with no fetch (`registerStoreSchemes`, `src/render/scheme.ts`). Today its host is always an artifact's id (a UUID). **A store frame** is a frame whose URL has that scheme.
- **A framed kind** is one of `pdf`, `html`, `video`, `audio`. **The frame** of a file is what draws it: an `<iframe>` for a PDF or an HTML page, a media element for the other two.
- **A token** is 32 lower-case hexadecimal characters that main draws at random and uses as the host of a URL, `maws-artifact://<token>/<name>`, whose last part is the file's base name, percent-encoded, so that Chromium's viewer titles itself with the name. **A token host** is a URL host of that shape. Main holds what a token stands for, the name among it, and answers a token only at that one path; no folder's name ever enters the URL.
- **A raw read** is a `files.read` that answers the bytes of exactly the range asked, never decoded and never re-cut. **The identity** of a file, as a raw read answers it, is a string made from what the opened descriptor knows (device, inode, size, modification time, change time); two reads that answer the same identity read the same version of the file.
- **A viewer entry** is the record the window keeps per open file (`ViewerEntry`, `src/renderer/src/tools/code/viewer/viewer-store.ts`), under the key a main tab of the file has (`fileKey`, `file:<machine>:<path>`). U6b-1 keeps an entry while any tab holds its file, in view or not, and across a move.
- **A watched file** is one inside the session's folders: the entry holds a watch on its folder and reads again on `files.changed`. **A named file** is one outside the folders that the session's transcript names (U6c): no watch follows it, and it is read again by `revisit`, when its tab is shown again or its link is clicked again.
- **Build F** is `f1852de3a` (root UC-14) and **build M** is master `2c7044231`: the two earlier builds a profile that runs this landing may have run before, or may be taken back to. Whatever this landing sends is stated against both.

## The landing's edge

**In.**

- The kind `frame` for a file whose type is PDF, HTML, video or audio, decided from the type the files service answered, and its drawing in the file's tab wherever a file's tab is (beside the chat, in the main area).
- The raw read of the files service, with the identity in its answer: one optional input and one optional answer field of `files.read`, and so one wire minor.
- Main's route: the tokens, the two commands that issue and release one, the event that says a read for one failed, the responder on the app windows' partition, the check of the asking window, and the copy for a session on another machine, held in a descriptor that never has a name while a byte is in it.
- "Open externally" in the file's bar for a drawn file; Chromium's PDF toolbar hidden beside the chat and kept in the main area; an HTML page with no declared charset served as UTF-8 when its head is valid UTF-8.
- The row a framed file keeps when it is not drawn: a sentence per reason, and no "Open externally" where the act can only fail. The body of a load that failed: one sentence and a button, "Open again".
- A video's or a sound's position kept across a move and a hide.
- The record: the tracker's row of 2026-10-08 closed; the row of 2026-10-06 naming the file frame beside the artifact frame (the cut, X1); the cross-build coverage table's row.

**Not in, and a later landing of U6b:** the words of a refusal (U6b-4; this landing words the row of a framed file that is not drawn and the failure body, "The sentences a person reads", and U6b-4 may word them again with the rest); a `file://` link and a relative link (U6b-4).

**Not in, and nobody's.**

- A Source view of an HTML file (card 1 asks).
- Drawing a framed file larger than 64 MiB from another machine, or any file a session's read refuses today.
- Loading a page's neighbouring files: an HTML page that needs a stylesheet or a script beside it is drawn without them (the child's file). On the owner's answer to card 2 the tab says so in one line when the page names such files (M5, decision 14; "A page that names files beside it"); loading them is a later landing with its own ticket.
- A change to `STORE_FRAME_CSP`, to the sandbox of the HTML frame, or to any existing predicate of `src/render/policies.ts`.
- The dead proxy that closes a relay over TCP (the first Office preview landing's; the cut, X1).
- The frames of an artifact: `ByteViewer` draws them as it does today.

## How Claude Desktop draws the same files, and where MAWS differs

Read in `readable/app-5.1231.2/` (law 1).

- **A PDF** is drawn by Chromium's own viewer in a native view of its own, on a partition of its own, loading `cowork-file://preview/<path>`: the scheme and partition at `main-process/index.chunk-BV3uOqbK.js:294608` and `:294610`, the view's preferences at `:375050`, the handler at `:294707`, its per-answer policy (none of `sandbox` for a PDF) at `:294753`.
- **An HTML file** is drawn in a sandboxed `<iframe>` whose page is served from the vendor's own remote origin, and the file's text is posted into it: `web/app/v1/cc61d0d63-BtF30gww.js:3319` to `:3331` (`sandbox`, `referrerPolicy="no-referrer"`), the sandbox value at `:1517`, the origin at `web/app/v1/shared-46-B-KgctpG.js:285`. Files beside the page are not loaded.
- **A video or a sound** is a native element whose source is a URL with a random token, `claude-media://v/<token>`, which main maps to the file and checks again at each request, answering ranges: `main-process/index.chunk-BV3uOqbK.js:404442` and `:404528`; the elements at `web/app/v1/cd2efac6e-DJ0bDCna.js:12828` and `:12839`.
- **Anything else** shows "Preview isn't available for this file" with ways out (`web/app/v1/cd2efac6e-DJ0bDCna.js:10443`).

An HTML page is served from this Mac with no network at all, where Claude Desktop's is hosted on a remote origin MAWS has none of.

## Decisions settled at authoring, as the rulings leave them

The cut fixes the edge and the route. These are what it left to this document, each with its reason and what it beat; decisions 2, 7, 8, 11 and 12 are as the rulings on the review changed them, and decisions 14 to 19 are the rulings on the drawn example.

1. **Exact byte ranges: `raw`.** `files.read` gains the optional input `raw: true`. A raw read answers `encoding: 'base64'` whatever the file's type, the bytes of exactly `[offset, min(offset + length, size))`, and never settles a chunk. It changes nothing of the admission: the same `precheck`, `openNoLink` and `confirm` run first. It is honoured for a caller on this machine only; for a caller on another machine the key is passed over and the plain read answered, as `named` is, so nothing new is offered to another machine. Lost: a second command for raw bytes, which would be a second admission path to keep equal to the first.
2. **One version across a response: `identity`, checked on both sides.** A raw read answers `identity`, a string of the descriptor's device, inode, size, modification time and change time in nanoseconds. The service reads the descriptor's state before the bytes and again after them, and refuses the read (`changed while reading: <path>`) when the two differ, so one answer never holds bytes of two versions. Main fixes the identity at a response's first read and ends the response in an error when a later read answers another. The change time joins the four values the cut names because a writer can set a modification time back and cannot set a change time; a false alarm costs one reload. This is the guarantee for a file on this Mac. For a copy of another machine's file the guarantee is decision 8's, which is weaker above 8 MiB; Interfaces §C states both exactly. Lost: a hash for every range on this Mac, which costs a read of the whole file per range and stops at 8 MiB.
3. **The type and the policy are main's, fixed at issue.** `layout.frameFile` makes one raw read of the file's head (`FRAME_HEAD_BYTES`, 64 KiB, from offset 0) and takes the type that read answered. `framedKindOf` of that type decides the frame, the `Content-Type` and the policy header (none for a PDF, `STORE_FRAME_CSP` for the other three), and all three stay with the token until it is released; for an HTML file the `Content-Type` is settled from that same head (decision 18). The window draws the frame main names, not the one its own read suggested. For a copy from another machine the type is the one the other machine answered for the first page of the copy that was written, and the head is read from the copy. A file whose type is no framed kind by then answers `row: 'unframed'`, which the window shows as a load that failed (the file changed between its read and main's; "Open again" reads it afresh). Lost: the type the window read, which would be the window's word on which answer goes without a sandbox.
4. **The token lives with the viewer entry, and the store asks for it.** The entry gains `frame`, and the viewer store, not a component, asks main when a read of a framed file lands. So a tab that is hidden and shown again, and a file moved between the side column and the main area, keep their token and their URL. A component that asked at each mount would issue at every show and could not release after its tab closed mid-ask. Lost: a token per mounted frame, which the cut's words "one mount" could also be read as; "released when its viewer entry goes" decides.
5. **One ask in flight per entry.** A read that lands while an ask is unanswered marks the entry for one more ask after the answer. An answer is applied only to the entry that asked (the same incarnation) and only when it is that entry's latest ask; any other answer's token is released at once. For a file of another machine this bounds the copies in flight to one per entry however fast the file changes.
6. **A re-read re-issues.** A landed re-read of a framed entry asks for a new token, after a `files.changed` and after a revisit alike: the new URL is what makes the frame load again. The frame already drawn stays until the new URL is ready; then the old token is released. After an event the entry flashes "Updated" as a row does today; a revisit that finds the same type and size flashes nothing.
7. **One failure path, and what the tab shows.** Every read main makes for a live token that fails tells the owning page (`layout.frameFailed`): the first read of a response, the probe for a suffix range and every later page alike, whether or not an answer has begun to stream (A3). The entry's frame becomes *failed*: the body draws one sentence in the frame's place with a button under it (decision 17), the token is released, and the bar keeps "Open externally". A failure starts nothing by itself. The file is read again by an act of the person: the button, showing its tab again, or opening the file again (U6c's `revisit`, whose predicate gains this case; A4); and, as any entry is, when a `files.changed` arrives for it. No timer and no retry: a file that keeps failing would otherwise loop.
8. **A file of another machine.** `layout.frameFile` with another machine as its target copies the file here, up to `REMOTE_COPY_MAX_BYTES`, and serves from the copy until the token is released. *The copy's bytes never exist under a name* (A5, A6): main creates an empty file in the profile's own data folder, removes its name before the first page is asked of the other machine, and keeps the one descriptor for the copy's life; the fetch writes through it and the frame is served from it. So there is no partial file, no rename and nothing to sweep, a crash leaves no byte readable under a name, and two profiles never share a folder. *The copy asks the hash from its first page* (A2), a key the copy of "Open externally" already sends. A file within the hashed read's cap (8 MiB) is one version: every page answered the file's hash, and the digest of what was written is compared with it at the end; a file that changed is copied again, and one that keeps changing is refused. Above the cap the other machine answers no hash, only the size is compared between pages, and an equal-size replacement during the copy can leave a copy of two versions, which the next read replaces; the tracker holds that case. A larger file than 64 MiB answers `row: 'too-large'`; a file the other machine sends only as text that is not valid UTF-8 fails with the copy's own sentence. The admission is the other machine's, page by page, at the copy; what is drawn afterwards is the copy, as a copy opened externally stays readable. The paged read is given a label with no path for its log (A7). "Open externally" and its copies are not touched.
9. **Bounds.** A window holds at most `FRAME_TOKENS_MAX` (32) tokens; the viewer keeps at most 20 entries that are not mounted, so only a fault in the window reaches the bound, and an ask past it fails. The space the copies can take is therefore bounded by the tabs a person keeps open on another machine's large files, 64 MiB each. A file on this Mac has no size bound, as a stored file's frame has none: media is read by range as it plays.
10. **A token is never a number.** A token is drawn again when it holds no letter from `a` to `f`: Chromium reads a host made of digits alone as an IPv4 address and refuses one that large (not measured at authoring; M1 measures it). Three in ten million tokens would otherwise never load.
11. **The owner's check is in the request filter** (R1, under A1's gate). `shouldCancelForOwner` cancels a request for a token host unless it comes from the web contents the token was issued to. A request with no web contents (one the browser itself started) is cancelled too. It is the listener's first question, before the branch that answers from a web contents' own filter, so the export's printer window is judged as well. Whether every request the responder answers passed this listener is not something the code shows: M1 measures it on the VM and M4's scene of record on a Mac, and neither M3's ownership interfaces nor M5 are built before their verdicts.
12. **Media.** A video or a sound that the element cannot play (an `error` of the element with no failure told by main for its token, before or after) draws its row in the player's place and releases its token (decision 16; L6). Its position is kept across a move and a hide: the element's time is written to the entry's view state as it plays and set again when the element next loads, paused. A video's zoom stays the artifact player's own bar, since the cut names that component.
13. **Nothing of the window's bridges is passed to a file's HTML frame**: no pick, no locate, no connector port. A file by a path carries no bridge script (it is served byte for byte), and its page is not the agent's by any rule.
14. **The URL's last part is the file's name, and it is the only path a token answers** (L3, as corrected). `frameUrl(token, name)` is `maws-artifact://<token>/<the base name, percent-encoded>`, so that Chromium's viewer, which titles itself with the URL's last part, reads the file's name and not "file". The name is the base name of the path the command gave, recorded with the token at its issue. The responder answers the token's file only for a URL with exactly one path segment after the host whose decoded value equals that name; a segment that does not decode, another name, a longer path and an empty path are each 404, and a query is 404 as it was before this ruling. So the title reads the name, the cut's refusal of every other path stands, and a page cannot load itself again under another path. No folder's name enters the URL. Lost: the fixed last part `file`, which made the viewer's title read "file"; and answering by the host alone, which revision 3 wrote for one commit and which gave up the refusal for nothing a person sees.
15. **Chromium's PDF toolbar follows the host the tab is drawn in** (L1, L2). `pdfFragment(host)` answers the fragment of the URL `PdfFrame` is given: `#toolbar=0&navpanes=0` in a side tab, `#navpanes=0` in a main tab. The fragment never reaches main. A tab that moves between the two gets a new frame element in its new place in any case ("What a frame keeps and loses"), and that element is made with the other fragment; the token does not change. M1 found both honoured on the VM (rows h and i; Decision Log 21), so both are used as written. Each fragment is used only if M1 found Electron's viewer honours it (rows h and i): where `#toolbar=0` is not honoured the toolbar is kept in both hosts, where `#navpanes=0` is not it is left out, and either finding goes to the architect.
16. **The row says why, and never offers an act that can only fail** (L4, L5, L6). One function, `rowWords(entry)` in `ExternalRow.tsx`, answers the row's sentence and whether it holds "Open externally", from the entry's kind and its frame's reason: a kind MAWS does not frame: today's "<Kind> files open outside MAWS" and today's rule for the button; a file of another machine larger than the copy's bound: its sentence, the size, and no button (the open copy has the same bound); a clip the player cannot play: its sentence and the button; a file of this Mac whose daemon cannot serve a frame: its sentence and the button. The sentences are in "The sentences a person reads". It is one place so that the owner's answer on card 3 can put today's words back.
17. **The failure body names its control** (L7). Under the sentence stands a button in the existing button shape, focusable, labelled "Open again". Pressing it reads the entry again, which asks for a new token: the same act as showing the tab again. A second failure returns to the same body. This is the explicit act of ruling A4; nothing presses it but a person.
18. **An HTML page with no declared charset is not left to Chromium's fallback** (L8). The reason, as M1's row f corrected it (Decision Log 21): Electron decodes an unlabelled page as windows-1252 whatever the interface language (the drawn example's EUC-KR under a Korean system was a browser's, not Electron's), so a UTF-8 page of non-ASCII text that declares nothing reads wrong for everyone; the rule stands as written. Main answers `Content-Type: text/html; charset=utf-8` when all three hold for the head it read at issue: no byte-order mark (UTF-8's or either UTF-16's) at its start; no charset declaration anywhere in it (a `meta` element with a `charset` attribute, or one with `http-equiv="content-type"` whose `content` names a charset, matched without regard to case); and its bytes are valid UTF-8, where a sequence cut short by the end of the read is not invalid. Otherwise the type goes out as today, `text/html`, and Chromium decides as it does now. **The bound of the check is the head: the first 64 KiB** (`FRAME_HEAD_BYTES`). A declaration or an invalid byte past it is not seen: a page in another encoding whose first 64 KiB are plain ASCII and that declares nothing there is sent as UTF-8, and its later text is drawn wrong; accepted, pinned by a test, said in the pull request. The value is fixed with the token, like the type.
19. **A page that names files beside it is drawn alone, and the tab says so** (L9; the owner's answer to card 2, Decision Log 19). Main answers the fact `neighbours` with an HTML file's token, read from the head it already read for decision 18; when it is true the tab shows one line under the file's bar, "Shown without the files beside it", and the page is still drawn. Built in M5 (decision 14); the rule is in "A page that names files beside it".

## Who owns a token

Main issues a token to one page of one app window, for one viewer entry. The page is the `ClientRef` the router handed the command's handler; its web contents' id is recorded with it.

| act | by whom | answer |
|---|---|---|
| issue | `layout.frameFile` from the top frame of an app window (the router's sender check) | the token, to that page only |
| use | a request on the default partition from the owning web contents | served |
| use from another web contents, or from none | | cancelled by the request filter before any handler runs |
| use on the capture partition | | cancelled by the filter there (no capture window owns a token), and the partition's chain has no responder: the store's own path answers 404 |
| use in the render host | | its process holds no tokens and proxies to the daemon, whose endpoint answers 404 for a host that is no artifact's id |
| release | `layout.releaseFrame` from the owning page | released; later uses answer 404 |
| release by another page, or of an unknown token | | the same failure for both, naming nothing; the token, if it lives, still serves its owner |
| the page ends (closed, crashed, reloaded) | main, on the client's end | every token of that page released, every copy's descriptor closed (which is the copy's end: it has no name) |
| the app quits | main | all released |

The window releases a token when its entry is removed (the tab closed, the preview tab reused for another file, the entry pruned), when a newer token for the entry is ready, when the entry's frame fails or turns into a row, and on the answer of an ask whose entry is gone or has asked again.

## Routes (law 5)

| route | how the bytes are read | what is drawn where it is not |
|---|---|---|
| **A session MAWS runs, on this Mac** | every range by a raw `files.read` of this Mac's daemon, with `named`, as the page that owns the token | — |
| **A terminal session, on this Mac** | the same: the files service has no branch on who holds the session | — |
| **A session MAWS runs, on another machine** | a copy fetched once per token, up to 64 MiB, into a descriptor with no name; then that descriptor. **Nothing new is asked of or offered to another machine.** Asked: `files.read { appSessionId, path, offset, length, hash }`, the keys the copy of "Open externally" sends today when it proves a text file; a frame's copy sends `hash` on every page from the first, for every type. Never `raw`, never `named`, and after U6e never `agent`. A test spies the link and compares the keys of every page with that set. Offered: a remote caller's `raw` is passed over (decision 1), with a test that the answer is the plain read's, byte for byte, and carries no `identity`. What differs from "Open externally" is when and how often the pages are sent: at an open of the file's tab and at each read of the entry while its tab lives, not only at a press of the button, and with the other machine hashing a file of up to 8 MiB once per page; decision 5 bounds it to one copy in flight per open file.

## The sequences that must hold

The states, the events and where each takes effect are fixed here, before the code.

**The entry's frame, in the window** (`entry.frame`; Interfaces §E). States: *none* (the kind is not `frame`, or no read has landed); *asking* (an ask is unanswered; what was drawn before stays drawn); *ready* (a token and its URL); *failed* (a read for its token failed; no token is held); *row* (with why).

| event | none | asking | ready | failed | row |
|---|---|---|---|---|---|
| **L**: a read of the entry landed as a framed kind (an open, a change, a revisit) | ask; *asking* | mark "again" | ask; *asking*, the frame still drawn | ask; *asking*, nothing drawn | ask; *asking* |
| **A+**: the ask answered ready | | the latest ask of a living entry: *ready* with the new token, the one before released; marked "again": ask once more. Any other answer: its token released | | | |
| **A0**: the ask answered a row | | `unframed`: *failed*; else *row* with that reason; the token before released | | | |
| **A×**: the ask failed | | the entry fails as a read fails, with the failure's words (so `revisit` reads it again); the token before released | | | |
| **F**: main says a read for this token failed | | for the token still drawn: nothing is drawn any more and that token is released; the ask goes on | *failed*; the token released | | why `unplayable`, for the token the row came from: *failed* |
| **U**: the media element reports an error | | | *row*, why `unplayable`; the token released and remembered | nothing | |
| **R**: the person presses "Open again", shows the tab again or opens the file again (`revisit`) | | | a named file, shown or opened again: read again (L follows) | read again (L follows) | |
| **M**: the entry is mounted again | | | | (R) | why `unserved`: ask; *asking* |
| **X**: the entry is removed | | nothing now; the answer's token is released when it comes | the token released | | |

An answer takes effect in one synchronous step of the store. Main records a token only after the admission read or the copy has completed, in one synchronous step that first checks that the asking page still lives. Nothing in this table is started by a clock.

1. **A token asked while the tab closes.** The ask is held open; the tab closes and the entry goes; the ask is answered ready. Then `layout.releaseFrame` is called with that token and no entry exists. Test (store): "an answer for an entry that is gone releases its token".
2. **A change during an ask.** The ask is held open; `files.changed` lands a read. No second ask starts. The first is answered: the store asks once more, and when that answers, the first token is released. Test: "a read that lands during an ask is followed by one more ask, never two in flight".
3. **The swap.** A frame is drawn; a change lands; while the new ask is open the old URL is still the frame's; on the answer the frame has the new URL and the old token is released, in that order. Test: "the frame drawn stays until the new token is ready, and the old one is released after".
4. **A read for a live token that fails, at any point of a response** (A3). Four cases of the responder's suite, each with the read stub held open and then failed: the first read of a response (the file gone; the admission lost; the daemon not answering; an older daemon's answer with no `identity`), the one-byte probe of a suffix range, a later page that answers another identity, and a later page that is refused. In each, `failed` is called once and no further page is asked; before a streaming answer the request gets 404, after it the stream errors. The window's half: "a token issued, its first request held and then failed: the tab draws the failure state" and "a change that lands after a failure draws the new version".
5. **A token used after its release.** 404. Also for a response in flight at the release: its next page is not read, the stream errors, and nobody is told. Test: "a release ends a response in flight and tells nobody".
6. **A copy from another machine that never arrives.** The link's own timeout answers the page; `fetchInto` fails; the sink is closed; the command fails with those words; no token is recorded, and the entry is an error that `revisit` reads again. At the held page, and after the failure, the copies folder lists no entry. Test (main), with a link whose page is held open until its timeout under fake timers.
7. **The page ends during an issue.** The admission read, or the copy, is held open; the page reloads; the read is answered. Nothing is recorded; a copy's descriptor is closed. Test: "an issue whose page ended meanwhile records nothing".
8. **A move.** A framed file beside the chat is moved to the main area. No release and no ask are made, and the frame mounted in the new place has the same URL. Test (store, with `holdKey`): "a move keeps the token".
9. **The daemon restarts during a response.** A page answers `host_unavailable`: sequence 4's last case. Nothing asks again by itself (sequence 12).
10. **A file changed within one read.** The service finds another descriptor state after the bytes than before them and refuses the read. Test (service), with the service's boundary point `after-read` between the two: "a raw read whose file changed while it was read is refused".
11. **A media position across a hide.** The element reports its time; the tab is hidden and shown; the new element is set to that time once its metadata has loaded, paused. Test: "a hidden and shown video is at the time it left, paused".
12. **A failed frame, read again by the person alone** (A4, L7). A response is held and then failed; the frame is *failed*, the body holds the sentence and the button. The service is restored and no file event comes. Time passes (fake timers): no command is sent. "Open again" is pressed: one read, one ask, a new token, a drawn frame. Tests (store and `FrameBody`): "a response held to failure, the service restored with no file event, Open again pressed: a new token and a drawn frame"; its twins with the tab shown again and with the file opened again while its tab is in view; and "Open again pressed while the read still fails returns to the same body, with one ask and no more".
13. **An equal-size replacement during a copy, within the hashed read's cap** (A2). The copy's second page is held; the other machine's file is replaced by one of the same size; the page is answered with another hash. The pass is `changed`, the descriptor truncated, the copy made again; what is served is one version. When it keeps changing past `REMOTE_READ_TRIES` the command fails and nothing is served. Test (`fetchInto`).
14. **The same above the cap: the recorded limit** (A2). The answers carry no hash; the second page is held and the file replaced by one of the same size. The copy is written from both versions and served. Pinned by a test that asserts exactly that and names the limit; the next read of the entry (a change's event, or the person's revisit) copies again.

## Plan of Work

### M1 — Spike: both ends of a request for a token host, and Chromium's PDF viewer on one

**A prototyping milestone.** Its deliverable is `spikes/file-frame/FINDINGS.md` with a results file per run; nothing of it is imported by the product, and it has no tests. It runs on the build VM under `xvfb-run` (R7). **Its verdict gates M3 and M4.** M2 does not depend on it and may be built beside it.

**The question.** Three facts the design rests on and no file of the repository shows. (1) That every request the scheme's handler answers was first decided by the partition's one `onBeforeRequest` listener, with the web contents that asked: the owner's check lives in that listener, and nothing in the tree shows the two ends meet for every request (A1). ### M2 — The raw read: exact ranges and one version; the wire's minor

**What exists at its end.** The daemon's `files.read`, asked with `raw: true` by a caller on its own machine, answers the bytes of exactly the range asked as `base64`, with the file's `identity`; refuses a read whose file changed under it; and answers a caller on another machine, or a caller that sent no `raw`, exactly as before. **What it touches.** `src/shared/ipc/schema/files.ts`; `src/services/files/service.ts` (`read`, `readOpened`, one test-only boundary point); `src/shared/ipc/wire.ts` and the two generated files beside it; `src/services/files/service.test.ts`, `src/shared/ipc/schema/files.test.ts`.

**Interfaces.** Exposes §B to M3. Consumes nothing.

**Decisions.**

1. The raw branch is inside `readOpened`, after the open is confirmed, so every admission path in front of it is the plain read's. `read` passes `raw` only when the request is not remote; `readResolved` never does, and `FilesReadResolvedInputSchema` omits the key as it omits `named`. `library.read`'s input picks three named keys of the read's and so takes none.
2. A raw read's `encoding` is `base64` and its `length` is the count of bytes answered. `mime`, `bytes`, `offset`, `truncated`, `named` are as the plain read's. `hash`, when asked with `raw`, is answered as today; no caller of this landing asks both.
3. `identity` is `identityOf(stat)` (Interfaces §B) of the confirmed descriptor. After the bytes are read the descriptor's state is read again; when `identityOf` of the two differs the read throws `changed while reading: <path>`, with the path as the request gave it, as `not found:` names it. What remains is a stated limit (Decision Log 22), not fixed and not measured in this landing: a same-size change made within one timestamp tick of the file system after the file's previous change keeps the identity, so a raw read spanning it is not refused; what a person could see is one drawing of a file whose parts come from two versions, until its next read; it reaches only a caller on the file's own machine, since a remote caller's `raw` is passed over. The pull request's text on it is drawn from this sentence, and the tracker holds it (M6, decision 4).
4. A new boundary point for tests, `after-read`, awaited between the bytes and the second state (sequence 10); it joins `BoundaryPoint` and is reached only by a raw read.
5. A plain read's answer carries no `identity`, so its shape is byte for byte today's. Pinned by a case that compares a plain read's answer before and after with `toEqual`.
6. *The wire's minor is one commit* (C1) that holds only `WIRE_MINOR`'s number with its note ("the UX wave's U6b-2: files.read's raw, and its answer's identity (N)"), the regenerated `wire-manifest.json`, and `wire-fingerprint.json` when it changes (it hashes the engine host's commands alone, so for `files.read` it does not: Decision Log 22), as every landing of the chain has it, because the chain merge takes the minor again in that commit's place. The VM sees only what is pushed, so the number is applied on the VM's checkout for the generation alone, the generated files are brought back, the VM's checkout is restored, and the changed files are committed once (Concrete Steps 4). The number is one past the tree's at this milestone's start, and provisional: the chain's landings ahead take theirs first. The manifest also records the optional `identity` on the outputs of `files.readResolved` and `library.read`, which share the read's output schema and never set it; that is the same one minor.
7. `test/endpoint/checkout-rows.test.ts` and `test/lane-b/offer-coverage.test.ts` are run and expected to pass unchanged, as they did for `named`: nothing under `src/endpoint/` is edited.

**What it does not touch.** `precheck`, `openNoLink`, `confirm`, the allowlist, the transcript's search, `files.openExternal`, any other command.

### M3 — The tokens, the byte sources and the responder

**Starts only on the architect's word on M1's verdict** (A1): the token table's ownership interface is built on what rows b and c showed.

**What exists at its end.** Three modules of main with no Electron import, proven by their own suites: a table of tokens with their owners; a source of bytes for a file on this Mac (raw reads) and one for a copy (a descriptor); a responder that answers a request for a token host from a source, range by range, holding one identity, and reports every failed read of a live token; and the copy of another machine's file into a descriptor that has no name. Nothing calls them yet.

**What it touches.** New: `src/shared/files/framed.ts`, `src/main/file-frames/tokens.ts`, `source.ts`, `responder.ts`, `charset.ts`, each with its test file. Edited: `src/services/artifacts/scheme/scheme-handler.ts` (`rangeOf` exported, nothing else); `src/main/lane-b/remote-copy.ts` (`fetchInto`, beside `fetchToFile`, which is not edited); `src/main/lane-b/remote-files-read.ts` (`readInPages` takes an optional label).

**Interfaces.** Exposes §C to M4 and `framedKindOf` to M5. Consumes §B.

**Decisions.**

1. The responder answers a request in this order: a host that is no token: null. A method other than GET and HEAD: 405. A token it does not hold: 404. A path that is not exactly one segment whose decoded value equals the name recorded with the token (decision 14), or any query: 404. Each 404 is `text/plain`, `no-store`, the body "not found", the same for every cause. Then the first read. The segment is decoded with `decodeURIComponent`; one that throws is a 404.
2. *The first read fixes the response.* For a request with no `Range`, or a range with a start, the first read is at that start for at most one page; it answers the file's size and the identity. For a suffix range the first read is of one byte at offset 0, to learn the size. A range that starts past the end: 416 with `Content-Range: bytes */<size>`. A multi-range or a malformed one: the whole file, as the store's handler answers.
3. *The body* is a stream that reads one page of at most `FRAME_PAGE_BYTES` per pull, so a frame that stops reading stops the reads. Before each page it checks that the token is still held.
4. *One failure path* (A3). Every read made for a live token that fails calls `failed(token)`, once per response: the response's first read, the one-byte probe of a suffix range, and every later pull; whether the failure is a refusal, a file that is gone, a daemon that does not answer, an answer with no `identity`, or a page whose identity differs from the first. Before a streaming answer exists the answer is 404; after it the stream errors. A token released under a response in flight errors the stream and tells nobody: nothing owns it any more.
5. The headers are the store's (`Content-Type` from the token, `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`, `Cache-Control: no-store`, `Accept-Ranges: bytes`), with `Content-Security-Policy` from the token, and no `Access-Control-Allow-Origin`: nothing loads a file's frame across origins, and the scheme admits no fetch.
6. The copy's source reads the descriptor at a position and answers a fixed identity; closing it closes the descriptor. Its size is what the copy wrote.
7. A token is 16 random bytes as hex (`randomBytes`), drawn again while it holds no letter (decision 10) or is already held.
8. *`fetchInto`* (A2, A5, A6; Interfaces §C) pages a session's file of another machine into a descriptor its caller opened, never into a name. It runs `fetchToFile`'s passes over the same inner read (`readInto`), with three differences. (a) Between two passes it truncates the descriptor to nothing instead of removing a part file; there is no rename. (b) Every page asks `hash` from the first one. While the answers carry a hash (a file within the hashed read's cap, `FILES_READ_MAX_LENGTH`), a page whose hash or size differs from the first makes the pass `changed`, and the digest of what was written is compared with that hash at the end, as `fetchToFile`'s hashed pass does. When the answers carry no hash (a larger file) the pass goes on as the unhashed pass does today: only the size is compared, and a text page that holds a replacement character is refused as not byte for byte. A text page whose answer carries a hash and says the bytes are not valid UTF-8 is refused the same way. (c) The first page of each pass is told to the caller (`seen`), and the paged read is given a label with no path. Written literally as "the existing hashed pass from the first page", it would refuse every text file larger than the cap (`readInto` answers `inexact` for a text page with no hash), which is why the asking of the hash and the proving of a text are two things here.
9. `readInPages` gains an optional last argument, `label?: string`, used in its two log lines in place of the path or the artifact's id (A7). Every caller of today passes none and logs as before. The sentence it answers when a file kept changing goes to the asking window, which named the path, and is unchanged.
10. `fetchToFile` and `remote.openCopy` are not edited, and their suites pass untouched.
11. *`htmlContentType(head)`* (decision 18; `charset.ts`) is a pure function of the bytes it is given: it answers `text/html; charset=utf-8` or `text/html`. The byte-order mark is looked for at offset 0; the declaration by one case-insensitive search of the bytes read as latin1, so that bytes of any encoding are searched without being decoded; validity by a strict UTF-8 decode that accepts a sequence cut short at the end.

**What it does not touch.** Electron, the router, the policies, any renderer file, "Open externally".

**What it proves.** The refusals named for `responder.test.ts` and `tokens.test.ts` in "The refusals of the route"; B12's route half; sequences 4, 5, 9, 13 and 14. Beside them, in `responder.test.ts`: "serves a file larger than one page as the pages' bytes in order, reading the next page only when the body is pulled"; "answers a range with 206, its Content-Range and exactly those bytes"; "answers a suffix range from the end"; "answers HEAD with the headers and no body"; "a PDF's answer carries no policy header and an HTML file's, a video's and a sound's carry the store's frame policy"; "every byte of one response is from reads that answered one identity"; "a release ends a response in flight and tells nobody"; "a first read that fails answers 404 and tells the owner: a file gone, an admission lost, a daemon that does not answer, an answer with no identity"; "a suffix range whose probe fails tells the owner". In `source.test.ts`: "a local read asks files.read with raw, named and the page that owns the token, and nothing else"; "an answer with no identity is unserved"; "an answer in a text encoding is unserved"; "a copy's source reads the descriptor and closes it". In `src/main/lane-b/remote-copy.test.ts`, for `fetchInto`: "asks the hash from its first page, and no key the copy of Open externally does not send"; "an equal-size replacement between two held pages of a file within the cap is copied again, and what the descriptor holds at the end is one version"; "the same replacement that keeps happening is refused, with nothing served"; "above the cap an equal-size replacement between two held pages is not seen: pinned as the recorded limit"; "a text file larger than the cap with no replacement character is copied"; "a pass that starts again leaves the descriptor holding only the last pass"; "a copy that pages, and one copied again after a change, log neither the path nor anything of the caller's" (a distinctive invented path, the captured log searched for it). `SchemeResponder` is `src/services/artifacts/scheme/artifact-handler.ts`'s. `localSource` asks `{ appSessionId, path, offset, length, raw: true, ...ask }` and nothing else, and throws `unserved` for an answer with no `identity` or with a text encoding.

**What "one version" means, exactly.** A response for a file on this Mac is one version: every read answers the identity, the service refuses a read whose file changed under it, and main ends a response whose identity moved. A copy of another machine's file is one version when the file is within the hashed read's cap (8 MiB, `FILES_READ_MAX_LENGTH`): every page answered the file's hash and the digest of what was written is that hash. Above the cap the other machine answers no hash and only the size is compared between pages, so an equal-size replacement during the copy can leave a copy made of two versions; it is drawn until the next read of the entry replaces it. The tracker holds that case. Once written, a copy cannot change: it has no name.
