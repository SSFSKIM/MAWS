## Purpose

A person who starts Claude Code in a terminal on this Mac can watch and drive that session from MAWS, through the bridge the sminos plugin runs inside it. When that session dispatches subagents, MAWS shows them badly today: the transcript's own row says an agent is working, but the card column has no Subagents card, and the Subagents panel lists every agent of the session under "On disk" with "status unavailable" under the sentence "Status is known only while the session runs here". The same session opened from another machine shows its agents correctly, because that machine's sminos derives each agent's status and sends it. So the one place where the person sits next to the terminal is the one place that cannot say what the terminal is running.

After this landing a terminal session on this Mac shows its subagents as a session MAWS runs does. While an agent runs, the Subagents card stands in the column with "N running", its first-level agents, and "(+N)" on a row that has agents running under it; the panel lists Running, then Done with each agent's own outcome ("finished", "finished with errors" in the danger colour, "stopped", "ended with the session"); the card leaves when the last agent ends; and when the terminal's process goes while an agent was still running, that agent ends too. Nothing is stored, no surface is added, and no word is added.

How to see it working: in a terminal session on this Mac that MAWS drives, ask the agent to dispatch two subagents in the background, one of which dispatches its own. The column shows a Subagents card that reads "2 running", then "3 running" once the nested one starts; the row of its parent reads "(+1)", and a press on that control shows the nested agent beneath it. Close the terminal while one still runs: the card leaves and the panel's Done reads "ended with the session" for it. Acceptance below gives the unit tests and the e2e scenes that prove each step.

## Words used here

- **A terminal session; driven.** A session whose engine runs in a terminal (root law 5, in code lane A). MAWS *drives* it while the bridge of the sminos plugin inside it answers on its socket and offers controls (`classify` in `src/services/lane-a/state.ts` answers `live`); the renderer then gives it lane A's controls (`controlsFor`). A terminal session with no such bridge is read-only, and for this document it is a session *not running here*.
- **The bridge.** The plugin's part inside the terminal's engine process and its child process: a Unix socket with `GET /status`, `GET /events` (one JSON line per event, a snapshot first) and `POST /command`. Main's lane A driver (`src/services/lane-a/driver.ts`) holds one `/events` stream per driven session (the *state stream*) and one more per watch.
- **A watch.** One page's subscription to one driven session (`laneA.watch`, `src/renderer/src/lane-a/watches.ts`): main reshapes the bridge's events into the messages sminos's own plane sends for a session on another machine (`src/services/lane-a/reshape.ts`), and emits them as `laneA.plane`. A watch exists only while something on the page holds it.
- **DX4; the `subagents` body.** DX4 is the name the repository gives the session-plane vocabulary a machine sends about one session (`desk-hub/protocol`, `apps/desk-hub/src/protocol/session.ts`). Its `subagents` body is `{ subagents, jobs, mcp }`: each subagent with its status and what the status rests on, the loop's background shells and monitors, its MCP servers' names.
- **The ledger.** `Ledger` in `src/services/lane-a/jobs.ts`: one transcript's rows, reduced to the words they say about tasks. It is a port of sminos's `sminos_jobs.py`, jobs only, pinned by the shared vectors `test/fixtures/lane-a/dx4-jobs.json` (a contract between the two repositories; `dx4-jobs.PROVENANCE.md` beside it).
- **A sidecar; the listing.** Beside a session's transcript the engine keeps a folder `<session>/subagents/` with, for each subagent, its own transcript `agent-<id>.jsonl` and a small file `agent-<id>.meta.json` (the *meta*: its type, description, the tool-use id of the call that started it, its parent agent's id when it is nested). The engine host lists them (`src/engine-host/fs/subagents.ts`), answers `fs.subagents`, and says `fs.subagentsChanged` when the set or a meta changes.
- **The task graph.** One graph of agents and background tasks per session in the renderer (`tools/agents/model/task-graph.ts`, held by `tools/agents/store.ts`); the Subagents card, the Subagents panel and the summaries read it and nothing else.
- **A session MAWS runs** is lane B; **a session on another machine** is reached over the machine link (root, "Words used in this document").

## The design

### The fact, and its one reading

The fact is "which subagents of a terminal session run, and how each one that ended, ended". It already has one reading in the product: the status sminos derives for each agent of a session (DX4, "Jobs and agent status", "Precedence"), which a window on another machine draws through `withStatuses`. Its rules are written down in the shared vectors' `about` and pinned by sixteen of their cases. They join four things: the words the transcript's rows say about an agent (its call's result, a task notification that names it, a `task_status`, a stop), the bridge's own account of which agents it holds as running, the parent agent's end for a nested agent, and whether the session's process still runs.

This landing gives a terminal session on this Mac that same reading, by the same rules, and draws it by the same function. Main's ledger gains the agents half of the module it was ported from; the driver feeds it the bridge's agents, the sidecars' metas and the parents' transcripts; the body rides the watch that already carries the jobs; the task-graph store lays `withStatuses` over the graph it built from this Mac's disk. A terminal session then reads the same wherever its terminal is, and the same from either machine: the person at this Mac and a person looking at this Mac's session from another machine see one status, because both come from the same rules over the same files and the same bridge.

### What was weighed

1. **Port the agents half of the ledger (chosen).** It is the reading the other machine's route already uses, it has a conformance fixture already vendored and already replayed for jobs, and the existing overlay draws it. Its cost is real and bounded: about 150 lines in `jobs.ts`, a small fold of the bridge's agent events, and a follower for each agent that has a nested agent still running.
2. **Feed the task graph the transcript's disk-form events (the ticket's second way). Rejected.** Three reasons, each from the code. (a) It would be a second reading of the same fact, and the two are known to differ: `lane-a/agents/dx4-statuses.test.ts` holds a recorded case where the backfill alone reads an agent `completed` and DX4 reads it `exited`, and the remote route exists in its present form because the body corrects the events. A session would then read one way at this Mac and another way from another machine. (b) A nested agent's call and result are in its parent agent's transcript, never in the main one, so the main transcript's events give a nested agent no start and no end; the "(+N)" this landing is for would stay unknown. (c) The follower sends one bounded window of a long transcript at a time, so an agent that started before the window has no start event either; and feeding these events to the graph also changes what every session that is not running here reads, which the child's file does not ask for and the owner was not shown.
3. **The bridge's agent list alone. Rejected.** It says running or not, never how an agent ended, so Done could say only "ended"; and an agent that ended before the bridge loaded is not in it.
4. **Ask this Mac's sminos for the body, as a remote caller does. Rejected.** It is the same derivation with no port, but it makes a terminal session on this Mac depend on the sminos daemon running here, which driving a session does not (P5 O9's decision of 2026-10-28 on derived jobs rejected "a full local DX4 plane" for the same reason), and it would put the machine link's phases between the person and a terminal on the same Mac.
5. **Use the derivation the repository already has in TypeScript** (`apps/desk-hub/fake-machine/jobs.ts`, "What the code holds today" 10). **Not taken, and reported (R1).** It is the desk's test double of a machine, in another workspace package, and the product would import a double's runtime code; the jobs half of the product's ledger would be deleted for it or live beside it. The vectors were written so that independent producers agree ("every expected body is written by hand from the rules, never computed by either implementation"), and the product's producer is `src/services/lane-a/jobs.ts`. The double is a second reading aid for the port's builder, beside the Python source.

### What is derived, and when it is sent

`derive` in `jobs.ts` answers DX4's body: for each meta, `{ agentId, meta, status, evidence }` with `running` and `spawn` where the bridge holds the agent and `outcome` where the rows say a word. The order of the rules is DX4's, the first that holds: (1) the rows' outcome is terminal: that status, evidence `rows`; (2) the session's process is gone: `exited`, `session`; the parent has ended, for a nested agent that is not a background agent (Decision Log 6, N1): `exited`, `parent`; the bridge holds the agent as not running: `exited`, `bridge`; (3) the bridge holds it as running: `running`, `bridge`; the rows say running (a background launch): `running`, `rows`; (4) `unknown`, `none`. Interfaces §A gives the signatures and §B the body.

*The start time.* DX4's body has no start time of its own; a window on another machine takes it from the start row it holds, else from `file.firstAt`. Here the driver adds one key DX4 does not have to each entry, `startedAt`: the timestamp of the row that holds the agent's `Agent` or `Task` call, read from the ledger of the loop that made the call (the main one, or the parent's). That is the moment a session MAWS runs and the disk-form reader both call an agent's start, it costs no read, and `withStatuses` takes it before `file.firstAt` (R2). An agent whose call is in no ledger this Mac follows (its parent's transcript is unreadable; a forked skill with no call) has none, and its running row reads "elapsed unavailable" in the panel and no time on the card, which are today's words for that.

*When.* The body is derived when one of its four inputs changed since the last derivation, and at no other time: the ledgers' count of facts, the bridge's map, the listing, the process flag. A ledger counts the rows that added a fact the body is made of: an `Agent` or `Task` call or its result, a job's start, and each word said about a task or a call (a notification, a `task_status`, a stop). New bytes that say nothing of an agent or a job, which is nearly every row of a transcript that streams, move no count and derive nothing; neither the derivation nor the comparison per watch runs once a second. A bridge `agent` event first asks for a read at once, so the row that says how the agent ended is usually in hand before the bridge's "not running" is applied. The body goes out in each watch's snapshot (DX4's snapshot carries `subagents` beside `jobs`) and afterwards as a `subagents` message to each watch whose last body differs, by JSON. Nothing in an entry changes while an agent merely works (no file size, no last timestamp), so a session whose agents run and say nothing new sends nothing. When an input does change the cost is plain: one pass over every listed agent and one whole-list message per watch, about twice in an agent's life.

*Settled and provisional.* A status has two grades. It is **settled** when it is an ended status (`completed`, `failed`, `stopped`, `exited`) that rests on the rows, on the session's process being gone, or on a parent that is itself settled: no later row can change it (but for an agent the engine wakes, R7's stated residual). It is **provisional** otherwise: `running` on either evidence, `unknown`, `exited` on the bridge's word alone, and `exited` under a parent that is not settled. A provisional ending is the case the first writing got wrong: the bridge reports a nested agent stopped, the read that follows finds no result row yet, and the row that says it failed arrives in its parent's file a moment later. And a nested background agent can outlive its parent (P3, `u8d-p3-nested-r1`: the parent completed while its nested agent still ran), so a parent's own end does not close its file while something under it is open (Decision Log 6, N2). So a parent's follower is governed by its nested agents' grades, not by "ended":

| the parent is | and a nested agent of it is | its follower |
|---|---|---|
| settled or not | running, or provisionally ended (one or more) | **open**: read in each tick |
| not settled | settled or `unknown`, every one | read once when it became a parent; not in the tick's set; reopened by the first row above |
| settled, and nothing under it open (this derivation made it so) | settled or `unknown`, every one | read **once more**, the body derived again, then **closed for good** |
| closed, or never readable | a new entry names it as parent | read again, as when it first became a parent |
| not readable (missing, or the read failed) | any | tried once when it became a parent; tried again only when the host's listing reports a change of that parent's own entry or names a new agent under it; never on the tick; one log line per parent per cause |

An `unknown` nested agent never keeps a follower in the tick's set, and neither does an unreadable parent, whatever runs under it. The set stays bounded: everything under a parent settles at the latest when the session's process goes (evidence `session`). sminos's own producer keeps checking every parent's file for as long as it is subscribed (a stat, and a read only when the file changed); the rule here reaches the same statuses with fewer reads, because it stops only where no later row can exist. The difference is in when files are looked at, never in what is derived from them.

*The listing is owed.* The first listing of a follow is owed until it is answered. If the read fails it is asked again on the driver's existing backoff (`Backoff` over `timing.backoff`, half a second doubling to eight; one attempt per step) and when main learns the engine host is streaming again (the host supervisor's `onStreaming('engine-host', …)`, which `src/services/spine-root.ts` already hands to other services); no signal is added. After the host comes back the listing is read again even when one was held, because a restarted host says changes only for sessions it has already read. Every answer is fenced by the follow's generation, and the retry's timer goes with the follow.

*Order, when things arrive between.* Every input lands in memory first and the derivation is one synchronous pass over what is held; two passes cannot interleave. A bridge event that arrives while a read is in flight waits for that read (`TranscriptJobs.read` already serializes) and derives after it. A spawn the bridge reports before the host has listed the agent's meta gives no entry yet (DX4 emits one entry per meta); the listing's change, a tenth of a second later by the host's own settle time, derives again. A stop the bridge reports before the engine has written the result row reads `exited` (evidence `bridge`), which is provisional: the loop that holds the agent's call keeps being read (the main one always; a parent's because that ending keeps it open), and the row, whenever it lands, gives the outcome with evidence `rows`. Until then the card is not affected (the row leaves it either way), and in the panel the agent is in Done, folded by default, under the word of C1. A later listing that fails to read leaves the last one standing and is logged once. When the last watch ends, the followers, the ledgers, the listing and any retry are dropped together; the bridge's agents stay with the state stream.

### What the window does with it

`lane-a/watches.ts` keeps a watch's `subagents` beside its `jobs` in the lane A store. The task-graph store, when the session it watches is one this Mac drives, holds the session's watch while it is watched and publishes its own graph with `withStatuses` laid over it, again at each change of either; its own reductions never read the patched graph (Interfaces §C). The card, the panel, the drill-in and the summaries are not edited: they read the graph. Two things follow without code of their own. Stop agent is offered only while the agent has not ended, because the node's status is now known. And the transcript's agents row keeps its own reader.

When the watch ends, the store keeps the last statuses only if none of them is `running` (the rule the jobs already follow): the driver sends the body of a gone process before it ends the watch, so an ended terminal's agents stay "ended with the session" in the panel for as long as the page lives; a watch that ends unheard-of drops them, and the graph reads from disk again.

*What ends the kept statuses* is a new process of this app's for the session, and nothing else. "The session has an engine status" is not that fact: a session a terminal drives can keep an exited engine status from an earlier run by this app (the driven session's cases of `subagents.test.tsx` mount exactly that), and the driver removes the session's lane A state last when the terminal goes. The fact the code already has is the launch: every engine status carries when its process was launched (`launchedAt`, beside `launchId`; the task-graph store's `applyStatus` already reads a new launch as the end of the old one's work). So the lane A store keeps, with a session's statuses, the time it last noted them; they are laid unless the session's engine status says a launch later than that, and such a status discards them: not hidden, and not laid again when that process exits. The test is the launch's time and not "a status whose process is not exited arrived", because the store applies statuses only while something watches the graph: a launch that came and went unwatched is first seen as an exited status, and must still end them; and an earlier run's exited status that reaches the page after the terminal's statuses were noted must not. A terminal that takes the session again afterwards is a new watch, whose statuses are noted at that later time.

One sentence changes place. "Status is known only while the session runs here" is drawn today above every driven session's lists. It is not drawn where the lane A store holds, for the session, at least one agent whose status is not `unknown` (R3).

### Where the source cannot know

1. **An agent the main loop is waiting for, with a bridge that reports no agents.** Its call has no result row yet, so the rows say nothing; only the bridge can say it runs. A bridge old enough to send no `agents` in its snapshot and no `agent` events leaves it `unknown`: On disk, "status unavailable", while the transcript's row says it works. When it ends, its result row gives its outcome and it is in Done. Background agents are unaffected (their launch is in the rows). Nothing detects such a bridge: this document found no capability key for agent reports in what the bridge says of itself, and an absent or empty list derives the same as a bridge that holds no agent. On a terminal session of `2.1.322` this does not arise today: the engine launches every `Agent` call in the background there (P4, 5 of 5, and P3's two nested calls; Decision Log 8, N11). It can arise in print mode or under another configuration, and the rules for it stay as the vectors hold them.
2. **A nested agent whose parent's transcript cannot be read** (deleted, or unreadable): its call and result are there. With the bridge's word it reads running or ended; without it, `unknown`. The file is tried once, and again only when the listing changes for that parent or names a new agent under it ("Settled and provisional"); a file that becomes readable with no such change stays unread until the page watches the session anew.
3. **An agent with no call** (the engine's forked skill: its meta has no `toolUseId`): the bridge's list is its only source; without it, `unknown`.
4. **An agent that started before MAWS watched the session.** Nothing is lost: the ledger is fed the whole transcript at the first read, and the bridge's snapshot holds every agent the bridge knows, those it found in the engine's own list when it loaded included.
5. **An agent that ended, and left the engine's list, before the bridge loaded, with no end in the rows.** It reads `running` from its launch row until the session's process goes. This follows from the order of DX4's rules, on both machines; no vector holds this exact case.
6. **A terminal session with no bridge, or with one that cannot be driven.** The session is not driven: no watch, so no body. It reads as a session not running here.
7. **A bridge that goes while the terminal's process lives.** The driver takes a session with no bridge as gone (`unbridge`), for its jobs today and for its agents now: they read "ended with the session" until the bridge answers again and a fresh watch says otherwise (R5). The transcript's own row follows the holder registry (U8b's M6), not the bridge, so for that stretch the row can still say the agent works while the panel says it ended.
8. **A session whose process is gone.** Every agent the rows hold no end for reads "ended with the session", once, before the watch ends. After the page is reloaded the session is one not running here.
9. **A workflow's agents.** In no list on any route; no entry is derived for them.

### What repaints, and what it costs with nobody looking

The measurement of an unattended window (item 566) is why the cards do not tick. The same standard applies to the source.

- **Main, per watched driven session, per second:** one read of the main transcript, which exists today (`jobsPollMs`, 1000: one `open`, one `stat`, and only the appended bytes); plus one such read for each *open parent*: an agent, ended or not, that has a nested agent that is running or has provisionally ended (N2). So a nested agent that ended on the bridge's word alone keeps its parent read, once a second, until the row arrives or the session's process goes; a parent whose nested agents are all settled or `unknown`, and a parent whose file cannot be read, cost nothing per second. A session with no parent open adds no read.
- **Per event, not per second:** one extra round of reads after each bridge `agent` event (two per agent: its spawn and its stop); one read of a parent when it becomes one and one more when it settles; one `fs.subagents` listing when a session's follow starts and one each time the host comes back, with a failed first one asked again on the backoff's steps.
- **File watches added: none.** The sidecar folder is watched by the engine host's one store watcher, as today; the driver reads its change event.
- **Derivations:** none per second. One pass over every listed agent when the ledgers' count of facts, the bridge's map, the listing or the process flag changed since the last one; a transcript that grows with no row about an agent or a job derives nothing, with any number of listed agents.
- **Messages:** one whole-list `subagents` message per watch when a derivation's body differs, by JSON, from the one that watch last carried: about two per agent over its life (it starts, it ends), and none while agents merely run. The comparison runs only after a derivation.
- **The window:** `withStatuses` returns the same graph object when a body changes no node, and the store writes nothing then, so no selector recomputes and no card repaints. A card's running row reads the slow clock (`useCardClock`, 30 s), as today; a panel's row ticks each second only while the panel is visible, as today.

*How tests pin it, by counts* (M2 and M3), each with a driver whose poll is short and whose dependencies count their calls:

- A watched session with two running first-level agents and an idle transcript, over N ticks: N main reads, zero parent reads, one listing read, zero derivations after the first, zero `subagents` messages.
- A transcript that grows on every tick with rows that name no agent and no job, with many agents listed: zero derivations and zero messages over N ticks.
- One nested agent the parent waits for, running under a running parent: at most N more reads, all of that one parent. The parent's own result row arrives in the main transcript: exactly one more read of the parent, and its count stops growing. (A background nested agent that still runs keeps its parent open past the parent's end, N2; that is the held-open test of M2's "the nested agent outlives its parent".)
- A session opened with several old parents whose nested agents read `unknown` and nothing running: over N ticks, zero parent reads after the first attempt of each, and at most one log line per parent.
- A bridge `agent` event: exactly one more round of reads and at most one message.
- In the window: the store's entry for the session is the same object after a second identical body.

`settled` is true for a status of `completed`, `failed`, `stopped` or `exited` whose evidence is `rows` or `session`, and for evidence `parent` when the parent's own entry is settled; false for `running` on any evidence, for `unknown`, for `exited` with evidence `bridge`, and for evidence `parent` under a parent that is not settled or has no entry. A nested agent is *provisionally ended* when its status is ended and it is not settled.

The status and its evidence, the first that holds (DX4, "Precedence"; the vectors' `about`):

| # | condition | status | evidence |
|---|---|---|---|
| 1 | the rows' outcome for the agent is terminal | that status | `rows` |
| 2 | the session's process is gone | `exited` | `session` |
| 3 | it is not a background agent, and its parent has a meta and has ended (`completed`, `failed`, `stopped`, `exited`) (N1) | `exited` | `parent` |
| 4 | the bridge holds it with `running` false | `exited` | `bridge` |
| 5 | the bridge holds it with `running` true | `running` | `bridge` |
| 6 | the rows' outcome is running (a launch) | `running` | `rows` |
| 7 | none | `unknown` | `none` |

The bridge counts only while the session's process runs. `running` is on an entry while the bridge holds the agent and the process runs; `spawn` is the bridge record's keys among `parentAgentId`, `subagentType`, `description`, `name`, `background`, `model`, `toolUseId`, kept after the process is gone; `outcome` is the rows' word, `{ status, raw, at, summary?, outputFile? }`. An agent's loop is the main ledger when it has no parent, else its parent's ledger; its call is the meta's `toolUseId`, else the bridge record's; it is a background agent when the meta's `requestShape` is `background`, the bridge record's `background` is true, or its call asked for it, and, for rule 3 alone, also when its loop's rows hold an `async_launched` result for it (Decision Log 8). *A nested agent's rows' outcome* (N7) is its parent's ledger's word when that word is terminal; otherwise the main ledger's word for the agent's id when that is terminal; otherwise the parent's ledger's launch; evidence `rows` either way.
