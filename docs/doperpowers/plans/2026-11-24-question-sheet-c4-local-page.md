**Facts of the code at the pin**, each read at `760d7ad1a`.

- **How `mawsd` is built and started.** `mawsd` is `out/main/mawsd.js`, the second input of main's build (`electron.vite.config.ts`), run as plain Node: the app's binary with `ELECTRON_RUN_AS_NODE=1` on a Mac, a pinned Node on Linux (`src/mawsd/index.ts`). The daemon is `mawsd run --unit|--private --dir <profile>/mawsd` with the profile in `MAWS_USER_DATA`; every other command is the command line's (`src/mawsd/cli.ts`), which reaches a running daemon through `machine.sock` and never starts one. The app installs the default profile's daemon as a unit (a LaunchAgent on macOS, a systemd user unit on Linux) and starts a private one for any other profile; a unit never exits by itself, a private one exits after ten minutes with no client, both hosts parked and no hold out (`src/mawsd/clocks.ts`). The default profile is `defaultProfileDir` (`src/shared/daemon/profile.ts`).
- **Its start and its exit** are one function, `startDaemon` (`src/mawsd/daemon.ts`): the directory, the lock, the token, the log, the sockets, the endpoint module, the adoption of running hosts, then `clocks.served()`. A socket that cannot listen there is fatal. The exit order closes the listeners, stops the endpoint, the render seam and the spine, closes the clients, and removes what is the daemon's own.
- **What it serves today, and how each entrance knows its caller** (`src/shared/daemon/files.ts`, `src/mawsd/daemon.ts`). Three Unix sockets, `engine-host.sock`, `pty-host.sock` and `machine.sock`, mode 0600 in a 0700 directory, whose clients present `mawsd.token`. `artifacts.sock`, which is HTTP over a Unix socket with no token and no loopback port: the file's mode is its whole check (`src/mawsd/artifacts-endpoint.ts`). A cua socket per session, checked by the peer's identity. The endpoint module's sealed channels, among them a WebSocket listener bound to the tailnet's addresses, never a wildcard, and by default only in a unit daemon (`src/endpoint/direct-listener.ts`, `src/endpoint/endpoint.ts`). The one loopback TCP listener in the tree is the connectors' OAuth callback (`src/services/connectors/oauth-callback.ts`): `127.0.0.1`, a random port, fixed text, closed when the flow ends. **So nothing in the repository answers a browser on a known port, checks a Host or an Origin header, or keeps a browser's credential: all of §L is new code**, and the composite's "first HTTP door" is exact in that sense and not in the sense that `mawsd` never spoke HTTP.
- **Nothing is loaded at an idle start.** `mawsd`'s deferred parts (the endpoint, the services library, the artifact handler, the render seam) are chunks loaded at their first use; `src/engine-host/bundle-guard.test.ts` has a case for each and keeps `ws` off the run path, and `src/mawsd/pack-chunks.test.ts` holds the Linux pack to every chunk the graph names. The artifact endpoint is the pattern for the deferral: a `node:net` server whose accepted connections are paused until the handler's chunk has loaded, then handed to an HTTP server that never listens (`src/services/artifacts/scheme/endpoint-library.ts`).
- **What Node's HTTP server does by itself**, each read in the runtime `mawsd` runs on by this document's reviewer, and each confirmed by a test in M1 before a check is trusted to it. It starts checking its header and request deadlines when it listens, so an HTTP server that is only handed sockets, as the artifact endpoint's is, enforces neither. Its parser stops collecting header pairs at `maxHeadersCount` and reports nothing, so `rawHeaders` at that length may be a cut list. Its parsed `headers` keeps one of a repeated `Host` or `Authorization` and drops the rest. And it answers some requests before any `request` listener runs: a request with no `Host` (400), an `Expect` it does not take (417), a malformed one (400), headers past their size (431).

**Where the page server lives, and when it serves.**

- **T1 · It is `mawsd`'s own part, outside the spine**, in `src/mawsd/sheet-page/`. Node's HTTP server owns the two listeners; what answers a request (the routes, the pairing, the bundle's table, the WebSocket) is a chunk loaded at the first request. It reaches sheets by calling C3's service in process, through the spine's root (§N). It is not a part of the spine because the spine is cold at start, is released when the machine is quiet and can be refused, while the shell, the pairing and the heartbeat must answer through all three. It does not go through the wire's `sheet.*` commands because `sheet.put`'s handler stamps every inbox line `by: 'maws'` (C3's §D), and a line from the page is `by: 'page'`. It does not copy the artifact endpoint's shape, a `node:net` listener handing its sockets to an HTTP server that never listens, because an HTTP server that never listens enforces none of its deadlines (the facts above), and this listener, unlike a 0600 socket, is one any program on the machine can hold open.
- **T2 · The default daemon serves the page; any other `mawsd` serves it only when `MAWS_SHEET_PAGE=1`**, and `MAWS_SHEET_PAGE=0` turns it off in any. The rule is the direct listener's (only a unit binds it by default), stated by profile and not by kind because the gate's launchd suites run unit daemons over scratch profiles, which must never take the port or write into a real sminos home. It also makes one page a machine account without any negotiation: there is one default profile. A daemon decides first from its own environment and the constant below, and only one that is going to serve captures the login shell's (for the sminos home, the port, and a `MAWS_SHEET_PAGE=0` exported there), so a private daemon that serves no page starts no shell for it and loads nothing for it. **Every test launcher forces the page off**: `launchEnvironment` (`e2e/support/scratch-env.ts`) sets `MAWS_SHEET_PAGE=0` and drops `MAWS_SHEET_PORT`, so an Electron suite run from a shell that opted in, beside a bundle an earlier build left, opens no port; the page's own rig is the one launcher that sets the switch, with a scratch home and a port of its own. Until M5 the constant `SHEET_PAGE_DEFAULT_ON` is false, so through M1 to M4 even the default daemon serves only under the switch; M5 sets it true after its live checks pass, and not before: the owner's answer is that the page is served by default ("The look", the fourth answer).
- **T3 · It listens on `127.0.0.1` and on `::1`, each named, never a wildcard, the same port on both, and serves on neither unless it holds both.** The name resolves to both addresses, and a browser may try `::1` first. Were the page on one address only, any process that bound the other would answer under the page's origin. A machine with no IPv6 loopback (the bind answers `EADDRNOTAVAIL` or `EAFNOSUPPORT`) is served on `127.0.0.1` alone. Because of this rule the real `mawsd` and another holder of the port are never reachable at once, which T28 stands on.
- **T4 · The port is 47590, or `MAWS_SHEET_PORT`** (1024 to 65535, or 0 for one the system picks, which the suites use), read from `mawsd`'s environment and then from the login shell's, as C3's S2 reads `MAWS_SMINOS_CLI`; a value that names no port is ignored with a log line, as `MAWS_ENDPOINT_PORT` is. **A taken port is not served and not registered.** The state reads `port-taken`, `mawsd status` says so, and the bind is tried again every 30 seconds. It does not move to another port: the port is part of the page's origin, so a page on another port is a browser that was never paired with drafts it cannot see, behind a link that changed; and whatever holds 47590 may be another profile's page, whose registration stands. A terminal session started meanwhile finds no live surface and has today's tool, which is the composite's own fallback.
- **T5 · A build with no bundle serves no page** (state `no-bundle`). The bundle is found beside the build (§P); a development run and the Electron suites' builds need none. T2's forced switch, and not the bundle's absence, is what keeps a test from serving: a tree can hold a bundle an earlier build left.
- **T6 · Nothing of the page can stop or delay the daemon.** The page server starts after `clocks.served()`, in the background; every failure in it (the shell capture, the bundle, a bind, the chunk's load, the sminos home, a write of the registration or of the browsers' file) is a state and a log line, never an exit. Where such a failure changes what a person was told, it is also told to them (T10's unpairing). Its listeners are closed first in the exit order, with the daemon's others, and its stop is bounded at half a second.

**Who is let in.**

- **T7 · The page's origin is one string, `http://sheet.localhost:<port>`, and the three checks are read from it** (§L has them request by request). The Host check compares the request's one `Host` header with `sheet.localhost:<port>`, case folded, and nothing else passes: not `127.0.0.1:<port>`, not `localhost:<port>`, not the name with a trailing dot or without its port, not two Host headers. It runs first, on every request, the shell and a WebSocket's upgrade included, so a requester with the wrong Host learns nothing, not even which paths exist. A refusal's body is a constant: nothing of the request is written back.
- **T8 · A code is eight characters of a 32-letter alphabet without look-alikes, shown as `XXXX-XXXX`: 40 bits.** `mawsd sheet pair` asks the running daemon for one over `machine.sock`, whose token only this user's processes can read, and prints it. A code is made only while the page is in state `listening`, is held in memory only, lives five minutes, works once, and there is one at a time: a second `pair` voids the first. Five wrong tries void it, and the page server answers at most ten exchanges a minute whatever their source. It is typed into the pairing screen, never carried in a link (the composite's writer, 2026-11-24): the composite's link has no secret, and a typed code pairs whichever browser the person is looking at. Since a code dies with the process that made it and none is made while the port is taken, a code typed into a page some other program serves is worth nothing to that program.
- **T9 · The credential is 32 random bytes, in base64url**, made at the exchange and sent back once. The page keeps it in `localStorage`, which is scoped to the origin, port included, and sends it as `Authorization: Bearer <credential>` on every request under `/api/` and on the live connection (rule 1), in both cases only to a server that has proven itself in that tab (T28). It is never a cookie, never in a URL and never in a log line. `mawsd` keeps two things made from it, in `<profile>/mawsd/sheet-page.json` (mode 0600 in the daemon's 0700 directory, written by replace): its SHA-256, which a presented credential is compared with in constant time, and the proof key of T28. Neither can be sent as the credential.
- **T10 · A credential lasts until it is revoked or has not been used for 90 days. Each browser pairs for itself**, with a code of its own; at most 16 are kept, and a seventeenth drops the one seen longest ago (the composite's writer: stands). `mawsd sheet browsers` lists them (an id, a label read from the user agent as one of a fixed set of words, when paired, when last seen); `mawsd sheet unpair <id>` and `--all` revoke, and the page's own menu unpairs the browser it runs in. **A revocation has two moments, and its answer waits for the second.** At once, in memory, the credential is refused and that browser's live connections are closed. Then the browsers' file is replaced, and only when that replace succeeded is the revocation answered as done. When it failed (a full or read-only volume) the answer says so, in the command's exit and words and in the route's status: the browser is refused until `mawsd` restarts and would be paired again after, and `mawsd` tries the replace again at each tick of its timer until it succeeds. A pairing is the same: a credential is handed out only after the file that knows it was replaced, and a failed replace refuses the exchange and leaves the code live. When a browser was last seen is written at most once an hour, and a failure of that write is only logged.
- **T11 · Three commands join the `daemon` namespace**, main-only and graded `internal`, so no caller that comes through the endpoint can mint a code or list a browser: `daemon.sheetPair`, `daemon.sheetBrowsers`, `daemon.sheetUnpair` (§K). Three commands and not one with a union for its input, because a member added to a union later breaks the wire (the reason `daemon.e2eRender` is a command of its own).
- **T28 · A tab proves the server before it sends its credential anywhere** (the composite's writer's ruling on the review's first finding). Whoever holds the port answers under the page's origin, and a tab that reconnected by itself and opened with its credential would hand it to that holder, who could use it against `mawsd` once `mawsd` had the port back. So the live connection opens with the tab's nonce, and the server answers with a MAC over it that only the `mawsd` this browser was paired with can make: the key is derived from the credential at the exchange, by both sides, and `mawsd` keeps it beside the hash. Only after checking the MAC does the tab send the credential, and **a tab makes no request that carries the credential unless its own proven connection is open at that moment**, the first after a load included. An open tab therefore gives a stranger on the port nothing: no credential on the socket, none on a fetch. §L has the exact form. Three properties it rests on: the nonce is fresh for each connection, so a proof recorded from one answers no other; the real `mawsd` will make a MAC for anyone who asks with the page's Origin, which helps nobody, since a MAC for one nonce says nothing of another's and, by T3, the real `mawsd` and another holder of the port are never reachable at once to relay between; and a refusal cannot be proven, since a server that unpaired a browser no longer has its key, so **a refusal makes the page delete nothing** (T19). The MAC is computed in the page with a hash library and not with the browser's own, which is a secure context's (T21). **What remains, and is the limit this child states and does not close:** a person who opens or reloads the page while another program holds the port runs that program's script in the page's origin, which can take the pairing and use it against `mawsd` after it returns, until that browser is unpaired. For a program of the same user this is today's trust. For another account on the Mac it is a gap; a key the browser cannot export would not close it, since the other program's script could still ask the key to act, and a service worker that program planted would outlive the visit. One instant is outside the proof and is stated, not closed: a request made between `mawsd`'s death and the tab seeing its socket close goes to whoever holds the port by then, since `proven()` reads the socket's state when asked. **A relay is not closed either** (the branch review, 2026-11-27): the proof shows that the paired `mawsd` answered the tab's nonce, not that it holds the tab's connection. So a program of another account that holds the tab's connection (it took the port while `mawsd` was not listening) can relay the hello to the real `mawsd` on another port or socket, return its proof and receive the credential. That is inside the class §8.2 leaves open, another account on the page's port. The MAC covers the page's origin (the host name and the port being served) and the tab checks it against its own `location.origin`, so a proof made by a `mawsd` serving another port is worth nothing here (below). That narrows the relay to one aimed at the same origin; closing it needs a sealed channel or the port held by launchd. The owner's ruling (2026-11-27) is to ship with the limit; board ticket 887 holds what closing it would take, and nothing of it is M5's. A stranger would have to take the port inside that instant, and the next request finds the socket closed; the instant covers a chunk of the page's code as it covers a fetch (below). **A tab makes no request to the page's origin that a stranger's answer could turn into running script or a spent credential unless its own proven connection is open at that moment** (the composite's writer, 2026-11-27): the page's own code is in its load, and the Markdown stack's lazy chunks (a code language's grammar, the diagram renderer) are loaded only through a loader the page hands it, which asks `proven()` first. While unproven, what would need a chunk is drawn plain (a code block as unhighlighted text, a diagram as its source in a code block) and drawn again once the connection is proven; a chunk whose load failed is tried again on the next proven connection.

**What it answers with.**

- **T12 · Every response carries the same headers** (§M), a refusal, a WebSocket's refused upgrade and the answers Node's own parser writes included: rule 3's three, and with them `frame-ancestors 'none'` in the content policy, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin`. The content policy starts from `default-src 'none'` and names only the page's own origin, `data:` and `blob:` for images, `data:` for fonts, and inline styles, which the highlighter and the component library write; it allows no inline script and no `eval`. The framing directive is this child's addition to rule 3, taken by the composite's writer: the four rules as first written did not stop another site from framing the page and steering a click onto Send. Node answers some requests before any handler of the page's runs (a malformed request, headers past their size, an `Expect` header); the page server takes those over (§J), so "every response" has no exception.
- **T13 · Static files are served from a table, never from a path.** At the chunk's load the bundle's directory is listed once into a map from URL path to file, regular files only; a request is a lookup in that map, so no path a requester writes is ever joined to a directory. `/` and anything under `/s/` answer the shell; a path that is neither in the table nor one of those is 404. Types come from a fixed list of extensions, and a file whose extension is not on it is not in the table. Everything static is `Cache-Control: no-cache` with an ETag, everything under `/api/` is `no-store`: on loopback a revalidation costs nothing, and after an update no browser holds a shell that names files that are gone.
- **T14 · The live connection is a WebSocket at `/live`**, served with the `ws` library the tree already bundles. A WebSocket and not an event stream, because the tab has to speak first (T28) and rule 2 asks for an Origin on it, which a browser sends on every WebSocket handshake but not on a same-origin `GET`. The upgrade is refused before the handshake unless the Host and the Origin pass. Then the server says nothing until the tab's hello, proves itself, and says nothing of any sheet until the credential has come and been checked. After that it sends a snapshot taken after the connection was subscribed, so no change falls between the two, and one small message per change; the page reads a model over HTTP only for the session it shows (C3's S7), **and reads it again at every snapshot before it lets Send be pressed**, because changes made while a tab was not connected are never replayed to it.
- **T15 · A live connection is a standing hold, and a request for data an operation's hold**, on the daemon (`DaemonServices.hold`). So the spine stays loaded while a page is listening and announces changes, a private daemon does not exit under an open page, and a tab forgotten in the background costs what an open app costs. To bound that, the page lets its connection go once its tab has been hidden for five minutes and connects again when it is shown. When the spine cannot be had, or leaves `loaded`, the server says so on the connection and keeps it, since the connection is also the tab's proof of the server; the page asks for the snapshot again after 5 and then every 10 seconds.
- **T29 · Before a snapshot the daemon's discovery is brought up to date**, as it is for a `session.list` from any client that is not the app (`src/mawsd/discovery-wake.ts`): a parked engine host is woken for one pass, within that wake's own bound, and parked again. Whether a session is running or stopped is the index's fact, not the record's (C3's `SheetSummary.live`), and the page is what a person has open when the app is closed, which is exactly when the index is otherwise as old as the app's last run. Without this the overview's "stopped ones apart" would be true only beside a running app. **As built in M3:** the wake as it stood resolved when the index had applied the store's scan, before it had folded the registry's holders, so right after it a held session still read stopped (a non-app `session.list` through the wake had the same lag). The index now tells a second signal, `onHoldersFolded`, once a generation, when a sync has read the registry; `SpineRoot.discovery` passes it on, and **only `mawsd`'s discovery wake awaits it**, both signals of one generation, within the wake's own bounds. `tellApplied()` is told where it was, so nothing the app waits on moves (the app's start is a measured bound). A failed registry read ends the wait once `applied` has come in that generation, unheard: nothing is cached as fresh and the park is asked as at a give-up; where the scan fails too, the wake's bounds decide.
- **T16 · A reference's or an upload's body is answered as bytes with one of five types**: `text/plain; charset=utf-8`, or `image/png`, `image/jpeg`, `image/gif`, `image/webp` (rule 4, to the letter). Which is decided by the record's own account of the body through C3's service, never by the bytes or a name: a captured HTML or SVG file is a text reference and goes out as plain text. Like every `/api/` path it needs the credential in a header, which a navigation, an `img` and a frame cannot send, so the body is only ever read by the page's own script, which hands it to C3's components as text or as an image's bytes.
- **T17 · A pasted image reaches the record through the page server before the door names it.** The page scales it as the app does (`downscaleImage`, `src/renderer/src/composer/editor/attachments.ts`, which imports only shared modules), posts the bytes with their type, and the page server holds them to 5 MiB before it hands them to C3's `upload`, which checks the bytes against the signature of the type they claim, writes `uploads/<name>` exclusively and answers the path. The draft carries that path; the Send's answer names it; the door checks the file.

**The registration.**

- **T18 · `mawsd` itself writes the registration, from a timer of its own that needs nothing loaded.** The file is `<sminos home>/sheet/surfaces/<name>.json`, `name` being `mawsd` for the default daemon and `mawsd-<12 hex of the profile path's SHA-1>` for any other, so a scratch daemon sharing a home never writes the default one's file. `url` is the page's origin with no path and no trailing slash, since the tool appends `/s/<session>` (C2's M5); `reach` is `local`; `pid` is the daemon's; `heartbeatAt` is `toISOString()`. It is written by replace at the first tick after the listeners are up and every 10 seconds after. The home is `sminosHome` over `mawsd`'s environment and one capture of the login shell's, the rule C3's reader reads by; where the home does not exist nothing is written or made, and it is looked for again at each tick, so a machine without sminos gets no directory from MAWS. `sheet/` and `surfaces/` are made 0700 when absent, the file is 0600, and a `sheet` or `surfaces` that is a link is refused as C3's Confinement refuses one. **At a clean stop the file is removed if it still names this process.** After a death it stays: its `pid` is then no running process and its `heartbeatAt` ages past 30 seconds, either of which makes it not alive to C2's reader. The heartbeat does not follow the spine's state: where the spine cannot load, the page says so (§P).

**What the page keeps, and what it reads.**

- **T19 · The browser keeps three kinds of thing, all in `localStorage` under `maws.sheet.`, and nothing else: no cookie, no service worker, no cache of its own.** The credential. The surface's memory (C3's `SheetMemory`), so that a reload, and a second tab opened from the terminal's link, show the draft and the "Updated" mark the first tab had. And nothing of a model. (Beside them, as built in M4, one value of no session's data: whether the outline is open, `maws.sheet.outline`, which F9 says is remembered.) **The memory is stored as one entry a thing, never as one value a session**: one entry for each question's draft, one for what was seen of each question, one for each act sent, one for each Send in flight. A tab writes only the entry of what the person just changed in it, so two tabs editing different cards cannot overwrite each other, whatever each last read; two tabs editing the same card are one draft, and the later write stands. A Send's entry is written once, at the press, before the request leaves, and nothing but that Send's own end removes it, so a Send keeps its keys through any other write; a tab that finds one older than the door's own time limit offers it again as the same inbox lines, which the key makes the same act (composite §4.2). Entries are adopted across tabs through the `storage` event, dropped for a question by C3's `reconcile` in whichever tab sees it gone, and swept after 30 days untouched. **A refusal deletes nothing**: a tab that is told it is not paired shows the pairing screen and keeps what is stored, because a refusal cannot be proven (T28) and a stranger on the port must not be able to make a browser forget. The person's own Unpair deletes every key; a new pairing replaces the credential.
- **T20 · The page reads its path and nothing else of its address.** No query parameter and no fragment does anything, so a link another site makes to the page can open a sheet and can do nothing more.
- **T21 · The page uses nothing a browser gives only to a secure context**: no `crypto.randomUUID`, no `crypto.subtle`, no asynchronous clipboard. Keys and nonces come from `crypto.getRandomValues`; T28's MAC from `@noble/hashes`, which the tree already holds for desk-web. Whatever a browser thinks of a name under `localhost`, the page works where it loads.
- **T22 · A link the sheet's policy refuses is drawn as text, on every surface, from this child on.** Rule 3 limits agent-written links to `http`, `https` and the question's own references. C3's `SheetMarkdown` makes a refused link inert by giving it no action, which is enough in the app. In a browser a `mailto:` link is still an anchor with its `href`, and the browser's own gestures follow it. **As C3 landed, this is already built, by another seam**: the Markdown takes an optional `link` component (`R/transcript/view/markdown/Markdown.tsx`), which the transcript does not pass, and `SheetMarkdown`'s own draws every refused link as `<a aria-disabled="true" data-link-refused>` with its children and **no `href`**, so no click, middle click, modified click or context menu has an address to follow. That is "drawn as its text" in every way a gesture can tell; this child adds no seam of its own (the `linkStands` function first planned here is not built), and M4's proof selects the element by `[data-link-refused]`.

**How the page is built, shipped and tested.**

- **T23 · The page is a workspace app, `apps/sheet-page`, built with Vite the way `apps/desk-web` is, into `out/sheet-page/`**, which the Mac app's archive already includes and which the Linux pack is taught to copy; `mawsd` finds it one directory above its own entry. Not under `out/main`: the bundle guard reads every `.js` file there as a main-process file and fails on the first character above U+00FF, which a Markdown stack is full of. Not a third page of the app's renderer build: that build shares its chunks with the app, so the page server would serve the app's own code, and the Linux pack ships no renderer. The page's build is a step after `electron-vite build` wherever a shippable tree is made (`pnpm build`, `pnpm build:app`, `pnpm mawsd:pack`) and is not part of `scripts/e2e-build.sh`, whose Electron suites never open the page. **A pack is strict by default and has one stated exception**: it refuses a tree with no bundle, and `--no-page` packs without one, for the two callers that pack what a partial build made (`src/mawsd/pack-chunks.test.ts` after the unit job's main-only build, and `test/support/remote-bench.ts` after an e2e build).
- **T24 · The page's browser suite lives in `apps/sheet-page/e2e/` and is a gate group of its own, `sheet-page`**, added to the workflow's three lists beside `desk-web` and to the step that installs Playwright's browsers. It starts the built `mawsd` as a process, which needs Node and no Electron, so it runs on the Linux pool. A new group and not cases in an existing one, because no existing group drives a browser against `mawsd`. The requests the four rules refuse are sent twice: by Node clients that write any header they like (class 1a, M1 and M3), and by a real browser from a real second origin, which cannot (this group, M2 and M4). The first shows the server refuses; the second shows what a web page can actually send. A browser's own account of a cross-origin request is not evidence of a refusal (a `no-cors` request reads the same whether it was refused or obeyed), so the second kind is judged from outside the page: by the status Playwright saw on the wire, and by the record's files.
- **T25 · Two landings.** C4a is M1 to M4, each provable on GitHub Actions and none served without the switch, so it can merge as soon as it is reviewed, before C2's terminal side exists. C4b is M5.
- **T26 · No measured idle scene is added for the heartbeat.** The idle bound's scenes (`e2e:daemon-idle*`) run private daemons, where the page is off, so one write of under 200 bytes every 10 seconds in the default daemon is in no measured scene. X4 fixes the interval, so a measurement could not change it, and what M1 and M3 pin instead is what could regress unseen: a daemon that serves no page loads nothing for it, and one that serves loads its chunk only at the first request. A measured scene would catch a heartbeat that grew expensive; this does not.
- **T27 · The gate drives Chromium; Safari and Firefox are checked by hand at M5**, on the Mac, each through pairing, a sheet, a Send and a reload. Nothing in the page is specific to one engine (T21), and the gate's runners have no Safari.

## The page server, as an attacker meets it

The composite names whom the page defends against (§8.2: web content and other hosts) and whom it does not (a process running as the same user). This table takes each of them in turn, says what each can send, and names the rule that refuses it and the test that sends it. "Rule 1" to "rule 4" are §8.2's four, in its order: the credential in origin-scoped storage and a header; the Host on everything, the Origin on writes and the live connection; the three headers and the content policy with the Markdown's limits; a body as plain text or a raster image. Rows marked in bold are not stopped by the four rules as first written. Three of them are stopped or narrowed by something this child builds, which the composite's writer has taken as sentences of the composite (the framing directive; the bind on both loopback addresses; the server's proof). What is left of them, and the two rows not stopped at all, are stated as limits. All are in the last section (entries 2, 4 and 7).

**The start.** `start()` decides in this order and stops at the first that holds: not this daemon's to serve (T2: read from its own environment and the constant, and, only when those say yes, from the login shell's), `off`; no `index.html` in `bundleDir`, `no-bundle`; a bind refused as in use, `port-taken`, tried again every `portRetryMs`; else `listening`. A bind is `127.0.0.1` first, then `::1` on the port the first got (with port 0 the pair is tried again, a few times, if the second is taken), each `exclusive`, the second `ipv6Only`; T3 says when one address is enough. Each change of state is one log line.

**The two HTTP servers** (T1). One `http.Server` for each address, made by `serve.ts` with the same listeners, each listening itself, so that Node's own deadlines run: an HTTP server starts the check of its header and request deadlines when it listens, and one handed sockets it did not accept never does. Their settings, which are the page server's limits, since it is a listener any program on the machine can reach:

    headersTimeout 10 s    requestTimeout 30 s    keepAliveTimeout 5 s    connectionsCheckingInterval 1 s    maxHeaderSize 16 KiB    requireHostHeader false
    HEADERS_MAX = 64, with server.maxHeadersCount = HEADERS_MAX + 1
    CONNECTIONS_MAX = 128, counted across both servers at 'connection'; one past it is destroyed

- **The deadlines are checked every second.** Node checks the header and request deadlines of its incomplete requests only on a timer whose default is 30 seconds (`connectionsCheckingInterval`), so a header deadline of 10 seconds is enforced somewhere between 10 and 40 seconds unless the interval is set; the page server sets it to one second, and `timing` shortens it with the deadlines it shortens (seen at the controller's pre-flight, 2026-11-24, on Node 22: a stalled request under a 300 ms `headersTimeout` was answered 408 at 305 ms with a 100 ms interval, at 1004 ms with 1 s and at 5004 ms with 5 s, so at the first check after the deadline).
- **A request with more than 64 headers is refused, 431, before anything reads a header.** Node's parser stops collecting header pairs at `maxHeadersCount` and says nothing, so a list of exactly that length may be a cut one, and a check that looks for a second `Host` or for an `Origin` in a cut list finds neither. So the parser is told one more than the bound, and a request or an upgrade that arrives with more than `HEADERS_MAX` pairs in `rawHeaders` is refused whole. The three checks then only ever read a list that is complete.
- **No answer leaves without the standing headers.** `requireHostHeader` is off so that a request with no `Host` reaches the Host check and gets its 421, not the parser's own 400. `clientError` (a malformed request, headers past their size, a deadline passed) is answered by `headers.ts`'s refusal and the socket ended. `checkContinue` and `checkExpectation` are answered 417 the same way: the page server takes no `Expect`. A request that arrives while the chunk cannot load is answered 503 the same way, and the next request loads again.
- A request or an upgrade that arrives while the chunk is loading waits for it; the deadlines above still run, since the servers own their sockets.
- A body: at most 1 KiB for a code, 8 MiB for a Send, 5 MiB for an image, each refused with 413 as soon as it is known to pass; `GET` and `POST` only; `OPTIONS` is 405, so no cross-origin request that needs a preflight is ever allowed; no compression.
- The live connections: at most 32, and at most 8 that have not yet been paired on the connection; frames of at most 4 KiB; a ping every `pingMs`, and a connection silent for `silentMs` is ended. An upgraded socket has left HTTP's deadlines, so the opening has its own: `helloMs` for each step of §L's opening.

**In `startDaemon`.** The page is created with the daemon's other parts and started after `clocks.served()`. `daemon.ts`'s spine `onState` tells it each state. Its `stop()` runs in the exit order right after the listeners close, before the endpoint's, so no session is offered a page that is going. `daemon.status` gains `sheetPage`, added as `render` and `artifacts` were:

    DaemonSheetPageSchema = { state: string, detail: string | null, url: localOnly(string | null), browsers: number | null, connections: number | null, registered: boolean }

`detail` is one sentence and holds no path; `browsers` and `connections` are null until the chunk has loaded, since a status reads no file and loads nothing. `mawsd status` prints one line from it: `sheet page: http://sheet.localhost:47590 (2 browsers paired, 1 open)`, or `sheet page: not served (the port is in use)`.

**The test launchers** (T2). `launchEnvironment` in `e2e/support/scratch-env.ts` returns `MAWS_SHEET_PAGE: '0'` and no `MAWS_SHEET_PORT`, whatever the runner's environment holds; `test/support/scratch-env.test.ts` pins it. `test/support/remote-bench.ts`, which builds its daemon's environment itself, does the same; M1's sweep found no other launcher that starts a `mawsd` from an inherited environment. A suite that starts a daemon in its own process (`startDaemon`) gives it an environment it built, never the runner's whole.

**As built in M1** (each a decision of the milestone, reviewed):

- **The bind decision is committed before anything is served.** A connection that arrives on the first listener while the second bind is pending is dropped and loads nothing; a stop during the pending bind closes the provisional listener (T3).
- **The commands' reach by state.** `pair` only in `listening` (T8). `browsers` and `unpair` read and change the browsers' file in every state but `stopped`, loading the chunk on demand, so a browser can be unpaired while the port is taken or the page is off; in `stopped` they answer `[]` and `{ removed: 0, saved: false, why: 'stopping' }`. Each rechecks the state after the chunk's load, so a stop that lands during the load mints no code and writes nothing. An idle start with no command and no request still loads nothing.
- **Status reads no file.** `daemon.status.sheetPage.browsers` is counted in memory: null before the chunk has loaded and while the browsers' file cannot be read.
- **The timer's tick** (an owed save retried, T10; from M3 the heartbeat, gated on `listening`) starts when the chunk loads, not when the page starts listening.
- **The live connection.** The upgrade is checked before `ws` sees it (`Upgrade: websocket`, version 13, a well-formed key, no subprotocol) and refused 400 with the standing headers, so `ws` never writes an answer of its own; the 101 carries the standing headers; past 32 live or 8 unpaired, 503 at the upgrade. A server-initiated close ends the socket one second later (`CLOSE_GRACE_MS`) whether or not the peer answers, since `ws` otherwise holds it 30 seconds. In M1 the spine's state is said (`unavailable`, `why: 'refused' | 'yielded'`) only on paired connections and only for those two states; a stop closes 1001.
- **An aborted body is not an empty one.** A request whose body was cut off changes nothing and is answered nothing; a parser error after a response's headers were sent destroys the socket and writes nothing.

**As built at C4a's branch review** (its fix wave, 2026-11-27):

- **A static file's bytes are held once.** Each file of the bundle's table is read at its first request, single-flight, and every later request is answered from that one buffer; a failed read is not kept. A daemon that serves no request holds nothing, and one that has served a page holds up to the start's size for its life.
- **A response its peer stops taking is ended.** A connection with bytes queued that has neither emptied its queue nor drained for `stallMs` (10 s, checked every `checkMs`) is destroyed and logged, which frees its slot; this covers upgraded sockets too, so a stalled live peer is ended sooner than `silentMs`. Bodies are written as 64 KiB views of the one buffer, the next after `drain`, so a peer that reads however slowly shows progress. Progress is judged per slice, not per byte: a peer that takes less than 64 KiB in 10 s is ended, a rate no browser on loopback meets (the review's finding, dismissed as within the purpose).
- **A write checks its pairing again just before its mutation.** A `put` or an `upload` whose body was still arriving when the browser was unpaired is answered 401 and reaches no service.
- **The holders are kept fresh while a page is open.** One timer runs while a paired live connection is open, every `refreshMs` (30 s): each ready connection gets a quiet snapshot by the same steps as §L's, and `ready` is sent only when the list or the door differs from what that connection was last told. Through the discovery wake's own cache the effective period is up to about a minute. A failed quiet refresh says nothing; the client's own `list` retry (T15) covers the next one.
- **The proof's MAC covers the origin** (§L's message): a daemon serving one port proves nothing to a tab of another. `prove` takes the origin, and the page's live client takes `origin` (its `location.origin`).
- **A remote `daemon.status` drops the page's address** inside the optional `sheetPage` object, as it drops every local-only field.

### §L · The three checks, request by request, and the opening of the live connection (M1; the sheet's routes M3)

`checks.ts` is pure: a request's method, target and raw headers in, a refusal or a route out. The order is fixed, and each check runs only if the one before passed: **the count of headers (§J), then Host, then the route and its method, then Origin, then the credential, then the body.**

    export function pageOrigin(port: number): string                                       // http://sheet.localhost:<port>
    export type Refusal = { status: 400 | 401 | 403 | 404 | 405 | 408 | 413 | 417 | 421 | 429 | 431 | 500 | 503; body: string }   // body: one of a fixed list of sentences
    export function hostPasses(rawHeaders: readonly string[], port: number): boolean       // exactly one Host header, equal to sheet.localhost:<port>, case folded; nothing else
    export function originOf(rawHeaders: readonly string[], port: number): 'absent' | 'page' | 'other'   // 'null' and a repeated header are 'other'
    export function bearerOf(rawHeaders: readonly string[]): string | null                 // the one Authorization header, scheme Bearer; two are none; never a cookie, never the target
    export function routeOf(method: string, target: string): Route | Refusal               // a target that is not origin-form (it does not start with '/') is refused

Every check reads `rawHeaders`, which keeps each header as it came; Node's parsed `headers` keeps one of a repeated `Host` or `Authorization` and drops the rest.

| request | Host | Origin | credential | answers |
|---|---|---|---|---|
| `GET /`, `GET /s/<anything>` | required | not read | none | the shell: the same bytes whatever follows `/s/` |
| `GET <a path of the bundle's table>` | required | not read | none | the file |
| `POST /api/pair` `{ "code" }` | required | **the page's** | none: this is how one is had | 200 `{ id, credential }`; 403 `{ why, left }`; 429; 503 `{ why: "not-saved" }` |
| `POST /api/unpair` | required | **the page's** | required | 204; 500 `{ why: "not-saved" }` (T10) |
| `GET /api/sheets/<session>` | required | the page's, or absent | required | 200 `{ model, door }` (§N) |
| `GET /api/sheets/<session>/body?…` | required | the page's, or absent | required | 200 with one of five types; 404 (§N) |
| `POST /api/sheets/<session>/put` | required | **the page's** | required | 200 `SheetPutResult` |
| `POST /api/sheets/<session>/uploads` | required | **the page's** | required | 200 `{ ok, path }` or `{ ok: false, why }` |
| `GET /live`, upgrading | required | **the page's** | on the connection, after the proof | 101, then the opening below |
| anything else | required | | | 404; a known path with another method, 405 |

A refused Host is 421, a refused Origin 403, a missing, malformed, repeated, unknown or revoked credential 401, each with its constant sentence as `text/plain` and every header of §M, with `Connection: close` and `Cache-Control: no-store`; Node's own request deadline is answered 408 the same way. The Origin is compared exactly, with no case folding: only the Host is folded. As built in M1, the routes the table leaves open: any method but `GET` and `POST` is 405 on any path (`OPTIONS` and `HEAD` included), and a `POST` to a file's path is 405; an unknown path under `/api/` is 404 (M3 adds the sheet's); a target that is not origin-form is 400; an upgrade to any path but `/live` is 404, and `GET /live` without an upgrade is 400. An `Expect` is answered 417 before the Host check (Node's `checkExpectation`), which tells a stranger nothing, the body being a constant. Files are `no-cache` with an ETag of size and time, answered 304 on `If-None-Match`.

**Rule 2, read for a browser.** The composite's rule asks for the Origin "exactly the page's" on every write and on the live connection, and a browser sends one on every `POST` and every WebSocket handshake, so those require it. A browser sends none on a same-origin `GET`, so a read cannot require one; it requires the credential, and refuses an Origin that is present and is not the page's. A navigation carries none, and the shell and the pairing screen stand on the Host check alone, as the rule says.

**Rule 1, read for the page.** "Everything that reads or changes a sheet requires the credential": every path under `/api/` but the exchange, and the live connection before it is sent anything of a sheet. On the live connection the credential is the tab's second message and not its first, by the composite's writer's ruling (T28): the first asks the server to prove itself.

**The opening of the live connection** (T28). One JSON object a frame, text frames only.

    1. tab → server      { "t": "hello", "v": 1, "id": "<the browser's id, 8 hex>", "nonce": "<43 characters of base64url: 32 bytes from crypto.getRandomValues>" }
    2. server → tab      { "t": "proof", "mac": "<base64url of HMAC-SHA-256( key: that browser's proof key, message: PROOF_MAC_LABEL + "\n" + origin + "\n" + id + "\n" + nonce )>" }   origin: the page's origin the daemon serves (http://sheet.localhost:<port>); the tab uses its own location.origin
                         or, for an id it does not know: close 4401
    3. tab               makes the same MAC from its credential and compares. Not equal, or anything else, or nothing within helloMs: it closes, sends nothing more, and tries again later
    4. tab → server      { "t": "credential", "credential": "…" }
    5. server → tab      { "t": "paired" }, or close 4401
    then, in M1:         { "t": "unavailable", "why": "no-service" }          from M3: §N's messages

    close codes:  4401 the browser is not known, the credential was refused, or a step did not come in time; 4403 this browser was unpaired while connected;
                  1008 the tab sent something this opening does not have; 1001 mawsd is stopping

The server answers one hello a connection and sends nothing before it. The credential of step 4 must be the one of the browser the hello named; another browser's is closed 4401. A tab holds a connection **proven** from step 3's check until that socket closes, and `src/api.ts` asks that before every request that carries the credential (§P).

### §N · Sheets through the page server (M3)

**C3's service, in process.** `SpineRoot` (`src/services/spine-root.ts`) carries `sheet?: SheetService`, set where `startSpine` makes the service and absent in a run refused the spine; C3's first landing exposes it at this child's request.

A request for data that meets `SheetsUnavailable` is answered 503 with `{ "why" }`; the shell, a static file, the pairing and the opening of the live connection never call it, so an unpaired link loads and a browser pairs whatever the spine's state. The page server passes a session's name on as the path gave it, decoded once: C3's service is the boundary that holds it to the engine's id form and confines every path (the composite's inheritance for this child). **The service never refuses by throwing; it answers its own negative value, and the page server passes it on**: a `read` of a name the service does not hold is `{ model: null, door }` with 200; a `put` it refuses is a `SheetPutResult` of `{ ok: false, why: 'refused', message }` with 200; an `upload` it refuses is `{ ok: false, why }` with 200; only a `body` that is `gone` is 404.

**The routes.**

- `GET /api/sheets/<session>` is `service.read(session)` and `service.door()`: `{ "model": SheetModel | null, "door": DoorState }`, as C3's `sheet.read` answers a window. That nothing is located or run before a record with something on it is read is the service's own rule.
- `POST …/put` takes `{ "lines": SheetLine[] }`, **sets `by: 'page'` on every line whatever the browser wrote**, and answers `service.put(session, lines)` as it stands; it adds no check of its own on the lines, since the service holds each to the surface's inbox line (`SheetLineSchema`: `answer`, `dismiss` or `retract` only, no other field) and refuses an `inbox.jsonl` that is a link or not a regular file, both with its `refused`: a `SheetPutResult`, whose `results` are `SheetPutEntry` objects, each `{ key, state: 'queued' }` or a verdict by its name with the verdict's own fields. The fifty-line bound and `lineError` are the service's own, at its own boundary (C3's §C).
- `GET …/body?ref=<sha256>`, `?upload=<name>` or `?text=<sha256>` is `service.body(session, of)`, an `upload` asked as `{ upload: 'uploads/<name>' }` (the service's request carries the directory): a `text` body goes out as `text/plain; charset=utf-8`, an `image` (`{ kind: 'image', mediaType, data }`, base64) as its bytes under its media type, which is one of the four, and `gone` as 404. This is rule 4: "it is sent as plain text or as a raster image type, never as HTML or SVG." The service answers an `upload` for any regular file under the record's `uploads/` whose name the line's schema allows, so a draft's own image can be read back.
- `POST …/uploads` takes the image's bytes as the body with one of the four types as its `Content-Type`, holds them to 5 MiB, and answers `service.upload(session, { mediaType, data })` with `data` in base64; the service checks the decoded bytes against the type's signature, bounds them at 5 MiB itself, and writes `uploads/maws-<32 hex>.<ext>` whoever uploads.

**The live connection, once paired.** After §L's `paired`:

    server → tab     { "t": "ready", "v": 1, "sessions": SheetSummary[], "door": DoorState }      a snapshot
                     { "t": "changed", "session": "<id>", "summary": SheetSummary | null }         one a change, after a snapshot
                     { "t": "unavailable", "why": "refused" | "yielded" | "exiting" | "no-service" }   no snapshot can be had now, or the spine left `loaded`
    tab → server     { "t": "list" }                                                              asks for a snapshot again; one sooner than a second after the last is ignored

For a snapshot the server takes its hold (T15, once a connection), has the service (which loads the spine, which the wake needs), awaits `discovery()` (T29), subscribes the connection to `sheet.changed` (through `onEvent`, owner `machine`; once a connection), and only then calls `service.list()`, so a change during the list is delivered after the snapshot and none is lost. `SheetsUnavailable` at any of it is `unavailable`, and the connection stays. **A spine that leaves `loaded`** is said as `unavailable` (`why: 'no-service'`) and ends every snapshot then in flight: each connection carries a generation, a list that answers for an older one is dropped, and no `changed` is sent until a fresh `ready`. The first snapshot is made at `paired` without being asked for.

**As built in M3.** The sheet's routes are their own chunk file, `sheet-routes.ts`. A `put` whose body is not JSON or holds no `lines` array, and an upload whose `Content-Type` is not one of the four, are 400. A request already aborted when it is dispatched (a client gone while the chunk loaded) takes no hold and is answered nothing, and every path that takes an operation's hold releases it. One timer runs the heartbeat and the owed save of T10. The suites reach the page's client helpers in `test/support/sheet-page-client.ts`, and `DaemonOptions.sheetPage.sheets` is a seam that M1's suite fills with the refusing stand-in. `sheet.changed` is one of `MACHINE_EVENTS`, with the payload `{ session, summary }` the `changed` message carries.

**The stand-in door in a suite** (C3's §E: `test/support/fake-sminos-cli.mjs`, `test/support/sminos-barrier.sh`). The service runs the command with the login shell's environment and the sminos home (`src/services/sheet/locate.ts`), so a stand-in's knobs (`FAKE_SMINOS_*`) reach it through the captured login shell, which inherits the daemon's environment; under a test runner the locator reads `MAWS_SMINOS_CLI` alone. `put` locates the command every time, through a cache of the commands already proven, and `read` locates it behind its answer while the door is not known to be available.

Before the first `paired`, a tab that holds a credential shows the bare ground; M4's band is what speaks there after a second. 4401 and 4403 read `unpaired`: the pairing screen shows, **nothing stored is deleted** (T19), and the client goes on trying with what is stored, so a tab that a stranger on the port sent to the pairing screen returns by itself when `mawsd` has the port again. `unavailable` reads so, and the client asks again (`list`) after 5 and then every 10 seconds. A tab hidden for five minutes closes its connection and one shown again opens it.

**The page's lazy chunks are gated as its requests are (T28).** No dynamic import leaves the page while `proven()` is null: the page owns the gate, handing the Markdown stack a loader (or wrapping its lazy entry points) that asks `proven()` first. A chunk whose load failed is retried on the next proven connection under a fresh specifier (`?again=N`, which the page server's table lookup ignores), since Chromium keeps a failed module failed for the page's life. **As built in M4:** the page's Vite build rewrites every dynamic `import()` of a chunk (Rollup's `renderDynamicImport`) into a call to the page's gate (`src/chunk-gate.ts`), which waits while unproven, lets the waiting loads through at each `paired`, and counts a failure against the connection the try was made on; Vite's dependency preloads are off (`build.modulePreload: false`). **A gated chunk names, through static imports, only modules already in the page's load**: every module two or more gated chunks share is folded into the startup chunk, since Rollup copies no module into two chunks, so no fetch follows a gated load past the gate, and `src/shell.test.ts` reads the built graph and fails on any gated chunk that imports outside the startup set. **As built at C4a's branch review** (its fix wave, four rounds of its task review, 2026-11-27):

## Plan of Work

Five milestones in two landings. M1 is the page server with its three checks, the pairing and the opening of the live connection, and waits on nothing: it reads no sheet. M2 is the page's shell in a browser, and waits on M1. M3 puts sheets behind the checks and writes the registration; M4 puts them on the page; both wait on C3's first landing. M5 is the live gate and waits on C2's terminal side. M2 and M3 are independent of each other.

### M1 — The page server: who is let in

**At its end.** A `mawsd` started with `MAWS_SHEET_PAGE=1` over a directory that holds a bundle listens on `127.0.0.1` and `::1`, answers the shell to a request whose Host is the page's and refuses every other, pairs a browser through a code that `mawsd sheet pair` prints, proves itself to a paired browser on the live connection and takes its credential there. What the work found that the document had not:
- **Node's deadlines run on a timer** (`connectionsCheckingInterval`, 30 s by default). The page server sets the timer to 1 s.
- **A deferred `import()` of a builtin is refused by the guarded-entry rule.** `node:http` is reached through `process.getBuiltinModule`.
- **The discovery wake resolved before the index had folded the registry's holders.** Right after a daemon start, a held session read stopped. A second signal now serves the wake only, so nothing the app waits on moved.
- **C3's components landed differently from the plan** in places, and §N and §P were rewritten against the code:
  - every memory change is an update;
  - drafts are compared by identity;
  - a per-window registry decides whether a Send is in flight;
  - the foot belongs to `SessionSheet`;
  - the refused link was already built.
- **A module that fails to load stays failed for the page's life** (Chromium). So the workspace is part of the page's own load, and the Markdown stack's lazy chunks pass through a gate on the proven connection.
- **A gated chunk's static imports were a second way past that gate.** The fix makes every gated chunk self-contained, at a start of 6.18 MB.
- **T19's two-tab memory needed more than "write only your own difference".** C3's `reconcile` prunes and rewrites from the model a tab holds, and a tab can hold an older model than another tab wrote against. So a tab writes `reconcile`'s changes only against a model read after its last adoption, from the view's own snapshot, entry by entry.

What the reviews were worth: every fix round found a real defect at a lifecycle or concurrency edge, none of them visible on the happy path. In the server: a bind not yet decided, an aborted body, a revocation not saved, a stale snapshot, a stranded hold, a registration that could hold the daemon's exit. In the page: a bearer that was never proven, a gap between `paired` and `ready`, a stale tab pruning another's draft. The browser suite judges a stranger's tries from the wire and the record.
