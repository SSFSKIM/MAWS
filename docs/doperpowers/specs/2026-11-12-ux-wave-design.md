## Purpose

The owner uses MAWS every day to supervise Claude Code sessions, and has kept a list of what gets in the way: marks on a comparison of MAWS with Claude Desktop, later observations with screenshots, deferred board tickets, and findings from P5's sittings. 240 items in all. Some were already built, some asked for the same thing twice, some contradicted each other, and some named a problem without a settled answer.

This wave turns that list into changes the owner can see, under the owner's own bar: **every change a clear improvement, nothing hasty.** A change is made only when the code shows what is wrong and the direction of the fix is settled, by the owner's words, by Claude Desktop's behaviour where the owner named it as the answer, or by a question put to the owner. Where none of these holds, the item waits for an answer, a design round or a hands-on check, and this document says which.

After the wave: requests for the owner's attention are drawn where the work is and stop counting once answered; the transcript reads as the agent produced it, with tool runs folded into one line and the to-human view drawn by the mod; what arrives in a session from elsewhere takes one line; the composer queues and steers on Claude Desktop's model, with the departures U4 names (among them the hold after a Stop, and what Esc does); Review, comments and source control are one simpler flow; a session on another machine can be forked, renamed and archived from this Mac, and an act that cannot reach it says why; and the smaller defects in each surface are gone.

How to see it working: the owner's sitting on the wave's build, following the scene script composed from the children's acceptance (Parent-level acceptance, 2).

## Design

### The wave's laws

These bind every child. [binding: they are the owner's standing positions and rulings, and each child would otherwise re-derive them differently]

1. **Claude Desktop is the benchmark** (charter D-14 and D-20 as amended 2026-11-12): where an item follows engine behaviour or a basic surface, it is built the way Claude Desktop `app-5.1231.2` builds it, read in its source and cited as `research/SOURCES.md` prescribes. The Claude Code CLI `2.1.322` is the reference for how the engine itself words and delivers things. An item that departs from Claude Desktop on purpose says so and says why.
2. **A pure mods client.** MAWS draws what the engine and the user's mods produce, and adds no drawing of its own in their place. Where no mod can draw (law 5), MAWS mirrors the mod's rule and says which rule it mirrors.
3. **Less on screen.** A row, a label or a card that does not earn its space goes. No setting is added where one behaviour serves.
4. **No complexity for a small gain.** When the grounding found an item larger than it reads, the item's section says so and the cheaper route is taken unless the owner asked for the larger one.
5. **Three routes, one behaviour.** A session reaches the window by one of three routes, and many of the wave's defects exist on one route only. Every item that touches the transcript, the requests or the composer states what it does on each route, and "not on this route" needs a reason:
   - **a session MAWS runs** (in code: lane B): MAWS launched the engine headless and drives it over its wire through the engine host; the user's mods can draw here.
   - **a terminal session** (lane A): the engine runs in a terminal; MAWS watches it through the sminos bridge and reads its transcript file. No mod draws here.
   - **a session on another machine**: either kind, reached over the machine link through that machine's daemon (`mawsd`); drawn from transcript rows. No mod draws here.
6. **The engine is not guessed at.** A claim about what the engine sends is verified against `spikes/protocol-probe/fixtures/` or a new probe on engine `2.1.322` before code depends on it (CLAUDE.md, working rules). The children name their probes.
7. **Visual language is not this wave's.** Rounder geometry, materials and colours are being designed elsewhere and come after. A child uses today's tokens and shapes; an item that is only visual language is handed to the renewal.
8. **Keep means keep.** A child that would change a behaviour the owner marked `keep` stops and reports.

### Words used in this document

- **Request:** something a running session needs from the person before it can go on or finish: a permission prompt, a question (the engine's AskUserQuestion, MAWS's own ask tool, the sminos ask tool), a plan to approve, an engine dialog or an MCP server's form. In code a request is an *attention item* (`src/shared/attention/`). The cards that are steps of a send (trusting a folder, a relay that is down, a start that failed) are not requests: they keep the composer's place and UC-1 does not count them.
- **Arrival:** anything that enters a session other than the person's typed prompt: a message from another session or a subagent, a background task's notification, a scheduled trigger, an answer to an asynchronous question, a slash command's output.
- **Tool run:** consecutive tool calls with no text between them, drawn as one group.
- **The to-human view:** the report the to-human mod draws: the agent's messages to the person, with the work between them folded under "working record".
- **Card column:** the column of cards that floats over the right of the main area beside the transcript (Environment, Context, Connectors and others; UC-9). **Side surface:** a tool opened beside the transcript (Review, Files, Terminal, Browser, Source control). **Main tabs:** the tab strip over the main area. **Destination:** a page that replaces the main area without being a tab (Customize, Projects, the Artifacts library; UC-12). **The Settings dialog:** Settings, opened over the window, over the tabs or over a destination; not a tab either (UC-12).
- **The machine link:** the connection from this window to another machine's daemon; an *offer* is an act that machine accepts over it (`src/endpoint/offers.ts`).

## Cross-child contracts

Each contract names its owner (the child whose landing defines it) and the children it binds. The statement here is what every child may rely on; the owner's file carries the full content (types, tables, wording), and the others code against it and do not re-decide it. Where a child's file and a statement here differ, the statement here binds and the difference is reported to the wave's architect.

**UC-1 · A request waits only until it is answered.** Owner U1; binds U2, U3, U7, U8, U9, U10, U12, U13. A request counts as waiting, everywhere it can show (its own drawing, the session's row and tab, Needs you, badges, notifications, the counts told to another device, the feed another machine reads), only until the person answers it. Once answered it raises nothing, whether or not the engine has yet confirmed the tool's first frame. The predicate is `waits(item)`, true only for a `pending` item, in `src/shared/attention/kinds.ts`, with `waitsOnAnswer` beside it; `isOpen`, which counts an answered and unconfirmed request as open against charter §4.6, is removed. The attention service publishes only waiting items, so a machine on an older build that reads the feed is right too. U1 also gives the predicate by tool-use id (for U2's runs) and by agent (for U8's "Approval needed"). On the terminal route an item stays `pending` until the bridge reports it settled, and "answered" there means the bridge accepted MAWS's answer; U1's file states the route's rule. Where a session is shown without its transcript (the chat over an artifact folded to its bar, or hidden; U10), a waiting request is not drawn there: one line, "Waiting for you · N", opens the conversation, and "Show chat" carries the mark. No child adds a second definition of "waiting".

**UC-2 · One reading of every arrival.** Owner U3; binds U1, U2, U4, U8, U9. One pure reader, `readArrivals(row)` in `src/shared/engine/arrival.ts` (and `readNext`, the same reading in order, which reads an arrival with two carriers once), classifies what enters a session other than the person's typed prompt. Its input is the raw wire frame or transcript row, never an X1 event: X1 lowers the origin to one word, and what proves who sent a row is on the raw row alone. That proof is the origin object, with one exception: the engine gives a scheduled trigger no origin object on any route, so that class is read from the fields the engine writes in its place (`turnOrigin: 'scheduled'` on the file's row, the terminal's `scheduled_task_fire` row, and on the live wire the `command_lifecycle` frame whose `wakeup_source` is `schedule_wakeup`). Three callers use it: the engine host's normaliser for the live wire, the transcript-file backfill, and the reader that serves a terminal session on another machine; a session MAWS runs on another machine arrives as events its own engine host made, so it is right once that machine runs the wave's build. Classes: a peer session's message; a subagent's message or hand-back; a background task's notification, by outcome, and one with no outcome (a monitor's event, a check-in); a scheduled trigger; the sminos bridge's own wake prompt; an answer to an asynchronous question (with the call's id and the answer in words, or "dismissed"); MAWS's own consent message for a call auto mode blocked (`consent`, the one line of U1's "Approve and retry"); a slash command's output; the person's own steer delivered by a fallback route, which stays the person's. The reader classifies; where a delivered row is placed stays with each caller. The class reaches the window on the existing companion events and one optional field, `arrival`, on X1's `user.message`: an amendment of X1, recorded in the charter when U3 lands. Arrivals are drawn one line each, in the CLI's wording, and the divider row gains `opener`, the class of what opened the turn. U1 fills a question's row from the answer class; U4 words a waiting answer from it; U2 reads the classes for the to-human fold and names a turn from `opener`; U8 relies on the arrival's line (the task notice, or the report line of an agent that handed back) as the trace of work that left its card.

**UC-3 · The transcript's model has one writer at a time.** Owner: the wave's architect; binds U1, U2, U3 and the children that insert. `src/renderer/src/transcript/model/` and `transcript/view/` are changed by three children in this order: U3 lands its reader and arrival rows first; U1's placement and U2's grouping start from a master that contains them. U3 owns the arrival and message rows and `transcript/view/Transcript.tsx`; U2 owns `groups.ts`, `classify.ts`, the group row, the turn line and `src/renderer/src/owner/`; U1 owns the question, ask and plan rows, the region at the transcript's end, and the waiting state of a call's row and of the jump button. Rules between them:
- A row that holds a waiting request (a question's, an ask's or a plan's form) ends a tool run, is never inside a fold (a run's, a turn's, the to-human view's working record), and asks no mod's site while its request waits.
- A call that waits for the person's permission stays in its tool run, and the run stays as the reader left it: a request neither opens nor closes it. While the call waits, its row reads "Waiting for approval", and so does the line of a folded run that holds it, in the warning tone (U1's l4-approvals-04; U2's A3 and A4); the prompt is answered at the card at the transcript's end. This is how Claude Desktop's default transcript renderer treats a group with a call awaiting approval; the renderer Desktop offers behind a server gate draws the group open while a step waits, and that rule was not taken (Decision Log, 2026-11-12, "A run is not opened for a waiting call"). In the to-human view, mod-drawn or mirrored, a run inside a folded working record stays folded with it, and the card at the transcript's end is the request's whole drawing. An allowed call is then an ordinary member of its run; a denied call is a row of its own.
- In a session whose mods surface is attached, U3's arrival rows ask the engine's `UserMessage` site and its sent-message row asks `ToolUse`, with the engine's props, so that a mod can fold or draw them as it does in the terminal; a mod that keeps the engine's drawing leaves MAWS's line.
- A row that folds still opens under the store's `jumpTo`, which find, the prompt chords and the waiting-requests card use. Where MAWS owns the fold (a run, a turn, the mirrored to-human view) the jump opens it. Where the mod owns it, MAWS can neither read nor change the fold, so the jump's target is *revealed*: `jumpTo` records it, and while it is revealed MAWS asks no site for it and draws it itself (U3 writes the set, U2's site asks read it).
- Insertions by other children are single rows or filters, rebased onto the last landing: U4's view-level filter that removes the held tail (`TranscriptSlot.tsx`); U5's user row that draws several anchored comments in one message; U10's third action on the `artifact` row; U9's two insertions in `Transcript.tsx`; one string each from U9, U11 and U12 in `transcript/model/copy.ts`.

**UC-4 · The session's working folder.** Owner U8; binds U1, U5, U6. *The working folder* is the checkout the agent's main loop is working in now: the launch folder until the engine's own record shows that the main loop moved into another worktree of the same repository (through the engine's worktree tool, which is Claude Desktop's rule, or by a `cd`, which U8's probe of 2026-11-12 showed the engine records: the first row of the main transcript after any move carries the new folder), then that one. A move inside a checkout, a subagent's move and a move into another repository do not count. One selector answers it: `workingFolder(record)` in `src/shared/sessions/working-folder.ts` and `useWorkingFolder(appSessionId)` in the renderer. Review, Source control, Files, a terminal's starting folder, "Open in" and the Environment card read it; none reads `record.worktree?.path ?? record.directory` itself (21 lines in 20 files do today), and a test keeps it so. What is about the record and not about where the agent is (the archive and delete dialogs, the Resume picker, the index's writes) stays on the record. The Files tree's roots are not such a reader: the tree keeps every root it has today (the launch folder, the added folders, the worktree) and the selector only says which one the agent is in. Two landings: the selector with today's behaviour, first and alone, so that U5 and U6 branch from it; then the live signal, which is the folder of the main transcript's newest row. The branch shown for the working folder is the one git reports there, for the card and for the record's label alike: the engine's rows keep the launch checkout's branch after a `cd`. A `relocated` row is never read as the working folder, and the record's launch folder stops moving on one once the working folder exists. The second landing also widens the folders a session's files may be read from (`recordDirectories`, `src/services/files/allowlist.ts`, `src/endpoint/targets.ts`), because Files and Review must read where the agent is: that is a security boundary. Its bound: the one folder added is a registered worktree of the launch repository that the engine's own record names for the main loop, passed through the checks every root passes today (the real path, the session's scope, and the rule that a caller on another machine never gets the machine's home as a root); a folder read from a transcript is never trusted without them. The landing takes the review panel with a reviewer on that boundary.

**UC-5 · One comment card.** Owner U5; binds U3, U4, U9, U10, U12. A comment on a document, an HTML page, a diff in Review or a page in the in-app browser is written in the same card with the same draft model. The card has one destination control, a "Send to main" checkbox: unchecked by default, ticked by default in Review and for a session started blank for the comment, and ticked and locked for a session on another machine until a side thread can be opened there (UC-7). Unchecked, the comment opens a side thread. A ticked comment is sent through the composer's own send path (`sendToSession`), which is what makes comments work for terminal sessions and sessions on other machines; `side.sendToMain` is retired. Several comments made in one pass are sent together on Review, the in-app browser and HTML pages; documents, decks and designs stay at one unsent comment per artifact. A draft survives the card closing, except the person's own Close, and does not survive a relaunch. After a send to main the card's place says "Sent to <title>", and a composing card says which session receives it when that is not the one on screen.

**UC-9 · What the card column holds.** Owner U8; binds U1, U4, U7. The column floats over the right of the main area when a session's tab is active, no side surface is open, the person has not turned the cards off, and there is room. It is not drawn while a side surface or a destination is open, and no request, agent or task opens the column or one of its panels by itself (an agent's `show_pane` and the Browser's own opening are U12's and unchanged); so the waiting-requests card is an aid, and the jump button's mark (U1) is the signal that always shows. The cards, in order: Waiting requests (only while a request of the session waits, UC-1; U1 supplies the component through the slot `sessionCardWaiting`, U8 mounts it first); Environment (open by default); Context; Connectors; Subagents (only while an agent of the session runs); Background tasks (only while a background task runs). A card with nothing to show is absent, not empty. Artifacts is an entry of the title bar's "More surfaces" menu, not a card. The three cards that fold remember it per device under the layout key `cards.open`. While a `/btw` side chat is open, U4's card sits at the column's foot through a slot U8 gives; when the column is not drawn U4 places the card over the pane's corner. A session with no record in this window has only the three conditional cards.

**UC-10 · Building and landing.** Binds all.
- **Base.** Every child branches from a master that contains the project registry's app branch (`registry-app`), which changes 54 renderer files including the sidebar, New chat and `sessions/actions.ts`. It landed on 2026-11-12 (master `1ed236bcb`, pull request #571); a child branches from that commit or a later one.
- **Where work happens.** A child is built in a git worktree on a branch `ux-wave/<child id>` (with a suffix where its section names several pull requests).
- **This MacBook.** No local typecheck, no multi-file eslint or vitest, and no local Electron on the owner's MacBook, at any load: one-file eslint and one-file vitest only. Typecheck, lint, the unit suite and the probes run on GitHub Actions through `scripts/ci-gate.sh <worktree>` (class 1a); Electron e2e groups run on a Mac under the load rule; a new or reworked e2e scene runs alone on a Mac before a final gate. An engine probe that needs a live engine runs off the MacBook: on another Mac, or, when it needs only the engine and its wire, on a cloud VM with the same engine version.
- **Review.** Each child's execution document gets an adversarial review before its executor starts. Each branch gets `doperpowers:review-code` before it lands: the panel (xhigh) for a branch of panel size or a delicate change, a single reviewer otherwise. Delicate by this document: UC-4's second landing, U10's early pull request, U6's route that serves a session's file to a frame, U13's reader of the stored layout, U9's offers.
- **Landing.** Nothing lands on master, and no build of the wave reaches the owner's machines, without the owner's word; the machines stay on build F until P5's verdict. A child's pull request is reviewed and landed by the session that keeps master (the P5 architect at this writing), by its gated merge: a merge commit built with `git merge-tree`, class 1a green on that exact tree, master unmoved, then the push.
- **The record.** A child's pull request carries the edits to the documents its items amend: each reversed ruling amended where it stands, dated, naming the owner's words (Decision Log, "Rulings reversed"), and each contract amended by a dated line (UC-15). At landing the register's rows are updated, and the board tickets and tracker rows the child closes are closed through the board scripts.

**UC-12 · The destination and the Settings dialog.** Owner U7; binds U6, U8, U10, U11, U13. Customize, Projects and the Artifacts library are *destinations*: pages that replace the main area beside the sidebar and are not tabs. Settings is not a tab either: it is a dialog over the window, over the tabs or over an open destination (the owner's answer of 2026-11-12, "As Desktop really does"). The layout store holds one `Destination` with `openDestination` and `closeDestination`, and, beside it, the dialog's state with `openSettings(section?)` and `closeSettings`. The open destination is stored under a layout key of its own and restored after a relaunch, because the relaunch that restores everything is the owner's `keep` (l7-shell-12); the dialog's state is held for the run only, as whether the Overview is open is. **UC-13 · The to-human advertisement.** Owner U2; binds U1 (for O-19). MAWS tells the engine's mods what it draws through the launch setting `MAWS_NATIVE_TO_HUMAN`, whose value is `TO_HUMAN_CONTRACT_VERSION` in `src/shared/owner/contract.ts`: 8 today. U2 raises it to 9 in the same change that removes MAWS's own drawing of the report for sessions it runs, and never before; from then a launch advertises 9 only when MAWS has decided that the mod draws that session's view, and 8 when MAWS will draw it itself. The mod's view (doperpowers `to-human`) draws on MAWS's surfaces when the value is 9 or more and steps aside for any other non-empty value, so build F, which advertises 8 and still draws its own report, is not drawn twice whenever the mod's change is merged. The mod's other readers do not change: the message tool registers at 8 and up; the notifier, the streaming hook and the sminos ask mod stay out for any non-empty value. MAWS decides at each launch who draws the view, from the mod's install record, and publishes it as `drawnBy: 'mod' | 'maws'`: the mod when the launch advertised 9 and the installed mod is the release that draws at 9 or a later one, MAWS everywhere else (a terminal session, a session on another machine, a session at rest, a session under an older mod). Because the number follows that decision, exactly one side draws in every combination of MAWS and mod versions, including a mod release that MAWS has listed as failing U2's probe; who draws is decided again after every plugin reload, from the launch's number and the release then loaded. So no MAWS work waits for the mod's merge. A later change of the ask mod's row (O-19) takes the next number of the same sequence.

**UC-14 · What the wave stores, build F can still read.** Owner U13; binds U6, U7, U8, U11, U12. Going back to build F after a trial of the wave's build is expected (UC-10), and F reads stored layout strictly: an unknown version makes it open default tabs and overwrite the file. So `main.tabs` keeps version 3 and its envelope, always written with one set under the key `none`; a stored value with several sets is merged into one strip on every read (U13's file gives the function). The same holds for every stored value F knows: F drops a tab of a kind it does not know and keeps a top-level key it does not know, but a value of a known kind or key that breaks F's schema fails the whole read (one such tab costs the saved strip; an unknown version of `regions` costs the sidebar's, the panel's and the Overview's stored layout).
