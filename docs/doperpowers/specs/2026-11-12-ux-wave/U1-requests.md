# U1 · Requests: permission prompts and questions

> **A child of the UX wave.** Root: `docs/doperpowers/specs/2026-11-12-ux-wave-design.md`. Read it first: it holds the wave's purpose, its laws (law 1 to law 8), the contracts UC-1 to UC-15, the ordering and the record. This file is this child's section of that document. Where this file and a contract's statement in the root differ, the root binds; report the difference. **Grain:** plan. Items are named by their ids in the register, `docs/doperpowers/evidence/ux-wave-2026-11/register.md`.

- **Purpose:** once this child lands, a request no longer takes the composer away, and it stops being announced the moment it is answered. A question's form is in the transcript where the agent asked it. A permission prompt is at the transcript's end, at less than half its old height, answered with one click or one chord, and the composer and Stop are there the whole time. A request that waits out of view is named by a card in the card column and by the jump button, and no side surface opens by itself. After an answer nothing goes on reading "Needs approval" or "Answered" while the tool runs, in this window or in one on another machine. A terminal session's asynchronous question behaves as one, and its answer shows on the question's own row. From a notification or the sidebar the person can deny any permission and allow a command or a read. A call that auto mode blocked can be approved for a retry from its own row.
- **Acceptance:** each on the routes it names (law 5): *runs* = a session MAWS runs on this machine, *terminal* = a terminal session, *remote* = a session on another machine.
  - **A1 · Answered means not waiting** (#358 with X-066, S-04, S-07; UC-1). In a mode that asks, the agent runs a command that takes a minute and prints nothing, and the person clicks Allow once. From that moment and for the whole minute: no card and no "Answered" line anywhere; the composer and Stop are there; the call's row reads as running; the session's row and tab read Working; Needs you does not list the session and the dock badge does not count it; a window on another machine that lists the session shows the same. Routes: runs; remote (answered from this window); terminal (the card leaves when the bridge accepts the answer); terminal on another machine, which is the ticket's case.
  - **A2 · A permission prompt** (l4-approvals-08, -07, -04, -02). The prompt is one card at the transcript's end, at most 200 px tall for a one-line command. The composer takes text and Stop stops the turn. The call's row reads "Waiting for approval: `cmd`" with no spinner or timer. There is no pointer row, and the words "Composer paused" appear nowhere. Routes: runs, terminal, remote.
  - **A3 · Keys on a prompt** (l4-approvals-02; UC-6). With the prompt in view and the composer empty, ⌘↩ allows once, ⇧⌘↩ gives the lasting scope the button names, Esc denies; each hint is on its button. With text in the composer, ⌘↩ is the composer's and the prompt stays. No key answers a prompt that is scrolled out of view or appeared less than 400 ms ago. Routes: runs, terminal, remote.
  - **A4 · A question from MAWS's ask** (l4-approvals-08 with l2-transcript-16, l4-approvals-07, O-17). With a file open in the side column, the agent asks a question. The form is in the row of the call; nothing appears above the composer; the side column still shows the file. Submitting turns the form into the answer lines. Routes: runs, remote.
  - **A5 · A terminal session's asynchronous question** (O-22). Its form is in the row of the call, the composer is free and the agent works on. The session's row, tab and Needs you read "Question waiting". Skip is disabled and says why. Routes: terminal, terminal on another machine.
  - **A6 · Its answer** (O-21). Answered in MAWS, and in a second run answered in the terminal: the question's row reads "header → answer"; no bubble holding the engine's framing text is drawn; after a reload the row reads the same. Routes: terminal, terminal on another machine.
  - **A7 · Finding what waits** (O-17, l2-transcript-10, l4-approvals-08). An asynchronous question is asked and the agent produces a screenful more. With the reader at the end, the card column shows "Waiting for you" with the question's line, and the jump button reads "Needs your input"; either one scrolls to the form and focuses it. Once answered, the card is absent and the button is gone. With nothing waiting the card is never present. Routes: runs (MAWS's non-blocking ask), terminal, remote.
  - **A8 · Several wait** (l4-approvals-08). With two permission prompts and a question waiting: one card is open at the end and one line stands under "Also waiting"; the question's form is in its row; the card in the column lists three, oldest first; opening the second line lets it be answered first. Route: runs.
  - **A9 · The composer while a request waits** (l4-approvals-08). A message sent while a prompt waits is queued as at any time a turn runs and answers nothing. Stop withdraws the prompt; an asynchronous question that was open stays open. Routes: runs, terminal.
  - **A10 · Double-click** (O-23). On a single-choice question a double-click on an option picks it and goes on (Next, or Submit on the last); on a multi-choice option and on "Other…" it does not submit. Routes: runs (MAWS's ask), terminal (the stepper).
  - **A11 · A file change** (l4-approvals-05). A prompt for a new file reads "Create <name>" and one for an existing file "Edit <name>", with the path relative to the working folder and the change as a diff with line numbers and "Show all". Routes: runs, remote.
  - **A12 · A plan** (l4-approvals-11). The primary button names the mode that follows; choosing another from its menu and approving leaves the session in that mode. Route: runs. On terminal the button reads "Implement" with no menu.
  - **A13 · Trust** (l4-approvals-13). In a folder with no project settings and no `.mcp.json`, the trust card shows the path, one line and three buttons, and no list. In a folder that has them, the found list as today.
  - **A14 · From outside** (l4-approvals-09, #333). With the window in the background, a prompt for a short command raises a notification with "Allow once" and "Deny", and each does what it says; a prompt for a file change raises one with "Deny" only. Hovering the session's row in the sidebar offers the same for the same requests. Routes: the notification on runs (a signed build); the hover card on runs, terminal, remote.
  - **A15 · A blocked call** (l4-approvals-12; after its probe). In auto mode a blocked call's row carries "Approve and retry"; a click draws one line, "You approved `cmd`", and the agent's retry runs. Routes: runs, terminal, remote.
  - **A16 · Keeps** (parent acceptance 3). Unchanged: Deny with a reason and Deny and stop (l4-approvals-03); the Question sheet's form, all questions on one page with Decide for me, Skip and one Submit (l4-approvals-06); answering in place from the Overview (l4-approvals-10); who asks and how many wait (l4-approvals-14); the transcript's follow behaviour (l2-transcript-10).

- **Contracts:**
  - **UC-1 · A request waits only until it is answered** (owned).
    - *The rule.* A request waits from the moment it is raised until the person's answer is written to its session. Written means: for a session MAWS runs, the engine host's flushed write of the answer, the moment the item's state becomes `delivered`; for a terminal session, the bridge's acceptance of MAWS's answer, or its word that the terminal answered; for MAWS's ask and for a question left in the to-human view, the moment the answer is taken, when their items leave the list as they do today. A write that failed is not an answer.
    - *The predicate*, in `src/shared/attention/kinds.ts`, the only definition of waiting:

      ```ts
      /** Whether an attention item still waits on the person. */
      export const waits = (item: Pick<AttentionItem, 'state'>): boolean => item.state === 'pending';
      /** A waiting item that stands for a request the person can answer (not a notice). */
      export const waitsOnAnswer = (item: Pick<AttentionItem, 'state'> & { request: Pick<AttentionItem['request'], 'requestId'> }): boolean =>
        waits(item) && item.request.requestId !== null;
      ```

      `isOpen` is removed from `kinds.ts` and nothing re-exports it.

      | state | what it means | waits |
      |---|---|---|
      | `pending` | raised; no answer written | yes |
      | `delivered` | the answer is written; the engine has not yet shown that it acted | no |
      | `confirmed` | a frame from the engine named the call | no |
      | `retired` | gone | no |

    - *The publisher.* The attention service (`src/services/attention/service.ts`) keeps and publishes only waiting broker items (it keeps "pending and delivered" today), so `attention.list`, `attention.changed` and the feed another machine reads carry no answered request, whatever build reads them. The list of a terminal session's requests omits a request from the moment MAWS's answer for it is accepted.
    - *Who reads it.* Each calls `waits` or `waitsOnAnswer`; none compares the state itself.

## #358 · An answered request stops waiting at the answer   (carries X-066; one cause with S-04 and S-07)
- **Today:** a request is an attention item in one of four states: `pending` (raised, not answered), `delivered` (the person's answer was written to the engine), `confirmed` (a frame from the engine named the call), `retired`. `isOpen` in `src/shared/attention/kinds.ts` counts both `pending` and `delivered` as waiting, and every reader takes its word. The engine host's broker (`PermissionBroker.confirm`, `src/engine-host/broker.ts`) leaves `delivered` only at the first frame that names the tool call: its result, a progress frame, a hook callback, an MCP call or a denial. A command that prints nothing until it ends sends none of these, so an allowed 60-second command "waits" for 60 seconds. (On engine `2.1.322` two frames do name such a call while it runs, `system/task_started` after about four seconds and a `tool_progress` heartbeat after thirty, seen in MAWS's journals; the broker reads neither, and UC-1 makes the question moot.) For a terminal session the item never becomes `delivered`: it stays listed, `pending`, until the bridge's `settled` reaches MAWS (`src/services/lane-a/attention.ts`), over the machine link when the session is on another machine, and a lost stream holds it five seconds more. That is the card the ticket saw standing as "Answered · Submitted" under the answer row.
- **After:** UC-1 as written under Contracts. On every route the request stops waiting when the answer is written: its card goes, and the transcript keeps the answer (the call's own row, the question's receipt). Nothing reads "Answered · …" in its place.
  - *A session MAWS runs* (this machine or another): at the broker's flushed write, which is when `delivered` is set today.
  - *A terminal session:* when the bridge accepts MAWS's answer (the answer call returns `delivered`), or when the bridge reports the terminal answered, whichever is first. The service that holds the session's list on the session's machine drops the request from the list at that moment, so every window and the feed another machine reads agree.
  - A question's row shows the answers the person just gave from that moment (they are held with the card's draft) until the transcript's own row carries them, so it never reads "Not answered" in between.
- **Why this, not that:** the charter already says a delivered item "is not an alarm state" (§4.6) and that an item enters Needs you "when a permission, question, plan approval, dialog or elicitation is pending" (§5.7); the readers contradicted it. The alternative was to keep `isOpen` and shorten the wait (a timeout on the collapsed card): it would still show "Needs approval" on a session that is working, and it adds a timer where a state already says the truth. Nothing is hidden by the change: if the process dies with an answer written and not acted on, the broker still counts it lost at exit and raises "interrupted" (`processExited`). The Claude Code CLI takes its prompt away at the answer.
- **Not included:** the broker's states and its confirmation rule stay as they are; they still decide what a process exit loses. The row's state word that comes from another machine's listing (S-05, S-06) is U9's.

## S-04 · A session reads "Needs approval" while the allowed command runs
- **Today:** the same cause as #358. `glyphFor` and `listedGlyph` (`src/renderer/src/attention/glyph.ts`) put any open item ahead of the session's state, Needs you (`waitingItem`, `src/renderer/src/attention/derive.ts`) lists it, the dock badge and the notifier (`src/main/attention/notifier.ts`) count it, and the feed another machine reads carries it (`src/services/attention/service.ts` keeps "pending and delivered"; `src/endpoint/attention-feed.ts` sends that list). So the sighting was not staleness after the app quit: the daemon went on publishing an answered item as waiting.
- **After:** from the answer, the session's row, its tab, the Overview card, Needs you, the dock badge and any notification follow the session's own state ("Working" while the command runs), in this window and in a window on another machine. A request raised after that one counts as before. It holds on all three routes, because each reads the one predicate.
- **Why this, not that:** one predicate read by every surface (UC-1) rather than a fix in each reader, because the sighting moved from surface to surface across two machines and any reader left on the old rule would bring it back.

## S-07 · The answered card leaves the composer at the answer
- **Today:** `swapOf` docks every open item, so an answered card keeps the composer's place, collapsed to "Answered · Allowed once", until its item retires; while it stands there is no message box and no Stop button. `src/renderer/src/composer/docked/swap.test.ts` pins it ("keeps an answered request docked (collapsed) until it retires"). It is C7's rule, recorded in `docs/doperpowers/plans/2026-09-28-c7-composer-requests.md` ("Delivery states").
- **After:** only a waiting request is drawn as a request. The moment the answer is written the card is gone and the composer is as it was. A failed write is not an answer: the card stays, with "Couldn't deliver the answer" and Retry. In the first pull request, before the placement work lands, this is the docked card leaving the dock at the answer; after it, the card at the transcript's end leaving. The card is one component, so it is the same on all three routes.
- **Why this, not that:** a paused composer with no Stop is worst exactly while a long command runs. A short "Answered" confirmation was considered and dropped: the call's row turning from "Waiting for approval" to "Running" is the confirmation, in the place the person is already looking.
- **Not included:** the three-second note for a request the terminal answered first ("Answered in the terminal: Allowed", the owner's ruling in P5 O9) stays; such a request does not count as waiting while the note shows.

## l4-approvals-08 · Where a waiting request is drawn   (carries l2-transcript-16)
- **Today:** the session's oldest answerable request takes the composer's place. The draft, the box with its Stop button and the toolbar are hidden behind a frame titled "<kind> · Composer paused · draft preserved", with "N more waiting" under it (`Frame.tsx`, `DockedCardFrame.tsx`, `swapOf`). To stop the turn the person must choose "Deny and stop"; to say anything, "Deny… with a reason". MAWS's own ask is the one exception: a capsule row, a notice above the composer and a form in a side sheet that opens by itself. A request of a terminal session or of a session on another machine has no place in the transcript at all, because only the engine's live request events make a row for it (`slotRow` in `src/renderer/src/transcript/model/derive.ts`); the dock is its only drawing.
- **After:** the owner's answer of 2026-11-12, as confirmed: a question's form sits in the transcript in the row of the call that asked; a permission prompt sits at the transcript's end; the composer stays free; a card in the card column lists what waits in the session.

  **Two places.** *The call's row* is the transcript row of the tool call that raised the request. *The transcript's end* is a region after the last row, inside the transcript's scroll and above the composer, so it is in view while the reader follows the session and scrolls away with the rest when they read back.
