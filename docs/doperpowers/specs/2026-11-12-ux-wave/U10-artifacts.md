## l6-artifacts-07 · an edit that resets the document; page settings; deleting a draft   (l6-artifacts-17 folds in: its extra working time was this item)

**(a) A formatting clean-up is never a write of its own.**

- **Today:** Every write reaches a document's live copy as an applied update (`hostReplica`, `content` and `writeCopy` in `src/engine-host/documents/service.ts`). Yjs, after applying an update to text that carries formatting, removes formatting markers that have become redundant, in a second transaction of its own that names no origin (`cleanupYTextAfterTransaction` in `@y/y` 14.0.0-rc.28, `src/utils/Transaction.js`). The live copy's listener, `integrated`, accepts a row only from a connection or a host replica and throws "the live doc of … was edited outside a replica" for anything else; `inFrame` then takes the frame's rows back and evicts the document, and the tool answers that the document was reset. An agent's `replace_text` that removes bold at the start of a list item leaves such markers, so the whole batch is refused, and the next edit is refused as stale. The same clean-up runs in every replica that receives an update: a person's open editor forwards it to the host as that person's write (`onDocUpdate` in `src/artifacts/provider/port.ts`), and a host replica forwards it as its agent's (`hostReplica`). When the live copy is loaded from the store its listener is attached after the load, so a clean-up at load changes the copy without a row. No test pushes a formatting change through the live copy and a replica.
- **After:** The clean-up Yjs runs after applying someone else's update is off on every document MAWS builds: the live copy, the host's replicas, the one-off replica that writes an accepted suggestion, and each open editor's replica. The clean-up a writer's own formatting edit does inside its own transaction stays; it is part of that write and lands in its row. So: the agent's edit lands as one row credited to the agent; no replica that only received an update sends anything; the live copy holds exactly what its log holds. Redundant markers that a merge of two writers' formatting leaves behind stay in the document; they change nothing a reader, an export or the agent's read can see.
- **Why this, not that:** The rule the owner was told is that a clean-up is never a write of its own, and the cheapest way to hold it is for the clean-up not to happen as its own transaction anywhere. The strongest alternative, the grounding's, keeps the clean-up in the live copy and credits it to the writer whose update caused it. It lost on what the code shows: the live copy's path assumes one row per apply (`lastApplied`, `edited`), so a credited clean-up either moves the revision twice for one edit or needs an already-appended row amended; `relay` skips the writer, so the writer's own replica would never receive the clean-up; and all of it sits on the path every document and deck write takes, for tidiness nobody can see (law 4). Claude Desktop has no equivalent to compare.
- **Not included:** Removing redundant markers some other way (at compaction, say); telling the agent who wrote since its last read (that is l6-artifacts-09's second half, under Waiting); any change to suggestion documents, which already run with the clean-up off.

**(b) Page size and density are settings of the document.**

- **Today:** A document's page comes from its design system's tokens, or from a size chosen per export (`pageOf` in `src/artifacts/document/export/design-system.ts`; the Export menu's six rows in `src/renderer/src/tools/document/header.ts`; `artifact_export.pageSize`). The document's own settings node holds only token overrides, which nothing outside tests writes (`src/artifacts/document/meta.ts`). No export answer says how many pages came out. The agent could not make a memo fit one page and redid it as an HTML page.
- **After:** The document's settings node gains a page setting, stored with the content so a version pins it:

  ```ts
  // in the document's `meta`, beside `dsOverrides`
  page?: { size?: 'letter' | 'a4'; density?: 'compact' }   // absent: the system's page, standard density
  ```

  The agent sets it with one more op of `artifact_edit`, atomic with the batch it is in, and reads it back in `artifact_read`'s answer for a document (`page: { size, density }`, the values in force):

  ```ts
  { op: 'set_page', size?: 'letter' | 'a4' | 'system', density?: 'standard' | 'compact' }   // at least one of the two
  ```

  The page an export prints on is, in order: the size named in the `artifact_export` call; the document's; the design system's; Letter. Compact density applies to the PDF, Word and web-page exports and to `artifact_screenshot`'s export layout: it is computed from the governing system's tokens when the export runs (type sizes × 0.9, block spacing × 0.75, a page margin of 0.75 in unless the system's is smaller) and applied beneath the document's own overrides. `artifact_export` to PDF answers `pages`, the page count. For the person, the document's Export menu becomes the four formats (Markdown, Web page, Word, PDF) followed by the page setting as checked items: Letter, A4, Compact. Choosing one writes the document's setting, as a row of the person's; the format rows then export with it. The editor's own view does not change with either setting (it has no pages). The document guide's sentence that page and spacing come from the system gains: "to fit a page, set the document's page with `set_page` and check the PDF's `pages`".
- **Why this, not that:** A setting in the document is the only place that makes the agent's check and the owner's export agree; with size chosen per export, the agent verifies one page on A4 and the owner's "PDF" prints Letter on two. A preset of two densities, derived from the system, keeps the document inside its design system; the alternative of letting the agent write arbitrary token overrides (the mechanism exists) hands it every colour and font and lost for that reason. A new tool for settings lost to one op on the tool the agent already holds. Claude Desktop has no page or density control for its documents; this is MAWS's own.
- **Not included:** Margins, orientation or columns as settings; a paginated editor; any change to a design system's own page tokens; page settings for other kinds. The three numbers of Compact are a first value: the owner looks at one memo at both densities before this lands.

**(c) The agent may delete a draft it made.**

- **Today:** The tool server has no delete (`MAWS_TOOL_NAMES` in `src/shared/maws/tools.ts`). The store deletes softly (`delete` in `src/engine-host/documents/store.ts` sets `deletedAt` and removes the artifact's connector grants); the person deletes from the Library's row menu; nothing restores. The agent asked the owner to delete its abandoned draft.
- **After:** A new tool, last in the list:

  ```ts
  artifact_delete { artifact: <id or handle> }  →  { status: 'deleted', artifactId, kind, title }
  ```

  It deletes softly, and only an artifact that this session, or a session it was opened from, created (the lineage the handle lookup already uses) and that no person has written to. Otherwise it refuses with the reason and what to do: "created by the user" or "the user has edited it", each ending "ask them to delete it in the Library"; a design system that still governs artifacts is refused as it is for the person. The tool is annotated as destructive and passes through the session's permission mode like any other tool. In the transcript the call draws the existing artifact row with a third action: "Deleted <title>" and an Undo button; Undo restores the artifact (a new store method and a call `artifacts.restore` beside today's `artifacts.delete`, clearing `deletedAt`) and the row reads "Restored <title>" with Open. Connector grants removed by the delete are not brought back; the person grants again. The row stays in view when its turn is folded, as the artifact row does today. For a session on another machine the row is drawn from that machine's transcript rows and Undo acts on that machine's library (UC-7).
- **Why this, not that:** The owner was handed the cleanup; an agent that can make an artifact should be able to take back its own. The Undo is in the transcript because that is where the owner learns of the delete, perhaps hours later; a toast would be gone. A "Recently deleted" view in the Library is the stronger alternative and lost only on size: it is a new view with its own questions (how long, whose deletes), and the row's Undo covers the agent's case. Claude Desktop's hosted artifact server lists `delete_artifact` in a permission class of its own (`app-5.1231.2/main-process/index.chunk-BV3uOqbK.js`, the tool-class table); its local artifact tools have none. MAWS follows the first.
- **Not included:** Hard deletion; an Undo for the person's own Library delete; a "Recently deleted" view; deleting versions or assets.

## X-141 · a presence redraw no longer writes a paragraph

- **Today:** When an agent's write leaves a chart as a document's last block, the editor's trailing-node repair adds an empty paragraph at the next transaction it is allowed to answer. `guard` in `src/artifacts/document/schema.ts` keeps repairs from answering the binding's transactions, attribution renders and the provisional layer's redraws, but not the redraw presence dispatches when another participant's state changes (`src/artifacts/document/editor/awareness.ts`, a transaction that carries only the presence plugin's mark). So an agent arriving in the document makes the owner's editor write a revision credited to the owner (tracker row 354).
- **After:** A repair answers only a transaction of the person's: one that changes the document or moves the selection, and is not the binding's. A transaction that changes neither is a redraw, whichever plugin sent it, and no repair answers it. This replaces the list of named redraws with one rule, so presence is covered and so is any redraw added later. Tracker row 354 closes with the test its close condition names (a remote write leaves a chart last, then a presence redraw: nothing is written).
- **Why this, not that:** Adding presence to the list of exceptions fixes this redraw and leaves the next one to be found the same way; the positive rule costs the same. The alternative of having the agent's write add the trailing paragraph itself would remove the repair's last cause, but it changes the agent's write path for every document and is not what the row asks.
- **Not included:** A click in such a document still lets the repair run, and that paragraph is the owner's: it is how a caret gets below a final chart. If the owner would rather a click wrote nothing, that is the row's other close condition and a separate decision.
