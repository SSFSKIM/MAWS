# U11 · Settings, connectors and the Org pages

> **A child of the UX wave.** Root: `docs/doperpowers/specs/2026-11-12-ux-wave-design.md`. Read it first: it holds the wave's purpose, its laws (law 1 to law 8), the contracts UC-1 to UC-15, the ordering and the record. This file is this child's section of that document. Where this file and a contract's statement in the root differ, the root binds; report the difference. **Grain:** plan. Items are named by their ids in the register, `docs/doperpowers/evidence/ux-wave-2026-11/register.md`.

- **Purpose:** Four smaller surfaces stop getting in the way. A connector that needs a sign-in can be signed in from the chat that uses it, whichever kind it is; until now the two kinds the owner meets most (a connector a plugin brings, and one added in MAWS's own Settings) had no Sign in anywhere and sent the person to a terminal. The dialog that lists a chat's connectors is one line per connector, is called Connectors wherever it is named, and says once what its switch reaches. A new chat shows its plugins, connectors and skills before the first message instead of a blank pane or "Available once the session starts". Settings is grouped so that its Engine section is no longer the place every setting landed, each row reads in one line, and a search finds a row by its words. On the Org pages every refusal says what to do next or who can act, every sheet reads as modal over the window, and the project Channel says when it is offline, lines up under classic scrollbars, cuts names sensibly, and can be opened without a right-click.

- **Acceptance:**
  - **A1 · A plugin's connector signs in from its chat** (l8-settings-01). In a session MAWS runs whose plugin brings a connector that needs a sign-in, "+" › Connectors › "Connectors in this chat…" shows the row as "Sign in needed" with Sign in. Pressing it opens the service's consent page in the browser; after consent the row reads Connected with its tool count. Holds for a session on this Mac and for a session MAWS runs on another machine (the browser opens on this Mac, the credential is kept on that machine). In a terminal session the dialog is unchanged: it lists connected servers only and points at the terminal's `/mcp`.
  - **A2 · MAWS's own list signs in too** (l8-settings-01). The same, for a server added under Settings › Sessions › MCP servers. Customize › Connectors › My items offers Sign in on that server's row while a session MAWS runs on this Mac holds it, and "Open a session, then sign in" while none does. The tracker row of 2026-10-21 (a needs-auth server with no sign-in) closes.
  - **A3 · The Connectors dialog reads at a glance** (l8-settings-04). In a session MAWS runs with five connectors the dialog shows five one-line rows (switch, name, status in words, tool count); transport, source and tool names appear only when a row is opened; the sentence about what the switch reaches appears once, in the dialog's head; the menu entry, the dialog's title and Customize all say Connectors. ## l8-settings-01 · Sign in for a plugin's connector and for MAWS's own list   (tracker row of 2026-10-21 closes with it)

- **Today:** The sign-in itself exists (`src/services/connectors/sign-in.ts`): MAWS asks the engine for an authorisation address, opens it, receives the browser's return on its own loopback listener and hands it to the engine. Two places offer it: Customize › Connectors › My items (`customize/connectors/ConnectorsSection.tsx`, `ServerRow`) and the session's Connectors dialog (`widgets/McpWidget.tsx`, `SignIn`). Both offer it only for a server configured in a file: `signInScope` in the dialog accepts the scopes `user`, `project` and `local`, and `ServerRow` gives a row of MAWS's own list (`scope === 'app'`) no target. Dynamic servers get nothing. That is every connector a plugin brings (the engine names it `plugin:<plugin>:<server>` and reports `scope: "dynamic"`; `cli.pretty.js` 2.1.322, the function at line 474720) and every server of MAWS's own list. The engine itself would sign either in: its `mcp_authenticate` looks the name up among the session's loaded servers (`cli.pretty.js:614200`), and it keys a credential by the server's name, type, address and headers, never by scope (`spikes/protocol-probe/findings-p4-r8-mcp-servers.txt`, items 2 and 5). The exclusion is MAWS's: the act the dialog sends, `connectors.signInServer`, takes only a name of letters, digits, hyphens and underscores (`McpServerNameSchema`, which a plugin server's colons fail) and only the three file scopes (`src/shared/ipc/schema/connectors.ts`), and main checks the request against a configuration file's entry (`sign-in-entry.ts`, `entryRefusal`).
- **After:**
  - *A session MAWS runs, on this Mac.* A row of the Connectors dialog whose status is `needs-auth` offers Sign in when its scope is `user`, `project`, `local` (as today) or `dynamic` (new). The press, the steps the row says while it runs, Cancel, and the ways it ends are today's. A second press for the same connector, from any session on that machine, cancels the first.
  - *A session MAWS runs on another machine.* The same, through the same act over the machine link, with the consent it asks today. Where that machine's engine keeps its own listener the row says "sign in on <machine>", as it does today for a file-scope server. On a machine whose build does not list the new command's capability, the row's Sign in is disabled with the update sentence (Contracts, UC-7).
  - *A terminal session.* Not on this route. The bridge's read lists only servers connected with tools and offers no command to authenticate, so a server that needs a sign-in is not in the list at all; the dialog keeps its sentence that the terminal's `/mcp` shows every server, and the sign-in is made there.
  - *Customize › Connectors › My items, this Mac.* A row of MAWS's own list offers Sign in while a session MAWS runs on this Mac is ready and holds that server (the page's attached session first, else any ready one). With none it says "Open a session, then sign in", the words file-scope rows use.
  - *The acts' inputs,* the one data change:

    ```ts
    // connectors.signInServer, as today
    { name: McpServerName, scope: 'user' | 'project' | 'local', cwd: string | null, appSessionId, callback? }
    // connectors.signInDynamicServer, new: its own grade row, offer row and capability
    { name: string /* 1 to 256 characters, as the session's mcp_status reports it */, appSessionId, callback? }
    ```

    A dynamic connector's identity, for "one sign-in at a time" and for which row shows a result, is its machine and its name (`connectorKey` and `signInKeyOf` treat `dynamic` as they treat `user`: no folder). Main's check for it reads the session, not a file: the session's `mcp_status` must list that name with scope `dynamic`; for a press from a Customize row of MAWS's own list the listed server's address must also be the entry's. A session that does not hold it is refused with today's reason `other_entry` and the words "that session has no <name> server" or "this session uses a different <name>; start a new session to sign in".
- **Why this, not that:** The dialog is where a person meets "Sign in needed", and the engine can already do the work, so the smallest honest change is to stop refusing the two kinds MAWS refuses. The strongest alternative was to wait for Customize to list plugin connectors (X-184) and sign in only there. It lost because Customize never starts a session and can sign in only through one that is running anyway, and because X-184 waits on the owner's answer about Customize's structure. Signing MAWS's own list in through MAWS's own credential store was rejected: that store serves MAWS's own connections, and the engine would not read it (the aggregator spec says so). Three departures from Claude Desktop, each on purpose. No "N connectors need attention · Reconnect all" line: the row already says it, and law 3. No "Paste the callback URL": MAWS runs the return listener itself, so nothing depends on the browser reaching the engine's port. No "Clear authentication": nobody asked.
- **Not included:** Connectors of the engine's `claudeai` scope and of managed scopes; the Session info panel's connector line; the refusal an agent's own connector call gets (X-181, left); a Sign in control on the rows of Settings › MCP servers, which show no state and whose future l8-settings-05 decides; plugin connectors in Customize's My items (X-184, waiting).

## l8-settings-04 · The Connectors dialog: one line per connector, one name, the switch's reach said once

- **Today:** The dialog a chat opens from "+" › Connectors › "Session connector controls…" is titled "MCP servers" (`WIDGET_TITLE.mcp` in `widgets/copy.ts`) under a menu entry that says Connectors. Each server takes five lines (`McpBody`'s default branch and `McpServerRow` in `widgets/McpWidget.tsx`): name and raw status, the transport, "scope … · from …", a tools disclosure, then the switch beside "Recorded by the engine for this project in ~/.claude.json" (`MCP_ACTIONS.persisted`) and Reconnect, on every row, connected or not. The switch is the engine's `mcp_toggle`, which writes `disabledMcpServers` into the project's entry of `~/.claude.json`: off in one chat is off for every session of that project. A terminal session's dialog (`widgets/McpDriven.tsx`) is already one line per server.
- **After, now:**
  - *Name.* The dialog's title is "Connectors", with "MCP servers" as a muted subtitle; the `/mcp` name beside it stays. The menu's entry to it reads "Connectors in this chat…", and its sibling "Session plugin details…" reads "Plugins in this chat…". "No MCP servers" reads "No connectors". The palette's description of `/mcp` reads "Connectors in this chat (MCP servers)".
  - *Row.* One line: the switch, the name as the engine reports it, the status in words, the tool count. Opening the row shows the transport, "from <source>", the scope, an error and the tool names. Status words, the same in the dialog and in the "+" › Connectors submenu: `connected` "Connected", `needs-auth` "Sign in needed", `failed` "Failed", `pending` "Connecting…", `disabled` nothing (the switch says it); any other status as the engine words it.
  - *Actions.* Sign in (l8-settings-01) and Reconnect sit on the line of a row that is `needs-auth` or `failed`; a connected row has Reconnect inside its opened part. The line a toggle or a reconnect answers with stays under its row, and the rule that the switch's position is read back from the engine and never inferred stays.
  - *The switch's reach, said once.* The dialog's head carries one sentence: "Off here is off for every session in <place>." (<place> is the project's name, or the folder's path when the chat has no project), with "The engine records it in ~/.claude.json." as its tooltip. No row repeats it.
  - *Routes.* A session MAWS runs, here or on another machine: all of the above (toggle and reconnect already cross the machine link). A terminal session: the title and the status words only; its Enable, Disable and Reconnect are the terminal's own `/mcp` commands and stay.
- **After, once the #476 probe has answered:** the switch comes to mean "off in this chat", and the project-wide off moves into the row's opened part as "Also off for every session in <place>". How "off in this chat" is done depends on what the probe finds (Probes and checks); until then the switch stays the engine's project-wide one, labelled truthfully.
- **Why this, not that:** The finding's complaint has two halves: a debugging view presented as the everyday control, and a switch that silently reaches the whole project. The first half is settled and needs nothing from the engine, so it goes now. The second needs an engine mechanism nobody has seen work (law 6), so the honest interim is to say what the switch does where the person presses it. The alternative of hiding the switch until the probe answers was rejected: turning a connector off for a project is useful, and it is the only off there is. Claude Desktop's switch means "this session, and the default for new ones" and writes no project file; MAWS departs until #476 is designed because the engine MAWS drives offers only the project-wide toggle over its wire today.
- **Not included:** per-chat or per-machine switches (#476); the "Add custom connector" form (l8-settings-05, waiting); a settings gear per row; any change to Customize's own connector rows beyond l8-settings-01's.

## l8-settings-03 · Plugins, Connectors and Skills before the first message

- **Today:** A new chat has no session record and no engine until its first message. Its Plugins dialog takes its folder from the engine or the record only (`PluginsWidget` in `widgets/PluginsWidget.tsx`: `engine.cwd ?? record.directory ?? null`), so its reads never run (`widgets/plugins/read.ts` disables a read with no folder) and My items shows nothing. The Connectors and Skills dialogs read the engine, and for an id with no record the frame says "Available once the session starts" (`availabilityRefusal` in `sessions/availability.ts`, `NOT_YET`). The "+" submenus say "Live details are unavailable until this session is running" (`composer/plus-menu/PlusMenu.tsx`). The folder is known all along: the tab's setup intent holds the location the person chose.
- **After, now** (a new chat on this Mac; a terminal session is never unstarted inside MAWS, so the route does not exist there):
  - *Plugins.* The dialog reads the tab's chosen folder (the user configuration when no folder is chosen), so My items lists what is installed and its management actions work as they do in Customize. What the session loaded keeps its existing "not observed yet" line.
  - *Connectors.* The "+" › Connectors submenu lists the inventory's connectors for the folder, each with its scope as the detail in place of a live status. The dialog lists the same rows with no switch, no Reconnect and no Sign in (there is no process to act on), under one line: "Configured for <place>. Connection state, and connectors from plugins, show once the chat starts." The second half of that line goes when X-184 lists plugin connectors.
  - *Skills.* `/skills` lists the inventory's skills in Customize's three groups (this project's, yours, from plugins) under "On disk for <place>. The chat may load more once it starts." Choosing a skill inserts `/<name> ` in the composer, as in a started chat. Reload skills is absent.
  - *The "+" › Plugins submenu* drops its "unavailable" sentence and keeps its two entries ("Plugins in this chat…", "Manage plugins…"); it lists no rows before the start, because listing them means running the plugin CLI each time the menu opens.
  - *A new chat set to another machine.* The three dialogs say "Shown once the chat starts on <machine>". The inventory and the plugin CLI read this Mac only, and this Mac's configuration is not that machine's.
- **After, once #476 is designed:** a switch per connector before the first message, whose choice joins the chat's launch (Claude Desktop's draft has such switches, though there they set an account-wide default). The lists above are what those switches will sit on.
- **Why this, not that:** The defect is a blank list for a folder the tab already knows; the cure is to read that folder. The grounding recommended only the Plugins fallback and left connectors and skills as they are. This goes one step further, because "Available once the session starts" on a list MAWS can already read from disk is the same defect, and Customize already draws both lists with no session. The alternative, a "Start now" button that launches the engine so the live lists can be read, was rejected: it starts a process to answer a question the disk answers.
- **Not included:** choosing connectors for a chat before it starts (#476); listing what only the running engine knows (connection state, a skill a marketplace declares but no folder holds).
