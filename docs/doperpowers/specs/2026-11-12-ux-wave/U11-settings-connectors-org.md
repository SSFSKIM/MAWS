# U11 · Settings, connectors and the Org pages

> **A child of the UX wave.** Root: `docs/doperpowers/specs/2026-11-12-ux-wave-design.md`. Read it first: it holds the wave's purpose, its laws (law 1 to law 8), the contracts UC-1 to UC-15, the ordering and the record. This file is this child's section of that document. Where this file and a contract's statement in the root differ, the root binds; report the difference. **Grain:** plan. Items are named by their ids in the register, `docs/doperpowers/evidence/ux-wave-2026-11/register.md`.

- **Purpose:** Four smaller surfaces stop getting in the way. A connector that needs a sign-in can be signed in from the chat that uses it, whichever kind it is; until now the two kinds the owner meets most (a connector a plugin brings, and one added in MAWS's own Settings) had no Sign in anywhere and sent the person to a terminal. The dialog that lists a chat's connectors is one line per connector, is called Connectors wherever it is named, and says once what its switch reaches. A new chat shows its plugins, connectors and skills before the first message instead of a blank pane or "Available once the session starts". Settings is grouped so that its Engine section is no longer the place every setting landed, each row reads in one line, and a search finds a row by its words. On the Org pages every refusal says what to do next or who can act, every sheet reads as modal over the window, and the project Channel says when it is offline, lines up under classic scrollbars, cuts names sensibly, and can be opened without a right-click. Customize answers 'what do I have' and 'what can I find' at its top level, with the kind as a filter, and every plugin, skill and connector has an image, a connector's site icon where Google's favicon service has one. A plugin's connectors are listed with the others and can be signed in from there. The model and the permission mode a person keeps choosing can be made the default from the menu that chooses them, for MAWS and the terminal alike. Another machine's connector list stays current without a Touch ID per read.

- **Acceptance:**
  - **A1 · A plugin's connector signs in from its chat** (l8-settings-01). In a session MAWS runs whose plugin brings a connector that needs a sign-in, "+" › Connectors › "Connectors in this chat…" shows the row as "Sign in needed" with Sign in. Pressing it opens the service's consent page in the browser; after consent the row reads Connected with its tool count. Holds for a session on this Mac and for a session MAWS runs on another machine (the browser opens on this Mac, the credential is kept on that machine). In a terminal session the dialog is unchanged: it lists connected servers only and points at the terminal's `/mcp`.
  - **A2 · MAWS's own list signs in too** (l8-settings-01). The same, for a server added under Settings › Sessions › MCP servers.   - **A3 · The Connectors dialog reads at a glance** (l8-settings-04). In a session MAWS runs with five connectors the dialog shows five one-line rows (switch, name, status in words, tool count); transport, source and tool names appear only when a row is opened; the sentence about what the switch reaches appears once, in the dialog's head; the menu entry, the dialog's title and Customize all say Connectors.   - **A4 · A new chat shows what it will have** (l8-settings-03).   - **A5 · Settings is grouped** (l8-settings-06). The index shows three groups (App; Sessions and engine; Org) and the sections of the table in this item.   - **A7 · Settings can be searched** (l8-settings-06).   - **A22 · The writer keeps what it did not write** (l8-settings-11; unit cases over a scratch config home, never the owner's).     | `handle`, `connectionId` | opaque ids by which the owner's acts name a row | no: each act that takes one is authorised by itself and keeps its step-up |
    | `saved`, `withdrawnUnattributed` | whether MAWS could read its saved connections at all; whether one was forgotten unattributed | no |

    The schema's own header states the exclusions: "Never a request URL (its query may be a secret), a resource, an issuer, a client, a token or a source id". No header, no environment value, no command and no argument is in any row. Two things the caller sends shape the answer: the artifact's id and up to 256 tool names. By choosing names, an administrator can already learn whether a server of a given name is configured and whether it has a given tool; that too is unchanged except for the missing proof of presence. On the machine the read does two things besides answer, both bounded and neither new: it notes that this device is showing that artifact's rows, so that later changes are announced to it, and it gives each row its opaque id (`listen` and `handleFor` in `src/services/connectors/owner.ts`). It starts no connector and contacts no provider. The P5 architect confirmed it by reading at master `6e8c72738`: the owner service's `servers()` and `read()` call no discover, run or start; `resolveSource` reaches `ConnectorStatusCache.lookup`, which reads the configuration and the host's memory; discovery is only `discoverAll` under `run()`, which is Connect's.
  - *What stays as it is under this form.* A machine whose policy is read-only refuses the read as today, and so does a machine whose copy of the org state is too old, because both rules test acts by grade and the read is still an act of that grade.
  - *The tests that would pin it.*
    1. `test/endpoint/artifact-rows.test.ts`, the case that keeps the owner's connector management at `machine-admin`: an unsigned `connectors.servers` from a member with the right is answered; from a member without it, `grade`; a signed one is still answered (a device on an older build); and, in a table over every other name of that case's `ADMIN` list, an unsigned act is still `step-up`.
    2. A unit case on `stepUpRequired`: false for `connectors.servers` at `machine-admin`; true for every other name at that grade; and the set holds exactly one name, so a second exception is a deliberate edit of a pinned test.
    3. The same file's read-only and too-old cases with `connectors.servers`: refused as today.
    4. A case that pins the row's field names per kind (in `src/shared/ipc/schema/connectors-owner.test.ts`): a row carrying `url`, `headers`, `env`, `token`, `command` or `args` fails the schema, and the list of fields per kind equals a written list, so that a field added later is a reviewed change to what crosses without Touch ID.
    5. The capability is in the endpoint's list; and `test/lane-b/remote.test.ts`, which reads the rows over a real link, shows the read answered with no step-up asked of the device's signer.
    6. The sheet: `tab.test.ts` and `ConnectorsSheet-remote.test.tsx` for both kinds of machine (one that lists the capability: no Show, a change reads again; one that does not: today's cases unchanged); `e2e/remote.spec.ts`, where today a Connect leaves the other device's rows marked stale, shows them read again by themselves.
    7. The read touches nothing outside (the ruling's condition 2): `connectors.servers` answered by the owner service over a direct route whose discover, connect and acquire throw if called; the read answers and none is called (beside `src/services/connectors/owner.test.ts`).
- **Why this, not that:** The owner chose it over one Touch ID that covers re-reads for ten minutes, which P5 had already rejected as "a new time-boxed admin grant". The grounding proposed making the read a call. Read at the source, that is the larger change: a call may carry only the grades `list` and `view`, so the row would need a grade of its own and a new flag for the right; changing the row's kind would refuse a device on build F, which sends the act, so the read would need a second name; and a call passes the read-only and too-old rules that an act does not, which would widen the read in two more states. Excusing the step-up for the one name changes one line of the endpoint's rule, follows a precedent in the same function, needs nothing of the device's main, keeps both directions of mixed builds working, and widens nothing but presence. The folder list of the remote setup is the precedent for the idea (owners read their own machine's folder names without a Touch ID per page); this takes the idea and the smaller form.
- **Not included:** any other read or act of that grade; a time window; the same change for a session's own Connectors dialog, which is not at that grade; a sheet whose change feed was resynchronised without a word about its rows (the tracker's X-193): once the read asks for nothing its fix becomes "read again at a resync", and by the ruling it may ride in this landing's plan.
