# U12 · In-app browser, computer use and delivery

> **A child of the UX wave.** Root: `docs/doperpowers/specs/2026-11-12-ux-wave-design.md`. Read it first: it holds the wave's purpose, its laws (law 1 to law 8), the contracts UC-1 to UC-15, the ordering and the record. This file is this child's section of that document. Where this file and a contract's statement in the root differ, the root binds; report the difference. **Grain:** plan. Items are named by their ids in the register, `docs/doperpowers/evidence/ux-wave-2026-11/register.md`.

- **Purpose:** An agent asked to open and test a page uses the Browser side surface the person is watching, without being told which tool reaches it, and no longer asks the person to click or reload for it. When the agent shows a page that is already open, the page is reloaded. The Browser gains two device sizes and a screenshot to the clipboard. A pane the agent opens from a session on another machine appears on the device the person is sitting at. While an agent drives the Mac through computer use, the session says so and offers Stop, and the on-screen agent cursor carries the session's name. Two changes that only the computer-use plugin can make are written here as tickets for that project; nothing MAWS builds waits for them.

Words used below. *The computer-use plugin* (in code and in its own documents: cua) is a Claude Code plugin whose MCP server `cua_repl` gives the agent a `js` tool: each call runs one JavaScript cell that drives macOS apps and browsers. *The in-app browser* is MAWS's Browser side surface; the agent reaches it through the same `js` tool, over a socket MAWS gives each session it runs (the session's *browser backend*). A *lease* is the agent's hold on one browser tab while it drives it.

## l9-browser-delivery-01 · The agent is told that the in-app browser is its browser

- **Today:** Asked to test a page "in the app's built-in browser", the agent opened the page with `show_pane`, tested it in a separate headless browser, reported that it could not act inside the pane, and asked the person to click. Told to use the computer-use plugin, it drove the pane without trouble. The cause is where the words are:
  - The plugin already makes the in-app browser the default: `cua.getBrowser()` with no id is the session's in-app browser. That rule (`MAWS_RULE` in the plugin's `src/mcp/surface.mjs`) is written only into the description of `profiles_list`, a tool the engine's tool search defers and the agent may never load. What the agent reads first says otherwise: the `js` tool's search hint is "control macos apps and the user's chrome browser profiles", the server's host notes open with "Use when a macOS app's GUI is the only way", and the plugin removes the vendor's own paragraph about an in-app browser from `js`'s description (`BROWSER_EDITS` in `src/repl-host/instructions.mjs`).
  - MAWS says nothing either. Its server instructions (`MAWS_SERVER_INSTRUCTIONS` in `src/shared/maws/instructions.ts`) speak of artifacts only. `show_pane`'s description lists "browser" with "a URL for browser". Its answer for a browser pane is a generic record of the side surface that opened (`showBrowser` in `src/renderer/src/tools/maws/panes/connect.ts`).
  - The owner asked whether MAWS should open the pane when the agent uses the in-app browser. It already does: at a lease's first acting command main emits `browser.agent.acting` (`CuaConnection.acting` in `src/main/browser/cua/connection.ts`), and a window showing that session opens its Browser, once per turn, unless one is already open (`connectBrowserAgent` in `src/renderer/src/tools/browser/agent/connect.ts`).
- **After:**
  - *The instructions.* A session MAWS launches with a browser backend gets one more paragraph in the `maws` server's instructions, after the artifact paragraph, exactly:

    `This session has MAWS's in-app browser: the Browser pane, which the user watches and can take over. It is your browser too. With cua_repl's js tool, cua.getBrowser() with no id is this browser, so open, click, type, reload and check pages there yourself instead of asking the user to; use Chrome or another browser only when the user names it.`

    A session launched without a browser backend gets the instructions as they are today. The paragraph is a second exported constant beside the first, so each stays pinned word for word.
  - *The pane's answer.* `show_pane`'s answer for the browser pane carries a `note` the agent reads at the moment it has put a page in front of the person (shapes and texts under l9-browser-delivery-02).
  - *Routes.* A session MAWS runs, here or on another machine: as above; on another machine the engine host there writes the same paragraph, and the agent's browser is that machine's (its app's when one is open there, otherwise the daemon's offscreen tabs, which the person sees from their device as the "Agent on `<machine>`" group). A terminal session: not on this route, because MAWS writes no instructions for it and gives it no browser backend.
  - *The agent's tab.* When the Browser opens by itself because the agent started acting in a page, it shows the agent's tab, except when the person is using the selected tab: they typed or clicked in it within the last three seconds, or it reads "You have the page" (`personUses` in `src/main/browser/agent/control.ts`, the one statement of that rule: the tab's control is `human`, or `personHolds`, which is the three-second grace alone and is not changed). The agent's tab is selected only together with a window's own opening of the Browser, which happens once in a turn and never while that session's panel already has a Browser tool. The window asks main first (a new command, `browser.agent.show`) and then opens the tool; main selects the agent's tab unless the person is using the selected tab or a panel in some window is showing it. Nothing else selects: not an acting command in main, not a later lease, and a Browser that is already open is not moved. This is the owner's answer of 2026-11-12, narrowed to the question on the owner's card, and reverses the owner's choice of 2026-10-08 (Rulings reversed). This item first had main select at every lease's first acting command, which can move the selection several times in a turn and change a tab the person is reading.
  - *The plugin's ticket.* The text an agent's tool search lands on is the plugin's. The ticket below asks for it; it is filed as cua#368. MAWS's paragraph does not wait for it.
- **Why this, not that:** The owner's direction is "This is cua_repl side fix", and the larger part of the fix is the plugin's text. MAWS adds its own paragraph anyway, because the person's worst outcome was being asked to click, and one paragraph from MAWS holds for every version of the plugin. Claude Desktop does the same in its system prompt, for the sessions that have its browser: "You have a built-in browser … The user sees the same pane and can take over" and "Never ask the user to check manually — verify and share proof directly" (`<built_in_browser>` and `<verification_workflow>`, `app-5.1231.2/main-process/index.chunk-BjORVu2_.js:28156-28160`, joined at `:28167-28182`). Both go only to a local Code session that carries its "Claude Browser" server (`:30642`). The first is further behind the gate `17519066` (off when not fetched), the organization not blocking the browser pane, and the person's setting (`main-process/index.chunk-BV3uOqbK.js:211149-211156`); the second is part of the verification text, sent only in a project that has `.claude/launch.json` without `autoVerify: false` (`:355768-355779`). **Ticket 1 on the computer-use plugin's board: filed on 2026-11-13 as cua#368** (the plugin's GitHub issues), labelled enhancement, priority P2, ready for an implementer. Its text as filed:

> **Title:** In a MAWS session, name the in-app browser where the agent looks first (the `js` tool's search hint and rules, the host notes)
>
> **Background.** MAWS is a macOS desktop app that runs Claude Code sessions. Each session it runs has a browser pane beside the conversation, the *in-app browser*, which the person watches and can take over. MAWS gives each session's engine a Unix socket in `CUA_BROWSER_BACKENDS`; with it set, `cua.getBrowser()` with no id is that session's in-app browser (key `maws`), since #13. For the agent this browser is a third surface of the computer-use tool, beside the Mac's screen and the user's Chrome.
>
> **What is wrong.** An agent in such a session does not learn this unless it loads `profiles_list`. The one text that says it is `MAWS_RULE` (`src/mcp/surface.mjs`), which is written only into `profiles_list`'s description. Under Claude Code's tool search `profiles_list` is deferred, so an agent can find and call `js` without ever reading it.
>
> **Seen.** In a MAWS session with tool search on, an agent that was asked to open a local page in the session's in-app browser and to test a button there opened the page with MAWS's own pane tool, tested it in a separate headless browser, reported that it could not act inside the pane, and asked the person to click. Told to use `cua_repl`, it drove the pane correctly. `MAWS_RULE` had shipped two weeks before.
>
> **Why it is so today.** Every text the agent reads before `profiles_list` points away from the in-app browser:
> - `js`'s search hint with both surfaces on is "control macos apps and the user's chrome browser profiles: click, type, fill forms, read, screenshot" (`BROWSER_HINTS`, `src/mcp/surface.mjs`). Tool search matches on it.
> - The host notes with the computer surface on open with "Use when a macOS app's GUI is the only way" (`COMPUTER_HEAD`) and say nothing of a browser.
> - `js`'s own rules end with a pointer to `profiles_list`'s description, for Chrome (`BROWSER_POINTER`); `jsRulesFor` is not told whether a MAWS backend is configured.
> - The vendor's paragraph on an in-app browser is removed from `js`'s description (`BROWSER_EDITS`, `src/repl-host/instructions.mjs`). That is right, since it describes another product's browser, but nothing replaces it.
>
> **Asked for,** only when a MAWS backend is configured (`inAppBrowser` is true in `modelTools`):
> 1. `js`'s search hint names the in-app browser first, for example: "control macos apps, this session's MAWS in-app browser and the user's chrome profiles: click, type, fill forms, read, screenshot".
> 2. `js`'s rules carry the rule itself and not only a pointer: "In MAWS: cua.getBrowser() with no id is this session's in-app browser (key maws), the pane the user watches; use it for any page unless the user names a Chrome profile. No profiles_list call is needed for it."
> 3. The host notes gain one line saying the same, inside the 2,048 characters the plugin's tests hold them to.
> 4. Optional: one line for the in-app browser in the browser documentation the first `js` call returns, in place of the removed vendor text.
>
> **Unchanged.** With no MAWS backend configured every text is byte for byte what it is today.
>
> **Acceptance.**
> - `tools/list` on a connection with a MAWS backend shows the new hint and the new rule on `js`; the `initialize` answer's instructions carry the new host note and stay within 2,048 characters.
> - The existing tests for a connection without a MAWS backend pass unchanged.
> - In a new MAWS session with tool search on, a prompt that names no tool and asks for a local page to be opened in the in-app browser and a button on it tested ends with the agent driving the in-app browser through `js`.
>
> **What MAWS does on its side, without waiting for this.** MAWS adds a paragraph to its own MCP server's instructions for sessions that have the in-app browser ("… With cua_repl's js tool, cua.getBrowser() with no id is this browser, so open, click, type, reload and check pages there yourself instead of asking the user to …"), and its pane tool's answer for a browser page says the same. That reaches an agent that reads MAWS's texts; this ticket reaches the agent whose tool search lands on `js`.

## l9-browser-delivery-02 · `show_pane` on a page already open reloads it

- **Today:** `show_pane`'s browser target opens with reuse by address (`BrowserHandle.open`), and `TabStore.open` in `src/main/browser/tabs.ts` selects a tab already at that address and loads it only when it has no view (a suspended tab). A loaded tab keeps showing the old page, so after fixing a page the agent told the person to reload.
- **After:** Only `show_pane` asks for the reload; a link, the address bar and the person's own opens do not.
  - The open request gains `reload?: true`, set by `show_pane`'s path alone. Main's rule for a tab of the session already at that address:

    | the tab | what main does | `page` |
    |---|---|---|
    | none at that address | opens a new tab and selects it | `opened` |
    | suspended (no view) | selects and loads it, as today | `reloaded` |
    | loaded, and the person is not using it | selects and reloads it | `reloaded` |
    | loaded, and the person is using it | selects it, reloads nothing | `kept` |

    The person is using a tab when the chrome reads "You have the page" (the tab's control is `human`) or their last input in it was within the hand-back window of three seconds (`personUses` in `src/main/browser/agent/control.ts`, the one statement of that rule). The reload goes through `Navigator.reloadForAgent`, which is not counted as the person's input, so the agent's reload does not make a tab read as in use.

    The limit: a reload by the agent discards what was typed in the page, as any reload does. `personUses` is the only protection, so a page the person typed in earlier and has left is reloaded like any other. That is the item's main case, a person who tested a page and asked for a fix.
  - The window awaits the open before it answers, and passes `page` back. On the wire this is one minor, which carries one optional key, `page`, in `maws.pane.answer` (its `ok: true` branch). A repeated `requestId` (a second window handling the same request) reloads nothing more and answers the first outcome.
  - The tool's result, which the agent reads as JSON, gains two optional fields:

    ```ts
    ShowPaneResult = { status: 'shown', pane, opened, page?: 'opened' | 'reloaded' | 'kept', note?: string }
    ```

    `page` is present for the browser pane with a target. `note` is present for the browser pane in a session launched with a browser backend, added by the engine host; a session launched without one gets `page` and no `note`, as it gets no paragraph of instructions, because the note's sentence would be false there. It is exactly one of:
    - shown on the session's machine, when `page` is absent, `opened` or `reloaded`: `This page is in the session's in-app browser, which the user sees. To act on it, use cua_repl's js tool: cua.getBrowser() with no id is this browser.`
    - shown on the session's machine, when `page` is `kept`: `The user is using this tab, so it was shown without reloading. To act on it, use cua_repl's js tool: cua.getBrowser() with no id is this browser.`
    - shown on another device (#435): `Shown in the user's MAWS on another device, in a tab of its own; your browser on this machine is separate.`

    One refusal is added, for a page MAWS could not open: an open that main refuses is answered as a refusal, nothing is opened, and the agent reads `show_pane: MAWS could not open "<target>" in its browser: <message>`. Answering "shown" there would tell the agent that its page is in front of the person.

    The journaled `maws.pane.shown` event keeps its shape; old journals read as before.
  - `show_pane`'s description changes in one clause: "a URL for browser" becomes "a URL for browser (a page already open is reloaded, unless the user is using that tab)". It still opens with its fallback sentence.
  - *Routes.* `show_pane` exists only in a session MAWS runs. On another machine the request goes to the device chosen by #435's rule, and the tab reloaded is that device's own tab at the address.
- **Why this, not that:** The agent called `show_pane` to show the current version; a reused tab that shows the old one defeats the call. Reloading on every reuse, from any opener, lost: a person clicking a link to a page they have open should not lose what they typed. Leaving it to the agent to reload through the plugin lost: that is what Claude Desktop's prompt tells its agent to do in a project with `.claude/launch.json` (step 2 of its verification text, "Reload if needed … Skip if HMR is active", `app-5.1231.2/main-process/index.chunk-BjORVu2_.js:28156-28157`), but it only helps an agent that already found the browser, and the `show_pane` reload covers the one that did not. Scroll position gets no special work: Chromium restores it on a reload of the same document.
- **Not included:** Reloading a tab the person is using. Protecting what the person typed earlier in a page they have left (considered and withdrawn on 2026-11-13; the root's Decision Log). A reload for any pane other than the browser. Selecting or reloading the agent's tab on another machine (see #435).

> **Title:** For a host such as MAWS: say what computer use is doing (task open, app in use), and stop the running cell when its call is cancelled, or say when it has ended
>
> **Background.** MAWS is a macOS desktop app that runs Claude Code sessions and shows each one's conversation. It launches the engine itself and reads the engine's stream-json output, and it renders the surfaces mods draw. When an agent in such a session drives the Mac through cua, the person watching MAWS wants to know which session is doing it, what it is acting on, and how to stop it.
>
> **What a host can and cannot do today.**
> - *State.* From the engine's output a host sees a `js` call start, with its code, and end. It cannot see whether a task is open, which app the cell acts on, or whether the cell touches the screen at all: handles persist between cells, the engine's stream-json output forwards no progress notification from an MCP server (read in Claude Code 2.1.322), and approvals are answered by the plugin's Elicitation hook inside the engine. So MAWS can show only "Computer use running" while a `js` call is in flight.
> - *Stop.* A host can interrupt the turn. The engine then withdraws the call (`notifications/cancelled`), and the REPL host does not stop the cell: `src/repl-host/supervisor.mjs` says "running + cancellation: nothing is stopped; the eventual result still settles (the vendor's behaviour)", and the host notes tell the agent "Only timeout_ms stops a running cell, not cancelling" (`GENERAL_NOTES`, `src/mcp/surface.mjs`). After the person presses Stop, the cell may go on acting, with nobody reading its result.
> - *When it is over.* A host cannot tell that either. `timeout_ms` is a budget and not a deadline: `executionBudget` (`src/repl-host/budget.mjs`) is suspended around approvals and a helper's start and resumes with what was left, and a call queued behind another (`enqueue`, `supervisor.mjs`) starts its budget later than the host saw the call. So a host that warns "computer use may still be acting" has no time at which it may stop warning. MAWS keeps that warning until a later call of the session settles, the session ends, the plugin's server is gone, or the person dismisses it.
>
> **Asked for.**
> 1. *The state, told to the host.* Per session: a task opened or closed; the app (or "browser") a cell is acting on, by name; the kind of each acting step (click, type, key, drag), never its content. Either of two shapes would serve, and MAWS can use both:
> - a mod surface the plugin draws itself (a band such as "Using `<app>` · Stop") in clients that render mods; MAWS prefers this where mods can draw;
> - a machine-readable report for where no mod draws (a session in a terminal that MAWS only watches, a session on another machine): over the session's existing MAWS backend connection, or to a path the host passes in the launch environment. If it rides the backend connection it must not count as browser demand: MAWS's broker for a session whose browser has not started treats every request it does not know as demand and starts the session's headless browser.
> 2. *Stop.* A cancelled `js` call stops its running cell and releases held input (a pressed button, a held key), or the plugin gives the host another way to stop the session's running cell. Failing both: a signal the host can read when a cancelled cell has ended (its code settled, its budget ran out, or its kernel was reset), so that the host knows when to stop warning.
> 3. *Smaller, optional.* The agent cursor's label is read once from `CUA_CURSOR_LABEL` when the engine starts (#235). MAWS sets it to the session's title at each launch; a label that follows a later rename would need the plugin to read it again at a task's start. The README says MAWS also sets `CUA_CURSOR_COLOR`; MAWS sets the label only and leaves the colour to the plugin's own pick.
>
> **Constraints.** No typed text, page content, secret or screenshot leaves the plugin on this channel: names of apps and kinds of step only. Nothing changes for a client that asks for none of it.
>
> **Acceptance.**
> - In a MAWS session, while a cell clicks in an app, the host can show that app's name within a second of the first step, and shows nothing of the kind for a cell that only computes.
> - Stop pressed during a cell that acts once a second for thirty seconds leaves no further step after the cancel is delivered, and no input stays held. If the cell is not stopped: the host is told within a second of the cell's end that it has ended, also when an approval had suspended its budget and when it had waited behind another call.
>
> **What MAWS does on its side, without waiting for this.** A line across the top of the session, "Computer use running" with Stop, inferred from the call in flight; Stop as a turn interrupt; after a Stop that withdrew a running call, the line "Computer use may still be finishing a step", which stays until a later computer-use call of the session settles, the session ends, the plugin's server is gone, or the person dismisses it; the call's row titled "Used computer use"; `CUA_CURSOR_LABEL` set at launch. When this ticket lands, MAWS shows the plugin's own surface where mods draw, uses the report elsewhere, and ends the "may still be finishing" line on the plugin's word.
>
> **To be added as a comment when it has run.** MAWS's hands-on check: a cell that types one character a second into a scratch document for thirty seconds, Stop pressed at five seconds, the characters counted at forty.
>
