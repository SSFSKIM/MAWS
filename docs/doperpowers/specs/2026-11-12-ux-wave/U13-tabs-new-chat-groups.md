# U13 · Tabs, New chat and session groups

> **A child of the UX wave.** Root: `docs/doperpowers/specs/2026-11-12-ux-wave-design.md`. Read it first: it holds the wave's purpose, its laws (law 1 to law 8), the contracts UC-1 to UC-15, the ordering and the record. This file is this child's section of that document. Where this file and a contract's statement in the root differ, the root binds; report the difference. **Grain:** plan for the one strip; design with the owner for groups. Items are named by their ids in the register, `docs/doperpowers/evidence/ux-wave-2026-11/register.md`.

- **Purpose:** Today the main tabs are kept in one hidden set per project, and the strip swaps to another set when a project is clicked, when a session of another project is opened, or when New chat is pressed from a project that has no folder on this Mac. The owner reads that as New chat replacing the tabs, finds several old "New chat" tabs waiting in the set it swapped to, and finds a click on the title bar's project chip starting a session nobody asked for. After this child there is one strip: everything open, from every project and every machine, in one place, the same after a relaunch. New chat adds one tab beside the tabs already there and brings an empty one back instead of piling up another; a New chat tab that arrives late takes nothing from the tab opened meanwhile; the chip starts no session. Session groups, the views of the sidebar and the folded sidebar are then designed with the owner on top of this strip, because the owner's answer made a group "a named set of sessions that you open as tabs" and that sentence leaves most of a group undecided.

- **Acceptance:** A session reaches the window by three routes (law 5); a tab is the same object on each, so every item below holds for a session MAWS runs, a terminal session and a session on another machine unless it says otherwise.
  - **A1 (O-01).** With tabs open for sessions of two projects and for one session on another machine, a click on any project row or machine row in the sidebar opens or closes that row and changes no tab. Opening a session of another project puts it in the same strip. No tab leaves the strip unless it is closed, replaced by a plain click (the rule of 2026-10-01 that stands, see "Not included") or its session is removed.
  - **A2 (O-01).** From each place New chat can be pressed (the sidebar's row, the strip's "+", ⌘N, the File menu, the palette, the empty main area, the Overview, a project row's "+"), with three tabs open: exactly one tab is added, right after the tab in front, and the three stay. The same with a session in front whose project has no folder on this Mac, which is the scene the owner reported.
  - **A3 (O-01).** With an empty unstarted chat already in the strip, pressing New chat again leaves one empty chat in the strip, with the keyboard in its composer: the same one brought to the front when the press asks for the same project, a new one in its place when it asks for another. With a draft typed in the first, a second chat opens and the first keeps its draft. Two presses in quick succession, before the first tab has arrived, make one chat.
  - **A4 (#497).** A renderer test holds main's answer to `session.create`, selects another tab, then releases the answer: the other tab is still selected and the chat's tab has been added unselected. With nothing selected in between, the chat opens selected.
  - **A5 (O-01; l7-shell-12, marked keep).** Quit and relaunch with a split, a pinned tab, a tab of a session on another machine and an unstarted chat holding a draft: the strip returns with the same tabs in the same order, the pin, the split and its ratio, and the same tab in front; the draft is in its chat. With that other machine switched off, its tab is still there, drawn as U9 draws a tab whose link is not up (#563); when the machine answers again the tab shows the session without being reopened.
  - **A6 (O-01, the upgrade).** A `layout.json` written by build F that holds several per-project sets opens with every tab of every set in the strip, the tabs of the set that was showing first and its active tab in front, and a notice that says so once. A unit test over a fixture with five sets proves that no tab id is missing and none appears twice. The cross-build e2e, run with build F named as the peer, proves both directions: this build opens F's layout whole, and F opens the value this build wrote with every tab present.
  - **A7 (O-01).** A unit test proves that the sessions main counts as open (`sessionsInTabs`, `remoteSessionsInTabs`) are the same set for a stored value before and after it is read into one strip, so the upgrade stops no session and drops no stream.
  - **A8 (O-31, first half).** The title bar's chip names the project, or the machine, of the session in front. A click on it shows that row in the sidebar, opened and focused, unfolding the sidebar if it is folded. It creates no session and no tab.
  - **A9 (O-01, how a tab names its place).** With session tabs of two projects open, each session tab names its project after its title, and a session on another machine also names the machine. With every session tab of one project on this Mac, no tab names it. A tab squeezed to its smallest width shows its mark and title only; its tooltip and the All tabs menu still give the full name.
  - **A10 (O-01, many tabs).** With forty tabs open the tabs shrink, then the row scrolls with the tab in front kept in view; "+" and the All tabs menu stay at the row's end; ⌘1 to ⌘9 select the first nine, ⌥⌘] and ⌥⌘[ walk all forty; "Close tabs to the right" on the third tab leaves three.
  - **A11 (l6-artifacts-13).** With a deck's tab and a document's tab open, opening a file from the session's card column adds or shows the file's tab and every other tab is still in the strip.
  - **A12 (law 8).** The rebindable keymap is untouched: no existing chord moves and none is added.
  - **Groups.** No acceptance is written yet. The groups half is accepted against items added to this section when the design round closes ("Groups", below).

    - **The strip.** One set of open main tabs for the window. Under a split it is drawn as two rows, one per pane, and both rows are the strip. In the layout store it is this value:

      ```ts
      interface Strip {
        panes: [Pane] | [Pane, Pane];        // one row of tabs per pane; two under a split (charter D-8)
        focusedPane: 0 | 1;
        splitRatio: number;
        floating?: { sessionTabId: string; foldedPanel?: true };  // the split's floating card, as today
        closedTabs: TabRef[];                // the reopen history (⌘⇧T), newest last, ten at most
      }
      interface Pane { tabs: TabRef[]; activeTabId: string }      // '' while the only pane is empty
      ```

      `TabRef`, `TabTarget` and `tabId` are unchanged: a tab's id is computed from what it shows, so a tab exists once in the strip.
    - **As stored (UC-14, owned: what the wave stores, build F can still read).** The key `main.tabs` of `<userData>/layout.json` keeps version 3 and is always written with exactly one set, under the key `none`:

      ```json
      { "version": 3, "current": "none",
        "sets": { "none": { "panes": [{ "tabs": [], "activeTabId": "" }], "focusedPane": 0, "splitRatio": 0.5 } },
        "closedTabs": [] }
      ```

      No field is added to a stored tab of an existing kind while a build older than this wave may still run on the same profile, because the older reader parses tabs strictly.
    - **As read.** Any stored value (version 1, version 2, or version 3 with any number of sets) becomes one strip by one pure function that runs on every read:
      1. the set that was showing (`current`) becomes the strip as it is: its panes, the order of its tabs, its pins, each pane's active tab, the focused pane, the split's ratio and the floating card;
      2. the tabs of every other set follow, set by set in the stored order, a set's left pane before its right, appended to the end of the strip's focused pane; none becomes active unless the strip was empty; pinned ones take their place among the pinned tabs;
      3. the other sets' splits and floating cards are dropped; `closedTabs` is kept;
      4. the side column's remembered session (`panelTools.surfaces.contexts`) keeps the entry of the set that was showing, written back under `none`;
      5. then today's repairs run unchanged (a tab whose session no longer exists is dropped, a tab of a kind this build does not name is dropped, each pane's active tab is one of its tabs).
    - **Rules.**
      1. Nothing changes what the strip holds except an open, a close, a move or a replace. A click on a project, machine or group row, a change of a session's project, a machine connecting and a New chat being given its project move no tab.
      2. `openTab(target, { pane?, activate? })` brings an open tab to the front, or adds a new one after the tab in front of the pane asked for. `openSession(id, { how?, split? })` keeps the rule of 2026-10-01 (I2): a plain open takes the place of the unpinned tab in front, `how: 'tab'` adds a tab, `split` opens in the other pane.
      3. Only a tab holds a session open. A session tab or an agent tab in the strip is what main counts when it decides which sessions the engine host may not release when idle, which the inactive sweep keeps and which sessions on other machines keep a stream. No other layout state may hold a session.
      4. **The session in front** is the session whose card column and side surfaces the window shows: the session of the active tab of the focused pane, or, when that tab belongs to no session (an artifact, a channel), the session last in front that still has a tab. It is today's `surfaceSession` in `src/renderer/src/panel/surface-model.ts`, now over one strip.
      5. **The current project** is the sidebar row the session in front sits under: a project's row, or a machine's own row for a session in no listed project; for an unstarted chat, the project chosen in it. `currentRow(): RowKey | null` answers it. `focusedProject(): ProjectId | null` keeps its name and callers and answers that row's folder on this Mac when it has one that is not hidden, else null.
      6. `newChat(opts?: { pane?: 0 | 1; row?: RowKey }): Promise<AppSessionId | null>` is the one way an empty chat is asked for; every New chat control calls it (O-01 carries its behaviour). `createSession(projectId, opts)` stays underneath for a creation that carries something: a worktree's checkout, a prefilled prompt.
      7. Showing a tab shows the tabs. Any change that brings a tab to the front passes one commit function in `stores/layout.ts`, `commitShown`: `openTab` when it activates, `openSession`, `activateTab`, `selectTab`, `cycleTab`, `reopenClosed`, a move or a reorder, a split made with the tab in front, and a pane the person chose (`showPane`: the keyboard move to the other pane, `pane.focusOther`, and opening, closing, floating, docking and focusing the split card). An open with `activate: false` does not count, and neither does `focusPane`, which only follows where the keyboard or a press already is. The commit stands for the act, whether or not the strip changes with it: a click on the tab already in front is an act.
      8. A child that retires a tab kind adds it to the reader's list of retired kinds, so a stored tab of it is dropped without a warning. A child that adds a kind accepts that an older build drops such a tab.

## O-01 · one strip for everything open; New chat adds one tab and reuses an empty one

- **Today:**
  - `main.tabs` holds one tab set per sidebar row (a project's, a machine's own, or `none` for no project) and names the one the strip shows: `LayoutMainSchema` in `src/shared/ipc/schema/layout.ts`. This is the ruling of 2026-10-01 (I3, built as W12).
  - A session's tab is filed in its project's set, and opening it moves the strip to that set: `openTab` in `src/renderer/src/stores/layout-model.ts` (through `switchSet`), with the set chosen by `setOfSession` in `stores/layout.ts`. A click on a project row moves the strip too: `toggleProject` in `src/renderer/src/sidebar/Sidebar.tsx` calls `setCurrentProject`. A session whose project changes has its tab moved to another set (`refile`).
  - Every New chat control runs the same code, `createSession(focusedProject())` in `src/renderer/src/keymap/actions-runtime.ts`: the sidebar's row, the strip's "+", ⌘N, the empty main area, the Overview. `focusedProject()` answers the project of the set the strip shows only when that project has a folder on this Mac. For a set whose project lives on another machine it answers none, the new chat is filed in the `none` set, and the strip jumps there. That jump is what reads as New chat replacing the tabs; the tabs are still in their own set, out of sight.
  - The `none` set keeps every earlier unstarted chat: an unstarted chat survives a relaunch through its setup intent (`retainsTab` in `src/renderer/src/sessions/connect.ts`) and nothing reuses an empty one. Those are the several New chats. The sidebar's New chat and the strip's "+" do not differ in code; what differed for the owner is the set each was pressed from.
  - A read of the layout file on one of the owner's machines on 2026-11-12 found 14 sets holding 28 tabs, one tab in the set that was showing.
- **After:**
  - **One strip.** The contract above. A click on a project or machine row opens or closes the row and nothing else. A session opens into the strip that is there, by the rules that already decide whether it replaces the tab in front or gets a tab of its own.
  - **The upgrade.** The first read of a stored value with more than one set applies the merge rule, writes the result back, and shows one notice: "Tabs from every project are now in one strip". A stored value that needs no merge but is not in the stored form (one set under a project's key, or an empty set beside `none`) is written back in the stored form too, without the notice: left as it was, its tabs would stay under the project's key while the side column's remembered session moved to `none`, and the next launch would not find that session. The tab menu gains "Close tabs to the right" beside "Close other tabs" (the pane's unpinned tabs right of that tab, each through its close guard), so a strip that arrives long can be cut in one act.
  - **The current project** is contract rule 5. It decides three things. The title bar's chip names it (O-31). New chat starts in it. Customize opened from the sidebar is scoped to it, as today through `focusedProject()`. The sidebar's selection is unchanged: the row of the session whose tab is in front is the selected row, and no project row is ever the selected one.
  - **How a tab names its place.** A session tab reads: its mark, its title, then its place in the small muted style the tab already has. The place is the name of its sidebar row (the project, or the machine's name for a session in no listed project) and, for a session on another machine, the machine as the sidebar marks it (`@name`). While that machine has not answered in this run the place is the machine alone. An unstarted chat's place is the project chosen in it. The place is drawn only when the session tabs in the strip are not all in one place, so a strip of one project on this Mac repeats nothing (the owner's l7-shell-05), and a mixed strip names every session's place (the example the owner chose from). When tabs shrink the place gives way before the title; the tooltip and the All tabs menu always carry both. A terminal session keeps its "Terminal" mark and an offline machine's tab its greyed title.
  - **New chat** is `newChat()`, the same from every control.
    - It opens an unstarted chat as a tab of the strip, after the tab in front of the pane asked for, with the keyboard in its composer.
    - Its project is the current project, or the row given by a project row's "+". It starts exactly as that row's "+" starts it on the registry branch: in the project's folder on this Mac when there is one; else on a machine that has the project, already chosen in the composer's machine menu; else with no project, where the composer reads "Choose a project". New chat is never refused for want of a project.
    - An empty unstarted chat is a chat with nothing typed or attached, no first message held, no start under way and no failed start to show. If the strip already holds one for the same project, New chat brings it to the front (moving it to the pane asked for, if it sits in the other) and creates nothing; otherwise it opens a new one. Every other empty chat in the strip is closed as it does so. That close is not the ordinary one: the ordinary close asks nothing of an empty chat, but it leaves the tab in the strip while its discard is on the way to main, and what the person types into it in that time would be discarded with it. So the chat is checked again and its tab is taken out of the strip in one step, before main is asked, and the tab is put back if main refuses; a chat that is in front, or is no longer empty at that moment, is left alone until the next press. So after a New chat the strip holds one empty chat, never two.
    - A press while an earlier press is still waiting for main makes no second chat.
    - The late arrival is #497.
    - A creation that carries something is not this rule's: the Worktrees dialog's chat on a checkout, the Library's "Ask Claude" with its prefilled prompt. Each makes its own chat and leaves an empty one alone.
