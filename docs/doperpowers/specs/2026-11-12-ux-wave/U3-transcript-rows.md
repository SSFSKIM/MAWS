- **Purpose:** Once this child lands, whatever enters a session from elsewhere reads the same on every route and takes one line. A message from another session or from a subagent is one dim line that opens on demand and folds with its turn. The end of a background task is one line where the agent was told, coloured by outcome, and a failed one no longer raises an error card. A peer's message is never drawn as the owner's own bubble, and the owner's own steer is never drawn as a peer's message. A slash command's output is a light line under the command. Code blocks wrap and stay inside the text column, message actions sit under the message, and an answer can be copied or forked from. A compaction in progress says so. The owner can find text in a session with ⌘F and move between prompts from the keyboard.

- **Contracts:**

  **UC-2 · One reading of every arrival (owned).** Its content, written once:

  *Words.* A **carrier** is the wire frame or transcript row that brought an arrival into a session: a `user` frame or row; a `queued_command` attachment row (what the engine took in at a tool boundary while a turn ran); a `hook_additional_context` attachment row (text a plugin's hook added to a tool's result or to the person's next prompt); an assistant frame or `system` row that carries a slash command's output. A **peer** is another session, on any machine. A **hand-back** is a subagent's final report to the session that started it. sminos is the owner's messaging between sessions; its **bridge** is the part of the sminos plugin that runs inside a session and delivers to it, and the engine's **inbox** is the engine's own socket for messages between sessions, which sminos uses when a session has no bridge. **sminos's frame line** is the first line sminos writes on what it delivers, naming the sender (`[sminos chat <project> <writer>:<seq> from <sender> → @you]`, `[sminos message from <sender> id=…]`); `[sminos steer from human]` opens the person's own steer and `[sminos bridge]` the bridge's own prompt that wakes a session.

  *The reader.* One pure module, `src/shared/engine/arrival.ts`, beside `peer-envelope.ts`, whose envelope and frame parsers it uses.

  ```ts
  /** Every arrival one wire frame or one transcript row carries, in order.
   *  Empty for the person's typed prompt and for anything that is no arrival. */
  export function readArrivals(row: unknown): Arrival[];

  /** Whose turn it is when the arrival opens one: `own` and `consent` are the person's, `peer` a peer's, every other class the engine's. */
  export function turnOriginOf(arrival: Arrival): 'human' | 'peer' | 'engine';

  /** MAWS's own answer envelope read from a message's text alone, for a message still waiting in MAWS's queue. */
  export function readAnswerEnvelope(text: string): Extract<Arrival, { class: 'answer' }> | null;

  export type Arrival =
    // a message from another session: by the engine's inbox, by the sminos bridge, or from a teammate
    | { class: 'peer'; via: 'inbox' | 'bridge' | 'team';
        sender: { name: string | null; address: string; session: string | null; owners: string[] | null };
        body: string;            // as drawn: sminos's frame line and reply line cut
        frame: string | null;    // sminos's frame line, kept whole for the reader that matches a send to its delivery
        midTurn: boolean; lineage: 'peer' | 'descendant'; replyTo: string | null }
    // a message from one of this session's subagents to its main conversation; `report` when it is a hand-back
    | { class: 'subagent'; agentId: string; body: string; report: string | null }
    // one <task-notification> block: a background command, agent, workflow, monitor or MCP task
    | { class: 'task'; taskId: string | null; toolUseId: string | null;
        outcome: 'completed' | 'failed' | 'stopped' | null;  // null: it reports no end (a monitor's event, a check-in on a quiet command)
        summary: string;         // the engine's own sentence, verbatim
        durationMs: number | null; outputFile: string | null;
        detail: string | null }  // what the engine delivered with it: the result, the note, the event's text
    // a scheduled prompt firing
    | { class: 'schedule'; prompt: string }
    // the person's answer to a question that was asked without waiting for it
    | { class: 'answer'; tool: 'maws' | 'sminos';
        call: string;            // the tool-use id of the call that asked
        summary: string;         // the answer as it was delivered to the model
        answers: AskAnswer[] | null }  // parsed, when the carrier holds them (MAWS's own envelope); else null
    // a slash command's output
    | { class: 'command'; run: { command: string; args: string } | null; stdout: string; stderr: string }
    // the person's own words delivered by a fallback route: theirs, never a peer's
    | { class: 'own'; via: 'chat' | 'steer'; words: string; frame: string }
    // the sminos bridge's own prompt, which wakes a session to read what it has not read
    | { class: 'wake' }
    // MAWS's own "Approve and retry" message for a call auto mode blocked (U1, l4-approvals-12): the person's act, not their prose
    | { class: 'consent'; kind: 'command' | 'call';
        subject: string };       // the command, or the call's input, as the message quotes it (JSON-unquoted)
  ```

  *Input.* The frame or row as the engine wrote it, parsed JSON: never an X1 event. X1 lowers a row's `origin` to one word, and who sent a row is proved only by the origin object (`{kind: 'plugin', asUser: true}`, a plugin's appended row, `{kind: 'task-notification', subkind: 'scheduled-trigger'}`).

  *Rules of reading.*
  1. **Marks first, text second.** A class is given only when the carrier's own marks allow it: its origin object, its envelope tag (`<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<task-notification>`, `<local-command-stdout>`), its attachment type, or the `local_command_source` field. A prompt the person typed is never an arrival whatever its text says: a frame line pasted into the composer stays the person's words. The two text-only readings are texts MAWS itself sends as prompts: its own answer envelope (`[MAWS ask <id>]`), and the consent message of U1's "Approve and retry", which is the engine's own sentence with one quoted string in it ("Permission granted for this exact command only, as one whole string: <…>. …"; U1's l4-approvals-12 holds the full text for a command and for a call). The reader matches that sentence whole, from its first word to its last, and nothing looser; a person who types the same sentence has said the same thing.
  2. **The frame line says whose a bridged row is.** Sender `human` is the person (`own`); any other sender is a peer. This holds for each way sminos delivers: the bridge submitting it as the user while the session is idle, the bridge appending it into a running turn, a queued command, and the engine's inbox envelope. A row that opens with `[sminos steer from human]` is the person's steer whichever of these carried it (X-032).
  3. **One carrier can hold several arrivals** (several `<task-notification>` blocks in one row, several answers in one hook context); each is read alone.
  4. **What no class claims is left alone.** The engine's other rows (the interrupt marker, the `!` command echo, a compaction's summary, a hook's feedback, a channel or coordinator message) keep the readers and the drawing they have today.

  *What a class becomes, the same from every caller.* Each caller turns a class into the same X1 events, so the transcript's model draws from events alone and cannot tell the routes apart.

  | class | the X1 events its carrier becomes | the turn it opens, when it opens one |
  |---|---|---|
  | `peer` | `user.message` of origin `peer` and its companion `peer.message`, exactly as an inbox message makes today | a peer's |
  | `subagent` | `user.message` of origin `peer` and its companion `subagent.message` (`from_child`) | the engine's |
  | `task`, `schedule`, `wake` | `user.message` of origin `task-notification` carrying the new field `arrival` | the engine's |
  | `answer` | from sminos: `user.message` of origin `task-notification`, synthetic, carrying `arrival`. MAWS's own envelope: today's steer event and turn, unchanged | from sminos: the engine's, when it arrived while the session was idle |
  | `command` | `user.message` of origin `local-command` whose content is the output; never an assistant block | none: it joins the command's turn |
  | `own` | `user.message` of origin `human` whose content is the words, the frame line cut | the person's |
  | `consent` | `user.message` of origin `human` carrying `arrival`; drawn as one line, "You approved `<subject>`", never as a bubble; it stays in view through a fold, as the person's own words do | the person's |

  X1's `user.message` gains one optional field, `arrival`: the arrivals of class `task`, `schedule`, `answer`, `wake` or `consent` read from its carrier (`peer` and `subagent` already have companion events that other code reads; `command` and `own` need none). It is an optional field and not a new event kind because of how builds a version apart talk over the machine link: the receiving side drops a key it does not know and keeps the event, while an event kind it does not know fails to read and is drawn as a gap (`src/shared/ipc/tolerant.ts`; `src/main/lane-b/remote-session.ts`). A machine on an older build therefore draws as it does today, and nothing breaks in either direction.

  *The rows.* One line each, in the CLI's wording. Two shapes serve every class: a **message line**, dim, led by `›`, for words from an agent; and a **notice line**, led by a dot whose colour is the outcome, for a fact about the session. The architect chose the CLI's one-line form over Claude Desktop's bordered cards because the owner asked for one line (O-12, O-28).
