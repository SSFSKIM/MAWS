- **Purpose:** Once this child lands, whatever enters a session from elsewhere reads the same on every route and takes one line. A message from another session or from a subagent is one dim line that opens on demand and folds with its turn. The end of a background task is one line where the agent was told, coloured by outcome, and a failed one no longer raises an error card. A peer's message is never drawn as the owner's own bubble, and the owner's own steer is never drawn as a peer's message. A slash command's output is a light line under the command. Code blocks wrap and stay inside the text column, message actions sit under the message, and an answer can be copied or forked from. A compaction in progress says so. The owner can find text in a session with ⌘F and move between prompts from the keyboard.

- **Contracts:**

  **UC-2 · One reading of every arrival (owned).** Its content, written once:

  *Words.* A **carrier** is the wire frame or transcript row that brought an arrival into a session: a `user` frame or row; a `queued_command` attachment row (what the engine took in at a tool boundary while a turn ran, or delivered with the person's next prompt); a `hook_additional_context` attachment row (text a plugin's hook added to a tool's result or to the person's next prompt); an assistant frame, a `user` frame or row, or a `system` row that carries a slash command's output; the terminal's `system` row of subtype `scheduled_task_fire`; and, for the two arrivals that reach an idle session MAWS runs with no `user` frame at all, the `system/task_notification` frame of a background task's end and the `command_lifecycle` frame of a scheduled fire. A **peer** is another session, on any machine. A **hand-back** is a subagent's final report to the session that started it. sminos is the owner's messaging between sessions; its **bridge** is the part of the sminos plugin that runs inside a session and delivers to it, and the engine's **inbox** is the engine's own socket for messages between sessions, which sminos uses for every message from a peer (sminos 1.46.2) and for the owner's own send wherever the bridge does not deliver: a session MAWS runs, where the bridge only observes, and a session that has no bridge. **sminos's frame line** is the first line sminos writes on what it delivers, naming the sender (`[sminos chat <project> <writer>:<seq> from <sender> → @you]`, `[sminos message from <sender> id=…]`); `[sminos steer from human]` opens the person's own steer and `[sminos bridge]` the bridge's own prompt that wakes a session. The bridge's **mirror line** is the log line it writes after a row it appended (`sminos: delivered: …`, `sminos: steer: …`), which a terminal keeps in the file as a `system` row of subtype `informational`.

  *The reader.* One pure module, `src/shared/engine/arrival.ts`, beside `peer-envelope.ts`, whose envelope and frame parsers it uses. `readArrivals` reads one frame or row alone. `readNext` is the same reading for a caller that maps a session in order; the three callers call it, so that an arrival with two carriers is read once and by one rule (rule 5).

  ```ts
  /** Every arrival one wire frame or one transcript row carries, in order.
   *  Empty for the person's typed prompt and for anything that is no arrival. */
  export function readArrivals(row: unknown): Arrival[];

  /** The same reading in order (rule 5). `open` is what earlier frames or rows of the session left open: a run whose
   *  report was handed back, a hand-back whose task notification has not come, a fire row, an appended delivery.
   *  A frame or row that is the second carrier of an arrival already read yields none. `OpenArrivals` is the module's
   *  own and opaque to a caller, which starts from `nothingOpen`. */
  export function readNext(row: unknown, open: OpenArrivals): { arrivals: Arrival[]; open: OpenArrivals };

  /** Whose turn it is when the arrival opens one: `own` and `consent` are the person's, `peer` a peer's, every other class the engine's. */
  export function turnOriginOf(arrival: Arrival): 'human' | 'peer' | 'engine';

  /** MAWS's own answer envelope read from a message's text alone, for a message still waiting in MAWS's queue. */
  export function readAnswerEnvelope(text: string): Extract<Arrival, { class: 'answer' }> | null;

  export type Arrival =
    // a message from another session: by the engine's inbox, by the sminos bridge, or from a teammate
    | { class: 'peer'; via: 'inbox' | 'bridge' | 'team';
        sender: { name: string | null; address: string; session: string | null; owners: string[] | null };
        body: string;            // as drawn: sminos's frame line and reply line cut
        frame: string | null;    // sminos's frame line, kept whole for the reader that matches a send to its delivery
        midTurn: boolean; lineage: 'peer' | 'descendant'; replyTo: string | null }
    // a message from one of this session's subagents to its main conversation; `report` when it is a hand-back
    | { class: 'subagent'; agentId: string; body: string; report: string | null;
        taskId: string | null }  // a hand-back's `senderTaskId`: the task whose end it is
    // a background task's notification: one <task-notification> block (a background command, agent, workflow, monitor or
    // MCP task), or, told to an idle session MAWS runs, the system/task_notification frame of a background command or monitor
    | { class: 'task'; taskId: string | null; toolUseId: string | null;
        runId: string | null;    // the run that ended: the frame's `run_id`, the origin's `runId`; null where the carrier names none
        outcome: 'completed' | 'failed' | 'stopped' | null;  // null: it reports no end (a monitor's event, the engine's notice that a command seems to wait for input, a check-in on a quiet command)
        summary: string;         // the engine's own sentence, verbatim; the block's first line when it has no <summary>
        durationMs: number | null;  // only an agent's and a workflow's notification carries one
        outputFile: string | null;
        detail: string | null }  // what the engine delivered with it: the result, the note, the event's text, the lines after the block
    // a scheduled prompt firing
    | { class: 'schedule'; prompt: string | null }  // null on the live wire, which does not carry the prompt's text
    // the person's answer to a question that was asked without waiting for it
    | { class: 'answer'; tool: 'maws' | 'sminos';
        call: string;            // the tool-use id of the call that asked
        summary: string;         // the answer as it was delivered to the model
        answers: AskAnswer[] | null }  // parsed, when the carrier holds them (MAWS's own envelope); else null
    // a slash command's output, its tags cut and a terminal's ANSI escapes removed
    | { class: 'command'; run: { command: string; args: string } | null; stdout: string; stderr: string }
    // the person's own words that sminos delivered (a send or a steer, through the inbox or by the bridge): theirs, never a peer's
    | { class: 'own'; via: 'chat' | 'steer'; words: string; frame: string }
    // the sminos bridge's own prompt, which wakes a session to read what it has not read
    | { class: 'wake' }
    // MAWS's own "Approve and retry" message for a call auto mode blocked (U1, l4-approvals-12): the person's act, not their prose
    | { class: 'consent'; kind: 'command' | 'call';
        subject: string };       // the command, or the call's input, as the message quotes it (JSON-unquoted)
  ```

  *Input.* The frame or row as the engine wrote it, parsed JSON: never an X1 event. X1 lowers a row's `origin` to one word, and what proves who sent a row is on the raw row alone: its origin object (`{kind: 'plugin', asUser: true}`, a plugin's appended row, `{kind: 'peer', handback: true, senderTaskId}`, `{kind: 'task-notification', runId}`) and, for the one class to which the engine gives no origin object on any route, a scheduled fire, the fields it writes in its place (rule 1).

  *Rules of reading.*
  1. **Marks first, text second.** A class is given only when the carrier's own marks allow it: its origin object, its envelope tag (`<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<task-notification>`, `<local-command-stdout>`), its attachment type, or the `local_command_source` field. One class has no origin object to read: a scheduled fire carries none on any route (probe 2: no frame and no row holds the `scheduled-trigger` subkind the engine's source names; the audit found none in 54 fires in the owner's files), so `schedule` is read from the fields the engine writes instead: `turnOrigin: 'scheduled'` on the file's meta `user` row, the terminal's `system` row of subtype `scheduled_task_fire`, and on the live wire the `command_lifecycle` frame of state `started` whose `wakeup_source` is `schedule_wakeup`. And the `system/task_notification` frame is a carrier only as O-28 says: for a task that was in the background, and only where its `summary` is the engine's sentence. A prompt the person typed is never an arrival whatever its text says: a frame line pasted into the composer stays the person's words. The two text-only readings are texts MAWS itself sends as prompts: its own answer envelope (`[MAWS ask <id>]`), and the consent message of U1's "Approve and retry", which is the engine's own sentence with one quoted string in it ("Permission granted for this exact command only, as one whole string: <…>. …"; U1's l4-approvals-12 holds the full text for a command and for a call). The reader matches that sentence whole, from its first word to its last, and nothing looser; a person who types the same sentence has said the same thing.
  2. **The frame line says whose a delivered row is.** Sender `human` is the person (`own`); any other sender is a peer. This holds for each way sminos delivers: the engine's inbox envelope (the only way in a session MAWS runs, where the origin's `name: 'human'` says the same as the frame line), the bridge submitting it as the user while the session is idle, the bridge appending it into a running turn, and a queued command. A row that opens with `[sminos steer from human]` is the person's steer whichever of these carried it (X-032).
  3. **One carrier can hold several arrivals** (several `<task-notification>` blocks in one row, several answers in one hook context); each is read alone. One block is one arrival even when it holds two things: a monitor's "stream ended" block can carry the monitor's last event inside it, which is then its `detail`.
  4. **What no class claims is left alone.** The engine's other rows (the interrupt marker, the `!` command echo, a compaction's summary, a hook's feedback, a channel or coordinator message, an unknown slash command, which is the model's prompt on the live wire and a warning row in a terminal's file) keep the readers and the drawing they have today.
  5. **An arrival with two carriers is read once.** Three pairs exist. In each, one carrier is the arrival and the other yields nothing: no row, and no turn beyond the one the arrival opens (`readNext`):
     - *An agent's end:* the hand-back (a `user` frame or row, or a `queued_command` row, of origin `{kind: 'peer', handback: true, handbackReportText, senderTaskId}`) and the task notification of the same task. What ties them: the origin's `senderTaskId` is the block's `<task-id>` and the `task_id` of the `system/task_notification` frame, and that frame's `handback_report.text` is the origin's `handbackReportText`. Where the agent handed back, the hand-back is the arrival and the notification of that run yields nothing; where the report was withheld, the notification is the arrival. Which of the two it is: on the live wire the frame says (`handback: 'send'` or `'withheld'`), and when it says `send`, that frame, a `user` frame that names its `run_id` and the turn whose `result` names it all yield nothing; in a file a hand-back claims the next notification of its task and no later one (the engine notifies again under the same task id when an agent is resumed and ends again), and where the session was idle the engine also marks that row `queueTranscriptOnly`.
     - *A scheduled fire in a terminal session:* the `system` row `scheduled_task_fire` and the meta `user` row after it, tied by that row's `scheduledFireId` (the fire row's uuid) where the engine wrote one, else by its place directly after. The fire row is the arrival; the `user` row yields nothing and is where the turn opens. The file of a session that ran headless has the `user` row alone, which is then the arrival.
     - *A delivery the bridge appended, in a terminal session:* the meta `user` row of the plugin's origin and the mirror line after it. The `user` row is the arrival; the mirror line yields nothing.
  6. **A notification block's outcome and text.** `<status>` gives the outcome: `completed`; `failed`; `killed`, `stopped`, `cancelled` and `interrupted` are all `stopped`. A block with no `<status>` reports no end and has `outcome: null`, never `completed`: a monitor's event (it carries `<event>`), the engine's notice that a command seems to wait for input, a check-in on a quiet command. Two fallbacks come from the audit of the owner's session files (about 3,200 carriers): a block with no `<summary>` (78 of them, with no child tag at all) takes the block's first line as its text; and an agent's block that says the agent was stopped and has no `<status>` (2 of them) is `stopped`, not "no end".
