- **Purpose:** Once this child lands the owner sends without thinking about modes. Enter always sends. While the agent works, Enter hands the message to the running turn and ⌘Enter keeps it for after the turn. A message that has not been read yet is drawn once, in a stack above the composer, where it can be sent now, taken back with ↑, edited or deleted. Around the box the controls get quieter and closer to Claude Desktop's: one small icon for send, stop and "this will wait"; a slash palette of names; a mode menu with Bypass set apart; a model chip that reads as a name; an effort control that can be hit; a paste that stays text; a project chooser that tells two folders of the same name apart; keys that reach the menus and the prompt history; and `/btw` as a small card at the bottom right that says how long it has been thinking.

## Sending: one design for l3-input-01, -02, -03, -04, -05, -08, -15 and X-049

Eight items are one change. This part states it once; the items that follow say what each one contributes and why.

**Words.** A *waiting message* is one the person sent and the agent has not read yet. It waits in one of two ways. *At the next step*: the engine holds it and reads it at the running turn's next tool boundary (in code, a pending steer of priority `next`). *After the turn*: MAWS's own queue holds it and sends it when the turn ends (in code, a `queued` entry of the app queue in the engine host). A message that Stop held back is an after-the-turn message in a paused queue. *The stack* is the list above the composer frame, and the only place a waiting message is drawn. *Send now* delivers a waiting message at once without stopping the agent's work where the engine can do that.

**What each key and control does, for a session MAWS runs.** "A request waits" means the turn is held at a permission prompt or a question that blocks it; a question the agent asked without waiting changes nothing in this table.

**Where a waiting message is shown.** In the stack, and nowhere else: not as a bubble in the transcript, not on the session's row or tab. The transcript draws a message when the engine has read it, at the place it was read. A message the engine dropped still draws as "Not sent" in the transcript, as today, because that is an outcome and not a wait.

**The stack.** One bordered list directly above the composer frame, present only while something waits.
- Rows are in the order they will be read: messages at the next step, oldest first, then messages after the turn, oldest first.
- A row is the message's text clamped to two lines (attachments and pasted chips named as today, `[Image #1]`, `[Pasted text #1 +40 lines]`), and at its right end when it goes: "Next step", "After the turn", or "Held" in a paused queue. The whole text is the row's hover title; a click on the text, or Enter on the focused row, opens the row to its whole text in place and closes it again, which changes neither the draft nor the queue.
- On hover or keyboard focus a row shows: Send now (an icon button), Delete (a bin), and a "…" menu with Edit and with the move to the other kind of wait ("Queue for after the turn" on a next-step row, "Send at the next step" on an after-the-turn row; both exist today as Hold and as the caret's item).
- Edit puts the message back in the composer, text and attachments, and removes it from the stack. It is offered only while the composer is empty, and says "The box holds a draft" otherwise. The inline editor inside a row (`QueueEdit.tsx`) goes.
- With one or two rows there is no header. With three or more the stack folds to one line, "N queued · Next: <the first row's text>", with a caret that opens it; open, it scrolls past five rows. Whether it is open is kept per session for the window's life, not saved.
- While the queue is paused the header is the pause's reason in today's words (`PAUSED_COPY` in `QueueList.tsx`) with Resume, and the stack is open.
- Three rows keep today's shape: a message that may not have been delivered (the crash-recovery row, with its warning, Resume, Edit and Delete); a submission that has lasted 300 ms ("Sending…"); and an answer to a question (X-049), which offers Send now only and is skipped by ↑.

**How Send now reaches the engine.** One new host command, for a message at the next step:

```
session.steer.sendNow { appSessionId, messageUuid } → { outcome: 'delivering' | 'stopped' | 'nothing_waiting' }
```

It writes the engine's control request `interrupt { send_now: true, message_uuid }` and returns the engine's own answer (`send_now` in the response). It does not pause MAWS's queue. `delivering`: the engine moved what could be moved; the row leaves the stack when the engine reports the message started. What follows depends on what was moved (P1): for a shell command the engine ends the turn (`result` of subtype `success` with `terminal_reason: aborted_tools`) and starts the message as the next turn; for a foreground subagent call the message is read in the same turn, with no `result` between; with a permission request pending the request is withdrawn, the turn ends the same way and the message runs next. `stopped`: nothing could be moved, so the engine ended the turn (`aborted_streaming`) and the message runs next. The host records each send-now it sends: a turn that ends as `aborted_tools` or `aborted_streaming` after one, with no Stop of the person's in between, is a send-now end. Its end reads "Ended for your message" and not "You stopped" (today's digest reads `aborted_tools` as a stop), it raises no "finished" notice, and it does not pause the queue. The host's record is needed because the `stopped` case is identical on the wire to a Stop except for the control response. In every case that ends the turn, the engine reports the lifecycle of the prompt that had started the cut turn as `cancelled` after `started`: that is the turn's cut, not a message the engine dropped, and it must not draw "Not sent" (a test pins it). `nothing_waiting`: the engine had already read it; nothing is shown. Send now on an after-the-turn row hands the entry to the engine at priority `now` (`session.queue.promote` with `now`), one step: P1 showed that a `now` message does on engine 2.1.322 what send-now does, moving a running command instead of killing it. With no turn running it is the same promote. Esc is Send now on the first row.

**How the automatic move works.** The engine host, not the window, watches each waiting next-step message that the person typed in the composer. The composer says so with a second command after the message is accepted:

```
session.steer.expedite { appSessionId, messageUuid } → void
```

While such a message waits, for each running Bash, Agent or Task call that has no result: once the engine has registered the call as a task (its `system/task_started` frame, which arrived 3.6 to 4.5 seconds after a shell call's frame in P1) and not sooner than three seconds after the call started, the host asks the engine to move it to the background with `background_tasks { tool_use_id }`, oldest call first. Before the call is registered the engine answers `backgrounded: false`, so a timer alone fails on its first try; a call the engine answers `false` for is retried each second for fifteen seconds. Once moved, the waiting message is read in the same turn (P1, three of three for a shell command and for a foreground subagent call); at most two calls are moved for one message; the watch ends when the engine reports the message started, when it is withdrawn, or after two minutes. The three seconds, the retry and the limit of two are Claude Desktop's (`main-process/index.chunk-BjORVu2_.js:720-748, 46950-47067`); the two-minute end is this section's own bound. This request can only move a call; it never interrupts. Messages that reach the session any other way (another session's message, an answer to a question, a comment sent to the main conversation) are never expedited: only the person's typing may move the agent's command.
