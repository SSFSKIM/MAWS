# U6 · Files, links and the keyboard

> **A child of the UX wave.** Root: `docs/doperpowers/specs/2026-11-12-ux-wave-design.md`. Read it first: it holds the wave's purpose, its laws (law 1 to law 8), the contracts UC-1 to UC-15, the ordering and the record. This file is this child's section of that document. Where this file and a contract's statement in the root differ, the root binds; report the difference. **Grain:** plan. Items are named by their ids in the register, `docs/doperpowers/evidence/ux-wave-2026-11/register.md`.

- **Purpose:** Once this child lands, opening a file never takes the conversation away: a file opens beside the chat, as a tab inside the Files side surface, and moves to the main area only when the owner asks. Files shows what changed and finds a file by name. A link the agent writes opens in MAWS whatever form it takes (a path, a `file://` URL, a PDF, a localhost address), and when it cannot open, the notice says why in plain words. A Word, PowerPoint or Excel file the agent wrote is drawn inside MAWS, read-only, with the Mac's own app one click away; a mention of an artifact reads as a link, and only the person opens it. "Open in" hands a file or the session's folder to an editor, a terminal or Finder. The keyboard reaches everything: chords for the side surfaces, Back and Forward, zoom, a palette that opens on what was used last, and one table behind the menus, the shortcut sheet and every child's new chord.

    - **The shape.** `ActionSpec` gains three things, and nothing else changes:

      ```ts
      menu: 'app' | 'file' | 'edit' | 'view' | 'go' | 'help' | null; // 'edit' is new: placed after the Edit menu's own items
      submenu?: string; // the submenu of its menu the item sits in ('Find', 'Tabs', 'More surfaces', 'Comments')
      fixed?: true;     // a key its own editing surface handles (Enter in the composer): listed, never dispatched, not rebindable
      ```

    - **Stored rebindings.** A rebinding the person stored wins over a default a later build gives another action: while their override holds a chord, the action that has it as its default reads as unbound (`effectiveChord`), and nothing stored is rewritten. A `fixed` row takes no rebinding. While build F may run on the same profile (UC-14), a row whose id F does not know takes none either: F's reader of `settings.json` is closed over its own action ids, and one unknown id fails its whole read of the client settings. Such a row is dispatched and listed like any other, but no route stores an override for it and Settings › Keyboard draws no control to change it. The ids F knows are one constant under `src/shared/keymap/` (they are the table as it stood before this wave), deleted with this rule when F is no longer a build to go back to.
    - **How a chord reaches the right region.** Two mechanisms exist in the code and a new chord picks one.
      - `sink: 'menu'`: the chord is the accelerator of a menu item (`menuTemplate`, `src/main/menu.ts`). macOS hands the key to the focused element first; if nothing there takes it, the menu item fires, main emits `layout.action`, and the renderer runs the handler (`runAction`), which finds its own target (the focused pane's session, the terminal that holds the keyboard). A menu chord therefore works wherever the keyboard is, including inside a terminal (`terminalKeyFilter` passes every ⌘ chord but ⌘C, ⌘V and ⌘A) and inside a page of the in-app browser (`keyAction` in `src/main/browser/keys.ts` takes only the page's own chords).
      - `sink: 'renderer'`: the key is matched in the page before any editor sees it (`dispatchKey`, a capture-phase listener) and reaches a `useKeyChord` binding by its `scope`. `app`: anywhere. `composer`: only when the key is typed inside an element marked `data-key-sink="composer"`. `pane`: only inside the binding's own element, which must hold the keyboard; never from a text field, a button, an open menu or dialog, or during input-method composition. Pane and composer rows never go in the menu, which cannot see focus.
      - **Focus first.** A region that has its own meaning for a key keeps that key while it holds the keyboard; everywhere else the key is the app's. This is the rule behind "⌘F acts on the focused region", and it needs no new machinery for a `menu` chord: an editor keeps a key simply by handling it. So a chord an editor may keep is a `menu` row; a chord that must win even inside an editor or a terminal (⌘. stop, ⌘L) is a `renderer` row with scope `app`.
      - **F6.** A child that adds a region to the window marks it so that F6 stops there: the stops are read from the DOM (`regionStops` in `src/renderer/src/keymap/shell-navigation.ts`: `#region-sidebar`, each `[data-pane]`, `[data-region="cards"]`, each `[data-surface]`).

- **Which files** [design]. A file is previewed when its name ends in `.docx`, `.pptx` or `.xlsx`, the files service answered it as binary, and its first four bytes are a zip's (`50 4B 03 04`).   export type OfficeFormat = 'docx' | 'pptx' | 'xlsx';
  ```ts
  export const OFFICE_PREVIEW_MAX_BYTES = 25 * 1024 * 1024;
  export type OfficeProblem = 'too-large' | 'protected' | 'old-format' | 'not-office';

  export function officeOf(name: string, bytes: number, head: Uint8Array): { format: OfficeFormat; problem: OfficeProblem | null } | null;
  ```

  It is asked only for a file the service answered as binary, and answers `null` for any other name (the viewer goes on as today). `old-format` is a `.doc`, `.xls` or `.ppt` name (the format is then the modern one of the same family). `protected` is a modern name whose first eight bytes are the compound-file signature (`D0 CF 11 E0 A1 B1 1A E1`), which is what a password-protected Office file is on disk. `not-office` is a modern name that is neither. `too-large` is a size over 25 MiB, checked first. - **How the bytes are checked before a library sees them** [design; the architect's rulings 2 and 5 on the review]. The frame's page runs a pass of MAWS's own over the archive first, and gives the buffer to a library only if the pass ends clean. The pass is about 150 lines, uses the browser's own inflater as a stream (`DecompressionStream('deflate-raw')`), counts what actually comes out, keeps none of it, and cancels the stream at a limit.
  1. *Structure.* It reads the end record and the central directory. It ends `unreadable` for: no end record; more than one disk; zip64 records; a method other than stored or deflate; an entry whose local header is not where the directory says, or names another file; two entries whose data overlap. It ends `protected` for an encrypted entry.
  2. *Count.* More than 4,000 entries: `too-big`.
  3. *Each entry, in the directory's order.* It inflates the entry, counting the output and computing its CRC-32. It ends `too-big` when one entry's output passes its limit (64 MiB for an entry whose first bytes are a picture's, 8 MiB for any other, which is where the XML is) or when the output of all entries passes 256 MiB. It ends `incoherent` when an entry's output length or CRC-32 is not the directory's.
  4. *Pictures.* For an entry whose first bytes are a PNG's, JPEG's, GIF's, BMP's or WebP's, it reads the picture's size in pixels from its header, and ends `too-big` when one picture is over 32 megapixels or all together are over 128 (at four bytes a pixel, 128 MiB and 512 MiB once decoded).

  The four archive figures are those of Claude Desktop's own Word and slides viewer (`renderer/file_viewer/app/turns-DjPfi_md.js:25277-25282`); the pixel figures are this design's. A worksheet's XML is the one part the 8 MiB limit may be raised for, by Excel's qualification and nothing else. The size the directory declares for an entry is never trusted for a limit: only the count of what came out. The spike confirmed the means: the inflater exists in the frame, and a page counted a stream's output and cancelled it part-way.
- **A file that changes while it is read** [design; ruling 5]. A size that stays the same does not show that the chunks are of one file: a file replaced, or rewritten at the same size, between two chunks gives bytes that never existed together, and the files service hashes a whole file only up to 8 MiB. The archive pass is the check. A buffer whose every entry inflates to the length and CRC-32 that the buffer's own directory states is an archive that reads coherently; anything else ends `incoherent` or `unreadable`, which the view takes to mean "the file is being written": it reads again, three reads at most, 300 ms apart, and then waits for the next `files.changed`.
  - *A replacement* (a new file renamed over the old): each chunk call opens the path anew, so chunks can come from both files. The directory comes from the last chunk; an entry whose bytes came from the other file fails its CRC unless those bytes are the same in both, and then the buffer is the new file there.
  - *A rewrite in place* (the file truncated and written again, which is how the common Python libraries save): a read during the write finds no end record, or a short entry, and is read again.
  - *Another machine, an older daemon.* It answers the same chunks and no hash for a large file. The check runs in the frame's page on the bytes that arrived, so it is the same check and needs nothing from the daemon.
  - *What this does not close.* A directory that itself lies across two chunks read from two versions, and still parses, with each record matching bytes of its own version, would pass as a mixture of whole entries from both. It needs the two directories to line up on an 8 MiB chunk boundary; it cannot happen to a file of at most 8 MiB, which one call reads from one open file; and the change event that follows the write draws the file again. CRC-32 detects accidents, not intent; nothing here is a security claim.
- **What bounds memory, and what only recovers** [design; ruling 2]. Bounds, each before the fact: the file's size (25 MiB); the archive pass's limits on actual output and on pictures' pixels; one draw at a time; and the frame being a process apart from the window's. Not bounded ahead of time: what a library allocates while it builds its drawing from bytes that passed. Main's reading of the preview processes' memory once a second is *recovery*: it ends a preview that has already grown, up to a second late. It is not described anywhere in this design as a limit.
  - **One draw at a time.** In a window, one preview at a time is being read, checked or drawn; another waits, showing "Loading".
  - **One budget for all of them.** Main sums the working sets of the window's preview processes. Over 2 GiB (Claude Desktop's figure for one viewer, `main-process/index.chunk-DuEFl4bp.js:58`, taken here for the sum) it ends the one that is drawing, or with none drawing the largest.
  - **A replacement draw** (the file changed) runs beside the drawing it replaces only when that sum is under 1 GiB as it starts. Otherwise the old drawing is removed first and the tab shows "Loading" for the redraw.
- **What ends a preview** [design; the architect's ruling 3 on the review, and the spike; the three bounds of time, processor and memory are Claude Desktop's, `main-process/index.chunk-DuEFl4bp.js:52-62, 387-425`]. Main reads the preview frames once a second while one exists: no event fires when a frame's process dies, so every guard on main's side is a reading, up to a second late.

  | the guard | the rule | ends as |
  |---|---|---|
  | before the hand-over | main compares the frame's process with the window's own (`WebFrameMain.osProcessId` of each); when they are the same, the window hands over no bytes | `unsafe` |
  | too long to draw | no `drawn` within 30 s of the hand-over | `slow` |
  | stopped answering | from `drawn` on, for as long as the frame lives, the window asks every 5 s and the page must answer; six asks in a row unanswered | `unresponsive` |
  | its process is gone | main's reading finds the frame destroyed or detached (`WebFrameMain.isDestroyed()`, `detached`), or its process absent from `app.getAppMetrics()`. The spike saw all three within about 23 ms of a kill, and the window's page saw nothing | `gone` |
  | too much memory | the budget above | `memory` |
  | too much processor | the frame's process gained half a second or more of processor time in each of 30 consecutive one-second readings (from the reading's `cpu.cumulativeCPUUsage`, so the number of cores does not enter). A reading is left out when, in that second, a key reached that frame or the pointer was over it; at most 60 readings in a row are left out | `busy` |

  The count of unanswered asks, not the clock, decides `unresponsive`, so a Mac that slept does not end a preview. Ending is always the same act: the window removes the frame, and its process goes with it (25 ms in the spike). What main can know of input inside a frame is narrow: a key typed there reaches main's `before-input-event` on the window, and main's `input-event` never fires for it; a pointer moving or a wheel turning inside the frame reaches nothing main or the window can hear. So the window tells main two facts it does know, that the pointer is over a frame's element and that the keyboard is in it, and the pointer being over the frame stands for pointer input. The cap of 60 keeps a preview that spins under a resting pointer from running on: it ends after a minute and a half.

- **The way out to the Mac's own app** [design]. "Open externally" is the existing button (`OpenExternally` in `ExternalRow.tsx`): on this Mac it hands the file to the system's app for it (`files.openExternal`, with `named`); for a session on another machine it opens a copy here and says so, as today. - **When the file changes on disk while it is open** [design: the file viewer's existing rule, which replaces a text or an image in place]. The store's watch reports the change as today. The view waits until the file has been quiet for half a second, reads it whole again, and compares its SHA-256 with the drawn one. The same bytes change nothing. Different bytes are drawn in a second frame behind the first, under a token of its own and so in a process of its own (or after it, by the budget rule above), with the place the person was at; when it says `drawn` the two swap and the bar shows "Updated" as it does for text. Claude Desktop's Files pane also refreshes an open document by itself, with no notice, and re-reads it only when its content hash moved (`web/app/v1/cb6e2b522-B5TBumEO.js:619-648`; `web/app/v1/cd2efac6e-DJ0bDCna.js:7487-7556`). The place (a scroll ratio; a slide; a sheet and its scroll) is the page's own note, at most 1 KiB, kept per tab in the store's view state for the run. - **A link inside a previewed file** [design; that a click does nothing more is the owner's answer of 2026-11-15, "Nothing; show the address (Recommended)"]. - **What an Excel preview may show** [owner: "Compute and say so (Recommended)"; the three rules are the architect's ruling 7 on the review and what the owner's drawing showed; the means are design]. A number that looks right and is wrong is worse than no preview. Three rules hold for every workbook that is shown, and a workbook for which MAWS cannot keep them is not shown (the notice above).
  1. *A value stored in the file is shown as stored.* It is never replaced by a recomputation that differs, unless the cell carries a mark saying so.
  2. *A cell that cannot be computed says so.* It shows the words "not computed" in the quiet colour, as drawn, never a zero and never a blank.
  3. *The bar says who computed.* When any value on screen was computed by the preview, the bar reads "Formulas computed by the preview, not by Excel" in place of "Preview".

From that alone it knows whether rule 3's sentence applies, and it decides which unstored formulas are *computable*: every function the formula names is on the list the qualification passed, and it has no reference to another workbook. What the library's public description gives and does not give:

  | needed for | given by the library's plain API, by its published description | not known; the qualification finds out |
  |---|---|---|
  | loading the engine without a network fetch | `setWasmSource` takes a URL, bytes or a compiled module | — |
  | read-only, no export | `readOnly`; the toolbar and the context menu are replaceable by nodes of MAWS's own, so its download and export are not reachable | whether any key still exports |
  | the theme | a dark switch, header and selection colours, `getCellStyle` | how much of the grid's chrome they cover |
  | rule 1 | "cached formula values" are listed as supported | whether a cell with a stored value is recomputed on load, and whether that can be switched off; whether a cell's computed value can be read to compare |
  | rule 2 | `getCellStyle` is called for every drawn cell with its address and its display text, and can set colour, fill, borders and text decoration | what the engine shows for a function it lacks, a circular reference and an external reference (an error text, a blank, a zero); whether MAWS can put its own words in a cell, which the default canvas drawing may not allow |
  | rule 3 | — (MAWS's own reading) | — |
  | the sheet tabs at the foot, as drawn | the list of sheets is given to a subscriber | the library draws its own strip at the top (the probe's picture); whether that strip can be hidden and the sheet in view set from outside. If not, the place of the tabs returns to the architect before the landing |

  **The qualification** gates the Excel landing. A fixture set of about twenty-five invented workbooks (the owner was told "about twenty"), written without stored values and again with them, covers: arithmetic and the aggregates (SUM, AVERAGE, MIN, MAX, COUNT, COUNTA); conditions (IF, IFS, IFERROR, AND, OR); conditional aggregates (SUMIF, SUMIFS, COUNTIF, COUNTIFS, AVERAGEIF, SUMPRODUCT); lookups (VLOOKUP, HLOOKUP, INDEX with MATCH, XLOOKUP); text (CONCAT, TEXTJOIN, LEFT, RIGHT, MID, LEN, TRIM, TEXT); dates (DATE, YEAR, MONTH, EDATE, EOMONTH, DATEDIF, NETWORKDAYS, the 1900 leap day); rounding (ROUND, ROUNDUP, ROUNDDOWN, INT, MOD); finance (PMT, NPV, IRR); statistics (MEDIAN, STDEV); dynamic arrays (FILTER, UNIQUE, SORT, SEQUENCE, and a spill); references across sheets, defined names and table references; error values carried through a chain; a reference to another workbook; a circular reference; the volatile functions (NOW, TODAY, RAND, OFFSET, INDIRECT); and a stored value that deliberately disagrees with its formula. Each fixture carries its expected values, stated by its generator and checked against a LibreOffice recalculation. It passes when every cell on screen either shows the expected value or shows the "not computed" mark, and no cell shows a wrong value; a function that fails goes off the computable list. The outcomes:
  - Rules 1 and 2 can be kept cell by cell (the engine leaves stored values alone or lets MAWS compare; MAWS can mark a cell): Excel lands as described.
  - A cell cannot be marked: a workbook with any formula that is not computable is not shown, and its notice says so without naming a function. That is less than the owner was shown (a cell that says "not computed" in a workbook that is otherwise drawn), so before it is built it is put to the owner (the question, with its options, is under Waiting). A workbook the engine would recompute over stored values that differ is not shown either.
  - The engine is wrong on a common family, or cannot be held to the rules at all: there is no Excel preview. An `.xlsx` keeps today's row with Open externally. Nothing is put in its place silently: a table that never computes was the owner's other option, and was not chosen.
- **What is stored, and build F** [design]. Nothing new is stored. A previewed file is a `file` tab with its path, the form F already reads and writes (UC-14); the place inside a preview lives in memory for the run. F opens such a tab with its own "Binary file" row. Nothing crosses a machine link that F does not know: what the window and main say to each other about a preview stays between them, and the wire's minor does not change.

**(b) The host: a sandboxed frame, and what it rests on**

- **The frame** [the architect's ruling after the spike]. `OfficeFrame.tsx`, beside the file viewer, draws `<iframe sandbox="allow-scripts">` at `maws-viewer://<token>/viewer.html?format=<docx|pptx|xlsx>`. The token is 32 hex characters drawn afresh for each mount. That is load-bearing: in the spike two frames of one host shared a process, and frames of different hosts each had their own. The frame's origin is opaque, it is a secure context, and it has no storage, no cookies and no IPC (the window's preload runs in the top frame only).
  - **The scheme.** `maws-viewer` is registered with the store's scheme in the one call Electron allows (`registerStoreSchemes` in `src/render/scheme.ts`), with `standard`, `secure`, `stream`, `corsEnabled` and `supportFetchAPI`. Its handler (`src/main/viewers/scheme.ts`, on the default session of the app process only) answers GET and HEAD of exactly the files the build's manifest lists for the viewer page, for a host of 32 hex characters, and 404 for anything else. Every answer carries `nosniff`, `Access-Control-Allow-Origin: *` (the frame's own module and WebAssembly loads are cross-origin requests from an opaque origin) and the policy.
  - **The policies**, exact. The spike's `webrtc 'block'` is not in them: Chromium 152 does not know the directive and logs it as unrecognised.

    ```
    Word, PowerPoint:
    sandbox allow-scripts; default-src 'none'; script-src maws-viewer:; style-src maws-viewer: 'unsafe-inline'; img-src maws-viewer: data: blob:; font-src maws-viewer: data: blob:; connect-src 'none'; media-src 'none'; worker-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'
    Excel: the same, with
    script-src maws-viewer: 'wasm-unsafe-eval'   and   connect-src maws-viewer: data: blob:
    ```

    No policy has `'unsafe-inline'` or `'unsafe-eval'` for script, so text from a file can never become script. The spike made 20 attempts to run script that the page did not ship (inline, `on…=` attributes, `javascript:`, `eval`, `data:` and `blob:` scripts, markup through `innerHTML`, `DOMParser` and `document.write`); none ran, and all three libraries drew their samples with no policy violation. Under the Word policy WebAssembly is refused; under the Excel policy the engine loads from the page's own host.
  - **The page.** A second entry of the renderer's build (`src/renderer/viewer.html` with `src/renderer/viewer/`), as the repair page is. Its entry script holds the messages, the archive pass and the click guard; each format's module is a dynamic import made when a file of that format arrives; the Excel engine and its fonts are assets that module asks for. Nothing in the window's own module graph imports any of the three libraries, which a test holds. The window's start and its bundle do not change; the app on disk grows by about 22 MB, almost all of it Excel's. The three libraries are pinned to exact versions.
  - **The messages**, exact (`src/shared/viewers/messages.ts`; both sides parse with these schemas). The window posts to the frame's own window with `'*'` (an opaque origin has no name) and only after `ready`; it reads a message only when `event.source` is that frame's window.

    ```ts
    // window → frame
    { type: 'maws-preview:file', format: OfficeFormat, name: string, bytes: ArrayBuffer, tokens: Record<string, string>, place: unknown } // once, after `ready`; `bytes` transferred
    { type: 'maws-preview:ask', n: number }                          // every 5 s from `drawn` on
    // frame → window
    { type: 'maws-preview:ready' }
    { type: 'maws-preview:drawn' }
    { type: 'maws-preview:failed', reason: 'unreadable' | 'incoherent' | 'protected' | 'too-big' | 'failed', detail: string } // detail ≤ 300 characters
    { type: 'maws-preview:place', place: unknown }                   // ≤ 1 KiB serialised; at most 4 a second
    { type: 'maws-preview:answer', n: number }
    ```

    `tokens` are the resolved values of the design tokens the page's own chrome uses. A transferred buffer of 25 MiB arrived whole in 64 to 76 ms in the spike, and left the sender empty.
  - **Between the window and main**, none of it across a machine link (`src/shared/ipc/schema/`, owner `main`): the command `viewers.admit { token }`, answered `{ shared: boolean, room: boolean }` (whether that frame's process is the window's own; whether the budget's sum is under 1 GiB) and asked before every hand-over; the command `viewers.attention { token, pointer: boolean, keyboard: boolean }`, sent when either changes; the event `viewers.stopped { token, reason: 'memory' | 'busy' | 'gone' }`. Main finds a token's frame among the window's frames by its URL's host (`src/main/viewers/watch.ts`).

- **The condition setting 1 rests on: the window's session makes no remote request of its own** [design; re-read at the cited master]. The proxy sits on the default session, which three kinds of window use: the app's windows (`src/main/window.ts`), the presenter's two (`src/main/presentations/present.ts`) and the repair window (`src/main/repair/index.ts`). Everything else has a session of its own: the in-app browser's tabs, popups and import views (its partitions), the capture and export windows (the capture partition). Ruled after the design's revision: this form of the host stands; the P5 architect read the presenter's windows and the repair window, and both load the app's own URL or file under main's policy.
  - *The main process.* No file under `src/` imports Electron's `net`, and none calls `net.fetch`, `net.request` or a `fetch` of the default session. Other machines are reached over the machine link, a Node socket.
  - *The window's page.* The production policy (`PRODUCTION_CSP` in `src/main/csp.ts`) names no remote origin in any directive: `'self'`, `'unsafe-inline'` for style, `data:`, `blob:` and `maws-artifact:` are all it has. Counted in the window's own code and the artifact editors it bundles (`src/renderer/src`, `src/artifacts`, tests and the development harness left out): **no** `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, beacon, worker, WebRTC or speech recognition call; **no** remote address in any style sheet or `@font-face`; and of the about twenty-five elements there that load something (`img`, `video`, `audio`, `iframe`), every source is image data, a `maws-artifact:` address or an inline document. A Markdown image in a transcript that is not inline data is drawn as a chip and loads nothing (`remarkTranscriptSources`); a tab's favicon, a bookmark's icon, an extension's icon, a profile's picture and a catalog icon each arrive from main as image data.

  - **The guard**, two parts, so that the condition cannot rot unseen.
