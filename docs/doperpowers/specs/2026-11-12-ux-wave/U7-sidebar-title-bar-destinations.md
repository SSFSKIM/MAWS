## S-11 · A new session is named by six words of its prompt

- **Today:** a session's title is projected in one place, `titleOf` in `src/services/index/sessions.ts`: the person's rename, then the engine's title, then the generated title, then the first prompt with its markup removed (`promptTitle`), uncut. The launch seeds the prompt (`firstPrompt`) so that the row is never blank, a ruling of 2026-10-01 (W11, I1). So every new session shows its whole first message as its name for some seconds, and for good when no title is ever generated. Another machine's listing carries the same projected text.
- **After:** the last step of the projection cuts the prompt as Claude Desktop cuts it. File mentions at the very start of the prompt are taken off first, one after another (Desktop's pattern is the quoted form, `@"path"` followed by a space, a line break or the end; MAWS's composer also writes a path that has no space bare, as `@path`, and the step covers both forms of a file mention). Then the first six words split on white space; when the mentions were all there was, the names of the mentioned files joined with ", " instead. If the result is longer than 60 characters, its first 59 and "…"; counted by code point, so a pair of surrogates is never split. The rename, the engine's title and the generated title are untouched. The stored prompt is untouched, so the conversation search, which reads the stored prompt, still matches all of it.
  - A session MAWS runs and a terminal session: both are named by this Mac's index, so both change.
  - A session on another machine: named by that machine's index, so it changes when that machine runs the wave's build. The window makes no second cut: it cannot tell a prompt from a title the person chose.
- **Why this, not that:** the row stays identifiable from the first second among many new sessions, which is what the 2026-10-01 ruling was for, and the long name is gone. This is built as Claude Desktop builds it, in its timing as well as in its cut. At the start of a local session Desktop cuts the first message (`di`, `readable/app-5.1231.2/web/app/v1/cef1e6037-C_l5Pvir.js:2017-2034`) and gives the result as the session's title before its title generator has answered (`:3767`, `:3779-3782`, `:3817-3823`); the generated title takes its place only while the title is still empty or still those words (`:3833-3847`), and the words stay when generation fails (`:3783-3790`). "Untitled session" is its fallback for a session with no title at all (`cd50800c7-D1LorkLv.js:385-389`). The cut is Desktop's too: the mentions at the start (`cef1e6037-C_l5Pvir.js:2018-2024`, the pattern at `shared-5-C9P6KnmH.js:16138`), six words, 60 code points. The one thing MAWS adds to the copied rule is the bare form of a mention, which Desktop's pattern does not match.
- **Not included:** no change to how or when a title is generated. The sidebar's own filter field matches the shown title, so a word past the sixth of an untitled session is found by "Search in conversations", not by the filter. A side thread's name is seeded through the same field and passes through the same cut for the moment before its rename lands.

## O-16 · Hide a session, and get it back

- **Today:** there is no hide. An expanded project shows five sessions, eight after Show more, the rest only in the Resume picker (`shownTrees` in `sidebar/derive.ts`); under the Priority sort finished sessions fall to the end but still fill the five places when fewer than five are active. Archive is a different act: it stops a process MAWS runs, is refused for a session a terminal holds, and is not offered for a session on another machine (`archiveRecord` in `src/services/sessions/record-actions.ts`, `sessionActionsFor` in `app/session-actions.ts`). A row of a session that is only listed has no menu at all unless the person may share it (`sidebar/ListedRow.tsx`).
- **After:**
  - **Hide** is an item in every session row's menu: the row's three dots and its context menu, for a local session, for a session on another machine that is open here, and for one that is only listed. The three dots therefore show on hover on every session row, where today only a row that can be renamed has them. Choosing Hide hides at once: no confirmation, nothing stopped, nothing sent to any machine.
  - A hidden session is not drawn among its project's sessions and does not count against the five and the eight. At the end of the project, after Show more, one row reads **Hidden · N**. It opens in place to the hidden sessions, newest activity first, each an ordinary row whose menu offers **Unhide** where the others offer Hide. The row is a tree item the arrow keys reach; it closes when its project closes and is closed after a relaunch.
  - **Unhide** returns the session to the project's list at its head, in the place a session started from this window takes (`leadsAsSpawned` in `sidebar/derive.ts`), until its next turn ends or the app restarts; after that it ranks like any other.
  - A hidden session **returns by itself** when it starts a turn after it was hidden.
  - Hiding changes nothing else: the session still counts in its project's waiting and working marks, is still listed under Needs you while it waits (UC-1), still appears in the sidebar's filter, in the Resume picker and in the palette, and keeps its open tab. A hidden pinned session is under Hidden and is pinned again when unhidden.
  - What is stored: a per-device layout key beside `sidebar.people`, written through the layout store's `layout.set`:
    ```ts
    // key `sidebar.hidden`
    { version: 1, hidden: Record<AppSessionId, string> }   // session address → when it was hidden (ISO-8601)
    ```
    A session is drawn hidden while it has an entry and has started no turn since that time (a record's turn start; a listing's `busy` state issued after it). The store deletes an entry when it sees such a turn, and when the session is archived or deleted.
  - Routes: the three are the same, because the key is a session's address and the act never leaves this window.
- **Why this, not that:** the owner asked for it in these words, and archive cannot do it: it cannot reach a session a terminal holds or a session on another machine, which are a large part of what crowds the list. The strongest alternative is Claude Desktop's own answer to the same clutter, which has no per-session hide. Desktop cuts every group of its sidebar to a first run of rows and keeps the rest behind "Show {count} more in {bucketLabel}", with "Show less in {bucketLabel}", "Load more sessions" and "Show more sessions" (`readable/app-5.1231.2/web/app/v1/shared-63-B1QmL_kC.js:7137-7163`), beside archive and folding by date; the words Active, Archived and All are in its catalogue, and the control that uses them was not traced. So the benchmark has the "show more" half of the owner's words ("a quick, one-click 'hide' that defers session behind 'show more'") with no act of hiding, and MAWS has that half already (five rows, eight after Show more). Hide is MAWS's own, on purpose: the owner asked for the act itself, one click on a chosen session, which a cut by order does not give, and archive cannot stand in for it, for the reason above. Storing the set in each machine's record of the reader (beside Pin) was the other alternative; it would follow the owner to another Mac, at the cost of a record change on every machine, and it still could not hold a listed row. It lost under law 4.
- **Not included:** no automatic hide (the opt-in automatic archive already exists); no hide for a project (Remove from sidebar exists); the set does not travel to the owner's other Macs. "One click" is read as one act with no confirmation; a hide button drawn on the row itself is not added (law 3); this is a reading the owner may see differently, and it is on the list put to the owner with the spec.

## O-38 · A listed session opens in a tab of its own   (carries #559)

- **Today:** a local session's row offers Open, Open in new tab and Open in split, and honours ⌘-click and middle-click (`sidebar/SessionRow.tsx`). A row of a session on another machine that is only listed calls its lane's opener with no choice (`activate` in `sidebar/ListedRow.tsx`), has no `onAuxClick`, and has a menu only for Share. Both lanes' openers already accept a new-tab request (`RemoteOpener` in `sessions/remote-openers.ts`; registered in `lane-a/remote-connect.ts` and `lane-b/remote-connect.ts`). A Needs you row's ⌘-click on a listed session skips the opener and opens the tab directly (`sidebar/NeedsYou.tsx`), so the retry that the opener makes for a session whose stream had ended does not run.
- **After:** a listed row's menu offers Open and Open in new tab (then Hide, then Share where it has it). ⌘-click and middle-click call the opener with the new-tab request; a plain click and Enter are as before. `openListed` takes the same request and Needs you passes it, so every way of opening a listed session goes through its lane's opener. Where a lane has registered no opener the two items are drawn disabled with "Not available here", as other menu items are.
  - A session MAWS runs and a terminal session on this Mac: unchanged, already built.
  - A session on another machine, of either kind: this item.
- **Why this, not that:** it is the same rule local rows already follow (the browser's rule, ruled as I2). Claude Desktop has no tab strip; its ⌘-click pops a session out to a window, which this wave does not build (l7-shell-10).
- **Not included:** Open in split for a listed row (the opener has none; a tab can be split once it is open).

## #407 · The sidebar says "reconnecting" while this Mac's daemon restarts

- **Today:** the sidebar's skeleton ends when the first read of this Mac's sessions has answered and the roster has settled, whether or not that read succeeded (`sessions().setLoaded()` in `src/renderer/src/ipc/events.ts`). After an update, while the daemon restarts, the read is refused and tried again until answered, and in between the sidebar shows only the few sessions that events have delivered, as if that were all.
- **After:** from the moment a read of this Mac's sessions fails until one succeeds, the sidebar draws what it has and the Projects heading carries the muted word "reconnecting", the word Needs you already uses for a machine whose link is down (`RECONNECTING` in `sidebar/NeedsYou.tsx`). While the word shows, "No projects yet" is not drawn. Nothing times out: the word leaves when the read succeeds.
- **Why this, not that:** the alternative is to hold the skeleton until the read succeeds. It lost because a daemon that never answers would leave a skeleton with no words for ever, and the word is the app's existing vocabulary for the same condition on another machine.
- **Not included:** other machines' rows (they already grey in place). A pitfall seen in the code: on an ordinary start there is an awaited step between the end of the skeleton and this Mac being marked loaded, so "this Mac is not loaded yet" is not the condition; the condition is that a read has failed.

## O-03 · The project chip stays inside its box

- **Today:** the chip's wrapper in `app/Toolbar.tsx` is 96 px wide at most and does not clip; the chip is a button that sizes to its text up to 192 px. - **Not included:** what the chip names once there is one strip, and what its click does, are U13's (O-01, O-31). This fix holds for whatever chip remains, and it may land ahead of the rest of this child as its own small pull request.

## O-40 · Settings opens as a dialog; Customize, Projects and the Artifacts library open as pages

- **Today:** each opens a singleton tab in the strip: Settings through the `settings.open` action (`gateway/actions.ts`), Customize and Projects through `customize/open.ts`, the library through `openArtifacts` (`main/artifacts.ts`); the kinds `settings`, `customize`, `projects` and `artifacts` are tab kinds in `TabRefSchema`, drawn by `main/Pane.tsx`, and they are the four kinds the pin control refuses (`UNPINNABLE_KINDS`).
- **After:**
  - **Two frames.** By the owner's answer of 2026-11-12, "As Desktop really does": Settings is a dialog over the window; Customize, Projects and the Artifacts library are pages that take the main area's place. None of the four is a tab, and the four tab kinds are removed.
  - **The state.** A page is a *destination*: a place in the app that is not a tab. The layout store holds at most one open destination, beside the tabs and independent of them, and, separately, whether the Settings dialog is open:
    ```ts
    type Destination =
      | { kind: 'customize'; view: 'mine' | 'discover'; show: 'all' | 'plugins' | 'skills' | 'connectors' }   // the owner's answer on Customize's structure (O-14; U11's file)
      | { kind: 'library' }                                        // the Artifacts library
      | { kind: 'projects' };

    destination: Destination | null;              // null: the main area shows the tabs
    openDestination(target: Destination): void;   // replaces an open one; the same kind again only changes its fields (Customize's view and filter); closes the Settings dialog
    closeDestination(): void;                     // back to the tabs, exactly as they were

    settings: { section: SettingsSection | null } | null;   // the Settings dialog; U11's sections, plus 'usage' (O-47); null: closed
    openSettings(section?: SettingsSection): void;          // over the tabs or over an open destination; open already: only the section changes
    closeSettings(): void;                                  // what was behind it is as it was
    ```
    The destination is stored under a layout key of its own, `destination`, and restored at a relaunch, because the relaunch that restores everything is the owner's `keep` (l7-shell-12); build F does not know the key and leaves it alone (UC-14). The dialog's state is held as the store holds whether the Overview is open, for the run only: a relaunch shows the tabs or the page that was behind it. The two are separate because the dialog opens over a page too: with one slot, ⌘, on the Customize page would throw the page away. Projects is a destination although the owner named three places, because it is the fourth of the same singleton kinds and would otherwise be the one page left in the strip; it is a list one browses, so it takes the pages' frame.
  - **The Settings dialog.** A modal dialog centred in the window, in the box the app's library dialogs already have (`WIDGET_DIALOG_BOX.library` in `composer/WidgetDialog.tsx`: 960 px wide at most, 800 px tall at most and never more than 85 % of the window's height; the height is fixed, so that changing section never resizes it). Inside it is U11's `SettingsView`, whose index carries the name "Settings"; a Close button sits at the dialog's top right. The window behind is dimmed with the one scrim U11 gives every sheet and dialog (#523) and takes no click. Everything behind stays drawn and mounted as it was: the sidebar, the title bar with the strip, the tabs or the open page, the side surfaces, the card column. An in-app browser's native view yields as it does under any dialog. The session behind the dialog still counts as on screen (`session/visibility.ts` is not changed for it), as under the app's other dialogs. A sheet or a menu that Settings itself opens (the enroll and grant sheets, a confirmation, the shortcut recorder) opens over the dialog, and Esc or a click outside closes only the topmost. Keys that belong to what is behind (the composer's keys, a request card's Enter and Esc) do not act while the dialog is open: the key dispatcher already refuses them under an open dialog (`OPEN_OVERLAY` in `keymap/dispatcher.ts`). App-wide chords and menu items keep working, as under the app's other dialogs; one that goes to a place closes the dialog (Leaving the dialog, below).
  - **A page: what is on screen.** A page takes everything right of the sidebar: the main area and the side column. The sidebar is unchanged and live; the row of the open destination is marked current, and no session row is marked selected. The tabs, their panes, the side surfaces and the card column are not drawn but stay mounted, so nothing in them is lost or reloaded, and an in-app browser's native view yields as it does under any overlay. The Overview still opens over a page.
  - **A page: the title bar.** The sidebar and Overview buttons stay. Where the project chip and the strip were: a Back button and the page's name (Customize, Projects, Artifacts). The strip, the "+", the surface icons and the session menu are not drawn. The usage ring stays.
  - **Entering.** Every existing way in calls `openSettings` or `openDestination`, by what it opens today. The gear, ⌘, and MAWS › Settings… (with a section when the action names one) open the dialog. The sidebar's Projects, Artifacts and Customize rows and View › Artifacts open a page. The palette's entries and the links inside the app that today open one of these tabs follow the same split (the composer's "Manage…" items, the plugins widget's Open Discover, the browser's extension and profile links, the engine error row's Settings link, the Artifacts list's "Open library", Settings' own link to Customize, the ring's "Usage settings"). ⌘, while Settings is open leaves it open.
