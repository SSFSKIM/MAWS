Each m1 scene checks its named state right before its capture, once the page has settled, with Settings open: on M1's build the reveal itself (the tooltip of its word, its row's note, its row's menu with its items, its chevron open) and the state it is named for (the search's results, the budget off, the probe's answer, the Org seed's distinguishing rows); on master's, the same state in master's terms. A scene that cannot prove it is recorded as not reached. The rig records each scene's meta and whether it was reached in `<WORDS_OUT>/_run.json`, with each run's build (its commit, the tracked files it changed and a digest of `out/`); an m2 scene refuses a build that does not match its checkout.

**Taking the pictures.** On a Mac (the rig opens app windows), from a clean checkout of the build to photograph:

    pnpm install
    WORDS_OUT=$HOME/maws-words/before pnpm shots:words

`pnpm shots:words` builds `out/` and runs the rig's sixteen launches through `playwright.words.config.ts`, its only selection (the file is not a `*.spec.ts`, so no e2e group and no default run collects it), in about 50 minutes. The pictures are `<WORDS_OUT>/<scene>.png`. `WORDS_ONLY=<id>,<prefix>*` narrows a run to some scenes. The "before" set is this command on master; the "after" set is the same command on a milestone's branch into another folder. A folder holds one build's pictures: a scene taken again loses its old picture before it starts, and a run of another build (another commit or another `out/`) moves every earlier result it does not take again aside, under `stale` in `_run.json` with its picture under `_stale/<build>/`. A scene not reached says why in `_run.json` and the log, naming the locator it waited on.

The `m1` scenes exist only in M1's rig, so master's own rig has no before for them. Their before is M1's rig, with its e2e support files, run against master's build: in a clean checkout of master, `git checkout ux-wave/word-cut-m1 -- e2e/words-shots.rig.ts e2e/support`, then the command above into the before folder (`WORDS_ONLY=m1-*` takes just these). Every launch's state comes from the rig and `e2e/support` (fixtures, and seams master's main already has: the Org page fixture, the scripted voice probe, the Chrome import's, the relay override), and the rig reads the Org copy that M1 added as absent there. Where master has no reveal, a scene requires and captures what master draws at rest in its place, in view: the form a chevron would hide, the worded buttons a menu would hold, the line or the words a note or a tooltip would carry. Whether the build has M1's parts is read once, the first time Settings opens (a row's note mounted at rest).

The `m2` scenes exist only in M2's rig, and their before is the same: M2's rig with its e2e support files run against master's build (`git checkout ux-wave/word-cut-m2 -- e2e/words-shots.rig.ts e2e/support` in a clean checkout of master; `WORDS_ONLY=m2-*` takes just these). Each checks its named state right before its capture: on M2's build the reveal itself (the tooltip of the control holding the keyboard or under the pointer, the fold open, the actions a pointer draws at full opacity) and the state it is named for; on master's, the same state in master's terms, in view: the words master draws at rest where M2 puts them behind a tooltip, master's caption, section or line where M2 drops it. The rig's imports from `src/` resolve to the checkout's own modules, so in the before they are master's (the rig with this branch's e2e support type-checks against master's `src/` at `92d962e78`), and a word M2 added or changed is absent or master's there. The checks therefore find their targets by data attributes, roles and places; the few words they read from a module the rig cannot import (one that loads the renderer) are written in the rig with their source, as each build has it, and read by the build. Whether the build has M2's cut is read once, the first time a message box draws: the microphone is named Dictate on both builds, and only master's carries a system `title`.
