# Word cut: the scenes

> Part of `docs/doperpowers/specs/2026-11-16-word-cut-design.md`. The screens the rig `e2e/words-shots.rig.ts` takes, each from any build on repository fixtures under a scratch profile, so that a before and an after picture differ only in the app's words. The 107 scenes of rounds 1 and 2 are the screens the owner judged at the pin (round 1 on 2026-11-15, round 2 on 2026-11-16); M0 carried them onto master (the UX wave as it left it, `028cecd10`) and added 68 (round `m0`) for states the rounds never reached and for surfaces the wave added. 3 of the old scenes have no target on master. M1 added 39 (round `m1`) for the Settings and Org states its cut draws: rows' notes on pointing and focus (each open over the rows that follow, the one placement the owner chose on 2026-11-21), tooltips reached by focus, menus opened, search, a pairing code refused, the relay up, the Org for someone who may not sign and for a quiet org. M2 added 24 (round `m2`) for the conversation's and the message box's states its cut draws: tooltips reached by focus or by pointing, a call opened, a listing folded and open, menus and popovers of the message box opened, and five recorded transcripts read from disk in a tenth launch for a steer, an ask the interrupt withdrew, a message from another session, a scheduled job's fires and the bridge's wake; that launch also holds the new chat's model menu, since only a launch on the session index makes a new chat with its setup intent. M3 added 44 (round `m3`) for the panels' states its cut draws: 40 in an eleventh launch of their own (Review, Source control, Files, the browser and its Chrome import, the surfaces' menus and names), 2 in a twelfth (the project Channel's folds), and one each in launches 3 and 4, where the state already was (a recorded workflow's page; an agent waiting on an approval). 282 scenes in all. Each m1 scene checks its named state right before its capture, once the page has settled, with Settings open: on M1's build the reveal itself (the tooltip of its word, its row's note, its row's menu with its items, its chevron open) and the state it is named for (the search's results, the budget off, the probe's answer, the Org seed's distinguishing rows); on master's, the same state in master's terms. A scene that cannot prove it is recorded as not reached. The rig records each scene's meta and whether it was reached in `<WORDS_OUT>/_run.json`, with each run's build (its commit, the tracked files it changed and a digest of `out/`); an m2 scene refuses a build that does not match its checkout.

**Taking the pictures.** On a Mac (the rig opens app windows), from a clean checkout of the build to photograph:

    pnpm install
    WORDS_OUT=$HOME/maws-words/before pnpm shots:words

`pnpm shots:words` builds `out/` and runs the rig's twelve launches through `playwright.words.config.ts`, its only selection (the file is not a `*.spec.ts`, so no e2e group and no default run collects it), in about 40 minutes. The pictures are `<WORDS_OUT>/<scene>.png`. `WORDS_ONLY=<id>,<prefix>*` narrows a run to some scenes. The "before" set is this command on master; the "after" set is the same command on a milestone's branch into another folder.

The `m1` scenes exist only in M1's rig, so master's own rig has no before for them. Their before is M1's rig, with its e2e support files, run against master's build: in a clean checkout of master, `git checkout ux-wave/word-cut-m1 -- e2e/words-shots.rig.ts e2e/support`, then the command above into the before folder (`WORDS_ONLY=m1-*` takes just these). Every launch's state comes from the rig and `e2e/support` (fixtures, and seams master's main already has: the Org page fixture, the scripted voice probe, the Chrome import's, the relay override), and the rig reads the Org copy that M1 added as absent there. Where master has no reveal, a scene requires and captures what master draws at rest in its place, in view: the form a chevron would hide, the worded buttons a menu would hold, the line or the words a note or a tooltip would carry. Whether the build has M1's parts is read once, the first time Settings opens (a row's note mounted at rest).

The `m2` scenes exist only in M2's rig, and their before is the same: M2's rig with its e2e support files run against master's build (`git checkout ux-wave/word-cut-m2 -- e2e/words-shots.rig.ts e2e/support` in a clean checkout of master; `WORDS_ONLY=m2-*` takes just these). Each checks its named state right before its capture: on M2's build the reveal itself (the tooltip of the control holding the keyboard or under the pointer, the fold open, the actions a pointer draws at full opacity) and the state it is named for; on master's, the same state in master's terms, in view: the words master draws at rest where M2 puts them behind a tooltip, master's caption, section or line where M2 drops it. The rig's imports from `src/` resolve to the checkout's own modules, so in the before they are master's (the rig with this branch's e2e support type-checks against master's `src/` at `92d962e78`), and a word M2 added or changed is absent or master's there. The checks therefore find their targets by data attributes, roles and places; the few words they read from a module the rig cannot import (one that loads the renderer) are written in the rig with their source, as each build has it, and read by the build. Whether the build has M2's cut is read once, the first time a message box draws: the microphone is named Dictate on both builds, and only master's carries a system `title`. M2's rig also makes sixteen carried scenes check their state before their capture (`m0-dialog-agents-none`, `m0-resume`, `session-question` (the first of two), `session-terminal-held`, `sidebar-hover`, `shell-tools`, `shell-tools-open`, `r2-model-menu`, `r2-context-popover` (the dormant reading it draws), `r2-mention-menu`, `m0-composer-bash`, `m0-composer-memory`, `m0-subagents-stopped`, `m0-background-stopped`, `r2-run-transcript` (two agents at work, in view), `m0-auto-blocked`), revises the setup of the four M0 scenes master's rig left unreached (their M0 column says why; none has run since), and logs a failed setup step's whole error, its stack and its cause, in the console.

The `m3` scenes exist only in M3's rig, and their before is the same: M3's rig with its e2e support files run against master's build (`git checkout ux-wave/word-cut-m3 -- e2e/words-shots.rig.ts e2e/support` in a clean checkout of master; `WORDS_ONLY=m3-*` takes just these). Whether the build has M3's cut is read once, from what the window loaded: M3's touch rule put one `[data-touch-fact]` rule into the app's stylesheet, which master's has nowhere; the checkout says which side it is by `src/renderer/src/ui/touch-fact.tsx`, and a build that draws the other side is refused, every m3 scene then not reached with why (M2's rule). Each m3 scene checks its named state right before its capture: on M3's build the reveal (a tooltip of the control holding the keyboard, a menu, a notice line) and the state it is named for; on master's, the same state in master's terms, in view (master's worded control, its foot line, its zoom row, the words it draws at rest). The words the checks read from a renderer module the e2e project does not list are written in the rig with their source, per build (`M3_WORDS`). Launch 11's states come from the rig alone: two sessions the engine store lists and nothing starts, on a `panels` repository (a tracked binary changed, a side branch merged with `--no-ff` and an empty commit after it, all unpushed; a symbolic link; two untracked folders, one holding a 5.6 MB log) and a `quiet` one (one commit, nothing changed, no remote); the browser's scratch server; the Chrome import's seams over launch 6's synthetic Chrome profile. Three browser notices only main's own limits raise (the page cap closing a tab it could not keep, the cap refusing an extension's options, an agent's download refused) are sent to the window as main sends them (`maws:evt:browser.notice`), in each scene's last step before its check, since a notice lasts four seconds. View › More surfaces is the OS's menu bar, which no capture of the window holds; the keymap's titles it shows (N156, N157) are photographed where the window draws the same titles: the command palette, Settings › Keyboard, Settings' search and the shortcuts window, each checking the exact title of its build. Launch 12 opens the project Channel from its row's menu over a channel a harness build's main answers from a file (`src/main/org/channel-fixture.ts`; the seed is `e2e/support/words-channel.ts`, a smaller one than `e2e/channel.spec.ts`'s, over the same stub scenario): a session's run of five messages to the whole project, an exchange of twelve between two sessions, one message to everyone and a person's word. Every scene sets up what it needs itself (the import, a loaded browser page, an edit and the disk's rewrite), so `WORDS_ONLY` on any one scene reaches its state on a fresh launch, and every action is bounded (`actionTimeout` in `playwright.words.config.ts`), so a target that never matches costs its own scene alone.

    WORDS_OUT=$HOME/maws-words/desk-after pnpm --filter desk-web shots:words

That builds `dist/` and runs every scene in a minute or two, headless. It writes `<WORDS_OUT>/desk-<scene>.png` and a `_desk-run.json` that records whether each scene was reached. For the before: in a clean checkout of master, run `git checkout <branch> -- apps/desk-web/e2e/words-shots.rig.ts apps/desk-web/playwright.words.config.ts apps/desk-web/package.json`, then the same command into another folder. `WORDS_ONLY` narrows the run. Each scene reads the build from the touch rule's stylesheet rule and checks that build's form before capture. Phone scenes run at 390x844 with `isMobile` and `hasTouch`, and check `(hover: none)`.
