돌고 있는 Claude Code 세션을 원격에서 이어 받는 세 가지 구조

사람이 터미널에서 claude로 일하다 자리를 뜬다. 다른 기계나 폰의 브라우저에서 그 세션을 그대로 이어 쓰려면 무엇이 필요한가. 이 글은 오늘의 desk(bridge mod), Claude 자신의 프로토콜들, 그리고 연구 중인 session holder 설계를 같은 그림 위에 놓고 처음부터 끝까지 따라간다.

1질문과 세 가지 답

원하는 것은 셋이다.

  1. 같은 세션을 이어 쓴다. 터미널에서 돌던 그 대화, 그 프로세스를 원격에서 본다.
  2. 제어 폭이 넓다. 말을 걸고, 권한에 답하고, 모델과 모드를 바꾸고, 되감는다. 터미널에서 할 수 있는 것은 원격에서도 된다.
  3. 돌던 일을 잃지 않는다. 세션은 거의 idle이 아니다. 백그라운드 셸, 서브에이전트, Monitor, MCP 작업이 늘 돈다.

위의 그림 1을 한 줄로 읽으면 이렇다.

  • 오늘의 desk는 세션 안에 손님으로 들어간 mod로 원격 제어를 한다. 프로세스는 사람의 터미널이나 엔진의 --bg supervisor가 쥔다.
  • Remote Control도 세션 안의 코드(REPL bridge)로 원격 제어를 하지만, 중계가 Anthropic 서버이고 URL이 거기에 고정돼 있다.
  • holder 설계는 사람이 치는 claude를 처음부터 우리 PTY holder 안에서 띄운다. 그래서 사람이 터미널 창을 닫아도 세션이 남는다. 웹은 desk처럼 세션 안의 mod로 구조화된 제어만 하고, mod로 안 되는 조작은 세션을 SDK 모양으로 다시 띄워서 한다. 웹 터미널 창은 두지 않는다.

2먼저 알아 둘 네 가지

세션 프로세스의 두 모양

Claude Code 세션은 같은 엔진이 두 모양으로 돈다. transcript 형식(JSONL)은 같다.

  • TUI(interactive). 사람이 claude를 치면 뜨는 것. 터미널(PTY)에 화면을 그리고 키를 받는다. 패널, 확인 창, rewind picker, Shift+Tab 모드 순환 같은 것은 이 화면에만 있다.
  • headless(stream-json). claude -p --input-format stream-json --output-format stream-json. 화면이 없다. 한 줄에 JSON 하나로 대화하고, 화면은 그 JSON을 받는 쪽(host)이 그린다. MAWS, Claude Desktop, claude.ai가 이 모양을 쓴다.

소유자: 프로세스를 쥔 쪽

소유자는 세션 프로세스의 부모이고, 그 PTY master 또는 stdin·stdout pipe를 쥔 쪽이다. 소유자가 죽으면 세션도 죽는다. PTY master가 닫히면 claude는 SIGHUP을 받고 exit 129로 끝난다(측정). 백그라운드 셸, 서브에이전트, Monitor, MCP 작업은 모두 그 프로세스 안이나 그 자식에서 돈다. 그래서 소유자를 바꾸지 않는 것이 곧 돌던 일을 지키는 것이다.

제어 표면: 원격이 무엇을 할 수 있는가

세션을 바깥에서 움직이는 통로는 넷이고, 폭이 다르다.

여기서 중요한 관찰 하나. 제어 폭이 가장 넓은 SDK 프로토콜은 headless 세션에만 있고, 사람이 쓰는 TUI 세션에는 mod와 키 입력만 닿는다. 이 글의 모든 갈림길이 여기서 나온다.

중계와 순번: 끊겼다 돌아왔을 때

원격 연결은 끊긴다. 다시 붙을 때 클라이언트가 "어디까지 봤다"를 말하고, 상대가 "그 뒤부터"를 줄 수 있어야 한다. 그러려면 누군가 이벤트에 순번(seq)을 매기고 최근 구간을 보관해야 한다. 그 주체가 권위다. Remote Control은 Anthropic 서버가, Desktop SSH 모드는 원격 기계의 데몬이 이 일을 한다. 오늘의 desk의 bridge 경로에는 이것이 없다.

3오늘의 desk: 세션 안의 bridge mod

흐름

  1. 세션 안. sminos 플러그인이 로드된 모든 claude 안에서 bridge mod가 돈다. mod는 transcript 행(session.append), 토큰 조각(turn.step), 권한 프롬프트(PermissionRequest hook)를 본다.
  2. 기계 안의 한 홉. mod는 이벤트마다 자기가 띄운 bridge child(Python 프로세스)에 Unix 소켓으로 HTTP POST를 한 번 한다.
  3. sminos 데몬. bridge child의 스트림을 구독한다. plane(세션 구독: snapshot부터, 그다음 live), uplink(hub로 가는 SSE 아래·POST 위), 신뢰 경계(웹에서 온 명령의 봉인 검증, nonce 원장, 읽기 전용, 권한 상한)가 여기 있다.
  4. desk-hub. Cloudflare Durable Object다. 기계와 브라우저를 잇는 중계일 뿐 믿지 않는다. transcript를 저장하지 않는다(설계 약속).
  5. desk-web. 브라우저에서 행과 델타를 그리고, 보내기·steer·권한 답 같은 명령을 봉인해 보낸다.

세션을 띄우는 길은 둘이다. 웹의 Spawn은 claude --bg, Resume은 claude --bg --resume을 돌려 엔진의 supervisor에 맡긴다(4.4). 사람이 터미널에서 연 세션에도 mod가 돌기 때문에 그 세션도 desk에 나타나고, 웹에서 제어된다.

되는 것과 안 되는 것

  • 된다: 행과 토큰 델타 관찰(서브에이전트 포함), idle일 때 프롬프트 보내기, 턴 중 steer($.session.append), 권한 프롬프트와 AskUserQuestion 답(터미널과 경쟁해 먼저 답한 쪽이 이긴다), interrupt, 모델·effort, $.command.run으로 /model·/mcp disable·/compact·/clear·/plan 같은 slash 명령.
  • 안 된다: 일반 dialog(request_user_dialog 37종 중 권한·질문·MCP elicitation 밖의 것), plan 밖의 권한 모드 전환, rewind 지점 고르기, /usage·/permissions 같은 panel. panel이 열리면 그 뒤의 명령이 줄을 서서 멈춘다. Esc로 턴을 멈춘 뒤에는 사람이 입력할 때까지 mod 명령이 거부된다.

성능과 약점

bridge 한 홉은 빠르다. 텍스트 델타가 mod에서 구독자까지 p50 1.8 ms, p95 5.7 ms, p99 14.5 ms였고, mod를 켜고 끈 차이가 엔진 성능에 나타나지 않았다. 사람이 느끼는 "desk가 느리다"는 다른 곳에서 온다.

  • 세션 열기가 느리다. 운영에서 한 번 여는 데 5.4 s, 19 s 넘게, 51 s 넘게 걸린 일이 있었다. plane이 엔진이 아직 쓰지 않은 행을 기다리고(2.0–2.4 s, 메시지가 끝나야 행이 써진다), 0.25 s 주기로만 다시 보고, 큰 transcript를 처음부터 색인하고, uplink 스레드 하나가 hub POST(매번 새 TLS, 140–230 ms)에 묶인다.
  • 연결 계약이 약하다(#52). Resume에 30초가 걸린다. 재전송한 명령이 60초 창을 넘겨 stale로 거부된다. 브라우저 소켓은 close 신호만 기다려 죽은 연결을 늦게 안다. 구독마다 snapshot부터 다시 받는다.
  • 뿌리. bridge 경로에는 순번과 보관 구간이 없고, hub는 아무것도 저장하지 않는다. 그래서 다시 붙을 때마다 기계까지 왕복해 처음부터 받는다.

이 구조의 진짜 장점

mod는 사람의 TUI 안에 손님으로 들어가 있을 뿐이다. 웹이 붙어도 프로세스는 옮겨지지 않으므로 터미널도, 백그라운드 일도 그대로다. 대신 제어 폭이 mod API로 묶이고, 사람이 터미널 창을 닫으면 세션도 끝난다.

4Claude의 네이티브 길들

4.1 Remote Control (RC)

  • 두 진입점. TUI 안에서 /remote-control을 켜면 그 프로세스 안의 REPL bridge가 worker가 된다(지금 이 대화 하나를 중계). claude remote-control은 headless 서버로, 자식 claude --print를 세션마다 띄운다.
  • 전송. worker는 SSE로 읽고(/worker/events/stream?from_sequence_num=n), HTTP로 쓴다. 이벤트 배치(POST /worker/events, 100개·10 MiB 이하), 상태 문서(PUT /worker: idle·running·requires_action, 모드·컨텍스트 등), 전달 영수증, heartbeat가 있다.
  • 서버가 권위다. 서버가 이벤트에 순번을 붙여 쌓는다. 그래서 client가 세션을 열거나 다시 붙을 때 worker 기계와 통신하지 않는다. 기계가 잠들어 있어도 기록은 열린다. 이것이 RC가 빠르게 열리는 근원이다.
  • worker는 세션당 하나(worker_epoch). 새 worker가 등록하면 옛 worker는 409와 close 4090으로 물러난다.
  • 제어. client가 worker로 넣을 수 있는 대화 프레임은 user 하나다. 나머지는 SDK와 같은 control_request 봉투의 23종(interrupt, set_model, set_permission_mode, stop_task 등)이다. worker가 client에게 묻는 것은 권한(can_use_tool)과 dialog(request_user_dialog) 둘이고, 터미널과 동시에 떠서 먼저 답한 쪽이 이긴다.
  • 약점. claude.ai의 실시간 소켓은 replay가 없다. keep-alive는 50초마다 오고, 오프라인 판정은 70초 뒤에 내리며, 6번 시도한 뒤에는 사람이 다시 눌러야 한다. 비교한 시스템 중 가장 느리다.
  • 우리가 쓸 수 없다. worker URL은 Anthropic 호스트로 고정돼 있다(--sdk-url allowlist, CLAUDE_BRIDGE_BASE_URL은 선언만 있고 늘 비어 있음). 같은 위치에 우리가 들어갈 수 있는 유일한 통로가 mod다. 그래서 desk의 bridge mod가 RC의 REPL bridge 자리를 흉내 낸다.

4.2 SDK stdio 제어 프로토콜

  • 무엇인가. Agent SDK의 Query 객체가 claude -p를 띄우고 stdin·stdout으로 말하는 프로토콜이다. MAWS의 engine host, Claude Desktop, claude.ai(브라우저가 SDK host로 동작)가 모두 이것을 쓴다.
  • 폭. host가 보낼 수 있는 제어 요청이 96종이다: interrupt, set_model, set_permission_mode, rewind_conversation, mcp_toggle, read_file, stop_task 등. 엔진은 host에게 권한, dialog, hook callback, MCP elicitation 등 16종을 묻는다.
  • dialog. request_user_dialog는 37종이다(권한 여러 종류, MCP elicitation, sandbox 네트워크, auto 모드, computer use 승인, plugin 힌트 등). host가 initialize에서 선언한 종류만 오고, 선언하지 않은 종류는 닫힌 채로 실패한다. 즉 host가 dialog를 그리는 GUI를 가지면 터미널 없이 모든 dialog를 다룰 수 있다.
  • 다시 붙기. host가 다시 initialize를 보내면 엔진이 열려 있던 권한·dialog 요청을 다시 보낸다. 대기 중인 질문은 이벤트가 아니라 엔진이 쥔 상태다.
  • 한계. 사람이 쓰던 TUI 세션은 이 프로토콜로 움직일 수 없다. TUI 세션을 이 모양으로 바꾸려면 프로세스를 끝내고 --resume으로 다시 띄워야 하고, 그때 돌던 일을 잃는다(5장).

4.3 Claude Desktop의 SSH 모드 (claude-ssh)

  • 원격 데몬이 프로세스를 소유한다. 원격 기계의 ~/.claude/remote/srv/<ver>/server --serve가 모든 claude의 부모다. SSH 연결은 그 데몬의 0600 Unix 소켓으로 가는 pipe일 뿐이라, 끊겨도 원격에는 변화가 없다.
  • 출력마다 순번, 입력마다 offset. 데몬이 프로세스마다 마지막 16 MiB의 출력 프레임을 seq와 함께 둔다. 입력은 process.stdin{data, offset}로 보내고 데몬이 stdinApplied를 알려 주므로, 같은 바이트를 두 번 보내도 한 번만 쓰인다.
  • 입력 전에 checkpoint. Desktop은 입력을 쓰기 전마다 줄 경계의 출력 위치 {seq, skipBytes}를 디스크에 남긴다. 앱을 껐다 켜도 살아 있는 프로세스를 재입양하고 정확히 그 뒤부터 replay한다.
  • 대기 중인 질문은 상태다. 다시 initialize하면 엔진이 열린 권한·dialog 요청을 다시 보내고, SDK가 request_id로 중복을 없앤다.
  • 생존 감지가 빠르다. 7초 동안 아무것도 오지 않을 때만 ping을 보내고, 2번 놓치면 끊는다. 깨어날 때, 네트워크가 바뀔 때 즉시 다시 붙는다.
  • 한계. 프로세스는 claude -p뿐이라 사람이 쓰던 TUI와는 상관이 없다. 데몬(helper)을 교체하면 자식이 모두 죽는다. 그리고 이 helper는 Desktop 전용이라 우리가 그대로 쓸 수 없다. 메커니즘만 가져온다.

4.4 엔진의 백그라운드 supervisor (claude --bg)

  • 무엇인가. claude --bg, claude agents, /background로 만든 세션은 엔진 자신의 supervisor(claude daemon run)가 소유한다. 세션마다 --bg-pty-host 프로세스가 PTY를 쥐고, 그 안에서 평범한 interactive REPL이 돈다. stream-json 세션이 아니다.
  • 내구성. supervisor가 재시작해도 살아 있는 pty-host를 다시 입양한다. 아무 터미널에서나 claude attach <short>로 붙을 수 있고, 여러 명이 동시에 붙는다.
  • 제어. control.sock(op 18개)이 목록, 상태, reply, subscribe, attach, kill을 준다. reply는 사람이 친 것처럼 slash 명령을 돌리고 턴 중에도 /model·/effort를 즉시 바꾸지만, 권한 프롬프트는 승인하지 못한다.
  • /background는 프로세스를 옮기지 않는다. transcript를 flush하고 --resume … --fork-session으로 새 job을 띄운 뒤 터미널 쪽 세션을 끝낸다. 엔진 자신의 resume handoff다(무엇이 따라가는지는 5장).
  • 우리 것으로 쓰기 어려운 이유. 소켓 경로는 설정으로 바꿀 수 없고, op와 프레임은 공개되지 않아 릴리스마다 바뀔 수 있다. 바이너리가 바뀌면 job을 새 버전으로 다시 띄우고, 부모도 클라이언트도 없는 pty-host는 60초 뒤 끝낸다. 돌던 일을 지키려는 목적과 맞지 않는 정책들이다.

4.5 막혀 있는 길

  • RC worker를 우리 서버로. --sdk-url은 Anthropic 호스트만 받는다. CLAUDE_BRIDGE_BASE_URL은 늘 비어 있다. SDK host가 보내는 remote_control 요청도 항상 Anthropic에 Anthropic 계정으로 붙는다.
  • TUI의 thin-client 모드. TUI 코드 안에는 원격 세션을 그리는 모드 셋(ccr, ssh, direct)과 claude cc://…, claude ssh 진입점이 있다. 그러나 진입점을 여는 값이 어디서도 설정되지 않아 2.1.300에서는 닿을 수 없다(코드로 확인, 2.1.307은 확인하지 않음).
  • Channels. MCP 서버가 세션에 메시지를 밀어 넣는 기능은 first-party 전용이고 기본으로 꺼져 있다. 들어온 메시지도 사람의 말이 아니라 <channel>로 감싸진다.

"터미널 세션을 원격에서 SDK 수준으로 제어하자"는 생각은 자연스럽게 "그 세션을 headless로 옮기자"가 된다. 실제로 옮겨 보았다(2.1.307).

결론

돌고 있는 터미널 세션을 원격에서 이어 쓰는 가장 확실한 길은 프로세스를 그대로 두고 그 위에 붙는 것이다. RC가 그렇게 하고, desk의 bridge mod도 그렇다. 남는 문제는 셋이다. 터미널 창을 닫으면 세션이 죽는다. 키로만 되는 조작이 원격에서 안 된다. desk의 연결 계약이 약하다. holder 설계는 첫째를 풀고, 둘째는 일부만 푼다. 웹 터미널 창으로 둘째를 다 푸는 길은 일부러 버렸다(6장).

6연구 중인 설계: session holder

생각은 하나다. 사람이 치는 claude를 처음부터 우리가 쥔 PTY 안에서 띄운다. 그러면 사람의 터미널은 그 PTY에 붙은 클라이언트가 되고, 창을 닫아도 세션은 holder 안에 남는다. 웹은 같은 프로세스에 bridge mod(구조화된 제어)로만 붙는다. 프로세스는 한 번도 옮겨지지 않는다. Claude Desktop SSH 모드의 "기계 쪽 데몬이 프로세스를 쥔다"를 사람의 TUI에 적용한 것이다.

원칙: 프로세스의 날것 스트림은 기계를 떠나지 않는다

웹이 받는 것은 bridge 행과 MAWS의 X1 이벤트이고, 보내는 것은 동작마다 봉인된 명령이다. PTY 바이트도, SDK stdio도 hub로 나가지 않는다(owner 결정 F5, 2026-10-23). 여기서 두 가지가 나온다.

  • 웹 터미널 창은 두지 않는다. 같은 TUI를 브라우저에 띄우고 키보드를 넘겨받는 창은 조작성이 가장 좋다. 그러나 실행 등급의 키 바이트가 믿지 않는 hub를 지나고, MAWS GUI가 모르는 두 번째 제어면이 생긴다. 그러면 바이트 offset·키보드 lease·화면 snapshot 프로토콜, passkey 재확인, 화면 무결성 문제를 따로 지게 된다.
  • Query는 브라우저가 아니라 기계의 MAWS 데몬에 있다. Desktop SSH 모드에서는 Desktop 앱이 Query를 쥐고, claude.ai는 브라우저가 Query를 직접 돌린다. holder 설계에서는 Desktop 앱의 자리를 같은 기계의 MAWS 데몬이 맡고, 브라우저는 그 바깥의 클라이언트다. MAWS의 in-process MCP 도구와 hook callback이 Query와 같은 프로세스에 살고, Query는 엔진의 질문에 답하는 쓰는 쪽 하나라 잠드는 탭에 둘 수 없기 때문이다.

구성 요소

  • session host (세션마다 하나, 작고 거의 바뀌지 않는다). claude 프로세스의 부모다. PTY master(또는 pipe 종류의 stdin·stdout)를 쥐고, 출력과 resize를 순서대로 담은 ring(약 8 MiB, 절대 offset)과 checkpoint 칸 하나를 둔다. 누가 입력할 수 있는지(lease), 어떤 연결의 프레임이 유효한지(fence)를 직접 집행하고, 모든 출력과 제어보다 인증을 먼저 한다. host가 죽으면 세션이 죽으므로 가능한 한 작게 둔다(Go가 유력).
  • holder manager (사용자당 하나, 언제든 바꿀 수 있다). host들의 roster를 읽어 재입양한다. lease 정책, 매크로, 24시간 정리 규칙, PTY와 pipe 사이의 경로 이동을 맡는다. 사람이 다시 붙을 때는 처음에 모드를 되돌리고 폭을 한 칸 흔들어 TUI가 다시 그리게 한다. xterm.js headless 에뮬레이터로 화면을 정확히 되살리는 것은 나중의 개선 항목이다. Node로 만든다.
  • claude wrapper. PATH 앞쪽의 shim이다. -p, subcommand, --bg 같은 것은 그대로 진짜 claude를 실행하고, interactive 실행만 host를 직접 띄운다. CLAUDE_HOLDER=0이면 우회한다.
  • bridge mod. 지금 것을 그대로 쓴다. 구조화된 제어를 맡고, holder를 위해 세션 id 변화를 보고하고, 정리 fence(아래)를 집행한다.
  • 웹. GUI만 있다. 세션마다 명령별로 gui | macro | none을 알려 준다. plan 모드에서 나오기처럼 키로만 되지만 bridge가 보고하는 상태로 결과를 확인할 수 있는 것은 기계 쪽 매크로로 한다. rewind 지점 고르기, panel, 일반 dialog 대부분은 none이고, 그 옆에 "GUI 모드로 이어 가기"를 보인다.
  • MAWS 데몬의 Query. MAWS 앱이나 웹에서 연 세션은 처음부터 pipe 종류로 띄우고 SDK 프로토콜로 제어한다. 같은 host 가족이 쥔다. Query는 브라우저가 아니라 이 데몬에 있다(위의 원칙).

holder는 독립된 작은 서비스로 MAWS 저장소의 apps/session-holder에 두고, sminos 데몬과 MAWS 데몬이 그 클라이언트가 된다. MAWS가 없는 Linux·devcloud 기계에도 설치된다.

장면으로 따라가기

장면 1. 사람이 claude를 친다

  1. wrapper가 host를 직접 띄운다(double fork + setsid, Linux에서는 user systemd scope 안).
  2. host가 소켓과 자기 roster 항목을 만들고 ready를 보낸다. wrapper가 commit을 보내야 host가 claude를 fork한다. commit 전에 무엇이 실패하면 claude는 아직 없으므로 plain claude로 돌아간다. commit 뒤에는 절대 plain을 하나 더 띄우지 않는다.
  3. 사람의 터미널은 host에 직접 붙어 바이트를 그대로 주고받는다. 화면, 키, Ctrl+Z(claude를 따로 process group으로 두고 foreground로 만든다)까지 plain과 같다. manager는 이 경로에 없다.

장면 2. 사람이 터미널 창을 닫는다

세션은 detach되어 계속 돈다(owner 결정 F1). 백그라운드 일도 그대로다. 같은 디렉터리에서 다음에 claude를 치면 "실행 중인 세션이 있다, 이어 붙을까?"를 묻는다. 다시 붙으면 처음에는 모드를 되돌리고 폭을 한 칸 흔들어 TUI가 다시 그리게 한다. 보이는 화면은 돌아오지만 그 위의 scrollback과 창 제목은 돌아오지 않는다(측정). plain claude였다면 창을 닫을 때 세션이 끝났다.

장면 3. 폰에서 웹으로 연다

  • GUI는 bridge mod로 흐름을 보고, 보내고, 권한에 답하고, 모델·effort·모드를 바꾼다(오늘의 desk와 같다).
  • "plan 모드에서 나오기"를 누르면 봉인된 명령 하나가 기계로 가고, 기계 쪽 매크로가 정해진 키(Shift+Tab)를 보낸다. 결과는 bridge가 보고하는 권한 모드로 확인한다. 턴이 돌거나 일이 남아 있으면 버튼은 이유와 함께 꺼져 있다. 그동안 사람의 TUI에는 "원격 매크로 실행 중"이 뜬다.
  • rewind 지점 고르기처럼 화면에서 골라야 하는 조작은 원격에서 바로 되지 않는다. 그 자리에 "GUI 모드로 이어 가기"가 보인다(장면 6).

장면 4. manager가 죽거나 업데이트된다

사람에게는 아무 변화가 없다. 사람의 터미널은 host에 직접 붙어 있기 때문이다. 다시 뜬 manager는 roster로 host들을 재입양하고, host에 남아 있는 lease·fence 기록을 초기화하지 않고 그대로 읽는다. 돌던 매크로는 취소되고 다시 실행되지 않는다. 세션을 재시작하지는 않는다.

장면 5. 24시간 동안 아무 일이 없다

Claude Code 프로세스 하나가 수백 MB를 쓰므로(이 MacBook에서 평균 281 MB) 오래 버려진 세션은 끝낸다(F2). 조건은 클라이언트도 웹 구독도 없고, 턴이 돌지 않고, 백그라운드 일과 예약된 cron이 없는 상태로 24시간이다. "일이 없다"는 판정은 잘못되면 일을 죽이므로 이렇게 한다.

  1. 일 상태는 unknown | nonempty | verified-empty다. 최신 턴 시작 뒤에 온 Stop hook의 목록이 비어 있을 때만 verified-empty가 된다. 사용자가 끊은 턴이나 API 오류로 끝난 턴은 Stop이 없으므로 unknown이고, unknown은 절대 끝내지 않는다.
  2. host가 claude의 자식 프로세스를 실시간으로 본다. bridge child, MCP·LSP 서버 말고 하나라도 있으면 일이 있는 것이다.
  3. 끝내기 전에 bridge mod의 turn.step hook에 fence를 건다. 이 hook은 모든 턴이 모델을 부르기 직전에 지나는 곳이라, 그 사이에 시작하려는 턴을 붙잡아 host에 묻는다(측정: 프롬프트 hook은 ! 셸 모드와 대기열의 턴을 놓친다).
  4. 마지막으로 확인한 뒤 SIGTERM을 보낸다. 측정에서 SIGTERM은 종료 hook을 돌리고, 터미널을 복원하고, 대화를 모두 저장한 뒤 약 1초 안에 끝났다. 끝나지 않으면 강제 종료하지 않고 살려 둔다.
  5. 끝난 세션은 "잠듦"으로 남고, 다시 열면 같은 실행 옵션에 --resume을 붙여 이어진다.

장면 6. "GUI 모드로 이어 가기 (세션을 다시 띄움)"

mod로 안 되는 조작(rewind 지점 고르기, panel, 대부분의 dialog)을 원격에서 하려면 웹에서 PTY 종류 세션을 pipe 종류로 넘긴다(owner 결정 F4의 이름). pipe 종류에서는 SDK 제어 96종과 dialog 37종을 GUI로 다룬다. 프로세스가 바뀌므로 절차가 있다.

  1. 요청. 세션에 배타 lock과 fence를 건다.
  2. 비우기(취소할 수 있다). 기본은 돌던 턴과 백그라운드 일이 없어질 때까지 기다린다.
  3. 비었음을 확인한다. 새 활동이 생기면 다시 2로.
  4. 옛 프로세스가 끝난 것을 host의 waitpid로 확인한다.
  5. 같은 host 자리에서 claude -p … --resume <id>를 띄우고, 모델·effort·권한 모드 같은 세션별 설정을 다시 적용한다.
  6. MAWS 데몬의 Query가 붙고 웹이 새 프로세스를 따라간다. 사람의 터미널에는 "웹의 GUI 모드에서 이어 가는 중, 돌려받으려면 Enter"가 뜬다.

"지금 넘기기"는 경고를 거치는 명시적 선택이다. 끊긴 턴을 이어 돌리면 프롬프트 전체가 처음부터 다시 실행되기 때문이다. 돌려받기도 같은 절차를 거꾸로 한다.

설계를 받치는 계약들

  • 식별자를 넷으로 나눈다. holderId(host 자리), processEpoch(claude 자식마다 새 값), engineSessionId(대화 id, /clear·/branch로 프로세스는 그대로인 채 바뀐다), bindingGeneration(채널을 다시 묶을 때 증가). 하나로 뭉치면 정리나 이어 열기가 엉뚱한 대화를 고른다.
  • 화면 복원은 처음에 약속하지 않는다. 다시 붙는 클라이언트가 사람의 터미널뿐이라, 처음에는 모드 복원과 다시 그리기만 하고 잃는 것(scrollback, 제목)은 "불완전"으로 알린다. 정확한 복원은 나중의 개선이다. 그때도 범위를 정해 약속해야 한다. xterm.js의 serialize는 셀과 일부 모드만 저장하고 parser 상태는 저장하지 않아, 제어 문자열 중간에서 저장하면 RED가 1mRED로 돌아왔다(측정).
  • 터미널 질의에 답하는 쪽은 하나다. TUI가 커서 위치나 배경색을 물을 때, 답하는 쪽을 입력 owner와 따로 정한다. 다른 클라이언트의 답과 snapshot을 다시 그리면서 생긴 답은 버린다. 고정된 답(기종 정보)은 cache하고, 크기는 host가 현재 값으로 답한다. 붙은 터미널이 없을 때 커서·모드 질의에는 답하지 않는다.
  • MAWS가 쥔 일은 따로 센다. pipe 종류 세션에서 CLI 안의 일은 MAWS 데몬이 재시작해도 산다. 그러나 MAWS 안에서 돌던 MCP 도구 호출은 메모리에 있어 사라진다. 그런 호출에는 "결과 불명, 이미 실행됐을 수 있음"이라고 답해 같은 일이 두 번 실행되지 않게 한다.
  • 로컬 신뢰 경계는 같은 uid다. 소켓은 0700 디렉터리에 두고, token은 argv·로그·claude의 env가 아니라 fd로 건넨다. 웹은 키 바이트를 보내지 않는다. 웹이 일으키는 키 입력은 이름이 정해진 매크로뿐이고, 키 순서는 기계 쪽에 고정되어 있어 hub가 바꿀 수 없다.

7한눈에 비교

구조 누가 프로세스를 쥐나 (세션 모양) 원격 제어 표면 중계와 다시 붙기 사람의 터미널 돌던 일 우리가 쓸 수 있나
오늘의 desk 사람의 터미널 또는 엔진 supervisor (TUI) mod API와 $.command.run sminos → desk-hub. 구독마다 snapshot부터, 순번·보관 없음 그대로 쓴다. 창을 닫으면 세션이 끝난다 프로세스가 그대로라 산다 지금 쓰고 있다
Remote Control 사람의 터미널(REPL bridge) 또는 headless 서버 (TUI 또는 -p) user와 제어 23종 api.anthropic.com. 서버의 순번 로그, 열 때 기계에 닿지 않는다 그대로 쓴다 산다 아니오. Anthropic에 고정
SDK host host 앱: MAWS engine host, Desktop (-p) 제어 96종, 모든 dialog 같은 기계의 pipe. 재-initialize로 대기 질문을 다시 받는다 쓸 수 없다 host가 살아 있는 한 산다 예. MAWS가 쓴다
Desktop SSH 원격 기계의 claude-ssh 데몬 (-p) 제어 96종, Query는 Desktop에 SSH. seq와 16 MiB ring, 입력 전 checkpoint 쓸 수 없다 연결이 끊겨도 산다. helper를 교체하면 죽는다 메커니즘만 참고
엔진 --bg 엔진 supervisor와 pty-host (PTY 안의 TUI) control.sock 18 op, claude attach, 안의 mod 로컬 소켓. attach하면 다시 그린다 claude attach로 붙는다 supervisor 재시작엔 산다. 업그레이드엔 새로 띄운다 예. 다만 내부 프로토콜
holder 설계 우리 session host (TUI 또는 -p) mod와 상태로 확인되는 매크로. 나머지는 GUI 모드로 넘겨 96종(Query는 기계의 MAWS 데몬에) sminos → desk-hub. 구조화된 흐름만 나간다. pipe 종류는 seq와 ring plain과 같다. 창을 닫아도 세션은 산다 프로세스를 옮기지 않으므로 산다 설계 단계

세로로 읽으면 갈림길이 보인다. TUI를 그대로 두는 구조(desk, RC, --bg, holder)는 돌던 일과 사람의 터미널을 지키지만 제어 폭이 mod로 묶이고, headless 구조(SDK host, Desktop SSH)는 제어 폭이 가장 넓지만 사람의 터미널과 끊긴다. holder 설계는 첫 번째 쪽에 선다. 폭의 빈 곳은 상태로 확인되는 매크로로 일부만 메우고, 나머지는 두 번째 쪽으로 넘어가는 절차(GUI 모드)에 맡긴다. 웹 터미널 창으로 빈 곳을 다 메우는 길은 sminos·MAWS 구조를 깨므로 버렸다.

8지금 어디까지 왔나

owner가 정한 것

  • 웹은 두 경로의 세션을 모두 다룬다: 터미널·--bg 세션(bridge mod로 제어)과 MAWS의 SDK 세션(2026-10-19).
  • 사람이 여는 터미널 세션은 처음부터 wrapper를 통해 holder 안에서 돈다. PTY는 우리가 만든 holder가 쥐고, 엔진의 supervisor는 참고만 한다.
  • 경로는 세션이 어디서 시작됐는지로 정한다. 웹에 "GUI 모드로 이어 가기 (세션을 다시 띄움)" 버튼을 둔다(F4).
  • 웹 터미널 창은 두지 않는다. 조작성은 좋지만 기존 sminos·MAWS 구조를 깨기 때문이다(F5, F6, 2026-10-23). 키로만 되는 조작은 bridge 상태로 결과를 확인할 수 있는 것만 기계 쪽 매크로로 하고, 나머지는 GUI 모드로 넘긴다.
  • 사람이 터미널 창을 닫으면 detach되어 계속 돈다(F1). 24시간 동안 일이 없으면 끝낸다(F2). holder는 독립된 작은 서비스다(F3).

재서 확인한 것

  • bridge 한 홉은 수 ms이고 엔진 비용이 없다. 느린 것은 세션 열기 경로다.
  • mod로 대부분의 slash 명령이 돌고, panel은 큐를 막으며, PTY 키로는 rewind picker와 panel까지 다 된다.
  • 세션을 옮기면 Monitor, MCP 작업, 일부 서브에이전트를 잃고, headless는 엔진의 인계를 받지 못한다.
  • 우리 PTY 아래의 plain claude는 manager를 SIGKILL해도 살아남는다. 다시 붙을 때 모드 복원과 폭 흔들기로 보이는 화면은 돌아오지만 그 위의 scrollback과 제목은 돌아오지 않는다. Ctrl+Z는 process group을 바로 잡으면 plain과 같다.
  • SIGTERM은 graceful하고, turn.step이 모든 턴을 모델 호출 직전에 붙잡는다.
  • 설계 전체는 독립된 비판 검토를 한 차례 거쳤고, 화면 복원 약속, 정리 판정, lease 집행, 시작 경계, 식별자, 인증이 그 결과로 바뀌었다.

아직 모르는 것

  • bridge가 권한 모드의 변화를 바로 보고하는가. 매크로의 결과 확인이 여기에 기댄다.
  • detach된 동안 TUI가 커서 위치를 물을 때 답하지 않아도 멈추지 않는가.
  • Claude TUI의 출력 범위를 열거하고 화면 복원이 그 범위에서 정확한지 재는 시험. 이제는 정확한 이어 붙기를 개선으로 켤 때만 필요하다.
  • macOS에서 holder 아래 claude의 파일 권한(TCC)이 plain처럼 터미널 앱에 귀속되는가.
  • Linux에서 로그아웃 뒤에도 holder가 살아남는가(user scope와 lingering).
  • IDE 터미널의 /ide 연결과 이미지 붙여넣기가 holder 아래에서도 되는가.
  • SDK·Remote Control·피어 메시지로 시작하는 턴이 turn.step을 지난다는 것은 코드로만 읽었다. Claude Code가 업데이트될 때마다 정리 신호를 다시 잰다.

설계 단계에서 할 일은 여기까지다. 구현을 결정하면 다음은 실행 명세(execspec)를 쓰는 것이다.

9용어

엔진
Claude Code 프로세스 자체. TUI든 headless든 같은 엔진이다.
TUI / headless
터미널에 화면을 그리는 interactive 모양과, -p stream-json으로 JSON 줄만 주고받는 모양.
Query
Agent SDK가 claude -p를 띄우고 제어 프로토콜로 말하는 객체. host 쪽에 있다.
control_request
SDK와 RC가 공유하는 제어 봉투. host(또는 client)가 엔진에, 엔진이 host에 보낸다.
mod
TUI 프로세스 안에서 도는 플러그인 코드. bridge mod는 sminos 플러그인의 mod다.
plane
sminos 데몬의 세션 구독 계층. 처음에 snapshot, 그다음 live 이벤트를 준다.
hub / DO
desk-hub. Cloudflare Durable Object로 만든 중계. 배포마다 재시작하므로 정확성을 기대지 않는다.
소유자
세션 프로세스의 부모이자 PTY master 또는 stdio pipe를 쥔 쪽. 소유자가 죽으면 세션이 죽는다.
session host / manager / wrapper
holder 설계의 세 부분. 세션마다 하나인 작은 소유자, 사용자당 하나인 교체 가능한 관리자, 사람이 치는 claude를 가로채는 shim.
ring / checkpoint
최근 출력 바이트를 offset과 함께 담는 원형 버퍼, 그리고 그 offset에 대응하는 화면 상태 직렬화.
매크로
웹의 봉인된 명령 하나로 기계 쪽에서 정해진 키 순서를 보내고, bridge가 보고하는 상태로 결과를 확인하는 조작. 웹이 키를 넣는 유일한 길이다.
lease / fence
누가 지금 입력과 크기를 가지는지의 기록과, 그 기록이 바뀔 때마다 올라가는 번호. 옛 번호를 단 프레임은 거절된다.
epoch
세대 번호. RC의 worker_epoch, holder의 processEpoch처럼 "같은 이름의 다른 실체"를 가른다.
