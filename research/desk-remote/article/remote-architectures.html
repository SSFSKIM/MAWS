Claude Code 세션을 원격에서 이어 쓰는 세 가지 구조

터미널에서 하던 일을 폰에서 이어 쓴다. MAWS 앱이나 웹에서 새 세션을 열기도 한다. 두 경우는 프로세스의 소유자와 제어 통로가 다르다. 이 글은 오늘의 desk(bridge mod), Claude 자신의 프로토콜들, 그리고 연구 중인 두 경로 설계를 같은 그림 위에 놓고 따라간다.

1질문과 세 가지 답

원하는 것은 셋이다.

  1. 같은 세션을 이어 쓴다. 터미널에서 돌던 프로세스는 옮기지 않고 원격에서 본다. MAWS·웹에서 연 세션도 연결이 끊긴 뒤 다시 붙는다.
  2. 제어 폭이 넓다. 말을 걸고, 권한에 답하고, 모델과 모드를 바꾸고, 되감는다. 경로 A는 mod의 한계 안에서 폭을 넓힌다. 경로 B는 SDK 제어를 GUI로 제공한다.
  3. 돌던 일을 잃지 않는다. 세션은 거의 idle이 아니다. 백그라운드 셸, 서브에이전트, Monitor, MCP 작업이 늘 돈다.

위의 그림 1을 한 줄로 읽으면 이렇다.

  • 오늘의 desk는 세션 안에 손님으로 들어간 mod로 원격 제어를 한다. 프로세스는 사람의 터미널이나 엔진의 --bg supervisor가 쥔다.
  • Remote Control도 세션 안의 코드(REPL bridge)로 원격 제어를 하지만, 중계가 Anthropic 서버이고 URL이 거기에 고정돼 있다.
  • 두 경로 설계는 세션이 시작된 곳을 기준으로 나눈다. 경로 A는 터미널·--bg 세션을 bridge mod로만 제어한다. 경로 B는 MAWS 앱이나 웹에서 연 claude -p 세션을 holder가 쥔다. 기계의 MAWS 데몬에 있는 Query가 제어한다. 살아 있는 터미널 세션은 B로 옮기지 않는다.

2먼저 알아 둘 네 가지

세션 프로세스의 두 모양

Claude Code 세션은 같은 엔진이 두 모양으로 돈다. transcript 형식(JSONL)은 같다.

  • TUI(interactive). 사람이 claude를 치면 뜨는 것. 터미널(PTY)에 화면을 그리고 키를 받는다. 패널, 확인 창, rewind picker, Shift+Tab 모드 순환 같은 것은 이 화면에만 있다.
  • headless(stream-json). claude -p --input-format stream-json --output-format stream-json. 화면이 없다. 한 줄에 JSON 하나로 대화하고, 화면은 그 JSON을 받는 쪽(host)이 그린다. MAWS, Claude Desktop, claude.ai가 이 모양을 쓴다.

소유자: 프로세스를 쥔 쪽

소유자는 세션 프로세스의 부모이고, 그 PTY master 또는 stdin·stdout pipe를 쥔 쪽이다. 소유자가 죽으면 세션도 죽는다. PTY master가 닫히면 claude는 SIGHUP을 받고 exit 129로 끝난다(측정). 백그라운드 셸, 서브에이전트, Monitor, MCP 작업은 모두 그 프로세스 안이나 그 자식에서 돈다. 그래서 소유자를 바꾸지 않는 것이 곧 돌던 일을 지키는 것이다.

제어 표면: 원격이 무엇을 할 수 있는가

세션을 바깥에서 움직이는 통로는 넷이고, 폭이 다르다.

여기서 중요한 관찰 하나. 제어 폭이 가장 넓은 SDK 프로토콜은 headless 세션에만 있고, 사람이 쓰는 TUI 세션에는 mod와 키 입력만 닿는다. 이 글의 모든 갈림길이 여기서 나온다.

중계와 순번: 끊겼다 돌아왔을 때

원격 연결은 끊긴다. 다시 붙을 때 클라이언트가 "어디까지 봤다"를 말하고, 상대가 "그 뒤부터"를 줄 수 있어야 한다. 그러려면 누군가 이벤트에 순번(seq)을 매기고 최근 구간을 보관해야 한다. 그 주체가 권위다. Remote Control은 Anthropic 서버가, Desktop SSH 모드는 원격 기계의 데몬이 이 일을 한다. 오늘의 desk의 bridge 경로에는 이것이 없다.

3오늘의 desk: 세션 안의 bridge mod

흐름

  1. 세션 안. sminos 플러그인이 로드된 모든 claude 안에서 bridge mod가 돈다. mod는 transcript 행(session.append), 토큰 조각(turn.step), 권한 프롬프트(PermissionRequest hook)를 본다.
  2. 기계 안의 한 홉. mod는 이벤트마다 자기가 띄운 bridge child(Python 프로세스)에 Unix 소켓으로 HTTP POST를 한 번 한다.
  3. sminos 데몬. bridge child의 스트림을 구독한다. plane(세션 구독: snapshot부터, 그다음 live), uplink(hub로 가는 SSE 아래·POST 위), 신뢰 경계(웹에서 온 명령의 봉인 검증, nonce 원장, 읽기 전용, 권한 상한)가 여기 있다.
  4. desk-hub. Cloudflare Durable Object다. 기계와 브라우저를 잇는 중계일 뿐 믿지 않는다. transcript를 저장하지 않는다(설계 약속).
  5. desk-web. 브라우저에서 행과 델타를 그리고, 보내기·steer·권한 답 같은 명령을 봉인해 보낸다.

세션을 띄우는 길은 둘이다. 웹의 Spawn은 claude --bg, Resume은 claude --bg --resume을 돌려 엔진의 supervisor에 맡긴다(4.4). 사람이 터미널에서 연 세션에도 mod가 돌기 때문에 그 세션도 desk에 나타나고, 웹에서 제어된다.

되는 것과 안 되는 것

  • 된다: 행과 토큰 델타 관찰(서브에이전트 포함), idle일 때 프롬프트 보내기, 턴 중 steer($.session.append), 권한 프롬프트와 AskUserQuestion 답(터미널과 경쟁해 먼저 답한 쪽이 이긴다), interrupt, 모델·effort, $.command.run으로 /model·/mcp disable·/compact·/clear·/plan 같은 slash 명령.
  • 안 된다: 일반 dialog(request_user_dialog 37종 중 권한·질문·MCP elicitation 밖의 것), plan 밖의 권한 모드 전환, rewind 지점 고르기, /usage·/permissions 같은 panel. panel이 열리면 그 뒤의 명령이 줄을 서서 멈춘다. Esc로 턴을 멈춘 뒤에는 사람이 입력할 때까지 mod 명령이 거부된다.

성능과 약점

bridge 한 홉은 빠르다. 텍스트 델타가 mod에서 구독자까지 p50 1.8 ms, p95 5.7 ms, p99 14.5 ms였고, mod를 켜고 끈 차이가 엔진 성능에 나타나지 않았다. 사람이 느끼는 "desk가 느리다"는 다른 곳에서 온다.

  • 세션 열기가 느리다. 운영에서 한 번 여는 데 5.4 s, 19 s 넘게, 51 s 넘게 걸린 일이 있었다. plane이 엔진이 아직 쓰지 않은 행을 기다리고(2.0–2.4 s, 메시지가 끝나야 행이 써진다), 0.25 s 주기로만 다시 보고, 큰 transcript를 처음부터 색인하고, uplink 스레드 하나가 hub POST(매번 새 TLS, 140–230 ms)에 묶인다.
  • 연결 계약이 약하다(#52). Resume에 30초가 걸린다. 재전송한 명령이 60초 창을 넘겨 stale로 거부된다. 브라우저 소켓은 close 신호만 기다려 죽은 연결을 늦게 안다. 구독마다 snapshot부터 다시 받는다.
  • 뿌리. bridge 경로에는 순번과 보관 구간이 없고, hub는 아무것도 저장하지 않는다. 그래서 다시 붙을 때마다 기계까지 왕복해 처음부터 받는다.

이 구조의 진짜 장점

mod는 사람의 TUI 안에 손님으로 들어가 있을 뿐이다. 웹이 붙어도 프로세스는 옮겨지지 않으므로 터미널도, 백그라운드 일도 그대로다. 대신 제어 폭이 mod API로 묶이고, 사람이 터미널 창을 닫으면 세션도 끝난다.

4Claude의 네이티브 길들

4.1 Remote Control (RC)

  • 두 진입점. TUI 안에서 /remote-control을 켜면 그 프로세스 안의 REPL bridge가 worker가 된다(지금 이 대화 하나를 중계). claude remote-control은 headless 서버로, 자식 claude --print를 세션마다 띄운다.
  • 전송. worker는 SSE로 읽고(/worker/events/stream?from_sequence_num=n), HTTP로 쓴다. 이벤트 배치(POST /worker/events, 100개·10 MiB 이하), 상태 문서(PUT /worker: idle·running·requires_action, 모드·컨텍스트 등), 전달 영수증, heartbeat가 있다.
  • 서버가 권위다. 서버가 이벤트에 순번을 붙여 쌓는다. 그래서 client가 세션을 열거나 다시 붙을 때 worker 기계와 통신하지 않는다. 기계가 잠들어 있어도 기록은 열린다. 이것이 RC가 빠르게 열리는 근원이다.
  • worker는 세션당 하나(worker_epoch). 새 worker가 등록하면 옛 worker는 409와 close 4090으로 물러난다.
  • 제어. client가 worker로 넣을 수 있는 대화 프레임은 user 하나다. 나머지는 SDK와 같은 control_request 봉투의 23종(interrupt, set_model, set_permission_mode, stop_task 등)이다. worker가 client에게 묻는 것은 권한(can_use_tool)과 dialog(request_user_dialog) 둘이고, 터미널과 동시에 떠서 먼저 답한 쪽이 이긴다.
  • 약점. claude.ai의 실시간 소켓은 replay가 없다. keep-alive는 50초마다 오고, 오프라인 판정은 70초 뒤에 내리며, 6번 시도한 뒤에는 사람이 다시 눌러야 한다. 비교한 시스템 중 가장 느리다.
  • 우리가 쓸 수 없다. worker URL은 Anthropic 호스트로 고정돼 있다(--sdk-url allowlist, CLAUDE_BRIDGE_BASE_URL은 선언만 있고 늘 비어 있음). 같은 위치에 우리가 들어갈 수 있는 유일한 통로가 mod다. 그래서 desk의 bridge mod가 RC의 REPL bridge 자리를 흉내 낸다.

4.2 SDK stdio 제어 프로토콜

  • 무엇인가. Agent SDK의 Query 객체가 claude -p를 띄우고 stdin·stdout으로 말하는 프로토콜이다. MAWS의 engine host, Claude Desktop, claude.ai(브라우저가 SDK host로 동작)가 모두 이것을 쓴다.
  • 폭. host가 보낼 수 있는 제어 요청이 96종이다: interrupt, set_model, set_permission_mode, rewind_conversation, mcp_toggle, read_file, stop_task 등. 엔진은 host에게 권한, dialog, hook callback, MCP elicitation 등 16종을 묻는다.
  • dialog. request_user_dialog는 37종이다(권한 여러 종류, MCP elicitation, sandbox 네트워크, auto 모드, computer use 승인, plugin 힌트 등). host가 initialize에서 선언한 종류만 오고, 선언하지 않은 종류는 닫힌 채로 실패한다. 즉 host가 dialog를 그리는 GUI를 가지면 터미널 없이 모든 dialog를 다룰 수 있다.
  • 다시 붙기. host가 다시 initialize를 보내면 엔진이 열려 있던 권한·dialog 요청을 다시 보낸다. 대기 중인 질문은 이벤트가 아니라 엔진이 쥔 상태다.
  • 한계. 사람이 쓰던 TUI 세션은 이 프로토콜로 움직일 수 없다. TUI 세션을 이 모양으로 바꾸려면 프로세스를 끝내고 --resume으로 다시 띄워야 하고, 그때 돌던 일을 잃는다(5장).

4.3 Claude Desktop의 SSH 모드 (claude-ssh)

  • 원격 데몬이 프로세스를 소유한다. 원격 기계의 ~/.claude/remote/srv/<ver>/server --serve가 모든 claude의 부모다. SSH 연결은 그 데몬의 0600 Unix 소켓으로 가는 pipe일 뿐이라, 끊겨도 원격에는 변화가 없다.
  • 출력마다 순번, 입력마다 offset. 데몬이 프로세스마다 마지막 16 MiB의 출력 프레임을 seq와 함께 둔다. 입력은 process.stdin{data, offset}로 보내고 데몬이 stdinApplied를 알려 주므로, 같은 바이트를 두 번 보내도 한 번만 쓰인다.
  • 입력 전에 checkpoint. Desktop은 입력을 쓰기 전마다 줄 경계의 출력 위치 {seq, skipBytes}를 디스크에 남긴다. 앱을 껐다 켜도 살아 있는 프로세스를 재입양하고 정확히 그 뒤부터 replay한다.
  • 대기 중인 질문은 상태다. 다시 initialize하면 엔진이 열린 권한·dialog 요청을 다시 보내고, SDK가 request_id로 중복을 없앤다.
  • 생존 감지가 빠르다. 7초 동안 아무것도 오지 않을 때만 ping을 보내고, 2번 놓치면 끊는다. 깨어날 때, 네트워크가 바뀔 때 즉시 다시 붙는다.
  • 한계. 프로세스는 claude -p뿐이라 사람이 쓰던 TUI와는 상관이 없다. 데몬(helper)을 교체하면 자식이 모두 죽는다. 그리고 이 helper는 Desktop 전용이라 우리가 그대로 쓸 수 없다. 메커니즘만 가져온다.

4.4 엔진의 백그라운드 supervisor (claude --bg)

  • 무엇인가. claude --bg, claude agents, /background로 만든 세션은 엔진 자신의 supervisor(claude daemon run)가 소유한다. 세션마다 --bg-pty-host 프로세스가 PTY를 쥐고, 그 안에서 평범한 interactive REPL이 돈다. stream-json 세션이 아니다.
  • 내구성. supervisor가 재시작해도 살아 있는 pty-host를 다시 입양한다. 아무 터미널에서나 claude attach <short>로 붙을 수 있고, 여러 명이 동시에 붙는다.
  • 제어. control.sock(op 18개)이 목록, 상태, reply, subscribe, attach, kill을 준다. reply는 사람이 친 것처럼 slash 명령을 돌리고 턴 중에도 /model·/effort를 즉시 바꾸지만, 권한 프롬프트는 승인하지 못한다.
  • /background는 프로세스를 옮기지 않는다. transcript를 flush하고 --resume … --fork-session으로 새 job을 띄운 뒤 터미널 쪽 세션을 끝낸다. 엔진 자신의 resume handoff다(무엇이 따라가는지는 5장).
  • 우리 것으로 쓰기 어려운 이유. 소켓 경로는 설정으로 바꿀 수 없고, op와 프레임은 공개되지 않아 릴리스마다 바뀔 수 있다. 바이너리가 바뀌면 job을 새 버전으로 다시 띄우고, 부모도 클라이언트도 없는 pty-host는 60초 뒤 끝낸다. 돌던 일을 지키려는 목적과 맞지 않는 정책들이다.

4.5 막혀 있는 길

  • RC worker를 우리 서버로. --sdk-url은 Anthropic 호스트만 받는다. CLAUDE_BRIDGE_BASE_URL은 늘 비어 있다. SDK host가 보내는 remote_control 요청도 항상 Anthropic에 Anthropic 계정으로 붙는다.
  • TUI의 thin-client 모드. TUI 코드 안에는 원격 세션을 그리는 모드 셋(ccr, ssh, direct)과 claude cc://…, claude ssh 진입점이 있다. 그러나 진입점을 여는 값이 어디서도 설정되지 않아 2.1.300에서는 닿을 수 없다(코드로 확인, 2.1.307은 확인하지 않음).
  • Channels. MCP 서버가 세션에 메시지를 밀어 넣는 기능은 first-party 전용이고 기본으로 꺼져 있다. 들어온 메시지도 사람의 말이 아니라 <channel>로 감싸진다.

"터미널 세션을 원격에서 SDK 수준으로 제어하자"는 생각은 자연스럽게 "그 세션을 headless로 옮기자"가 된다. 실제로 옮겨 보았다(2.1.307).

결론

돌고 있는 터미널 세션을 이어 쓰는 길은 프로세스를 그대로 두고 bridge mod로 제어하는 것이다. 제어 폭은 mod API 안에서 넓힌다. 살아 있는 세션을 headless로 옮기는 길은 버렸다(F7). holder는 MAWS 앱이나 웹에서 처음부터 여는 경로 B 세션만 쥔다. 끝난 터미널 세션은 살아 있는 소유자가 없음을 확인한 뒤 B로 다시 열 수 있다. 근거는 설계 §1·§7과 인계 측정이다.

6연구 중인 설계: 두 경로와 holder

경로 A는 사람이 터미널에서 띄운 세션과 엔진의 --bg 세션이다. holder 밖에서 돌고, 원격 제어는 bridge mod만 맡는다. 경로 B는 MAWS 앱이나 웹에서 연 claude -p stream-json 세션이다. 세션마다 작은 host가 프로세스를 쥔다. Query는 같은 기계의 MAWS 데몬에서 제어한다. 데몬이 재시작해도 CLI 프로세스는 건드리지 않는 것이 목표다. 다음은 구현 결과가 아니라 2026-10-24 설계다.

원칙: 프로세스의 날것 스트림은 기계를 떠나지 않는다

웹이 받는 것은 bridge 행과 MAWS의 X1 이벤트다. 보내는 것은 동작마다 봉인된 명령이다. PTY 바이트도 SDK stdio도 hub로 나가지 않는다(F5).

  • 웹 터미널 창은 두지 않는다. raw 입력이 믿지 않는 hub를 지나면 기존 신뢰 계약 밖에 실행 통로가 생긴다. MAWS GUI가 모르는 두 번째 제어면도 생긴다.
  • Query는 브라우저가 아니라 기계의 MAWS 데몬에 둔다. MAWS의 in-process MCP 도구와 hook callback은 Query와 같은 프로세스에 산다. Query는 엔진의 질문에 답하는 쓰는 쪽 하나다. 잠드는 탭이나 여러 탭 중 하나에 맡길 수 없다.

구성 요소

  • session host. 세션마다 하나이며 작게 유지한다. claude의 stdin·stdout·stderr pipe를 쥔다. stdout을 JSONL 줄로 나눠 seq를 붙이고 최근 출력 ring을 둔다. 보관 창 밖의 요청에는 gap을 알린다. 입력 offset으로 중복을 없앤다. writer fence로 옛 Query의 쓰기를 거절한다. 비공개 출력과 제어보다 인증이 먼저다. 실제 종료는 waitpid로 확인한다.
  • holder manager. 사용자당 하나이며 교체할 수 있다. roster의 pid·시작 시각·식별자를 인증된 host의 hello와 대조해 재입양한다. 수명 정책은 manager에 둔다. fence와 적용 offset은 host에 남는다. manager가 재시작해도 이 기록을 초기화하지 않는다.
  • MAWS 데몬의 Query. input을 쓰기 전에 출력 checkpoint를 영속 저장한다. 다시 붙을 때 입력 offset을 host의 stdinApplied로 맞춘다. 재초기화로 대기 중인 권한·dialog를 다시 받는다. MAWS 소유 도구의 효과를 실행하기 전에는 durable request ledger를 쓴다.
  • bridge mod. 경로 A에서는 통제자다. 경로 B에서는 제어를 거절하거나 MAWS 데몬으로 넘긴다. 관찰 전용으로 서브에이전트 델타를 Query 쪽에 주고, turn.step에서 정리 문을 집행하는 설계다.
  • 웹과 plane. 두 경로는 cursor와 연결·신뢰 계약, X1 표시 어휘를 공유한다. 웹은 세션의 명령별 gui | none 목록으로 조작을 그린다. 경로 A의 plane seq는 sminos 데몬이 매긴다. 경로 B의 plane seq는 MAWS 데몬 하나만 매긴다.

holder는 MAWS engine host에 흡수한다(F3 개정). 지금 엔진 프로세스를 쥐는 E10 supervisor를 claude-ssh의 전송·재입양 방식으로 강화하는 것이다. manager는 Electron에 기대지 않는 Node 빌드다. 세션마다의 작은 native host도 MAWS가 함께 배포한다. Go가 유력하지만 확정된 구현은 아니다(설계 §3).

장면으로 따라가기

장면 1. 폰에서 MAWS 세션을 연다

  1. 웹이 봉인된 명령을 보낸다. desk-hub를 거친 명령은 sminos 데몬이 검증한 뒤 MAWS 데몬에 전달한다.
  2. manager가 세션 host를 띄운다. host가 소켓과 roster 항목을 만들고 ready를 보낸다. manager의 commit을 받은 뒤에만 claude를 fork한다. commit 뒤 응답이 사라져도 같은 세션을 하나 더 띄우지 않고 기록을 대조한다.
  3. 기계의 Query가 host를 통해 claude -p와 통신한다. 웹은 X1 이벤트로 화면을 그린다. SDK 제어 요청 96종과 dialog 37종을 GUI로 다루는 것이 설계의 제어 범위다.

장면 2. 폰이 잠들었다가 다시 연결된다

폰과 hub의 연결이 끊겨도 Query와 host는 기계에서 계속 돈다. 웹은 마지막으로 본 cursor를 보내 놓친 구간을 요청한다. 두 경로가 같은 연결 계약을 쓴다. 웹의 cursor와 host의 출력 checkpoint는 서로 다른 복구 경계다. host ring은 Query의 재입양에 쓰고, 웹에는 raw stdout 대신 plane의 구조화된 흐름을 준다. 보관 구간을 벗어난 gap은 정확한 replay처럼 숨기지 않는다(연구 §3.7·§4).

장면 3. MAWS 데몬이 재시작된다

  1. session host와 claude는 계속 돈다. CLI가 소유한 백그라운드 셸·서브에이전트·Monitor는 같은 프로세스에서 이어진다.
  2. 새 manager가 roster로 host들을 재입양한다. 새 Query가 writer fence를 얻으면 옛 Query의 늦은 쓰기는 거절된다.
  3. Query가 저장된 출력 checkpoint부터 읽는다. 입력 offset은 stdinApplied로 맞춘다. ring에 gap이 있으면 줄 경계를 맞추고 transcript를 다시 읽어 상태를 세운다.
  4. 다시 initialize한다. 엔진이 대기 요청을 다시 보내면 request id로 replay와의 중복을 없앤다.
  5. MAWS 안에서 돌던 MCP 도구 호출과 hook callback은 별도 복구 대상이다. ledger의 고아 요청에는 “결과 불명, 이미 완료됐을 수 있다”고 답한다. 자동 재시도로 같은 효과를 다시 내지 않는다.

계획된 재시작에서는 MAWS 소유 요청이 끝나기를 기다린다. timeout만으로 강제 중단을 허용하지 않는다. host 자체가 죽으면 pipe가 닫혀 세션이 끝난다. 그 경우는 재입양이 아니라 종료를 표시하고 resume을 제안한다(설계 §3.3·§5).

장면 4. 24시간 동안 아무 일이 없다

24시간 정리는 경로 B에만 적용한다(F2). 붙은 Query는 클라이언트로 세지 않지만 웹 구독은 센다. 클라이언트가 없고, 턴이 없고, 일이 verified-empty이며, descendant 검사에도 일의 흔적이 없을 때만 시계가 간다. 조건이 깨지거나 manager가 재시작하면 시계는 0부터 간다. 24시간은 설정값이다.

  1. 최신 turn start 뒤의 Stop에서 background_tasks와 session_crons가 모두 명시적으로 비어 있어야 verified-empty다. 목록이 없거나 턴이 interrupt·API error로 끝나면 unknown이다. unknown은 정리하지 않는다.
  2. turn start, background tool launch, Query 재접속, 대화 id 변경은 빈 상태 판정을 무효화한다. 등록된 bridge child와 MCP·LSP 서버 외의 descendant가 있으면 정리를 막는다. 자식이 없다는 것만으로 일이 비었다고 판단하지 않는다.
  3. host가 관찰 bridge의 turn.step 문에 reap fence를 먼저 건다. 문이 건강하지 않으면 정리하지 않는다. cron과 task 알림은 Query를 거치지 않고 턴을 시작하므로 Query만 막아서는 부족하다.
  4. 일 상태·generation·클라이언트·descendant를 최종 확인한 뒤 SIGTERM을 보낸다. 경쟁한 턴은 정리를 취소하고 진행하거나, 이미 신호를 보낸 경우 종료 중이라는 응답을 받는다.
  5. 끝나지 않으면 SIGKILL로 올리지 않는다. unknown으로 되돌리고 세션을 살려 둔다. waitpid로 종료를 확인한 경우에만 “잠듦”으로 기록한다. 다시 열 때 충돌하는 기존 실행 인자를 지우고 --resume <engineSessionId>를 넣는다.

이 정리 문과 SIGTERM 마감은 TUI에서만 측정했다. 경로 B의 -p에서 같은 보장을 얻는지는 아직 검증해야 한다(측정, 설계 §3.2·§9).

장면 5. 터미널 세션을 폰에서 제어한다

사람이 터미널에서 시작한 claude는 plain으로 남는다. --bg 세션은 엔진 supervisor가 쥔다. 웹은 둘 다 bridge mod를 통해 제어한다. holder는 관여하지 않는다. 웹은 경로 이름 대신 capability 목록을 보고 가능한 조작만 제공한다.

  • gui. 행·토큰 조각·서브에이전트 관찰, 프롬프트·steer, interrupt, 권한·질문 답, model·effort 덮어쓰기, $.command.run으로 닿는 slash 명령이다.
  • 현재의 none. rewind 지점 고르기, /usage·/permissions·인자 없는 /mcp panel, 일반 dialog 대부분, plan 외의 권한 모드 전환이다. mod 제어 표면을 넓히면 이 목록을 바꾼다.

권한 답은 터미널과 경합한다. 먼저 답한 쪽이 이긴다. mod 제어 한계를 없애려고 살아 있는 세션을 B로 옮기지는 않는다(현재 측정, 설계 §3.4·§3.5).

장면 6. 끝난 터미널 세션을 다시 연다

  1. 기계가 엔진 레지스트리(~/.claude/sessions/<pid>.json)에서 살아 있는 소유자를 확인한다. 있으면 B로 다시 열기를 거절한다.
  2. 소유자가 없으면 MAWS가 claude -p … --resume <id>로 경로 B 세션을 연다. 대화를 이어 여는 것이지 살아 있는 프로세스나 작업을 옮기는 것이 아니다.
  3. 첫 resume에 CLAUDE_CODE_RESUME_INTERRUPTED_TURN을 자동으로 켜지 않는다. 끊긴 턴을 다시 돌리면 foreground 명령까지 처음부터 실행되기 때문이다.

설계를 받치는 계약들

  • 식별자를 넷으로 나눈다. holderId는 host 자리다. processEpoch는 claude 자식마다 새 값이다. engineSessionId는 현재 대화다. bindingGeneration은 채널을 다시 묶을 때 증가한다. 대화 id가 바뀌면 제어와 transcript를 원자적으로 다시 묶고 옛 맥락의 명령을 거절한다.
  • 출력 보관과 소비 기록은 다르다. host의 seq ring만으로 Query의 소비 위치와 응답 이력이 복원되지는 않는다. Query는 input write 전에 줄 경계의 {seq, skipBytes}를 영속 commit한다. gap이면 transcript로 상태를 다시 세우고 정확한 replay로 표시하지 않는다.
  • 쓰는 쪽은 하나다. host가 writer fence를 집행한다. 새 Query는 stdinApplied로 입력 offset을 맞춘다. 재전달된 권한·dialog 요청은 request id로 중복을 없앤다.
  • MAWS가 쥔 일은 따로 복구한다. CLI 생존이 MAWS 소유 호출의 생존을 뜻하지 않는다. 효과 전에 durable request ledger를 남긴다. 재시작 뒤 결과를 알 수 없으면 그 불확실성을 응답에 남긴다.
  • 인증 뒤에 출력과 제어를 연다. 로컬 신뢰 경계는 같은 uid다. 소켓은 0700 디렉터리에 두고 소유권과 symlink를 검사한다. token은 fd나 pipe로 건네며 argv·로그·claude 자식의 env에 넣지 않는다. 원격 명령은 principal·session·processEpoch·bindingGeneration에 묶는다. 표시 무결성과 hub가 내려주는 JS의 신뢰 한계는 아직 열린 결정이다.

계약의 세부는 설계 §3–§6에 있다. 전송과 재입양의 기준은 claude-ssh 조사다. 엔진 supervisor의 orphan 정리나 claude-ssh의 멈춘 프로세스 교체 정책은 가져오지 않는다.

이전 판에서 설계했다가 뺀 것

첫 판은 모든 터미널 claude를 wrapper로 우리 PTY holder 안에서 띄웠다. 창을 닫아도 세션을 남기려는 구조였다. 웹 터미널 창은 raw 입력과 별도 제어면을 만들기 때문에 먼저 뺐다(F5). 살아 있는 세션의 “GUI 모드로 이어 가기”도 뺐다(F7). 옮기면 Monitor·MCP 작업을 잃고 서브에이전트의 진행 중 명령을 다시 돌리는 대가가 컸다. PTY holder만 남겨도 모든 실행 경로를 바꿔야 했다. 매크로와 화면 복원 설계도 함께 철회했다. 근거와 이력은 설계 §7·§11, 이전 PTY 측정, 백그라운드 작업 인계 측정에 남아 있다.

7한눈에 비교

구조 누가 프로세스를 쥐나 (세션 모양) 원격 제어 표면 중계와 다시 붙기 사람의 터미널 돌던 일 우리가 쓸 수 있나
오늘의 desk 사람의 터미널 또는 엔진 supervisor (TUI) mod API와 $.command.run sminos → desk-hub. 구독마다 snapshot부터, 순번·보관 없음 그대로 쓴다. 창을 닫으면 세션이 끝난다 프로세스가 그대로라 산다 지금 쓰고 있다
Remote Control 사람의 터미널(REPL bridge) 또는 headless 서버 (TUI 또는 -p) user와 제어 23종 api.anthropic.com. 서버의 순번 로그, 열 때 기계에 닿지 않는다 그대로 쓴다 산다 아니오. Anthropic에 고정
SDK host host 앱: MAWS engine host, Desktop (-p) 제어 96종, 모든 dialog 같은 기계의 pipe. 재-initialize로 대기 질문을 다시 받는다 쓸 수 없다 host가 살아 있는 한 산다 예. MAWS가 쓴다
Desktop SSH 원격 기계의 claude-ssh 데몬 (-p) 제어 96종, Query는 Desktop에 SSH. seq와 16 MiB ring, 입력 전 checkpoint 쓸 수 없다 연결이 끊겨도 산다. helper를 교체하면 죽는다 메커니즘만 참고
엔진 --bg 엔진 supervisor와 pty-host (PTY 안의 TUI) control.sock 18 op, claude attach, 안의 mod 로컬 소켓. attach하면 다시 그린다 claude attach로 붙는다 supervisor 재시작엔 산다. 업그레이드엔 새로 띄운다 예. 다만 내부 프로토콜
두 경로 설계 A: 터미널·엔진 supervisor (TUI). B: MAWS의 session host (-p) A: bridge mod. B: SDK 제어 96종과 dialog 37종. Query는 기계에 있다 같은 sminos → desk-hub plane과 cursor 계약. B의 Query는 host ring·checkpoint로 재입양한다 A: 그대로 쓴다. B: 터미널 없이 GUI만 쓴다 A: 소유자를 바꾸지 않는다. B: CLI 일은 데몬 재시작에도 유지하는 설계다. MAWS 소유 호출은 별도 복구한다 설계 단계. holder는 B에만 적용한다

세로로 읽으면 제어 표면과 프로세스 소유가 별개임을 알 수 있다. 새 설계는 두 경로를 유지한다. 터미널에서 시작한 A는 프로세스를 옮기지 않고 mod 제어 폭을 넓힌다. MAWS·웹에서 시작한 B는 처음부터 headless로 열고 SDK 제어를 쓴다. 두 경로의 차이는 기계 안에 두고, 웹은 같은 plane과 capability 목록을 쓴다. 끝난 A의 대화는 B로 다시 열 수 있지만 살아 있는 소유자가 있으면 거절한다.

8지금 어디까지 왔나

owner가 정한 것

  • 두 경로. 터미널·--bg 세션은 A다. MAWS 앱이나 웹에서 연 세션은 B다. 경로는 시작점으로 정한다.
  • F7 (2026-10-24). 터미널 세션은 holder 밖에서 bridge mod로만 제어한다. 제어 한계는 받아들이되 mod 표면을 최대한 넓힌다. 살아 있는 세션을 B로 옮기지 않는다. 끝난 대화의 resume만 남긴다. F1의 창을 닫아도 유지하는 약속과 F4의 전환 버튼은 철회됐다.
  • F5 (2026-10-23). 웹 터미널 창은 두지 않는다. raw 프로세스 스트림은 기계를 떠나지 않는다. F6에서 남겼던 우회 조작도 F7로 철회됐다.
  • F3 개정 (2026-10-24). holder는 독립 서비스가 아니라 MAWS engine host의 일부다. E10 supervisor를 claude-ssh 방식으로 강화한다.
  • F2. 클라이언트와 턴, 백그라운드 일, cron이 없는 상태로 24시간이 지난 경로 B 세션을 정리한다. unknown은 정리하지 않는다. 시간은 설정값이다.

유효한 결정과 철회 이력은 설계 §1·§7을 따른다. 구현 승인은 아직 아니다.

재서 확인한 것과 코드로 읽은 것

  • bridge 측정에서 한 홉은 수 ms였다. mod를 켜고 끈 엔진 성능 차이는 관측되지 않았다. 세션 열기와 hub 왕복이 느린 구간이었다.
  • 명령 측정에서 mod로 대부분의 slash 명령이 돌았다. panel은 큐를 막았다. 현재의 제어 가능·불가능 목록은 이 측정에 근거한다.
  • 인계 측정에서 Monitor·MCP 작업을 잃었다. 서브에이전트의 진행 중 명령은 재실행될 수 있었다. headless는 엔진의 인계 파일을 읽지 않았다.
  • 2.1.308 정리 측정은 TUI에서 했다. SIGTERM의 graceful 마감과 turn.step이 ! 셸 모드 완료·대기열 prompt의 턴을 붙잡는 것을 확인했다. -p에서 확인한 결과는 아니다.
  • SDK·Remote Control·peer·channel origin이 같은 턴 경로를 쓴다는 것은 코드로만 읽었다. claude-ssh 조사의 전송·재입양 계약도 새 holder가 이미 구현됐다는 증거는 아니다.

아직 모르는 것

  • -p stream-json에서 관찰 bridge가 로드되는가. turn.step이 cron 발화와 task 알림의 턴까지 붙잡는가. SIGTERM이 TUI와 같은 graceful 마감을 하는가.
  • 경로 A의 mod 제어 표면을 어디까지 넓힐 수 있는가. 닿지 않는 조작을 어떻게 메울 것인가.
  • Linux user transient scope와 lingering이 logind session cgroup, KillUserProcesses, 로그아웃에서 의도대로 동작하는가.
  • macOS에서 데몬 아래 claude의 파일 접근 권한(TCC)은 어느 앱에 귀속되는가.
  • Windows를 범위 밖으로 둘 것인가.

이 목록은 설계 §9를 따른다. Claude Code가 업데이트되면 관련 측정을 다시 한다. 다음 검증은 -p의 정리 문과 마감이다. 구현을 결정하면 재입양·입력 중복 방지·ledger·정리 경쟁을 포함한 실행 명세를 쓴다.

9용어

엔진
Claude Code 프로세스 자체. TUI든 headless든 같은 엔진이다.
TUI / headless
터미널에 화면을 그리는 interactive 모양과, -p stream-json으로 JSON 줄만 주고받는 모양.
Query
Agent SDK의 제어 객체다. 경로 B에서는 기계의 MAWS 데몬에 두고, host가 쥔 claude -p와 통신한다.
control_request
SDK와 RC가 공유하는 제어 봉투. host(또는 client)가 엔진에, 엔진이 host에 보낸다.
mod
세션 안에서 도는 플러그인 코드다. bridge mod는 경로 A에서 제어를 맡는다. 경로 B에서는 관찰과 정리 문을 맡도록 설계한다.
plane
sminos 데몬의 세션 구독 계층. 처음에 snapshot, 그다음 live 이벤트를 준다.
hub / DO
desk-hub. Cloudflare Durable Object로 만든 중계. 배포마다 재시작하므로 정확성을 기대지 않는다.
소유자
세션 프로세스의 부모이자 PTY master 또는 stdio pipe를 쥔 쪽. 소유자가 죽으면 세션이 죽는다.
경로 A / B
A는 터미널·--bg 세션이다. B는 MAWS 앱이나 웹에서 연 -p 세션이다. A는 bridge mod가, B는 MAWS 데몬의 Query가 제어한다.
session host / holder manager
경로 B의 세션마다 pipe를 쥔 작은 소유자와, 사용자당 하나인 교체 가능한 관리자다. MAWS engine host의 일부로 설계한다.
ring / checkpoint
ring은 seq가 붙은 최근 출력을 보관한다. Query의 checkpoint는 어디까지 읽었는지를 나타내는 영속 기록이다. ring이 남아 있어도 checkpoint를 대신하지 못한다.
writer fence / reap fence
writer fence는 옛 Query의 늦은 쓰기를 거절하는 장치다. reap fence는 세션 정리와 새 턴 시작의 경쟁을 막는 장치다.
request ledger
MAWS 소유 도구의 효과를 실행하기 전에 남기는 영속 요청 원장이다. 재시작 뒤 결과를 모르는 호출이 자동으로 중복 실행되지 않게 한다.
capability 목록
세션의 명령마다 gui | none을 알리는 목록이다. 웹은 이 목록으로 가능한 조작을 그린다.
epoch
세대 번호. RC의 worker_epoch, holder의 processEpoch처럼 "같은 이름의 다른 실체"를 가른다.
