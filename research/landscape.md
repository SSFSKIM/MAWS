# MAWS external landscape

Research date: 2026-09-28. Sources were accessed during this research. Vendor documentation establishes documented availability, not independently tested quality. GitHub issues establish observed behavior, not necessarily a released fix. Undated live pages can change; version-lock dependencies and capture screenshots during implementation evaluation.

## Executive summary

**Build MAWS as an attention-and-review workstation, not just another chat wrapper.** The strongest inspirations are Warp’s navigable parent/child activity, cmux’s persistent pane-level attention, Kilo’s session/worktree distinction, Antigravity’s reviewable artifacts, and Sculptor’s deliberate human takeover. Sources appear with the detailed findings below.

**Ghostty in Electron is realistic now.** `ghostty-web` runs Ghostty’s terminal core as WASM, and an actual Electron application, Coder’s Mux/Xum, declares it as a dependency. Native `libghostty-vt` has C/Zig APIs and Node bindings, but those bindings are not a GUI renderer. For MAWS’s explicit Ghostty preference, prototype `ghostty-web` behind a terminal adapter; retain xterm.js/WebGL as the lower-risk fallback if compatibility testing fails.

**Recommended UI stack:** Streamdown with opt-in KaTeX/Mermaid/Shiki plugins; TanStack Virtual’s now-documented chat anchoring; `@git-diff-view/react` for review; CodeMirror 6 for file tabs; Tiptap for the composer. Use official `@shikijs/stream` rather than the retired `shiki-stream` package when custom incremental highlighting is necessary.

**Recommended Electron approach:** a sandboxed React 19 renderer, narrow typed IPC, privileged agent/PTY helpers outside the renderer, and a separate WebContentsView for shared browsing. Electron-vite plus electron-builder/electron-updater is a coherent default; Forge remains reasonable, but its Vite plugin is still documented as experimental. Sign and notarize builds distributed to other Macs.

**Important landscape corrections:** Crystal is deprecated in favor of Nimbalyst; Vibe Kanban is sunsetting commercially; Terragon’s site says shutdown. Neither browser previews, worktrees, artifacts, subagents nor scheduled work can honestly be called missing from both benchmarks in September 2026. The ten proposed differentiators below are specific interaction patterns, not certified feature absences.

## Part A — Agent-workspace GUIs

### How to read the comparison

The observations below focus on documented distinctive UX across sessions/worktrees, subagents, transcript treatment, review, approvals, terminals, browsers, attention, and layout. **A capability not mentioned is unverified, not absent.** In particular, do not infer granular apply/revert semantics or a visible subagent graph merely because a product says “multi-agent.”

### Established and emerging products

**T3 Code — active, broad control surface, explicitly early.** Its README documents Electron/web/mobile surfaces and six providers: Claude Code, Codex, Cursor, Grok Build, OpenCode and Antigravity. It explicitly warns “We are very very early… Expect bugs.” Do not repeat older claims that it is Codex-only. Its docs include permissions, project settings, source control, multiple accounts and remote access. Transcript issues establish expandable tool groups and a distinction between standalone calls and grouped activity; newer PRs describe independently collapsed reasoning and keeping failed calls visible within an activity group, but a PR is not release evidence. A reported bug distinguishes local Bash tasks from subagents in the Agents panel—useful evidence that task execution and child agents should not share an indiscriminate icon. **Borrow:** semantically summarized activity groups with errors visible while collapsed; independent expansion state. Sources: [README](https://github.com/pingdotgg/t3code), [tool-group interaction issue](https://github.com/pingdotgg/t3code/issues/11009), [reasoning-collapse PR](https://github.com/pingdotgg/t3code/pull/12302), [failure-grouping PR](https://github.com/pingdotgg/t3code/pull/12270), [Bash/subagent misclassification](https://github.com/pingdotgg/t3code/issues/10375).

**Conductor — worktree-first orchestration and review loop.** Its workflow joins running-app checks, manual diff review, agent review, inline comments sent back as composer attachments, and a Checks tab for Git/CI/deployments/comments/todos. Checkpoints are stored in private Git refs, separately from the working branch’s history; reverting rewinds both later code and conversation, with destructive consequences clearly documented. Spotlight testing projects a selected workspace into the root checkout for an existing dev server. Changelog search results document consecutive MCP calls grouped by server name/logo, with errors directly on tool rows; the source page itself returned 404 when fetched, so treat that particular detail as search-index evidence pending live confirmation. **Borrow:** comments as first-class feedback attachments; make “restore files” versus “rewind conversation” semantics explicit. Sources: [workflow](https://docs.conductor.build/workflow), [checkpoints](https://docs.conductor.build/core/checkpoints), [spotlight](https://docs.conductor.build/guides/spotlight-testing), [indexed Allegro release](https://www.conductor.build/changelog/0.49.0-conductor-allegro), [approval release](https://www.conductor.build/changelog/0.41.0-tool-approval-codex-plan-mode-beta).

**Zed Agent Panel — multi-buffer review and cross-project threads.** Threads Sidebar groups concurrent threads by project; a title-bar picker isolates a thread in a worktree. Review Changes opens a multi-buffer tab with per-hunk or whole-change acceptance/rejection; optional single-file review embeds the controls in ordinary editors. Checkpoints appear above the user message, including after interrupted edits. Queued messages can be steered into the built-in agent at the next step. External-agent capabilities differ: checkpoints/history restoration/token display may not be available. The docs show live tool indicators but do not establish sophisticated tool-call grouping. **Borrow:** one review surface spanning multiple files, with jump-back to the transcript that caused a change. [Agent Panel](https://zed.dev/docs/ai/agent-panel).

**Cursor — promote active work into isolation and compare candidates.** Agents Window can start or move an in-progress agent into a worktree. `/worktree`, `/apply-worktree`, and `/delete-worktree` expose the lifecycle; `/best-of-n` creates isolated candidates but does not merge the winner automatically. `.cursor/worktrees.json` supplies setup commands with visible setup output. Worktree cleanup is a real lifecycle concern: docs describe automatic pruning under a machine-wide cap. Cloud-agent/browser claims should be taken from current Cursor docs rather than older “background agents” reviews. **Borrow:** “continue this session in a worktree” rather than forcing isolation decisions before a task is understood; explicit comparison before applying a winner. [Worktrees](https://cursor.com/docs/configuration/worktrees), [Agents Window community release discussion](https://forum.cursor.com/t/worktrees-in-agents-window/158956).

**Warp — best documented subagent attention model in this sample.** Parent and children are independent conversations. A pill bar displays the parent and named children with live state, and clicking switches to the corresponding transcript. Cloud run views group children under a parent and expose a Sub-agents tab. Parent/child communication has explicit lifecycle states including BLOCKED. Notifications are deliberately parent-only, avoiding child-event storms; child state remains visible in the pill bar and parent transcript. General notifications distinguish complete/request/error, and the management panel retains unread attention. **Borrow:** navigable topology plus aggregation, not a decorative graph or a toast per event. Caveat: MAWS must still make blocked children actionable, rather than inheriting notification suppression blindly. [Orchestration](https://docs.warp.dev/platform/orchestration/), [notifications](https://docs.warp.dev/agents/capabilities/agent-notifications/), [agent management](https://docs.warp.dev/agents/using-agents/managing-agents).

**Amp — threads that travel across surfaces.** June 2026’s Agents Everywhere describes a sidebar for watching and driving agents across web/mobile/CLI; the current site describes a macOS runner. Amp’s manual describes subagents as isolated contexts whose parent receives final summaries, not necessarily step-by-step interactive child supervision. Code review has been decoupled from its UI and can run through `amp review` or a thread request. **Borrow:** portable session identity and review as a reusable operation, while distinguishing that from a shipped interactive subagent topology. [Agents Everywhere](https://ampcode.com/news/agents-everywhere), [manual](https://ampcode.com/manual), [review](https://ampcode.com/news/liberating-code-review), [current site](https://ampcode.com/).

**OpenCode desktop/TUI — persistent task surfaces and inspectable children.** TUI docs cover session switching, undo/redo-style snapshots, and attention for questions/permissions/errors/completion; desktop notifications are focus-aware. Permissions support allow/ask/deny with session-scoped “always” approval. Desktop release notes describe reopened/background tabs, review-pane improvements, and keeping terminals mounted while switching sessions. A Desktop v2 issue establishes that clicking a subagent card navigates to the child session, while middle-click/new-tab behavior was broken; another reports child-tab restoration problems after restarting the TUI. These are next/v2-channel observations, not a guarantee of stable-channel behavior. **Borrow:** retain terminal state while switching conversations and support parent-preserving child navigation. [TUI](https://opencode.ai/docs/tui/), [permissions](https://opencode.ai/docs/permissions/), [desktop release](https://github.com/anomalyco/opencode/releases/tag/v1.17.14), [child-tab issue](https://github.com/anomalyco/opencode/issues/38949), [TUI restoration issue](https://github.com/anomalyco/opencode/issues/38948).

**Kilo Code — unusually explicit separation of workspace, session and subagent.** Agent Manager is a full editor tab with isolated worktrees or shared Local sessions; multiple transcripts can share one worktree. Multi-Version Mode produces up to four candidate implementations. Task subagents are children, not independent Agent Manager workspaces; the docs explicitly distinguish them. Review supports Branch/Staged/Unstaged/Session scopes, unified/split views, inline feedback, Apply to local, and PR readiness/checks. Each session gets a correctly rooted terminal. Existing branches, external worktrees and PR URLs can be imported; “Continue in Worktree” promotes a sidebar chat. **Borrow:** the data model and the import/promotion paths, not merely the visual layout. [Agent Manager](https://kilo.ai/docs/automate/agent-manager), [snapshots](https://kilo.ai/docs/code-with-ai/features/checkpoints).

**Cline — granular consent and reversible work.** The IDE flow surfaces proposed edits with Approve/Reject and editable diffs. Checkpoints are a major part of its recovery story; repository documentation/changelog describes browser automation, terminal execution and configurable auto-approval. Search-indexed checkpoint material distinguishes restore-files, restore-task and restore-both. Treat these as separate user intents in MAWS; do not promise rollback of arbitrary shell side effects. **Borrow:** clear local consent with actionable diffs, plus unobtrusive checkpoint affordances rather than giant repetitive transcript blocks. [IDE documentation](https://docs.cline.bot/usage/ide), [repository](https://github.com/cline/cline), [changelog](https://github.com/cline/cline/blob/main/CHANGELOG.md).

**Google Antigravity — artifacts as the supervisory interface.** Its current Artifacts docs describe Antigravity 2.0’s sidebar/review pane for implementation plans, code diffs, diagrams, images and browser recordings. The agent can pause at configurable milestones; inline feedback on a plan can redirect work before local files change. The introductory post describes an Agent Manager inbox for concurrent work. **Borrow:** a deliverables tray with review state and origin-session links, not a miscellaneous “files sent” bucket. [Artifacts](https://antigravity.google/docs/artifacts/), [agent overview](https://antigravity.google/docs/agent/), [launch post](https://antigravity.google/blog/introducing-google-antigravity).

**Devin — explicit human takeover of the same environment.** Its session tools expose shell-command history with output previews and command-based time navigation. The interactive Browser/Computer view lets a human solve MFA/CAPTCHAs or test an app. Its IDE terminals can switch from read-only to writable; docs recommend pausing Devin before taking over and telling it what changed when resumed. This is not evidence of a complete frame-by-frame terminal video replay. **Borrow:** visible “agent driving / you driving” ownership and intentional handback. [Session tools](https://docs.devin.ai/work-with-devin/devin-session-tools).

**Factory Droid — artifacts and code review share a feedback model.** The July 7, 2026 desktop release documents documents/slides/spreadsheets/PDF previews, a live browser beside the originating session, and file-by-file diffs. Design mode attaches feedback to selected elements; code feedback attaches to diff lines. Sidebar filtering/grouping organizes sessions. The announcement says these features are available on macOS and Windows across plans. **Borrow:** one consistent “comment on the actual output” interaction across code, browser and artifacts. [Desktop release](https://factory.com/news/working-with-droid-in-the-desktop-app), [app overview](https://docs.factory.ai/factory-app/overview).

**Windsurf/Cascade — code-aware side chat and previews.** Current documentation is branded Devin Desktop in places; do not assume product naming is unchanged. Cascade supports code/chat workflows, editor/terminal selection as context, checkpoints, terminal tools and multiple conversations. Documentation warns that concurrent Cascades editing the same files can race and recommends worktrees. Browser Preview documentation shows local app interaction inside the environment. **Borrow:** context follows an explicit selection; the user need not rebuild file/line references manually. [Cascade](https://docs.windsurf.com/windsurf/cascade/cascade), [browser previews](https://university.windsurf.build/cascade-tools/browser-previews).

**Claude Code VS Code extension — closest engine-aligned reference.** Native UI supports editable plan review, inline/side-by-side diffs, file/line mentions and conversations in separate tabs/windows. Current docs distinguish fork-conversation, rewind-code, and fork-plus-rewind. Status dots distinguish pending permission from completion while hidden. These details are more useful than assuming all CLI capabilities automatically exist in every GUI. **Borrow:** explicit conversation/code history controls and focus-sensitive attention, while retaining engine permission semantics. [Official extension docs](https://code.claude.com/docs/en/vs-code).

### Parallel-agent newcomers and project status

**Crystal → Nimbalyst.** Crystal’s repository says deprecated in February 2026 and points to Nimbalyst. Its current README describes the successor’s worktree isolation and live multi-editor surfaces: Monaco code, Markdown, spreadsheets, Excalidraw diagrams and mockups. Do not cite this current page as proof of Crystal’s old diff/timeline UI. **Borrow:** artifacts can be editable working documents rather than read-only attachments. [Crystal status and successor](https://github.com/stravu/crystal).

**Vibe Kanban.** The site says the commercial product is sunsetting and continues as community-maintained open source. It advertises task boards, worktree/setup automation, PR-to-worktree creation, inline diff comments and browser click-to-edit. Team/cloud feature descriptions on a sunset landing page are not reliable proof those services remain operational. **Borrow:** task-stage organization that differs from a chat-history list. [Official site/status](https://www.vibekanban.com/).

**Superset.** Current site shows host-grouped workspaces, worktree branches, working/review/ready states, terminal tabs, diff scopes such as Against Main and Unstaged, PR review and scheduled automations. It exposes file-tree/open-in workflows. An embedded browser was not established by the homepage; a Preview button is not sufficient evidence. **Borrow:** workspace status and Git divergence visible before opening a conversation. [Official site](https://superset.sh/).

**Sculptor.** Imbue’s current page says rebuilt and out of research preview for Apple Silicon Mac/Linux. Agents work in containers. Pairing Mode brings an agent’s changes into the local repo with bidirectional edits for human testing; merge tooling flags likely conflicts. Agent forking, custom MCP and Dockerfile configuration were listed as roadmap items on the fetched page, not shipped features. **Borrow:** explicit testing/takeover mode; recognize container isolation is different from worktree isolation. [Official product page](https://imbue.com/sculptor/).

**Terragon.** Its live site returned the heading “Terragon Shutdown” and no useful current feature documentation. Treat it as historical, not an active product to benchmark. [Official site](https://www.terragonlabs.com/).

**Emdash.** Tasks bundle branch, terminal, conversation and review state, with default worktree isolation. The article documents ACP chat, queued prompts, conversation export, stage/discard/commit/push/PR actions, task browser tabs with persistent profiles, issue-linked tasks, scheduling, and SSH/tmux-backed remote work. Notification details were not documented in this source. **Borrow:** a task is a workspace aggregate, not synonymous with a single chat tab. [Official product explanation](https://emdash.com/blog/what-is-emdash).

**cmux — add this to the shortlist.** Native Swift/AppKit, not Electron, and uses libghostty for rendering. Vertical/horizontal tabs show branch, PR status, cwd, ports and latest notification. Pane notification rings and a persistent unread panel support direct keyboard jumping. Browser panes have an automation API; session restore includes layout, scrollback and browser history. **Borrow:** exact-pane attention and a shared browser/terminal workspace. Its native implementation does not prove a turnkey native Ghostty view exists for Electron. [Repository](https://github.com/manaflow-ai/cmux), [HN launch discussion](https://news.ycombinator.com/item?id=47079718).

**Coder Mux/Xum — relevant to both UX and terminal feasibility.** Current repository describes isolated local/worktree/SSH workspaces, divergence UI, agent-status sidebar, integrated review, Costs tab, compaction controls and rich Markdown. The README now uses Xum after a rename; the `coder/mux` URL remains useful. Its package manifest directly declares Electron, ghostty-web and a node-pty package. **Borrow:** session resource/context visibility, especially across parallel work. [Repository](https://github.com/coder/mux), [dependency manifest](https://raw.githubusercontent.com/coder/mux/main/package.json).

### Ten UX ideas worth considering — novelty qualification

The literal request for ten things “neither Claude Desktop nor Codex ships” cannot responsibly be certified from public documentation. Both benchmarks have evolved: Claude Desktop documents sessions/worktrees, browser previews and diff feedback; Codex documentation now covers browsers, artifacts, subagents, notifications, scheduled work and record/replay. The Codex features URL redirects to a shared ChatGPT Learn surface. Consequently, **these are specific candidate differentiators whose exact absence remains unverified**, not claims of exclusive invention. Benchmark sources: [Claude Desktop](https://code.claude.com/docs/en/desktop), [Codex features](https://developers.openai.com/codex/app/features), [redirected features](https://learn.chatgpt.com/docs/features).

1. **An attention inbox that deep-links to the precise blocked pane or child**, with persistent unread state rather than transient completion toasts. [cmux](https://github.com/manaflow-ai/cmux).
2. **A navigable parent/child strip with live blocked/failed/completed states and aggregated notifications**, preserving the parent position when inspecting a child. [Warp](https://docs.warp.dev/platform/orchestration/).
3. **Separate workspace, session and subagent identities**, allowing multiple chats in one worktree without pretending they are separate isolated jobs. [Kilo](https://kilo.ai/docs/automate/agent-manager).
4. **Promote ongoing work into a new isolated checkout**, with visible setup and context continuity rather than restarting the conversation. [Cursor](https://cursor.com/docs/configuration/worktrees).
5. **A deliberate “pair with this agent” mode**, synchronizing a selected candidate into the human’s test environment and making takeover ownership visible. [Sculptor](https://imbue.com/sculptor/).
6. **A reusable task board over sessions**, where investigation, implementation, review and handoff are work states, not merely chat timestamps. [Vibe Kanban](https://www.vibekanban.com/).
7. **One annotation system across plans, code, browser elements and generated files**, retaining the referenced location when feedback is sent. [Factory](https://factory.com/news/working-with-droid-in-the-desktop-app).
8. **Semantic tool-call groups with independently expandable reasoning and prominently preserved failures.** Prototype the interaction; the T3 changes cited are PR evidence, not proven stable release behavior. [T3 grouping](https://github.com/pingdotgg/t3code/pull/12270), [reasoning](https://github.com/pingdotgg/t3code/pull/12302).
9. **Compare isolated candidate implementations before selecting one**, without silently applying a winner or hiding branch provenance. [Kilo Multi-Version](https://kilo.ai/docs/automate/agent-manager), [Cursor best-of-n](https://cursor.com/docs/configuration/worktrees).
10. **Context/cost inspection beside a cross-workspace divergence view**, so supervising many agents includes resource and integration awareness, not just more tabs. [Mux/Xum](https://github.com/coder/mux).

These are proposed MAWS combinations and interactions, not a recommendation to ship all ten immediately. The strongest first-wave combination is attention routing + topology + review-linked outputs.

## Part B — A Ghostty-based terminal in Electron

### 1. Native libghostty / libghostty-vt

The September 2025 announcement said the C API was not ready; that is now stale. Ghostty’s current README says `libghostty-vt` is usable from C and Zig on macOS/Linux/Windows/WASM. It is not yet version-tagged and API signatures remain in flux. The VT library handles terminal parsing/state; it is not interchangeable with a native embedded rendered terminal view. Sources: [2025 announcement](https://mitchellh.com/writing/libghostty-is-coming), [current upstream README](https://github.com/ghostty-org/ghostty), [C header](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty/vt.h).

Node bindings exist: `coder/libghostty-vt-node` uses ABI-stable Node-API and exposes feed/resize/snapshot/visible text/debug formatting. Its README explicitly says it is **not a screenshot, browser or GUI renderer**. It pins an upstream Ghostty commit; initial prebuilds cover Linux x64/arm64 and macOS arm64, with initial Windows support absent. Electron compatibility was not documented by this binding README. Native ABI stability does not make the upstream C API stable. [Node binding](https://github.com/coder/libghostty-vt-node).

cmux demonstrates full native Ghostty rendering in Swift/AppKit, but that is a different integration path from Electron. A native view bridge would mean owning native composition, focus/input/accessibility and cross-platform packaging; that is an engineering implication, not a shipped Electron capability claim. [cmux](https://github.com/manaflow-ai/cmux).

### 2. ghostty-web

**Canonical repository:** [coder/ghostty-web](https://github.com/coder/ghostty-web). It uses Ghostty’s WASM-compiled terminal core, rather than merely copying Ghostty’s visual theme. The README documents roughly 400 KB of WASM and no runtime dependencies, and claims improved grapheme/escape-sequence support. These are maintainer claims, not independent benchmarks.

API example from the README: `await init()`, `new Terminal(options)`, `terminal.open(element)`, `terminal.onData(...)`, `terminal.write(...)`. It **aims** at xterm.js API compatibility; the required initialization already makes “change only the import” incomplete advice. No full addon/feature parity matrix or reproducible numeric performance advantage was established by the fetched README. It builds a patched/pinned Ghostty source and intends eventually to consume an official WASM distribution. [Repository and API](https://github.com/coder/ghostty-web).

There is direct Electron deployment evidence, not just theoretical browser compatibility: Mux/Xum’s manifest currently declares `electron: ^40.9.3`, `ghostty-web: ^0.4.0-next.7.g03ead6e`, and `@lydell/node-pty: 1.1.0`. The prerelease dependency is a useful maturity warning; it is not proof that every terminal edge case works. [Manifest](https://raw.githubusercontent.com/coder/mux/main/package.json).

### 3. xterm.js + WebGL + node-pty

xterm.js’s WebGL addon provides a WebGL2 renderer loaded after opening the terminal. Its documented context-loss callback matters for GPU resets/suspend. node-pty supplies the PTY; it is not part of either browser terminal renderer. It runs subprocesses at the parent’s privileges and is not thread-safe across worker threads. [WebGL addon](https://github.com/xtermjs/xterm.js/tree/master/addons/addon-webgl), [node-pty](https://github.com/microsoft/node-pty).

**Verification limit:** the assertion that both benchmark desktop apps use exactly xterm.js/WebGL/node-pty was supplied in the research brief, not independently established here from first-party public source. Do not present their internal implementation as a verified public fact.

### Recommendation

**For MAWS’s explicit Ghostty preference, prototype and, if it passes, ship ghostty-web behind a small terminal-renderer adapter.** This is justified by real Electron usage, not a plan to invent native embedding. Keep PTY lifecycle/input/output separate from the renderer. Acceptance tests should cover Claude/Codex TUIs, alternate screen, synchronized output, Unicode/emoji/CJK/RTL, IME, selection/copy/paste, hyperlinks, search, scrollback, resize/reflow, sustained output, keyboard shortcuts, accessibility and sleep/resume. This is a proposed validation plan, not an assertion those features are all complete. [ghostty-web](https://github.com/coder/ghostty-web), [actual Electron dependency](https://raw.githubusercontent.com/coder/mux/main/package.json).

**Choose xterm.js/WebGL instead if delivery certainty, accessibility or established addon behavior wins over Ghostty-core fidelity, or if that validation fails.** Choose native libghostty only if MAWS deliberately adopts a native terminal host and accepts its integration burden. Native Node bindings alone do not solve rendering. [xterm addons](https://xtermjs.org/docs/guides/using-addons/), [native binding limits](https://github.com/coder/libghostty-vt-node).

### Important corrections and implementation implications

- **`shiki-stream` has moved.** The old repository is archived; from `shiki-stream@4.2.0` it re-exports `@shikijs/stream`, and its README directs new code to the official package. That package can emit stable line-ish tokens or finer tokens with recall instructions; its React renderer handles recalls. Do not implement a naive append-only consumer if recall is enabled. [Old package status](https://github.com/antfu/shiki-stream), [official API](https://shiki.style/packages/stream).
- **TanStack’s old “you must build all chat anchoring yourself” comparison is stale.** Current APIs include `anchorTo:'end'`, `followOnAppend`, `scrollEndThreshold`, `scrollToEnd()` and `isAtEnd()`. Stable IDs and normal DOM ordering are required; scrolling upward must not be overridden by a streaming message. [Chat guide](https://tanstack.com/virtual/latest/docs/chat).
- **Do not promise built-in virtualization for `@git-diff-view/react`.** The fetched README confirmed template mode, workers, ranges and widgets, but did not establish a virtualized React list. Virtualize the file/hunk surface as necessary and benchmark realistic diffs. [Repository](https://github.com/MrWangJustToDo/git-diff-view).
- **Diff components do not own repository mutation.** Proposed MAWS design: apply/revert/stage actions go through a privileged Git service with base/content checks; the renderer displays and requests actions. A visual accept button is not a safe patch engine. This distinction follows the libraries’ documented rendering/widget scope and Electron’s IPC boundary. [Diff library](https://github.com/MrWangJustToDo/git-diff-view), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security).
- **Markdown is untrusted.** react-markdown avoids raw HTML by default and recommends `rehype-sanitize` when plugins warrant it. Marked explicitly does not sanitize its HTML output, and its homepage does not document an incremental streaming parser contract. Lazy rendering is a performance choice, not a security boundary. [react-markdown](https://github.com/remarkjs/react-markdown), [marked](https://marked.js.org/).
- Proposed MAWS transcript implementation: immutable completed message blocks, a separately updated active block, batched token updates, lazy expensive diagrams, and stable IDs across collapse/expand. React Compiler does not replace these dataflow decisions or list virtualization. [Streamdown](https://github.com/vercel/streamdown), [TanStack chat](https://tanstack.com/virtual/latest/docs/chat), [React Compiler](https://react.dev/blog/2025/10/07/react-compiler-1).

## Part D — Electron architecture facts and recommendations

### Views and process boundaries

**Use WebContentsView for the shared browser, not an iframe with privileged preload access.** It is a main-process native View associated with a WebContents, attached with `contentView.addChildView()` and positioned with bounds. BrowserView is deprecated. It is not a DOM node: MAWS must coordinate bounds, overlays, focus and destruction explicitly. Keep ordinary transcript/file tabs in the main React renderer unless a separate WebContents boundary is actually needed. [WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view).

**Use utilityProcess for Node helpers that should not block/crash the UI process.** It supports `fork`, process lifecycle events, stdout/stderr pipes and transferable MessagePorts. It is not automatically a sandbox for arbitrary shell code. Leave `allowLoadingUnsignedLibraries` disabled unless a concrete signed-native-module requirement demands it. **Session durability caveat:** a utility process is not a guarantee that agents survive application exit; detached daemon/service ownership is a separate architecture decision. [utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process).

**PTY service:** keep node-pty out of the renderer, externalize/package its native addon for the target Electron build, and manage lifecycle, resize and backpressure centrally. node-pty explicitly warns it is not thread-safe and subprocesses inherit parent permissions. Worktrees do not alter those permissions. [node-pty](https://github.com/microsoft/node-pty), [Forge native-module guidance](https://www.electronforge.io/config/plugins/vite).

### Security and typed IPC

Set `contextIsolation:true`, `sandbox:true` and `nodeIntegration:false` explicitly on untrusted browser content. Expose narrow, intention-specific preload methods only to trusted MAWS UI. Deny unexpected permission requests/navigation/popups; validate IPC sender frames/origins and payloads. TypeScript types are not runtime validation or authorization. Browser content must not receive the shell/Git/agent bridge. Electron’s security guide specifically warns against generic raw IPC exposure and unvalidated `shell.openExternal`. [Security guide](https://www.electronjs.org/docs/latest/tutorial/security), [context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation).

**Recommendation:** a small shared command/event schema with runtime validation and typed wrappers. `@electron-toolkit/typed-ipc` is a relevant lightweight event-map option; `electron-trpc` provides inferred router/client types and is attractive if tRPC is already desired. Neither should be sold as a security layer or mandatory code generation. `electron-vite` is build tooling; `@electron-toolkit/preload` is not, by itself, a hardened domain API. [Toolkit](https://github.com/alex8088/electron-toolkit), [electron-trpc](https://electron-trpc.dev/), [electron-vite development/security note](https://electron-vite.org/guide/dev).

### Build and renderer stack

**Recommend electron-vite + electron-builder + electron-updater** as a coherent initial route. Electron-vite handles main/preload/renderer development; packaging/signing/updating remain separate responsibilities. **Forge + Vite** is a valid alternative when Forge’s makers/plugins are preferred, but the fetched official Vite page still explicitly labels its support experimental and permits breaking changes in minor releases. Avoid confusing `electron-vite` with the separate `vite-plugin-electron` project. [electron-vite](https://electron-vite.org/), [Forge Vite](https://www.electronforge.io/config/plugins/vite), [builder](https://github.com/electron-userland/electron-builder).

**React 19 + React Compiler is reasonable for a new renderer.** Compiler 1.0 became stable October 7, 2025; adopt its linting and profile the transcript/editor integrations. **Tailwind v4** is also a reasonable default, with CSS-first configuration and a first-party Vite plugin. These are implementation choices, not explanations for performance problems caused by reparsing huge transcripts every token. [Compiler announcement](https://react.dev/blog/2025/10/07/react-compiler-1), [Tailwind v4](https://tailwindcss.com/blog/tailwindcss-v4).

### Updating and internal macOS builds

**Prefer electron-updater for an Electron app.** Its current docs require signing for macOS auto-update and a ZIP artifact for Squirrel.Mac; default macOS targets include DMG plus ZIP, with `latest-mac.yml` metadata. Use a controlled HTTPS release feed; do not put broad private-repository credentials into the application. Sparkle is a credible native-macOS choice—cmux uses it—but adopting it in Electron means an additional native integration rather than the usual JavaScript updater path. [electron-updater](https://www.electron.build/docs/features/auto-update/), [Electron updates](https://www.electronjs.org/docs/latest/tutorial/updates), [cmux](https://github.com/manaflow-ai/cmux).

For a build used only on the developer’s own machine, signing/notarization is not a prerequisite to ordinary Electron development. For internal distribution to other Macs without Gatekeeper workarounds, use **Developer ID Application signing, hardened runtime with necessary entitlements, notarization and stapling** through the packaging toolchain. Sign bundled native code/helpers appropriately and test the packaged build on a clean machine. macOS updater signing requirements remain even when distribution is internal. Secrets belong in environment/keychain/CI facilities, not the repo. [Electron signing](https://www.electronjs.org/docs/latest/tutorial/code-signing), [Forge macOS signing/notarization](https://www.electronforge.io/guides/code-signing/code-signing-macos), [updater requirement](https://www.electron.build/docs/features/auto-update/).

Proposed MAWS policy: download updates in the background, but make restart coordination explicit while agents or terminal jobs are active. This is a product recommendation, not a guarantee from the updater library.

### Can Playwright drive the exact browser the user sees?

**Yes, with important limits.** A WebContentsView is Chromium content. Electron can expose CDP using `--remote-debugging-port`, and Playwright can attach with `chromium.connectOverCDP(httpOrWebSocketEndpoint)`. Select the intended browser-panel target rather than assuming the first page is correct. The user and agent then interact with the same live page/session. Playwright documents CDP attachment as Chromium-only and lower-fidelity than its own protocol. [Playwright CDP](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp), [Electron-target tooling example](https://github.com/svvysh/electron-agent-tools).

**`webContents.debugger` is a CDP transport, not a drop-in Playwright endpoint.** Electron exposes attach/sendCommand/events in process. Playwright’s documented connectOverCDP API accepts an HTTP/WebSocket endpoint, not Electron’s debugger object. To combine them requires a custom protocol bridge; alternatively implement the bounded browser tools directly on debugger CDP commands. DevTools attachment can detach that debugger client. [Electron Debugger API](https://www.electronjs.org/docs/latest/api/debugger), [Playwright API](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp).

**Do not expose a broad debug endpoint casually.** A debug port can expose privileged application targets, not just the intended browser pane. A custom partition isolates browser storage but is not an authorization boundary for CDP access; an open Playwright issue also documents imperfect mapping of Electron partitions into Playwright BrowserContexts. Recommendation: prototype on an opt-in loopback-only endpoint, verify exact target/partition behavior, then choose either tightly controlled Playwright attachment or a narrow in-process browser-tool service. Provide an explicit pause/takeover control so human and agent do not type/click concurrently. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security), [partition/context limitation](https://github.com/microsoft/playwright/issues/34815), [Devin takeover precedent](https://docs.devin.ai/work-with-devin/devin-session-tools).

## Recommended next step

Build three bounded feasibility spikes before locking the architecture: **(1)** ghostty-web plus the chosen PTY service under realistic coding-agent workloads; **(2)** WebContentsView shared browsing with target-restricted automation and human takeover; **(3)** a long streaming transcript with nested child activity, Markdown/code/diagrams and stable scroll anchoring. These resolve the highest-cost empirical uncertainties while leaving product layout decisions reviewable. They are proposed next work, not work performed in this research.

Research limitations: no product was installed or interactively tested; performance claims are not independent measurements; the exact benchmark terminal internals and ten absolute feature absences were not verified. All implementation recommendations should be checked against pinned package versions before adoption.
