(1) HUMAN AGAINST SYNTHESISED INPUT
======================================================================================================================
Scenario (pass2/main.mjs inputScenario and, after the review, input2Scenario; results/pass2/input.json, input2.json).
Run one: the view loads A's a.html (a button, a text field). The preload (view-preload.cjs, sandboxed) records every
pointer, mouse, click, key, beforeinput, input and wheel event with isTrusted, sourceCapabilities, pointerType, client
and screen coordinates, movement, pressure and timing, and reports each to main at once. Main records webContents
'input-event' (with the undocumented raw `_modifiers` integer) and 'before-input-event', and the bridge reports every
Input.* command's send and reply. Eleven phases: Playwright's locator.click, mouse.click, keyboard.press,
locator.fill, keyboard.type and mouse.wheel; a raw Input.dispatchMouseEvent triple from main on the same debugger
session; and the human stand-in through sendInputEvent (mouse without and with globalX/globalY, a key, a wheel). Run
two: embed.html on A with a cross-site iframe from B; main also records 'before-mouse-event'; agent and stand-in
clicks on the top page and inside the iframe, a stand-in key, the stand-in pressing while the agent's mousePressed is
in flight (at another pixel, then at the same pixel), and an agent click at zoom 1.25. All clocks are epoch
milliseconds from performance.timeOrigin + performance.now(); the renderer's and main's clocks differ by about 0.1
to 0.25 ms, in a direction that varied between runs, which is the size of the finest intervals below.

What the page sees: nothing. Every event from every source had isTrusted true, sourceCapabilities
{firesTouchEvents:false} on mouse and key events (null on pointer, input and wheel events), pointerType 'mouse',
buttons 1 and detail 1 on mousedown, pressure 0.5 on pointerdown for Playwright's clicks and the stand-in alike (a raw
Input.dispatchMouseEvent without a `force` parameter gives 0; Playwright's carry 0.5, so the agent's clicks do not
differ there either). screenX minus clientX was 805,78 for Playwright's clicks and for the raw CDP
triple: the view's screen origin (window 156,33 plus view 649,45). CDP input in this Chromium carries real screen
coordinates, so the old bot-detection tell (screenX equal to clientX) does not exist here. The naive sendInputEvent
without globalX/globalY gave screen 0,0 (minus 66,97): a stand-in artifact, fixed by passing the screen point, which
the probe does in its second mouse phase.

What main sees. 'input-event' fires for CDP-dispatched input exactly as for sendInputEvent: three events for a
three-command click (mouseMove, mouseDown, mouseUp), two per key press (keyDown, keyUp), five for a wheel (mouseWheel,
gestureScrollBegin, gestureScrollUpdate, mouseWheel, gestureScrollEnd). Input.insertText (Playwright's fill) produces
no input-event at all, only DOM beforeinput/input. The mouse InputEvent object has the keys type, clickCount,
movementX, movementY, button, globalX, globalY, x, y and no modifiers field of any kind; keyboard and wheel events
carry `modifiers` and the raw `_modifiers`. 'before-mouse-event' (Electron's WebContentsDelegate::PreHandleMouseEvent,
electron_api_web_contents.cc:1700-1704) fires for CDP and stand-in clicks alike (3 and 3) with the same nine keys and
no modifiers, so it is no signal either; what it adds is reach, below.
  The key signals: Chromium sets WebInputEvent::kFromDebugger = 1 << 23 ("Indication this event was injected by the
  devtools", third_party/blink/public/common/input/web_input_event.h at 152.0.7977.130, excerpt in
  results/pass2/web_input_event-modifiers-152.0.7977.130.txt; its comment says the flag is to be removed once
  callbacks can be bound, so it is a signal with a shelf life) on every event Input.dispatchKeyEvent and
  Input.dispatchMouseEvent inject. Observed: `_modifiers` 8388608 (bit 23) on all six CDP keyDown/keyUp events and on
  both mouseWheel events of the CDP wheel; 0 on sendInputEvent's rawKeyDown, char, keyUp and mouseWheel; 0 on the
  gestureScroll* events Chromium derives from either wheel (input.json rawModifierBitsSeen: candidate bit 23, 8
  synthesised events carrying modifiers against 5 stand-in ones). Mouse button events: unobservable, the field is
  absent. The second: 'before-input-event' fired for the stand-in's keyDown and keyUp (2 of 2, both runs) and for
  none of the six CDP key commands (Chromium's PreHandleKeyboardEvent path is the native one). A third, weaker: a CDP keyDown with text arrives as input-event type 'keyDown' (the combined synthetic
  type); native keys arrive as 'rawKeyDown' then 'char'.
  Reach into iframes (input2). Electron attaches its input-event observer to the primary main frame's widget only
  (electron_api_web_contents.cc:1072-1074 and 2198-2205), and CDP's InputHandler hands an event to the target widget
  directly: the agent's click on the button inside the cross-site iframe raised 0 input-events and 3
  before-mouse-events, the latter in the iframe's own coordinates (57.6,68.4 for a command at 83.6,181.9: the frame's
  offset), and incremented the frame's count. The stand-in cannot model a human click into an OOPIF: sendInputEvent
  hands the event to the root widget, so its click at the button's page coordinates raised 3 input-events and 3
  before-mouse-events and reached nothing (the frame's count did not move, the field stayed empty). A real click or
  key into an OOPIF is routed by the browser to the child widget, where no input-event observer exists but the
  WebContents delegate hooks still run; so before-mouse-event and before-input-event are the hooks that cover iframes,
  and input-event's `_modifiers` bit covers only the top frame. Not measured: OS-routed input into an OOPIF (no real
  input in this spike).
  The window. Input.dispatch* send-to-reply: median 0.85 ms, max 4.8 ms (n = 13); Playwright's locator.click as a
  whole 20.6 ms, mouse.click 1.7, keyboard.press 4.6, fill 5.5, type 3.9, wheel 1.4. Every CDP mouse and key
  input-event fell inside its own command's window with matching type and integer coordinates (click 3/3, 3/3;
  press 2/2; type 4/4). Order per press: command sent at 0; input-event +0.02 to +0.43 ms; the DOM event's timestamp
  within 0.25 ms of it (the two clocks' skew); the preload's report in main +0.3 to +0.9 ms; the command's reply +0.7
  to +4.5 ms. So both the input-event and the DOM report precede the reply, and a mouse event is attributable at the
  moment it arrives, not after the action ends. The stand-in's events in run one fell outside every window by
  construction (its phases issue no commands), so run two interleaved them, classified by the rule the verdict
  states (before-mouse-events, type and window only, each command consumed once; input2.json attributedEvents): with
  the stand-in pressing at another pixel while the agent's mousePressed was in flight, 6 events went to the agent and
  2 to the human, one human press; the stand-in's press, arriving first inside the window, took the agent's slot and
  the agent's own press was the one left unmatched (Playwright also re-issued its click once when the foreign press
  landed, and the count rose by one); with the stand-in pressing at the same pixel, the same shape (3 agent, 2 human,
  one human press, the count rose by two). Only the human-first order was exercised (the stand-in fires from the
  bridge's send hook, before the command reaches the debugger), and the windows carry a 0.05 ms tolerance. The raw
  CDP triple issued from main directly (bypassing the bridge hook) matched nothing, as expected: MAWS's own Input.*
  use must go through the same hook as the tools'. Coordinates cannot be part of the match: at zoom 1.25 the command
  carries CSS px (63.1,86.6) and the hooks carry widget px (78.9,108.2), and inside an iframe before-mouse-event
  carries the frame's own space; without them the zoom click and the iframe click attribute to the agent 3/3. Wheel: the CDP wheel's second mouseWheel arrived after the command's reply (0.1 ms after in this run), so
  the window does not cover wheels and only the bit does; the gestureScroll* events carry 0 for both and are not
  input.

Verdict: the takeover rule can rely on a signal for keys and wheels and must rely on the window for mouse buttons,
and the window to use is the command, not the action. Keys: a before-input-event is the human's (CDP keys never raise
it); an input-event with bit 23 in `_modifiers` is the agent's (top frame only). Wheels: the bit alone; gestureScroll*
ignored. Mouse: neither mouse hook exposes modifiers, so a before-mouse-event mouseDown/mouseUp is the agent's iff an
Input.dispatchMouseEvent of the matching type (mousePressed/mouseReleased) is in flight (sent, not replied) and not
yet consumed by an earlier event of that type; otherwise it is the human's. No coordinates in the match. The race is
nil in practice: with consumption, a human press inside an agent press's window leaves exactly one press unmatched
whichever arrives first, and the takeover fires; the assumption behind it is that every in-flight command yields
exactly one event of its type, so a command that errors or yields none can absorb one same-type human event, which
the TabDebugger closes by releasing a window when its reply is an error. The coarse "agent action in flight" window (21 ms for a click, longer
with actionability waits) is not a discriminator on its own because a human click during an agent action is exactly
the case the rule exists for; with per-command matching it needs no separate state. mouseMove is not a trigger
(humans move constantly; Playwright moves once per click). Nothing in the preload can attribute; its report serves
the cursor and hover UI, and the attribution lives in main beside the TabDebugger that owns the outstanding-command
table and sees MAWS's own Input.* commands through the same hook. If kFromDebugger goes (its TODO), keys keep
before-input-event, and wheels become a window match with a tolerance past the reply or stop being a trigger.
[parent-impact] E4's ledger names "the preload's input report" as the control state's source. The report cannot tell
the two apart; attribution is main's: before-mouse-event against the TabDebugger's in-flight Input commands (mouse),
before-input-event (keys) and the kFromDebugger bit on input-event (keys and wheels, top frame). A precision of §3 D's
takeover, not a contradiction. `_modifiers` is undocumented and the bit is slated for removal; E4c pins a unit test on
it against the Electron version and carries the fallbacks above.

(2) A WebContentsView LAYERED OVER A BrowserWindow RENDERER
======================================================================================================================
Scenario (layerScenario; results/pass2/layer.json; shots/). The shell page lays out a 44 px toolbar, a 240 px
sidebar, a chat pane and a browser pane split by a handle; shell.js reports the pane's rect with a ResizeObserver
(window resizes, layout changes) and, during a simulated drag, from inside each requestAnimationFrame callback before
the frame is presented (60 steps, split 0.42 to 0.20); main rounds the rect and calls view.setBounds on receipt.
A renderer-drawn sheet sends browser.view.cover; main calls setVisible(false) and later setVisible(true).

Geometry. With titleBarStyle hiddenInset the window's content bounds equal its bounds (1200x800), the shell's
innerWidth/innerHeight equal the content size, and getBoundingClientRect maps 1:1 onto setBounds coordinates (CSS px
are DIPs at zoom 1; DPR 2 is the backing scale only). The CSP header installed on the default session reached the
shell (its inline script was refused) and not the view's partition (its inline script ran), so the browser view keeps
page CSP intact. ResizeObserver rects are fractional (x 649.195, width 550.805; 20 of 24 resize reports); main rounds
them, which can leave a sub-pixel seam between the pane's edge and the view; E4a should size the pane on integer px.

Window resize (24 setSize steps of 20 by 12 px): the renderer's report reached main 3.2 ms median (p95 4.9, max 7.0)
after setSize, 2.1 ms of it in the renderer-to-main hop; main applied it 0.1 ms later; exactly one report per resize.
The window's own 'resize' event fires at 1 ms, so a layout the renderer owns costs about 2 ms more than one main
could compute itself; under one 8.3 ms frame of this display.
Split drag (60 rAF frames, 8.3 ms apart): report sent 0.1 to 0.4 ms into the callback; renderer-to-main 0.18 ms
median (max 0.23); bounds applied 0.47 ms median, 0.62 ms max after the callback began; 60 of 60 within one frame.
What reaches the screen was not measured (the series ends when setBounds returns in main, and the page was occluded
throughout, see below); by construction the shell's own frame is presented at least one compositor frame after its
rAF callback, so the view's new bounds should land at or before the shell's new pane edge, a mismatch bounded by one
UI-compositor frame with the view leading. A single layout change through the ResizeObserver route (no rAF report)
applied in 0.9 ms.
Screenshot series: per-layer capturePage at the checkpoints after resize, after drag and after the sheet is in shots/;
the initial view capture failed on all eight retries over 0.8 s ("Current display surface not available for
capture": no frame had been submitted yet, see the visibility finding) and the first success came after the resize
series. A composited capture of both layers needs Screen Recording; the status on this machine for the dev Electron
binary was 'granted', yet desktopCapturer.getSources returned empty thumbnails after 3.0 s each and the app then
never returned from app.exit (ScreenCaptureKit teardown); the path was removed and no prompt was raised. E4a's e2e
should not depend on composited capture; the timing series is the only alignment measure here.
Sheet: cover sent to setVisible(false) applied in 0.27 ms; view.getVisible false; the page kept its state; while
hidden, capturePage still works (5.2 ms, 1102x1510 at DPR 2) so a frozen placeholder can be taken before or after
hiding; restore 0.27 ms. While hidden, setInterval(1 ms) ran at 388 ms per tick.

The visibility observation, and the condition it was made under (pass2/visibility.mjs to visibility5.mjs;
results/pass2/visibility.json to visibility5.json). Throughout this pass the owner's screen was locked: the session
dictionary reads CGSSessionScreenIsLocked = 1 and the power log shows the display turned off and on in 30-second
bursts all morning (results/pass2/screen-lock-evidence.txt: off at 08:03:54, 08:04:29, ... 09:58:21, 10:03:04;
UserIsActive 0). Every window of the session was therefore occluded; consistent with it, isFocused stayed false in
every run and `app.focus({steal: true})` could not make a window key (visibility5 step F). (win.isVisible() returned
true throughout; NativeWindowMac::IsVisible in 44.4.5 reads `[window isVisible] && !(occlusionState ==
NSWindowOcclusionStateVisible)`, native_window_mac.mm:537-540, which taken literally would make that an "occluded"
reading, but the raw occlusion state was never read and the lock evidence stands on its own.) The review of the
first draft raised exactly this (the window was never in front) and it was right. What was observed under that
condition, and what it does and does not establish:
  Observed. The child view's page reports document.visibilityState 'hidden', gets no requestAnimationFrame callback
  and presents no frames (webContents.beginFrameSubscription counted 0 in 1.5 s while a 100 ms timer rewrote the
  page's text), from load onwards, in seven construction orders (visibility.json: BrowserWindow show:false then
  showInactive(), then show(), showInactive() before addChildView, backgroundThrottling:false at construction,
  BaseWindow show:true as pass one built it, BaseWindow showInactive, BrowserWindow show:true with the view added
  after ready-to-show), after every restore, with the window pinned at the floating level on every Space (visibility5
  A; still occluded by the lock), covered by a second window (B) and uncovered (C), and after setBounds, setVisible
  toggles, webContents.focus(), removeChildView + addChildView, win.focus(), win.blur(), a reload, a second window. In
  the same window and the same tests the window's own renderer is 'visible', gets rAF and presents 11 to 16 frames
  per second, whatever the window order. Timers in the child run at hidden-page rates (setInterval(1 ms) at 106 to
  388 ms per tick).
  What that establishes. Under occlusion, Chromium treats the child view's page as a hidden page, which is its normal
  behaviour for an occluded window, and the BrowserWindow's own page is exempt because Electron force-shows it:
  BrowserWindow::Show, ShowInactive and OnWindowShow call web_contents()->WasShown() unconditionally
  (electron_api_browser_window.cc:278-305; OnWindowHide calls WasOccluded, :287), and under the lock nothing hid it
  again (whether an occlusion change on an unlocked display would is not shown: the lock meant no occlusion change
  ever happened during visibility5's cover and uncover). The asymmetry between the two renderers is real and
  Electron's; the hidden state of the child is the display's.
  What it does not establish: how a child view behaves on an unlocked, uncovered display. It was not measurable in
  this pass (no run can unlock the owner's screen). The reference point outside the probe is not clean evidence
  either way: Claude Desktop 2.16120 (Electron 44.4.3) hosts its whole UI as a WebContentsView added with
  contentView.addChildView and uses no focus emulation, but it does toggle setBackgroundThrottling on that view
  (off during boot and while popouts, the glow, the computer-use lock or display capture are live; the review's
  reading of its readable source, main-process/index.chunk-kXuYPTnM.js:375837-375855), and visibility3 shows that
  toggle is itself an un-hide path that keeps rAF alive until the next navigation, which a single-page app rarely
  makes. Electron issues #54626 (a WebContentsView
  re-attached with removeChildView/addChildView stays hidden on Linux, 44.0.0 through 44.5.1, macOS 44.3.0 reported
  unaffected) and #44590 (a WebContentsView 'hidden' with innerWidth 0 when occluded, Apple Silicon) and PR #54311
  (setBackgroundThrottling leaving a page's visibility desynchronised) are the neighbours of this behaviour, none
  of them this case.
  What wakes an occluded child (visibility3, visibility4), should E4a ever need it. Playwright connected through the
  bridge: 'visible', rAF fires, 11 frames per second; disconnected: hidden again (so pass one, which attached
  Playwright before measuring anything, never saw the hidden state). Of Playwright's attach sequence replayed one
  command at a time on a bare webContents.debugger (the replay is cumulative and stopped at the first success), the
  command that does it is `Emulation.setFocusEmulationEnabled {enabled: true}`, after Page.enable, Runtime.enable,
  Page.setLifecycleEventsEnabled, Log.enable, Network.enable, Target.setAutoAttach,
  Page.addScriptToEvaluateOnNewDocument and Page.setInterceptFileChooserDialog had changed nothing; visibility4
  confirms it alone is enough and holds through a same-site navigation, a cross-site process swap (renderer 5 -> 6),
  a reload and the cover (under setVisible(false) the page stays 'visible' and keeps presenting 11 frames per second,
  with rAF paused); switching it off returns the page to 'hidden' at once, detaching the debugger too. Its costs:
  document.hasFocus() is true whatever the window's state (the window's own renderer reports false when the window is
  inactive), a covered or background view keeps painting, and an idle detach (E4c's "detaching after idle") would put
  the page back to sleep. webContents.setBackgroundThrottling(false) at run time (Electron's own un-hide,
  electron_api_web_contents.cc:2861-2881, ending in ShowWithVisibility(kHiddenButPainting)) makes rAF fire and
  frames flow with the page still 'hidden', and is lost on the next navigation; not a route.

Verdict, the cover protocol E4a needs. Placement: the renderer reports the pane's rect from inside the frame that
moves it (rAF during a drag, ResizeObserver otherwise) as `browser.view.place {x, y, width, height}` in CSS px of the
window's content area; main rounds to integers and calls setBounds at once; no interpolation, no throttling, no
main-side layout model is needed (sub-frame latency measured). Cover: the renderer sends `browser.view.cover {covered:
true}` before it paints a sheet, palette or dialog layer; main calls setVisible(false) (0.3 ms) and the renderer shows
a placeholder in the pane, ideally the capturePage image main hands it (5 ms) so the sheet's backdrop dims the page
rather than a blank; on close the renderer sends covered:false, main calls setVisible(true), and the renderer drops
the placeholder. A covered view is a hidden page (no rAF), so a browser_act that waits on actionability while a sheet
is open waits until the cover lifts; E4c says so in the tool's row ("waiting: a sheet covers the page") rather than
timing out. [parent-impact] First thing E4a does, before its design binds: run pass2/visibility2.mjs and visibility5.mjs with the
owner present (display on, screen unlocked, the window in front) and read the child's visibilityState, rAF and frame
count with nothing attached. If the child is 'visible' there, A-31's lazy attach stands and nothing below applies. If
it is hidden on an unlocked display too, the measured remedy is focus emulation on the tab's debugger session,
attached at tab creation, switched off for covered and background tabs and when the window hides or minimises (else
they keep painting), never detached on idle; and the Electron issue is filed with visibility2.mjs as the
reproduction. Either way the e2e cannot see this state (Playwright's own attach wakes the page): the check reads
document.visibilityState and a frame count from main with nothing attached, as visibility2.mjs does.

(3) CROSS-SITE NAVIGATION UNDER THE BRIDGE
======================================================================================================================
Scenario (crosssiteScenario; results/pass2/crosssite.json). Bridge and Playwright attached on A; six navigations
without reattaching: page.goto B (cross-site), goBack to A (cross-site), goto A:17337 (same host, other port: same
site), goto C (cross-site), webContents.loadURL back to A (the chrome's address bar, cross-site), page.reload. After
each: the renderer process id, Page.getFrameTree's main frame id, the debugger's attachment, Playwright's connection
and page.url(), evaluate, a click by locator, a snapshot and the Target button's ref.

Result (the second run, after the analysis fix). Renderer process ids 5 -> 6 -> 7 -> 7 -> 8 -> 9 -> 9: a new
process on each of the four cross-site navigations, none on the same-site one or the reload (site isolation is on in
Electron; `localhost`, `127.0.0.1` and `[::1]` are three sites). Through all of them: webContents.debugger stayed
attached (no 'detach'), the browser stayed connected, page.url() matched the destination, evaluate returned the new
host, the click worked (30 to 37 ms), the snapshot worked (3.9 to 4.6 ms), and the main frame id stayed the same
through every swap, so the bridge's announced targetId (pass one's rule: the real main frame id) remains valid
across process swaps. Debugger events per swap: Page.frameStartedNavigating, Runtime.executionContextsCleared twice,
Page.frameNavigated; no Target.* event, no new session. Cross-site goto took 77 to 81 ms against 9 to 12 ms same-site

app.isPackaged reads false; a build:app binary differs only in the executable and resources path), writing a step
log from inside. Five variants.

  external: playwright-core in `dependencies`, packed into the asar. Bundle 130 KB (the app, the bridge, ws); asar

    app.asar/node_modules/playwright-core/index.js and loads in 114 ms; bridge start 5.8 ms; connectOverCDP 44.5 ms

    Nothing was unpacked: playwright-core 1.63 has no native code, its bundles read through Electron's asar fs
    patch, and connectOverCDP spawns nothing (lib/webp_codec.wasm was not exercised: the screenshot is PNG).
  external-unpacked: the same with node_modules/playwright-core left outside the asar (electron-builder's
    asarUnpack; asar 160 KB plus 13.1 MB unpacked). The same results (connect 32.3 ms, snapshot 22 ms, click
    21.4 ms). Unpacking buys nothing.
  bundled-plain and bundled: playwright-core bundled into main (no `dependencies`). With nothing externalised Rollup
    stops on playwright-core's optional dynamic import of `kerberos` (lib/utilsBundle.js; bundled-plain, recorded);
    with `kerberos` in rollupOptions.external the build passes in 4.7 s (6.6 MB bundle) with warnings
    (chromium-bidi/lib/cjs/* unresolved and treated as external; eval in coreBundle.js), and the bundle keeps 14 bare
    requires it could not resolve (chromium-bidi x2, enquirer, ./custom-prompt, ajv runtime x4, ajv-formats, kerberos,

built app, since the dev tree masks both failures. [parent-impact] none for §3 D: "playwright-core runs in the main
process" holds; the build rule above is E4c's to carry.

Scenario (chipsScenario; results/pass2/chips.json). On about:blank with the view's debugger attached:
Network.setCookie {name chips_probe, domain 127.0.0.1, secure, SameSite=None, url http://127.0.0.1:17335/,
partitionKey {topLevelSite "http://localhost", hasCrossSiteAncestor true}} (the shape pass one used for an imported
CHIPS row), an unpartitioned control plain_probe the same way, and a third through Electron's session.cookies.set
with a partitionKey field. Then four loads whose B request logs its Cookie header on the server: A embedding B's
/echo-cookies in an iframe (the partition the cookie was set for), C embedding B (another partition), B top-level
(the unpartitioned context), A embedding B again.

Result. Both Network.setCookie calls succeeded on http loopback (secure cookies are allowed there; an import's rows
are https). Network.getAllCookies lists chips_probe with its partitionKey and the other two with none: the cookie
set through cookies.set with a partitionKey was accepted without error and stored unpartitioned. Sent: A-embeds-B
chips_probe plain_probe electron_pk_probe (Sec-Fetch-Site cross-site, Sec-Fetch-Dest iframe); C-embeds-B plain_probe
electron_pk_probe; B-top plain_probe electron_pk_probe; A-embeds-B again all three. session.cookies.get lists
chips_probe beside the others with no partition field at all.

Verdict: a CHIPS cookie imported through Network.setCookie on the tab's debugger session is sent exactly where Chrome
would send it (its top-level site, as a cross-site subresource) and nowhere else, so pass one's import route is
complete end to end. [parent-impact] E4b must never route a partitioned row through session.cookies.set: Electron accepts the key and
drops it, which would turn a partitioned cookie into one sent to every embedding site (a privacy regression over
Chrome, silent). The import report verifies partitioned rows through Network.getAllCookies on the same session, not
through cookies.get, which cannot see the partition.
