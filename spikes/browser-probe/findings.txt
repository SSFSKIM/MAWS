ENVIRONMENT AND METHOD
  Electron 44.4.5 (MAWS's pin; Chromium 152.0.7977.130, Node 24.21.0), playwright-core 1.63.0, ws 8.22.0. macOS 26
  (Darwin 25.6.0), arm64. The probe app is spikes/browser-probe/main.mjs: a BaseWindow holding a WebContentsView in the
  persistent partition "persist:maws-probe", a local HTTP server on 127.0.0.1:17333 serving page/index.html (a form, a
  list without ids, a login form) plus a cookie echo and a report sink, and a preload (preload.cjs) that names an
  alt-clicked element with shared/locator.cjs. Scenarios: cdp-port, cdp-bridge, cdp-pipe (raw and through Playwright's
  Electron launcher), import, extensions; `pnpm start` runs the four in-app scenarios in one process (results/all.json,
  the run quoted below unless stated). Chrome data: the owner's Default profile stores were copied with cp into
  /tmp/maws-e0b-chrome/Default (History, Cookies, Login Data, Login Data For Account, Local State, Extensions/), never
  read in place; macOS allowed the copy (no "Operation not permitted"). The real Safe Storage key was never fetched;
  every decrypt ran against a synthetic profile built by import/synthetic.mjs with a generated password. Only counts,
  schemas and shapes of the real copies were read; no URL, cookie, user name or password value was printed or stored.
  The copies and the probe's partition are deleted at hand-back.

S2 PLAYWRIGHT OVER CDP AGAINST A WebContentsView
======================================================================================================================

S2 (a) Attaching playwright-core's connectOverCDP. YES, both routes; the bridge is the one to build on.

  Route 1, --remote-debugging-port (cdp/ in main.mjs cdpPortScenario).
    app.commandLine.appendSwitch('remote-debugging-port', '9339') before ready; chromium.connectOverCDP('http://127.0.0.1:9339').
    Attach 45.7 ms cold, 10.4 ms on a second connect (Playwright's first-connect setup dominates, not the transport).
    Disconnect 8 ms; the view is untouched afterwards.
    What it exposes: every WebContents in the process. The inventory listed 2 pages (the browser view and a second
    WebContentsView standing in for MAWS's own renderer), 3 while DevTools was open (the DevTools frontend is a page
    target too). Playwright attaches to all of them (Page/Runtime/Network/Log enabled in each). Any local process that
    can reach 127.0.0.1:9339 drives the whole app, renderer included; Chromium's own token check is only on the
    /json endpoints, and the port must be chosen before ready (a fixed port or stderr parsing for port 0).
    webContents.debugger beside a connected Playwright: webContents.debugger.attach('1.3') succeeded while Playwright
    was connected (Chromium multi-client), main's Runtime.evaluate returned the title, Playwright's evaluate and click
    kept working during and after main's detach. No conflict observed.
    DevTools beside Playwright: openDevTools succeeded, Playwright kept working.

  Route 2, webContents.debugger bridged to a browser-level endpoint (cdp/bridge.mjs, 150 lines).
    The debugger is a page session; Playwright needs a browser target. The bridge answers exactly five browser-level
    methods itself (Browser.getVersion, Target.setAutoAttach, Browser.setDownloadBehavior, Target.getTargetInfo,
    Target.activateTarget; stats.unknownBrowserMethods stayed empty), announces the one view as an attached target
    under a synthetic session id, and forwards every session-scoped command to webContents.debugger.sendCommand(method,
    params, sessionId) with debugger events broadcast back. Child sessions (OOPIFs, workers) from the page's own
    Target.setAutoAttach pass through with their real ids (declared, not exercised: the test page has no iframe).
    Bridge start 1.5-11.6 ms; attach 37-46 ms cold (6 ms when Playwright is already warm); disconnect 1.5-4.5 ms.
    Traffic for the whole driver: 654-656 forwarded commands, 212-226 events, 5 browser-level calls, 2 forwarded errors
    (`Runtime.callFunctionOn: Could not find object with given id`, Playwright's post-navigation cleanup, harmless).
    One rule learned the hard way: the announced targetId must be the view's real main-frame id (Page.getFrameTree
    frame.id). In CDP a page target's id is its main frame's id and Playwright keys its FrameSession on that equality;
    with an invented id page.url() stayed "" and evaluate waited forever for an execution context.
    What it exposes: one page. inventory = 1 context, 1 page, the view's URL. browserContext.newPage() fails with the
    bridge's own error (Target.createTarget is not available: tabs are MAWS's to create). No port, no stderr line, a
    WebSocket on 127.0.0.1 with an ephemeral port and an unguessable path (add a token in the product).
    Debugger beside the bridge: the debugger IS the transport. A second webContents.debugger.attach() throws
    "Debugger is already attached to the target"; but main can call webContents.debugger.sendCommand on the shared
    session while Playwright is connected (Runtime.evaluate returned the title and Playwright kept working), so MAWS's
    own CDP needs (screenshot for a comment, Input events for takeover) ride the same attachment. DevTools opened
    beside the bridge and Playwright kept working; the debugger stayed attached through open and close.

  Route 3, --remote-debugging-pipe.
    Raw (cdp/pipe-raw.mjs): Electron honours the switch; the parent owning fds 3/4 speaks NUL-framed JSON;
    Browser.getVersion in 6.8 ms, Target.getTargets listed one page target, Target.attachToTarget + Runtime.evaluate +
    Page.captureScreenshot (101,871 bytes) worked; nothing is printed to stderr. Playwright cannot use it directly:
    chromium.connectOverCDP accepts only a ws:// or http:// endpoint, so a pipe needs a WebSocket adapter in the
    launcher. Playwright's own _electron.launch does not use the pipe either: process.argv in the launched app showed
    `--inspect=0 --remote-debugging-port=0` (results/cdp-pipe-playwright-electron.json). Either way the pipe belongs to
    the process that spawned Electron, which is never MAWS's own main process: the pipe is an e2e route, not the
    in-app route.
    Through _electron.launch (launch-pipe.mjs): launch 391-1011 ms; electronApp.windows() listed the WebContentsView's
    page as a window; the full driver passed with the same numbers; refs read `e20` for the first document and `f1e20`
    after a reload (the frame prefix appears once a second document exists).

  What E4's cut should take: the bridge, one per browser view, started lazily when a browser tool first targets the
  tab (the attach is ~40 ms, the bridge itself ~2-12 ms), closed when the tab closes. playwright-core runs in the
  main process (where the views live). Never ship --remote-debugging-port in the product: it exposes MAWS's own
  renderer and every other view to any local process. MAWS's own CDP needs go through the same webContents.debugger
  attachment, not a second one. The pipe route is the e2e harness's business (MAWS's e2e already uses Playwright's
  Electron launcher).
  Open: OOPIF child sessions through the bridge (declared, untested); more than one connected client per bridge
  (the WebSocket server accepts several; Playwright's semantics for shared pages were not tested); a token on the
  bridge URL.

S2 (b) Snapshot with refs, click and fill by ref, read-only evaluate, screenshot. YES.
    page.ariaSnapshot({ mode: 'ai' }) is public in 1.63 (the MCP's `_snapshotForAI` path is now this option): YAML with
    `[ref=f5e20]` on every interactive or named node, `[active]`, `[level=1]`, `[cursor=pointer]`, `/url:` children.
    The test page gives 59 lines, 2,164 characters, 46 refs. Default mode has no refs (hasRefs false); `boxes: true`
    appends `[box=37,275,87,32]` (viewport CSS pixels), useful for comment-mode crops.
    page.locator('aria-ref=f5e20') resolves a ref (the selector engine still exists in 1.63). On the view: click x10
    (count 0 -> 10), fill x10 ("Ada 9"), selectOption x3 ("coffee"), check (true), evaluate (title and count),
    page.screenshot PNG 99,306 bytes at 1100x760, locator.screenshot 2,459 bytes, goto + goBack.
    Read-only evaluate is a policy, not a mechanism: page.evaluate runs anything; `browser_eval` must enforce
    read-only by its own means (an allow-list of expressions or a wrapper that rejects assignments; out of scope here).
    What E4 should take: snapshot = ariaSnapshot({mode:'ai'}) on the tab's page; act = locator('aria-ref=<ref>')
    with Playwright's actionability waits; screenshot = page.screenshot or locator.screenshot; `boxes: true` when the
    snapshot feeds comment mode's overlay.

S2 (d) Do refs survive a reload and a DOM mutation. PARTLY: mutation yes, reload no, rooted snapshot partly.
    Refs are `f<frameOrdinal>e<n>` and element-bound inside one document: the same element kept f5e20 across six page
    snapshots (incrementRefStable true); inserting three sibling buttons before it gave them f5e47-49 and left
    Increment at f5e20; the old ref resolved without a new snapshot (oldRefResolvesWithoutResnapshot = "increment").
    Across a reload the old ref fails at once ("Invalid frame in aria-ref selector"); the new snapshot numbers the
    same element f6e20 (the frame ordinal moved from 5 to 6; the `e20` part repeats only because traversal order is
    the same, it is not identity). A rooted snapshot (locator.ariaSnapshot({mode:'ai'})) keeps the picked element's
    ref (page-level f5e20 == rooted f5e20) but drops refs outside its subtree: "Insert siblings" timed out until the
    next page-level snapshot. So Playwright keeps one ref table per frame, replaced by the most recent snapshot.
    What E4 should take: a ref is valid for one document and until the next snapshot of that frame. browser_snapshot
    returns the refs the agent may use; browser_act re-snapshots and returns a clear error naming the stale ref when
    resolution fails; comment-mode anchors never store a bare ref (S2e). If MAWS takes rooted snapshots for mapping,
    it follows them with a page-level one or does the mapping without a snapshot (the CSS route below).

S2 (e) Mapping the human's pick to the agent's ref, or to a locator both agree on. YES.
    The preload (sandbox off in the probe so it can require shared/locator.cjs; MAWS bundles) catches an alt-click in
    the capture phase, takes document.elementFromPoint, and names the element with shared/locator.cjs:
    cssPath (nearest unique id, then tag:nth-of-type steps), a11yPath (role "name" chain with a basic implicit-role
    table), role, name, rect. It reports over IPC to main (6-9 ms end to end, picks counted 3 and 6) and through a
    contextBridge getter for an external driver.
    Three targets, both routes: button "Increment" (#increment), button "Act" inside an id-less list
    (body > main > section:nth-of-type(2) > ul > li:nth-of-type(2) > button), textbox "Name" (#name).
      human css -> agent ref: page.locator(css).ariaSnapshot({mode:'ai'}) first line's ref == the page-level ref  3/3 (1-2 ms)
      agent ref -> human css: locator('aria-ref=<ref>').evaluate(cssPath) == the preload's css                       3/3
      role and name agree                                                                                          3/3
    The a11y paths do not agree textually: Playwright's chain is `generic > main > region > generic > button
    "Increment"` (it emits `generic` nodes and omits the region's aria-labelledby name), the preload's is `main >
    region "A form" > button "Increment"`. The a11y path is a human label, not the key.
    Synthesizing the human's click: Playwright's mouse.click(x, y, {modifiers:['Alt']}) did NOT set altKey on the DOM
    event in this Electron (the page logged `click alt=false`); keyboard.down('Alt') + mouse.click did (`alt=true`),
    and was used for every pick. webContents.sendInputEvent with modifiers ['alt'] is wired as a third fallback and
    was never needed, so it is unverified. A physical option-click is what the product gets, so this is a probe
    quirk, not a product risk.
    What E4 should take: the X10 browser-element locator is {css, role, name, pageUrl, box?} produced by a shared
    module the preload and the tools both import; the agent's ref is resolved to it on demand (rooted snapshot or
    evaluate), and the human's pick is resolved to a live ref the same way at the moment the agent needs it. Refs
    are transport, locators are storage.
    Open: the implicit-role table in shared/locator.cjs is small; adopt a maintained ARIA role computation (or ask
    Playwright for role and name through a rooted snapshot and store its answer) before the anchor format binds.

S1 CHROME PROFILE IMPORT BY COPY
======================================================================================================================

Where the stores are on this machine (Chrome Default profile, read from the copy; counts only).
    Local State: profile.info_cache has 10 profiles; each entry carries name, gaia_name, user_name, avatar_icon (and
    25 more fields); every profile has a name. The picker reads this file and shows name plus gaia_name.
    Default/History: 38 MB, urls schema v70, 17,554 URLs, 34,411 visits, visit_count sum 33,346, 779 distinct hosts,
    last_visit_time range 2024-07-30 .. 2026-10-05.
    Default/Cookies (at Default/, not Default/Network/, on this Chrome 14x; an import checks both): schema v24, 5,112
    rows, all encrypted (`v10` prefix 5,112, plain `value` 0), 1,005 partitioned (top_frame_site_key set, CHIPS),
    1,170 distinct host_keys.
    Default/Login Data (the local store): schema v43, 91 rows, all blacklisted_by_user = 1 ("never save"), 0 passwords.
    Default/Login Data For Account (the Google-account store): 320 rows, 228 with an encrypted password (`v10`), 91
    blocklist, 1 empty. The owner's saved passwords live here; an import that reads only "Login Data" finds none.
    keychain_identifier is empty in both: no legacy per-item Keychain passwords remain.
    Default/Extensions: 21 unpacked directories (20 ids; Claude has two versions), 602 MB copied.
    Copying while Chrome ran worked with plain cp (take the -journal files too); SQLite opened the copies read-only.

S1 (a) History. YES: plain SQLite; Electron keeps none, so MAWS keeps its own.
    import/stores.mjs readHistory opens the copy read-only with node:sqlite (the same module src/main/index/db.ts
    already uses; statements need setReadBigInts(true) because Chrome's microsecond timestamps exceed 2^53), reads
    urls (url, title, visit_count, typed_count, last_visit_time, hidden) in 185 ms for 17,554 rows. Chrome time is
    microseconds since 1601-01-01; crypto.mjs converts.
    What MAWS keeps itself: Electron's session has no history store and no address-bar model; `webContents`
    navigation history is per-view and dies with it. E4 adds a MAWS-owned `browser_history` table (url, title,
    visit_count, typed_count, last_visit, source: 'imported' | 'maws', profile partition) in the app's index
    database, fed by did-navigate and page-title-updated, read by the address bar's suggestions and by a future
    history view; imported rows carry their source so they can be dropped with the profile. The agent sees history
    only through a tool that is explicitly added later, never through browser_snapshot.
    Open: `visits` (per-visit transitions) is not needed for suggestions; skip it.

S1 (b) Cookies. YES, proved end to end on a synthetic store; the real key gates it.
    Scheme (import/crypto.mjs): key = PBKDF2-HMAC-SHA1(password, "saltysalt", 1003, 16 bytes); AES-128-CBC with a
    16-space IV; value = "v10" + ciphertext; at store version 24 (this profile; recent Chrome 13x) the plaintext is
    SHA-256(host_key) (32 bytes) + value, so a decrypt verifies the domain hash and strips it (hashedPrefix 3 of 3);
    older stores hold the bare value and decryptCookieValue accepts both.
    Synthetic store (import/synthetic.mjs, the real CREATE TABLE statements): 5 rows -> 3 set, 2 skipped with a
    reason: the CHIPS cookie (Electron's cookies.set has no partition key) and a SameSite=None cookie without Secure
    (Chromium rejects it on set: EXCLUDE_SAMESITE_NONE_INSECURE). session.cookies.set took 0.8 ms for 3; the jar
    showed hostOnly/domain, httpOnly, secure, sameSite (lax, unspecified, strict) and expiration as mapped; a request
    to http://localhost:17333/echo-cookies carried `probe_session` (httpOnly) and `probe_pref` with the right value;
    document.cookie saw only the non-httpOnly one. Mapping (stores.mjs toElectronCookie): url =
    scheme://host_key-without-dot + path (https when is_secure or source_scheme 2), domain = host_key only when it
    starts with '.', sameSite -1/0/1/2 -> unspecified/no_restriction/lax/strict, expirationDate from expires_utc when
    has_expires. A wrong key fails cleanly (bad padding), 0 of 2 decrypted, no garbage accepted.
    The real key, one command and one prompt:
      security find-generic-password -s "Chrome Safe Storage" -a "Chrome" -w
    macOS shows: `security wants to use your confidential information stored in "Chrome Safe Storage" in your
    keychain.` with Deny / Allow / Always Allow. MAWS runs it once per import, keeps the password in memory for the
    duration of the import only, and tells the user before the prompt appears what it is for and to click Allow (not
    Always Allow, which would grant the `security` binary standing access). Electron has no Keychain read API for
    arbitrary items (safeStorage is MAWS's own item, "<app> Safe Storage"), so the child process is the way.
    [parent-impact] §3 D reads "copies cookies and history from its on-disk stores, decrypts saved passwords with
    Chrome's Safe Storage key after one Keychain consent": on this profile every cookie value is encrypted with that
    same key (`value` is empty for all 5,112 rows), so the Keychain consent gates the cookies category too, not only
    passwords. History and extensions need no key.
    What E4 should take: the decrypt and mapping as written here; a per-cookie skip list in the import report
    ("N cookies, K skipped: partitioned, M skipped: rejected"); the partition is per imported profile
    (session.fromPartition('persist:chrome-<profile dir>')); expired rows dropped before set.
    Open: 1,005 of 5,112 real cookies are partitioned and will not import until Electron exposes partition keys;
    the real Cookies file may be under Default/Network/ on other machines.

S1 (c) Login Data. PARTLY: decrypt yes, consumer no.
    Decrypt: same key, no hash prefix; the synthetic store's 2 credentials decrypted and matched, the blocklist row
    was skipped, the wrong key failed 2 of 2. A credential is {origin_url, action_url, username_element,
    username_value, password_element, password, signon_realm}. The real stores: see above, 228 passwords in the
    account store, 0 in the local one.
    What Electron offers a consumer: nothing. No password manager, no autofill (the CDP Autofill domain is absent
    through webContents.debugger: "'Autofill.enable' wasn't found"; no chrome.autofill); the webContents 'login'
    event is HTTP Basic/Digest only. Codex has a consumer because its Electron is a fork: the app ships "Codex
    Framework" (sources under `owl/`), with `owl/browser/browser_profile_importer.cc`,
    `browser_profile_importer_extensions.cc`, `electron_api_autocomplete.cc`, and Chromium's
    components/password_manager and components/autofill compiled in (51 and 96 source-path strings in the binary); its
    JS side (readable/chatgpt-26.928.40906/main-process/main-BvBtZhys.js:50729-50808) only calls
    session.browserProfileImporter.list/getSignals/import. MAWS runs unmodified Electron.
    What a consumer would need in MAWS: (1) a credential store in the profile's partition directory, encrypted with
    Electron's safeStorage (MAWS's own Keychain item), keyed by signon_realm; (2) a login-form detector in the browser
    preload (a password field plus the nearest username field, origin matched to signon_realm, honouring
    autocomplete=username/current-password); (3) a fill affordance MAWS draws (a key icon in the field or the chrome's
    address row, listing matching user names, filling on click, never on load, never auto-submitting), with the fill
    done through the preload or Input.insertText; (4) a save prompt on submit for new or changed credentials;
    (5) a settings surface to see, copy and delete entries. That is a child of its own, about the size of comment mode.
    Recommendation: P1 imports cookies and history (and extensions, S1d); the consent sheet shows "Saved passwords"
    disabled with "needs MAWS autofill, later"; nothing is decrypted that has no consumer. Importing passwords into a
    store nothing reads adds risk and no capability. [parent-impact] §3 D's "decrypts saved passwords" is feasible
    but has no consumer on unmodified Electron; §12 already anticipates holding passwords; the cut should make that
    the plan, not a fallback.

S1 (d) Extensions. PARTLY: MV3 core loads and runs; much of the API surface does not exist.
    session.extensions.loadExtension(dir) (Electron 44; the old session.loadExtension is gone) needs a persistent
    partition and must be repeated each boot; packed .crx is unsupported; unpacked Chrome Extensions/<id>/<ver>/
    directories load as they are (names resolve through _locales: "Google Translate", "MetaMask").
    The probe's MV3 extension (ext/test-ext): loaded in 3.5 ms; the background service worker ran
    (session.serviceWorkers.getAllRunning listed it); the content script injected (DOM marker) and round-tripped a
    message to the worker (fromTab 1); chrome.scripting.executeScript ran in the tab; an offscreen document was
    created and ran. Present and working in the worker: runtime (messaging, getManifest, getURL), storage.local and
    storage.session, tabs.query (WebContents appear as tabs with ids and urls), scripting, alarms, action.setTitle
    (there is no toolbar to show it), declarativeNetRequest.getDynamicRules, webRequest.onBeforeRequest.addListener,
    offscreen, management, i18n, extension. Absent (undefined): cookies, contextMenus, notifications, webNavigation,
    sidePanel, windows, tabGroups, identity, history, bookmarks, downloads, commands, permissions, debugger, proxy,
    privacy, sessions, favicon, topSites, webRequestAuthProvider, runtime.connectNative (nativeMessaging). Electron
    logs "Permission 'x' is unknown" for each unsupported permission and loads anyway. No popup, options page, side
    panel or omnibox surface exists; `action` has nowhere to appear.
    The owner's 21 directories: 21 of 21 loaded (total 204 ms, 1-31 ms each); 13 service workers ran: Adblock Plus,
    Infinity New Tab, Ona, Lyrics, GoFullPage, Office Editing, Google Docs Offline, Save to Google Drive, WEBZEN
    Starter, ChatGPT, Application Launcher For Drive, Playwright Extension, MetaMask. 8 did not run: 7 workers died
    at script evaluation ("Service worker registration failed. Status code: 15") because top-level code touches an
    absent API: Google Translate (contextMenus.onClicked), Obsidian Web Clipper (commands.onCommand), Claude x2
    (tabGroups .Color), NordVPN (webNavigation.onErrorOccurred), VeePN (proxy/privacy .network), iCloud Passwords
    (webNavigation.onBeforeNavigate); Chrome Web Store Payments is MV2 without a worker. Five of the 13 running
    workers logged uncaught errors on the same kind of gap (Adblock Plus webNavigation.onBeforeNavigate, Infinity
    .contains, Ona .onRemoved, Save to Google Drive storage.sync, ChatGPT windows.onFocusChanged) and keep running
    partially. results/extensions-stderr-digest.txt has the per-id digest.
    What E4 should take: "loads" is not "works". The import report lists each extension as loaded / background
    running / background failed on chrome.<api> / errors, from session.serviceWorkers state and the main-process
    console lines, and the consent sheet names the unsupported permissions per extension before the import (the
    manifest is enough: any of the 21 absent namespaces predicts the failure). Codex's allowUnverifiedExtensions
    confirmation (codex-extensions.txt §1) has its MAWS equivalent here. Extensions with content scripts and storage
    only (clippers, formatters, Playwright Extension) are the realistic win; anything needing a toolbar, side panel,
    context menu, cookies, webNavigation or native messaging is not.
    Open: whether Electron's extension storage survives removeExtension + reload (not tested); CSP and host
    permission prompts for content scripts on arbitrary sites (not tested); loading from the Chrome directory in place
    is never done, the directory is copied into the partition's own extensions folder first.

S1 (e) The consent surface per category, and what the import must never do.
    One sheet, one profile picked from Local State (name and gaia_name shown, nothing else), four categories each
    with its own checkbox and its own line of consequence:
      History:     "17,554 pages. Read from a copy; needs no password. Shown in the address bar's suggestions."
      Cookies:     "5,112 cookies (1,005 partitioned cookies cannot be imported). macOS will ask once to read Chrome's
                    Safe Storage password; click Allow. Nothing is written back to Chrome."
      Passwords:   disabled in P1: "needs MAWS's autofill, not yet built" (the count can still be shown: 228).
      Extensions:  "21 extensions; 8 will not run in MAWS (lists them with the API they need); the others run with the

    Then the report row: "N cookies, M history entries, K extensions, J skipped: <reasons>" and a "Remove imported
    profile" action that drops the partition and the imported history rows.
    Never: log or display a cookie value, password or history URL during the import (counts and reasons only; the
    probe's own output follows this rule); keep the Safe Storage password past the import, write it anywhere, or ask
    with "Always Allow"; copy the stores anywhere but a temporary directory inside the app's data directory, deleted
    when the import ends; import into the default partition or into another profile's partition; import `Web Data`
    (payment methods) at all; read or write Chrome's directory while Chrome runs other than copying; drive Chrome or
    modify any of its files; import passwords without a consumer; run imported extensions' service workers before the
    user confirms the unverified-files sheet; expose imported data to the agent except through the tools that are
    explicitly on the spine (browser_* act on the live page; no history or cookie tool exists in P1).

WHAT E4'S CUT SHOULD TAKE, IN ONE PLACE
======================================================================================================================
  View and import child: WebContentsView per tab in a per-profile persistent partition; the copy-and-import pipeline
    (History -> MAWS history table; Cookies -> cookies.set with the skip list; Extensions -> loadExtension per boot with
    the per-extension report); the Keychain prompt once, for cookies; passwords held; the consent sheet above.
  Comment mode child: the shared locator module (css, role, name, box) in the preload and in the tools; the anchor
    stores the locator and the page URL, never a bare ref; the overlay crops from `boxes: true` or capturePage.
  Browser tools child: one debugger bridge per tab, playwright-core in main, lazy attach (~40 ms), kept attached while
    the agent holds the tab; browser_snapshot = ariaSnapshot({mode:'ai'}); browser_act by aria-ref with a stale-ref
    error that names the ref; browser_eval read-only by policy; browser_screenshot by page or ref; new tabs through
    browser_tabs, never Target.createTarget; the human's takeover rides the same attachment (Input events are not
    needed to detect the human: the preload sees the real clicks).

[parent-impact] COLLECTED
  1. §3 D: the Keychain consent gates cookies as well as passwords (every cookie value in a current Chrome profile is
     encrypted with the Safe Storage key). The sentence should bind the consent to the cookies category.
  2. §3 D and §12: on unmodified Electron there is no consumer for imported passwords; Codex's consumer is its Electron
     fork's compiled password manager and autofill. Recommend the cut holds passwords out of P1 and the design says so,
     rather than a per-child fallback.
  3. §3 D "playwright-core connected to the view's debugger, or the CDP protocol directly": both hold; the finding is
     that the debugger route needs the small browser-level bridge (five methods, real frame id as target id) and that
     the remote-debugging port must not ship. Not a contradiction; a precision.
