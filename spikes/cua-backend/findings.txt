==== S1: dialogs, the -run-dialog wrap holding Electron's callback ====
Setup: Electron's one -run-dialog listener (count 1 before the wrap, as on 44.4.5) is replaced by one that stores
(info, callback) and never calls Electron's original. Dialogs are fired from a page task (setTimeout inside Runtime.evaluate)
so the evaluate returns before the renderer blocks; results read back by Runtime.evaluate of window.r and document.title.

Q1  Is Page.javascriptDialogOpening delivered while the callback is held?  YES, both views, every dialog.
    alert:   {"defaultPrompt":"","frameId":"…","hasBrowserHandler":true,"message":"hello alert","type":"alert","url":"http://127.0.0.1:<port>/"}
    confirm: {"defaultPrompt":"","frameId":"…","hasBrowserHandler":true,"message":"ok to proceed?","type":"confirm","url":"http://127.0.0.1:<port>/"}
    Note: hasBrowserHandler is true (Electron's dialog manager is still the content-layer handler, even though the wrap shows
    nothing). Ordering: the CDP event reached main's JS before the -run-dialog emission (the first round logged "held
    callbacks: 0" at javascriptDialogOpening, then "-run-dialog alert … (held)"); MAWS cannot assume it has seen -run-dialog
    when the CDP event arrives.

Q2  Does Page.handleJavaScriptDialog resolve alert/confirm, and does Page.javascriptDialogClosed arrive?  YES, both views.
    alert  handle {accept:false} -> {} | closed {"result":false,"userInput":""} | page {"r":"alert-returned","title":"after-alert"}
    confirm handle {accept:false} -> {} | closed {"result":false,"userInput":""} | page {"r":false,"title":"confirm:false"}
    confirm handle {accept:true}  -> {} | closed {"result":true,"userInput":""}  | page {"r":true,"title":"confirm:true"}
    alert  handle {accept:true}  -> {} | closed {"result":true,"userInput":""}  | page {"r":"alert2-returned","title":"after-alert2"}

Q3a Held callback called after CDP answered:
    - first call: no throw, no effect: callback(false) after CDP accept:true left the page at {"r":true,"title":"confirm:true"};
    - second call of the same callback: THROWS "One-time callback was called more than once" (a catchable JS Error in main;
      no crash);
    - a later dialog afterwards works normally (confirm/accept:true -> page confirm:true, closed event arrives);
    - (3e) a stale callback (its dialog already answered by CDP) called WHILE a newer dialog is open: no throw, no
      javascriptDialogClosed within 800 ms, the page stays blocked on the newer dialog (evaluate did not return), and CDP's
      handle(true) on the newer one then resolves it normally ({"r":true,"title":"confirm:true"}). A stale callback is
      inert; it cannot answer a newer dialog.
    - (3d) the reverse order: the wrap answers through the held callback FIRST (callback(true)): javascriptDialogClosed
      arrives ({"result":true,"userInput":""}), page confirm:true, and a later Page.handleJavaScriptDialog returns
      ERROR "No dialog is showing". So whichever side answers first wins; the other is a no-op (callback) or a clean
      protocol error (CDP).
Q3b Held callback never called and dropped (--js-flags=--expose-gc, references dropped, global.gc() x5):
    - after CDP answered: a FinalizationRegistry on the callbacks proves collection
      (finalized ["confirm:after late?","confirm:ok to proceed?","alert:hello alert"]); the next confirm and alert are
      answered by CDP normally; no crash, renderer not crashed, debugger still attached;
    - (3c) dropped BEFORE CDP answers (the wrap keeps no reference; gc while the dialog is open; finalizer fired:
      ["confirm:dropped before answer?"]): CDP handle(true) still resolves it ({} | closed result:true | page confirm:true)
      and the next alert is answered normally. Collection of the callback does NOT auto-answer the dialog (otherwise CDP's
      handle would have failed "No dialog is showing" and r would be false).

Q4  Native box / freeze: none. The wrap never calls Electron's listener, so no sheet/NSAlert can be shown; the hidden window's
    'sheet-begin' never fired; main's 50 ms setInterval max gap over each scenario was 55 ms (placed) and 54 ms (unplaced,
    where Electron's own listener would have been a parentless runModal that freezes main, per findings-e4c-unplaced.txt).
    renderer crashed? false in every case; no render-process-gone / child-process-gone; process exit 0.

Q5  Never-placed view (no owner window): identical results to the placed view for Q1 to Q4 (see the unplaced lines below).

Caveat for the product (not a failure of the probe): a held callback that nobody answers leaves the page blocked
indefinitely; with no CDP client handling dialogs on the tab (cua not attached, Page not enabled), MAWS must still answer
through the callback (as its current routes do).

==== Verdicts ====
S1: PROMOTE — with the wrap only holding Electron's callback, CDP's own Page.javascriptDialogOpening / handleJavaScriptDialog / javascriptDialogClosed work for alert and confirm on placed and never-placed views with no native box and no main freeze; first answer wins, a later single callback call is an inert no-op (even with a newer dialog open), a second call of the same callback throws a catchable "One-time callback was called more than once", and dropping/GC'ing it (before or after CDP answers) is harmless.
S2: PROMOTE — Page.setInterceptFileChooserDialog, Page.fileChooserOpened and DOM.setFileInputFiles pass through webContents.debugger unchanged (placed and never-placed views); the only caveats are input delivery (focus emulation needed on hidden pages; send mouseMoved before press on never-placed views), not interception.
