P4-AGG M4: can MAWS drive the engine's own MCP sign-in? The spike's findings
(docs/doperpowers/specs/2026-10-24-plugin-aggregator-design.md, M4 "The spike comes first"; 2026-10-25)

Method. spikes/p4-aggregator/m4-signin-spike.mjs, run on the Mac mini through the gate as an e2e:discover case
(e2e/discover-connectors.spec.ts "spike: …"; scripts/ci-gate.sh --gates e2e:discover --runner macos --class1a pool
--evidence, run 40175924834 on 295e97229, green): engine 2.1.309 (the runner's ~/.local/share/claude/versions/2.1.309)
in stream-json with no prompt, under the runner's HOME and a scratch CLAUDE_CONFIG_DIR, every server `claude mcp add
--transport http <name> <fixture>/mcp --scope user`; M1's OAuth fixture in engine mode (auto-approving /authorize, so the
browser step is a GET of the authorization URL followed by hand). Each question in its own engine process over the same
configuration. The control frames, OAuth query values redacted and initialize answers reduced to their keys:
spikes/protocol-probe/fixtures/p4/p4-agg-m4-signin.jsonl (pinned by fixtures.test.mjs "p4/p4-agg-m4-signin").
Keychain custody (e2e/support/connector-oauth.ts engineKeychainCustody): the scratch directory's exact item,
`Claude Code-credentials-ae335039`, absent before and claimed; after every engine had exited, found, deleted by that
exact name and verified gone. No `.credentials.json` was written. The fixture logged no refusal (7 registrations, 7
authorizations, 5 code exchanges).

Which keychain path this measures: the runner's own login keychain, under the runner's HOME (a scratch
CLAUDE_CONFIG_DIR, so the one item is the exact derived name above). Not a scratch keychain under a scratch HOME.

An incident, recorded so it is not repeated. Before the gate run, the same script was dry-run once on the owner's
MacBook under a scratch HOME (2026-10-25, 01:10:50 to 01:15:07 PDT), meant to check only its mechanics, against the
brief, which kept every sign-in on the mini. A scratch HOME on a Mac with a logged-in desktop does not fail silently:
the engine's token and client-information saves failed with errSecNoDefaultKeychain about 120 times, and each failure
raised a modal "keychain cannot be found" dialog on the owner's screen (the exchange then answered "Existing OAuth client
information is required when exchanging an authorization code"). The architect's rule since: every engine sign-in,
every Keychain write and everything under acceptance 9 runs only in gate jobs on the mini (`--runner macos`), scratch
keychains included; none of it on the MacBook in any form. Should a run on the mini ever need a keychain under a scratch
HOME, give that HOME its own: `HOME=$root/home security create-keychain -p '' $root/home/Library/Keychains/login.keychain-db`,
deleted in teardown.

1. custom scheme. mcp_authenticate {serverName, redirectUri: http://127.0.0.1:<MAWS's port>/callback} answered in 137 ms
   {authUrl, requiresUserAction: true, callbackExpected: true, redirectScheme: "custom", state} (the client registered
   for that URI first). The browser step's redirect came to that URI with code and state; mcp_oauth_callback_url
   {serverName, callbackUrl} answered success in 67 ms, after the token exchange ("Saving tokens", "Tokens after auth:
   Present"). mcp_status still read needs-auth 30 s later: the engine does not reconnect a server whose callback came
   through mcp_oauth_callback_url (2.1.309 cli.pretty.js 856500 to 856503: `Pu.has(server)` → no reconnect). An
   mcp_reconnect then answered success in 62 ms and mcp_status read connected with the fixture's tool. So the custom
   scheme completes with a reconnect after the callback.
2. localhost scheme. mcp_authenticate with no redirectUri answered redirectScheme "localhost" with a callbackPort; the
   redirect delivered to http://localhost:<callbackPort>/callback (the engine's own page, 200) completed the flow, and
   mcp_status read connected on the next poll, no reconnect needed.
3. A second mcp_authenticate while one is pending starts a new flow (success, a new state, 62 ms); the first flow's
   callback is then refused: "Callback URL not accepted: it belongs to a different sign-in attempt (OAuth state mismatch)
   or carries no authorization code. The sign-in in progress is still waiting; submit the redirect URL from its own
   browser page." The second flow's callback is accepted. There is no "already authenticating" refusal.
4. Cancel then retry. A flow MAWS abandons (its listener closed) does not block a retry: a new mcp_authenticate starts
   and its callback is accepted. The abandoned flow's callback afterwards answers "No active OAuth flow for server:
   fx-cancel".
5. A server added to the file configuration after the session started (`claude mcp add … --scope user` while the
   session ran) never appears in that session's mcp_status (5 s later: absent), but mcp_authenticate for it answered an
   authUrl (not "Server not found"), and mcp_reconnect for it answered "Server status: needs-auth". The completion of such
   a sign-in in that session was not measured.
6. Path A. In a session holding a --mcp-config server and an SDK server (initialize's sdkMcpServers, as MAWS's `maws`),
   mcp_set_servers {servers: {fx-dynamic}} answered {added: [fx-dynamic], removed: [spike-sdk]}: the call removes the
   session's SDK server (the --mcp-config server stayed). Naming both servers again removed it as well (an SDK server
   cannot be named there). The loaded server signed in through the custom scheme (callback success). Path A's first
   condition fails: in a MAWS session it would drop the `maws` server.
7. The next session. A fresh session over the file configuration (fx-dynamic added there now, same name and URL) read
   every server signed in above connected, fx-dynamic included: the engine keys a credential by the server's name and
   configuration, so a sign-in in any session serves every later session with that entry (P4-R8 finding 2).
8. mcp_authenticate's latency against the fixture: 134 to 234 ms. The supervisor's 10 s bound is ample, so
   session.mcpAuthenticate stays a bounded call (M4 Decisions' last item).

Verdict: promote, path B. Sign-in completes through both schemes with the server reported connected (the custom scheme
after a reconnect). Path A is not taken: mcp_set_servers removes the session's SDK server.

UX wave U11a, M1 (2026-11-12): a dynamic connector's sign-in through MAWS's redirect
(docs/doperpowers/plans/2026-11-12-ux-wave-U11a-settings-connectors-org.md, M1 and P1; §A "The redirect")

Question. For a server of the launch's own list (`--mcp-config`) and for a plugin's server: does mcp_authenticate with
MAWS's redirect answer the custom scheme, do mcp_oauth_callback_url and then mcp_reconnect take the server's name
(`plugin:<plugin>:<server>` for the second), does mcp_status then read connected, and does a later engine process that
loads the same server read it connected?

Method. Two questions added to the spike: `dynamic` (fx-own, given through --mcp-config as MAWS's own list is) and
`plugin` (fx-oauth from a scratch plugin given through --plugin-dir, expected name plugin:fx-plugin:fx-oauth), each in its
own engine process holding an SDK server, signing in as MAWS's operation does (callback, then reconnect at once), then a
second process launched the same way reading the server's status; and, had the custom callback or reconnect been
refused, a second sign-in with no redirect through the engine's own listener (`fallback`). Engine 2.1.322 (Claude Code),
given to the spike case alone through MAWS_SIGNIN_SPIKE_ENGINE_BIN; the rest of the group stayed on 2.1.309. Run on the
Mac mini through the gate as the e2e:discover case "spike: …" with MAWS_SIGNIN_SPIKE=1: run 43357272365 (branch
ux-wave/U11a-p1 at 2c39159fc) and run 43358963647 (the script as at ux-wave/U11a 4119e0ff2). Both: 10 of 10 cases
passed, no Keychain prompt, the scratch directory's item found and deleted by custody, no plaintext credentials.

1. dynamic (both runs). name fx-own; before needs-auth, scope dynamic; mcp_authenticate ok, redirectScheme custom;
   callback ok; reconnect ok; connected true; the next process read it connected, scope dynamic, tools [read_series];
   fallback null.
2. plugin, first run: no verdict. The server was never listed in mcp_status (name null). The engine's debug file:
   "Suppressing plugin MCP server "plugin:fx-plugin:fx-oauth": duplicates manually-configured "fx-custom"". The engine
   drops a plugin's server whose address a file-configured server already names, and a later plugin's duplicate of an
   earlier plugin's (cli.pretty.js 2.1.322, the function near line 476051; a URL server's key is its normalised URL). The
   spike's file-configured servers all named the fixture's one resource. Fixed by removing the five (`claude mcp remove`,
   each answering 0) before the plugin question.
3. plugin, second run. name plugin:fx-plugin:fx-oauth; before needs-auth, scope dynamic; mcp_authenticate ok,
   redirectScheme custom; callback ok; reconnect ok; connected true; the next process read it connected, scope dynamic,
   tools [read_series]; fallback null. Steps: initialize, mcp_status, mcp_authenticate, browser, mcp_oauth_callback_url,
   mcp_status, mcp_reconnect, mcp_status, exit; then the next process's initialize and mcp_status.
4. On 2.1.322 the older questions custom, cancel and pathA are listed as failures ("the server did not report
   connected"): the server reads needs-auth after mcp_oauth_callback_url until mcp_reconnect, then connected, and the next
   process read all five connected. That is point 1 above, which src/services/connectors/sign-in.ts already handles by
   sending the reconnect; nothing new.

Verdict, by M1's criteria: promote as designed for both kinds. DYNAMIC_REDIRECT = { plugin: 'maws', own: 'maws' }.
Beyond the spike: a plugin's server is listed with scope `dynamic`, the same as a server of the launch's own list, so a
name starting `plugin:` is the only thing that tells them apart; and a plugin's connector that a hand-configured server
duplicates by address never appears in a session's status at all, which bears on who is offered Sign in and on X-184's
plugin rows.
