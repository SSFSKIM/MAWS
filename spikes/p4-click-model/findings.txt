1. WHAT THIS PHASE ESTABLISHED

The prototype. With the prototype on (the e2e seam's `armed(mode)`; off otherwise, every path P3's), one selected text
element's text box mounts ARMED: focused, editable, its caret drawn transparent, no mark bar, the solid selection frame
with handles. The stage's keys reach the armed box first, in the capture phase: the first printable or keyCode-229
keydown clears the content and flips the box to the edit with no remount and no focus change, its default left to
insert the key or let the input method compose (T10 and T11 as one rule); Enter edits with everything selected (T12);
the element keys (Escape, Delete, arrows, Tab, ⌘D, ⌘G, ⌘A) are the stage's; ⌘Z stays the box's (the deck's stack); ⌘C,
⌘X and ⌘V stay the Edit menu's, whose clipboard events the stage takes before the editor. Two modes: `clear` (the
caret hidden at the start, the content cleared at the first key) and `select` (the whole text selected and drawn
transparent, the key or the composition replacing it natively). Files: src/artifacts/slides/editor/armed.ts,
TextBox.tsx, transform/Overlay.tsx, Stage.tsx, textbox.css; src/renderer/src/tools/presentation/e2e-seam.ts.

The simulated cases: e2e/presentations-ime.spec.ts, eight cases, all green on the MacBook (quiet, 2026-10-19 23:32Z;
part of `pnpm e2e:presentations`). They drive the renderer's IME entry points over a CDP session (e2e/support/ime.ts)
in the order Chromium's macOS view sends a key the input method took: a keydown with keyCode 229, then the commit
(Input.insertText, the browser's ImeCommitText) and the new marked text (Input.imeSetComposition).

Q1. Does an ARMED editor keep a first Hangul syllable intact?
  In the renderer, yes, in both modes (I2): 한글 typed on an armed "Hello" leaves exactly 한글 (NFC) in the model; the
  editor's root is the same node object from the first key to the last; compositionstart and compositionend fire twice
  each, all on that root; no focusin or focusout during the typing; no text box mounts during it; ARMED flips to EDIT
  once. 하나 carries its ㄴ into the second syllable (L2's shape). A first jamo arriving bare (keyCode 71, no input
  method) and then re-composed through a replacement range ends as 한글, with nothing written to the box between the two
  keys (I3).
  On the real Mac: not yet answered. What a simulation cannot stand in for is exactly what Q1 turns on: whether AppKit
  routes the first key to the input method at all. Chromium gives a non-editable focus no input context
  (render_widget_host_view_cocoa.mm L2508-2509) and lets AppKit fetch a new one only 100 ms after the text-input state
  changes (render_widget_host_view_mac.mm L835-836, kDelayUpdateWindowsAfterTextInputStateChanged, on by default).
  The trace shows the armed editor focused 22 ms after the press that selects it (pointerdown at 6.6 ms, focusin of the
  text box at 28.4 ms, e2e/fixtures/ime/l1-hangul.json). So, predicted: a first key more than about 125 ms after that
  press composes in place (L1, L3); a first key inside that window, from a stage that held a non-editable focus before
  the press, may reach no input method and arrive as a bare jamo (L4). Between two text boxes the window should not
  open, because the view's input context is one object and AppKit's cached copy stays set while focus passes through
  the stage for a few milliseconds (L5 checks it). If L4 fails, the remedy is the one Google Docs and Handsontable use:
  an editable focus target under the stage whenever the deck has focus, so the text-input type never drops to none.

Q2. Can the content be cleared on the first keyCode-229 keydown, before the composition starts?
  In the renderer, yes. The trace of I2 in mode clear: the first keydown (keyCode 229, key ㅎ, isComposing false, not
  cancelled) sees "Hello" before the page's handlers and "" after them; compositionstart then fires on the empty box
  and the first input leaves ㅎ as its whole text. Chromium's macOS view forwards that keydown before the commit and
  the marked text of the same key (render_widget_host_view_cocoa.mm L1608 before L1638 and L1650), all on the widget's
  one ordered input channel, so the page's keydown handlers finish before the composition message arrives; nothing in
  the page can be late for it. On unmarked text the clear writes nothing near a composition (none exists yet) and the
  flip to EDIT writes only outside the editor (the stage's data-armed attribute, the overlay's frame, the mark bar).
  On text that is one marked run (bold all over), the clear sets those marks as stored marks so the new text keeps
  them, and ProseMirror then redraws the cursor's mark wrapper at compositionstart (prosemirror-view 1.42.6
  dist/index.js L3591-3597, its own path for typing a composition after ⌘B): a DOM write at the composition's start,
  before any marked text exists. CDP shows it harmless (I2's bold "World" ends as a bold 하나 in both modes); the live
  L2 types into the bold box to show it under the real input method.
  What is left for the real Mac: the input method keeps its own marked text in the browser process, so a cleared DOM
  does not disturb the syllable it is composing; the one way the clear could still fail is the input method asking
  the document for its text or selection between keys and seeing it stale for one round trip. L1's trace settles it.
  If it does fail, replace need not degrade to append: mode select keeps replace with no clear at all. The same I2
  case passes in mode select, where compositionstart carries "Hello" (the selection it replaces) and the first input
  leaves ㅎ alone. So the fallback order is clear, then select, then append. Both keep the marks a text carried all
  over (a bold "World" typed over stays bold: mode clear sets them as the clearing transaction's stored marks, mode
  select inherits them natively; I2 checks it in both modes).

Q3. Does preventDefault suppress Electron's menu accelerators while armed?
  Yes. Chromium sends a ⌘ key equivalent to the page first (render_widget_host_view_cocoa.mm performKeyEquivalent:,
  L1344-1375, through keyEvent:wasKeyEquivalent:YES) and passes on only an event the page did not consume
  (render_widget_host_impl.cc L2701-2709: `!processed && !skip_if_unhandled`) to Electron, whose
  PlatformHandleKeyboardEvent offers it to the main menu (electron_api_web_contents_mac.mm L37-65 at v44.4.5). The
  exceptions are a hotkey the system reserves (it never reaches the page; ⌃Space, the input-source switch, is one) and
  a Fn/Globe shortcut (the menu first).
  The Q3 case shows it through a probe menu whose Edit items count their accelerators: on the stage an unhandled ⌘C
  reached the probe's Copy and the ⌘Z the deck cancels did not reach its Undo; while armed, ⌘Z (the box's own Mod-z,
  cancelled) undid the element's nudge in the deck's stack and never reached the menu; ⌘C, left alone, reached Copy;
  a page listener
  cancelling ⌘C kept it from the menu. A CDP key enters that path at the unhandled-event step (with a native key code
  and its characters set; see finding 2), not at AppKit's performKeyEquivalent:, and the quiet e2e window is never key;
  L8 ran the same keys on the real Mac with a key window at the app's event-queue level and passed (§4).
  The Edit menu by the mouse (webContents' copy, paste and undo, which the role items' selectors reach): Copy and
  Paste act on the armed element (the stage's handlers take the events before the editor; a cancelled beforecopy
  enables Copy on a collapsed caret), never on its text. Undo does not: see finding 1.

Further findings
  1. The Edit menu's Undo and Redo do not reach the deck's stack. Observed (the Q3 case, nothing typed natively in
     the page): Edit › Undo while armed dispatches no event at all, and on the stage it leaves a nudge in place; ⌘Z and
     the toolbar's Undo work. Read from the source: Blink runs Undo only when its own undo stack can undo
     (editor_command.cc L1320 EnabledUndo = CanUndo, L1968-1970 CanNotExecuteWhenDisabled, L2123-2127), and when it
     can, its beforeinput goes to the root editable of Blink's newest undo step, not to the focused element
     (L2133-2149, UseUndoStepElementDispatchBeforeInput, stable at 152). So after native typing somewhere (the notes
     field, a text box typed in), the menu's Undo is enabled and lands on that element, which may be neither the
     selection nor the deck. K6's "each also works from the Edit menu with the mouse" therefore needs the Edit menu's
     Undo and Redo to be app actions the focused editor answers, in the shell's menu (src/main/menu.ts), not role
     items; see [parent-impact] in the hand-back.
  2. Playwright's keyboard never reaches Electron's menu: its CDP keys carry no native key code, and a key without one
     is marked skip_if_unhandled (input_handler.cc L1271-1272); with one, devtools builds the NSEvent's characters
     from `text` alone (native_input_event_builder_mac.mm), so the key matches no menu item unless `text` is set too.
     No e2e case has exercised a menu accelerator by key until this one (e2e/support/ime.ts `Ime.command`).
  3. L5's renderer half: a press on box B while box A composes 하 finishes A's composition as the stage takes the
     focus (compositionend 하 on A), A keeps 하 and B gets a fresh composition. The prototype needed one change for it:
     the text box no longer ends the edit itself on a plain press elsewhere on the stage (that armed A again for a
     moment, writing its selection while the composition was still ending); the stage's new selection ends it. A
     modified press (shift or ⌘, which may keep A selected) and a press on a comment pin still end it from the box.
  4. The e2e deck stage is small: in a 1600 × 1000 window (the presentations specs' size; 1512 × 900 inner) the main
     region is 832 px between the sidebar (300) and the panel (380), and the slide draws 256 × 144 px, a scale of
     0.133, where a 9 px handle covers about 70 slide px and a 64 px heading is 8.5 px tall (measured 2026-10-20 with a
     throwaway spec). B2's pointer cases (P2's caret at character 3, P5's grouped heading, P8's cell drag) need a
     bigger stage: the live harness fills the work area with the sidebar and the panel collapsed (0.49 on the MacBook).
  5. Known gaps of the prototype, for the plan rather than the spike: a press on the armed box begins the edit there,
     so the armed text cannot be dragged (T2 needs the stage to keep the press: the armed root without pointer events,
     the caret placed by posAtCoords on release); arming binds the text, and the binding writes an empty text node into
     an element that has none (ENSURE_ORIGIN): a model write on a selection; a press the stage keeps while a box is
     armed (a handle, a drag of the frame) gives the focus back to the box at its release, which the plan's PRESS and
     DRAG states must keep doing; ⌘B, ⌘I and ⌘U act on the armed box's text
     (all of it in mode select, as Slides does for an object-selected box: a choice for the plan); boards are not
     armable yet (`armable` is the deck's stage only); F9's typed-key path and its Hangul exclusion stay for the
     prototype-off path.
