## 1. The decision rule (fixed 2026-10-19, before any record run)

Tasks and cells. Four tasks, the prompt verbatim in both apps (tasks.json, which both arms read): B1 a one-word fix in
the document's schedule paragraph; B3 a rewrite of its introduction paragraph at about the same length; B5 a date change
on slide 2 of a six-slide deck; B7 a slide added after slide 2 with a title and three bullets. A cell is one task in one
arm on one surface (MAWS; Desktop's Code session or Cowork). A task is judged on one Desktop surface: if Desktop ran it
on more than one, the report needs the judged one named (`parse.py report --judge B5=cowork`, the owner's deck call of
§7) and gives no verdict until it is; the other surfaces are reported beside the verdict. The artifacts are equivalent
seeds in each app's native form (seed/; §4). The only words that differ between the apps' prompts are the artifact's
handle ({ref}): MAWS's `maws-artifact:` link, Desktop's file name or artifact name.

The measure decided on: send to edit landed, per edit, from each app's own engine transcript through the one parser
(parse.py):
- send is the engine's human `user` record (the engine's clock; the host's in both apps), so neither driver's latency
  counts;
- edit landed is the `tool_result` record of the turn's first successful landing call (MAWS: `artifact_edit`,
  `artifact_publish`; Desktop's Code session: `Edit`, `Write`, `MultiEdit` on the artifact's own file, doc.md or
  deck.html; Cowork's deck: the `Artifact` publish, or `update_artifact`, never a local edit before it).

Repetitions. At least five valid repetitions per cell, each a fresh session, the two arms interleaved in the order of
§7 fixed now, the cache state recorded per repetition. A repetition is valid when (parse.py `valid`):
- its records are there (the manifest names a transcript, and every record it names is on disk);
- its timed turn was its session's first (parse.py's `priorTurns`, the human turns before it in its transcript, is 0): a
  prompt that went into an existing session, as when the driver's New fails silently, carries that session's context
  and cache. The rule holds for both arms; a MAWS repetition is always a new session's first turn, and the Desktop
  driver refuses to send into a session that is not new (§6);
- its turn ran in Auto mode: both arms run in Auto, and a repetition whose turn the records show in another mode (the
  human `user` record's `permissionMode`) is invalid;
- no human stopped it: a permission card the Desktop driver had to answer makes it invalid (MAWS's arm already fails a
  repetition that waits on a permission);
- its edit landed, and the checker (check.py, one set of rules for both apps, read from the artifact before and after
  the turn) passed;
- for a Cowork deck, it ran on a seed `before --seed` took (§7a; `seedId` in the manifest), that seed, rebuilt from its
  records, is the bench's (`check.py same seed/maws-deck`), and its timed turn ran in another session than its seed's
  (`freshSession`).
An invalid repetition is listed with its reason, never dropped silently; an attempt made again keeps its own directory
(…-a2, …-a3) and nothing recorded is overwritten. A cell short of five valid repetitions is run again in the same hold,
never judged short.

Reported per cell: the median with the spread (minimum, quartiles, maximum) of send to edit landed, and beside it, per
edit, §4.2's breakdown: requests, input tokens (the context size), first-byte wait, generation time and output tokens,
server hold, tool execution; send to first token; send to turn end.

The verdict, per task, with no middle band: MAWS's median send-to-edit-landed above 1.2 times Desktop's median means
Desktop is faster on that task; otherwise parity. (§4.2; the architect's "about 20 %" made one threshold by Decision
Log 16.2.)

What voids a task's verdict: the model (the request's `model`), the effort (`output_config.effort`, else the record's
`effort`) or the thinking type differing between the arms, where both arms' records carry it (parse.py `VOIDING`). A
control one arm's records lack is not compared, and the report says "<control> not in <arm>'s records" beside the
verdict. Desktop's engine 2.1.299 writes no `api-request` records, so its thinking type is not recorded; the report
gives instead whether thinking ran (a thinking block or thinking tokens in the turn's responses), never a type. Recorded
beside the verdict and not voiding it: the cache state, the route, the load, the engine versions, the requested context
variant, the advisor model and any usage iteration that is not a message (Desktop's records carry `advisorModel:
claude-opus-5-5`, MAWS's none). The route differs by design: MAWS runs through the owner's relay (the gateway route, as
the owner runs it) and Desktop's Code sessions go direct (§3); the relay's first-byte overhead is therefore inside
MAWS's numbers and, if the breakdown names it, it is a cause outside the levers.

The deck cells' Desktop arm, cloud Cowork's Slides (Decision Log 25, §7b), differs from both other surfaces in four ways.
All four are recorded beside the deck verdicts and none of them voids a verdict:
- the host: Anthropic's cloud VM (entrypoint remote_cowork), not the mini, so it shares no load with the MAWS arm, and the
  cloud's load is not recorded;
- the route: the VM calls the API from where it runs;
- the engine: 2.1.305, against 2.1.304 for Desktop's Code sessions and 2.1.305 for MAWS;
- the records: its transcript carries no `api-request` records, so its requests are grouped by request id and its
  first byte is estimated from the transcript, as for engine 2.1.299.

What follows (binding, Decision Logs 10, 16.2 and 17):
- parity on every judged task closes the question and tracker row 296 (its closing line written at A1's landing,
  Decision Log 10's form);
- Desktop faster on a judged task: the breakdown names the cause. A cause among the deferred levers (patch publish for
  decks and designs, the request diet, the context diet; §9) returns as P4-A3, and P4 closes only when MAWS's median is
  within 1.2 times Desktop's on that task, re-measured on this harness. A cause outside them (the relay's first byte,
  the user scope's tool count, a server hold) becomes a tracker row, never A3;
- a kind Desktop lacks altogether: its MAWS components are reported, with no verdict.


## 2. The measurement-only rule

Where Desktop's arm cannot be pinned to the owner's setting (Opus 5.5 at the owner's `effortLevel`, xhigh for
claude-opus-5-5 in ~/.claude/settings.json), MAWS's arm for that cell is pinned to Desktop's actual setting, read from
Desktop's own records for that cell (the transcript's per-record `effort`, Cowork's audit `system/init`, the session's
local_<id>.json), never from what the picker showed. The MAWS repetitions run with MAWS_BENCH_PIN=<model>:<effort>;
their manifests carry `pin` and `measurementOnly: true` and the report marks the cell.

The cell is judged under the same 1.2 times rule at that setting, and its verdict stands as the task's result for the
close criterion, marked measurement-only, since no comparison at the owner's setting exists for that task. No effort
decision follows from it (Decision Log 8): it argues neither for tuning MAWS's effort nor for changing the owner's. (This
reading of "recorded as such" is the executor's; the architect may rule otherwise before the run.)

## 4. The one parser (parse.py), and its validation

What it reads: an engine transcript (both apps), plus where present MAWS's X8 journal (per request `ttft_ms` on
`message_start`, block stops, `message_delta`, `tools/call` to `control_response`), ClaudeUsage's relay log (first
byte, total, upstream gap per request, joined by request id), Cowork's audit (`result.ttft_ms`). It prints aggregates
only. `turns` tabulates a transcript, `edit` measures one repetition from its manifest, `report` builds the per-edit
rows, the cells (medians and spread), the controls and the verdict.

Validated on the sitting's records (read-only; nothing copied): the note session's transcript
(~/.claude/projects/-private-tmp-p3-sitting-project/720e2008-….jsonl, engine 2.1.303, 35 human turns, 192 `api-request`
records), its X8 journal (~/Library/Application Support/MAWS/engine-host/journal/97989a60-…/gstpcfz3.jsonl) and the
relay logs of 2026-10-19 (191 rows joined):
- with the relay it reproduces the grounding's §3.1 table (research/p4-edit-speed/sitting-table.md) turn for turn:
  send to first block, send to edit landed, send to turn end, API calls, first-byte wait, generation, post-tool hold,
  output and thinking tokens, context, to within 0.1 s (rounding);
- the journal alone agrees with the relay: per request first byte within 0.04 to 0.13 s (median 0.07 s, the relay
  sitting upstream of the engine), the turn's hold median 0.00 s (at most 0.64 s), generation median 0.15 s;
- the transcript alone, Desktop's case, gives the decision measure, send to turn end, requests and tokens exactly (no
  difference on any of the 14 edit turns); its first-byte estimate runs high by a median 0.25 s per request (p90
  0.93 s), about 1.4 s per turn, which its generation figure gives back; holds are not separable from it, so Desktop's
  breakdown reports the symmetric tool span (tool_use record to tool_result) where MAWS's splits hold and execution.
On Desktop records: the newest Desktop Code session on disk (2026-10-01, d04310a8-…, entrypoint `claude-desktop`, engine
2.1.284, claude-opus-5-5 at xhigh, Auto mode) parses with no `api-request` records (requests grouped by request id, sent
at the preceding record), its effort, cache state and mode read; it made no edit, so no landing was measured. Desktop's
current engine 2.1.299 writes no `api-request` records (they begin at 2.1.300), which is the path just validated, and
why its thinking type is unrecorded (§1). No Cowork audit exists after July, so the audit path is untested on real
records; the parser takes the session's first `result` written at or after the measured turn's send.

The rule itself is checked on synthesized records (parse_test.py; fixtures/ holds one B1 turn as each engine records
it, with identical timings): five MAWS and five transcript-only Desktop repetitions give parity at a ratio of 1.0, a
control both arms record and that differs still voids, two Desktop surfaces give no verdict until one is named, and a
missing record, another permission mode, a human stop, a failed seed or an edit of another file each exclude the
repetition with the reason.

Learned from the journal while validating: the engine writes `tools/call` to MAWS as soon as the response's end reaches
it and only then the `message_delta` and `message_stop` stream events, so the stream's end is the earlier of the two
(parse.py uses it). And in auto mode every MAWS call waits for the response's end (the server's verdict) before it runs,
so the post-tool hold falls inside MAWS's send-to-edit-landed; a Desktop session in Accept-edits mode runs `Edit` without
that wait. The permission mode is therefore a validity rule (§1): the hold sets Auto on every Desktop session (§7), the
driver checks the control shows it, and the records decide.

## 6. The Desktop arm

desktop-prep.py is the non-GUI half. `before` opens the repetition's attempt (desktop-<task>-r<rep>, a later attempt
…-a2; an attempt laid and never closed by `after` is closed as aborted), lays the pristine doc.md and deck.html in the
arm's folder, removes the folder's .claude/ (where a permission answered "always" would carry over) and prints the exact
prompt. `after --permissions-answered N` finds Desktop's own records for the session (Code: claude-code-sessions/
<account>/<org>/local_<id>.json's `cliSessionId`, then ~/.claude/projects/<slug>/<id>.jsonl; Cowork:
local-agent-mode-sessions/…/audit.jsonl and its private transcript), copies or rebuilds the edited artifact, runs the
checker, writes the manifest (N above 0 is a human stop) and prints the turn's recorded permission mode and whether the
attempt is valid, so the hold knows at once which cell needs another repetition. When `after` cannot close the attempt
(no session found, or a deck it can neither rebuild nor take from bench-after/) it exits and leaves the attempt open, so
`after` can run again once the cause is fixed (a wrong --seed-transcript, bench-after/ still to be written); the reason
is kept in the attempt's pending.json, and an attempt redone instead is closed as aborted with that reason. `deck`
rebuilds a Cowork deck from a session's records for the hold's first read and prints, beside `same`, the deck's url
and the permission mode each of the session's human turns was recorded in; `kinds` is the first read of §3 and prints
the recorded permission mode too (a Cowork audit's system/init, a transcript's human records).

A Cowork deck is rebuilt from the records. The engine's `Artifact` tool publishes local files (2.1.302's schema and
cli.pretty.js `bg()`: `file_path` the page or, on an Artifact made from a type such as the Slides deck, a data file
served at its path relative to `root`, else to the working directory, and refused when it lies outside; `edits`,
old_str/new_str pairs applied to that file on disk and then published; `files` the other files, either a map
{published path: source path | {from, contentType} | null} or a list [{path, contentType}] publishing each file at its
own spelling from that path; `root` the folder relative sources resolve against, which never changes a published
path), so the deck's text lives in the transcript's own `Write`, `Edit` and `MultiEdit` calls, the publish's `edits`,
and the published files `read_file` saves locally. 2.1.302's Slides flow is a quickstart, a `type_url` publish that
creates the deck, the index and slides written under one folder and published to the deck's url with `root`,
`file_path` and `files`; a later edit reads the deck, saves the slide's file with `read_file`, edits it there and
publishes it. The rebuild replays the successful calls in order and computes each published path the engine's way, so
a publish whose `root` serves the slide anywhere but its project/ path adds a stray file rather than editing the slide,
and fails. It follows one deck: a `type_url` publish (a create) starts it from its own files and is allowed only in the
seed's calls; the first publish or read_file naming a url after the seed's last create names the deck's url, and every
later one must name the same Artifact, compared the engine's way (cli.pretty.js `Yt`: by the uuid a url names, so
claude.ai/artifact/<22-character short id, the uuid in base58> and claude.ai/code/artifact/<uuid>, either with a
`<name>-` vanity prefix, are one Artifact, checked against the engine's own functions; a url the engine does not read as
an Artifact's equals only itself). A publish naming no url goes where the engine's frameUrls sends its `file_path`,
which holds one file per Artifact, the last one published to it in the session (each publish drops the Artifact's other
entries, and a create points its `file_path` at the new Artifact even when the call then fails), and is followed only
when that file is the deck's in the same session (otherwise the engine sends it somewhere the records do not show, or
makes a new Artifact). When the seed's records name no url (a create whose url is only in its
result, or no seed records), the timed turn's first url is taken as the deck's and the manifest says so (`deckUrl`,
`deckUrlFrom`). A `read_file` puts the published text under the published path wherever it was saved; every other
action of the engine's list (cli.pretty.js `Qe()`, and its consolidated spellings) leaves the files as they were, save
those that change the artifact in ways the records do not carry (sync, write_db, upload_asset, delete_asset, copy_from,
delete, call_endpoint, a mutating run_script). The seed's calls (`after --seed-transcript T`, T possibly the timed
transcript itself; its calls up to the timed turn's send) give the deck before, checked `same` against seed/maws-deck
and recorded as seedCheck; the timed turn's calls carry it on to the deck after. A file named under another session's
mount of the folder is matched by its trailing path. Anything the rebuild cannot follow (an edit of a file whose text is
not in the records, one of those actions or one not in the list, an edit or a files entry of an unknown shape, a data
file outside its `root`, published files outside the deck's layout, a create in the timed turn, a publish or read_file
to another url or to an unknown one, any unexpected error on the way) fails loudly; for the deck after, the files the
driver's untimed follow-up has the model write to bench-after/ are then the last resort, and the manifest says so
(`afterSource`, with `rebuildError`). The rebuild is tested on synthesized records only (prep_test.py, the 2.1.302
Slides flow among them, and the publishes it must refuse); the hold's first step tries it on real ones.

Dry-run end to end against a fake Desktop store (the Desktop fixture as the session's transcript) through `report`.
desktop-driver.js is the GUI half for `cua_repl`. Its labels were Desktop 2.42304's at first and are 3.1623.0's Korean
UI since Part A read them live (§7b), each Korean label its own pattern (JavaScript's `\b` is ASCII-only, so it never
sits beside Hangul). driver_labels_test.mjs checks them with node against Part A's lines and their near misses, and
`bench.probe()` against the live accessibility tree at a hold's start. After choosing Auto the driver checks that the
permission-mode control shows Auto; a permission card it has to answer is counted in `bench.rep()`'s result, which
step 3 passes on.

Before it sends any prompt, the session on screen must be a new one: in the Code tab the sidebar's selected item is the
new session (항목 새 세션, Value: 1), in the Claude tab the page is claude.ai/new. Otherwise the driver refuses to send,
since a New click that failed silently would put the prompt into an existing session; §1's first-turn rule catches the
same in the records. `bench.rep()` waits the turn out. `bench.send()` returns once Stop appears, with the session's url,
and `bench.reopen(url)` opens that session again from the Claude tab's recent list (its items clicked in turn until the
page's url is the one asked for, the first eight only), so cloud seeds can run side by side (§7a). `bench.handOver()`
(§7a) clicks the transcript's own file card: the last Download button after the line naming the .jsonl file, else the
last one, never an earlier card such as a deck's. These flows are tested against a fake Claude tab in
driver_labels_test.mjs. The recent list's item (`recentItem`) is the one label not read live; the probe reads it first.
