Question. The owner runs 2.1.312 every day; MAWS was verified against 2.1.296 (TESTED_ENGINE_VERSION) and its replay
fixtures were recorded on 2.1.283 to 2.1.299. A lane B session on 2.1.312 raised the notice "Claude Code 2.1.312 is newer
than the version MAWS was verified against (2.1.296); some events were not understood". What does 2.1.312 send in normal
use that MAWS does not understand, what must MAWS understand, and what may it knowingly ignore?

Verdict. The notice came from a coverage gap older than 2.1.296, not from a change in 2.1.312. `system/session_title_changed`
ships since 2.1.284 to 2.1.287 (absent from the 2.1.283 bundle, present in 2.1.287's), and two more normal-use frames
are older still: MAWS's own journals on the owner's machine, replayed through the Normalizer, hold exactly three frames
it did not understand, `session_title_changed` (2.1.294, 2.1.296, 2.1.303, 2.1.309, 2.1.310), `vcs_state_changed`
(2.1.283) and `permission_check_status` (2.1.294, 2.1.303, 2.1.309), and no `invalid_frame`. They were silent before only
because the notice fires on a version newer than tested. Nine `system/*` subtypes a MAWS launch can receive in normal use
had no schema; each is now typed and mapped knowingly (below). Everything else 2.1.312 can write to stdout needs a
condition MAWS's launch never creates, and stays unmapped on purpose, so that a frame from such a path still raises the
notice. The control protocol's semantics are unchanged for MAWS: every engine-to-host request it can receive is one it
already handles.

Method.
  1. The bundle. ~/claude-code-bundle/<v>/cli.pretty.js for 2.1.292 (the nearest extracted build at or below 2.1.296)
     and 2.1.312, read three ways: the SDK protocol schema registry around the published stdout union (the line that
     `describe`s "Everything the CLI writes to its output stream"), every `{ type: "system", subtype: … }` literal the
     code emits, and the paths those literals take to stdout: filter 1 of the headless session (`RC`, 2.1.312
     cli.pretty.js:534845-534965, which passes only status, init, notification, api_retry, model_refusal_*,
     memory_recall, thinking_tokens, compact_boundary, model_fallback, model_consent_fallback and informational of the
     internal system messages), and the SDK event queue (`ea`, cli.pretty.js:149986), which every other emitter writes to
     directly and the headless session drains to stdout unfiltered. Each candidate's emit condition read at its site.
  2. The owner's journals. MAWS's spawn journals on this MacBook (three profiles, 2.1.283 to 2.1.310) replayed through
     the Normalizer by a scratch vitest file that never left the machine: counts and versions only, as above. The O9
     sitting's 2.1.312 journal was removed with its scratch profile.
  3. Live probes on 2.1.312 (scenarios/pass3/p5-e312.mjs and a sweep of the existing scenarios), run on a devcloud VM:
     see "Probe results".

The delta 2.1.292 → 2.1.312 (registry and emit literals). One system subtype added to the registry,
`inherited_asks_settled` (a cloud session's resume reporting the asks it kept; written only on the remote transport),
and three emitted with no schema, `checkpoint_done`, `rewind_stand_in` (an internal transcript stand-in) and
`turn_began_before_init` (all three cloud or internal). Six control subtypes added: five client-to-engine requests MAWS
does not send (`get_cloud_session`, `get_cloud_session_transcript`, `list_cloud_sessions`, `start_shell_task`,
`submit_survey_feedback`) and `ui_prompt_paint`, an engine-to-surface ask sent only to a client that declares it (below).
No stdout type added or removed. Fields: the schemas
of every subtype MAWS already maps (`task_notification`, `session_state_changed`, `hook_response`, `peer_message_hold`,
`api_retry`, `notification`, `permission_denied`, `status`, `compact_boundary`, init) only added optional keys, which
MAWS's loose schemas keep.

What a MAWS launch receives in normal use and now understands (src/shared/wire/frames.ts, src/engine-host/
normalizer-system.ts; the mapping rule: a frame maps to nothing when an existing path already shows its fact promptly,
and to that path when the fact would show late or not at all):
  session_title_changed   {title}: the session's custom name (`/rename`, `rename_session`, a hook's sessionTitle; never
                          the AI title), at startup when the session has one and after every change. None: the same
                          rename appends a `custom-title` record, which C4's title rule reads through the fs watcher's
                          re-summary (50 ms debounce); the probe measures the record's lag behind the frame.
  vcs_state_changed       {kind: commit|push|merge|rebase (open), branch?, cwd}: a foreground Bash command moved the
                          repository. None: C4's git watcher sees the head and refs move.
  code_change_published   {provider, url, repo, identifier, action?, branch?}: a `gh pr` verb, or a push to a PR's
                          branch. To the PR row's Refresh: no ref moves, so the row (polled every 2 minutes, main keeping
                          an answer 60 s) would show a new or merged PR late. The status tracker keeps it as the status's
                          additive `published` {url, action, at} (X6; wire minor 6), and the panel's app-level listener
                          (renderer ipc/events.ts) asks `scm.pr.state` with refresh when its time moves, for a PR state a
                          surface holds. A new X1 event kind would have been a wire major (a union member set changes).
  permission_check_status {tool_use_id, agent_id?, status: checking|done}: an auto-mode permission check has waited about
                          four seconds. None: no MAWS surface shows a pending check (Claude Desktop does; a UX decision).
  per_turn_effort_changed {per_turn_effort_active: false}: per-turn effort went off after a server refusal. None: it
                          carries no effort for the effort chip.
  memory_recall           {mode, memories[{path, scope, content?}]}: auto memory surfaced memories. None: no surface
                          shows a recall.
  dev_intent              {kind, trigger?}: the conversation or the repository shows iOS or Android development (an
                          Xcode project for iOS at the repository root, from the scan every headless session starts).
                          None: no surface offers device tooling. (The engine's SPEC 45 says print mode drops it; the
                          2.1.312 headless session starts the scan, cli.pretty.js:545216-545217, and `ea` bypasses
                          filter 1.)
  model_fallback          {trigger, original_model, fallback_model, content}: the turn moved to the configured fallback
                          model. `notice.posted` warning with the engine's text (turn-scoped).
  model_consent_fallback  {choice, original_model, fallback_model, persisted_as_default?, content}: a pre-send consent
                          gate (the Fable 5 usage-credit gate) moved the session off the requested model.
                          `notice.posted` warning; every later turn's system/init reports the model it runs.

The sleep guard, a change of behaviour, not of the wire, that this bump brings to MAWS's sessions (the bundle reading,
with lines, in live-mini.txt). From 2.1.310 the Bash tool refuses a foreground command whose first part is `sleep N` with
N >= 25 (`sleep 45`, `sleep 45; echo x`, `sleep 25 && x`; not `sleep 24; x`, `echo a; sleep 60`, or any other program),
before any permission check and without running it, for the main thread's calls and every agent's alike, unless the call
runs in the background or the session has background tasks or their completion notices off. The tool's description tells
the model so ("Long leading `sleep` commands are blocked …"), and the refusal points it at Monitor with an until-loop or
run_in_background. Up to 2.1.309 the same code sat behind the GrowthBook flag `tengu_amber_sentinel`, off for MAWS's
sessions (2.1.296, the tested engine before, never refused); 2.1.310's changelog: "long foreground sleeps are now blocked
there too". What MAWS users see: a Bash row that fails at once with the engine's text, `Blocked: sleep 45 followed by:
echo … To wait for a condition, use Monitor with an until-loop … Do not chain shorter sleeps to work around this
block.` (an errored tool result, no permission request), then whatever the model does instead; the refusal steers it
to a background command or a Monitor loop, which MAWS already shows (Background work, the Monitor cell, the task rows).
No frame is new,
so nothing to map; a user who wants the agent to wait in the foreground meets the engine's refusal, as in the terminal.
The live specs that held a turn open with a leading sleep (S5, p1-live S3 case 3, agents-live v to vii) now run a `node`
timer of the same length (e2e/support/p1-live.ts `foregroundJob`).
