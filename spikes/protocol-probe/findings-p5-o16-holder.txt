Question (D-1). What the session host, the adoption and the reap take from the engine, measured on MAWS's own launch
line before M2 and M5 build on it: the six questions of M0.

Method. scenarios/pass3/p5-o16-holder.mjs: MAWS's launch line and initialize (p1-common: ENGINE_FLAGS, the constant
environment, a scratch CLAUDE_CONFIG_DIR, the trust attestation), the engine spawned detached as transport.ts spawns it,
MAWS_LANE=B and SMNS_MEMBER the probe's own pid (the engine's parent), CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 (the owner's
switch), TZ=UTC, a Stop host callback (maws_Stop_1) answered {} and every tool allowed unless a question holds a request.
sminos 1.27.17 installed into each scratch config home from the doperpowers checkout at cc459470f9cc (`claude plugin
marketplace add <checkout>`, `claude plugin install sminos@doperpowers`; a directory marketplace loads the plugin in
place). A `turn.step` fence of the probe's own (a plugin under --plugin-dir, the shape O12 M4's observer will have) reads a
mode file before a turn's first main request and holds 3.0 s, refuses, or passes, logging each step with $.ui.log. The
Messages API is a scripted stand-in over stub-api.mjs's sseOf keyed by content (a prompt's [[O16:<plan>]] marker; a
tool_result continues its plan; a task notification is answered as one), nothing spent. Fixtures fixtures/p5/
p5-o16-holder-<arm>.jsonl on the pin and -<arm>-installed.jsonl on the installed engine, tests in fixtures.test.mjs
("p5 O16", 25 pass). Question 6: p5-o16-relay/ (main.go, D3's Go prototype given M1's hot path; bench.mjs), summary
fixtures/p5/p5-o16-holder-relay.json.
Engines (D22): 2.1.283, the fixture pin (FIXTURE_ENGINE_VERSION), and 2.1.316, the Claude Code the VM installs and mawsd

Arms.
  main              sminos, the fence and two stdio MCP servers (one from --mcp-config, one user-scope in the scratch
                    .claude.json); the trees at rest, during a foreground Bash, a background Bash (sleep 600), a Monitor
                    (tail -f), a subagent's Bash, and after stop_task of each; then four engine-started turns: a task
                    notification with the fence passing (baseline), held 3.0 s, a one-shot cron fire held 3.0 s, and a
                    task notification refused. The mode is written after the prompt's own turn ends, so it applies to
                    the turn the engine starts.
  end-session, sigterm      a background `sleep 300`, then end_session {reason: stop} or SIGTERM to the engine's pid;
  ...-pending               the same with a Bash permission (curl to a closed port) held unanswered. A SessionEnd command
                    hook in the scratch settings and a SessionEnd host callback record the reason.
  reinit            a background `sleep 900`; then one message of three concurrency-safe calls, each kept outstanding:
                    the maws server's `hold` (its tools/call unanswered), a Read of /etc/hostname (its permission
                    unanswered), the maws server's `hooked` (its PreToolUse host callback unanswered); a control_response
                    to an id the engine never sent; a second initialize as an adopter sends it (the same hooks and
                    sdkMcpServers); then the late answers, one kind at a time.
  await-seed, await-resume, plain-resume   a session holding an every-minute session cron, then --resume of it with
                    --await-initialize and without, initialize withheld 75 s, then sent.

The answers (the expected-line form; the pin first, then the installed engine; a difference is named).

   main request: yes (2.1.283: 3,030 ms; 2.1.316: 3,030 ms inside, 3,047 ms from the start). The baseline task turn,
   fence passing, reached its request 23 ms (2.1.283) and 37 ms (2.1.316) after its start. A refusal (the fence yields
   the reason as the turn's text, never calls next) ends the engine-started turn with result "O16 fence refused this
   turn." and no main request, on both. The bridge: 2.1.316 loads sminos's hooks module (events include turn.step) and
   runs its child, `python3 …/sminos.py bridge --session <id> --launch=<id>`, a direct child of claude; 2.1.283 loads no
   sminos module at all: `hooks module sminos@doperpowers failed to load: … bridge.tsx … "session.append" is not an
   event` (sminos at cc459470 hooks an event the pin does not have), while the probe's fence, a separate plugin, loads on

   hold is read from the turn's start to its request.
   (main: q1 notes task-baseline, task-held, cron-held, task-refused; debug_full.)

   takes): claude; `/usr/bin/node <root>/o16-mcp.mjs user` and `… flag`, the two stdio MCP servers, direct children in

   fixture) and, in an earlier recording not kept, a `[2.1.316] <defunct>` zombie. Working tree: each Bash, foreground
   (sleep 6), background (sleep 600), a Monitor's (tail -f, 2.1.316 only: 2.1.283 answers "Monitor is disabled") and a
   subagent's (sleep 8), is `/bin/bash -c source <config>/shell-snapshots/snapshot-bash-….sh … eval …` with its command as
   a child, a direct child of claude that leads a process group and session of its own (pgid = pid, stat s): none of them
   is in claude's group. A subagent adds no process of its own. get_settings's `effective` carries no mcpServers on either

   command, args} exactly as launched, with scope `dynamic` (--mcp-config) or `user`.
   (main: tree notes rest, foreground-bash, background-bash, monitor, subagent, rest-after-stop; get_settings, mcp_status.)

Q5 --await-initialize: accepted (both engines; a hidden option), cron held yes. With it, the resumed session writes
   nothing and calls nothing for the 75 s initialize is withheld, though its every-minute cron was due; initialize is
   answered 1.0 s (2.1.283) | 1.5 s (2.1.316) after it is sent; then the cron fires (2.1.283 at once, 0.16 s after the
   answer, catching up the missed minute; 2.1.316 at the next minute, 27 s later). Without it, the resurrected cron
   fires before any initialize: 1.6 s after spawn and then every minute (2.1.283: three fires and three results while
   initialize was withheld), at the first minute (2.1.316), each a full turn with no host hooks registered (no Stop
   callback). Difference: catch-up of a fire missed while waiting (2.1.283 fires it at once, 2.1.316 does not).
   (await-seed, await-resume, plain-resume: q5_withheld, q5_after_initialize.)

Q6 relay p50/p95 120.5/146.7 µs (gate 500/1500): under the gate. The stamped replay of 2.1.316's own stream (1,081
   lines in 5.0 s, 303 bytes at p50, 17,730 at most, 8 turns of 120 streamed deltas through MAWS's launch line), six
   rounds each way alternating, 6,486 lines each: engine write to manager arrival p50/p95/p99 176.3/255.6/308.3 µs on a
   pipe, 296.8/402.3/471.8 µs through the relay; the hop is their difference, 120.5/146.7/163.6 µs. The live engine under
   the relay: the host's read of a line to its arrival at the manager's socket, 157.6/248.2/348.6 µs (1,081 lines). The
   input direction (not gated): 174.1/192.5 µs added at p50/p95 (2,400 stamped lines every 5 ms). Even the hosted total,
   402 µs at p95, is under the gate's p50 bound; the hop is paid twice per round trip, about 0.24 ms at p50 against OX7's
   1.3 ms headroom. A second run 46 minutes later, the same bench (fixtures/p5/p5-o16-holder-relay-repeat.json): hop
   125.9/158.7/187.5 µs, live segment 182.1/278.1 µs, input 194.6/216.0 µs. The clock: CLOCK_MONOTONIC in every
   process (Node's process.hrtime, Go's runtime.nanotime). The relay is Go 1.25.3, static linux/amd64 (sha256 0a341ede43d2…).

Verdicts for the controller (each question's discard rule in the document):
- Q1: the gate holds an engine-started turn in -p; OX10 stays adoptable. The bridge itself needs an engine past the pin
  (session.append), so O12 M4's observer is tested on 2.1.316, not on the fixture pin.
- Q2: both rungs end -p within 2 s and take the shell with them; the "ignored" branch never arose, so M5's
  term_ignored path is defensive, not observed. end_session exits 1 with a turn running.
- Q3: M3's table holds as written for permissions (redelivered by id), tools/call (kept) and hook callbacks (retired:
  answering {} later is harmless, the engine has already cancelled them and failed the tool with a retry text); a
  snapshot follows re-initialize, so M3's seeding of tasks may also take it. `ambient` is never present, so MAWS's
  `ambient === true` reads false for every task observed.
- Q4: registration by get_settings cannot work: it carries no mcpServers. mcp_status carries each stdio server's command
  and args (the launch's and the user's alike), and is the source to use. Tools' shells are never in claude's group, so
  the tree rule (D17) is the one that sees them. Startup can show transient engine children (an `rg` scan, a zombie).
- Q5: the flag exists on the pin and holds the fire; without it a resumed session runs cron turns before any initialize.
- Q6: under the gate by a factor of four at p50 and ten at p95; M2 may start.

Notes.
- 2.1.316 sends a `role: "system"` message after the last user message in every main request (the budget line); a stub
  keyed on the last message reads nothing there, so this scenario reads the last user message.
- The `rest` tree of 2.1.283 has no sminos child (the module never loaded); its process group and state columns are the
  same as 2.1.316's otherwise.
- Fixtures carry the VM's scratch paths under /tmp and /home/o16probe; no credential was on the VM user, and the harness
  redaction ran on every row.
