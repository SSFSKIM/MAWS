Q1. The SDK MCP round trip (spec §4 S3; SPEC 45 §45.21)
--------------------------------------------------------

Answer: yes. A server named in `initialize.sdkMcpServers` is handshaken by the engine over `mcp_message` (the JSON-RPC
initialize before the initialize answer returns, `notifications/initialized` and `tools/list` after it, so the answer
does not mean "listed and ready"), its tool is in system/init.tools as `mcp__maws__echo_file`, the model calls it, the result
reaches the model as ordinary tool_result content, a client-sent `notifications/tools/list_changed` makes the engine
re-list, and `mcp_set_servers` adds a second SDK server mid-session, with one trap: it is authoritative.

Fixture p1-sdk-mcp-roundtrip.jsonl (session ef3cd43b-fafc-4a6d-b127-70e6c9c22e24; US$0.039, three haiku turns).

1. Registration and handshake. The initialize request (seq 4) is MAWS's payload plus `sdkMcpServers: ["maws"]`. The
   engine drives the MCP handshake as the client, each JSON-RPC message wrapped in a control_request
   `{subtype:"mcp_message", server_name:"maws", message}`; it begins before the initialize answer (seq 7) and finishes
   after it:
   - seq 5: `{jsonrpc:"2.0", id:0, method:"initialize", params:{protocolVersion:"2025-11-25", capabilities:{},
     clientInfo:{name:"claude-code", title:"Claude Code", description, websiteUrl, version:"2.1.290"}}}`. The host answers
     the control request with `{mcp_response: <the JSON-RPC response>}` (seq 6: result protocolVersion 2025-11-25,
     capabilities {tools:{listChanged:true}}, serverInfo). The engine echoes the host's control_response back on stdout
     (seq 9; the known echo, pass 3's integrity rule).
   - seq 7: the initialize answer, with no `sdk_mcp_manifests_parked` (none were sent) and `capabilities:
     ["ui_surface_v1"]`.
   - seq 10: `{jsonrpc:"2.0", method:"notifications/initialized"}` (no id). The host answers as the official SDK does
     (S287 chunk-j0381q8k.js:591107): `{mcp_response:{jsonrpc:"2.0", result:{}, id:0}}` (seq 11).
   - seq 13: `{jsonrpc:"2.0", id:1, method:"tools/list"}`; the host returns the tool list (seq 14; name, description,
     inputSchema).
   The protocol version the engine offers is the one SPEC 45 §45.21.3 names (`Ide`, 2025-11-25). The engine sent no
   `sdkMcpServerManifests`-related frame and parked nothing; the control-channel handshake is the path for a host that

   destination:"localSettings"}], tool_use_id}`; the probe allowed it (seq 65). Then the engine sends the call (seq 71):
   `{jsonrpc:"2.0", id:2, method:"tools/call", params:{name:"echo_file", arguments:{path:"probe.txt"},
   _meta:{"claudecode/toolUseId":"toolu_01EThq…", progressToken:2}}}`; the host answers (seq 72)
   `{mcp_response:{jsonrpc:"2.0", id:2, result:{content:[{type:"text", text:"MCP_ECHO_7731\n"}]}}}`; the model sees the
   tool_result user frame (seq 74): `content:[{type:"text", text:"MCP_ECHO_7731\n"}]`, `tool_use_result` the same array,

What MAWS must implement (E1). Declare `sdkMcpServers: ["maws"]` in the initialize request and answer every
`control_request/mcp_message` for `server_name === "maws"` with `{mcp_response}` before and after the initialize answer
(the handshake interleaves with it); answer a notification with `{jsonrpc:"2.0", result:{}, id:0}`; serve initialize

unknown methods with a JSON-RPC error. A JSON-RPC request from the engine has no timeout (SPEC 45 §45.21.1), so a blocking

through `params._meta["claudecode/toolUseId"]`. Treat can_use_tool for `mcp__maws__*` as any MCP permission
(`mcp_server.source === "sdk"` identifies ours). To add a tool at runtime send `notifications/tools/list_changed`
client→CLI and expect a tools/list; to add a server mid-session send `mcp_set_servers` with the complete SDK server map
(every server MAWS hosts), not the delta. Expect the model to ToolSearch our tools first: each tool's description must
carry the words the model will search for (the fallback text of D-12 belongs in the description, which is what
ToolSearch indexes). The normaliser must map `control_request/mcp_message` (today `frame.unknown`, allowlisted in the
conformance suite until E1 maps it).

Open points. The timeout on a notification or response frame from the engine is 70 s (SPEC 45 §45.21.1); the probe
answered within milliseconds, so the expiry path is unrecorded. A tools/call error (JSON-RPC `error` or `isError:
true`) was not exercised. Whether a server MAWS removes with `mcp_set_servers` leaves its tools callable until the next
turn was not exercised (the removal here was immediately undone). The re-handshake of an already registered server on an
authoritative set is a cost E1 should keep in mind (two handshakes per set).


Q2. `fork_conversation` against the `--fork-session` launch (spec §4 S4, §3 C; SPEC 45 control table, SPEC 36 §10.6)
----------------------------------------------------------------------------------------------------------------------

Answer: no. On 2.1.290 under MAWS's launch `fork_conversation` never forks: every well-typed request is answered in a
success envelope with `{forked:false, error:"unsupported", reason:"unsupported"}`, no child session starts and no new
transcript appears. The engine's own fork requires a Remote Control bridge or an `--sdk-url` hosted session and, even
there, spawns a background process. `--fork-session` (C10's path) remains the one fork MAWS has; it is a new launch, it
copies the history under the new id, and its JSONL carries no lineage field.

Fixture p1-fork-start.jsonl (session 3719bfe4-7393-4e3e-8ce1-9ee74b9431a7, pinned X; US$0.029) and
p1-fork-session-flag.jsonl (session bfdf4123-a931-4896-abd3-1f99c542f54e, pinned Y, `--resume X --fork-session
--session-id Y`; US$0.031).

1. Shapes on the wire. After one turn ("Remember the word ZEBRA", result seq 28), four requests:
   - seq 29 `{subtype:"fork_conversation", title:"MAWS E0a fork"}` → seq 32 success `{forked:false, error:"unsupported",
     reason:"unsupported"}`.
   - seq 33 `{…, target_message_uuid:"b1277739-…" (the prompt's uuid), title}` → seq 34 the same answer.
   - seq 35 `{…, title:5}` → seq 36 error envelope `"fork_conversation: title must be a string"` (type validation runs
     before the capability check; `target_message_uuid` is validated the same way, SPEC 36 §10.6).
   - seq 37 `{subtype:"fork_conversation"}` → seq 38 the same unsupported answer.
   The project directory held the same two entries before and after (seq 40: `X.jsonl`, `memory`), and the only system
   frame in the window was the idle `session_state_changed` (seq 31). The same request on the forked session answers the
   same (p1-fork-session-flag seq 31 → 34).
   SPEC 45's table gives the success shape `forked`, `sessionId`, `targetMessageUuid?`, `prefillText?` when true and
   `error` when false; the wire adds `reason`. S287's headless handler (cli.pretty.js:995571 → `Qv`, :991992-992005)
   returns unsupported unless `--sdk-url` resolves a fork target and the first-party provider and egress checks pass; the
   REPL-bridge stub of SPEC 36 §10.6 answers `reason:"requires_remote_control_server"`, which the headless path does not
   use (the wire says `"unsupported"`, as pass 2 recorded on 2.1.283). The implementation behind a supported fork
   (cli.pretty.js:514725-514810, `bZe`) creates a cloud session, uploads the history and calls `spawnBackgroundFork(…,
   "remote_fork", …)`: a new process, not an in-process child.

2. The `--fork-session` launch, for comparison. system/init.session_id is the pin Y (seq 11); the fork recalls ZEBRA
   (seq 27, note 28). After exit, `Y.jsonl` holds 33 records (seq 39, `fork_jsonl`; seq 40 `jsonl_snapshot` has them in
   full): session-level records first (`ai-title`, `mode`, `atis-latch`, `file-history-snapshot`, two
   `queue-operation`), then the parent's history re-written under `sessionId: Y` with the parent's record uuids and
   parentUuid chain intact (15 of the child's uuids are the parent's; the first user record's `parentUuid` is null), then
   the fork's own turn. No record of the child carries `forkedFrom`, `forkedFromSessionId` or `parentSessionId`; the
   parent's file is unchanged (size and mtime). This matches SPEC 35 §35.16.6 ("no bulk copy of the parent file and no
   pointer record"; the loaded messages are re-written as the new session proceeds) and §35's producer table:
   `forkedFrom` has exactly one producer, the `/branch` command.

3. Which can start a side thread "at the current point" with the parent's context. Neither in-process. `--fork-session`
   does: a new process resumed from the parent's transcript as it stands on disk, with the parent's cwd and
   permissions (C10), then its own turns; it takes the parent's history up to the last record written, which is "the
   current point" once the parent's turn has flushed. A fork taken while the parent is mid-turn gets the history up to
   the last flushed record (unverified here; W7 recorded the engine's branch-on-collision behaviour). The engine's
   `fork_conversation` would not serve MAWS even if it were supported: it forks into a cloud-hosted background session.

What MAWS must implement (E3). Side threads use C10's `--fork-session` launch (spec A-4 resolves to the flag). Lineage
must come from the launch intent, persisted by MAWS (X11's `lineage` from `intent.ts`), because the disk carries no
parent pointer.

[parent-impact] X11 says lineage is "filled from the launch intent and, on the disk path, from the JSONL's `forkedFrom`
with `kind: 'fork'`", and §8 says `session.started.forked` comes from `forkedFrom` on the disk path
(src/engine-host/fs/backfill.ts:95). On 2.1.290 a `--fork-session` child writes no `forkedFrom`; only a `/branch` fork
does. The disk path can detect a fork only by the parent's uuids reappearing under another sessionId in the same project
directory (15 shared uuids here), or not at all. X11's disk-path clause should be re-worded to that or dropped; the
launch intent is the one reliable source. E3's gate G5 ("MAWS reads its lineage from the record, and from the JSONL's
`forkedFrom` when the record is absent") has the same problem: for a `--fork-session` side thread the fallback can
never fire, so the gate cannot pass as written and needs the same re-wording (the shared-uuid match, or no disk
fallback).

Open points. `fork_conversation` under a `--sdk-url` hosted session was not probed (MAWS does not launch one). The
`forkedFrom`-bearing `/branch` fork is a terminal command MAWS does not issue.


Q3. `side_question`, the `/btw` path (spec §3 C, §4 S4; SPEC 45 §45.22.11, SPEC 11 §11.9.2 and §11.11.6)
---------------------------------------------------------------------------------------------------------

Answer: yes. `{subtype:"side_question", question, history?}` answers `{response, synthetic}` whole, not streamed, after
one `system/control_request_progress {status:"started"}`; it runs beside a turn without blocking it (answered while a
20 s Bash tool was running); and it leaves no record in the session JSONL.

Fixture p1-side-question-session.jsonl (session 9aa9686c-27a8-44cc-a068-58c1fe15f3ac; US$0.035 as the results count
it).

1. Idle. After the planting turn (result seq 86), seq 88 `{subtype:"side_question", question:"What word did I ask
   you to remember? Answer with just the word."}` → seq 91 `{type:"system", subtype:"control_request_progress",
   request_id, status:"started", uuid, session_id}` → seq 92 success `{response:"ZEBRA", synthetic:false}`, 1.6 s. The
   frames between request and answer (seqs 89 to 91) are the previous prompt's `command_lifecycle completed`, the idle
   `session_state_changed` and the progress frame: no assistant frame, no stream_event, no result. The answer arrives
   whole in the control_response. The question was answered from the shared conversation (the word planted by the main
   turn), as SPEC 11 §11.11.6 describes (the side question's prompt is the conversation plus the §11.9.2 reminder).
2. `history`. seq 95 `{…, question:"Repeat that word in lowercase letters, nothing else.", history:[{question,
   response}]}` → seq 97 `{response:"zebra", synthetic:false}`: the bridge's documented shape (an array of {question,
   response} strings, cli.pretty.js:139355) is accepted by the headless handler too, which destructures `{question,
   history}` without validating (cli.pretty.js:996573). The `/btw` thread history is the host's to keep and resend; the
   engine keeps none across requests.
3. Mid-turn. A prompt asking for `sleep 20; echo SLEPT_OK` (seq 99); the assistant's Bash tool_use (seq 123) ran with
   no can_use_tool (sleep and echo pass the engine's safe-command analysis, SPEC 25). 1.5 s later, seq 128 side_question
   → seq 129 progress → seq 130 `{response:"ZEBRA", synthetic:false}` (2.7 s), then the Bash tool_result (seq 133,
   `SLEPT_OK`, about 20 s after the tool_use), the assistant's text (seq 143) and the turn's result (seq 147, success,
   num_turns 2). The side question answered 3 frames before the tool result and the main turn finished unaffected: the
   answer is concurrent, not queued behind the turn. SPEC 45 §45.22.11's other outcomes, "Session is shutting down" and
   "Side question cancelled" (error envelopes), and the `api_retry` progress status (§45.14.4) were not provoked.
4. Records. The session JSONL (seq 156; 46 records) holds no record of any of the three side questions: no text of
   theirs, no `querySource` or `forkOrigin` key on any record (both sets are `[null]`), as SPEC 11 §11.11.6 says
   (`skipTranscript: true`, `skipCacheWrite: true`). `forkOrigin: "btw"` is the terminal's `/btw`-as-fork path
   (`spawnForkFromDirective(…, "btw")`), not the control request's; `querySource: "side_question"` is in-memory only.
   The answer shape carries `synthetic` (true when the engine substituted the text: a model that tried to call a tool,
   an API error, a cut-off; §11.11.6 step 4) and may carry `refusal_fallback {original_model, fallback_model, content}`
   (the SDK wrapper, cli.pretty.js:591405-591406); `response` is null when there was no answer.

What MAWS must implement (E3). `/btw` sends `side_question {question, history}` with the pane's own exchange history;
the pane draws the answer when the control_response arrives (no deltas to render; a spinner from the `started` progress
frame), shows `synthetic` answers as the engine's notices, and keeps the main transcript untouched (there is no row to
draw from the JSONL and none should be synthesised there). The typed schema in src/shared/wire/control.ts is wrong:
`SideQuestionResponseSchema` expects `{text}`; the wire is `{response: string|null, synthetic?: boolean,
refusal_fallback?: {original_model, fallback_model, content}}`, and `SideQuestionRequest` should gain `history?:
{question, response}[]`. Until E3 corrects it, the conformance suite lists the three side_question requests of this
fixture as expected `invalid_response` failures. Map `system/control_request_progress` (allowlisted as unknown today).
Promoting a side question to a side thread (§3 C) means a `--fork-session` launch plus a first prompt carrying the
side exchange; nothing in the engine links the two.

Open points. Whether a side question's tokens count in the main result's `total_cost_usd` (the result's total rose
from 0.0198 after the planting turn to 0.0346 after the Bash turn; the two idle side questions in between are not
separable in that figure). The 600 s client timeout the engine's own bridge applies to side questions
(cli.pretty.js:468261) is not a wire fact; the host chooses its own. Cancellation (`control_cancel_request` for the
request_id) was not exercised.


Q4. An AskUserQuestion preview-format declaration (spec §9 E0a; SPEC 21 §12.4 "Preview section")
---------------------------------------------------------------------------------------------------

Answer: no declaration exists in the handshake or in any control request; the one client knob is the environment
variable CLAUDE_CODE_QUESTION_PREVIEW_FORMAT (`markdown` or `html`) at launch, and under MAWS's launch (an `sdk-*`
entrypoint) no format is in effect unless the variable reaches the engine. MAWS does not set it today, but
buildEnvironment passes through every `CLAUDE_`-prefixed variable of the owner's captured login shell
(src/engine-host/launch.ts, ALLOWED_PREFIXES), so an owner who exports it gets that format; the probe's emptied
environment could not show this. Setting `html` makes the engine validate every preview before the permission request
and tells the model what a preview is.

Where the format lives in the engine. 2.1.287 (cli.pretty.js:868048-868052): at startup, `CLAUDE_CODE_QUESTION_PREVIEW_FORMAT`
is honoured when it is exactly `markdown` or `html`; otherwise the format defaults to `markdown` for client types other
than `sdk-*`, `claude-desktop`, `local-agent`, `remote` and the vscode case, and is left unset for those. The setter
(`replaceQuestionPreviewFormat`, :375779, called through `Wsr`, :377744) has no other caller: no initialize field, no
control request. The TypeScript SDK's `askUserQuestion.previewFormat` option is exactly this variable
