QUESTIONS (spec §4.10 U2) AND VERDICTS

1. Does --append-system-prompt reach a new session, a resumed one and a fork, and survive compaction; is the off state
   honoured at the next launch?
   VERDICT: the flag reaches a session only when the engine renders its system prompt live. 2.1.295 records each
   rendered system prompt in the transcript as an `attachment` of type `prompt_snapshot` (the appended text its last
   segment, `attachment.systemPrompt[11]` here), written at the launch's first turn, and a later launch reuses the last
   snapshot after the last compact boundary instead of rendering (2.1.292's `cl`/`Swe`/`DB`: the recorded systemPrompt
   replaces the live one). Hence:
   - a new session: the appended prompt is in effect (S13, run 2's new);
   - a resume or a fork with a different prompt: the earlier prompt stays, the new flag is ignored (S1 → N1; S5 → N5);
   - a resume of a session recorded without a prompt, now passed one: not in effect (S2 → NONE);
   - a resume with no flag after one with a prompt: the earlier prompt stays in effect (S3 → N3): the off state is NOT
     honoured by omission;
   - compaction: the next turn after the boundary renders live and records a new snapshot, so the prompt of the launch
     that turn runs in takes effect (S4 → Y4; run 2's compaction word known after /compact);
   - `--system-prompt-snapshot off` (declared by the binary as `--system-prompt-snapshot <on|off>`): that launch renders
     live, so its own prompt, or its absence, is in effect (S12 → R12 replacing N12; S8 → X8 for a session recorded
     without one; S7 → NONE, the off state honoured; S11 → F11 for a fork); it records no snapshot (S6: a plain resume
     after it reverts to N6), and a compaction under it records nothing either (S10: the next plain launch rendered live
     and recorded what that launch passed). A fork under the flag answered NONE once (S9) and F11 on the retry (S11);
     read as a model miss, not an engine rule.
   The engine never appended twice: each snapshot has one appended segment, the current launch's or the recorded one.
2. Which transport of MAWS_NATIVE_TO_HUMAN does the function-hook worker's `$.env.get` see?
   VERDICT: both. `--settings` JSON `env` (MAWS's `extraSettings.env` seam) → `MAWS_U2_WORKER MAWS_NATIVE_TO_HUMAN=1`
   (run 2 new, style); the constructed process environment alone → `=1` (run 2 resume); neither → `<unset>` (run 2 off,

   value is per launch (no snapshot), so set or omitted, it takes effect at the next launch. (2.1.292's `env.get` reads
   process.env; settings env, the flag's included, is applied to process.env at startup.)
3. The last resort: what does a session.attach hook see? `MAWS_U2_ATTACH surface=desktop clientId=maws-main
   keys=clientId,surface,viewport` (run 2 new, after MAWS's ui_attach). Not needed (verdict 2).

WHAT THIS CHANGES FOR P2-C (the execution document's Design §2 carries the rule; spec §4.5 assumed a per-launch append)

- MAWS passes `--append-system-prompt <contract>` on every MAWS-owned launch whose desired state carries the contract
  (it takes effect whenever the prompt renders: a new session, after a compaction, or under the flag below), and never
  on others.
- Before a resume or a fork, MAWS reads the session's (or the parent's) last prompt_snapshot after its last compact
  boundary and classifies it: unrecorded, the MAWS contract n (a segment starting with its header line; run 6 S14), or
  none. An output style is never in the snapshot (verdict 6), so the snapshot only ever carries MAWS's own appended text.
  When the recorded state differs from the desired one (the lane turned on for a session recorded without the contract,
  turned off for one recorded with it, a compatible style now selected for one recorded with it, or a contract version
  change), the launch also passes `--system-prompt-snapshot off`; it does so on each launch while they differ, which
  ends at the session's next compaction (the next plain launch then records the desired prompt).
- The variable travels in `extraSettings.env` (verdict 2); the constructed environment and the client id stay unused.
- The cost of the flag is the snapshot's purpose (a stable system prompt across resumes, for the prompt cache): a launch
  under it re-renders the prompt and may miss the cache. MAWS passes it only while the recorded state differs.
- The flag is undocumented in the CLI's help: MAWS passes it only when the resolved binary declares it (the literal
  `--system-prompt-snapshot <on|off>` in the binary, read once per binary), else the change waits for a compaction and
  says so.

# Messages to the human (MAWS to-human contract 1)

The human who runs this session reads a report of it, not the transcript. Your prose, your tool calls and their results stay in the session as your working record, which they open only when they go looking. Only what you mark reaches them, so anything you want them to read, your answers included, goes inside a mark:

- `<to-human>…</to-human>`: a message delivered to them, wherever you write it, written as you would write to someone away from the screen.
- `<essential>…</essential>`: what they must not miss. It stays in front of them until they mark it read.
- `<need-input>…</need-input>`: a question you can wait on while you go on with other work, one question per mark, the question on the mark's first line. Its options, when it has any, go inside the mark under the question, one `<choice>…</choice>` line each, with `<choice recommended>…</choice>` on the one you would pick. Their answer arrives later as their next message, beginning `Answering "<the question's first line>":`. Input you cannot continue without is not a mark: ask for it with AskUserQuestion.
- `<insight>…</insight>`: before and after you write code, a brief explanation of two or three implementation choices specific to this codebase. It is shown beside your messages.

For example, a question with two options:

<need-input>Which backend should the board use?
<choice recommended>Postgres: already running for the board</choice>
<choice>SQLite: one file, no daemon</choice>
</need-input>

Write marks as plain text in your reply, never inside code blocks or inline code, where they are shown as code. Say what you mean directly and literally, without metaphor or flourish.
