UX wave U8, Probes and checks 1: what engine 2.1.322 reports when the agent changes folder (l5-code-14, UC-4)
(docs/doperpowers/specs/2026-11-12-ux-wave/U8-card-column-working-folder.md, "Probes and checks", first entry; the
contract UC-4 in docs/doperpowers/specs/2026-11-12-ux-wave-design.md; 2026-11-12)

Question. When the agent changes folder, which signal says so, promptly and reliably, on each route: the wire (a
session MAWS runs), the transcript file (all three routes), a CwdChanged hook callback, MAWS's own index? The six
outcomes the spec names decide l5-code-14's second landing.

Verdict, in the spec's terms.
  Outcome 1 occurred: the transcript's rows show the main loop's folder promptly after every kind of move. The first
  row written after the move (the tool's own result row) carries the new `cwd`, for EnterWorktree, ExitWorktree, a
  shell `cd` into a second worktree made with `git worktree add`, and a `cd` into a subfolder; the same in the
  terminal session. The one move the rows do not show is a `cd` outside the launch folder, and that is because the
  engine undoes it at once ("Shell cwd was reset to <launch folder>"), so the rows are right. l5-code-14 can be built
  as written, a shell's `cd` included, reading the newest main-loop row's `cwd`.
  With one correction the item needs: the rows' `gitBranch` is not re-read after a shell `cd`. In the second worktree
  (git: pz-beta) every row still says `master`, the launch checkout's branch, until the session ends; only EnterWorktree
  and ExitWorktree update it. The spec already reads the card's branch from git at the working folder, which is right;
  but its sentence "The record's branch label and the card agree, because both now come from where the agent is" does
  not hold as long as the record's branch comes from the newest row (`upsertFromSummary`): after a `cd` the record
  would keep `master`. The branch must come from git at the working folder for the record too, or the two disagree.
  Outcome 3 did not occur as stated: a CwdChanged callback registered at initialize is never called on its own. It is
  called (with old_cwd and new_cwd) only when a CwdChanged hook is also configured in settings, because the engine
  checks the settings' and the main thread's hooks before firing and does not count SDK callbacks; and CwdChanged
  never fires for EnterWorktree or ExitWorktree, only for a shell `cd`. Recorded, not used, as the spec says.
  Outcome 4 occurred: the index already moves the record on a `relocated` row. EnterWorktree writes `relocated` and
  `worktree-state` rows and the index's next summary re-files the record to the worktree (directory, worktree path and
  branch); ExitWorktree writes them back and the record returns. A shell `cd` writes no `relocated` row, so the record
  stays on the launch folder. So, as the outcome says, once the working folder exists the launch folder must stop
  moving on EnterWorktree, and a test pins it.
  Outcome 5 did not occur: no subagent's move appears in the main transcript. A subagent cannot call EnterWorktree (the
  tool refuses), and a subagent launched with isolation "worktree" writes its rows, with its worktree as `cwd`, to its
  own file under `<session>/subagents/`, `isSidechain: true`; the main file has no sidechain row at all.
  Outcomes 2 and 6: not the case (1 holds).
  Confidence: high for the sequence run (headless once, terminal once, plus three controls); each move was made once
  per route, so a move that sometimes fails to write its row would not have been seen.

Things the spec does not say, observed.
  - The transcript file moves. On EnterWorktree the session file is moved to the worktree's own project folder
    (`projects/<slug of the worktree path>/<id>.jsonl`, the whole history with it); on ExitWorktree it moves back. The
    old folder is left empty. A reader that follows the file by path (the engine host's follower, the index's
    discovery) sees the session's file vanish and reappear under another slug at every EnterWorktree/ExitWorktree; the
    index handled it (same engine id, same record), but the follower's behaviour was not tested here.
  - `relocated` rows are also re-stamped with the file's own project folder at other times (headless rows 140, 183,
    213, terminal rows 137, 173, 207: `relocatedCwd` the launch folder while the main loop was in pz-beta/sub). So
    `relocated` names where the file lives, not where the agent is; it must not be read as the working folder.
  - Each turn's `system/init` frame carries the main loop's cwd at the turn's start (it is repeated every turn under
    MAWS's launch), so a session MAWS runs has a wire signal too, one turn late at worst.
  - A resumed session goes back to the worktree EnterWorktree left it in (resumed from the launch folder or from the
    worktree: init cwd the worktree), but not to a folder a shell `cd` left it in (init cwd the launch folder, and the
    rows with it). The rows are right in both cases.
  - `vcs_state_changed` was never sent: none of the moves is a push, merge or rebase, the kinds it reports.
  - EnterWorktree's result (wire `tool_use_result`, file `toolUseResult`): {worktreePath, worktreeBranch, message};
    ExitWorktree's: {action, originalCwd, worktreePath, worktreeBranch, restoredCwd, originalCwdMissing, message}. The
    spec cites the first's two fields; confirmed.

Inference, for the second landing.
  - Signal: the newest main-loop row's `cwd` (isSidechain false; rows without `cwd` skipped) is prompt and correct for
    every move on both routes recorded; it is what l5-code-14 asks. A session MAWS runs also has each turn's init
    `cwd`. Neither `relocated` nor CwdChanged can replace it (the first names the file's folder and misses `cd`s; the
    second misses the worktree tool and needs a settings hook).
  - Branch: read it with git at the working folder; the row's gitBranch is stale after a `cd`. The record's branch
    (today from the newest row) needs the same change or it disagrees with the card.
  - The record moves on EnterWorktree today (outcome 4); after the second landing that move and the working folder
    would say the same thing for the worktree tool, but for a `cd` only the working folder moves. Pin the launch
    folder, as the outcome says.
  - Subagents need no filtering in the main file (none of their rows is there), but a reader of `subagents/` must not
    take an isolated agent's cwd for the session's.
  - The worktree a `cd` reaches outside the launch folder is never reached (the engine resets it); UC-4's bound "a
    registered worktree of the launch repository" is then about worktrees under the launch folder (or added
    directories, not tried).

Not tried. Added directories (`--add-dir`) and a `cd` into one; a worktree of another repository; a session on another
machine (its own machine follows the same file); ExitWorktree with action remove; the engine host's follower across the
file's move; repeated runs of each move.
