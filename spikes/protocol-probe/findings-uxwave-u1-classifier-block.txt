UX wave U1: a classifier block on MAWS's own wire, engine 2.1.322
(docs/doperpowers/specs/2026-11-12-ux-wave/U1-requests.md, "Probes and checks", "Probe: a classifier block on MAWS's
own wire", serving l4-approvals-12 "Approve a call that auto mode blocked, from its row"; root
docs/doperpowers/specs/2026-11-12-ux-wave-design.md; recorded 2026-11-12)

The owner's question: when the auto-mode classifier denies a call, can a person approve it from that row and have it
run? On this engine and route: yes, by the route l4-approvals-12 chose. The call itself is over when the row appears,
but the grant sentence sent as an ordinary user message got the model's retry through the classifier 5 times out of 5
under a soft_deny rule. Under a hard_deny rule it never did (3/3), and nothing on the wire or in the transcript file
tells a hard block from a soft one.

Verdict per question, in the spec's terms.
1. A block looks as the spec expects, on the wire and in the file (14/14 blocks): no can_use_tool; a `system`
   `permission_denied` frame (tool name, tool_use_id, decision_reason_type "classifier", decision_reason, message; no
   input); the call's error tool result whose frame carries tool_result_meta `non_execution_kind: "automode-blocked"`
   with permission_decision {decision "reject", source "config", reason_type "classifier"}; an entry in the turn
   result's permission_denials, with the input; and in the session's transcript file the tool-result row's
   `toolDenialKind: "automode-blocked"`. So the row's derivation needs no correction, and the file reader can map
   `toolDenialKind` (the spec's first branch), not the result text.
   One difference from the spec's reading: through the gateway the reason is always the engine's stand-in, "The
   server-side auto mode classifier judged this action dangerous (it gave no explanation)" (14/14), never the rule or
   an explanation. The row's "· reason" will carry that sentence every time.
2. The grant sentence gets the retry through every time under soft_deny (5/5, five distinct marker commands, one fresh
   session each): "through every time: build the sentence alone, as written". Under hard_deny the model retried each
   time and the retry was blocked again (3/3): "if it never passes, the row of such a block offers no button" applies,
   but the row cannot know which rule blocked it (the frames of a hard and a soft block are identical, the message text
   byte for byte; the file row carries the same toolDenialKind). See "Where the engine differs".
3. Not run: question 2 was reliable, which is the spec's condition for skipping it.
4. Yes, with a correction to the count: the third consecutive block in a turn is not sent as a block at all; the
   engine turns it into an ordinary permission request (can_use_tool) with `decision_reason_type: "classifier"` and
   decision_reason "3 consecutive actions were blocked. Please review the transcript before continuing.\n\nLatest
   blocked action: The server-side auto mode classifier judged this action dangerous (it gave no explanation)" (2/2).
   Allowing it runs the call. The next block in the same turn asks again ("4 consecutive actions were blocked ..."):
   the person's allow did not reset the count (2/2). So: "nothing to build, the prompt is an ordinary one, and its card
   shows the engine's reason", and the row before it is the second block, not the third.

case per process (`-e UXW_CASE=<case> -e UXW_RUN=<n>`), each launched by spikes/protocol-probe/vm-run.sh on the devcloud
VM dc-uxprobe-dc94 (Linux), never on the MacBook. Engine 2.1.322 (system/init claude_code_version "2.1.322"), node
v26.13.1. Model sonnet, resolved to claude-sonnet-5-5 (no owner aliases on the VM, VM.md); auto mode held

through the forward at 127.0.0.1:8641 (spawn row `routed: true`), the feature cache seeded. No direct-route result

Where the engine differs from the spec's reading of the source.
1. The classifier's reason through the gateway is never an explanation: every block reads "The server-side auto mode
   classifier judged this action dangerous (it gave no explanation)" (14/14). Today's row "Auto mode blocked: `cmd` ·
   reason" would always end in that sentence.
2. "After three blocks in a row ... the engine stops blocking and asks": the ask replaces the third block (two rows are
   blocked, the third call is a prompt), and once in that state each further block in the turn asks too, even after
   the person allowed one.
3. A hard_deny block cannot be told from a soft_deny one by MAWS: the wire and the file carry no list name. The spec's
   "the row of such a block offers no button" cannot be applied per row from what the engine sends; the button shows on
   both, and on a hard block the retry is blocked again (the row then offers the button again, and after the second
   block in a row the engine asks, per 2).

Bearing on other parts of the spec.
- The file reader's half of the routes table: the transcript row carries toolDenialKind "automode-blocked", so a
  terminal session's or a remote session's blocked row can read the same as a live one by mapping that field
  (src/engine-host/fs/backfill.ts sets no denial kind today).
- MAWS's live reader already reads tool_result_meta[].non_execution_kind (src/engine-host/normalizer.ts, around line
  397), which is where the wire carries it.
- The ask after two blocks arrives as an ordinary permission request with permission_suggestions; U1's permission card
  shows it, with the engine's reason text above.
