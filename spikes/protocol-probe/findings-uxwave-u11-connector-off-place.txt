UX wave, child U11a, P2: where does engine 2.1.322 record a connector switched off over the control protocol, and
which new sessions start with it off? (docs/doperpowers/plans/2026-11-12-ux-wave-U11a-settings-connectors-org.md on
ux-wave/U11a: P2 in "Probes and checks", §C "<place>", point 5; 2026-11-12, VM dc-uxwave2-e584, branch
ux-wave/probe3-u11)

Question. The Connectors dialog will say "Off here is off for every session in <place>", <place> being the project's
name, else the session's folder. Which key of `projects` in .claude.json holds `disabledMcpServers` after
`mcp_toggle {enabled: false}` from a session in a repository's root, in a linked worktree, and in a subfolder of the
repository; and does a NEW session in each other folder start with the server off?

Verdict. The document's first outcome: "the repository's root for both", so §C's <place> stands for the project.
  - From the root, from a linked worktree beside the repository, from a linked worktree inside it
    (<root>/.claude/worktrees/<name>, where MAWS's own go) and from a subfolder of the repository, the engine writes
    `disabledMcpServers` under the key of the repository's MAIN root, and only there. No worktree or subfolder key is
    ever created (not even for trust). A new session in any of the four folders then starts with the server off,
    whichever folder switched it off: 16 of 16 (origin, folder) pairs, two runs each, identical.
  - Outside any repository the key is the session's own folder, exactly: a subfolder is a place of its own. Off in
    <plain> leaves <plain>/sub on, and off in <plain>/sub leaves <plain> on (both directions seen).
  What the sentence would get wrong: its fallback, "else the session's folder". For a session with no project whose
  folder is a linked worktree or a repository's subfolder, that names a narrower place than the engine's (the switch
  reaches every session in the repository, its root, every subfolder and every worktree). The fallback is right only
  outside a repository. The project's name is right exactly when MAWS's project for the session is the repository
  whose main root holds the key (`git rev-parse --git-common-dir`'s parent); this probe did not check how MAWS
  derives a session's project (intentProjectName), which is the architect's to confirm.

Method.
  Engine 2.1.322 (/opt/maws-probe/engines/2.1.322 under vm-run.sh, spikes/protocol-probe/VM.md; vm-check.mjs's claims
  re-checked on this VM before the first run: version, routed, the four builtin plugins only, no MCP server, Monitor,
  the control CLAUDE.md alone), route: the gateway through the loopback forward, but no model is called: no prompt is
  sent in any session. Scratch config home ($HOME/.claude under /tmp/p3u-*, no CLAUDE_CONFIG_DIR, as MAWS launches).
  Scenario scenarios/pass3/uxwave-u11-connector-place.mjs. Every session is MAWS's launch (uxwave-common-arrivals.mjs
  mawsLaunch: src/engine-host/launch.ts's flags, setting sources user,project,local, no --strict-mcp-config, MAWS's
  environment and its initialize, which accepts trust for the session's folder). `mcp_toggle {serverName, enabled}`
  is the request src/engine-host/ipc.ts:645 sends.
  Folders: <root> (the scratch repository), <worktree> (`git worktree add`, beside it), <root>/.claude/worktrees/
  p3u-nested (a second linked worktree inside the repository), <root>/sub; and, in the second run, <scratch>/plain
  (no repository) and <scratch>/plain/sub. Both worktrees' `git rev-parse --git-common-dir` is <root>/.git.
  Servers: two invented stdio servers (a 20-line JSON-RPC stub written to the scratch root), `p3u-user` in the
  top-level `mcpServers` of the scratch .claude.json (user scope) and `p3u-project` in the repository's committed
  .mcp.json (so both worktrees' checkouts have it), approved by `enableAllProjectMcpServers` in the user settings
  file. Only p3u-user loads in the plain folders.
  Per origin folder O, with .claude.json restored to its baseline first: a session in O polls mcp_status until both
  servers leave `pending`, sends mcp_toggle off for each, reads mcp_status again, ends; the `projects` keys are read;
  then one new session in each folder (O included) reads mcp_status at start.
  Run 1 is committed; run 2 (--out to /tmp) gave the same statuses and keys in every case (compared field by field).

Cases (fixtures/uxwave/; the record u11-connector-place.ndjson and u11-connector-place-plain.ndjson, one case a line).
  Each `<origin>-toggle` journal: mcp_status at seq 25 both `connected`; mcp_toggle answered `success` at seq 27
  (p3u-user) and 29 (p3u-project); mcp_status at seq 31 both `disabled`.
  origin        key holding disabledMcpServers       new session starts with both servers off in
  root          <root>                               root, worktree, nested, sub   u11-connector-place-root-*.jsonl
  worktree      <root>                               root, worktree, nested, sub   …-worktree-*.jsonl
  nested        <root>                               root, worktree, nested, sub   …-nested-*.jsonl
  sub           <root>                               root, worktree, nested, sub   …-sub-*.jsonl
  (each `<origin>-then-<folder>` journal's first mcp_status after settling, seq 22 or 23: `disabled` for both)
  The plain run (u11-connector-place-plain-*.jsonl; toggle mcp_status at 23 `connected`, toggle `success` at 25 for
  p3u-user, `error` at 27 for p3u-project, which is not loaded there; mcp_status at 29 `disabled`):
  plain         <scratch>/plain                      plain only; plainsub `connected` (seq 23), root and sub
                                                     `connected` (25)
  plainsub      <scratch>/plain/sub                  plainsub only; plain `connected` (23), root and sub `connected` (25)

Beside the question.
  - Read, not seen: the engine computes the key once per process (cli.pretty.js ~1323295, Axe(): the canonical git
    root of the start folder, else the folder itself, cached), so a later `set_cwd` would not move where a session's
    switch is written.
  - Seen: a server from the repository's .mcp.json is switched off exactly as a user-scope one, through
    `disabledMcpServers` under the root's key; mcp_toggle does not use `disabledMcpjsonServers`.
