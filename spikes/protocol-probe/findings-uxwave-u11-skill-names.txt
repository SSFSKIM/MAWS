Question. "Use in chat" will insert `/<name> ` for a person's and a project's skill and `/<plugin>:<name> ` for a
plugin's, <name> being what Customize lists and <plugin> the installed plugin's key up to its `@`. Customize lists
the inventory's `name` (src/engine-host/customization/inventory.ts:154, `words.name ?? basename(path)`: the front
matter's `name`, else the folder's name; CustomizeView.tsx:194 shows `skill.name`) and a plugin skill's `plugin` is the
key of installed_plugins.json (inventory.ts:195). Does the engine run the skill when that form is a message's first
token, per group and per variant (front-matter name equal to the folder's, and different)?

Verdict. Person: confirmed. Project: confirmed. Plugin: confirmed when the plugin's manifest `name` equals its
marketplace entry's name (the key's part before `@`); NOT confirmed when they differ.
  - Person and project, both variants: the inserted form runs the skill. With a front-matter name that differs from
    the folder's, the front-matter name runs it AND the folder's name runs it; the engine's replay of the command
    names the folder either way (`<command-name>/p3u-person-dir</command-name>` for `/p3u-person-label now`).
  - Plugin, manifest name = entry name, both variants: `/<key before @>:<front-matter name>` runs the skill (and the
    folder's name runs it too, as above).
  - Plugin whose manifest `name` (`p3u-manifest`) differs from its marketplace entry (`p3u-entry`, key
    `p3u-entry@p3u-market`): the engine names the plugin by the MANIFEST, `p3u-manifest:p3u-mani-skill`. The inserted
    `/p3u-entry:p3u-mani-skill now` runs nothing: no command replay, no skill body, and the text reaches the model as
    an ordinary message (it answered that no such command is installed), with no error on the wire. 2 of 2 runs.
    `/p3u-manifest:p3u-mani-skill` and the bare `/p3u-mani-skill` run it.
  So the plugin group keeps "Use in chat" only if <plugin> is the plugin's manifest name (`.claude-plugin/plugin.json`
  `name` under the row's installPath, which the inventory already reads at inventory.ts:205-206), not the key up to
  `@`; or the form is checked against the engine's list once the chat starts. Which is the architect's call. The key
  rule alone fails silently for any plugin whose marketplace names it differently from its manifest.

The engine's lists do not agree on which name they show (lists journal u11-skill-names-lists.jsonl):
  - the initialize answer's `commands` (seq 6), what MAWS's composer reads: the FRONT-MATTER name, plugin skills as
    `<manifest name>:<front-matter name>` (`p3u-person-label`, `p3u-plugin:p3u-plug-label`, `p3u-manifest:p3u-mani-skill`);
  - `system/init` `skills` and `slash_commands` (seq 28): the FOLDER's name (`p3u-person-dir`, `p3u-plugin:p3u-plug-dir`);
    `plugins` names the second plugin `p3u-manifest`;
  - get_skills_dialog (seq 39): `name` the folder's, `display_name` the front matter's; plugin skills carry
    `handles.aliases` with the bare name (`p3u-plug-label`, `p3u-mani-skill`), which is why the bare form runs.

Beside the question.
  - A slash form the engine does not know is not refused: it goes to the model as text, which answers in its own words
    (result subtype `success`, no tool used). A wrong inserted form therefore fails without any error MAWS could show.
  - A person's or project's skill with a front-matter name different from its folder shows in the transcript (and so
    in MAWS's transcript row) under the folder's name, not the name Customize listed.
  - The bare form of a plugin skill runs it (get_skills_dialog's alias), but would collide with a person's or project's
    skill of that name; not tried.
