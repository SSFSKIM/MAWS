UX wave, child U11, l8-settings-11: does engine 2.1.322 take its default model and permission mode from the user
settings file, under MAWS's launch and in a terminal, and does it rewrite that file by itself?
(the draft of the spec's U11 section as it stood then, kept outside the repository; the section is `docs/doperpowers/specs/2026-11-12-ux-wave/U11-settings-connectors-org.md`: l8-settings-11 and its "Probes and checks";
2026-11-12/13, VM dc-uxwave2-e584, branch ux-wave/probe2-text-defaults)

Question. With `model` and `permissions.defaultMode` in `<config home>/settings.json` and no flag: what `system/init`
reports in a session driven as MAWS drives one, and what a terminal session uses; what `--model` and
`--permission-mode` do over the file; what a project's file does over it; what the engine does with a value it does
not know; whether the engine rewrites the file at start (the draft: a model's name to a newer one); and the bytes of
the file after a settings change made through the engine (the draft: two-space JSON with a final newline).

Verdict. The spec's first outcome, "as stated, the item stands", with three corrections the design should take.
  - Both keys are taken from the user file on both routes, aliases and full ids alike; a flag beats the file; a
    project's `.claude/settings.json` beats the user's for both keys. Nothing the catalogue would write is refused.
  - Correction 1, a bad value: a `permissions.defaultMode` the engine does not know makes it skip the WHOLE user file,
    so its `model` is lost too (MAWS's route: silently, the default model and `default` mode, the error only in
    `get_settings.errors`; the terminal: a blocking "Settings Error" dialog, "Files with errors are skipped entirely,
    not just the invalid settings."). An unknown `model` is not validated at all: it is reported verbatim and fails
    at the first request. The writer's allow-list of four modes keeps MAWS from writing the first; a hand-edited
    file can still hold it, and the draft's reader already answers null per key, which is not what the engine does.
  - Correction 2, the engine's own write: after `/model haiku` in a terminal ("Set model to Haiku 5.5 and saved as
    your default for new sessions") the file is two-space JSON with a final newline, as the draft says, every key
    and value kept, but the keys are reordered: the engine's known keys first in its own order (`env`,
    `permissions`, `model`, `effortLevel` here), then unknown keys in their old order. So "byte for byte the form the
    engine writes" holds for the layout, not for key order: a writer that keeps each key's place matches the engine
    only on a file the engine last saved, and only when the edited key already exists.
  - Correction 3, the rewrite at start: the rewrite that fired is not the one the draft cites. `claude-opus-4-1` was
    rewritten to `opus` at start (the legacy-Opus migration, cli.pretty.js ~564222, run once per migrationVersion),
    and the session then ran claude-opus-5-5. The cited one (`claude-fable-5-1` to `fable`, :1090885-1090903) did
    not fire on this route; the value was used as is. A hand-laid file with current values was not touched at start,
    with the migrations re-armed or not. MAWS's in-chat model change (`set_model`) does not write the file.

Seen beyond the question (observed; inferences marked):
  - Plan mode with the alias `haiku` runs on Sonnet: with `haiku` (flag or a project file) and plan mode, init and
    the banner name claude-haiku-5-5 but every turn's assistant rows are claude-sonnet-5-5 (maws-mode-plan,
    maws-mode-project, term-project; 3 of 3). With the full id `claude-haiku-5-5` in plan mode the turn stayed on
    haiku (term-id-plan). The engine's "haiku plan upgrade" (cli.pretty.js:1332658, `e === "opusplan" || e ===
    "haiku"`). A "Your default" mark and a chip that name the file's model are right about the setting and wrong
    about what a plan-mode turn runs on when the setting is the alias.
  - With no mode in the file the terminal starts in auto, MAWS's route (no flag) in `default`. MAWS passes the mode
    as a flag, so its chats are unaffected; the draft's "no value in the file means Auto" is the terminal's reading
    on this setup (vm-run.sh marks the auto-mode notices seen, as on the owner's Macs).
  - The default model on this route with no setting is claude-opus-5-5 on both routes.
