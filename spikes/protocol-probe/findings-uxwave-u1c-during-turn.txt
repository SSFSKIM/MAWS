Question. In one turn the model runs the marker command and then a 30 s foreground wait. Once the block is seen, the
grant is written as a `user` frame of priority 'next' (MAWS's steer while a turn runs). Is the retry run, three of
three, and when is the grant read? Added: the grant and an ordinary message ("Also say the word EXTRA when done.")
both written as next-step messages, in either order; and two grants for two blocked commands of the same turn,
waiting together. Is each blocked call retried and allowed, and how does the engine write the joined message?

Verdict. Honoured every time: 27 of 27 runs, every blocked command retried once and allowed by the classifier
(tool_result_meta permission_decision {accept, config, classifier}; the marker file written). The document's default
for Reported 3 holds: the press sends as Enter does, a steer while a turn runs; `when: 'after'` is not needed, and a
terminal session's button need not close during a turn (probe T agrees).
When it is read. A next-step message is taken at the first tool boundary after it is queued: the engine adds it
after the next tool result, in the same turn, and the model retries in that turn. A grant written the instant the
block's permission_denied frame arrives is queued about 30 ms after the block's own tool result was handed back, so
it is not taken there: it waits for the next call's result (here the 30 s wait: read 33 s after it was written in b-1..3, 27 s in b-wait-1..3).
So the "waiting" state of the document's Design 4 lasts until the call running after the block ends, whatever its
length. If no tool boundary remains (the turn ends in a written reply), the messages wait to the turn's end and start
the next turn, and the retry runs there.
Joined messages (the addition), two forms:
  - Mid-turn (a tool boundary left): NOT joined. Each next-step message becomes its own `queued_command` attachment row
    in the transcript (origin {kind: "human"}, commandMode "prompt", source_uuid = its frame's uuid), in the order
    written, and its own text block in the next request, each wrapped "The user sent a new message while you were
    working:\n<text>\n\nThis is how Claude Code surfaces messages ..."; on the wire each is replayed with its own uuid
    and its own text (isReplay true). 9/9 (grant first 3, other first 3, two grants 3).
  - At the turn's end (no tool boundary left; the messages written while the turn's last reply streams): JOINED. The
    engine dequeues both and starts one turn with one `user` row in the transcript whose text is the two messages'
    texts joined by a single "\n", in the order written, and whose uuid is the SECOND frame's uuid; its origin
    {kind: "human"}, promptSource "sdk". On the wire it replays the first frame's uuid with the first text alone, then
    the second frame's uuid with the joined text. Both command_lifecycle `started` frames come together. 9/9 (grant
    first 3, other first 3, two grants 3). Every joined grant was honoured: the model retried the command (both
    commands, for two grants) and the classifier allowed each.
  The engine's plural sentence ("these exact commands, each as one whole string: ...", cli.pretty.js `Yn` with more
  than one call) was never written or suggested in any recording of this probe or of T, C, D, E: no row of the
  engine's and no model text holds "these exact commands", "these exact calls" or "each as one whole string".

What bears on the design (inference).
  - A joined row's text is not a grant whole, so a reader that matches the text whole (arrival.ts `consentOf`) reads
    no consent from the transcript file's row in the end-of-turn form, though the engine honoured it: the blocked row
    would not read approved from the file, and the button would return after the settle time (Design 3). On the live
    wire the second replay carries the joined text under the grant's or the other message's uuid, depending on the
    order. Which rows the normaliser marks from the frame MAWS wrote was not checked here (no product code was run).
  - The mid-turn form leaves one row per grant, matching the reader; two grants in one turn give two rows.

  Inference: on this date the server classifier lets a soft_deny rule yield to the person's own request in the
  prompt (the engine's own guidance for its rules says soft_deny is "by stated intent at runtime",
  cli.pretty.js:365738), and a soft block arises when the call is the agent's own step. The recordings
  u1-soft-seeded-1..5 stay valid as recordings; a new owner sitting that wants a soft block (Proofs an executor cannot
  run, 6) should make the command the agent's own step rather than ask for it by name.
