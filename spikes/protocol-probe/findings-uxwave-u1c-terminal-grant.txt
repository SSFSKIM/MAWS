UX wave U1c, probe T: the grant sentence of "Approve and retry" delivered to a terminal session through the sminos
bridge, as MAWS's terminal route sends it, on engine 2.1.322
(docs/doperpowers/plans/2026-11-15-ux-wave-U1c-approve-and-retry.md on ux-wave/U1c, "Probes asked for" T, which serves
"Reported to the architect" 2 and the gate of M2; 2026-11-15, VM dc-uxwave5-26dc, branch ux-wave/U1c-probes)

Question. After a marker command is blocked by auto mode's classifier in an interactive session, the grant sentence is
delivered through the bridge as `laneA.send` delivers any message: (a) with the session idle, (b) 5 s into a 30 s
foreground call of a later turn, (c) after an Esc during such a call. Does the engine run the blocked command again,
three of three in each state? What rows carry the block, the delivered grant, the mirror line and the retry, and how
does the classifier decide the retry?

Verdict. Yes, in every state: 9 of 9 (idle 3/3, during a turn 3/3, after an Esc 3/3). Each time the model ran the
exact command again, the classifier allowed it (the retry's result row has permissionDecision {decision: "accept",
source: "config", reasonType: "classifier"}, no toolDenialKind), and the command ran (its marker file written). No
permission prompt was raised. The document's default for Reported 2 holds: the button is offered on a terminal
session, in all three states; nothing closes the gate for a state, and M2 stands.
The classifier's framing of a plugin row as `non-user` (cli.pretty.js `j9`, Reported 2) did not stop it: a grant
delivered as the plugin's row of origin {kind: "plugin", name: "sminos"}, with or without asUser, was taken as the
person's consent every time. (The observation; why the server-side classifier accepts it is not visible here.)

The rows, as the document's Reported 1 reads them (confirmed, with one detail added):
  - idle: one `user` row, content a string, origin {kind: "plugin", name: "sminos", asUser: true}, promptSource
    "system", no isMeta. It is the prompt of a new turn. No mirror line.
  - during a turn: one `user` row, isMeta true, content one text block, origin {kind: "plugin", name: "sminos"} (no
    asUser); then a `system` row, subtype informational, level notice, content "sminos: delivered: <the text>" (the
    mirror line). The model reads it at the next tool boundary: the request after the wait's result carries the tool
    result and then the grant's text as a plain text block (the api-request-blob row). The grant is not wrapped as
    the engine wraps a person's mid-turn message ("The user sent a new message while you were working: ...").
  - after an Esc: the interrupted call's result row (toolDenialKind "user-rejected", "User rejected tool use") and the
    "[Request interrupted by user for tool use]" row come first; then the same isMeta row of the plugin's origin and
    its mirror line; then two queue-operation rows and the bridge's wake: a `user` row, isMeta true, promptSource
    "system", origin {kind: "peer", from: "unknown", name: "sminos bridge", verifiedPeerPid, verifiedPeerProcStart,
    body: "[sminos bridge]\nA message for you was added to the conversation after your turn was stopped. ..."},
    content the engine's cross-session wrapper. The next request carries, in order, the rejected call's result, the
    interruption line, the grant, and the wake.
  The bridge marks none of these rows with the delivery's key; the row is found by the uuid of the stream's
  `delivered` `entered` event. No row in any state says whose words they are beyond the origin above.

Method. Engine 2.1.322 (the pinned copy, `--version` 2.1.322), model haiku (claude-haiku-5-5), gateway route through
vm-run.sh's loopback forward, the feature cache seeded, no managed settings (vm-run.sh without --managed). The engine
is interactive in tmux (160 x 48) in vm-run.sh's scratch work folder, started by the scenario inside the same
namespace as uxwave-u8d-terminal.mjs starts it: `claude --model haiku --session-id <uuid> --plugin-dir
/var/lib/devcloud/marketplaces/doperpowers/sminos --debug-file <scratch>/engine-debug.log`, with
CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1. sminos 1.47.0, the VM marketplace copy's own install (nothing installed by the
probe); `sminos project init --name uxw` in the work folder first. The plugin's state is the scratch HOME's; before
each run the scenario checks the containment of uxwave-u3-sminos.mjs (HOME under /tmp, no SMINOS_HOME, DAEMON_HOME,
AGORA_HOME, SMINOS_RL10, MAWS_USER_DATA, XDG_CONFIG_HOME, MAWS_HOLDER_SOCKET; the owner's sminos state and mawsd
endpoint not visible; no enrolment; no managed settings). Auto mode: the footer read "auto mode on" in every run.
The rule, in the scratch user settings: {"autoMode": {"soft_deny": ["$defaults", "Probe Marker: running any shell
command that contains the string maws-probe-marker (a test marker on this machine)."]}} (U1's rule). The marker
command is U1's `curl -s -o marker-<n>.txt "https://example.com/?maws-probe-marker-<n>"`. It reaches the model as the

The send is the scenario posting as src/services/lane-a/driver.ts and deliveries.ts post a `laneA.send` (the terminal

Inference.
  - For M2: the three row forms the document's §C reads are the forms the bridge writes for a grant, in every state,
    and the model acts on each. A grant delivered during a turn waits in the transcript as the isMeta row until the
    running call's result; the model's retry follows that result, in the same turn (busy) or in the turn the wake
    starts (esc). So the "waiting" state of Design 4 lasts until the running call ends: up to 22 s here, and as long
    as the running call takes in general.
  - The terminal route's grant reads as consent without being framed as the person's mid-turn message; nothing in
    these runs asks for the grant to be sent another way on this route.
  - The retry is a new call with a new tool_use id; its row carries no mark that it was a retry or that a grant
    allowed it (permissionDecision is the classifier's ordinary accept).

Not run. The terminal route on another machine (the same bridge rows, mapped in this window: M2's reader, not the
engine, decides it). A grant during a turn whose running call outlasts the bridge's 10 s answer: not needed, the post
answers at once (`submitted`) and the fate `entered` follows within 190 ms in every run.
