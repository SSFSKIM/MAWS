UX wave, child U3, probe 4: a command's output and a compaction that fails, on engine 2.1.322
(docs/doperpowers/specs/2026-11-12-ux-wave/U3-transcript-rows.md, "Probes and checks" 4; it serves O-18 with #330, the
failure rule of #331, and the `command` class of UC-2 in docs/doperpowers/specs/2026-11-12-ux-wave-design.md;
2026-11-12, VM dc-uxprobe-dc94, branch ux-wave/probe-arrivals)

Question. Which commands' output arrives as the assistant frame with `local_command_source`, whether any still arrives
as a `user` frame, how an error's text arrives, what `local_command_outcome` holds, and what the engine sends when
`/compact` fails (`compact_result`, `compact_error`, the command's own error). And, for the reader's other two routes,
what a terminal session's transcript file writes for the same commands.

Verdict. The reader must take three forms, not two, and #331's rule holds as written.
  1. Every command tried except a successful `/compact` sends its output as the assistant frame of model `<synthetic>`
     with `local_command_source` (the output inside `<local-command-stdout>` or `<local-command-stderr>`) and, for a
     command the person typed, `local_command_run {command, args}`. `local_command_outcome` was seen once, `{kind:
     "failed"}`, on `/compact` with nothing to compact; it is absent on every other output, an error included.
  2. A successful `/compact` still sends its output ("Compacted ") as a `user` frame holding `<local-command-stdout>`
     (isReplay true, no origin). It is on the wire with and without `--replay-user-messages`.
  3. In a terminal session's file the same output is either a `system` row of subtype `local_command` or a `user` row
     holding `<local-command-stdout>`, depending on the command, and the command itself is either a `user` row holding
     `<command-name>` or a `system` row `local_command` whose content is that `<command-name>` block. The content keeps
     the terminal's ANSI escapes.
  A failed compaction says so on the status frame that ends it: `status: null, compact_result: "failed",
  compact_error: "API Error: Request was aborted."`, followed by the command's output "Compaction canceled.". So a line
  drawn while `status` is `compacting` and removed at the next status goes on failure as on success; the spec's
  outcome "#331's rule is confirmed" applies, and `compact_result` is there if a check is wanted.
  Two things the spec does not expect, both of which bear on #330 ("an output under the wrong command"): on the wire a
  command's output arrives BEFORE the replay of the command's own `<command-name>` frame; and after a compaction that
  preserves a segment, the engine sends that segment's last command output again, with the same uuid, between the
  summary and the new "Compacted" (3 of 3 runs).

Inference, in the spec's terms.
  - O-18's reading of the newer form (the assistant frame with local_command_source) covers every output but a
    successful /compact's; the reader also needs the `user` frame or row holding <local-command-stdout> on the live
    wire, as UC-2's table already lists for the file. "The assistant frame becomes a user.message of origin
    local-command, never an assistant block" stands, and the `user` form needs the same treatment.
  - `local_command_outcome` cannot be the test of an error: the /model error came as stdout with no outcome. Text in
    <local-command-stderr> is the only reliable mark of an error's colour, and some errors do not carry it.
  - Placement under the command's bubble cannot assume the bubble is already there: on the wire the output comes
    first. The replay of the command follows within the same turn and before its `result`.
  - A command's output that the engine re-sends after a compaction (same uuid) must be dropped by uuid, or it is drawn
    under the /compact that re-sent it: one concrete way for #330's "output under the wrong command".
  - In the file, the command bubble and its output each come in two row types; a reader that takes the bubble from
    `user` rows alone misses /rename's, /context's and /model's, and one that takes the output from `system` rows alone
    misses /effort's and a successful /compact's. Contents carry ANSI escapes from the terminal, which must be stripped
    before the line is drawn.
  - #331: the status frame that ends a compaction always followed its start, on failure as on success (3 runs of each).
    Repeated `compacting` statuses mean the line must be idempotent on the same status. "A compaction that fails
    leaves no line behind" holds with the status alone; `compact_result: "failed"` and `compact_error` are available.
  - The unknown command is the model's prompt on the live wire and a warning row in the terminal: neither is class
    `command`.

Not provoked. A compaction that fails on an API error other than an abort, and "Not enough messages to compact."
  (the too-few-groups failure of a session with a little history): the session with one exchange compacted
  successfully. /cost in a terminal writes nothing, so its file form is not known.
