UX wave, child U3, probe 2: a scheduled prompt firing, headless and in a terminal session, on engine 2.1.322
(docs/doperpowers/specs/2026-11-12-ux-wave/U3-transcript-rows.md, "Probes and checks" 2; it serves the `schedule` class
of UC-2 in docs/doperpowers/specs/2026-11-12-ux-wave-design.md; 2026-11-12, VM dc-uxprobe-dc94, branch
ux-wave/probe-arrivals)

Question. What the wire and the file carry at a fire. The only earlier fixture (pass3/e7-cron.jsonl, 2.1.291) shows no
`user` frame at a fire; the spec read in the 2.1.322 source that the prompt is stamped with origin `{kind:
'task-notification', subkind: 'scheduled-trigger'}` and that a terminal writes a `system` row `scheduled_task_fire`.

Verdict. Neither outcome the spec names occurred as written; the result is closest to its second outcome ("only the
terminal's system row"), with one live mark the spec does not name.
  - Live wire (a session MAWS runs): no `user` frame carries the prompt, with MAWS's flags (--replay-user-messages
    included). A fire is visible as a `command_lifecycle` frame `{state: "started", wakeup_source: "schedule_wakeup",
    command_uuid: <the prompt row's uuid>}` followed by a `system/init` with no `user_message_uuids` and a `result`
    with NO `origin` key. The prompt's text is not on the wire. 4 of 4 fires.
  - File, headless: a `user` row holding the prompt, isMeta true, promptSource "system", turnOrigin "scheduled",
    wakeupSource "schedule_wakeup", and NO `origin` object (so no subkind). 4 of 4.
  - File, terminal: a `system` row `scheduled_task_fire` ("Running scheduled task (<date time>)", with taskId, cron and
    prompt), then the same meta `user` row, which there also names scheduledTaskId and scheduledFireId (= the system
    row's uuid). No origin object either. 3 of 3.
  So the `schedule` class cannot be read from an origin object on any route (UC-2 rule 1 names it as the mark). It can
  be read from the file's `turnOrigin: "scheduled"` (both kinds of session) and the terminal's `scheduled_task_fire`
  row. On the live route the turn can be told apart by the lifecycle frame's `wakeup_source`, but the prompt cannot be
  drawn from the wire alone.

Inference, in the spec's terms.
  - The spec's first outcome ("a user frame or row with the subkind") does not hold on 2.1.322 for a CronCreate job:
    no row or frame carries `{kind: 'task-notification', subkind: 'scheduled-trigger'}`. The subkind exists in the
    source (cli.pretty.js:367654-367690); which path stamps it was not traced. This job's prompt was queued as a meta
    prompt with `turnOrigin: "scheduled"` and no origin.
  - File and remote routes: read the class from `turnOrigin: "scheduled"` on the meta `user` row (both session kinds),
    and in a terminal session from `scheduled_task_fire` (which also gives the job's id and cron). The row's own
    text is the prompt, so `{class: 'schedule', prompt}` is complete from the file.
  - Live route: as the spec's second outcome says, the prompt is not on the wire, so a session MAWS runs cannot draw
    "Running scheduled task · <prompt>" when it fires. It can tell the turn is a scheduled wakeup from the lifecycle
    frame (wakeup_source "schedule_wakeup"), which is more than "Continued for …" needs; whether `schedule_wakeup` is
    also what a ScheduleWakeup (/loop) tick carries was not probed, so the line could not yet name it a cron job.
    The result frame of such a turn has no `origin`, which a reader keyed on the result's origin (UC-2 pitfall 5)
    must treat as "not the person's".
  - Placement: a job that falls due during a turn waits for it and opens its own turn (1 of 1), so its row is always
    a turn's first row.

Not probed. A durable job (`durable: true`), a one-shot job, a /loop tick (ScheduleWakeup), and a fire in a session
  resumed from disk; a fire with the bare launch.
