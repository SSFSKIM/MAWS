UX wave, child U3, probe 1: what the 2.1.322 wire carries for a task notification, in each of its forms
(docs/doperpowers/specs/2026-11-12-ux-wave/U3-transcript-rows.md, "Probes and checks" 1; it serves O-28, O-34 and the
`task` class of UC-2 in docs/doperpowers/specs/2026-11-12-ux-wave-design.md; 2026-11-12, VM dc-uxprobe-dc94, branch
ux-wave/probe-arrivals)

Question. In a session MAWS runs, does the engine send the `user` frame of origin `task-notification` with the
`<task-notification>` text both when it tells an idle model and when it takes the notification in at a tool boundary of
a running turn? Does it for a monitor's event, a check-in on a quiet command, an MCP task and a resumed agent? Is
`<duration_ms>` there for a command or only for an agent?

Verdict. The frame is there in the opposite cases from the ones the spec's design leans on.
  - Taken in during a running turn (a tool boundary): YES. The engine sends it as a replayed `user` frame (isReplay
    true, origin {kind: "task-notification", producer: "session-task", runId?}) for commands, agents and monitor
    events alike: 10 of 10 (5 notifications in each of two runs).
  - Told to an idle model, in a turn the engine opens: NO, for every form tried (a command that exits 0 or 1, an
    agent, a resumed agent, a monitor's events and its end, the engine's stall notice): 0 of 16 (9 in r1, 7
    in r2). The turn shows only as `system/init` without user_message_uuids and a `result` whose origin is {kind: "task-notification",
    producer: "session-task", runId?}. The file has the `user` row.
  - A notification that arrives while idle but is not given a turn of its own (a task the host stopped with
    stop_task) waits, and is replayed with the next prompt the person sends (2 of 2).
  - All of it depends on `--replay-user-messages`: without MAWS's three product flags not one notification frame
    reaches the wire, busy included (u3-tasks-bare).
  So for the idle case, the spec's outcome "where it is missing for a case, that case's line appears on the live route
  only once the session is read from its file … and O-34's removal does not apply to that case on that route" is the
  branch that applies: to every command and agent the owner leaves running while idle, which is the common case.
  The spec's reason for not drawing from the earlier `system/task_notification` frame, however, no longer holds on
  2.1.322 for commands and monitors: that frame now carries the CLI's own sentence as `summary`, verbatim the
  `<summary>` the model later reads, and a `run_id` equal to the `runId` on the turn's `result` origin and on the
  file row's origin. Its timing differs (it is sent when the task ends, which for a busy session is before the model
  is told). For an agent the same frame's `summary` is the hand-back note, not "Agent … finished"; for a task the host
  stopped it is only the task's description; and a long foreground command sends one too, with no notification to
  the model at all. A design choice is therefore open that the spec closed on a premise now false (see Inference).
  `<duration_ms>` is in agent notifications only (inside `<usage>`, and as usage.duration_ms on the system frame);
  no command notification carries a duration.

Inference, in the spec's terms.
  - O-28's live route as designed ("read from the `user` frame of origin task-notification that the engine sends when
    it tells the model") draws the busy cases and none of the idle ones. By the spec's own rule, the idle cases then
    appear only once the session is read from its file, the acceptance A3 must name the routes, and O-34's removal of
    the error item does not apply on the live route to a failed command or agent the model was told about while idle.
  - The premise behind "MAWS does not write a sentence of its own from the earlier system/task_notification frame
    (which has no sentence)" is false on 2.1.322 for commands and monitors (summary verbatim; 58, 148, 559, 581, 743,
    824). Drawing the idle line from that frame would be the engine's sentence, not MAWS's. The pairing is exact:
    the frame's `run_id` = the `runId` of the `result` origin of the turn that told the model = the file row's
    origin.runId (58/118/line 38; 148/177/line 60; 743/780/line 252). A reader could hold the system frame and draw
    the line when the `result` with that runId arrives (or the replayed `user` frame, busy), which gives the live
    route every command, agent end and monitor end, and lets O-34 apply everywhere. Three traps it must avoid: a
    long foreground command also sends task_started/task_notification (summary = description, output_file ""),
    never told to the model (600, 664, 826): only a notification with a matching told-turn or `user` frame is
    drawn; for agents the system summary is the hand-back note and the CLI's sentence ("Agent \"…\" finished") is
    only in the file; for a host-stopped task the system frame has the description and status "stopped" while the
    model's block says status "killed" with the sentence, and is delivered only with the next prompt.
  - The foreground trap is live in MAWS today, not only in a future reader: src/engine-host/normalizer-system.ts maps
    every system/task_notification that is not an agent's to a `task.notification` event without looking at
    is_backgrounded, and src/services/attention/service.ts derives "Background task failed: <summary>" from any of
    status "failed". A foreground command of three seconds or more that exits non-zero (80, 217 here) therefore raises
    a "Background task failed: <its description>" card today (inferred from the code and these frames; not run in
    MAWS). O-34's removal takes it away with the rest; if any part of the derivation is kept (the spec's fallback for
    a case with no live line), it must keep only notifications whose task_started said is_backgrounded true.
  - One agent's end gives two carriers. Busy, both are replayed at one tool boundary, the hand-back first (origin
    peer, handback true, handbackReportText, senderTaskId = the task id) and the notification second (666/667,
    513/514). Idle, the hand-back is replayed and opens a turn (337, 273), and the notification is written to the
    file with `queueTranscriptOnly: true` (line 114) and gets an empty "turn" (result num_turns 0, no API call: 356,
    331): the model is told once, by the hand-back. When the report is withheld (agent-resume, handback "withheld"),
    the notification is the model's and opens a real turn (500). What ties them: origin.senderTaskId = <task-id> =
    the system frame's task_id; the system frame's handback_report.text = origin.handbackReportText. U3 has to pick
    one line for an agent's end; the hand-back is the carrier the model reads when there is one.
  - Monitor events and the stall notice have no system frame and no runId: on the live wire they are a turn whose
    result origin is task-notification and nothing else, so their line (outcome null) is file-only.
  - `outcome: null` for a block with no <status> is right (monitor events: 226-242; stall notice: 297); the
    backfill's default of `completed` would colour both green (U3's pitfall 1 confirmed).
  - The `<status>` values seen: completed, failed, killed (the host's stop; the system frame says "stopped").
  - A3's "the duration after it when the engine gave one": only agents give one.
  - The hand-back arrives as its own `peer`-origin message (class `subagent`, report) before the task notification,
    and each opens a turn when idle, so one agent's end makes two turns.
  - A replayed notification merged into the person's prompt (idle-stop) arrives before the prompt's own replay; its
    row belongs above that prompt.

Not provoked or not run. The engine's check-in on a quiet command (gate forced; nothing in 150 s). An MCP task: it
  needs a server that speaks MCP's task protocol (2.1.322's client takes `execution.taskSupport` and the sep2663
  task runtime, cli.pretty.js:685075-685093 and 824500-824560); the probe has no such server and none was written.
  A Workflow run and a remote agent. The stalled command's stop while busy.
