UX wave, landing U3b, probe 3: an automatic compaction on engine 2.1.322
(docs/doperpowers/plans/2026-11-15-ux-wave-U3b-transcript-rows-find.md, "Probes" 3; it serves acceptance 10 and "Engine
facts" 9; 2026-11-15, VM dc-uxwave5-26dc, branch ux-wave/U3b-probes)

Question. In a session launched as MAWS launches it, when the context fills and the engine compacts by itself, does the
wire carry `system/status` `compacting` before the boundary and a status that is not `compacting` after it? What does
each status carry, does `compacting` repeat, what does the boundary hold, and how does this differ from a typed
`/compact` (fixtures/uxwave/u3-commands-r1.jsonl)?

Verdict. Yes, as the document's default reads it, in 3 of 3 automatic compactions, and none of them failed. The order
is always the same: `status: "requesting"` for the prompt's request, then `status: "compacting"` (which also carries
`compact_output_chars: 0`), then `{status: null, compact_result: "success"}` 5.7 to 8.0 s later, then the replay of
the prompt that set it off, then `compact_boundary` with `compact_metadata.trigger: "auto"`, then the summary, then the
model's answer to that same prompt, all in one turn. "The next status that is not `compacting`" ends it, as with a
typed /compact. So acceptance 10 stands as written, covering typed and automatic compactions, and no tracker row is
needed. Each compaction sent `compacting` once: none lasted the 30 s after which the engine repeats it, so a repeat
during an automatic compaction was not seen either way. "Engine facts" 9 says "the end sometimes with no
`compact_result`"; that did not occur, since every end carried `compact_result: "success"`. The bundle's ends without
a result belong to a compaction that is skipped or aborted (cli.pretty.js:433215, 439512), and none was provoked here.

Compared with a typed /compact (u3-commands-r1.jsonl seq 150 to 157; its file lines 141 to 145).
  - A typed compaction's `compacting` (seq 150) has no compact_output_chars, and no `requesting` comes before it.
    An automatic one comes after the prompt's `requesting` and carries compact_output_chars: 0.
  - Typed: end status, system/init, then compact_boundary with trigger "manual" and no preserved segment, the summary,
    the user frame "<local-command-stdout>Compacted </local-command-stdout>", the replay of <command-name>/compact,
    and then the result. Automatic: the replay of the person's own prompt comes BETWEEN the end status and the
    boundary, the boundary preserves a segment holding that prompt, and the turn goes on to the model's answer to
    it. There is no command output and no command row, on the wire or in the file.
  - Both end with {status: null, compact_result: "success"}.

Inference, in the document's terms.
  - Default held: "yes, as the bundle reads", for typed and automatic alike. Nothing in the reader has to tell them
    apart. If a line is wanted that names the automatic case, compact_metadata.trigger "auto" (wire) or
    compactMetadata.trigger (file) is the mark, and so is compact_output_chars on the compacting status.
  - The prompt that set off the compaction is replayed after the end status and before the boundary, and the
    boundary's preserved segment keeps it. A view that drops everything above a boundary would lose that prompt.
    It is preserved, and the summary sits before it in the engine's own order (preserved_segment anchor = the
    summary).
  - When the compaction comes: in r2 the turn that took the context from 947,075 to 975,073 did not compact before
    its own request; the next prompt did. In the resumed session the first prompt compacted before its own request
    (pre_tokens 970,887 counts that prompt). So the check reads the last response's usage when the process has one,
    and after a resume it counts the whole history with the new prompt. One run of each, so this is read from
    timing and not confirmed.
  - Not answered here: whether `compacting` repeats every 30 s during an automatic compaction ("Engine facts" 2 is
    recorded for typed ones only), and what a failed or skipped automatic compaction sends.
