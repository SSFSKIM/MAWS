UX wave, landing U3b, probe 2: a slash command the sminos bridge ran, beside the same command typed, engine 2.1.322
(docs/doperpowers/plans/2026-11-15-ux-wave-U3b-transcript-rows-find.md, "Probes" 2; it serves `userRow` in
model/derive.ts, as a follow-on, and "Engine facts" 6; 2026-11-15, VM dc-uxwave5-26dc, branch ux-wave/U3b-probes)

Question. When the bridge runs a slash command in a session (`$.command.run`, the bridge's `command` op), does the
live frame's `local_command_run` or the file row's `commandRun` carry a mark a typed command's does not (the bundle's
schema names `plugin`), and does the command's own row differ?

Verdict. `local_command_run` and `commandRun` carry NO mark: both are {command, args} for the bridge's command as for
the typed one, with no `plugin` key (4 bridge runs and 4 typed, in 2 terminal sessions and 1 headless one). The
`system` row of subtype `local_command` that holds the output is the same field for field. What differs is elsewhere:
  - In a terminal session's file, the command's other rows are the same as well. The bridge's run is preceded by a
    `queue-operation` enqueue and dequeue pair, which a typed one does not have. The isMeta `user` row the command
    leaves for the model (here /rename's "<system-reminder> The user named this session …") carries `origin: {kind:
    "plugin", name: "sminos"}` and `queuePriority: "later"`, where a typed one's has neither.
  - In a headless session (the bridge controlling, no MAWS_LANE), the replayed command frame on the wire (the `user`
    frame holding <command-name>, isReplay true) and the turn's `result` carry `origin: {kind: "plugin", name:
    "sminos"}`, where a typed one's has no origin (replay) and `{kind: "human"}` (result). In the file, the caveat row
    and the <command-name> `user` row carry the same origin. The output (`assistant` <synthetic> with
    `local_command_run` on the wire, the `system` local_command row with `commandRun` in the file) carries none.
  - In a session MAWS runs (MAWS_LANE=B) the bridge refuses the op: {ok: false, error: "MAWS controls this session",
    code: "lane-b"}. A command run by the bridge therefore never reaches a session MAWS drives itself; it arises only
    in the sessions MAWS reads by the file (terminal sessions, lane A).
  So the document's default, "no rule; such a command draws as the person's", holds for the command's output row,
  which is what `userRow` would read. If the follow-on wants the mark, it is the command's `user` rows' `origin`
  (headless file and wire) or, in a terminal's file, only the meta row's origin and the queue-operation pair. The
  output row has none.
  `/cost` and `/context`, the commands the brief names, cannot be run through the bridge on this engine: its route
  table (sminos 1.47.0, routes measured at 2.1.310) refuses `cost` as {code: "unknown-builtin", error: "not a command
  this session knows"} (it is an alias the listing does not name), `usage` as {code: "panel", "opens a panel in the
  terminal; it would hold the session's queue"}, and `context` as {code: "routed", "the desk does this with its own
  control (read usage), not as a command"}. All three are refused within 15 ms with nothing written. `/rename <name>`
  (a `run` route, whose output is "Session renamed to: <name>") stands in for them.

Inference, in the document's terms.
  - "Does a mark exist?": not on `local_command_run`, not on `commandRun`, and not on the output row. The bundle's
    `plugin` field was absent in every run. The default (no rule) applies to `userRow` as it reads the output.
  - The only mark is the origin on the command's `user` rows (headless) or on its meta reminder (terminal), plus the
    queue-operation pair in a terminal file. A follow-on that wants to draw a bridge-run command as a line can key
    on those. In a terminal's file it would have to look past the output row to the meta row after it.
