UX wave, landing U3b, probe 6: "Fork from here" when a typed local command follows the answer, engine 2.1.322
(docs/doperpowers/plans/2026-11-15-ux-wave-U3b-transcript-rows-find.md, "Fork from here" passes the id of what follows
the answer; asked by the architect 2026-11-15 after probe 5; VM dc-uxwave5-26dc, branch ux-wave/U3b-probes)

Verdict. Five points.
  - The rewind takes the id of any `user` row: the caveat (isMeta), the <command-name> row, the next prompt, and
    after a /compact also the summary and the "Compacted" row. It REFUSES the id of a command's output with
    {rewound: false, prefillText: null, precedingAssistantUuid: null, error: "target not found", reason:
    "target_not_found"} (2 of 2: /rename's and /cost's `system` local_command rows, which are the wire's assistant
    <synthetic> frames). It also refuses any message from before a compaction, the first prompt included.
  - Rewinding to what directly follows the first answer works and is clean. That is the command's caveat row, which
    is in the file only; the wire has no frame for it. The fork keeps ONE and its answer and nothing of the command,
    and the answer is the last thing kept. Rewinding to the command's <command-name> row (the uuid the person's
    command was sent with, and the one its wire replay carries) keeps the caveat above it. The fork's context then
    has a caveat that introduces a command which is gone.
  - Control: a rewind to the second prompt (TWO) keeps everything above it, both commands' caveat, command and
    output rows included, between ONE's answer and the fork's new prompt.
  - After a /compact (a short session, no fill): a rewind to the prompt after the compaction keeps the boundary,
    the summary, the caveat, the /compact command and its "Compacted" row, and nothing from before the boundary. A
    rewind to the /compact command's row keeps the boundary, the summary and the caveat. A rewind to the summary
    keeps the boundary alone, so the fork starts with no conversation at all. ONE (before the boundary) is refused,
    target_not_found.
  - `precedingAssistantUuid` is the last REAL assistant message above the target, never a command's output. It was
    ONE's answer for every target in the commands session (TWO included, though the two outputs stand between), and
    null for every target after the compaction.
  So "the id of what follows the answer" is accepted, and it gives the fork the document intends, when that id is
  the next `user` row in the file (here the caveat). If MAWS passes the id of the command frame it saw on the wire
  (the replay of <command-name>), the fork is accepted too but keeps an orphan caveat row. If it passes the output's
  id (the assistant <synthetic> frame), the engine refuses it in the words above.

Inference, in the document's terms.
  - For "Fork from here" under an answer followed by a typed command, the clean fork comes from the next `user` row
    in the file (the caveat). On the live wire that row has no frame. The frames MAWS sees after the answer are the
    output (refused) and then the command's replay (accepted, but it keeps an orphan caveat). A view built from the
    wire that wants the clean cut has to rewind to the command's replay. Taking prefillText then puts the
    <command-name> block in the composer, and the fork has a caveat line in its context. Alternatively it can read
    the caveat's uuid from the file.
  - A rewind onto a command's output always fails ("target not found"). If the document's "what follows the answer"
    can be an output frame (in a session MAWS runs, an output arrives BEFORE the replay of its command: u3-commands
    findings), the code must skip outputs when it picks the id. If it does not, the fork's own tab shows the refusal.
  - precedingAssistantUuid ignores command outputs and is null after a compaction, so it does not identify "the
    answer the fork was asked from".
  - Rewinding to anything at or before a compaction's summary empties or refuses: a fork from an answer above a
    boundary cannot be made by rewind.
