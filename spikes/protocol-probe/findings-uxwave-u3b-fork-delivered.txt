UX wave, landing U3b, probe 5: a fork that rewinds to a prompt that was delivered, not typed, engine 2.1.322
(docs/doperpowers/plans/2026-11-15-ux-wave-U3b-transcript-rows-find.md, "Probes", the premise named after item 4:
"Fork from here" passes the id of the prompt that follows the answer; 2026-11-15, VM dc-uxwave5-26dc, branch
ux-wave/U3b-probes)

Question. When the prompt that follows an answer was delivered into the session and not typed (a message the sminos
bridge delivered into an interactive session; or, on the stream-json wire, a prompt that waited in the queue and was
read as a `queued_command`), does the engine's rewind accept that id, so that the fork starts with the conversation
cut before that prompt, or refuse it, and in which words?

Verdict. It accepts every one (5 of 5 rewinds, each in a fork of its own): the typed control, the queued prompt by
its sent uuid, the queued prompt by its file row's uuid, the bridge-delivered prompt, and a typed control in the
same terminal session. Each answer is {rewound: true, targetMessageUuid, prefillText: the prompt's text,
precedingAssistantUuid}. The fork's next prompt hangs below the point before the target, and the target and
everything after it are gone. No refusal arose, so there are no refusal words to report. The refusal recorded
elsewhere is {rewound: false, error: "target not found", reason: "target_not_found"}, for a target already rewound
(findings-p4-w2a-rewind.txt). The premise holds: no code is needed for a delivered prompt.
Two details the document's reading may want:
  - A queued prompt has no `user` row in the file. Its only row is an `attachment` of type `queued_command` (its own
    uuid, `source_uuid` = the uuid the prompt was sent with). On the wire the engine replays it as a `user` frame
    with the SENT uuid (isReplay true). The rewind takes either id. Given the attachment's uuid, it answers with
    targetMessageUuid = the source_uuid, so the id it reports can differ from the id it was given.
  - A queued prompt arrives mid-turn, so the cut keeps the turn's earlier tool call and result (the fork's chain
    ends at the tool_result row, before the queued_command attachment), and the answer that followed is gone.

Method. Engine 2.1.322, model haiku (claude-haiku-5-5), the gateway route (spikes/protocol-probe/VM.md). Scenario
scenarios/pass3/uxwave-u3b-fork-delivered.mjs. The fork is launched as MAWS launches one (src/engine-host/launch.ts:
`--resume <source> --fork-session --session-id <new>`, with the rest of the launch of uxwave-common-arrivals.mjs) and
rewound as rewindFork (src/services/sessions/setup.ts) asks through src/engine-host/rewind.ts:
`rewind_conversation` {target_message_uuid, last_seen_user_message_uuid: the source's newest non-meta user row,
interrupt_if_running: false}. After an accepted rewind, the fork is sent "Without using any tool, reply with only the
word FORKED.", so that it writes its file; the chain from that prompt's row back to the root is noted
(`uxw_fork_chain`). Each fork runs in the source's scratch HOME (vm-run.sh -e HOME, PROBE_WORK, PROBE_ROOT).

Inference, in the document's terms.
  - The unprobed premise holds for both delivered forms. "If it refuses, the fork's own tab says so in the engine's
    words" does not arise for them.
  - For a queued prompt, the id MAWS holds is the one it sent (the replay frame's uuid), and that id is accepted. A
    reader of the file that takes the queued_command attachment's uuid gets the same result. Neither needs mapping.
  - prefillText is the delivered prompt's full text, the bridge's "[sminos message from … id=…]" header included. A
    fork that puts prefillText in the composer would show that header.
