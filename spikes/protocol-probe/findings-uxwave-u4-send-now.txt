UX wave U4 P1: Send now and the move to the background on engine 2.1.322, on MAWS's own wire
(docs/doperpowers/specs/2026-11-12-ux-wave/U4-composer.md, "Probes and checks", P1, serving "Sending: one design for
l3-input-01 ..." and l3-input-01; root docs/doperpowers/specs/2026-11-12-ux-wave-design.md; recorded 2026-11-12)

Question. What does the engine do, and put on the wire, for (a) `interrupt {send_now: true, message_uuid}` while a
`next` message waits behind a running foreground shell command; (b) the same behind a running Agent call; (c) the same
while the model only writes text; (d) the same while a permission request is pending; (e) `background_tasks
{tool_use_id}` for a running shell command and for a running Agent call, a `next` message waiting; (f) a user frame at
priority `now` during a running shell command; (g) case (a) on the gateway route, where the two feature flags may never
be fetched; (h) a plain interrupt after case (a). For each: the control response, the tool result's text, whether the
command's process survives, the frames that end or continue the turn, the message's lifecycle frames, and what tells a
send-now ending from a Stop.

Verdict, in the spec's terms.
- (a) answers `delivering` and the command is moved and survives, but the message is NOT read in the same turn: the
  engine ends the turn first (`result` subtype success, terminal_reason aborted_tools) and starts the message as the
  next turn. So "Send now is built as written" holds for what the engine does to the command, and the fallback
  (`background_tasks` instead) is not needed; but A3's "the agent answers the message in the same turn" and the table's
  "reads the message in the same turn" are false for a shell command, and the host must recognise this turn end as a
  send-now end (it reads like no Stop on the wire; see "telling the endings apart").
- (b) for a foreground Agent call (run_in_background: false): `delivering`, the call is moved, and the message IS read
  in the same turn (no `result` between). On 2.1.322 Agent calls run in the background by default, so a foreground one
  exists only when the model passes run_in_background: false; with only a background agent running, (b) is (c).
- (c) answers `stopped`; the turn ends (aborted_streaming) and the message runs as the next turn: as written. Nothing on
  the wire tells this ending from a Stop except the control response: the host's own record decides, as the spec's
  fallback says.
- (d) answers `delivering` (not `stopped`): the engine withdraws the permission request (control_cancel_request), the
  call's result is "Tool permission request aborted", the turn ends (success / aborted_tools, the call listed in
  permission_denials) and the message starts the next turn. The table's last column ("the turn ends at the request,
  which is withdrawn ..., and the message starts the next turn") is what happens; Send now need not be disabled there.
  The model then asked for the same call again in the next turn (2/2).
- (e) shell: `background_tasks` answers `{backgrounded: false}` when it arrives before the engine has registered the
  running command as a task (the `system/task_started` frame for that tool_use_id), and `{backgrounded: true}` one
  second later, once registered (3/3 with the retry; 3/3 false without it). Once moved, the tool result reads "Command
  was manually backgrounded by user with ID: ...", the process survives, and the waiting message is read in the same
  turn. Agent: `{backgrounded: true}` at the first try (3/3), the message read in the same turn. So the automatic move
  is built as written, and its retry is load-bearing; it covers shell commands and foreground Agent calls.
- (f) a `now` frame during a running shell command does what send-now does: the command is moved to the background
  ("so that a message that arrived while it was running can reach you"), survives, and the turn ends with success /
  aborted_tools; the message runs as the next turn. Charter §4.2's sentence ("`priority: 'now'` preempts the running
  turn (ended as aborted_streaming)", measured on 2.1.283) no longer holds during a shell command on 2.1.322. Also run
  (beyond the spec's list): `now` behind a foreground Agent call moves it and the message is read in the same turn;
  `now` while the model writes ends the turn with success / aborted_streaming and no interrupt marker.
- (g) no difference: with an empty feature cache every flag-dependent case (a, b, e) behaved exactly as with the seeded
  cache, and the engine wrote no feature cache during the run (nothing was fetched through the gateway). The flags
  (`tengu_velvet_panda`, `tengu_bubbly_meteor`) are true in the owner's cache and default to true in the code, so an
  unfetched flag reads on. The fallback does not apply to gateway sessions; nothing for Surprises.
- (h) differs from the spec's reading: a plain interrupt after a Send now does NOT stop the command the engine moved.
  The Stop ends the message's turn (aborted_streaming, "[Request interrupted by user]", the message's lifecycle
  `cancelled`), the moved command keeps running to its end, and its completion starts a turn of the engine's own
  (2/2). The engine's `notePersonsStop` stops moved tasks only where `fw()` holds, which requires
  `CLAUDE_CODE_SESSION_ORIGIN === "claude_ai_chat"` (cli.pretty.js:526543, 612709-612712, 600851-600870); MAWS's
  sessions are not that.

Telling the endings apart (observation, then inference).
- Send now that moved a shell command (a), or a `now` frame that did (f): result subtype success, is_error false,
  terminal_reason aborted_tools; no interrupt marker; the call's tool_use_result carries backgroundedToDeliverMessage
  true (the text: "Command was moved to the background ... so that a message that arrived while it was running can
  reach you"). A Stop during a shell command (s0): result error_during_execution, is_error true, aborted_tools, the
  marker "[Request interrupted by user for tool use]", the call's non_execution_kind "user-rejected". These differ on
  the wire.
- Send now with nothing movable (c) and a Stop while writing (c0): identical from the response on (error_during_
  execution, aborted_streaming, "[Request interrupted by user]"). Only the control response differs (`send_now:
  "stopped"`), so the host's own record of having sent the request is the only tell, as the spec's fallback for (c)
  says.
- `now` while writing (f-text): success / aborted_streaming and no marker, which differs from a Stop.
- In every case that ends a turn, the first prompt's command_lifecycle reads `cancelled` after `started`.
Inference: MAWS today reads aborted_tools and aborted_streaming as the person's stop (src/services/sessions/digest.ts,
around line 184), so without new code the (a) ending would read "You stopped". The host already knows it sent the
send_now and got `delivering`, which covers (a), (c) and (d) alike; the wire features above are a second, independent
check for (a) and (f).

Where the engine differs from the spec's reading of the source.
1. "Reads the message in the same turn" (the table's Send now cell, "How Send now reaches the engine", A3): true for a
   foreground Agent call (b) and after background_tasks (e); false for a shell command under send_now (a) and under a
   `now` frame (f), where a `result` (success / aborted_tools) comes first and the message is the next turn. The command
   is still moved and still survives, so the design's intent holds; what changes is that MAWS sees a turn end it must
   name ("Ended for your message" rather than "You stopped") in the `delivering` case too, not only in `stopped`.
2. (d) answers `delivering`, not `stopped`, while the turn does end and the message runs next.
3. background_tasks answers `{backgrounded: false}` for a shell command until the engine registers it as a task, about
   3.6 to 4.5 s after the tool_use frame in these runs (the permission check and the spawn come first); a request after
   the call's `system/task_started` frame succeeds. The spec's three seconds from the call's start falls before that
   point, so the first request is usually refused and the retry does the work. A trigger on task_started for the
   call's tool_use_id would move it at the first try.
4. A Stop after a Send now does not stop the moved command for a MAWS session (h); the U4 sentence "when the person
   presses Stop after a Send now, the engine also stops the command it had moved for that delivery (`notePersonsStop`
   ...)" does not hold on this wire. The command runs on, and its completion starts a turn by itself.
5. Charter §4.2's `now` sentence (measured on 2.1.283) no longer holds during a shell command or an Agent call: `now`
   moves the call and keeps it alive (f, f-agent); only while the model writes does it end the turn (f-text), and then
   as success / aborted_streaming.

Bearing on other parts of the spec.
- Subagents run in the background by default on 2.1.322 (b's first take; the system prompt's sentence), so "a running
  subagent call" that a message waits behind is the rarer run_in_background: false case; the common case is the main
  loop's own model request, where send_now answers `stopped` and cuts the reply (b-asyncdefault).
- A moved shell command's completion starts a turn the engine runs by itself (a-seeded-1 system/init 210 with no user
  uuid, result 248; h-seeded-2 68-137): a turn MAWS did not start, relevant to how U3 draws arrivals and to the "N
  turns" bookkeeping.
- After MAWS's plain Stop with `cancel_queued: false`, a waiting `next` message runs as the next turn (s0 45, c0 142);
  MAWS's holdAll before the Stop is what keeps it held (session.ts interrupt()), unchanged.
- The cut turn's prompt reads `cancelled` after `started` (every turn-ending case); MAWS must not read that as a message
  that was never sent.
- Haiku (claude-haiku-5-5) holds auto mode on 2.1.322 through the gateway (system/init permissionMode "auto", the
  classifier's accept on every shell call); findings-pass2.md's "Haiku cannot hold auto mode" was 2.1.283.
- Whether `now` can replace the two steps for an after-the-turn row (f's question): on the wire `now` does what send_now
  does in every case measured (moves a shell or Agent call, ends the turn only when nothing can move), with a more
  distinguishable ending while writing (f-text), but it returns no `delivering` / `stopped` answer and keeps the
  ending of (a). Promoting at `now` therefore serves an after-the-turn row as well as promote-then-send_now; the choice
  is the design's.

Not provoked. A send_now that the engine answers `nothing_waiting` (the message already read) was not attempted.
Background agents' moves were not timed against a three-second rule. No run on the direct route (it cannot
authenticate on this VM).
