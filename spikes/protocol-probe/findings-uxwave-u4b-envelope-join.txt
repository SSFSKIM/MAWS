UX wave U4b, probes 2: an ask's answer envelope and a person's prompt both waiting at the engine's next step, on
engine 2.1.322, on MAWS's own wire and environment (asked by the architect 2026-11-15; the prompt-only recordings it
compares with are u4p3-end2-*, u4p3-end3-1, u4b-two-*, u4b-two-late-* and u4p3-promote-*, findings-uxwave-u4-send-now-

Verdict.
  Joined or not, per case (14 recordings, every case twice, the same each time):
    1. turn ends by itself, envelope first:            JOINED 2/2
    2. turn ends by itself, prompt first:              JOINED 2/2
    3. Send now early (u4b-two's timing), envelope first: JOINED 2/2; prompt first: JOINED 2/2
    4. control, both written once the call is a task (u4b-two-late's timing), envelope first: NOT joined 2/2;
       prompt first: NOT joined 2/2
    5. case 1 with the multi-line variant:             JOINED 2/2
  The engine treats the envelope exactly as it treats a prompt. Every case joins or splits as the prompt-only
  recordings did, and nothing in the envelope (its length, its lines, its fenced block, its first line) changes that.
  The joined form, byte for byte (each joined replay and each joined transcript user line equals the two members'
  texts joined by "\n", compared exactly):
    - Order: the order written. The first-written member comes first, whichever it is.
    - Separator: exactly one "\n" between the members. Nothing is added, trimmed or escaped.
    - Each member's bytes are intact: the envelope's em dash, its fenced block, the multi-line variant's escaped
      "\n" inside JSON strings, and its `note:` line.
    - Envelope first: the closing fence "```" is followed by exactly one "\n", then the prompt's first byte.
      Envelope last: the text ends with the fence, as the envelope alone does.
    - The joined message carries the LAST-written member's uuid (its replay, isReplay true, and the transcript's one
      user line under that uuid). The first member also has its own replay holding only its own text, under its own
      uuid, one frame earlier (seq n), and no transcript line. The joined replay comes at n+6, after the status
      `requesting` that names both uuids. Both members are `started` at consecutive seqs and `completed` at
      consecutive seqs.
  What differs from the prompt-only recordings: nothing on the engine's side. On MAWS's side: the joined row's text
  does not parse as an answer steer in either order (`parseAskSteer` null 10/10 joined recordings). Its tag must open
  the text (`^\[MAWS ask …\] `), which fails when the prompt is first. Its `json` block must end the text, which fails
  when the envelope is first. So the transcript model draws the joined row as one ordinary user bubble showing the
  envelope's raw text and JSON beside the prompt. In a session read from its file alone, the ask's answers are not
  recorded from it.

  The model (the normaliser's user.message events and the reducer's user rows):
    joined cases (10): the user.message events are MAWS's own writes of each member (out frames, E alone parses as

Inference, in U4b's terms.
  - Engine: an envelope and a prompt waiting together at `next` are delivered exactly as two prompts are. They join
    when the turn ends by itself or after the Send now cut, and stay apart at a tool boundary inside the turn. The
    joined message is the members' texts, in writing order, joined by one "\n", under the last uuid. The ruling
    "form b by the text" holds for an envelope member too.
  - MAWS: the joined row is a bubble showing the envelope's raw text. parseAskSteer does not read an envelope with
    anything before or after it, so derive's answersHeldAsk cannot hide it. In a live session (journal with MAWS's
    own write), reduce.ts:704 calls recordAskSteer on every non-synthetic user.message; the envelope's own out
    event parses, so the answers would be recorded when the ask's call is in the session (not exercised here). From
    a file alone (the transcript holds only the joined line) they would not be. Reading the joined text by its
    members (split on the known member texts, or find the `[MAWS ask` line and the fence that closes its block)
    would fix both; that is U4b's call.
