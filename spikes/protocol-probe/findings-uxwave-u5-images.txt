UX wave U5, P1: several images in one message (docs/doperpowers/specs/2026-11-12-ux-wave/U5-review-comments-source-control.md,
Probes and checks, P1; law 6 of the root spec; it serves UC-5's pass of several comments with their screenshots;
2026-11-12)

Question. Does engine 2.1.322 keep a message of several image blocks and one text block when it is sent idle, sent as a
steer during a turn, and given as a fork's first message? The spec's branch: if a steer drops or reorders images, a pass
sent during a turn carries the first screenshot only and the card says so before sending.

Verdict: kept, in all three. Each message of three images and one text reached the model with the three images in the
order sent, in 3 of 3 runs of each case. The model named the three colours in the order sent in 10 of the 12
answers; of the other two, one named the earlier message's colours and one ended its turn before the colour line, and
in both the request it answered held the steer's images in order (model slips, not the wire). So the
branch "a pass sent during a turn carries the first screenshot only" is not needed. Confidence: high.

Method. scenarios/pass3/uxwave-p1-images.mjs, run three times on devcloud VM dc-uxprobe-dc94 through vm-run.sh
(-e UXP1_RUN=1..3), engine 2.1.322 (system/init claude_code_version, every fixture), routed through the gateway (spawn
row routed: true), model haiku (claude-haiku-5-5; the question is about the wire, not the model). Launch line, as MAWS
launches (src/engine-host/launch.ts, checked against the product code): the harness's line, --forward-subagent-text
--replay-user-messages --include-hook-events, --setting-sources user,project,local, no --strict-mcp-config,
--settings {"dialogExpiry":"never"}, --model haiku, --permission-mode default, --session-id; the side thread adds
--resume <parent> --fork-session (MAWS's side-thread launch). Environment: vm-run.sh's plus buildEnvironment's constants
(CLAUDE_CODE_FORK_SUBAGENT, CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING, CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS,
ENABLE_TOOL_SEARCH, TERM=dumb, DISABLE_AUTOUPDATER). After initialize (MAWS's payload, probe-initialize.mjs) the probe
sends set_max_thinking_tokens {max_thinking_tokens: null, thinking_display: "summarized"}, as session.ts does before
any prompt. Differences from MAWS's launch, none bearing on the question: the probe serves no `maws` MCP server (so
neither MAWS's sdkMcpServers nor its --disallowedTools/--allowedTools pair); --max-budget-usd 0.40 is a probe guard; the
gateway token is the VM's, not MAWS's marker.
Images: three 16x16 solid PNGs generated by the scenario (red, green, blue). Messages are MAWS's composer order
(serialize.ts): the images, then the text. Cases, in one parent session and its side thread:
  idle         [red, green, blue, text], priority now (queue.ts's default for a send)
  steer-next   a Bash turn (sleep 15), then 4 s after its tool_use [blue, red, green, text] with priority next
               (the composer's Send during a turn)
  steer-now    the same with priority now and [green, blue, red, text]
  fork-first   --resume <parent> --fork-session --session-id <child>, first message [green, blue, red, text]
Read, per case: the user frame the engine replays (--replay-user-messages); the Messages API request the engine makes
(a loopback forwarder in front of vm-run.sh's gateway forward records each message's role and blocks: an image as which
of the three it is, a text by its first 200 characters; no headers); the engine's transcript (JSONL); the answer.
Fixtures: fixtures/uxwave/uxwave-p1-images-parent-<n>.jsonl and -fork-<n>.jsonl, n = 1..3; the `case` meta rows hold
each case's frames, requests and answers.

Observed (run 1 seqs; runs 2 and 3 the same in every respect but the answers noted).
  idle. Replayed user frame (seq 14, isReplay) [red, green, blue, text]. The request (api 1): the user message is two
    <system-reminder> texts, then red, green, blue, the text, then three texts the engine adds, "[Image: source:
    <tmp>/<session>/images/1.png]" (2.png, 3.png): it saves each image to disk and names it. Transcript: one user record
    [red, green, blue, text], and a user record of the three source lines. Answer "red, green, blue" (seq 82; 3/3).
  steer-next. Replayed (seq 112) [blue, red, green, text]. Delivered at the tool boundary: the next request (api 3) has
    the tool_result, then the steer as "The user sent a new message while you were working:\n<the text>", then blue,
    red, green. One result (seq 157) names both prompts' uuids. Transcript: an attachment record of type queued_command
    whose prompt is [blue, red, green, text] (commandMode prompt), not a user record. Answers "blue, red, green" in runs
    1 and 3; run 2 answered "red, green, blue" (the idle message's), with the steer's images in order in its request.
  steer-now. Replayed (seq 187) [green, blue, red, text]; delivered the same way (api 5); the running Bash was moved to
    the background (a task-notification user frame follows, seq 305) rather than the turn being ended; one result names
    both uuids. Transcript: a queued_command attachment as above. Answers end "green, blue, red" in runs 1 and 2; in run
    3 the turn ended while the backgrounded command still ran, before the colour line (a model choice, the request held
    the images in order).
  fork-first. Replayed (fork seq 13) [green, blue, red, text]; the request (api 8) carries the parent's context with all
    nine earlier images (the idle message's and both steers', from their queued_command records) and then the new
    message [green, blue, red, text] with its three source lines (its images saved as 4.png to 6.png in the child's own
    folder: the numbering continues the parent's). Transcript of the child: the parent's idle user record and its own.
    Answer "green, blue, red" (3/3).

Differs from what the spec reads, or bears on other parts.
  - A steer's text is not where MAWS put it: the engine moves it before the images and wraps it ("The user sent a new
    message while you were working:\n…"), so the model sees text, then images. The order of the images among
    themselves is kept. A steer's images are not saved to disk and get no "[Image: source: …]" line, unlike an idle
    message's or a fork's first message's.
  - A steer with images is stored in the JSONL as an attachment of type queued_command (prompt = the blocks as sent), not
    as a user record. Anything in MAWS that reads screenshots back from the transcript (the transcript's rows after a
    reload, a resume) must read that record too; a resumed or forked session does get those images in its context.
  - A `now` steer during a Bash call did not end the turn here: the engine moved the command to the background and folded
    the steer in at once (queue.ts's comment reads `now` as preempting the running turn).
