UX wave, landing U8d, probe P5 (the coordinator's, after P3's nested finding): where engine 2.1.322 writes the end of a
nested background agent N that outlives its parent P, with the session's process still running; and what happens to N
when P is stopped (docs/doperpowers/plans/2026-11-15-ux-wave-U8d-terminal-subagents.md, the DX4 parent rule and the
table's row "an agent ended, something under it still runs"; 2026-11-15, VM dc-uxwave5-26dc, branch ux-wave/U8d-probes)

Questions. (a) P launches N in the background and hands back at once; N then ends (a 20 s sleep, a one-word reply).
Where is N's end written: P's file (a task notification, a queue record, a result), the main transcript, N's own
file, N's meta (`finished: true`?), and when relative to N's last row? Does a failure differ? (b) P is stopped with
TaskStop while N runs: does N keep running, or end with P, and what is written for N?

Verdict.
  (a) N ends on its own and its end is written in THREE places (3 of 3 runs, 2 completing, 1 "failing"):
    - the MAIN transcript: a queue record `enqueue` <task-id>N</task-id> <status>completed</status> "Agent "uxw
      nested N" finished", with N's tool-use-id and output file. About 2 s later the same block is recorded as
      `operation: "remove"`. There is no dequeue and no user row in the main transcript for N.
    - P's file: N's hand-back as a peer `user` row ("Another Claude session sent a message while you were working"),
      then the task notification as an isMeta `user` row of origin task-notification, <status>completed</status>,
      about 2 s after N's end. N's end WAKES P: P's file gains assistant rows (P runs a new turn). P then ends again,
      and the main transcript gets a SECOND notification for P (enqueue, dequeue, user row, <status>completed</status>
      "Agent "uxw parent P" finished"). So P has two completion notifications under one task id.
    - the metas: N's meta gains `finished: true`, written in the same 100 ms as N's last rows (its SubagentHandback
      call and result) and the main transcript's enqueue. P's meta LOSES `finished` when N wakes P (rewritten without
      the key), and regains it when P ends again: P's meta history reads finished true, absent, true (r2 and the
      fail run), or true, absent, true, absent, true (r1).
    - Failure: N's command exited 3 and N reported FAILED. Nothing distinguishes that run: the notification says
      <status>completed</status> "Agent "uxw nested N" finished", and the meta has `finished: true` with the same keys.
      An agent's own judgement that its task failed is not an engine failure. An engine-side failure (an API error)
      gives <status>failed</status> (findings-uxwave-u8d-waited-agent.txt, p4-fail), and its meta is again only
      `finished: true`.
  (b) N KEEPS RUNNING when P is stopped (2 of 2). P's stop writes, in the main transcript, P's own `killed`
    notification (queue enqueue <status>killed</status> "Agent "uxw parent P" was stopped by Claude", dequeue, user
    row), and in P's file its in-flight Bash result "User rejected tool use" and the "[Request interrupted by user for
    tool use]" row. NOTHING is written for N at the stop: no row in P's file, none in the main transcript, no meta
    change. N's sleep process stayed alive (polled every 5 s: alive at each of 8 polls after the stop). N finished
    about 45 s later as in (a). Because its parent was stopped, N's hand-back and notification went to the MAIN
    transcript: a peer hand-back row, then the user row of origin task-notification <status>completed</status> "Agent
    "uxw nested N" finished", after an enqueue and a dequeue. N's meta got `finished: true`. P's meta was never
    rewritten (no `finished`, no `stoppedByUser`).
  So the shared vector's premise that N ends with a stopped parent is false on this engine. The design's new premise
  (it does not) holds.

Inference.
  - DX4's parent rule ("the parent has ended: `exited`, evidence `parent`") reads N as ended in both cases while N runs,
    for up to the rest of N's life. In both cases N's real end is in the rows: a completed notification in P's file
    and a queue record in the main transcript (a), or a notification in the main transcript (b). A rule that let the
    rows' later word (or the bridge's running) outrank the parent rule would read N correctly. In (a) the end is in
    P's file, which the design follows only "while the parent has a nested agent that has not ended". If the parent
    rule ends N, that follower stops and N's notification in P's file is not read. The main transcript's `enqueue`
    record (and its `remove` twin) for N would still be read by the main follower, if the ledger accepts a nested
    agent's id there.
  - P's waking gives P a second notification and moves its meta's `finished` off and on. A reader that takes a
    terminal word as final (DX4's "accepted residual", R7) keeps P ended while it runs that second turn.
  - Where N's notification lands depends on P's state: P's file when P had ended normally (P is woken), the main
    transcript when P was stopped.
