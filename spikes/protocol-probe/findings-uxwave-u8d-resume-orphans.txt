UX wave, landing U8d, probe P1 (and the coordinator's addition on shells): what engine 2.1.322 writes when a terminal
session is resumed after its process ended with background agents, or background shell commands, still running
(docs/doperpowers/plans/2026-11-15-ux-wave-U8d-terminal-subagents.md, "Probes to arrange" P1 and R9; it serves
"Engine facts" 10 and M4's scene of the gone terminal; 2026-11-15, VM dc-uxwave5-26dc, branch ux-wave/U8d-probes)

Question. A session's process ends while two agents launched in the background still run; the session is then resumed
in a terminal. What does the engine write to the main transcript for each orphan, and when: one block per agent or one
block naming both, with which <status>; or does it restart one under the same id; and does either meta change? The
same with one orphan; and with two (and one) background shell commands.

Verdict.
  - Two orphaned agents: ONE block naming both. It has two <task-id> elements, one <status>stopped</status>, no
    <tool-use-id> and no <output-file>, and a summary naming each agent with its id. It is written as a queue record
    (enqueue), then a dequeue, then a `user` row of origin task-notification (promptSource "system",
    queueTranscriptOnly true). It is written about 1 to 3.5 s after the resumed engine starts, before any prompt, and
    it opens no model turn. 4 of 4 runs: 2 resumed at once, 2 with the agents' files and metas set 72 h back first.
  - One orphaned agent: one block, one <task-id>, an <output-file>, no <tool-use-id>, <status>stopped</status>,
    "Background agent "…" didn't finish before the previous session ended", in the same three rows. 4 of 4 runs (2 at
    once, 2 with files 72 h old).
  - No restart under the same id in any run (0 of 8), including the four whose agent files were seconds old. In the
    terminal the resumed engine wrote nothing in any agent's file. No meta changed at the exit or at the resume.
  - So "Engine facts" 10 holds for the one-block form and the status word. Its "or it restarts the agent under the same
    id" did not happen on a terminal resume. Its "failed" did not either: the agent's file existed, so the word was
    stopped. The document's default for P1 (as the bundle reads) held. R9's gap is the common case, not a corner: every
    resume with two or more orphaned agents gave one block, so a reader of the first <task-id> leaves every other orphan
    `running` until the process goes.
  - Shells, two orphaned: ONE block with three <task-id> elements: the two shells' ids and `__orphan_summary__:shell`,
    which is no task. The block's <note> says ids beginning "__orphan_summary" are internal scan markers. It has
    <status>stopped</status>, no <tool-use-id>, and a summary "2 background shell command tasks didn't finish before
    the previous session ended. Task ids: <a>, <b>." It is written as the same three rows (enqueue, dequeue, user row).
    No per-shell record is written at the resume. 2 of 2 runs. No `__orphan_summary_live__:` marker appeared (none of
    the shells was still alive).
  - Shells, one orphaned: one block, the shell's <task-id> and its <tool-use-id>, <status>stopped</status>, "Background
    shell command didn't finish before the previous session ended". 2 of 2 runs.
  - At the process end itself (SIGTERM), each running background shell got a per-shell queue record: <status>killed
    </status>, "Background command "…" was stopped", with its <tool-use-id> and <output-file>, enqueue only, no
    dequeue and no user row. 4 of 4 runs, 6 shells. The resume's scan still counted those shells as orphans. Agents get
    no such record at the exit (P3).

Inference.
  - The block an agent orphan gets on a terminal resume is the bundle's grouped form (B:941409-941416: the `stopped`
    group of agents that can be continued, emitted by `Ti` when it has more than one member, by `tt` for one). The
    restart branch needs a resume callback (B:941398 tests `s !== void 0`). Of the callers of the restore
    (`Yzt`), B:610283 (the headless print path), B:1205272 and B:1205651 pass `undefined` for it, and B:1205647 passes
    `this.resumeOrphanedAgents`. Which of them a terminal resume takes was not established from the source; on the
    terminal no restart happened in 8 of 8 runs.
  - For M4's scene of the gone terminal: after a resume, the rows give each orphan `stopped`. For two or more agents
    that is one block. For the ledger's jobs half, the shell block's ids include `__orphan_summary__:shell`, which
    names no job, and a shell's first word at the exit is `killed` (queue record), which DX4's ledger reads as an end
    before any resume.
