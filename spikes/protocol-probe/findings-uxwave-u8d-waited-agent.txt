UX wave, landing U8d, probe P4: what the main transcript's result row carries for an agent the main loop waits for,
when it completes, fails and is interrupted (docs/doperpowers/plans/2026-11-15-ux-wave-U8d-terminal-subagents.md,
"Probes to arrange" P4; it serves "Engine facts" 5 and the ledger's reading of an Agent call's result; 2026-11-15, VM
dc-uxwave5-26dc, branch ux-wave/U8d-probes)

Question. An agent the main loop waits for completes, fails, and is interrupted by the person. What does each result
row in the main transcript carry (`toolUseResult.status`, `is_error`)?

Verdict.
  - In a TERMINAL session, as the owner's sessions are configured on 2.1.322 (the owner's feature-gate cache), the
    main loop never waits for an agent. Every Agent call is launched in the background, even with
    `run_in_background` set to false. The tool's own text says "Subagents run in the background; you'll be notified
    when one completes". The call's result is `status: "async_launched"`, the meta has `requestShape: "background"`,
    and the end comes as a task notification. 5 of 5 terminal runs, plus 2 of 2 nested calls in P3. So on this
    landing's route, P4's case does not arise. A terminal agent's outcome is always read from its notification.
    That notification's words were recorded: `completed` (2 of 2), and `failed` for an agent whose API call failed
    (1 of 1). This is the first `failed` for an AGENT recorded on disk; "Engine facts" 4 had only `completed`.
    Pressing Escape while a background agent ran wrote nothing and did not stop it (2 of 2).
  - In PRINT mode (`claude -p`, the same engine and gate cache) the tool says "Subagents run in the background by
    default". The model passed `run_in_background: false` (a boolean), and the loop waited (meta `requestShape:
    "foreground"`). The three result rows:
      completed: `toolUseResult.status: "completed"`, no `is_error` (2 of 2). The ledger reads `completed`. Held.
      failed (an API error inside the agent): `is_error: true`, and `toolUseResult` is a STRING, "Error: Agent
        terminated early due to an API error: …" (2 of 2). The ledger reads an error, so "finished with errors".
        Held.
      interrupted (SIGINT to the print-mode engine while the agent ran its command): `is_error: true`,
        `toolUseResult: "User rejected tool use"`, content "The user doesn't want to proceed with this tool use. The
        tool use was rejected …". It is followed by a `user` row "[Request interrupted by user for tool use]" (2 of
        2). Nothing in the result row says "interrupted" or "stopped"; it is an error row. The ledger's rule
        therefore reads an interrupted agent as `error`, so "finished with errors" (danger colour), not "stopped".
        This is the case the document asked to have reported.
  - Metas: a completed or failed agent's meta is rewritten with `finished: true`, in both modes, at the end. A failure
    is not told apart in the meta: the fields are the same as for a completion. An interrupted waited-for agent's
    meta is NOT rewritten: no `finished`, no `stoppedByUser`. That `stoppedByUser` key ("Engine facts" 11, B:378462)
    appeared in no meta in any run of P1 to P4.

Inference.
  - For U8d nothing changes in code: on a terminal session every agent is a background one, and its end is a
    notification with `completed`, `failed`, or (P2) `killed`. The document's "Where the source cannot know" 1 (an
    agent the main loop waits for, known only from the bridge) does not arise in the owner's terminal sessions on
    2.1.322. It can arise in print mode, and in a configuration whose gate allows foreground agents.
  - Where a waited-for agent exists (print mode, other gates), an interrupted agent reads "finished with errors" by the
    ledger's rule. Telling it apart would take the row's text ("User rejected tool use" / the "[Request interrupted by
    user for tool use]" row after it). That is sminos's rule to change, not the port's (R10).
