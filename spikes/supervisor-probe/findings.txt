Q1 — The engine when its parent dies
------------------------------------
VERDICT: the engine does NOT exit on stdin EOF mid-turn. It finishes the turn it is in (tools keep running, the model is
called again, the transcript is written in full), and only then exits through its ordinary end-of-input path. Here that
was 21.9 s after its host died, bounded by nothing but the length of the turn. THE ORPHAN SWEEP IS LOAD-BEARING, not
hygiene.

Setup (q1-engine-parent-death.mjs, variant parent-killed). A wrapper Node process stands in for the host. It spawns the
engine as src/engine-host/transport.ts does: `detached: true`, stdio ['pipe','pipe','pipe']. The launch line is
launch.ts's ENGINE_FLAGS plus `--model haiku --permission-mode default --session-id <uuid> --max-budget-usd 0.30
--settings {"dialogExpiry":"never"} --debug-file <scratch>`. The environment is buildEnvironment's gateway constants
(CLAUDE_CODE_ENTRYPOINT=sdk-ts, relay URL and marker token, ENABLE_TOOL_SEARCH, the C12/E1 variables, TERM=dumb,
DISABLE_AUTOUPDATER=1) over the base keys only. CLAUDE_CONFIG_DIR is a scratch home seeded by p1-common's scratchRun
(settings.json {}, .claude.json with onboarding done and the scratch repository trusted), and assertScratch passed. The
wrapper sends MAWS's initialize (probeInitialize) and one turn: "Run exactly this shell command with the Bash tool:
sleep 20 && echo q1-done; then reply: finished". 2.1.291 ran `sleep` and `echo` without a can_use_tool request. Once
`sleep 20` showed under the engine in ps, the probe waited 1 s and SIGKILLed the wrapper, then sampled every 100 ms.

Timeline (ms after the SIGKILL; results/q1-parent-killed.json):
  -3794  engine spawned (pid 74108, PPID = wrapper 74097, PGID 74108, STAT Ss: its own session and group)
     -0  tool running: /bin/zsh -c ... (pid 74988, PGID 74988: the Bash tool's shell has its own process group)
         -> sleep 20 (pid 74996, PGID 74988)
    102  engine alive, PPID 1 (reparented to launchd), registry row present, sleep running
  18835  sleep 20 finished (the tool completed normally after its host was dead)
         the engine then made the turn's second model request (debug log: "[API REQUEST] /v1/messages", first byte
         508 ms; "[engine] turn 1 end (turns=2 ... cost=$0.0173 ... stop=end_turn)"), i.e. it spent money after the
         host died
  21736  registry row sessions/74108.json unlinked
  21894  engine gone from ps
  The debug log's last lines are the orderly shutdown: "[uds-messaging] Shutting down", "LSP server manager shut down
  successfully", the telemetry flush, "Cleaned up session snapshot", "session.end". Stderr was empty. Writing stream
  events, the result frame and session_state_changed into the dead stdout pipe did not crash it (no EPIPE exit).

Exit code: in the real case the engine's status goes to launchd, which reaps it, so it cannot be read. The
idle-pipes-closed variant reads the end-of-input exit directly at no model cost (results/q1-idle-pipes-closed.json).
There the engine is initialized, no prompt is sent, and the wrapper (alive, still the parent) destroys the engine's stdin
and its read end of stdout. Result: exit code 0, signal null. The registry row was gone at the first 100 ms sample and the
process by 255 ms. The parent-killed run ended through the same shutdown sequence, so its code was almost certainly 0
too (inferred, not observed).

Transcript on disk: it ends cleanly. 32 lines, all parse, a final newline. The tool_use has its tool_result ("q1-done",
is_error false), and the final assistant text "finished" comes after it, followed by the engine's `last-prompt` and
`cost-state` records. The whole turn is on disk, including everything after the host's death. MAWS's own journal for
such a launch would stop at the host's death; the engine's transcript does not.

Why this makes the sweep load-bearing:
  - Inferred from the timeline, not traced in the engine's code: EOF takes effect only when the engine next waits for
    input, i.e. after the turn ends. A turn can run for minutes or
    hours (an agentic task, a long build, subagents), and until it ends the orphan keeps running tools in the owner's
    repository and keeps spending, with no host to show or stop it.
  - Not probed (it would need more paid runs): any control request the engine sends after the host died. That covers
    can_use_tool for a tool that needs permission, mcp_message to the `maws` SDK server (MAWS declares it at every
    launch; this probe's launch omitted --mcp-config and declared no SDK server), hook callbacks, elicitation and
    request_user_dialog. Each goes into a dead pipe, and no answer can ever come. Unless the engine times such a
    request out, the process would wait there indefinitely. The sweep is the only thing that ends those cases.
  - Hygiene still holds where the design expected it: an idle engine (no turn) exits with code 0 within ~0.1-0.25 s of
    its pipes closing and unlinks its registry row, so after a supervisor crash only rows that were mid-turn linger.
Consequences for M2 (§Design 1 "The orphan ledger and sweep"):
  - The Bash tool's shell runs in its own process group (PGID 74988, not the engine's 74108). A SIGKILL to the engine,
    or to the engine's group (-pid, as transport.ts's signalGroup does), does not reach the tool's processes. Not
    probed: whether the engine's SIGTERM handler stops its tool groups before exiting. The sweep's SIGTERM-first order
    is the right one. A SIGKILL fallback may leave tool processes orphaned, and M2 should test that case or record it.
  - The registry row carries the engine's `procStart` (see Q5). The sweep and the live-ledger code can check against
    the same notion of process identity the engine itself records.
  - The sweep runs only when a successor supervisor starts. If the app has crashed for good (C1's ladder ended in
    `crashed`), or no app is open, no successor starts, and nothing sweeps: the orphans run until their turns end, or
    indefinitely in the waiting cases above.
  - Between a supervisor's crash and the successor's sweep, an orphan's live registry row (entrypoint sdk-ts, its pid
    no longer in any process table) reads as foreign-live under C4's holder rule and D-12. A resume of that session in
    this window is refused as held elsewhere, until the sweep or the turn's end removes the row.

Q4 — Socket path limit
----------------------
VERDICT: on this Mac a Unix socket path of up to 104 bytes binds and connects under both runtimes. At 105 bytes and above,
the supervisor's runtime (Electron 44.4.5 / Node 24.21.0) refuses both listen and connect with EINVAL, which is a safe and
loud failure. Plain Node 22.23.2 instead silently TRUNCATES the path to 104 bytes: the bind succeeds at the truncated
name, and a connect to the long path reaches it. §Design 1's rule ("at most 103 bytes, else the $TMPDIR fallback") is
safe and one byte conservative.

results/q4.json (dir under os.tmpdir(), 71 bytes; each path written as dir/s<x...>.sock):
  bytes   node v22.23.2                                 electron 44.4.5 as node v24.21.0
  100     bind ok, name intact, connect ok              bind ok, name intact, connect ok
  103     bind ok, name intact, connect ok              bind ok, name intact, connect ok
  104     bind ok, name intact, connect ok              bind ok, name intact, connect ok
  105     bind "ok" but file name is 104 bytes,          listen EINVAL, no file; connect EINVAL
          connect to the 105-byte path ok (truncated)
  110     same as 105 (104-byte file)                    listen EINVAL, no file; connect EINVAL
Consequence: tests that bind sockets under plain Node (the unit suite runs on the PATH Node) must keep paths at 103 bytes
or less, or a too-long path will pass there and fail in the supervisor. The lock's recorded socketPath plus the 103-byte
rule covers production.

Findings beside the verdict:
  - The engine's SIGTERM handler stops its tool's process group. M0 Q1 left this open: the Bash tool's shell runs in its
    own group, so a group kill of the engine does not reach it. Here the sweep's SIGTERM to the engine pid took `sleep
    20` (pid 17662, PGID 17658, a different group from the engine's) down with it. So the sweep's SIGTERM-first order
    leaves no tool orphan in the common case. Only the SIGKILL fallback, after a 5 s grace, could.

    from the state file, in state "released" (no recovery transition; nothing was re-sent).

    session: <id>". This is the probe's gap, not a defect. A session with no stream answers from C4's diskEvents

    (`--resume`), and that is what Q7 proves.

    lasted, here, from the kill to the sweep's end: about 5.3 s, sweep included. The resume came after it and was not
